# malloc/free + buffer overflow: ทำไม security = เรื่อง memory (ตอนที่ 16) — CS Fundamentals: จาก 0 สู่พื้นฐานที่แท้จริง

ตอนที่แล้ว (ตอนที่ 15) เราปิดท้ายด้วยสองคำถามค้างไว้:

1. ถ้า heap ต้อง "คืนเอง" แล้วการ **ลืมคืน** (memory leak = จองหน่วยความจำแล้วไม่คืน สะสมจนเปลือง) หรือ **คืนแล้วใช้ต่อ** (use-after-free = ใช้หน่วยความจำที่คืนไปแล้ว) มันอันตรายแค่ไหนกันแน่
2. ทำไม **security** (ความปลอดภัยของระบบ) ถึงผูกกับเรื่องหน่วยความจำ — **buffer overflow** (เขียนข้อมูลล้นขอบเขตที่จองไว้) ตัวร้ายที่ทำให้แฮกเกอร์ยึดเครื่องได้คืออะไร และมันทำงานยังไง

วันนี้เราจะตอบทั้งสองคำถามด้วยการ "ดูของจริง" เหมือนทุกตอนที่ผ่านมา — ทุกโปรแกรมข้างล่างคอมไพล์และรันจริงบนเครื่องเรา (Linux 64 บิต aarch64, GCC 14.2.0) และผลลัพธ์ที่เห็นคือผลรันจริง ไม่ใช่สิ่งที่เดาขึ้นมา

> ก่อนเริ่ม ขอย้ำศัพท์สามตัวที่ใช้ซ้ำตลอดบทนี้: **malloc** (memory allocate = ฟังก์ชันจองหน่วยความจำจาก heap) · **free** (ฟังก์ชันคืนหน่วยความจำกลับ heap) · **buffer** (บัฟเฟอร์ = พื้นที่เก็บข้อมูลชั่วคราว มักเป็น array ขนาดจำกัด) · **overflow** (ล้น = เขียนข้อมูลเกินขอบเขตที่จองไว้)

## 1. เปิดฝา malloc ดูข้างใน: จริง ๆ แล้วเรา "ได้" มากกว่าที่ "ขอ" (ภาพที่ 1)

ก่อนจะพูดเรื่องบั๊ก เราต้องรู้ก่อนว่า `malloc` (ที่เราใช้จอง heap มาหลายตอนแล้ว) จริง ๆ แล้วให้อะไรเรากลับมาบ้าง — เพราะความเข้าใจผิดตรงนี้เองคือรากของบั๊กหลายชนิด

เขียนโปรแกรมแรก `malloc_blocks.c` ไล่ดูห้าประเด็น (โปรแกรมเต็มอยู่ใน `course/code/ep16/malloc_blocks.c`):

```c
/* ... ส่วนบนตัดออก: #include, ฟังก์ชัน row() ที่พิมพ์ "ขอเท่าไร -> ได้จริงเท่าไร" ... */

int main(void)
{
    printf("=== 1) ขนาดที่ \"ขอ\" กับขนาดที่ \"ได้จริง\" ไม่เท่ากัน ===\n");
    size_t wanted[] = { 1, 8, 16, 24, 25, 40, 41, 100 };
    void *keep[sizeof wanted / sizeof wanted[0]];
    for (size_t i = 0; i < sizeof wanted / sizeof wanted[0]; i++) {
        keep[i] = malloc(wanted[i]);
        row("malloc", keep[i], wanted[i]);   /* พิมพ์ address + ขนาดจริงที่ได้ */
    }
    /* ... free หมด, แล้วต่อข้อ 2) free แล้วจองใหม่ได้ที่เดิม, ข้อ 3) malloc vs calloc,
           ข้อ 4) realloc ย้ายที่, ข้อ 5) กรณีขอบ malloc(0)/free(NULL)/malloc(SIZE_MAX) ... */
}
```

> ศัพท์ใหม่ในโค้ดนี้: `size_t` = ชนิดตัวเลขใช้เก็บ "ขนาด" (หน่วยไบต์) · `malloc_usable_size(p)` = ฟังก์ชันเสริมของ glibc (ชุดไลบรารีมาตรฐานของ Linux) ที่ถามว่า "ก้อนที่ได้มานี้ใช้ได้จริงกี่ไบต์" — ตัวนี้ไม่มีบน macOS/Windows เป็นความสามารถเฉพาะ Linux · `SIZE_MAX` = ตัวเลขมากสุดที่ `size_t` เก็บได้

รัน (`gcc -std=c17 -Wall -Wextra -Wpedantic -o malloc_blocks malloc_blocks.c && ./malloc_blocks`) ได้ผล:

เห็นอะไร 3 ข้อ:

1. **ได้มากกว่าที่ขอเสมอ** — ขอ 1 ไบต์ แต่ได้ 24 ไบต์, ขอ 25 ได้ 40, ขอ 41 ได้ 56, ขอ 100 ได้ 104 ตัวจัดหน่วยความจำ (memory allocator = โค้ดที่คอยแจก/เก็บคืนก้อนหน่วยความจำใน heap) ปัดขนาดขึ้นเป็น "ช่องมาตรฐาน" ของมันเสมอ เพราะต้องเผื่อที่ไว้เก็บข้อมูลของตัวเอง (หัวก้อน ที่จดว่า "ก้อนนี้ใหญ่เท่าไร, ก้อนถัดไปอยู่ไหน") บวกกับเศษที่เหลือจากการปัด
2. **ที่อยู่หาร 16 ลงตัวเสมอ** — ทุก address ลงท้ายด้วย `...b0`/`...d0`/`...f0` (เลขฐานสิบหก) เพราะตัวจัดหน่วยความจำ "จัดเรียง" (align = ปรับตำแหน่งให้ตรงกรอบ) ก้อนให้ตรงกับกรอบ 16 ไบต์ เพื่อให้ CPU อ่าน/เขียนข้อมูลได้เร็วที่สุด (CPU หลายรุ่นอ่านข้อมูลช้า ถ้าข้อมูลไม่ตรงกรอบ และบางรุ่นถึงกับไม่ยอมอ่านเลย)
3. **พื้นที่ส่วนเกินที่ได้มา คือ "กับดัก"** — ถ้าเราเผลอเขียน 100 ไบต์ลงไปในก้อนที่ "ขอแค่ 1 ไบต์" โปรแกรมจะ**ไม่พัง** เพราะมันได้ที่มา 24 ไบต์แล้ว — นี่คือเหตุผลที่บั๊กแบบ "เขียนเกิน" มักไม่โผล่ทันที แต่ซ่อนตัวรอวันระเบิด เรื่องนี้จะกลับมาสำคัญมากในหัวข้อ buffer overflow

ต่อด้วยประเด็นที่เหลือของ `malloc_blocks.c` — ดูเฉพาะส่วนที่ "เซอร์ไพรส์" คนเรียนใหม่ (ผลรันจริงทั้งหมด):

```
=== 2) คืนแล้วจองใหม่ขนาดเดิม: ได้ช่องเดิมกลับมา ===
  free(b) แล้ว malloc(24) อีกครั้ง: d=0x5555c88b92f0 -> ได้ที่เดิมเป๊ะ

=== 3) malloc ไม่ล้างค่าให้ · calloc ล้างให้ (ตั้งศูนย์) ===
  malloc(8) ให้มา 3 ไบต์แรก: ed 97 0c · ทั้งก้อนเป็นศูนย์: ไม่ใช่
  calloc(8,1) ให้มา 3 ไบต์แรก: 00 00 00 · ทั้งก้อนเป็นศูนย์: ใช่

=== 4) realloc: ขยายก้อนเดิม (บางครั้งต้อง "ย้ายที่") ===
  ขยาย 32 -> 4096 ไบต์: 0x5555c88b9360 -> 0x5555c88b9440 (ย้ายที่) · ข้อมูลเดิมยังอยู่: อยู่ครบ

=== 5) กรณีขอบ: malloc(0), free(NULL), จองเกินกว่าที่ระบบให้ได้ ===
  malloc(0) = ได้ pointer มา (ถ้าค่าที่ได้ไม่ใช่ NULL ต้องคืนด้วย free)
  free(NULL) ผ่านไปได้ (ปลอดภัย ไม่ทำอะไร)
  malloc(SIZE_MAX) = (nil) · errno = 12 (Cannot allocate memory)
  -> นี่คือเหตุผลเดียวที่ต้องเช็ค NULL: ก้อนใหญ่ ๆ ที่ระบบปฏิเสธจะได้ NULL ไม่ใช่พังทันที
```

อ่านจุดสำคัญ:

- **คืนแล้วจองใหม่ ได้ที่เดิม** — ตัวจัดหน่วยความจำเก็บช่องที่เพิ่งว่างไว้ใน "รายการช่องว่าง" แล้วหยิบมาใช้ซ้ำก่อนเสมอ (เร็ว และลดการแตกกระจายของหน่วยความจำ) นี่คือกลไกเดียวกับที่ทำให้ use-after-free อันตราย (หัวข้อ 3)
- **`malloc` ไม่ล้างค่าให้ แต่ `calloc` ล้างให้** — `malloc(8)` ให้ค่าเดิม ๆ กลับมา (ในที่นี้เป็น `ed 97 0c` = ค่าขยะจากช่องนั้นที่เคยถูกใช้มาก่อน — ตัวเลขนี้เปลี่ยนทุกครั้งที่รัน อย่ายึดค่า) ส่วน `calloc(8, 1)` ตั้งศูนย์ให้ทุกไบต์ — ถ้าโค้ดเราหวังว่าหน่วยความจำใหม่ "ว่างเปล่าเป็นศูนย์" แต่ดันใช้ `malloc` นี่คือบั๊กรอวัน (อ่านค่าขยะก่อนเขียน) · `calloc` (clear-allocate = จองพร้อมล้าง) จึงเป็นตัวเลือกปลอดภัยเมื่อเราจะอ่านก่อนเขียน
- **`realloc` ย้ายที่ได้** — ขยาย 32 → 4096 ไบต์ มัน**ย้าย**ข้อมูลไปไว้ที่ใหม่ (address เปลี่ยนจาก `...9360` เป็น `...9440`) แต่คัดลอกข้อมูลเดิมไปให้ครบ — ประเด็นคือต้อง**รับ pointer ตัวใหม่**ที่มันคืนกลับมา ไม่ใช่ใช้ pointer ตัวเก่าต่อ (และถ้า `realloc` ล้มเหลว มันคืน `NULL` แต่ก้อนเก่ายังอยู่ ต้องคืนเอง)
- **`malloc(0)` และ `free(NULL)` ถูกต้องตามมาตรฐาน** — ได้ pointer มา (หรือ `NULL` ก็ได้ ขึ้นกับระบบ) และ `free(NULL)` ทำอะไรก็ไม่เกิด ไม่ต้องกันเอาไว้
- **เหตุผลเดียวที่ต้องเช็ค `NULL`** — `malloc` ไม่ได้ "พังทันที" ตอนขอเยอะเกิน มัน**คืน `NULL`** (ตัวชี้ว่างเปล่า — สังเกตว่า glibc พิมพ์ `NULL` เป็นคำว่า `(nil)` ความหมายเดียวกัน) พร้อมตั้ง `errno` (รหัสบอกสาเหตุข้อผิดพลาดของระบบ) ให้ — ถ้าเราไม่เช็ค `NULL` แล้วเขียนข้อมูลลงไป จะกลายเป็น "เขียนผ่านตัวชี้ว่าง" = พังแบบไม่มีข้อความ

> **หมายเหตุ** ขนาดจริงที่ `malloc` ให้ (24/40/56/104 ไบต์) เป็นพฤติกรรมของ **glibc** (ไลบรารีมาตรฐานของ Linux) บนเครื่องนี้ — ระบบอื่นหรือไลบรารีอื่น (เช่น macOS) จะปัดต่างกัน แต่หลักการ "ได้มากกว่าที่ขอ + ปัดให้ตรงกรอบ + เก็บหัวก้อนไว้ข้าง ๆ" เป็นจริงทุกที่

## 2. memory leak: จองแล้ว "ลืมคืน" หน่วยความจำหายไปเรื่อย ๆ (ภาพที่ 2)

กลับมาที่คำถามค้างข้อแรก: ลืมคืนแล้วเป็นไง? เขียน `leak_demo.c` ให้เห็นชัด ๆ (โปรแกรมเต็มอยู่ใน `course/code/ep16/leak_demo.c`):

```c
#define BLOCK_BYTES (1024 * 1024) /* 1 เมกะไบต์ */
#define ROUNDS 8

int main(void)
{
    long start = vm_rss_kb();   /* vm_rss_kb() = อ่าน "VmRSS" จาก /proc/self/status
                                    = หน่วยความจำจริง (RAM) ที่โปรเซสนี้ใช้อยู่ */

    printf("=== 1) จอง 8 ก้อน ก้อนละ 1 เมกะไบต์ แล้ว \"ลืมคืน\" ===\n");
    for (int i = 1; i <= ROUNDS; i++) {
        char *p = malloc(BLOCK_BYTES);
        touch(p, i);            /* เขียนทับทั้งก้อน เพื่อบังคับให้ระบบจ่าย RAM จริง */
        /* ตั้งใจไม่เขียน free(p) — ตัวชี้ p หายไปตอนจบรอบ หน่วยความจำก้อนนี้ไม่มีใครคืนได้อีก */
        ...
    }

    printf("=== 2) จองเท่ากันเป๊ะ แต่คืนทุกก้อน ===\n");
    for (int i = 1; i <= ROUNDS; i++) {
        char *p = malloc(BLOCK_BYTES);
        touch(p, i);
        free(p);                /* ต่างกันแค่บรรทัดนี้ */
        ...
    }
}
```

> ศัพท์ใหม่: **โปรเซส** (process = โปรแกรมที่กำลังรันอยู่หนึ่งตัว) · **RAM** (หน่วยความจำจริงของเครื่อง) · `VmRSS` = ค่าที่ระบบปฏิบัติการจดไว้ว่า "โปรเซสนี้ใช้ RAM จริงไปกี่กิโลไบต์" — เราใช้อ่านจากไฟล์พิเศษ `/proc/self/status` (ไฟล์ของระบบที่แสดงสถานะของโปรเซสตัวเอง)

รัน (`./leak_demo`) ได้ผล (ตัดเฉพาะหัว/ท้ายที่สำคัญ):

```
VmRSS เริ่มต้น = 1200 kB (หน่วยความจำจริงที่โปรเซสนี้ใช้อยู่)

=== 1) จอง 8 ก้อน ก้อนละ 1 เมกะไบต์ แล้ว "ลืมคืน" ===
  ก้อนที่ 1: จอง+ใช้งาน -> VmRSS =   2432 kB (โตขึ้น +1232 kB)
  ...
  ก้อนที่ 8: จอง+ใช้งาน -> VmRSS =   9712 kB (โตขึ้น +1040 kB)

=== 2) จองเท่ากันเป๊ะ แต่คืนทุกก้อน ===
  ก้อนที่ 1: จอง+ใช้งาน+คืน -> VmRSS =   9712 kB (ต่างจากก้อนก่อน +0 kB)
  ก้อนที่ 2: จอง+ใช้งาน+คืน -> VmRSS =  10736 kB (ต่างจากก้อนก่อน +1024 kB)
  ก้อนที่ 3..8: VmRSS =  10736 kB (ไม่โตต่อ)

สรุป: รอบ 1 (ไม่คืน) VmRSS โตขึ้น 8512 kB = หน่วยความจำ 8 เมกะไบต์ที่ไม่มีทางคืน
      รอบ 2 (คืนทุกก้อน) ต่างกันแค่บรรทัด free() แต่ VmRSS เปลี่ยนไปเพียง +1024 kB
      โปรแกรมไม่พัง ไม่มี error ให้เห็นเลย — นี่คือความน่ากลัวของ memory leak
```

เห็นความต่างชัดเจน:

- **รอบ 1 (ไม่คืน)**: VmRSS ไต่ขึ้นเรื่อย ๆ จนโต +8512 kB — หน่วยความจำ 8 เมกะไบต์ถูก "กักไว้" ตลอด และ**ไม่มีทางคืน** เพราะตัวชี้ `p` ถูกทิ้งหายไปตอนจบรอบ (ตัวแปรท้องถิ่นตายพร้อมเฟรม ตามที่เรียนตอน 15) ไม่เหลือใครรู้ที่อยู่ของก้อนนั้น
- **รอบ 2 (คืนทุกก้อน)**: VmRSS แทบไม่โต (เพิ่มแค่ 1024 kB จากค่าใช้จ่ายของระบบครั้งแรก) เพราะพอ `free` แล้ว ระบบเก็บคืนไปใช้ต่อได้

**จุดที่อันตรายสุดคือ "มันไม่พัง"** — memory leak ไม่ทำให้โปรแกรมตายทันที ไม่มี error ฟ้องออกมา ไม่มีอะไรบอกเลย มันแค่ค่อย ๆ กัดหน่วยความจำไปทีละนิด ถ้าโปรแกรมนี้รันเป็นบริการยาว ๆ (เช่น เว็บเซิร์ฟเวอร์ที่รับคำขอวันละล้านครั้ง) หน่วยความจำจะค่อย ๆ หมดจนระบบทั้งเครื่องหนืดหรือต้องรีสตาร์ท — นี่คือเหตุผลที่ "หน่วยความจำรั่ว" เป็นบั๊กที่น่ากลัวที่สุดชนิดหนึ่ง เพราะ**มันเงียบ**

## 3. use-after-free กับ double free: คืนแล้วยังแตะ = ระเบิดเวลา (ภาพที่ 2 ต่อ)

ถ้า memory leak คือ "ลืมคืน" อีกด้านของเหรียญคือ **คืนแล้วยังใช้ต่อ** (use-after-free) และ **คืนซ้ำสองครั้ง** (double free) เขียน `use_after_free.c` ดู (โปรแกรมเต็มอยู่ใน `course/code/ep16/use_after_free.c`):

```c
int main(void)
{
    printf("=== 1) คืนแล้วยังอ่านต่อ ===\n");
    unsigned char *p = malloc(N);   /* N = 32 ไบต์ */
    memset(p, 0x41, N);             /* ยัด 'A' (0x41) ทุกไบต์ */
    dump("malloc แล้วยัด 'A' ทั้งก้อน:", p, 8);
    free(p);                        /* คืนไปแล้ว */
    dump("หลัง free(p) แต่ยังอ่าน p:", p, 8);   /* ผิด: แตะหน่วยความจำที่คืนไปแล้ว */
    ...

    printf("=== 2) คืนแล้วจองใหม่: คนใหม่เช่าที่เดิม ===\n");
    unsigned char *q = malloc(N);   /* ได้ที่เดิมเป๊ะ */
    ...
}
```

รัน (`./use_after_free`) ได้ผล:

```
=== 1) คืนแล้วยังอ่านต่อ ===
  malloc แล้วยัด 'A' ทั้งก้อน:41 41 41 41 41 41 41 41 
  หลัง free(p) แต่ยังอ่าน p:b1 b6 5c 55 05 00 00 00   (ค่าเปลี่ยนทุกครั้งที่รัน)
  -> ค่าเดิมหายไปแล้ว! ตัวจัดหน่วยความจำเขียนข้อมูลของมันลงไปแทน
     (และเราไม่มีสิทธิ์อ่านตรงนี้แล้ว — "ยังอ่านได้" ไม่ได้แปลว่า "ถูกต้อง")

=== 2) คืนแล้วจองใหม่: คนใหม่เช่าที่เดิม ===
  p = 0x5555dae652b0 · q = 0x5555dae652b0 -> ได้ที่เดิมเป๊ะ
  เขียนของใหม่ผ่าน q:42 42 42 42 42 42 42 42 
  อ่านผ่าน p (ตัวชี้เก่า):42 42 42 42 42 42 42 42 
  -> p กับ q ชี้ที่เดียวกัน ข้อมูลที่ p "เห็น" กลายเป็นของ q
     ถ้า q เป็นข้อมูลของผู้ใช้รายอื่น/งานส่วนอื่น = ข้อมูลรั่วข้ามขอบเขต
```

อ่านให้เห็นภาพชัด:

1. **พอ `free` แล้ว ค่า `'A'` (41) หายไปทันที** — กลายเป็น `b1 b6 5c 55 05 00 00 00` (ค่าเปลี่ยนทุกครั้งที่รัน) เพราะตัวจัดหน่วยความจำเอาช่องที่ว่างไปจดข้อมูลภายในของมัน (เช่น ที่อยู่ของช่องว่างถัดไปในรายการ) — **"ยังอ่านได้" ไม่ได้แปลว่า "ถูกต้อง"** เราแค่บังเอิญอ่านเข้าไปในเขตข้อมูลของระบบ
2. **จองใหม่ได้ที่เดิมเป๊ะ** — `p` (ตัวชี้เก่าที่คืนไปแล้ว) กับ `q` (ตัวชี้ใหม่) ชี้ที่เดียวกัน ถ้าเราเผลอเขียนผ่าน `p` ต่อ (คิดว่ามันยังเป็นของเรา) ข้อมูลที่เขียนจะไปทับของ `q` = **ข้อมูลรั่วข้ามขอบเขต** — นึกภาพว่า `q` เป็นข้อมูลของผู้ใช้รายอื่นหรือส่วนอื่นของโปรแกรม แล้วเราดันไปเขียนทับมันผ่านตัวชี้เก่าที่ค้างไว้

และตัวที่หนักกว่าคือ **double free** (คืนซ้ำสองครั้ง) — ทั้ง use-after-free และ double free จัดอยู่ในกลุ่ม **undefined behavior** (พฤติกรรมที่มาตรฐานภาษา C ไม่รับประกันผล) ซึ่งเราจะเปิดกล่องอธิบายเต็ม ๆ หลังดูผลรัน เขียน `double_free.c` (โปรแกรมเต็มอยู่ใน `course/code/ep16/double_free.c`):

```c
int main(void)
{
    char *p = malloc(16);
    free(p);
    printf("free ครั้งที่ 1: ผ่านไปได้ (ถูกต้อง)\n");
    free(p);   /* ผิด: p ถูกคืนไปแล้ว การคืนซ้ำคือ undefined behavior */
    printf("บรรทัดนี้จะไม่ถูกพิมพ์เลย\n");
}
```

รัน (`./double_free`) ได้ผล:

```
free ครั้งที่ 1: ผ่านไปได้ (ถูกต้อง)
free(): double free detected in tcache 2
[exit code: 134]   (โปรแกรมถูกสั่งหยุด — Aborted)
```

โชคดีที่ glibc ตรวจจับได้ทันและหยุดโปรแกรมเลย (`double free detected in tcache` = ตรวจพบการคืนซ้ำ — **tcache** คือที่พักก้อนที่เพิ่งคืนไว้หยิบใช้เร็ว ๆ) แทนที่จะปล่อยให้ข้อมูลภายในของมันเสียหายแบบเงียบ ๆ

> **undefined behavior (UB)** = "พฤติกรรมที่มาตรฐานภาษา C ไม่รับประกันผล" — เขียนโค้ดแบบนี้แล้วผลจะเป็นยังไงก็ได้ ขึ้นกับคอมไพเลอร์/ระบบ/โชค: อาจทำงานได้ตามที่เราหวัง (บนเครื่องนี้ มัน "ดูเหมือนทำงานได้") อาจได้ค่าขยะ อาจพังทันที หรือแย่สุดคือ **ทำงานผิดเงียบ ๆ ไม่มีวี่แวว** — นี่คือเหตุผลว่าทำไม UB ถึงน่ากลัว และทำไมทุกตอนที่ผ่านมาเราถึงเน้น "คอมไพล์ให้ไม่มี warning" เพราะ warning มักเป็นสัญญาณของ UB

แล้วถ้ามันเงียบขนาดนี้ เราจะจับ use-after-free ได้ยังไง? ใช้ **AddressSanitizer** (เรียกย่อ ๆ ว่า ASan = ตัวตรวจหน่วยความจำที่คอมไพเลอร์แทรกโค้ดตรวจเข้าไปตอนคอมไพล์) — คอมไพล์ใหม่ด้วย `-fsanitize=address` แล้วรัน (`gcc -std=c17 -Wall -Wextra -Wpedantic -fsanitize=address -o use_after_free_asan use_after_free.c && ./use_after_free_asan`):

```
=================================================================

READ of size 1 at 0x503000000040 thread T0
    #0 ... in dump .../use_after_free.c:19
    #1 ... in main .../use_after_free.c:34
    ...

    #1 ... in main .../use_after_free.c:33   <- บรรทัดที่ free

    #1 ... in main .../use_after_free.c:27   <- บรรทัดที่ malloc
SUMMARY: AddressSanitizer: heap-use-after-free .../use_after_free.c:19 in dump
```

ASan ไม่ปล่อยให้ "เงียบ" — มันหยุดโปรแกรมทันทีที่เจอการอ่านหลังคืน (`heap-use-after-free`) พร้อม**รายงานทั้งสองตำแหน่ง**: บรรทัดที่ `malloc` (บรรทัด 27) และบรรทัดที่ `free` (บรรทัด 33) และบรรทัดที่เราใช้ต่อ (บรรทัด 19) — ครบทุกที่ที่ต้องไปแก้

> ASan กับ Valgrind ต่างกันตรง "วิธีทำงาน": ASan **คอมไพล์โค้ดตรวจเข้าไปในโปรแกรม** (เร็วกว่ามาก ใช้ในงานจริงได้) ส่วน Valgrind **รันโปรแกรมของเราในเครื่องจำลอง** (ไม่ต้องคอมไพล์ใหม่ ใช้ได้กับโปรแกรมที่คอมไพล์แล้ว แต่ช้าลง 10–50 เท่า) — ทั้งคู่เป็นเครื่องมือที่วิศวกรตัวจริงใช้จับบั๊กหน่วยความจำทุกวัน

**กฎทองที่ต้องจำติดตัว**: `free` ตัวไหนแล้ว ตัวนั้น "ตาย" ทันที ห้ามแตะอีกเด็ดขาด วิธีกันที่นิยมคือพอ `free(p)` เสร็จให้ตั้ง `p = NULL` ทันที (แต่ระวัง: ถ้ามี pointer ตัวอื่นชี้ไปที่เดียวกัน มันก็ยังเป็น use-after-free อยู่ดี)

## 4. buffer overflow: เขียนเกินขอบเขต = เขียนทับเพื่อนบ้าน (ภาพที่ 3)

มาถึงคำถามค้างข้อสอง — buffer overflow ตัวร้ายที่ผูก security เข้ากับ memory หลักการของมันง่ายมาก: **บัฟเฟอร์ (array) มีขนาดจำกัด แต่โค้ดบางตัวเขียนข้อมูลลงไปโดยไม่เช็คว่าเกินขอบเขตหรือไม่** ส่วนที่เกินก็ "ล้น" ไปทับข้อมูลที่อยู่ข้าง ๆ ในหน่วยความจำ

เริ่มจากตัวอย่างที่เห็นผลชัดที่สุดบน **struct** (โครงสร้างข้อมูลที่รวมตัวแปรหลายตัวไว้ด้วยกัน — มาตรฐาน C การันตีว่าสมาชิกเรียงตามลำดับที่เขียน) เขียน `overflow_struct.c` (โปรแกรมเต็มอยู่ใน `course/code/ep16/overflow_struct.c`):

```c
struct account {
    char name[8];      /* บัฟเฟอร์ชื่อ: มีที่ให้ 8 ไบต์ (รวมที่ให้ '\0' ด้วย) */
    unsigned long pin; /* ข้อมูลลับที่อยู่ติดกัน — ห้ามโดนเขียนทับ */
};

/* ตัวคัดลอกแบบไม่ตรวจขอบเขต: คัดลอกไปเรื่อย ๆ จนเจอ '\0' (นี่คือสิ่งที่ strcpy ทำ) */
static void copy_unbounded(char *dst, const char *src)
{
    while ((*dst++ = *src++) != '\0') {
        /* ไม่มีการถามเลยว่า dst ยังมีที่ว่างเหลือไหม */
    }
}
```

> ศัพท์: `strcpy` = ฟังก์ชันคัดลอกสตริง (ข้อความ) แบบไม่เช็คขอบเขต เป็นตัวร้ายคลาสสิกที่ถูกแบนในแนวปฏิบัติความปลอดภัยแทบทุกแห่ง · `'\0'` = ตัวอักษรพิเศษ "ปิดท้ายสตริง" (ค่า 0) ที่บอกว่าข้อความจบตรงนี้ — โค้ด C รู้ความยาวของสตริงโดยการไล่หาตัว `'\0'` นี้

รัน (`./overflow_struct`) ดูว่าเกิดอะไรขึ้นตอนคัดลอกชื่อยาว 12 ตัวอักษรลงใน `name[8]`:

```
โครงสร้าง struct account: name อยู่ offset 0 (8 ไบต์) · pin อยู่ offset 8 (8 ไบต์)
รวมทั้งโครงสร้าง = 16 ไบต์

=== 1) คัดลอกแบบ "พอดี" (ตรวจขอบเขต) — ไม่มีอะไรเสียหาย ===
  คัดลอก "bee" (ครบ) · pin = 0x1111111122222222 · name = "bee"

=== 2) คัดลอกแบบไม่ตรวจขอบเขตด้วยชื่อยาว 12 ไบต์ ===
  ก่อนคัดลอก: 00 00 00 00 00 00 00 00 22 22 22 22 11 11 11 11 
  และค่าของ pin คือ: pin = 0x1111111122222222
  หลังคัดลอก: 41 42 43 44 45 46 47 48 49 4a 4b 4c 00 11 11 11 
  และค่าของ pin คือ: pin = 0x111111004c4b4a49 <- เปลี่ยนไปแล้ว!
  ไบต์ของ "IJKL" กับตัวปิดท้าย ('\0') ล้นจาก name ไปทับ pin
```

ดูการเปลี่ยนแปลงของหน่วยความจำ (จาก hex ทั้ง 16 ไบต์ของ struct):

- **ก่อน**: `00 00 00 00 00 00 00 00 | 22 22 22 22 11 11 11 11` — 8 ไบต์แรกคือ `name` (ว่าง), 8 ไบต์หลังคือ `pin` = 0x1111111122222222
- **หลังคัดลอก "ABCDEFGHIJKL"**: `41 42 43 44 45 46 47 48 | 49 4a 4b 4c 00 11 11 11` — ตัวอักษร `A`–`H` (41–48) ลงใน `name[8]` พอดี แต่ `I J K L` (49 4a 4b 4c) บวกตัว `'\0'` (00) **ล้นออกไปทับ `pin`** ทำให้ `pin` เปลี่ยนจาก `0x1111111122222222` เป็น `0x111111004c4b4a49`

> **ทำไม `pin` ถึงกลายเป็น `0x...4c4b4a49`** — เครื่องนี้เก็บเลขหลายไบต์แบบ **little-endian** (ไบต์ที่ "มีนัยสำคัญน้อยที่สุด" อยู่ก่อน) ตัวอักษร `I J K L` = 0x49 0x4a 0x4b 0x4c จึงไปทับ**ส่วนท้าย**ของ `pin` (เพราะ `pin` อยู่ถัดจาก `name` พอดี และไบต์ต่ำสุดของ `pin` อยู่ชิด `name` ที่สุด) — เราเรียนเลขฐานสิบหกไปแล้วในตอน 8 ส่วน little-endian พูดถึงไปแล้วตอนดู byte ของ int

ลองจินตนาการว่าถ้า `pin` คือรหัสลับ/ยอดเงิน/สิทธิ์การเข้าถึง — การเขียนชื่อยาวเกินไปนิดเดียว ก็เปลี่ยนข้อมูลลับของระบบได้แล้ว นี่คือหัวใจของ buffer overflow

อีกด้านหนึ่งของเหรียญคือ **อ่านเกินขอบเขต** (โปรแกรม `overflow_struct.c` ข้อ 3) — อ่าน 16 ไบต์จาก `name` ทั้งที่เรามีสิทธิ์แค่ 8 ไบต์ (นี่คือการ "อ่าน" เกินขอบเขต ตรงข้ามกับข้อ 2 ที่เป็น "เขียน" เกิน):

```
=== 3) อ่านเกินขอบเขต: ข้อมูลข้าง ๆ รั่วออกมาได้ ===
  อ่าน 16 ไบต์เริ่มจาก name (มีสิทธิ์แค่ 8 ไบต์): "ABCDEFGHIJKL...."
  -> 8 ไบต์หลังคือข้อมูลของ pin ที่รั่วออกมา (I J K L คือไบต์ที่ข้อ 2 ล้นลงไป · ที่เหลือเป็น 0x00 0x11 0x11 0x11)
     นี่คือรูปแบบเดียวกับที่ทำให้ Heartbleed รั่วกุญแจลับ
```

เห็นข้อมูลของ `pin` ปนออกมาด้วย: 8 ไบต์หลังคือ `I J K L` (ไบต์ที่ข้อ 2 ล้นลงไป) ต่อด้วย `00 11 11 11` (ส่วนที่เหลือของ `pin` เดิม) — **นี่คือรูปแบบเดียวกับช่องโหว่ Heartbleed** (บั๊กชื่อดังปี 2014 ที่ทำให้เซิร์ฟเวอร์ทั่วโลกรั่วกุญแจเข้ารหัส) คือโปรแกรมอ่านข้อมูลเกินขอบเขตบัฟเฟอร์แล้วส่งกลับไปให้ผู้โจมตีโดยไม่รู้ตัว

### 4.1 ลุกลามไปถึง "การควบคุมโปรแกรม": บัฟเฟอร์บน stack

ที่พูดมาทั้งหมดเป็นการทับ "ข้อมูลข้าง ๆ" แต่ buffer overflow อันตรายสุดเมื่อมันล้นไปถึง**ข้อมูลที่ควบคุมการทำงานของโปรแกรม**บน stack — นึกย้อนตอน 15 ที่เราเห็นว่า stack frame (กรอบพื้นที่ของฟังก์ชัน) เก็บ **return address** (ที่อยู่ของคำสั่งที่ต้องกลับไปหลังฟังก์ชันจบ) ไว้ด้วย

เขียน `overflow_stack.c` จำลองฟังก์ชันตรวจรหัสผ่านที่มีบัฟเฟอร์ 16 ไบต์ แล้วส่งข้อมูลยาว 64 ไบต์เข้าไป (โปรแกรมเต็มอยู่ใน `course/code/ep16/overflow_stack.c`):

```c
#define INPUT_MAX 128

static int check_login(const char *input)
{
    char buf[16];                          /* ที่ให้ 16 ไบต์ */
    unsigned long marker = 0xAABBCCDDEEFF0011UL; /* ตัวแปร "เพื่อนบ้าน" ไว้ให้เห็นการทับ */

    printf("[check_login] บัฟเฟอร์ %zu ไบต์ · marker เริ่มต้น = 0x%016lx\n", sizeof buf, marker);
    copy_unbounded(buf, input);            /* คัดลอกแบบไม่เช็คขอบเขต */
    printf("[check_login] หลังคัดลอก: marker = 0x%016lx (%s)\n", marker, ...);
    return strcmp(buf, "letmein") == 0;
}
```

> ศัพท์: `strcmp` = ฟังก์ชันเปรียบเทียบสตริงสองตัวว่าเท่ากันไหม · `marker` ในที่นี้คือตัวแปรธรรมดาที่เราจงใจวางไว้ "ข้าง ๆ" บัฟเฟอร์ เพื่อเป็นเหยื่อล่อให้เห็นว่าการเขียนเกินขอบเขตทับข้อมูลเพื่อนบ้านได้จริง

คอมไพล์**สองเวอร์ชัน**แล้วเทียบกัน (นี่คือจุดสำคัญของหัวข้อนี้):

```bash
# เวอร์ชัน A: ปิดเกราะป้องกันของคอมไพเลอร์
gcc -std=c17 -Wall -Wextra -Wpedantic -fno-stack-protector -o overflow_noguard overflow_stack.c
# เวอร์ชัน B: เปิดเกราะ (ต้องระบุ flag เอง — ค่า default ของ GCC บนเครื่องนี้ไม่เปิดให้ ต่างจาก distro บางตัวที่เปิด default)
gcc -std=c17 -Wall -Wextra -Wpedantic -fstack-protector-strong -o overflow_guard overflow_stack.c
```

รันทั้งคู่ด้วยข้อมูลสั้น (3 ไบต์) ก่อน — ปกติทั้งคู่:

```
[main] โหมด = short · ความยาวข้อมูล = 3 ไบต์
[check_login] บัฟเฟอร์ 16 ไบต์ · marker เริ่มต้น = 0xaabbccddeeff0011
[check_login] หลังคัดลอก 3 ไบต์: marker = 0xaabbccddeeff0011 (ยังไม่ถูกแตะ)
[check_login] buf (16 ไบต์แรก) = "bee"
[main] ผลการตรวจสอบรหัส: ไม่ผ่าน
[main] กลับมาถึง main เรียบร้อย (ถ้าเห็นบรรทัดนี้ = การควบคุมยังไม่พัง)
```

ทีนี้รันด้วยข้อมูลยาว 64 ไบต์ (`./overflow_noguard long` — เวอร์ชันไม่มีเกราะ):

```
[main] โหมด = long · ความยาวข้อมูล = 64 ไบต์
[check_login] บัฟเฟอร์ 16 ไบต์ · marker เริ่มต้น = 0xaabbccddeeff0011
[check_login] หลังคัดลอก 64 ไบต์: marker = 0x4141414141414141 (ถูกเขียนทับแล้ว!)
[check_login] buf (16 ไบต์แรก) = "AAAAAAAAAAAAAAAA"
[main] ผลการตรวจสอบรหัส: ไม่ผ่าน
[main] กลับมาถึง main เรียบร้อย (ถ้าเห็นบรรทัดนี้ = การควบคุมยังไม่พัง)
Bus error    <- โปรแกรมตายตอน main พยายาม "return" ไปที่อยู่ที่ถูกเขียนทับแล้ว
```

เกิดอะไรขึ้นทีละขั้น (เรายืนยันด้วยการเปิดดู assembly จริงของ `check_login` ผ่านคำสั่ง `gcc -S` — เฟรมของฟังก์ชันนี้ใหญ่ 64 ไบต์):

1. บัฟเฟอร์ `buf[16]` อยู่ที่ offset `sp+40` (ตำแหน่งบน stack ห่างจากยอด 40 ไบต์) ถูกยัด `'A'` (0x41) ไป 64 ไบต์ — 16 ไบต์แรกเต็มบัฟเฟอร์พอดี ส่วนอีก 48 ไบต์**ล้นออกไป**
2. ไบต์ที่ล้นทับ `marker` (ตัวแปรเพื่อนบ้านที่วางติดกันที่ offset `sp+56`) จนกลายเป็น `0x4141414141414141` (`'A'` แปดตัว)
3. ไบต์ที่เหลือ (40 ไบต์) ล้นต่อไป**เลยเฟรมของ `check_login`** เข้าไปในเฟรมของ `main` (ฟังก์ชันที่เรียกมัน — เฟรมของผู้เรียกวางอยู่ "สูงกว่า" เพราะ stack โตลง) แล้วทับ **return address ของ `main`** (ที่อยู่ที่ `main` ต้องกระโดดกลับไปหลังจบงาน)
4. สังเกตว่า `check_login` ยัง "กลับได้ปกติ" — เพราะ return address ของมันเองอยู่ที่ offset `sp+8` ซึ่ง**ต่ำกว่า**บัฟเฟอร์ จึงไม่ถูกแตะ เราเลยเห็นข้อความ `[main] กลับมาถึง main เรียบร้อย` พิมพ์ออกมา พอ `main` จบงานจะ `return` มันต้องกระโดดตาม return address ของตัวเอง — แต่ตอนนี้ address นั้นกลายเป็น `0x4141414141414141` → CPU กระโดดไปที่อยู่ที่ไม่มีอยู่จริง → **Bus error** (โปรแกรมตายทันที)

**ทำไมเป็น return address ของ "main" ไม่ใช่ของ "check_login"** — เรื่องนี้ขึ้นกับสถาปัตยกรรม CPU (การออกแบบภายในของ CPU แต่ละตระกูล):

- บนเครื่องเรา (**aarch64**) คำสั่งแรกของฟังก์ชันเก็บ return address ไว้ที่**ต่ำสุด**ของเฟรม (offset `sp+8`) ส่วนตัวแปรท้องถิ่นวางไว้**สูงกว่า** — การเขียนเกินบัฟเฟอร์ (ซึ่งโตขึ้นไปทาง address สูง) จึงวิ่งเลยเฟรมตัวเองเข้าไปทับเฟรมของผู้เรียก
- แต่บน **x86-64** (พีซี/แล็ปท็อปทั่วไป) เครื่องวาง return address ไว้**เหนือ**ตัวแปรท้องถิ่น ตรงข้ามกันเป๊ะ — การล้นบัฟเฟอร์จะทับ return address ของฟังก์ชัน**ตัวเอง**โดยตรง (สถานการณ์คลาสสิกของการโจมตี)
- ใจความที่ต้องจำคือ "เขียนเกินบัฟเฟอร์ = ไปทับข้อมูลสำคัญที่ควบคุมการทำงาน" ไม่ว่ามันจะเป็นของฟังก์ชันไหน

> **ทำไม "Bus error" ไม่ใช่ "Segmentation fault"** — ทั้งคู่คือ "โปรแกรมพยายามเข้าถึงหน่วยความจำที่ไม่มีสิทธิ์" แต่เกิดคนละจุด: Segmentation fault มักเกิดตอนอ่าน/เขียนข้อมูลในที่อยู่ต้องห้าม ส่วน Bus error มักเกิดตอน CPU พยายาม**ดึงคำสั่ง**จากที่อยู่ที่ไม่มีอยู่จริง — ตัวเลขปลายทางต่างกันแค่นั้น ใจความคือ "โปรแกรมตายเพราะพยายามกระโดดไปที่อยู่ขยะ"

แล้วตอนนี้ดูเวอร์ชัน**มีเกราะ** (`./overflow_guard long`):

```
[main] โหมด = long · ความยาวข้อมูล = 64 ไบต์
[check_login] บัฟเฟอร์ 16 ไบต์ · marker เริ่มต้น = 0xaabbccddeeff0011
[check_login] หลังคัดลอก 64 ไบต์: marker = 0xaabbccddeeff0011 (ยังไม่ถูกแตะ)
[check_login] buf (16 ไบต์แรก) = "AAAAAAAAAAAAAAAA"
*** stack smashing detected ***: terminated
Aborted
```

ความต่างสองจุด:

1. **`marker` รอด** — เพราะพอเปิดเกราะ (`-fstack-protector-strong`) คอมไพเลอร์จัดเรียงตัวแปรในเฟรมใหม่: ย้าย `marker` ไปวางไว้**ก่อน**บัฟเฟอร์ (offset `sp+16` ซึ่งต่ำกว่าบัฟเฟอร์ที่ `sp+24`) ให้พ้นทางล้น และวาง **canary** (ค่าเฝ้ายามแบบสุ่ม) ไว้**คั่นระหว่างบัฟเฟอร์กับ return address** พอดี
2. **โปรแกรมตายแบบ "มีข้อความชัดเจน"** — หลังคัดลอก 64 ไบต์เสร็จ ก่อนจะ `return` ระบบตรวจค่า canary แล้วพบว่ามันถูกเขียนทับ (เพราะ 'A' วิ่งทะลุไป) จึงหยุดโปรแกรมทันทีพร้อมฟ้องว่า `*** stack smashing detected ***` (ตรวจพบการทุบบัฟเฟอร์บน stack) — แทนที่จะปล่อยให้โปรแกรมกระโดดไปที่อยู่ขยะแบบเงียบ ๆ

![stack frame ของ check_login ที่มีบัฟเฟอร์ 16 ไบต์ เปรียบเทียบแบบไม่มี canary กับมี canary](/assets/diagrams/ep16-03-stack-overflow-canary.svg)

> **canary** (คานารี = ชื่อนกที่คนงานเหมืองถ่านหินสมัยก่อนเอาใส่กรงลงไปในอุโมงค์เพื่อเป็น "สัญญาณเตือนก๊าซพิษ" — ถ้านกตาย แปลว่าอันตราย) — ในที่นี้คือ "ค่าเฝ้ายาม" ที่วางไว้หน้าจุดสำคัญ ถ้ามันถูกเขียนทับ = มีคนเขียนเกินขอบเขต = หยุดทุกอย่างทันที ชื่อนี้มาจากประวัติศาสตร์จริงของอุตสาหกรรมเหมือง

**นี่คือหัวใจของคำตอบ "ทำไม security = เรื่อง memory"** — บั๊กที่ดูเล็ก ๆ อย่าง "ลืมเช็คขอบเขตบัฟเฟอร์" ไม่ใช่แค่ทำให้โปรแกรมพัง แต่มันเปิดทางให้ผู้โจมตี**เขียนข้อมูลทับ return address** แล้วบังคับให้โปรแกรมกระโดดไปรันโค้ดของผู้โจมตีได้ (เราไม่สอนวิธีทำ — แค่ให้เข้าใจกลไกว่าทำไมมันถึงเป็นไปได้ และทำไมทุกคนถึงต้องรู้ว่า memory ทำงานยังไง)

## 5. เกราะป้องกัน: ทำอย่างไรให้ปลอดภัย (ภาพที่ 4)

ตอนนี้เรารู้จักตัวร้ายครบแล้ว (leak / use-after-free / double free / buffer overflow) มาดู "ชุดเกราะ" ที่วิศวกรตัวจริงใช้ป้องกัน — ไล่จากสิ่งที่เราควบคุมได้เอง ไปจนถึงสิ่งที่ระบบจัดการให้

### 5.1 เกราะชั้นแรก: เขียนโค้ดไม่ให้เกินขอบเขตตั้งแต่แรก

กับดักที่คนเขียน C เจอบ่อยมากคือ `strncpy` (strcpy เวอร์ชันจำกัดความยาว n ไบต์) — หลายคนเข้าใจผิดว่ามัน "ปลอดภัย" เพราะมันคัดลอกแค่ `n` ไบต์ แต่มันมีกับดักซ่อนอยู่ เขียน `strncpy_trap.c` ดู (โปรแกรมเต็มอยู่ใน `course/code/ep16/strncpy_trap.c`):

```c
char src[64];
build_source(src, sizeof src, SRC_LEN);  /* ได้ "ABCDEFGHIJ" (10 ไบต์) */
char dst[8];
strncpy(dst, src, sizeof dst);           /* คัดลอกได้ 8 ไบต์ — ไม่มีที่ให้ '\0' เหลือเลย */
```

รัน (`./strncpy_trap`) ได้ผล:

```
strncpy(dst, "ABCDEFGHIJ" (10 ไบต์), 8) — ที่ปลายทางมี 8 ไบต์:
  ไบต์ทั้ง 8 ของ dst = A B C D E F G H 
  หาตัวปิดท้าย ('\0') ในขอบเขต 8 ไบต์: ไม่เจอเลย!
  ถ้าเอาตัวแปรนี้ไปใช้ต่อ (strlen / printf "%s" / strcmp) มันจะอ่านเลยขอบเขตไปเรื่อย ๆ
  จนกว่าจะบังเอิญเจอไบต์ 0 — นั่นคือ undefined behavior ตรง ๆ
```

กับดักของ `strncpy`: เมื่อต้นทางยาวเท่ากับหรือเกิน `n` มัน**ไม่ใส่ `'\0'` ปิดท้าย** — แล้วพอเอา `dst` ไปใช้ต่อกับฟังก์ชันที่ไล่หา `'\0'` (อย่าง `strlen`/`printf("%s")`/`strcmp`) มันจะอ่านเลยขอบเขตไปเรื่อย ๆ จนเจอไบต์ 0 โดยบังเอิญ = UB เงียบ ๆ อีกแล้ว

วิธีที่ปลอดภัยกว่า — ใช้ `snprintf` (printf เวอร์ชันที่จำกัดขนาดปลายทาง) ซึ่ง**ปิด `'\0'` เสมอ** และ**บอกได้ว่าโดนตัดหรือไม่**:

```
วิธีที่ถูก: จองที่เพิ่มหนึ่งไบต์สำหรับตัวปิดท้าย แล้วใช้ snprintf
  snprintf บอกว่า "ต้องใช้ 10 ไบต์" · เรามี 9 ไบต์ -> ถูกตัด (รู้ตัวได้ ไม่ต้องเดา)
  ค่าที่ได้ = "ABCDEFGH"
```

หลักสามข้อของการคัดลอก/อ่านข้อมูลอย่างปลอดภัย (รวบรวมไว้ใน `safe_copy.c` โปรแกรมเต็มอยู่ใน `course/code/ep16/safe_copy.c`):

```c
/* หลักที่ยึด: รู้ขนาดปลายทางเสมอ · เขียน '\0' ปิดท้ายเสมอ · บอกได้ว่า "ครบ" หรือ "ถูกตัด"
 *            · ไม่เก็บสถานะซ่อน (เรียกซ้ำด้วยค่าเดิมได้ผลเดิม = idempotent)
 *            · ข้อความ error ไม่บอกที่อยู่หน่วยความจำภายใน (ไม่รั่วข้อมูลของระบบ)
 *            · ไม่ใช้ตัวแปร static กลางไฟล์ จึงเรียกจากหลายเธรดพร้อมกันได้ (ไม่มี race)
 *            · เช็คการคูณล้นก่อนจอง array (integer overflow -> ก้อนเล็ก -> เขียนล้น heap) */

static enum copy_status copy_str(char *dst, size_t dst_size, const char *src)
{
    if (dst == NULL || src == NULL || dst_size == 0) {
        return COPY_INVALID;               /* พารามิเตอร์ไม่ถูกต้อง: ไม่เขียนอะไรเลย */
    }
    size_t i = 0;
    while (i + 1 < dst_size && src[i] != '\0') {
        dst[i] = src[i];
        i++;
    }
    dst[i] = '\0';                         /* ปิดท้ายเสมอ ไม่ว่าครบหรือถูกตัด */
    return (src[i] == '\0') ? COPY_OK : COPY_TRUNCATED;   /* บอกผลตรง ๆ */
}
```

> ศัพท์สำคัญสองตัว: **idempotent** (เรียกซ้ำด้วยค่าเดิม ได้ผลเดิมเสมอ = ปลอดภัยถ้าถูกเรียกซ้ำ) · **race condition** (ข้อผิดพลาดที่เกิดเมื่อหลายเธรดแย่งกันแก้ข้อมูลเดียวกันพร้อมกัน — เธรด = หน่วยย่อยของโปรแกรมที่ทำงานพร้อมกันได้) · **integer overflow** (การคูณ/บวกเลขจนเกินขนาดที่เก็บได้ แล้วหดกลับเป็นค่าเล็ก ๆ — เช่น `n * size` ล้นจนกลายเป็นเลขน้อย ๆ แล้ว `malloc` จองก้อนเล็กกว่าที่คิด → เขียนล้นอีกทอด)

ผลรัน (`./safe_copy`) — สังเกตว่าทุกกรณี**รายงานผลตรง ๆ** และ**เรียกซ้ำได้ผลเดิม**:

```
=== 1) คัดลอกด้วยตัวที่ตรวจขอบเขต: ผลลัพธ์บอกได้เสมอ ===
  พอดีเป๊ะ (15 ไบต์) -> ครบทุกไบต์ dst="0123456789abcde" · ทำซ้ำได้ผลเดิม: ใช่
  สั้นกว่าที่ (3 ไบต์) -> ครบทุกไบต์ dst="bee" · ทำซ้ำได้ผลเดิม: ใช่
  ยาวเกินที่ (20 ไบต์) -> ถูกตัด (ที่ปลายทางไม่พอ) dst="012345678901234" · ทำซ้ำได้ผลเดิม: ใช่
  ปลายทางขนาด 0 -> พารามิเตอร์ไม่ถูกต้อง dst="###############" · ทำซ้ำได้ผลเดิม: ใช่
  แหล่งข้อมูลเป็น NULL -> พารามิเตอร์ไม่ถูกต้อง dst="###############" · ทำซ้ำได้ผลเดิม: ใช่

=== 2) อ่านบรรทัดด้วย fgets + จัดการบรรทัดที่ยาวเกิน ===
  [บรรทัดสั้น] อ่านได้ 31 ไบต์: "สวัสดีครับ" -> ได้ครบทั้งบรรทัด
  [บรรทัดยาว 65 ไบต์] อ่านได้ 31 ไบต์: "Havebit-cs-fundamentals-line-th" -> บรรทัดยาวเกินบัฟเฟอร์: ต้องอ่านส่วนเกินทิ้ง!

=== 3) เช็คการคูณล้นก่อนจองหน่วยความจำ ===
  alloc_array(100, 4)          = สำเร็จ
  alloc_array(SIZE_MAX/2, 4)   = ถูกปฏิเสธ (ถ้าไม่เช็ค ผลคูณจะล้นแล้วจองก้อนเล็ก ๆ)
```

> **กับดักสำคัญของ `fgets`** (ฟังก์ชันอ่านหนึ่งบรรทัดจากไฟล์/คีย์บอร์ด): มันอ่านได้สูงสุด `n-1` ไบต์แล้วหยุด — แต่ถ้าบรรทัดยาวเกินบัฟเฟอร์ มันจะอ่านได้**แค่ครึ่งบรรทัด** ทิ้งส่วนเกินค้างไว้ในไฟล์ แล้วการเรียก `fgets` ครั้งถัดไปจะอ่านได้ข้อมูลครึ่ง ๆ กลาง ๆ (บั๊กคลาสสิก) — วิธีแก้คือเช็คว่าเจอ `'\n'` (เครื่องหมายจบบรรทัด) หรือไม่ ถ้าไม่เจอ ต้องอ่านส่วนเกินทิ้งจนจบบรรทัดก่อน (ดู `safe_copy.c` ข้อ 2 และโปรเจกต์ท้ายบท)

### 5.2 เกราะชั้นถัดไป: ASLR — ทำให้ผู้โจมตีเดาที่อยู่ไม่ได้

**ASLR** (Address Space Layout Randomization = การสุ่มตำแหน่งหน่วยความจำ) คือกลไกที่ระบบปฏิบัติการ**สุ่มตำแหน่งของ stack/heap/โค้ดใหม่ทุกครั้งที่รัน** — เราเคยเห็นมันตอน 13 แล้วว่าทำไม address เปลี่ยนทุกครั้ง วันนี้มาดูของจริงด้วย `aslr_demo.c` (โปรแกรมเต็มอยู่ใน `course/code/ep16/aslr_demo.c`):

```
รันครั้งที่ 1:
  โค้ด main  (text)  = 0x5555ad2c0828
  ตัวแปร static (data) = 0x5555ad2e004c
  ตัวแปรท้องถิ่น (stack) = 0x7fffd80b9dc4
  ที่จองจาก heap        = 0x5555ba3fc2a0

รันครั้งที่ 2:
  โค้ด main  (text)  = 0x555651e50828     <- เปลี่ยน
  ตัวแปร static (data) = 0x555651e7004c   <- เปลี่ยน
  ตัวแปรท้องถิ่น (stack) = 0x7fffc24ff334  <- เปลี่ยน
  ที่จองจาก heap        = 0x55567daa82a0  <- เปลี่ยน
```

ทุก address เปลี่ยนทุกครั้งที่รัน — เพราะฉะนั้นแม้ผู้โจมตีจะหาช่องโหว่ buffer overflow เจอ เขาก็**เดาไม่ได้ว่า return address อยู่ตรงไหน** จะ "เขียนทับแล้วบังคับให้กระโดดไปโค้ดตัวเอง" จึงทำได้ยากขึ้นมาก (และพิสูจน์ให้เห็นว่ามันคือ ASLR จริง ๆ ด้วยการปิดชั่วคราว: `setarch aarch64 -R ./aslr_demo` แล้วรันสองครั้ง address จะเท่าเดิมเป๊ะทุกครั้ง)

### 5.3 เกราะชั้นท้าย: เครื่องมือตรวจอัตโนมัติ

เราเห็นไปแล้วสองตัว — **AddressSanitizer** (คอมไพล์เข้าไปในโปรแกรม ใช้รันช่วงพัฒนา) และ **Valgrind** (รันตรวจโปรแกรมที่คอมไพล์แล้ว) — ทั้งคู่เปลี่ยนบั๊ก "เงียบ" ให้กลายเป็น "ฟ้องดัง ๆ" และนี่คือเกราะหกชั้นโดยสรุป:

![เกราะป้องกัน 6 ชั้นสำหรับปัญหาหน่วยความจำ พร้อมสิ่งที่แต่ละชั้นทำไม่ได้](/assets/diagrams/ep16-04-defense-layers.svg)

สิ่งสำคัญที่ต้องเข้าใจ: **ไม่มีเกราะชั้นไหนกันได้ทุกอย่าง** — แต่ละชั้นกันคนละแบบ (ตามภาพ: เขียนโค้ดรู้ขนาด · เช็คคูณล้น · canary · ASLR · เครื่องมือตรวจ · ภาษา memory-safe) วิศวกรตัวจริงจึง**ซ้อนหลายชั้น** เพราะชั้นหนึ่งรั่ว อีกชั้นยังช่วยกันไว้ได้

## 6. เทียบกับ Go: ภาษาแบบ "memory-safe" ให้อะไรกับเรา

เราถามมาตลอดทั้งคอร์สว่า "Go ซ่อนอะไรไว้ให้เรา" — เรื่องความปลอดภัยหน่วยความจำนี่คือคำตอบใหญ่ที่สุดอีกรอบ เขียน `go_memory_safety.go` (โปรแกรมเต็มอยู่ใน `course/code/ep16/go_memory_safety.go`):

```go
func main() {
    acct := account{name: "bee", pin: 0x1111111122222222}

    // 1) เขียนเกินขอบเขตทำไม่ได้: runtime หยุดทันที (panic) แทนที่จะทับข้อมูลข้าง ๆ แบบเงียบ ๆ
    buf := make([]byte, 8)
    for i := 0; i <= 8; i++ {   // i = 8 เกินขอบเขต (ช่องที่ใช้ได้คือ 0..7)
        buf[i] = 'A'
    }
    // ... โปรแกรมถูกหยุดตรงนี้ ก่อนจะพิมพ์อะไรต่อ
}
```

> ศัพท์: **slice** (ชิ้นส่วนอาร์เรย์แบบยืดหยุ่นของ Go ที่เรียนไปในตอน 6) · **panic** (การที่ runtime ของ Go "หยุดทุกอย่าง" เมื่อเจอข้อผิดพลาดที่กู้ไม่ได้) · **recover** (คำสั่งจับ panic กลับมา — ในตัวอย่างนี้ใช้เพื่อให้โปรแกรมแสดงข้อความแล้วทำงานต่อได้ ไม่ตายค้าง)

รัน (`go run go_memory_safety.go`) ได้ผล:

```
[Go] เขียนเกินขอบเขตถูกสกัดไว้: runtime error: index out of range [8] with length 8
[Go] หลังพยายามเขียนเกิน: name="bee" pin=0x1111111122222222 · ข้อมูลข้าง ๆ ไม่ถูกแตะเลย
[Go] อ่านเกินขอบเขตถูกสกัดไว้: runtime error: index out of range [23] with length 18
[Go] จอง 8 ก้อน ก้อนละ 1 เมกะไบต์: HeapAlloc 0.1 -> 8.1 เมกะไบต์
[Go] หลังปล่อยให้เก็บคืน (GC): HeapAlloc = 0.1 เมกะไบต์ · ไม่มีอะไรค้างอยู่
[Go] ไม่มี free = ไม่มี 'ลืมคืน' และไม่มี 'คืนแล้วใช้ต่อ' — ความเสี่ยงย้ายไปที่อื่นแทน
```

เทียบกับ C ตรง ๆ สามเรื่อง:

1. **เขียนเกินขอบเขต = หยุดทันที** — Go ตรวจขอบเขตทุกครั้งที่เข้าถึง slice แล้ว**หยุดทันที** (`index out of range [8] with length 8`) แทนที่จะเขียนทับข้อมูลข้าง ๆ แบบเงียบ ๆ — `pin` ของ `acct` จึงไม่ถูกแตะเลย (`0x1111111122222222` เหมือนเดิม) ต่างจาก `overflow_struct.c` ที่ `pin` เปลี่ยนค่าไป
2. **ไม่มี `free` = ไม่มี leak และไม่มี use-after-free** — Go ใช้ **garbage collector** (GC = ระบบเก็บคืนหน่วยความจำอัตโนมัติ) ที่คอยดูว่าก้อนไหนไม่มีใครอ้างถึงแล้ว ก็เก็บคืนให้เอง ดูจาก `HeapAlloc` (หน่วยความจำบน heap ที่ใช้อยู่) ที่ไต่ไป 8.1 เมกะไบต์ตอนจอง แล้วพอเลิกอ้างถึง (`blocks = nil` — nil = ค่า "ว่าง" ของ pointer/slice ใน Go) แล้วให้ GC ทำงาน ค่าก็กลับมา 0.1 เมกะไบต์ — ไม่มีอะไรค้างอยู่เลย
3. **แต่ "ความเสี่ยงไม่ได้หายไป"** — ภาษาที่ memory-safe (ปลอดภัยเรื่องหน่วยความจำโดยกลไก) ขจัดบั๊กคลาสนี้ไปได้จริง แต่ต้องแลกกับ "ต้นทุน" (GC มี overhead, บางกรณีต้องควบคุมหน่วยความจำเองไม่ได้) และยังมีบั๊กชนิดอื่นที่ GC กันไม่ได้ — นี่คือเหตุผลว่าทำไมเราถึงต้อง**เข้าใจกลไกเบื้องล่าง** แม้จะเขียน Go เป็นหลัก เพราะวันหนึ่งเราอาจต้องไปดูแลโค้ด C ที่ฝังอยู่ในระบบจริง

## สรุป

วันนี้เราตอบคำถามค้างจากตอน 15 ครบทั้งสองข้อ และได้เห็น "ของจริง" ของบั๊กหน่วยความจำทั้งตระกูล เก็บหัวข้อที่ต้องจำให้ครบ:

- **malloc ให้มากกว่าที่ขอ** — มีหัวก้อน + ปัดให้ตรงกรอบ 16 ไบต์, `malloc` ไม่ล้างค่าแต่ `calloc` ล้าง, `realloc` ย้ายที่ได้ (ต้องรับ pointer ใหม่), `free(NULL)` ปลอดภัย, และ**ต้องเช็ค `NULL`** เพราะ `malloc` คืน `NULL` แทนที่จะพัง
- **memory leak = จองแล้วไม่คืน** — หน่วยความจำหายไปเรื่อย ๆ โดย**ไม่พัง ไม่ฟ้อง** (น่ากลัวตรงนี้) ต่างจาก "คืนทุกก้อน" แค่บรรทัด `free()` บรรทัดเดียว — จับด้วย Valgrind (`definitely lost`) หรือ LeakSanitizer (ตัวตรวจการรั่วที่มาพร้อม AddressSanitizer)
- **use-after-free / double free = คืนแล้วยังแตะ / คืนซ้ำ** — เป็น **undefined behavior**: หลัง `free` ตัวจัดหน่วยความจำเขียนข้อมูลมันลงไป (ค่าเดิมหาย) และจองใหม่ได้ที่เดิม → ข้อมูลรั่วข้ามขอบเขต — จับด้วย AddressSanitizer (`heap-use-after-free` พร้อมตำแหน่ง malloc/free)
- **buffer overflow = เขียนเกินขอบเขต** — ล้นไปทับข้อมูลเพื่อนบ้าน (ตัวอย่าง `struct`: เขียนชื่อ 12 ตัวทับ `pin` ให้เปลี่ยนค่า) และที่ร้ายสุดคือทับ **return address** บน stack จนควบคุมการทำงานของโปรแกรมได้ = **นี่คือคำตอบว่าทำไม security = เรื่อง memory**
- **เกราะ 6 ชั้น** — เขียนโค้ดตรวจขอบเขตเอง (`snprintf`/`fgets` + ตรวจตัดท้าย, เช็ค integer overflow, idempotent, ไม่มี race, ไม่รั่วข้อมูลภายใน) → canary (`-fstack-protector`) → ASLR → ASan → Valgrind → ภาษา memory-safe (Go) — **ไม่มีชั้นไหนกันได้ทุกอย่าง ต้องซ้อนกัน**
- **Go กันได้จริง** — เขียน/อ่านเกินขอบเขต → panic ทันที, ไม่มี `free` → ไม่มี leak/use-after-free (GC เก็บให้) — แต่แลกกับต้นทุน และความเสี่ยงย้ายไปอยู่ที่อื่น

สองคำถามที่เราทิ้งไว้ค้างและจะเฉลยในตอนถัดไป:

(1) ตลอดคอร์สนี้เราเขียน `gcc -o prog prog.c` แล้วก็รันได้เลย — แต่จริง ๆ แล้วระหว่าง "ไฟล์ .c" กับ "โปรแกรมที่รันได้" มีขั้นตอนอะไรซ่อนอยู่บ้าง **preprocess → compile → assemble → link** แต่ละขั้นทำอะไร และ `malloc`/`printf` ที่เราเรียกใช้ อยู่ที่ไหนกันแน่ ตอนไหนถึงมาอยู่ในโปรแกรมของเรา

(2) เราเห็น return address ถูกเขียนทับได้เพราะมันวางอยู่บน stack — แล้วถ้าเราอยากรู้ "ตำแหน่งที่แท้จริง" ของฟังก์ชัน `main` ในไฟล์โปรแกรมสุดท้าย (executable) จะดูได้ยังไง และทำไมบางทีโปรแกรมที่ "เชื่อม" พลาดถึงฟ้อง `undefined reference` ตอนคอมไพล์

## ภาคผนวกท้ายบท (ข้ามได้)

- **ขนาดจริงที่ `malloc` ปัดให้ (24/40/56/104 ไบต์) เป็นพฤติกรรมของ glibc** — ระบบอื่นหรือไลบรารีอื่น (macOS, musl, Windows) ปัดต่างกัน แต่หลักการ "ได้มากกว่าที่ขอ + ปัดกรอบ + เก็บหัวก้อน" เหมือนกัน · `malloc_usable_size()` เป็นฟังก์ชันเฉพาะ Linux ไม่มีข้ามระบบ
- **ผลรันของ UB ไม่ใช่ "กฎ"** — ค่าขยะที่เห็นหลัง `free` (เช่น `b1 b6 5c 55...` — เปลี่ยนทุกครั้ง) และการที่ `double_free` ถูกจับได้ทันที เป็นพฤติกรรมของ glibc 2.41 บนเครื่องนี้ — glibc รุ่นอื่น/ระบบอื่นอาจให้ค่าแตกต่าง หรือไม่จับ double free เลยก็ได้ นี่คือความหมายที่แท้จริงของคำว่า "undefined behavior": ไม่มีอะไรรับประกัน
- **`Bus error` vs `Segmentation fault`** — บนเครื่องนี้การกระโดดไป address ที่เป็น `0x4141...` (เขียนทับ return address ด้วย 'A') ให้ผลเป็น Bus error แต่บนระบบอื่น/สถาปัตยกรรมอื่นอาจเป็น Segmentation fault หรือพังแบบอื่น — ใจความคือ "โปรแกรมตายเพราะ return address ถูกทับ" ไม่ใช่ชื่อเฉพาะของสัญญาณ
- **ASan กับ Valgrind ใช้ร่วมกันได้** — ASan เหมาะกับช่วงพัฒนา (เร็ว ครอบคลุม buffer overflow + use-after-free + leak) ส่วน Valgrind เหมาะกับโปรแกรมที่คอมไพล์แล้วหรือไลบรารีที่แก้ซอร์สไม่ได้ — งานจริงนิยมรันทั้งคู่ใน CI (ระบบตรวจอัตโนมัติตอน push โค้ด)
- **เวอร์ชันที่ใช้ในบทความนี้** — GCC 14.2.0 (Debian 14.2.0-19) บน Linux aarch64, Go 1.24.4 linux/arm64, Valgrind 3.24.0, glibc ที่ติดมากับ Debian ณ วันที่เขียน 19 กันยายน 2026 · สเปคภาษา C ปัจจุบันคือ C23 (ISO/IEC 9899:2024) และ GCC 15 ขึ้นไปเปลี่ยน default เป็น `-std=gnu23` — แต่เราใช้ `-std=c17` เพื่อให้พฤติกรรมตรงกับที่สอนและรันได้เหมือนเดิมทุกเครื่อง ถ้าเครื่องคุณเป็น GCC รุ่นใหม่กว่า ข้อความ warning/error อาจต่างเล็กน้อยแต่ความหมายเหมือนกัน
