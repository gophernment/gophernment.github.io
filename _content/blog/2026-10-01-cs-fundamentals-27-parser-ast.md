# parser: recursive descent → AST — เปลี่ยน "คำ" ให้เป็น "ต้นไม้" (ตอนที่ 27)

ตอนที่แล้ว (ตอนที่ 26) เราสร้าง **lexer** เสร็จแล้ว — ตัวที่คอยตัดข้อความโปรแกรมออกเป็น "คำ" ที่เรียกว่า **token** ตอนที่ปิดท้ายเราเห็นภาพหนึ่งชัดมาก: token ที่ได้มาเรียงกันเป็น**เส้นแบน ๆ** ไม่มีต้นไม้ ไม่มีโครงสร้าง

```text
LET(let) IDENT(x) ASSIGN(=) NUMBER(3) PLUS(+) NUMBER(4) STAR(*) NUMBER(5) SEMI(;) ...
```

ประโยคสุดท้ายของตอนที่ 26 บอกไว้ว่า "lexer รู้จักคำ แต่ไม่รู้จักประโยค" — ตอนนี้เราจะสร้างตัวที่**รู้จักประโยค**ขึ้นมา มันชื่อว่า **parser**

> **parser** (อ่านว่า "พาร์เซอร์") = โปรแกรมที่อ่านลำดับ token แล้วประกอบมันขึ้นเป็น "ต้นไม้" ที่บอกว่า อะไรเป็นส่วนหนึ่งของอะไร งานของมันคือถามว่า "คำที่เรียงกันแบบนี้ เป็นประโยคที่ถูกไวยากรณ์ไหม และถ้าใช่ ความหมายของมันคือก้อนไหนบวกก้อนไหน"

ยินดีต้อนรับกลับเข้าสู่ระยะที่ 6 (Compiler/Interpreter) อีกครั้ง — ตอนนี้จะเป็นตอนที่เรา "เห็นภาพ" ของ compiler ชัดที่สุด เพราะผลงานของเราจะเป็นรูปเป็นร่างให้**มองด้วยตาได้จริง**

> **ที่อยู่ของโค้ดในตอนนี้:** ทุกอย่างอยู่ใน `course/code/ep27/`
> - **01–05** = โฟลเดอร์โปรแกรม แยกตามเลขโปรแกรม
> - **`out/`** = ผลรันจริงของทุกโปรแกรม — นอกจาก `00_env.txt` แล้ว ยังมีอีกสองไฟล์ที่**ไม่ใช่ผลรันโปรแกรม**: `06_drill_answer.out.txt` = **เฉลยโจทย์ท้ายบท** และ `07_go_real.out.txt` = ผลรันของโปรแกรมทดลองใน `_probe_go/` ที่เทียบกับ parser จริงของ Go
> - **`internal/parser/`** = parser ตัวเต็ม (13 ฟังก์ชัน) ที่ทุกโปรแกรมเรียกใช้ร่วมกัน — เปิดดูตามไปด้วยได้ตลอด

## 1. ปัญหา: เส้นแบนบอก "มีคำอะไร" แต่ไม่บอกว่า "อะไรกินอะไร"

ลองนึกภาพว่าเราเห็นแค่ **รายการคำ** ของนิพจน์หนึ่ง — รู้ว่ามีคำอะไรบ้าง แต่ไม่รู้ว่าใครเกาะกับใคร:

```text
คำที่มี: 3, +, 4, *, 5
```

รายการนี้ตรงกับทั้ง `3 + 4 * 5` และ `(3 + 4) * 5` (จริง ๆ ตรงกับอีกหลายแบบด้วย) แล้วถ้าถามว่า "เท่ากับเท่าไร" — คุณตอบไม่ได้เลย จนกว่าจะรู้ว่า `*` จับคู่กับอะไร: ถ้าเป็น `(3 + 4) * 5` คำตอบคือ 35 ถ้าเป็น `3 + (4 * 5)` คำตอบคือ 23 — **คำชุดเดียวกัน ความหมายต่างกัน** แค่เพราะ "กลุ่ม" ของมันต่างกัน

นี่คือปัญหาที่ lexer แก้ไม่ได้ ตัว lexer บอกได้แค่ "ในซอร์สโค้ดนี้มีคำว่า 3, +, 4, *, 5 เรียงตามลำดับนี้" แต่มัน**ไม่รู้จักกลุ่ม** เลย

คำถามต่อมาคือ แล้วเราจะแทน "กลุ่ม" ด้วยอะไร?

ลองคิดตามดู: `3 + (4 * 5)` เขียนใหม่เป็นวงเล็บซ้อนแบบไหนก็ได้ เพื่อให้เห็นความสัมพันธ์ว่า "5 อยู่กับ 4" และ "ก้อนนั้นอยู่กับ 3":

```text
บวก(3, คูณ(4, 5))
```

เขียนแบบนี้แล้ว ความหมาย**ชัดเจน ไม่กำกวมเลย** — และสังเกตว่าเราไม่ต้องมี `;` ไม่ต้องมี `(` `)` ไม่ต้องมีช่องว่างด้วยซ้ำ เพราะสิ่งที่เหลือคือ "ก้อนความหมาย" ล้วน ๆ

โครงสร้างแบบนี้ เรียกเป็นทางการว่า **AST**

> **AST** ย่อมาจาก **Abstract Syntax Tree** (อ่านว่า "แอบสแตรกต์ ซินแทกซ์ ทรี") = **ต้นไม้โครงสร้างโปรแกรม**
> - **Tree (ต้นไม้)** = โครงสร้างที่ของแต่ละชิ้นมี "ลูก" ได้ ของชิ้นบนเรียกว่า node แม่ (parent) ของชิ้นล่างเรียกว่า node ลูก (child)
> - **Syntax (วากยสัมพันธ์)** = โครงสร้างของประโยค — เรื่องที่ว่า "คำเรียงกันแบบนี้เป็นประโยคที่ถูกไหม"
> - **Abstract (นามธรรม)** = **ตัดรายละเอียดที่ไม่จำเป็นต่อความหมายทิ้งไปแล้ว** — คำว่า "abstract" นี่แหละที่บอกเราว่าต้นไม้ที่เราได้จะไม่มี `;` ไม่มี `(` `)` ไม่มี `{` `}` เหลืออยู่ เพราะเครื่องหมายพวกนี้มีไว้ให้**มนุษย์**อ่านกับให้**ตัวจัดกลุ่ม**เท่านั้น
> - **node** (อ่านว่า "โหนด") = ของแต่ละชิ้นบนต้นไม้ หนึ่งก้อน หนึ่งปม

![จากสตรีมแบน ๆ สู่ต้นไม้ AST](/assets/diagrams/ep27-01-pipeline.svg)

ภาพข้างบนคือภาพรวมทั้งตอน: ทางซ้ายคือซอร์สโค้ด ตรงกลางคือ lexer (ตอนที่ 26) ที่คาย **token stream** (ลำดับ token) ออกมาเป็นเส้นตรง แล้ว parser (ตอนนี้) เปลี่ยนเส้นตรงนั้นให้เป็น**ต้นไม้** ทางขวา

และช่องล่างสุดของแผนผังคือเส้นทางที่เหลือ: **parser → AST (ตอนนี้)** → **interpreter: tree-walking** (ตอนที่ 28 — ตัวรันโปรแกรมที่เดินตามต้นไม้) → **type/scope** (ตอนที่ 29) → **codegen** (ตอนที่ 30)

## 2. ต้นไม้ต้นแรก: parse นิพจน์ `3 + 4 * 5`

เราเริ่มจากของเล็กที่สุดเท่าที่จะเล็กได้เหมือนเคย (โปรแกรม `01_parse_expr`) — รับ "นิพจน์เดี่ยว" หนึ่งก้อน (นิพจน์ = ก้อนที่คำนวณออกมาเป็นค่าได้ เช่น `3 + 4`) แล้วโชว์ให้ดูว่าเส้นแบนกลายเป็นต้นไม้ได้ยังไง

ใน AST ของเรา node ทุกตัวแปลงตัวเองเป็นข้อความได้สองแบบ — เราใช้ทั้งคู่ตลอดตอนนี้:

1. **S-expression** (อ่านว่า "เอส-เอ็กซ์เพรสชัน") = เขียนต้นไม้เป็นวงเล็บซ้อน `(+ 3 (* 4 5))` — ตัว operation มาก่อน แล้วตามด้วยลูกของมัน **ข้อดีคืออ่าน "ใครเป็นลูกของใคร" จากซ้ายไปขวาได้ทันที** (S มาจาก Symbolic — สัญลักษณ์)
2. **ต้นไม้ย่อหน้า (indented tree)** = วาดเป็นเส้นแตกกิ่งลงมา ให้เห็นรูปร่างของต้นไม้ตรง ๆ

ผลรันจริงของโปรแกรม 01:

```text
-- "3 + 4 * 5" --
   1) lexer ตัดได้ 6 token: NUMBER(3) PLUS(+) NUMBER(4) STAR(*) NUMBER(5) EOF()
   2) S-expression: (+ 3 (* 4 5))
   3) ต้นไม้ AST:
      BinaryExpr +
      ├─ NumberLit 3
      └─ BinaryExpr *
         ├─ NumberLit 4
         └─ NumberLit 5
```

มาอ่านด้วยกันทีละส่วน (นี่คือท่าอ่านต้นไม้ที่เราจะใช้ตลอดคอร์ส):

- **`BinaryExpr +`** = "ก้อนนี้เป็น **binary expression**" (binary = สองฝั่ง) คือ operation ที่มี**สอง**ลูก — ของมันคือเครื่องหมาย `+` ตัวนี้มีลูกสองตัวตามที่เห็นขีดแตกออกไป
- **แขนขวา (`└─`) เป็น `BinaryExpr *` อีกก้อน** — คือ `4 * 5` ถูกประกอบเป็น**ก้อนเดียว**ก่อน แล้วก้อนนั้นค่อยมาเป็นลูกของ `+`
- **`NumberLit`** = "number literal" (literal = ค่าที่เขียนตรง ๆ ในโค้ด) — ใบไม้ที่ล่างสุด ต่อไปไม่ได้แล้ว
- **`EOF()`** ปรากฏในบรรทัด token แต่**ไม่ปรากฏในต้นไม้เลย** — เพราะ EOF (end of file = สัญญาณจบไฟล์) ไม่ใช่ของในโปรแกรม เราเก็บมันไว้แค่เพื่อรู้ว่า "หมดแล้ว" เหมือนป้ายบอกทาง ไม่ใช่ป้ายชื่อเมือง

นี่คือของที่ lexer ให้กับเรา (เส้นแบน) เทียบกับของที่ parser ให้ (ต้นไม้):

```text
lexer  : NUMBER(3) PLUS(+) NUMBER(4) STAR(*) NUMBER(5) EOF()     ← 6 token เรียงเป็นเส้นเดียว
parser : (+ 3 (* 4 5))                                          ← ต้นไม้ที่มีชั้น มีความสัมพันธ์
```

**จำนวน token กับจำนวนชิ้นบนต้นไม้ไม่เท่ากันก็ได้** และนั่นคือประเด็น: เครื่องหมาย `+` `*` กับ `EOF` ไม่ได้กลายเป็น "ใบไม้" ของต้นไม้ มันกลายเป็น "ปมที่เชื่อมลูกสองตัว" แทน

โปรแกรมเดียวกันยัง parse ตัวอย่างอื่นให้ดูด้วย ลองสังเกต `1 + 2 + 3` กับ `-x + 1`:

```text
-- "1 + 2 + 3" --
   2) S-expression: (+ (+ 1 2) 3)
      BinaryExpr +
      ├─ BinaryExpr +
      │  ├─ NumberLit 1
      │  └─ NumberLit 2
      └─ NumberLit 3

-- "-x + 1" --
   2) S-expression: (+ (- x) 1)
      BinaryExpr +
      ├─ UnaryExpr -
      │  └─ Ident x
      └─ NumberLit 1
```

- `1 + 2 + 3` ได้ `(+ (+ 1 2) 3)` — **จับกลุ่มซ้ายก่อน** (เขียนต่อกันแบบนี้เรียกว่า left-associative) ถ้าเราเขียน parser ให้กลายเป็น `(+ 1 (+ 2 3))` ผลบวกจะไม่ต่างกันในทางคณิตศาสตร์ แต่กับเครื่องหมายลบ/หารมันต่างกันทันที เช่น `10 - 3 - 2` ถ้าจับขวาก่อนจะได้ 10 - (3 - 2) = 9 ซึ่ง**ผิด**จากที่มนุษย์อ่าน
- `-x + 1` ได้ `(+ (- x) 1)` — เกิด node ชนิดใหม่คือ `UnaryExpr` (unary = ฝั่งเดียว) เพราะเครื่องหมายลบอยู่หน้า `x` ตัวเดียว ไม่ได้เชื่อมสองก้อน
- `Ident` = identifier = ชื่อที่เราตั้งเอง ซึ่ง parser ไม่ได้ไปถามว่า "x ประกาศไว้หรือยัง" — **งานนั้นเป็นของตอน type/scope (ตอนที่ 29)** parser ทำแค่ "โครงสร้าง"

โปรแกรมนี้ยังโชว์เคส `1` เดี่ยว ๆ ด้วย: ได้ `NumberLit 1` เป็นต้นไม้ที่มี **node เดียวทั้งต้น** — ย้ำว่า "ต้นไม้" ไม่ได้แปลว่าต้องมีหลายชั้น ใบไม้หนึ่งใบก็เป็นต้นไม้ได้

## 3. grammar: กฎไวยากรณ์ 1 ข้อ = ฟังก์ชัน 1 ตัว

ก่อนเขียนโค้ดต่อ เราต้องเขียน "กติกาของภาษา" ให้ชัดก่อน กติกานี้เรียกว่า **grammar** (อ่านว่า "แกรมม่าร์" = ไวยากรณ์)

> **grammar** = ชุดกฎที่บอกว่าประโยคในภาษานี้หน้าตาเป็นแบบไหนได้บ้าง
> วิธีที่ตำราใช้เขียนกฎนี้เรียกว่า **BNF** (Backus–Naur Form) รูปแบบคือ `ชื่อกฎ = รูปของมัน`
> - `|` อ่านว่า "หรือ"
> - `*` อ่านว่า "ซ้ำกี่ครั้งก็ได้ (รวมศูนย์ครั้ง)"
> - `?` อ่านว่า "มีหรือไม่มีก็ได้"
> - `"..."` อ่านว่า "ต้องเป็น token ชนิดนี้ตรง ๆ"

ไวยากรณ์ของภาษาจิ๋วของเรา 13 กฎ มีหน้าตาแบบนี้ (นี่คือข้อความจริงที่โปรแกรม 02 พิมพ์ออกมาจาก `parser.Rules` ในโค้ด) — ถ้าเพิ่งเริ่ม อ่านแค่ 3 แถวล่างสุดก่อนก็พอ (`factor`, `unary`, `primary`) ที่เหลือค่อยย้อนกลับมาอ่านทีหลัง:

| rule | = รูปของกฎ | → ฟังก์ชัน |
|---|---|---|
| `program` | `statement* EOF` | `ParseProgram` |
| `statement` | `letStmt \| ifStmt \| printStmt \| exprStmt` | `parseStatement` |
| `letStmt` | `"let" IDENT "=" expression ";"` | `parseLet` |
| `ifStmt` | `"if" expression block ("else" block)?` | `parseIf` |
| `printStmt` | `"print" expression ";"` | `parsePrint` |
| `exprStmt` | `expression ";"` | `parseExprStmt` |
| `block` | `"{" statement* "}"` | `parseBlock` |
| `expression` | `comparison` | `parseExpression` |
| `comparison` | `term (("==" \| "!=" \| "<" \| ">") term)*` | `parseComparison` |
| `term` | `factor (("+" \| "-") factor)*` | `parseTerm` |
| `factor` | `unary (("*" \| "/") unary)*` | `parseFactor` |
| `unary` | `("-" \| "+") unary \| primary` | `parseUnary` |
| `primary` | `NUMBER \| IDENT \| "true" \| "false" \| "(" expression ")"` | `parsePrimary` |

![กฎไวยากรณ์ 1 ข้อ = ฟังก์ชัน 1 ตัว](/assets/diagrams/ep27-04-grammar-func.svg)

อ่านตารางนี้จากบนลงล่าง: **ชั้นบน = จับหลวม (ตัดสินใจทีหลัง) · ชั้นล่าง = จับแน่น (ตัดสินใจก่อน = ถูกคำนวณก่อน)** — ทำไมถึงเป็นแบบนั้น เดี๋ยวหัวข้อ 4 จะเฉลย แต่ก่อนอื่นเรามาดู "กลเม็ด" ของทั้งเรื่องนี้ก่อน

### กลเม็ดที่ทั้งวงการใช้: recursive descent

เทคนิคที่เราจะใช้ชื่อว่า **recursive descent** (อ่านว่า "รีเคอร์ซีฟ ดิเซนต์")

> - **recursive** (รีเคอร์ซีฟ) = ฟังก์ชันที่เรียกตัวเองได้
> - **descent** (ดิเซนต์) = "ไล่ลง" — ไล่ลงจากกฎชั้นบน ลงไปหาชั้นล่าง
> - รวมกัน = **เขียน parser โดยไล่ลงตามกฎไวยากรณ์ทีละชั้น โดย "หนึ่งกฎไวยากรณ์ = หนึ่งฟังก์ชัน"**

พูดแบบสั้นที่สุด: **ตาราง 13 แถวข้างบน ก็คือรายชื่อฟังก์ชัน 13 ตัวในโค้ดของเรา** — คอลัมน์ขวาสุดคือชื่อฟังก์ชันจริง ๆ ที่ทำงานตามกฎนั้น

นี่คือเหตุผลที่วิธีนี้ได้รับความนิยมที่สุดในการเขียน parser ด้วยมือ (ไม่ใช่แค่ parser จิ๋วของเรา — parser ของ Go เองก็เขียนแบบนี้): **อ่านกฎในเอกสาร แล้วเดินไปเขียนฟังก์ชันตามชื่อกฎได้เลย** ไม่มีอะไรต้องตีความ ไม่มีตารางลึกลับให้จำ

มาดูโค้ดจริงของสองฟังก์ชันล่าง ๆ ที่ตรงกับกฎตรง ๆ ก่อน (จาก `internal/parser/parser.go`):

```go
// parseFactor — กฎ: factor = unary (("*" | "/") unary)*
func (p *Parser) parseFactor() (Expr, error) {
	left, err := p.parseUnary()      // ← ตามกฎ: เริ่มจาก "unary" ทางซ้ายมือ
	if err != nil {
		return nil, err
	}
	for p.check(lexer.STAR) || p.check(lexer.SLASH) {   // ← ตามกฎ: ((* | /) ...)*
		op := p.advance()
		right, err := p.parseUnary() // ← ตามกฎ: "unary" อีกตัวทางขวา
		if err != nil {
			return nil, err
		}
		left = &BinaryExpr{Op: op.Literal, OpTok: op, Left: left, Right: right}
	}
	return left, nil
}
```

เทียบกฎกับโค้ดทีละท่อน จะเห็นว่ามันคือรูปเดียวกัน:

```text
กฎ    : factor   = unary   (("*" | "/")  unary  )*
โค้ด  : parseFactor → parseUnary()  ,   วงวนตรวจ STAR/SLASH → parseUnary() อีกครั้ง
```

กับดักที่มือใหม่เจอบ่อยตรงนี้มีข้อเดียว: `parseFactor` **เรียก `parseUnary` (ชั้นล่าง) ไม่ใช่เรียก `parseFactor` ตัวเองหรือชั้นบน** ให้ยึดหลักว่า "ชั้นไหนเรียกชั้นล่าง ฝั่งซ้ายและฝั่งขวาก็ต้องเป็นชั้นล่าง" แล้วรูปของกฎจะตรงเสมอ

และดู `parsePrimary` — ชั้นล่างสุด ที่เป็นจุดที่วงเล็บทำงาน:

```go
// parsePrimary — กฎ: primary = NUMBER | IDENT | "true" | "false" | "(" expression ")"
func (p *Parser) parsePrimary() (Expr, error) {
	tok := p.cur()
	switch tok.Type {
	case lexer.NUMBER:
		p.advance()
		n, err := NumberValue(tok)
		if err != nil {
			return nil, &Error{Pos: tok.Pos, Msg: err.Error()}
		}
		return &NumberLit{Value: n, Text: tok.Literal, At: tok.Pos}, nil
	case lexer.IDENT:
		p.advance()
		return &Ident{Name: tok.Literal, At: tok.Pos}, nil
	case lexer.TRUE, lexer.FALSE:
		p.advance()
		return &BoolLit{Value: tok.Type == lexer.TRUE, At: tok.Pos}, nil
	case lexer.LPAREN:
		// เจอ "(" → "รีเซ็ต" กลับไปเริ่มที่ expression ชั้นบนสุดอีกครั้ง
		p.advance()
		e, err := p.parseExpression()
		if err != nil {
			return nil, err
		}
		if _, err := p.expect(lexer.RPAREN, "')' to close group"); err != nil {
			return nil, err
		}
		return e, nil
	}
	// ... (ต่อด้วยการคืน error — ดูหัวข้อ 9)
}
```

บรรทัดสำคัญที่สุดในทั้งตอนอาจเป็น `p.parseExpression()` ใน `case lexer.LPAREN` — **พอเจอ `(` parser จะกระโดดกลับขึ้นไปชั้นบนสุดใหม่** นั่นคือกลไกที่ทำให้วงเล็บ "บังคับกลุ่ม" ได้ ไม่ว่าเรากำลังอยู่ลึกแค่ไหนตอนเจอมัน และผลลัพธ์ก็คือวงเล็บถูก**ทิ้งไปเลย** — เพราะมันทำหน้าที่เสร็จแล้ว นี่คือความหมายของคำว่า "abstract" ที่เราพูดถึงในหัวข้อ 1

ศัพท์ที่ต้องรู้ก่อนไปต่อ (จะโผล่ในโค้ดข้างบน):

- **`func (p *Parser) parseFactor() (Expr, error)`** = ฟังก์ชันที่ผูกกับ `Parser` (เขียน `(p *Parser)` หน้า ชื่อฟังก์ชัน) เรียกใช้ได้ว่า `p.parseFactor()` — วิธีนี้ทำให้ทุกฟังก์ชันของ parser แชร์ "นิ้ว" (`p.pos`) ตัวเดียวกันได้
- **`Expr`** = ชนิดข้อมูลแบบ interface ของเรา หมายถึง "node อะไรก็ได้ที่เป็นนิพจน์" — คืนค่ามาเป็น `Expr` แล้วผู้เรียกจะไม่ต้องรู้ว่าได้ต้นไม้รูปอะไร
- **`error`** = ชนิดข้อมูลของ "ความผิดพลาด" ใน Go — ฟังก์ชันที่อาจล้มเหลวคืนสองค่า: ของที่ต้องการ กับ error
- **`nil`** (อ่านว่า "นิล") = "ไม่มีค่า" — ตรงช่อง error หมายถึง "ไม่มี error"; ตรงช่องของอื่นหมายถึง "ว่างเปล่า"
- **`tok.Literal`** = ข้อความจริงของ token (เช่น `"+"`) · **`tok.Pos`** = ตำแหน่งบรรทัด:คอลัมน์ของ token นั้น
- **`&BinaryExpr{...}`** = สร้างก้อน node ขึ้นมาแล้วส่ง "ที่อยู่ของมัน" (ตัว `&`) ออกไป — เราใช้ pointer (ตัวชี้) เพราะต้นไม้โตขึ้นได้เรื่อย ๆ และหลายที่อ้างถึง node เดียวกัน
- **`p.advance()`** = ขยับ "นิ้ว" ไปหนึ่ง token · **`p.check(ชนิด)`** = ดูว่าตอนนี้ชี้อยู่ที่ token ชนิดนั้นไหม (ยังไม่ขยับ) · **`p.cur()`** = token ที่นิ้วชี้อยู่

## 4. precedence: ทำไม `3 + 4 * 5` ต้องเป็น `3 + (4 × 5)`

นี่คือหัวใจของทั้งตอน และเป็นเรื่องที่เข้าใจง่ายมากถ้ามองจากภาพ

> **precedence** (อ่านว่า "เพรสซิเดนซ์") = **ลำดับความสำคัญของเครื่องหมาย** — ตัวไหน "จับแน่นกว่า" กัน กฎสากลคือ `*` `/` จับแน่นกว่า `+` `-` และ `==` จับหลวมกว่าเลขคณิตทั้งหมด

คำถามคือ parser ของเรารู้เรื่องนี้ได้ยังไง ในเมื่อเรา**ไม่เคยเขียนโค้ดบอกเลยว่า `*` มาก่อน `+`**?

คำตอบคือ: **เรื่องนี้ถูกกำหนดไว้ใน "ลำดับชั้นของกฎไวยากรณ์" ตั้งแต่ต้นแล้ว ไม่ต้องเขียนเพิ่มแม้แต่บรรทัดเดียว**

ดูสองกฎนี้ช้า ๆ:

```text
term   = factor (("+" | "-") factor)*        ← ชั้นของ + –   แต่มันเรียก "factor" เป็นลูก
factor = unary (("*" | "/") unary)*          ← ชั้นของ * /   อยู่ "ลึกกว่า" term หนึ่งชั้น
```

อ่านกฎแล้วถามว่า: ตอนที่ `parseTerm` กำลังอ่าน `3 + 4 * 5` พอเจอ `+` แล้วมันจะหาลูกฝั่งขวาได้ยังไง → มันเรียก `parseFactor` → `parseFactor` **อ่าน `4 * 5` ให้เสร็จเป็นก้อนเดียว** (เพราะกฎของมันคือ "จับ `*` กับ `/` ให้หมดก่อน") แล้วค่อยคืนก้อนนั้นกลับมาให้ `+` → ผลคือ `+` ได้ลูกฝั่งขวาเป็น `(4 * 5)` **ทั้งก้อน**

พูดอีกแบบ: **`*` ไม่ได้ "สูงกว่า" เพราะเราบอกว่าให้สูง — มันสูงกว่าเพราะมันอยู่ลึกกว่า** และการที่มันอยู่ลึกกว่า แปลว่า "ฟังก์ชันที่จัดการมันถูกเรียกทีหลัง ระหว่างที่ของชั้นบนกำลังหาลูก" (เรียกทีหลัง แต่**ประกอบเสร็จก่อน**)

มาดูต้นไม้จริงของสองนิพจน์จากโปรแกรม 01 วางเทียบกัน (ต้นไม้ชุดเดียวกัน ใช้วงเล็บต่างกัน):

![ทำไม 3 + 4 * 5 จึงเป็น 3 + (4 × 5)](/assets/diagrams/ep27-02-ast-tree.svg)

```text
-- "3 + 4 * 5" --                          -- "(3 + 4) * 5" --
   1) lexer ตัดได้ 6 token                    1) lexer ตัดได้ 8 token
   2) S-expression: (+ 3 (* 4 5))            2) S-expression: (* (+ 3 4) 5)
      BinaryExpr +                              BinaryExpr *
      ├─ NumberLit 3                            ├─ BinaryExpr +
      └─ BinaryExpr *                           │  ├─ NumberLit 3
         ├─ NumberLit 4                         │  └─ NumberLit 4
         └─ NumberLit 5                         └─ NumberLit 5
```

สองต้นนี้ต่างกันสิ้นเชิง และค่าเมื่อคำนวณจริง (จากโปรแกรม 05) ก็ต่างกัน:

```text
3 + 4 * 5     = 23        (บวกทีหลัง: คูณก่อน)
(3 + 4) * 5   = 35        (วงเล็บบังคับ: บวกก่อน)
```

จุดที่ต้องจำให้ขึ้นใจจากหัวข้อนี้คือ **`(` ไม่ได้ทำอะไรวิเศษ** — มันแค่เรียก `parseExpression` อีกรอบจากชั้นล่างสุด (`parsePrimary`) ผลคือ "การอ่านเริ่มนับหนึ่งใหม่จากชั้นบนสุด" ตัววงเล็บเองจบหน้าที่แล้วก็ถูกทิ้งไป ไม่เหลือในต้นไม้

และในมุมกลับกัน: **การเรียงชั้นของกฎคือตัวกำหนด semantics (อ่านว่า "ซีแมนติกส์" = ความหมายของสิ่งที่โค้ดทำ) ทั้งหมด** ถ้าสลับชั้น `term` กับ `factor` เราจะได้ `3 + 4 * 5` เป็น `(* (+ 3 4) 5) = 35` ทันที — ผิดจากที่มนุษย์อ่าน กับดักข้อนี้อยู่ในโปรแกรม 05 หัวข้อ 10

## 5. call chain จริง: ไล่ลงหกชั้นแล้วค่อยประกอบกลับ

ทฤษฎีในหัวข้อ 4 ฟังดูดี แต่จะดีกว่านี้มากถ้าเรา**เห็นกับตา**ว่าโปรแกรมเราทำจริงแบบนั้น

โปรแกรม 02 จึงมีสวิตช์พิเศษ: `parser.Trace` — เป็น field ชนิดฟังก์ชัน ถ้าเราใส่ค่าเข้าไป parser จะเรียกมันทุกครั้งที่ "ไล่ลงชั้นใหม่" ถ้าไม่ใส่ (เป็น `nil`) มันก็ไม่ทำอะไรเลย นี่เป็นท่าเขียนโค้ดที่ใช้กันจริงเวลาเราต้องการ "ดู" โปรแกรมที่เดินซับซ้อน โดยไม่ต้องแก้ logic ข้างใน

> **field** (อ่านว่า "ฟีลด์") = ช่องข้อมูลใน struct (โครงสร้างข้อมูล) · **รุปแบบนี้เรียกว่า callback** (อ่านว่า "คอลแบ็ก") = ฟังก์ชันที่เราส่งไปให้โปรแกรมอื่นเรียกกลับ

ผลรันจริงของ trace สำหรับ `3 + 4 * 5` (ทั้ง 11 บรรทัด):

```text
== B) call chain จริงของ "3 + 4 * 5" ==
  (depth มาก = ลึกกว่า · "token ปัจจุบัน" = token ที่นิ้วชี้ตอนเข้าฟังก์ชัน)
  → parseExpression token ปัจจุบัน: NUMBER "3"
    → parseComparison token ปัจจุบัน: NUMBER "3"
      → parseTerm       token ปัจจุบัน: NUMBER "3"
        → parseFactor     token ปัจจุบัน: NUMBER "3"
          → parseUnary      token ปัจจุบัน: NUMBER "3"
            → parsePrimary    token ปัจจุบัน: NUMBER "3"
        → parseFactor     token ปัจจุบัน: NUMBER "4"
          → parseUnary      token ปัจจุบัน: NUMBER "4"
            → parsePrimary    token ปัจจุบัน: NUMBER "4"
          → parseUnary      token ปัจจุบัน: NUMBER "5"
            → parsePrimary    token ปัจจุบัน: NUMBER "5"
```

![call chain ของ recursive descent](/assets/diagrams/ep27-03-callchain.svg)

อ่าน trace นี้ทีละช่วง แล้วมันจะเล่าทั้งเรื่องของ parser ให้ฟัง:

**ช่วงที่ 1 (บรรทัดที่ 1–6) — ไล่ลงเฉย ๆ** สังเกตว่าทุกชั้นยังชี้ token **ตัวเดียวกัน** คือ `NUMBER "3"` เพราะ**ยังไม่มีการตัดสินใจอะไรเลย** ทุกฟังก์ชันแค่เรียกชั้นล่างต่อ ("ตรงนี้ฉันยังไม่รู้ ไปถามชั้นล่างก่อน") จนถึงชั้นล่างสุดที่เจอของจริงคือเลข 3 แล้วคืน `NumberLit 3` กลับขึ้นมา

**ช่วงที่ 2 (บรรทัดที่ 7) — กลับเข้า `parseFactor` อีกครั้ง แต่คราวนี้เจอ `NUMBER "4"`** หมายความว่า: ตอนนั้นเราอยู่ใน `parseTerm` ซึ่งอ่านได้ `3` แล้ว พอมองเห็น token ถัดไปเป็น `+` มันจึง**กิน `+`** แล้วเรียก `parseFactor` อีกรอบเพื่อหาลูกฝั่งขวา — และนี่คือจุดที่ "token ปัจจุบัน" ขยับจาก `3` มาเป็น `4` เป็นครั้งแรก

**ช่วงที่ 3 (บรรทัดที่ 8–9)** `parseFactor` อ่านได้ `4` แล้วมองเห็น `*` → กิน `*` → เรียก `parseUnary` → `parsePrimary` ได้ `5` → **ประกอบเป็น `(* 4 5)` แล้วคืนกลับขึ้นไป**

สรุปสั้น ๆ ว่าเกิดอะไรขึ้นในหัวเรา:

```text
parseTerm  : 3  เห็น +  → เรียก parseFactor ฝั่งขวา → ได้ (* 4 5)  → ประกอบเป็น (+ 3 (* 4 5))
parseFactor: 4  เห็น *  → เรียก parseUnary   ฝั่งขวา → ได้ 5        → ประกอบเป็น (* 4 5)
```

และนี่คือเหตุผลที่ตัวตนของ **"ความลึกของชั้น"** = **precedence**: `*` ถูกประกอบเป็นก้อนเสร็จเรียบร้อย (อยู่ในช่วงที่ 3) **ก่อน**ที่ `+` จะได้ลูกของตัวเองครบทั้งสองข้าง (จบช่วงที่ 2) — `+` เลยต้องถือก้อนที่ประกอบเสร็จแล้ว ทั้งหมดนี้เกิดขึ้นเองโดยที่เราไม่ต้องเขียน if อะไรเพิ่มเลย

tail ของผลรันโปรแกรม 02 คือต้นไม้ที่ได้ ซึ่งตรงกับที่โปรแกรม 01 แสดงไว้เป๊ะ (เราตรวจกันเองแบบนี้อีกชั้นด้วย):

```text
== C) ผลลัพธ์ ==
  S-expression: (+ 3 (* 4 5))
  ต้นไม้ AST:
    BinaryExpr +
    ├─ NumberLit 3
    └─ BinaryExpr *
       ├─ NumberLit 4
       └─ NumberLit 5
```

## 6. AST node types: ของทุกชิ้นบนต้นไม้มีหน้าตาเป็นยังไง

ตอนนี้เราพร้อมจะเปิดฝาดู "ของ" ที่เราใช้สร้างต้นไม้แล้ว — ทั้งหมดอยู่ในไฟล์ `internal/parser/ast.go`

จุดแรกคือข้อตกลงว่า node ทุกตัวต้องทำอะไรได้บ้าง — เขียนเป็น `interface`

> **interface** (อ่านว่า "อินเทอร์เฟซ") = "สัญญา" ที่บอกว่า ของชนิดนี้ต้องมีฟังก์ชันอะไรบ้าง ถ้าชนิดไหนมีฟังก์ชันครบตามสัญญา ก็ถือว่าเป็นไปตาม interface นั้นโดยอัตโนมัติ (ไม่ต้องประกาศว่าสืบทอดจากใคร)

```go
// Node — ของทุกชิ้นใน AST ต้องทำได้สองอย่าง
//
//   - Pos() บอกว่าตัวเอง "อยู่ตรงไหน" ในไฟล์ (ใช้รายงาน error ให้มนุษย์อ่านออก)
//   - String() แปลงตัวเองเป็นข้อความแบบ S-expression
type Node interface {
	Pos() lexer.Position
	String() string
}
```

จากนั้นแยกเป็นสองตระกูล — เพราะของในโปรแกรมมีสองบทบาทที่ไม่เหมือนกัน:

```go
// Stmt — หมวด "คำสั่ง" (statement) = ประโยคที่สั่งให้โปรแกรมทำอะไรสักอย่าง
type Stmt interface {
	Node
	stmtNode()
}

// Expr — หมวด "นิพจน์" (expression) = ก้อนที่ "คำนวณออกมาเป็นค่า" ได้
type Expr interface {
	Node
	exprNode()
}
```

- **statement** (อ่านว่า "สเตตเมนต์") = คำสั่ง เช่น `let x = 3; print x; if y > 10 { ... }` — สั่งให้ทำอะไร
- **expression** (อ่านว่า "เอ็กซ์เพรสชัน") = นิพจน์ เช่น `3 + 4`, `x` — คำนวณออกมาเป็นค่า

ฟังก์ชัน `stmtNode()` กับ `exprNode()` **ไม่ได้ทำอะไรเลย** (ไม่มีโค้ดข้างใน) มันมีไว้ "ติดป้าย" ว่าชนิดนี้เป็น Stmt หรือ Expr เท่านั้น ท่าแบบนี้มีชื่อว่า **marker method** และข้อดีของมันคือ: ถ้าเราลืมส่ง node ให้ถูกหมวด คอมไพเลอร์ (ตัวแปลภาษา — ดูตอนที่ 26) จะฟ้องตั้งแต่ตอน build (สั่งสร้างโปรแกรม) ไม่ต้องรอไปพังตอนรัน

นี่คือ node ตระกูล Stmt/Expr ทั้ง 10 ตัวของเรา บวก `Block` อีก 1 (รวมเป็น 11 แถวด้านล่าง)

| node | เป็นหมวด | หมายถึง |
|---|---|---|
| `Program` | ต้นไม้ทั้งต้น | ลูก = คำสั่งทุกคำสั่ง เรียงตามลำดับในไฟล์ |
| `LetStmt` | Stmt | `let NAME = VALUE;` |
| `IfStmt` | Stmt | `if CONDITION BLOCK` และ `else BLOCK` ถ้ามี |
| `PrintStmt` | Stmt | `print EXPR;` |
| `ExprStmt` | Stmt | นิพจน์เปล่า ๆ ปิดด้วย `;` |
| `Block` | (ใน IfStmt) | กลุ่มคำสั่งที่ครอบด้วย `{ }` |
| `BinaryExpr` | Expr | สองฝั่งกับเครื่องหมายกลางหนึ่งตัว เช่น `3 + 4` |
| `UnaryExpr` | Expr | เครื่องหมายนำหน้าหนึ่งตัว เช่น `-x` |
| `NumberLit` | Expr | ตัวเลขตรง ๆ ในโค้ด |
| `Ident` | Expr | ชื่อที่อ้างถึง เช่นตัวแปร `x` |
| `BoolLit` | Expr | `true` หรือ `false` |

(ตารางมี 11 แถวเพราะนับ `Block` มาด้วย ซึ่งไม่ใช่ทั้ง Stmt และ Expr แต่เป็น node ที่ `IfStmt` ใช้เก็บลูกของตัวเอง — ตัวอย่างของจริงมักมีของ "ในหมวด" มากกว่าสองแบบเสมอ)

ดูของสองตัวที่สำคัญที่สุด — `BinaryExpr` ที่ทำให้ต้นไม้แตกกิ่ง และ `Block` ที่ทำให้ `if` มีลำตัว:

```go
// BinaryExpr — นิพจน์ที่ประกอบด้วยสองฝั่งกับเครื่องหมายกลางหนึ่งตัว เช่น 3 + 4
type BinaryExpr struct {
	Op    string      // เครื่องหมาย เช่น "+" "*" "=="
	OpTok lexer.Token // token ของเครื่องหมาย (เก็บตำแหน่งไว้รายงาน error)
	Left  Expr        // ฝั่งซ้าย
	Right Expr        // ฝั่งขวา
}

func (e *BinaryExpr) Pos() lexer.Position { return e.OpTok.Pos }
func (e *BinaryExpr) String() string {
	return "(" + e.Op + " " + e.Left.String() + " " + e.Right.String() + ")"
}
```

```go
// Block — กลุ่มคำสั่งที่ครอบด้วย { }
type Block struct {
	Stmts []Stmt
	At    lexer.Position // ตำแหน่งของ '{'
}
```

สองจุดที่ควรสังเกต:

1. **`Left` กับ `Right` เป็นชนิด `Expr` (interface) ไม่ใช่ `*BinaryExpr`** — แปลว่าลูกของ `+` จะเป็นนิพจน์อะไรก็ได้: เลข, ชื่อ, การคูณ, หรือวงเล็บก็ได้ **นี่คือ "ความเรียกซ้ำ" (recursive) ที่อยู่ในตัวชนิดข้อมูลเอง** — ต้นไม้คือ "ของที่มีลูกเป็นของอย่างเดียวกัน" และเพราะ Go ให้เราประกาศแบบนี้ได้ มันจึงรองรับต้นไม้ลึกไม่จำกัดชั้นโดยไม่ต้องเขียนโค้ดอะไรเพิ่ม
2. **ทุก node เก็บ `Pos`** — ไม่มีข้อยกเว้น นี่ไม่ใช่ของประดับ แต่คือสิ่งที่ทำให้ error ของ parser บอกได้ว่า "บรรทัดไหน คอลัมน์ไหน" (หัวข้อ 9)

และนี่คือท่าที่ใช้ "เดินดู" ต้นไม้ทั้งต้นได้โดยไม่ต้องรู้จักชนิด node ทุกตัว — ฟังก์ชัน `Children` ที่คืน "ลูกของ node นี้":

```go
// Children — ลูกของ node นี้ (node ที่ไม่มีลูกจะคืน nil)
// ใช้เดินดูต้นไม้ทั้งต้นได้โดยไม่ต้องรู้จัก type ทุกตัว
func Children(n Node) []Node { return childrenOf(n) }

// childrenOf คือฟังก์ชันที่รู้จัก node ทุกชนิด แล้วคืนลูกของมัน
// (อยู่ใน ast.go — เป็น switch ตามชนิด node ไม่ต้องไล่อ่านก็ได้)
```

ฟังก์ชันหนึ่งตัวแค่นี้ก็พอให้เดินทั้งต้นไม้ได้แล้ว — เรียก `Children` ที่ราก แล้วเรียกซ้ำกับทุกตัวที่ได้ จนกว่าจะไม่มีลูก นี่คือท่า **tree walking** ที่ตอนที่ 28 (interpreter) จะใช้รันโปรแกรมของเราจริง ๆ

## 7. สองวิธี "ดู" AST: ต้นไม้ย่อหน้า กับ S-expression

ตรวจงาน AST ด้วยตาเปล่าไม่ได้ ถ้าต้นไม้มี 30 node แล้วพิมพ์เป็น struct ดิบ ๆ เราจะอ่านไม่ออกเลย เราจึงมีสองวิธี "แปลงต้นไม้เป็นข้อความ" ซึ่งให้สองอย่างที่ต่างกัน:

**แบบที่ 1: S-expression (`String`)** ตอบคำถามว่า "ก้อนนี้ประกอบด้วยอะไร" — สังเกตว่า `String()` ของแต่ละ node ก็เรียก `String()` ของลูกตัวเองด้วย (เรียกซ้ำอีกแล้ว) ช่างสั้นจริง ๆ:

```go
func (e *BinaryExpr) String() string {
	return "(" + e.Op + " " + e.Left.String() + " " + e.Right.String() + ")"
}
```

**แบบที่ 2: ต้นไม้ย่อหน้า (`Tree`)** ตอบคำถามว่า "ใครเป็นลูกของใคร ลึกแค่ไหน" — ของแบบนี้ทำด้วยการ **ส่งต่อ "คำนำหน้าบรรทัด" ลงไปให้ลูกรู้ด้วย** เพื่อให้รู้ว่าต้องวาดเส้นต่อยังไง:

```go
// Tree — พิมพ์ AST เป็น "ต้นไม้ย่อหน้า" ให้คนดูออกด้วยตา
func Tree(n Node) string {
	var b strings.Builder
	writeTree(&b, n, "", true, true)
	return strings.TrimRight(b.String(), "\n")
}

func writeTree(b *strings.Builder, n Node, prefix string, isLast, root bool) {
	conn := ""
	if !root {
		if isLast {
			conn = "└─ "          // ลูกตัวสุดท้าย — ใช้มุมปิด
		} else {
			conn = "├─ "          // ยังมีพี่น้องต่อ — ใช้เส้นตั้งให้ลากลง
		}
	}
	b.WriteString(prefix + conn + NodeLabel(n) + "\n")

	kids := childrenOf(n)
	for i, k := range kids {
		childPrefix := prefix
		if !root {
			if isLast {
				childPrefix += "   "   // แม่เป็นตัวสุดท้าย → ลูกก็ไม่ต้องมีเส้นตั้ง
			} else {
				childPrefix += "│  "   // แม่ยังมีพี่น้อง → ลากเส้นตั้งต่อลงมา
			}
		}
		writeTree(b, k, childPrefix, i == len(kids)-1, false)
	}
}
```

หัวใจของมันอยู่ที่ `childPrefix` — คำนำหน้าที่**ส่งต่อ**ลงไปให้ลูกลึกขึ้นเรื่อย ๆ (`"   "` กับ `"│  "` สลับกันตามว่าแม่เป็นลูกตัวสุดท้ายไหม) ถ้าเรารู้สึกว่าโค้ดนี้ "ซับซ้อนกว่าที่ควร" ให้มองแบบนี้: มันคือการ "สืบทอดประวัติว่าบรรพบุรุษเป็นลูกคนสุดท้องหรือไม่" ลงไปยังชั้นลึกสุด

สังเกตบรรทัด `var b strings.Builder` — `strings.Builder` (อ่านว่า "สตริงส์ บิลเดอร์") = ตัวช่วยต่อข้อความที่มีประสิทธิภาพใน Go (การต่อ string ตรง ๆ ด้วย `+` ในวงวนจะช้ากว่ามากเพราะ Go ต้องคัดลอกข้อความใหม่ทุกครั้ง)

## 8. parse โปรแกรมเต็ม: `let` / `if` / `else` / `print`

ถึงตรงนี้เรามี parser ที่รองรับ "นิพจน์" แล้ว แต่ภาษาที่เราเขียนในตอนที่ 26 ยังมี **คำสั่ง** ด้วย โปรแกรม 03 จึง parse โปรแกรมเต็ม ๆ สามตัว ไล่เก็บผลรันจริง:

**โปรแกรม A — ตัวอย่างหลักของคอร์ส:**

```text
  1 | let x = 3 + 4 * 5;
  2 | let y = (x - 2) * 2;
  3 | if y > 10 { print y; }
  token: 30 ตัว · statement: 3 คำสั่ง
  S-expression: (program (let x (+ 3 (* 4 5))) (let y (* (- x 2) 2)) (if (> y 10) (block (print y))))
```

ต้นไม้เต็มของมัน (ต้นไม้จริงจากผลรัน — ไม่ได้วาดใหม่):

```text
Program
├─ LetStmt let x
│  └─ BinaryExpr +
│     ├─ NumberLit 3
│     └─ BinaryExpr *
│        ├─ NumberLit 4
│        └─ NumberLit 5
├─ LetStmt let y
│  └─ BinaryExpr *
│     ├─ BinaryExpr -
│     │  ├─ Ident x
│     │  └─ NumberLit 2
│     └─ NumberLit 2
└─ IfStmt
   ├─ BinaryExpr >
   │  ├─ Ident y
   │  └─ NumberLit 10
   └─ Block
      └─ PrintStmt
         └─ Ident y
```

อ่านสี่อย่างจากต้นนี้:

- **`Program` เป็นรากเดียวที่ห่อทุกอย่าง** — ลูก 3 ตัวคือ 3 คำสั่ง เรียงตามบรรทัดในไฟล์เป๊ะ (ลำดับสำคัญมาก เพราะตอนรันจริง โปรแกรมจะทำบนลงล่าง)
- **`LetStmt let y` มีลูกตัวเดียว** (ไม่ใช่สอง!) — เพราะชื่อตัวแปร `y` เก็บเป็นข้อความ (`Name string`) ไม่ได้เป็นต้นไม้ ส่วนลูกที่มีคือ "ค่าที่จะไปใส่ใน y" เท่านั้น
- **`IfStmt` มีลูก 2 ตัวในเคสนี้** (เงื่อนไข + บล็อก) ถ้ามี `else` จะมี 3 ตัว — เคสนี้ไม่มี `else` เลยมีแค่ 2
- **`Block` เป็นท่อนที่ทำให้ `if` มี "ตัว"** และภายใน `Block` ก็เก็บ `PrintStmt` ซึ่งมี `Ident y` เป็นลูก — เห็นได้ชัดว่า "คำสั่งซ้อนในบล็อก" กลายเป็น "ชั้นที่ลึกลงไปในต้นไม้"

**โปรแกรม B — เพิ่ม `else` / `true` / `==` / เครื่องหมายลบหน้า:**

```text
  1 | let ok = true;
  2 | let z = -(x + 1);
  3 | if z == 0 { print ok; } else { print z; }
  token: 31 ตัว · statement: 3 คำสั่ง
  S-expression: (program (let ok true) (let z (- (+ x 1))) (if (== z 0) (block (print ok)) (block (print z))))
```

สังเกต `(let z (- (+ x 1)))` — ลบที่อยู่หน้า `(x + 1)` กลายเป็น `UnaryExpr` ที่มีลูกเป็นวงเล็บทั้งก้อน และสังเกตว่า `IfStmt` ของโปรแกรมนี้มี **สอง `Block`** ต่อท้ายเงื่อนไข นั่นคือ `then` กับ `else`

**โปรแกรม C — เพิ่ม `/` `<` `!=` `false`:**

```text
  1 | let t = 20 / 4;
  2 | if t < 6 { print false; }
  3 | if t != 5 { print t; }
  token: 26 ตัว · statement: 3 คำสั่ง
  S-expression: (program (let t (/ 20 4)) (if (< t 6) (block (print false))) (if (!= t 5) (block (print t))))
```

และนี่คือผลตอบแทนที่จ่ายออกมาแล้วจากตอนที่ 26 ที่เราบ่นว่ามี "7 ชนิดที่ยังไม่เคยถูกใช้เลย" — ตอนนี้ตัวอย่างทั้งสามของเรา**ใช้ชนิด token ครบทุกตัวที่ภาษามี**:

```text
== สรุป: ชนิด token ที่โผล่ในตัวอย่างทั้ง 3 โปรแกรม ==
  ใช้ไป 23/23 ชนิด
  ยังไม่ถูกใช้เลย: ไม่มี — ครบทุกชนิด
  นับรายชนิด:
    NUMBER 12
    IDENT  15
    LET    5
    IF     4
    ELSE   1
    TRUE   1
    FALSE  1
    PRINT  5
    PLUS   2
    MINUS  2
    STAR   2
    SLASH  1
    ASSIGN 5
    EQ     1
    NEQ    1
    LT     1
    GT     1
    LPAREN 2
    RPAREN 2
    LBRACE 5
    RBRACE 5
    SEMI   10
    EOF    3
```

`EOF 3` ก็คือ "3 โปรแกรม" — และ `SEMI 10` ที่มากที่สุดในบรรดาเครื่องหมาย ไม่ใช่เรื่องบังเอิญ: ภาษาที่ใช้ `;` ปิดคำสั่งจะให้ parser เห็น `;` เกือบทุกก้าว

## 9. error: บอก "ตรงไหน" และ "คาดหวังอะไร vs เจออะไร"

ถึงส่วนที่ทำให้ parser ต่างจากโปรแกรมสาธิตทั่วไป — **error handling** โปรแกรม 04 ทดลอง 8 เคส แล้วเก็บผลรันจริง ทั้งหมดนี้ **รัน lexer ก่อน แล้วค่อยรัน parser** เพื่อให้เห็นเส้นแบ่งงานจากตอนที่ 26 ชัด ๆ

รูปแบบการรายงานของเราเอาสูตรเดียวกับ lexer:

```text
line <บรรทัด>, column <คอลัมน์>: expected <สิ่งที่ต้องการ>, found <สิ่งที่เจอ>
```

ดูของจริงสองเคสที่เราเตรียมไว้ตั้งแต่ตอนที่ 26 (เคสที่ lexer ผ่านสบาย ๆ แต่ parser ต้องเป็นคนจับ):

```text
-- [1] นิพจน์มีเครื่องหมายติดกัน --
   โค้ด 1 | 1 + * 3
   lexer : ตัดได้ 5 token — ผ่าน  (NUMBER(1) PLUS(+) STAR(*) NUMBER(3) EOF())
   parser: error → line 1, column 5: expected expression, found STAR "*"

-- [2] ใช้ '<=' ที่ภาษายังไม่มี --
   โค้ด 1 | x <= 5
   lexer : ตัดได้ 5 token — ผ่าน  (IDENT(x) LT(<) ASSIGN(=) NUMBER(5) EOF())
   parser: error → line 1, column 4: expected expression, found ASSIGN "=" (hint: this language has no one-token '<=' or '>=' yet — '<' and '=' come as two tokens)
```

มาอ่านข้อความ error นี้ให้เป็น:

- `expected expression, found STAR "*"` = "ตรงนี้ฉันต้องการ **นิพจน์** (อะไรก็ได้ที่คำนวณเป็นค่าได้) แต่เจอ token ชนิด `STAR` ที่มีข้อความจริงว่า `"*"`" — สังเกตว่าเราเจาะจงถึง**ชนิด**และ**ข้อความจริง** ไม่ใช่แค่ "syntax error" ลอย ๆ
- `column 5` คือตำแหน่งของ `*` (นับเป็นไบต์จากต้นบรรทัด + 1) — **ทำไมต้องเป็นตำแหน่งของ `*` ไม่ใช่ของ `1`?** เพราะ error เกิดตอนที่ parser ต้องการ "ลูกฝั่งขวาของ `+`" แล้วเงยหน้ามาเจอ `*` — **ตำแหน่งที่รายงานคือตำแหน่งที่เราติด ไม่ใช่ตำแหน่งที่เริ่มต้น**
- ทำไมฟังก์ชันที่ติดคือ `parsePrimary` — เพราะการอ่านไล่ลงมาแล้ว: `parseExpression → parseComparison → parseTerm` (กิน `1` กับ `+` ไปแล้ว) `→ parseFactor → parseUnary → parsePrimary` แล้วชั้นล่างสุดเท่านั้นที่ "ต้องเจอของจริง" แต่มันเจอ `*`

และเคส `x <= 5` ให้ตัวอย่างที่ดีมากเรื่อง**เส้นแบ่งงาน**: lexer ตัดได้ `LT(<)` กับ `ASSIGN(=)` แยกกันสองตัว (เพราะภาษาจิ๋วยังไม่มี token เดียวสำหรับ `<=`) แล้ว lexer ก็**ไม่ผิด** เพราะมันดูแค่คำ — parser ต่างหากที่ติด เพราะพอกิน `<` (เครื่องหมายเปรียบเทียบ) แล้วมันต้องการ "นิพจน์ฝั่งขวา" แต่เจอ `=` แทน จึงรายงานที่ **คอลัมน์ 4** คือตำแหน่งของ `=` (โปรแกรมเดียวกันยังต่อท้าย error ด้วยข้อความใบ้ว่า ภาษานี้ยังไม่มี `<=` เป็น token เดียว — `<` กับ `=` มาเป็นคนละ token)

สเปกสองข้อที่ error ของ parser ต้องมี — และทั้งสองข้ออยู่ในโค้ดจริง:

**ข้อ 1 — ต้องมีตำแหน่ง** มาจากการที่ node ทุกตัวและ error ทุกตัวพก `Pos` มาด้วย:

```go
// Error — error ที่ parser รายงาน พร้อมตำแหน่ง token ที่ทำให้ผิด
type Error struct {
	Pos lexer.Position
	Msg string
}

func (e *Error) Error() string {
	return fmt.Sprintf("line %d, column %d: %s", e.Pos.Line, e.Pos.Column, e.Msg)
}
```

การมี method ชื่อ `Error() string` ทำให้ชนิดนี้เป็นไปตาม interface `error` ของ Go — แปลว่าเราส่งมันกลับไปเป็น error ธรรมดาได้เลย และข้อความจะถูกจัดรูปให้เสมอเมื่อใครพิมพ์มันออกมา

**ข้อ 2 — ข้อความต้องบอก "คาดหวัง vs เจอ"** มาจากฟังก์ชันช่วยตัวเดียวที่บรรทัดอื่นเรียกกันทั่ว:

```go
// expect — บังคับว่า token ต้องเป็นชนิดที่ระบุ ถ้าไม่ใช่คืน error "expected X, found Y"
func (p *Parser) expect(t lexer.Type, what string) (lexer.Token, error) {
	if p.check(t) {
		return p.advance(), nil
	}
	return lexer.Token{}, &Error{
		Pos: p.cur().Pos,
		Msg: "expected " + what + ", found " + describe(p.cur()),
	}
}

// describe — ข้อความสั้น ๆ บอกว่า token ตัวนี้คืออะไร
func describe(t lexer.Token) string {
	if t.Type == lexer.EOF {
		return "end of file"
	}
	return fmt.Sprintf("%s %q", t.Type, t.Literal)
}
```

`describe` มีหน้าที่เดียวแต่มีค่ามาก: **แปลง EOF ให้เป็นข้อความที่มนุษย์อ่านออก** แทนที่จะพิมพ์ออกมาว่า `EOF ""` (ซึ่งดูเหมือน "เจออะไรว่าง ๆ") เรากลับบอกว่า `end of file` — ลองเทียบเคสจริงสองเคสนี้ดู:

```text
-- [4] ลืม ';' ท้ายคำสั่ง print --
   โค้ด 1 | print 1
   parser: error → line 1, column 8: expected ';' to end print statement, found end of file

-- [5] ลืม ')' ปิดวงเล็บ --
   โค้ด 1 | let x = (1 + 2;
   parser: error → line 1, column 15: expected ')' to close group, found SEMI ";"
```

เคส [4] บอกว่า "หาสิ่งที่ต้องมี แต่ดันไปเจอจุดจบไฟล์" — คนอ่านเข้าใจทันทีว่าลืมอะไร (และรู้ด้วยว่าไปลืมที่คอลัมน์ 8) ส่วนเคส [5] บอกชัดว่าเจอ `;` แทน `)` — ทั้งสองแบบคือข้อความที่**คนเขียนโค้ดอ่านแล้วแก้ต่อได้**

และนี่คือสรุปทั้ง 8 เคส (ผลจริงจาก `out/04_errors.out.txt`):

- `1 + * 3` → parser: `line 1, column 5: expected expression, found STAR "*"`
- `x <= 5` → parser: `line 1, column 4: expected expression, found ASSIGN "=" ...`
- `let = 5;` → parser: `line 1, column 5: expected identifier after 'let', found ASSIGN "="`
- `print 1` → parser: `line 1, column 8: expected ';' to end print statement, found end of file`
- `let x = (1 + 2;` → parser: `line 1, column 15: expected ')' to close group, found SEMI ";"`
- `let x = 1;` + `if x > 0 { print x;` → parser: `line 2, column 20: expected '}' to close block, found end of file`
- `1 2` → parser: `line 1, column 3: expected ';' to end statement, found NUMBER "2"`
- `let x = @;` → **lexer**: `line 1, column 9: unexpected character '@'` (ตกที่ด่านนี้ parser ไม่ได้ทำงาน)

```text
== สรุป ==
  ทั้งหมด 8 เคส · lexer จับ error ได้ 1 เคส · parser จับได้ 7 เคส · รวม 8
  ทุกเคสถูกจับ "พอดีหนึ่งด่าน" — ไม่มีเคสไหนที่ทั้งสองด่านผ่านไปได้
```

ตัวเลข "รวม 8" นี้คือข้อความสำคัญของทั้งระยะ: **สองด่านนี้แบ่งงานกันพอดี ไม่มีรูรั่วและไม่ทับกัน** — lexer จับอักขระที่ไม่เป็นคำ, parser จับการเรียงคำที่ไม่เป็นประโยค

> **จุดที่ต้องระวังตอนอ่านเลขคอลัมน์:** เคส `1 2` กับโปรแกรม 05 ให้ข้อความต่างกัน (นี่ไม่ใช่ความขัดแย้ง) เพราะโปรแกรม 04 กำลัง parse **ทั้งโปรแกรม** คำสั่ง `1` จึงต้องปิดด้วย `;` → ข้อความจึงเป็น "expected ';' to end statement" ส่วนโปรแกรม 05 ใช้โหมด **parse นิพจน์เดี่ยว** ซึ่งหลังนิพจน์ต้องเป็น EOF → จึงได้ "expected end of input" บทเรียนคือ error ที่ดีต้องบอกด้วยว่า "ตอนนี้เรากำลังอยู่บริบทไหน" ไม่ใช่แค่ "เจออะไร"

## 10. กับดักสามข้อที่เจอแน่ถ้าเขียน parser เอง

โปรแกรม 05 รวมกับดักที่พบบ่อยที่สุดไว้ให้ดูของจริงสามข้อ — พร้อม "เวอร์ชันที่ผิด" ที่เขียนไว้ในโปรแกรมนั้นเองเพื่อเทียบกัน

### กับดักที่ 1 — สลับชั้น `term` / `factor` แล้ว precedence พังทั้งระบบ

นี่คือกับดักที่อันตรายที่สุด เพราะ**โปรแกรมจะยังคอมไพล์ผ่าน (ตัวแปลภาษาแปลงโค้ดโดยไม่ error) และรันได้** แค่ต้นไม้ที่ได้จะผิด — เราเขียน parser จิ๋วสองตัวเทียบกัน: ตัวหนึ่งคือ `parser.ParseExpr` ของเรา (ถูก) อีกตัวคือ `mini` ในโปรแกรม 05 ที่ตั้งใจสลับชั้น (ให้ `* /` อยู่ชั้นนอก และ `+ -` อยู่ชั้นใน):

```text
== A) กับดัก: สลับชั้น expression / term / factor ==
  "3 + 4 * 5"
    parser ที่ถูก : (+ 3 (* 4 5))    = 23
    parser ที่ผิด : (* (+ 3 4) 5)    = 35   ← ต้นไม้ผิด ค่าก็ผิด

  "(3 + 4) * 5"
    parser ที่ถูก : (* (+ 3 4) 5)    = 35
    parser ที่ผิด : (* (+ 3 4) 5)    = 35   ← ตรงกันโดยบังเอิญ (วงเล็บบังคับกลุ่มอยู่แล้ว)
```

เคสแรกคือหายนะ: `3 + 4 * 5` ให้ **23** กับ **35** ต่างกันคนละเรื่องทั้งที่โค้ดเหมือนกัน (และกับดักนี้จะทำให้ทุกบรรทัดของโปรแกรมที่ผู้ใช้เขียนเพี้ยนไปหมด แต่โปรแกรมก็ยังรัน "ได้") ส่วนเคสที่สองสอนบทเรียนสำคัญว่า **ด้วยเหตุนี้ ถ้าเราทดสอบด้วยนิพจน์ที่มีวงเล็บ จะจับ parser ที่ผิดไม่ได้** — ต้องทดสอบด้วยนิพจน์ที่**ไม่มี**วงเล็บ ซึ่งเป็นที่ที่ precedence มีผลจริง

### กับดักที่ 2 — ไม่ตรวจ EOF แล้วทิ้งของเงียบ ๆ

```text
== C) กับดัก: parser ที่ไม่ตรวจ EOF ==
  "1 2"
    ไม่เช็ค EOF: ยอมรับเงียบ ๆ → 1 (ทิ้ง token ที่เหลือ 2 ตัวโดยไม่บอก)
    เช็ค EOF   : error → line 1, column 3: expected end of input, found NUMBER "2"
```

parser ที่อ่าน "นิพจน์เดียว" แล้วเลิก (ไม่ถามว่า token หมดหรือยัง) จะยอมรับ `1 2` ผ่าน และคืนค่า `1` โดย**ทิ้ง `2` ไปทั้งตัว** โดยไม่บอกใคร — โปรแกรมจะทำงานผิดโดยไม่มีสัญญาณเตือนเลย วิธีกันคือ `ParseExpr` ของเราบังคับว่า **หลังนิพจน์ต้องเป็น EOF ทันที** (หรือในโหมดโปรแกรมเต็ม ก็คือ `ParseProgram` วนจนกว่าจะเจอ EOF — ไม่มีทางออกอื่น)

### กับดักที่ 3 — ตอน error ไม่ขยับนิ้ว วงวนก็ไม่จบ

กับดักนี้เป็นญาติกับที่เราเจอในตอนที่ 26 (lexer ที่ลืมขยับนิ้ว) แต่คราวนี้ย้ายมาอยู่บนนิ้วของ parser — "นิ้ว" ในที่นี้คือ `p.pos` ดัชนีของ token ที่เรากำลังดูอยู่:

```text
== D) กับดัก: ตอน error ไม่ขยับนิ้ว → วนไม่จบ ==
  อินพุต: "+ 1" · ลองอ่านซ้ำโดยมีเพดาน 5 รอบ (กันโปรแกรมค้างจริง)
  เวอร์ชันผิด (คืน error โดยไม่ขยับนิ้ว):
    รอบ 1: token "+" ที่ดัชนี 0 ไม่รู้จัก → คืน error
    รอบ 2: token "+" ที่ดัชนี 0 ไม่รู้จัก → คืน error
    รอบ 3: token "+" ที่ดัชนี 0 ไม่รู้จัก → คืน error
    รอบ 4: token "+" ที่ดัชนี 0 ไม่รู้จัก → คืน error
    รอบ 5: token "+" ที่ดัชนี 0 ไม่รู้จัก → คืน error
    ...ครบเพดาน 5 รอบแล้วยังไม่จบ (โปรแกรมจริงจะค้างเป็นอนันต์)
  เวอร์ชันแก้แล้ว (ขยับนิ้วก่อนคืน error):
    รอบ 1: token "+" ที่ดัชนี 0 ไม่รู้จัก → คืน error
    รอบ 2: token "1" เป็น statement ที่อ่านได้ → ขยับนิ้ว
    รอบ 3: เจอ EOF → จบการทำงาน
```

ความต่างมีแค่**บรรทัดเดียว**: เวอร์ชันที่ผิด `continue` โดยไม่ขยับ `p.pos` → รอบถัดไปเจอ `+` ตัวเดิมที่ดัชนีเดิม → วนไปเรื่อย ๆ ตลอดกาล (ในโปรแกรมจริงคือค้าง) ส่วนเวอร์ชันที่แก้แล้วขยับก่อนคืน error → จบใน 3 รอบ

สัญญาที่ต้องจำ (ญาติกับสัญญาของ lexer หัวข้อ 7 ของตอนที่ 26):

> **สัญญาของ parser:** เมื่อคืน error ต้องรับประกันว่า "นิ้ว" ขยับไปแล้วอย่างน้อยหนึ่งตำแหน่ง — ไม่งั้นผู้เรียกที่วนอ่านต่อจะวนไม่จบ

กับดักอีกสองข้อที่ควรระวังและเรา**ดักไว้ในโค้ดจริง**แล้ว (ดูได้จากโครงสร้างที่เราเขียน ไม่ใช่จากผลรัน):

1. **`parseBlock` ที่เจอ EOF ก่อนเจอ `}`** — ถ้าเราเขียน `for !p.check(lexer.RBRACE) { parseStatement() }` เฉย ๆ แล้วไม่เช็ค EOF ก่อน ก่อนสิ้นไฟล์ `parseStatement` จะไปเรียกชั้นล่างแล้วเจอ EOF → คืน error แต่ถ้าเราไม่ได้ดักไว้ชัด ๆ จะพลาดเคส "ลืมปิดบล็อก" ไปเรื่อย ๆ — เราจึงดักเป็นกรณีแรกในวงวนเลย
2. **ชั้นบนเรียกชั้นบนด้วยกันเอง** — ถ้า `parseTerm` เผลอเรียก `parseTerm` ตัวเองแทน `parseFactor` มันจะวนไม่จบโดยไม่ต้องมี error ด้วยซ้ำ (เพราะเรียกตัวเองก่อนอ่าน token ใหม่) วิธีกันคือยึดกฎ "ชั้นไหนเรียกชั้นล่างเท่านั้น" แล้วตรวจด้วยตารางกฎ ↔ ฟังก์ชันในหัวข้อ 3

## 11. ของจริงทำแบบนี้: `go/parser` กับ `go/ast`

ก่อนปิดบท เรามาตรวจว่าของจริงที่โปรแกรมเมอร์ Go ใช้ทุกวันหน้าตาเหมือนของเรายังไง — โปรแกรม `_probe_go/goreal_check.go` ใช้ `go/parser` (parser จริงของ Go ที่อยู่ใน standard library — ไลบรารีมาตรฐาน = ชุดโค้ดที่ Go แถมมาให้ เรียกใช้ได้เลย) แล้วเทียบกับ parser ของเรา:

```text
== ใช้ go/parser (parser จริงของ Go) กับนิพจน์เดียวกับบทความ ==

"3 + 4 * 5"
  type ของ node บนสุด: *ast.BinaryExpr
  BinaryExpr +
    BasicLit 3
    BinaryExpr *
      BasicLit 4
      BasicLit 5
  Pos() = บรรทัด 1 คอลัมน์ 1 · End() = บรรทัด 1 คอลัมน์ 10

"(3 + 4) * 5"
  type ของ node บนสุด: *ast.BinaryExpr
  BinaryExpr *
    ParenExpr (Go เก็บวงเล็บไว้เป็น node)
      BinaryExpr +
        BasicLit 3
        BasicLit 4
    BasicLit 5
  Pos() = บรรทัด 1 คอลัมน์ 1 · End() = บรรทัด 1 คอลัมน์ 12
```

เทียบกันทีละจุด จะเห็นว่าเราเดินถูกทางมาแล้วทั้งเส้น:

| ของเรา (ตอนที่ 27) | ของจริง (Go) |
|---|---|
| `parser.Node` มี `Pos() lexer.Position` | `go/ast.Node` มี `Pos() token.Pos` **และ** `End() token.Pos` |
| `BinaryExpr{Op, OpTok, Left, Right}` | `ast.BinaryExpr{X, OpPos, Op, Y}` |
| `NumberLit{Value, Text, At}` | `ast.BasicLit{ValuePos, Kind, Value}` (แสดงเฉพาะฟิลด์ที่เทียบกัน) |
| ต้นไม้ของเราทิ้งวงเล็บ | Go **เก็บ** วงเล็บเป็น node `ParenExpr` |
| `lexer.Position{Line, Column, Offset}` (ตอนที่ 26) | `go/token.Position{Filename, Offset, Line, Column}` (ตัวจริงมี 4 ฟิลด์) |

สองจุดที่ต่างกันและเป็นบทเรียน:

1. **Go เก็บวงเล็บไว้เป็น node (`ParenExpr`)** — เพราะเครื่องมือของ Go (gofmt, formatter, IDE — โปรแกรมที่ใช้เขียนโค้ด เช่น VS Code) ต้อง**สร้างโค้ดกลับออกมา**ได้ ซึ่งต้องรักษาวงเล็บที่ผู้ใช้เขียนไว้ ต้นไม้แบบเราที่ทิ้งวงเล็บเหมาะกับ "อ่านแล้วเอาความหมายไปใช้" (แบบ compiler/interpreter ของเรา) มากกว่า — นี่คือตัวอย่างจริงของการเลือกว่าจะ "abstract" แค่ไหน
2. **Go มี `End()` เพิ่ม** — เพราะการรายงาน error และการจัด format ต้องรู้ทั้งจุดเริ่มและจุดจบของแต่ละ node เราตัด `End()` ออกเพื่อให้บทสั้นลง แต่ถ้าคุณอยากต่อยอด (โจทย์ mini-project ด้านล่าง) การเพิ่ม `End()` เป็นแบบฝึกหัดที่ดีมาก

และปิดท้ายด้วยข้อสังเกตที่ตรวจได้จากเครื่องที่ใช้เขียนบทความนี้: โค้ดของ `go/parser` ใน standard library ทั้งหมด (`parser.go`, `interface.go`, `resolver.go`) **เป็นโค้ดที่เขียนมือ** — ไม่มีไฟล์ไหนขึ้นหัวว่า "Code generated" แบบที่ไฟล์ซึ่ง generate จากเครื่องมือจะขึ้น และ `ast.ParenExpr{Lparen, X, Rparen}` ก็เป็น node ที่ถูกสร้างขึ้นมาเก็บวงเล็บจริง ๆ ตามผลรันด้านบน นี่คือเหตุผลที่ตัวแปลภาษาชั้นนำหลายตัวเลือกทาง "เขียน parser เองแบบไล่ลงตามชั้นไวยากรณ์" แทนที่จะ generate จากเครื่องมือ: เราคุม**คุณภาพของ error message** ได้เอง และปรับให้เข้ากับภาษาของเราได้ละเอียดกว่ามาก

### ระดับ Drill (ฝึกมือ)

1. ตัดคำ + parse `let total = 10 - 3;` — ได้ token ทั้งหมดกี่ตัว (รวม EOF)? S-expression คืออะไร และต้นไม้หน้าตาเป็นยังไง? (เฉลยตรวจได้จาก `out/06_drill_answer.out.txt`)
2. อธิบายด้วยคำพูดตัวเองว่า ทำไม `3 + 4 * 5` ถึงได้ `(+ 3 (* 4 5))` — ฟังก์ชันชั้นไหนเป็นตัวทำให้ `*` ถูกประกอบก่อน `+` (ใบ้: ย้อนดูหัวข้อ 4 กับ 5)
3. `1 + * 3` ผิดที่บรรทัด/คอลัมน์ไหน และฟังก์ชันตัวไหนของ parser เป็นคนเจอความผิดนี้? (เฉลยอยู่ใน `out/06_drill_answer.out.txt`)
4. `3 + 4 * 5` กับ `(3 + 4) * 5` ให้ S-expression ต่างกันยังไง และค่าจริงต่างกันเท่าไร? (S-expression เฉลยที่ `out/06` · ค่าจริงเฉลยที่ `out/05_precedence.out.txt`)
5. `let x = 1` (ลืม `;`) — parser บอก error ว่าอะไร ตำแหน่งไหน? (เฉลยที่ `out/06`)
6. ทั้งสามโปรแกรมในหัวข้อ 8 ใช้ชนิด token ไปกี่ชนิดจากทั้งหมด 23 ชนิด? และทำไมตัวเลขนี้ถึงตอบว่า "สเปกตอนที่ 26 ถูกใช้ครบแล้ว"?

### Mini-project (ต่อยอดจากโปรแกรม 04–05 และ `internal/parser`)

ก่อนเริ่ม รู้จักโครงไฟล์ที่ต้องแตะ: **`internal/parser/ast.go`** = ชนิดของ node ทั้งหมด + ตัวพิมพ์ต้นไม้ · **`internal/parser/parser.go`** = ฟังก์ชัน parse ทั้ง 13 ตัว (หนึ่งตัวต่อหนึ่งกฎ) + ตาราง `Rules` · **`internal/lexer/lexer.go`** = ตัวตัดคำจากตอนที่ 26 · รันทุกอย่างพร้อมกันด้วย `./run_all.sh`

ให้ทำสามอย่างเรียงจากง่ายไปยาก:

1. **รองรับ `<=` และ `>=` ให้ครบทั้งภาษา** — ต่อจาก mini-project ของตอนที่ 26 (ที่ให้เพิ่ม `LTE`/`GTE` ในตัว lexer) คราวนี้มาถึงฝั่ง parser:
   - เพิ่ม `lexer.LTE` `lexer.GTE` เข้าไปในเงื่อนไขของ `parseComparison` (ตอนนี้มีแค่ `EQ` `NEQ` `LT` `GT`) อย่าลืมเขียน `case` ให้ครบ
   - เพิ่มบรรทัดในตาราง `Rules` (กฎ `comparison`) ให้สะท้อนว่าเครื่องหมายที่รองรับมีอะไรบ้าง — ตารางนี้คือเอกสารที่โปรแกรมพิมพ์ออกมาเอง ถ้าแก้โค้ดแล้วไม่แก้ตาราง เอกสารกับโค้ดจะหลุดกันแบบเงียบ ๆ ซึ่งเป็นอาการที่เราเห็นใน ep26 ด้วย
   - ทดสอบว่า `x <= 5` ผ่านได้แล้ว: ลอง parse `if x <= 5 { print x; }` และเทียบกับ `out/04_errors.out.txt` เดิมว่าข้อความ error หายไปแล้วจริง
2. **error recovery — เก็บ error ได้หลายจุดในรอบเดียว** (แบบเดียวกับที่ lexer ของเรา "เดินต่อได้" ในตอนที่ 26) ตอนนี้ `ParseProgram` เจอ error แล้ว `return nil, err` ทันที ทำให้เห็นได้ทีละจุด ลองเปลี่ยนเป็น:
   - เพิ่ม `(p *Parser) synchronize()` ที่ "ข้าม token ไปจนกว่าจะเจอ `;` หรือ `}` หรือ EOF" แล้วเรียกมันใน `ParseProgram` เมื่อ `parseStatement` คืน error (เก็บ error ใส่ `[]error` แล้วอ่านต่อ)
   - ให้ `ParseProgram` คืนค่าทั้งต้นไม้และรายการ error — ออกแบบ API ให้โปรแกรม 04 พิมพ์ error ได้หลายบรรทัดต่อหนึ่งไฟล์
   - **อย่าลืมสัญญาของ parser**: ทั้ง `synchronize` และทุกเส้นทางที่คืน error ต้องขยับ `p.pos` เสมอ ไม่งั้นจะวนไม่จบ (นี่คือกับดักที่ 3 ของหัวข้อ 10)
3. **เดินต้นไม้ + คำนวณค่า** (สะพานไปตอนที่ 28) — ใช้ `parser.Children` เดินทั้งต้นไม้ แล้วทำสองอย่าง:
   - เขียนฟังก์ชันนับ node แต่ละชนิด (เช่น `BinaryExpr` 5 ตัว, `NumberLit` 6 ตัว (รวมทั้งต้น 20 node)) แล้วพิสูจน์ว่าต้นไม้ที่ได้จากโปรแกรม A มี node รวมกี่ตัว
   - ยก `eval` จากโปรแกรม 05 มาขยายให้รองรับ `==` `!=` `<` `>` (คืนค่าเป็น `bool`) แล้วลองคำนวณ `if y > 10 { ... }` ว่าเงื่อนไขเป็นจริงหรือเท็จ — นี่คือการเริ่มเป็น interpreter จริง ๆ และมันจะบอกคุณได้ทันทีว่าต้องเพิ่มอะไรในตอนที่ 28 (ใบ้: ต้องมี "ที่เก็บค่าของตัวแปร" ซึ่งคือหัวข้อของตอนที่ 29 ด้วย)
