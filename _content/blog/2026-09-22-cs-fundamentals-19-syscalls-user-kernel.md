# syscall — ประตูบานเดียวที่โปรแกรมเข้าหาเคอร์เนลได้ (user space / kernel space) (ตอนที่ 19) — CS Fundamentals: จาก 0 สู่พื้นฐานที่แท้จริง

ตอนที่แล้ว (ตอนที่ 18) เราเห็นว่าเคอร์เนล (kernel = แกนกลางของระบบปฏิบัติการที่คุม hardware โดยตรง) เป็นคนจัดคิวว่าโปรเซสไหนได้ใช้ CPU ตอนไหน และเราได้วัดราคา context switch จริงไปแล้ว ~2.1 µs (ไมโครวินาที = หนึ่งในล้านวินาที) ต่อครั้ง

ตอนนั้นมีของชิ้นหนึ่งที่เราวัดผ่าน ๆ ไป: **ราคา syscall เปล่า ๆ 178 ns (นาโนวินาที = หนึ่งในพันล้านวินาที) ต่อครั้ง** แล้วก็ยังไม่ได้อธิบายว่าตัวเลขนั้นมาจากไหน

ตอนนี้คือเวลาลงลึกกับคำถามที่สำคัญที่สุดข้อหนึ่งของระบบปฏิบัติการ: **โปรแกรมของเราอยู่คนละโลกกับเคอร์เนล แล้วมัน "คุย" กันยังไง** — และทำไมถึงต้องแยกกันตั้งแต่แรก

ประเด็นที่บทนี้จะตอบด้วยการรันจริงทั้งหมด:

1. **user space กับ kernel space** คืออะไร ทำไม CPU ต้องมี "โหมดสิทธิ์" สองระดับ และใครเป็นคนบังคับ (ไม่ใช่แค่ "ตกลงกันว่าไม่ทำ")
2. **syscall** (system call = "การเรียกใช้บริการของเคอร์เนล") คือประตูบานเดียวที่โปรแกรมใช้ขอให้เคอร์เนลทำเรื่องอันตรายให้ — บนเครื่อง arm64 ของเราประตูนั้นคือคำสั่ง `svc #0`
3. **กลไกจริง**: เลข syscall ใส่ตรงไหน argument ส่งผ่านทางไหน ผลตอบกลับมาอย่างไร และ `errno` (รหัสข้อผิดพลาด) เกิดจากตรงไหน
4. **ราคา**: syscall แพงกว่า "เรียกฟังก์ชันธรรมดา" กี่เท่า และราคาแพงเพราะอะไร

ทุกตัวเลขในบทนี้มาจากการรันจริงบนเครื่องเรา (Raspberry Pi 5, Linux 6.18.39+rpt-rpi-2712 aarch64, GCC 14.2.0, glibc 2.41, strace 6.13) — ไม่มีตัวเลขไหนยกมาจากตำราโดยไม่รัน

> **คำศัพท์พื้นฐานที่จะใช้ตลอดบทนี้** (อธิบายครั้งเดียวตรงนี้ แล้วใช้ต่อเลย):
> - **เคอร์เนล** (kernel) = แกนกลางของ OS · โค้ดก้อนที่คุม hardware โดยตรง (อ่าน/เขียนดิสก์, ต่อการ์ดเน็ต, จัดการหน่วยความจำ, แบ่ง CPU)
> - **user space** = โลกของโปรแกรมเรา · วิ่งที่ EL0 (Exception Level 0 = ระดับสิทธิ์ต่ำสุดของ CPU arm64) · ทำอะไรอันตรายไม่ได้
> - **kernel space** = โลกของเคอร์เนล · วิ่งที่ EL1 (สิทธิ์เต็ม) · เห็นและควบคุมทุกอย่าง
> - **syscall** (system call) = "การเรียกใช้บริการของเคอร์เนล" · โปรแกรมขอให้เคอร์เนลทำอะไรให้ (อ่านไฟล์, เขียนจอ, ขอหน่วยความจำ) แล้วรอผล
> - **รีจิสเตอร์** (register) = ช่องเก็บข้อมูลเล็ก ๆ ความเร็วสูงภายใน CPU (เราเคยเจอตอนที่ 15 ตอนเรียน calling convention แล้ว)
> - **libc** = ไลบรารีมาตรฐานของภาษา C (ตัวห่อ) · ฟังก์ชันอย่าง `printf`/`read`/`open` ของเราจริง ๆ แล้ว "ข้างใน" เป็นการเรียก syscall อีกที
> - **errno** = ตัวแปรเก็บ "รหัสข้อผิดพลาด" ของการทำงานล่าสุด · เป็นตัวแปรของแต่ละเธรด (thread-local)
> - **MMU** (Memory Management Unit) = ฮาร์ดแวร์ใน CPU ที่แปล "ที่อยู่ปลอม" ของโปรแกรมเป็นที่อยู่จริงบน RAM (เราจะลงลึกเต็ม ๆ ในตอนที่ 20)
> - **fd** (file descriptor) = "หมายเลขตั๋ว" ที่เคอร์เนลแจกให้โปรเซสใช้แทนไฟล์/ช่องที่เปิดอยู่ · **stdout** = ช่องออกมาตรฐาน (จอ) หมายเลข 1 · **stderr** = ช่องข้อผิดพลาด หมายเลข 2
> - **สัญญาณ** (signal) = ข้อความสั้น ๆ ที่เคอร์เนลส่งให้โปรเซสบอกเหตุการณ์ เช่น "เธอทำผิดกติกา" (SIGSEGV) หรือ "คำสั่งนี้เธอไม่มีสิทธิ์" (SIGILL)
> - **strace** = เครื่องมือที่คอยส่อง "syscall ทุกครั้ง" ที่โปรแกรมเรียก แล้วพิมพ์ออกมาให้เราดู

## 1. แนวคิด: CPU มีสองโหมดสิทธิ์ และประตูมีบานเดียว (ภาพที่ 1)

ก่อนเขียนโค้ด ขอตั้งภาพใหญ่ให้ตรงกันก่อน หลายคนเข้าใจผิดว่า "โปรแกรมไม่ไปแตะของเคอร์เนลเพราะมัน**ไม่รู้**" — ความจริงแล้วมัน**รู้** แต่ **CPU กับ MMU ปฏิเสธมันจริง ๆ** ระดับฮาร์ดแวร์

![เส้นแบ่ง user space (EL0) กับ kernel space (EL1) บน arm64 พร้อมหลักฐานจากการรันจริง](/assets/diagrams/ep19-01-user-vs-kernel-boundary.svg)

ภาพที่ 1 สรุปไว้ครบ: CPU ของ arm64 แบ่ง "ระดับสิทธิ์" (เรียกว่า Exception Level) ออกเป็นชั้น ๆ โดยโปรแกรมทั่วไปวิ่งที่ **EL0** (user space) ส่วนเคอร์เนลวิ่งที่ **EL1** (kernel space) กติกาคือ:

- **EL0 (user) ทำอะไรอันตรายไม่ได้**: สั่ง hardware ตรง ๆ ไม่ได้ · อ่าน/เขียนหน่วยความจำที่ "ไม่ได้จองไว้ให้" ไม่ได้ · แตะทะเบียนควบคุมของระบบไม่ได้
- **EL1 (kernel) ทำได้ทุกอย่าง**: ตั้ง MMU ว่าใครเห็นที่อยู่ไหน · สั่ง hardware · เห็นหน่วยความจำของทุกโปรเซส

ทำไมต้องแยก? เหตุผลสามข้อที่โยงของจริงได้ทันที:

1. **กันโปรแกรมทำลายกันเอง** — ถ้าโปรแกรมไหนเขียนหน่วยความจำของโปรแกรมอื่นได้ตามใจ โปรแกรมพังตัวเดียวก็น็อกทั้งเครื่อง
2. **กันแอปเล่น hardware ตรง ๆ** — ถ้าแอปสั่งดิสก์/การ์ดเน็ตเองได้ แอปมั่วตัวเดียวก็อ่านไฟล์ของคนอื่นหรือทำลายข้อมูลทั้งดิสก์
3. **กันโปรแกรมหลอกให้เครื่องคิดว่าตัวเองคือระบบ** — เรื่อง security แทบทั้งหมดของ OS ตั้งอยู่บนกำแพงนี้

แล้วถ้าโปรแกรมอยาก "ทำเรื่องอันตราย" จริง ๆ ล่ะ (เช่นเขียนไฟล์ลงดิสก์)? คำตอบคือมันทำเองไม่ได้ แต่**ขอเคอร์เนลทำให้ได้** — ผ่านประตูบานเดียวที่ชื่อ **syscall**

บน arm64 ประตูนั้นคือคำสั่ง `svc #0` (Supervisor Call) ซึ่งเป็นคำสั่ง CPU คำเดียวที่บอกว่า "ยกสิทธิ์ให้ฉันเป็น EL1 ชั่วคราว แล้วให้เคอร์เนลทำงานให้หน่อย"

จุดสำคัญที่ต้องจำแม่น: **กำแพงนี้บังคับโดย hardware (CPU + MMU) ไม่ใช่ข้อตกลงของโปรแกรมเมอร์** — เราจะพิสูจน์ในหัวข้อ 7 ว่าถ้าโปรแกรมพยายามข้ามกำแพงเอง มันจะโดนสัญญาณ (signal = ข้อความสั้น ๆ ที่เคอร์เนลส่งมาบอกโปรเซสว่า "เธอทำผิดกติกา") ตายกลางคันจริง ๆ

## 2. ลงมือทำ 1: `raw_write.c` — คุยกับเคอร์เนลเอง ไม่ผ่าน libc

วิธีพิสูจน์ว่า syscall เป็น "คำสั่ง CPU ธรรมดา" ไม่ใช่เวทมนตร์ของไลบรารี คือเขียนโปรแกรมที่**เรียก syscall ตรง ๆ ด้วยมือ** โดยไม่เรียกฟังก์ชันของ libc ที่ห่อ syscall (อย่าง `printf`/`write`) เลยแม้แต่ตัวเดียว โปรแกรมนี้ไม่มี `#include <stdio.h>` ไม่มี `printf` ไม่มี `return` จาก `main` ที่ทำงานจริง (บรรทัด `return 0;` ที่เห็นคือโค้ดตายไว้กัน compiler บ่น) — การเข้าหาเคอร์เนลทุกครั้งทำด้วย `svc #0` ตรง ๆ

(หมายเหตุไบนารี: ในไฟล์ที่คอมไพล์แล้วยังโผล่ `strlen@plt` เพราะคอมไพเลอร์แปลงลูปนับความยาวใน `slen()` เป็นการเรียก strlen ของ libc เอง กับ startup `__libc_start_main` ที่ gcc ใส่ให้ทุกโปรแกรม — ตรงนี้ `@plt` คือ "จุดเชื่อม" ที่คำเรียกวิ่งผ่านตัวโหลดไลบรารี ไม่ใช่ symbol versioning อย่าง `printf@GLIBC_2.17` ที่เห็นในตอนที่ 17 · ดูได้ในไฟล์ objdump เต็ม `course/code/ep19/out/objdump_raw_write.txt`)

```c
/* raw_write.c — เรียก syscall ตรง ๆ ด้วย svc #0 (ไม่เรียก libc ที่ห่อ syscall)
 *
 * build: gcc -std=c17 -Wall -Wextra -Wpedantic -O2 -o raw_write raw_write.c
 * run  : ./raw_write
 *
 * aarch64 (arm64) syscall ABI:
 *   x8 = หมายเลข syscall · x0..x5 = argument · เรียกด้วย `svc #0`
 *   ค่าที่คืนกลับมาอยู่ใน x0 (ค่าลบ = error: -errno)
 */

/* ---------- หมายเลข syscall ของ arm64 (จาก asm-generic/unistd.h) ---------- */
#define NR_WRITE 64
#define NR_EXIT_GROUP 94
#define NR_GETPID 172
#define NR_GETPPID 173

typedef long sysret_t;

/* เรียก syscall ที่ไม่มี argument (ใส่หมายเลขใน x8 แล้วยิง svc #0) */
static sysret_t sys0(long nr)
{
    register long x8 __asm__("x8") = nr;
    register long x0 __asm__("x0");

    __asm__ volatile("svc #0" : "=r"(x0) : "r"(x8) : "memory", "cc");
    return (sysret_t)x0;
}

/* เรียก syscall ที่มี 3 argument (write = (fd, buf, count)) */
static sysret_t sys3(long nr, long a0, long a1, long a2)
{
    register long x8 __asm__("x8") = nr;
    register long x0 __asm__("x0") = a0;
    register long x1 __asm__("x1") = a1;
    register long x2 __asm__("x2") = a2;

    __asm__ volatile("svc #0"
                     : "+r"(x0)
                     : "r"(x8), "r"(x1), "r"(x2)
                     : "memory", "cc");
    return (sysret_t)x0;
}

/* เรียก syscall ที่มี 1 argument และไม่คืนกลับ (exit_group) */
static void sys1_never_returns(long nr, long a0)
{
    register long x8 __asm__("x8") = nr;
    register long x0 __asm__("x0") = a0;

    __asm__ volatile("svc #0" : "+r"(x0) : "r"(x8) : "memory", "cc");
    __builtin_unreachable(); /* เคอร์เนลไม่คืนกลับมาที่นี่ */
}

/* ---------- ตัวช่วยพิมพ์แบบไม่พึ่ง libc ---------- */
static long slen(const char *s)          /* หาความยาวข้อความเอง */
{
    long n = 0;

    while (s[n] != '\0') {
        n++;
    }
    return n;
}

static void out(const char *s)           /* พิมพ์ด้วย syscall write ตรง ๆ */
{
    long n = slen(s);

    if (n == 0) {
        return;
    }
    sysret_t r = sys3(NR_WRITE, 1 /* stdout */, (long)s, n);
    if (r != n) {
        /* เขียนไม่ครบ = ปัญหาจริง บอกแล้วออกด้วยรหัส 1 */
        const char msg[] = "raw_write: write() ล้มเหลว\n";

        (void)sys3(NR_WRITE, 2 /* stderr */, (long)msg, (long)(sizeof(msg) - 1));
        sys1_never_returns(NR_EXIT_GROUP, 1);
    }
}

/* (ฟังก์ชัน out_long = พิมพ์เลขฐานสิบแบบไม่พึ่ง libc — ดูไฟล์เต็มใน course/code/ep19/) */

int main(void)
{
    out("== raw_write: คุยกับเคอร์เนลเอง ไม่ผ่าน libc ==\n");

    sysret_t pid = sys0(NR_GETPID);
    out("syscall getpid  (nr=172) -> pid = ");
    out_long(pid);
    out("\n");

    sysret_t ppid = sys0(NR_GETPPID);
    out("syscall getppid (nr=173) -> ppid = ");
    out_long(ppid);
    out("\n");

    out("บรรทัดนี้พิมพ์ด้วย syscall write (nr=64) โดยตรง\n");
    out("== จบ: ปิดโปรเซสด้วย exit_group(0) ไม่ใช่ return ==\n");

    /* ไม่ return จาก main — ออกจากโปรเซสด้วย syscall เองทั้งหมด */
    sys1_never_returns(NR_EXIT_GROUP, 0);
    return 0; /* ไม่มีทางมาถึง (วางไว้กัน compiler บ่น) */
}
```

ขออธิบายจุดที่มือใหม่ต้องรู้ก่อนรัน:

- **`__asm__ volatile("svc #0" ...)`** คือวิธีเขียน "ภาษาเครื่อง" แทรกลงในภาษา C โดยตรง (เรียกว่า inline assembly) · คำสั่ง `svc #0` คือตัวประตู: พอ CPU เจอคำสั่งนี้ มันจะหยุดงานของเรา เปลี่ยนโหมดจาก EL0 ไป EL1 แล้วกระโดดไปที่โค้ดของเคอร์เนลทันที
- **`register long x8 __asm__("x8") = nr`** = "เอาค่า `nr` ไปวางไว้ในรีจิสเตอร์ชื่อ x8 แล้วห้ามแตะมัน" · นี่คือกติกาที่เรียกว่า **ABI** (Application Binary Interface = ข้อตกลงว่าค่าต่าง ๆ ผ่านรีจิสเตอร์ไหน) — บน arm64 หมายเลข syscall ต้องอยู่ใน **x8** argument ต้องอยู่ใน **x0 ถึง x5** ตามลำดับ และผลลัพธ์จะคืนกลับมาทาง **x0**
- `typedef long sysret_t;` = ตั้งชื่อเล่นให้ชนิด `long` ว่า `sysret_t` (ค่าที่ syscall คืนกลับมา) — ชนิดจริงก็คือ `long` ตัวเดิม แค่ให้โค้ดอ่านง่ายขึ้น · ส่วนเครื่องหมาย `: "=r"(x0)` กับ `: "+r"(x0)` ในโค้ด `sys0`/`sys3` คือบอกคอมไพเลอร์ว่าตัวแปร x0 ตัวไหน "เขียนอย่างเดียว" (รับผลลัพธ์กลับ = `=r`) ตัวไหน "อ่านแล้วเขียน" (ส่ง argument เข้าไปด้วยแล้วรับผลกลับ = `+r`)
- `__builtin_unreachable()` = บอกคอมไพเลอร์ว่า "บรรทัดหลังนี้ไม่มีวันถูกทำ" (เพราะ `exit_group` สั่งให้เคอร์เนลจบทั้งโปรเซสแล้ว ไม่มีทางไหลมาถึง `return`)
- หมายเลข 64/94/172/173 ไม่ได้มโน — หาได้จริงจากไฟล์ `/usr/include/asm-generic/unistd.h` บนเครื่องเรา (ดูในหัวข้อ 7.2)

```
== raw_write: คุยกับเคอร์เนลเอง ไม่ผ่าน libc ==
syscall getpid  (nr=172) -> pid = 21469
syscall getppid (nr=173) -> ppid = 21421
บรรทัดนี้พิมพ์ด้วย syscall write (nr=64) โดยตรง
== จบ: ปิดโปรเซสด้วย exit_group(0) ไม่ใช่ return ==
```

โปรแกรมนี้พิสูจน์ได้ว่าทั้งหมดที่ libc ทำก็คือ "เตรียมรีจิสเตอร์แล้วยิง `svc #0`" กับ "รับค่ากลับมาจาก x0" — ไม่มีอะไรลึกลับกว่านั้น ถ้าดูไบต์นารีจริงด้วย `objdump -d raw_write` (objdump = เครื่องมือถอดภาษาเครื่องกลับมาเป็นข้อความให้อ่าน) จะเห็นประตูเป็นคำสั่ง CPU เป๊ะ:

```
698:  d2801588   mov  x8, #0xac        // #172 = __NR_getpid
69c:  d4000001   svc  #0x0             <- ประตู: เข้า kernel
6c8:  d28015a8   mov  x8, #0xad        // #173 = __NR_getppid
6cc:  d4000001   svc  #0x0
8a8:  d2800808   mov  x8, #0x40        // #64  = __NR_write
8b0:  d4000001   svc  #0x0
708:  d2800bc8   mov  x8, #0x5e        // #94  = __NR_exit_group
710:  d4000001   svc  #0x0
```

(หมายเหตุ: ข้อความ `= __NR_getpid` ต่อท้ายบรรทัด objdump เราเติมเองเพื่อให้อ่านง่าย — ไฟล์จริงมีแค่ `// #172`)

สังเกตสองอย่าง: (1) `mov x8, #0xac` = เอาค่า 172 (ฐานสิบหกคือ 0xac) ใส่ x8 แล้ว `svc #0` ทันที — ตรงกับกติกา ABI เป๊ะ · (2) ทั้งไฟล์มีคำสั่ง `svc` แค่ **6 ครั้ง** (getpid, getppid, write ใน `out`, write ในทาง error, exit ในทาง error, exit ใน `main`) — นับได้ครบ ไม่มี "write ของ libc" ซ่อนอยู่เลย

## 3. กลไก syscall: จาก `svc #0` ถึงค่าที่ได้ใน x0 (ภาพที่ 2)

คราวนี้ซูมเข้าไปดูว่า "ข้างใน" ประตูเกิดอะไรขึ้นบ้าง ตั้งแต่เรายิง `svc #0` จนได้ผลกลับมา

![กลไกการเรียก syscall บน arm64: svc #0 → syscall table → handler → eret](/assets/diagrams/ep19-02-syscall-mechanism.svg)

ภาพที่ 2 แสดง 8 จังหวะของ syscall หนึ่งครั้ง (ตัวอย่างคือ `write`):

1. **โปรแกรมเรียกฟังก์ชัน** — โค้ด C ของเราที่ EL0 (ในกรณี `raw_write` เรายิงเองตรง ๆ ไม่ผ่าน libc)
2. **libc เตรียมค่า** — (ถ้าผ่าน libc) ตัวห่อจะวางเลข syscall ไว้ที่ x8 และ argument ไว้ที่ x0/x1/x2
3. **`svc #0`** — คำสั่งเดียวที่เข้าเคอร์เนล CPU เปลี่ยน EL0 → EL1
4. **CPU กระโดดตาม vector** — ไปที่ "จุดรับคำขอ" ของเคอร์เนล (เรียกว่า exception vector)
5. **บันทึก context** — เคอร์เนลเก็บค่ารีจิสเตอร์/ตำแหน่งที่เรากำลังทำไว้ใน kernel stack (stack ฝั่งเคอร์เนล แยกจาก stack ของโปรแกรมเรา — เพื่อกลับมาทำต่อได้)
6. **อ่าน x8 แล้วดูตาราง** — เคอร์เนลใช้ค่าใน x8 ไปเปิด **syscall table** (ตารางที่แมป "เลข" → "ฟังก์ชันในเคอร์เนล") ได้ตัวที่ต้องเรียก เช่น `sys_write`
7. **handler ทำงาน** — ฟังก์ชันนั้นทำงานจริง (เขียนข้อมูลลงไฟล์/จอ) ซึ่งผู้ใช้ไม่เห็นการทำงานนี้
8. **`eret` กลับ EL0** — ส่งผลกลับทาง x0 แล้วคืนสิทธิ์ให้เรา

ประเด็นที่อยากให้เห็นชัดคือ**ข้อ 6**: มี "ตาราง" จริง ๆ ไม่ใช่ if-else ก้อนยักษ์ ถ้าเลขใน x8 เกินขอบเขตตาราง เคอร์เนลจะตอบกลับด้วยรหัสพิเศษ `-ENOSYS` (ไม่มี syscall นี้) — เราจะพิสูจน์ตารางนี้ด้วยมือในหัวข้อ 7.2

อีกจุดที่หลายคนงง: ทำไมต้อง "บันทึก context" ในข้อ 5? เพราะพอเข้าเคอร์เนล รีจิสเตอร์เดิมของเราอาจถูกเคอร์เนลเขียนทับ ถ้าไม่เก็บไว้ก่อน กลับมาปุ๊บโปรแกรมเราจะทำงานผิด (ตัวแปรหาย/ข้ามไปผิดบรรทัด) — นี่คือกลไก**คล้ายกับ** "context switch" ที่เราเห็นในตอนที่ 18 แต่เล็กกว่า (แค่เข้า-ออกเคอร์เนลของโปรเซสเดิม ไม่ถึงกับสลับไปโปรเซสอื่น)

## 4. ลงมือทำ 2: `errno` มาจากไหน — เคอร์เนลคืน "ค่าลบ" ไม่รู้จัก errno

ตอนเขียนโปรแกรม C มา 6 ตอน (13–18) เราคุ้นเคยกับรูปแบบนี้: ฟังก์ชันคืน `-1` แล้วเราอ่าน `errno` เพื่อรู้ว่าผิดอะไร แต่เคอร์เนล**ไม่รู้จัก**ตัวแปรชื่อ errno เลย — มันแค่คืน**ค่าลบ**กลับมาทาง x0 แล้ว libc เป็นคนแปลงเป็น "คืน -1 + ตั้ง errno" ให้

`raw_errno.c` พิสูจน์เรื่องนี้ด้วยการเทียบ syscall ดิบ กับ ฟังก์ชัน libc ในการทำเรื่องเดียวกัน (เปิดไฟล์ที่ไม่มีอยู่จริง):

```c
/* raw_errno.c — "errno มาจากไหน": เทียบ syscall ดิบ กับ ฟังก์ชัน libc */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

#define NR_OPENAT 56

static long raw_sys3(long nr, long a0, long a1, long a2)
{
    register long x8 __asm__("x8") = nr;
    register long x0 __asm__("x0") = a0;
    register long x1 __asm__("x1") = a1;
    register long x2 __asm__("x2") = a2;

    __asm__ volatile("svc #0" : "+r"(x0) : "r"(x8), "r"(x1), "r"(x2) : "memory", "cc");
    return x0;
}

int main(void)
{
    const char *missing = "/definitely/not/here/ep19.txt";

    /* 1) syscall ดิบ: เห็น "ค่าลบ" ตรง ๆ */
    long raw = raw_sys3(NR_OPENAT, -100 /* AT_FDCWD = "ใช้ cwd ปัจจุบัน" */,
                        (long)missing, O_RDONLY /* = 0 */);
    printf("== 1) syscall openat ดิบ (nr=%d) ==\n", NR_OPENAT);
    printf("ค่าที่ได้ใน x0 = %ld  (= -%ld) -> เคอร์เนลบอก \"ผิดพลาด\" ด้วยค่าลบ\n",
           raw, raw < 0 ? -raw : 0);

    /* 2) ฟังก์ชัน libc: เห็น -1 + errno */
    errno = 0;
    int fd = open(missing, O_RDONLY);
    printf("== 2) ฟังก์ชัน open() ของ libc ==\n");
    printf("ค่าที่คืนมา = %d   errno = %d (%s)\n", fd, errno,
           errno != 0 ? strerror(errno) : "-");

    /* 3) กับดัก: errno ไม่ถูกล้างให้เอง (ต่อจากข้อ 2: errno ยังเป็น 2 = ENOENT) */
    printf("== 3) กับดัก errno ==\n");
    (void)strerror(ENOENT); /* เรียกฟังก์ชันที่ "สำเร็จ" — มันไม่ล้าง errno ให้ */
    printf("เรียก strerror(ENOENT) แล้ว errno ยังเป็น %d (ฟังก์ชันที่สำเร็จไม่ต้องล้าง errno)\n",
           errno);
    fd = open("/tmp", O_RDONLY); /* สำเร็จ */
    printf("open(\"/tmp\") สำเร็จ (fd=%d) แต่ errno = %d -> อย่าใช้ errno ถ้า return ไม่บอกว่าพลาด\n",
           fd, errno);
    if (fd >= 0) {
        close(fd);
    }
    printf("\nหลักปฏิบัติ: เช็ค \"ค่าที่คืน\" ก่อนเสมอ · ถ้าค่าที่คืนบอกว่าพลาด ค่อยอ่าน errno\n");
    printf("             strerror() ใช้แปลง errno เป็นข้อความ · perror() พิมพ์ให้อัตโนมัติ\n");
    return EXIT_SUCCESS;
}
```

รันจริง:

```
== 1) syscall openat ดิบ (nr=56) ==
ค่าที่ได้ใน x0 = -2  (= -2) -> เคอร์เนลบอก "ผิดพลาด" ด้วยค่าลบ
แมปความหมายได้ว่า: -2 = -ENOENT (ENOENT = 2 = "No such file or directory")

== 2) ฟังก์ชัน open() ของ libc ==
ค่าที่คืนมา = -1   errno = 2 (No such file or directory)
libc แปลง -2 (จากเคอร์เนล) เป็น: return -1, ตั้ง errno = 2

== 3) กับดัก errno ==
เรียก strerror(ENOENT) แล้ว errno ยังเป็น 2 (ฟังก์ชันที่สำเร็จไม่ต้องล้าง errno)
open("/tmp") สำเร็จ (fd=3) แต่ errno = 2 -> อย่าใช้ errno ถ้า return ไม่บอกว่าพลาด

หลักปฏิบัติ: เช็ค "ค่าที่คืน" ก่อนเสมอ · ถ้าค่าที่คืนบอกว่าพลาด ค่อยอ่าน errno
             strerror() ใช้แปลง errno เป็นข้อความ · perror() พิมพ์ให้อัตโนมัติ
```

อ่านผลได้สามชั้น:

1. **syscall ดิบได้ `-2` ตรง ๆ** — เคอร์เนลไม่รู้จัก errno มันคืนเลขลบ (คือ `-errno`) กลับมา · ตรงนี้ `-2` = `-ENOENT` (ไฟล์/โฟลเดอร์ไม่มีอยู่จริง)
2. **libc แปลงให้** — ฟังก์ชัน `open()` ของ libc เห็นค่า -2 แล้วทำสองอย่าง: คืน `-1` (บอกเราว่า "ล้มเหลว") แล้วตั้ง `errno = 2` (บอกเราว่า "ล้มเพราะอะไร") · นี่คือเหตุผลที่โปรแกรม C ไม่เคยเห็นค่าลบจาก syscall ตรง ๆ
3. **กับดักคลาสสิก**: `errno` ไม่ถูกล้างให้เอง — ถ้า `open()` สำเร็จ ค่า errno จะค้างจาก syscall ครั้งก่อน (ทั้งที่สำเร็จและล้มเหลว) · กฎทองคือ **เช็คค่าที่คืนก่อนเสมอ** ถ้ามันบอกว่า "ล้มเหลว" (เช่น -1) ค่อยไปอ่าน errno

(ศัพท์ที่โผล่ตรงนี้: `AT_FDCWD` = บอก openat ว่า "ให้ตีความเส้นทางไฟล์เทียบกับโฟลเดอร์ที่กำลังทำงานอยู่" — โดย cwd = current working directory = โฟลเดอร์ที่โปรแกรมกำลังทำงานอยู่ · ส่วน `fd` กับ `strerror` อธิบายไว้ในกล่องคำศัพท์บนหัวบทแล้ว)

## 5. ลงมือทำ 3: ราคา syscall จริงเท่าไร (ภาพที่ 3)

ตอนที่ 18 เราวัด syscall เปล่า ๆ ได้ 178 ns ต่อครั้งแบบผ่าน ๆ คราวนี้มาวัดให้ละเอียด: syscall แพงกว่า "เรียกฟังก์ชันธรรมดา" กี่เท่า และ libc (ตัวห่อ) กินราคาไปเท่าไร

`syscall_cost.c` วัดของ 9 อย่าง อย่างละ 1,000,000 รอบ วัด 5 ครั้งแล้วเอา "เวลาที่เร็วสุด" (เร็วสุด = ตัวแทนของ "ตอนที่ไม่มีอะไรมารบกวน") — ใช้ `CLOCK_MONOTONIC` (นาฬิกา monotonic ที่ไม่ถูกปรับย้อนหลัง) วัดเป็นนาโนวินาที

```c
/* syscall_cost.c — วัดราคา syscall เทียบ "เรียกฟังก์ชันธรรมดา" (ย่อ)
 * build: gcc -std=c17 -Wall -Wextra -Wpedantic -O2 -o syscall_cost syscall_cost.c
 * run  : ./syscall_cost [จำนวนรอบ]        (ค่าเริ่มต้น 1000000)
 */
__attribute__((noinline, noipa)) static long noop(void)
{
    return 42;
}

/* เรียก noop 10 ครั้งต่อรอบ: ราคาฟังก์ชัน 1 ครั้งเล็กมาก (ราว 1 ns)
 * การวัด 10 ครั้งต่อรอบแล้วหารสิบ ช่วยลดความคลาดเคลื่อนของการวัดลงได้มาก */
static long bench_noop_x10(long n, long *ok)
{
    long acc = 0;

    for (long i = 0; i < n; i++) {
        acc += noop(); acc += noop(); acc += noop(); acc += noop(); acc += noop();
        acc += noop(); acc += noop(); acc += noop(); acc += noop(); acc += noop();
    }
    *ok = 1;
    return acc;
}
```

(ย่อ — ไฟล์เต็มมีตัววัดทั้ง 9 ตัว: ลูปเปล่า, noop x1, noop x10, getpid/getppid ทั้งผ่าน libc และผ่าน svc ตรง, write 1 ไบต์ไป /dev/null · พร้อมฟังก์ชัน `measure` ที่จับเวลาและหัก "ราคาลูปเปล่า" ออก · อยู่ใน `course/code/ep19/`)

รายละเอียดเทคนิคที่มือใหม่ควรเห็น: `noinline, noipa` สองคำสั่งนี้บังคับคอมไพเลอร์ว่า "ห้ามยุบฟังก์ชันนี้รวมเข้ากับลูป" และ "ห้ามมองเข้าไปในฟังก์ชันนี้" — เพราะถ้าคอมไพเลอร์รู้ว่า `noop` คืน 42 ตลอด มันจะตัดการเรียกทิ้งแล้วเราก็วัด "ความว่างเปล่า" แทน · นี่คือกับดักการวัด (benchmark) ที่เจอบ่อย

ผลรันจริง:

```

จำนวนรอบต่อตัววัด = 1000000 · วัดตัวละ 5 รอบ แล้วเอาเวลาที่เร็วสุด

[ราคารวมของทั้งลูป]
  1) ลูปเปล่า (ตัวลบ)                         0.4 ns/รอบ
  2) เรียก noop() แบบ noinline                1.7 ns/รอบ
  3) getpid() ผ่าน libc                     171.9 ns/รอบ
  4) getpid ผ่าน svc #0 ตรง ๆ               166.7 ns/รอบ
  5) getpid ผ่าน svc #0 x2 ต่อรอบ           331.3 ns/รอบ
  6) write 1 ไบต์ไป /dev/null (svc)         196.1 ns/รอบ
  7) getppid() ผ่าน libc                    177.0 ns/รอบ
  8) getppid ผ่าน svc #0 ตรง ๆ              172.4 ns/รอบ
  9) เรียก noop() x10 ต่อรอบ                 10.0 ns/รอบ

[หักราคาลูปเปล่าออกแล้ว = ราคาเนื้อ ๆ ต่อ 1 ครั้ง]
  เรียกฟังก์ชันเปล่า ๆ (noop)                1.25 ns
  เรียกฟังก์ชันเปล่า ๆ (noop x10 ÷10)        0.96 ns
  syscall getpid ผ่าน libc                 171.4 ns
  syscall getpid ผ่าน svc #0               166.3 ns
  syscall getpid ผ่าน svc #0 (2 ครั้ง/รอบ ÷2) 165.5 ns
  syscall write 1 ไบต์ไป /dev/null         195.7 ns
  syscall getppid ผ่าน libc                176.6 ns
  syscall getppid ผ่าน svc #0              172.0 ns

[อ่านเป็นประโยค]
  syscall แพงกว่าเรียกฟังก์ชันธรรมดา 173.1 เท่า (166.29 ns vs 0.96 ns)
  ตัวห่อของ libc เพิ่มราคาไป 5.1 ns (3% ของราคาทั้งหมด)
  syscall 1 ครั้ง = 166.3 ns · ถ้าเรียก 1,000,000 ครั้ง/วินาที จะกิน CPU 17%
  getppid: libc 176.6 ns · svc ตรง 172.0 ns (ตอนที่ 18 วัดได้ 178 ns ต่อครั้ง)
```

![ราคา syscall เทียบการเรียกฟังก์ชันจริง พร้อมรายการ syscall จริงของ hello world จาก strace](/assets/diagrams/ep19-03-syscall-cost-strace.svg)

ภาพที่ 3 สรุปตัวเลขสำคัญทั้งหมด มาอ่านความหมายทีละข้อ:

1. **syscall แพงกว่าฟังก์ชัน ~173 เท่า** (166.3 ns vs 0.96 ns) — เพราะการเรียกฟังก์ชันธรรมดาคือ "กระโดดไปโค้ดในโปรเซสเดียวกัน" (แค่ผลักค่าใส่ stack + `bl` + `ret` ใช้เวลาไม่ถึงนาโนวินาที) · แต่ syscall ต้อง**ข้ามกำแพง**: เปลี่ยนโหมด, บันทึก context, เปิดตาราง, ทำงาน, คืนโหมด — ทั้งชุดนี้คือของแพงที่เราจ่ายทุกครั้ง
2. **libc (ตัวห่อ) กินไปแค่ 3%** (5.1 ns) — 97% ของราคาคือ "การข้ามกำแพง" เอง ไม่ใช่ความช้าของ libc · แปลว่าถ้าอยากให้โปรแกรมเร็ว **ลดจำนวน syscall** ไม่ใช่หนี libc (libc แทบไม่เสียอะไรเลย แถมเขียนสะดวกกว่ากันเยอะ)
3. **ตัวเลขตรงกับตอนที่ 18** — ตอนนั้นวัด getppid ผ่าน libc ได้ 178 ns/ครั้ง · วันนี้วัดใหม่ได้ 176.6 ns (ต่างกัน ~1% = ค่าคงที่ระดับเครื่อง ไม่ได้มั่ว)
4. **"ถ้าเรียก 1 ล้านครั้ง/วินาที จะกิน CPU 17%"** — ตรงนี้คือบทเรียนปฏิบัติสำหรับวิศวกร: โค้ดที่เรียก syscall ในลูปร้อน ๆ (hot loop = ลูปที่ถูกวนถี่มากจนกิน CPU ส่วนใหญ่) โดยไม่จำเป็น เช่น อ่านไฟล์ทีละ 1 ไบต์ วน 1 ล้านรอบ จะเสีย CPU ไป 17% เฉพาะกับการเคาะประตู · วิธีแก้คือ "อ่านทีละก้อนใหญ่" (batch) เพื่อให้ syscall ครั้งเดียวทำงานได้เยอะ ๆ

(หมายเหตุการวัด: สังเกต "noop x10 ÷10 = 0.96 ns" นิ่งกว่า "noop x1 = 1.25 ns" — เพราะของที่เล็กมาก ๆ ต้อง**ขยายสัญญาณก่อนวัด** (วัด 10 ครั้งแล้วหาร 10) ไม่งั้นความคลาดเคลื่อนของนาฬิกาจะกลบตัวเลขจริง · นี่เป็นนิสัยการวัดที่ควรติดตัว)

## 6. ลงมือทำ 4: strace — แอบดู syscall ทุกครั้งของโปรแกรม

ทีนี้มาใช้เครื่องมือส่องของจริง: `strace` (system trace = ตัวติดตาม syscall) จะรายงาน syscall ทุกครั้งที่โปรแกรมเรียก พร้อม argument และผลลัพธ์ เริ่มจากโปรแกรม hello world ที่ง่ายที่สุด:

```c
/* hello_strace.c — โปรแกรมจิ๋วที่สุดที่ยังเป็น "โปรแกรมจริง"
 * build: gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -static -o hello_strace hello_strace.c */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(void)
{
    if (puts("hello จาก user space") == EOF) {
        perror("puts");
        return EXIT_FAILURE;
    }
    printf("pid = %d\n", (int)getpid());
    return EXIT_SUCCESS;
}
```

(ศัพท์ในโค้ดนี้: `puts` = พิมพ์ข้อความแล้วขึ้นบรรทัดใหม่ · `EOF` = End Of File เครื่องหมาย "จบไฟล์" ที่ `puts` คืนเมื่อเขียนไม่ออก · `perror` = พิมพ์ข้อความ error พร้อม errno ให้อัตโนมัติ · `EXIT_SUCCESS`/`EXIT_FAILURE` = รหัสออก 0/1 บอกว่าโปรแกรมจบปกติหรือผิดพลาด)

รันผ่าน strace โดยกรองดูเฉพาะ syscall ที่โปรแกรมเราเขียนเอง (คำสั่งจริงคือ `strace -e trace=write,getpid,exit_group ./hello_strace` — ตัดบรรทัดที่ข้อความของ syscall ระบบพิมพ์ซ้อนออกแล้ว):

```
write(1, "hello จาก user space\n", 27) = 27
getpid()                                = 21570
write(1, "pid = 21570\n", 12)           = 12
exit_group(0)                           = ?
+++ exited with 0 +++
```

เห็นชัดเลย: บรรทัด `puts("hello จาก user space")` ที่ดูเหมือนคำสั่งเดียว จริง ๆ คือ **syscall `write` หนึ่งครั้ง** เขียน 27 ไบต์ไปที่ fd 1 (= stdout = จอ) · `printf("%d", getpid())` ก็คือ syscall `getpid` + syscall `write` อีกครั้ง · และ `return` จาก main คือ `exit_group(0)`

แต่เดี๋ยวก่อน — ถ้าใช้ `strace -c` (ธง `-c` = นับรวมเป็นตารางสรุป) จะเห็นว่า "hello world หนึ่งบรรทัด" จริง ๆ เรียก syscall ไปตั้ง 16 ครั้ง (ไบต์นารีแบบ static — ที่เห็นเยอะกว่า 4 บรรทัดข้างบน เพราะ `-c` ไม่ได้กรอง จึงรวม syscall ที่ระบบต้องเรียกก่อนถึง `main` เข้ามาด้วย):

```
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
  0.00    0.000000           0         1           write
  0.00    0.000000           0         1           readlinkat
  0.00    0.000000           0         1           fstat
  0.00    0.000000           0         1           set_tid_address
  0.00    0.000000           0         1           set_robust_list
  0.00    0.000000           0         1           getpid
  0.00    0.000000           0         5           brk
  0.00    0.000000           0         1           execve
  0.00    0.000000           0         1           mprotect
  0.00    0.000000           0         1           prlimit64
  0.00    0.000000           0         1           getrandom
  0.00    0.000000           0         1           rseq
------ ----------- ----------- --------- --------- ----------------
100.00    0.000000           0        16           total
```

ที่เกินมาจาก "hello world" ล้วนเป็นงานตั้งต้นที่ระบบทำก่อนถึง `main`: `execve` (โหลดโปรแกรมขึ้นมา) · `brk` 5 ครั้ง (libc ขอหน่วยความจำจากเคอร์เนล) · `mprotect`/`prlimit64`/`set_tid_address` (งานเตรียมความปลอดภัยและเธรด) · `getrandom`/`rseq` (งานของไลบรารี) — **ทุกโปรแกรม แม้แต่ hello world ก็ยืนบน syscall เป็นสิบครั้งโดยที่เราไม่รู้ตัว**

ประเด็นที่สวยที่สุดอยู่ท้ายหัวข้อที่แล้ว (ภาพที่ 3): ลองรันโปรแกรมเดียวกันสองแบบ —

- **รันใน terminal (มี tty)**: เห็น `write` **2 ครั้ง** (27 ไบต์ + 12 ไบต์) — เพราะ libc ปรับให้ stdout เป็น "line-buffered" (ส่งออกทีละบรรทัด) เพื่อให้คนเห็นข้อความทันที
- **รันแบบไม่ใช่ terminal (redirect ไปไฟล์ หรือต่อท่อ pipe = ให้ข้อมูลไหลไปโปรแกรมอื่น)**: เห็น `write` **1 ครั้ง** (39 ไบต์รวมกัน) — เพราะปลายทางไม่ใช่คน libc เปลี่ยนเป็น "block-buffered" (รอสะสมก้อนใหญ่ก่อนส่ง) เพื่อให้เร็วขึ้น

ความต่างนี้คือหลักฐานว่า **แม้แต่ "เมื่อไรจะเรียก syscall" ก็มีคนคอยตัดสินใจให้เรา** — และถ้าคอมไพล์แบบไดนามิก (ค่าเริ่มต้นของ gcc) จำนวน syscall จะกระโดดเป็น 32 ครั้ง เพราะตัวโหลดไลบรารี (dynamic loader) ต้องเรียก `openat`/`mmap` (mmap = ขอจองหน่วยความจำจากเคอร์เนล — จะลงลึกในตอนที่ 20) เพิ่มอีกชุดเพื่อหาไลบรารีมาโหลด

## 7. ลงมือทำ 5: พิสูจน์กำแพงด้วย hardware (boundary_demo + enosys_probe)

สองโปรแกรมสุดท้ายปิดท้ายด้วยการพิสูจน์ว่า "กำแพง" ในหัวข้อ 1 ไม่ใช่แค่คำพูด แต่ hardware ปฏิเสธจริง

### 7.1 `boundary_demo.c` — อ่านทะเบียนของเคอร์เนล แล้วดูมันตาย

arm64 มีรีจิสเตอร์พิเศษกลุ่มหนึ่ง (system register) ที่ควบคุมระบบ ตัวที่ชื่อลงท้าย `_el0` โปรแกรมเรา (EL0) อ่านได้ · ตัวที่ลงท้าย `_el1` สงวนให้เคอร์เนล (EL1) เท่านั้น โปรแกรมพยายามอ่านเมื่อไร CPU จะยิงสัญญาณ **SIGILL** (Illegal Instruction = "คำสั่งนี้เธอไม่มีสิทธิ์ใช้") ใส่หน้าเลย:

```
== 1) อ่าน system register ของ arm64 จากโปรแกรม user space ==
  อ่านได้  cntvct_el0   = 0x00002d647d85da76   นาฬิกาเสมือน: EL0 อ่านได้ (มี _el0 ลงท้าย)
  อ่านได้  cntfrq_el0   = 0x000000000337f980   ความถี่นาฬิกา: EL0 อ่านได้
  อ่านได้  tpidr_el0    = 0x00007fff7b3f8740   ที่เก็บ pointer ของเธรด: EL0 อ่านได้
  ถูกกัน  CurrentEL    -> Illegal instruction (signal 4)   อยากรู้ว่าเราอยู่ exception level ไหน
  ถูกกัน  sctlr_el1    -> Illegal instruction (signal 4)   สวิตช์ระบบของ kernel (EL1 เท่านั้น)
  ถูกกัน  ttbr0_el1    -> Illegal instruction (signal 4)   ตัวชี้ตารางแปลที่อยู่ของ MMU (EL1 เท่านั้น)
  สรุป: ตัวที่ลงท้าย _el1 ถูก CPU กันไว้จริง — ไม่ใช่ข้อตกลง แต่เป็น hardware
```

(สามตัวที่ถูกกันล้วนสำคัญ: `CurrentEL` = ตัวบอกว่าตอนนี้เราอยู่ระดับสิทธิ์ไหน · `sctlr_el1` = สวิตช์ควบคุมระบบของเคอร์เนล · `ttbr0_el1` = ตัวชี้ "ตารางแปลที่อยู่" ของ MMU ซึ่งเป็นพระเอกของตอนที่ 20)

แล้วถ้าไม่แตะทะเบียน แต่พยายาม**อ่านหน่วยความจำของเคอร์เนล**ตรง ๆ ล่ะ (ที่อยู่ฝั่ง kernel เริ่มต้นด้วย `0xffff...`):

```
== 2) แตะที่อยู่ใน kernel space ==
  อ่านที่อยู่ 0x0000000000000000 ไม่ได้: Segmentation fault · si_addr=0x0 · si_code=1 (SEGV_MAPERR: ไม่มี mapping ตรงที่อยู่นี้)
  อ่านที่อยู่ 0xffff000000000000 ไม่ได้: Segmentation fault · si_addr=0xffff000000000000 · si_code=1 (SEGV_MAPERR: ไม่มี mapping ตรงที่อยู่นี้)

== 3) ที่อยู่ที่โปรเซสนี้แตะได้จริง (สรุปจาก /proc/self/maps) ==
  จำนวนช่วงที่อยู่ (region) = 16  (อ่านได้ 15 · เขียนได้ 7 · รันโค้ดได้ 4)
  ช่วงที่อยู่ที่โปรเซสแตะได้ = 0x55560cd00000 .. 0x7fffe0030000
  &main = 0x55560cd00d74  ·  ตัวแปรบน stack = 0x7fffe002bcb8
  ทั้งหมดนี้อยู่ในย่าน user space — ที่อยู่ของเคอร์เนล (0xffff...)
  ไม่มีอยู่ในตารางเลย จึงไม่มีทางอ่านได้จากโปรแกรมเรา
```

ผลชัดเจน: แตะที่อยู่เคอร์เนล → **SIGSEGV** (Segmentation fault = "แตะหน่วยความจำที่ไม่มีสิทธิ์") · `si_code=1` (SEGV_MAPERR) แปลว่า "ที่อยู่นี้ไม่มีอยู่ในตารางที่ MMU อนุญาตให้โปรเซสนี้แตะ" (ตารางนี้เปิดดูได้จาก `/proc/self/maps` = ไฟล์พิเศษที่เคอร์เนลเปิดไว้ให้โปรเซสอ่านแผนที่หน่วยความจำที่ตัวเองแตะได้) · สังเกตว่าที่อยู่ของโปรแกรมเราทั้งหมด (ตัวโค้ด 0x5555..., stack 0x7fff...) อยู่ในย่าน user space และ**ไม่มี**ที่อยู่ `0xffff...` ของเคอร์เนลปะปนอยู่ในตารางเลย — นี่คือหลักฐานว่ากำแพงเป็นของ MMU จริง ๆ

ศัพท์ที่โผล่ตรงนี้ ขอแยกเป็นข้อ ๆ:

- `SIGSEGV` กับ `SIGILL` เป็น "สัญญาณ" (signal) ที่เคอร์เนลส่งมาบอกโปรเซสว่า "เธอทำผิดกติกา"
- `si_addr` = ที่อยู่ที่ทำให้เกิดปัญหา · `si_code` = รหัสบอกรายละเอียด
- โปรแกรมที่แตะที่อยู่เคอร์เนลแล้วไม่จับสัญญาณจะตายด้วยรหัสออก **139** = 128 + 11 (11 คือหมายเลขของ SIGSEGV) — ซึ่ง `segv_trigger.c` ในโฟลเดอร์โค้ดสาธิตให้เห็น

(หมายเหตุ: ตัวเลขที่อยู่เปลี่ยนทุกครั้งที่รัน เพราะระบบมีกลไก **ASLR** (Address Space Layout Randomization = สุ่มตำแหน่งของโค้ด/stack ทุกครั้งที่รัน) เพื่อให้คนร้ายเดาตำแหน่งของโค้ดยากขึ้น — ที่เห็นในภาพที่ 1 เป็นอีกรันหนึ่ง จึงเลขไม่ตรงกับตรงนี้ แต่นับจำนวน region ได้เท่ากัน)

### 7.2 `enosys_probe.c` — พิสูจน์ว่ามี "ตาราง syscall" จริง

หัวข้อ 3 เราบอกว่าเคอร์เนลใช้ x8 ไปเปิดตาราง แล้วถ้าตารางไม่มีจริงล่ะ? พิสูจน์ด้วยการยิงเลข syscall ที่มั่วขึ้นมา แล้วดูว่าเคอร์เนลตอบยังไง — บน arm64 ไฟล์ `/usr/include/asm-generic/unistd.h` ประกาศว่า `#define __NR_syscalls 470` แปลว่าตารางมีช่อง 0..469 — และนี่คือที่มาของเลข syscall ที่เราใช้ทั้งบท (ย่อจากไฟล์จริง):

```
158:#define __NR_openat 56
160:#define __NR_close 57
172:#define __NR_read 63
174:#define __NR_write 64
260:#define __NR_exit_group 94
461:#define __NR_getpid 172
463:#define __NR_getppid 173
862:#define __NR_syscalls 470
```

```
== ลองยิงเลข syscall ไปที่ตาราง แล้วดูเคอร์เนลตอบ ==
  svc #0 nr=0    -> -22  (= -22 EINVAL: มีช่องแต่ยังไม่รองรับ/อาร์กิวเมนต์ผิด)   มีช่องหมายเลข 0 จริง (io_setup) — ไม่มี argument ที่ถูก ที่นี่เลยได้ -EINVAL/-EFAULT
  svc #0 nr=469  -> -22  (= -22 EINVAL: มีช่องแต่ยังไม่รองรับ/อาร์กิวเมนต์ผิด)   ช่องสุดท้ายของตาราง (469)
  svc #0 nr=470  -> -38  (= -38 ENOSYS: ไม่มี syscall หมายเลขนี้)   เลขแรกที่ "เกินตาราง" = __NR_syscalls
  svc #0 nr=471  -> -38  (= -38 ENOSYS: ไม่มี syscall หมายเลขนี้)   เกินตารางไปอีก
  svc #0 nr=999  -> -38  (= -38 ENOSYS: ไม่มี syscall หมายเลขนี้)   เกินไปไกล

สรุป: เลขที่เกิน __NR_syscalls (470) ได้ -ENOSYS (= -38) เสมอ
      -> มี "ตาราง" จริง เพราะถ้าไม่มี จะดูเลขแล้วตอบแบบนี้ไม่ได้
      ที่มาของเลข: /usr/include/asm-generic/unistd.h (arm64 ใช้ตาราง generic)
```

อ่านผล: เลขที่ "มีช่องในตาราง" (0..469) เคอร์เนลตอบด้วย `-EINVAL` (รหัส -22 = "มี syscall นี้อยู่ แต่ argument ที่ส่งมาไม่ถูกต้อง") · เลขที่ "เกินตาราง" (470 ขึ้นไป) ตอบ `-ENOSYS` (รหัส -38 = "ไม่มีฟังก์ชันนี้ในระบบ") ทันที — ความสม่ำเสมอนี้เป็นไปไม่ได้ถ้าไม่มีตารางจริง ๆ อยู่เบื้องหลัง

## 8. สรุปสิ่งที่ได้เรียนรู้

1. **CPU มีสองโหมดสิทธิ์** — user space (EL0) กับ kernel space (EL1) · กำแพงระหว่างสองโลกนี้**บังคับโดย hardware** (CPU + MMU) ไม่ใช่ข้อตกลง · โปรแกรมข้ามกำแพงเองไม่ได้ (โดน SIGILL/SIGSEGV)
2. **syscall คือประตูบานเดียว** — บน arm64 คือคำสั่ง `svc #0` · ใส่เลข syscall ใน x8, argument ใน x0..x5, ผลกลับมาทาง x0 · libc เป็นแค่ "ตัวห่อ" ที่เตรียมรีจิสเตอร์แล้วยิงประตูให้เรา
3. **เคอร์เนลมีตาราง syscall** — ใช้ x8 เปิดตารางหาฟังก์ชัน · เลขเกินตาราง (470+) ตอบ `-ENOSYS` · ตัวตารางยืนยันได้จาก unistd.h
4. **errno เป็นสิ่งประดิษฐ์ของ libc** — เคอร์เนลคืน "ค่าลบ" (=-errno) · libc แปลงเป็น "คืน -1 + ตั้ง errno" · ต้องเช็คค่าที่คืนก่อนเสมอ อย่าอ่าน errno ลอย ๆ
5. **syscall แพงกว่าเรียกฟังก์ชัน ~173 เท่า** (166.3 ns vs 0.96 ns) — ราคาเกือบทั้งหมดอยู่ที่ "การข้ามกำแพง" · libc กินแค่ 3% · ลดจำนวน syscall = ทำให้โปรแกรมเร็ว
6. **ทุกโปรแกรมยืนบน syscall** — แม้แต่ hello world เรียก syscall 16 ครั้ง (static) / 32 ครั้ง (dynamic) · strace ใช้ส่องได้ทุกครั้ง

## 9. โจทย์ฝึกมือ (2 ระดับ)

### ระดับ Drill (ซ้อมทวนความเข้าใจ)

1. แก้ `raw_write.c` ให้เรียก syscall `getuid` (หาเลขจาก `/usr/include/asm-generic/unistd.h` ก่อน — อย่าเดา) แล้วพิมพ์ค่า UID ของตัวเองออกมา · ยืนยันด้วยคำสั่ง `id -u` ใน terminal
2. รัน `strace -c ls` ในโฮมไดเรกทอรี แล้วนับว่า `ls` เรียก syscall ทั้งหมดกี่ครั้ง · ตัวไหนถูกเรียกบ่อยสุด · เทียบกับ hello world ของเราที่เรียก 16 ครั้ง — ทำไม `ls` ถึงเยอะกว่า
3. ดูผล `./syscall_cost 1000000` ที่คุณรันเอง — ตัวเลขต่างจากในบทนี้เล็กน้อยไหม? ทำไมการวัดถึงไม่มีทางได้เลขเท่ากันเป๊ะทุกครั้ง (ใบ้: เรื่อง "เอาเวลาที่เร็วสุด" กับ "อะไรกำลังวิ่งอยู่บน CPU เดียวกัน")

### ระดับ Mini-Project (ประกอบความรู้)

**เขียนโปรแกรม `raw_cat.c`** — "แมว" เวอร์ชันไม่พึ่ง libc สำหรับงาน I/O: รับชื่อไฟล์จาก argument แล้วแสดงเนื้อหาออกจอ โดยเรียก syscall `openat` (nr=56), `read` (nr=63), `write` (nr=64), `close` (nr=57) ตรง ๆ ด้วย `svc #0` ทั้งหมด

- ข้อกำหนด: ต่อยอดจาก `raw_write.c` (ใช้ `out()` เดิม) · อ่านทีละก้อน 4096 ไบต์ (อย่าอ่านทีละ 1 ไบต์ — จำบทเรียนเรื่องราคา syscall) · หยุดเมื่อ `read` คืน 0 (= จบไฟล์) หรือค่าลบ (= ผิดพลาด)
- เช็คผล: `./raw_cat /etc/hostname` ต้องแสดงเนื้อหาเหมือน `cat /etc/hostname` เป๊ะ · แล้วลอง `./raw_cat /ไม่มีไฟล์นี้` ดูว่าได้ค่าลบ `-ENOENT` ตรง ๆ (ไม่ใช่ -1)
- โบนัส: ลองอ่านทีละ 1 ไบต์แล้วรัน `strace -c` นับจำนวน `read` เทียบกับแบบ 4096 ไบต์ — อธิบายว่าทำไมแบบ 1 ไบต์ถึงแพงกว่ามาก

## 10. คำเตือนตามกาลเวลา + แหล่งอ้างอิง

**As of กันยายน 2026** — ข้อเท็จจริงทั้งหมดในบทนี้ยืนยันจากการรันจริงบน Raspberry Pi 5 (Linux 6.18.39+rpt-rpi-2712 aarch64, GCC 14.2.0, glibc 2.41, strace 6.13) · ค่าคงที่ที่อ้างถึง (เลข syscall เช่น write=64/getpid=172, `__NR_syscalls=470`, ราคา syscall ~166 ns/ครั้ง) เป็นค่าของ **arm64 + เคอร์เนลรุ่นนี้บนเครื่องนี้** — สถาปัตยกรรมอื่น (เช่น x86) ใช้เลข syscall และคำสั่งเข้าเคอร์เนล (`syscall`) ต่างออกไป เคอร์เนลรุ่นใหม่ก็เพิ่ม/ย้าย syscall ได้ จึงควรตรวจจากแหล่งปัจจุบันเสมอ (เช่น `grep __NR_ /usr/include/asm-generic/unistd.h`, `man 2 syscall`, เอกสาร kernel.org, หรือลองรันเองตามโค้ดใน `course/code/ep19/`)

แนวคิดเรื่อง user space/kernel space และ syscall อาจถูกท้าทายได้ในอนาคต (เช่น เทคนิค syscall แบบใหม่ที่ลดราคาการข้ามกำแพง, kernel ที่เปลี่ยนรูปแบบ อย่าง microkernel/library OS, หรือแนวคิดปลอดภัยแบบใหม่) — จุดที่ไม่เปลี่ยนคือ**หลักการ**: การแยกสิทธิ์เพื่อความปลอดภัย และ "ประตูเดียว" ที่ควบคุมการเข้าถึงระบบ

**แหล่งอ้างอิงหลัก**: เอกสาร Linux `man 2 syscall` (ตาราง syscall ของ arm64) · `man 2 intro` (ภาพรวม syscall) · ARM Architecture Reference Manual (exception levels EL0/EL1 และคำสั่ง `svc`/`eret`) · `man 1 strace` · ไฟล์ `/usr/include/asm-generic/unistd.h` บนเครื่อง · เอกสาร glibc (errno และ thread-local storage)
