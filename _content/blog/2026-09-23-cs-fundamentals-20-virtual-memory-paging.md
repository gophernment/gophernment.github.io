# virtual memory — ที่อยู่ปลอมที่โปรแกรมเห็น + paging (ตอนที่ 20) — CS Fundamentals: จาก 0 สู่พื้นฐานที่แท้จริง

ตอนที่ 18 เราเห็นเรื่องที่ชวนงงที่สุดเรื่องหนึ่งของระบบปฏิบัติการ: พอ `fork` (สั่งให้โปรเซสแยกตัวเองเป็นพ่อ-ลูก — เรียนแล้วในตอนที่ 18) ออกมาเป็นสองโปรเซส **ตัวแปรตัวเดียวกันกลับมี "ที่อยู่" ตัวเลขเดียวกันเป๊ะ** (`&g_counter` ของพ่อกับลูกเป็น `0x5556530f0080` เท่ากัน) แต่เขียนฝั่งหนึ่ง อีกฝั่งไม่เปลี่ยน

ตอนที่ 19 เราเรียนว่าโปรแกรมอยู่คนละโลกกับเคอร์เนล และ "กำแพง" ระหว่างสองโลกบังคับโดย hardware — ตอนนั้นมีตัวหนึ่งที่เราบอกว่า "จะลงลึกในตอนที่ 20" นั่นคือ **MMU (Memory Management Unit = ฮาร์ดแวร์ใน CPU ที่แปลที่อยู่)** ตอนนี้คือตอนนั้นครับ

คำถามของบทนี้มีข้อเดียว แต่ตอบแล้วจะเข้าใจหน่วยความจำทั้งระบบ:

> **RAM มีก้อนเดียว แต่ทำไมแต่ละโปรแกรมถึงเห็น "ที่อยู่ของตัวเองทั้งก้อน" ได้?**

และคำถามพ่วงที่ตามมา: ที่อยู่ที่โปรแกรมเห็น (`0x5555...`, `0x7fff...`) มันคือที่อยู่จริงบนชิป RAM หรือเปล่า? ถ้าไม่ใช่ แล้วมันคืออะไร? ใครเป็นคนแปล? และการแปลเกิดขึ้นกี่ครั้งต่อการอ่านตัวแปร 1 ตัว?

สิ่งที่บทนี้จะตอบ พร้อมรันจริงทุกข้อ:

1. **ภาพลวงตา** — โปรเซสเห็น address space (พื้นที่ที่อยู่) ของตัวเองเต็ม ๆ ตั้งแต่ `0x5555...` ถึง `0x7fff...` ทั้งที่แชร์ RAM ก้อนเดียว
2. **virtual address กับ physical address** — ที่อยู่ปลอมกับที่อยู่จริงต่างกันยังไง และทำไมต้องมีชั้นนี้ทำไมต้องแยก (isolation · protection · overcommit · shared library)
3. **paging** — หน่วยความจำถูกตัดเป็นหน้า (page), แปลผ่านตาราง (**page table**) แล้ว MMU ทำงานยังไง
4. **page fault** — หน้าที่ "ยังไม่ถูกจองจริง" แล้วเกิดอะไรขึ้น ทำไมมันไม่ใช่ crash
5. **TLB** — แคชของการแปลที่อยู่ และตัวเลขจริงว่าไม่ต้องแปลทุกครั้งเร็วขึ้นเท่าไหร่

> **หมายเหตุเรื่อง page size — สำคัญมากและต้องพูดก่อนเลย**
> หลายตำรา (และโจทย์หลายที่) จะบอกว่า page = **4096 ไบต์**
> **บนเครื่องที่เราใช้อยู่ในคอร์สนี้ไม่ใช่ 4096** — เครื่องนี้คือ Raspberry Pi 5 ที่รัน kernel ซึ่งคอมไพล์มาสำหรับ **16 KiB granule** (granule = ขนาดหน่วยย่อยของตารางแปลที่ MMU ใช้ — บนเครื่องนี้เท่ากับ page พอดี):
> ```
> $ getconf PAGESIZE
> 16384
> $ grep -E "ARM64_16K_PAGES|ARM64_4K_PAGES|PGTABLE_LEVELS|ARM64_VA_BITS=" /boot/config-6.18.39+rpt-rpi-2712
> CONFIG_PGTABLE_LEVELS=3
> # CONFIG_ARM64_4K_PAGES is not set
> CONFIG_ARM64_16K_PAGES=y
> CONFIG_ARM64_VA_BITS=47
> ```
> ดังนั้นเลขทุกตัวในบทนี้คิดบน **page = 16384 ไบต์** เสมอ การเช็ค page size ของเครื่องตัวเองเป็นสิ่งแรกที่ต้องทำ และ **อย่าเดา** — ใช้ `getconf PAGESIZE` ถ้าคุณรันบน x86-64 ทั่วไปจะได้ 4096, ถ้ารันบน Pi 5 จะได้ 16384, ถ้ารันในคอนเทนเนอร์จะได้เท่ากับเครื่องแม่ (เพราะใช้ kernel ตัวเดียวกัน)

ทุกตัวเลขในบทนี้มาจากการรันจริงบนเครื่องเรา (Raspberry Pi 5, Linux 6.18.39+rpt-rpi-2712 aarch64, Cortex-A76 2.4 GHz 4 คอร์, GCC 14.2.0, glibc 2.41, Go 1.24.4) — โค้ดทุกไฟล์อยู่ที่ `course/code/ep20/` และผลรันดิบอยู่ที่ `course/code/ep20/out/`

> **คำศัพท์พื้นฐานของบทนี้** (อธิบายครั้งเดียวตรงนี้ แล้วใช้ต่อทั้งบท — ไม่มี footnote ในบทความนี้เพราะ dev.to ไม่รองรับ):
> - **virtual memory (หน่วยความจำเสมือน)** = ชั้น "ที่อยู่ปลอม" ที่ OS สร้างให้ทุกโปรเซส เพื่อให้แต่ละโปรเซสเห็นหน่วยความจำของตัวเองทั้งก้อน
> - **address space (พื้นที่ที่อยู่)** = ช่วงที่อยู่ทั้งหมดที่โปรเซสหนึ่งเห็น · บนเครื่องนี้ 47 บิต = 128 TiB
> - **virtual address (VA)** = ที่อยู่ปลอมที่โปรแกรมเห็น · ค่าที่ `printf("%p")` พิมพ์ออกมา
> - **physical address (PA)** = ที่อยู่จริงบนชิป RAM · โปรแกรมผู้ใช้ไม่มีทางเห็นค่านี้ตรง ๆ
> - **MMU** (Memory Management Unit) = ฮาร์ดแวร์ใน CPU ที่แปลง VA → PA ทุกครั้งที่แตะหน่วยความจำ
> - **page (หน้า)** = บล็อกขนาดเท่ากันที่หน่วยความจำถูกตัดเป็น · บนเครื่องนี้ 16384 ไบต์
> - **frame (กรอบ)** = ช่องจริงบน RAM ขนาดเท่า page หนึ่งหน้า · RAM 8 GiB ของเรา (ใช้ได้จริง 7.9 GiB = 8,454,012,928 ไบต์) จึงมี `8,454,012,928 ÷ 16384 = 515,992` frames
> - **offset (ระยะคลาด)** = ตำแหน่งภายในหน้าหนึ่ง (0..16383) · ท่อนนี้ "ไม่ต้องแปล" ผ่านตรง ๆ
> - **VPN** (virtual page number) = เลขหน้าที่อยู่เสมือน · **PFN** (page frame number) = เลข frame จริงบน RAM
> - **page table (ตารางหน้า)** = ตารางที่เก็บว่า VPN ไหน → PFN ไหน · โปรเซสละตาราง
> - **PTE** (page table entry) = หนึ่งช่องในตาราง · เก็บเลข frame + "ธง" สิทธิ์ (present/read-write/user/dirty/accessed)
> - **page walk (เดินตาราง)** = กระบวนการไล่ตารางทีละชั้นเพื่อหาค่าแปล · บนเครื่องนี้ 3 ชั้น
> - **TLB** (Translation Lookaside Buffer) = แคช (หน่วยความจำเร็วพิเศษขนาดเล็ก) ใน MMU ที่จำ "ผลแปลล่าสุด" ไว้ ไม่ต้องเดินตารางซ้ำ
> - **page fault** = เหตุการณ์ที่ MMU เปิดตารางแล้วไม่เจอค่าแปลที่ใช้ได้ · CPU กระโดดเข้าเคอร์เนลให้จัดการ
> - **minor fault** = fault ที่แก้จบในหน่วยความจำ (หา frame ว่างให้) · **major fault** = fault ที่ต้องรออ่านจากดิสก์/สวอป
> - **lazy allocation (จองแบบขี้เกียจ)** = จองที่อยู่ไว้ก่อน แต่ยังไม่ให้ frame จริงจนกว่าจะแตะ
> - **overcommit** = อนุญาตให้ผลรวมที่อยู่ที่จองไว้ "เกิน" RAM จริงที่มี
> - **COW** (copy-on-write = คัดลอกเมื่อเขียน) = แชร์ frame กันก่อน พอมีใครเขียนค่อยแยก frame ให้
> - **VS / RSS** = `VS` (virtual size) ที่อยู่ทั้งหมดที่โปรเซสจอง · `RSS` (resident set size) ส่วนที่อยู่ใน RAM จริง · อ่านได้จาก `/proc/<pid>/statm` (`<pid>` = เลขประจำตัวโปรเซส) (หน่วยเป็น "หน้า")
> - **ASLR** (Address Space Layout Randomization) = การสุ่มตำแหน่งเริ่มต้นของแต่ละก้อนทุกครั้งที่รัน เพื่อไม่ให้เดาง่าย
> - **TTBR0_EL1 / TTBR1_EL1** = รีจิสเตอร์ที่เก็บ "ฐานของตาราง" ของฝั่ง user / ฝั่ง kernel
> - **mprotect()** = ฟังก์ชันเปลี่ยนสิทธิ์ (อ่าน/เขียน/รัน) ของช่วงที่อยู่ · **MAP_NORESERVE / MAP_POPULATE** = ธงตอนขอหน่วยความจำ (ไม่จองที่สำรอง / จ่ายล่วงหน้าเลย)
> - **/proc/self/maps** = ไฟล์ที่เคอร์เนลบอกว่า VA ช่วงไหนคืออะไร · **/proc/self/pagemap** = ไฟล์ที่บอกว่าหน้าไหนมี frame จริงแล้ว
> - **mmap() / munmap()** = ฟังก์ชันขอ / คืนช่วงที่อยู่จาก OS เป็นก้อน (ไม่ต้องมีไฟล์ต้นทางก็ได้)
> - **pid** = เลขประจำตัวของโปรเซส (process id) · ใช้แทน `<pid>` ในเส้นทาง `/proc/<pid>/...`
> - **รีจิสเตอร์** (register) = ช่องเก็บค่าชนิดพิเศษใน CPU อ่าน/เขียนได้เร็วที่สุด
> - **แคช** (cache) = หน่วยความจำเร็วพิเศษขนาดเล็กที่เก็บสำเนาข้อมูลที่เพิ่งใช้/จะใช้ · **DRAM** = ชิป RAM ตัวจริง (ช้ากว่าแคชหลายเท่า)
> - **heap** = พื้นที่ที่ขอตอนโปรแกรมรัน (malloc) · **stack** = พื้นที่เก็บตัวแปรในฟังก์ชัน (ย้อนตอนที่ 15) · **.data/.bss** = ตัวแปร global มี/ไม่มีค่าเริ่มต้น (ย้อนตอนที่ 17) · **.rodata** = ข้อมูลค่าคงที่ อ่านได้อย่างเดียว
> - **runtime** = โค้ดที่แถมมากับภาษา (เช่น Go) ทำหน้าที่จัดการเบื้องหลังให้ ไม่ใช่โค้ดที่เราเขียนเอง

## 1. แนวคิด: ภาพลวงตาที่ทุกโปรแกรมเชื่อสนิท (ภาพที่ 1)

![โปรเซสเห็นที่อยู่ปลอมของตัวเอง แล้ว MMU แปลเป็น frame จริงบน RAM ก้อนเดียว พร้อมหลักฐานจาก fork/COW](/assets/diagrams/ep20-01-virtual-vs-physical.svg)

ภาพที่ 1 คือคำตอบสั้น ๆ ของทั้งบท: มี "ตารางแปลที่อยู่" คั่นกลาง โปรเซสซ้ายเห็น VA ของตัวเอง ฝั่งขวาคือ frame จริงบน RAM และตรงกลางคือ MMU ที่อ่านตารางของโปรเซสนั้น

ก่อนจะไปโค้ด ขอตั้งภาพให้ตรงกัน 3 ข้อ:

**ข้อ 1 — ที่อยู่คือ "เลข" ไม่ใช่ "ช่อง"** มือใหม่มักคิดว่า `0x5555a39f42a0` คือ "ตำแหน่งบนแรม" จริง ๆ แต่ในโลกของโปรแกรม มันคือเลขที่ OS กำหนดให้เป็นชื่อเล่นต่างหาก สองโปรเซสใช้ชื่อเล่นซ้ำกันได้ เพราะต่างคนต่างมีตารางแปลของตัวเอง

**ข้อ 2 — ท่อนล่างของที่อยู่ถูกใช้ตรง ๆ** เมื่อ VA = 16384 × VPN + offset ท่อน offset (14 บิตล่างสุด) ไม่ต้องแปลเลย — มันหมายถึง "ไบต์ที่เท่าไรในหน้านั้น" เหมือนเดิมทุกโปรเซส สิ่งที่ต้องแปลมีแค่ VPN เท่านั้น นี่คือเหตุผลที่หน่วยความจำถูกตัดเป็นหน้า: แทนที่จะแปลทีละไบต์ (ไม่มีทางทำได้จริง) ก็แปลทีละหน้า

**ข้อ 3 — ที่อยู่ถูกจัดเป็นสองช่วงที่ห่างกันมาก** โปรแกรมหนึ่งตัวบน Linux aarch64 จะเห็นที่อยู่ 2 กลุ่ม:
- กลุ่ม `0x5555...` (ต่ำ) = โค้ดของโปรแกรม · ข้อมูล global · heap
- กลุ่ม `0x7fff...` (สูง) = ไลบรารีที่แชร์ (libc) · stack · หน่วยความจำที่ `mmap` ขอมา (mmap = ฟังก์ชันขอช่วงที่อยู่ใหม่จาก OS เป็นก้อน)

ทั้งสองกลุ่มอยู่ในฝั่ง user space ทั้งคู่ (โปรเซสผู้ใช้ไม่เห็นฝั่ง kernel ที่ขึ้นต้นด้วย `0xffff...`) และช่องว่างระหว่างสองกลุ่มจะเวิ้งว่างเป็น "รู" ขนาดหลายสิบ TiB ที่โปรเซสไม่มีอะไรอยู่เลย — ทั้งหมดนี้คือผลของ ASLR + การจัด layout ของเคอร์เนล

## 2. ลงมือทำ: `01_addr_layout.c` — จับที่อยู่จริงของทุกอย่างในโปรแกรมเดียว

เริ่มจากเครื่องมือตรวจที่อยู่ก่อน เพราะทุกอย่างหลังจากนี้ต้องใช้มัน

> **แผนที่ไฟล์ของบทนี้** (ทั้งหมดใน `course/code/ep20/`): 01=ที่อยู่ของทุกอย่าง (หัวข้อ 2) · 02=เลขคณิตหน้า/ตาราง (หัวข้อ 5) · 03=mmap กับไฟล์ (หัวข้อ 4) · 04=fork ภาพลวงตา (หัวข้อ 3) · 05=ราคา fault (หัวข้อ 6.2) · 06=mprotect กำแพงสิทธิ์ (หัวข้อ 6.3) · 07=TLB (หัวข้อ 7) · 08=Go (หัวข้อ 8) — ลำดับไฟล์ไม่ตรงกับลำดับหัวข้อ เพราะแต่ละไฟล์โฟกัสคนละคำถาม · **ทุกบล็อกโค้ดที่เห็น `...` คือตัดมาเฉพาะแกน ไฟล์เต็มอยู่ที่ `course/code/ep20/`**

```c
/* 01_addr_layout.c — "ที่อยู่" ที่โปรแกรมเห็น (virtual address) ของข้อมูลแต่ละชนิด
 *
 * build: gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -g -o 01_addr_layout 01_addr_layout.c
 * run  : ./01_addr_layout
 */
#define _GNU_SOURCE
#include <inttypes.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static int         g_data = 42;                 /* .data  — มีค่าเริ่มต้น */
static int         g_bss;                       /* .bss   — ไม่มีค่าเริ่มต้น */
static const char *const g_ro = "ข้อความใน .rodata";

static int helper(void)
{
	return (int)(uintptr_t)&helper & 1;   /* เอาเลขที่อยู่ของฟังก์ชันมา & 1 ให้ได้ค่าที่คอมไพเลอร์เดาไม่ได้ -> linker ต้องเก็บฟังก์ชันนี้ไว้ */
}

static void show(const char *what, uintptr_t va, long page)
{
	uintptr_t base = va & ~((uintptr_t)page - 1);   /* ตัดท่อน offset ทิ้ง = หัวหน้าของหน้า */

	printf("%-20s VA = 0x%012" PRIxPTR "   หน้า = 0x%012" PRIxPTR "   offset = %5" PRIuPTR "\n",
	       what, va, base, va - base);
}

int main(void)
{
	long  page = sysconf(_SC_PAGESIZE);
	int  *heap = malloc(sizeof *heap);
	int   stack_var = 7;
	int   stack_arr[4] = { 1, 2, 3, 4 };

	if (page <= 0) {
		perror("sysconf(_SC_PAGESIZE)");
		return 1;
	}
	if (heap == NULL) {          /* malloc คืน NULL ได้จริง ถ้าหน่วยความจำหมด */
		perror("malloc");
		return 1;
	}
	*heap = 1234;
```

1. **ทุกช่วงยาวเป็นจำนวนเท่าของ 16384 เสมอ** — ไม่มีช่วงไหนยาว 1000 ไบต์เดี่ยว ๆ เพราะหน่วยที่จัดการคือ "หน้า" ไม่ใช่ "ไบต์"
2. **`r-xp` ของโค้ด · `r--p` ของค่าคงที่ · `rw-p` ของตัวแปร** — สิทธิ์ถูกกำหนดเป็นหน้า ๆ ไป (นี่คือ protection ที่จะเห็นผลจริงในหัวข้อ 5)
3. **`---p` ของ libc เป็น "ช่วงปิด" ยาว 65536 ไบต์** — เคอร์เนลกันไว้เป็นกำแพง (guard) ให้โปรแกรมที่เขียนล้นออกจากพื้นที่ของ libc โดน SIGSEGV (สัญญาณที่ทำให้โปรเซสถูกฆ่าทันที — ที่บ้านเราเรียก segmentation fault) ทันที ไม่ไหลไปทับของคนอื่น
4. **`[vvar]` กับ `[vdso]`** — หน้าเล็ก ๆ ที่เคอร์เนลแปะไว้ให้ user space อ่านข้อมูลเวลา/เรียกฟังก์ชันเร็ว ๆ ได้ โดยไม่ต้องข้ามกำแพงด้วย syscall (ตัว `linux-vdso.so.1` เคยโผล่ในผล `ldd` ของตอนที่ 17 แล้ว)
5. **`[heap]` ช่วง `0x5555a39f4000–0x5555a3a18000` ยาว 147,456 ไบต์ (9 หน้า)** แต่เราจองแค่ 4 ไบต์! — แปลว่า malloc ขอพื้นที่มาเป็นก้อนใหญ่เผื่อไว้แล้ว แค่ 4 ไบต์นั้นต้องใช้จริง

ข้อ 5 คือเบาะแสสำคัญของเรื่องที่บทนี้ทั้งบทจะพูดถึง: **"ที่อยู่ที่จอง" กับ "ที่อยู่ที่ใช้จริง" คนละจำนวนกัน**

## 3. พิสูจน์ภาพลวงตา: `04_fork_illusion.c`

ก่อนไปเรื่อง paging เรามาพิสูจน์ "ที่อยู่ซ้ำกันของสองโปรเซส" ให้ชัดก่อน — เพราะเป็นหลักฐานที่ตรงที่สุดว่าที่อยู่ไม่ใช่ตำแหน่งจริงบน RAM (ต่อยอดจากตอนที่ 18 ตรง ๆ)

โค้ดจริงใน `04_fork_illusion.c` (ตัดมาเฉพาะแกน ไฟล์เต็มอยู่ `course/code/ep20/04_fork_illusion.c`):

```c
static int g_shared = 100;

static void dump(const char *who, int *heap)
{
	struct rusage ru;
	if (getrusage(RUSAGE_SELF, &ru) != 0) {
		perror("getrusage");
	}
	printf("%-8s pid=%-7ld &g_shared=%p (=%3d)  heap=%p (=%5d)  minflt=%ld\n",
	       who, (long)getpid(), (void *)&g_shared, g_shared, (void *)heap, *heap,
	       (long)ru.ru_minflt);
}

int main(void)
{
	int  *heap = malloc(sizeof *heap);
	int   on_stack = 500;

	*heap = 555;
	dump("พ่อ(ก่อน)", heap);

	fflush(stdout);                 /* สำคัญ! ล้างบัฟเฟอร์ก่อน fork ไม่งั้นข้อความซ้ำสองรอบ */
	pid_t pid = fork();
	...
	if (pid == 0) {
		dump("ลูก(ก่อน)", heap);
		g_shared = -1;
		*heap = -2;
		on_stack = -3;
		dump("ลูก(เขียน)", heap);
		fflush(stdout);         /* _exit ไม่ล้างบัฟเฟอร์ให้ ต้องล้างเองก่อน */
		_exit(0);
	}
	/* ฝั่งพ่อ: waitpid() แล้วอ่านค่าตัวเองซ้ำ */
	dump("พ่อ(หลัง)", heap);
	...
}
```

รันจริงได้:

```

ลูก(ก่อน) pid=392248  &g_shared=0x5555ee2c0090 (=100)  heap=0x55560b1102a0 (=  555)  minflt=13
```

อ่านผล 4 อย่าง:

1. **ที่อยู่เท่ากันเป๊ะ** ทั้ง `&g_shared` (`0x5555ee2c0090`) และ heap (`0x55560b1102a0`) — ไม่ใช่ "บังเอิญใกล้กัน" แต่เป็นเลขเดียวกันจริง ๆ
2. **ข้อมูลแยกกันจริง** ลูกเขียน `-1`, `-2`, `-3` พ่อกลับอ่านได้ `100`, `555`, `500`
3. **`minflt` ของลูกเพิ่มจาก 13 → 22** (minor fault เพิ่ม 9 ครั้ง — เลขนี้ขึ้นกับ buffering ของ stdout: บนเครื่อง/เงื่อนไขอื่นอาจได้ 8–9 ครั้ง แต่ทิศทางเดิมเสมอ) — นี่คือร่องรอยของ **copy-on-write**: ตอน `fork` เคอร์เนลไม่ได้คัดลอกหน่วยความจำทั้งก้อน (จะช้ามาก) มันแค่ **ให้สองโปรเซสชี้ frame ชุดเดียวกันก่อน แล้วปิด "ธงเขียน" ไว้ทั้งคู่** พอฝ่ายไหนเขียน เคอร์เนลถึงคัดลอกเฉพาะ *หน้านั้น* ให้ใหม่ (นั่นแหละที่ทำให้เกิด minor fault)
4. **พ่อมี 74 → 83** ด้วย เพราะต้องรับรู้การตายของลูก (เก็บสถานะ, ปลด resource) ซึ่งมีการแตะหน่วยความจำของตัวเอง

สรุปเป็นประโยคเดียว: **"ที่อยู่" คือชื่อเล่นที่ OS แจก ส่วน "frame" คือของจริงที่ OS จัด** สองโปรเซสใช้ชื่อเล่นซ้ำกันได้ เพราะคนละตารางแปล — และนี่คือเหตุผลทั้งหมดที่ต้องมี MMU

## 4. VA กับ PA ต่างกันแค่ไหน: `03_mmap_demo.c` (จอง 1 GiB แล้วดู RSS)

ทีนี้มาดูความต่างของ "จอง" กับ "ใช้จริง" ด้วยตัวเลขก้อนใหญ่ ๆ ที่เถียงไม่ได้

```c
	const size_t ONE_GI = (size_t)1024 * 1024 * 1024;

	statm("[ก่อนจองอะไร]", page);

	/* ---------- 1) จอง 1 GiB แต่ยังไม่แตะ ---------- */
	void *big = mmap(NULL, ONE_GI, PROT_READ | PROT_WRITE,
			 MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE, -1, 0);
	printf("mmap 1 GiB (MAP_NORESERVE) คืน VA = %p\n", big);
	statm("[จอง 1 GiB แล้ว ยังไม่แตะ]", page);

	((volatile char *)big)[0] = 1;          /* แตะแค่ 1 หน้า */
	statm("[แตะ 1 หน้าแรก]", page);

	for (size_t i = 0; i < 256; i++) {      /* แตะอีก 256 หน้า (หน้าละ 16384 ไบต์) */
		((volatile char *)big)[i * PAGE] = (char)i;
	}
	statm("[แตะอีก 256 หน้า]", page);
```

(ฟังก์ชัน `statm()` อ่าน `/proc/self/statm` เอา 2 ตัวแรก: จำนวนหน้าเสมือน · จำนวนหน้าที่อยู่ใน RAM จริง)

รันจริงได้:

```
[ก่อนจองอะไร] size(VS) =      154 หน้า (   2.4 MiB)   resident(RSS) =       90 หน้า (   1.4 MiB)

mmap 1 GiB (MAP_NORESERVE) คืน VA = 0x7ffe89a90000
[จอง 1 GiB แล้ว ยังไม่แตะ] size(VS) =    65690 หน้า (1026.4 MiB)   resident(RSS) =       90 หน้า (   1.4 MiB)
[แตะ 1 หน้าแรก] size(VS) =    65690 หน้า (1026.4 MiB)   resident(RSS) =       91 หน้า (   1.4 MiB)
[แตะอีก 256 หน้า] size(VS) =    65690 หน้า (1026.4 MiB)   resident(RSS) =      346 หน้า (   5.4 MiB)
munmap 1 GiB แล้ว (คืน VA ให้ระบบ)
```

ตัวเลขนี้คือหัวใจของบทนี้:

- **VS พุ่งจาก 154 หน้า → 65,690 หน้า (1,026 MiB)** เพราะเราขอ 1 GiB (1 GiB ÷ 16384 = 65,536 หน้า + ของเดิม 154)
- **RSS ยังเท่าเดิมที่ 90 หน้า (1.4 MiB)** — ไม่มี frame จริงถูกใช้เลยแม้แต่หน้าเดียว เพราะยังไม่แตะ
- **แตะ 1 หน้า → RSS 91 หน้า** (+1 หน้าเป๊ะ)
- **แตะอีก 256 หน้า → RSS 346 หน้า** (91 + 255 = 346 เพราะรอบแรก i=0 แตะหน้า #0 ที่ถูกนับไปแล้วตอน "แตะ 1 หน้าแรก")

แปลว่าโปรแกรมหนึ่งตัวสามารถ "จอง" ที่อยู่ 1 GiB ได้โดยใช้ RAM จริง 1.4 MiB — ถ้าให้ RAM ตอบทุกอย่างเลย เครื่อง 8 GiB จะรับโปรแกรมแบบนี้ได้ไม่ถึงสิบตัว แต่เพราะมีชั้น VA จึงรับได้เป็นพัน

**ทำไมทำแบบนี้ได้ และใครอนุญาต** — เคอร์เนลมีนโยบายชื่อ overcommit (`/proc/sys/vm/overcommit_memory`):

```
$ cat /proc/sys/vm/overcommit_memory
0
$ grep -E "CommitLimit|Committed_AS|MemTotal|SwapTotal" /proc/meminfo
MemTotal:        8255872 kB
SwapTotal:       6291424 kB
CommitLimit:    10419360 kB
Committed_AS:    9020496 kB
```

โหมด `0` = **heuristic overcommit** (ค่าตั้งต้นของ Linux) ตามเอกสารเคอร์เนล: "Obvious overcommits of address space are refused. Used for a typical system. It ensures a seriously wild allocation fails while allowing overcommit to reduce swap usage." และ `MAP_NORESERVE` จะ **ไม่ถูกตรวจเลย** ในโหมดนี้ — นี่คือเหตุผลที่ `mmap` 1 GiB สำเร็จทั้งที่เครื่องเหลือ RAM ว่างจริงไม่ถึง 1 GiB

บนเครื่องเราตอนนี้ `Committed_AS` (ผลรวมที่ทุกโปรเซสสัญญาไว้ว่าจะใช้) = 9,020,496 kB ≈ 8.6 GiB ซึ่ง **มากกว่า RAM จริง 7.9 GiB** และยังอยู่ต่ำกว่า `CommitLimit` 10,419,360 kB (สวอป + RAM × 50% — สูตรเต็มจาก `man 5 proc_sys_vm`) — ของจริงบนเครื่องนี้กำลัง overcommit อยู่แล้วตลอดเวลา

### 4.1 แชร์ไฟล์ได้ด้วย VA: MAP_SHARED กับ MAP_PRIVATE

ชั้น VA ไม่ได้มีแค่เรื่องประหยัด RAM — มันทำให้ "ไฟล์" กลายเป็น "หน่วยความจำ" ได้ด้วย

```
MAP_SHARED  -> VA = 0x7ffec9c60000   อ่านได้: 'AAAAAAAAAA...'
เขียน sh[0]='S' ผ่าน VA -> อ่านไฟล์ตรง ๆ ได้ 'S' (VA กับไฟล์คือเนื้อเดียวกัน)

MAP_PRIVATE -> VA = 0x7ffec9c60000   อ่านได้: 'SAAAAAAAAA...'
เขียน pr[0]='P' ผ่าน VA -> อ่านไฟล์ตรง ๆ ได้ 'S' (ไฟล์ไม่เปลี่ยน = copy-on-write ทำงาน)
```

- **`MAP_SHARED`** = เขียนผ่าน VA เท่ากับเขียนลงไฟล์จริง ๆ (ใช้ `msync()` บังคับให้ลงดิสก์แล้วอ่านไฟล์กลับมายืนยัน)
- **`MAP_PRIVATE`** = เขียนผ่าน VA แต่ไฟล์ไม่เปลี่ยน (COW อีกครั้ง แต่คราวนี้คู่กรณีเป็น "ไฟล์" กับ "สำเนาใน RAM")
- สังเกตว่า **ทั้งสองครั้งได้ VA เดิม (`0x7ffec9c60000`)** เพราะเราปิด mapping แรกไปแล้ว — เคอร์เนลเลยแจกที่อยู่เดิมกลับมาได้ **ที่อยู่ไม่ใช่ทรัพยากรที่มีค่าในตัวมันเอง** ใช้ซ้ำได้เสมอ ขอแค่ไม่มีใครใช้อยู่

การที่โปรแกรม 100 ตัวรันพร้อมกันแล้วใช้ libc ตัวเดียวกันโดยไม่ต้องโหลดซ้ำ 100 รอบนั้นไม่ใช่เรื่องบังเอิญ — เคอร์เนล map **ไฟล์ libc.so.6 ไฟล์เดียวกัน** เข้าไปใน VA คนละช่วงของแต่ละโปรเซส แต่ frame บน RAM ที่เก็บโค้ด libc เป็นชุดเดียวกัน (จำได้ไหมว่า `/proc/self/maps` ของเราเห็น `libc.so.6` ใน 4 ช่วง (r-xp/---p/r--p/rw-p) บวกอีก 1 ช่วง anonymous ต่อท้ายที่เป็น bss ของ libc = รวม 5 mapping ต่อหนึ่งโปรเซส)

## 5. กลไก paging: ตัดหน่วยความจำเป็นหน้า แล้วแปลด้วยตาราง (ภาพที่ 2)

![เดินตาราง 3 ชั้นบน arm64 16 KiB page: VA 47 บิต แยกเป็น L1 L2 L3 offset และธงใน entry](/assets/diagrams/ep20-02-page-table-walk.svg)

### 5.1 หน้าคือ 2 ยกกำลัง — เลยใช้ bit ทำงานได้ทั้งหมด (`02_page_math.c`)

```c
	const long page = sysconf(_SC_PAGESIZE);
	if (page <= 0 || (page & (page - 1)) != 0) {
		fprintf(stderr, "page size ไม่ใช่ 2 ยกกำลัง — สมมติฐานพัง\n");
		return 1;
	}
	const unsigned shift = (unsigned)__builtin_ctzl((unsigned long)page);
	/* __builtin_ctzl = นับจำนวนบิต 0 ต่อท้าย = log2 ของค่า (16384 -> 14) */

	printf("page size = %ld ไบต์ = 2^%u\n", page, shift);
	printf("=> ตัด offset ได้ด้วย : va & (page-1)\n");
	printf("=> ถอดเลขหน้าได้ด้วย : va >> %u\n\n", shift);
```

รันจริงได้:

```
page size = 16384 ไบต์ = 2^14
=> ตัด offset ได้ด้วย : va & (page-1)
=> ถอดเลขหน้าได้ด้วย : va >> 14
```

การที่ page size เป็น 2 ยกกำลัง (และ OS บังคับให้เป็นอย่างนั้นทุกตัว) ทำให้ "ตัดท่อน" กับ "ต่อท่อน" เป็นคำสั่ง CPU ระดับ bit ไม่ต้องหาร/คูณเลย — สำคัญมาก เพราะการแปลที่อยู่เกิดขึ้น *ทุกครั้งที่แตะหน่วยความจำ* ถ้าต้องหาร ทุกการอ่านตัวแปรจะแพงขึ้นทันที

### 5.2 ที่อยู่ที่ห่างกัน 32 ไบต์ ยังอยู่หน้าเดียวกัน (`02_page_math.c`)

```
a = malloc(16) -> 0x5555953662b0   หน้า #5726688473 offset 8880
b = malloc(16) -> 0x5555953662d0   หน้า #5726688473 offset 8912
ห่างกัน 32 ไบต์ -> อยู่ 'หน้าเดียวกัน' (frame เดียวกัน)
```

`malloc(16)` สองครั้งได้ที่อยู่ห่างกัน 32 ไบต์ (หัวก้อน ~8 ไบต์ + พื้นที่ใช้ได้ 24 ไบต์ = ก้อนจริง 32 ไบต์ ตามที่วัดในตอนที่ 16) แต่ทั้งคู่อยู่ **หน้าเดียวกัน** และ **frame เดียวกัน** — ถ้าเราอ่าน `a[0]` กับ `b[0]` สองตัว MMU แปลที่อยู่คนละค่า (คนละ offset) แต่ผลลัพธ์ชี้ไป frame เดียวกัน ประหยัดการเดินตารางไปครึ่งหนึ่ง

### 5.3 ตารางมี 3 ชั้น แล้วแต่ละชั้นเดินยังไง

บนเครื่องนี้ (`CONFIG_PGTABLE_LEVELS=3`, `VA_BITS=47`, granule 16 KiB) VA 47 บิตถูกหั่นเป็น 4 ท่อน:

| ท่อน | บิต | จำนวนช่อง | ใช้ทำอะไร |
|---|---|---|---|
| index L1 | 46:36 | 2048 | ชี้ไปตาราง L2 (1 ช่องครอบคลุม 64 GiB) |
| index L2 | 35:25 | 2048 | ชี้ไปตาราง L3 หรือ map เป็น **block 32 MiB** (แปลทีละ 32 MiB ข้ามตาราง L3) |
| index L3 | 24:14 | 2048 | 1 ช่อง = 1 หน้า = 16384 ไบต์ |
| offset | 13:0 | 16384 | ตำแหน่งในหน้า (ส่งผ่านตรง ๆ) |

(ท่อนละ 11 บิต เพราะ 2^11 = 2048 ช่อง × 8 ไบต์ = 16384 ไบต์ = **หนึ่งหน้าเต็มพอดี** — โครงสร้างนี้จัดมาให้ลงตัวกับ granule)

หน้าที่ของแต่ละชั้น:

1. รีจิสเตอร์ **TTBR0_EL1** เก็บ "ฐานตาราง L1" ของโปรเซสที่กำลังรันอยู่ (ฝั่ง kernel ใช้ TTBR1_EL1 สำหรับ `0xffff...` — เอกสารเคอร์เนลระบุว่า **"TTBRx selection is given by bit 55 of the virtual address"**)
2. เอา 11 บิตแรกของ VA ไปเป็นดัชนีในตาราง L1 → ได้ที่อยู่ของตาราง L2
3. เอา 11 บิตถัดไปเป็นดัชนีในตาราง L2 → ได้ที่อยู่ของตาราง L3 (หรือเจอ block 32 MiB = แปลทีละ 32 MiB ในครั้งเดียว ก็จบเลย ไม่ต้องเดินต่อ)
4. เอา 11 บิตถัดไปเป็นดัชนีในตาราง L3 → ได้ **PFN** (เลข frame จริง)
5. เอา offset 14 บิตต่อท้าย → ได้ที่อยู่จริงบน RAM

จุดที่คนมักไม่รู้: **ตารางแต่ละชั้นก็กินหน่วยความจำจริง** (2048 × 8 = 16384 ไบต์ = 1 หน้า ต่อ 1 ตาราง) และมันถูกจัดสรรแบบขี้เกียจเช่นกัน — ตาราง L2/L3 จะเกิดเมื่อมีอะไรถูก map ในย่านนั้นจริง ๆ ถ้าโปรแกรมจอง VA 1 GiB แล้วแตะแค่ 1 หน้า ระบบจะสร้างตารางแค่เส้นทางที่จำเป็นต้องใช้เท่านั้น ไม่สร้างครบทั้ง 1 GiB

### 5.4 ธงใน entry: ไม่ได้มีแค่เลข frame

PTE หนึ่งช่อง (64 บิต) เก็บทั้งเลข frame และ "กติกา" ของหน้านั้น:

| ธง | ความหมาย | ถ้าผิดกติกาเกิดอะไร |
|---|---|---|
| **present** | มี frame จริงรองรับแล้วหรือยัง | `0` → **page fault** (หัวข้อ 6) |
| **read-write** | เขียนได้ หรืออ่านอย่างเดียว | เขียนใส่หน้าอ่านอย่างเดียว → SIGSEGV |
| **user / supervisor** | โปรแกรมผู้ใช้เข้าถึงได้ไหม | `0` = เฉพาะ kernel → SIGSEGV (กำแพงจากตอนที่ 19) |
| **dirty** | เคยถูกเขียนหรือยัง | ใช้ตัดสินว่าต้องเขียนกลับดิสก์ไหม |
| **accessed** | เพิ่งถูกใช้ล่าสุดเมื่อไร | ใช้เลือกว่าจะเก็บหน้าออกจาก RAM ตัวไหน |

แล้วเราดูธงพวกนี้จากผู้ใช้ทั่วไปได้ไหม? ได้บางส่วน — `/proc/self/pagemap`:

```
  หน้าแรกก่อนเขียน : present=0 pfn=0
หลังเขียนแค่ p[0]:
  หน้า#0 (เขียนแล้ว)   : present=1 pfn=0
  หน้า#1 (ยังไม่แตะ)   : present=0 pfn=0
  หน้า#2 (ยังไม่แตะ)   : present=0 pfn=0
  => present=0 คือ 'ที่อยู่มีจริง แต่ยังไม่มี frame จริงรองรับ' (lazy)
  => pfn=0 หมด เพราะไม่มีสิทธิ์ CAP_SYS_ADMIN (ปิดตั้งแต่ Linux 4.0)

ลองเขียน p[page] (= หน้า#1 ตัวแรก) แล้วอ่าน pagemap ซ้ำ:
  หน้า#1 : present=1   (เดิม 0 → ตอนนี้ 1 = fault แล้วได้ frame)
```

**`pfn` เป็น 0 หมดไม่ใช่ความผิดพลาด** — เอกสารเคอร์เนล (`Documentation/admin-guide/mm/pagemap.rst`) ระบุตรง ๆ ว่า:

> "Since Linux 4.0 only users with the CAP_SYS_ADMIN capability can get PFNs. In 4.0 and 4.1 opens by unprivileged fail with -EPERM. Starting from 4.2 the PFN field is zeroed if the user does not have CAP_SYS_ADMIN. Reason: information about PFNs helps in exploiting Rowhammer vulnerability."

คือ **ปิดเพราะความปลอดภัย** — ถ้ารู้เลข frame จริงก็สามารถออกแบบการโจมตี Rowhammer (แถว RAM ที่เขียนถี่ ๆ แล้ว bit ข้าง ๆ เพี้ยน) ได้ ที่เหลือที่ยังเห็นได้คือ `present` ซึ่งพอแล้วสำหรับการเรียนเรื่อง lazy allocation: **หน้าที่ไม่ถูกแตะ = ไม่มี frame จริง**

## 6. page fault: เหตุการณ์ที่เกิดถี่จนเราไม่รู้ตัว (ภาพที่ 3)

![ลำดับการเกิด page fault 6 ขั้น พร้อมตัวเลขวัดจริงจาก lazy allocation และ mprotect](/assets/diagrams/ep20-03-page-fault.svg)

### 6.1 เกิดอะไรขึ้นตอน "แตะหน้าที่ไม่มี frame"

1. CPU ต้องอ่าน/เขียน VA หนึ่งค่า → ส่งให้ MMU
2. MMU ถาม **TLB** ก่อน (แคชผลแปล) — ถ้าเจอ จบในไม่กี่นาโนวินาที
3. ถ้าไม่เจอ ต้องเดินตาราง 3 ชั้น → เจอ PTE แต่ **`present` = 0**
4. MMU แจ้ง CPU ว่า fault → CPU **หยุดคำสั่งนี้ไว้** แล้วกระโดดเข้าเคอร์เนล (EL0 → EL1 ผ่านกลไกเดียวกับ syscall ในตอนที่ 19)
5. เคอร์เนลจัดการ: หา frame ว่าง · ถ้าเป็นไฟล์ก็อ่านจากดิสก์ · ถ้าเป็น anonymous ก็ให้หน้าที่ว่างเปล่า (ศูนย์ทั้งหน้า)
6. เคอร์เนลเขียน PTE (ตั้ง `present` + สิทธิ์) แล้ว **กลับไปทำคำสั่งเดิมซ้ำ** — รอบนี้สำเร็จ

จากมุมของโปรแกรม **ไม่มีอะไรเกิดขึ้นเลย** มันไม่รู้ด้วยซ้ำว่าเมื่อกี้ "หยุด" ไปหนึ่งรอบ นี่คือเหตุผลที่เราบอกว่า page fault "ปกติ" — โปรแกรมที่จอง 64 MiB แล้วเขียนทั้งก้อน จะเกิด fault พัน ๆ ครั้งแล้วก็จบแบบไม่มีอาการอะไร

### 6.2 ราคาจริง: วัด fault ตอนจอง 64 MiB (`05_fault_lazy.c`)

โค้ดจริงใน `05_fault_lazy.c` — ตัวจอง/ลูปเขียนทุกหน้าเหมือนกับหัวข้อ 4 (ตัดมาเฉพาะแกน ไฟล์เต็มอยู่ `course/code/ep20/05_fault_lazy.c`):

```c
	volatile char *buf = calloc(1, bytes);          /* A) จอง 64 MiB + ตั้ง 0 ก่อน */
	for (size_t i = 0; i < bytes; i += (size_t)page) { buf[i] = 1; }  /* แตะทุกหน้า -> fault 4096 ครั้ง */
	...
	/* B) mmap ปกติ / C) mmap MAP_POPULATE ใช้ลูปเขียนเดียวกัน ต่างกันแค่ตอนขอ */
```

รันจริง (fault นับจาก `getrusage(RUSAGE_SELF)` → `ru_minflt + ru_majflt`):

```
A) calloc + เขียนทุกหน้า
   calloc :      0.0 ms  → fault เพิ่ม      3 ครั้ง (RSS 93 หน้า)
   เขียน  :     14.2 ms  → fault เพิ่ม   4095 ครั้ง
   รวม    :     14.2 ms · fault รวม 4098 ครั้ง

B) mmap ปกติ + เขียนทุกหน้า
   mmap   :    0.011 ms → fault เพิ่ม      0 ครั้ง
   เขียน  :     13.4 ms  → fault เพิ่ม   4096 ครั้ง  (เกือบ 1 fault ต่อ 1 หน้า)
   รวม    :     13.4 ms · fault รวม 4096 ครั้ง

C) mmap MAP_POPULATE + เขียนทุกหน้า
   mmap   :     14.5 ms  → fault เพิ่ม   4096 ครั้ง  (จ่ายล่วงหน้าตรงนี้)
   เขียน  :    0.187 ms → fault เพิ่ม      0 ครั้ง  (แทบไม่มี fault แล้ว)
   รวม    :     14.6 ms · fault รวม 4096 ครั้ง
```

อ่านผล:

- **64 MiB = 4096 หน้า และเราเห็น fault 4,095–4,096 ครั้ง** — ตรงกันเกือบเป๊ะ (1 fault ต่อ 1 หน้า) นี่คือหลักฐานว่า "ที่อยู่ถูกจองเป็นหน้า ๆ" จริง ไม่ใช่ทั้งก้อน
- **`mmap` ใช้เวลา 0.011 ms** (แทบไม่มีอะไรเกิดขึ้น) แต่การเขียนครั้งแรกใช้ 13.4 ms — เกือบทั้งหมดคือราคาของ fault 4096 ครั้ง
- **`MAP_POPULATE` ย้ายการจ่ายเงินไปข้างหน้า** (`mmap` กลายเป็น 14.5 ms) แล้วการเขียนกลายเป็น 0.187 ms

แล้วแบบไหนดีกว่ากัน? **ไม่ตายตัว** — ถ้างานคุณแตะไม่ครบทุกหน้า (เช่น array 100 MB ที่จริง ๆ ใช้ไม่ถึงครึ่ง) แบบ lazy จะประหยัดทั้งเวลาและ RAM แต่ถ้าเป็นงานที่รู้แน่ว่าจะใช้ทั้งก้อน (เช่นอ่านไฟล์ทั้งไฟล์เข้าหน่วยความจำ) การจ่ายทีเดียวอาจให้ความแน่นอนเรื่องเวลา (ไม่มีสะดุดกลางงาน) มากกว่า

### 6.3 fault ที่ "ไม่ปกติ" — เมื่อเคอร์เนลปฏิเสธ (และนี่คือกำแพง hardware ของตอนที่ 19)

fault 2 ชนิดนี้หน้าตาเหมือนกันเป๊ะจากมุม MMU แต่จบต่างกันคนละโลก:

- **หน้าที่ไม่มี frame** → เคอร์เนลหา frame ให้ → โปรแกรมไปต่อ (ไม่มีใครรู้)
- **หน้าที่มี frame แต่สิทธิ์ไม่ให้** → เคอร์เนลตัดสินว่าโปรแกรมทำผิดกติกา → ส่งสัญญาณให้ตาย (SIGSEGV)

พิสูจน์ด้วย `06_mprotect_wall.c` — เราเป็นเจ้าของหน่วยความจำก้อนนั้นเอง (จองเองด้วย `mmap`) และตัวชี้ก็ยังดีอยู่ แต่พอ `mprotect(PROT_NONE)` แล้วแตะ:

```c
	printf("ช่วง VA: หน้า#0 = %p (offset 0) · หน้า#1 = %p (offset %ld)\n\n",
	       (void *)p, (void *)(p + page), page);
	try_access("อ่านหน้า#0 (r--)", (volatile char *)&p[0], 0);
	...
	if (mprotect(p, LEN, PROT_NONE) != 0) { perror("mprotect PROT_NONE"); return 1; }
	try_access("อ่านหน้า#0 หลังปิด", (volatile char *)&p[0], 0);
	try_access("เขียนหน้า#1 หลังปิด", (volatile char *)&p[page], 1);
```

รันจริงได้:

```
page size = 16384 ไบต์ · จอง 2 หน้าไว้ที่ 0x7ffed7414000

ช่วง VA: หน้า#0 = 0x7ffed7414000 (offset 0) · หน้า#1 = 0x7ffed7418000 (offset 16384)

อ่านหน้า#0 (r--) : อ่าน/เขียนผ่านได้ (ไม่มี fault)
อ่านหน้า#1 (r--) : อ่าน/เขียนผ่านได้ (ไม่มี fault)

mprotect(2 หน้า, PROT_NONE)  → ที่อยู่ยังเป็น 0x7ffed7414000 เหมือนเดิมทุกไบต์
อ่านหน้า#0 หลังปิด : โดน SIGSEGV · si_addr=0x7ffed7414000 (= ที่อยู่ที่พยายามแตะจริง)
เขียนหน้า#1 หลังปิด : โดน SIGSEGV · si_addr=0x7ffed7418000 (= ที่อยู่ที่พยายามแตะจริง)

mprotect(แค่หน้า#0, PROT_READ) → สิทธิ์ตั้งได้ "ทีละหน้า"
อ่านหน้า#0 (r--) : อ่าน/เขียนผ่านได้ (ไม่มี fault)
เขียนหน้า#0 (จะโดน) : โดน SIGSEGV · si_addr=0x7ffed7414000 (= ที่อยู่ที่พยายามแตะจริง)
อ่านหน้า#1 (ยังปิด) : โดน SIGSEGV · si_addr=0x7ffed7418000 (= ที่อยู่ที่พยายามแตะจริง)

เปิดหน้า#1 คืน (rw-) → ค่าที่เคยเขียนไว้ยังอยู่ไหม? p[16384] = 'b'
```

สามอย่างที่พิสูจน์ได้จาก output นี้:

1. **`si_addr` ตรงกับ VA ที่เราพยายามแตะเป๊ะ** — ไม่ใช่ที่อยู่ของข้อมูล ไม่ใช่อะไรอื่น แต่เป็น "ที่อยู่ที่ถูกปฏิเสธ" ตัวจริง
2. **สิทธิ์ตั้งได้ทีละหน้า** — หน้า#0 เปิดอ่าน หน้า#1 ยังปิด อยู่ใน mapping ก้อนเดียวกัน
3. **การปิดสิทธิ์ไม่ย้ายข้อมูล** — พอเปิดคืน `p[16384]` ยังเป็น `'b'` เหมือนเดิม เพราะ `mprotect` แก้แค่ "ธงใน PTE" ไม่ได้แตะเนื้อข้อมูล

ข้อ 1 กับ 3 คือหลักฐานว่า **การป้องกันหน่วยความจำมาจาก hardware ไม่ใช่จากมารยาทของโปรแกรม** — ต่อให้โปรแกรมของเราตั้งใจจะอ่านเอง (เราเรียกผ่านตัวชี้ของเราเอง) MMU ก็ยังปฏิเสธกลางทาง และส่ง SIGSEGV ที่มีที่อยู่ชัดเจน นี่คือกลไกเดียวกันกับที่ทำให้โปรแกรมหนึ่งอ่านหน่วยความจำของอีกโปรแกรมหนึ่งไม่ได้เลย

## 7. TLB: ถ้าต้องเดินตารางทุกครั้ง ชีวิตจะช้าแค่ไหน (ภาพที่ 4)

![กราฟวัดจริง: ns ต่อการแตะตามขนาดพื้นที่ และผลของจำนวนการแตะต่อหน้า](/assets/diagrams/ep20-04-tlb-reach.svg)

จนถึงตอนนี้เราพูดว่า "MMU เดินตาราง 3 ชั้น" เหมือนเป็นเรื่องเบา ๆ แต่คิดดูดี ๆ: **ทุกครั้งที่โปรแกรมอ่านค่าตัวแปรในลูป** ถ้าต้องเดินตาราง 3 ชั้นก็หมายถึงอ่านหน่วยความจำเพิ่มอย่างน้อย 3 ครั้งต่อการอ่าน 1 ครั้ง — ช้าลงหลายเท่าและสิ้นเปลือง bandwidth มหาศาล ฮาร์ดแวร์จึงมี **TLB** (แคชเล็ก ๆ ใน MMU ที่จำ "ผลแปลล่าสุด") ถ้า VA ที่แตะอยู่ใน TLB แล้ว ก็ได้ PFN ออกมาทันที

คำถามคือ TLB จุได้เท่าไร และเกินแล้วราคาเป็นยังไง — เราวัดเองด้วย `07_tlb_stride.c` โดยเดินหน่วยความจำแบบ **pointer chase** (กระโดดตามตัวชี้ ทำให้ CPU เดา/ทำล่วงหน้าไม่ได้) แล้วจับเวลา

### 7.1 พื้นที่ยิ่งใหญ่ ราคาต่อการแตะยิ่งแพง

```
การทดลอง 1: เดินแบบสุ่ม (ทุกการแตะ = 1 ครั้ง) บนพื้นที่ขนาดต่าง ๆ
พื้นที่(KiB) จำนวนหน้า  ns/การแตะ  เปลี่ยนแปลง
64           4          2.6          +0.0%
256          16         4.6          +76.1%
1024         64         11.2         +145.1%
4096         256        61.9         +453.6%
16384        1024       96.1         +55.4%
65536        4096       111.2        +15.6%
```

จาก 2.6 ns (64 KiB — ทั้งข้อมูลและค่าแปลอยู่ในแคช) ไป 111.2 ns (64 MiB) = **ช้ากว่า ~43 เท่า** ทำงานบนข้อมูลชุดเดียวกัน จำนวนการแตะเท่ากัน ต่างแค่ "พื้นที่ที่เดิน"

### 7.2 พื้นที่เท่ากัน แต่ "กี่ครั้งต่อหน้า" ต่างกัน

(ก่อนตารางนี้มี **การทดลอง 2** — พื้นที่ 64 MiB เท่ากัน เปลี่ยนแค่ stride: stride 64 B = 4.64 ns · stride 16 KiB = 11.87 ns · stride 256 KiB = 47.46 ns · stride 1 MiB = 11.62 ns — สรุปไว้ในภาพที่ 4)

```
การทดลอง 3: พื้นที่ 16 MiB เท่ากันทุกแถว · จำนวนบรรทัดแคชที่แตะเท่ากัน
             แต่จำนวนครั้งที่ "ต้องแปลหน้าใหม่" ต่างกัน
stride     การแตะ/หน้า    ns/การแตะ    แปลหน้าใหม่/การแตะ
1024       16             11.21         0.062
4096       4              13.44         0.250
16384      1              11.93         1.000
```

ผลที่ได้ไม่เป็นไปตามที่เดาง่าย ๆ ว่า "แตะหน้าเดิมซ้ำ = ถูกกว่า" เป๊ะ:
- **stride 1024** (16 ครั้ง/หน้า) = 11.21 ns — เร็วสุด เพราะค่าแปลถูกใช้ซ้ำ 16 ครั้ง
- **stride 16384** (1 ครั้ง/หน้า = ข้ามหน้าทุกครั้ง) = 11.93 ns — แทบไม่ต่างจาก stride 1024 ทั้งที่ต้องแปลหน้าใหม่ทุกครั้ง
- **stride 4096** (4 ครั้ง/หน้า) = 13.44 ns — กลับช้าสุด

ถ้า "การแปลหน้าใหม่" เป็นราคาหลักจริง stride 16384 น่าจะช้าสุด แต่ตัวเลขไม่เป็นแบบนั้น — แปลว่า **ผลของ TLB ปนกับผลของแคชข้อมูลจนแยก "ราคาแปลหน้า" ออกมาเป็นตัวเลขเดียวไม่ได้** (หัวข้อ 7.3 อธิบายต่อ) สิ่งที่สรุปได้แน่นอนมีแค่ทิศทาง: แตะหน้าเดิมซ้ำ ๆ และเดินในพื้นที่เล็ก = ถูกกว่า

แล้วทำไม stride 1 MiB (ดูการทดลอง 2 ในภาพที่ 4) ถึงเร็ว (11.62 ns) ทั้งที่กระโดดไกล? เพราะมันแตะแค่ **64 ตำแหน่ง** บนพื้นที่ 64 MiB — ทั้งหมดยังอยู่ในแคช L1 ไม่ต้องออกไป DRAM บทเรียนจากแถวนี้คือ **TLB ไม่ได้ช่วยคนเดียว แคชข้อมูลก็ช่วย** และ "พื้นที่ที่เดิน" ต้องมองทั้งสองอย่าง

### 7.3 ตัวเลขนี้ต้องอ่านอย่างระวัง

ผมต้องพูดตรง ๆ ตรงนี้ เพื่อไม่ให้เข้าใจผิดเกินหลักฐาน:

- ตัวเลขนี้ **ผสมทั้งผลของ TLB และแคชข้อมูล** (L1D 64 KiB/คอร์ · L2 512 KiB/คอร์ รวม 2 MiB · L3 2 MiB แชร์ 4 คอร์ บน Cortex-A76 ตัวนี้) การแยกสองอย่างออกจากกันต้องใช้ตัวนับ PMU (Performance Monitoring Unit = ตัวนับฮาร์ดแวร์ใน CPU เช่น `perf stat -e dTLB-load-misses`) ซึ่ง **เครื่องนี้ไม่มี `perf` ติดตั้ง** (และ `perf_event_paranoid` = 2 ก็ต้องใช้สิทธิ์เพิ่ม) เราจึงบอกได้แค่ "ราคารวม" ไม่ใช่ "ราคาเฉพาะ TLB"
- **จำนวน entry ของ TLB เราไม่อ้าง** — รายละเอียดนี้อยู่ใน Cortex-A76 Technical Reference Manual (บท A5 "Memory Management Unit / TLB organization") ถ้าต้องการตัวเลขจริงให้ไปเปิดเอกสารนั้น ไม่ควรเชื่อตัวเลขจากความจำ (หรือจากบทความที่ไม่มีแหล่งอ้างอิง)
- ตัวเลขเวลา **ไม่มีทางเท่ากันเป๊ะทุกครั้งที่รัน** เพราะมีงานอื่นวิ่งบน 4 คอร์เดียวกัน เราจึงใช้ "เวลาที่ดีที่สุดจาก 3 รอบ" เป็นตัวแทน
- ที่ยังเชื่อได้แน่ ๆ คือ **ทิศทาง**: ทำงานในพื้นที่เล็กและแตะหน้าเดิมซ้ำ = ถูกกว่าเสมอ นี่คือเหตุผลที่การจัด layout ข้อมูลให้เดินแบบต่อเนื่อง (sequential access) ยังชนะเสมอในการเพิ่มความเร็ว

## 8. เทียบกับ Go: runtime เป็นคนเรียก mmap ให้ (`08_go_memory.go`)

Go ไม่ได้ให้คุณเรียก `mmap` เอง (จริง ๆ เรียกได้ผ่าน `syscall.Mmap` แต่ไม่ใช่ทางหลัก) เพราะ runtime (โค้ดที่แถมมากับภาษา Go ทำหน้าที่จัดการเบื้องหลังให้เรา ไม่ใช่โค้ดที่เราเขียนเอง) จัดการหน่วยความจำทั้งหมดให้ แล้วให้ **GC** (garbage collector = ตัวเก็บขยะหน่วยความจำ) มาดูแลต่อในตอนที่ 31

โค้ดจริงใน `08_go_memory.go` (ตัดมาเฉพาะแกน ไฟล์เต็มอยู่ `course/code/ep20/08_go_memory.go`):

```go
	fmt.Printf("&global     = %p   (ข้อมูลระดับแพ็กเกจ)\n", &global)
	fmt.Printf("heap1       = %p   (new(int))\n", heap1)
	fmt.Printf("&slice[0]   = %p   (make([]byte, 8 MiB))\n", &slice[0])
	...
	runtime.ReadMemStats(&ms)
	fmt.Printf("  HeapAlloc (ใช้จริงที่ GC เห็น) = %6.2f MiB\n", float64(ms.HeapAlloc)/1048576.0)
	fmt.Printf("  HeapSys   (ที่อยู่ที่จองไว้)  = %6.2f MiB\n", float64(ms.HeapSys)/1048576.0)
```

รันจริงได้ (Go 1.24.4):

```
== 08_go_memory — Go มองหน่วยความจำยังไง ==
go version          : go1.24.4
page size (getpagesize) : 16384 ไบต์
GOMAXPROCS / NumCPU     : 4 / 4

&global     = 0x1c0a48   (ข้อมูลระดับแพ็กเกจ)
heap1       = 0x400000e110   (new(int))
&slice[0]   = 0x4000180000   (make([]byte, 8 MiB))

/proc/self/statm : VS = 76625 หน้า (1197.3 MiB) · RSS = 176 หน้า (2.8 MiB)

runtime.MemStats หลังจองข้อมูล:
  HeapAlloc (ใช้จริงที่ GC เห็น) =   8.08 MiB
  HeapSys   (ที่อยู่ที่จองไว้)  =  11.69 MiB
  Sys       (ทุกอย่างที่ runtime จองจาก OS) =  14.46 MiB
  StackInuse =   0.28 MiB · NumGC = 1

syscall.Mmap 1 MiB ได้ที่อยู่ = 0x7ffe9ee48000
  (vs C: mmap ของ C ก็ได้ที่อยู่แบบเดียวกัน — ตัวเลขช่วงเดียวกัน)

หลัง runtime.GC() 1 รอบ:
  HeapAlloc =   0.08 MiB · HeapSys =  11.69 MiB · NumGC = 2
  VS = 1198.3 MiB · RSS = 3.1 MiB  (ผลต่างนี้คือ "ที่อยู่ที่จองแต่ยังไม่ใช้")
```

สี่ข้อที่เห็นจากตัวเลขนี้:

1. **Go จองที่อยู่ล่วงหน้าเป็นเขตใหญ่** — heap ของ Go อยู่ที่ `0x4000...` (ที่อยู่ที่ runtime ขอจากเคอร์เนลมาเป็นผืน) ต่างจาก C ที่ `malloc` ค่อย ๆ ขอจาก `[heap]` ใกล้ ๆ ตัวโปรแกรม (`0x5555...`)
2. **VS 1,197.3 MiB แต่ RSS แค่ 2.8 MiB** — ตัวเลขนี้ยืนยันเรื่องเดิมจากอีกภาษา: **ที่อยู่ที่จอง ≠ RAM ที่กิน** (Go จองที่อยู่ไว้เพื่อจัดวาง heap ให้ต่อเนื่องได้ในอนาคต ไม่ได้แปลว่ากิน RAM 1 GiB)
3. **`HeapAlloc` 8.08 MiB กับ `HeapSys` 11.69 MiB** ห่างกัน = runtime จองมากกว่าที่ใช้จริง (มีที่ว่างรอไว้) พอเรียก `runtime.GC()` แล้ว `HeapAlloc` เหลือ 0.08 MiB แต่ `HeapSys` **ยังเท่าเดิม 11.69 MiB** — Go ไม่คืนที่อยู่ให้ OS ทันที (เก็บไว้ใช้ซ้ำ เพราะการขอคืน/ขอใหม่แพง)
4. **`syscall.Mmap` ของ Go ได้ที่อยู่ช่วง `0x7ffe...`** อยู่ในช่วงเดียวกันกับ `mmap` ของ C (ขึ้นต้น `0x7ffe...` เหมือนกัน แต่ไม่ใช่เลขเดียวกัน) — ไม่ใช่เพราะเขียนโค้ดเหมือนกัน แต่เพราะ **ทั้งสองภาษาเรียก syscall ตัวเดียวกัน** เข้า kernel ตัวเดียวกัน ผ่าน MMU ตัวเดียวกัน

และที่สำคัญสำหรับตอนที่ 31 (GC): `syscall.Mmap` ที่เราขอเองนั้น **GC ไม่รู้จักและไม่ดูแล** — ถ้าเราลืม `Munmap` หน่วยความจำก้อนนั้นจะไม่ถูกเก็บกวาดให้เลย (ต่างจาก slice ที่ GC ตามเก็บให้) เป็นกับดักก้อนใหญ่ของคนที่ยืม `syscall.Mmap` มาใช้ใน Go

## 9. กับดักที่เจอจริงตอนทำบทนี้

บันทึกไว้เพราะเป็นของจริงที่เจอระหว่างเขียนโค้ด 7 ไฟล์ .c (บวก Go อีก 1) นี้ (ไม่ใช่ทฤษฎี):

1. **`-Wpedantic` ไม่ยอมให้แปลง function pointer เป็น `void *`** — `(const void *)&main` โดน warning `-Wpedantic` (จะเป็น error ก็ต่อเมื่อใส่ `-Werror`) ตอนคอมไพล์ ทางออกที่ถูกคือส่งเป็น `uintptr_t` ตรง ๆ (`show("main()", (uintptr_t)&main, page)`)
2. **`_exit()` ไม่ล้างบัฟเฟอร์ `stdout`** — ตอนแรกฝั่งลูกของ `04_fork_illusion` พิมพ์ข้อความออกมา **หายไปทั้งหมด** เพราะ stdout ถูกต่อท่อ (pipe = ส่งข้อมูลต่อให้โปรแกรมอื่น) แล้ว `_exit` ไม่ล้างบัฟเฟอร์ให้ ต้อง `fflush(stdout)` เองก่อน (ถ้ารันตรง ๆ บน terminal จะไม่เจออาการนี้เลย — เพราะ terminal เป็น line-buffered = พิมพ์ออกทันทีเมื่อจบบรรทัด)
3. **อ่าน `/proc/self/pagemap` ต้องใช้ page size ในการหา index** — ครั้งแรกผมลองใช้ `addr / 4096` แล้วได้ `present = 0` ทั้งที่ข้อมูลอยู่จริง! เพราะเครื่องนี้ page size = 16384 → index ต้องเป็น `addr / 16384` ผิดไป 4 เท่า
4. **`MAP_PRIVATE` กับ `MAP_SHARED` ได้ VA เดิม** (`0x7ffec9c60000`) เมื่อตัวแรกถูก `munmap` ไปก่อน — เตือนใจว่า VA ไม่ใช่ทรัพยากรหายาก
5. **ตัวเลขเวลาไม่เคยเท่ากันเป๊ะ** การวัด TLB 3 รอบ ได้ 2.6/2.7 สลับกันตลอด — จึงใช้ "ดีที่สุดจาก 3 รอบ" และระบุเงื่อนไขเสมอ
6. **ตัวเลขที่อยู่เปลี่ยนทุกครั้ง** เพราะ ASLR + heap layout ที่ไม่คงที่ → ในบทความนี้ทุกเลขที่อยู่เป็น "ตัวอย่างจากการรันหนึ่งครั้ง" ไม่ใช่ค่าคงที่

## 10. สรุปสิ่งที่ได้เรียนรู้

1. **ที่อยู่ที่โปรแกรมเห็น (VA) ไม่ใช่ตำแหน่งบน RAM** — มันคือ "ชื่อเล่น" ที่ OS แจกให้ในตารางแปลของโปรเซสนั้น โปรเซสละตาราง จึงใช้ชื่อซ้ำกันได้ (`&g_shared` ของพ่อกับลูกเท่ากันเป๊ะ)
2. **ทุกอย่างถูกจัดเป็นหน้า ๆ** เครื่องนี้ page = **16384 ไบต์** (ไม่ใช่ 4096 — เช็คด้วย `getconf PAGESIZE`) และเพราะเป็น 2^14 การตัด/ต่อที่อยู่จึงเป็นคำสั่ง bit ล้วน (`va >> 14`, `va & (page-1)`)
3. **VA 47 บิต → เดินตาราง 3 ชั้น** (`PGTABLE_LEVELS=3`) ท่อนละ 11 บิต (2048 entry) + offset 14 บิต · L2 map ได้เป็น block 32 MiB · TTBR0_EL1 เก็บฐานตารางของโปรเซสปัจจุบัน (bit 55 ของ VA เป็นตัวเลือกฝั่ง user/kernel)
4. **PTE เก็บทั้ง PFN และธงสิทธิ์** — `present` 0 → fault · `read-write` ผิด → SIGSEGV · และ `mprotect` แก้แค่ธง ไม่แตะเนื้อข้อมูล (เปิดคืนแล้วค่าที่เคยเขียนยังอยู่: `p[16384] = 'b'`)
5. **"จอง" ≠ "ใช้"** จอง VA 1 GiB แล้ว RSS ยัง 1.4 MiB เท่าเดิม (แตะ 257 หน้า → 5.4 MiB) · Go จอง 1,197.3 MiB ได้ RSS 2.8 MiB · เครื่องนี้ `Committed_AS` 8.6 GiB มากกว่า RAM 7.9 GiB จริง (โหมด `overcommit_memory = 0`)
6. **page fault ปกติและเกิดถี่มาก** จอง 64 MiB เขียนทั้งก้อน = fault 4,096 ครั้ง (1 ครั้งต่อ 1 หน้า) · lazy 13.4 ms · `MAP_POPULATE` 14.5 ms แต่ย้ายการจ่ายไปตอนขอ
7. **fork = copy-on-write** แชร์ frame ก่อน พอลูกเขียนครั้งแรกค่อยแยกให้ (minflt เพิ่ม ~8–9 ครั้ง ขึ้นกับ buffering) — นี่คือคำตอบที่ค้างจากตอนที่ 18
8. **TLB เป็นแคชของการแปล** แตะหน้าเดิมซ้ำ (stride 1024, 16 ครั้ง/หน้า) = 11.2 ns แต่ผลมันผสม TLB กับแคชข้อมูลจนแยกราคาแปลออกมาเป็นตัวเลขเดียวไม่ได้ (stride 4096 กลับช้าสุด 13.4 ns) · สิ่งที่ชัดคือพื้นที่ยิ่งใหญ่ยิ่งแพง (2.6 → 111 ns = ~43 เท่า)

## 11. โจทย์ฝึกมือ (2 ระดับ)

### ระดับ Drill (ซ้อมทวนความเข้าใจ)

1. **ยืนยัน page size ของเครื่องคุณ แล้วอธิบายว่ามันไม่ใช่ 4096** — รัน `getconf PAGESIZE` และ `grep -E "ARM64_16K_PAGES|PGTABLE_LEVELS|ARM64_VA_BITS=" /boot/config-$(uname -r)` (บนเครื่องอื่น path ของ config อาจเป็น `/boot/config-...` หรือ `/proc/config.gz`) แล้วตอบ: เครื่องคุณใช้ page กี่ไบต์ · มีตารางกี่ชั้น · VA กี่บิต · แล้ว RAM ทั้งหมดของคุณมีกี่ frame (คำนวณจาก `MemTotal` ใน `/proc/meminfo`)
2. **แก้ `02_page_math.c` ให้จอง 5 หน้า แล้วแตะเฉพาะหน้า #3** — เขียน `p[page*3] = 'Z';` แล้วอ่าน pagemap ของทั้ง 5 หน้า พิมพ์ `present` ของแต่ละหน้า แล้วอธิบายว่าทำไมได้ค่าอย่างนั้น (เปรียบเทียบกับผลในบทนี้ที่แตะแค่หน้า#0) — โบนัส: ทำไม `pfn` ถึงเป็น 0 ทุกหน้า
3. **วัด TLB ด้วย stride ที่ไม่เท่าใคร** — แก้ `07_tlb_stride.c` ในส่วนการทดลอง 2 ให้ใช้ stride = 8192 (ครึ่งหน้า → 2 ครั้งต่อหน้า) แล้วเทียบกับ stride = 16384 (1 ครั้งต่อหน้า) และ 4096 (4 ครั้งต่อหน้า) — ตั้งสมมติฐานก่อนรัน แล้วดูว่าตรงไหม พร้อมอธิบายว่าทำไม stride ครึ่งหน้าถึงยังถูกกว่า stride เต็มหน้า

### ระดับ Mini-Project (ประกอบความรู้)

**เขียน `vm_report.c` — "รายงานหน่วยความจำของโปรเซสอื่น"**

โปรแกรมรับ `pid` จาก argument แล้วสรุปให้ครบใน 1 หน้าจอ:

- อ่าน `/proc/<pid>/statm` → พิมพ์ VS และ RSS เป็นทั้ง "จำนวนหน้า" และ MiB (ใช้ page size จาก `sysconf(_SC_PAGESIZE)` — อย่าฮาร์ดโค้ด 4096)
- อ่าน `/proc/<pid>/maps` → นับจำนวน region ทั้งหมด · ผลรวมขนาด VA ของทุก region (เป็น MiB) · นับแยกตามสิทธิ์ (อ่านได้/เขียนได้/รันได้) · พิมพ์ 5 region ที่ใหญ่สุดพร้อมชื่อ (ชื่อไฟล์ หรือ `[heap]`/`[stack]`)
- ใช้ `/proc/<pid>/pagemap` นับว่าในพื้นที่ของ region ที่ใหญ่สุด มีกี่หน้าที่ `present = 1` (เตือนผู้ใช้ในผลลัพธ์ด้วยว่า `pfn` จะเป็น 0 เสมอถ้าไม่มีสิทธิ์ `CAP_SYS_ADMIN`)

ข้อกำหนด:
- จัดการ error ให้ครบและไม่รั่ว: `pid` ไม่มีจริง → `open()` คืน `-1` ต้องรายงาน `errno` เป็นข้อความไทยที่อ่านรู้เรื่อง (ไม่ใช่แค่ "error") · ปิดไฟล์ทุกทางออก (`fclose`/`close`) · ตรวจค่าที่คืนจาก `fscanf`/`pread` ทุกครั้ง
- รับ `pid` ผิดรูปแบบ (`"abc"`, `"0"`, `"-5"`) → ต้องไม่ตาย ไม่ crash และไม่พิมพ์ขยะ
- **เกณฑ์ผ่าน:** รัน `./vm_report $$` (ของ shell ที่คุณใช้อยู่) แล้วตัวเลข VS/RSS ต้องสอดคล้องกับ `ps -o vsz,rss -p $$` (สังเกต: `ps` รายงานเป็น KiB ไม่ใช่จำนวนหน้า — ต้องคูณ page size เอง)
- โบนัส: เปรียบเทียบ `./vm_report` ของ 2 โปรเซสที่แชร์ libc ตัวเดียวกัน (เช่น shell 2 ตัว) แล้วดูว่า region ของ `libc.so.6` มี VA ต่างกันแต่มาจากไฟล์เดียวกัน

**โบนัสท้าทาย (ไม่บังคับ): `vm_watch.c`** — เขียนโปรแกรมที่ `fork()` ลูก แล้วฝั่งพ่อคอยอ่าน `/proc/<ลูก>/statm` ทุก ๆ 100 ms ขณะที่ลูกค่อย ๆ แตะหน่วยความจำทีละหน้า (sleep 1 ms ต่อหน้า) พิมพ์กราฟง่าย ๆ ว่า RSS ของลูกไต่ขึ้นทีละหน้าแบบเส้นตรงหรือไม่ แล้วอธิบายว่าทำไมเส้นถึงเป็นบันได (ไม่ใช่เส้นตรงเป๊ะ)

## 12. คำเตือนตามกาลเวลา + แหล่งอ้างอิง

**As of กันยายน 2026** — ข้อเท็จจริงในบทนี้ยืนยันจากการรันจริงบน Raspberry Pi 5 (Linux 6.18.39+rpt-rpi-2712 aarch64, GCC 14.2.0, glibc 2.41, Go 1.24.4, man-pages 6.9.1) ค่าคงที่ที่อ้างถึงเป็นของ **เครื่องนี้**: page = 16384 ไบต์ · VA 47 บิต · ตาราง 3 ชั้น · RAM 8 GiB = 515,992 frames · `overcommit_memory = 0` — ค่าเหล่านี้ **ไม่ใช่ค่าสากล**:

- **page size ต่างกันตามเครื่องและสถาปัตยกรรม** x86-64 ทั่วไป = 4096 · Pi 5 (kernel `bcm2712` defconfig) = 16384 · บางระบบ (เช่น 64 KiB granule) ต่างออกไปอีก และในอนาคตอาจมีหน้าใหญ่ (huge page) มาใช้ในระดับที่ผู้ใช้เห็นได้ (kernel นี้ `CONFIG_TRANSPARENT_HUGEPAGE` = ปิด) — **เช็คด้วย `getconf PAGESIZE` เสมอ**
- **จำนวนชั้นของตาราง/ความกว้าง VA เปลี่ยนตาม config ของ kernel** (`CONFIG_PGTABLE_LEVELS`, `CONFIG_ARM64_VA_BITS`) — เครื่องเดียวกันเปลี่ยน kernel แล้วค่าเปลี่ยนได้
- **ตัวเลขราคา (ns, ms, จำนวน fault) ขึ้นกับงานที่วิ่งอยู่และฮาร์ดแวร์** ต้องวัดเองบนเครื่องที่ใช้งานจริง
- **รายละเอียด TLB (จำนวน entry, ระดับชั้น) เป็นของ microarchitecture** เปลี่ยนรุ่น CPU แล้วเปลี่ยน — ต้องเปิด Technical Reference Manual ของรุ่นนั้น ๆ

อย่างหนึ่งที่ควรรู้เพราะเจอในชีวิตจริง: **page size ไม่เท่ากันทำให้ไบนารี/คอนเทนเนอร์บางตัวรันบน Pi 5 ไม่ได้** (มีรายงานจริงจากผู้ใช้ เช่นไบนารีที่ลิงก์มาสำหรับ 4 KiB แล้วเจอข้อผิดพลาดเรื่อง alignment) — นี่คือผลพวงตรง ๆ ของสิ่งที่เราเรียนในบทนี้ และเป็นเหตุผลว่าทำไม "รู้ page size ให้ถูก" จึงไม่ใช่เรื่องวิชาการล้วน

**แหล่งอ้างอิงหลักที่ใช้ในบทนี้**:
- เอกสารเคอร์เนล `Documentation/admin-guide/mm/pagemap.rst` — โครงสร้าง 64 บิตของ `/proc/pid/pagemap`, การปิด PFN ตั้งแต่ Linux 4.0 เพราะเรื่อง Rowhammer
- เอกสารเคอร์เนล `Documentation/arch/arm64/memory.rst` — layout ของ VA บน AArch64, "TTBRx selection is given by bit 55", จำนวนชั้นของตาราง
- เอกสารเคอร์เนล `Documentation/mm/overcommit-accounting.rst` + `man 5 proc_sys_vm` — โหมด overcommit 0/1/2 และความหมายของ `CommitLimit`/`Committed_AS`
