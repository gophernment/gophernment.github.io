# แบ่งงานใหญ่เป็นชิ้นเล็ก: ฟังก์ชัน (function), การแยกส่วน และขอบเขตของตัวแปร (ตอนที่ 05) — CS Fundamentals: จาก 0 สู่พื้นฐานที่แท้จริง

> 📅 เขียนเมื่อ: 8 กันยายน 2026 | โค้ดตัวอย่างทุกชิ้นทดสอบจริงด้วย Go 1.24.4 (เครื่องที่ใช้เขียนซีรีส์นี้); เวอร์ชันล่าสุดของ Go ณ วันเขียนคือ **1.27.1** (ตรวจจาก https://go.dev/dl และ https://go.dev/doc/devel/release — major release 1.27.0 ออก 19 สิงหาคม 2026 และ minor revision 1.27.1 ออก 1 กันยายน 2026)
> ⚠️ เวอร์ชันเครื่องมือ/ภาษามีการออกใหม่เรื่อย ๆ — ตรวจสอบเอกสารล่าสุดก่อนใช้งานจริงเสมอ

จำโปรแกรม BMI ที่เราสร้างในตอน 04 ได้ไหม? โค้ดใน `func main` ยาวร่วม 60 บรรทัด — มีทั้งการถามน้ำหนัก ถามส่วนสูง แปลงตัวเลข เช็คค่าผิด ๆ คำนวณ แปลงสถานะ พิมพ์ผล แล้ววนกลับไปถามใหม่

ตอนนั้นเราพอไหว เพราะมันเป็นโปรแกรมเดียวเรื่องเดียว และเรารู้เนื้อในทุกบรรทัด (เราเพิ่งเขียนเอง)

แต่ลองจินตนาการว่าโปรแกรมเริ่มใหญ่ขึ้น: อยากให้คำนวณได้ทั้ง BMI ของคนหลายคน คิดเงินเดือน พิมพ์ใบแจ้งหนี้ เก็บประวัติไว้ในไฟล์... `main` จะยาวเป็นร้อยเป็นพันบรรทัด และที่แย่กว่าคือ**เวลาอ่านโค้ด เราต้องไล่อ่านตั้งแต่ต้นจนจบ**ถึงจะรู้ว่าโปรแกรมทำอะไร — ถ้าเกิดบั๊ก (bug = บั๊ก = ข้อผิดพลาด) ขึ้นมา เราก็ต้องมุดหาในก้อนโค้ดยักษ์ก้อนเดียว

dev (นักพัฒนาโปรแกรม) เจอปัญหานี้มานานแล้ว และคำตอบของเขาคือหัวข้อของตอนนี้: **ฟังก์ชัน** (function) — กล่องคำสั่งที่มีชื่อ เรียกใช้เมื่อไรก็ได้ตามที่เรากำหนด — เครื่องมือ**แบ่งงานใหญ่เป็นชิ้นเล็ก** แล้วประกอบกลับเป็นโปรแกรมที่อ่านง่าย แก้ไขง่าย

เป้าหมายของตอนนี้: **อ่านจบแล้ว คุณแยกโปรแกรมออกเป็นฟังก์ชันย่อย ๆ ได้เอง** — และเข้าใจคำว่า decomposition กับ scope ซึ่งเป็นสองคำที่ dev ใช้พูดกันทุกวัน ไม่ใช่แค่ใน Go แต่ในทุกภาษา

## โปรแกรมใหญ่ขึ้นเรื่อย ๆ — ปัญหาที่ dev ทุกคนต้องเจอ

ของสามอย่างที่เราเรียนผ่านมา สรุปได้ว่า:

- ตอน 03 — **ของ** (data): ตัวแปร ชนิดข้อมูล การคำนวณ
- ตอน 04 — **การควบคุม** (flow control): if/else, for loop, การรับ input
- ตอนนี้ (05) — **การแบ่งงาน** (structure): ฟังก์ชัน

ลองคิดถึงชีวิตจริงก่อน: ถ้าคุณต้องทำกับข้าว 50 อย่างด้วยตัวคนเดียวในคืนเดียว — จะเกิดอะไรขึ้น? หัวหมุน เหนื่อย ระหว่างรอผัดอย่างหนึ่ง ซุปอีกอย่างก็ไหม้... ทางแก้ของร้านอาหารจริงไม่ใช่ "พยายามทำคนเดียวให้ได้" แต่คือการ**แบ่งงาน**: มีคนหนึ่งหั่นผัก อีกคนย่าง อีกคนจัดจาน — แต่ละคนเก่งงานของตัวเองชิ้นเดียว แล้วส่งต่อให้คนถัดไป

ร้านอาหารทั้งร้าน = โปรแกรมใหญ่ 1 ตัว / แต่ละสถานีงาน = ฟังก์ชัน 1 ตัว / ส่งต่อกันระหว่างสถานี = argument กับ return (จะอธิบายด้านล่าง)

นี่คือหลักคิดที่ dev เรียกว่า **decomposition** (ดีคอมโพซิชัน = การแยกส่วน) — แบ่งปัญหาที่ใหญ่เกินจะเข้าใจในครั้งเดียว ออกเป็นปัญหาย่อยที่เล็กพอจะเข้าใจได้ทีละอัน แล้วค่อยเอามาต่อกัน

ดูหลักฐานจากโลกจริงที่คุณใช้อยู่ทุกวัน: โค้ดของ Linux kernel (เคอร์เนล = แกนกลางของระบบปฏิบัติการ — ซีรีส์นี้จะเรียนตอน 18–21) มีหลายสิบล้านบรรทัด — ไม่มีมนุษย์คนไหนอ่านจบทั้งก้อนได้ แต่พอถูกแบ่งเป็นฟังก์ชันเล็ก ๆ หลายหมื่นฟังก์ชัน แต่ละฟังก์ชันทำอะไรแค่อย่างเดียว เราถึงอ่านและดูแลมันไหว

**แล้วทำไมต้องเป็น "ฟังก์ชัน" โดยเฉพาะ?** เพราะฟังก์ชันคือหน่วยแบ่งงานที่ภาษาคอมพิวเตอร์ทุกภาษามีให้ — เรามาดูกันว่ามันหน้าตาเป็นยังไง

## ฟังก์ชัน — ของจริงที่คุณใช้มาตลอดโดยไม่รู้ตัว

จริง ๆ แล้วคุณเขียนฟังก์ชันตัวแรกตั้งแต่ตอน 03 แล้ว — นั่นคือ `func main()` ที่โปรแกรมทุกโปรแกรมต้องมี

และคุณก็**เรียกใช้**ฟังก์ชันของคนอื่นตลอดตั้งแต่ตอน 02 เช่น `fmt.Println("สวัสดี")` — `Println` ก็คือฟังก์ชันที่อยู่ใน standard library (สแตนดาร์ด ไลบรารี = กล่องเครื่องมือมาตรฐานที่มากับภาษา Go) มีคนเขียนไว้ เราแค่เรียกใช้ โดยไม่ต้องรู้ว่า**ข้างใน**มันพิมพ์ยังไง

นี่คือพลังแรกของฟังก์ชัน: มันคือ **abstraction** (แอบสแตรกชัน = การซ่อนรายละเอียด) — เหมือนคุณสั่ง "ข้าวผัดกระเพราหนึ่งจาน" โดยไม่ต้องลงไปยืนสั่งแม่ครัวทุกขั้นตอนว่าหั่นกระเทียมยังไง

### แกะฟังก์ชันทีละชิ้น

สร้างไฟล์ `funcs1.go` ในโฟลเดอร์ `gopher-course` (โฟลเดอร์เดียวกับตอนก่อน ๆ) แล้วพิมพ์ตาม:

```go
package main

import "fmt"

// add บวกเลขสองตัว แล้วคืนผลลัพธ์กลับไป
func add(a int, b int) int {
	return a + b
}

// greet พิมพ์คำทักทาย — ฟังก์ชันแบบไม่คืนค่า
func greet(name string) {
	fmt.Println("สวัสดี", name)
}

func main() {
	greet("สมชาย")                        // เรียกฟังก์ชันที่ไม่คืนค่า

	result := add(3, 5)                   // เรียกฟังก์ชันที่คืนค่า → เก็บผลลัพธ์ในตัวแปร
	fmt.Println("3 + 5 =", result)

	fmt.Println("10 + 20 =", add(10, 20)) // เอาค่าที่คืนมาใช้ได้ทันที ไม่ต้องเก็บก่อน
}
```

รันด้วย `go run funcs1.go` — ผลลัพธ์จริงที่เครื่องของผม:

```
สวัสดี สมชาย
3 + 5 = 8
10 + 20 = 30
```

ลองไล่แกะโครงสร้าง `func add(a int, b int) int` ทีละคำ (วิธีแกะแบบเดียวกับตอน 03 ที่เคยทำกับ `func main` ทีละชิ้น):

| ชิ้นส่วน | ความหมาย |
|---|---|
| `func` | (ฟังก์ = ย่อจาก function) คำบอกภาษา Go ว่า "ต่อไปนี้คือการประกาศฟังก์ชัน" |
| `add` | **ชื่อฟังก์ชัน** — ตั้งเองได้ (กฎเดียวกับชื่อตัวแปรตอน 03) ควรเป็นคำบอกว่า "ทำอะไร" |
| `(a int, b int)` | **parameter** (พารามิเตอร์ = ตัวแปรรับข้อมูล) — รายการ "ช่องรับข้อมูลเข้า" แต่ละช่องมีชื่อ + ชนิดกำกับ |
| `int` ตัวสุดท้าย | **ชนิดของค่าที่คืน** (return value = รีเทิร์น แวลู = ค่าที่ฟังก์ชันส่งกลับไปให้คนเรียก) |
| `{ ... }` | **body** (บอดี้ = ตัวเนื้อ) — ปีกกาขอบเขตเดียวกับตอน 03–04: คำสั่งที่ฟังก์ชันนี้จะทำ |
| `return a + b` | (รีเทิร์น = คืนกลับ) สั่งให้ฟังก์ชัน**หยุดตรงนี้ แล้วส่งค่า `a + b` กลับไป**ให้คนเรียก |

สองข้อที่คนเริ่มเรียนใหม่สับสนบ่อย ขอเน้น:

1. **ฟังก์ชันที่ "คืนค่า" ต้องบอกชนิดค่าที่คืนไว้ที่หัวฟังก์ชัน** — `func add(...) int` บอกว่า "ฟังก์ชันนี้จะคืน int" แล้วข้างในต้องมี `return` พร้อมค่าที่เป็น int เสมอ (ทุกเส้นทาง! — เส้นทาง = ทางที่โปรแกรมอาจเดินไปแต่ละกรณี เช่น กรณี if เป็นจริง/เท็จ — ถ้าเส้นทางไหนไม่มี return compile ไม่ผ่าน — ดูหัวข้อกับดักด้านล่าง)
2. **ฟังก์ชันที่ "ไม่คืนค่า" ไม่ต้องเขียนชนิดคืน** — ดู `func greet(name string)` — จบแค่วงเล็บ ไม่มีชนิดต่อท้าย ข้างในก็ไม่ต้องมี return ก็ได้ (อยากจบกลางคันก็เขียน `return` เปล่า ๆ ได้) — หลายภาษาเรียกฟังก์ชันแบบนี้ว่า void (วอยด์ = ว่างเปล่า) แต่ Go ไม่มีคำว่า void ใช้วิธี "ไม่ประกาศชนิดคืน" แทน

### การเรียกฟังก์ชัน (call = คอล = เรียก)

การเรียกคือการเขียนชื่อฟังก์ชันตามด้วยวงเล็บ:

- `greet("สมชาย")` — สั่งให้ไปทำอะไรก็ตามใน body ของ greet
- `add(3, 5)` — สั่งให้ไปบวก แล้ว**ได้ค่ากลับมา** ค่านี้เอาไปใช้ได้ทันที ไม่ว่าจะเก็บใส่ตัวแปร (`result := add(3, 5)`) หรือแทรกในคำสั่งอื่น (`fmt.Println(add(10, 20))`)

สังเกต: ตัวแปร `result` ใน `main` กับตัวแปร `a`, `b` ใน `add` — **เป็นคนละตัวกัน** ข้อมูลไม่ได้ "ไหลปนกัน" แต่ถูก**ส่งผ่าน**ช่อง parameter เข้าไป แล้ว**ส่งกลับ**ผ่าน return — ตรงนี้จะสำคัญมากเมื่อเรียนเรื่อง scope ในอีกสองสามหัวข้อข้างหน้า

## ศัพท์คู่ที่ dev ใช้สลับกันจนมือใหม่งง: parameter กับ argument

คำว่า argument เราเห็นครั้งแรกตั้งแต่ตอน 03 ตอนที่แกะ `func main` — ตอนนี้ขอวางให้ชัด เพราะ dev พูดสองคำนี้ปนกันตลอดเวลา:

- **parameter** (พารามิเตอร์) = **ช่อง**ที่ประกาศไว้ในหัวฟังก์ชัน — คือ `a` กับ `b` ใน `func add(a int, b int)`
- **argument** (อาร์กิวเมนต์) = **ค่าจริง**ที่ส่งเข้าไปตอนเรียก — คือ `3` กับ `5` ใน `add(3, 5)`

จำง่าย ๆ ด้วยอุปมาเดียว: parameter คือ **"ป้ายชื่อโต๊ะ"** ที่ร้านติดไว้ประจำโต๊ะแต่ละตัว (โต๊ะ A กับโต๊ะ B — เทียบได้กับช่อง `a` กับ `b` ของ `add`) — ป้ายเป็นของตายตัว ส่วน argument คือ **"ลูกค้าที่มานั่งที่โต๊ะ A"** ในแต่ละคืน — ตัวจริงที่เปลี่ยนไปได้ทุกครั้งที่มีคนมา ตรงนี้คือความต่างเชิงทฤษฎี: parameter คือ "ช่อง" ที่ประกาศไว้ตอนนิยามฟังก์ชัน ส่วน argument คือ "ค่าจริง" ที่ใส่ลงในช่องตอนเรียก — ในชีวิตจริง dev ใช้ปนกัน ฟังแล้วไม่ต้องตกใจ ขอแค่เราเข้าใจนิยามชัด ๆ ตัวเอง

อีกคำที่ควรรู้: **function signature** (ซิกเนเจอร์ = ลายเซ็นของฟังก์ชัน) — หมายถึง "หัวฟังก์ชันรวมชนิด" คือ `add(a int, b int) int` ทั้งบรรทัดแรก ไม่รวม body — เวลาคุยกัน dev มักพูดว่า "ฟังก์ชันนี้ signature เป็นยังไง" = "รับอะไร คืนอะไร"

## จุดเด่นของ Go: ฟังก์ชันคืนค่าได้หลายค่าพร้อมกัน

ภาษาโปรแกรมส่วนใหญ่ ฟังก์ชันคืนค่าได้**ค่าเดียว** แต่ Go คืนได้หลายค่า — และนี่คือหนึ่งในเหตุผลที่ dev สาย Go ชอบภาษานี้มาก

คุณเห็นของจริงมาแล้วตั้งแต่ตอน 04: `strconv.Atoi(s)` คืน **2 ค่า** — (ตัวเลขที่แปลงได้, error) — ตอนนั้นเราเขียน `age, err := strconv.Atoi(text)` รับทั้งคู่ หรือเขียน `_, err := ...` เมื่ออยากทิ้งค่าแรก (`_` = อันเดอร์สกอร์ = "ช่องทิ้ง" รับค่าไว้แต่ไม่ใช้)

มาลองเขียนฟังก์ชันคืน 2 ค่าของเราเอง — สร้าง `return2.go`:

```go
package main

import "fmt"

// divMod หารเอาเศษ — คืน 2 ค่าพร้อมกัน: ผลหาร กับ เศษ
func divMod(a int, b int) (int, int) {
	return a / b, a % b
}

// rectArea หาพื้นที่สี่เหลี่ยมผืนผ้า — ใช้ named return value
// คือประกาศชื่อตัวแปรผลลัพธ์ (result) ไว้ที่หัวฟังก์ชันแล้ว
func rectArea(width float64, height float64) (result float64) {
	result = width * height
	return // return เปล่า ๆ = คืนค่าที่อยู่ในตัวแปร result ณ ตอนนั้น
}

func main() {
	q, r := divMod(17, 5) // รับ 2 ค่าพร้อมกันด้วย :=
	fmt.Println("17 ÷ 5 ได้", q, "เศษ", r)

	area := rectArea(3.5, 2)
	fmt.Println("พื้นที่สี่เหลี่ยม =", area)
}
```

ผลลัพธ์จริง:

```
17 ÷ 5 ได้ 3 เศษ 2
พื้นที่สี่เหลี่ยม = 7
```

แกะโค้ด:

- `func divMod(a int, b int) (int, int)` — วงเล็บที่หัวฟังก์ชันมีชนิด 2 ตัว = "คืน int 2 ค่า"
- `return a / b, a % b` — คืน 2 ค่า**คั่นด้วยลูกน้ำ** เรียงตามลำดับชนิดที่ประกาศไว้
- ฝั่งรับ: `q, r := divMod(17, 5)` — รับ 2 ค่าด้วย `:=` ค่าแรกเข้าตัวแปรแรก ค่าที่สองเข้าตัวแปรที่สอง

**named return value** (เนมด์ รีเทิร์น แวลู = ค่าที่คืนแบบมีชื่อ) ใน `rectArea` — แทนที่จะคืนค่าตอนเขียน return เราประกาศ**ชื่อตัวแปรผลลัพธ์**ไว้ที่หัวฟังก์ชัน (`(result float64)`) ข้างในก็แค่กำหนดค่าให้ `result` แล้วปิดท้ายด้วย `return` เปล่า ๆ — Go จะคืนค่าปัจจุบันของตัวแปรชื่อนั้นให้เอง

ขอพูดตรง ๆ ว่า named return เป็นเรื่อง "เกริ่นให้รู้จัก" มากกว่า — dev ส่วนใหญ่เขียน `return` พร้อมค่าให้ชัดเจน (แบบ `divMod`) เพราะอ่านง่ายกว่ากันเยอะ คุณจะได้เจอ named return บ่อยตอนอ่านโค้ดในโลกจริง เลยควรพอคุ้นหน้าไว้ — แต่ช่วงนี้เขียนแบบชัดเจนไปก่อนได้เลย

จุดที่ฟังก์ชันคืนหลายค่าจะระเบิดพลังจริงคือตอน **error handling** (แฮนด์ลิง = การจัดการความผิดพลาด) — dev Go มีธรรมเนียมว่า "ฟังก์ชันที่อาจพลาดได้ ต้องคืนค่าปกติ + error เป็นค่าที่สอง" เราจะเรียนเต็มรูปแบบตอน 07 — ตอนนี้ขอใช้หลักเดียวกันกับ "สัญญาณ ok/ไม่ ok" ในโปรแกรมด้านล่างก่อน

## scope — ขอบเขตของตัวแปร: ประกาศในปีกกาไหน ใช้ได้แค่ในนั้น

จำตอน 03–04 ได้ไหม เราย้ำหลายรอบว่า "ตัวแปรที่ประกาศในปีกกา `{ }` ใช้ได้แค่ในปีกกานั้น" — ตอน 04 เรายังมีโจทย์ให้แก้อาการ "ตัวแปรหลุดออกจากปีกกา" ด้วยซ้ำ

วันนี้เราจะให้ชื่อทางการกับกฎนี้: **scope** (สโคป = ขอบเขต) — ขอบเขตที่ตัวแปร "มีชีวิตและมองเห็นได้" ตัวแปรทุกตัวเกิดมาใน scope หนึ่ง และ**ตายเมื่อออกจาก scope นั้น** เอาไปใช้ข้างนอกไม่ได้เด็ดขาด

ลองสร้างไฟล์ `scopebad.go` แล้วรันดู:

```go
package main

import "fmt"

func main() {
	total := 0
	for i := 1; i <= 10; i++ {
		total += i
	}
	fmt.Println(total) // ใช้ได้ — total ประกาศใน func main (นอกปีกกา loop)

	if total > 50 {
		verdict := "เยอะมาก"
		fmt.Println(verdict)
	}
	fmt.Println(verdict) // error! verdict ประกาศในปีกกาของ if — ออกนอกปีกกาแล้วมองไม่เห็น
}
```

รันด้วย `go run scopebad.go` — compile ไม่ผ่าน (compile = คอมไพล์ = ขั้นตอนที่ภาษาแปลงโค้ดของเราเป็นโปรแกรม — ตอน 02–03 เราเจอมาแล้ว) error จริงที่เครื่องของผม:

```
./scopebad.go:16:14: undefined: verdict
```

**undefined** (อันดีไฟน์ด์ = ไม่มีตัวตน/ไม่รู้จัก) — Go บอกว่า "ผมไม่รู้จัก verdict ณ จุดนี้" เพราะ `verdict` เกิดในปีกกาของ `if` และตายไปแล้วทันทีที่ออกจากปีกกานั้น แม้จะอยู่คนละบรรทัดใน `main` เดียวกันก็ตาม

วิธีแก้ (สร้าง `scopegood.go`):

```go
package main

import "fmt"

func main() {
	total := 0
	for i := 1; i <= 10; i++ {
		total += i
	}
	fmt.Println(total)

	verdict := "ปานกลาง" // ประกาศไว้ที่ func main — มีชีวิตตลอดทั้งฟังก์ชัน
	if total > 50 {
		verdict = "เยอะมาก" // แค่เปลี่ยนค่า ไม่ต้องประกาศใหม่
	}
	fmt.Println(verdict) // ใช้ได้แล้ว
}
```

ผลลัพธ์จริง:

```
55
เยอะมาก
```

หลักการคือ: ถ้าอยากใช้ตัวแปรทั้งในและนอกปีกกา ก็ต้อง**ประกาศมันในขอบเขตที่กว้างพอ** — ที่นี่คือระดับ `func main` (ประกาศ `verdict` ไว้นอก `if` แล้วข้างในแค่**เปลี่ยนค่า** ไม่ใช้ `:=` ประกาศซ้ำ — จำตอน 03: `:=` ใช้ประกาศตัวแปรใหม่เท่านั้น)

แผนผังด้านล่างสรุปกฎ scope ให้เห็นเป็นภาพ — ตัวแปรที่ประกาศในปีกกาชั้นไหน ใช้ได้ในปีกกาชั้นนั้นกับปีกกาลูกที่ซ้อนข้างในเท่านั้น:

![ขอบเขตของตัวแปร (scope): ปีกกาชั้นไหนประกาศ ปีกกานั้นกับปีกกาลูกใช้ได้ ตัวแปรรั่วออกจากปีกกาไม่ได้](/assets/diagrams/ep05-02-scope-blocks.svg)

### scope ในระดับฟังก์ชัน — กฎที่ทำให้ฟังก์ชัน "ปลอดภัย"

กฎเดียวกันนี้ใช้กับฟังก์ชันทุกตัว: ตัวแปรที่ประกาศใน `func A` **ใช้ใน `func B` ไม่ได้** แม้ B จะถูกเรียกจาก A ก็ตาม — พารามิเตอร์ของฟังก์ชันก็เป็นตัวแปรแบบหนึ่ง (มี scope = ทั้งฟังก์ชันนั้น)

ลองดูตัวอย่างที่ dev เจอประจำ — สร้างไฟล์นี้รันดู (`pkgvar.go`):

```go
package main

import "fmt"

// package-level variable: ประกาศนอกทุกฟังก์ชัน
// ทุกฟังก์ชันใน package main นี้ใช้ได้หมด
var appName = "เครื่องคิดเลขส่วนตัว"

func header() {
	fmt.Println("=== " + appName + " ===")
}

func footer() {
	fmt.Println("=== จบ " + appName + " ===")
}

func main() {
	header()
	fmt.Println("ตัวแปรระดับ package ใช้ได้ทุกฟังก์ชันในไฟล์เดียวกัน")
	footer()
}
```

ผลลัพธ์จริง:

```
=== เครื่องคิดเลขส่วนตัว ===
ตัวแปรระดับ package ใช้ได้ทุกฟังก์ชันในไฟล์เดียวกัน
=== จบ เครื่องคิดเลขส่วนตัว ===
```

ตัวแปร `appName` ประกาศ**นอกทุกฟังก์ชัน** จึงมี scope กว้างที่สุดระดับหนึ่ง — เรียกว่า **package-level variable** (แพ็กเกจ-เลเวล = ระดับกล่อง package — package = แพ็กเกจ = หน่วยรวมโค้ดของ Go ที่เราเห็นคำว่า `package main` อยู่บรรทัดบนสุดของทุกไฟล์) — ฟังก์ชัน `header`, `footer`, `main` ใช้มันได้หมด

ขอเกริ่นไว้ก่อนว่า: dev มืออาชีพ**ระวัง**ตัวแปรระดับกว้างแบบนี้ (รวมถึง package-level) เพราะยิ่ง scope กว้าง ตัวแปรยิ่งถูกแก้จากหลายที่ → หาบั๊กยาก — dev มีคำพูดติดปากว่า **"ยิ่ง scope กว้าง ยิ่งเสี่ยง"**

แนวทางที่นิยมคือ**ประกาศตัวแปรให้แคบที่สุดเท่าที่จำเป็น** แล้วส่งข้อมูลผ่าน parameter/return แทนที่จะฝากไว้ในตัวแปรกลางกว้าง ๆ จำประโยคนี้ไว้ แล้วตอน 06–07 เราจะเห็นมันเป็นรูปธรรม

## ทำไม dev ถึงบอกว่า "อย่าเขียนซ้ำ" — DRY

มีหลักการชื่อดังในวงการ dev ชื่อ **DRY** (ดราย) — ย่อจาก **Don't Repeat Yourself** = อย่าทำตัวเองซ้ำซ้อน หมายถึง: **อย่าเขียนโค้ดชิ้นเดียวกันซ้ำหลายที่**

มองย้อนไปที่โปรแกรม BMI ตอน 04: โค้ดอ่านน้ำหนักกับอ่านส่วนสูง**เกือบเหมือนกันทุกบรรทัด** (ต่างแค่ข้อความถาม) — ถ้าเราอยากเปลี่ยนพฤติกรรม เช่น เปลี่ยนวิธีกันค่าผิด เราต้องแก้**สองที่** และถ้าเผลอแก้ที่เดียว อีกที่ก็จะทำพฤติกรรมเก่า → บั๊กมาเยือนแบบหาไม่เจอ

อุปมาที่ dev ชอบเล่า: โค้ดที่ copy ไปแปะหลายที่ = เอกสารที่ถ่ายสำเนาไว้หลายใบ — พอต้องแก้ข้อมูล ต้องไล่แก้**ทุกใบ** และเกือบทุกครั้งจะลืมอย่างน้อยหนึ่งใบเสมอ

ฟังก์ชันคือเครื่องมือกำจัดความซ้ำซ้อน: เขียนชิ้นงานหนึ่งครั้ง ตั้งชื่อให้มัน แล้ว**เรียกใช้กี่ครั้งก็ได้** อยากเปลี่ยนพฤติกรรม เปลี่ยน**ที่เดียว** — ที่เหลืออัตโนมัติ

เราจะได้เห็นของจริงในหัวข้อถัดไป: เราเขียนฟังก์ชันอ่านคำตอบ **หนึ่งครั้ง** แล้วใช้มันทั้งตอนถามน้ำหนักและตอนถามส่วนสูง

## ลงมือทำ: refactor โปรแกรม BMI ตอน 04 ให้เป็นฟังก์ชัน

**refactor** (รีแฟกเตอร์ = ปรับโครงสร้างโค้ดใหม่ โดยที่พฤติกรรมของโปรแกรมไม่เปลี่ยน — แค่ทำให้โค้ดอ่านง่าย/ดูแลง่ายขึ้น) — นี่คืองานที่ dev ทำกันเป็นกิจวัตร

ขั้นแรก วิธีคิดแบบ dev: อ่านโค้ด 60 บรรทัดของตอน 04 แล้วหา "ชิ้นงานอิสระ" ที่แยกออกมาได้:

1. **อ่านคำตอบจากผู้ใช้** (ถามหนึ่งคำถาม อ่านหนึ่งบรรทัด กัน `q`/input หมด) — ใช้ทั้งตอนถามน้ำหนักและถามส่วนสูง → แยกเป็นฟังก์ชันเดียว เรียก 2 ครั้ง (DRY!)
2. **คำนวณ BMI** — `weight / (height * height)` → ฟังก์ชัน `bmi`
3. **แปลง BMI เป็นข้อความสถานะ** — if/else ไล่เกณฑ์ → ฟังก์ชัน `bmiStatus`
4. `main` เหลือหน้าที่ "เล่าเรื่อง": ถาม → คำนวณ → พิมพ์ → วน

จะเห็นว่าข้อ 1 แยกออกมา**เฉพาะส่วนอ่าน** ไม่รวม "แปลงเลข + เช็คค่าผิด" — เพราะตอน 04 ตรวจ**ทีละรอบรวมทั้งสองค่า** (ถามน้ำหนัก+ส่วนสูงครบก่อน แล้วค่อยเช็ค ถ้าผิดก็ถามใหม่ทั้งคู่) ถ้าเราเช็คทีละค่าทันทีในฟังก์ชันอ่าน พฤติกรรมจะเปลี่ยนไปจากตอน 04 — refactor ที่ถูกต้องคือ**แบ่งตามหน่วยพฤติกรรม** ไม่ใช่แค่ย้ายบรรทัดที่หน้าตาคล้ายกัน

สร้างไฟล์ `bmi_funcs.go` (เขียนใหม่จาก `bmi.go` ของตอน 04):

```go
package main

import (
	"bufio"
	"fmt"
	"math"
	"os"
	"strconv"
	"strings"
)

// readLine ถามคำถามหนึ่งคำถาม แล้วอ่านคำตอบหนึ่งบรรทัดจากผู้ใช้
// คืน 2 ค่า: (ข้อความที่พิมพ์, ยังเล่นต่อไหม)
// ค่าที่สองเป็น false = ผู้ใช้พิมพ์ q หรือ input หมด → ผู้เรียกควรเลิกโปรแกรม
func readLine(reader *bufio.Reader, prompt string) (string, bool) {
	fmt.Print(prompt)
	text, err := reader.ReadString('\n')
	if err != nil { // input หมด (Ctrl+D / อ่านไฟล์จนจบ) → ส่งสัญญาณ "เลิก" กลับไป
		return "", false
	}
	text = strings.TrimSpace(text)
	if text == "q" {
		return "", false
	}
	return text, true
}

// bmi คำนวณค่า BMI จากน้ำหนัก (กก.) กับส่วนสูง (เมตร)
func bmi(weight float64, height float64) float64 {
	return weight / (height * height)
}

// bmiStatus แปลงค่า BMI เป็นข้อความสถานะ (เกณฑ์ตัวอย่างเพื่อการเรียนเท่านั้น)
func bmiStatus(value float64) string {
	if value < 18.5 {
		return "น้ำหนักน้อย"
	}
	if value < 25 {
		return "น้ำหนักปกติ"
	}
	if value < 30 {
		return "น้ำหนักเกิน"
	}
	return "อ้วนระดับที่ต้องพบแพทย์"
}

func main() {
	fmt.Println("=== โปรแกรมคำนวณ BMI แบบโต้ตอบ (เวอร์ชันฟังก์ชัน) ===")
	fmt.Println("(พิมพ์ q เพื่อออกจากโปรแกรม)")

	reader := bufio.NewReader(os.Stdin)

	for {
		weightText, ok := readLine(reader, "น้ำหนัก (กิโลกรัม เช่น 68.5): ")
		if !ok { // พิมพ์ q หรือ input หมด → เลิกอย่างสุภาพ
			fmt.Println("ลาก่อน!")
			break
		}
		heightText, ok := readLine(reader, "ส่วนสูง (เมตร เช่น 1.75): ")
		if !ok {
			fmt.Println("ลาก่อน!")
			break
		}

		// ถามครบทั้งสองค่าแล้ว — ค่อยตรวจรวมกันทีเดียว (จังหวะเดียวกับตอน 04)
		weight, errW := strconv.ParseFloat(weightText, 64)
		height, errH := strconv.ParseFloat(heightText, 64)
		if errW != nil || errH != nil { // || = มีตัวไหนผิดตัวหนึ่งก็เข้าเงื่อนไขนี้
			fmt.Println("ขอโทษครับ อ่านเป็นตัวเลขไม่ได้ — ลองพิมพ์ใหม่ (เช่น 68.5)")
			continue // ถามใหม่ทั้งสองค่า (ไม่คิดคำนวณ)
		}

		// กันค่าที่เป็นไปไม่ได้: <= 0 รวมทั้ง NaN/Inf ที่ ParseFloat รับได้แบบไม่ error (NaN/Inf — gloss เต็มในตอน 04)
		if weight <= 0 || height <= 0 ||
			math.IsNaN(weight) || math.IsNaN(height) ||
			math.IsInf(weight, 0) || math.IsInf(height, 0) {
			fmt.Println("น้ำหนักและส่วนสูงต้องเป็นตัวเลขปกติที่มากกว่า 0 — ลองใหม่นะครับ")
			continue
		}

		value := bmi(weight, height) // ฟังก์ชันคำนวณ
		status := bmiStatus(value)   // ฟังก์ชันแปลงเป็นสถานะ
		fmt.Printf("BMI = %.2f → %s\n", value, status)
		fmt.Println("--------------------------------")
	}
}
```

ก่อนรัน ขอพักที่ signature ของ `readLine` แวบหนึ่ง — นี่คือครั้งแรกที่เราเห็น parameter หน้าตาแบบนี้: `reader *bufio.Reader` — `bufio.Reader` คือชนิดของ "เครื่องอ่าน" ที่เราสร้างใน `main` ด้วย `bufio.NewReader(os.Stdin)` ส่วน `*` ที่นำหน้าเป็นเครื่องหมายว่า parameter ตัวนี้เป็น **pointer** (พอยน์เตอร์ = ตัวชี้/ตัวอ้างอิง — จะเรียนเต็มรูปแบบตอน 14 ตอนนี้แค่เข้าใจว่า "ส่งเครื่องอ่านเข้ามา" ก็พอ ยังไม่ต้องสนใจกลไก) แล้วทำไมต้องส่ง `reader` เข้ามาทาง parameter ด้วยล่ะ? เพราะ `reader` ถูกประกาศใน `main` — และกฎ scope ที่เพิ่งเรียนบอกว่า ตัวแปรใน `main` ฟังก์ชันอื่น**ใช้ตรง ๆ ไม่ได้** — ทางเดียวที่ข้อมูลจะเดินทางไปยังฟังก์ชันได้คือ**ส่งผ่าน parameter** แบบนี้เอง (เหมือนส่งของต่อให้สถานีงานถัดไปในอุปมาร้านอาหาร)

รันด้วย `go run bmi_funcs.go` — ผลลัพธ์จริงจากการป้อนข้อมูลชุดหนึ่ง: รอบแรกน้ำหนัก 68.5 + ส่วนสูง 1.75 → รอบถัดไปป้อน `abc` เป็นน้ำหนัก (กันค่าแปลงไม่ได้) → รอบถัดไปป้อน `NaN` เป็นน้ำหนัก (กันค่าพิเศษ) → ป้อน 80 + 1.9 → สุดท้ายพิมพ์ `q` ออก — สังเกตว่าทุกครั้งที่น้ำหนักผิด โปรแกรมยังถามส่วนสูงให้ครบก่อน แล้วค่อยบอกว่าใช้ไม่ได้ (จังหวะเดียวกับตอน 04):

```

(พิมพ์ q เพื่อออกจากโปรแกรม)
น้ำหนัก (กิโลกรัม เช่น 68.5): ส่วนสูง (เมตร เช่น 1.75): BMI = 22.37 → น้ำหนักปกติ
--------------------------------
น้ำหนัก (กิโลกรัม เช่น 68.5): ส่วนสูง (เมตร เช่น 1.75): ขอโทษครับ อ่านเป็นตัวเลขไม่ได้ — ลองพิมพ์ใหม่ (เช่น 68.5)
น้ำหนัก (กิโลกรัม เช่น 68.5): ส่วนสูง (เมตร เช่น 1.75): น้ำหนักและส่วนสูงต้องเป็นตัวเลขปกติที่มากกว่า 0 — ลองใหม่นะครับ
น้ำหนัก (กิโลกรัม เช่น 68.5): ส่วนสูง (เมตร เช่น 1.75): BMI = 22.16 → น้ำหนักปกติ
--------------------------------
น้ำหนัก (กิโลกรัม เช่น 68.5): ลาก่อน!
```

โปรแกรมทำงาน**เหมือนตอน 04 ทุกประการ** (พฤติกรรมไม่เปลี่ยน — นี่คือหัวใจของ refactor) แต่โครงสร้างต่างกันลิบลับ ลองเทียบ:

**แผนผังด้านล่าง** แสดงว่า main กลายเป็น "ผู้เล่าเรื่อง" ที่เรียกฟังก์ชันย่อยตามลำดับ — อ่านบรรทัด main ทีเดียวก็รู้ว่าโปรแกรมทำอะไร ส่วนรายละเอียด "ทำยังไง" ไปซ่อนอยู่ในแต่ละฟังก์ชัน:

![แผนผังการแยกส่วน (decomposition): โปรแกรม BMI ถูกแบ่งเป็นฟังก์ชันย่อยที่ main เรียกใช้](/assets/diagrams/ep05-01-decomposition-tree.svg)

จุดที่ควรสังเกตในโค้ด:

- **`readLine` คืน 2 ค่า `(string, bool)`** — `bool` ตัวที่สองคือ "สัญญาณ": `true` = ได้ข้อความมา, `false` = ต้องเลิก (พิมพ์ q หรือ input หมด) — เราใช้หลัก "คืนหลายค่า" จากหัวข้อก่อนหน้านี้เอง และนี่คือต้นแบบของสิ่งที่ตอน 07 จะทำด้วย `error` จริง
- **`readLine` ถูกเรียก 2 ครั้ง** (อ่านน้ำหนัก, อ่านส่วนสูง) — เขียนครั้งเดียว ใช้สองที่ = DRY
- **การแปลงเลข + เช็คค่าผิดยังอยู่ที่ `main`** — เพราะตอน 04 ตรวจทีละรอบรวมทั้งสองค่า (ถามครบแล้วค่อยเช็ค ถ้าผิดถามใหม่ทั้งคู่) การย้ายไปไว้ใน `readLine` ทีละค่าจะทำให้พฤติกรรมเพี้ยน — แบ่งฟังก์ชันตาม "หน่วยพฤติกรรม" ไม่ใช่แค่ย้ายบรรทัดที่หน้าตาคล้ายกัน
- **ฟังก์ชันย่อยไม่รู้จักกันและกัน** — `bmi` เห็นแค่ `weight` กับ `height` ที่ส่งเข้าไป `bmiStatus` เห็นแค่ `value` — ไม่มีตัวแปรใด "ลอด" ระหว่างฟังก์ชันได้ (scope!) ข้อมูลไหลผ่าน parameter → return → parameter → return เท่านั้น
- ถ้าอยากเพิ่มฟีเจอร์ เช่น รับน้ำหนักเป็นปอนด์แล้วแปลง — ก็แค่เพิ่มฟังก์ชันใหม่ หรือแก้ใน `readLine`/`bmi` ที่เดียว ไม่ต้องมุดแก้กลาง main

หมายเหตุเล็กน้อย: ใน `readLine` เราใช้ `err` จาก `ReadString` เช็ค "input หมด" แล้วส่งสัญญาณผ่าน `bool` กลับไป แต่เวลาจะ "ส่งต่อ" error ให้คนเรียกอย่างเป็นทางการ เราจะทำตอน 07 — เดี๋ยวจะเห็นว่าการที่ Go คืนหลายค่าได้นั้นออกแบบมาเพื่อเรื่องนี้โดยเฉพาะ

## ลงมือทำ: refactor เกมทายเลข (mini-project ตอน 04) ให้เป็นฟังก์ชัน

เกมทายเลขที่คุณเขียนในตอน 04 — ถ้าเขียนตาม Hint ครบ (สุ่มเลข, วนถาม, กัน `abc`, รองรับ `q`) โค้ดใน main จะยาวร่วม 50 บรรทัดและมีเงื่อนไขซ้อนกันหลายชั้น ลองจัดระเบียบด้วยฟังก์ชัน — สร้าง `guess_funcs.go`:

```go
package main

import (
	"bufio"
	"fmt"
	"math/rand"
	"os"
	"strconv"
	"strings"
)

// newSecret สุ่มเลขลับ 1 ตัวระหว่าง 1–10
func newSecret() int {
	return rand.Intn(10) + 1
}

// readGuess อ่านตัวเลขที่ผู้ใช้ทาย คืน (ตัวเลขที่ทาย, ยังเล่นต่อไหม)
// ค่าที่สองเป็น false = ผู้ใช้พิมพ์ q หรือ input หมด → ควรเลิกเกม
func readGuess(reader *bufio.Reader) (int, bool) {
	for {
		fmt.Print("ทายเลข 1–10 (พิมพ์ q เพื่อเฉลย): ")
		text, err := reader.ReadString('\n')
		if err != nil {
			return 0, false
		}
		text = strings.TrimSpace(text)
		if text == "q" {
			return 0, false
		}

		guess, err := strconv.Atoi(text)
		if err != nil { // พิมพ์อะไรที่ไม่ใช่ตัวเลข
			fmt.Println("พิมพ์เป็นตัวเลขสิ (เช่น 5)")
			continue
		}
		return guess, true
	}
}

// guessGame เกมทายเลขทั้งเกม: สุ่มเลขลับ วนถามจนกว่าจะทายถูกหรือเลิก
func guessGame(reader *bufio.Reader) {
	secret := newSecret()
	tries := 0

	for {
		guess, playing := readGuess(reader)
		if !playing { // ผู้ใช้ขอเลิก
			fmt.Printf("เฉลย: เลขลับคือ %d\n", secret)
			return
		}
		tries++

		if guess < secret {
			fmt.Println("น้อยไป!")
			continue
		}
		if guess > secret {
			fmt.Println("มากไป!")
			continue
		}
		fmt.Printf("ถูกต้อง! (ลอง %d ครั้ง)\n", tries)
		return // จบเกม — return ออกจาก guessGame กลับไป main
	}
}

func main() {
	fmt.Println("=== เกมทายเลข 1–10 (เวอร์ชันฟังก์ชัน) ===")
	guessGame(bufio.NewReader(os.Stdin))
	fmt.Println("ขอบคุณที่เล่น!")
}
```

รันจริง 2 รอบ (เลขลับสุ่มทุกครั้ง ผลจึงต่างกันได้):

รอบที่ 1 — ป้อน `1`, `2`, `3` แล้วพิมพ์ `q` (ตัวอย่างที่เลขลับคือ 5):

```
=== เกมทายเลข 1–10 (เวอร์ชันฟังก์ชัน) ===
ทายเลข 1–10 (พิมพ์ q เพื่อเฉลย): น้อยไป!
ทายเลข 1–10 (พิมพ์ q เพื่อเฉลย): น้อยไป!
ทายเลข 1–10 (พิมพ์ q เพื่อเฉลย): น้อยไป!
ทายเลข 1–10 (พิมพ์ q เพื่อเฉลย): เฉลย: เลขลับคือ 5
ขอบคุณที่เล่น!
```

รอบที่ 2 — ป้อน `abc` (ทดสอบกันข้อมูลเสีย) แล้วทายไล่ `1`–`10` (ตัวอย่างที่เลขลับคือ 4 — ทายถูกในครั้งที่ 4):

```
=== เกมทายเลข 1–10 (เวอร์ชันฟังก์ชัน) ===
ทายเลข 1–10 (พิมพ์ q เพื่อเฉลย): พิมพ์เป็นตัวเลขสิ (เช่น 5)
ทายเลข 1–10 (พิมพ์ q เพื่อเฉลย): น้อยไป!
ทายเลข 1–10 (พิมพ์ q เพื่อเฉลย): น้อยไป!
ทายเลข 1–10 (พิมพ์ q เพื่อเฉลย): น้อยไป!
ทายเลข 1–10 (พิมพ์ q เพื่อเฉลย): ถูกต้อง! (ลอง 4 ครั้ง)
ขอบคุณที่เล่น!
```

สังเกตว่า `main` เหลือแค่ 3 บรรทัด: พิมพ์หัวเกม → เรียก `guessGame` → พิมพ์อำลา — "เกมทั้งเกม" ถูกย้ายเข้า `guessGame` ไปเรียบร้อย ส่วน `guessGame` เองก็แบ่งงานต่ออีกชั้น: สุ่มเลขลับ (`newSecret`) และอ่านคำทายพร้อมกันข้อมูลเสีย (`readGuess`) — นี่คือ decomposition แบบลูกโซ่: ใหญ่ → กลาง → เล็ก แต่ละชั้นอ่านง่าย เข้าใจง่าย ทดสอบทีละชั้นได้

## เบื้องลึก: ตอนเรียกฟังก์ชัน คอมพิวเตอร์ "กระโดดไป กระโดดกลับ"

> **อ่านข้ามได้ — เบื้องลึกของ CPU:** ในตอน 04 เรารู้ว่าโปรแกรมทำงานทีละบรรทัด และ if/loop ที่เราเขียน พอ compile ไปแล้วกลายเป็นคำสั่ง "กระโดด" (jump) ของ CPU — ฟังก์ชันก็คือ "การกระโดดแบบมีที่กลับ": ตอนโปรแกรมเจอ `add(3, 5)` CPU จะ**จำที่อยู่ของบรรทัดถัดไปไว้** (dev เรียก return address = รีเทิร์น แอดเดรส = "ที่อยู่ที่จะกลับ") แล้วกระโดดไปรันโค้ดของ `add` พอรันถึง `return` ก็กระโดดกลับมาที่ที่จำไว้ แล้วรันต่อ — เหมือนคุณขอยืมหนังสือในห้องสมุดแล้วทิ้งที่คั่นหนังสือไว้หน้าเดิม พอคืนหนังสือก็เปิดกลับมาหน้าที่คั่นไว้ ที่เก็บ "ที่คั่น" เหล่านี้เรียงซ้อนกัน เรียกว่า call stack (คอล สแต็ก = กองซ้อนของการเรียกฟังก์ชัน) — เราจะเห็นของจริงตอน 12 (assembly) และเจาะลึกตอน 15 (stack กับ calling convention) — แต่ถ้ายังไม่พร้อม ข้ามกล่องนี้ไปก่อนได้ ไม่กระทบเนื้อหาที่เหลือ

ที่ควรจำไว้ตอนนี้คือ: **ฟังก์ชันไม่ใช่แค่เรื่อง "จัดระเบียบโค้ดให้สวย"** — มันคือกลไกที่ CPU รองรับจริง ๆ ตั้งแต่ยุคภาษาเครื่อง การที่ทุกภาษา (Go, C, ทุกภาษา) มีฟังก์ชันให้ใช้ เพราะฮาร์ดแวร์มีคำสั่ง call/return ให้อยู่แล้ว

## ตารางสรุป: ของใหม่ที่เรียนวันนี้

| คำศัพท์ | ความหมาย | ตัวอย่าง |
|---|---|---|
| ฟังก์ชัน (function) | กล่องคำสั่งมีชื่อ รับข้อมูลเข้า ทำงาน คืนผลกลับ | `func add(a int, b int) int` |
| parameter | "ช่องรับข้อมูล" ที่ประกาศในหัวฟังก์ชัน | `a`, `b` ใน `add` |
| argument | "ค่าจริง" ที่ส่งตอนเรียกฟังก์ชัน | `3`, `5` ใน `add(3, 5)` |
| return value | ค่าที่ฟังก์ชันส่งกลับ (ระบุชนิดไว้ที่หัวฟังก์ชัน) | `return a + b` |
| การเรียก (call) | สั่งให้ฟังก์ชันทำงาน เขียนชื่อ + วงเล็บ + argument | `add(3, 5)` |
| คืนหลายค่า | Go คืนได้หลายค่าพร้อมกัน คั่นด้วยลูกน้ำ | `return a / b, a % b` |
| named return value | ตั้งชื่อตัวแปรผลลัพธ์ไว้หัวฟังก์ชัน แล้ว `return` เปล่า ๆ | `(result float64)` |
| scope | ขอบเขตที่ตัวแปรมีชีวิต — ปีกกาชั้นไหนประกาศ ใช้ได้แค่ในนั้น (กับปีกกาลูก) | `verdict` ในปีกกา if |
| package-level variable | ตัวแปรประกาศนอกฟังก์ชัน ใช้ได้ทั้ง package — dev ใช้อย่างระวัง | `var appName = "..."` |
| decomposition | การแยกปัญหใหญ่เป็นปัญหาย่อย | BMI → readLine/bmi/bmiStatus |
| DRY | Don't Repeat Yourself = อย่าเขียนโค้ดซ้ำหลายที่ | เขียน readLine ครั้งเดียวใช้สองที่ |
| refactor | ปรับโครงสร้างโค้ดโดยไม่เปลี่ยนพฤติกรรม | BMI เวอร์ชันตอน 04 → เวอร์ชันฟังก์ชัน |

## กับดักยอดฮิตของมือใหม่ + error ที่จะเจอ (ทุกอันทดสอบจริง)

(สูตรเดิมจากตอน 02: `ชื่อไฟล์:เลขบรรทัด:เลขหลัก: สาเหตุ` — เลขบรรทัดใน error ของคุณอาจต่างจากของผมถ้าโค้ดต่างกัน ขอให้อ่านที่ "สาเหตุ" เป็นหลัก)

**1. ฟังก์ชันที่ประกาศว่าคืนค่า แต่มีบางเส้นทางไม่มี return**

```go
func half(n int) int {
	if n%2 == 0 {
		return n / 2
	}
	// ถ้า n เป็นเลขคี่ ตกมาถึงตรงนี้ — ไม่มี return → error
}
```

error จริง: `missing return` (Go บอกว่า "ฟังก์ชันนี้อาจจบโดยไม่ได้คืนค่า แต่เธอบอกว่าจะคืน int นะ")

วิธีแก้: ทุกเส้นทางต้องมี return — เช่น เติม `return n / 2` ข้างนอก if ด้วย หรือเขียน else

**2. เรียกฟังก์ชันโดยส่ง argument ไม่ครบ หรือส่งชนิดผิด**

```go
fmt.Println(add(1))      // add ต้องการ int 2 ตัว ให้แค่ตัวเดียว
fmt.Println(add("x", 2)) // ตัวแรกต้องเป็น int แต่ให้ string
```

error จริง:

```
not enough arguments in call to add
	have (number)
	want (int, int)
cannot use "x" (untyped string constant) as int value in argument to add
```

Go ตรวจ**จำนวนและชนิด**ของ argument ให้เราตอน compile เลย — จำนวนต้องตรงกับ parameter ทุกตัว ชนิดต้องตรง (หรือแปลงให้ตรงก่อนส่ง)

**3. return ค่าผิดชนิด**

```go
func labelBMI(bmi float64) string {
	if bmi >= 30 {
		return 999 // ผิด: ฟังก์ชันประกาศว่าคืน string แต่คืน int
	}
	return "ปกติ"
}
```

error จริง: `cannot use 999 (untyped int constant) as string value in return statement`

**4. ใช้ตัวแปรนอก scope** — ที่เราทดสอบกันไปแล้วด้านบน: `undefined: verdict` — ตัวแปรเกิดในปีกกาไหน ใช้ได้แค่ในนั้น อย่าลืมว่าการประกาศก่อนใช้ยังไม่พอ ต้องประกาศใน**ขอบเขตที่กว้างพอ**ด้วย (ดู `scopegood.go`)

### ระดับ Drill (10–15 นาที)

1. **ฟังก์ชันเช็คเลขคู่**: เขียน `func isEven(n int) bool` (คืน `true` ถ้า `n` เป็นเลขคู่ — Hint: ใช้ `%` จากตอน 03 เอาเศษ) แล้วเขียนโปรแกรมที่วนพิมพ์เลขคู่ 1–20 โดยเรียก `isEven` ใน loop
2. **ฟังก์ชันเรียกฟังก์ชัน** (decomposition ขั้นต่อไป): เขียน `func maxOf(a int, b int) int` คืนค่าที่มากกว่าระหว่างสองตัว แล้วเขียน `func maxOf3(a int, b int, c int) int` ที่**ข้างในเรียก `maxOf` ซ้ำ** (Hint: หาค่าสูงสุดของ a กับ b ก่อน แล้วเอาผลไปเทียบกับ c) — ลองสังเกตว่าโค้ดสั้นและอ่านง่ายแค่ไหน
3. **แปลงโปรแกรมเก่าของคุณเอง**: เปิด `bmi.go` (หรือ `guess.go`) ที่เขียนในตอน 04 แล้ว refactor เป็นฟังก์ชันด้วยตัวเองก่อนดูเฉลยด้านบน — เปรียบเทียบกับของผม: โครงสร้างเหมือนกันไหม? ชื่อฟังก์ชันต่างกันตรงไหน? (ไม่มีคำตอบถูกผิด — ขอแค่โค้ดรันได้และอ่านเข้าใจ)
4. **แก้โค้ดพัง**: โค้ดข้างล่าง compile ไม่ผ่านหลายจุด — หาให้ครบแล้วแก้ (Hint: มองหาตัวแปรที่ใช้ผิด scope, เรียกฟังก์ชันผิดจำนวน argument, return ผิดชนิด, และเส้นทางที่ไม่มี return):

```go
package main

import "fmt"

func double(n int) int {
	return n * 2
}

func describe(score int) string {
	if score >= 50 {
		return 100 // ผิดชนิด: describe ประกาศว่าคืน string
	}
	// ถ้า score < 50 ตกมาถึงตรงนี้ — ไม่มี return
}

func main() {
	fmt.Println(double(1, 2)) // ผิด: double รับ int แค่ตัวเดียว

	if true {
		inside := "อยู่ในปีกกา"
		fmt.Println(inside)
	}
	fmt.Println(inside) // ผิด: inside ตายไปแล้วเมื่อออกจากปีกกา if
}
```

### ระดับ Mini-project (30–60 นาที) — "โปรแกรมตรวจ BMI คนทั้งบ้าน"

เขียนโปรแกรม `family_bmi.go` ที่ถามข้อมูลทีละคนแล้วสรุปสถิติทั้งครอบครัว โดย**บังคับใช้ฟังก์ชัน**:

1. เขียน `func bmi(weight, height float64) float64` และ `func bmiStatus(b float64) string` (ลอก/เขียนจากบทความได้)
2. เขียน `func readPerson(reader *bufio.Reader) (name string, weight float64, height float64, ok bool)` — ถามชื่อ + น้ำหนัก + ส่วนสูงทีละคน แล้วคืนทั้งหมด (สังเกต: **4 ค่า** — named return value ช่วยให้โค้ดอ่านง่ายขึ้น ลองใช้ดู!) — ถ้าผู้ใช้พิมพ์ `q` ตอนถามชื่อ ให้คืน ok = false
3. ใน `main` วนเรียก `readPerson` จนกว่าจะ ok = false — แต่ละคน คำนวณ BMI + สถานะ พิมพ์ออกมา แล้ว**อัปเดตสถิติสะสม**: จำนวนคน, BMI รวม (ไว้หาค่าเฉลี่ย), ค่า BMI สูงสุด + ชื่อคนนั้น, ค่า BMI ต่ำสุด + ชื่อคนนั้น (Hint: เก็บ `bestName`, `bestBMI` ฯลฯ เริ่มจากคนแรก แล้วคนถัดไปค่อยเทียบ — ตอน 06 เราจะเรียน slice ซึ่งทำให้เก็บ "หลาย ๆ ค่า" ง่ายกว่านี้มาก แต่ตอนนี้ขอใช้ตัวแปรเดี่ยว + การเปรียบเทียบไปก่อน)
4. พิมพ์สรุปตอนจบ เช่น: "ตรวจทั้งหมด 3 คน — ค่าเฉลี่ย BMI 23.40 — สูงสุด: สมหญิง (27.10) — ต่ำสุด: สมชาย (21.50)"

**เกณฑ์ผ่าน:** โปรแกรมรันได้ กันข้อมูลเสียเหมือนโปรแกรม BMI (พิมพ์ `abc`/`NaN`/ค่าติดลบ ต้องถามใหม่ ไม่พัง) รองรับ `q` ได้ทุกจุดถาม และสรุปสถิติถูกต้อง — ทดสอบด้วยการป้อน 3–4 คน สลับลำดับให้คน BMI สูงสุด/ต่ำสุดไม่ใช่คนแรกเสมอ (จะได้การันตีว่า logic เปรียบเทียบถูกต้อง)

Hint: ลำดับการถามภายใน `readPerson` — ถามชื่อก่อน แล้วค่อยถามน้ำหนัก/ส่วนสูง (ถ้าพิมพ์ q ตอนน้ำหนัก/ส่วนสูง จะถือว่าเลิกทั้งโปรแกรมด้วย — ตัดสินใจเองแล้วเขียนให้สม่ำเสมอ)

## สรุปตอนที่ 05

- **ฟังก์ชัน = กล่องคำสั่งมีชื่อ** — ประกาศด้วย `func ชื่อ(parameters) ชนิดที่คืน { ... }` รับข้อมูลผ่าน parameter คืนผลผ่าน return — โครงสร้างเดียวกับ `func main` ที่เราเขียนมาตั้งแต่ตอน 03
- **parameter คือ "ช่องรับ" ส่วน argument คือ "ค่าที่ส่งตอนเรียก"** — dev ใช้ปนกัน แต่ความหมายต่างกัน — ฟังก์ชันเรียกด้วยชื่อ + วงเล็บ + argument จำนวน/ชนิดต้องตรงกับที่ประกาศ
- **Go คืนค่าได้หลายค่าพร้อมกัน** — `(int, int)` หรือ `(float64, bool)` — ใช้ส่งทั้ง "ผล" และ "สัญญาณ ok/ไม่ ok" ต้นแบบของคู่ (ค่า, error) ที่จะเจอเต็มรูปแบบตอน 07 — named return value คือการตั้งชื่อตัวแปรผลลัพธ์ไว้หัวฟังก์ชัน (เกริ่นให้รู้จักไว้)
- **scope = ขอบเขตของตัวแปร** — ปีกกาชั้นไหนประกาศ ใช้ได้แค่ปีกกานั้นกับปีกกาลูก — ฟังก์ชันแต่ละตัว "กันแสง" กันเอง: ตัวแปรในฟังก์ชันหนึ่งใช้ในอีกฟังก์ชันไม่ได้ ข้อมูลเดินทางผ่าน parameter/return เท่านั้น — package-level variable มี scope กว้างทั้ง package แต่ dev ใช้อย่างระมัดระวัง
- **decomposition = แบ่งปัญหาใหญ่เป็นชิ้นเล็ก** — และฟังก์ชันคือเครื่องมือแบ่ง — main ที่ดีคือ "ผู้เล่าเรื่อง" สั้น ๆ ที่เรียกฟังก์ชันย่อยตามลำดับ
- **DRY = อย่าเขียนซ้ำ** — เขียนชิ้นงานครั้งเดียว เรียกใช้หลายที่ แก้ครั้งเดียวจบ — ถ้าพบว่าตัวเองกำลัง copy โค้ดวางซ้ำ = ถึงเวลาแยกฟังก์ชัน
- **refactor = ปรับโครงสร้างโดยไม่เปลี่ยนพฤติกรรม** — โปรแกรม BMI/เกมทายเลขตอน 04 ทำงานเหมือนเดิมทุกประการ แต่ main สั้นลงหลายเท่าและอ่านง่ายขึ้น — นี่คือทักษะที่ dev ใช้ทุกวัน
- เบื้องลึก: ตอนเรียกฟังก์ชัน CPU จำ "ที่อยู่ที่จะกลับ" (return address) แล้วกระโดดไปรัน — กลไก call stack จะเจาะลึกตอน 12 และ 15

ตอนนี้คุณมีครบ 3 เสาหลักของการเขียนโปรแกรมแล้ว: ตัวแปร (ตอน 03) + การควบคุม (ตอน 04) + การแบ่งงาน (ตอนนี้) — เหลือเสาที่ 4 นั่นคือ**การเก็บข้อมูลหลายชิ้นไว้ด้วยกัน** เช่น รายชื่อคนทั้งบ้านที่ mini-project เพิ่งเจอ — การเก็บ 10 ค่าโดยใช้ตัวแปรเดี่ยว 10 ตัวมันเริ่มอึดอัดแล้วใช่ไหม? ตอนหน้าเราจะเรียน **slice, map, struct** (สไลซ์ = รายการข้อมูล, แมป = พจนานุกรม, สตรัคต์ = แบบฟอร์มข้อมูล) — เครื่องมือที่ทำให้ "ข้อมูลจำนวนมาก" กลายเป็นของง่าย และโปรแกรม BMI หลายคนจะสั้นลงอีกหลายเท่า

ระหว่างรอ อย่าลืมทำ mini-project "ตรวจ BMI คนทั้งบ้าน" แล้วลองสังเกตตัวเอง: ตอนเขียนฟังก์ชันแรก ๆ จะรู้สึก "เพิ่มขั้นตอน" แต่พอโปรแกรมใหญ่ขึ้น คุณจะเริ่มเห็นว่ามันคือสิ่งที่ทำให้โปรแกรมของคุณ**ไม่พังเมื่อโตขึ้น** — นี่คือความต่างระหว่าง "โค้ดที่รันได้" กับ "โค้ดที่อยู่รอดในโลกจริง"
