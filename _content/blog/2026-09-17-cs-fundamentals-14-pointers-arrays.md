# pointer + array: มองหน่วยความจำเป็น address (ตอนที่ 14) — CS Fundamentals: จาก 0 สู่พื้นฐานที่แท้จริง

ตอนที่ 13 เราจับ pointer ได้เป็นครั้งแรก: `&x` คือการขอ **address** (เลขที่ช่องในหน่วยความจำ) และ `*p` คือการเดินตามเลขนั้นไปเอาค่าจริง — เราเห็นด้วยตาว่า `sizeof(int) = 4` แต่ `sizeof(int *) = 8` และที่สำคัญที่สุด: **`a[i]` กับ `*(a + i)` เป็นสิ่งเดียวกัน**

ตอนนี้เราจะขยายความประโยคสุดท้ายนั้นให้ถึงก้นบึ้ง — เพราะมันคือหัวใจของ C ทั้งภาษา

คำถามที่ตอนนี้จะตอบให้ได้:

1. จริง ๆ แล้ว "ชื่อ array" กับ "pointer" เป็นของเดียวกันหรือไม่
2. ถ้าเป็นของเดียวกัน ทำไม `sizeof(a)` ได้ 12 แต่ `sizeof(p)` ได้ 8
3. ทำไมพอส่ง array เข้าฟังก์ชัน ความยาวของมันถึง "หายไป" ซะเฉย ๆ
4. ทำไม `p + 1` บางทีเลื่อน 4 ไบต์ บางทีเลื่อน 8 บางทีเลื่อน 1 ไบต์
5. `int m[2][3]` มันอยู่เรียงกันในหน่วยความจำยังไงจริง ๆ
6. ทำไมเขียนทับข้อความอย่าง `"hello"` แล้วโปรแกรมตายทันที

ทั้งหมดนี้คือเรื่องเดียวกันในมุมต่าง ๆ — และเมื่อจบตอนนี้ เราจะ **มองเห็นหน่วยความจำเป็นแถว address** ได้จริง ๆ ไม่ใช่แค่ท่องจำกฎ

## 1. array decay — ชื่อ array คือ pointer ที่ชี้ช่องแรก (ภาพที่ 1)

![array 3 ช่องในหน่วยความจำ และ pointer ที่ชี้ช่องแรก พร้อมกฎ sizeof ที่ต่างกัน](/assets/diagrams/ep14-01-array-decay.svg)

**ภาพที่ 1:** ด้านซ้ายคือตัวแปรสามก้อน — array `a` (12 ไบต์), pointer `p` (8 ไบต์) และ `&a` (8 ไบต์) · ด้านขวาคือหน่วยความจำจริงที่ทั้ง `a`, `&a[0]` และ `p` ชี้ออกไปที่ช่องแรกของ array เดียวกัน (address เดียวกันเป๊ะ)

ทวนศัพท์สองคำให้แน่นก่อนลงมือ (เราสอนไปแล้วในตอนก่อน ๆ แต่ตอนนี้จะใช้มันทุกบรรทัด):

- **array** (อาเรย์) = ช่องข้อมูลเรียงติดกันหลายช่อง แต่ละช่องมีเลขกำกับ เริ่มนับจาก 0 เราเรียกเลขนั้นว่า **index** (ดัชนี) — ถ้าไม่ระบุเป็นอย่างอื่น "ช่องที่ 0" คือ `a[0]`
- **ไบต์** (byte) = หน่วยนับที่เล็กที่สุดของหน่วยความจำ 1 ไบต์ = 8 บิต — `int` กว้าง 4 ไบต์บนเครื่องของเรา
- **decay** (ดึเคยฺ, "การสลายตัว" — ในทางเทคนิคคือ array-to-pointer conversion) = ปรากฏการณ์ที่ **ชื่อ array ถูกแปลงเป็น pointer ชี้ช่องแรกโดยอัตโนมัติ** ทันทีที่มันถูกใช้ในนิพจน์
- **นิพจน์** (expression) = ส่วนของโค้ดที่คำนวณออกมาเป็นค่าได้หนึ่งค่า เช่น `a`, `a + 1`, `n * 2` — คำนี้จะโผล่บ่อยมากในตอนนี้ เพราะ "array decay เกิดเมื่อชื่อ array ถูกใช้ใน**นิพจน์**" แปลว่า "ถูกใช้ในที่ที่ต้องได้ค่าออกมา" (รวมถึงการบวก `+ 0` ด้วย)

เขียนไฟล์ `decay.c` แบบนี้

```c
/* decay.c — ชื่อ array กับ &a[0] ให้ address เดียวกันจริงไหม และ sizeof ต่างกันยังไง
 *
 * คอมไพล์: gcc -std=c17 -Wall -Wextra -Wpedantic -o decay decay.c
 */
#include <stdio.h>

int main(void) {
    int a[3] = {10, 20, 30};
    int *p = a;                 /* ชื่อ array ในนิพจน์ = pointer ชี้ช่องแรก (array decay) */

    printf("=== 1) address: a กับ &a[0] ===\n");
    printf("a      = %p\n", (void *)a);
    printf("&a[0]  = %p\n", (void *)&a[0]);
    printf("p      = %p\n", (void *)p);
    printf("a == &a[0] ? %s\n", (a == &a[0]) ? "เท่ากัน" : "ไม่เท่ากัน");
    printf("a == p     ? %s\n", (a == p) ? "เท่ากัน" : "ไม่เท่ากัน");

    printf("\n=== 2) ช่องถัดไปห่างกันเท่าไร ===\n");
    printf("&a[0] = %p\n", (void *)&a[0]);
    printf("&a[1] = %p  (+%td ไบต์)\n", (void *)&a[1],
           (char *)&a[1] - (char *)&a[0]);   /* แปลงเป็น char * เพื่อให้ผลลบเป็นไบต์ ไม่ใช่จำนวนช่อง */
    printf("&a[2] = %p  (+%td ไบต์ จากช่องแรก)\n", (void *)&a[2],
           (char *)&a[2] - (char *)&a[0]);

    printf("\n=== 3) sizeof: 'a' คือทั้ง array ไม่ใช่ pointer ===\n");
    printf("sizeof(a)  = %zu ไบต์  (ทั้ง array = 3 ช่อง x %zu ไบต์)\n", sizeof a, sizeof(int));
    printf("sizeof(a[0]) = %zu ไบต์  (หนึ่งช่อง = int)\n", sizeof a[0]);
    printf("sizeof(p)  = %zu ไบต์  (ตัว pointer เอง บนเครื่อง 64 บิต)\n", sizeof p);
    printf("sizeof(&a) = %zu ไบต์  (ที่อยู่ของทั้ง array ก็ยังเป็น pointer)\n", sizeof &a);

    printf("\n=== 4) จุดที่ 'a' หยุดเป็น array และกลายเป็น pointer ===\n");
    printf("sizeof(a)       = %zu ไบต์  <-- ยังเป็น array อยู่\n", sizeof a);
    printf("sizeof(a + 0)   = %zu ไบต์  <-- เติมอะไรก็ได้ เท่ากับ +0 มันก็กลายเป็น pointer แล้ว\n",
           sizeof(a + 0));
    printf("sizeof(*a)      = %zu ไบต์  <-- *a คือช่องแรก (int หนึ่งตัว)\n", sizeof *a);
    printf("*(a + 1)        = %d        <-- เท่ากับ a[1]\n", *(a + 1));
    printf("a[1]            = %d\n", a[1]);
    printf("ค่าของ *p หลัง p = p + 2: ");
    p = p + 2;                  /* เลื่อน 2 ช่อง = 2 x 4 = 8 ไบต์ */
    printf("*p = %d (คือ a[2])\n", *p);

    return 0;
}
```

> **สองอย่างที่เพิ่งโผล่ในโค้ดนี้** — `(char *)` คือการ **แปลงชนิด pointer** (cast) ให้เป็น "pointer ไป `char`" เพื่อให้ผลลบของ pointer ออกมาเป็น **ไบต์** ไม่ใช่จำนวนช่อง · ส่วน `%td` คือ format สำหรับผลลบ pointer (ชนิด `ptrdiff_t`) ทั้งคู่จะอธิบายเต็ม ๆ ในหัวข้อ 4 — ตรงนี้ให้อ่านผ่านตาไปก่อนได้เลย

รันแล้วได้ผลแบบนี้ (ผลจริงจากการรันบนเครื่อง ARM64 ของเรา)

```
=== 1) address: a กับ &a[0] ===
a      = 0x7fffc0881418
&a[0]  = 0x7fffc0881418
p      = 0x7fffc0881418
a == &a[0] ? เท่ากัน
a == p     ? เท่ากัน

=== 2) ช่องถัดไปห่างกันเท่าไร ===
&a[0] = 0x7fffc0881418
&a[1] = 0x7fffc088141c  (+4 ไบต์)
&a[2] = 0x7fffc0881420  (+8 ไบต์ จากช่องแรก)

=== 3) sizeof: 'a' คือทั้ง array ไม่ใช่ pointer ===
sizeof(a)  = 12 ไบต์  (ทั้ง array = 3 ช่อง x 4 ไบต์)
sizeof(a[0]) = 4 ไบต์  (หนึ่งช่อง = int)
sizeof(p)  = 8 ไบต์  (ตัว pointer เอง บนเครื่อง 64 บิต)
sizeof(&a) = 8 ไบต์  (ที่อยู่ของทั้ง array ก็ยังเป็น pointer)

=== 4) จุดที่ 'a' หยุดเป็น array และกลายเป็น pointer ===
sizeof(a)       = 12 ไบต์  <-- ยังเป็น array อยู่
sizeof(a + 0)   = 8 ไบต์  <-- เติมอะไรก็ได้ เท่ากับ +0 มันก็กลายเป็น pointer แล้ว
sizeof(*a)      = 4 ไบต์  <-- *a คือช่องแรก (int หนึ่งตัว)
*(a + 1)        = 20        <-- เท่ากับ a[1]
a[1]            = 20
ค่าของ *p หลัง p = p + 2: *p = 30 (คือ a[2])
```

### 1.1 อ่านผลลัพธ์ให้เป็น: คำตอบของคำถาม "เป็นของเดียวกันไหม"

**คำตอบคือ "เป็นของเดียวกันตอนใช้งาน แต่ไม่ใช่ของเดียวกันตอนวัดขนาด"** — และนี่คือจุดที่คนใหม่สับสนมากที่สุดในภาษา C ขอแยกเป็นสามข้อ

**ข้อ 1) address เท่ากันจริง** — `a`, `&a[0]` และ `p` พิมพ์ออกมา `0x7fffc0881418` เหมือนกันหมด และ `a == &a[0]` ให้ผลเป็น "เท่ากัน" ตัวเลข `0x...` คือ **เลขฐานสิบหก** (hexadecimal — เลขฐาน 16 ซึ่งเราเรียนไปแล้วในตอนที่ 8 · ทำไมต้องฐาน 16 เพราะเขียนสั้นกว่าฐาน 10 และจับคู่ตรงกับบิตได้ลงตัว) ส่วน `&a[0]` ก็คือการขอ address ของ "ช่องที่ 0" นั่นเอง

**ข้อ 2) แต่ `sizeof` เปิดโปงความจริง** — `sizeof(a)` ได้ **12 ไบต์** (คือ *ทั้ง array* = 3 ช่อง × 4 ไบต์) ขณะที่ `sizeof(p)` ได้ **8 ไบต์** (คือ *ตัว pointer* เอง ซึ่งเก็บ address ยาว 8 ไบต์บนเครื่อง 64 บิต — เรื่องนี้เราพูดไปแล้วในตอน 13)

พูดอีกแบบ: **ถ้า `a` เป็น pointer เฉย ๆ จริง ๆ มันต้องได้ 8 ไบต์** ที่มันได้ 12 ไบต์เพราะ compiler ยังจำได้ว่า `a` คือ array ที่มี 3 ช่อง — แต่ความรู้นั้นหายไปทันทีที่ `a` ถูกใช้ในนิพจน์ (ดูข้อ 3)

จะเห็นได้ชัดจากบรรทัดนี้ (สองบรรทัดล่างนี้เป็น **ผลลัพธ์ที่โปรแกรมพิมพ์ออกมา** ไม่ใช่โค้ด — อย่าลอกไปคอมไพล์)

```
sizeof(a)       = 12 ไบต์  <-- ยังเป็น array อยู่
sizeof(a + 0)   = 8 ไบต์  <-- เติมอะไรก็ได้ เท่ากับ +0 มันก็กลายเป็น pointer แล้ว
```

แค่ `+ 0` (บวกศูนย์!) ก็เปลี่ยนความหมายแล้ว — เพราะการบวกทำให้ `a` ต้อง "ถูกใช้ในนิพจน์" จึงเกิด decay ขึ้น

**ข้อ 3) `&a` กับ `a` ไม่เหมือนกัน — ต่างกันที่ "ชนิด"** จุดนี้ลึกขึ้นหนึ่งชั้น และเป็นกับดักที่วิศวกรที่ทำงานจริงยังพลาดกัน

- `a` (หลัง decay) มีชนิดเป็น `int *` = "pointer ที่ชี้ไปช่องหนึ่งช่อง (ช่องละ `int`)"
- `&a` มีชนิดเป็น `int (*)[3]` = "pointer ที่ชี้ไปที่ **array ทั้งก้อน** (3 ช่อง)"

ทั้งสองให้ address เดียวกัน แต่ **"หนึ่งช่อง" ของมันไม่เท่ากัน** ลองรัน `type_ok.c` (โปรแกรมเต็มอยู่ใน `course/code/ep14/type_ok.c`)

```c
int *p = a;          /* a decay เป็น int * (ชี้ไป "ช่อง") */
int (*pa)[3] = &a;   /* &a คือ int (*)[3] (ชี้ไป "ทั้ง array") — วงเล็บจำเป็น */
```

ผลการรันจริง

```
a และ &a ให้ address เดียวกัน: a = 0x7fffc1bce300, &a = 0x7fffc1bce300
p  = 0x7fffc1bce300

sizeof(*p)  = 4 ไบต์  (p ชี้ไปช่อง เดียว: int)
sizeof(*pa) = 12 ไบต์  (pa ชี้ไปทั้ง array 3 ช่อง)
(*pa)[2]    = 30
pa[0][1]    = 20  (เขียนแบบไม่ต้องมีวงเล็บก็อ่านได้)

(char *)(p + 1)  - (char *)p  = 4 ไบต์
(char *)(pa + 1) - (char *)pa = 12 ไบต์  (ข้ามทั้ง array 3 ช่อง)
```

อ่านบรรทัดท้ายให้ดี: `p + 1` เลื่อน **4 ไบต์** (ไปช่องถัดไป) แต่ `pa + 1` เลื่อน **12 ไบต์** (ข้าม array ทั้งก้อนไปเลย) — address เริ่มต้นเดียวกัน ชนิดต่างกันแค่นิดเดียว พฤติกรรมต่างกันคนละเรื่อง

และถ้าเราเผลอเอา `&a` ไปใส่ตัวแปรชนิด `int *` compiler จะไม่ยอม — นี่คือโปรแกรม `type_mismatch.c` ที่ **ตั้งใจ** ให้ผิด (โปรแกรมเต็มอยู่ใน `course/code/ep14/type_mismatch.c`)

```c
int *p = &a;    /* ตั้งใจให้ผิด */
```

ข้อความจริงจากหน้าจอ (คัดลอกทั้งดุ้น รวมเลขบรรทัด)

```
type_mismatch.c: In function ‘main’:
type_mismatch.c:11:14: error: initialization of ‘int *’ from incompatible pointer type ‘int (*)[3]’ [-Wincompatible-pointer-types]
   11 |     int *p = &a;    /* ตั้งใจให้ผิด: &a มีชนิดเป็น "pointer to array of 3 int" ไม่ใช่ "pointer to int" */
      |              ^
```

**นี่ไม่ใช่ warning แต่เป็น error — คอมไพล์ไม่ผ่านเลย** (`-Wincompatible-pointer-types` กลายเป็น error โดยค่าเริ่มต้นใน GCC 14) ข้อความบอกตรง ๆ ว่า "ชนิด pointer ไม่เข้ากัน" พร้อมชี้ชนิดที่ถูกต้องให้ในวงเล็บ

เคล็ดลับอ่านชนิด: `int (*pa)[3]` — **วงเล็บ**รอบ `*pa` สำคัญมาก ถ้าไม่มีวงเล็บ `int *pa[3]` จะแปลว่า "array 3 ช่อง ที่แต่ละช่องเก็บ `int *`" (คนละเรื่องกันเลย) — เป็นอีกเหตุผลที่เราต้องอ่านโค้ด C จากในออกนอก ไม่ใช่ซ้ายไปขวา

**สรุปหัวข้อ 1 เป็นตารางเดียว**

| สิ่งที่เขียน | ชนิดจริง | `sizeof` | เลื่อน `+1` เท่าไร | ใช้ยังไง |
|---|---|---|---|---|
| `a` | `int[3]` → decay เป็น `int *` | 12 ไบต์ (ทั้ง array) | 4 ไบต์ | เข้าถึงช่องด้วย `a[i]` หรือ `*(a + i)` |
| `&a[0]` | `int *` | 8 ไบต์ | 4 ไบต์ | เหมือน `a` ทุกอย่าง |
| `p` (คือ `int *p = a;`) | `int *` | 8 ไบต์ | 4 ไบต์ | pointer ที่ย้ายที่ได้ (`p = p + 1`) |
| `&a` | `int (*)[3]` | 8 ไบต์ (`*&a` = 12) | 12 ไบต์ | ใช้กับ array ของ array, ส่งทั้งก้อนเข้าฟังก์ชัน |

## 2. ส่ง array เข้าฟังก์ชัน = ส่ง pointer (ภาพที่ 2)

![ส่ง array เข้าฟังก์ชันคือส่ง pointer ขนาด array จึงหายไป และคำเตือนจริงจาก GCC](/assets/diagrams/ep14-02-array-param-pointer.svg)

**ภาพที่ 2:** ฝั่งซ้าย (`main`) มี array 3 ช่อง = 12 ไบต์อยู่ในมือ · สิ่งที่ส่งข้ามไปคือ **address ของช่องแรก** (8 ไบต์) เท่านั้น · ฝั่งขวา (`sum`) จึงไม่รู้เลยว่า array ยาวเท่าไร จนกว่าจะมีใครบอก

นี่คือคำถามที่มือใหม่ถามบ่อยมาก: "ทำไมใน Go เขียน `len(a)` ได้ แต่ใน C ต้องส่งความยาวมาด้วยทุกครั้ง?"

คำตอบสั้น: **เพราะใน C เราไม่ได้ส่ง array ไป — เราส่งแค่ที่อยู่ของมัน**

เขียนไฟล์ `array_param.c` (โปรแกรมเต็มอยู่ใน `course/code/ep14/array_param.c` — นี่คือส่วนสำคัญ)

```c
/* สามประกาศนี้ "ความหมายเดียวกันเป๊ะ" — compiler มองเป็น int *arr ทุกตัว
 * เลข 3 ใน int arr[3] ไม่มีผลอะไรเลย (แค่บอกคนอ่านว่าตั้งใจรับ 3 ช่อง) */
static int sum_bracket(int arr[], int n) {
    /* บรรทัดล่างนี้คือ "หลักฐาน" ว่า arr กลายเป็น pointer ไปแล้ว:
       ถ้ามันยังเป็น array จริง การกำหนดให้ int * จะต้องได้ warning — แต่นี่ไม่มีเลย */
    int *q = arr;
    printf("  ใน sum_bracket: sizeof(q) = %zu ไบต์ (ขนาด pointer ไม่ใช่ขนาด array จริง)\n",
           sizeof q);
    int total = 0;
    for (int i = 0; i < n; i++) {
        total += arr[i];
    }
    return total;
}

static int sum_pointer(int *arr, int n) { /* เนื้อในเหมือนกันเป๊ะกับข้างบน */ }

static int sum_fixed(int arr[3], int n) {   /* เลข 3 นี้ถูก compiler มองข้าม */
    int *r = arr;
    printf("  ใน sum_fixed  : sizeof(r) = %zu ไบต์ (ยังเป็น pointer อยู่ดี)\n", sizeof r);
    /* ...บวกค่าทั้งหมด... */
}
```

### 2.1 สามอย่างที่โปรแกรมนี้พิสูจน์ให้เราเห็น

**อย่างที่ 1: `int arr[]`, `int *arr` และ `int arr[3]` เป็นชนิดเดียวกันทั้งหมด** — ทั้งสามตัวรับ array ก้อนเดียวกันได้เหมือนกัน และข้างในก็ได้ `sizeof` = 8 ไบต์เหมือนกันหมด (ตามมาตรฐานภาษา C ตัวรับที่ประกาศเป็น array จะถูกปรับเป็น pointer ให้ทันที — เลข `3` ที่เขียนไว้ไม่ถูกนำมาใช้เลย) ฉะนั้นถ้าจะเขียนให้คนอ่านเข้าใจว่าฟังก์ชันนี้ต้องการ array ให้เขียนอย่างไหนก็ได้ แต่ **ต้องส่งความยาวแยกมาด้วยเสมอ**

**อย่างที่ 2: คอมไพเลอร์เตือนเราเองถ้าเราเผลอ** — ลองเขียนฟังก์ชันที่เอา `sizeof` ไปใช้กับตัวรับโดยตรง (`sizeof_param_warn.c` — โปรแกรมเต็มอยู่ใน `course/code/ep14/sizeof_param_warn.c`)

```c
static void show_size(int arr[], int n) {
    (void)n;
    printf("sizeof(arr) ในฟังก์ชัน = %zu ไบต์ (ทั้งที่ผู้เรียกมี 100 ช่อง = 400 ไบต์)\n",
           sizeof arr);
}
```

คำเตือนจริงจาก GCC (คัดลอกทั้งดุ้น)

```

   14 |            sizeof arr);
      |                   ^~~
sizeof_param_warn.c:11:27: note: declared here
   11 | static void show_size(int arr[], int n) {
      |                       ~~~~^~~~~
```

อ่านข้อความให้ครบ: *"'sizeof' on array function parameter 'arr' will return size of 'int *'"* = "การเรียก `sizeof` บนตัวรับที่เป็น array จะคืนขนาดของ `int *`" — GCC ไม่ได้แค่เตือน มันอธิบายสาเหตุให้เลยด้วย และมี **note** ชี้กลับไปบรรทัดที่ประกาศฟังก์ชันให้เราดู (`declared here`) นี่คือตัวอย่างที่ดีของคำเตือนที่มีประโยชน์ — **warning คือเพื่อน ไม่ใช่ศัตรู** ส่วน `-Wsizeof-array-argument` ที่เห็นในวงเล็บเหลี่ยมคือ **ชื่อคำเตือนนี้เอง (ไม่ใช่ชื่อธงที่ต้องสั่งเปิด)** — GCC **เปิดให้อยู่แล้วโดยค่าเริ่มต้น** ของโปรแกรม C/C++ ลองคอมไพล์โดยไม่ใส่ `-Wall -Wextra` เลยก็ยังได้คำเตือนนี้ (เราเพิ่งลองบนเครื่องจริง: ได้เหมือนกันเป๊ะ)

รันโปรแกรมนี้ดูผลจริง

```
sizeof(big) ใน main    = 400 ไบต์
sizeof(arr) ในฟังก์ชัน = 8 ไบต์ (ทั้งที่ผู้เรียกมี 100 ช่อง = 400 ไบต์)
```

array 100 ช่อง (400 ไบต์) กลายเป็น pointer 8 ไบต์ในทันทีที่ข้ามเข้าไปในฟังก์ชัน — **นี่คือรอยต่อที่ข้อมูล "ขนาด" หายไป** และเป็นเหตุผลว่าทำไมภาษา C ทุกวันนี้ยังมีบั๊กที่เกิดจาก "ส่งขนาดผิด" หรือ "ลืมส่งขนาด" อยู่เรื่อย ๆ

**อย่างที่ 3: เพราะส่งไปแค่ address ฟังก์ชันจึงแก้ข้อมูลตัวจริงได้** — บรรทัด `หลังเรียก double_all: 20 40 60` คือหลักฐาน: ฟังก์ชัน `double_all(int *arr, int n)` เขียนทับ array ของ `main` ได้จริง **เพราะไม่มีอะไรถูกคัดลอกเลย** (สังเกตว่าตรงนี้กลับกันกับตอนที่ 13 ที่เราส่งตัวแปรเดี่ยว ๆ เข้าฟังก์ชันแล้วการแก้ไม่มีผล — เพราะตัวแปรเดี่ยวถูกคัดลอกค่า แต่ array ส่งแค่ที่อยู่)

> **หมายเหตุที่ต้องฝังหัว** — ขอแยกเป็นสามข้อสั้น ๆ จะได้จำง่าย:
>
> - **ฟังก์ชันไม่รู้ขนาด array** ถ้าเราส่ง `n` ผิด (array มี 3 ช่องแต่ส่ง `n = 5`) ฟังก์ชันจะเดินไปอ่าน/เขียน "ช่องที่ 4, 5" ที่ไม่ใช่ของ array
> - อาการนี้เรียกว่า **ออกนอกขอบเขต** (out-of-bounds) และตามมาตรฐานภาษา C มันคือ **พฤติกรรมไม่นิยาม** (undefined behavior = พฤติกรรมที่มาตรฐานไม่รับประกันว่าโปรแกรมจะทำอะไร — อาจได้ค่าขยะ อาจทับตัวแปรอื่น อาจดูเหมือนทำงานถูกไปอีกครึ่งปีแล้วค่อยพัง)
> - **Go เลือกทางอื่น** — Go บังคับให้ใช้ slice ที่พาความยาวมาด้วย จึงไม่เปิดช่องนี้เลย (แต่ก็แลกด้วยต้นทุนที่ต้องมี — เราจะเห็นเต็ม ๆ ในตอน 16)

## 3. เดินผ่าน array ด้วย pointer

ตอนนี้เรารู้แล้วว่า array ส่งเข้าไปเป็น pointer ได้ ก็ถึงเวลาใช้มันให้เป็นประโยชน์: **การเดินผ่าน array ด้วย pointer arithmetic**

**pointer arithmetic** (การบวก/ลบเลขกับ pointer) = `p + 1` แปลว่า "เลื่อนไป**หนึ่งช่อง**" **ไม่ใช่** "บวกหนึ่งไบต์" — หนึ่งช่องกว้างเท่าไรมาจาก**ชนิด**ที่ pointer ชี้ออกไป (เรื่องเต็มอยู่ในหัวข้อ 4)

เขียนไฟล์ `walk.c` (โปรแกรมเต็มอยู่ใน `course/code/ep14/walk.c`) — นี่คือสามเครื่องมือที่เราจะใช้จริงตลอดอาชีพ: ผลรวม, หาค่ามากสุด, และกลับด้าน

```c
/* หาผลรวมด้วยการเดิน pointer: ตั้งแต่ begin ถึง end (end ไม่รวม) */
static int sum_walk(const int *begin, const int *end) {
    int total = 0;
    for (const int *p = begin; p < end; p++) {
        total += *p;
    }
    return total;
}

/* หาค่ามากสุด แล้วคืน pointer ที่ชี้ไปยังช่องนั้น (ชี้ NULL ถ้าไม่มีข้อมูล) */
static const int *max_walk(const int *begin, const int *end) {
    if (begin == end) {
        return NULL;                 /* ไม่มีข้อมูลเลย */
    }
    const int *best = begin;
    for (const int *p = begin + 1; p < end; p++) {
        if (*p > *best) {
            best = p;
        }
    }
    return best;
}

/* กลับด้าน array ในที่ (in-place) — ไม่ใช้ array ช่วย แล้วจึงไม่กินหน่วยความจำเพิ่ม */
static void reverse_in_place(int *begin, int *end) {
    while (begin < end) {
        int tmp = *begin;
        *begin = *end;
        *end = tmp;
        begin++;
        end--;
    }
}

/* ... ฟังก์ชัน show() ที่พิมพ์ array ออกจอ ตัดออกตรงนี้ ... */

int main(void) {
    int a[6] = {4, 8, 15, 16, 23, 42};
    const int n = 6;

    /* เดินถอยหลังด้วย pointer: ตั้ง p ไว้ที่ a + n ("เลยช่องท้ายไปหนึ่ง") แล้วถอยก่อนอ่าน
       เขียนแบบนี้เพื่อเลี่ยงการสร้าง a - 1 ซึ่งเป็น pointer ที่ออกนอก array = พฤติกรรมไม่นิยาม */
    for (const int *p = a + n; p != a; ) {
        --p;
        printf("%d%s", *p, (p == a) ? "\n" : " ");
    }

    /* ... ผลรวม, หาค่ามากสุด, reverse_in_place(a, a + n - 1) และเทียบกับลูปแบบ index ... */
    return 0;
}
```

> **โค้ดข้างบนตัดมาเฉพาะส่วนสำคัญ** — โปรแกรมเต็ม (ทั้งไฟล์ 80 บรรทัด) อยู่ที่ `course/code/ep14/walk.c`

คำที่เพิ่งโผล่มา 2 คำ อธิบายตรงนี้เลย:

- **`const int *`** (อ่านว่า "pointer to const int") = pointer ที่ **อ่านได้อย่างเดียว** ห้ามเขียนทับค่าที่มันชี้อยู่ — เป็นวิธีบอกเพื่อนร่วมงานและ compiler ว่า "ฟังก์ชันนี้จะไม่แก้ข้อมูลของเธอ" (เรา **ควร** ใส่ `const` ทุกครั้งที่ฟังก์ชันมีหน้าที่แค่อ่าน — มันช่วยจับบั๊กให้ตั้งแต่ตอนคอมไพล์)
- **in-place** (อ่านว่า "อินเพลส" = "ทำในที่เดิม") = แก้ข้อมูลชุดเดิมให้กลายเป็นผลลัพธ์เลย โดยไม่จองหน่วยความจำก้อนใหม่ — การกลับด้านแบบนี้ใช้ตัวแปรชั่วคราวแค่ `tmp` ตัวเดียว ไม่ว่าจะมีกี่ล้านช่อง

ผลการรันจริง

```
array ตั้งต้น     : 4 8 15 16 23 42
ผลรวม (walk)     : 108
ค่ามากสุด (walk) : 42  ที่ช่องที่ 5 (นับจาก 0)
เดินถอยหลังจากช่องท้าย: 42 23 16 15 8 4
ก่อน reverse     : 4 8 15 16 23 42
หลัง reverse     : 42 23 16 15 8 4
ผลรวม (index)    : 108  (เท่ากับแบบ pointer: เท่ากัน)
```

### 3.1 สี่แบบของการไล่ array (เทียบให้เห็นชัด ๆ)

| แบบ | เขียนยังไง | ใช้เมื่อไร |
|---|---|---|
| ไล่ด้วย index | `for (int i = 0; i < n; i++) total += a[i];` | อ่านง่ายที่สุด — ใช้เป็นค่าเริ่มต้นเสมอถ้าไม่ติดเรื่องประสิทธิภาพจริง ๆ |
| ไล่ด้วย pointer จาก `begin` ถึง `begin + n` | `for (int *p = a; p < a + n; p++) total += *p;` | เมื่อต้องรู้ address ของช่องปัจจุบันด้วย (เช่นส่งต่อให้ฟังก์ชันอื่น) |
| ไล่ด้วย pointer จาก `begin` ถึง `end` (แบบไม่ต้องรู้ `n` ในลูป) | `for (const int *p = begin; p < end; p++) total += *p;` | รูปแบบที่ห้องสมุดมาตรฐานของ C ใช้ทั้งภาษา (`begin` = "ช่องแรก", `end` = "ช่องที่ **เลยช่องสุดท้ายไปหนึ่ง**") |
| ไล่ถอยหลัง | `for (p = a + n; p != a; ) { --p; ... }` | กลับด้าน, ประมวลผลจากท้าย — เขียนแบบนี้เลี่ยง `a - 1` ที่เป็นพฤติกรรมไม่นิยาม |

**จุดที่ต้องเข้าใจให้ถูก: ทำไม `end` ถึงเป็น "เลยช่องสุดท้ายไปหนึ่ง"?**

ถ้า array มี 6 ช่อง (`a[0]`…`a[5]`) แล้วเราส่ง `a + 6` เป็น `end` — `a + 6` **ไม่ใช่ address ของข้อมูลจริง** มันคือ address "ถัดจากช่องสุดท้าย" (ตามมาตรฐานภาษา C อนุญาตให้สร้าง pointer ที่ "เลยท้ายไปหนึ่งช่อง" ได้ แต่ **ห้าม dereference** เด็ดขาด) และเพราะมันไม่ใช่ข้อมูลจริง เลข `end - begin` จึงเท่ากับจำนวนช่องพอดีเป๊ะ (6) — สังเกตว่าต้องเป็น `end` ลบ `begin` ไม่ใช่กลับกัน

การเขียนแบบ `begin`/`end` แบบนี้เป็นจารีตที่ทำให้ **array ว่าง** ทำงานได้โดยไม่ต้องเขียนเงื่อนไขพิเศษ: ถ้า array ว่าง `begin == end` แล้วลูปไม่ทำงานเลยแม้แต่รอบเดียว (โปรแกรมของเราเช็ค `begin == end` ใน `max_walk` เพื่อคืน `NULL` = pointer ว่าง · `NULL` คือค่าพิเศษที่หมายถึง "ไม่ชี้ที่ไหน" ซึ่งเราเจอในเรื่อง `malloc` ของตอน 13)

**กับดักสามข้อที่ต้องระวัง**

1. `p < end` กับ `p <= end` ให้ผลต่างกันคนละโลก — ถ้าใช้ `<=` ลูปจะเข้าไปหนึ่งรอบที่ `p == end` แล้ว dereference `*p` ซึ่งเป็น "ช่องที่ไม่มีข้อมูล" → พฤติกรรมไม่นิยามทันที
2. การเปรียบเทียบ pointer สองตัว (`p < end`) มีความหมาย **เฉพาะเมื่อทั้งคู่ชี้อยู่ใน array เดียวกัน** เท่านั้น — ถ้าเทียบ pointer ที่มาจาก array คนละก้อน compiler ไม่เตือน และผลลัพธ์ไม่มีความหมายเลย
3. ระวัง **การเดินถอยหลัง**: ลูปแบบ `for (p = a + n - 1; p >= a; p--)` ดูไม่ผิด แต่มันต้องสร้าง `a - 1` หนึ่งครั้งตอนจบรอบสุดท้าย — และ `a - 1` เป็น pointer ที่**ออกนอก array** = พฤติกรรมไม่นิยาม วิธีที่ปลอดภัยคือตั้ง `p = a + n` (เลยช่องท้ายไปหนึ่ง) แล้วถอยก่อนอ่านแบบที่อยู่ใน `walk.c`

## 4. pointer arithmetic กับชนิดข้อมูล (ภาพที่ 3)

![p+1 เลื่อนกี่ไบต์ขึ้นกับชนิดที่ pointer ชี้ออกไป](/assets/diagrams/ep14-03-pointer-arith-by-type.svg)

**ภาพที่ 3:** ชนิดเดียวกันของการเขียน `p + 1` แต่ได้ผลต่างกัน — `int *` เลื่อน 4 ไบต์, `double *` เลื่อน 8 ไบต์, `char *` เลื่อน 1 ไบต์ เพราะ "หนึ่งช่อง" ของแต่ละชนิดกว้างไม่เท่ากัน

คำถามสำคัญ: **แล้ว C รู้ได้ยังไงว่าต้องเลื่อนกี่ไบต์?** คำตอบมาจากตอนที่ 13 ตรง ๆ — เพราะ pointer **มีชนิด** และชนิดนั้นบอกขนาดของช่อง

เขียนไฟล์ `ptr_sizes.c` (โปรแกรมเต็มอยู่ใน `course/code/ep14/ptr_sizes.c`)

```c
/* วิธีวัดว่า p+1 เลื่อนไปกี่ไบต์: แปลงเป็น char * (ช่องละ 1 ไบต์) แล้วลบกัน */
printf("int    * : &pi[0] = %p -> &pi[1] = %p  = +%td ไบต์\n",
       (void *)&pi[0], (void *)&pi[1],
       (char *)(pi + 1) - (char *)pi);
```

> **โค้ดข้างบนตัดมาเฉพาะส่วนสำคัญ** (ที่นี่เอาเฉพาะบรรทัดของ `int *` มาให้ดู) — โปรแกรมเต็มอยู่ที่ `course/code/ep14/ptr_sizes.c`

เทคนิคในบรรทัดนี้คุ้มค่าที่จะจำ: `(char *)` คือการ **แปลง pointer เป็นชนิด `char *`** ซึ่ง "หนึ่งช่อง" กว้าง 1 ไบต์พอดี — พอแปลงแล้วลบกัน เราได้ผลต่างเป็น **จำนวนไบต์จริง ๆ** (ถ้าไม่แปลง ลบ pointer ตรง ๆ จะได้เป็น "จำนวนช่อง" ซึ่งมีหน่วยต่างกัน)

ผลการรันจริง

```
sizeof: int = 4, double = 8, char = 1 ไบต์
sizeof ของ pointer เอง: int* = 8, double* = 8, char* = 8 ไบต์

int    * : &pi[0] = 0x7fffdcfd5f90 -> &pi[1] = 0x7fffdcfd5f94  = +4 ไบต์
double * : &pd[0] = 0x7fffdcfd5f80 -> &pd[1] = 0x7fffdcfd5f88  = +8 ไบต์
char   * : &pc[0] = 0x7fffdcfd5f78 -> &pc[1] = 0x7fffdcfd5f79  = +1 ไบต์

ยืนยันด้วยค่าที่อ่านได้หลังเลื่อน:
*(pi + 1) = 2
*(pd + 1) = 2.5
*(pc + 1) = B

&ai[1] - &ai[0] = 1  <-- ผลลบ pointer ได้ 'จำนวนช่อง'
(char *)&ai[1] - (char *)&ai[0] = 4 ไบต์  <-- แปลงเป็น char * ก่อนจึงได้เป็นไบต์
&ad[1] - &ad[0] = 1  <-- จำนวนช่องเท่าเดิม แม้ชนิดจะกว้างกว่า
```

อ่านสามบรรทัดสุดท้ายให้ดี เพราะมันคือความเข้าใจที่คนส่วนใหญ่พลาด:

- `&ai[1] - &ai[0]` = **1** (ไม่ใช่ 4!) เพราะผลลบของ pointer สองตัวคือ **จำนวนช่อง** ไม่ใช่จำนวนไบต์ — และถึงแม้จะเป็น `double` ที่กว้าง 8 ไบต์ `&ad[1] - &ad[0]` ก็ยังได้ 1 เพราะ "หนึ่งช่องของ double" คือหนึ่งช่อง
- `(char *)&ai[1] - (char *)&ai[0]` = **4** เพราะเราแปลงเป็น `char *` ก่อน (ทำให้ "หนึ่งช่อง" = 1 ไบต์) ผลลบจึงกลายเป็นหน่วยไบต์
- และ `sizeof ของ pointer` = 8 ไบต์ **เท่ากันทั้งหมด** — `int *`, `double *`, `char *` กินที่เท่ากัน เพราะข้างในเก็บแค่เลข address (ตัวเลข 8 ไบต์) ไม่ได้เก็บตัวข้อมูลจริง ๆ พร้อมขนาด

**แบบฝึกการอ่านโค้ด:** `p + 1` อ่านว่า "ไปยัง **ช่องถัดไป**ของชนิดที่ p ชี้อยู่" ไม่ใช่ "บวก 1 ไบต์" — เราจึงควรอ่านมันเป็นภาษาไทยว่า "เลื่อนไปหนึ่งช่อง" ตลอด

ตารางสรุปที่ควรจำ (บนเครื่อง ARM64 ของเรา)

| ชนิดที่ pointer ชี้ | `sizeof` ของชนิด | `p + 1` เลื่อนไป | เขียนเป็นจำนวนไบต์ |
|---|---|---|---|
| `char` | 1 ไบต์ | 1 ไบต์ | `p + 1` = +1 |
| `int` | 4 ไบต์ | 4 ไบต์ | `p + 1` = +4 |
| `double` | 8 ไบต์ | 8 ไบต์ | `p + 1` = +8 |
| `int *` (pointer ไป int) | 8 ไบต์ | 8 ไบต์ | `p + 1` = +8 |

และอีกเรื่องที่ต้องรู้สำหรับการอ่านโค้ดของคนอื่น: **ผลลบของ pointer มีชนิดชื่อ `ptrdiff_t`** (อยู่ในไฟล์ `<stddef.h>`) จึงต้องพิมพ์ด้วย `%td` ไม่ใช่ `%d` — ถ้าใช้ผิดเครื่องหมาย compiler จะเตือนเรื่อง format string (เราจะเจอเรื่อง format string เต็ม ๆ ในตอนที่ 16)

## 5. array หลายมิติ: `int m[2][3]` วางเรียงยังไง (ภาพที่ 4)

![int m[2][3] เรียงในหน่วยความจำแบบ row-major พร้อม address ของทุกช่อง](/assets/diagrams/ep14-04-matrix-row-major.svg)

**ภาพที่ 4:** 6 ช่องเรียงติดกันเป็นเส้นเดียว — แถว 0 สามช่องก่อน แล้วต่อด้วยแถว 1 สามช่อง ไม่มีที่ว่างคั่น และไม่มี "ตาราง" จริง ๆ อยู่ในหน่วยความจำ

เวลาคิดถึง `int m[2][3]` ภาพในหัวของมือใหม่คือตาราง 2 แถว 3 คอลัมน์ — ซึ่งถูกในทางคณิตศาสตร์ แต่ **ผิดในทางหน่วยความจำ** ของจริงคือ 6 ช่องเรียงกันเป็นเส้นตรง แล้ว C แค่คำนวณที่อยู่ให้เราจากเลขแถวกับเลขคอลัมน์ วิธีเรียงแบบนี้เรียกว่า **row-major order** (เรียงทีละแถว — จบแถวหนึ่งก่อน แล้วค่อยขึ้นแถวถัดไป) และมันคือวิธีที่ C ใช้ (ภาษา Go ก็ใช้แบบเดียวกัน)

คำว่า **multi-dimensional array** (array หลายมิติ) จริง ๆ แล้วในภาษา C มันคือ **array ของ array** — ไม่มีของวิเศษอะไรเพิ่มมาเลย

เขียนไฟล์ `matrix.c` (โปรแกรมเต็มอยู่ใน `course/code/ep14/matrix.c`)

```c
int m[2][3] = {
    {1, 2, 3},     /* แถว 0 */
    {4, 5, 6},     /* แถว 1 */
};

printf("sizeof(m)       = %zu ไบต์ (2 แถว x 3 ช่อง x %zu)\n", sizeof m, sizeof(int));
printf("sizeof(m[0])    = %zu ไบต์ (หนึ่งแถว = 3 ช่อง)\n", sizeof m[0]);
printf("sizeof(m[0][0]) = %zu ไบต์ (หนึ่งช่อง)\n", sizeof m[0][0]);
printf("จำนวนแถว = %zu, จำนวนคอลัมน์ = %zu\n\n",
       sizeof m / sizeof m[0], sizeof m[0] / sizeof m[0][0]);

for (int r = 0; r < 2; r++) {
    for (int c = 0; c < 3; c++) {
        ptrdiff_t off = (char *)&m[r][c] - (char *)&m[0][0];
        printf("&m[%d][%d] = %p  (ห่างจากช่องแรก +%td ไบต์)  ค่า = %d\n",
               r, c, (void *)&m[r][c], off, m[r][c]);
    }
}
```

> **โค้ดข้างบนตัดมาเฉพาะส่วนสำคัญ** (เฉพาะส่วนที่วัดขนาดและเดินดู address) — โปรแกรมเต็มอยู่ที่ `course/code/ep14/matrix.c`

ในโค้ดข้างบนมีสองบรรทัดที่ควรอ่านให้ดี: `sizeof m / sizeof m[0]` = **จำนวนแถว** และ `sizeof m[0] / sizeof m[0][0]` = **จำนวนคอลัมน์** — เป็นสูตรมาตรฐานของ C ที่ใช้หาขนาด array หลายมิติโดยไม่ต้องพิมพ์ตัวเลขเอง (เราเอาไปใช้ซ้ำในโจทย์ drill ข้อ 5 ด้านล่าง)

ผลการรันจริง

```
sizeof(m)       = 24 ไบต์ (2 แถว x 3 ช่อง x 4)
sizeof(m[0])    = 12 ไบต์ (หนึ่งแถว = 3 ช่อง)
sizeof(m[0][0]) = 4 ไบต์ (หนึ่งช่อง)
จำนวนแถว = 2, จำนวนคอลัมน์ = 3

=== address ของทุกช่อง (เรียงติดกันจากบนลงล่าง) ===
&m[0][0] = 0x7fffd1099828  (ห่างจากช่องแรก +0 ไบต์)  ค่า = 1
&m[0][1] = 0x7fffd109982c  (ห่างจากช่องแรก +4 ไบต์)  ค่า = 2
&m[0][2] = 0x7fffd1099830  (ห่างจากช่องแรก +8 ไบต์)  ค่า = 3
&m[1][0] = 0x7fffd1099834  (ห่างจากช่องแรก +12 ไบต์)  ค่า = 4
&m[1][1] = 0x7fffd1099838  (ห่างจากช่องแรก +16 ไบต์)  ค่า = 5
&m[1][2] = 0x7fffd109983c  (ห่างจากช่องแรก +20 ไบต์)  ค่า = 6

m[1][2]                = 6
*(*(m + 1) + 2)        = 6  (เขียนด้วย pointer ล้วน)
(*(m + 1))[2]          = 6
m[1] + 2 -> *(m[1] + 2) = 6

&m[1] - &m[0] = 1  <-- ผลลบของ pointer ไป 'แถว' ได้จำนวนแถว
ขนาดหนึ่งแถวเป็นไบต์: (char *)&m[1] - (char *)&m[0] = 12 ไบต์

=== เดินแบบแบน (flat) ด้วย pointer ช่อง ===
flat[0] = 1 (ที่ +0 ไบต์)  flat[1] = 2 (ที่ +4 ไบต์)  flat[2] = 3 (ที่ +8 ไบต์)  flat[3] = 4 (ที่ +12 ไบต์)  flat[4] = 5 (ที่ +16 ไบต์)  flat[5] = 6 (ที่ +20 ไบต์)
flat[4] เท่ากับ m[1][1] ? ใช่ (ค่าคือ 5)
```

### 5.1 อ่านผลลัพธ์ให้เป็น: สูตรที่ compiler ใช้จริง

**หลักฐานว่าเรียงเป็นเส้นเดียว:** address ของทั้ง 6 ช่องห่างกันทีละ 4 ไบต์เท่ากันหมด ไม่มี "กระโดด" ตอนข้ามแถว (จาก `m[0][2]` ไป `m[1][0]` ก็ยังห่าง 4 ไบต์เท่าเดิม) — และ `&m[1][0]` อยู่ที่ +12 ไบต์ ซึ่งเท่ากับ 3 ช่องแรกพอดี

**สูตรคำนวณที่อยู่** (นี่คือสิ่งที่ compiler ทำแทนเราทุกครั้งที่เขียน `m[r][c]`) — คำว่า **offset** ในสูตรแปลว่า "ระยะห่างเป็นไบต์จากจุดเริ่มต้น" (คือจากช่องแรกสุด `m[0][0]`)

```
offset (ไบต์) = (แถว x จำนวนคอลัมน์ + คอลัมน์) x sizeof(ช่อง)
m[1][2]  ->  (1 x 3 + 2) x 4 = 5 x 4 = 20 ไบต์   (ตรงกับผลรันจริง: +20 ไบต์)
```

**ชื่อ array แต่ละชั้นมีชนิดไม่เหมือนกัน** — นี่คือส่วนที่ลึกที่สุดของหัวข้อนี้ และเป็นเหตุผลเดียวกับหัวข้อ 1

| สิ่งที่เขียน | ชนิด | "หนึ่งช่อง" ของมัน | เลื่อน +1 |
|---|---|---|---|
| `m` | `int[2][3]` → decay เป็น `int (*)[3]` (pointer ไป "หนึ่งแถว") | หนึ่งแถว = 12 ไบต์ | +12 ไบต์ |
| `m[0]` (หรือ `m[1]`) | `int *` (pointer ไป "หนึ่งช่อง") | หนึ่งช่อง = 4 ไบต์ | +4 ไบต์ |
| `m[0][0]` | `int` | — | — |

หลักฐานจากผลรัน: `&m[1] - &m[0] = 1` (นับเป็น "แถว") แต่ `(char *)&m[1] - (char *)&m[0] = 12 ไบต์` — เหมือนกับคู่ `p`/`pa` ในหัวข้อ 1 เป๊ะ แค่ซ้อนขึ้นมาอีกชั้น

**แล้ว `m[1][2]` ที่เราเขียนสบาย ๆ นั่น compiler มองเป็นอะไร?** มันคือ

```c
*(*(m + 1) + 2)
```

อ่านจากในออกนอก: `m + 1` = "แถวที่ 1" (เลื่อน 12 ไบต์) → `*(m + 1)` = "แถวนั้นทั้งแถว" ซึ่งพอใช้ในนิพจน์ก็ decay เป็น pointer ไปช่องแรกของแถว → `+ 2` = "ช่องที่ 2 ของแถว" (เลื่อน 8 ไบต์) → `*` ตัวหน้าก็คือ "ค่าที่ช่องนั้น"

เพราะฉะนั้น **`m[1][2]` กับ `*(*(m + 1) + 2)` เป็นสิ่งเดียวกันจริง ๆ** — ซึ่งเรายืนยันด้วยการรันมาแล้ว (ทั้งคู่ได้ 6) เหมือนกับที่ `a[2]` กับ `*(a + 2)` เป็นสิ่งเดียวกันในหัวข้อ 1

**เดินแบบแบน (flat)** — เพราะทุกช่องเรียงติดกัน เราจึงเอา pointer ไปที่ช่องแรกสุด (`&m[0][0]`) แล้วเดินต่อเนื่องทีละช่องได้เลย (`flat[4]` = `m[1][1]` = 5 ตามผลรัน) วิธีนี้ใช้บ่อยในงานจริง (เช่นการอ่านข้อมูลจากไฟล์ หรือการประมวลผลภาพที่เก็บเป็นตาราง) **แต่ต้องรู้จำนวนช่องทั้งหมดเอง** — และเช่นเคย ถ้าเดินเกิน 6 ช่องเมื่อไร = พฤติกรรมไม่นิยามทันที

**ส่ง array หลายมิติเข้าฟังก์ชัน** — จุดนี้ต้องบอกตรง ๆ เพราะมันคือกับดักที่คนเขียน C มือใหม่เจ็บทุกคน

```c
void f(int m[2][3]);   /* ความหมายจริงคือ void f(int (*m)[3]) — "จำนวนแถว" หายไป */
```

จำนวนแถว (2) หายไปเหมือนกับทุกครั้ง แต่ **จำนวนคอลัมน์ (3) ไม่หาย** เพราะมันเป็นส่วนหนึ่งของชนิด `int (*)[3]` — ฉะนั้นฟังก์ชันที่รับ array หลายมิติต้องรู้จำนวนคอลัมน์ตั้งแต่ตอนคอมไพล์

สำหรับ array ที่รู้ขนาดตอนรัน (เช่นอ่านข้อมูลจากไฟล์มาไม่รู้ล่วงหน้ากี่แถว) ทางที่ยืดหยุ่นกว่าคือส่ง `int *flat` + `rows` + `cols` แล้วคำนวณ offset เอง (`n` ที่เราส่งในหัวข้อ 2 ก็คือแนวคิดเดียวกัน) — นี่คือโจทย์ท้าทายข้อ 4 ของ mini-project ด้านล่าง

## 6. `char *` — ข้อความใน C คือ pointer (ภาพที่ 5)

![เทียบ char array ที่แก้ได้ กับ pointer ไปข้อความคงที่ที่ห้ามแก้](/assets/diagrams/ep14-05-string-literal-vs-array.svg)

**ภาพที่ 5:** ทั้งสองแบบพิมพ์ออกมาเป็น "hello" เหมือนกัน แต่ตัวอักษรอยู่คนละที่ในหน่วยความจำ — แบบซ้ายเป็น array ของเราบน **stack** (แก้ได้) แบบขวาเป็น pointer ไปยังข้อความที่ compiler เตรียมไว้ให้ (แก้ไม่ได้) — *stack* คือพื้นที่หน่วยความจำชั่วคราวของฟังก์ชันที่กำลังทำงาน (เป็นเนื้อหาหลักของตอน 15)

เราปูไว้แล้วในตอน 13 ว่า **C ไม่มีชนิด `string` ในตัว** สิ่งที่ C มีคือ array ของ `char` ที่ปิดท้ายด้วยไบต์ `'\0'` — ตอนนี้เรามีเครื่องมือครบพอจะเข้าใจมันจริง ๆ แล้ว

เขียนไฟล์ `strings.c` (โปรแกรมเต็มอยู่ใน `course/code/ep14/strings.c`)

```c
/* นับความยาวข้อความเองด้วยการเดิน pointer (เวอร์ชันของเราเอง ไม่ใช้ strlen) */
static size_t my_strlen(const char *s) {
    const char *p = s;
    while (*p != '\0') {        /* เดินไปเรื่อย ๆ จนเจอไบต์ปิดท้าย */
        p++;
    }
    return (size_t)(p - s);     /* จำนวนช่องที่นับได้ = ความยาว */
}

int main(void) {
    char  t[] = "hello";        /* รวม 6 ช่อง (5 ตัวอักษร + '\0') อยู่ใน array ของเราเอง (แก้ได้) */
    const char *s = "hello";    /* pointer ชี้ไปยังข้อความที่ compiler เก็บไว้ให้ (ห้ามแก้) */
    /* ... */
}
```

สามคำใหม่ที่ควรรู้:

- **`size_t`** = ชนิดจำนวนเต็ม "ไม่มีเครื่องหมายลบ" ที่ใช้แทน **ขนาด/ความยาว** (เป็นชนิดเดียวกับที่ `sizeof` คืนออกมา) — ฟังก์ชันนับความยาวจึงคืน `size_t` ไม่ใช่ `int` และพิมพ์ด้วย `%zu`
- **`strlen`** = ฟังก์ชันมาตรฐานใน `<string.h>` ที่ **ทำหน้าที่เดียวกับ `my_strlen` เป๊ะ** (ไล่อ่านจนเจอ `'\0'`) — เราเขียนเองเพื่อให้เห็นกลไกข้างใน แต่ในงานจริงให้ใช้ `strlen` ของมาตรฐาน (เร็วกว่าและผ่านการทดสอบมามากกว่า)
- **`'\0'`** อ่านว่า "null character" = ตัวอักษรที่มีค่ารหัส 0 (คนละตัวกับ `'0'` ที่มีรหัส 48) — มันคือเครื่องหมาย "ข้อความจบตรงนี้" ที่ทุกข้อความในภาษา C ต้องมี

ผลการรันจริง

```
=== สองแบบนี้ต่างกันตรงไหน ===
t (array) : sizeof(t) = 6 ไบต์  (5 ตัว + '\0' 1 ตัว)
s (pointer): sizeof(s) = 8 ไบต์  (แค่ตัว pointer ไม่นับตัวอักษร)

text ของ t = hello (ที่ 0x7ffffe119ea0)
text ของ s = hello (ที่ 0x5555dfbb0a60)
address ต่างกัน ? ต่างกัน — คนละที่ในหน่วยความจำ
ข้อความเท่ากันไหม (เทียบทีละตัวอักษร) ? เท่ากัน

=== เดินอ่านข้อความด้วย pointer ===
'h' (รหัส 104) ที่ 0x5555dfbb0a60
'e' (รหัส 101) ที่ 0x5555dfbb0a61
'l' (รหัส 108) ที่ 0x5555dfbb0a62
'l' (รหัส 108) ที่ 0x5555dfbb0a63
'o' (รหัส 111) ที่ 0x5555dfbb0a64

my_strlen("") = 0 (ข้อความว่าง)

```

### 6.1 สองสิ่งที่ผลลัพธ์นี้บอก (และมันสำคัญกว่าที่คิด)

**เรื่องที่ 1: `sizeof` ต่างกันเพราะมันคือของคนละแบบ**

- `char t[] = "hello";` → `sizeof(t)` = **6** (ตัวอักษร 5 + `'\0'` 1) — เพราะ `t` เป็น **array** ที่มีที่ของตัวเองบน **stack** (stack = พื้นที่หน่วยความจำชั่วคราวของฟังก์ชันที่กำลังทำงาน · เรื่องนี้เป็นเนื้อหาหลักของตอน 15)
- `const char *s = "hello";` → `sizeof(s)` = **8** — เพราะ `s` เป็นแค่ **pointer** ไม่ได้เป็นเจ้าของตัวอักษรเลย

และสังเกต address: `0x7ffffe119ea0` (ของ `t`) อยู่คนละช่วงกับ `0x5555dfbb0a60` (ของ `s`) อย่างเห็นได้ชัด — เพราะ **"hello" ที่เขียนในโค้ด** ถูก compiler เก็บไว้ในส่วนของโปรแกรมที่สงวนไว้สำหรับค่าคงที่ (ส่วนนี้เป็น **read-only** = อ่านได้อย่างเดียว เขียนไม่ได้) ส่วน `t` เป็นตัวแปรธรรมดาที่เกิดตอนโปรแกรมรัน จึงอยู่ใน stack

**เรื่องที่ 2: เขียนทับข้อความคงที่ = โปรแกรมตายทันที** ลองโปรแกรมนี้ (`literal_write.c` — โปรแกรมเต็มอยู่ใน `course/code/ep14/literal_write.c` และ **เป็นโปรแกรมที่ตั้งใจให้ผิด** ตามมาตรฐานภาษา C)

```c
const char *s = "hello";   /* ข้อความคงที่ — compiler เก็บไว้ในส่วนที่ห้ามเขียน */
char *w = (char *)s;       /* cast ทิ้ง const เพื่อให้ compiler ยอมให้คอมไพล์ */
w[0] = 'H';                /* ตั้งใจเขียนทับ */
```

แต่ทำไมต้องมี `(char *)s` ด้วยล่ะ? เพราะถ้าไม่ cast แล้วเขียน `s[0] = 'H';` ตรง ๆ (บน `const char *s`) compiler จะ**ปฏิเสธตั้งแต่ยังไม่ทันรัน** ด้วย error `assignment of read-only location '*p'` (โปรแกรมสาธิตตัวนี้อยู่ใน `literal_const_reject.c`) — `const` คือ **ด่านแรก** ที่กันไว้ตอนคอมไพล์ และการ cast ก็คือการขอ "ข้ามด่านแรก" ไป

คำว่า **`(char *)s`** ที่เห็นคือการ **cast** (แปลงชนิด) — เรากำลังบอก compiler ว่า "ฉันรู้ว่ากำลังทำอะไรอยู่" ทั้งที่ความจริงเราไม่รู้ และผลลัพธ์จริงคือ

```
ก่อนแก้: s = hello (ที่ 0x5555594308b0)
Segmentation fault
```

(บรรทัด `Segmentation fault` เป็นข้อความที่ **shell** รายงานว่ามันสั่งหยุดโปรแกรมให้ · ตัวโปรแกรมเองไม่ได้พิมพ์อะไรเพิ่มเลย)

โปรแกรมตายทันทีที่เขียนตัวอักษรตัวแรกทับ เราเรียกอาการนี้ว่า **segfault** (ย่อจาก "segmentation fault") = โปรแกรมถูก **ระบบปฏิบัติการ** สั่งหยุดกลางทางทันที เพราะไปแตะหน่วยความจำที่ไม่มีสิทธิ์เขียน · กลไกที่ระบบสั่งหยุดแบบนี้เรียกว่า **สัญญาณ** (signal = ข้อความที่ระบบปฏิบัติการส่งให้โปรเซสเพื่อสั่งให้หยุด) เช็คได้จากรหัสจบงาน

```bash
$ echo $?
139        # $? = รหัสจบงานของคำสั่งล่าสุด · 139 = 128 + 11 (สัญญาณหมายเลข 11 = SIGSEGV)
```

บทเรียนที่ต้องฝังหัว: **กติกาของ C ไม่ได้บังคับด้วย compiler อย่างเดียว** — compiler ยอมให้เราทำลายข้อตกลงของตัวเองได้ (เพราะมันจำเป็นในงานระดับต่ำจริง ๆ) แต่ **ระบบปฏิบัติการไม่ยอม** นี่คือหน้าตาของ "ความปลอดภัยที่ C ไม่มีให้" ที่เราพูดถึงในตอน 13 — และเป็นเหตุผลที่การ cast ทิ้ง `const` ต้องมีเหตุผลที่หนักแน่นกว่าคำว่า "compiler ด่า"

> ถ้าอยากแก้ข้อความให้ได้จริง ให้ประกาศเป็น array: `char t[] = "hello";` แล้ว `t[0] = 'H';` — ทำงานได้ตามผลรัน (`t = Hello`) เพราะตัวอักษรก๊อปปี้มาไว้ในที่ของเราเองตั้งแต่เริ่มโปรแกรม

**แบบฝึกที่ควรทำทันที:** ลองเปิด `strings.c` แล้วเปลี่ยน `my_strlen` ให้เดิน **ถอยหลัง** จากตัวสุดท้าย (ใบ้: ต้องหา pointer ไปยัง `'\0'` ก่อน แล้วนับถอยหลัง) — ยังไม่ต้องแก้โค้ดจริง แค่คิดตามให้ออกก็พอ แล้วเราจะเฉลยในโจทย์ mini-project

## 7. เทียบกับ Go: ทำไมเรื่องนี้ Go ยังต้องมี แต่เล่าไม่เหมือนกัน

ตอนที่ 13 เราบอกว่า Go ห้ามบวก address — แต่นั่นยังไม่ใช่ทั้งหมดของเรื่อง array/pointer ขอยกตัวอย่าง Go ที่รันจริงบนเครื่อง (โปรแกรมเต็มอยู่ใน `course/code/ep14/go_arrays.go`)

```go
// รับ array "เป็นค่า" — มีการคัดลอกทั้งก้อน ไม่ใช่ส่ง pointer
func doubleCopy(a [3]int) {
	a[0] = a[0] * 2
	fmt.Println("  ใน doubleCopy (array ที่ถูกคัดลอก):", a)
}

// รับ slice — ส่งผ่าน "ตัวอ้างอิง" พร้อมความยาว ข้อมูลตัวจริงจึงถูกแก้
func doubleSlice(s []int) {
	for i := range s {
		s[i] = s[i] * 2
	}
}
```

รันจริงได้

```
array a = [10 20 30]  len = 3
  ใน doubleCopy (array ที่ถูกคัดลอก): [20 20 30]
หลังเรียก doubleCopy(a): a = [10 20 30]  (ไม่เปลี่ยน — ถูกคัดลอก)
หลังเรียก doubleSlice(a[:]): a = [20 40 60]  (เปลี่ยน — ส่งผ่านตัวอ้างอิง)
sumArray(a) = 120
หลัง *p = 99 (p := &a[0]): [99 40 60]
```

จุดที่ต่างจาก C อย่างชัดเจน:

1. **array ของ Go ส่งเข้าไปแล้วถูก "คัดลอกทั้งก้อน"** (`doubleCopy` แก้ค่าข้างในได้ แต่ผู้เรียกไม่เห็นการเปลี่ยนแปลง) — ตรงข้ามกับ C ที่ array decay แล้วส่งไปแค่ address **นี่คือความต่างที่ทำให้คนเขียน Go งงเวลาเจอบั๊กใน C และกลับกัน**
2. **Go ไม่มีการ decay** — `a` ใน Go ยังเป็น array เต็มตัว ใช้ `len(a)` ได้เสมอ (ถ้าใน C เขียน `len(a)` ก็ต้องส่ง `n` มาจากผู้เรียกเอง)
3. **slice ของ Go พาความยาวมาด้วย** (`len(s)`) จึงไม่ต้องส่ง `n` แยก และ Go จะ **panic** ทันทีถ้าเราเข้าถึงเกินขอบเขต (ใน C เรื่องเดียวกันจบด้วยพฤติกรรมไม่นิยาม — บทเรียนจากเรื่องนี้จะเข้มขึ้นในตอน 16)
4. **Go ยังมี `&a[0]` และ `*p` เหมือน C** — แต่ห้าม `p + 1` เด็ดขาด (compiler ฟ้อง `invalid operation: p + 1 (mismatched types *int and untyped int)` ตามที่เราพิสูจน์มาแล้วในตอน 13) งานที่ C ทำด้วยการเลื่อน pointer Go ให้เขียนเป็น index หรือ `for range`

**สรุปตารางเดียว: "งานเดียวกัน ทำคนละแบบ"**

| งาน | C | Go |
|---|---|---|
| เข้าถึงช่องที่ i | `a[i]` หรือ `*(a + i)` | `a[i]` (เท่านั้น) |
| รู้ความยาว array ในฟังก์ชัน | ต้องส่ง `n` มาเอง | `len(a)` / `len(s)` |
| ส่ง array เข้าฟังก์ชัน | ส่ง address (แก้ตัวจริงได้) | array = คัดลอก · slice = อ้างอิง |
| เดินผ่านข้อมูล | เลื่อน pointer ได้ | ใช้ `for i := range s` |
| เขียนเกินขอบเขต | พฤติกรรมไม่นิยาม (เงียบ ๆ) | panic ทันที |
| จัดการหน่วยความจำเอง | `malloc` / `free` | GC |

## 9. โจทย์ฝึก (2 ระดับ)

### ระดับ 1 — drill (ฝึกความแม่นยำ)

ตอบทุกข้อ **โดยยังไม่รันโปรแกรม** แล้วค่อยรันตรวจ (ทักษะ "ทำนายก่อนรัน" คือทักษะที่แยกวิศวกรเก่งออกจากคนที่แค่พิมพ์ตามได้ — และในตอนนี้มันฝึกได้ตรง ๆ เพราะเรามีเครื่องมือวัดขนาดในมือ)

1. `int a[5];` — `sizeof(a)`, `sizeof(p)` (โดย `int *p = a;`), `sizeof(a + 0)`, `sizeof(*a)` ได้เท่าไรบ้าง
2. `double d[4];` — `&d[3]` ห่างจาก `&d[0]` กี่ไบต์ และ `d + 3` เลื่อนไปกี่ไบต์
3. `char s[] = "abc";` — `sizeof(s)` กับ `strlen(s)` ได้เท่ากันไหม เพราะอะไร
4. ฟังก์ชัน `void show_size(int arr[3])` — ข้างใน `sizeof(arr)` ได้เท่าไร (`int` = 4 ไบต์) และถ้าผู้เรียกมี array 100 ช่องแล้วฟังก์ชันเขียน `arr[99]` จะปลอดภัยไหม
5. `int m[3][4];` — `sizeof(m)` เท่าไร และ `&m[2][1]` ห่างจาก `&m[0][0]` กี่ไบต์ (ลองใช้สูตรในหัวข้อ 5.1)
6. `const char *p = "hi";` กับ `char t[] = "hi";` — `sizeof` ของทั้งสองต่างกันเท่าไร และถ้าเขียน `p[0] = 'H';` จะเกิดอะไรขึ้น

**เฉลย** (ยืนยันด้วยการรันจริง — โปรแกรม `drill_check.c` อยู่ใน `course/code/ep14/drill_check.c`)

```
ข้อ 1: sizeof(int a[5]) = 20 ไบต์, sizeof(a + 0) = 8 ไบต์, sizeof(*a) = 4 ไบต์
ข้อ 2: &d[0] ถึง &d[3] ห่างกัน 24 ไบต์ และ d + 3 เลื่อนไป 24 ไบต์
   (sizeof(d) = 32 ไบต์, sizeof(double) = 8 ไบต์)
ข้อ 3: sizeof(s) = 4 ไบต์ แต่ strlen(s) = 3 (ต่างกัน 1 เพราะไบต์ปิดท้าย '\0')
ข้อ 4: main มี array 100 ช่อง = 400 ไบต์ (100 ช่อง)
ข้อ 4: sizeof(arr) ในฟังก์ชัน = 8 ไบต์เสมอ (ไม่ว่า main จะมีกี่ช่อง)
   (โปรแกรมตรวจวัดผ่าน int *q = arr; — ค่าเดียวกัน และเลี่ยงคำเตือน -Wsizeof-array-argument)
ข้อ 5: sizeof(int m[3][4]) = 48 ไบต์, &m[2][1] ห่างจาก &m[0][0] = 36 ไบต์
   สูตร: (แถว x คอลัมน์ + คอลัมน์) x sizeof(int) = (2 x 4 + 1) x 4 = 36 ไบต์
   sizeof(m) / sizeof(m[0]) = 3 แถว, sizeof(m[0]) / sizeof(m[0][0]) = 4 คอลัมน์
ข้อ 6: sizeof(const char *p) = 8 ไบต์, sizeof(char t[]) = 3 ไบต์
```

คำอธิบายข้อที่คนพลาดบ่อย:

- **ข้อ 3** — ต่างกัน 1 เสมอสำหรับข้อความที่มีตัวอักษรจริง เพราะ `sizeof` นับ "ที่ที่ต้องใช้" (รวม `'\0'`) แต่ `strlen` นับ "ความยาวของข้อความ" (ไม่นับ `'\0'`)
- **ข้อ 4** — คำตอบคือ **8 ไบต์** และไม่มีทางที่ฟังก์ชันจะรู้จัก `n` ได้ด้วยตัวเอง (ไม่ว่า array จะ 3 ช่องหรือ 100 ช่อง) ข้อสองเป็นกับดักสำคัญ: **ไม่ปลอดภัย** ถ้าผู้เรียกลืมบอกความยาว (เราต้องส่ง `n` เสมอ) — และถ้าเขียน `arr[99]` บน array ที่ไม่มี 100 ช่องจริง มันจะไปทับข้อมูลของตัวแปรอื่นแบบเงียบ ๆ (นี่คือ **buffer overflow** ที่เราจะเรียนเต็ม ๆ ในตอน 16)
- **ข้อ 5** — สูตรให้สี: `(2 × 4 + 1) × 4 = 36` ไบต์ ซึ่งตรงกับที่วัดได้จริงในโปรแกรม — และเกร็ดที่ต้องแยกให้ออกคือ `sizeof(m) / sizeof(m[0])` ได้จำนวนแถว แต่ `sizeof(m[0]) / sizeof(m[0][0])` ได้จำนวนคอลัมน์
- **ข้อ 6** — `p` เป็น pointer (8 ไบต์) แต่ `t` เป็น array (3 ไบต์) ส่วน `p[0] = 'H'` บน `const char *p` นั้น **คอมไพล์ไม่ผ่าน** (`assignment of read-only location`) เพราะ `const` กันไว้ตั้งแต่ตอนคอมไพล์ — ถ้า cast ทิ้ง `const` ก่อน (`((char *)p)[0] = 'H';`) จึงจะคอมไพล์ผ่าน แล้วค่อย **segfault ตอนรัน** (ตามที่สาธิตในหัวข้อ 6.1 ด้วย `literal_const_reject.c` และ `literal_write.c`) ส่วน `t[0] = 'H'` ทำได้ปกติ

### ระดับ 2 — mini-project: "กล่องเครื่องมือ pointer" (`ep14_toolbox.c`)

โจทย์: เขียนโปรแกรม C ที่มีฟังก์ชัน 3 ตัว ทำงาน **ด้วย pointer walk ล้วน** — ห้ามใช้ `[]` ในฟังก์ชันเหล่านี้เลย (ให้ใช้แค่ `*p`, `p++`, `p - q`)

ข้อกำหนด:

1. `size_t my_strlen(const char *s)` — นับความยาวข้อความจนเจอ `'\0'` (แบบเดียวกับในหัวข้อ 6)
2. `const int *my_max(const int *begin, const int *end)` — คืน pointer ไปยังช่องที่มีค่ามากสุด และคืน `NULL` ถ้าไม่มีข้อมูลเลย
3. `void my_reverse(int *begin, int *end)` — กลับด้าน array **in-place** โดย `end` ชี้ช่องสุดท้ายจริง ๆ (ไม่ใช่ "เลยช่องสุดท้าย") — เขียนให้แก้ array ที่มี 6 ช่องได้ และ **ใช้ตัวแปรชั่วคราวได้แค่ตัวเดียว**
4. `main()` ต้องทดสอบทั้งสามตัวกับข้อมูลนี้
   - `int a[6] = {4, 8, 15, 16, 23, 42};`
   - `const char *word = "havebit";`
   - และทดสอบ **กรณีว่าง** ด้วย: `my_max(a, a)` ต้องคืน `NULL` และ `my_reverse(a, a - 1)`… **ข้อนี้ให้คิดก่อน** ว่า array ว่างควรส่งอะไรเข้าไปถึงจะไม่พัง
5. คอมไพล์ด้วย `gcc -std=c17 -Wall -Wextra -Wpedantic` — **ต้องไม่มี warning** และห้ามจองหน่วยความจำ (`malloc`) เลยทั้งโปรแกรม

ผลลัพธ์ที่ต้องได้ (ตรวจได้เองทีละบรรทัด)

```

my_strlen("")        = 0
ค่ามากสุดใน a = 42 ที่ช่องที่ 5 (นับจาก 0)  -> &a[5] - a = 5
my_max บน array ว่าง คืน NULL ? ใช่

```

**ท้าทายเพิ่ม (ข้อ 6-8)**

6. เขียน `int sum_flat(const int *m, int rows, int cols)` ที่รับ pointer ไปช่องแรกสุดของ matrix แล้วบวกทุกช่องแบบแบน แล้วเรียกด้วย `int mm[2][3]` — จงอธิบายว่า **ทำไมต้องเขียน `sum_flat(&mm[0][0], 2, 3)` ไม่ใช่ `sum_flat(mm, 2, 3)`** (ใบ้: ชนิดของ `mm` หลัง decay คืออะไร — ดูตารางในหัวข้อ 5.1)
7. เปลี่ยน `my_strlen` ให้เดิน **ถอยหลัง** (จากตัวสุดท้ายย้อนมาช่องแรก) แล้วพิสูจน์ว่าได้ผลเท่าเดิม — ต้องหา pointer ไปที่ `'\0'` ก่อนด้วยการเดินหน้า (ใบ้: `while (*p) p++;` แล้วเดิน `p--` นับไปเรื่อย ๆ จนกลับถึง `s`)

## สรุป

ตอนนี้เราเปิด "สองหน้าตา" ของหน่วยความจำ — หน้าหนึ่งคือ array (ข้อมูลเรียงติดกัน) อีกหน้าคือ pointer (เลขที่ช่อง) — และเห็นว่ามันเป็นของเดียวกันในมุมต่าง ๆ เก็บหัวข้อที่ต้องจำให้ครบ:

- **array decay** = ชื่อ array ถูกแปลงเป็น pointer ชี้ช่องแรกโดยอัตโนมัติเมื่อใช้ในนิพจน์ จึงเป็นจริงทั้ง `a == &a[0]` และ `*(a + i) == a[i]`
- **แต่ `a` ไม่ใช่ pointer เฉย ๆ** — `sizeof(a)` = 12 ไบต์ (ทั้ง array) ขณะที่ `sizeof(p)` = 8 ไบต์ (ตัว pointer) และ `sizeof(a + 0)` = 8 เพราะแค่ `+ 0` ก็เกิด decay แล้ว
- **`a` กับ `&a` address เท่ากันแต่ชนิดต่างกัน** — `int *` กับ `int (*)[3]` · `p + 1` เลื่อน 4 ไบต์ แต่ `pa + 1` เลื่อน 12 ไบต์ และ compiler **ไม่ยอม** ให้สลับกัน (error `-Wincompatible-pointer-types`)
- **ส่ง array เข้าฟังก์ชัน = ส่ง pointer** — `int arr[]`, `int *arr`, `int arr[3]` เป็นชนิดเดียวกันทั้งหมด ขนาดหายไปตรงรอยต่อนี้ จึงต้อง **ส่งความยาว `n` แยกเสมอ** และการแก้ข้อมูลในฟังก์ชันมีผลกับตัวจริง (เพราะไม่มีการคัดลอก)
- **เดินผ่าน array ด้วย pointer** — `for (p = begin; p < end; p++)` เป็นจารีตของ C (พร้อม `const` เมื่ออ่านอย่างเดียว) และ `begin == end` ทำให้กรณี "ไม่มีข้อมูล" ทำงานได้เองโดยไม่ต้องเขียนเงื่อนไขพิเศษ
- **`p + 1` เลื่อนเป็น "ช่อง" ตามชนิด** — `char` +1, `int` +4, `double` +8 ไบต์ · ส่วน **ผลลบของ pointer ได้ "จำนวนช่อง"** (พิมพ์ด้วย `%td`) ถ้าอยากได้เป็นไบต์ต้องแปลงเป็น `char *` ก่อน
- **array หลายมิติคือ 6 ช่องเรียงเป็นเส้นเดียว** (row-major) — `m[1][2]` จริง ๆ คือ `*(*(m + 1) + 2)` และจำนวนคอลัมน์เป็นส่วนหนึ่งของชนิด (ส่งเข้าฟังก์ชันแล้วไม่หาย) ส่วนจำนวนแถวหาย จึงต้องบอกจำนวนแถวเอง
- **ข้อความใน C คือ `char *`** — `char t[] = "hello"` เป็น array ของเรา (แก้ได้ · `sizeof` = 6) แต่ `const char *s = "hello"` เป็น pointer ไปข้อความคงที่ (**แก้ไม่ได้** · `sizeof` = 8) — เขียนทับแล้วได้ **segfault** (exit 139) ตรง ๆ
- **Go ใช้คำศัพท์เดียวกันแต่กติกาต่าง** — array ของ Go ถูก **คัดลอก** ตอนส่งเข้าไป, `len()` มีให้เสมอ, slice พาความยาวมาด้วย, และไม่มี pointer arithmetic ให้ใช้เลย

สองข้อที่ตอนนี้ **ทิ้งไว้ค้าง** และจะเฉลยในตอนถัดไป: (1) ตัวแปรแต่ละตัวอยู่ตรงไหนของหน่วยความจำ — ช่วงที่เราเห็นว่า `t` กับ `s` อยู่คนละช่วงกันนั่นแหละ (stack กับ heap = พื้นที่ที่ขอเพิ่มได้ตอนรัน) และ (2) เวลาส่ง argument เข้าฟังก์ชัน มัน "เดินทาง" ไปยังไงถึงได้คัดลอกค่าให้บางอย่าง แต่ส่ง address ให้บางอย่าง

ตอนต่อไปเราจะเปิดผ่าหน่วยความจำจริง ๆ: **stack กับ heap และ calling convention** (calling convention = ธรรมเนียมการเรียกฟังก์ชันว่า argument เดินทางยังไง) — เราจะเห็นว่าทำไมตัวแปรท้องถิ่นถึง "เกิดที่ stack", `malloc` ไปเอาเนื้อที่จากที่ไหน, และเวลาฟังก์ชันถูกเรียก เกิดอะไรขึ้นกับ address เหล่านั้น

## ภาคผนวกท้ายบท (ข้ามได้)

- **address ในบทความนี้จะไม่เหมือนเดิมถ้ารันเอง** — เราพูดถึงเรื่องนี้ในตอน 13 แล้ว (กลไก **ASLR** = การสุ่มตำแหน่งหน่วยความจำ) ทุกครั้งที่รัน โปรแกรมจะได้ตำแหน่งใหม่ ตัวเลข `0x7fff...` และ `0x5555...` ที่เห็นจึงเป็นของ "การรันครั้งนั้น" เท่านั้น — **ขนาดและระยะห่าง** (4, 8, 12, 20 ไบต์) ต่างหากคือสิ่งที่ต้องจำ เพราะมันมาจากชนิดข้อมูล ไม่ได้มาจากการสุ่ม
- **ทำไม address หน้าตาต่างกันสองช่วง** — ช่วง `0x7fff...` คือพื้นที่ของ stack (ตัวแปรท้องถิ่นอย่าง `t`, `a`, `m`) ส่วนช่วง `0x5555...` คือที่ที่โปรแกรมและค่าคงที่ถูกโหลดไว้ในหน่วยความจำ (`"hello"` ที่ `s` ชี้อยู่) — ระบบปฏิบัติการเป็นคนจัดวาง และเรื่องนี้จะชัดขึ้นมากในตอน 15 และตอน 20 (virtual memory)
- **GCC 16 ขึ้นไป (รุ่นล่าสุด 16.2, สิงหาคม 2026)** มีข้อความ error/warning ที่อ่านง่ายขึ้นกว่าเดิม (มีโหมด HTML ด้วย) — ข้อความที่ยกมาในบทความนี้มาจาก **GCC 14.2.0** ที่ติดตั้งบนเครื่องทดสอบ ถ้าเครื่องของคุณเป็น GCC รุ่นใหม่กว่า ข้อความอาจต่างเล็กน้อย (เช่นเครื่องหมายคำพูดหรือการจัดวาง) แต่ **ความหมายและชื่อธง** (`-Wincompatible-pointer-types`, `-Wsizeof-array-argument`) เหมือนกัน
- **`ptrdiff_t`, `size_t`, `NULL`** อยู่ในไฟล์ `<stddef.h>` · `strlen` อยู่ใน `<string.h>` · การลืม include ที่ประกาศฟังก์ชันไว้คือ error ทันทีใน GCC 14 ขึ้นไป (เรื่องนี้เราสอนในตอน 13)
