# interpreter: tree-walking — เปลี่ยน "ต้นไม้" ให้เป็น "ค่า" (ตอนที่ 28)

ตอนที่ 26 เราสร้าง **lexer** (ตัวตัดข้อความโปรแกรมออกเป็น "คำ" ที่เรียกว่า token) และตอนที่ 27 เราสร้าง **parser** (ตัวประกอบ token ขึ้นเป็น "ต้นไม้" ที่เรียกว่า AST) แต่ถ้าถามตรง ๆ ตอนนี้ — ทั้ง lexer และ parser **ยังไม่เคย "คำนวณอะไร" ให้เราเลยสักตัว**

```text
lexer  : ข้อความโปรแกรม  →  ลำดับ token (เส้นแบน ๆ)
parser : ลำดับ token      →  ต้นไม้ AST (โครงสร้าง)
                        ↑ ถึงตรงนี้เรามีแต่ "รูปทรง" ยังไม่มี "ค่า"
```

ต้นไม้ที่ได้จากตอนที่ 27 บอกครบว่า "อะไรเป็นลูกของอะไร" แต่**บอกไม่ได้เลย**ว่า `3 + 4 * 5` เท่ากับเท่าไร — เพราะมันเป็นแค่รูปทรง ยังไม่มี "ค่า" อยู่ในตัวมัน

ตอนนี้เราจะปิดวงจรให้ได้ผลลัพธ์จริง ๆ เสียที ตัวที่ทำหน้าที่นี้ชื่อว่า **interpreter**

> **interpreter** (อ่านว่า "อินเทอร์พรีเตอร์") = ตัวที่**เดินตามต้นไม้**แล้วคำนวณค่าออกมา งานของมันคือ "เอารูปทรงไปใช้จริง" — เห็น node บวก ก็คำนวณค่าของลูกสองข้างแล้วบวกกัน (ท่าที่จะเรียกว่า eval — นิยามเต็ม ๆ อยู่หัวข้อ 2) เห็นคำสั่ง print ก็ประเมินค่าแล้วเขียนออกจอ
>
> วิธีที่ interpreter แบบนี้ทำงานเรียกว่า **tree walking** (อ่านว่า "ทรี วอล์กกิง") = การเดินตามต้นไม้ จากรากลงไปถึงใบไม้ แล้วประกอบผลกลับขึ้นมา

ยินดีต้อนรับเข้าสู่ตอนกลางของระยะที่ 6 (Compiler/Interpreter) — ตอนนี้จะเป็นตอนแรกที่ภาษาจิ๋วของเรา **รันได้จริง** ตั้งแต่ข้อความโปรแกรมจนถึงผลลัพธ์ที่พิมพ์ออกมา

> **ที่อยู่ของโค้ดในตอนนี้:** ทุกอย่างอยู่ใน `course/code/ep28/`
> - **01–05** = โฟลเดอร์โปรแกรม แยกตามเลขโปรแกรม
> - **`out/`** = ผลรันจริงของทุกโปรแกรม — `00_env.txt` = สภาพแวดล้อม (เวอร์ชัน Go/เครื่อง/วันที่) · `06_drill_answer.out.txt` = เฉลยโจทย์ท้ายบท · `07_go_real.out.txt` = ผลเทียบกับเครื่องมือจริงของ Go · `08_go_traps.out.txt` = กับดักที่ interpreter ต้องหลบ
> - **`internal/eval/`** = ตัว interpreter (ไฟล์เดียว `eval.go`) ที่ทุกโปรแกรมเรียกใช้ร่วมกัน · **`internal/lexer/` + `internal/parser/`** = ของเดิมจากตอน 26–27 ที่เรานำกลับมาใช้โดยไม่แตะ

![ครบวงจรของภาษาจิ๋ว: ข้อความ → token → AST → ค่า](/assets/diagrams/ep28-01-tree-to-value.svg)

ภาพข้างบนคือภาพรวมของทั้งตอน: จากซ้ายไปขวาคือข้อความ → lexer (ตอน 26) → parser (ตอน 27) → **interpreter (ตอนนี้)** แล้วคายออกมาเป็น "ค่า" (value) และ "ผลที่โปรแกรมทำ" (print เขียนออกจอ) — สังเกตว่าต้นไม้ที่เข้าไปใน interpreter ยังไม่มีค่า แต่ของที่ออกมามีค่าแล้ว

## 1. ปัญหา: ต้นไม้บอก "โครงสร้าง" แต่ไม่บอก "ค่า"

ย้อนกลับไปดูผลงานของตอนที่ 27 — เรามีต้นไม้ที่สวยงามต้นหนึ่ง:

```text
-- "3 + 4 * 5" --
S-expression: (+ 3 (* 4 5))
      BinaryExpr +
      ├─ NumberLit 3
      └─ BinaryExpr *
         ├─ NumberLit 4
         └─ NumberLit 5
```

ต้นไม้นี้**สวยและถูกต้อง** แต่มันไม่ตอบคำถามที่คนใช้โปรแกรมอยากรู้ที่สุด: "แล้วมัน**เท่ากับเท่าไร**?"

ถ้าจะให้ได้คำตอบ เราต้อง "เดิน" ลงไปตามกิ่งของต้นไม้ แล้วค่อย ๆ คำนวณ — เดินไปที่ `NumberLit 3` ได้ค่า 3, เดินไปที่ `4 * 5` ได้ค่า 20, แล้วประกอบขึ้นมาที่เครื่องหมาย `+` ได้ 3 + 20 = 23

แนวคิดนี้มีชื่อเรียกอยู่แล้วสองคำที่เราจะใช้บ่อยมากในตอนนี้:

> - **evaluate** (อ่านว่า "อีแวลูเอต" / คำกริยาย่อว่า **eval**) = **การคำนวณค่านิพจน์ออกมา** นิพจน์ (expression) คือก้อนที่ "คำนวณเป็นค่าได้" เช่น `3 + 4` หรือ `x * 2` หรือแค่เลข 5 ตัวเดียว
> - **value** (อ่านว่า "แวลู") = **ค่าที่คำนวณได้** เช่น eval `3 + 4` แล้วได้ value คือ 7

ส่วนคำสั่ง (statement) เช่น `let x = 1;` หรือ `print x;` ไม่ได้ "เป็นค่า" แต่มัน "สั่งให้ทำอะไรบางอย่าง" — เราจึงใช้คำกริยาอีกตัวสำหรับมัน: **execute** (อ่านว่า "เอกเซ็กคิวต์") = **การลงมือทำคำสั่งให้เกิดผล**

เท่านี้เราก็แบ่งงานของ interpreter ออกเป็นสองท่าได้ชัดแล้ว:

| ท่า | กินอะไร | คายอะไร |
|---|---|---|
| `eval` | นิพจน์ (Expr) | **ค่า** (Value) — "คำนวณแล้วได้เท่าไร" |
| `execute` | คำสั่ง (Stmt) | **ผลข้างเคียง** — "ทำอะไรสักอย่าง" เช่นพิมพ์ออกจอ |

> **ผลข้างเคียง** (side effect) = สิ่งที่โปรแกรม "ทำ" ต่อโลกภายนอก เช่น เขียนข้อความลงจอ เปลี่ยนค่าตัวแปร เขียนไฟล์ — ตรงข้ามกับ "การคำนวณค่าล้วน ๆ" ที่ไม่ทิ้งร่องรอยอะไรไว้

## 2. คำตอบแรก: eval = เดินต้นไม้ + ประกอบค่า (recursive)

หัวใจของทั้งตอนคือฟังก์ชัน `eval` ตัวเดียว ซึ่งโค้ดจริงอยู่ใน `internal/eval/eval.go` — ข้างล่างเป็นเวอร์ชัน**ย่อ**ให้อ่านง่าย (โค้ดจริงยังมี case ของ `BoolLit` และนับจำนวน node ที่เดิน + ตรวจชนิดเต็มรูปแบบ ซึ่งเราตัดออกเพื่อไม่ให้บทเยอะเกินไป):

ก่อนอ่านโค้ด รู้จักของสามอย่างที่จะเจอ (ทั้งหมดคือศัพท์ที่เราจะใช้ซ้ำทั้งคอร์ส):

> - **method** (อ่านว่า "เมธอด") = ฟังก์ชันที่ "ผูก" อยู่กับตัวแปรชนิดหนึ่ง — ใน `func (in *Interpreter) eval(...)` ตัว `(in *Interpreter)` ข้างหน้าเรียกว่า receiver (ตัวรับ) แปลว่า "ฟังก์ชันนี้เป็นของ Interpreter และ `in` คือตัว Interpreter ที่กำลังถูกเรียกใช้"
> - **ค่าคืนหลายตัว** — ท้าย `(Value, error)` แปลว่า eval คืนค่าสองอย่าง: "ค่าที่คำนวณได้" กับ "error (ถ้ามี)" — ใน Go ฟังก์ชันคืนได้หลายค่าพร้อมกัน ซึ่งเราใช้แทน "ค่าบวกสถานะผิดพลาด" มาโดยตลอด
> - **depth** (อ่านว่า "เด็บท์" = ความลึก) = ตัวนับว่า "เดินลงมาลึกแค่ไหน" — เริ่ม 0 ที่ราก แล้วลูกแต่ละชั้นบวก 1 (เห็นจาก `depth+1` ในโค้ด) เราเก็บไว้เพื่อจัดเยื้องเวลาแสดงผลตอน debug เท่านั้น ไม่ได้เปลี่ยนวิธีคำนวณ

```go
// eval — หนึ่ง node ของต้นไม้ = หนึ่ง case ใน switch นี้
func (in *Interpreter) eval(e parser.Expr, depth int) (Value, error) {
	switch n := e.(type) {   // switch แบบ .(type) = เลือก case ตาม "ชนิด" ของ node ไม่ใช่ตามค่า
	case *parser.NumberLit:
		// ใบไม้: ตัวเลข "เป็น" ค่าของตัวเอง ไม่ต้องถามใครเลย
		return IntValue(n.Value), nil

	case *parser.Ident:
		// ใบไม้ที่ไม่ธรรมดา: ชื่อไม่ได้มีความหมายในตัวเอง
		// ความหมายของมันอยู่ใน env — ถ้าไม่มี นี่คือ runtime error
		v, ok := in.env.Lookup(n.Name)
		if !ok {
			return Value{}, &RuntimeError{
				Pos: n.At,
				Msg: fmt.Sprintf("undefined variable %q", n.Name),
			}
		}
		return v, nil

	case *parser.UnaryExpr:
		right, _ := in.eval(n.Right, depth+1)   // "_" = ช่องที่เราไม่ใช้ค่า (blank identifier)
		// (ย่อ: จริง ๆ ยังตรวจว่า right ต้องเป็น int — ถ้าไม่ใช่จะคืน error
		//  "cannot apply '-' to bool" ตามเคส 6 ในหัวข้อ 5)
		if n.Op == "-" {
			return IntValue(-right.Num), nil    // "-" หน้าเลขตัวเดียว: ทำให้เป็นค่าลบ (แบบ -5)
		}
		return right, nil                        // "+" หน้าเลข: ค่าเท่าเดิม (เพื่อให้เขียน +x ได้)

	case *parser.BinaryExpr:
		return in.evalBinary(n, depth)
	}
	return Value{}, &RuntimeError{Msg: fmt.Sprintf("cannot evaluate node of type %T", e)}
}
```

> **recursive** (อ่านว่า "รีเคอร์ซีฟ") = **การที่ฟังก์ชันเรียกตัวเอง** สังเกตว่า `eval` เรียก `eval` ซ้ำกับลูกของมันเอง (เช่น `in.eval(n.Right, ...)`) — นี่คือท่าเดียวกับ `writeTree` ที่เราพิมพ์ต้นไม้ในตอนที่ 27 ต้นไม้มัน "บังคับ" ให้ทุกอย่างเป็นฟังก์ชันแบบนี้อยู่แล้ว เพราะกิ่งไหนก็เป็นต้นไม้ย่อยที่เล็กกว่า

และ `evalBinary` (ตัวจัดการนิพจน์สองฝั่ง) ก็เดินแบบเดียวกัน — "eval ลูกซ้าย → eval ลูกขวา → ประกอบ" (โค้ดจริงเต็ม ๆ อยู่ใน `eval.go` — ข้างล่างย่อเฉพาะโครงสร้างด้วย `// ...`):

```go
func (in *Interpreter) evalBinary(n *parser.BinaryExpr, depth int) (Value, error) {
	left, _  := in.eval(n.Left, depth+1)
	right, _ := in.eval(n.Right, depth+1)

	switch n.Op {
	case "+", "-", "*", "/":
		// ...ตรวจชนิดก่อน แล้วค่อยคำนวณ (หารด้วยศูนย์ = runtime error)
	case "==", "!=":
		// ...เทียบค่า คืน bool
	case "<", ">":
		// ...เทียบจำนวนเต็ม คืน bool
	}
	// ...
}
```

จุดที่อยากให้เห็นคือ **ลำดับการเดิน** — ลูกก่อน พ่อทีหลัง เพราะพ่อต้องรอค่าของลูกครบทั้งสองข้างก่อนจึงจะประกอบได้ ลำดับแบบนี้มีชื่อทางการว่า **post-order** (อ่านว่า "โพสต์-ออร์เดอร์" = เยี่ยมลูกก่อน แล้วค่อยเยี่ยมตัวมันเอง) — ตรงข้ามกับ "อ่านบนลงล่าง" แบบมนุษย์อ่านประโยค

ดูผลรันจริงของโปรแกรม `01_eval_expr` กับนิพจน์ `3 + 4 * 5`:

```text
-- "3 + 4 * 5" --
   1) S-expression (สรุปต้นไม้เป็นบรรทัดเดียว): (+ 3 (* 4 5))
   3) interpreter เดินต้นไม้นี้ (post-order: ลูกก่อน พ่อทีหลัง):
        eval NumberLit 3          = 3
          eval NumberLit 4          = 4
          eval NumberLit 5          = 5
        eval (* 4 5)              = 20
      eval (+ 3 (* 4 5))        = 23
   4) ค่า = 23 (ชนิด int · เดินทั้งหมด 5 node)
```

อ่านทีละบรรทัด: เราเริ่มที่เครื่องหมาย `+` แต่**ยังคำนวณบวกไม่ได้** เพราะไม่รู้ค่าของลูก → ลงไป eval ลูกซ้าย `3` ได้ 3 → ลงไป eval ลูกขวา `4 * 5` ซึ่งก็ต้องลงไป eval `4` และ `5` ก่อน ได้ 20 → เพิ่งตอนนี้เองที่กลับขึ้นมาบวกระดับบนสุดได้ 23

แล้วลองเทียบกับ `(3 + 4) * 5` ซึ่งเป็น "คำชุดเดียวกัน แต่วงเล็บต่าง" — ได้ค่า**ต่างกัน**:

```text
-- "(3 + 4) * 5" --
   1) S-expression (สรุปต้นไม้เป็นบรรทัดเดียว): (* (+ 3 4) 5)
   3) interpreter เดินต้นไม้นี้ (post-order):
          eval NumberLit 3          = 3
          eval NumberLit 4          = 4
        eval (+ 3 4)              = 7
        eval NumberLit 5          = 5
      eval (* (+ 3 4) 5)        = 35
   4) ค่า = 35 (ชนิด int · เดินทั้งหมด 5 node)
```

นี่คือหลักฐานชิ้นสำคัญว่า **ต้นไม้สองต้นที่หน้าตาเกือบเหมือนกัน ให้ค่าต่างกันได้** — และ interpreter ไม่ได้ "ฉลาด" อะไรเลย มันแค่เดินตามกิ่งที่ parser (ตอน 27) ประกอบไว้ให้แล้วเท่านั้น ความถูกต้องทั้งหมดมาจาก parser ที่จับกลุ่มได้ถูกต้อง

![เดินต้นไม้จริง: post-order — ลูกก่อน พ่อทีหลัง](/assets/diagrams/ep28-02-walk-order.svg)

ภาพข้างบนเปรียบเทียบสองต้นไม้เคียงกัน: ซ้ายคือ `(+ 3 (* 4 5))` ได้ 23 ขวาคือ `(* (+ 3 4) 5)` ได้ 35 — ทั้งคู่มี 5 node เท่ากัน ต่างกันแค่ "ใครเป็นลูกของใคร" ซึ่ง parser เป็นคนกำหนด

โปรแกรม 01 เดินทั้งหมด 8 นิพจน์: `3 + 4 * 5` → 23, `(3 + 4) * 5` → 35, `1 + 2 + 3` → 6, `10 - 3 - 2` → 5, `20 / 4` → 5, `-5 + 3` → -2, `7 > 3` → true, `1 == 2` → false — สังเกตสองตัวสุดท้ายคายค่าเป็น **bool** (อ่านว่า "บูล" = ค่าจริง/เท็จ) ออกมา ส่วนหกตัวแรกเป็น **int** (อ่านว่า "อินต์" = จำนวนเต็ม) นี่คือประเด็นสำคัญที่เราจะเจอต่อในหัวข้อ 5

## 3. ตัวแปร = ต้องมี "ที่เก็บ" (environment)

นิพจน์ `x + 1` ประเมินค่าไม่ได้เลย ถ้าไม่รู้ว่า `x` ตอนนี้เท่ากับเท่าไร — และ `x` ก็ไม่ได้ "ฝังค่า" อยู่ในต้นไม้ (ตอนที่ 27 เราเห็นแล้วว่า parser สร้าง `Ident x` แบบไม่ถามว่า x ประกาศไว้หรือยัง)

ดังนั้น interpreter ต้องมีของใหม่ชิ้นหนึ่งที่ parser ไม่มี: **ที่เก็บค่าตัวแปร** เรียกว่า **environment** (อ่านว่า "เอนไวรอนเมนต์") ย่อว่า **env**

> **environment / env** = ตารางที่จับคู่ "ชื่อตัวแปร" กับ "ค่าปัจจุบันของมัน" — พูดง่าย ๆ คือ "สมุดบันทึกว่าตอนนี้ตัวแปรแต่ละตัวเท่ากับเท่าไร" โปรแกรมรันไปได้แค่ไหน env ก็จะถูกเขียนไปด้วย (`let` เขียนค่าเข้า env, อ่าน `x` ก็ไปเปิด env ดู)

ของจริงในโค้ดของเราคือ struct (โครงสร้างข้อมูลที่รวมหลายฟิลด์เป็นก้อนเดียว) ที่ห่อ map ไว้ (map = ตารางจับคู่กุญแจ→ค่า ซึ่งเป็นโครงสร้างพื้นฐานใน Go):

```go
type Env struct {
	vars map[string]Value
}

func (e *Env) Lookup(name string) (Value, bool) { v, ok := e.vars[name]; return v, ok }
func (e *Env) Define(name string, v Value)      { e.vars[name] = v }
```

แล้วคำสั่ง `let` กับ `print` ก็ใช้ env ตัวนี้ — นี่คือส่วน "execute" ของ interpreter:

```go
case *parser.LetStmt:
	v, err := in.eval(n.Value, depth+1)   // คำนวณค่าฝั่งขวาก่อน
	if err != nil { return err }
	in.env.Define(n.Name, v)               // แล้วเขียนค่าเข้า env
	return nil

case *parser.PrintStmt:
	v, err := in.eval(n.Value, depth+1)
	if err != nil { return err }
	fmt.Fprintln(in.out, v.String())       // เขียนค่าออกจอ
	// (ย่อ: จริง ๆ ยังดัก error ของการเขียนจอ แล้วห่อเป็น RuntimeError —
	//  ไม่ปล่อยให้ error ภายในของระบบรั่วออกไปหาโปรแกรมของผู้ใช้)
	return nil
```

> **state** (อ่านว่า "สเตท" = สถานะ) = ข้อมูลที่บอกว่า "ตอนนี้ระบบอยู่ที่ตรงไหน" — env ก็คือ state ชนิดหนึ่ง มันคือ "ความทรงจำ" ของโปรแกรมระหว่างรัน การมี env นี่แหละที่ทำให้ `let x = 1; print x;` กับ `print x;` ให้ผลต่างกัน ทั้งที่โค้ดคำสั่ง `print x;` เขียนเหมือนกันทุกตัวอักษร

ดูผลรันจริงของโปรแกรม `02_variables` ที่เดินทีละคำสั่ง พร้อมโชว์ env หลังทุกคำสั่ง:

```text
โปรแกรม:
  1 | let x = 3 + 4 * 5;
  2 | let y = (x - 2) * 2;
  3 | print x + y;
  [1] (let x (+ 3 (* 4 5)))
      let x      = 23     → env { x = 23 }
  [2] (let y (* (- x 2) 2))
            eval Ident x              = 23
            eval NumberLit 2          = 2
          eval (- x 2)              = 21
          eval NumberLit 2          = 2
        eval (* (- x 2) 2)        = 42
      let y      = 42     → env { x = 23, y = 42 }
  [3] (print (+ x y))
          eval Ident x              = 23
          eval Ident y              = 42
        eval (+ x y)              = 65
      print 65          → เขียน "65" ออกจอ
  ผลลัพธ์ที่โปรแกรมเขียนออกจอ: "65\n"
  env สุดท้าย: { x = 23, y = 42 } (2 ตัวแปร) · เดินไปทั้งหมด 16 node
```

สังเกตบรรทัด `eval Ident x = 23` — ตอน interpreter เจอ `Ident x` มันไม่ได้ "รู้" ค่าเอง แต่ไป**เปิด env ดู**แล้วเจอ 23 ที่ `let x` เขียนไว้ก่อนหน้า นี่คือที่มาของความหมายของตัวแปรทั้งหมด

แล้วถ้าใช้ตัวแปรที่**ยังไม่เคยประกาศ**ล่ะ? นี่คือเคสแรกของ runtime error:

```text
  โค้ด 1 | print z + 1;
  parser: ผ่าน — ต้นไม้คือ (program (print (+ z 1)))
  interpreter: error → line 1, column 7: undefined variable "z"
               (hint: declare it first, e.g. 'let z = 1;')
  สังเกต: ตำแหน่งที่รายงานคือคอลัมน์ของ z (ต้นเหตุ) ไม่ใช่คอลัมน์ของ +
```

สองจุดที่น่าจด:

1. **parser ผ่านสบาย** — เพราะ parser ดูแค่ "รูปประโยค" ว่า `z + 1` เป็นนิพจน์ที่ถูกไวยากรณ์ไหม ซึ่งมันถูก ส่วน "z มีจริงหรือเปล่า" เป็นเรื่องของ**ค่าที่ไหลผ่าน** ซึ่ง parser ไม่รู้จัก
2. **ตำแหน่งที่รายงานคือ `column 7`** = ตำแหน่งของตัว `z` เอง (ต้นเหตุที่แท้จริง) ไม่ใช่ตำแหน่งของเครื่องหมาย `+` — หลักการเดียวกับตอนที่ 27: รายงาน error ที่ "ตัวที่ทำให้พัง"

**เรื่อง env ที่ต้องปักหมุดไว้ก่อน** เพราะมันเป็นสะพานไปตอนที่ 29 โดยตรง:

- env ของเราตอนนี้เป็น **"ตารางเรียบชั้นเดียว"** — ประกาศชื่อซ้ำก็แค่**ทับ**ค่าเดิม (ลองดู: `let x = 1; let x = x + 1; print x;` ให้ผลเป็น `2`)
- ส่วนภาษาจริงมี "ขอบเขต" (**scope** = พื้นที่ที่ตัวแปร "มองเห็นได้") ที่ซ้อนกันได้ เช่น ตัวแปรที่ประกาศในบล็อก `{ }` จะมองไม่เห็นจากข้างนอก
- เรื่อง scope + ตารางสัญลักษณ์ (**symbol table** = ตารางที่เก็บชื่อพร้อมชนิดของมัน) ที่เป็นทางการ คือ**เนื้อหาทั้งตอนของตอนที่ 29** — เราจงใจทำ env เรียบที่สุดในตอนนี้เพื่อให้เห็นว่า "การมีตัวแปร" แท้จริงแล้วต้องการแค่นี้

## 4. control flow: if/else เลือกก้อนที่จะทำ

ของชิ้นที่สองที่ interpreter ทำได้ซึ่ง parser ทำไม่ได้ คือการ **เลือกเส้นทาง** — โปรแกรมส่วนใหญ่ไม่ได้รัน "ทุกบรรทัดเสมอไป" แต่มันเลือกว่าจะทำก้อนไหนจากเงื่อนไข

![environment + control flow: ที่เก็บค่าตัวแปร และการเลือกเส้นทาง](/assets/diagrams/ep28-03-env-branch.svg)

ภาพข้างบนรวมสองเรื่องไว้ในภาพเดียว: **ฝั่งซ้าย**คือ env (ที่เก็บค่าตัวแปรจากหัวข้อ 3) บันทึกค่าของ `x` และ `y` ลงสมุดทีละคำสั่ง · **ฝั่งขวา**คือ control flow — การ์ด "โปรแกรม 1/2/3" แสดงว่าถ้าเงื่อนไขเป็นจริงหรือเท็จ interpreter จะเดินลงแขนไหน และผลลัพธ์ออกจอเป็นเท่าไร

> **control flow** (อ่านว่า "คอนโทรล โฟลว์") = **ทิศทางการไหลของการทำงานของโปรแกรม** — โปรแกรมธรรมดาไหล "บนลงล่าง" แต่ `if/else` ทำให้มัน**แยกทาง**ได้ตามเงื่อนไข (ส่วน `loop` = การวนซ้ำ ที่จะวนกลับ คืออีกความสามารถหนึ่งซึ่งภาษานี้ยังไม่มี — อยู่ในโจทย์ท้ายบท)

ต้นไม้ของ `if` ประกอบด้วย node เงื่อนไข 1 ตัว + แขน `then` (บล็อกที่ทำเมื่อจริง) และมีแขน `else` (บล็อกที่ทำเมื่อเท็จ) เพิ่มอีก 1 ถ้ามี — แต่ interpreter **เดินแค่แขนเดียวเสมอ** — ดูโค้ดส่วนนี้:

```go
case *parser.IfStmt:
	c, err := in.eval(n.Cond, depth+1)   // ประเมินเงื่อนไขก่อน
	if err != nil { return err }
	if c.Kind != Bool {
		return &RuntimeError{ /* เงื่อนไขของ if ต้องเป็น bool เท่านั้น */ }
	}
	if c.Flag {
		return in.executeBlock(n.Then, depth)   // จริง → วิ่งลงบล็อก then
	}
	if n.Else == nil {
		return nil                              // เท็จ + ไม่มี else → ข้ามหมด
	}
	return in.executeBlock(n.Else, depth)       // เท็จ → วิ่งลงบล็อก else
```

จุดที่อยากให้เห็นชัดคือ **"แขนที่ไม่ถูกเลือก ไม่ถูกทำเลย"** — ไม่ใช่ทำแล้วทิ้งผล ดูผลรันจริงโปรแกรม 2 ของ `03_control_flow`:

```text
-- โปรแกรม 2: เงื่อนไขเป็นเท็จ → เข้าบล็อก else (และ 111 ไม่ถูกพิมพ์เลย) --
  1 | let n = 10 - 4 - 3;
  2 | if n > 5 { print 111; } else { print n; }
        eval (- (- 10 4) 3)       = 3
      let n      = 3      → env { n = 3 }
        eval (> n 5)              = false
      if    false       → false: เข้าบล็อก else
      block { … } → ทำ 1 คำสั่ง
          eval Ident n              = 3
        print 3           → เขียน "3" ออกจอ
  ผลลัพธ์ออกจอ: "3\n"
```

ตัวเลข `111` **ไม่เคยถูกประเมินค่าเลยแม้แต่นิดเดียว** — เพราะ interpreter วิ่งลงแขน `else` ไปแล้ว ไม่เฉียดแขน `then` นี่คือความหมายที่แท้จริงของ "การเลือกเส้นทาง"

และลองดู if ซ้อน if (โปรแกรม 3) เพื่อให้เห็นว่า **เงื่อนไขชั้นในจะถูกคิดก็ต่อเมื่อชั้นนอกเลือกเดินมาถึงมันก่อน**:

```text
  1 | let t = 7;
  2 | if t > 3 {
  3 |   if t > 5 { print 1; } else { print 2; }
  4 | } else { print 3; }
      ...
      if    true        → true: เข้าบล็อก then
      block { … } → ทำ 1 คำสั่ง
          eval (> t 5)              = true
        if    true        → true: เข้าบล็อก then
          print 1           → เขียน "1" ออกจอ
  ผลลัพธ์ออกจอ: "1\n"
```

โปรแกรม 03 รันทั้งหมด 5 โปรแกรม (สำเร็จ 4 ติด error 1) — ด้านบนเราโชว์แค่โปรแกรม 2 และ 3 กับเคสที่พัง ส่วนโปรแกรม 1 และ 4 มีผลเต็มใน `out/03_control_flow.out.txt` · เคสที่ติด error คือ `if 1 { print 1; }` ซึ่งเงื่อนไขเป็น**ตัวเลข**ไม่ใช่ bool:

```text
  โค้ด 1 | if 1 { print 1; }
  parser: ผ่าน — ต้นไม้คือ (program (if 1 (block (print 1))))
  interpreter: error → line 1, column 4: condition must be bool, got int
               (hint: use a comparison, e.g. 'if x > 0 { ... }')
```

ทำไมเราถึง**ดัก**ให้เงื่อนไขของ if ต้องเป็น bool เท่านั้น? เพราะบางภาษา (เช่น C) ถือว่า "0 = เท็จ, อื่น ๆ = จริง" ซึ่งสะดวกแต่**อันตราย** — พิมพ์ `if x = 3` (ตั้งใจจะเขียน `==` แต่พิมพ์ `=` ตัวเดียว — ลืมเครื่องหมายตัวที่สอง) แล้วโปรแกรมจะเงียบ ๆ ประเมินเป็นจริงเสมอ ภาษาที่เคร่งเรื่องชนิดแบบนี้จะจับความผิดได้เร็วกว่า นี่คือตัวอย่างของการ "ยอมเขียนโค้ดเพิ่มไม่กี่บรรทัด เพื่อจับบั๊กได้เร็วขึ้น"

## 5. runtime error: ด่านที่สามของความผิดพลาด

ตอนที่ 26–27 เรามี error สองด่านที่ทำงาน**ก่อน**โปรแกรมรัน: lexer จับ "ตัวอักษรผิด" และ parser จับ "รูปประโยคผิด" — คราวนี้มาถึงด่านที่สามที่ทำงาน**ระหว่างรัน**

> **runtime** (อ่านว่า "รันไทม์") = **ช่วงเวลาที่โปรแกรมกำลังรันจริง** — runtime error จึงแปลว่า "error ที่เกิดตอนรัน" ตรงข้ามกับ compile-time (ช่วงที่แปลงโค้ดก่อนรัน)

ความต่างของสองด่านนี้จับได้เป็นประโยคเดียว:

> **parser จับ "รูปประโยค" · interpreter จับ "ค่า"** — parser เช็คว่าโค้ด "เขียนถูกไวยากรณ์ไหม" โดยไม่รู้จักค่าอะไรเลย ส่วน interpreter เช็คว่า "ค่าที่ไหลผ่านต้นไม้มันใช้ด้วยกันได้จริงไหม"

![parser จับ "รูปประโยค" · interpreter จับ "ค่า" — สองด่านที่ไม่ทับกัน](/assets/diagrams/ep28-04-two-gates.svg)

ภาพข้างบนคือ "แผนที่สองด่าน": แต่ละการ์ดเป็นหนึ่งความผิดพร้อมผลของ parser (ผ่าน/error) กับ interpreter (error ข้อความ) เคียงกัน — จะเห็นว่าหกเคสแรก parser บอก "ผ่าน" แล้ว interpreter จับ error ต่อ ส่วนเคสสุดท้ายกลับกัน

โปรแกรม `04_runtime_errors` รันทั้งหมด 7 เคส เพื่อแสดงให้เห็นว่า**แต่ละความผิดถูกจับ "พอดีหนึ่งด่าน"**:

| เคส | โค้ด | ใครจับได้ |
|---|---|---|
| 1 | `print z;` | interpreter: `undefined variable "z"` |
| 2 | `let x = 7 / 0;` | interpreter: `division by zero` |
| 3 | `let x = 1 + true;` | interpreter: `cannot use "+" with int and bool` |
| 4 | `if 1 { print 1; }` | interpreter: `condition must be bool, got int` |
| 5 | `let b = 3 < true;` | interpreter: `cannot compare int with bool using "<"` |
| 6 | `let b = -true;` | interpreter: `cannot apply "-" to bool` |
| 7 | `let x = 1 + ;` | **parser**: `expected expression, found SEMI` |

หกเคสแรก**ผ่าน parser หมด** เพราะรูปประโยคถูกทุกตัวอักษร — ความผิดเพิ่งโผล่ตอนที่ค่าไหลผ่าน node ส่วนเคสสุดท้ายพลิกกลับ: parser จับได้ตั้งแต่ยังไม่เป็นต้นไม้ **interpreter ไม่ได้ทำงานเลย** เพราะไม่มีต้นไม้ให้เดิน

จุดสำคัญอีกข้อที่โปรแกรม 04 โชว์คือ **runtime error หยุดโปรแกรมทันที** — ไม่ใช่แค่ข้ามบรรทัดนั้นแล้วรันต่อ:

```text
   1 | print 1;
   2 | let x = 7 / 0;
   3 | print 3;
   ผลลัพธ์ที่ออกจอก่อนโปรแกรมตาย: "1\n"
   error ที่ทำให้ตาย: line 2, column 11: division by zero
   บรรทัดที่ 3 ไม่ถูกทำ — ตัวเลข 3 ไม่โผล่บนจอเลย
   เพราะ "คำสั่งถัดไป" มีอยู่ได้ก็ต่อเมื่อคำสั่งก่อนหน้าสำเร็จ
```

เพราะใน `Run` ของเรา เรา `return err` ทันทีที่คำสั่งใดคืน error — คำสั่งที่เหลือของโปรแกรมจึงไม่ถูกทำ นี่คือพฤติกรรมเดียวกับภาษาจริงส่วนใหญ่: พอเจอ error ที่จัดการไม่ได้ โปรแกรมก็ตายตรงนั้น (และ Go เองก็มีกลไกพิเศษกว่านั้นที่เรียกว่า panic ซึ่งเราจะเจอในหัวข้อถัดไป)

ประเด็นที่ควรเก็บไปคิดต่อ: **runtime error "รอให้โปรแกรมรันไปถึง" ก่อนจึงโผล่** — ต่างจาก parser error ที่โผล่ทันทีตอนแปลงโค้ด นี่แปลว่าการดูแค่ว่า "โปรแกรมคอมไพล์ผ่าน" **ไม่พอ** จะเจอ runtime error ต้อง**รันจริง**และทดสอบให้ครบทุกเส้นทาง (บางบรรทัดรันไม่ถึงด้วยซ้ำถ้า if เลือกอีกแขน)

## 6. กับดักที่ interpreter ต้องหลบ (จากโค้ดจริงของ Go)

หัวข้อก่อน ๆ เราเขียน interpreter ด้วยภาษา Go — กับดักของ Go จึงกลายเป็นกับดักของ interpreter เราโดยอัตโนมัติ และมีอยู่สามข้อที่ถ้าไม่รู้ จะเขียนบั๊กแบบเงียบ ๆ ได้ง่ายมาก โปรแกรม `_probe_go/go_traps.go` (ผลใน `out/08_go_traps.out.txt`) พิสูจน์ทั้งสามข้อให้ดู:

**กับดัก 1 — int หารด้วยศูนย์ใน Go จะ panic ไม่ใช่คืน error**

> **panic** (อ่านว่า "แพนิก") = กลไกของ Go ที่ทำให้โปรแกรม**หยุดทั้งตัวทันที**เมื่อเจอความผิดที่ถือว่า "ไม่ควรปล่อยผ่าน" ต่างจาก error ธรรมดาที่เป็นแค่ "ค่าที่ฟังก์ชันคืนกลับมาให้ผู้เรียกจัดการต่อได้"

ในภาษา Go เอง ถ้าเขียน `x / y` โดย `x` กับ `y` เป็นตัวแปร int ที่มีค่า 7 และ 0 (แบบใน `go_traps.go`) มันจะ panic ทันที (ชนิด runtime.errorString — โปรแกรมของเราดักจับกลับมาได้ด้วยคำสั่ง recover ซึ่งเป็นตัว "จับ panic" ไม่ให้โปรแกรมตายทั้งตัว) — หมายเหตุ: ถ้าทั้งสองฝั่งเป็นค่าคงที่ตรง ๆ เช่น `7 / 0` Go จะ**ไม่ยอมคอมไพล์ตั้งแต่แรก** (`invalid operation: division by zero`) ซึ่งเป็นเรื่องของตัวตรวจค่าคงที่ในตอนที่ 29 — ถ้า eval ของเราเผลอปล่อยให้ Go หารเองตรง ๆ ผู้ใช้โปรแกรมจิ๋วของเราจะ**พาโปรแกรมทั้งตัวตาย** แทนที่จะได้ข้อความ error ดี ๆ ดังนั้นเราจึงตรวจ `right.Num == 0` **ก่อน**หารทุกครั้ง แล้วคืน `RuntimeError` ปกติให้ผู้เรียกจัดการต่อได้:

```go
if right.Num == 0 {
	return Value{}, &RuntimeError{
		Pos: n.OpTok.Pos,
		Msg: "division by zero",
		Hint: "the right side of '/' must not be 0",
	}
}
return IntValue(left.Num / right.Num), nil
```

**กับดัก 2 — typed-nil: interface ที่ห่อ pointer nil จะ "หน้าตาไม่ใช่ nil"**

ใน Go มีกับดักที่เงียบมากตัวหนึ่ง: ถ้าเราประกาศตัวแปร `var p *Node = nil` (pointer ชี้ไปที่ nil) แล้วเก็บมันใส่ `interface{}` (หรือ `any`) ค่าที่ได้จะ `== nil` เป็น **false** ทั้งที่ข้างในมันว่าง

ทำไมถึงเป็นแบบนั้น? เพราะ interface (สัญญาชนิดของ Go ที่เรารู้จักจากตอนที่ 27) เก็บ "ชนิด + ค่า" สองอย่างแยกกัน พอมีชนิดติดมาด้วย (แม้ค่าจะเป็น nil) ตัวมันเองก็ไม่เท่ากับ nil แล้ว

ผลรันจริงใน `out/08`:

```text
2) typed-nil: interface ที่ห่อ pointer nil จะไม่เท่ากับ nil
   p == nil              : true
   (any ที่ห่อ p) == nil : false   ← กับดัก! เช็ค != nil แล้วผ่าน แต่ของข้างในเป็น nil
   (any ว่างจริง) == nil : true
```

เราหนีกับดักนี้ได้โดย**ไม่ใช้ interface เก็บค่าเลย** — `Value` ของเราเป็น struct ธรรมดา (โครงสร้างข้อมูลที่มีฟิลด์ตายตัว) ที่มี `Kind`, `Num`, `Flag`

> **zero value** (อ่านว่า "ซีโร แวลู" = ค่าเริ่มต้นของชนิด) = ค่าที่ตัวแปรชนิดนั้นมีอัตโนมัติถ้าเรายังไม่กำหนดอะไร เช่น int มีค่าเริ่มต้น 0 ส่วน string มี "" (ข้อความว่าง) — เพราะ `Value` เป็น struct ค่า "ศูนย์" ของมันจึงเป็น struct ที่อ่านได้เสมอ ไม่มีทาง "หน้าตาไม่ใช่ nil แต่พังตอนใช้"

**กับดัก 3 — ลำดับการวน map ใน Go ไม่คงที่**

ถ้าเรา `for` วน map เพื่อพิมพ์ env ออกมา ลำดับของคู่ชื่อ→ค่าจะ**เปลี่ยนไปทุกครั้งที่รัน** เพราะ Go ตั้งใจไม่รับประกันลำดับของ map (เพื่อให้เร็วขึ้นและกันไม่ให้คนไปพึ่งลำดับ) — ผลรันจริง: วน map ดิบ 200 รอบ เจอลำดับต่างกันถึง 3 แบบ ส่วนเราต้องการให้บทความนี้ reproduce ได้ทุกครั้ง เราจึง `sort.Strings` ชื่อก่อนพิมพ์ทุกครั้ง:

```go
func (e *Env) Names() []string {
	names := make([]string, 0, len(e.vars))
	for n := range e.vars { names = append(names, n) }
	sort.Strings(names)     // เรียงชื่อ — ไม่งั้นผลรันเปลี่ยนทุกครั้ง
	return names
}
```

> **deterministic** (อ่านว่า "ดีเทอร์มินิสติก") = **รันกี่ครั้งก็ให้ผลเหมือนเดิมทุกครั้ง** — เป็นคุณสมบัติที่สำคัญมากสำหรับโปรแกรมที่ต้อง "พิสูจน์ได้" ว่าโค้ดกับเอกสารตรงกัน ถ้าโปรแกรมให้ผลสุ่มทุกครั้ง เราจะจับความผิดพลาดไม่ได้เลย (คำที่ตรงข้ามคือ non-deterministic)

## 7. ปิดวงจร: ภาษาจิ๋วรันได้จริง

เมื่อประกอบทุกชิ้นเข้าด้วยกัน — lexer (ตอน 26) + parser (ตอน 27) + interpreter (ตอนนี้) — เราก็ได้ภาษาจิ๋วที่**รันได้จริงครบวงจร** โปรแกรม `05_mini_lang` รันโปรแกรมเดียวที่ใช้ทุกอย่างที่ภาษามี:

```text
ซอร์สโค้ด:
   1 | let base = 2 * 3 + 4;
   2 | let bonus = base - 4;
   3 | let total = base * 2 - bonus;
   4 | if total > 10 {
   5 |   print total;
   6 |   print total / 2;
   7 | } else {
   8 |   print 0;
   9 | }
  10 | if total == 14 { print true; }
  11 | print false;
```

ตัวแปร `base` ได้ 10 (เพราะ `2 * 3 + 4` = 6 + 4), `bonus` ได้ 6 (10 - 4), `total` ได้ 14 (20 - 6) — แล้วเงื่อนไข `total > 10` เป็นจริง จึงพิมพ์ `14` และ `7` ออกมา ตามด้วย `total == 14` เป็นจริง จึงพิมพ์ `true` สุดท้ายพิมพ์ `false`:

```text
-- ผลลัพธ์ที่โปรแกรมเขียนออกจอ (4 บรรทัด) --
    14
    7
    true
    false

== สถิติการเดินต้นไม้ ==
  คำสั่งระดับบนสุด      : 6
  ตัวแปรใน env          : 3 → { base = 10, bonus = 6, total = 14 }
  node ที่เดินผ่านทั้งหมด: 34 (นับทั้งคำสั่งและนิพจน์)
  บรรทัดที่พิมพ์ออกจอ    : 4
```

ตัวเลข `34 node` นี้คือ **"ต้นทุน" ของ tree-walking** — ทุกครั้งที่รันโปรแกรม ต้องเดินต้นไม้ใหม่ทั้งหมดตั้งแต่ต้น แม้โปรแกรมจะเหมือนเดิมเป๊ะก็ตาม (และโปรแกรม 05 ก็พิสูจน์แล้วว่ารันซ้ำด้วย interpreter ตัวใหม่ ผลออกมา**เหมือนเดิมทุกไบต์** = deterministic)

นี่คือจุดที่เราจะต่อยอดในตอนที่ 30 (codegen): ของจริงส่วนใหญ่จะไม่ "เดินต้นไม้" ซ้ำทุกครั้ง แต่จะ**แปลงต้นไม้เป็นชุดคำสั่งแบน ๆ (bytecode) แล้ววนรันเร็ว ๆ** — แนวคิดเดียวกัน ต่างแค่ "เดินต้นไม้ไปทำอะไร"

และโปรแกรม 05 ยังแสดง "ขอบเขตของภาษาตอนนี้" ไว้ตรง ๆ ด้วย — ภาษานี้ยัง**ไม่มี loop และไม่มีฟังก์ชัน**:

```text
  loop: ภาษายังไม่มี while
    โค้ด 1 | let x = 3; while x > 0 { print x; }
    parser: error → line 1, column 18: expected ';' to end statement, found IDENT "x"

  function: ภาษายังไม่มี fn
    โค้ด 1 | fn add(a, b) { print a + b; }
    parser: error → line 1, column 9: unexpected character ','
```

เหตุผลที่ "ไม่มี loop" ไม่ใช่ความขี้เกียจ — มันคือ**หัวใจของทั้งระยะนี้**: จะเพิ่มความสามารถอะไรให้ภาษาจิ๋ว ต้องเติม**ทั้งสามชั้นพร้อมกัน** (lexer → parser → interpreter) เสมอ นั่นคือโจทย์ mini-project ท้ายบท

## 8. ของจริงทำแบบนี้: tree-walking interpreter ในประวัติศาสตร์

ก่อนปิดบท เรามาตรวจว่า "การเดินต้นไม้เพื่อคำนวณค่า" ไม่ใช่ของที่เราประดิษฐ์เองเล่น ๆ — มันคือวิธีที่ภาษาโปรแกรมจริงใช้จริงมาหลายทศวรรษ:

- **Lisp** (ปี 1958) — ภาษาที่เก่าแก่ที่สุดภาษาหนึ่งของวงการ ซึ่งออกแบบมาให้ "โปรแกรมเป็นข้อมูล" กลไก `eval` ของ Lisp คือ **interpreter แบบ tree-walking ตัวจริง** และ S-expression ที่เราใช้เขียนต้นไม้มาตลอดคอร์ส ก็คือ "คู่แฝด" ของ Lisp นั่นเอง (S มาจาก Symbolic)
- **Smalltalk** (ปี 1972) — ภาษาต้นแบบของการเขียนโปรแกรมเชิงวัตถุ (object-oriented) ยุคแรก ๆ ก็ใช้ interpreter เดินต้นไม้เช่นกัน
- **Ruby** ยุคแรก — Matz (ยูกิฮิโระ มัตสึโมโตะ) ผู้สร้างภาษา Ruby เขียน interpreter ตัวแรกแบบ tree-walking ก่อนที่ Ruby 1.9 จะเปลี่ยนไปใช้ **YARV** ซึ่งเป็น virtual machine (เครื่องเสมือน = โปรแกรมที่จำลองเครื่องคอมพิวเตอร์มาเพื่อรันชุดคำสั่ง) ที่รัน bytecode (ชุดคำสั่งแบน ๆ แทนการเดินต้นไม้ — แนวทางเดียวกับตอนที่ 30 ของเรา)

แล้วในวันนี้ มันยังมีชีวิตอยู่ไหม? ตรวจได้จากเครื่องมือจริงที่นักเขียน Go ใช้ทุกวัน — โปรแกรม `_probe_go/goreal_check.go` (ผลใน `out/07_go_real.out.txt`) เทียบ interpreter ของเรากับ `types.Eval` ของ Go:

> ศัพท์ใหม่สามคำที่โผล่ในผลรันนี้: **`go/ast`** = package (ชุดโค้ดสำเร็จรูปที่ Go แถมให้) ที่เก็บต้นไม้ AST ของภาษา Go จริง ๆ · **`types.Eval`** = ตัวประเมินนิพจน์ของ Go ที่คำนวณค่าของนิพจน์ออกมา · **`untyped int`** = ค่าจำนวนเต็มที่ยังไม่ถูก "บังคับชนิด" ให้เป็น int แบบตายตัว (รายละเอียดเรื่องชนิดเต็ม ๆ อยู่ตอนที่ 29)

```text
-- "3 + 4 * 5" --
   (1) interpreter ของเรา : 23
   (2) เดินบน go/ast      : 23
   (3) types.Eval ของ Go  : 23 (ชนิด untyped int)
   → ทั้งสามทางให้ค่าตรงกัน

   สรุป: ตรงกัน 7/7 นิพจน์
```

ทั้ง 7 นิพจน์ให้ค่าตรงกันเป๊ะ — และจุดที่น่าสนใจที่สุดอยู่ในหมายเหตุท้ายผลรัน:

```text
   go/types เก็บค่าคงที่ด้วย package go/constant (จำนวนเต็ม/ตรรกยะแบบไม่ปัดเศษ)
   และตัวตรวจชนิดของ Go เองก็เดิน AST แบบ recursive เหมือน eval ของเรา
   ต่างกันแค่: ของมันเดินเพื่อให้ "รู้ชนิด" ส่วนของเราเดินเพื่อให้ "ได้ค่า"
```

นี่คือข้อสรุปที่สวยงามของทั้งตอน: **การเดินต้นไม้เป็นเทคนิคเดียว แต่ใช้ทำได้หลายอย่าง** — interpreter เดินเพื่อ "ได้ค่า", ตัวตรวจชนิด (type checker) ของ Go เดินเพื่อ "รู้ชนิด", ส่วน compiler เดินเพื่อ "สร้างโค้ด" (ตอนที่ 30) ต้นไม้จาก parser (ตอน 27) จึงเป็นเหมือน "ทางแยก" ที่เครื่องมือหลายชนิดเดินเข้าไปใช้ต่อได้

และที่เห็นความต่างชัดที่สุดคือเคส `1 / 0`:

```text
-- "1 / 0" --
   interpreter ของเรา : line 1, column 3: division by zero
   types.Eval ของ Go  : eval:1:5: invalid operation: division by zero
   ทั้งคู่บอกว่าหารด้วยศูนย์พัง — แต่ของเราเพิ่งรู้ "ตอนรัน"
   ส่วน Go รู้ตั้งแต่ยังไม่รัน (เพราะมีตัวตรวจชนิด/ค่าคงที่ — ตอนที่ 29)
```

Go **จับได้ก่อนโปรแกรมจะรัน** เพราะมันมี "ตัวตรวจชนิด + ค่าคงที่" ที่ทำงานตอนคอมไพล์ — ซึ่งก็คือเนื้อหาของตอนที่ 29 นั่นเอง (และขอชี้จุดที่ดูเหมือนขัดกับหัวข้อ 6: ที่นี่ `types.Eval` เป็น**ตัวตรวจชนิด**ที่คิดค่าคงที่ก่อนรัน ส่วนหัวข้อ 6 พูดถึง**โค้ด Go ที่รันจริง**ซึ่ง int หารศูนย์จะ panic ตอนรัน — สองอย่างนี้คนละจังหวะกัน ไม่ขัดกัน) ตอนนี้เรายังไม่มีชั้นนั้น จึงได้แค่รู้ "ตอนรัน" ซึ่งช้ากว่าแต่ก็ยังดีกว่าไม่รู้เลย

### Mini-project (ต่อยอดจาก `internal/eval` และ `internal/parser`)

ก่อนเริ่ม รู้จักโครงไฟล์ที่ต้องแตะ: **`internal/eval/eval.go`** = ตัวเดินต้นไม้ทั้งหมด · **`internal/parser/ast.go` + `parser.go`** = ชนิด node + ตัว parse จากตอน 27 · **`internal/lexer/lexer.go`** = ตัวตัดคำจากตอน 26 · รันทุกอย่างพร้อมกันด้วย `./run_all.sh`

ให้ทำสามอย่างเรียงจากง่ายไปยาก (ทุกอย่างต้องเติม**ครบทั้งสามชั้น** — lexer → parser → interpreter — นี่คือบทเรียนหลักของหัวข้อ 7):

1. **เพิ่มเครื่องหมาย `%` (modulo — หารเอาเศษ)** — ต้องเติมครบสามชั้นเช่นกัน:
   - lexer: เพิ่ม token ชนิด `PERCENT` สำหรับ `%`
   - parser: เพิ่ม `%` เข้าไปในชั้น `factor` (อยู่ระดับเดียวกับ `*` `/`)
   - eval: เติม case `"%"` ที่คืน `left.Num % right.Num` พร้อม**ตรวจหารด้วยศูนย์ก่อน**เหมือนกรณี `/` (กับดัก 1 ของหัวข้อ 6)
   - ทดสอบว่า `print 10 % 3;` ได้ `1`
2. **เพิ่ม `while` loop ให้ภาษาจิ๋ว** — นี่คือความสามารถที่โปรแกรม 05 บอกว่า "ยังไม่มี" ต้องเติม:
   - lexer: เพิ่มคำสงวน `while` (และ token `W...`)
   - parser: เพิ่มกฎ `whileStmt = "while" expression block` + node ใหม่ `WhileStmt` (อย่าลืมเติมลงใน `childrenOf` ของ ast.go เพื่อให้พิมพ์ต้นไม้ได้)
   - interpreter: execute `WhileStmt` = "eval เงื่อนไข → ถ้าจริง execute block → **วนกลับมา eval เงื่อนไขอีกครั้ง**" (ใบ้: ใช้ `for` loop ใน Go เพื่อวน)
   - **ระวัง infinite loop** (อ่านว่า "อินฟินิต ลูป" = วนไม่รู้จบ): ถ้าเงื่อนไขเป็นจริงตลอด โปรแกรมจะวนไม่หยุด — แก้ด้วยการใส่ตัวนับรอบสูงสุด (เช่น วนได้มากสุด 1000 รอบแล้ว error) เพื่อกันโปรแกรมค้าง
   - ทดสอบว่า `let x = 3; while x > 0 { print x; }` ควรพิมพ์ `3`, `2`, `1` — แต่เดี๋ยวก่อน! `x` ไม่มีทางลดลงเพราะภาษายังไม่มีตัวดำเนินการลดค่า — ลองคิดว่าต้องเพิ่มอะไรอีกถึงจะทำให้ loop นี้ "หยุดได้จริง" (นี่คือเหตุผลที่ภาษาโปรแกรมจริงมีตัวดำเนินการแบบ `x = x - 1`)
3. **สร้าง REPL จิ๋ว** — REPL (อ่านว่า "เรเพิล" = Read-Eval-Print Loop) คือโปรแกรมที่ "อ่านคำสั่ง → ประเมิน → พิมพ์ผล → วนอ่านคำสั่งใหม่" แบบที่คุณพิมพ์ใน terminal แล้วเห็นผลทันที เช่น:
   - วน `for` อ่านข้อความหนึ่งบรรทัดจากผู้ใช้ (`bufio.Scanner` = ตัวอ่านข้อความทีละบรรทัดจากแป้นพิมพ์) แล้ว `parser.Parse` + `eval.Run` ด้วย interpreter **ตัวเดียวกัน** (เพื่อให้ env อยู่ข้ามบรรทัด — ตัวแปรที่ประกาศในบรรทัดแรกยังใช้ได้ในบรรทัดถัดไป)
   - พิมพ์ผลลัพธ์แต่ละครั้ง แล้วรอคำสั่งถัดไป (ออกจากโปรแกรมด้วยคำสั่งพิเศษเช่น `exit`)
