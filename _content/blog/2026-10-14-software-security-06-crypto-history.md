## 1. แนวคิด: cipher คือ "ฟังก์ชัน" ที่มีกุญแจ

### 1.1 ศัพท์สี่คำที่ต้องแม่นก่อนไปต่อ

- **plaintext** (ข้อความต้นฉบับ) = ข้อความที่เราอยากเก็บเป็นความลับ · **ciphertext** (ข้อความลับ) = สิ่งที่ได้หลังเข้ารหัส · **key** (กุญแจ) = ค่าที่ทำให้การเข้ารหัสครั้งนี้ไม่เหมือนครั้งอื่น
- **encryption** (การเข้ารหัส) = เปลี่ยน plaintext เป็น ciphertext ด้วย key · **decryption** (การถอดรหัส) = ทางกลับกัน
- **cipher** (ระบบรหัส) = *วิธี* ที่แปลงสองทางนี้ ส่วน **cryptography** = ศาสตร์ทั้งหมด และ **cryptanalysis** = ศาสตร์ของการหักมัน ("attacker" ในบทนี้หมายถึง cryptanalyst — คนที่พยายามอ่านข้อความที่ไม่ใช่ของเขา)
- **keyspace** (ขนาดกุญแจ) = จำนวน key ที่เป็นไปได้ทั้งหมด · ถ้า keyspace คือ 26 แปลว่ามี key 26 แบบ ถ้า keyspace คือ 2^56 ก็คือ key 7.2×10^16 แบบ

ประโยคของ **Auguste Kerckhoffs** (ค.ศ. 1883 — หลัก **Kerckhoffs's principle**) ที่ต้องท่องให้ขึ้นใจ:

> ระบบรหัสต้อง **ไม่ต้องเป็นความลับ** จึงจะปลอดภัย — ความลับทั้งหมดต้องอยู่ใน **key** เท่านั้น

พูดแบบชาวบ้าน: ต่อให้ศัตรูรู้ว่าเราใช้ **AES-256-GCM** (โหมด AEAD — ข้อ 1.2 และ 3.7) ก็ไม่เป็นไร ขอแค่เขาไม่รู้ key 16/24/32 ไบต์ของเรา (AES-256 = 32 ไบต์) — เพราะจะลอง key ทุกตัวก็ไม่ไหว แต่ถ้าเราใช้ "cipher ลับที่คิดเองไม่บอกใคร" แล้วเขาแอบรู้วิธีได้ **ทุกอย่างก็จบในครั้งเดียว** นี่คือเหตุผลที่เราห้าม "เขียน crypto เอง" ในระดับเดียวกับที่ห้ามเอาความลับไปไว้ในวิธี

### 1.2 สามคำที่คนชอบปนกัน และ crypto แยกให้เราสามแบบ

ในโลกความปลอดภัยมีคุณสมบัติสามข้อที่ถูกพูดถึงตลอดเวลา ย่อว่า **CIA triad** (ใน[ตอนที่ 01](/blog/post.html?slug=2026-10-09-software-security-01-why-security-matters) เราเกริ่นไว้ · ตอนที่ 10 จะลงรายละเอียดทั้งหมด) — และในบทนี้เราสนใจสามข้อแรกนี้เป็นพิเศษเพราะ **crypto คือเครื่องมือที่ให้มันทั้งสาม**:

- **confidentiality** (ความลับ) = คนที่ไม่ควรอ่าน อ่านไม่ได้ → ได้จาก **การเข้ารหัส**
- **integrity** (ความครบถ้วน) = ถ้ามีใครแก้ข้อมูล เรารู้ตัว → ได้จาก **hash / HMAC / tag ของ AEAD** (นิยามในข้อ 3.6, 3.7 และ 3.8)
- **authenticity** (ความแท้) = เรารู้แน่ว่าข้อความนี้มาจากใคร (และสำหรับ TLS: เรากำลังคุยกับเว็บที่เราคิดจริง ๆ) → ได้จาก **ลายเซ็นดิจิทัล** และ **certificate**

และมีคำอีกสองคำที่จะโผล่บ่อยในบทนี้:

- **adversary model** (โมเดลของผู้โจมตี) = เราสมมติว่าศัตรูทำอะไรได้บ้าง · โมเดลที่ crypto ใช้มักจะแรงที่สุดคือ **"ศัตรูควบคุมเครือข่ายได้ทั้งหมด"** — RFC 9846 (ข้อกำหนด TLS 1.3 ฉบับปรับปรุง, กรกฎาคม 2026) เขียนไว้ตรง ๆ ว่า TLS ออกแบบมาเพื่อ "in the face of an attacker who has complete control of the network" · ในโลกของ crypto เราไม่สมมติว่าศัตรู "แค่ฟัง" — เราสมมติว่าเขาอ่าน **และเขียน** ได้
- **AEAD** (Authenticated Encryption with Associated Data) = โหมดเข้ารหัสที่ทำ **confidentiality + integrity ในครั้งเดียว** (ตัวที่ใช้กันทั่วไปคือ **AES-GCM** และ **ChaCha20-Poly1305**) · "Associated Data" คือข้อมูลที่ *ไม่* เข้ารหัส แต่ยังถูกตรวจการแก้ เช่น header ของแพ็กเก็ต

> **ประโยคเดียวที่เป็นหัวใจของทั้งบทนี้:** crypto ไม่ได้ทำให้ข้อความ "อ่านไม่ออก" เท่านั้น — มันทำให้การแก้ไข **ตรวจจับได้** และทำให้เรารู้ว่า **กำลังคุยกับใคร**

ภาพด้านล่างสรุปการจับคู่ของทั้งสามข้อกับเครื่องมือ crypto ที่ให้คุณสมบัตินั้น — เราจะกลับมาที่มันอีกครั้งหลังจากที่เขียนโค้ดจริงแล้ว

### 1.3 symmetric กับ asymmetric: ทำไมต้องมีทั้งคู่

- **symmetric cipher** (key เดียว) = ฝั่งเข้ารหัสกับฝั่งถอดรหัสใช้ key **ตัวเดียวกัน** · เร็วมาก · ตัวอย่าง: AES
- **asymmetric cipher** (public-key, key คู่) = มี **public key** (แจกได้) กับ **private key** (เก็บไว้) · ช้ากว่ามาก · ตัวอย่าง: RSA, ECDSA, ECDH

คำถามที่คนสงสัยทันที: ถ้ามี asymmetric แล้วทำไมยังต้องมี symmetric?

คำตอบคือ **"การแลก key"** — ถ้าสองฝ่ายไม่เคยพบกันมาก่อน จะตกลง key เดียวกันได้ยังไงบนสายที่ศัตรูอ่านได้? ยุค 1976 มีคำตอบแล้ว: **Diffie–Hellman** ให้สองฝ่าย *คำนวณ* key ร่วมกันได้โดยไม่เคยส่ง key นั้นออกไปเลย · และงานจริงก็คือ **hybrid**: ใช้ asymmetric เพื่อตกลง key สั้น ๆ แล้วใช้ symmetric (AES) เข้ารหัสข้อมูลจริง — ซึ่งเป็นสิ่งที่ TLS ทำอยู่ทุกวันนี้

## 2. ทำไมสำคัญ: ทุกขั้นของ crypto เกิดเพราะขั้นก่อนมีช่องโหว่

นี่คือแก่นของซีรีส์นี้ — ไม่มีขั้นไหนเกิดขึ้นโดยไม่มีเหตุ ทุกขั้นเกิดขึ้นเพราะของเดิม **พัง** ที่จุดใดจุดหนึ่ง และจุดนั้นมักไม่ใช่ "คณิตศาสตร์อ่อน" แต่เป็น **"คนใช้ผิด"** หรือ **"กำลังของศัตรูเพิ่มขึ้น"**

เรามาดูกันทีละขั้น และดูว่าแต่ละขั้น "ปิดช่อง" ไหน

### 2.1 เริ่มจากของง่ายที่สุด: Caesar cipher (สับเปลี่ยนด้วย shift คงที่)

**Caesar cipher** เป็น **substitution cipher** (cipher แทนที่) ชนิดง่ายที่สุด: เลื่อนตัวอักษรทุกตัวไปข้างหน้าเท่ากันด้วยค่า shift หนึ่งค่า (ชื่อของมันมาจาก **Julius Caesar** ที่ใช้ในการติดต่อส่วนตัวของเขา — ตัวอย่างที่ตำราอ้างถึงเสมอก็คือ shift เท่ากับ 3 — แต่ต้องระวัง: ตำราแต่ละเล่ม "เลื่อน" คนละทาง · ถ้าเลื่อน **ถอยหลัง** 3 (แบบ left rotation ที่ตำราอ้างบ่อย) `E` → `B` ส่วนถ้าเลื่อน **ไปข้างหน้า** 3 ตามสูตรด้านล่าง `E` → `H` — ทั้งสองแบบคือ Caesar cipher ตัวเดียวกัน ต่างกันแค่เครื่องหมายของ shift)

เขียนด้วยเลขคณิตล้วน ๆ ก็คือ (โดยที่ `A` = 0, `B` = 1, …, `Z` = 25):

```text
E_n(x) = (x + n) mod 26        (เข้ารหัส)
D_n(x) = (x − n) mod 26        (ถอดรหัส)
```

จุดอ่อนของมันเรียบง่ายจนน่าประหลาดใจ: **keyspace มี 26 แบบ** · คนที่ดักข้อความได้แค่ลอง **ทุก shift** ก็จบ — 26 ครั้ง ใช้เวลาไม่ถึงไมโครวินาทีบนเครื่องที่คุณนั่งอยู่

นี่คือ **brute force** (การค้นหากำลังดิบ) รูปแบบบริสุทธิ์ที่สุด และเป็นบทเรียนแรกของสายงาน security: **ถ้า keyspace เล็กพอที่จะลองหมดได้ cipher นั้นไม่ใช่ cipher**

### 2.2 ค.ศ. 850: Al-Kindi เปลี่ยนการหักรหัสให้เป็น "สถิติ"

ที่กรุงแบกแดด ราวปี ค.ศ. 850 นักปราชญ์นาม **Abu Yusuf Ya'qub ibn Ishaq al-Kindi** (ราว 801–873) เขียนตำรา *Risalah fi Istikhraj al-Mu'amma* ("ว่าด้วยการไขข้อความที่ถูกเข้ารหัส") — ซึ่งเป็นงาน cryptanalysis ระบบแรกเท่าที่รู้จัก

แนวคิดของเขาเรียบง่ายและทรงพลังมาก:

> ให้เพื่อนเก็บตัวอย่างข้อความในภาษาเดียวกันไว้ **ยาวสักหน้ากระดาษ** แล้วนับว่าตัวอักษรไหนโผล่กี่ครั้ง · จัดอันดับจากมากไปน้อย · แล้วทำแบบเดียวกันกับข้อความที่ถูกเข้ารหัส · จับคู่อันดับที่หนึ่งกับอันดับที่หนึ่ง อันดับที่สองกับอันดับที่สอง … ไปเรื่อย ๆ

นั่นคือ **frequency analysis** — การวิเคราะห์ความถี่ตัวอักษร · หัวใจอยู่ที่ข้อเท็จจริงง่าย ๆ นี้:

> cipher ที่ "สับเปลี่ยนชื่อตัวอักษร" ไม่เปลี่ยน **ความถี่** ของมันเลย — ตัวที่ถูกใช้บ่อยที่สุดในข้อความก็ยังถูกใช้บ่อยที่สุดใน ciphertext แค่เปลี่ยนหน้าตา

นี่คือช่องโหว่ที่ Caesar (และ substitution cipher ทุกตัว) ปิดไม่ได้ **เป็นเวลากว่าพันปี** จนกระทั่งมี cipher ที่ "เลื่อนตัวอักษรละแบบ"

### 2.3 1553: Vigenère — เลื่อนตัวอักษร "ละแบบ" ด้วย key

**Vigenère cipher** (ชื่อตาม **Blaise de Vigenère** แต่คนที่ตีพิมพ์ก่อนคือ **Giovan Battista Bellaso** ในปี 1553 — ประวัติศาสตร์ให้เครดิตผิดมานาน) แก้จุดอ่อนข้อ 2.2 ด้วยไอเดียง่าย ๆ:

> อย่าใช้ shift เดียวทั้งข้อความ — ใช้ **key เป็นคำ** แล้วเลื่อนตัวอักษรตัวที่ i ด้วยค่าของ key ตัวที่ i (วนซ้ำเมื่อ key หมด)

ผลลัพธ์คือ **polyalphabetic cipher** (cipher หลายชุดตัวอักษร): ตัวอักษร `E` ตัวแรกของข้อความอาจกลายเป็น `L` แต่อีก `E` ตัวถัด ๆ ไปกลายเป็นตัวอื่น — **ยอดความถี่ถูกเกลี่ยให้แบน** และ frequency analysis แบบ Al-Kindi ใช้ไม่ได้ทันที

มันจึงได้ฉายาว่า **"le chiffrage indéchiffrable"** (cipher ที่ถอดไม่ได้) และยืนหยัดได้ราว **สามศตวรรษ**

### 2.4 1863: Kasiski — หาความยาว key ก่อน แล้วค่อยหักทีละคอลัมน์

**Friedrich Kasiski** ตีพิมพ์วิธีทั่วไปในการหัก Vigenère ในปี 1863 · แนวคิดคือ:

1. **หาความยาวของ key** — Vigenère ที่ใช้ key ยาว `p` จะมี "คาบ" `p` · ถ้าเราเดา `p` ถูก เราจะแยกข้อความออกเป็น `p` ชุดตามตำแหน่ง (ชุดที่ 1, 6, 11, … · ชุดที่ 2, 7, 12, …)
2. **แต่ละชุดกลับเป็น Caesar cipher!** เพราะทุกตัวในชุดเดียวกันถูกเลื่อนด้วยค่าเดียวกัน
3. **โจมตี Caesar ทีละชุด** — ด้วย frequency analysis ที่เราเขียนไว้ในข้อ 2.2 หรือด้วยคะแนนทางสถิติ

ในบทนี้เราจะใช้เครื่องมือที่ "มองเห็นคาบได้จากสถิติ" แทนการนับข้อความซ้ำแบบ Kasiski — ชื่อว่า **index of coincidence (IC)**:

> IC = Σ nᵢ(nᵢ−1) / (N(N−1)) · โดย nᵢ = จำนวนของตัวอักษรตัวที่ i · N = จำนวนตัวอักษรรวม

ตัวเลขสองตัวที่ต้องจำ: **ข้อความภาษาอังกฤษธรรมชาติ ≈ 0.066** · **ข้อความสุ่ม ≈ 1/26 ≈ 0.038** · Caesar **ไม่เปลี่ยน** ค่านี้เลย (เพราะแค่เปลี่ยนชื่อตัวอักษร) แต่ Vigenère **ลด** มันลงเข้าหา 0.038 — และเมื่อเราแยกข้อความตามคาบที่ถูกต้อง ค่า IC ของแต่ละคอลัมน์จะ **เด้งกลับขึ้นมาใกล้ 0.066** นั่นคือสัญญาณว่าเราหา "คาบ" เจอแล้ว

### 2.5 1932 → 1945: Enigma — เครื่องจักรที่พังเพราะ "คน" ไม่ใช่เพราะคณิตศาสตร์

**Enigma** คือเครื่องเข้ารหัสพกพาที่มี **rotor** (จานหมุน) และ **plugboard** (แผงสายสลับ) — ทุกครั้งที่กดตัวอักษรหนึ่ง ตัวอักษรจะถูกสับเปลี่ยนหลายชั้น และ rotor จะหมุน ทำให้ **keystream** (กระแสตัวอักษรที่ถูกนำมาผสมกับข้อความทีละตัว — ดูข้อ 3.5 และ 3.10) ของมันยาวและซับซ้อนกว่า Vigenère มาก · เยอรมนีใช้เป็นระบบรหัสหลักของกองทัพในสงครามโลกครั้งที่สอง (และมีใช้ในเชิงพาณิชย์มาตั้งแต่ต้นทศวรรษ 1920)

ไทม์ไลน์ที่ต้องรู้:

- **ธันวาคม 1932** นักคณิตศาสตร์ชาวโปแลนด์ **Marian Rejewski** แห่งกองบัญชาการใหญ่โปแลนด์ หัก Enigma ได้เป็นครั้งแรก โดยใช้ทฤษฎีกลุ่มการสลับเปลี่ยน (permutation group) ร่วมกับข้อมูลจากสายลับที่ฝรั่งเศสส่งให้
- **1938** ทีมโปแลนด์สร้างเครื่องช่วยหักชื่อ **cryptologic bomb** และ **Henryk Zygalski** คิด "แผ่น Zygalski" ขึ้นมาช่วย
- **ปลายเดือนกรกฎาคม 1939** (ราวห้าสัปดาห์ก่อนสงครามโลกเริ่ม) โปแลนด์แชร์เทคนิคและเครื่องมือทั้งหมดให้ฝรั่งเศสและอังกฤษในการประชุมลับใกล้กรุงวอร์ซอ
- **1940s** **Bletchley Park** (Government Code and Cypher School) ต่อยอดเป็นขีดความสามารถขนาดใหญ่ · **Alan Turing** เป็นคนสำคัญที่คิดวิธีอัปเกรดเครื่อง bomb ของโปแลนด์ · ข้อมูลข่าวกรองที่ได้มีชื่อรหัสว่า **Ultra** และหลายความเห็นบอกว่ามันย่นระยะเวลาสงครามลงอย่างมีนัยสำคัญ

**บทเรียนที่อยากให้จำจากข้อนี้:** หนังสือหลายเล่มบอกว่า "Enigma ถูกหักเพราะคนเยอรมันใช้ผิด" ไม่ใช่เพราะเครื่องอ่อน — ผู้ใช้เลือก settings ซ้ำ · ข้อความที่มีรูปแบบซ้ำ predictable ทำให้เกิด **crib** (ข้อความที่ทายได้ล่วงหน้า เช่นคำพยากรณ์อากาศประจำวัน) · และเมื่อเรืออูเปลี่ยนไปใช้ Enigma แบบ 4 rotor (ราวต้นปี 1942) อังกฤษก็ "ตาบอด" ไปพักหนึ่งจนกว่าจะจับ key และเครื่อง bomb ที่เร็วกว่าของกองทัพเรือสหรัฐฯ มาช่วย

**นี่คือเรื่องเดียวกันกับปี 2026:** ระบบ crypto ที่แข็งแรงที่สุดในโลกยังพังได้ ถ้ากระบวนการใช้ของมนุษย์รั่ว

### 2.6 1949: Shannon เปลี่ยน crypto จากงานฝีมือเป็นคณิตศาสตร์

**Claude Shannon** ตีพิมพ์ *Communication Theory of Secrecy Systems* ในปี 1949 — เป็นจุดที่วิชานี้กลายเป็นคณิตศาสตร์ที่พูดถึงได้แบบมีแบบแผน (เขาให้กรอบคิดเรื่อง **entropy** ของ key (ปริมาณความไม่แน่นอนของ key — ยิ่งมากยิ่งเดายาก), perfect secrecy, และงานที่ต่อยอดไปถึงทฤษฎีสารสนเทศทั้งหมด)

ตั้งแต่จุดนี้เป็นต้นไป คำถามของ crypto ไม่ใช่ "มีใครอ่านออกไหม" อีกต่อไป แต่เป็น **"การโจมตีแบบไหนที่เราพิสูจน์ได้ว่าทำไม่ได้ ถ้าศัตรูมีกำลังเท่านี้"** — และนั่นคือที่มาของคำว่า **computationally infeasible** (คำนวณไม่ไหว) ที่เราจะเห็นเป็นตัวเลขในหัวข้อถัด ๆ ไป (ถ้าอยากทบทวนแนวคิดเรื่องความยากของปัญหาคำนวณและชั้นความซับซ้อน ดู[ตอนที่ 25 ของ CS Fundamentals](/blog/post.html?slug=2026-09-29-cs-fundamentals-25-complexity-p-np))

### 2.7 1977: DES — มาตรฐานแรก และบทเรียนราคาแพงเรื่อง "ขนาด key"

**DES** (Data Encryption Standard) เป็นมาตรฐานการเข้ารหัสของรัฐบาลสหรัฐฯ ตัวแรก (FIPS 46) ประกาศในเดือนมกราคม 1977 · ออกแบบโดย IBM และถูกปรับแก้โดย NSA · ตัวมันเองเป็น cipher ที่ "แข็งแรงตามยุค" แต่มีจุดที่กลายเป็นตำนาน: **key ยาวแค่ 56 บิต**

จากมุมของ keyspace: 2^56 = **72,057,594,037,927,936** แบบ — ฟังดูเยอะ แต่มันไม่เยอะพอ:

- **กุมภาพันธ์ 1998** RSA DES Challenge II-1 ถูกหักใน **39 วัน** ด้วยเครือข่ายคอมพิวเตอร์นับหมื่นเครื่องที่ต่อกันผ่านอินเทอร์เน็ต
- **กรกฎาคม 1998** มูลนิธิ EFF สร้างเครื่องเฉพาะทางชื่อ **Deep Crack** ด้วยงบไม่ถึง **250,000 ดอลลาร์** แล้วหัก key ครบใน **56 ชั่วโมง** (ค้นได้กว่า 88,000 ล้าน key ต่อวินาที)
- **มกราคม 1999** DES Challenge III ใช้เวลาที่เหลือ **22 ชั่วโมง 15 นาที** เท่านั้น

บทเรียน: **keyspace ไม่ได้ขึ้นกับ cipher เท่านั้น มันขึ้นกับฮาร์ดแวร์ของฝ่ายตรงข้าม ณ เวลานั้นด้วย** — และฮาร์ดแวร์มีแต่ถูกลงและเร็วขึ้น

ผลลัพธ์คือยุคของการหา DES ตัวใหม่ ซึ่งนำไปสู่ **AES**: NIST เปิดการประกวดในปี 1997 · คัดจนเหลือ 5 ตัวสุดท้าย (MARS, RC6, Rijndael, Serpent, Twofish) · **Rijndael** (ของ Joan Daemen และ Vincent Rijmen) ชนะในเดือนตุลาคม 2000 · และกลายเป็นมาตรฐานเมื่อตีพิมพ์ **FIPS 197 เมื่อ 26 พฤศจิกายน 2001** — block 128 บิต (ประมวลผลทีละ 128 บิต) · key 128/192/256 บิต

**AES ไม่พังเพราะถูกไล่ key** (2^128 = 3.4×10^38 — ไม่มีทางในทางปฏิบัติ) สิ่งที่พังคือ **วิธีใช้** และบทนี้จะโชว์ให้ดูด้วย **nonce** (nonce = ตัวเลขใช้ครั้งเดียว ผูกกับ key หนึ่งตัว ห้ามซ้ำ) ซ้ำในหัวข้อ 3.10

### 2.8 1976 → 1977: Diffie–Hellman และ RSA — ยกเครื่องทั้งแนวคิด

ทุกอย่างข้างบนเป็น **symmetric** (key เดียว) ซึ่งมีปัญหาที่แก้ไม่ได้ด้วยคณิตศาสตร์ล้วน: **ทำไมสองฝ่ายที่ยังไม่รู้จักกันถึงจะมี key ร่วมกันได้?**

- **พฤศจิกายน 1976** กระดาษสำคัญชื่อ *New Directions in Cryptography* ของ **Whitfield Diffie** และ **Martin Hellman** ให้คำตอบ: สองฝ่ายตกลง key ร่วมกันได้บนช่องทางที่ศัตรูอ่านได้ โดยไม่เคยส่ง key นั้นออกไปเลย
- **เมษายน 1977** **Ron Rivest, Adi Shamir และ Leonard Adleman** ตีพิมพ์ **RSA** — ระบบ public-key แรกที่ใช้ได้จริงสำหรับทั้งการเข้ารหัสและการเซ็นชื่อ · Martin Gardner นำไปเขียนใน *Scientific American* ฉบับสิงหาคม 1977 ในชื่อบทความที่ชวนจำว่า "A new kind of cipher that would take millions of years to break" พร้อมโจทย์ **n/modulus 129 หลัก (ciphertext 128 หลัก)** ที่ตั้งรางวัล 100 ดอลลาร์ให้ใครหักได้ (ถูกหักสำเร็จในปี 1994)

**RSA ทำงานบนความต่างของความยากสองอย่าง:**

- **คูณ**จำนวนเฉพาะใหญ่สองตัว → ง่าย (ใช้เวลาเป็นมิลลิวินาที)
- **แยกตัวประกอบ**ผลคูณกลับเป็นสองตัวนั้น → เป็นปัญหาที่เชื่อว่าไม่มีวิธีเร็วบนคอมพิวเตอร์คลาสสิก (computationally infeasible ในทางปฏิบัติ สำหรับ n ขนาดที่ใช้จริง)

เราจะเขียน RSA เองด้วย `math/big` ในหัวข้อ 3.11 เพื่อดูทุกตัวเลข (n, φ(n), e, d) และดูว่ามันพังแค่ไหนเมื่อ n เล็ก

### 2.9 1995 → 2025: TLS — crypto ที่ทำงานอยู่ทุกวินาทีที่คุณเปิดเว็บ

ทุกอย่างที่เราเรียนมาอยู่ในโปรโตคอลที่คุณใช้ทุกวันคือ **TLS** (Transport Layer Security — ชื่อเดิม **SSL** ตั้งแต่ยุค Netscape ที่ต้องการให้คนพิมพ์หมายเลขบัตรเครดิตในเบราว์เซอร์):

| รุ่น | เอกสาร | สถานะวันนี้ |
|---|---|---|
| SSL 2.0 (1995) | ไม่ได้ออกเป็น RFC | **ห้ามใช้** — RFC 6176 |
| SSL 3.0 (1996) | ไม่ได้ออกเป็น RFC | **ห้ามใช้** — RFC 7568 |
| TLS 1.0 (1999) | RFC 2246 | **เลิกใช้** — RFC 8996 |
| TLS 1.1 (2006) | RFC 4346 | **เลิกใช้** — RFC 8996 |
| TLS 1.2 (2008) | RFC 5246 (**ถูก obsoletes โดย RFC 9846**) | ใช้ได้ |
| TLS 1.3 (2018) | RFC 8446 → **ปรับปรุงเป็น RFC 9846 (ก.ค. 2026)** | **แนะนำ** |

การเปลี่ยนจาก 1.2 มาเป็น 1.3 เป็นการ **"ลบ" มากกว่า "เพิ่ม"**:

- **handshake** (ขั้นตอนที่สองฝ่ายตกลงค่าก่อนเริ่มส่งข้อมูลจริง) **เหลือ 1 round trip** และทุกอย่างหลัง ServerHello **ถูกเข้ารหัสแล้ว** — ใบรับรองไม่ต้องวิ่งบนสายแบบเปิดเผยอีก
- **key exchange ต้องเป็น ephemeral ทุกครั้ง** (ephemeral = key ชั่วคราวที่เกิดใหม่ทุกการเชื่อมต่อ ใช้แล้วทิ้ง — ปกติคือ ECDHE) → ได้ **forward secrecy** (ความลับไปข้างหน้า) เป็นคุณสมบัติของโปรโตคอล ไม่ใช่ตัวเลือกที่ต้องไปตั้งค่าเอง · นี่แปลว่าถ้า private key ของเซิร์ฟเวอร์รั่วในอนาคต ข้อมูลที่ดักไว้เมื่อวานก็ยังถอดไม่ได้
- **cipher suite** (ชุดอัลกอริทึมที่ตกลงใช้ทั้งชุด — key exchange + การเข้ารหัส + การตรวจแก้) **ที่รอดมีแต่แบบ AEAD** → กำจัดปัญหาทั้งคลาสของ **CBC padding** (การเติมไบต์ให้ครบ block ของโหมด CBC ซึ่งเป็นที่มาของช่องโหว่ padding oracle) ออกไป · รายการ suite หดจากหลายร้อยเหลือ **ห้าแบบ**
- เพิ่ม **0-RTT resumption** (กลับมาใช้ session เดิม แล้วส่งข้อมูลได้ตั้งแต่ก้อนแรกโดยไม่ต้อง handshake ใหม่) ซึ่งเร็วกว่า แต่มีข้อควรระวังที่เขียนไว้ชัดในข้อกำหนด: ข้อมูล 0-RTT **ถูก replay ได้** จึงใช้กับคำขอที่ทำซ้ำได้อย่างปลอดภัยเท่านั้น

### 2.10 วันนี้: crypto ไม่เคยสำคัญเท่านี้ และยังไม่เคยพังง่ายเท่านี้

- **OWASP Top 10:2025** จัด **A04 Cryptographic Failures** อยู่อันดับ **4** (ตกจากอันดับ 2 ในฉบับ 2021) โดยมี CWE แมปอยู่ **32 ตัว** และเก็บข้อมูลได้กว่า **1,665,348 ครั้ง** · CWE ที่โผล่บ่อยคือ **CWE-327** (ใช้ algorithm ที่พังหรือเสี่ยง), **CWE-331** (entropy ไม่พอ), **CWE-338** (ใช้ **PRNG** = ตัวสร้างเลขสุ่มเทียม ที่ไม่ปลอดภัยทาง crypto) — สังเกตว่าทั้งสามตัวเป็นเรื่อง **"ใช้ผิด"** มากกว่า **"ไม่มี"**
- **NIST SP 800-57 Part 1 Rev 5** (พฤษภาคม 2020) กำหนดว่า **112 บิต** ของ security strength ใช้ได้ถึงปี **2030** และ **128 บิต** ตั้งแต่ปี **2031** เป็นต้นไป — แปลว่า RSA-2048 (≈112 บิต) เหลือเวลาไม่มาก และ RSA-3072 (≈128 บิต) กลายเป็นค่าที่ควรใช้สำหรับระบบใหม่
- **ยุค post-quantum เริ่มแล้ว:** NIST ประกาศมาตรฐานรุ่นแรกเมื่อ **13 สิงหาคม 2024** — **FIPS 203 (ML-KEM)** สำหรับ key establishment · **FIPS 204 (ML-DSA)** และ **FIPS 205 (SLH-DSA)** สำหรับลายเซ็นดิจิทัล · ค่าเริ่มต้นที่แนะนำกว้าง ๆ คือ **ML-KEM-768** (Go มี `crypto/mlkem` ใน standard library ตั้งแต่ Go 1.24) เหตุผลเรื่องความเร่งด่วนไม่ใช่ว่าคอมพิวเตอร์ควอนตัมมีแล้ว แต่มันคือ **"harvest now, decrypt later"** — ข้อมูลที่ศัตรูดักเก็บไว้ *วันนี้* จะถูกถอดในวันที่ควอนตัมพร้อม เพราะฉะนั้นการเปลี่ยน key exchange ต้องเริ่มก่อน ไม่งั้นข้อมูลวันนี้จะไม่ลับในอีกสิบปี

### 3.2 หัวใจของ Caesar cipher: ห้าบรรทัด

นี่คือทั้ง cipher ในรูปแบบที่ใช้งานได้ (จาก `classical/classical.go`):

```go
// Normalize ตัดทุกอย่างที่ไม่ใช่ A–Z ออก แล้วแปลงเป็นตัวพิมพ์ใหญ่
// ใช้ก่อนทุกครั้งที่เราจะ "วิเคราะห์" ข้อความ เพราะการวิเคราะห์ทางสถิติ
// สนใจแค่ตัวอักษร ไม่สนใจช่องว่างหรือเครื่องหมายวรรคตอน
func Normalize(s string) string {
	var b strings.Builder
	for _, r := range strings.ToUpper(s) {
		if r >= 'A' && r <= 'Z' {
			b.WriteRune(r)
		}
	}
	return b.String()
}

// Caesar เข้ารหัส s ด้วย Caesar cipher แบบเลื่อน "ไปข้างหน้า" shift ตำแหน่ง
// shift ติดลบได้ (ถูก normalize เข้า 0–25); ตัวที่ไม่ใช่ A–Z ผ่านไปเฉย ๆ
func Caesar(s string, shift int) string {
	shift = ((shift % 26) + 26) % 26
	out := []byte(strings.ToUpper(s))
	for i, c := range out {
		if c < 'A' || c > 'Z' {
			continue
		}
		out[i] = 'A' + byte((int(c-'A')+shift)%26)
	}
	return string(out)
}

// CaesarDecrypt คือ Caesar ที่เลื่อนถอยหลัง shift ตำแหน่ง
// เขียนแยกออกมาเพราะ "ถอดรหัสด้วย Caesar" ไม่ได้แปลว่าอะไรพิเศษไปกว่า
// การเลื่อนไปในทางตรงข้าม — กุญแจของ Caesar มีแค่ 26 แบบเท่านั้น
func CaesarDecrypt(s string, shift int) string { return Caesar(s, -shift) }
```

สังเกตสิ่งสำคัญสามอย่างในโค้ดนี้:

1. **`Normalize`** แยก "ข้อความที่คนอ่าน" ออกจาก "ข้อความที่เครื่องคิด" — สถิติทั้งหมดสนใจแค่ตัวอักษร
2. **การถอดรหัสไม่ใช่อัลกอริทึมใหม่** — `CaesarDecrypt` เรียก `Caesar` ด้วย shift ที่ติดลบ · นี่คือหลักการที่ใช้จริงใน crypto สมัยใหม่ทุกตัว: **cipher และ inverse ของมันเป็นคู่ที่นิยามพร้อมกัน**
3. **ตัวอักษรที่ไม่ใช่ A–Z ผ่านไปเฉย ๆ** — เราทำแบบนี้เพื่อให้อ่านผลลัพธ์ออกด้วยตา ไม่ใช่เพราะมันปลอดภัย (ของจริง **ห้าม** ปล่อยให้ความยาวของ plaintext กับ ciphertext ต่างกันแบบเดาได้ — นั่นทำให้ attacker รู้ข้อมูลจากความยาว)

### 3.3 ผลรันจริง: Caesar แตกในเวลาไม่ถึงไมโครวินาที

ข้อความทดสอบของเรา (เขียนเองในบทนี้ ยาว **820 ตัวอักษร**) ถูกเข้ารหัสด้วย shift 7:

```
--- 1. Caesar: cipher ที่มี key แค่ 26 แบบ ---
shift          = 7
plaintext      : THE ONLY WAY TO KEEP A SECRET IS TO TRUST NOBODY WITH IT AND TO   ← ตัดมาแสดงแค่ 64 ตัวแรก (ข้อความเต็ม 820 ตัวอักษร หลังตัดช่องว่างออก)
ciphertext     : AOL VUSF DHF AV RLLW H ZLJYLA PZ AV AYBZA UVIVKF DPAO PA HUK AV 
decrypt(shift7): THE ONLY WAY TO KEEP A SECRET IS TO TRUST NOBODY WITH IT AND TO 
key space      = 26 แบบ · ถอดรหัสคือ Caesar ที่เลื่อนถอยหลัง (ไม่ใช่วิธีพิเศษอะไร)
```

แล้วลอง brute force ทั้ง 26 shift และจัดอันดับด้วย **chi-square** (ทดสอบทางสถิติที่วัดว่า "การกระจายตัวของตัวอักษรในข้อความนี้ห่างจากภาษาอังกฤษแค่ไหน" — ยิ่งน้อยยิ่งเหมือน):

```
--- 2. โจมตีแบบ brute force: ลองทั้ง 26 shift แล้วจัดอันดับด้วย chi-square ---
อันดับ 1: shift=07  chi²=   46.8  THE ONLY WAY TO KEEP A SECRET IS TO TRUST NOBO
อันดับ 2: shift=19  chi²= 1934.5  HVS CBZM KOM HC YSSD O GSQFSH WG HC HFIGH BCPC
อันดับ 3: shift=13  chi²= 2628.6  NBY IHFS QUS NI EYYJ U MYWLYN CM NI NLOMN HIVI
(จริง ๆ shift = 7 → ถูกพบเป็นอันดับที่ 1 จาก 26)
จำนวน shift ที่ต้องลองทั้งหมด = 26 — น้อยพอที่เครื่องจะลองครบในเวลาไม่ถึงไมโครวินาที
```

อ่านให้ดี: **อันดับ 1 คือ shift จริง (7) ให้คะแนน chi² = 46.8 ส่วนอันดับ 2 ได้ 1934.5** — ไม่ใช่ "ชนะแบบหวุดหวิด" แต่เป็น "ชนะแบบทิ้งห่างกันเป็นเท่าตัว" เพราะข้อความ 820 ตัวอักษรมีข้อมูลทางสถิติมากพอจะชี้ขาด

นี่คือหน้าตาของ cipher ที่ keyspace เล็ก: **ข้อความที่ยาวขึ้นไม่ช่วยอะไร** — ยิ่งยาวยิ่งหักง่ายขึ้นด้วยซ้ำ

### 3.4 frequency analysis: การโจมตีที่อายุ 1,176 ปี และยังใช้ได้

ทีนี้ลองใช้วิธีที่ Al-Kindi เขียนไว้เมื่อราวปี ค.ศ. 850 — **นับตัวอักษร** ไม่ต้องไล่ key:

```
--- 3. frequency analysis: การโจมตีที่ Al-Kindi เขียนไว้เมื่อราวปี ค.ศ. 850 ---
ตารางอ้างอิงความถี่ภาษาอังกฤษ (Lewand 2000): E 12.7% · T 9.1% · A 8.2% · O 7.5% · I 7.0% · N 6.7% · S 6.3% · H 6.1%
ตัวอักษรที่พบบ่อย 5 อันดับแรก:
  plaintext  : E(114, 13.9%) T(89, 10.9%) O(71, 8.7%) S(69, 8.4%) A(68, 8.3%)
  ciphertext : L(114, 13.9%) A(89, 10.9%) V(71, 8.7%) Z(69, 8.4%) H(68, 8.3%)
ตัวที่พบบ่อยสุดของ ciphertext คือ 'L' และของ plaintext คือ 'E' → ห่างกัน 7 ตำแหน่ง
เดาว่า 'L' = 'E' แล้วเลื่อนถอยหลัง 7 → ได้ข้อความที่อ่านออก: THE ONLY WAY TO KEEP A SECRET IS TO TRUST NOBO
chi-square ของทุก shift ก็จัดอันดับให้ shift=7 อยู่อันดับ 1 ด้วย (บรรทัดบน)
```

จับตาสามบรรทัดนี้:

- `plaintext : E(114, 13.9%) T(89, 10.9%) O(71, 8.7%) S(69, 8.4%) A(68, 8.3%)`
- `ciphertext : L(114, 13.9%) A(89, 10.9%) V(71, 8.7%) Z(69, 8.4%) H(68, 8.3%)`
- **`ตัวที่พบบ่อยสุดของ ciphertext คือ 'L' ... ห่างกัน 7 ตำแหน่ง`**

จำนวนการนับเท่ากันเป๊ะ ๆ · ลำดับเหมือนกันเป๊ะ ๆ · ต่างกันแค่ "ชื่อตัวอักษร" ที่ถูกเลื่อนไป 7 ตำแหน่ง · เราเดาว่า `L` = `E` แล้วได้ shift 7 ออกมา **โดยไม่ต้องลอง key เลย** — ใช้แค่ความรู้ว่า "ข้อความภาษาอังกฤษมี E เยอะ"

นี่คือเหตุผลที่ substitution cipher **ตาย** ตั้งแต่ปี ค.ศ. 850 และเป็นเหตุผลที่คนคิด cipher ยุคต่อมาต้องหาวิธี "เกลี่ยความถี่ให้แบน"

### 3.5 Vigenère: เกลี่ยความถี่สำเร็จ แต่ทิ้งรอยอื่นไว้

Vigenère ทำงานแบบนี้: เลื่อนตัวอักษรตัวที่ i ด้วยค่าของ key ตัวที่ i mod len(key) — ด้วย key `LEMON` (ค่าตัวอักษร L=11, E=4, M=12, O=14, N=13) keystream จะวนซ้ำแบบนี้:

```
--- 4. Vigenère: cipher ที่เลื่อนตัวอักษรละแบบ ---
key            = LEMON (5 ตัวอักษร)
keystream      : LEMONLEMONLEMONLEMONLEMONLEMONLEMONLEMONLEMONLEMONLEMONLEMONLEMO  ← ตัดมาแสดงแค่ 64 ตัวแรก (keystream เต็มยาว 820 ตัว เท่าจำนวนตัวอักษรของข้อความ)
ciphertext     : ELQ CAWC IOL ES WSRA E ESPCIF WF ES FFHDX ZCOZHK KVEL UH NYH FC 
decrypt(key)   : THE ONLY WAY TO KEEP A SECRET IS TO TRUST NOBODY WITH IT AND TO 
ข้อสังเกตสำคัญ: ตัวอักษรตัวเดียวกันของ plaintext กลายเป็นตัวอักษร cipher ไม่เหมือนกัน
  ตัวอักษร 'E': Caesar ให้ตัวอักษร cipher ต่างกัน 1 แบบ · Vigenère ให้ 5 แบบ
keystream มีคาบเท่ากับความยาว key — ความยาว key จึงเป็น "ความลับหนึ่งเดียว" ที่ attacker ต้องหา
```

สองบรรทัดที่สำคัญที่สุด:

- **`ตัวอักษร 'E': Caesar ให้ตัวอักษร cipher ต่างกัน 1 แบบ · Vigenère ให้ 5 แบบ`** — ใน Caesar ตัว `E` ทุกตัวกลายเป็นตัวเดียวกันเสมอ (นั่นคือที่ที่ frequency analysis เข้าได้) แต่ใน Vigenère ตัว `E` กลายเป็น 5 ตัวที่ต่างกัน เพราะถูกเลื่อนด้วยค่าที่ต่างกัน 5 ค่า
- **`keystream มีคาบเท่ากับความยาว key`** — และนี่คือรอยรั่วใหม่: **ความยาว key กลายเป็น "ความลับหนึ่งเดียว" ที่ attacker ต้องหา** ถ้าเขาหามันเจอ งานที่เหลือก็เป็นแค่ "โจมตี Caesar หลายชุดพร้อมกัน"

แต่ก่อนจะไปถึงตรงนั้น เขาต้องผ่านด่านแรกก่อน — และนี่คือคำตอบของคำถามข้อ 2.4 ว่าทำไม frequency analysis ตรง ๆ ใช้ไม่ได้:

```
--- 5. frequency analysis ใช้กับ Vigenère ตรง ๆ ได้ไหม ---
index of coincidence (IC) — ยิ่งเข้าใกล้ 0.066 ยิ่งเหมือนภาษาอังกฤษธรรมชาติ
  plaintext  = 0.0701  (ภาษาอังกฤษ)
  caesar     = 0.0701  (เท่าเดิมเป๊ะ ๆ กับการเลื่อนชื่อตัวอักษร)
  vigenere   = 0.0424  (แบนลงอย่างชัดเจน)
ตัวอักษรที่พบบ่อย 3 อันดับแรก:
  caesar     : L(114, 13.9%) A(89, 10.9%) V(71, 8.7%)   ← ยอดแหลมยังอยู่ครบ
  vigenere   : E(52, 6.3%) S(51, 6.2%) R(48, 5.9%)   ← ยอดถูกเกลี่ยให้แบน
→ การนับตัวอักษรตรง ๆ หัก Vigenère ไม่ได้ · ต้องหาความยาว key ให้ได้ก่อน
```

อ่านตัวเลขให้ดี (นี่คือหัวใจของ Vigenère):

- `IC` ของ plaintext = **0.0701** (ข้อความอังกฤษธรรมชาติ — ใกล้ค่า 0.066 ที่ท่องกัน)
- `IC` ของ Caesar = **0.0701** — **เท่ากันเป๊ะ** เพราะการเลื่อนชื่อตัวอักษรไม่เปลี่ยนความถี่เลย
- `IC` ของ Vigenère = **0.0424** — **ลดลงเกือบเท่าความสุ่ม** (0.0424 เทียบ 0.038 ของข้อความสุ่มในกรอบผลรัน · 1/26 = 0.0385)
- และยอดที่เคยแหลม (`L(114, 13.9%)`) ถูกเกลี่ยเหลือ (`E(52, 6.3%)`) — **ยอดหายไป**

เพราะฉะนั้นการหัก Vigenère ต้องแบ่งเป็นสองจังหวะ และนี่คือโค้ดที่ทำจังหวะที่สอง (หา key ทีละคอลัมน์ ซึ่งเมื่อแยกแล้วแต่ละคอลัมน์ **กลับเป็น Caesar**):

```go
// CrackVigenere หัก Vigenère เต็มขั้นตอน: เดาคาบด้วย IC → แยกคอลัมน์ →
// หา shift ที่ดีที่สุดของแต่ละคอลัมน์ด้วย chi-square → ประกอบเป็น key
// คืนค่า key ที่กู้ได้, คาบที่ใช้, และผลการเดารายคอลัมน์ (shift + ตัวอักษร)
func CrackVigenere(s string, maxPeriod int, threshold float64) (key string, period int, shifts []int, ranked []ICSample) {
	period, ranked = GuessKeyLength(s, maxPeriod, threshold)
	cols := SplitPeriods(s, period)
	kb := make([]byte, 0, period)
	for _, col := range cols {
		best, bestChi := 0, math.Inf(1)
		for shift := 0; shift < 26; shift++ {
			if chi := ChiSquare(CaesarDecrypt(col, shift)); chi < bestChi {
				best, bestChi = shift, chi
			}
		}
		kb = append(kb, byte('A'+best))
		shifts = append(shifts, best)
	}
	return string(kb), period, shifts, ranked
}
```

และผลรันจริงของการหักครบขั้นตอน:

```
--- 6. หัก Vigenère: เดาความยาว key จาก IC ก่อน แล้วค่อยแยกทีละคอลัมน์ ---
  p=20  mean_IC=0.0704
  p= 5  mean_IC=0.0695  ← คาบที่เล็กที่สุดที่ผ่านเกณฑ์
  p=10  mean_IC=0.0693
  p=15  mean_IC=0.0680
เกณฑ์ที่ใช้: mean_IC ≥ 0.055 (อยู่ระหว่าง 0.038 ของข้อความสุ่ม กับ 0.066 ของภาษาอังกฤษ)
ความยาว key ที่เลือก = 5
  คอลัมน์ 1: หา shift ที่ chi-square ต่ำสุดได้ 11 → ตัวอักษร 'L'
  คอลัมน์ 2: หา shift ที่ chi-square ต่ำสุดได้  4 → ตัวอักษร 'E'
  คอลัมน์ 3: หา shift ที่ chi-square ต่ำสุดได้ 12 → ตัวอักษร 'M'
  คอลัมน์ 4: หา shift ที่ chi-square ต่ำสุดได้ 14 → ตัวอักษร 'O'
  คอลัมน์ 5: หา shift ที่ chi-square ต่ำสุดได้ 13 → ตัวอักษร 'N'

```

**`key ที่กู้ได้ = LEMON (ของจริง LEMON)`** — ตรงเป๊ะ ไม่มีเดา

ขอชี้จุดที่ซื่อสัตย์กับผู้อ่าน — ตารางคาบข้างบนมีเรื่องที่ต้องอธิบาย:

- **`p=20` ให้ `mean_IC=0.0704` สูงกว่า `p=5` ที่ได้ `0.0695`** — นี่ไม่ใช่บั๊ก แต่เป็นธรรมชาติของสถิติบนข้อความสั้น
- **คาบที่เป็นพหุคูณของคาบจริง (5, 10, 15, 20) ให้ IC สูงพอกันหมด** — เพราะแยกเป็น 20 คอลัมน์ก็ยังได้คอลัมน์ที่เป็น Caesar อยู่ดี
- **ยิ่งแยกคอลัมน์มาก ตัวอักษรต่อคอลัมน์ยิ่งน้อย ค่า IC ยิ่งแกว่ง** (p=20 เหลือคอลัมน์ละ 41 ตัวอักษร)
- **วิธีที่ใช้จริงจึงเลือก "คาบที่เล็กที่สุดที่ผ่านเกณฑ์"** (ในโค้ดคือ `mean_IC ≥ 0.055` แล้วเลือกตัวที่เล็กสุด) ซึ่งได้ 5 อย่างถูกต้อง

**บทเรียนจากข้อ 3.5:** Vigenère "แก้" ช่องโหว่ของ Caesar ได้จริงในระดับความถี่ — แต่ทิ้ง **รอยใหม่** ไว้คือคาบของ keystream · crypto ทุกวันนี้คือเกมแบบเดียวกันนี้เป๊ะ ๆ: **เราไม่ได้สร้าง cipher ที่หักไม่ได้ เราแค่ทำให้การหักมันแพงกว่าผลตอบแทน**

### 3.6 hash ≠ encryption — สามคำที่คนใช้ปนกันบ่อยที่สุด

**hash function** (ฟังก์ชันแฮช) เช่น **SHA-256** รับข้อมูลอะไรก็ได้ แล้วคืนค่าไบต์คงที่ (256 บิต = 32 ไบต์) โดยมีคุณสมบัติสามข้อ:

1. **deterministic** — ข้อมูลเดิมได้ค่าเดิมเสมอ
2. **one-way** — ย้อนกลับจากค่า hash ไปหาข้อมูลต้นทางไม่ได้ (ไม่มี key ให้ใช้ถอด)
3. **avalanche effect** — เปลี่ยน input แค่ 1 ตัว ค่าที่ได้ "เปลี่ยนทั้งก้อน"

```
--- 1. hash ≠ encryption ---
SHA-256("correct horse battery staple") = c4bbcb1fbec99d65bf59d85c8cb62ee2db963f0fe106f483d9afa73bd4e39a8a
SHA-256("correct horse battery staplf") = 7b21f13de330753042fd37aa7ccf1aee712eba586faa3812f4d618994d9872d9
เปลี่ยน input 1 ตัว → บิตที่ต่างกัน 141 จาก 256 (55.1%)
คำนวณซ้ำด้วย input เดิม → ได้ค่าเดิม: true
hash ไม่มี key → ย้อนกลับไม่ได้ แต่ก็ไม่ได้ซ่อนอะไร: ใครมี input ก็คำนวณซ้ำได้
```

ดูผลรัน: เปลี่ยน `staple` เป็น `staplf` (ตัวเดียวท้ายสุด) แล้วบิตที่ต่างกันคือ **141 จาก 256 บิต (55.1%)** — ใกล้เคียง "ครึ่งหนึ่ง" ที่ควรจะเป็นแบบสุ่ม ต่างกันสิ้นเชิงกับการแก้ข้อความปกติที่ "แก้ตัวเดียวก็เปลี่ยนตัวเดียว"

และข้อที่คนพลาดบ่อยที่สุด (เขียนไว้เป็นตัวนับในผลรันด้วย): **`hash ไม่มี key → ย้อนกลับไม่ได้ แต่ก็ไม่ได้ซ่อนอะไร`** — ใครที่รู้ input ก็คำนวณซ้ำได้ · และในทางกลับกัน **ใครที่เดา input ได้ก็ตรวจได้ว่าเดาถูกไหม** ซึ่งในบริบทของ "เก็บรหัสผ่าน" มันคือหายนะ (จะอธิบายในข้อ 3.9)

### 3.7 AES-256-GCM: confidentiality + integrity ในครั้งเดียว

นี่คือ cipher ที่คุณควรใช้ และนี่คือโค้ดที่ใช้จริง (จาก `modern/main.go`):

```go
	// ---------- 2. AES-256-GCM ----------
	fmt.Println("--- 2. AES-256-GCM: confidentiality + integrity พร้อมกันในครั้งเดียว (AEAD) ---")
	// aes.NewCipher: เลือก AES ตามความยาว key (32 ไบต์ = AES-256) แล้วคืน block cipher
	blk, err := aes.NewCipher(demoKey)
	if err != nil {
		panic(err)
	}
	// cipher.NewGCM: ห่อ block cipher เป็นโหมด GCM (AEAD) — เข้ารหัส + ตรวจ tag ในตัวเดียว
	gcm, err := cipher.NewGCM(blk)
	if err != nil {
		panic(err)
	}
	fmt.Printf("key   (%2d byte) = %s\n", len(demoKey), hex.EncodeToString(demoKey))
	fmt.Printf("nonce (%2d byte) = %s\n", len(demoNonce), hex.EncodeToString(demoNonce))
	// gcm.Overhead(): ความยาว tag ที่ GCM ต่อท้ายให้เอง (16 ไบต์) — ไม่ต้องเก็บแยก
	fmt.Printf("tag   (%2d byte) = ส่วนท้ายที่ GCM ต่อให้อัตโนมัติ (ตรวจการแก้ไข)\n", gcm.Overhead())
	fmt.Printf("plaintext       = %q\n", demoMessage)
	// gcm.Seal: เข้ารหัส + ต่อ tag ให้เสร็จในครั้งเดียว (nil = ให้จัดหน่วยความจำใหม่เอง)
	// AAD ถูกส่งเข้าไปด้วย: ไม่ถูกเข้ารหัส แต่ถูกตรวจการแก้ และผูกกับ ciphertext ก้อนนี้
	ct := gcm.Seal(nil, demoNonce, []byte(demoMessage), []byte(demoAAD))
	fmt.Printf("ciphertext+tag  = %s\n", hex.EncodeToString(ct))
	fmt.Printf("                  (%d byte = %d ของข้อความ + %d ของ tag)\n",
		len(ct), len(demoMessage), gcm.Overhead())
	// gcm.Open: ตรวจ tag ก่อน แล้วจึงถอดรหัส — tag ไม่ตรงจะคืน error และไม่คืนข้อความ
	pt, err := gcm.Open(nil, demoNonce, ct, []byte(demoAAD))
	fmt.Printf("open(ciphertext) = %q  (err=%v)\n", string(pt), err)
	fmt.Printf("plaintext_round_trip = %d\n", boolToInt(err == nil && string(pt) == demoMessage))
```

และผลรันจริง — โดยเฉพาะส่วนที่ "ลองแก้ข้อมูลทีละแบบ":

```

nonce (12 byte) = a0a1a2a3a4a5a6a7a8a9aaab

                  (48 byte = 32 ของข้อความ + 16 ของ tag)

  ลองแก้ข้อมูลทีละแบบ — GCM จะไม่ยอมคืนข้อความเลยถ้าตรวจไม่ผ่าน:
  แก้ ciphertext 1 บิต → err=cipher: message authentication failed  (detected=1)
  แก้ tag 1 บิต       → err=cipher: message authentication failed  (detected=1)
  แก้ AAD 1 ตัวอักษร  → err=cipher: message authentication failed  (detected=1)

```

สี่บรรทัดที่ต้องอ่านให้ครบ:

```
  แก้ ciphertext 1 บิต → err=cipher: message authentication failed  (detected=1)
  แก้ tag 1 บิต       → err=cipher: message authentication failed  (detected=1)
  แก้ AAD 1 ตัวอักษร  → err=cipher: message authentication failed  (detected=1)
  ใช้ key ผิด         → err=cipher: message authentication failed  (detected=1)
```

**ข้อความ error เดียวกันทั้งสี่กรณี — และนั่นคือสิ่งที่ถูกต้อง** นี่คือหลัก **fail closed** (ตรวจไม่ผ่าน = ปฏิเสธไปเลย ไม่พยายามเดาต่อ) **/ ไม่บอกข้อมูลเพิ่ม**: ไม่ว่า attacker จะทำผิดแบบไหน เขาก็ได้คำตอบเดียว · ถ้าเราคืน error ที่ต่างกัน (เช่น "tag ผิด" กับ "key ผิด") เราก็กำลังช่วยเขาแยกแยะความพยายามของตัวเอง

อีกจุดที่ต้องสังเกต: ในกรอบผลรันมีบรรทัด **`(48 byte = 32 ของข้อความ + 16 ของ tag)`** — ciphertext ที่ได้ยาว 48 ไบต์ = ข้อความ 32 ไบต์ + tag 16 ไบต์ (ตรงกับ `gcm_tag_bytes=16` ใน `out/02_modern.txt`) · และค่า **`tag (16 byte)`** นี้เองคือส่วนที่ให้ **integrity** ส่วนที่เข้ารหัสคือ **confidentiality**

**AAD (Additional Authenticated Data)** คือส่วนที่ผมอยากให้จำเป็นพิเศษ: มันคือข้อมูลที่ **ไม่ถูกเข้ารหัส** แต่ **ถูกตรวจการแก้** · ใช้กับสิ่งที่ต้องอ่านได้ระหว่างทางแต่ห้ามแก้ เช่นหมายเลขเวอร์ชันโปรโตคอลหรือ header · ผลรันบรรทัดที่สามพิสูจน์ว่ามันทำงาน: แก้ AAD แค่ตัวอักษรเดียว → `Open` ปฏิเสธทันที แม้ ciphertext จะไม่ถูกแตะเลย

### 3.8 HMAC: integrity ที่ "ไม่ได้" ให้ confidentiality

**HMAC** (Keyed-Hash Message Authentication Code) คือเอา hash + key มารวมกัน เพื่อให้ได้ **MAC** — ค่าที่พิสูจน์ว่าข้อความ "มาจากคนที่มี key" และ "ไม่ถูกแก้" โดยไม่ต้องซ่อนข้อความ:

```
--- 3. HMAC-SHA256: integrity โดยไม่ปิดบังความลับ ---
message        = "TRANSFER 1000 THB TO ACCOUNT 777"
อ่านข้อความได้   = 1  ← HMAC ไม่ได้ซ่อนข้อความเลย (ต่างจาก AES-GCM)
hmac           = 94faf11c37e112e734f84b7e12836206f540223b4100a30a88a405f2d093d0cb
verify(ข้อความแท้)                = true
verify(แก้เลข 777 → 999)          = false
ใช้ hmac.Equal เท่านั้น: เทียบ bytes ตรง ๆ ด้วย == จะรั่วเวลา (timing side channel)
```

สังเกตบรรทัด `อ่านข้อความได้ = 1 ← HMAC ไม่ได้ซ่อนข้อความเลย (ต่างจาก AES-GCM)` — **นี่คือความต่างที่ต้องเข้าใจให้ลึก**:

| | AES-GCM | HMAC |
|---|---|---|
| confidentiality | ✅ | ❌ (ข้อความอ่านได้ตรง ๆ) |
| integrity | ✅ (tag) | ✅ (MAC) |
| ต้องการ key | ✅ | ✅ |
| ใช้เมื่อไหร่ | ต้องซ่อนข้อความ | แค่ต้องรู้ว่าถูกแก้ไหม |

และข้อสุดท้ายในบล็อกนั้นคือกับดักที่คนพลาดกันจริง ๆ: **`ใช้ hmac.Equal เท่านั้น`** — การเทียบ MAC ด้วย `==` (หรือ `bytes.Equal`) จะ **คืนค่าต่างกันเร็วกว่า** เมื่อ MAC ตรงกันยาวขึ้นเรื่อย ๆ ทำให้ attacker ที่วัดเวลาได้ฟื้น MAC ทีละไบต์ได้ · นี่เรียกว่า **timing side channel** และเป็นเหตุผลที่คนเขียน crypto ต้องใช้ฟังก์ชันที่ออกแบบมาสำหรับงานนี้โดยเฉพาะ

### 3.9 จาก "รหัสผ่านที่คนจำได้" ไปเป็น "key 32 ไบต์"

ข้อ 3.8 ปิดท้ายที่ความต่างระหว่าง "ซ่อนข้อความ" (AES-GCM) กับ "แค่รู้ว่ามีคนแก้" (HMAC) — แต่ทั้งคู่เริ่มจาก **key** ที่สุ่มเต็มที่ แล้วคำถามที่ยังค้างอยู่คือ: key พวกนั้นมาจากไหน ในเมื่อสิ่งที่มนุษย์มีจริง ๆ คือ "รหัสผ่าน"?

ปัญหาที่ทุกคนเจอ: รหัสผ่านของผู้ใช้ยาว 20 ตัวอักษร แต่ AES ต้องการ key 32 ไบต์ที่ **สุ่มเต็มที่** · การนำรหัสผ่านไปแปะเป็น key ตรง ๆ เป็นความผิดมหันต์ (เพราะพื้นที่ของ "รหัสผ่านที่คนจำได้" เล็กกว่าพื้นที่ key มาก)

ก่อนไปต่อ — **salt** คือค่าสุ่มที่เก็บคู่กับผู้ใช้แต่ละคน แล้วใส่เข้าไปใน **key derivation function (KDF)** เพื่อให้รหัสผ่านเดียวกันได้ key ที่ต่างกันในแต่ละคน (ดูผลรันด้านล่าง: salt ต่าง → key ต่าง)

และ KDF ที่เราใช้จริงในบทนี้คือ `crypto/pbkdf2`:

```go
	// ---------- 4. PBKDF2 ----------
	fmt.Println("--- 4. PBKDF2: จากรหัสผ่านที่คนจำได้ → key 32 byte ---")
	fmt.Printf("iterations ที่ OWASP แนะนำ (PBKDF2-HMAC-SHA256) = %d\n", owaspIters)
	fmt.Printf("salt1 (%d byte) = %s\n", len(saltOne), hex.EncodeToString(saltOne))
	fmt.Printf("salt2 (%d byte) = %s\n", len(saltTwo), hex.EncodeToString(saltTwo))
	// pbkdf2.Key(hash, password, salt, iterations, keyLen) — เรียงตามนี้: sha256.New · รหัสผ่าน
	// · salt 16 ไบต์ · 600,000 รอบ · แล้วตัด key ออกมา 32 ไบต์ (ตัวสุดท้าย = "ความยาว key ที่ต้องการ")
	k1, _ := pbkdf2.Key(sha256.New, demoPass, saltOne, owaspIters, 32)
	k2, _ := pbkdf2.Key(sha256.New, demoPass, saltTwo, owaspIters, 32)
	k3, _ := pbkdf2.Key(sha256.New, demoPass, saltOne, weakIters, 32)
	fmt.Printf("pbkdf2(salt1, %q, %d) = %s\n", demoPass, owaspIters, hex.EncodeToString(k1))
	fmt.Printf("pbkdf2(salt2, รหัสเดิม, %d)          = %s\n", owaspIters, hex.EncodeToString(k2))
	fmt.Printf("pbkdf2(salt1, รหัสเดิม, %7d)          = %s\n", weakIters, hex.EncodeToString(k3))
	fmt.Printf("salt ต่าง → key ต่าง        : %d\n", boolToInt(!bytes.Equal(k1, k2)))
	fmt.Printf("iterations ต่าง → key ต่าง  : %d\n", boolToInt(!bytes.Equal(k1, k3)))
	fmt.Printf("เทียบแบบ constant time      : %d (ใช้ subtle.ConstantTimeCompare)\n", subtle.ConstantTimeCompare(k1, k1))
```


ในบล็อกผลรันข้างบน สองบรรทัดนี้คือคู่ที่ต้องอ่านด้วยกัน (ตัดมาแค่ครึ่งแรกของค่า hex ให้อ่านง่าย — ค่าเต็มอยู่ใน `out/02_modern.txt`):
`pbkdf2(salt1, "correct horse battery staple", 600000) = a7fe3eb8f898393305a3096819bf09ef…` กับ `pbkdf2(salt2, รหัสเดิม, 600000) = 7e5a418e0ee349197a01a04c30212590…`

**รหัสผ่านเดียวกัน แต่ salt ต่างกัน → key ที่ได้ไม่เหมือนกันเลย** · นี่คือกลไกที่ฆ่า **rainbow table** (ตาราง precompute ของ hash ที่คนร้ายสร้างล่วงหน้า) เพราะเขาไม่สามารถคำนวณล่วงหน้าได้อีก — ต้องคำนวณสด ๆ ต่อ salt ต่อผู้ใช้

และทำไม `600000` ถึงสำคัญ? เพราะจำนวน iterations คือมาตรวัดว่า **"แพงแค่ไหนต่อการเดาหนึ่งครั้ง"** — ยิ่งมาก การเดาแต่ละครั้งยิ่งแพง

คู่มือ *OWASP Password Storage Cheat Sheet* แนะนำ **PBKDF2-HMAC-SHA256 จำนวน 600,000 iterations** · ถ้าเลือกได้ ตัวเลือกแรกที่แนะนำคือ **Argon2id** (memory 19 MiB, iterations 2, parallelism 1) และสำหรับระบบเดิมที่ใช้ **bcrypt** อยู่แล้ว ให้ work factor ≥ 10

เทียบกับ SHA-256 เปล่า ๆ ที่คำนวณได้หลายพันล้านครั้งต่อวินาที — ต่างกันเป็นหลักล้านเท่า และนั่นคือความต่างระหว่าง "รหัสผ่านถูกเดาเสร็จในหนึ่งวัน" กับ "ถูกเดาเสร็จในหนึ่งศตวรรษ"

**สิ่งที่ต้องเข้าใจให้ถูก:** รหัสผ่านเดียวกัน + salt เดียวกัน + iterations เดียวกัน → key เดียวกันเสมอ (ผลรันยืนยัน: `salt ต่าง → key ต่าง : 1` และ `iterations ต่าง → key ต่าง : 1`) · KDF ไม่ได้ทำให้ "คาดเดาไม่ได้" มันแค่ทำให้ **การเดาแต่ละครั้งแพงขึ้น**

### 3.10 "cipher ที่เขียนเอง" พังตรงไหน — และของจริงก็พังด้วย

เรามาเขียน cipher เองกัน — XOR ข้อมูลกับ keystream ที่วนซ้ำจาก key สั้น ๆ วิธีนี้ดูฉลาดมากในตอนแรก (และมัน **คือ** รากของ one-time pad ซึ่งปลอดภัยที่สุดในทางทฤษฎี) แต่มีจุดที่ต้องจับตา:

```go
// xorBytes คือ "cipher" ทั้งหมดของเรา — XOR ข้อมูลกับ keystream ทีละไบต์
// (ในเกรด crypto จริง การ XOR กับ keystream สุ่มยาวเท่าข้อความคือ one-time pad
//  ซึ่งปลอดภัยที่สุดในทางทฤษฎี · ปัญหาทั้งหมดอยู่ที่ "keystream มาจากไหน")
func xorBytes(data, stream []byte) []byte {
	out := make([]byte, len(data))
	for i := range data {
		out[i] = data[i] ^ stream[i]
	}
	return out
}

// keystreamFrom สร้าง keystream จาก key โดย "วนซ้ำ" ให้ยาวเท่าที่ต้องการ
// ← บรรทัดนี้คือบั๊กทั้งหมดของไฟล์นี้
func keystreamFrom(key []byte, n int) []byte {
	out := make([]byte, n)
	for i := 0; i < n; i++ {
		out[i] = key[i%len(key)]
	}
	return out
}
```

```
--- 1. stream cipher ที่ประกอบเองจาก key 6 ไบต์ ---
key             = "SECRET" (6 ไบต์)
keystream       = SECRETSECRETSECRETSECRET  ← วนซ้ำทุก 6 ไบต์ (รอยรั่วที่ 1) · พิมพ์มาแค่ 24 ไบต์แรก (ข้อความยาว 26)
message         = "TRANSFER 1000 THB TO ALICE"
ciphertext (hex)= 0717021c16121617636375646365171a0774070a6313091d1000
ดูเผิน ๆ ก็ "เข้ารหัสแล้ว" — attacker อ่าน hex ตรง ๆ ไม่ออกจริง ๆ
```

`ciphertext (hex)` ที่ได้ดู "สุ่มดี" จริง ๆ — แต่มีรอยรั่วที่ซ่อนอยู่: **keystream วนซ้ำทุก 6 ไบต์** ถ้า attacker รู้ข้อความแค่ 6 ไบต์แรก เขาก็ได้ key ทั้งตัว:

```
--- 2. โจมตีด้วย known-plaintext (attacker รู้ว่า request ขึ้นต้นว่าอะไร) ---
attacker เดาว่า 6 ไบต์แรกของข้อความคือ "TRANSF"
c XOR guess    = keystream = SECRET  ← กลายเป็น key ทั้งตัว
ถอดทั้งก้อน     = "TRANSFER 1000 THB TO ALICE"
ตรงกับต้นฉบับ   = true
บทเรียน: cipher ที่ไม่มี padding / IV (ค่าตั้งต้นที่ต้องสุ่มใหม่ทุกก้อน) / keystream สุ่ม = ข้อมูลรู้บางส่วน → key หลุดทั้งตัว
```

`c XOR guess = keystream = SECRET ← กลายเป็น key ทั้งตัว` · นี่คือ **known-plaintext attack** (การโจมตีด้วยข้อความที่รู้ล่วงหน้า) — และในโลกจริงมัน **ง่ายมาก** ที่ attacker จะรู้ข้อความบางส่วน เช่น request ที่ขึ้นต้นด้วย `GET /` เสมอ หรือ field ที่มีค่าคงที่

รอยรั่วที่สองโหดกว่านั้น — **ใช้ keystream ชุดเดิมสองครั้ง**:

```
--- 3. สองข้อความใช้ keystream เดียวกัน (two-time pad) ---
m1 = "TRANSFER 1000 THB TO ALICE"
m2 = "TRANSFER 9000 THB TO EVE!!"
c1 ^ c2 = 000000000000000000080000000000000000000000041a0c6264  ← key ไม่โผล่เลย (มันตัดกันเอง)
ไบต์ที่เท่ากันในสองข้อความ = 20 จาก 26 (ตำแหน่งนั้น c1^c2 = 0x00 → attacker รู้ทันที)
นี่คือเหตุผลที่ one-time pad ต้อง "ใช้ครั้งเดียว" — ใช้ซ้ำเมื่อไรก็เป็นแบบนี้เสมอ:
attacker รู้ m1 (เช่น เป็นข้อความของตัวเอง) → m2 = m1 ^ (c1 ^ c2) = "TRANSFER 9000 THB TO EVE!!"
กู้ m2 ได้ตรงเป๊ะ = true
```

คณิตศาสตร์ของมันสวยงามจนน่ากลัว:

```text
c1 = m1 ⊕ k        (⊕ คือ XOR — สลับบิต)
c2 = m2 ⊕ k
c1 ⊕ c2 = (m1 ⊕ k) ⊕ (m2 ⊕ k) = m1 ⊕ m2 ⊕ (k ⊕ k) = m1 ⊕ m2
```

**key หายไปทั้งตัว** — และผลรันยืนยันเป๊ะ ๆ: `c1 ^ c2` ให้ค่า byte ที่ **เหมือนกับ** `m1 ^ m2` ทุกไบต์ · นี่คือเหตุผลที่ one-time pad ต้อง "ใช้ครั้งเดียว" จริง ๆ ไม่ใช่ชื่อเล่น

นี่เรียกว่า **two-time pad** และมันคือสาเหตุของหายนะ crypto ในโลกจริงซ้ำแล้วซ้ำอีก (เพราะคนมักคิดว่า "ใช้ key เดิมหลายครั้งก็ได้ถ้าเปลี่ยนอะไรนิดหน่อย")

**แล้วของจริงพังแบบนี้ไหม?** คำตอบคือ **พัง — ถ้าใช้ผิดวิธีเดียวกัน** และนี่คือผลรันที่ผมอยากให้ทุกคนดูมากที่สุดในบทนี้:

```
--- 4. ของจริงก็พังถ้า nonce ซ้ำ — นี่คือเหตุผลที่ nonce ห้ามซ้ำเด็ดขาด ---
AES-256-GCM · key เดียว · nonce ซ้ำ:
  c1 ^ c2        = 000000000000000000080000000000000000000000041a0c6264
  m1 ^ m2        = 000000000000000000080000000000000000000000041a0c6264
  เท่ากันหรือไม่   = true  ← ข้อความรั่วแบบ two-time pad เป๊ะ
  และ tag ก็รั่วด้วย — Joux (2006) พิสูจน์ว่า nonce ซ้ำทำให้ผู้โจมตีฟื้นกุญแจตรวจสอบ (H) ได้

แต่ถ้าใช้ nonce ใหม่ทุกครั้ง:
  c1 ^ c2 = m1 ^ m2 หรือไม่ = false  ← ปลอดภัย
สรุป: ความต่างระหว่าง "เข้ารหัสแล้ว" กับ "เข้ารหัสถูก" อยู่ที่รายละเอียดแบบนี้
       ซึ่งเป็นเหตุผลที่เราใช้ library ที่ผ่านการตรวจ ไม่ใช่เขียนเอง
```

อ่านสามบรรทัดนี้ให้ช้า ๆ:

```
  c1 ^ c2        = 000000000000000000080000000000000000000000041a0c6264
  m1 ^ m2        = 000000000000000000080000000000000000000000041a0c6264
  เท่ากันหรือไม่   = true  ← ข้อความรั่วแบบ two-time pad เป๊ะ
```

**AES-256-GCM** — cipher ที่ไม่มีใครหักด้วยกำลังดิบได้ — ให้ผลลัพธ์ที่ **รั่วแบบเดียวกับ cipher ของเล่นที่เราเขียนเองเป๊ะ ๆ** เมื่อใช้ nonce ซ้ำกับ key เดิม · และร้ายกว่านั้น: งานวิเคราะห์ของ **Antoine Joux** (*Authentication Failures in NIST version of GCM*, 2006) แสดงว่า nonce ซ้ำยังทำให้ผู้โจมตี **ฟื้นกุญแจตรวจสอบยืนยัน (authentication key H)** ได้ ซึ่งแปลว่าเขาสามารถ **ปลอม tag** ให้ข้อความที่เขาแต่งเองได้ตามใจ

แล้วถ้าใช้ nonce ใหม่ทุกครั้งล่ะ? บรรทัดสุดท้ายตอบให้: **`c1 ^ c2 = m1 ^ m2 หรือไม่ = false ← ปลอดภัย`**

> **นี่คือเหตุผลที่ตอนนี้ต้องมี:** "เข้ารหัสแล้ว" กับ "เข้ารหัสถูก" ต่างกันที่รายละเอียดแบบนี้ — และรายละเอียดแบบนี้ไม่ใช่สิ่งที่เราควรคิดเองตอนตีสอง เพราะมันคือเหตุผลที่เราใช้ **`crypto/cipher` ของ standard library** ที่ผ่านการตรวจจากคนทั้งโลก ไม่ใช่การ XOR ที่เราเพิ่งคิดออกเอง

**ข้อควรระวังเวลาใช้ GCM ในงานจริง:** nonce ยาว 12 ไบต์ต้อง **ไม่ซ้ำเด็ดขาดภายใต้ key เดียวกัน** วิธีที่ปลอดภัยที่สุดคือ **สุ่ม nonce ใหม่ด้วย `crypto/rand` ทุกครั้ง** (และยอมรับความเสี่ยง **birthday bound** = โอกาสที่ nonce สุ่มสองตัวจะชนกันเมื่อใช้ไปหลายก้อน ซึ่งตามทฤษฎีต้องถึงหลัก 2^48 ก้อนต่อ key — แต่ **NIST SP 800-38D §8.3** กำหนดเพดานใช้งานจริงไว้ต่ำกว่านั้นมาก: ราว 2^32 ครั้งต่อ key เพื่อให้ความน่าจะเป็นที่ชนกัน ≤ 2^-32) หรือใช้ **counter ที่ไม่ซ้ำแน่นอน** — แต่ห้ามใช้ `math/rand`, ห้ามใช้เวลาปัจจุบัน, และห้ามใช้ counter ที่รีเซ็ตตอนรีสตาร์ท

### 3.11 RSA: จากคณิตศาสตร์ล้วน ถึงของที่ใช้ได้จริง

เราเขียน RSA เองสองรอบ: รอบแรกด้วย `math/big` เพื่อให้เห็นทุกตัวเลข รอบที่สองด้วย `crypto/rsa` เพื่อดูว่าของจริงต่างกันตรงไหน

```go
	// ---------- 1. สร้าง key แบบเห็นทุกตัวเลข ----------
	fmt.Println("--- 1. สร้าง key จากจำนวนเฉพาะสองตัว (ขั้นตอนเดียวกับ RSA จริง) ---")
	// Mul = คูณเลขขนาดไม่จำกัด: n = p*q (modulus ที่ประกาศเป็น public key)
	n := new(big.Int).Mul(toyP, toyQ)
	// Sub = ลบ: p−1 และ q−1 (ต้องเป็นแบบนี้เพราะ φ(n) = (p−1)(q−1) เมื่อ p, q เป็นจำนวนเฉพาะ)
	pMinus1 := new(big.Int).Sub(toyP, big.NewInt(1))
	qMinus1 := new(big.Int).Sub(toyQ, big.NewInt(1))
	// φ(n) = (p−1)(q−1) — จำนวนของเลขที่ coprime กับ n ในช่วง 1..n
	phi := new(big.Int).Mul(pMinus1, qMinus1)
	// e = 65537 = 2^16+1 — public exponent ที่นิยมใช้จริง (คูณเร็ว และมีบิตเป็น 1 แค่สองตัว)
	e := big.NewInt(65537)
	// ModInverse = หา d ที่ e·d ≡ 1 (mod φ) — ขั้นนี้ต้องรู้ p, q เท่านั้น (นี่คือความลับของ RSA)
	d := new(big.Int).ModInverse(e, phi)
	fmt.Printf("p            = %v\n", toyP)
	fmt.Printf("q            = %v\n", toyQ)
	fmt.Printf("n = p*q      = %v   (%d บิต)\n", n, n.BitLen())
	fmt.Printf("φ(n) = (p-1)(q-1) = %v\n", phi)
	fmt.Printf("e            = %v   (ค่าที่นิยมใช้จริง: 65537)\n", e)
	fmt.Printf("d = e⁻¹ mod φ = %v   ← เฉพาะคนที่รู้ p และ q หาเลขตัวนี้ได้\n", d)
	fmt.Println("public key   = (n, e)  ← บอกใครก็ได้")
	fmt.Println("private key  = (d)     ← เก็บไว้ การหัก RSA = การหา d จาก (n, e)")
```

```
--- 1. สร้าง key จากจำนวนเฉพาะสองตัว (ขั้นตอนเดียวกับ RSA จริง) ---
p            = 10007
q            = 10009
n = p*q      = 100160063   (27 บิต)
φ(n) = (p-1)(q-1) = 100140048
e            = 65537   (ค่าที่นิยมใช้จริง: 65537)
d = e⁻¹ mod φ = 35910881   ← เฉพาะคนที่รู้ p และ q หาเลขตัวนี้ได้
public key   = (n, e)  ← บอกใครก็ได้
private key  = (d)     ← เก็บไว้ การหัก RSA = การหา d จาก (n, e)
```

ทั้งหมดที่ RSA ทำคือ **ยกกำลังแบบ modulo** — สามฟังก์ชันล้วน ๆ:

- `c = m^e mod n` (เข้ารหัส, ใครก็ทำได้เพราะ `(n, e)` คือ public key)
- `m = c^d mod n` (ถอดรหัส, ต้องมี `d`)
- `d = e⁻¹ mod φ(n)` (หา inverse ของ e — **เฉพาะคนที่รู้ p และ q เท่านั้นที่หาได้**)

ความปลอดภัยทั้งหมดพึ่งข้อเท็จจริงเดียว: **หา `d` จาก `(n, e)` ได้ก็ต่อเมื่อแยกตัวประกอบ `n` ได้** และการแยกตัวประกอบ n ที่ใหญ่พอเป็นปัญหาที่เชื่อว่าไม่มีวิธีเร็วบนคอมพิวเตอร์คลาสสิก (computationally infeasible ในทางปฏิบัติ)

**กับดักที่หนึ่ง: RSA แบบไม่ใส่ padding เป็น deterministic** — ข้อความเดิมได้ ciphertext เดิมทุกครั้ง ซึ่งแปลว่า attacker รู้ทันทีว่า "สองข้อความนี้เหมือนกัน" โดยไม่ต้องถอดรหัสอะไรเลย:

```
--- 3. กับดักแรก: ถ้าไม่ใส่ padding ผลลัพธ์จะ "เดิมทุกครั้ง" ---
c ครั้งที่ 1 = 9294169
c ครั้งที่ 2 = 9294169
เท่ากัน: true  → ข้อความเดิมได้ ciphertext เดิม (attacker รู้ว่า "เท่ากัน" ทันที)
และถ้าข้อความสั้น ciphertext จะสั้นด้วย — ดูจาก BitLen ตัวอย่างเช่น m=42
นี่คือเหตุผลที่ RSA จริง "ต้อง" มี padding (OAEP) — ดูข้อ 6
```

**กับดักที่สอง: n เล็กก็พังด้วยการลองหาร** — จำนวนรอบของ trial division เป็นสัดส่วนกับ √n:

```
--- 4. หักมัน: trial division กับ n ที่เล็กระหว่าง 10007 กับ 10009 ---
trial_division_steps = 10006 รอบ ก็เจอตัวประกอบแล้ว: 10007
(วิธีนี้คือ "ลองหารทุกเลขจนถึง √n" — จำนวนรอบจึงเป็นสัดส่วนกับ √n)
```

**กับดักที่สาม (ที่คนไม่ค่อยรู้): ถ้า p กับ q อยู่ใกล้กัน มีวิธีที่เร็วกว่ามาก** — **Fermat factoring** อาศัยการเขียน `n = a² − b² = (a−b)(a+b)`:

```
--- 5. กับดักที่สาม: ถ้า p กับ q "ใกล้กัน" มีวิธีที่เร็วกว่า trial division ---
Fermat factoring ใช้แค่ 1 รอบก็เจอ (p=10007, q=10009 ต่างกันแค่ 2)
  a = (p+q)/2 = 10008 · b = (q-p)/2 = 1 · และ a² − b² = n เป๊ะ ๆ
บทเรียน: p กับ q ต้องห่างกันมาก ๆ — เครื่องมือสร้าง key ที่ดีบังคับเงื่อนไขนี้ให้เอง
```

`Fermat factoring ใช้แค่ 1 รอบก็เจอ` — **1 รอบ** เทียบกับการลองหาร 10,006 รอบ · นี่คือเหตุผลที่ key generator ที่ดี **บังคับ** ให้ p กับ q ห่างกันมาก ๆ

แล้วของจริงล่ะ? `crypto/rsa` จัดการทั้งหมดนี้ให้ และเพิ่มสิ่งที่ขาดไม่ได้คือ padding แบบสุ่ม:

```
--- 6. RSA ของจริง (crypto/rsa): 2048 บิต + padding + ลายเซ็นดิจิทัล ---
rsa_key_bits            = 2048
primes_per_key          = 2
|p−q| ใหญ่พอกันไหม      = true  (เกิน 1,000 บิต — กัน Fermat factoring ในกับดักที่สาม)
e                       = 65537
→ สร้างใหม่ทุกรอบ (ค่าต่างกันทุกครั้ง) เราจึงไม่พิมพ์เลขของ key ลงในบทความ
signature_bytes         = 256  (= 2048/8)
verify(ข้อความแท้)       = <nil>
verify(แก้ 1000→9000)    = crypto/rsa: verification error  ← ลายเซ็นไม่ผ่าน
OAEP เข้ารหัสข้อความเดิม 2 ครั้ง ได้ ciphertext เท่ากันไหม: false
→ padding แบบสุ่ม "ทำลาย" ความ deterministic ที่เป็นจุดอ่อนของข้อ 3
→ และลายเซ็นให้ "authenticity" ไม่ได้ให้ "confidentiality" (ข้อความยังอ่านได้ปกติ)
```

เปรียบเทียบให้เห็นชัด: ข้อ 3 บอกว่า ciphertext เดิมสองครั้งเท่ากัน (`true`) แต่ของจริงบอกว่า **`OAEP เข้ารหัสข้อความเดิม 2 ครั้ง ได้ ciphertext เท่ากันไหม: false`** — padding แบบ **OAEP** (Optimal Asymmetric Encryption Padding) ใส่ค่าสุ่มเข้าไป ทำให้ ciphertext ต่างกันทุกครั้งที่เข้ารหัส · **นี่คือการ "ปิดกับดักที่หนึ่ง" ด้วยการออกแบบ**

และสองบรรทัดสุดท้ายของบล็อกนั้นสำคัญเท่ากับทั้งบท:

- **ลายเซ็นดิจิทัลให้ authenticity ไม่ได้ให้ confidentiality** — ข้อความที่เซ็นแล้วยังอ่านได้ปกติทุกตัวอักษร (เหมือน HMAC ในข้อ 3.8)
- ลายเซ็นยาว **256 ไบต์** = 2048/8 · เพราะมันคือค่าที่ถูกยกกำลังด้วย `d` mod `n` ก็เลยยาวเท่า modulus เป๊ะ ๆ

![comparison of key space sizes for Caesar, Vigenere, DES, AES-128 and RSA-2048 with the work required to break each](/assets/diagrams/ep06-04-keyspace.svg)

**ตัวเลขที่ควรจำจาก RSA ในงานจริง:**

| ประเด็น | ตัวเลข |
|---|---|
| RSA-250 (829 บิต) ถูกแยกตัวประกอบได้ | 28 กุมภาพันธ์ 2020 ด้วยกำลังราว **2,700 core-years** (sieving 2,450 + matrix 250) |
| RSA-240 (795 บิต) | ธันวาคม 2019 |
| ขนาดที่ NIST แนะนำ | **≥ 2048 บิต** ถึงปี 2030 · **≥ 3072 บิต** ตั้งแต่ปี 2031 |

และเราก็ **วัดค่าของจริงบนเครื่องเราเองได้** ด้วยตัวนับในผลรัน: `trial_division_steps_rsa2048_digits=309` — นั่นคือ √(2^2048) = 2^1024 เป็นเลข **309 หลัก** · ที่ความเร็ว 10^9 รอบต่อวินาทีต่อเครื่อง ก็ยังต้องใช้เวลาราว **10^281 เท่าของอายุเอกภพ** · นี่คือความหมายของคำว่า **computationally infeasible**

### 3.12 TLS จริง ๆ: เปิดเซิร์ฟเวอร์ ต่อเป็น client แล้วดูว่า "บนสาย" เห็นอะไร

เรามาปิดท้ายด้วยของจริงในชีวิตประจำวัน เราเขียนเดโมที่ (ก) สร้าง **CA** (Certificate Authority = หน่วยที่ออกใบรับรองและเป็น "รากที่เชื่อถือได้") และใบรับรองขึ้นเองในหน่วยความจำ (ข) เปิดเซิร์ฟเวอร์ HTTPS บน loopback (ค) ลอง client สามแบบ และ (ง) **ดักอ่านไบต์ที่วิ่งบนสายจากในโปรเซสเอง**

หัวใจของ "ดักอ่าน" อยู่ที่การห่อ connection เพื่อแอบคัดลอกทุกไบต์ที่ `Read`:

```go
func (c *sniffConn) Read(p []byte) (int, error) {
	n, err := c.Conn.Read(p)
	if n > 0 {
		// mu.Lock(): Read ถูกเรียกจากหลาย goroutine — ต้องล็อกก่อนแตะ buf ไม่งั้น append ชนกัน (race)
		c.l.mu.Lock()
		// เก็บแค่ 16 KiB แรก เพื่อไม่ให้หน่วยความจำบวม (พอสำหรับดูว่า "บนสาย" เห็นอะไร)
		if len(c.l.buf) < 16384 {
			c.l.buf = append(c.l.buf, p[:n]...)
		}
		c.l.mu.Unlock()
	}
	return n, err
}
```

**client แบบที่ 1 — ไม่รู้จัก CA นี้:** เบราว์เซอร์/โปรแกรมที่ไม่มี CA ของเราใน **trust store** (รายการรากที่เชื่อถือได้ซึ่งติดมากับ OS หรือเบราว์เซอร์) จะปฏิเสธทันที:

```
--- 2. client ที่ "ไม่รู้จัก" CA นี้ → ปฏิเสธการเชื่อมต่อ ---
untrusted_client_error = tls: failed to verify certificate: x509: certificate signed by unknown authority
untrusted_client_blocked = true   ← นี่คือสิ่งที่หยุด MITM
ถ้าเบราว์เซอร์ยอมเชื่อมต่อทุกใบรับรอง ใครก็แอบอยู่กลางได้ — authenticity จึงต้องมี "รากที่เชื่อ"
```

`tls: failed to verify certificate: x509: certificate signed by unknown authority` — **นี่คือบรรทัดที่หยุดการโจมตี MITM (Man-in-the-Middle = ผู้โจมตีแทรกกลางวง) ทั้งหมดบนอินเทอร์เน็ต** · ถ้าไม่มีกลไกนี้ ใครก็ตั้งเซิร์ฟเวอร์ปลอมแล้วดักข้อมูลได้

**client แบบที่ 2 — เชื่อ CA แต่ต่อด้วย "ชื่ออื่น":** เราออกใบรับรองให้ IP `127.0.0.1` เท่านั้น (ตั้งใจไม่ใส่ DNS name) แล้วลองต่อด้วยชื่อ `localhost`:

```
--- 3. client ที่เชื่อ CA นี้ แต่ต่อด้วย "ชื่ออื่น" → ปฏิเสธเหมือนกัน ---
wrong_hostname_error = tls: failed to verify certificate: x509: certificate is not valid for any names, but wanted to match localhost
wrong_hostname_blocked = true
ใบรับรองผูกกับ "ชื่อ/ที่อยู่" ไม่ใช่แค่ "กุญแจ" — ต่อผิดชื่อเท่ากับคุยกับคนอื่น
```

**ใบรับรองผูกกับ "ชื่อ/ที่อยู่" ไม่ใช่แค่ "กุญแจ"** — ต่อผิดชื่อเท่ากับคุยกับคนละคน นี่คือเหตุผลที่การโจมตีแบบ certificate ที่ถูกต้องแต่วางผิดบริบทไม่มีทางสำเร็จ

**client แบบที่ 3 — เชื่อ CA และชื่อตรง:**

```
--- 4. client ที่เชื่อ CA นี้และต่อด้วยชื่อที่ตรง → handshake สำเร็จ ---
negotiated_version = TLS 1.3
negotiated_cipher  = TLS_AES_128_GCM_SHA256
server_authenticated = true
handshake_complete   = true
response_body        = "server เห็นข้อมูล 16 ไบต์"
TLS 1.3: key exchange ใช้ ephemeral (ECDHE) ทุกครั้ง → ย้อนหลังถอดไม่ได้ (forward secrecy)
         cipher suite ที่รอดมีแต่แบบ AEAD (เข้ารหัส+ตรวจแก้ในครั้งเดียว) — RFC 9846
```

`negotiated_version = TLS 1.3` · `negotiated_cipher = TLS_AES_128_GCM_SHA256` · `server_authenticated = true` — handshake จริง สมบูรณ์ บนเครื่องเดียว ไม่แตะเครือข่ายภายนอกเลย

และส่วนที่สนุกที่สุด — **attacker ที่นั่งอยู่บนสายเห็นอะไร**:

```
--- 5. eavesdropper ที่นั่งอยู่บนสาย (sniffer ในโปรเซสนี้) เห็นอะไร ---
plain HTTP : sees_method=true  sees_payload=true  sees_password=true
TLS        : sees_method=false  sees_payload=false  sees_password=false
TLS บนสาย · ไบต์แรก 3 ไบต์ = 160301   (0x16 = handshake record · 0x0301 = เวอร์ชันของ record layer)
หลัง ClientHello จบ ทุกไบต์ที่เหลือบนสายถูกเข้ารหัสแล้ว — ไม่มีคำว่า password หลุดออกไปเลย
(ส่วน hex ของไบต์ที่ดักได้ เราไม่ยกมาอ้างเพราะมีค่าสุ่มจากการ handshake ปนอยู่ทุกครั้ง)
```

อ่านเทียบทีละบรรทัด:

```
plain HTTP : sees_method=true  sees_payload=true  sees_password=true
TLS        : sees_method=false  sees_payload=false  sees_password=false
```

เราส่งข้อมูล **ชุดเดียวกันเป๊ะ ๆ** (`password=hunter2`) ไปทั้งสองเซิร์ฟเวอร์ · บน HTTP ธรรมดา attacker เห็นทั้ง method, body และรหัสผ่าน · บน TLS **ไม่เห็นสักอย่าง** แม้แต่คำว่า `POST`

และบรรทัดที่แสดงว่าเราพิสูจน์อย่างซื่อสัตย์: `TLS บนสาย · ไบต์แรก 3 ไบต์ = 160301` — สามไบต์แรกของ stream คือ **record header ของ handshake** (`0x16` = handshake record · `0x0301` = เวอร์ชันของ record layer) ซึ่งยืนยันว่าเรากำลังดู TLS record จริง ๆ ไม่ใช่ข้อมูลที่ถูกแปลงหน้าตา

**ความซื่อสัตย์ทางเทคนิคที่ต้องบอก:** ใน TLS 1.3 **ClientHello ยังส่งแบบเปิดเผย** (ในเดโมนี้จึงยังเห็นไบต์หัวเป็น record ปกติ) ซึ่งหมายความว่าบาง metadata เช่นชื่อเซิร์ฟเวอร์ (SNI) และขนาดของข้อมูลยังมองเห็นได้ · TLS 1.3 เองก็เขียนไว้ชัดในข้อกำหนดว่า **"TLS does not hide the length of the data it transmits"** — มันซ่อน *เนื้อหา* ไม่ได้ซ่อน *ว่ามีการคุยกันเกิดขึ้น* เรื่องนี้จำได้เลยว่าเป็นหัวข้อของ **traffic analysis** และเป็นข้อจำกัดที่รู้กันดี ไม่ใช่ช่องโหว่

### ระดับ Drill (5–10 นาที)

1. **ถอด Caesar ที่กำหนด** — ciphertext นี้ถูกเข้ารหัสด้วย Caesar cipher (ตัวอักษร A–Z เท่านั้น, ช่องว่างคงเดิม):
   `JXDUG WKH VHFUHWV RI WKH GDUN`
   จงหาข้อความต้นฉบับและ shift ที่ใช้ · **เขียนเหตุผลว่าทำไมคุณถึงเลือก shift นั้น** (ห้ามเดา — ให้ใช้การนับตัวอักษรที่พบบ่อยที่สุด)
2. **อธิบายด้วยคำของคุณเอง** ว่าทำไม `IC` ของ Caesar **เท่ากับ** IC ของ plaintext เป๊ะ ๆ ในขณะที่ IC ของ Vigenère **ลดลง** · คำตอบต้องพูดถึงคำว่า "ความถี่" และ "การเลื่อนชื่อตัวอักษร" ไม่ใช่แค่ "เพราะ cipher ต่างกัน"
3. **หา key ของ Vigenère ที่ยาว 3 ตัว** จาก ciphertext นี้ (ข้อความภาษาไทย **ไม่ต้อง** — ใช้ข้อความอังกฤษสั้น ๆ ที่คุณเขียนเองกับ key 3 ตัว แล้วให้เพื่อนถอด) · เขียนอธิบายว่าคุณแยกคอลัมน์ยังไง
4. **`IC` ของข้อความสุ่มเท่ากับเท่าไร และทำไม?** — เขียนทั้งสูตรและเหตุผล (ใบ้: คิดว่าในข้อความสุ่ม ตัวอักษรแต่ละตัวมีโอกาสเกิดเท่าไร และ `Σ nᵢ(nᵢ−1)` กลายเป็นอะไร)
5. **จากข้อ 3.9:** ถ้าเราใช้ `SHA-256(password)` เก็บรหัสผ่านแทน PBKDF2+600k iterations ให้ประเมินว่าแย่ลงกี่เท่า · แล้วอธิบายว่าทำไม **salt** ถึงจำเป็นแยกจากเรื่อง iterations (สองอย่างนี้แก้ปัญหาคนละอย่าง)
6. **จากข้อ 3.12:** ในบล็อกผลรัน TLS มีบรรทัด `sees_payload=false` และ `TLS บนสาย · ไบต์แรก 3 ไบต์ = 160301` · อธิบายว่าทั้งสองอย่างนี้สอดคล้องกันได้ยังไง ทั้งที่เราบอกว่า "TLS ซ่อนทุกอย่าง"

## 5. สรุปตอนที่ 06

- **cipher คือฟังก์ชันที่มี key** — plaintext → ciphertext → plaintext กลับมา · และความลับทั้งหมดต้องอยู่ที่ **key** เท่านั้น (Kerckhoffs's principle, 1883) ไม่ใช่ที่ "ความลับของวิธี"
- **CIA triad สามข้อแรกมาจาก crypto สามตัวคนละตัว:** **confidentiality** มาจากการเข้ารหัส (AES-GCM) · **integrity** มาจาก tag/MAC (GCM tag 16 ไบต์ · HMAC 32 ไบต์) · **authenticity** มาจากลายเซ็นและ certificate (RSA 2048 = ลายเซ็น 256 ไบต์) · และทั้งสาม **แยกกันพังได้** — hash ให้ integrity แต่ไม่ให้ authenticity เพราะใครก็สร้าง hash ได้
- **ประวัติศาสตร์คือบันทึกของช่องโหว่ที่ถูกปิดทีละชั้น:** Caesar (keyspace 26) → ถูกหักด้วย brute force · substitution ทั้งคลาส → ถูกหักด้วย **frequency analysis** ของ Al-Kindi (ค.ศ. 850) · **Vigenère** (1553) เกลี่ยความถี่สำเร็จ (IC 0.0701 → **0.0424**) แต่ทิ้ง **คาบของ keystream** ไว้ → **Kasiski** (1863) ใช้มันหัก · **Enigma** ปลอดภัยทางคณิตศาสตร์แต่พังเพราะ **กระบวนการของคน** · **DES** (1977) พังเพราะ key 56 บิตเล็กเกินไป (Deep Crack 1998: **56 ชั่วโมง** แล้วเหลือ **22 ชั่วโมง 15 นาที** ในปี 1999) · **AES** (2001) ไม่พังด้วยกำลัง แต่พังด้วย **วิธีใช้**
- **RSA ทำงานเพราะความต่างของความยากสองอย่าง:** คูณจำนวนเฉพาะ = ง่าย · แยกตัวประกอบ = computationally infeasible (√(2^2048) = 2^1024 = เลข **309 หลัก**) · ของเล่นของเรา (n 27 บิต) ถูกแยกใน 10,006 รอบ; RSA-250 (829 บิต) ถูกแยกจริงในปี 2020 ด้วยกำลังราว 2,700 core-years; NIST แนะนำ **≥ 2048 บิต** ถึงปี 2030 และ **≥ 3072 บิต** หลังจากนั้น
- **บทเรียนที่สำคัญที่สุดของบทนี้ (พิสูจน์ด้วยผลรัน):** "เข้ารหัสแล้ว" ≠ "เข้ารหัสถูก" · AES-256-GCM ที่ **ไม่มีใครหักด้วยกำลังดิบได้** ให้ผลลัพธ์ที่ **รั่วแบบ two-time pad เป๊ะ ๆ** (`c1 ⊕ c2` = `m1 ⊕ m2`) เมื่อใช้ **nonce ซ้ำ** · และถ้าใช้ nonce ใหม่ทุกครั้งก็ปลอดภัย · **ความต่างทั้งหมดอยู่ที่รายละเอียดไม่กี่บรรทัด — ซึ่งคือเหตุผลที่เราห้ามเขียน crypto เองในงานจริง** (หัวข้อ 3.10 และ 3.11)
- **ของจริงที่ใช้ได้:** AES-256-GCM สำหรับเข้ารหัส+ตรวจแก้ · HMAC-SHA256 สำหรับ integrity ที่ไม่ต้องซ่อน (ใช้ `hmac.Equal` เท่านั้น) · PBKDF2-HMAC-SHA256 **600,000 iterations** (หรือ Argon2id) พร้อม **salt ใหม่ต่อผู้ใช้** สำหรับเก็บรหัสผ่าน · RSA-OAEP หรือ ECDSA สำหรับ public-key · และ **TLS 1.3** สำหรับทุกอย่างที่วิ่งบนสาย
- **TLS ในชีวิตจริง (ผลรันของเราเอง):** client ที่ไม่รู้จัก CA → ปฏิเสธ (`x509: certificate signed by unknown authority`) · client ที่ต่อผิดชื่อ → ปฏิเสธ · client ที่เชื่อ CA และชื่อตรง → **TLS 1.3 + TLS_AES_128_GCM_SHA256** สำเร็จ · และ eavesdropper บนสาย: HTTP ธรรมดาเห็น `sees_password=true` แต่ TLS เห็น `false` ทุกช่อง
- **วันนี้:** OWASP Top 10:2025 จัด **A04 Cryptographic Failures** อันดับ 4 (32 CWE, 1,665,348 ครั้ง) · NIST SP 800-57 Rev 5 ให้ **112 บิตถึงปี 2030, 128 บิตหลังจากนั้น** · และยุค **post-quantum** เริ่มแล้ว (FIPS 203/204/205, 13 ส.ค. 2024) เพราะภัยที่แท้จริงของวันนี้ไม่ใช่ "ควอนตัมมีแล้ว" แต่คือ **"harvest now, decrypt later"**
- **คำถามที่ควรถามตัวเองก่อนปิดบทนี้:** *"ในโปรเจกต์ที่ฉันดูแลอยู่ มีที่ไหนที่ฉัน **เข้ารหัสเอง แฮชเอง หรือ XOR เอง** แทนที่จะเรียก library? และมีที่ไหนที่ฉันใช้ nonce/key/salt ซ้ำ?"* สองข้อนี้ครอบสาเหตุของ crypto failure ส่วนใหญ่ในโลกจริงไว้แล้ว

ตอนหน้า (ตอนที่ 07) เราจะอยู่กับหัวข้อเดิมแต่เปลี่ยนมุม: เราจะไปดู **วันที่ crypto ที่ "ถูกต้องตามตำรา" ยังพังได้** — เพราะบั๊กไม่ได้อยู่ในคณิตศาสตร์ แต่อยู่ใน **หน่วยความจำ** · เราจะเล่าเรื่อง **Heartbleed (2014)** ช่องโหว่ใน OpenSSL ที่อ่านหน่วยความจำเกินขอบเขต แล้วปล่อยความลับออกไปทีละ 64 กิโลไบต์ · และเราจะตอบคำถามที่ต่อจากบทนี้ตรง ๆ: *ถ้า library ที่คนทั้งโลกร่วมกันตรวจ ยังพลาดได้ แล้วเราควรพึ่งอะไร?* (คำตอบจะพาไปที่ memory-safe languages อย่าง Go และ Rust — ซึ่งเป็นเส้นเรื่องที่ตอนที่ 02 และ 03 ปูไว้แล้ว)

ระหว่างรอ ลองหาจุดที่โปรเจกต์คุณใช้ `math/rand` ในบริบทความปลอดภัย แล้วเปลี่ยนเป็น `crypto/rand` — ถ้าเจอ นั่นคืองานที่ควรทำก่อนสิ่งอื่น

  - **nonce ซ้ำใน GCM** — Antoine Joux, *Authentication Failures in NIST version of GCM* (2006): repeated IV ทำให้ผู้โจมตีเรียนรู้ **authentication key H** และปลอม tag ได้ — <https://csrc.nist.gov/csrc/media/projects/block-cipher-techniques/documents/bcm/joux_comments.pdf>
- ภาพ SVG ทั้งสี่ภาพในตอนนี้สร้างจากสคริปต์ `security/code/ep06/gen_svgs.py` ที่ดึงตัวเลขจาก `out/` โดยตรง (มี `assert` ตรวจค่าที่ parse ได้ว่าตรงกับค่าที่คาด เช่น `caesar_keyspace == 26`, `shift_from_top == caesar_shift == 7`, `vig_recovered_exact == 1`, `plain_sees_pw == 1 and tls_sees_pw == 0`) และผ่านประตูตรวจ `check_svg_readability.py` (วัดความกว้างข้อความจริงเทียบขอบ viewBox ตรวจข้อความซ้อนกัน) รวมทั้งตรวจด้วยตาจากการ render จริงด้วย `rsvg-convert`
- **จริยธรรม (ย้ำอีกครั้ง — สำคัญที่สุด):** บทนี้สอน **วิธีหัก cipher** ตั้งแต่ brute force, frequency analysis, index of coincidence, known-plaintext ไปจนถึง two-time pad ตรง ๆ · เทคนิคทั้งหมดนี้ **ใช้ได้กับระบบของคนอื่นโดยไม่ได้รับอนุญาตไม่ได้** และเป็นความผิดทางกฎหมายในแทบทุกประเทศ · เดโมของเราทำกับข้อความที่เราเขียนเองและ socket ของตัวเองเท่านั้น · **โค้ด crypto ที่เขียนเองในบทนี้ (Caesar, Vigenère, XOR cipher, RSA ของเล่น) เป็นเพื่อการศึกษาเท่านั้น ห้ามใช้ใน production เด็ดขาด** — ของจริงต้องใช้ library มาตรฐาน (`crypto/*` ของ Go) เพราะรายละเอียดอย่าง padding, nonce, constant-time comparison และ error ที่ไม่รั่วข้อมูล คือส่วนที่ทำให้ crypto ปลอดภัยจริง และเป็นส่วนที่เรามักมองข้ามเมื่อเขียนเอง
