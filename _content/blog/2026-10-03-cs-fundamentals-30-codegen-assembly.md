# codegen → assembly — แปลงต้นไม้ให้เป็นโค้ดเครื่อง (ตอนที่ 30)

ตอนที่ 26–29 เราสร้างของสามชิ้นที่เปลี่ยนข้อความโปรแกรมให้กลายเป็น "ความหมาย": **lexer** ตัดข้อความออกเป็น token (ชิ้นคำ), **parser** ประกอบ token ขึ้นเป็นต้นไม้ AST (abstract syntax tree = ต้นไม้โครงสร้างของโปรแกรม), แล้ว **interpreter** (ตอน 28) เดินตามต้นไม้คำนวณค่าออกมา และ **type checker** (ตอน 29) เดินตามต้นไม้เพื่อพิสูจน์ "ชนิด" ก่อนรัน

แต่ทุกอย่างยังมีจุดร่วมจุดเดียว — มัน "อยู่ใน Go" ทั้งหมด ตัว interpreter เองก็คือโปรแกรม Go ที่ค่อย ๆ เดินต้นไม้ที่เก็บอยู่ใน **memory** (หน่วยความจำ = ที่พักข้อมูลของโปรแกรมระหว่างรัน) ของ Go เอง

```text
ข้อความ → lexer (26) → parser (27) → interpreter (28) → ค่า        ← เดินต้นไม้ "ตอนรัน"
                                     → check (29) → ชนิด           ← เดินต้นไม้ "ก่อนรัน"
```

ตอนนี้เราจะเดินไปจนถึงปลายทางจริงของภาษาทุกภาษา: **codegen** (ย่อจาก code generation = การสร้างโค้ด) เปลี่ยนต้นไม้ให้กลายเป็น**ภาษาแอสเซมบลี** (assembly — ภาษาที่เครื่องอ่านได้โดยตรง ต่างจาก**ซอร์สโค้ด**ซึ่งเป็นโค้ดที่คนเขียนและคนอ่าน)

จากนั้นเอา assembly ไปผ่านเครื่องมือสองตัวของเครื่อง:

1. **assembler** แปล assembly → **object** (ไฟล์กลางที่ยังรันไม่ได้ มีโค้ดเครื่องแต่ยังไม่ผูกที่อยู่)
2. **linker** แปล object → **executable** (ไฟล์ที่รันได้จริง)

ผลลัพธ์คือโปรแกรมที่รันได้จริงโดย**ไม่มี interpreter มาคั่นกลาง**

> **ที่อยู่ของโค้ดในตอนนี้:** ทุกอย่างอยู่ใน `course/code/ep30/`
> - **01–05** = โฟลเดอร์โปรแกรม แยกตามเลขโปรแกรม
> - **`out/`** = ผลรันจริงของทุกโปรแกรม — `00_env.txt` = สภาพแวดล้อม (เวอร์ชัน Go/เครื่อง/assembler/วันที่) · `06_drill_answer.out.txt` = เฉลยโจทย์ท้ายบท
> - **`internal/codegen/`** = ตัวสร้างโค้ด (ไฟล์ `codegen.go` + `run.go`) ที่ทุกโปรแกรมเรียกใช้ร่วมกัน · **`internal/lexer/` + `parser/` + `eval/` + `check/`** = ของเดิมจากตอน 26–29

![ไปป์ไลน์ครบวงจร: จากข้อความ ไปจนถึงโค้ดเครื่องที่รันได้จริง](/assets/diagrams/ep30-01-pipeline.svg)

ภาพข้างบนคือภาพรวมทั้งตอน: ไปป์ไลน์เดิมของเราจบที่ "อยู่ใน Go" ตอนนี้เราต่อหางออกไปให้ถึงปลายทางจริง — **codegen** (ช่องสีน้ำเงิน) เดินต้นไม้แล้วปล่อย assembly ออกมา แล้ว **as** (assembler) กับ **ld** (linker) แปลให้กลายเป็น executable ที่ CPU รันได้โดยตรง

## 1. ปัญหา: "เดินต้นไม้" กับ "สร้างโค้ด" ต่างกันตรงไหน

ย้อนไปดู interpreter ของตอนที่ 28 หนึ่งก้าว มันมีฟังก์ชัน `eval` ที่หน้าตาประมาณนี้ (ย่อมาเฉพาะแก่น) — ก่อนดูโค้ด รู้จักศัพท์สองตัวที่ใช้ตลอดตอน: **node** (โหนด = จุดหนึ่งจุดบนต้นไม้ AST เช่น ตัวเลขตัวเดียวก็เป็น node หนึ่ง ต้นไม้ทั้งต้นประกอบจาก node หลายตัว) และ **switch** (คำสั่งใน Go ที่ "เลือกสาขาตามชนิดของ node" — ถ้าเป็นตัวเลขทำแบบหนึ่ง ถ้าเป็นนิพจน์บวกทำอีกแบบ):

```go
func (in *Interpreter) eval(e parser.Expr, depth int) (Value, error) {
    switch n := e.(type) {
    case *parser.NumberLit:
        return in.done(e, depth, IntValue(n.Value))   // ตัวเลข → กลายเป็น "ค่า" ทันที
    case *parser.BinaryExpr:
        left, _ := in.eval(n.Left, depth+1)           // คำนวณลูกซ้าย
        right, _ := in.eval(n.Right, depth+1)         // คำนวณลูกขวา
        return IntValue(left.Num + right.Num)         // บวกแล้วคืน "ค่า"
    }
    ...
}
```

สังเกตสิ่งที่ interpreter ทำ: มัน**คำนวณค่าทันที** — เจอ `3 + 4` มันก็บวกให้เลย ได้ `7` ออกมา แล้วเก็บ `7` ไว้ในตัวแปร Go ความรู้เรื่อง "จะบวกยังไง" อยู่ใน**ตัวโค้ด Go เอง** (บรรทัด `left.Num + right.Num`) ไม่มีวันออกไปนอกโปรแกรม Go

codegen ทำตรงกันข้าม: มัน**ไม่คำนวณค่าเลย** แต่มัน**พิมพ์คำสั่งที่เครื่องจะใช้คำนวณออกมา** แทนที่จะเขียน `return left.Num + right.Num` มันเขียนข้อความ `add x0, x0, x1` ลงในไฟล์ (คำสั่ง "บวก" จริง ๆ ของเครื่อง) ผลลัพธ์ของ codegen ไม่ใช่ตัวเลข แต่เป็น**ข้อความโค้ด**ที่เอาไปรันทีหลังได้

ตอนนี้ต้องรู้จักศัพท์ภาษาแอสเซมบลีสองตัวที่ใช้ซ้ำตลอดทั้งตอน (จะเห็น `x0` `x1` `add` `mov` แบบนี้ทั้งบท):

> **register** (รีจิสเตอร์) = ช่องเก็บค่าขนาดเล็กที่อยู่**ในตัว CPU** เอง เร็วที่สุดแต่มีจำนวนจำกัด บนสถาปัตยกรรม aarch64 (สถาปัตยกรรมของ Raspberry Pi 5 ที่รันบทความนี้) มี 31 ตัว ชื่อ `x0` ถึง `x30` — ในตอนนี้เราจอง `x0` เป็น "ที่เก็บผลลัพธ์ของนิพจน์" และ `x1` เป็น "ตัวช่วยตัวที่สอง"
>
> **instruction** (อินสตรักชัน = คำสั่งเครื่อง) = คำสั่งหนึ่งบรรทัดที่ CPU ทำได้ เช่น `mov x0, #3` แปลว่า "ยัดเลข 3 ใส่ register x0" · `add x0, x0, x1` แปลว่า "x0 = x0 + x1" · `ldr x0, [x29, #-16]` แปลว่า "อ่านค่าใน memory ตรงตำแหน่ง (x29 ลบ 16) มาใส่ x0"

นี่คือหัวใจของตอนนี้: **interpreter เดินต้นไม้เพื่อ "ได้ค่า" · codegen เดินต้นไม้เพื่อ "ได้โค้ด"** — ต้นไม้ต้นเดียวกัน แต่มือที่เดินมันทำงานคนละอย่าง

และเพื่อ "ได้โค้ด" นั้น codegen ต้องทำของสามอย่างที่ eval/check ไม่เคยทำ — ซึ่งคือโครงของสามหัวข้อถัดไป: **(1) เลือก register** ว่าแต่ละค่าอยู่ตรงไหน (หัวข้อ 2) · **(2) จัดสรรตำแหน่งบน stack ให้ตัวแปร** (หัวข้อ 3) · **(3) ตั้งป้ายชื่อ (label) ให้ branch กระโดดไปหา** (หัวข้อ 4)

## 2. ของชิ้นที่ 1 — เลือก register: codegen เดินต้นไม้ (compileExpr)

ตัวสร้างโค้ดของเราชื่อ `codegen.Compiler` และหัวใจของมันคือฟังก์ชัน `compileExpr` ซึ่งหน้าตา**เหมือน** `eval` (ตอน 28) และ `checkExpr` (ตอน 29) แทบทุกตัวอักษร — หนึ่ง node ของต้นไม้ = หนึ่ง case แล้วเรียกตัวเองกับลูก — ต่างกันแค่ "สิ่งที่ปล่อยออกมา":

```go
func (c *Compiler) compileExpr(e parser.Expr) (Type, error) {
    switch n := e.(type) {
    case *parser.NumberLit:
        c.emitf("    mov x0, #%d", n.Value)   // ตัวเลข → "โหลดเลขใส่ register x0"
        return Int, nil
    case *parser.Ident:
        info, _ := c.lookup(n.Name)           // ชื่อ → หาช่องบน stack ที่จองไว้
        c.emitf("    ldr x0, [x29, #%d]", info.offset)   // อ่านค่าจาก memory ใส่ x0
        return info.typ, nil
    case *parser.BinaryExpr:
        return c.compileBinary(n)             // สองฝั่ง → ปล่อยโค้ดของทั้งสองฝั่งแล้ว "ประกอบ"
    }
    ...
}
```

โค้ดข้างบนมีของใหม่ตัวเดียวคือ `c.emitf(...)` — **emit** (ปล่อย) คือฟังก์ชันที่ "พิมพ์บรรทัด assembly ออกมา" หนึ่งบรรทัด เช่น `emitf("mov x0, #%d", 3)` ก็คือปล่อยข้อความ `mov x0, #3` ลงไปในไฟล์ นี่คือแก่นของ codegen: แทนที่จะ "คืนค่า" เหมือน interpreter มัน "พิมพ์โค้ด" ออกมาเป็นบรรทัด ๆ

ตอนนี้ดูทั้งโปรแกรมแรกของตอนนี้ — จาก `3 + 4 * 5` ไปจนถึงโค้ดเครื่องที่รันได้จริง:

```text
ซอร์ส:  let x = 3 + 4 * 5;  print x;
```

แล้ว parser ของตอนที่ 27 ก็ประกอบเป็นต้นไม้ (นี่คือผลจริงจากโปรแกรม 01 — อ่านจาก**ราก** (บรรทัดบนสุด `Program` = ทั้งโปรแกรม) ลงมาหา**ใบ** (บรรทัดล่างสุด `NumberLit` = ตัวเลขตรง ๆ) โดย `├─`/`└─` บอกว่าใครเป็นลูกของใคร):

```text
Program
├─ LetStmt let x          ← คำสั่ง "ประกาศตัวแปร x"
│  └─ BinaryExpr +        ← นิพจน์ "บวก" (ค่าของ x)
│     ├─ NumberLit 3      ← ฝั่งซ้าย = ตัวเลข 3
│     └─ BinaryExpr *     ← ฝั่งขวา = นิพจน์ "คูณ"
│        ├─ NumberLit 4   ← ฝั่งซ้ายของการคูณ = 4
│        └─ NumberLit 5   ← ฝั่งขวาของการคูณ = 5
└─ PrintStmt              ← คำสั่ง "พิมพ์"
   └─ Ident x             ← สิ่งที่พิมพ์ = ตัวแปร x
```

codegen เดินต้นไม้นี้แล้วปล่อย assembly ออกมา (นี่คือผลรันจริงจากโปรแกรม 01 — ดูฉบับเต็มได้ใน `out/01_codegen_expr.out.txt`):

(ในโค้ดข้างล่างจะเห็น `sp` — ตัวย่อของ **stack pointer** (ตัวชี้ตำแหน่ง "บนสุด" ของ **stack** = พื้นที่หน่วยความจำที่โปรแกรมใช้พักข้อมูลชั่วคราว) เราจะลงรายละเอียดเรื่อง stack และเฟรมแบบเต็ม ๆ ในหัวข้อ 3)

```asm
    mov x0, #3          ; 3 → x0
    str x0, [sp, #-16]! ; พักค่า 3 ลง stack ชั่วคราว (spill)
    mov x0, #4          ; 4 → x0
    str x0, [sp, #-16]! ; พักค่า 4 ลง stack
    mov x0, #5          ; 5 → x0
    mov x1, x0          ; x1 = 5 (ตัวช่วย)
    ldr x0, [sp], #16   ; ดึง 4 กลับมา x0
    mul x0, x0, x1      ; x0 = 4 * 5 = 20
    mov x1, x0          ; x1 = 20
    ldr x0, [sp], #16   ; ดึง 3 กลับมา x0
    add x0, x0, x1      ; x0 = 3 + 20 = 23
    str x0, [x29, #-16] ; เก็บ 23 ลงช่องของตัวแปร x
    ldr x0, [x29, #-16] ; อ่าน x กลับมา
    bl print_int        ; เรียกฟังก์ชันพิมพ์ตัวเลข
```

ผลรัน (CPU จริง ๆ ผ่าน syscall — system call = การขอให้ระบบปฏิบัติการช่วยทำงาน ซึ่งเราอธิบายเต็ม ๆ ในหัวข้อ 6):

```text
23
```

สังเกตสามอย่างที่ทำให้เห็นว่ามัน "เป็นโค้ดเครื่องจริง" แล้ว:

1. **ลำดับ `mul` มาก่อน `add`** — โจทย์คือ `3 + 4 * 5` ที่ต้องคูณก่อนบวก codegen **ไม่ได้** "รู้" กฎคูณก่อนบวกเอง — กฎนั้น parser ของตอนที่ 27 ฝังไว้ในรูปต้นไม้แล้ว (คูณอยู่ลึกกว่า) codegen แค่เดินตามต้นไม้ ผลจึงถูกโดยอัตโนมัติ
2. **spill (การพักค่า)** — สังเกต `str x0, [sp, #-16]!` กับ `ldr x0, [sp], #16` คู่กัน: เพราะค่าทุกตัวไหลผ่าน x0 ตัวเดียว พอจะคำนวณฝั่งขวา ต้องเอาค่าซ้ายไปพักบน stack ชั่วคราวก่อน แล้วค่อยดึงกลับมา — ท่านี้เรียกว่า **spill** และเป็นของที่ตัวสร้างโค้ดจริงทุกตัวต้องทำ
3. **`bl print_int`** — การ "พิมพ์ออกจอ" ในภาษาเครื่องไม่ใช่เรื่องง่าย (ต้องแปลงเลขเป็นข้อความก่อน) codegen จึงแนบฟังก์ชันช่วย `print_int` มาให้ แล้วเรียกด้วย `bl` (branch and link = กระโดดไปแล้วจำทางกลับ) — เรื่องนี้เราจะดูในหัวข้อ 6

## 3. ของชิ้นที่ 2 — ตัวแปรไม่ใช่ "ชื่อ" แต่เป็น "ช่องบน stack"

ตอนที่ 28 interpreter เก็บตัวแปรใน **map ของ Go** (ตารางชื่อ → ค่า) แต่เมื่อโปรแกรมจะกลายเป็นโค้ดเครื่อง ตัวแปรต้องมี**ที่อยู่ใน memory จริง** — codegen จึงจอง "ช่อง" บน stack (พื้นที่หน่วยความจำที่โปรแกรมใช้เก็บข้อมูลชั่วคราวระหว่างรัน) ให้ตัวแปรแต่ละตัว

ภาพนี้คือผังเฟรม (frame layout = ผังว่าใครอยู่ตรงไหนของ stack) ที่ codegen จองให้โปรแกรมที่มีตัวแปร `a b c` และมี `a` ซ้อนในบล็อกอีกตัว (ผลจริงจากโปรแกรม 03):

![ผังเฟรม: ตัวแปร = ช่องบน stack (มีที่อยู่จริง)](/assets/diagrams/ep30-02-frame.svg)

อ่านภาพจากบนลงล่าง (ก่อนอื่น: **frame** (เฟรม) = ช่วงพื้นที่หนึ่งบน stack ที่เป็นของฟังก์ชันหรือโปรแกรมหนึ่ง ๆ — ในภาพทั้งกล่องคือเฟรมของโปรแกรมนี้):

- **x29** คือ **frame pointer** (ตัวชี้เฟรม) — register ที่จด "ตำแหน่งฐานของเฟรมปัจจุบัน" ไว้เป็นหลักอ้างอิง ทุกตัวแปรในเฟรมจะอ้างอิงตำแหน่งจาก x29
- พอเข้า `_start` (จุดเริ่มของโปรแกรม Linux) เราต้อง save ค่าเดิมของ x29 และ x30 ไว้ก่อน (ด้วยคำสั่ง `stp x29, x30, [sp, #-16]!` — เก็บสอง register ลง stack แล้วเลื่อน sp ลง 16 ไบต์) แล้วตั้ง x29 ใหม่ — ส่วน **x30** คือ **link register** (register ที่เก็บ "ที่อยู่สำหรับกลับ" เมื่อฟังก์ชันถูกเรียก ตอนที่ 12 เรียกของแบบนี้ว่า return address)
- ตัวแปรแต่ละตัวได้ช่องถอยลงทีละ 8 ไบต์: `a` ที่ `-16`, `b` ที่ `-24`, `c` ที่ `-32` — การ "อ่านตัวแปร x" จึงกลายเป็นคำสั่ง `ldr x0, [x29, #-16]` (อ่าน memory ตรง x29 ลบ 16)

จุดที่สำคัญมากคือ**ชื่อซ้ำในบล็อก (shadowing)**: โปรแกรม 03 มี `let a = 1;` ข้างนอก แล้วในบล็อก if มี `let a = 99;` อีกตัว — codegen จองช่อง**ใหม่** `-40` ให้ `a` ตัวใน ไม่ทับ `a` ตัวนอกที่ `-16` (ตรงกับตารางสัญลักษณ์และ scope ของตอนที่ 29 เป๊ะ) ผลคือ:

```text
รันแล้วได้:
99      ← print a; ในบล็อก อ่านช่อง -40
1       ← print a; นอกบล็อก อ่านช่อง -16 (ตัวเดิมกลับมา)
3       ← print c;  อ่านช่อง -32
```

นี่คือความหมายที่แท้จริงของ "ตัวแปร": จาก "ชื่อใน map ของ Go" กลายเป็น "ช่อง memory ที่มีที่อยู่จริง" — ตัวสร้างโค้ดคือคนที่ตัดสินใจว่าแต่ละชื่อไปนั่งตรงไหนของ stack

## 4. ของชิ้นที่ 3 — if ไม่มีจริงในภาษาเครื่อง มีแต่ "กระโดดแบบมีเงื่อนไข"

ตอนที่ 28 interpreter ทำ `if` โดย "เลือกเส้นทางเอง" (ถ้าเงื่อนไขจริงก็เข้า then) แต่ CPU ไม่มีความคิดเรื่อง "ถ้า" เลย — มันมีแค่คำสั่ง**กระโดดแบบมีเงื่อนไข** (conditional branch): "ถ้าเงื่อนไขตรง ก็ข้ามไปที่ป้ายชื่อ X"

ภาพนี้คือการแปลง `if x > 5 { ... } else { ... }` เป็น branch (คำสั่งจริงจากผลรันโปรแกรม 02):

![if ไม่มีจริงในภาษาเครื่อง — มีแต่ 'กระโดดแบบมีเงื่อนไข'](/assets/diagrams/ep30-03-if-branch.svg)

โค้ดที่ codegen ปล่อยออกมา (แก่น):

```asm
    cmp x0, x1          ; เปรียบเทียบ x0 กับ x1 (x0 = x, x1 = 5)
    cset x0, gt         ; ถ้า x0 > x1 → x0 = 1 (จริง) ไม่ใช่ก็ 0 (เท็จ)
    cmp x0, #0          ; เทียบผลกับ 0
    b.eq .Lelse1        ; ถ้า == 0 (เท็จ) → กระโดดไป else
    ; ...โค้ดของ then...
    b .Lend2            ; กระโดดข้าม else
.Lelse1:
    ; ...โค้ดของ else...
.Lend2:
```

สังเกตสองจุด:

1. **ค่าจริง/เท็จ = ตัวเลข 1/0** — `cset x0, gt` (conditional set = "ตั้งค่า 1 ถ้าเงื่อนไขตรง") แปลงการเปรียบเทียบเป็นเลข 1 (จริง) หรือ 0 (เท็จ) แล้ว `cmp x0, #0` + `b.eq` ก็คือ "ถ้าเป็นเท็จ (== 0) ให้กระโดด"
2. **`b.eq` / `b` + ป้ายชื่อ (label)** — ป้ายชื่อ `.Lelse1` `.Lend2` เป็น "หมุด" ที่ codegen ตั้งไว้ให้คำสั่งกระโดดมาเกาะ ที่น่าสนใจคือตอนที่เขียนโค้ดยังไม่รู้เลยว่าหมุดอยู่ "ที่อยู่" ไหน — งานแปลงชื่อป้ายเป็นที่อยู่จริงเป็นหน้าที่ของ **assembler** (เครื่องมือ `as`) ซึ่งเป็นเหตุผลหนึ่งที่ต้องมีขั้นตอน assemble

บทเรียนตรงนี้คือ: **โครงสร้างระดับสูงของภาษา (if/else) ไม่มีอยู่ในภาษาเครื่อง — compiler มีหน้าที่ "ลดรูป" มันลงเป็นของดิบ (กระโดด + เปรียบเทียบ) ที่เครื่องทำได้**

## 5. กับดัก — โค้ดเครื่องไม่มี "ตาข่ายนิรภัย" ของ interpreter

interpreter ของตอนที่ 28 มีโค้ดตรวจการหารด้วยศูนย์ฝังอยู่ใน `evalBinary` — ถ้าเจอ `7 / 0` มันจะคืน error สุภาพ ๆ ว่า "division by zero" แต่โค้ดเครื่องที่ codegen ปล่อยออกมา **ไม่มี** การตรวจนั้นโดยอัตโนมัติ ถ้า codegen ปล่อยคำสั่ง `sdiv` (signed divide = คำสั่งหารแบบมีเครื่องหมายของ aarch64) เฉย ๆ แล้วตัวหารเป็น 0 จะเกิดอะไรขึ้น?

![กับดัก: 7 / 0 ผ่าน 3 ทางเดิน ให้ผลต่างกัน](/assets/diagrams/ep30-04-div-zero.svg)

ผลจริงจากโปรแกรม 04 — เอาโปรแกรม `print 7 / 0;` ไปรันผ่าน 3 ทาง:

```text
1) interpreter (ตอน 28):
   error → line 1, column 9: division by zero
2) โค้ดเครื่องแบบไม่ตรวจ (naive codegen):
   รัน → 0   (เงียบ! ไม่มี error แต่คำตอบผิด)
3) โค้ดเครื่องแบบตรวจ (guarded codegen):
   รัน → division by zero (exit code 1)
```

นี่คือกับดักของตอนนี้ และมัน**แย่กว่าที่คิด**ด้วย:

- บน x86 (สถาปัตยกรรมของคอมพิวเตอร์ส่วนใหญ่) การหารด้วยศูนย์จะทำให้ CPU ส่งสัญญาณ SIGFPE (สัญญาณแจ้ง "เลขคณิตผิดพลาด" — ระบบปฏิบัติการจะบังคับให้โปรแกรมหยุด) แล้วโปรแกรม "พัง" ทันที — อย่างน้อยก็พังแบบเห็น ๆ
- แต่บน **aarch64** (เครื่องนี้) สถาปัตยกรรม ARM กำหนดไว้ว่า `sdiv` หารด้วยศูนย์จะ**คืน 0 อย่างเงียบ ๆ** ไม่ error — นี่แย่กว่าพัง เพราะมันให้**คำตอบผิดแบบไม่เตือน** ผู้ใช้เห็นเลข 0 แล้วคิดว่าโปรแกรมทำงานถูกต้อง

บทเรียนสำคัญ: **compiler ไม่ใช่แค่ "แปลคำต่อคำ" แต่มันต้องรักษาความหมาย (semantics) ของภาษาด้วย** — รวมถึงพฤติกรรมเมื่อเกิด error ด้วย ตัวสร้างโค้ดของเราจึงต้อง "แปล" การตรวจของ interpreter ลงเป็นโค้ดเครื่องด้วย คือปล่อย `cbz x1, .Ldiv_zero` (ถ้า x1 == 0 ให้กระโดดไปตัวจัดการหารด้วยศูนย์) ก่อน `sdiv` ทุกครั้ง:

```asm
    cbz x1, .Ldiv_zero  ; ถ้าตัวหารเป็น 0 → กระโดดไปพิมพ์ error + exit 1
    sdiv x0, x0, x1     ; หารแบบมีเครื่องหมาย (signed)
```

ซึ่งเป็นเหตุผลว่าทำไม codegen ถึงต้อง**รู้ชนิด** (ของที่เราสร้างไว้ในตอนที่ 29) — การจะรู้ว่า "ต้องปล่อยโค้ดตรวจแบบไหน" codegen ต้องรู้ว่ากำลังจัดการกับ int อยู่ ไม่ใช่แค่ "ค่าอะไรก็ได้"

## 6. รันไทม์เล็ก ๆ — print_int / print_bool / syscall

พอพูดถึง "พิมพ์ออกจอ" ในภาษาเครื่อง จะเจอความจริงข้อหนึ่ง: **CPU ไม่มีคำสั่ง "พิมพ์"** — การพิมพ์ต้องขอให้ระบบปฏิบัติการช่วย ผ่านกลไกที่ชื่อ **syscall** (system call = การเรียกใช้บริการของระบบปฏิบัติการ ซึ่งเราเจอแล้วในตอนที่ 19)

codegen ของเราจึงแนบ "รันไทม์" (runtime = โค้ดสนับสนุนที่ compiler ใส่มาให้อัตโนมัติ) ไปกับทุกโปรแกรม ประกอบด้วยฟังก์ชันสองตัว:

- **`print_int`** — รับเลขใน x0 แปลงเป็นข้อความทศนิยม (ต้องหารเอาเศษทีละหลัก แล้วเติมเครื่องหมายลบถ้าติดลบ) แล้วเรียก syscall `write` (หมายเลข 64 บน aarch64) เขียนออก **stdout** (ช่องผลลัพธ์มาตรฐาน = ที่ที่โปรแกรมพิมพ์ข้อความออกให้คนเห็น บน terminal)
- **`print_bool`** — รับ 1/0 ใน x0 พิมพ์ `true` หรือ `false` แล้ว syscall `write`

และตอนจบโปรแกรมก็เรียก syscall `exit` (หมายเลข 93) ด้วยรหัส 0 (สำเร็จ) — ดูโค้ดเต็มของรันไทม์ได้ใน `out/01_codegen_expr.out.txt` (ส่วนท้ายของ assembly)

จุดน่าสังเกต: เพราะโปรแกรมที่เราสร้างใช้ syscall ตรง ๆ (ไม่ผ่าน **libc** = ไลบรารีมาตรฐานของภาษา C ซึ่งเป็นของสนับสนุนที่โปรแกรม C เกือบทุกตัวพึ่งพา) มันจึง**รันได้ด้วยตัวมันเองโดยไม่ต้องพึ่ง libc** — นี่คือเหตุผลที่เราลิงก์ด้วย `ld` ตรง ๆ ได้ ไม่ต้องผ่าน **gcc** (คอมไพเลอร์ภาษา C ที่ปกติใช้เป็นตัวเชื่อม) (ลองสังเกต `out/00_env.txt` ว่าใช้แค่ `as` + `ld`)

## 7. ด่านตรวจสุดท้าย — compiler ให้ผลเท่ากับ interpreter ไหม

คำถามที่ค้างอยู่ตลอดตอนนี้: **เรารู้ได้ยังไงว่า codegen "ถูก"?** ถ้าคอมไพเลอร์แปลความหมายของภาษาเพี้ยนไป โปรแกรมที่คอมไพล์แล้วจะให้คำตอบต่างจาก interpreter

วิธีตรวจที่ตรงไปตรงมาที่สุดเรียกว่า **differential testing** (การทดสอบแบบเทียบผล — เอาโปรแกรมเดียวกันรันสองทางที่ควรให้ผลเหมือนกัน แล้วเทียบ stdout) โปรแกรม 05 เอาโปรแกรมทดสอบ 10 ตัว มารันผ่านทั้ง interpreter และ compiler แล้วเทียบผลทีละตัว:

```text
  1) expr           interpreter="23"                 compiled="23"                 OK
  2) precedence     interpreter="14 20"              compiled="14 20"              OK
  3) neg            interpreter="-5 -3 -7"           compiled="-5 -3 -7"           OK
  4) div            interpreter="3 5 0"              compiled="3 5 0"              OK
  5) compare        interpreter="true true false true" compiled="true true false true" OK
  6) branch         interpreter="100"                compiled="100"                OK
  7) branch-false   interpreter="0"                  compiled="0"                  OK
  8) no-else        interpreter="7"                  compiled="7"                  OK
  9) shadow         interpreter="99 1"               compiled="99 1"               OK
 10) nested         interpreter="2 1"                compiled="2 1"                OK

  ผล: ตรงกัน 10/10 โปรแกรม
```

ตรงกันครบ 10/10 — หมายความว่า compiler ของเรา (อย่างน้อยในชุดทดสอบนี้) แปลความหมายของภาษาได้ตรงกับ interpreter นี่คือด่านตรวจที่คอมไพเลอร์จริงใช้ยืนยันความถูกต้องเช่นกัน (แม้จะซับซ้อนกว่ามาก)

## สรุป: จาก "เดินต้นไม้" สู่ "สร้างโค้ด"

ตอนนี้เราเดินครบวงจรของภาษาจิ๋วแล้ว ตั้งแต่ตอน 26 ถึง 30:

| ตอน | ชั้น | หน้าที่ | ได้อะไรออกมา |
|---|---|---|---|
| 26 | lexer | ตัดข้อความเป็นคำ | token |
| 27 | parser | ประกอบคำเป็นต้นไม้ | AST |
| 28 | interpreter | เดินต้นไม้หาค่า | ค่า (ตอนรัน) |
| 29 | check | เดินต้นไม้หาชนิด | ชนิด + ตารางสัญลักษณ์ |
| 30 | codegen | เดินต้นไม้หาคำสั่งเครื่อง | assembly → executable |

ตัวเดียวกันเดินต้นไม้คนละเป้าหมาย — `eval` เดินเพื่อ**ได้ค่า** · `check` เดินเพื่อ**ได้ชนิด** · `codegen` เดินเพื่อ**ได้โค้ดเครื่อง** และสิ่งที่ codegen ต้องทำเพิ่มจากสองตัวก่อนหน้าคือของสามชิ้นที่เราเห็นในตอนนี้: **เลือก register** (ค่าทุกตัวไหลผ่าน x0/x1 + spill — หัวข้อ 2) · **จัดสรรตำแหน่งให้ตัวแปร** (บน stack — หัวข้อ 3) · **ตั้งป้ายชื่อ (label)** ให้คำสั่ง branch กระโดดไปหา (หัวข้อ 4)

ตอนที่ 31 เราจะเดินต่อจากตรงนี้สู่เรื่องสุดท้ายของระยะนี้ — **GC / runtime ของ Go** (GC = garbage collector = ตัวเก็บกวาดหน่วยความจำที่โปรแกรมไม่ใช้แล้ว · goroutine = หน่วยงานที่รันพร้อมกันของ Go · pointer = ตัวชี้ตำแหน่งในหน่วยความจำ — ทั้งสามคำจะได้เจอเต็ม ๆ ในตอนที่ 31): ทุกสิ่งที่เรียนมาจะมาบรรจบกันในตัว runtime ที่จัดการหน่วยความจำให้ภาษา Go จริง ๆ

### Mini-project (ต่อยอดจาก `internal/codegen`)

ก่อนเริ่ม รู้จักโครงไฟล์ที่ต้องแตะ: **`internal/codegen/codegen.go`** = ตัวสร้างโค้ดทั้งหมด (compileExpr / compileBinary / compileStmt / prologue / runtime) · **`internal/codegen/run.go`** = ตัวช่วย as+ld+รัน · **`internal/parser/`** = ชนิด node + ตัว parse · **`internal/lexer/`** = ตัวตัดคำ · รันทุกอย่างพร้อมกันด้วย `bash run_all.sh`

ให้ทำสองอย่างเรียงจากง่ายไปยาก:

1. **เพิ่มตัวดำเนินการ `%` (modulo = เศษจากการหาร)** — ต้องแตะครบสามชั้นเหมือนเดิม:
   - lexer: เพิ่ม token `PERCENT` สำหรับ `%`
   - parser: เพิ่ม `%` ในระดับเดียวกับ `*` `/` (ใน `parseTerm`)
   - codegen: ใน `compileBinary` เพิ่ม case `%` — เศษ = ตัวตั้ง − (ตัวตั้ง ÷ ตัวหาร) × ตัวหาร เคล็ดลับคือใช้คำสั่ง `msub` (multiply-subtract = คูณแล้วลบ) เพื่อได้เศษในคำสั่งเดียว แต่ต้อง**เก็บตัวตั้งไว้ก่อน** (spill) เพราะ `sdiv` จะเขียนทับ x0
   - ทดสอบว่า `print 7 % 3;` ให้ผล `1` (อย่าลืม guard หารด้วยศูนย์ด้วย — `% 0` ก็ต้องจับได้)
2. **เพิ่มคำสั่ง loop `while CONDITION BLOCK`** — อันนี้ยากกว่า เพราะต้องสร้าง label ใหม่สองตัว (จุดเช็คเงื่อนไข + จุดจบ loop):
   - lexer: เพิ่ม keyword `while`
   - parser: เพิ่ม `WhileStmt` (อย่าลืมเติมใน `childrenOf` ของ ast.go)
   - codegen: `compileWhile` ปล่อยป้าย `.LloopN` (เช็คเงื่อนไข) + `.LendN` แล้ว `b .LloopN` วนกลับ — โครงสร้างเดียวกับ `if` แต่มี branch วนกลับมาแทนที่จะวิ่งไปทางเดียว
   - ทดสอบด้วยโปรแกรมที่ตัวแปรเปลี่ยนค่าในแต่ละรอบ (อาจต้องเพิ่ม operator `=` สำหรับ "assign" คือเปลี่ยนค่าตัวแปรเดิม — ต่างจาก `let` ที่ใช้ประกาศตัวแปรใหม่)
