ตอนที่แล้วเราจบด้วยการบ้านที่ให้หยิบ CVE มาหนึ่งใบ แล้วตอบสามคำถาม: มันคือช่องโหว่แบบไหน (CWE) คะแนนเท่าไร (CVSS) และกระทบอะไร

ถ้าคุณทำการบ้านนั้นจริง คุณจะเจอช่องว่างที่ผมเจอ: **เราอ่านช่องโหว่ทีละใบได้แล้ว แต่ยังไม่มีคำตอบสำหรับคำถามที่หัวหน้าถามว่า "แล้วแอปเราควรตรวจอะไรบ้าง"** · CVE เป็นทะเบียนของสิ่งที่ *เกิดขึ้นแล้ว* · CWE เป็นทะเบียนของ *รูปแบบ* ที่ทำให้เกิด · แต่ทั้งสองไม่เคยบอกว่า "เริ่มจากตรงไหนก่อน"

บทนี้คือคำตอบที่วงการใช้กันจริง: **OWASP (มูลนิธิไม่แสวงหากำไรด้านความปลอดภัยซอฟต์แวร์) Top 10 (เอกสารสรุปสิบหมวดช่องโหว่ที่พบบ่อยและเจ็บที่สุดในแอปเว็บ)** · และผมอยากบอกตั้งแต่ต้นว่ามันเป็นคำตอบที่ดี แต่เป็นคำตอบที่คนอ่านผิดมากที่สุดในวงการนี้ — เพราะคนส่วนใหญ่ใช้มันเป็น *รายการสิ่งที่ต้องแก้* ทั้งที่มันเป็น *รายการสิ่งที่ต้องตรวจ*

สามตัวเลขที่บทนี้จะพาไปดู — ผมบอกก่อนว่ากำลังจะวัดอะไร:

- **เดโม 1** — checklist audit แอปตัวอย่างหนึ่งตัว (audit = ตรวจอย่างเป็นระบบแล้วจดหลักฐานไว้) ด้วยสิบหมวดของปี 2025 · ผลคือ **pass=2 · partial=2 · fail=6 จาก 10 ข้อ** · และสามข้อที่ควรแก้ก่อนไม่ใช่ข้อที่ร้ายที่สุดในลิสต์ แต่เป็นข้อที่อันดับสูงสุดในบรรดาข้อที่เราตก
- **เดโม 2** — แผนที่ 2021 → 2025 · ขยับ **5** (ในนั้น 1 คือ A03 ที่ขยายจาก A06:2021) · เกิดใหม่ **1** · อยู่ที่เดิม **4** · และ 5 หมวดที่ขยับนั้นทำให้เลขเดิมไม่ได้หมายถึงเรื่องเดิมอีก — A06:2021 กับ A06:2025 คนละเรื่อง
- **เดโม 3** — ชุดข้อมูลจำลอง **20** แอป · **80** findings (finding = จุดที่เครื่องสแกนรายงานว่าพบปัญหา · หนึ่งจุด = หนึ่ง finding) · นับแบบ "ครั้งที่เจอ" กับ "แอปที่กระทบ" ให้อันดับต่างกัน **7/10** หมวด และ top-3 ทับกันแค่ **2/3** — นี่คือเหตุผลที่ OWASP ไม่นับความถี่ และเป็นเหตุผลที่ตัวเลขของคุณจะไม่ตรงกับลิสต์ของ OWASP (ซึ่งไม่ใช่ความผิดของใครทั้งคู่)

## 1. แนวคิด: เอกสาร awareness ที่ไม่ได้บังคับใคร

### 1.1 OWASP คือใคร และทำไมเอกสารของเขาถึงถูกอ้าง

OWASP (Open Worldwide Application Security Project) เป็นมูลนิธิไม่แสวงหากำไรที่ทำงานเรื่องความปลอดภัยของซอฟต์แวร์ · เว็บทางการระบุว่าโครงการเริ่ม **1 ธันวาคม 2001** และจดทะเบียนเป็นองค์กรการกุศลในสหรัฐเมื่อ **21 เมษายน 2004** · ทุกอย่างที่ OWASP ผลิต — เครื่องมือ เอกสาร มาตรฐาน — เปิดให้ใช้ฟรีภายใต้สัญญาอนุญาตแบบเปิด

เหตุผลที่เอกสารของเขาได้รับการอ้างอิงกว้าง: **มันไม่ได้มาจากคนเดียวหรือบริษัทเดียว** · ข้อมูลของ Top 10 รุ่น 2025 มาจากผู้ให้ข้อมูล 12 ราย (Veracode, Sonar, Semgrep, Bugcrowd, Contrast, Orca, Wallarm และอื่น ๆ) บวกผู้ไม่ประสงค์ออกนามอีกหลายราย ส่งผลทดสอบรวมกว่า **2.8 ล้านแอป** · นี่คือชุดข้อมูลที่ใหญ่ที่สุดเท่าที่โครงการนี้เคยมี และเป็นเหตุผลว่าทำไมตัวเลขในลิสต์ถึงควรค่ากับการอ่าน — ไม่ใช่เพราะ OWASP มีอำนาจสั่งใครได้

และนี่คือประโยคที่ผมอยากให้จำ: **OWASP ไม่มีอำนาจสั่งใครได้เลย** · Top 10 ไม่ใช่มาตรฐานที่ต้องผ่าน ไม่มีใบรับรอง ไม่มีผู้ตรวจ ไม่มีการสอบตก · หน้าโครงการเองเรียกมันว่า "standard awareness document" — เอกสารสร้างความตระหนัก · มันไม่ได้บอกว่า "ระบบคุณต้องผ่านสิบข้อนี้" · มันบอกว่า "สิบเรื่องนี้คือเรื่องที่เจอบ่อยและเจ็บที่สุดในข้อมูลของเรา ปีนี้"

ความต่างนี้ไม่ใช่เรื่องเล่นคำ · มันเปลี่ยนวิธีที่คุณใช้มันทั้งหมด · ผมจะกลับมาที่จุดนี้ในหัวข้อ 4

### 1.2 ประวัติ: เอกสารที่ถูกเขียนใหม่ทุกสามถึงสี่ปี

Top 10 ไม่ได้เกิดมาสมบูรณ์ · ลองไล่ดู — ชื่อในตารางเป็นชื่อทางการของแต่ละรุ่น คำที่ยังไม่คุ้นผมวงเล็บไว้ให้ตรงจุด · และมีคำหนึ่งที่ต้องนิยามก่อนเพราะมันจะโผล่ซ้ำอีกสามที่ในบทนี้: **SSRF = หลอกให้เซิร์ฟเวอร์ของเราไปเรียก URL ที่คนอื่นกำหนด**

| ปี | สถานะ | สิ่งที่เปลี่ยน |
|---|---|---|
| 2003 | รุ่นแรก | หัวข้อที่อ้างอิงจากประสบการณ์ของผู้เขียนเป็นหลัก |
| 2004 | ปรับเล็กน้อย | เพิ่ม A9 Denial of Service (หมวดใหม่เดียวของรุ่นนี้) · ยุบ A9:2003 Remote Administration Flaws เข้า A2 · ปรับศัพท์ตาม WAS Thesaurus (A2 เริ่มพูดถึง "Insecure Ids" — กลายเป็น IDOR ในปี 2007) |
| 2007 | จัดชุดหมวดใหม่ทั้งชุด | ไม่ใช่การแก้ถ้อยคำ — เลขหมวดของรุ่นนี้ไม่เหมือนรุ่นก่อนหน้าอีกต่อไป: XSS ขึ้นเป็น A1 · Injection เป็น A2 · Malicious File Execution เข้ามาเป็น A3 · IDOR เป็น A4 · CSRF เป็น A5 · Information Leakage เป็น A6 · Insecure Communications เป็น A9 |
| 2010 | เขียนใหม่ | เปลี่ยนวิธีจัดอันดับจาก "พบมากแค่ไหน" เป็น "เสี่ยงแค่ไหน" — จุดนี้สำคัญที่สุดในประวัติของมัน |
| 2013 | ปรับตามข้อมูล | ขยายบางหมวดให้ครอบคลุมกว้างขึ้น และเรียงใหม่ตามความเสี่ยง |
| 2017 | ปรับตามข้อมูล | เพิ่ม XXE และ insecure deserialization เป็นหมวดของตัวเอง · XSS ยังเป็นหมวดเดี่ยว (ย้ายจาก A3:2013 ไปเป็น A7) และปรับชื่อหลายหมวด |
| 2021 | เขียนใหม่ | รวม XSS เข้า Injection · ยุบ deserialization เข้า integrity failures · เพิ่ม insecure design และ SSRF |
| 2025 | รุ่นที่ 8 | เพิ่ม supply chain failures และ mishandling of exceptional conditions · ยุบ SSRF เข้า access control |

ห้าคำในตารางที่คนอ่านมักสะดุด — IDOR = เข้าถึงข้อมูลของคนอื่นได้โดยแก้ id ในคำขอ · DoS = ทำให้ระบบล่มด้วยคำขอถล่ม · CSRF = หลอกเบราว์เซอร์ของผู้ใช้ที่ล็อกอินอยู่ให้ส่งคำขอแทนเรา · XXE = สั่งให้ตัวอ่าน XML ไปดึงไฟล์หรือเรียกที่อยู่ภายใน · deserialization = แปลงข้อมูลกลับเป็น object ซึ่งถ้าข้อมูลมาจากคนนอกก็อันตราย

การเปลี่ยนปี 2010 คือการเปลี่ยนปรัชญา: **จาก "อะไรพบบ่อย" เป็น "อะไรทำให้เจ็บ"** · เพราะสองอย่างนี้ไม่เหมือนกัน · ช่องโหว่ที่พบในเก้าสิบเปอร์เซ็นต์ของแอปอาจทำให้แค่เห็นข้อความ error ส่วนช่องโหว่ที่พบในหนึ่งเปอร์เซ็นต์อาจยกฐานข้อมูลทั้งก้อนไปได้

จำการเปลี่ยนนี้ไว้ เพราะเดโม 3 ของบทนี้คือการทดลองเล็ก ๆ ที่ทำให้เห็นว่ามันหมายความว่าอะไรในทางปฏิบัติ

นี่คือรายการเต็มของปี 2025 พร้อมอันดับของปี 2021 เพื่อให้เห็นการเคลื่อนไหวในบรรทัดเดียว:

| A02 | Security Misconfiguration | 5 | ขึ้น 3 |
| A03 | Software Supply Chain Failures | 6 | ขยายจาก A06:2021 |
| A04 | Cryptographic Failures | 2 | ลง 2 |
| A05 | Injection | 3 | ลง 2 |
| A06 | Insecure Design | 4 | ลง 2 |
| A07 | Authentication Failures | 7 | เปลี่ยนชื่อ |

| A09 | Security Logging & Alerting Failures | 9 | เปลี่ยนชื่อ |
| A10 | Mishandling of Exceptional Conditions | — | หมวดใหม่ |

ก่อนไปต่อ ผมจะเติมคำอธิบายให้หกหมวดที่ชื่อมันไม่บอกตัวเอง — เพราะเวลาสอนผมเจอว่าคนอ่านติดตรงนี้มากที่สุด:

- **Broken Access Control (A01)** = กติกาว่าใครมีสิทธิ์ทำอะไรกับข้อมูลอะไร ถูกละเมิด · ผู้ใช้ที่ล็อกอินถูกต้องแล้วทำสิ่งที่ไม่ควรทำได้ (อ่านใบของคนอื่น แก้ข้อมูลที่ไม่มีสิทธิ์)
- **Security Misconfiguration (A02)** = ตั้งค่าผิด หรือลืมปิดของที่เปิดไว้ — **ไม่ใช่บั๊กในโค้ด** เช่น debug endpoint (endpoint = เส้นทาง URL ที่แอปเปิดรับคำขอ) เปิดค้าง หรือที่เก็บไฟล์เปิดให้คนนอกอ่าน
- **Insecure Design (A06)** = ช่องโหว่ที่ติดมาจากชั้นออกแบบ ก่อนจะเขียนโค้ดบรรทัดแรก · เขียนโค้ดให้ดีแค่ไหนก็ไม่หาย ถ้า design ผิดตั้งแต่ต้น
- **Integrity Failures (A08)** = ซอฟต์แวร์หรือข้อมูลถูกแก้โดยที่เราไม่รู้ตัว · เช่น build ดึงโค้ดจากที่ที่เราไม่ได้ตรวจ signature (signature = ลายเซ็นดิจิทัล พิสูจน์ว่าไฟล์มาจากแหล่งที่ควรและไม่ถูกแก้ระหว่างทาง)
- **Mishandling of Exceptional Conditions (A10)** = จัดการ error และเงื่อนไขผิดปกติผิด · กลืน error แล้วทำงานต่อเหมือนไม่มีอะไรเกิดขึ้น
- **Software Supply Chain Failures (A03)** = ปัญหาที่ไม่ได้อยู่ในโค้ดที่เราเขียนเอง แต่เข้ามากับของที่เราดึงมาใช้ — dependency ที่มีช่องโหว่, ระบบ build ที่ถูกแก้, ระบบแจกจ่ายที่ปลอมได้

สามอย่างที่ผมอยากให้สังเกตจากตารางนี้ ก่อนจะไปดูว่ามันทำมาอย่างไร:

**หนึ่ง — ชื่อเปลี่ยนแม้อันดับไม่เปลี่ยน** · A07 จาก "Identification and Authentication Failures" เหลือ "Authentication Failures" · A08 จาก "Software and Data Integrity Failures" เป็น "Software or Data Integrity Failures" (คำว่า *and* กลายเป็น *or* — เปลี่ยนคำเดียว ความหมายกว้างขึ้น) · A09 จาก "Security Logging and Monitoring Failures" เป็น "Security Logging & Alerting Failures" — เข็มชี้ไปที่ *alerting* เพราะ log ที่ไม่มีใครถูกเตือนคือ log ที่ไม่มีค่า

**สอง — SSRF (Server-Side Request Forgery) หายไปจากลิสต์** · นิยามที่ให้ไว้ข้างบนยังใช้ได้ — ส่วนที่ทำให้มันน่ากลัวคือคำขอที่วิ่งออกไปนั้นไปถึงระบบภายในที่คนนอกเข้าไม่ถึง · มันหายไปไม่ใช่เพราะหมดปัญหา แต่เพราะปี 2025 ตัดสินใจว่ามันเป็นกรณีหนึ่งของ broken access control · การที่หมวดหายไปจากลิสต์ไม่เคยแปลว่าช่องโหว่หายไปจากโลก

**สาม — เลขเดิมความหมายใหม่** · A06 ของปี 2021 คือ vulnerable components (ส่วนประกอบที่เอามาใช้แล้วมีช่องโหว่ที่รู้กันแล้ว) ส่วน A06 ของปี 2025 คือ insecure design · ถ้าทีมคุณมี ticket เขียนว่า "แก้ A06" แล้วไม่มีปีกำกับ คุณกำลังอ่านเอกสารคนละรุ่นโดยไม่รู้ตัว — ผมเจอเรื่องนี้จริงในรีวิว และมันทำให้เถียงกันเปล่า ๆ สามวัน

### 1.4 วิธีที่ลิสต์นี้ถูกทำ: data-informed แต่ไม่ใช่ data-driven

"data-informed แต่ไม่ใช่ data-driven" แปลว่า: ใช้ข้อมูลประกอบการตัดสิน แต่คนยังเป็นคนเลือก — ตัวเลขบอกน้ำหนัก ไม่ได้เลือกแทน · ต่างจากการจัดอันดับด้วยสูตรล้วน ๆ ที่ปล่อยให้ข้อมูลเรียงลำดับเอง

ส่วนนี้คือส่วนที่คนข้ามมากที่สุด และเป็นส่วนที่ทำให้เราอ่านตัวเลขเป็น · ทีม Top 10 อธิบายขั้นตอนไว้เอง (ผมสรุปเป็นห้าขั้น):

1. **เก็บข้อมูล** — ขอจากผู้ให้ข้อมูลแต่ละรายเป็นจำนวน *แอปที่ทดสอบ* ในแต่ละปี และจำนวน *แอปที่มีอย่างน้อยหนึ่งจุด* ของ CWE นั้น (ทำไมนับแบบนี้ — อธิบายถัดจากภาพ)
2. **จัดกลุ่ม CWE** — รุ่นนี้มี CWE ในชุดข้อมูล **589** ตัว (จากประมาณ 30 ตัวในปี 2017 และเกือบ 400 ตัวในปี 2021) จัดเป็น **12 หมวด** แล้วจัดอันดับด้วยข้อมูล
3. **เติมสิ่งที่ข้อมูลจับไม่ได้** — เลือกเพิ่มได้อีก 2 หมวดจากแบบสำรวจชุมชน เพราะบางเรื่องยังไม่มีเครื่องมือทดสอบระดับใหญ่
4. **ได้สิบหมวด** — **10 หมวด · 248 CWE** ตามเอกสาร introduction · กำหนดเพดานไม่เกิน 40 CWE ต่อหมวด
5. **ใช้เป็น checklist** — นี่คือจุดที่งานของเราทั้งบทเริ่ม

ตัวเลขที่ควรเทียบกันให้เป็น: **248 CWE อยู่ในสิบหมวด จาก 968 CWE** ที่อยู่ในดิกชันนารีที่ดาวน์โหลดได้จาก MITRE (องค์กรไม่แสวงหากำไรที่ดูแลทะเบียน CVE/CWE — ตัวเดียวกับที่อ่านในตอนที่ 16) ตอนที่เอกสารนี้ออก · ไล่ให้เห็นสามชั้น: **589** = CWE ที่โผล่ในข้อมูลดิบ · **248** = ที่ถูกยกขึ้นลิสต์สิบหมวด · **968** = ทั้งทะเบียนที่ MITRE มีตอนนั้น · แปลว่าลิสต์นี้ครอบคลุมประมาณหนึ่งในสี่ของทะเบียนทั้งหมด ไม่ใช่ทั้งหมด · และนั่นคือเหตุผลที่มันชื่อ Top 10 ไม่ใช่ลิสต์ทั้งหมด · การรู้ว่าอะไร *ไม่อยู่* ในลิสต์จึงสำคัญพอ ๆ กับการรู้ว่าอะไรอยู่

![จากข้อมูลจริงถึง checklist: ห้าขั้นของการทำ Top 10](/assets/diagrams/ep17-01-data-to-checklist.svg)

**สิ่งที่สำคัญที่สุดในขั้นที่หนึ่ง:** OWASP นับ *จำนวนแอปที่กระทบ* ไม่นับ *จำนวนครั้งที่เจอ* · เอกสารระบุเหตุผลตรง ๆ ว่าทำไมเขาไม่นับ frequency: ถ้าแอปหนึ่งมี XSS เจ็ดจุดกับอีกแอปมีหนึ่งจุด ทั้งคู่ก็คือ "แอปที่กระทบ" เท่ากัน · และเพราะเครื่องมืออัตโนมัติรายงานทุกจุด ขณะที่คนทดสอบมักรายงานจุดเดียวต่อแอป ตัวเลข frequency จึงขึ้นกับ *เครื่องมือ* มากกว่าขึ้นกับ *โลกความจริง*

นี่ไม่ใช่รายละเอียดทางเทคนิค · มันคือเหตุผลว่าทำไมตัวเลขของคุณจะไม่ตรงกับของ OWASP · และเดโม 3 ของบทนี้คือการทำให้เห็นด้วยตา

**อีกเรื่องที่ควรรู้** — OWASP ให้คะแนนแต่ละหมวดจากสองส่วน: **prevalence** (สัดส่วนแอปที่กระทบ — อธิบายแล้วข้างบน) กับ **ความรุนแรงจาก CVSS** (exploit + impact) · ครึ่งแรกจบแล้ว ครึ่งที่เหลือคือความรุนแรง ซึ่งทีมดึงจากข้อมูล CVE ใน NVD (National Vulnerability Database = ฐานข้อมูลกลางของช่องโหว่ที่ประกาศแล้ว) ผ่าน OWASP Dependency Check (เครื่องมือของ OWASP ที่ไล่ดูว่า dependency ของเรามีช่องโหว่ไหม) · ตรงนั้นมีตัวเลขสามชั้น:

- **ระเบียน CVE ที่ map (จับคู่) กับ CWE** ประมาณ **175k** (จาก 125k ในปี 2021) · CWE ที่ map ได้ **643** ตัว (จาก 241)
- **ในจำนวน CVE ที่ดึงมาประมาณ 220k ระเบียน** มีคะแนน CVSS v2 อยู่ **160k** · v3 อยู่ **156k** · v4 อยู่ **6k** — คือข้อมูลสามรุ่นปนกัน ไม่ใช่ชุดเดียว · CVE ใบเดียวมีคะแนนได้หลายรุ่นพร้อมกัน ยอดจึงบวกเกิน 220k ได้ ไม่ใช่หลักฐานว่าดึงข้อมูลมาผิด
- **ทำไมไม่ใช้ CVSS v4.0 ทั้งหมด:** เอกสารอธิบายว่าเพราะสูตร v4 เปลี่ยนโครงสร้างจนแยกเป็น *exploit score* (ช่องโหว่นี้ลงมือใช้ยากง่ายแค่ไหน) กับ *impact score* (ถ้าโดนใช้จริงจะเสียหายแค่ไหน) แบบเดิมไม่ได้

### 1.5 อ่านเอกสารอย่างมีวิจารณญาณ: ตัวเลขเดียวกันในเอกสารชุดเดียวกันยังไม่ตรงกัน — และไม่ตรงกันคนละแบบ

ตรงนี้ผมจะพาคุณทำสิ่งที่ผมสอนในทุกบท: **ตรวจเลขก่อนเชื่อ** · ผมเปิดหน้า A01 ถึง A10 ของปี 2025 แล้วเทียบกับหน้า introduction · ก่อนอื่นนิยามคำ: **score table = ตารางสรุปตัวเลขท้ายหน้า A0x ของ OWASP** (CWEs Mapped = จำนวน CWE ในหมวด · Incidence Rate = สัดส่วนแอปที่พบหมวดนี้ · Total Occurrences = จำนวนครั้งที่เจอทั้งหมด · CVEs = จำนวน CVE ที่ map เข้าหมวด) ส่วนย่อหน้าด้านบนของหน้าเดียวกันคือคำอธิบายที่คนเขียนขึ้น — และนั่นคือต้นตอของเรื่องทั้งหมด

เจอสิ่งเหล่านี้ (ทั้งหมดตรวจเมื่อ 26 ต.ค. 2026):

- introduction บอกว่าทั้งสิบหมวดมี **248** CWE · แต่ผลบวกของคอลัมน์ "CWEs Mapped" ใน score table ของทั้งสิบหน้าได้ **249** · เดโมของเราบวกได้เลขหลัง (ดู `cwe_mapped=249` ในผลรัน)
- **หน้า introduction (bullet A01) บอก 3.73%** · แต่ score table ของหน้า A01 บอก **3.74%** — คนละหน้า ไม่ใช่หน้าเดียวกัน
- **introduction บอก 38 CWE · หน้า A05 (ทั้งย่อหน้าและตาราง) บอก 37** · หน้านี้ไม่ขัดกันเอง มันขัดกับ introduction
- **introduction บอก 5 CWE · หน้า A03 ลิสต์ 6 และตารางบอก 6** · และในหน้า A03 เอง ย่อหน้าบอก average incidence **5.19%** · ตารางหน้าเดียวกันบอก **5.72%** — กรณีนี้คือ "หน้าเดียวกันไม่ตรงกัน" จริง ๆ
- **โบนัสที่ทำให้เห็นภาพ:** 248 เป็นเลขที่ลงตัวก็ต่อเมื่อยึดตารางทุกหมวดแต่ใช้ A03=5 ตาม introduction (249 − 1 = 248) · แต่ถ้าบวกตามย่อหน้า introduction เอง ซึ่งระบุ A05=38 ด้วย จะได้ 249 เท่ากับตาราง → ยอด 248 ในหัวข้อ introduction จึงไม่ตรงกับตัวเลขในย่อหน้าของมันเอง ไม่ใช่ผลของการบวกพลาดทั้งสิบหมวด

ผมไม่ได้ยกมาเพื่อจับผิด · ผมยกมาเพราะมันสอนสามอย่างที่ใช้ได้ตลอดอาชีพ:

**หนึ่ง — เอกสารที่มีคนเขียนย่อมมีเลขไม่ตรงกัน** · ไม่ใช่เพราะคนเขียนไม่เก่ง แต่เพราะมันยาวหลายหมื่นคำและแก้กันหลายรอบ · หน้าที่ของเราคือ *ระบุว่าอ้างเลขจากหน้าไหน* ไม่ใช่พูดลอย ๆ ว่า "OWASP บอกว่า"

**สอง — เมื่อเลขไม่ตรง ให้ยึดตาราง ไม่ยึดย่อหน้า** · score table คือที่ที่ตัวเลขถูกคำนวณ ส่วนย่อหน้าเป็นคำอธิบายที่เขียนด้วยมือ · ในเดโม 2 ผมจึง parse จากตาราง

**สาม — และนี่คือเหตุผลที่ checklist ต้องมีวันที่** · "ผ่าน OWASP Top 10" ที่ไม่มีปีกำกับคือประโยคที่ตรวจสอบไม่ได้ · เหมือน "ผ่าน ISO" ที่ไม่มีเลขรุ่น

## 2. ทำไมมันสำคัญ: การขยับอันดับคือข้อมูล ไม่ใช่การตลาด

ตรวจเลขเสร็จแล้ว คำถามต่อไปคือตัวเลขที่ขยับมันเล่าอะไร

![อันดับที่ขยับระหว่าง 2021 กับ 2025: A02 ขึ้น 3 อันดับ · A03 ขยายจาก A06:2021](/assets/diagrams/ep17-02-rank-map.svg)

ลองดูการขยับทีละตัว แล้วถามว่า "ทำไม" — เพราะคำตอบของทุกตัวคือประวัติศาสตร์ของอุตสาหกรรมเราในรอบสี่ปี

**A02 Security Misconfiguration: 5 → 2** · เหตุผลที่เอกสารให้ (ยกจากหน้า A02 ของปี 2025) คือการทำงานของแอปฝากไว้กับ config มากขึ้นทุกปี · ฟังดูเป็นประโยคเทคนิค แต่แปลว่า: สมัยก่อนแอปหนึ่งตัวมี config สามหน้า ตอนนี้มี IAM policy (กติกาว่าใครเข้าถึง resource อะไรได้) · CORS (กติกาว่าโดเมนไหนเรียก API ของเราได้) · bucket policy (กติกาการเข้าถึงที่เก็บไฟล์) · TLS policy (TLS = การเข้ารหัสการรับส่งข้อมูลระหว่าง client กับเซิร์ฟเวอร์)

ทุกอันคือที่ที่คนตั้งผิดได้ — และ 100% ของแอปที่ทดสอบมี misconfiguration รูปแบบใดรูปแบบหนึ่ง · หมวดนี้ไม่ได้โตเพราะมีช่องโหว่ใหม่ แต่เพราะจำนวนจุดที่ต้องตั้งให้ถูกเพิ่มขึ้นทุกปี

**A03 Software Supply Chain Failures: ใหม่ (ขยายจาก A06:2021)** · หมวดนี้ได้คะแนนโหวตสูงสุดจากแบบสำรวจ — 50% ของผู้ตอบจัดให้เป็นอันดับ 1 · และมันขยายขอบเขตจาก "component ที่มีช่องโหว่รู้แล้ว" ไปเป็น "ทุกอย่างที่พังได้ใน supply chain: dependency, ระบบ build, ระบบแจกจ่าย" · ถ้าคุณอ่านตอนที่ 8 เรื่อง Log4Shell กับ SolarWinds มาแล้ว คุณจะรู้ทันทีว่าทำไมคนถึงโหวตแบบนั้น · และมีรายละเอียดที่ควรรู้: หมวดนี้มี CVE เพียง **11** ใบในข้อมูล — น้อยที่สุดในสิบหมวด — แต่มี average exploit score สูงที่สุด · แปลว่ามันไม่ได้พบบ่อย แต่มันเจ็บหนัก

สองคำที่หมวดนี้พูดถึงตลอด: **SBOM (Software Bill of Materials = รายการส่วนประกอบทั้งหมดของซอฟต์แวร์พร้อมเลขรุ่น)** กับ **pin digest = ล็อกเวอร์ชันด้วย hash ของไฟล์ ไม่ใช่แค่เลขรุ่น เพื่อให้ build ดึงชิ้นเดิมทุกครั้ง** · สองอย่างนี้ตอบคนละคำถาม: SBOM บอกว่า "เรามีของอะไรบ้าง" ส่วน pin digest บอกว่า "ของที่ดึงมาครั้งนี้เป็นชิ้นเดิมกับที่เคยตรวจจริงไหม" — ขาดอย่างใดอย่างหนึ่ง การตรวจก็ไม่ครบ

**A04 Cryptographic Failures: 2 → 4 · A05 Injection: 3 → 5 · A06 Insecure Design: 4 → 6** · ทั้งสามลงสองอันดับด้วยเหตุผลเดียวกัน: มีสองหมวดแซงขึ้นไป (A02 ขึ้นจาก 5 มาที่ 2 และ A03 เข้ามาที่ 3) · ไม่ได้แปลว่าปัญหาลดลง · ตัวเลขของ A05 ทำให้เห็นภาพ: หมวดนี้มี CVE มากที่สุดในสิบหมวด — **62,445** ใบ · มากกว่า A01 เกือบสองเท่า · แต่ prevalence (สัดส่วนแอปที่กระทบอย่างน้อยหนึ่งจุด ไม่ว่าจะกี่จุด) อยู่ที่ 3.08% ต่ำกว่า A01

นี่คือคำอธิบายว่าทำไม "มี CVE เยอะ" กับ "เจอบ่อย" ถึงเป็นคนละแกน และทำไมลิสต์เดียวไม่พอสำหรับตัดสินใจ

**A10 Mishandling of Exceptional Conditions: ใหม่** · 24 CWE ว่าด้วย error handling, logical error, และ **fail open** (fail open = เจอ error แล้วปล่อยผ่าน/ทำงานต่อเหมือนไม่มีปัญหา) · เอกสารบอกตรง ๆ ว่าหมวดนี้เคยซ่อนอยู่ใต้คำว่า "poor code quality" ซึ่งกว้างเกินไปจนใช้สอนไม่ได้ · สำหรับผม นี่คือหมวดที่เชื่อมกับตอนที่ 13 เรื่อง fail closed ตรงที่สุด — และมันเป็นหมวดที่คนเขียนโค้ดมองข้ามมากที่สุด เพราะมันไม่โผล่ตอนแอปทำงานปกติ

**และ A01 ที่อยู่ที่ 1 ทั้งสองรุ่น** · เอกสารปี 2025 เขียนว่า 100% ของแอปที่ทดสอบมี broken access control รูปแบบใดรูปแบบหนึ่ง และหมวดนี้มี 40 CWE (เพดานสูงสุดที่โครงการตั้งไว้) · มันอยู่ที่หนึ่งเพราะมันเป็นรากของเรื่องที่เราเรียนมาตั้งแต่ตอนที่ 12 เรื่อง least privilege: **การล็อกอินสำเร็จไม่ได้แปลว่ามีสิทธิ์ทำสิ่งนั้น**

**ข้อควรระวังเรื่องคำว่า "ใหม่":** OWASP เรียกสองหมวดนี้ว่าใหม่ทั้งคู่ — introduction เขียนว่า "There are two new categories and one consolidation" และสไลด์ประกาศก็ติดป้าย "New!" ทั้ง A03 กับ A10 · แต่ A03 ไม่ได้เกิดจากศูนย์ มันคือการขยาย A06:2021 ให้กว้างขึ้น · เดโม 2 ของเราจึงแยกเป็น `new=1` (A10 ของใหม่จริง) · `expanded=1` (A03 ขยายจากของเดิม) — ภาพข้างบนจึงติดป้ายแถว A03 ว่า "ขยายจาก A06:2021" ไม่ใช่ "ขึ้น 3" เพราะถ้าติดป้ายเหมือน A02 จะกลายเป็นบอกว่ามีสองหมวดที่พุ่งขึ้นมาด้วยกลไกเดียวกัน ซึ่งไม่จริง

## 3. ลงมือทำ: ใช้มันเป็น checklist จริง ๆ

ก่อนเขียนโค้ด ผมอยากวางกติกาห้าวข้อที่ทำให้ checklist นี้ใช้งานได้จริง — เพราะความล้มเหลวส่วนใหญ่ไม่ใช่ "ตรวจไม่ครบ" แต่คือ "ตรวจแล้วไม่ได้อะไร"

1. **หนึ่งหมวด หนึ่งแถว หนึ่งหลักฐาน** · ถ้าแถวไหนเขียนว่า PASS โดยไม่มีหลักฐานว่าไปดูอะไร ถือว่ายังไม่ได้ตรวจ
2. **PARTIAL เป็นสถานะที่ต้องมี** · โลกจริงไม่ได้แบ่งเป็นผ่าน/ไม่ผ่าน · "ปิด debug endpoint แล้ว แต่ bucket เอกสาร (ที่เก็บไฟล์บน cloud) ยังเปิดให้ใครก็อ่านได้ (public-read)" คือ partial และการยอมรับสถานะนี้ทำให้ตารางไม่โกหก
3. **อันดับของ OWASP ไม่ใช่ลำดับความสำคัญของแอปคุณ** · มันเป็นลำดับของ "ความเสี่ยงโดยรวมของทั้งอุตสาหกรรม" · แอปที่ไม่มี pipeline (pipeline = สายงานอัตโนมัติ build–ทดสอบ–ปล่อยโค้ด) build หรือไม่ได้ดาวน์โหลดโค้ดจากภายนอกเลย ก็ไม่ควรเอา A08 ไปไว้บนสุดเพราะมันอันดับ 8
4. **ระบุปีของลิสต์ในรายงาน** · "ตรวจด้วย OWASP Top 10:2025 เมื่อ 2026-10-26" คือประโยคที่ตรวจสอบได้ · "ตรวจด้วย OWASP Top 10" ไม่ใช่
5. **ตรวจซ้ำเมื่อลิสต์เปลี่ยน** · รุ่นออกทุกสามถึงสี่ปี · รายงานที่อ้าง 2021 ในปี 2027 คือรายงานที่ตกยุค

### 3.1 เดโม 1: audit แอปหนึ่งตัวด้วยสิบหมวด

เดโมนี้จำลองสิ่งที่ทีมเราทำจริง: เอาแอปตัวอย่าง (ระบบวางบิลของเราจำลอง ชื่อ `havebit-billing`) มาวางเทียบกับสิบหมวด แล้วจดว่าข้อไหนผ่าน ข้อไหนไม่ พร้อมหลักฐานและ CWE

ข้อมูลสิบหมวดถูกฝังในไบนารี (ไม่มีการอ่านไฟล์ ไม่มี network) พร้อมตัวเลขจาก score table:

```go
// category คือหนึ่งหมวดของ OWASP Top 10:2025 พร้อมบริบทจากรุ่น 2021
type category struct {
	code     string // A01 ถึง A10
	name     string // ชื่อทางการของปี 2025
	rank2021 int    // อันดับในปี 2021 · 0 = หมวดใหม่ในปี 2025
	cwes     int    // จำนวน CWE ที่ถูก map เข้าหมวดนี้ (score table 2025)
	avgInc   string // Avg Incidence Rate (% ของแอปที่พบอย่างน้อยหนึ่งครั้ง)
	findings int    // Total Occurrences ในข้อมูลที่ OWASP เก็บ
	cves     int    // Total CVEs ที่ map กับ CWE ในหมวดนี้
	change   string // สถานะเมื่อเทียบกับ 2021
	renamed  bool   // ชื่อเปลี่ยนจากรุ่น 2021 แม้อันดับไม่เปลี่ยน
	expanded string // หมวดเดิมที่ถูกขยายขอบเขต เช่น "A06:2021" · "" = ไม่ได้ขยาย
}
```

และผลตรวจคือ slice ของ `check` — โครงสร้างเดียวกันกับที่คุณจะใช้ในรายงานจริง:

```go
// check คือผลตรวจหนึ่งข้อของแอปตัวอย่าง "havebit-billing"
type check struct {
	code     string
	status   string // PASS / PARTIAL / FAIL
	cwes     string // CWE ที่ตรงกับสิ่งที่เจอ · "-" = ไม่มี
	evidence string // สิ่งที่เห็นในโค้ด/การตั้งค่า
	fix      string // สิ่งที่ต้องทำเพื่อปิดข้อนี้
}
```

สองแถวแรกของตาราง — สังเกตว่า "หลักฐาน" คือสิ่งที่ทำให้ตารางนี้มีค่า ไม่ใช่คำว่า FAIL · และสังเกตว่า struct literal นี้ไม่ใส่ชื่อ field: เขียนแบบนี้ได้เพราะลำดับตรงกับ type `check` — code, status, cwes, evidence, fix (สั้นกว่า แต่ถ้าลำดับผิดแล้วคอมไพล์ผ่าน มันคือ bug เงียบ):

```go
var audit = []check{
	{"A01", "FAIL", "CWE-639", "GET /invoices/{id} ไม่ตรวจเจ้าของ — แก้เลข id แล้วอ่านใบของลูกค้ารายอื่นได้",
		"ย้าย owner check ลงไปที่ชั้น data access และเขียนเทสต์ยิงด้วย user คนละคน"},
	{"A02", "PARTIAL", "CWE-16", "ปิด debug endpoint แล้ว แต่ bucket เอกสารยัง public-read",
		"ทำให้ config ถูกตรวจด้วยสคริปต์ทุก environment ไม่ใช่ตั้งมือ"},
```

ผลรันจริง (ทั้งสิบแถว):

```

avg% = Avg Incidence Rate ของ OWASP (สัดส่วนแอปที่พบหมวดนี้) — ไม่ใช่ตัวเลขของแอปเรา

code status   avg%   cwe         สิ่งที่เจอ
---- ------   ----   ---         ---------

A02  PARTIAL  3.00   CWE-16      ปิด debug endpoint แล้ว แต่ bucket เอกสารยัง public-read

```

อ่านผลนี้ให้ถูก มีสามอย่างที่ผมอยากให้เห็น · แต่ก่อนอื่น แปลศัพท์ในตารางที่คนอ่านมักข้าม: `bcrypt cost 12` = จำนวนรอบคำนวณ ยิ่งสูงยิ่งเดารหัสช้า (และยิ่งกิน CPU) · CWE-639 = เข้าถึงข้อมูลคนอื่นได้เพราะไม่ตรวจเจ้าของ · CWE-16 = ตั้งค่าผิด · CWE-798 = ฝังรหัสผ่านไว้ในโค้ดหรือไฟล์ตั้งค่า · CWE-799 = ไม่จำกัดความถี่ของการกระทำ (Improper Control of Interaction Frequency) — ตรงกับ OTP ที่ลองได้ไม่จำกัด · `public-read` = เปิดให้ใครก็อ่านได้

**หนึ่ง — แอปที่ "ผ่านการรีวิว" ยังตกหกข้อ** · นี่คือค่าปกติของโค้ดที่ยังไม่เคยผ่าน checklist อย่างเป็นระบบ · ถ้าคุณ audit โปรเจกต์ตัวเองครั้งแรกแล้วได้ผ่านแปดข้อ ผมจะสงสัยหลักฐานของคุณก่อนสงสัยโค้ดของคุณ

**สอง — คอลัมน์ avg% ไม่ใช่ตัวเลขของเรา** · มันคือ Avg Incidence Rate ของ OWASP ที่ผมใส่มาเพื่อให้เห็นบริบท และมันมีกับดัก: A03 มี avg 5.72% สูงที่สุดในสิบหมวด แต่ละแอปของเราตก A03 เพราะ dependency ค้าง ไม่ได้เพราะค่าเฉลี่ยอุตสาหกรรมบอกอย่างนั้น · **ตัวเลขของอุตสาหกรรมใช้จัดลำดับความสนใจ ตัวเลขของเราใช้จัดลำดับงาน**

**สาม — สองข้อที่ผ่าน (A04 · A08) ไม่ได้แปลว่าไม่มีปัญหา** · มันแปลว่า "ไม่พบหลักฐานตรงข้ามในสิ่งที่เราตรวจ" · ในรายงานจริงผมเขียนแบบนี้ทุกครั้ง เพราะคนอ่านมักอ่านคำว่า PASS ว่า "ปลอดภัย" ซึ่งไม่จริง

แล้วลำดับที่ควรแก้? โปรแกรมไม่ได้ใช้ avg% หรือจำนวน CWE — มันใช้ **อันดับของ OWASP ในบรรดาข้อที่เราตก**:

```
# สามข้อที่ควรแก้ก่อน (FAIL/PARTIAL เรียงตามอันดับของ OWASP Top 10:2025)
1. A01  Broken Access Control                  ย้าย owner check ลงไปที่ชั้น data access และเขียนเทสต์ยิงด้วย user คนละคน
2. A02  Security Misconfiguration              ทำให้ config ถูกตรวจด้วยสคริปต์ทุก environment ไม่ใช่ตั้งมือ
3. A03  Software Supply Chain Failures         pin digest + สร้าง SBOM ใน CI แล้วสแกนทุก build
```

เหตุผลที่ใช้วิธีนี้: ทั้งสิบหมวดสำคัญหมด แต่คุณแก้ทีละสิบข้อพร้อมกันไม่ได้ · การเอา "อันดับของอุตสาหกรรม" มาใช้ตัดสินว่าอะไรก่อน คือการใช้ข้อมูลที่มีอยู่แล้วให้เป็น — และมันดีกว่าการใช้ความรู้สึกว่า "อันนี้น่าจะร้าย" มาก · แต่ต้องเข้าใจข้อจำกัดของมันด้วย: A06 ที่ตกแบบ partial อาจร้ายกว่า A02 ที่ตกแบบ partial ในแอปของคุณ · อันดับเป็นจุดตั้งต้นของการคุย ไม่ใช่คำตัดสิน

### 3.2 เดโม 2: แผนที่ 2021 → 2025 (และกับดักของการจำเลข)

เดโมนี้แปลงตารางอันดับเป็นข้อมูลที่โปรแกรมตรวจได้ เพื่อตอบคำถามที่เจอบ่อยในรีวิว: "เลขนี้หมายถึงอะไร"

```go
// moveLabel แปลงอันดับสองรุ่นเป็นป้ายบอกการขยับ
//
// คืนสองค่าที่เป็น "คนละชุดสัญญะ" อย่าอ่านปนกัน:
//   - ป้าย (string) = ข้อความที่พิมพ์ลงตาราง · "+3" = อันดับดีขึ้น 3 (เลขอันดับเล็กลง)
//   - ทิศ (int)     = ตัวเลขสำหรับ switch ในโปรแกรม · -1 = ดีขึ้น · 0 = เดิม · 1 = แย่ลง · 2 = หมวดใหม่
//
// ทำไมไม่ใช้ค่าเดียวกัน: ป้ายต้องอ่านรู้เรื่องสำหรับคน ("+3" ดีขึ้น) แต่ switch
// ต้องการค่าที่เทียบเท่าเดิมได้ → แยกเป็นสองชุดแล้วเขียนกำกับไว้ตรงนี้
func moveLabel(rank2021, rank2025 int) (string, int) {
	if rank2021 == 0 {
		return "new", 2
	}
	d := rank2021 - rank2025 // บวก = ขยับขึ้น (เลขอันดับเล็กลง)
	switch {
	case d > 0:
		return fmt.Sprintf("+%d", d), -1
	case d < 0:
		return fmt.Sprintf("%d", d), 1
	}
	return "0", 0
}
```

**อ่านเครื่องหมาย + ให้ถูกก่อนไปต่อ:** ในตารางนี้ `+3` = **ดีขึ้น 3 อันดับ** (เลขอันดับเล็กลง) ไม่ใช่ "อันดับเพิ่มขึ้น 3" · ในโค้ดจึงมีสองค่าที่เป็นคนละชุดสัญญะ: **ป้าย** ที่พิมพ์ลงตาราง (`+3` = ดีขึ้น) กับ **ทิศทาง** ที่ใช้ใน switch (`-1` = ดีขึ้น) · และเดโม 3 ข้างหน้าจะมีคอลัมน์เครื่องหมายอีกอันที่กลับด้าน (ค่าบวก = แย่ลง เพราะนั่นคือ "อันดับเพิ่มขึ้น") — เครื่องหมายเดียวกันคนละคอลัมน์ ไม่ได้หมายถึงเรื่องเดียวกัน

และส่วนที่ผมคิดว่าสำคัญที่สุดของเดโมนี้ — เพราะมันคือคำเตือนที่ใช้ได้จริง:

```

และคนที่พูดว่า "A06" อาจหมายถึงคนละเรื่องกันคนละปี (2021 = component, 2025 = design)
```

ห้าหมวดที่เคยมีอยู่แล้วเปลี่ยนเลข และอีกหนึ่งหมวดเป็นของใหม่ · ในทางปฏิบัติ นี่แปลว่า ticket ที่เขียนว่า "A06: เพิ่ม dependency scanning" คือ ticket ที่ถูกต้องในปี 2021 และผิดในปี 2025 (ตอนนี้ A06 คือ insecure design ส่วน supply chain คือ A03) · ถ้าคุณกำลังทำ migration จากรายงานเก่า ให้แปลงเป็น *ชื่อ* ก่อน แล้วค่อยแปลงเป็นเลขใหม่ — ชื่อเสถียรกว่าเลข

### 3.3 เดโม 3: ทำไมลิสต์ถึงเรียงแบบนั้น (และทำไมของคุณจะไม่ตรง)

เดโมสุดท้ายคือการทดลองที่ผมชอบที่สุดในบทนี้ เพราะมันพิสูจน์ให้เห็นด้วยตา จากการรันชุดข้อมูลที่เราสร้างเอง ว่า "นับอย่างไร" เปลี่ยน "อันดับ" ได้จริง

ชุดข้อมูลจำลอง: 20 แอป · 80 findings · สิบหมวด · นิยามข้อมูลก่อน — `appFindings` คือ slice ของ struct ที่มี `id` (ชื่อแอป) และ `codes` (finding ทั้งหมดของแอปนั้น) · หนึ่งแอปจึงมี finding ได้หลายรายการ และ finding เดียวกันโผล่ซ้ำได้ (เพราะสแกนเนอร์รายงานทุกจุด):

```go
var appFindings = []struct {
	id    string
	codes []string
}{
	{"app-01", []string{"A05", "A05", "A05", "A05", "A05", "A01", "A02", "A07"}},
	{"app-02", []string{"A05", "A05"}},
	// ชุดเต็มมี 20 แอป — บทความยกมาแค่สองแอปแรกให้เห็นรูปข้อมูล · ที่เหลือคือ app-03 ถึง app-20
```

จากข้อมูลชุดเดียวนี้ โปรแกรมคำนวณสองหน่วยพร้อมกัน:

```go
// countFindings นับสองหน่วยพร้อมกันจากชุดข้อมูลเดียวกัน
//   - freq  = จำนวน "ครั้งที่เจอ" (frequency) — สิ่งที่สแกนเนอร์รายงาน
//   - prev  = จำนวน "แอปที่กระทบ" (prevalence) — สิ่งที่ OWASP Top 10 ใช้นับ
//
// แอปเดียวที่มีปัญหาเดียวกัน 9 จุด นับเป็น 9 ใน freq แต่เป็น 1 ใน prev
func countFindings() (freq, prev map[string]int) {
	freq = map[string]int{}
	prev = map[string]int{}
	for _, app := range appFindings {
		seen := map[string]bool{} // กันนับแอปเดิมซ้ำ — เจอ 9 ครั้งในแอปเดียวก็นับ 1
		for _, code := range app.codes {
			freq[code]++
			if !seen[code] {
				prev[code]++
				seen[code] = true
			}
		}
	}
	return freq, prev
}
```

**หนึ่ง — อันดับ 1 กับการเป็นปัญหาอันดับ 1 ไม่ใช่เรื่องเดียวกัน** · A05 Injection มี findings มากที่สุด (17) แต่กระทบแค่ 5 แอป · นับตามแอปแล้วมันอยู่อันดับ 7 · ทำไม? เพราะแอปสองตัวในชุดข้อมูลมีปัญหานี้ตัวละห้าจุด และอีกสามตัวมีสองถึงสามจุด · นั่นคือสิ่งที่สแกนเนอร์ทำจริง และเป็นเหตุผลที่เอกสาร OWASP ระบุตรง ๆ ว่าทำไมเขาไม่นับความถี่

**สี่ — top-3 ทับกัน 2/3** · ถ้าคุณจัดลำดับงานด้วย "จำนวนครั้งที่เจอ" คุณจะเริ่มจาก A05 · ถ้าจัดด้วย "แอปที่กระทบ" คุณจะเริ่มจาก A01 · ทั้งสองมีเหตุผล แต่ต้องรู้ว่ากำลังเลือกอะไร · การจัดลำดับงานซ่อมควรใช้ prevalence (เพราะการแก้หนึ่งครั้งช่วยทั้งแอป) ส่วนการจัดลำดับงานตรวจ (ให้ tester ไปตรวจอะไรก่อน) ใช้ frequency ได้ เพราะมันบอกว่าจุดไหนมีของจริง

## 4. โจทย์

### 4.1 Drill (ทำคนเดียว ใช้เวลาราวหนึ่งชั่วโมง)

**ข้อ 1 — audit ของจริงสิบแถว** · เลือกโปรเจกต์ที่คุณเป็นเจ้าของ (หรือ open source ที่คุณอ่านโค้ดจริง) แล้วสร้างตารางสิบแถวแบบเดโม 1 · กติกา: ทุกแถวต้องมีหลักฐานเป็น path ของไฟล์หรือชื่อ setting ที่ระบุได้ · ห้ามใช้คำว่า "น่าจะ" · ถ้าหาหลักฐานไม่ได้ ให้เขียน PARTIAL และบอกว่าต้องไปดูอะไร

**ข้อ 2 — หา CWE ที่ภาษาของคุณทำไม่ได้** · เปิดลิสต์ CWE ของหมวดใดหมวดหนึ่งในปี 2025 แล้วหาหนึ่งตัวที่ Go (หรือภาษาที่คุณถนัด) ไม่สามารถก่อให้เกิดได้ · อธิบายว่าทำไม · คำถามนี้มีคำตอบจริงและมันสอนเรื่องสำคัญ: หลาย CWE ผูกกับคุณสมบัติของภาษา เช่น pointer arithmetic หรือ memory layout · นี่คือเหตุผลที่ OWASP ใช้ *หมวด* ไม่ใช่ CWE เดี่ยว ๆ เป็นหน่วยของลิสต์

**ข้อ 3 — อธิบายการยุบ SSRF** · SSRF เคยเป็นหมวด A10 ในปี 2021 และถูกยุบเข้า A01 ในปี 2025 · ตอบให้ได้สามข้อ: (ก) ช่องโหว่ SSRF เองเปลี่ยนไหม (ข) ทำไมการยุบนี้ไม่ทำให้มันหายไปจากรายการที่ต้องตรวจ (ค) ถ้าทีมคุณมี checklist เก่าที่มีแถว SSRF คุณควรทำอะไรกับแถวนั้น

### 4.2 Mini-project: `owaspcheck` — เครื่องมือแปลงผลสแกนเป็น checklist

เป้าหมาย: เขียนเครื่องมือ Go ที่รับผลการสแกน (CWE ids) แล้วสร้างรายงาน checklist สิบหมวดแบบที่ใช้ส่งหัวหน้าได้

ข้อกำหนดที่ผมจะตรวจ:

1. **อินพุตเป็น JSON** ที่มีระเบียนแบบ `{"app": "billing", "cwe": "CWE-89"}` หลายรายการ · ห้ามฝังผลลัพธ์ตายตัวไว้ในโค้ด (hardcode)
2. **แปลง CWE → หมวด** ด้วยตารางที่ฝังในโค้ด พร้อม comment ระบุว่าคัดจากหน้าไหนของ OWASP และวันที่ · CWE ที่ไม่อยู่ในตารางต้องถูกรายงานเป็น `unmapped` ไม่ใช่ทิ้งเงียบ ๆ
3. **คำนวณสองหน่วย**: จำนวน finding และจำนวนแอปที่กระทบ · รายงานทั้งคู่ และบอกว่าอันดับที่ให้ยึดหน่วยไหน
4. **มีสถานะ PASS / PARTIAL / FAIL ต่อหมวด** โดยกติกาต้องเขียนไว้ใน README: หมวดที่ไม่มี finding เลยคือ PASS หรือ UNKNOWN? (ผมอยากให้ตอบว่า UNKNOWN ถ้าไม่มีข้อมูลทดสอบ — เพราะ "ไม่พบ" กับ "ไม่ได้ตรวจ" ต่างกัน)
5. **ผลลัพธ์คงที่**: รันสองครั้งต้องได้ไฟล์เดียวกันทุกไบต์ · ถ้ามี tie ต้องมีกติกา tie-break ที่เขียนไว้
6. **มีเทสต์อย่างน้อยสามตัว**: กรณีปกติ · กรณี CWE ไม่รู้จัก · กรณีแอปเดียวมี finding ซ้ำหลายรายการ (ต้องได้ prevalence 1)
7. **ไม่มี network ไม่มี time.Now() ในเส้นทางที่ผลิตผลลัพธ์** · เพื่อให้รายงาน reproduce ได้

เกณฑ์ผ่านของผมคือข้อ 4 กับข้อ 5 · เพราะสองข้อนั้นคือเส้นแบ่งระหว่าง "สคริปต์ที่นับเลขเป็น" กับ "เครื่องมือที่ใช้ใน audit ได้จริง"

## 5. สรุป

จบบทนี้ ผมอยากให้คุณถือสามประโยคไป:

**หนึ่ง — Top 10 คือเอกสาร awareness ไม่ใช่มาตรฐานบังคับ** · ความน่าเชื่อถือของมันมาจากข้อมูล 2.8 ล้านแอปและชุมชนที่ตรวจสอบกันได้ ไม่ได้มาจากอำนาจ · ดังนั้นการอ้างมันต้องแม่น: ระบุปี ระบุหมวด ระบุ CWE

**สอง — ลิสต์เปลี่ยน และการเปลี่ยนคือข้อมูล** · A02 ขึ้นสามอันดับเพราะโลกย้ายไปอยู่บน config · A03 เกิดใหม่เพราะ supply chain กลายเป็นเป้าหลัก · A10 เกิดใหม่เพราะเรายอมรับว่า "โค้ดคุณภาพต่ำ" ไม่ใช่คำอธิบายที่ใช้สอนได้ · คนที่รู้ว่าทำไมอันดับขยับ จะใช้ลิสต์ได้ดีกว่าคนที่ท่องได้

**สาม — checklist ทำให้เราตรวจสม่ำเสมอ ไม่ได้ทำให้เราปลอดภัย** · เดโม 1 ตกหกข้อจากสิบข้อบนแอปที่ "ผ่านการรีวิว" มาแล้ว · เดโม 3 แสดงว่าอันดับขึ้นกับวิธีนับ · ทั้งสองอย่างบอกว่าเครื่องมือนี้มีค่าที่ทำให้เราถามคำถามซ้ำ ๆ ได้ทุกไตรมาส — ไม่ใช่ที่ทำให้เราเลิกคิด

การบ้านของบทนี้คือ Drill ข้อ 1 · ทำตารางสิบแถวของโปรเจกต์ตัวเองให้เสร็จก่อนอ่านตอนหน้า · เพราะตอนหน้าเราจะพาลิสต์นี้เข้าไปในกระบวนการพัฒนา — ตั้งแต่ design ถึง deploy — และคุณจะเห็นว่าที่ที่ควรตรวจไม่ใช่แค่ตอนท้าย

## หมายเหตุท้ายบท: ไฟล์และวิธีรันซ้ำ

ทุกตัวเลขในบทนี้มาจากผลรันจริงในโฟลเดอร์ `code/ep17/out/`:

| ไฟล์ | เก็บอะไร |
|---|---|
| `out/00_env.txt` | สภาพแวดล้อมที่ใช้รัน (OS, Go, Python, rsvg) |
| `out/01_audit.txt` | ผล checklist audit สิบหมวด + สามข้อที่ควรแก้ก่อน |
| `out/02_mapping.txt` | แผนที่ 2021 → 2025 + ตัวเลข score table |
| `out/03_prevalence.txt` | ชุดข้อมูลจำลอง 20 แอป · frequency กับ prevalence |
| `out/04_setup.txt` | ตัวตรวจ (gate) คุณภาพโค้ด (gofmt, vet, ไม่มี network/time/rand) |

รันซ้ำทั้งหมด (คำสั่งเดียวจบ — สคริปต์สร้าง `out/` แล้วต่อด้วยสร้าง SVG จาก `out/` และปิดท้ายด้วยการเขียน fence ในบทจาก `out/` พร้อมตรวจทั้งบท):

```bash
cd code/ep17 && bash run_all.sh
```

ถ้าแก้บทอยู่แล้วอยากดูแค่ผลรัน (ข้ามขั้นเขียน fence + ตรวจบท) ใช้ `EP17_SKIP_VERIFY=1 bash run_all.sh` · ถ้าต้องการเขียน SVG ไปที่อื่น ตั้ง `EP17_SVG_DIRS=/path/a:/path/b` (ค่าเริ่มต้นคือเขียนสองที่: `assets/diagrams/` ของ repo blog และของโฟลเดอร์ draft)

สภาพแวดล้อมที่ใช้ (ยกมาจาก `out/00_env.txt`):

```
host: Linux 6.18.39+rpt-rpi-2712 aarch64
cpu_cores: 4
go_version: go version go1.24.4 linux/arm64
system_go: go version go1.24.4 linux/arm64
go_mod_go: go 1.24
```

ตัวตรวจ (gate) ของเดโม (ต้องเป็นศูนย์ทุกตัวที่ระบุ):

```
# ตัวตรวจ (gate) ความปลอดภัยของเดโม:
go_files=1
build_warnings=0  (ต้องเป็น 0 — คอมไพล์เงียบ)
gofmt_unformatted=0  (ต้องเป็น 0)
socket_capable_imports=0  (ต้องเป็น 0 — ไม่มีไฟล์ใดเปิด socket)
time_now_calls=0  (ต้องเป็น 0 — เดโมต้องรันซ้ำได้ผลเดิม)
random_calls=0  (ต้องเป็น 0 — ค่าคงที่ทุกตัวเพื่อให้ reproduce ได้)
os_exec_imports=0  (ต้องเป็น 0 — เดโมไม่สั่งคำสั่งภายนอก)
filesystem_writes=0  (ต้องเป็น 0 — เดโมไม่เขียนไฟล์)
filesystem_reads=0  (ต้องเป็น 0 — ข้อมูลฝังในไบนารี ไม่มี os.Open/os.Getenv)
external_deps=0  (standard library ล้วน)
go_vet=ok
```

`go.mod` ของเดโม (ไม่มี dependency ภายนอก):

```go
module ep17

go 1.24
```
