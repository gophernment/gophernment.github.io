แล้วข้อมูลทั้งหมดหายไป

ไม่ใช่หายแบบไปกองที่ถังขยะนะ — มันหายแบบไม่เหลืออะไรเลย เพราะข้อมูลทุกชิ้นที่เราอุตส่าห์พิมพ์เข้ามา อยู่ใน **RAM** (แรม = หน่วยความจำชั่วคราวที่โปรแกรมใช้ทำงาน) ซึ่งเป็นของชั่วคราวของโปรแกรมนั้น พอโปรแกรมจบ ระบบปฏิบัติการก็กวาดคืนทันที

นี่คือกำแพงด่านที่ทุกโปรแกรมต้องข้าม: **โปรแกรมที่ข้อมูลหายเมื่อปิดตัวลง ยังใช้ทำงานจริงไม่ได้** — โปรแกรมจริงทุกตัวในโลกต้องเก็บข้อมูลให้อยู่รอดข้ามการปิด-เปิดโปรแกรม และวิธีพื้นฐานที่สุดที่มนุษย์ใช้มาตั้งแต่ยุคแรกของคอมพิวเตอร์ก็คือ **ไฟล์**

ตอนนี้เราจะเรียน 3 เรื่องที่มาด้วยกันเสมอในงานจริง:

1. **อ่าน/เขียนไฟล์** — ทำให้ข้อมูลอยู่ถาวรบนดิสก์
2. **CLI** (อ่านว่า ซี-แอล-ไอ ย่อจาก command-line interface = ช่องทางให้ผู้ใช้สั่งงานผ่านคำสั่งที่พิมพ์) — ทำให้โปรแกรมของเรา "รับคำสั่ง" ตอนสั่งรันได้ ไม่ต้องเข้าไปแก้โค้ดทุกครั้ง
3. **error handling** (การจัดการข้อผิดพลาด) — ทำให้โปรแกรมรับมือกับสิ่งที่ไม่เป็นไปตามแผนได้อย่างสุภาพ แทนที่จะพังหรือให้ข้อมูลผิดกับเราเงียบ ๆ

สามเรื่องนี้แยกกันเรียนได้ แต่ใช้ด้วยกันจริง — เพราะทุกครั้งที่แตะไฟล์ ทุกครั้งที่รับ input จากผู้ใช้ผ่าน command line เราเปิดช่องให้ "ความไม่แน่นอน" เข้ามาในโปรแกรม

## 1. ข้อมูลหายไปไหนเมื่อปิดโปรแกรม — RAM กับดิสก์

ก่อนเขียนโค้ด ขอวางภาพใหญ่ก่อนว่าความรู้จากตอน 03–06 (ตัวแปร, slice, map, struct) อยู่ตรงไหนของเครื่อง

![ตัวแปรอยู่ในหน่วยความจำ RAM ซึ่งเป็นของชั่วคราว ปิดโปรแกรมแล้วหายไป ส่วนไฟล์อยู่บนดิสก์อย่างถาวร เปิดโปรแกรมใหม่ก็ยังอ่านกลับมาได้](/assets/diagrams/ep07-01-memory-vs-file.svg)

ศัพท์ที่ต้องรู้ก่อนอ่านโค้ดในตอนนี้ทั้งหมด:

- **RAM** (แรม = random access memory) = พื้นที่ทำงานชั่วคราว เร็วมาก — ตัวแปรทุกตัวที่เราเรียนมา อยู่ในนี้ทั้งหมด หมดอายุพร้อมโปรแกรม
- **ดิสก์** (disk / storage = อุปกรณ์เก็บข้อมูล) = ของถาวร ไฟดับก็ยังอยู่ — แต่ช้ากว่า RAM หลายเท่า
- **ไฟล์** (file) = ก้อนข้อมูลที่ถูกตั้งชื่อและเก็บไว้บนดิสก์ ระบบปฏิบัติการเป็นคนจัดการให้ — ตัวไฟล์เองมองเห็นเป็น "ชื่อ" ที่เราอ้างถึงเท่านั้น
- **path** (พาธ = เส้นทางบอกตำแหน่งไฟล์ในเครื่อง) เช่น `notes.txt` (ไฟล์ในโฟลเดอร์ปัจจุบัน), `/home/user/data/notes.txt` (บอกทางเต็ม) — ตรงนี้เป็นแค่ข้อความที่เราส่งให้ระบบปฏิบัติการ มันจะหาภายใน "ไดเรกทอรีปัจจุบัน" (current directory = โฟลเดอร์ที่เรารันโปรแกรมอยู่) ถ้าไม่ใช่ path เต็ม
- **I/O** (อ่านว่า ไอ-โอ ย่อจาก input/output = การรับเข้าและส่งออกข้อมูล) — การอ่านเขียนไฟล์คือ I/O ที่ช้ากว่าการคิดใน RAM มาก นี่คือเหตุผลที่ dev จริงจังกับเรื่องนี้
- **syscall** (อ่านว่า ซิสคอล ย่อจาก system call = การเรียกใช้บริการของระบบปฏิบัติการ) — โปรแกรมของเราเขียนไฟล์เองไม่ได้ตรง ๆ ต้องขอให้ kernel (เคอร์เนล = แกนกลางของระบบปฏิบัติการ) ทำให้ เราเจาะเรื่องนี้เต็มรูปแบบตอน 19 และเรียนเรื่องระบบไฟล์เต็ม ๆ ตอน 21

จำภาพนี้ไว้: **ตัวแปร = ข้อมูลชั่วคราวใน RAM · ไฟล์ = ข้อมูลถาวรบนดิสก์** และการเคลื่อนข้อมูลระหว่างสองที่นี้คือการอ่าน (`Read`) กับการเขียน (`Write`)

## 2. อ่าน/เขียนไฟล์แบบง่ายที่สุด — `os.ReadFile` และ `os.WriteFile`

**แพ็กเกจ** (package = กลุ่มโค้ดสำเร็จรูปที่ภาษาจัดมาให้ ห่อเป็นกล่อง ๆ แล้วเรียกใช้ผ่าน `import`) ที่เราจะใช้ชื่อ `os` (อ่านว่า โอ-เอส ย่อจาก operating system) — ของทุกอย่างที่แตะระบบปฏิบัติการ ไม่ว่าจะเป็นไฟล์, environment variable (ค่าตั้งต้นของระบบ), การจบโปรแกรม อยู่ในนี้

สร้างไฟล์ `hello_file.go` ในโฟลเดอร์ `gopher-course` (โฟลเดอร์เดียวกับตอนก่อน ๆ) แล้วพิมพ์ตาม:

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	msg := "สวัสดีจากไฟล์!\n"

	// เขียน: สร้าง/ทับไฟล์ note.txt
	err := os.WriteFile("note.txt", []byte(msg), 0644)
	if err != nil {
		fmt.Println("เขียนไฟล์ไม่สำเร็จ:", err)
		return
	}
	fmt.Println("เขียน note.txt เรียบร้อย")

	// อ่าน: ดึงเนื้อหาทั้งไฟล์เข้ามาเป็น []byte
	data, err := os.ReadFile("note.txt")
	if err != nil {
		fmt.Println("อ่านไฟล์ไม่สำเร็จ:", err)
		return
	}
	fmt.Printf("อ่านได้ %d ไบต์\n", len(data))
	fmt.Print("เนื้อหา: ", string(data))
}
```

รันด้วย `go run hello_file.go` จะได้

```
เขียน note.txt เรียบร้อย
อ่านได้ 41 ไบต์
เนื้อหา: สวัสดีจากไฟล์!
```

ถ้าลองเปิดไฟล์ `note.txt` ในโฟลเดอร์นั้นดู (เช่นด้วยคำสั่ง `cat note.txt`) คุณจะเห็นข้อความ `สวัสดีจากไฟล์!` อยู่ในไฟล์จริง ๆ — ลองปิดโปรแกรม เปิดใหม่ รันโค้ดอ่านไฟล์ (บรรทัด `os.ReadFile`) อย่างเดียว ข้อมูลก็ยังอยู่ นี่คือความต่างทั้งหมดระหว่าง RAM กับดิสก์ที่เราพูดถึงในหัวข้อ 1

### แกะโค้ดทีละบรรทัด

`import ( "fmt" "os" )` — ตอนนี้เรามี 2 แพ็กเกจ: `fmt` สำหรับพิมพ์ข้อความ (รู้จักจากตอน 03) และ `os` สำหรับคุยกับระบบปฏิบัติการ

`msg := "สวัสดีจากไฟล์!\n"` — ตัวแปร `string` ธรรมดา ๆ จากตอน 03 เลย สังเกตตัว `\n` ท้ายข้อความ: มันคือ "อักขระขึ้นบรรทัดใหม่" (newline) ตัวเดียว ไม่ใช่ 2 ตัวอักษร — เขียนแบบนี้ได้เพราะ Go อ่าน `\n` ในเครื่องหมายคำพูดเป็นรหัสพิเศษ

`err := os.WriteFile("note.txt", []byte(msg), 0644)` — บรรทัดนี้ทำงาน 3 อย่างพร้อมกัน:

- `os.WriteFile` เป็น **ฟังก์ชัน** (จากตอน 05) ที่รับ 3 argument (argument = ค่าที่เราส่งให้ฟังก์ชัน เรียงตามลำดับ — นิยามเต็มอยู่ในหัวข้อ 4): ชื่อไฟล์, ข้อมูลที่จะเขียน, และ **permission** (เพอร์มิชชัน = สิทธิ์ว่าใครอ่าน/เขียนไฟล์นี้ได้บ้าง)
- `[]byte(msg)` — เจ้าตัวนี้ยัด 4 ความคิดไว้ในบรรทัดเดียว แยกออกมาดูทีละอัน:
  - **แปลงอะไร**: แปลงชนิดข้อมูลจาก `string` ให้กลายเป็น **`[]byte`** (อ่านว่า สไลซ์-ไบต์)
  - **`[]byte` คืออะไร**: slice ของ `byte` (ไบต์ = หน่วยข้อมูล 1 ตัว เก็บค่าได้ 0–255) — จำ `[]int`, `[]string` จากตอน 06 ได้ไหม? `[]byte` คือญาติตัวเดียวกัน แต่เก็บ "ตัวเลขดิบ" แทน
  - **ทำไมต้องแปลง**: ฟังก์ชันระดับระบบปฏิบัติการทำงานกับไบต์ดิบ ไม่รู้จัก `string` ของ Go
  - **ได้อะไรกลับ**: `os.WriteFile` เขียนไบต์เหล่านี้ลงไฟล์ตรง ๆ — ตัวอักษรที่ตาเราเห็นจะกลายเป็นตัวเลขไบต์ (เรื่องนี้จะชัดมากในตอน 08)
- ค่าที่คืนกลับมาเก็บใน `err` — ตัวแปรนี้จะเป็น `nil` ถ้าทุกอย่างเรียบร้อย (`nil` = ไม่มีค่า/ว่างเปล่า ในที่นี้แปลว่า "ไม่มี error")

`if err != nil { ... return }` — นี่คือ **หัวใจของ error handling ใน Go** และเป็น **แพตเทิร์น** (pattern = แบบแผนการเขียนที่ใช้ซ้ำจนเป็นมาตรฐาน) ที่คุณจะเห็นซ้ำร้อยครั้งต่อจากนี้ไปอีก: เช็ค error ก่อน แล้วจัดการ (หรือส่งต่อ) แล้วออกจากฟังก์ชันทันทีถ้าไปต่อไม่ได้

`data, err := os.ReadFile("note.txt")` — `ReadFile` คืนค่า 2 อย่าง คือข้อมูล ([`[]byte`]) กับ error — **การคืนค่าหลายค่า** (multiple return) ที่เราเรียนตอน 05 ถูกใช้เต็มที่ตรงนี้ และเป็นสาเหตุว่าทำไมเราต้องเช็ค `err` ก่อนใช้ `data`: ถ้าอ่านไม่สำเร็จ `data` จะเป็นค่าว่าง (`nil`) — การใช้ค่าว่างโดยไม่รู้ตัวคือที่มาของบั๊กเงียบ ๆ ที่น่ากลัวที่สุด

`fmt.Printf("อ่านได้ %d ไบต์\n", len(data))` — `len()` ใช้กับ `[]byte` ได้เหมือน slice ปกติ (ตอน 06)

`fmt.Print("เนื้อหา: ", string(data))` — `string(data)` แปลง `[]byte` กลับเป็น `string` เพื่อให้พิมพ์ออกมาอ่านรู้เรื่อง

### ทำไม 41 ไบต์ ทั้งที่ข้อความดูสั้น

นี่เป็นจุดที่มือใหม่ตกใจบ่อย แต่เป็นความรู้สำคัญมาก: ตัวอักษรไทย 1 ตัว **ไม่เท่ากับ 1 ไบต์** — มันกิน 3 ไบต์ ในรหัส **UTF-8** (อ่านว่า ยู-ที-เอฟ-เอท = มาตรฐานการเข้ารหัสตัวอักษรที่รองรับทุกภาษาในโลก)

ข้อความ `สวัสดีจากไฟล์!` มีตัวอักษร 14 ตัว แต่มองในมุมไบต์:

- ตัวอักษรไทย 13 ตัว × 3 ไบต์ = 39 ไบต์
- เครื่องหมาย `!` 1 ตัว = 1 ไบต์
- ตัวขึ้นบรรทัดใหม่ `\n` = 1 ไบต์

รวมเป็น 39 + 1 + 1 = **41 ไบต์** — ตรงกับที่โปรแกรมพิมพ์ออกมา เรื่องนี้จะกลายเป็นเรื่องใหญ่มากตอน 08 (การแทนข้อมูล) และเป็นเหตุผลว่าทำไมเวลาโปรแกรมตัดข้อความไทยผิด ๆ กลางคำ มันถึงได้พัง — เราจะเข้าใจกลไกทั้งหมดตรงนั้น

### กับดักสำคัญ: `os.WriteFile` **เขียนทับของเดิม**

`os.WriteFile` ไม่ได้เขียน "ต่อท้าย" — มันล้างไฟล์เดิมทิ้งทั้งหมดแล้วเขียนใหม่ เอกสารทางการของ Go อธิบายไว้ว่า ถ้าไฟล์มีอยู่แล้ว `WriteFile` จะ **truncate** (ทรังเคต = ตัด/ล้างเนื้อหาเดิม) ก่อนเขียน โดยไม่เปลี่ยน permission เดิม สร้างไฟล์ `truncate1.go` ในโฟลเดอร์ `gopher-course` แล้วรันด้วย `go run truncate1.go` ดู:

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	os.WriteFile("t.txt", []byte("ข้อความยาว ๆ หลายบรรทัด\nบรรทัดสอง\n"), 0644)
	fi, _ := os.Stat("t.txt") // Stat = ขอดูข้อมูลของไฟล์ (ขนาด, เวลา, สิทธิ์)
	fmt.Println("ขนาดก่อน:", fi.Size())

	os.WriteFile("t.txt", []byte("สั้น\n"), 0644) // เขียนทับ
	fi, _ = os.Stat("t.txt")
	fmt.Println("ขนาดหลัง:", fi.Size())

	b, _ := os.ReadFile("t.txt")
	fmt.Print("เนื้อหาหลังเขียนทับ: ", string(b))
}
```

ผลลัพธ์จริง

```
ขนาดก่อน: 94
ขนาดหลัง: 13
เนื้อหาหลังเขียนทับ: สั้น
```

ไฟล์หดจาก 94 ไบต์เหลือ 13 ไบต์ — ของเดิมหายหมด **จำไว้**: ถ้าอยาก "เพิ่มข้อความต่อท้าย" ต้องบอกระบบปฏิบัติการให้ชัดว่าเปิดแบบ **append** (แอพเพนด์ = ต่อท้าย) เดี๋ยวเราทำในหัวข้อ 6

เรื่อง **permission 0644** ที่ดูเหมือนตัวเลขวิเศษ: มันคือสิทธิ์ของไฟล์แบบดั้งเดิมของระบบตระกูล Unix เขียนเป็นเลขฐานแปด (จะเข้าใจฐานตัวเลขเต็ม ๆ ตอน 08) — จำแบบใช้งานจริงว่า `0644` = "เจ้าของอ่านเขียนได้ คนอื่นอ่านได้อย่างเดียว" เป็นค่าที่นิยมที่สุด

อีก 2 เรื่องของ `os.WriteFile` ที่ต้องรู้ก่อนไปต่อ:

1. **permission มีผลแค่ตอนสร้างไฟล์ใหม่** — ถ้าไฟล์มีอยู่แล้ว ค่า `0644` ที่เราส่งไปจะถูกละเลย permission เดิมของไฟล์ไม่ถูกแก้
2. **การเขียนทับไม่ใช่การทำงานแบบอะตอม** (atomic = จบในขั้นตอนเดียว ไม่มีสภาพ "ทำค้างไว้ครึ่งทาง") — เอกสาร Go บอกตรง ๆ ว่า `WriteFile` ต้องเรียกงานระบบหลายรอบ ถ้าล้มกลางทางอาจเหลือไฟล์ที่เขียนค้างไว้ครึ่งเดียว

เพราะข้อ 2 นี่เอง งานที่ต้องการความแม่นยำสูง (เช่นเขียนฐานข้อมูล) เขาไม่ใช้วิธี "เขียนทับไฟล์เดิม" ตรง ๆ แต่เขียนลงไฟล์ใหม่ก่อนแล้วค่อยสลับชื่อไฟล์ (เรื่องนี้จะกลับมาอีกตอน 21)

## 3. เปิดไฟล์เองทีละขั้น — `os.Create`, `bufio` และ `defer`

`os.WriteFile` เหมาะกับงานสั้น ๆ ที่ "เตรียมข้อมูลใน RAM จบแล้วเขียนทิ้งทีเดียว" แต่ในงานจริงเรามักเจอกรณีที่ต้องเขียน **หลายรอบ** หรือเขียนข้อมูลที่**ใหญ่จนไม่อยากกักไว้ใน RAM ทั้งก้อน** — ตรงนี้เราต้อง "เปิดไฟล์ค้างไว้" แล้วเขียนใส่เป็นระยะ ๆ

การเปิดไฟล์ = การบอกระบบปฏิบัติการว่า "ยกไฟล์นี้มาให้โปรแกรมใช้" แล้วระบบปฏิบัติการจะคืนสิ่งที่เรียกว่า **file descriptor** (ไฟล์ดีสคริปเตอร์ = หมายเลขช่องทางที่ใช้คุยกับไฟล์นั้น) กลับมา และหมายเลขนี้เป็นทรัพยากรที่มีจำกัด — โปรแกรมหนึ่งเปิดไฟล์ค้างไว้ได้ไม่กี่พันตัวต่อโปรเซส (โปรเซส = กระบวนการทำงานของโปรแกรมหนึ่งตัว) **นี่คือเหตุผลที่ต้องปิดไฟล์เสมอ** ไม่ใช่แค่เรื่องความเรียบร้อย สร้างไฟล์ `bufio_write.go` แล้วพิมพ์ตาม (รันด้วย `go run bufio_write.go`):

```go
package main

import (
	"bufio"
	"fmt"
	"os"
)

func main() {
	f, err := os.Create("log.txt")
	if err != nil {
		fmt.Println("สร้างไฟล์ไม่สำเร็จ:", err)
		return
	}
	// ปิดไฟล์แน่นอนตอนฟังก์ชันนี้จบ และรายงาน error ที่อาจเกิดตอนปิด
	defer func() {
		if cerr := f.Close(); cerr != nil {
			fmt.Println("ปิดไฟล์ไม่สำเร็จ:", cerr)
		}
	}()

	w := bufio.NewWriter(f)
	for i := 1; i <= 3; i++ {
		if _, err := fmt.Fprintf(w, "บรรทัดที่ %d\n", i); err != nil {
			fmt.Println("เขียนไม่สำเร็จ:", err)
			return
		}
	}
	if err := w.Flush(); err != nil {
		fmt.Println("flush ไม่สำเร็จ:", err)
		return
	}
	fmt.Println("เขียน log.txt 3 บรรทัดเรียบร้อย")
}
```

รันแล้วได้

```
เขียน log.txt 3 บรรทัดเรียบร้อย
```

และเนื้อหาใน `log.txt` คือ

```
บรรทัดที่ 1
บรรทัดที่ 2
บรรทัดที่ 3
```

### แกะโค้ด

`f, err := os.Create("log.txt")` — `os.Create` คือการเปิดไฟล์แบบที่พบบ่อยที่สุดในงานเขียน เอกสาร Go ระบุว่า: ถ้าไฟล์มีอยู่แล้ว **มันจะถูก truncate ทิ้ง** ถ้าไม่มีก็สร้างใหม่ด้วยโหมด `0o666` — เขียนได้ทั้ง `0o666` และ `0666` เป็นค่าเดียวกัน แล้วระบบจะเอาไปตัดสิทธิ์ตาม **umask** (= ค่าตั้งต้นของระบบที่กำหนดว่าไฟล์ใหม่ไม่ควรได้สิทธิ์อะไร) ชื่อ `Create` ทำให้มือใหม่เข้าใจผิดบ่อย ๆ ว่ามัน "สร้างไฟล์" เฉย ๆ — ความจริงคือ "เปิดไฟล์เพื่อเขียน โดยสร้างให้ถ้ายังไม่มี **และล้างของเดิมทิ้งถ้ามี**"

`f` ตรงนี้เป็น **`*os.File`** (พอยน์เตอร์ไปยังโครงสร้างที่แทนไฟล์ที่เปิดอยู่ — เครื่องหมาย `*` และคำว่า pointer เราจะเรียนเต็ม ๆ ตอน 13–14 ตอนนี้ให้อ่านว่า "ตัวแทนของไฟล์ที่เปิดอยู่" พอ) แล้วเราก็ใช้ `f` เป็นตัวแทนของไฟล์นั้นตลอดการทำงาน

`w := bufio.NewWriter(f)` — หลายคนสงสัยว่าทำไมไม่เขียนลง `f` ตรง ๆ ได้เลย คำตอบคือเรื่องประสิทธิภาพ: ทุกครั้งที่เขียนลงไฟล์จริง เราต้องผ่าน syscall ไปหา kernel (ช้า) — **`bufio`** (อ่านว่า บัฟ-ไอโอ ย่อจาก buffered I/O = I/O ที่มีที่พักข้อมูลชั่วคราว) เป็นตัวกลางที่รับข้อมูลของเรามา **กักไว้ใน RAM ก่อน** (เรียกว่า **buffer** = บัฟเฟอร์ = ที่พักข้อมูลชั่วคราว) พอเต็มก้อนหรือเราสั่ง `Flush` มันถึงส่งลงไฟล์จริงทีเดียว

`bufio.NewWriter(f)` จึงแปลว่า "สร้างตัวเขียนที่มีบัฟเฟอร์ ห่อไฟล์ `f` ไว้" — และเราก็เขียนผ่าน `w` ตั้งแต่นั้น ไม่ใช่ `f`

`defer func() { ... f.Close() ... }()` — **`defer`** (อ่านว่า ดีเฟอร์ = ผัดไว้ทำทีหลัง) เป็นคำสั่งของ Go ที่แปลว่า "จดงานนี้ไว้ก่อน แล้วไปทำ**ตอนฟังก์ชันรอบนี้กำลังจะจบ**" ไม่ว่าจะจบด้วยทางไหน — จบปกติ, `return` กลางทาง, หรือแม้แต่เกิด panic (ข้อผิดพลาดร้ายแรงที่หยุดโปรแกรมกลางคัน) — `defer` จะยังทำงานให้

กติกาของ `defer` ที่ต้องรู้:

- ทำงานแบบ **LIFO** (last in, first out = เข้าทีหลัง ออกก่อน) ถ้ามีหลายอันในฟังก์ชันเดียวกัน อันที่ประกาศ**หลังสุด**จะทำงาน**ก่อน**
- argument ของคำสั่งที่ถูก defer จะถูก "จดค่า" ไว้ ณ ตอนที่เจอคำสั่ง defer ไม่ใช่ตอนที่มันทำงาน (เดี๋ยวเราเจอผลกระทบของข้อนี้ตอนเรียน closure — ยังไม่ต้องกังวลตอนนี้)
- ถ้าไม่ใช้ `defer` เราจะต้องเขียน `f.Close()` เองทุกทางออก ซึ่งเรามักลืม — โดยเฉพาะเมื่อมี `return` หลายจุด

ทำไมต้องห่อด้วย `func() { ... }()` แทนที่จะเขียน `defer f.Close()` ตรง ๆ? เพราะ `f.Close()` **คืนค่าเป็น error ได้** และเราต้องไม่ทิ้ง error นั้น — การห่อเป็นฟังก์ชันที่เรียกใช้ทันที (`func(){...}()` = ประกาศฟังก์ชันแล้วเรียกมันเดี๋ยวนั้นเลย — เราจะเห็นบ่อยขึ้นในภายหลัง) ทำให้เราเช็ค error ตอนปิดได้

> ถ้าเขียน `defer f.Close()` เปล่า ๆ ตัวคอมไพเลอร์ (คอมไพล์เลอร์ = ตัวแปลงโค้ด Go ให้เป็นโปรแกรมที่เครื่องรันได้) ของ Go ไม่เตือนอะไรเลย — แต่เรากำลังทิ้งข้อมูลไว้ 1 อย่าง (นี่คือเหตุผลที่งานจริงหลายทีมกำหนดมาตรฐานว่าเขียนแบบห่อฟังก์ชัน)

`for i := 1; i <= 3; i++` กับ `fmt.Fprintf(w, "บรรทัดที่ %d\n", i)` — `fmt.Fprintf` เหมือน `fmt.Printf` แต่ส่งข้อความไปที่ **ตัวเขียนที่เราระบุ** (ที่นี่คือ `w`) แทนที่จะออกจอ ตำแหน่ง `_` ตัวแรกคือจำนวนไบต์ที่เขียนไป — เราไม่ใช้ จึงทิ้งด้วย `_` (รู้จักจากตอน 06) **และเช็คแค่ error เท่านั้น** เพราะจำนวนไบต์ที่เขียนไม่ใช่สิ่งที่เราต้องสนใจในงานนี้

`if err := w.Flush(); err != nil { ... }` — **บรรทัดที่ห้ามลืมเมื่อใช้ `bufio`** บัฟเฟอร์ไม่ส่งข้อมูลลงไฟล์เองจนกว่าจะเต็ม (ค่าเริ่มต้นของ `bufio.Writer` คือ 4 KiB = 4096 ไบต์) เราจึงต้อง **`Flush`** (ฟลัช = ระบายข้อมูลในบัฟเฟอร์ออกไปให้หมด) ก่อนจบ ถ้าลืม โปรแกรมจะ "เหมือนทำงานสำเร็จ" แต่ไฟล์ว่างเปล่า — บั๊กแบบนี้หลอกตาที่สุด เพราะไม่มี error อะไรโผล่มาเลย

> จุดที่ต้องระวังเป็นพิเศษ: `bufio.Writer` **ไม่มีเมธอด `Close`** ของตัวเอง (มีแค่ `Flush`) — **เมธอด** (method) = ฟังก์ชันที่ผูกอยู่กับชนิดข้อมูล เช่น `f.Close` คือเมธอดของไฟล์ `f` — การปิดไฟล์ `f` ไม่ได้ทำให้บัฟเฟอร์ถูกระบายอัตโนมัติ ดังนั้นรูปแบบที่ปลอดภัยคือ `Flush()` แล้วเช็ค error **จากนั้น** จึงปิดไฟล์ (และเช็ค error ของ `Close` อีกครั้ง) ตามที่โค้ดข้างบนทำ

### อ่านไฟล์ทีละบรรทัด — `os.Open` + `bufio.Scanner`

สลับด้านบ้าง เวลาอ่านไฟล์ใหญ่หรืออ่านทีละบรรทัด การใช้ `os.ReadFile` ที่ดูดทั้งไฟล์เข้า RAM ไม่เหมาะ วิธีที่นิยมคืออ่านทีละบรรทัดด้วย **`bufio.Scanner`** (สแกนเนอร์ = อุปกรณ์/ตัวช่วยไล่อ่านทีละบรรทัด) — สร้างไฟล์ `readline.go` แล้วพิมพ์ตาม (รันด้วย `go run readline.go` ต่อจาก `log.txt` ที่เพิ่งสร้าง):

```go
package main

import (
	"bufio"
	"fmt"
	"os"
	"strings"
)

func main() {
	f, err := os.Open("log.txt") // Open = เปิดเพื่อ "อ่าน" เท่านั้น
	if err != nil {
		fmt.Println("เปิดไฟล์ไม่สำเร็จ:", err)
		return
	}
	defer f.Close()

	sc := bufio.NewScanner(f)
	n := 0
	for sc.Scan() { // อ่านทีละบรรทัด จนจบไฟล์
		n++
		fmt.Printf("%d> %s\n", n, strings.TrimSpace(sc.Text()))
	}
	if err := sc.Err(); err != nil { // ต้องเช็ค error หลังวนจบด้วย
		fmt.Println("อ่านไม่สำเร็จ:", err)
	}
	fmt.Println("รวม", n, "บรรทัด")
}
```

ผลลัพธ์จริง (รันต่อจาก `log.txt` ที่เราเพิ่งสร้าง)

```
1> บรรทัดที่ 1
2> บรรทัดที่ 2
3> บรรทัดที่ 3
รวม 3 บรรทัด
```

ประเด็นที่ต้องเข้าใจในโค้ดนี้:

- **`os.Open` vs `os.Create`** — ชื่อคล้ายกัน แต่คนละเจตนา: `Open` เปิด**เพื่ออ่าน** (สิทธิ์อ่านเท่านั้น) และ **ไม่แตะเนื้อหาในไฟล์เลย** ส่วน `Create` เปิดเพื่อเขียนและล้างของเดิมทิ้ง นี่คือความต่างที่ทำให้มือใหม่เสียข้อมูลมาแล้วนับไม่ถ้วน — ถ้าแค่อยากอ่าน ใช้ `Open`
- **`sc.Scan()`** คืนค่า `bool` (จริง/เท็จ) จึงใช้เป็นเงื่อนไขของ `for` ได้ตรง ๆ — มันจะอ่านทีละบรรทัด แล้วคืน `true` ไปเรื่อย ๆ จนหมดไฟล์จึงคืน `false`
- **`sc.Text()`** คืนข้อความของบรรทัดนั้น (ตัดตัวขึ้นบรรทัดใหม่ออกให้แล้ว) — `strings.TrimSpace` เป็นการตัดช่องว่างหัวท้ายออกอีกชั้น เพื่อกันข้อมูลที่ผู้ใช้เผลอเคาะ space ทิ้งไว้ตอนบันทึก (เราจะใช้ท่านี้บ่อยมากใน mini-project)
- **`sc.Err()`** — บรรทัดนี้คนลืมกันเยอะที่สุด เอกสาร Go ระบุชัดว่า การสแกนจะหยุดแบบกู้คืนไม่ได้เมื่อเจอ 3 กรณี: จบไฟล์, เจอ error จาก I/O, หรือเจอบรรทัดที่ยาวเกินบัฟเฟอร์ — ที่แย่คือการหยุดเพราะ error กับหยุดเพราะจบไฟล์ **หน้าตาเหมือนกันเป๊ะในมุมของ loop** (`Scan` คืน `false` ทั้งคู่) ทางเดียวที่จะแยกได้คือถาม `sc.Err()` หลังวงวนจบแล้ว — ถ้าเป็น `nil` แปลว่าจบไฟล์ตามปกติ

**สรุปว่าจะเลือกวิธีไหน**

| อยากทำอะไร | ใช้อะไร | เหตุผล |
|---|---|---|
| อ่านไฟล์เล็กทั้งไฟล์ | `os.ReadFile` | สั้นที่สุด ได้ข้อมูลก้อนเดียวจบ |
| อ่านทีละบรรทัด / ไฟล์อาจใหญ่ | `os.Open` + `bufio.Scanner` | ไม่กิน RAM ทั้งไฟล์ และอ่านทีละบรรทัดได้ |
| เขียนครั้งเดียวทั้งก้อน | `os.WriteFile` | สั้น ปลอดภัยสำหรับข้อมูลเล็ก |
| เขียนหลายรอบ / ต่อท้าย / ไฟล์ใหญ่ | `os.OpenFile` + `bufio.Writer` (+`Flush`) | คุมได้ละเอียด ต่อท้ายได้ |

## 4. ทำ CLI — ให้โปรแกรมรับคำสั่งตอนสั่งรัน

ทุกโปรแกรมที่เราเขียนมาตอน 03–06 ต้องเข้าไปแก้โค้ดในไฟล์ทุกครั้งที่อยากเปลี่ยนค่า เช่นเคยเขียน `temps := []int{31, 33, 29}` ไว้ตรง ๆ แล้วอยากลองเลขชุดอื่นก็ต้องแก้แล้วรันใหม่ ซึ่งใช้ไม่ได้ในโลกจริง

**CLI** (command-line interface) คือวิธีที่เก่าแก่และยังทรงพลังที่สุด: ผู้ใช้พิมพ์คำสั่งพร้อมค่าต่าง ๆ ต่อท้าย แล้วโปรแกรมของเรารับค่าเหล่านั้นไปทำงาน — ลองนึกถึงคำสั่งที่คุณใช้ทุกวันอย่าง `go run hello_file.go` ตรง `hello_file.go` ก็คือ argument ที่เราส่งให้โปรแกรม `go`

**คำศัพท์ที่ต้องรู้**

- **command** (คอมมานด์ = คำสั่ง) = ชื่อโปรแกรมที่เราสั่งรัน
- **argument** (อาร์กิวเมนต์ = ค่าที่ส่งให้โปรแกรมต่อท้ายชื่อ) เช่นใน `go run hello_file.go` มี argument 2 ตัวคือ `run` กับ `hello_file.go`
- **flag** (แฟล็ก = argument พิเศษที่ขึ้นต้นด้วย `-` เพื่อบอก "ตัวเลือก" ของโปรแกรม) เช่น `-name สมชาย`
- **usage** (ยูเสจ = ข้อความวิธีใช้) = คำอธิบายว่าโปรแกรมนี้รับ flag อะไรบ้าง

### 4.1 ระดับพื้นฐานสุด: `os.Args`

**`os.Args`** คือ slice ของ `string` (ตอน 06 มาถึงตรงนี้!) ที่ระบบปฏิบัติการส่งทุกอย่างบน "บรรทัดคำสั่ง" มาให้โปรแกรม — ที่เรียกว่าบรรทัดคำสั่งก็คือบรรทัดเดียวที่เราพิมพ์ใน **terminal** (เทอร์มินัล = โปรแกรมหน้าจอที่เราใช้พิมพ์คำสั่งคุยกับระบบปฏิบัติการ แทนการคลิกเมาส์) ช่องที่ 0 คือชื่อโปรแกรมเสมอ ส่วนช่องถัดไปคือ argument ที่ผู้ใช้พิมพ์

![หนึ่งบรรทัดที่พิมพ์ใน terminal ถูกแยกเป็น argument หลายชิ้นใน os.Args แล้ว flag.Parse จับคู่แต่ละ flag ให้ตัวแปรของเรา](/assets/diagrams/ep07-02-cli-args-flag.svg)

สร้างไฟล์ใหม่ชื่อ `args.go` ในโฟลเดอร์ `gopher-course` (ชื่อไฟล์ต้องตรงกับที่ใช้ในคำสั่งด้านล่าง) แล้วพิมพ์ตาม:

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	fmt.Println("ชื่อโปรแกรม:", os.Args[0])
	fmt.Println("จำนวน argument ที่ส่งมา:", len(os.Args)-1)
	for i, a := range os.Args[1:] {
		fmt.Printf("argument ตัวที่ %d: %s\n", i+1, a)
	}

	if len(os.Args) < 2 {
		fmt.Println("วิธีใช้:", os.Args[0], "<ชื่อของคุณ>")
		return
	}
	fmt.Println("สวัสดี", os.Args[1])
}
```

ก่อนรัน ขอแยกให้ชัดก่อนว่า 2 คำสั่งนี้ต่างกันตรงไหน (เราใช้สลับกันมาตลอดแต่ยังไม่เคยอธิบาย):

- **`go run args.go`** = คอมไพล์ (แปลงโค้ดเป็นโปรแกรมที่รันได้) แล้วรันให้เลยในคำสั่งเดียว ไฟล์โปรแกรมที่ได้เป็นไฟล์ชั่วคราว ซึ่งถูกลบทิ้งหลังรันจบ
- **`go build -o args args.go`** = คอมไพล์เป็นไฟล์โปรแกรมเก็บไว้ใช้ซ้ำ — อ่านว่า "คอมไพล์ `args.go` แล้วตั้งชื่อไฟล์โปรแกรมที่ได้ว่า `args`"

หลังจาก build เสร็จ เราเรียกโปรแกรมนั้นด้วย **`./args`** — เครื่องหมาย `./` แปลว่า "ไฟล์ในโฟลเดอร์ปัจจุบัน" (ถ้าพิมพ์แค่ `args` เฉย ๆ ระบบจะไปหาชื่อนี้ในโฟลเดอร์ระบบของเครื่องแทน แล้วจะหาไม่เจอ) ลองเทียบกันดู: `go run args.go` ให้ผลลัพธ์เหมือนกัน แต่ `os.Args[0]` จะเป็นที่อยู่ไฟล์ชั่วคราวที่ `go` สร้างขึ้น ไม่ใช่ `./args`

รันแบบไม่ส่งอะไรเลย (`go build -o args args.go` แล้ว `./args`)

```
ชื่อโปรแกรม: ./args
จำนวน argument ที่ส่งมา: 0
วิธีใช้: ./args <ชื่อของคุณ>
```

รันแบบส่ง argument จริง

```
$ ./args สมชาย และ สมหญิง
ชื่อโปรแกรม: ./args
จำนวน argument ที่ส่งมา: 3
argument ตัวที่ 1: สมชาย
argument ตัวที่ 2: และ
argument ตัวที่ 3: สมหญิง
สวัสดี สมชาย
```

สังเกต 2 อย่าง:

1. **`os.Args[0]` คือชื่อโปรแกรม** — ที่เห็น `./args` เพราะเราสั่งรันแบบนั้น ถ้ารันด้วย path เต็ม ตรงนี้ก็จะโชว์ path เต็ม (นี่คือเหตุผลที่เราใช้ `os.Args[0]` ในข้อความวิธีใช้ได้ — โปรแกรมจะบอกวิธีใช้ถูกต้องตามวิธีที่ผู้ใช้เรียกมัน) และถ้าเป็น `go run args.go` ตรงนี้จะเป็นที่อยู่ไฟล์ชั่วคราวที่ `go` สร้างขึ้นมา
2. **การตัด slice ด้วย `[1:]`** มาจากตอน 06 ตรง ๆ — เรา "ตัดชื่อโปรแกรมทิ้ง" เพื่อให้เหลือแค่ argument ของผู้ใช้ แล้ว `range` วนตามลำดับ

**กับดักที่อันตรายที่สุดของ `os.Args`**: ถ้าดัชนีไม่มีอยู่ Go จะ **panic** ทันที ลองรันโค้ดที่จงใจเข้าถึง `os.Args[1]` โดยไม่เช็ค `len` ก่อน — สร้างไฟล์แยกต่างหากชื่อ `args_panic.go` (ต้องเป็นไฟล์ใหม่ ไม่ใช่ `args.go` เพราะในโฟลเดอร์เดียวกันมี `func main` ซ้ำกัน 2 ตัวไม่ได้ — เราจึงรันโปรแกรมเหล่านี้แบบระบุชื่อไฟล์ ซึ่งนับเป็นไฟล์เดียว ไม่ได้ยกทั้งโฟลเดอร์มาคอมไพล์พร้อมกัน) แล้วพิมพ์ตาม:

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	// จงใจไม่เช็ค len(os.Args) ก่อนเข้าถึง os.Args[1]
	fmt.Println("สวัสดี", os.Args[1])
}
```

ผลลัพธ์จริงเมื่อรันโดยไม่ส่ง argument (`go run args_panic.go`)

```
panic: runtime error: index out of range [1] with length 1

goroutine 1 [running]:
main.main()
	/tmp/ep07/args_panic.go:10 +0xa0
exit status 2
```

ข้อความ `index out of range [1] with length 1` อ่านตรงตัวว่า "ขอช่องที่ 1 แต่ของที่มียาวแค่ 1 ช่อง (มีแค่ช่อง 0)" — **panic** คืออาการที่โปรแกรมยอมแพ้ทันที ไม่มีโอกาสได้บอกผู้ใช้ว่าอะไรผิด ไม่ได้คืน error ให้ใครจัดการ — จากมุมผู้ใช้ มันคือโปรแกรมพังแบบเห็นข้อความแปลก ๆ ที่ไม่ช่วยอะไร **เพราะฉะนั้นการเช็คขอบเขตก่อนเข้าถึง index (ทั้ง slice และ os.Args) คือวินัยที่ต้องติดตัว** — นี่คือข้อผิดพลาดชนิดเดียวกับที่เราฝึกหลบใน drill ตอน 06

อีกเรื่องที่ต้องเข้าใจ: **ช่องว่างคือตัวแบ่ง argument** ในบรรทัด `./args สมชาย และ สมหญิง` โปรแกรมได้ 3 arguments ไม่ใช่ 1 — ถ้าต้องการส่งข้อความที่มีช่องว่างเป็นชิ้นเดียว ต้องครอบด้วยเครื่องหมายคำพูด

ตัวอย่างข้างล่างใช้ชื่อ `notecli` ซึ่งเป็นโปรแกรมที่เราจะสร้างจริงในหัวข้อ 6 (ตอนนี้ยังไม่มีโปรแกรมนี้ — ไม่เป็นไร ให้ดูแค่การแบ่ง argument พอ)

```bash
./notecli -text "ซื้อนม"     # ได้ 1 argument: ซื้อนม
./notecli -text ซื้อนม       # ได้ 2 arguments: ซื้อนม  ← คนละเรื่องเลย
```

### 4.2 ระดับใช้งานจริง: แพ็กเกจ `flag`

`os.Args` ทำงานได้ แต่พอ flag มากขึ้นการนับตำแหน่งช่อง (ช่องที่ 3 คือชื่อไฟล์ ช่องที่ 4 คือจำนวน) จะเปราะและอ่านไม่ออก แพ็กเกจ `flag` ของ Go มาตรฐานจึงเข้ามาจัดการแทน: เราประกาศ "โปรแกรมนี้รับ flag อะไร ชื่ออะไร ค่าตั้งต้นเท่าไร" แล้วให้มันอ่านให้

สร้างไฟล์ใหม่ชื่อ `flags.go` แล้วพิมพ์ตาม (หลังจากนี้เราจะ build ด้วย `go build -o flags flags.go` แล้วรันด้วย `./flags ...` เหมือนที่ทำกับ `args` ข้างบน)

```go
package main

import (
	"flag"
	"fmt"
)

func main() {
	// ประกาศ flag: flag.String(ชื่อ, ค่าเริ่มต้น, คำอธิบาย) → คืน *string
	name := flag.String("name", "ไม่ระบุชื่อ", "ชื่อเจ้าของบันทึก")
	lines := flag.Int("n", 3, "จำนวนบรรทัดที่ต้องการ")
	loud := flag.Bool("loud", false, "พิมพ์ตัวพิมพ์ใหญ่")

	flag.Parse() // อ่านค่าที่ผู้ใช้พิมพ์จาก command line

	fmt.Println("name =", *name)
	fmt.Println("n    =", *lines)
	fmt.Println("loud =", *loud)
	fmt.Println("argument ที่เหลือ (ไม่ใช่ flag) =", flag.Args())
}
```

รันเปล่า ๆ (สร้างโปรแกรมก่อนด้วย `go build -o flags flags.go` แล้วรัน `./flags` ไม่ส่ง flag อะไรเลย) จะได้ค่าตั้งต้นทั้งหมด

```
name = ไม่ระบุชื่อ
n    = 3
loud = false
argument ที่เหลือ (ไม่ใช่ flag) = []
```

รันพร้อม flag

```
$ ./flags -name สมหญิง -n 5 -loud extra1 extra2
name = สมหญิง
n    = 5
loud = true
argument ที่เหลือ (ไม่ใช่ flag) = [extra1 extra2]
```

**แกะโค้ด**

`name := flag.String("name", "ไม่ระบุชื่อ", "ชื่อเจ้าของบันทึก")` — argument 3 ตัวคือ ชื่อ flag (ไม่มีขีดนำหน้า), ค่าตั้งต้น, และคำอธิบายสำหรับข้อความวิธีใช้ ค่าที่คืนมาเป็น **`*string`** คือ *pointer ไปยัง string* ไม่ใช่ `string` ตรง ๆ — สังเกตว่าเราใช้ `*name` (มีเครื่องหมาย `*` นำหน้า) ตอนจะอ่านค่า จุดนี้ทำให้มือใหม่สับสนมาก แต่ยังไม่ต้องเข้าใจลึกตอนนี้: **จำว่า flag ทุกตัวคืน pointer มา แล้วเวลาอ่านค่าต้องเติม `*`** เพราะแพ็กเกจ `flag` มีรูปแบบการใช้งานแบบนี้ตายตัว (เราจะเข้าใจ pointer จริง ๆ ตอน 14) ถ้าไม่อยากใช้ pointer มีทางเลือกคือ `flag.StringVar(&myVar, "name", ...)` ที่ผูกค่าลงตัวแปรของเราโดยตรง

`flag.Int("n", 3, ...)` และ `flag.Bool("loud", false, ...)` — เหมือนกันแต่คืน `*int` และ `*bool` การที่เราต้องบอกชนิดล่วงหน้าแบบนี้ทำให้ `flag` แปลงข้อความ (`"5"`) กลับเป็นตัวเลข (`5`) ให้เราเอง และ**ถ้าแปลงไม่ได้ มันจะไม่ปล่อยผ่าน** — ลองส่งค่าที่ไม่ใช่ตัวเลขไปที่ `-n`

```
$ go run flags.go -n abc
invalid value "abc" for flag -n: parse error
Usage of /tmp/go-build.../exe/flags:
  -loud
    	พิมพ์ตัวพิมพ์ใหญ่
  -n int
    	จำนวนบรรทัดที่ต้องการ (default 3)
  -name string
    	ชื่อเจ้าของบันทึก (default "ไม่ระบุชื่อ")
exit status 2
```

สังเกตว่า: (1) มันบอกชื่อ flag ที่ผิดและสาเหตุ (2) มันพิมพ์ **usage อัตโนมัติ** จากคำอธิบายที่เรากรอกไว้ — นี่คือผลตอบแทนของการใส่คำอธิบายดี ๆ (3) มันตั้ง **exit code** เป็น 2 ให้เอง (exit code คืออะไร เราจะอธิบายในหัวข้อ 5.3 และได้ใช้จริงในหัวข้อ 6) — และการเรียก `./flags -h` หรือ `--help` จะพิมพ์ usage แบบเดียวกันนี้ให้ดูโดยไม่ทำอะไรต่อ

**กติกาการพิมพ์ flag ที่ต้องรู้**

- ใช้ `-flag` หรือ `--flag` ก็ได้ **เทียบเท่ากัน** ใน Go
- `-flag=ค่า` หรือ `-flag ค่า` ก็ได้ทั้งคู่ — **ยกเว้น flag ชนิด bool ที่ใช้ได้แค่ `-loud` (ได้ `true`) หรือ `-loud=false` (ได้ `false`) เท่านั้น — ห้ามเขียน `-loud false`** เพราะ `flag` จะอ่าน `-loud` ว่าเป็น `true` แล้วมอง `false` เป็น argument ธรรมดาไปเลย
- **การอ่าน flag จะหยุดทันทีเมื่อเจอชิ้นแรกที่ไม่ใช่ flag** — เป็นข้อที่มือใหม่เจ็บตัวบ่อย ลองรันคำสั่งนี้

```
$ ./flags extra1 -name สมหญิง
name = ไม่ระบุชื่อ
n    = 3
loud = false
argument ที่เหลือ (ไม่ใช่ flag) = [extra1 -name สมหญิง]
```

`-name` ที่พิมพ์ไว้**หลัง** `extra1` ถูกมองเป็น "argument ธรรมดา" ไปแล้ว ไม่ได้ถูกอ่านเป็น flag — เอกสารของ `flag` เขียนไว้ชัดว่า `Flag parsing stops just before the first non-flag argument` (อ่านว่า flag parsing สต็อป จัสต์ บีฟอร์ เดอะ เฟิร์สต์ นอน-แฟล็ก อาร์กิวเมนต์) **วิธีใช้ที่ปลอดภัยคือพิมพ์ flag ไว้ก่อน argument ที่เหลือเสมอ**

`flag.Args()` — คืน slice ของ argument ที่เหลือ "หลังหัก flag ออกแล้ว" (เทียบได้กับ `os.Args[1:]` ที่ถูกกรองแล้ว) ส่วน `flag.NArg()` ก็คือ**จำนวน**ของ argument เหล่านั้น — เท่ากับ `len(flag.Args())` เป๊ะ ๆ เลือกใช้ตัวไหนก็ได้ทั้งคู่ เหมาะกับงานที่ต้องรับทั้ง flag และ argument อิสระพร้อมกัน เช่น `notecli -file notes.txt add "ซื้อนม"`

## 5. error handling เบื้องต้น — "error คือค่า"

ถึงหัวข้อที่สำคัญที่สุดของตอนนี้ และเป็นสิ่งที่แยก "คนเขียนโค้ดได้" กับ "คนเขียนโค้ดใช้จริง" ออกจากกัน

**หลักการเดียวที่ต้องจำให้ขึ้นใจ**: ในภาษา Go **`error` คือ "ค่า" ธรรมดา ๆ ชนิดหนึ่ง** เหมือน `int` หรือ `string` — ไม่ใช่กลไกพิเศษ ไม่ใช่คำสั่ง ไม่ใช่หายนะ มันคือค่าที่ฟังก์ชันหนึ่ง ๆ ส่งกลับมาเพื่อบอกว่า "ฉันทำไม่สำเร็จ และนี่คือเหตุผล"

มองแบบนี้แล้ว ทุกอย่างจะเข้าที่: ถ้าฟังก์ชันคืน `(ผลลัพธ์, error)` ก็คือการที่ฟังก์ชันบอกเราสองอย่างพร้อมกันคือ "ได้ผลลัพธ์อะไร" กับ "มีปัญหาอะไรไหม" — ซึ่งเป็นรูปแบบเดียวกับ **comma-ok idiom** ที่เราเรียนในตอน 06 เป๊ะ ๆ

```go
v, ok := m["สมชาย"]           // ตอน 06: ของ + สถานะว่ามีจริงไหม
data, err := os.ReadFile(path) // ตอน 07: ผลลัพธ์ + สถานะว่าสำเร็จไหม
```

**`error` คือ interface** (อ่านว่า อินเทอร์เฟซ = ชุดข้อกำหนดว่า "ของแบบนี้ต้องทำอะไรได้บ้าง") ที่กำหนดไว้สั้นมาก: อะไรก็ตามที่มีเมธอด `Error() string` ถือเป็น error ได้ — เราจึงสร้าง error ของตัวเองได้ง่ายมาก และ `nil` ในตำแหน่ง error แปลว่า "ไม่มีข้อผิดพลาด" เสมอ

![error คือค่าที่ถูกส่งกลับขึ้นมาทีละชั้นด้วยคำสั่ง fmt.Errorf และเครื่องหมายเปอร์เซ็นต์ w โปรแกรมชั้นบนสุดเช็คด้วย errors.Is ว่าต้นเหตุคือ error ตัวไหน](/assets/diagrams/ep07-03-error-wrapping.svg)

### 5.1 แพตเทิร์นที่ใช้ทุกวัน: `if err != nil`

```go
data, err := os.ReadFile(path)
if err != nil {
	return fmt.Errorf("อ่านไฟล์ %q ไม่ได้: %w", path, err)
}
// มาถึงตรงนี้แปลว่า err == nil → ใช้ data ได้อย่างปลอดภัย
```

ท่านี้เรียกว่า **early return** (รีเทิร์นเร็ว) หรือ **guard clause** (การ์ด-คลอส = ประตูตรวจก่อนเข้า): จัดการกับความผิดพลาดก่อนแล้วออกจากฟังก์ชันทันที ทำให้ "เส้นทางที่สำเร็จ" ของโค้ดไม่ถูกบิดเบี้ยวด้วย `if` ซ้อนกันหลายชั้น

ถ้าเขียนแบบซ้อนกันจะอ่านยากขึ้นทันที และที่ร้ายกว่านั้นคือมีโอกาสลืมเช็คในบางกิ่ง

```go
// ❌ อ่านยาก และลืมเช็คง่าย
if err == nil {
	data := ... // ...งานยาว ๆ 20 บรรทัด
}
```

**กติกาเหล็ก**: หลังเรียกฟังก์ชันที่คืน error **ต้องเช็คก่อนใช้ค่าที่ได้** ไม่มีข้อยกเว้นในงานจริง ลองดูว่าถ้าไม่เช็คจะเกิดอะไร

```go
data, _ := os.ReadFile("missing.txt") // ทิ้ง error ด้วย _
fmt.Printf("ไม่เช็ค err → len=%d ข้อความ=%q\n", len(data), string(data))
```

ผลลัพธ์จริง

```
ไม่เช็ค err → len=0 ข้อความ=""
```

โปรแกรม **ไม่พัง** แต่ไม่ได้อ่านอะไรเลย — แล้วมันก็เดินต่อด้วยข้อมูลว่างเปล่า ให้ผลลัพธ์ผิด ๆ อย่างมั่นใจ **นี่คือบั๊กที่อันตรายกว่า panic มาก** เพราะ panic ทำให้เรารู้ตัวทันที แต่บั๊กแบบนี้หลอกเราเงียบ ๆ อาจโผล่มาเป็นรายงานที่ตัวเลขผิด หรือข้อมูลที่หายไปเป็นเดือน ๆ

### 5.2 สร้าง error ของเราเอง

มี 2 เครื่องมือหลัก

**`errors.New`** — สร้าง error จากข้อความล้วน ๆ นิยมใช้ทำ **sentinel error** (เซนติเนล เออเรอร์ = error ตัวแทนที่ใช้เป็น "เครื่องหมาย" ให้เทียบว่าคือเหตุการณ์นี้หรือไม่) ตั้งชื่อตัวแปรขึ้นต้นด้วย `Err` ตามธรรมเนียม

```go
var ErrNoText = errors.New("ไม่ได้ระบุข้อความ")
```

**`fmt.Errorf`** — สร้าง error พร้อมใส่ค่าลงไปในข้อความ (ใช้ `%s`, `%d`, `%q` เหมือน `fmt.Printf`) และถ้าใช้ **`%w`** จะถือว่าเรา "ห่อ" (wrap) error ตัวเดิมไว้ข้างใน

```go
return fmt.Errorf("บันทึกไม่ได้: %w", ErrNoText)
```

**`%w` ต่างจาก `%v` ยังไง** — ข้อความที่ตาเห็นเหมือนกันเป๊ะ แต่ความหมายข้างในต่างกันคนละเรื่อง ลองรัน

```go
var ErrNoText = errors.New("ไม่ได้ระบุข้อความ")

func withW() error { return fmt.Errorf("ห่อด้วย w: %w", ErrNoText) }
func withV() error { return fmt.Errorf("ห่อด้วย v: %v", ErrNoText) }

fmt.Printf("errors.Is(ห่อด้วย w, ErrNoText) = %t\n", errors.Is(withW(), ErrNoText))
fmt.Printf("errors.Is(ห่อด้วย v, ErrNoText) = %t\n", errors.Is(withV(), ErrNoText))
fmt.Printf("ข้อความที่ตาเห็น: w → %s | v → %s\n", withW(), withV())
```

ผลลัพธ์จริง

```
errors.Is(ห่อด้วย w, ErrNoText) = true
errors.Is(ห่อด้วย v, ErrNoText) = false
ข้อความที่ตาเห็น: w → ห่อด้วย w: ไม่ได้ระบุข้อความ | v → ห่อด้วย v: ไม่ได้ระบุข้อความ
```

ข้อความที่พิมพ์ออกมาทางเดียวกันเลย แต่ `%w` ยัง "จำ" ได้ว่าต้นเหตุคือ `ErrNoText` ส่วน `%v` ตัดขาดข้อมูลนั้นทิ้งไปเลย **กฎง่าย ๆ: ถ้าตั้งใจจะให้คนอื่นตรวจสอบสาเหตุต่อ ใช้ `%w` · ถ้าแค่ต้องการอ่านข้อความ ใช้ `%v`**

**`errors.Is`** คือเครื่องมือตรวจว่าต้นเหตุเป็น error ตัวที่เราสนใจหรือไม่ — เอกสาร Go แนะนำให้ใช้แทนการเทียบ `==` ตรง ๆ เพราะ `errors.Is` จะ **ไล่แกะทุกชั้น** ของ error ที่ถูกห่อไว้ (เรียกว่าเดินตาม "ต้นไม้ของ error") แล้วเจอตัวจริงที่ซ่อนอยู่ข้างใน

```go
if errors.Is(err, ErrNoText) { ... }   // ✅ แกะทุกชั้น
if err == ErrNoText { ... }            // ❌ เจอแค่ชั้นนอกสุด
```

มี `errors.As` ที่ทำงานคล้ายกันแต่ใช้ดึง error ที่เป็น **ชนิดเฉพาะ** ออกมา (เช่น error ที่มี field เพิ่มเติมให้อ่านอย่างละเอียด — **field** = ช่องข้อมูลใน struct ที่เราเรียนตอน 06) — เราจะใช้คล่องตอน 26–30 ที่ทำ compiler เอง ตอนนี้รู้จักชื่อไว้ก็พอ

**คู่หูที่ต้องรู้จัก: `os.ErrNotExist`** — error มาตรฐานที่แปลว่า "ไม่พบไฟล์/ไดเรกทอรี" เรื่องนี้มีชื่อคล้ายกัน 3 ชื่อที่มือใหม่สับสนได้ง่าย จำแบบนี้:

- **`fs.ErrNotExist`** — แพ็กเกจ `fs` (file system) เป็นเจ้าของค่า "ไม่พบไฟล์" ตัวจริง เอกสาร Go แนะนำให้ใช้ตัวนี้: `errors.Is(err, fs.ErrNotExist)`
- **`os.ErrNotExist`** — **ค่าเดียวกันเป๊ะ** กับ `fs.ErrNotExist` แค่แพ็กเกจ `os` มีชื่อให้เรียกด้วย (เพราะ `os` ให้บริการเรื่องไฟล์มาก่อน)
- **`os.IsNotExist(err)`** — อันนี้ไม่ใช่ error แต่เป็น**ฟังก์ชัน**ยุคเก่าก่อนจะมี `errors.Is` มันมองเห็นแค่ error ที่มาจากแพ็กเกจ `os` เท่านั้น ทำงานไม่ได้กับ error ที่เราห่อไว้เอง — เอกสารเขียนตรง ๆ ว่า "โค้ดใหม่ควรใช้ `errors.Is(err, fs.ErrNotExist)` แทน"

```go
import "io/fs"

if errors.Is(err, fs.ErrNotExist) {
	fmt.Println("ยังไม่มีไฟล์นี้ — ไม่ใช่ความผิดพลาดร้ายแรง")
}
```

### 5.3 ข้อความ error ที่ดี + "ไม่ leak internal error"

นี่คือหัวข้อที่แยกโค้ดนักเรียนกับโค้ดอาชีพ

**"ไม่ leak internal error"** (ลีค = รั่วไหล) หมายความว่า **อย่าส่งรายละเอียดภายในระบบออกไปให้ผู้ใช้ปลายทางเห็น** เช่น ที่อยู่ไฟล์เต็มในเครื่อง, ชื่อผู้ใช้ระบบ, ชื่อฐานข้อมูล, query (คำสั่งฐานข้อมูล), ที่อยู่เครือข่ายภายใน หรือ credential (ข้อมูลลับสำหรับเข้าใช้งาน) — เพราะข้อมูลเหล่านี้เอาไปใช้โจมตีระบบได้ และทำให้ผู้ใช้สับสนโดยไม่ได้อะไรกลับไป

แต่ในเวลาเดียวกัน **เราก็ไม่อยากทิ้งข้อมูลนั้นไปเลย** เพราะเวลาแก้บั๊กตอนตี 2 ข้อความ "เกิดข้อผิดพลาด" ล้วน ๆ ไม่ช่วยอะไร ทางออกที่ถูกต้องคือ **แยกผู้รับ**:

| ผู้รับ | ควรเห็นอะไร | ไปทางไหน |
|---|---|---|
| ผู้ใช้ (คน) | ข้อความที่บอกว่า "ทำอะไรอยู่ + ต้องแก้ยังไง" | stdout/stderr ของโปรแกรม |
| dev (เรา) | ข้อความเต็มพร้อมรายละเอียดต้นเหตุ | ไฟล์ log (ล็อก = บันทึกเหตุการณ์ที่โปรแกรมเขียนทิ้งไว้ให้ย้อนดูภายหลัง) |
| โปรแกรมที่เรียกเราต่อ | **exit code** (เลขบอกผลลัพธ์ของการรัน) | ค่าที่โปรแกรมคืนให้เชลล์ |

**เชลล์** (shell) = โปรแกรมที่รับคำสั่งที่เราพิมพ์ใน terminal แล้วสั่งให้ระบบทำงานต่อ (เช่น `bash`, `zsh`) — มันเป็นตัวรับ exit code ที่โปรแกรมของเราคืนกลับไป แล้วส่งต่อให้สคริปต์หรือโปรแกรมอื่นตัดสินใจต่อ

ในตอนนี้เรายังไม่มีระบบ log จริงจังหรอก ขอให้จำได้ว่า **ข้อความ error ที่ดีต้องบอก 3 อย่าง**:

1. **เรากำลังทำอะไรอยู่** — "อ่านไฟล์ config" ดีกว่า "error"
2. **กับอะไร** — ใส่ชื่อไฟล์/ค่าที่เกี่ยวข้องไปด้วย (ใช้ `%q` เพื่อให้เห็นชัดว่าชื่อไฟล์มีช่องว่างหรือตัวอักษรแปลก ๆ ซ่อนอยู่ไหม)
3. **ต้นเหตุคืออะไร** — ห่อ error ตัวจริงมา ไม่ใช่แทนที่ด้วยข้อความกว้าง ๆ

ตัวอย่างการเขียน error สองแบบ

```go
// ❌ ผู้ใช้ไม่รู้อะไรเลย dev ก็ไม่รู้เหมือนกัน
return errors.New("error")

// ✅ บอกว่าทำอะไร กับไฟล์อะไร ต้นเหตุคืออะไร (ต้นเหตุยังตรวจสอบได้ด้วย errors.Is)
return fmt.Errorf("อ่านไฟล์บันทึก %q ไม่ได้: %w", path, err)
```

และโค้ดตัวอย่างรวม ๆ ของเรื่อง error ในตอนนี้ — `errors.go`

```go
package main

import (
	"errors"
	"fmt"
	"os"
)

// error ที่เราสร้างเอง ใช้เทียบด้วย errors.Is ได้
var ErrAgeTooLow = errors.New("อายุต่ำเกินไป")

func readAge(path string) (int, error) {
	// ตัวอย่างย่อ: ตัดการอ่านค่าจริงจากไฟล์ออก เพื่อโฟกัสที่ "การห่อ error" อย่างเดียว
	age := 15
	if age < 18 {
		// %w = ห่อ (wrap) error เดิมไว้ข้างใน เพื่อให้ errors.Is ยังตรวจได้
		return 0, fmt.Errorf("อ่านอายุจาก %q ไม่ได้: %w", path, ErrAgeTooLow)
	}
	return age, nil
}

func main() {
	_, err := readAge("profile.txt")
	if err != nil {
		// ตรวจว่า error ข้างในคือ ErrAgeTooLow หรือไม่
		if errors.Is(err, ErrAgeTooLow) {
			fmt.Println("ผู้ใช้ยังอายุไม่ถึง:", err)
		}
	}

	// ตัวอย่าง error จาก os
	_, err = os.ReadFile("ไม่มีไฟล์นี้.txt")
	if err != nil {
		fmt.Println("ข้อความดิบจาก os:", err)
		fmt.Println("เป็น error ประเภท 'ไม่พบไฟล์' ไหม:", errors.Is(err, os.ErrNotExist))
	}
}
```

ผลลัพธ์จริง

```
ผู้ใช้ยังอายุไม่ถึง: อ่านอายุจาก "profile.txt" ไม่ได้: อายุต่ำเกินไป
ข้อความดิบจาก os: open ไม่มีไฟล์นี้.txt: no such file or directory
เป็น error ประเภท 'ไม่พบไฟล์' ไหม: true
```

สังเกตบรรทัดที่สอง: ข้อความจาก `os` ประกอบด้วย 3 ส่วนเสมอ — **การกระทำ** (`open`), **กับอะไร** (`ไม่มีไฟล์นี้.txt`), และ **ต้นเหตุ** (`no such file or directory`) นี่คือตัวอย่างของ "error ที่ดี" จากภาษามาตรฐานให้เราลอกแบบ — และจะเป็นประโยชน์มากตรงที่เราสามารถ **กลืน** ข้อความอังกฤษนี้ไว้ข้างใน แล้วส่งข้อความไทยที่อ่านรู้เรื่องให้ผู้ใช้แทนได้ โดยที่โปรแกรมยัง "รู้" ต้นเหตุจริง ๆ ผ่าน `errors.Is`

**สิ่งที่ห้ามทำ (และทำไม)**

- **`panic` ในโค้ดธุรกิจ** — `panic` เหมาะกับกรณี "โปรแกรมเป็นไปไม่ได้แล้วจริง ๆ" เท่านั้น ถ้าใช้กับสิ่งที่คาดเดาได้ (เช่นผู้ใช้พิมพ์ไฟล์ชื่อผิด) เรากำลังปล้นโอกาสจัดการของโปรแกรมเอง — โปรแกรมที่พังเพราะผู้ใช้พิมพ์ผิดคือโปรแกรมที่ใช้ทำงานไม่ได้
- **`log.Fatal` กลางทาง** (`log` เป็นแพ็กเกจมาตรฐานสำหรับพิมพ์ข้อความ log) — มันเรียก `os.Exit` ทำให้ `defer` ทุกตัวที่ค้างอยู่**ไม่ได้ทำงาน** (รวมถึงการปิดไฟล์ของเรา) ตั้งใจไว้สำหรับ `main` ตอนที่ไปต่อไม่ได้จริง ๆ เท่านั้น
- **เทียบข้อความ error ด้วยสตริง** — `if err.Error() == "ไม่ได้ระบุข้อความ"` เปราะสุด ๆ เพราะข้อความเปลี่ยนได้ตลอดเวลาที่เราแก้โค้ด ใช้ sentinel + `errors.Is` แทน
- **ทิ้ง error ด้วย `_`** — ถ้าตั้งใจทิ้งจริง ๆ ให้เขียนคอมเมนต์กำกับว่าทำไม ไม่งั้นคนอ่าน (รวมถึงตัวเราในอีก 3 เดือน) จะคิดว่าลืม

## 6. ประกอบร่างทั้งหมด — mini-project "notecli" โปรแกรมจดบันทึกลงไฟล์

ตอนนี้เรามีครบทุกชิ้น: อ่าน/เขียนไฟล์, เปิดแบบต่อท้าย, CLI ด้วย `flag`, และ error handling แบบห่อด้วย `%w` — มาประกอบเป็นโปรแกรมที่**ใช้งานได้จริง**กัน

โค้ดชิ้นนี้ยาวที่สุดในตอน และมีของใหม่ 2 อย่างที่ยังไม่เคยอธิบาย อ่านตรงนี้ก่อนจะได้ไม่สะดุด:

- **`switch` / `case` / `default`** = คำสั่ง**เลือกทำอย่างเดียวจากหลายกรณี** ใช้แทน `if / else if / else` ที่ยาวเป็นบันไดได้: `switch` คือค่าที่จะเอาไปเทียบ · `case` คือแต่ละกรณี · `default` คือ "ไม่ตรงกับกรณีไหนเลย" (เทียบได้กับ `else` ตัวสุดท้าย) — โปรแกรมจะเข้าแค่ `case` เดียวแล้วออกจาก `switch` ทันที ไม่ต้องเขียน `break` ปิดท้าย (Go ไม่มีพฤติกรรม "ไหลไปกรณีถัดไป" แบบบางภาษา)
- **`fmt.Fprintln`** = **พิมพ์แล้วขึ้นบรรทัดใหม่ให้เสมอ** (สังเกต `ln` ท้ายชื่อ) เหมือน `fmt.Println` แต่ส่งข้อความไปยัง **ตัวเขียนที่เราระบุ** แทนที่จะออกจอ — ที่นี่เราระบุ `os.Stderr` (ถ้าใช้ `fmt.Fprint` จะไม่ขึ้นบรรทัดใหม่ให้)

สร้างไฟล์ `notecli.go` ในโฟลเดอร์ `gopher-course` แล้วพิมพ์ตาม:

```go
package main

import (
	"bufio"
	"errors"
	"flag"
	"fmt"
	"os"
	"strings"
)

// error ที่เราสร้างเอง เพื่อบอกผู้ใช้ว่าพิมพ์คำสั่งผิด
var ErrNoText = errors.New("ไม่ได้ระบุข้อความ")

func addNote(path, text string) error {
	text = strings.TrimSpace(text)
	if text == "" {
		return fmt.Errorf("บันทึกไม่ได้: %w", ErrNoText)
	}

	f, err := os.OpenFile(path, os.O_APPEND|os.O_CREATE|os.O_WRONLY, 0644)
	if err != nil {
		return fmt.Errorf("เปิดไฟล์บันทึก %q ไม่ได้: %w", path, err)
	}
	defer func() {
		if cerr := f.Close(); cerr != nil {
			fmt.Fprintln(os.Stderr, "ปิดไฟล์ไม่สำเร็จ:", cerr)
		}
	}()

	if _, err := fmt.Fprintln(f, text); err != nil {
		return fmt.Errorf("เขียนบันทึกไม่ได้: %w", err)
	}
	fmt.Println("เพิ่มบันทึกแล้ว:", text)
	return nil
}

func listNotes(path string) error {
	f, err := os.Open(path)
	if err != nil {
		if errors.Is(err, os.ErrNotExist) {
			fmt.Println("ยังไม่มีบันทึก (ไฟล์", path, "ยังไม่ถูกสร้าง)")
			return nil
		}
		return fmt.Errorf("เปิดไฟล์บันทึก %q ไม่ได้: %w", path, err)
	}
	// เปิดอ่านอย่างเดียว (os.Open) จึงไม่มีข้อมูลค้างรอเขียนอยู่ในเครื่อง — พลาด error ตอนปิดได้
	// แต่ฝั่งเขียน (addNote) ต้องเช็ค error ของ Close เสมอ
	defer f.Close()

	sc := bufio.NewScanner(f)
	n := 0
	for sc.Scan() {
		line := strings.TrimSpace(sc.Text())
		if line == "" {
			continue
		}
		n++
		fmt.Printf("%d) %s\n", n, line)
	}
	if err := sc.Err(); err != nil {
		return fmt.Errorf("อ่านบันทึกไม่ได้: %w", err)
	}
	fmt.Println("รวม", n, "รายการ")
	return nil
}

func main() {
	cmd := flag.String("cmd", "list", "คำสั่ง: add หรือ list")
	text := flag.String("text", "", "ข้อความที่ต้องการบันทึก")
	file := flag.String("file", "notes.txt", "ไฟล์ที่ใช้เก็บบันทึก")
	flag.Parse()

	var err error
	// switch = เลือกทำอย่างเดียวจากหลายกรณี (มีคำอธิบายใต้โค้ด)
	switch *cmd {
	case "add":
		err = addNote(*file, *text)
	case "list":
		err = listNotes(*file)
	default:
		err = fmt.Errorf("ไม่รู้จักคำสั่ง %q (ใช้ add หรือ list)", *cmd)
	}
	if err != nil {
		fmt.Fprintln(os.Stderr, "ผิดพลาด:", err)
		os.Exit(1)
	}
}
```

ก่อนรัน ให้ build ด้วย `go build -o notecli notecli.go` แล้วลองใช้งานจริงทั้งวงจร (นี่คือ session จริงที่รันบนเครื่อง — เรียงตามลำดับ)

**จุดที่อยากให้สังเกตในโค้ดนี้**

- **`os.OpenFile` คือตัวที่คุมได้ละเอียดที่สุด** — เราไม่ได้ใช้ `os.Create` เพราะมัน **ล้างไฟล์ทิ้ง** แต่เราต้องการ**ต่อท้าย** จึงต้องส่ง flag รวมกัน 3 ตัวด้วยตัวดำเนินการ `|` (ไพป์ = "หรือ" ระดับบิต ซึ่งเป็นการรวมธงเข้าด้วยกัน — เรื่องบิตเราจะเห็นเต็ม ๆ ตอน 08–09):
  - `os.O_WRONLY` = เปิดมาเพื่อเขียน
  - `os.O_CREATE` = ถ้าไฟล์ยังไม่มี ให้สร้างใหม่
  - `os.O_APPEND` = เขียนต่อท้ายเสมอ ไม่ทับของเดิม
  เอกสาร `os` อธิบายว่า `O_APPEND` แปลว่า "append data to the file when writing" และเมื่อรวมกับ `O_CREATE` ระบบจะสร้างไฟล์ด้วย permission ที่เราส่ง (0644) ให้อัตโนมัติ
- **การตรวจ input ก่อนแตะไฟล์** — `addNote` เช็ค `text` ว่างก่อนเปิดไฟล์ เพราะไม่ควรสร้างไฟล์ (หรือแตะไฟล์) ถ้างานจะล้มเหลวอยู่แล้ว นี่คือการเรียงลำดับงานที่ลดผลข้างเคียง (side effect) ให้เหลือน้อยที่สุด
- **ห่อ error ทุกชั้นจนถึง `main`** — `main` ไม่ต้องรู้รายละเอียดเลย มันแค่ "ถ้ามี error ให้พิมพ์และออกด้วยรหัส 1" ส่วนข้อความที่ผู้ใช้เห็นยังครบทุกชั้นเพราะเราห่อด้วย `%w` ไว้
- **`continue` ในวงวนแสดงรายการ** — มาจากตอน 04: ข้ามบรรทัดว่างไป แล้วไปบรรทัดถัดไปเลย ทำให้ไฟล์ที่มีบรรทัดว่างคั่น (เช่นไฟล์ที่ถูกแก้ด้วยมือ) ยังแสดงผลสวย
- **`fmt.Fprintln(os.Stderr, ...)`** — `fmt.Fprintln` **= พิมพ์แล้วขึ้นบรรทัดใหม่ให้เสมอ** เหมือน `fmt.Println` แต่ส่งข้อความไปที่ **ตัวเขียนที่เราระบุ** แทนที่จะออกจอ — ที่นี่ส่งไปที่ **stderr** (สแตนดาร์ด เออเรอร์ = ช่องทางข้อผิดพลาด) ไม่ใช่ stdout (สแตนดาร์ด เอาต์พุต = ช่องทางผลลัพธ์ปกติ) นี่คือธรรมเนียมสำคัญของ CLI เพราะทำให้ผู้ใช้**แยกข้อมูลจริงออกจากข้อความ error ได้** เช่น `./notecli -cmd list 2> error.log` จะเก็บแค่ error ไว้ในไฟล์แยก และ `./notecli -cmd list > notes-backup.txt` ได้เฉพาะรายการบันทึกที่สะอาด ไม่มีข้อความ error ปน
- **`os.Exit(1)` = exit code 1** (เอ็กซิตโค้ด = ตัวเลขที่โปรแกรมคืนให้เชลล์ตอนจบ) เลข `0` แปลว่าสำเร็จ เลขอื่นแปลว่ามีปัญหา — เรื่องนี้สำคัญมากเมื่อโปรแกรมของเราถูกเรียกจากสคริปต์หรือระบบอัตโนมัติอย่าง **cron** (ตัวตั้งเวลาของระบบ ใช้สั่งให้โปรแกรมรันเองซ้ำ ๆ ตามเวลา) หรือ **CI** (ระบบที่รันคำสั่งทดสอบอัตโนมัติทุกครั้งที่เราส่งโค้ดขึ้นเซิร์ฟเวอร์) เพราะระบบเหล่านี้ดูแค่ตัวเลขนี้ตัดสินว่าสำเร็จหรือล้มเหลว **ใน Go ไม่มีคำสั่ง `exit` เฉย ๆ (แบบในสคริปต์เชลล์) — ต้องเรียก `os.Exit(1)`** และจำไว้เสมอว่า `os.Exit` จะข้าม `defer` ทั้งหมด (ในโค้ดนี้ปลอดภัย เพราะเราเรียกที่ `main` หลังงานปิดไฟล์เสร็จแล้ว)

## 7. กับดักที่พบบ่อย (รวมของตอนนี้)

1. **ใช้ค่าที่อ่านได้โดยไม่เช็ค `err`** → ได้ข้อมูลว่างเปล่าโดยไม่รู้ตัว (ผลลัพธ์ `len=0 ข้อความ=""` ข้างบน) — **แก้:** เช็ค `if err != nil` เป็นบรรทัดแรกทุกครั้ง
2. **`os.Args[1]` โดยไม่เช็ค `len`** → `panic: index out of range` — **แก้:** เช็คจำนวนก่อนเสมอ แล้วพิมพ์ข้อความวิธีใช้
3. **ใช้ `os.Create` ทั้งที่ต้องการต่อท้าย** → ข้อมูลเก่าถูกล้างหายทั้งหมด — **แก้:** ใช้ `os.OpenFile` กับ `O_APPEND|O_CREATE|O_WRONLY`
4. **ใช้ `os.WriteFile` กับไฟล์ที่มีข้อมูลอยู่** → เขียนทับทั้งไฟล์ (94 ไบต์ → 13 ไบต์) — **แก้:** ตั้งใจให้ชัดว่าต้องการทับหรือต่อท้าย และสำรองไฟล์ก่อนถ้าไม่แน่ใจ
5. **ใช้ `bufio.Writer` แล้วลืม `Flush`** → โปรแกรมบอก "สำเร็จ" แต่ไฟล์ว่าง — **แก้:** `Flush()` ก่อนออกเสมอและเช็ค error ของมัน (จำไว้ว่า `bufio.Writer` ไม่มี `Close` ให้เราเรียก)
6. **ลืมปิดไฟล์** → file descriptor รั่ว ถ้าโปรแกรมรันนาน (เช่นเซิร์ฟเวอร์) จะเปิดไฟล์ใหม่ไม่ได้ในที่สุด — **แก้:** `defer` ปิดไฟล์ทันทีหลังเปิดสำเร็จ
7. **ทิ้ง error ของ `Close`** → ข้อมูลที่ยังค้างในเส้นทาง I/O อาจหายเงียบ ๆ — **แก้:** `defer func(){ if cerr := f.Close(); cerr != nil { ... } }()`
8. **พิมพ์ `-name` ไว้หลัง argument อื่น** → flag นั้นไม่ถูกอ่าน — **แก้:** วาง flag ไว้ต้นบรรทัด
9. **ลืมเครื่องหมายคำพูดกับข้อความที่มีช่องว่าง** → ข้อความถูกตัดเป็น 2 arguments
10. **เทียบ error ด้วยข้อความ** (`err.Error() == "..."`) → เปราะ พังเมื่อข้อความเปลี่ยน — **แก้:** ใช้ `errors.Is` กับ sentinel error
11. **ใช้ `%v` ทั้งที่ต้องการให้ตรวจสอบต้นเหตุต่อ** → `errors.Is` จะคืน `false` — **แก้:** ใช้ `%w` เมื่อตั้งใจจะส่งต่อข้อมูลต้นเหตุ
12. **`panic` / `log.Fatal` แทนการคืน error** → โปรแกรมตายโดยไม่มีใครรับมือได้ และ `defer` ถูกข้าม — **แก้:** คืน error ขึ้นไป ให้ `main` เป็นคนตัดสินใจสุดท้าย

2. **`-add`**: ตรวจว่า
   - จำนวนเงินเป็นตัวเลขบวกเท่านั้น (ใช้ `strconv.ParseFloat` จากตอน 04)
   - หมวดต้องอยู่ในรายการที่อนุญาต เช่น `food, transport, home, other` (ใช้ map เป็น "ชุดที่อนุญาต" จากตอน 06 — `v, ok := allowed[cat]` ตามด้วยเช็ค `ok`)
   - หมายเหตุว่างได้ แต่หมวดห้ามว่าง
   ถ้าข้อมูลผิด **ต้องไม่แตะไฟล์เลย** — บอกเหตุผลว่า "ผิดตรงไหน" แล้วจบด้วย exit code 1
3. **`-list`**: อ่านทีละบรรทัดด้วย `bufio.Scanner` แสดงเลขลำดับ + ข้อมูลแต่ละรายการ + ยอดรวม ถ้าไฟล์ยังไม่มี ให้บอกสุภาพว่า "ยังไม่มีรายจ่าย" (ไม่ใช่ error)
4. **`-sum`**: คำนวณยอดรวมและแสดงผลเป็นทศนิยม 2 ตำแหน่ง (`%.2f`) พร้อมจำนวนรายการ
5. **การอ่านไฟล์ที่ผู้ใช้อาจแก้ด้วยมือ**: บรรทัดว่างข้ามไป บรรทัดที่จำนวนเงินไม่ใช่ตัวเลข **ห้ามทำให้โปรแกรมพัง** — บอกว่า "บรรทัดที่ N อ่านไม่ได้: <เหตุผล>" แล้วข้ามไปอ่านบรรทัดถัดไป (นับจำนวนบรรทัดที่พังไว้แสดงท้ายด้วยก็ดี)
6. **error handling ครบ**: ห่อ error ด้วย `%w` ทุกจุด · ใช้ `errors.Is` แยกกรณี "ไม่พบไฟล์" ออกจาก "เปิดไฟล์ไม่ได้ด้วยเหตุอื่น (เช่นสิทธิ์ไม่พอ)" · เช็ค error ของ `Close` · ปิดไฟล์ด้วย `defer` เสมอ
7. **แยกฟังก์ชัน**: `parseAmount`, `loadExpenses`, `addExpense`, `sumExpenses` — `main` ทำแค่แปลง flag แล้วตัดสินใจว่ามี error ให้พิมพ์และออกหรือไม่ (ย้ำหลักการ decomposition จากตอน 05: `main` ไม่ควรยาวเกิน 30 บรรทัด)

**เกณฑ์ผ่าน**

- `./expense -add "45.5 food ข้าวกลางวัน"` แล้ว `./expense -list` เห็นรายการทันที (เขียนต่อท้าย ไม่ทับของเดิม)
- `./expense -add "abc food ทดสอบ"` ต้องบอกว่าจำนวนเงินไม่ใช่ตัวเลข และ **ไฟล์ต้องไม่ถูกแตะ** (เช็กด้วย `cat` ก่อน-หลัง)
- `./expense -add "45 พาไปเที่ยว ไหนก็ไม่รู้"` ต้องบอกว่าหมวดไม่ถูกต้อง พร้อมบอกหมวดที่ใช้ได้
- แก้ไฟล์ด้วยมือให้มีบรรทัดที่พัง แล้ว `-list` / `-sum` ต้องไม่พัง และยังรวมยอดของบรรทัดที่ดีอยู่ได้
- ลบไฟล์ทิ้งแล้ว `-list` ต้องบอกสุภาพ ไม่ออก exit code 1

**โจทย์ท้าทายเพิ่ม (ถ้าอยากไปต่อ)**: เพิ่ม `-month 2026-09` กรองเฉพาะเดือนนั้น (ใช้ `strings.HasPrefix` ก็ได้) — หรือเพิ่มการตรวจว่าวันที่ที่บันทึกอยู่ในรูปแบบ `YYYY-MM-DD` จริงด้วย `time.Parse` (ลองไปอ่านเอกสารแพ็กเกจ `time` เอง นี่คือทักษะ "อ่านเอกสารเอง" ที่ dev ใช้ทุกวัน)

## สรุปตอนที่ 07

**ข้อมูลอยู่รอดได้เพราะไฟล์**

- ตัวแปร / slice / map / struct ที่เราเรียนมาตอน 03–06 อยู่ชั่วคราวใน RAM — หมดอายุพร้อมโปรแกรม
- ไฟล์บนดิสก์คือทางเดียวที่ข้อมูลอยู่ข้ามการปิดโปรแกรม
- ทุกการแตะไฟล์ต้องผ่าน kernel ด้วย **syscall**

**อ่าน/เขียนแบบง่าย**

- `os.ReadFile(path)` คืน `([]byte, error)`
- `os.WriteFile(path, data, perm)` **เขียนทับทั้งไฟล์** ไม่ใช่ต่อท้าย
- ทั้งคู่ใช้ **permission** แค่ตอนสร้างไฟล์ใหม่ (ไฟล์ที่มีอยู่แล้ว permission เดิมไม่ถูกแก้)
- `[]byte` ↔ `string` แปลงด้วย `[]byte(s)` และ `string(b)`
- **ตัวอักษรไทย 1 ตัว = 3 ไบต์** ใน UTF-8 — นั่นคือเหตุผลที่ข้อความสั้น ๆ กลายเป็น 41 ไบต์

**เปิดไฟล์เอง**

- `os.Create` = เปิดเพื่อเขียนและ **ล้างของเดิมทิ้ง** (ข้างในคือ `os.OpenFile` ด้วย `O_RDWR|O_CREATE|O_TRUNC` — `O_RDWR` = เปิดอ่าน/เขียนได้, `O_CREATE` = สร้างให้ถ้ายังไม่มี, `O_TRUNC` = ล้างของเดิม)
- `os.Open` = เปิดเพื่อ**อ่านอย่างเดียว ไม่แตะเนื้อหา**
- `os.OpenFile` + `O_APPEND|O_CREATE|O_WRONLY` = เขียนต่อท้าย
- `bufio.Writer` กักข้อมูลใน buffer แล้วต้อง **`Flush`** เอง — มัน **ไม่มี `Close`**
- `bufio.Scanner` อ่านทีละบรรทัด และ **ต้องเช็ค `sc.Err()`** หลังวนจบ เพราะ "จบไฟล์" กับ "พังกลางทาง" หน้าตาเหมือนกันในวงวน

**`defer`**

- ผัดงานไว้ทำตอนฟังก์ชันจบ — ทำงานแบบ **LIFO** และทำงานแม้เกิด panic
- ใช้ปิดไฟล์ทันทีหลังเปิดสำเร็จ และ**เช็ค error ของ `Close`** ด้วย
- **อย่าให้ `os.Exit` / `log.Fatal` ตัดหน้า `defer` ที่สำคัญ**

**CLI**

- `os.Args` เป็น slice ของ string — ช่อง 0 คือชื่อโปรแกรมเสมอ
- **ต้องเช็ค `len` ก่อนเข้าถึง index ใด ๆ** ไม่งั้น panic
- ช่องว่างคือตัวแบ่ง argument (ข้อความที่มีช่องว่างต้องใส่เครื่องหมายคำพูด)
- แพ็กเกจ `flag` ดีกว่า: ประกาศ `flag.String/Int/Bool` แล้วเรียก `flag.Parse()`
- ค่าที่ได้เป็น **pointer** — อ่านด้วย `*`
- รับได้ทั้ง `-flag` และ `--flag`
- bool ใช้ได้แค่ `-flag` หรือ `-flag=false` — **ห้าม `-flag false`**
- **การอ่านหยุดที่ argument ที่ไม่ใช่ flag ตัวแรก**
- `flag.Args()` ได้ argument ที่เหลือ · `-h` พิมพ์ usage ให้เอง

**error คือค่า**

- `error` เป็น interface ที่ต้องการแค่ `Error() string` — `nil` = สำเร็จ (ไม่มีข้อผิดพลาด)
- แพตเทิร์น **`if err != nil` แล้ว return ออกทันที** (early return)
- **ห้ามใช้ค่าที่อ่านได้ก่อนเช็ค err** — `len=0` ที่ไม่มีใครรู้ตัวคือบั๊กที่อันตรายกว่า panic
- สร้าง error เองด้วย `errors.New` (sentinel) และ `fmt.Errorf` ที่ใช้ **`%w` เพื่อห่อ (wrap) ต้นเหตุ**
- ตรวจต้นเหตุด้วย **`errors.Is`** (ไล่แกะทุกชั้น) ไม่ใช่ `==` หรือเทียบข้อความ
- "ไม่พบไฟล์" ใช้ `errors.Is(err, fs.ErrNotExist)` ซึ่งเป็นค่าเดียวกับ `os.ErrNotExist` และเป็นวิธีที่เอกสาร Go แนะนำแทน `os.IsNotExist` แบบเก่า

**ข้อความ error ที่ดี**

- บอก 3 อย่าง: ทำอะไรอยู่ · กับอะไร · ต้นเหตุคืออะไร
- แยกผู้รับให้ชัด: ผู้ใช้เห็นข้อความที่แก้ไขได้ · dev เห็นรายละเอียดทั้งหมด · โปรแกรมอื่นเห็น **exit code** (0 = สำเร็จ, อื่น ๆ = มีปัญหา)

**กับดักที่ต้องระวังตลอดชีวิต dev**

- ใช้ค่าที่อ่านได้โดยไม่เช็ค err
- ใช้ `os.Create` ทั้งที่ต้องการต่อท้าย (ข้อมูลเก่าถูกล้างหมด)
- ลืม `Flush` · ลืม `Close` · ทิ้ง error ของ `Close`
- เทียบ error ด้วยข้อความ
- ใช้ `panic` / `log.Fatal` แทนการคืน error

ตอนนี้โปรแกรม Go ของคุณ "อยู่รอดในโลกจริง" ได้แล้ว — เก็บข้อมูลถาวร รับคำสั่งจากผู้ใช้ และไม่พังเมื่อเจอสิ่งที่ไม่คาดคิด นี่คือสามสิ่งที่ทำให้โปรแกรมจากแบบฝึกหัดกลายเป็นเครื่องมือที่ใช้ทำงานได้

แต่ยังมีคำถามที่เรา**เลี่ยงมาตลอดทั้ง 7 ตอน** และถึงเวลาต้องเผชิญหน้าแล้ว: ข้อมูลที่เก็บในไฟล์ — ทั้งเลข 41, ทั้งตัวอักษรไทย, ทั้งเลขทศนิยมอย่าง 45.5 — ระบบเก็บมันลงไปเป็น "อะไร" กันแน่? ทำไมข้อความไทย 1 ตัวถึงกิน 3 ไบต์ แต่ตัวอักษรอังกฤษกิน 1 ไบต์? ทำไม `0.1 + 0.2` ถึงไม่เท่ากับ `0.3` ในหลายภาษาโปรแกรม? และไบต์กับบิตต่างกันยังไง?

คำตอบทั้งหมดอยู่ในตอนหน้า และมันคือพื้นฐานที่ทำให้เราเข้าใจทุกอย่างตั้งแต่หน่วยความจำจนถึงไฟล์ — **ตอนที่ 08: เลขฐานสอง ฐานสิบหก และการแทนข้อมูล**

ระหว่างรอ ลองทำ mini-project "บันทึกรายจ่าย" ให้จบ แล้วลอง**จงใจทำมันพัง** หลาย ๆ แบบ: ลบไฟล์กลางคัน, แก้ไฟล์ให้เละด้วยมือ, ใส่จำนวนเงินเป็นตัวอักษร, ลบโฟลเดอร์ทิ้งแล้วรันใหม่ — แล้วสังเกตว่าโปรแกรมของเราตอบสนองยังไง ทุกครั้งที่มันตอบได้อย่างสุภาพโดยไม่ต้องแก้โค้ด นั่นคือสัญญาณว่าคุณกำลังเขียนโปรแกรมแบบ dev มืออาชีพ ไม่ใช่แบบฝึกหัด
