# Complexity P/NP — ทำไมบางปัญหา "ยาก" (ตอนที่ 25)

ยินดีต้อนรับกลับมา ตอนนี้คือ**ตอนสุดท้ายของระยะที่ 5** (ทฤษฎีการคำนวณ) — ระยะที่เราถอยออกมาจากการเขียนโปรแกรมแล้วถามคำถามเชิง "ขอบเขต" ของคอมพิวเตอร์

ก่อนจบระยะ เรามาทวนบันไดที่เราเดินขึ้นมาแล้วสามขั้น:

- **ตอนที่ 22** — **finite automaton** (เครื่องสถานะจำกัด): เครื่องที่จำอะไรไม่ได้เลย จึงรับภาษาแบบ "วงเล็บสมดุล" หรือ `aⁿbⁿ` ไม่ได้
- **ตอนที่ 23** — **pushdown automaton** (เครื่องมีกอง/stack): แปะกองเข้าไปหนึ่งกอง ก็เริ่มนับได้ รับ `aⁿbⁿ` ได้แล้ว
- **ตอนที่ 24** — **Turing machine**: เครื่องที่มีเทปไม่จำกัด = นิยามที่แม่นยำของคำว่า "คอมพิวเตอร์" และเราพิสูจน์ว่า **halting problem** (โปรแกรมนี้จะหยุดไหม) เป็นปัญหาที่**ตัดสินไม่ได้** (undecidable)

ตอนที่ 24 ตอบคำถามว่า "อะไรที่คอมพิวเตอร์**ทำไม่ได้**เลย" คืนนี้เรามาถามคำถามถัดไปที่แคบลงมาหน่อย แต่ใกล้ตัวเรากว่ามาก:

> ในบรรดาปัญหาที่คอมพิวเตอร์**ทำได้** (ตัดสินได้) — ทำไมบางอันมันถึง "**ยาก**" จนทำได้จริง ๆ ไม่ได้?

สองคำถามนี้อยู่คนละแกนกัน อย่าเพิ่งสับสน: **ตอนที่ 24** = ขอบเขตของ "ทำได้ vs ทำไม่ได้" (ใช้เวลาเท่าไหร่ก็ตอบได้ ไม่สนใจ) ส่วน**ตอนที่ 25** = ขอบเขตของ "ทำได้**เร็ว** vs ทำได้**ช้า**" (ตอบได้ แต่รอจนชาตินี้ไม่จบ)

> **ที่อยู่ของโค้ดในตอนนี้:** โปรแกรมทุกตัวอยู่ที่ `course/code/ep25/` แยกโฟลเดอร์ตามเลขโปรแกรม (01–05) พร้อมผลรันจริงในโฟลเดอร์ `out/` — เปิดดูตามไปด้วยได้ตลอด

## 1. คำว่า "ยาก" ในทางทฤษฎีหมายถึงอะไร?

เวลาเราเขียนโปรแกรมแล้วรู้สึกว่า "โปรแกรมนี้ช้า" เรามักพูดเป็น**วินาที** ("รัน 5 วิเลย") แต่วินาทีเป็นมาตรวัดที่**ไม่น่าเชื่อถือ** เพราะมันขึ้นกับเครื่อง: โปรแกรมเดียวกันบนแล็ปท็อปใหม่รัน 0.1 วิ แต่บน Raspberry Pi ของเราอาจรัน 3 วิ

นักทฤษฎีจึงไม่วัดวินาที แต่วัด**จำนวนขั้นตอน** (steps) — คือ "งานย่อยพื้นฐานที่ต้องทำกี่รอบ" (ในโปรแกรมของเราตอนนี้ 1 ขั้นตอน = 1 รอบของงานย่อยชื่อ `spin` ซึ่งคือการคูณ+บวกจำนวนเต็มหนึ่งรอบ) ซึ่งเครื่องไหนก็เท่ากัน แล้วค่อยเอาไปคูณ "ราคาต่อหนึ่งขั้นตอน" (เครื่องแรงก็ราคาถูกกว่า วิ่งเร็วขึ้น) เพื่อให้ได้เวลาจริง:

```
เวลาจริง  =  จำนวนขั้นตอน  ×  ราคาต่อขั้นตอน
```

คำถามสำคัญจึงกลายเป็น: **พอขนาดของโจทย์ (input) ใหญ่ขึ้น จำนวนขั้นตอนมัน "โต" แบบไหน?**

เราเรียกขนาด input ว่า `n` (เช่น ถ้าโจทย์คือ "หาเลขในลิสต์" แล้ว `n` = จำนวนตัวเลขในลิสต์) แล้วอธิบายการโตด้วยสัญลักษณ์ **big-O** (อ่านว่า "บิ๊กโอ") — มันคือการถามว่า "ถ้า n โตขึ้น ขั้นตอนจะโต**ประมาณ**เท่าฟังก์ชัน (สูตรคณิต) ไหน"

หนึ่งในสูตรที่โผล่บ่อยคือ `log n` (อ่าน "ล็อกเอ็น") = "ต้องหาร n ครึ่งไปกี่ครั้งถึงจะเหลือ 1" — เป็นการโตที่**ช้ามาก ๆ** (ข้อมูลล้านตัว log n ก็แค่ ~20 ขั้นตอน) รู้ไว้แค่นี้ก็พอแล้ว เดี๋ยวเราจะเห็นมันในตาราง

ลองดูโปรแกรมแรก ซึ่ง**นับจำนวนขั้นตอนจริง**ให้เราเห็นตาตัวเอง ไม่ใช่ทฤษฎีบนกระดาษ:

```go
// stepsOf — จำนวนขั้นตอนของอัลกอริทึมแต่ละชนิดที่ขนาด input n
func stepsOf(kind string, n int) float64 {
	nf, l := float64(n), math.Log2(float64(n)) // float64 = เลขทศนิยม · Log2 = log ฐาน 2
	switch kind {
	case "O(1)":
		return 1                          // ค่าคงที่ ไม่ขึ้นกับ n
	case "O(log n)":
		return math.Ceil(l)               // Ceil = ปัดเศษขึ้น
	case "O(n)":
		return nf                         // โตเท่า n
	case "O(n log n)":
		return nf * l
	case "O(n^2)":
		return nf * nf                    // n × n
	case "O(n^3)":
		return nf * nf * nf               // n × n × n
	case "O(2^n)":
		return math.Exp2(nf)              // Exp2 = 2 ยกกำลัง n
	}
	return math.NaN()                    // NaN = "ไม่ใช่ตัวเลข" (กันกรณีเรียกผิด)
}
```

โค้ดนี้ไม่มีอะไรลึกลับ: แต่ละบรรทัดคือ "ถ้าอัลกอริทึมชนิดนี้ทำงานกับข้อมูล n ตัว มันต้องทำกี่ขั้นตอน" เช่น `O(n)` ก็คือ n ขั้นตอน, `O(n^2)` (อ่านว่า "โอของเอ็นกำลังสอง") ก็คือ n×n ขั้นตอน, `O(2^n)` (อ่านว่า "โอของสองยกกำลังเอ็น") ก็คือ 2 คูณตัวเอง n ครั้ง

รันแล้วได้ตารางนี้ (ตัวเลขทุกตัวคำนวณจริง):

```
ที่ n = 100:
  O(1)        1 ขั้นตอน                ← คงที่เสมอ ไม่ว่านจะกี่ตัว
  O(log n)    7 ขั้นตอน
  O(n)        100 ขั้นตอน
  O(n log n)  664 ขั้นตอน
  O(n^2)      10,000 ขั้นตอน
  O(n^3)      1,000,000 ขั้นตอน
  O(2^n)      1.27e+30 ขั้นตอน   ← 127 ตามด้วยศูนย์อีก 28 ตัว
```

ดูช่องสุดท้ายให้ดี — ที่ n = 100 แค่ร้อยตัว `O(2^n)` ปาไป **1.27×10³⁰ ขั้นตอน** (คือ 127 ตามด้วยศูนย์อีก 28 ตัว) ซึ่งมากกว่าจำนวนดาวฤกษ์ทั้งหมดในเอกภพที่มองเห็นได้ (ราว 10²²–10²⁴ ดวง) เป็นล้านถึงร้อยล้านเท่า ส่วน `O(n)` แค่ 100 ขั้นตอน

ทีนี้มาดู**อัตราการโต** — พอ n คูณสอง ขั้นตอนคูณกี่เท่า:

| อัลกอริทึม | n ×2 → ขั้นตอน ×? | หน้าตา |
|---|---|---|
| O(n) | ×2 | ข้อมูลสองเท่า งานสองเท่า |
| O(n²) | ×4 | ข้อมูลสองเท่า งานสี่เท่า |
| O(n³) | ×8 | ข้อมูลสองเท่า งานแปดเท่า |
| O(2ⁿ) | **กลายเป็นยกกำลังสอง** | ข้อมูลเพิ่มแค่**ตัวเดียว** งานก็คูณสอง |

แถวสุดท้ายเป็นกรณีพิเศษที่ต้องแยกพูด: `O(2ⁿ)` พอ n เพิ่มแค่ **1** (ไม่ใช่คูณสอง) งานก็คูณสองแล้ว — พอ n คูณสอง งานกลับ**ยกกำลังสอง** (จาก 2ⁿ กลายเป็น (2ⁿ)²) ซึ่งโตเร็วกว่าทุกแถวบนรวมกัน นี่แหละคือ "การเติบโตแบบทวีคูณ" ที่เราจะกลับมาหามันทั้งตอน

นี่คือจุดที่ต้องฝังหัวให้แน่น: การเติบโตแบ่งเป็นสองตระกูลใหญ่

- **พหุนาม** (polynomial) — `n`, `n²`, `n³`, `n log n`: คือการโตที่ไม่เกิน "n ยกกำลังเลขคงที่" (n², n³, …) — ตัวแปร n ไม่ไปอยู่ในเลขชี้กำลัง (`n log n` ก็ยังช้ากว่า n² จึงจัดอยู่ในกลุ่มเดียวกัน) — n โตขึ้นงานก็โตขึ้น แต่ยัง "ตามไหว" พวกนี้คืออัลกอริทึมที่เราใช้ได้จริงในชีวิตประจำวัน
- **ทวีคูณ** (exponential) — `2ⁿ`: n เพิ่มแค่ **1** งานก็คูณสอง ข้อมูลใหญ่ขึ้นนิดเดียว งานระเบิดเป็นทวีคูณ

แล้วเราจะเชื่อตารางนี้แค่ไหน? โปรแกรม 01 ยัง**จับเวลาจริง**เพื่อยืนยันว่า "จำนวนขั้นตอน" กับ "เวลาจริง" ไปด้วยกัน ผลคือขั้นตอนคูณ 4 เท่า เวลาจริงก็คูณ 4.04 เท่า (O(n)) และคูณ 16.00 → เวลา ×16.11 (O(n²)) — ไล่ตามกันเกือบเป๊ะ

ส่วน "ราคาต่อหนึ่งขั้นตอน" บนเครื่องนี้อยู่ที่ประมาณ **0.84 นาโนวินาที** (นาโนวินาที = หนึ่งในพันล้านของวินาที) แปลว่า "เวลาจริง = ขั้นตอน × ราคาต่อขั้น" เป็นเรื่องจริง ไม่ใช่คำอุปมา

## 2. P กับ NP — ความไม่สมมาตรระหว่าง "หา" กับ "ตรวจ"

ตอนนี้เรามีไม้บรรทัดแล้ว มาถึงใจกลางของตอนนี้เลย: **P vs NP**

- **P** (Polynomial time) = เซตของปัญหาที่**หาคำตอบ**ได้ในเวลาพหุนาม (n, n², n³ …) — แปลว่าข้อมูลใหญ่ขึ้นก็ยังแก้ได้จริง
- **NP** (Nondeterministic Polynomial time) = เซตของปัญหาที่**ตรวจคำตอบ**ได้ในเวลาพหุนาม — พอมีคนยื่น "คำตอบ" มาให้ เรายืนยันได้เร็วว่า "ใช่/ไม่ใช่" (คำตอบที่ยื่นมาตรวจแบบนี้ มีชื่อเรียกเฉพาะว่า **certificate** อ่าน "เซอทิฟิเคต" = ใบรับรองคำตอบ)

**กับดักศัพท์ที่คนเข้าใจผิดกันมากที่สุด:** NP **ไม่ได้**ย่อมาจาก "Non-Polynomial" (ไม่ใช่พหุนาม) — ตัว N ย่อมาจาก **Nondeterministic** (การเลือกโดยไม่กำหนดล่วงหน้า) ถ้าใครบอกคุณว่า "NP = ไม่ใช่พหุนาม" นั่นคือข้อมูลผิด โปรดจำไว้ว่ามันคือ "ตรวจได้เร็ว" ต่างหาก

แก่นของ P vs NP คือ**ความไม่สมมาตร**ข้อนี้:

> **"ตรวจว่าคำตอบถูก" มักง่ายกว่า "หาคำตอบเอง" มาก**

ลองดูโจทย์คลาสสิกชื่อ **subset sum** (ผลรวมสับเซต) — "สับเซต" (subset) คือการเลือก**บางตัว**จากชุดเดิม: ให้ชุดตัวเลขมา แล้วถามว่า "มีสับเซตที่ผลรวมเท่ากับเป้าหมายไหม"

- **การหา**คำตอบ = ลอง**ทุกสับเซต** — ตัวเลข n ตัว แต่ละตัวเลือกได้ 2 แบบ (เลือก / ไม่เลือก) คูณกัน n ครั้ง จึงมีทั้งหมด 2ⁿ สับเซต = เติบโตแบบทวีคูณ
- **การตรวจ**คำตอบ = มีคนยื่น "สับเซตชุดนี้" มาให้ เราก็แค่**บวกเลขตามนั้น** n ครั้ง = เติบโตแบบเส้นตรง

สองงานหน้าตาแทบเหมือนกัน แต่ราคาต่างกันมหาศาล ดูโค้ดเปรียบเทียบ:

```go
// find — "หา" คำตอบ: ลองทุกสับเซต (2ⁿ) จนกว่าจะเจอตัวที่ผลรวมตรงเป้า
func find(vals []int64, target int64) (uint64, int64, bool) {
	total := int64(1) << uint(len(vals)) // จำนวนสับเซตทั้งหมด = 2ⁿ (n = จำนวนตัวเลข)
	for mask := int64(0); mask < total; mask++ { // mask = "จะเลือกตัวไหนบ้าง" ลองทุกชุด
		var sum int64
		for i, v := range vals {
			if mask&(1<<uint(i)) != 0 { // บิตที่ i เป็น 1 = "เลือกตัวที่ i"
				sum += v
			}
		}
		if sum == target {
			return uint64(mask), mask + 1, true // เจอแล้ว → คืนสับเซตที่เจอ + จำนวนที่ลอง
		}
	}
	return 0, total, false // ลองครบทุกสับเซตแล้ว ไม่เจอ
}

// verify — "ตรวจ" คำตอบ: บวกตามบิตมาสก์ที่ยื่นมา (แค่ n ขั้นตอน)
func verify(vals []int64, target int64, cert uint64) (bool, int64) {
	var sum, steps int64
	for i, v := range vals {
		steps++
		if cert&(1<<uint(i)) != 0 { // cert = คำตอบ (certificate) ที่ยื่นมาตรวจ
			sum += v
		}
	}
	return sum == target, steps // ผลรวมตรงเป้าหมายไหม + ใช้กี่ขั้นตอน
}
```

> **ตัวดำเนินการ `<<` และ `&` (ย่อ ๆ):** `1 << i` (shift ซ้าย) = เลื่อนบิต "1" ไปทางซ้าย i ตำแหน่ง = ค่า 2ⁱ ส่วน `mask & (1 << i)` (AND ระดับบิต) = เช็คว่า "บิตที่ i ของ mask เป็น 1 ไหม" — ถ้าเป็น 1 แปลว่าเลือกตัวที่ i (เราคุ้นกับแนวคิดบิตจากตอน 08–09 แล้ว ถ้าลืมกลับไปปัดฝุ่นได้)

ในโค้ดนี้ "คำตอบ" ถูกแทนด้วย **บิตมาสก์** (bitmask) — เลขฐานสองชุดหนึ่ง ที่บิตตำแหน่ง i เป็น 1 แปลว่า "เลือกตัวที่ i" เป็น 0 แปลว่า "ไม่เลือก" (เช่น `1010` แปลว่าเลือกตัวที่ 1 กับ 3 — นับตำแหน่งจากขวาเริ่มที่ 0) วิธีนี้ทำให้คำตอบของโจทย์ขนาด n ยาวแค่ n บิตเสมอ ไม่ว่าโจทย์จะยากแค่ไหน

```
      n   สับเซตทั้งหมด      หาเอง (ms)     ตรวจ (ns)     ต่างกัน (เท่า)
     16         65,536          1.562           23.8        6.57e+04
     18        262,144          6.706           26.8        2.5e+05
     20      1,048,576         29.905           29.6        1.01e+06
     22      4,194,304        132.716           33.2        4e+06
```

(หน่วย `ms` = มิลลิวินาที = หนึ่งในพันของวินาที · `ns` = นาโนวินาที = หนึ่งในพันล้านของวินาที · สัญกรณ์ `6.57e+04` = 6.57 × 10⁴ = 65,700)

อ่านตาราง: พอ n โตจาก 16 เป็น 22 (เพิ่มแค่ 6 ตัว) การหาเองช้าลงจาก 1.5 มิลลิวินาทีเป็น 132 มิลลิวินาที แต่การตรวจยังเร็วเท่าเดิม ~33 นาโนวินาที — ต่างกัน **4 ล้านเท่า** และช่องว่างนี้จะยิ่งถ่างออกเรื่อย ๆ

และโปรแกรมยังทดสอบอีกอย่าง: ถ้า**แก้คำตอบผิดไปหนึ่งบิต** (พลิกบิตเดียว) การตรวจก็จับได้ทันทีว่าผิด ใช้แค่ n ขั้นตอน — แปลว่าคำตอบที่ยื่นมานั้นถูกต้องแม่นยำ ไม่มีการ "ประมาณเอาว่าใกล้ ๆ"

![P, NP, NP-complete — "ง่าย" กับ "ยาก" ในทางทฤษฎี](/assets/diagrams/ep25-02-p-vs-np.svg)

เห็นภาพข้างบนแล้วจะเริ่มเข้าใจคำถามสำคัญที่ตามมา — เรามีตารางที่พิสูจน์แล้วว่า "ตรวจ" ถูกกว่า "หา" มหาศาล คำถามถัดไปจึงเป็นว่า ช่องว่างนี้เป็นของจริงหรือแค่เรายังไม่ฉลาดพอ:

> P = NP หรือไม่? — ถ้า "ตรวจง่าย" ทุกอย่างแปลว่า "หาง่าย" ด้วยหรือเปล่า?

สังเกตว่าเรารู้แน่ ๆ ว่า **P ⊆ NP** (⊆ อ่านว่า "เป็นสับเซตของ" = ทุกตัวของ P อยู่ใน NP — ทุกสิ่งที่หาได้เร็ว ย่อมตรวจได้เร็ว เพราะตรวจคือ "หาแล้วเทียบ") คำถามจริงคือ**กลับกันไหม**: มีปัญหาที่ตรวจง่ายแต่หายากจริง ๆ หรือเปล่า หรือแค่ "เรายังหาไม่เจอวิธีเร็ว ๆ เอง"?

## 3. NP-complete และ "การลด" (reduction)

จะรู้ว่าปัญหา "ยากแค่ไหน" ได้ยังไง ถ้าเรายังหาอัลกอริทึมเร็ว ๆ ไม่เจอ? คำตอบคือเครื่องมือชื่อ **การลด** (reduction) — วิธี**แปลงโจทย์หนึ่งไปเป็นอีกโจทย์หนึ่ง**

แนวคิดคือ: ถ้าเรามี "สูตรแปลง" ที่เปลี่ยนโจทย์ A ไปเป็นโจทย์ B ได้ในเวลาสั้น ๆ (พหุนาม) แล้วคำตอบยังตรงกัน — แปลว่า **B ยากอย่างน้อยเท่า A** (เพราะถ้าใครแก้ B ได้เร็ว เขาก็แก้ A ได้เร็ว ด้วยการ "แปลง A → แก้ B → แปลงกลับ")

ความงามของมันคือเรา**ไม่ต้องพิสูจน์ทีละปัญหา**:

1. **Cook–Levin (1971)** — Stephen Cook พิสูจน์ว่า **SAT** (Boolean satisfiability: หาค่าจริง/เท็จของตัวแปรให้สูตรลอจิกเป็นจริง) เป็นปัญหาที่ "ยากที่สุด" ใน NP — เรียกชั้นนี้ว่า **NP-complete** (NP สมบูรณ์) Leonid Levin ก็ค้นพบสิ่งเดียวกันอย่างอิสระ
2. **Karp (1972)** — Richard Karp ใช้การลดจาก SAT ไปหาโจทย์อีก **21 ปัญหา** (Knapsack/subset sum, วงจร Hamilton ซึ่งเป็นญาติของ TSP — ปัญหาพนักงานขายเดินทาง: หาเส้นทางสั้นสุดที่แวะทุกเมืองแล้วกลับจุดเดิม, การลงสีกราฟ …) แปลว่าพวกนี้ NP-complete เหมือนกันหมด — ปัญหาที่ดูต่างกันสิ้นเชิง กลับ "ยากเท่ากัน" เพราะแปลงหากันได้

(ทั้งคู่ได้รางวัล **Turing Award** — รางวัลสูงสุดของวิทยาการคอมพิวเตอร์ เทียบเท่า "โนเบลของสายนี้": Cook ได้ปี 1982, Karp ได้ปี 1985)

โปรแกรม 03 ของเราทำการลด **3-SAT → subset sum** (3-SAT = SAT ที่แต่ละวงเล็บมีตัวอักษรไม่เกิน 3 ตัว) จริง ๆ แล้วตรวจสองทาง เพื่อยืนยันว่าการลด "รักษาคำตอบไว้" จริง ไม่ใช่แค่พูด — โปรแกรมทดลองกับ **5 สูตร (F1–F5)** ที่มี 3–5 ตัวแปร แล้วตรวจทุกคำตอบของแต่ละสูตร:

- **ขาไป:** ทุกคำตอบของ 3-SAT สร้างสับเซตที่ผลรวมตรงเป้าได้
- **ขากลับ:** สับเซตที่ผลรวมตรง (ชุดที่โปรแกรมหาเจอ) อ่านค่าตัวแปรกลับได้ และทำให้สูตรจริงทุกสูตร

หลักการแปลงสวยงามมาก: ใช้**เลขฐานสิบเป็นภาชนะ**เก็บตัวนับหลายชุดพร้อมกัน — หลักแรก ๆ เก็บ "เลือกค่าตัวแปรตัวที่ i แล้ว" ส่วนหลักท้าย ๆ เก็บ "วงเล็บ (clause) ที่ j มีตัวอักษร (literal) ที่ให้ค่าจริงกี่ตัว" โดยเป้าหมายคือหลักตัวแปรต้อง = 1 ทุกหลัก และหลักประโยคต้อง = 3

```
สูตร F1 = (x1∨x2∨x3) ∧ (¬x1∨¬x2∨x3) ∧ (¬x1∨x2∨¬x3)
        (∨ = หรือ · ∧ = และ · ¬ = ไม่)
มี 3 ตัวแปร 3 ประโยค → แปลงเป็นตัวเลข 12 จำนวน หลักละ 6 หลัก
  12 จำนวน = ตัวแปร 3×2 (ค่าจริง/เท็จ) + ตัวเติม 3×2 = 12
  6 หลัก   = 3 หลักตัวแปร + 3 หลักประโยค
เป้าหมาย = 111333   (หลักตัวแปร 3 หลัก = 1 · หลักประโยค 3 หลัก = 3)

ผลตรวจสองทาง:
  ทางที่ 1: คำตอบของ 3-SAT ทั้งหมด 30 คำตอบ → สร้างสับเซตสำเร็จ 30 ครั้ง (100%)
  ทางที่ 2: อ่านค่าตัวแปรกลับได้ และทำให้สูตรจริงครบ 4 สูตรจาก 5 (F2 ไม่มีคำตอบ
           เพราะเป็นสูตรที่ "เป็นเท็จเสมอ" — ตรงกับภาพด้านล่าง)
```

จุดสำคัญทางความคิด: การแปลงเสร็จใน "ไม่กี่ขั้นตอน" (แค่ประกอบตัวเลข ไม่มีการค้นหา) — **ความยากไม่ได้อยู่ที่การแปลง แต่อยู่ที่การแก้โจทย์ปลายทาง** ดังนั้นถ้าใครแก้ subset sum ได้เร็ว เขาก็แก้ SAT (และทุกปัญหาใน NP) ได้เร็วด้วย และเพราะ subset sum เองก็อยู่ใน NP ทั้งสองจึง "ยากเท่ากัน" พอดี

![การลด (reduce) 3-SAT → subset sum — หัวใจของคำว่า NP-complete](/assets/diagrams/ep25-03-reduce-3sat.svg)

คำศัพท์ที่ต้องแยกให้ออก (เห็นในภาพ):

- **NP-complete** = ปัญหาที่อยู่ใน NP **และ**ยากที่สุดใน NP (SAT, subset sum, TSP) — แก้ตัวใดตัวหนึ่งได้เร็ว = แก้ทุกตัวใน NP ได้เร็ว
- **NP-hard** = ปัญหาที่ "ยากอย่างน้อยเท่า NP-complete" แต่**อาจไม่อยู่ใน NP** (คืออาจตรวจคำตอบไม่เร็วด้วยซ้ำ)

แล้วสนามนี้สรุปสถานะปัจจุบัน (ตรวจกับแหล่งปัจจุบัน ณ เวลาที่เขียน) ได้ว่า: **P vs NP ยังเป็นปัญหาที่ไม่มีใครพิสูจน์ได้** — เป็น 1 ใน 7 ปัญหา **Millennium Prize Problems** ของ Clay Mathematics Institute ที่มีเงินรางวัลข้อละ **1,000,000 ดอลลาร์สหรัฐ** ให้คนแรกที่พิสูจน์ถูกต้อง

และนักทฤษฎีส่วนใหญ่**เชื่อว่า P ≠ NP** (คือมีปัญหาที่ตรวจง่ายแต่หายากจริง) แต่ก็ยังไม่มีหลักฐานชี้ขาด — ตรงนี้เป็นเรื่องสำคัญที่ต้องเก็บไว้ในหัวแบบ "ยังไม่รู้" ไม่ใช่ "รู้แล้ว"

## 4. รู้ว่าโจทย์เป็น NP-hard แล้วต้องทำยังไง?

ถ้าคุณทำงานจริง แล้วเจอว่าโจทย์ของตัวเองเป็น NP-hard (เช่น การจัดตาราง, การจัดเส้นทางส่งของ, การแพ็กของลงกล่อง) คุณมีทางเลือกสองทาง — และ**ทางที่ถูกคือยอมแพ้เรื่อง "คำตอบที่ดีที่สุด"**

โปรแกรม 04 เทียบสามวิธีบนโจทย์เดียวกัน (เลือกสับเซตให้ผลรวมมากที่สุด แต่ไม่เกินเป้าหมาย):

- **exact** (คำตอบดีที่สุด) = ลองทุกสับเซต → ได้คำตอบดีสุดเสมอ แต่ใช้เวลาโตแบบ 2ⁿ
- **greedy** (ละโมบ) = เรียงตัวเลขมาก→น้อย แล้วหยิบเท่าที่ใส่ได้ → เร็วมาก (n log n) แต่พลาดได้
- **rand-greedy** = สุ่มลำดับแล้วทำ greedy ซ้ำ 2,000 รอบ เอาผลดีสุด → ยังเร็ว แต่คุณภาพดีขึ้น

```go
// greedy — เรียงจากมากไปน้อย แล้วหยิบเท่าที่ใส่ได้ (เร็ว แต่ไม่มีหลักประกัน)
func greedy(vals []int64, target int64) int64 {
	s := append([]int64(nil), vals...) // สำเนาชุดตัวเลขไว้ก่อน (ไม่แตะตัวตั้งต้น)
	sort.Slice(s, func(i, j int) bool { return s[i] > s[j] }) // เรียงมาก → น้อย
	var sum int64
	for _, v := range s {
		if sum+v <= target { // ใส่ได้ (ยังไม่เกินเป้า) ก็หยิบ
			sum += v
		}
	}
	return sum
}
```

ผลจริงจากเครื่องนี้ (หน่วย `µs` = ไมโครวินาที = หนึ่งในล้านของวินาที):

```
      n      exact (ms)    greedy (µs)    พลาด     rnd-greedy (µs)   พลาด
     20          32.8            4.8     2.78%           528.2      0.00%
     22         156.7            1.7     4.82%           559.1      0.00%
     24         605.2            1.8     4.20%           609.7      0.00%
```

เห็นภาพชัด: exact โตแบบ 2ⁿ (n แค่ 24 ก็กิน 605 ms แล้ว) ส่วน greedy ยังอยู่ระดับไมโครวินาที และ "พลาด" ไปแค่ ~3–5%

แต่ต้องระวัง! greedy **ไม่มีหลักประกันคุณภาพ** — โปรแกรมจึงใส่ "กับดัก" มาพิสูจน์ด้วย ดูตัวอย่างนี้:

```
ชุดตัวเลข = [51 50 50 50 50 50] · เป้าหมาย = 100
  คำตอบดีที่สุด = 50+50 = 100
  greedy เลือก 51 ก่อน → ใส่ 50 ต่อไม่ได้ (51+50 = 101 > 100) → ตันที่ 51
  → greedy พลาด 49%   (ได้ 51 จากที่ควรได้ 100)
  rand-greedy สุ่ม 2,000 รอบ → เจอ 100 (พลาด 0%)
```

นี่คือบทเรียน: วิธีแบบ **heuristic** (ฮิวริสติก = วิธี "กะเกณฑ์" ที่เร็วแต่ไม่รับประกันคำตอบดีสุด) ใช้ได้ดี แต่ต้องรู้ว่า "มันพลาดได้" และพลาดแบบไหน — การสุ่มหลายรอบช่วยเยอะ แต่ก็ยังไม่ใช่การรับประกัน

![กำแพงเวลา · ทางออกด้วย heuristic · สมมติฐานที่การเข้ารหัสยืนอยู่](/assets/diagrams/ep25-04-wall-heuristics.svg)

## 5. กำแพงของเวลา กับ ทำไมเรื่องนี้ถึงสำคัญกับทุกคน

โปรแกรม 05 ตอกย้ำภาพสุดท้าย: วัด**อัตราจริง**ของเครื่องนี้ (ไล่ทุกสับเซตของชุด 24 ตัว = 16,777,216 สับเซต ใน 0.535 วินาที → อัตรา **3.14×10⁷ สับเซต/วินาที**) — ที่นี่ไล่นับล้วน ๆ ไม่ได้เทียบผลรวมแบบโปรแกรม 04 จึงเร็วกว่า แล้วใช้มัน "พยากรณ์" ว่าโจทย์ขนาดต่าง ๆ จะใช้เวลานานแค่ไหน:

```
      n      สับเซตทั้งหมด         เวลาที่ต้องใช้
     50           1.13e+15                 1.14 ปี
     60           1.15e+18             1,170 ปี
    100           1.27e+30       1.28e+15 ปี  =  92,900 เท่าของอายุเอกภพ
    256           1.16e+77       1.17e+62 ปี  =  8.48e+51 เท่าของอายุเอกภพ
```

(อายุเอกภพ ≈ 13.8 พันล้านปี — ใช้เป็น "ไม้บรรทัด" ให้เห็นภาพเฉย ๆ)

ประเด็นที่ต้องฝังหัว: **การโตแบบทวีคูณไม่ใช่ "ช้า" แต่มันคือ "กำแพง"** แล้วทางออก "ก็รอให้คอมพิวเตอร์เร็วขึ้นสิ" ได้ผลแค่ไหน?

โปรแกรม 05 ทดลองให้ดู: สมมติเครื่องเร็วขึ้น **1 พันล้านเท่า** (เร็วกว่าที่เป็นไปได้ในเร็ว ๆ นี้มาก) ผลคือแก้โจทย์ได้ใหญ่ขึ้นแค่ **ราว 30 บิต** เท่านั้น (เพราะ log₂(10⁹) ≈ 29.9) — จากที่ n=60 เคยรอพันปี ก็เหลือแค่ 36.8 วินาที แต่พอ n=70 ก็กลับมาเป็น 10.5 ชั่วโมงอีก

ทำไมถึงเป็นแบบนี้? เพราะ**กำแพงทวีคูณไม่สนใจความเร็วเครื่อง**: ถ้าเพิ่มความเร็วเป็น N เท่า กำแพงจะถูกเลื่อนออกไปแค่ **log₂N บิต** เท่านั้น — เพิ่มแรงเป็นพันล้านเท่า ก็เลื่อนได้แค่ราว 30 บิต ไม่ใช่ "แก้ได้พันล้านเท่า"

แล้วทำไมเรื่องนี้ถึงสำคัญกับ**ทุกคนที่ใช้อินเทอร์เน็ต**? เพราะความปลอดภัยของการเข้ารหัสทั้งโลกยืนอยู่บนสมมติฐานเดียวกันนี้:

- การเข้ารหัสแบบ **RSA** (ชื่อระบบเข้ารหัสที่เว็บใช้ทำธุรกรรมออนไลน์) พึ่งพาความยากของ**การแยกตัวประกอบ** — การแยกจำนวนเต็มให้เป็นตัวประกอบเฉพาะ (ทับศัพท์ว่า factorization) ซึ่งเชื่อกันว่ายากมาก ยังไม่มีใครทำได้เร็ว
- ส่วนการเข้ารหัสแบบใช้**คีย์** (กุญแจรหัส) ที่เครื่องต้องไล่เดาไปเรื่อย ๆ — ถ้าสมมติเครื่องเดาได้ 1 ล้านล้านคีย์/วินาที คีย์ 128 บิตต้องใช้เวลา **1.08×10¹⁹ ปี** (782 ล้านเท่าของอายุเอกภพ) ถึงจะลองครบ
- ถ้ามีคนพิสูจน์ได้ว่า **P = NP** (คือทุกสิ่งที่ตรวจง่าย ก็หาง่ายได้เร็วด้วย) การเข้ารหัสส่วนใหญ่จะพังแทบจะทันที — ตามเอกสารทางการของ Clay เอง ระบุว่าอัลกอริทึมแก้ 3-SAT ได้ในเวลา n² จะทำให้ถอดรหัสเลข 200 หลักได้ภายในไม่กี่นาที

> **ข้อควรระวังเรื่องความแม่นยำ:** การแยกตัวประกอบ (factorization) อยู่ใน NP และเชื่อกันว่า**ไม่ใช่** NP-complete — มัน "ยาก" ในทางปฏิบัติแต่สถานะทางทฤษฎีต่างจาก SAT เล็กน้อย ตรงนี้ขอให้เข้าใจแบบกว้าง ๆ ว่า "ความปลอดภัยของการเข้ารหัสตั้งบนความเชื่อว่ามีปัญหาที่หายากจริง" ซึ่งก็คือความเชื่อว่า P ≠ NP นั่นเอง และ ณ เวลาที่เขียนยังไม่มีใครพิสูจน์ได้

## สรุปสิ่งที่เรารู้วันนี้

- **"ยาก"** วัดที่**จำนวนขั้นตอน** (ไม่ใช่วินาที) และอธิบายการโตด้วย **big-O** — โลกแบ่งเป็น "โตแบบพหุนาม" (ใช้ได้จริง) กับ "โตแบบทวีคูณ" (กำแพง)
- **P** = หาคำตอบได้เร็ว · **NP** = ตรวจคำตอบได้เร็ว (ไม่ใช่ "Non-Polynomial") · ความไม่สมมาตร "ตรวจง่าย ≠ หาง่าย" คือหัวใจของเรื่องทั้งหมด
- **NP-complete / NP-hard** เชื่อมปัญหาที่ยากเข้าด้วยกันผ่าน**การลด** (Cook–Levin 1971, Karp 1972) — พิสูจน์ตัวเดียว ยากยกแก๊ง
- **P vs NP** ยังเป็นคำถามเปิดมูลค่า 1 ล้านดอลลาร์ และนักทฤษฎีส่วนใหญ่เชื่อว่า P ≠ NP
- ทำงานจริงเจอ NP-hard → **อย่ารอคำตอบดีที่สุด** ให้ใช้ **heuristic** ที่เร็ว + ยอมรับว่าพลาดได้ (และสุ่มหลายรอบช่วยได้)

แล้วคืนถัดไปเราจะเปิด**ระยะที่ 6 (Compiler/Interpreter)** — ระยะที่เรานำทุกอย่างที่เรียนมา (ภาษา, หน่วยความจำ, ทฤษฎี) มาสร้างสิ่งที่เราทุกคนใช้อยู่ทุกวัน: ตัวแปลโปรแกรม เริ่มจากก้าวแรกคือ **lexer** (ตัวตัดข้อความโปรแกรมออกเป็น "คำ") — เป็นการเปลี่ยนจาก "ผู้ใช้เครื่องมือ" สู่ "ผู้สร้างเครื่องมือ" อย่างแท้จริง

### ระดับ Drill (ฝึกมือ)

1. ใช้ตาราง "ที่ n = 100" ในหัวข้อ 1 คำนวณว่า `O(n³)` ที่ n = 200 จะเป็นกี่ขั้นตอน (ใบ้: n คูณสอง → n³ คูณแปด → เอา 1,000,000 × 8)
2. อธิบายด้วยคำพูดตัวเองว่าทำไม "ตรวจคำตอบ subset sum" ถึงใช้แค่ n ขั้นตอน แต่ "หาคำตอบ" ต้องลอง 2ⁿ สับเซต (เทียบกับโค้ด `verify` และ `find` ในหัวข้อ 2)
3. ลองทำนายด้วยมือว่า greedy จะได้คำตอบเท่าไหร่ กับชุดตัวเลข `[6, 5, 5]` เป้าหมาย 10 (ใบ้: greedy เรียงจากมากไปน้อย แล้วหยิบเท่าที่ใส่ได้) แล้วหาคำตอบดีที่สุดที่แท้จริง เทียบว่าพลาดไปเท่าไหร่ (ใช้มือ ไม่ต้องรัน)

### Mini-project (ต่อยอดจากโปรแกรม 02)

เขียนโปรแกรม Go (แยกไฟล์ใหม่ใน `course/code/ep25/`) ที่รับชุดตัวเลขกับเป้าหมาย แล้ว**ทั้งหาและตรวจ**คำตอบของ subset sum แต่เปลี่ยนการ "หา" เป็นแบบ **meet-in-the-middle**: แบ่งตัวเลขเป็นสองครึ่ง หาผลรวมที่เป็นไปได้ทั้งหมดของแต่ละครึ่ง (ครึ่งละ 2^(n/2) แบบ) แล้วดูว่ามีคู่ที่รวมกันได้เป้าหมายไหม — เป้าหมายคือให้เห็นว่า "อัลกอริทึมที่ฉลาดกว่า brute force" (brute force = ไล่ทุกทางแบบดิบ ๆ) ทำให้ n = 30 แก้ได้จริงในเวลาอันสั้น (2^15 ≈ 32,768 สับเซตต่อครึ่ง) เทียบกับ brute force ตรง ๆ ที่ต้องลอง 2³⁰ ≈ 1 พันล้านสับเซต แล้วอธิบายว่าเหตุใด meet-in-the-middle ยังคง "โตแบบทวีคูณ" อยู่ดี (2^(n/2)) แค่เลขชี้กำลังลดลงครึ่งเดียว — มันไม่ได้เปลี่ยนคลาสของปัญหา
