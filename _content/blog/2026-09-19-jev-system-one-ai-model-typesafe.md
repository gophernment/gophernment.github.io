# Jev กับ System One Model: AI ที่ไม่พิมพ์ข้อความสักคำ แต่คืน "คำตัดสิน" ที่โค้ดเอาไปใช้ต่อได้เลย

> 📅 เขียนเมื่อ: 19 กันยายน 2026 | อ้างอิงเอกสารทางการของ TypeSafe AI (docs.typesafe.ai) และ typesafe.ai ณ วันที่เขียน — โมเดล `jev-1.13.0` / Python SDK `typesafe-sdk` 0.7.0 (SDK = ชุดโค้ดสำเร็จรูปที่ผู้ให้บริการเตรียมไว้ให้เราเรียกใช้ ไม่ต้องเขียนเองทั้งหมด)
> ⚠️ Jev ยังอยู่ช่วง early access (เปิด 15 กันยายน 2026) ตัวเลข ราคา rate limit และ API อาจขยับได้ตลอด — เช็คเอกสารต้นทางก่อนตัดสินใจใช้จริง

เคยไหม — เราอยากให้ AI ช่วย "ตัดสินใจ" อะไรสักอย่างในโปรแกรมของเรา เช่น "ข้อความนี้เป็นการขอ refund (ขอเงินคืน) หรือเปล่า" หรือ "ticket (เรื่องที่ลูกค้าแจ้งเข้ามาให้ทีมซัพพอร์ตจัดการ) นี้ควรไปหาแผนกไหน" แล้วเราก็ต้องไปหลอกให้ **LLM** (โมเดลภาษาขนาดใหญ่ — ตัวที่เราคุยด้วยเป็นข้อความได้อย่าง ChatGPT) พ่น **JSON** (รูปแบบข้อมูลหน้าตาเป็นคู่ชื่อ–ค่า ที่โค้ดอ่านออก) ออกมา แล้วภาวนาว่าก้อน JSON นั้นจะ **parse** (แปลงข้อความให้กลายเป็นข้อมูลที่โปรแกรมเอาไปใช้ต่อได้) ผ่าน

ไม่เป็นไรถ้าศัพท์ในย่อหน้านี้ยังไม่คุ้นเลย — บทความนี้ตั้งใจเขียนสำหรับคนที่ไม่รู้จัก Jev มาก่อน และทุกคำที่ technical จะมีคำอธิบายสั้น ๆ กำกับไว้ตรงที่เจอครั้งแรก

พอมันไม่ผ่านก็ต้อง retry (ยิงคำถามเดิมซ้ำอีกครั้ง) คิดเงินเพิ่ม แล้วก็ไม่มีทางรู้เลยว่าคำตอบที่ได้มานั้น "โมเดลมั่นใจแค่ไหน" — มันตอบด้วยน้ำเสียงมั่นอกมั่นใจเท่ากันทั้งตอนที่ถูกและตอนที่มั่ว

มีบริษัทหนึ่งที่มองว่าปัญหานี้ไม่ใช่เรื่อง prompt engineering (ศิลปะการเขียนคำสั่งเป็นข้อความ เพื่อหลอกให้โมเดลตอบอย่างที่เราต้องการ) แต่เป็นเรื่อง "โจทย์ผิด" ตั้งแต่แรก แล้วเขาไปสร้างโมเดลใหม่ทั้ง class (ตระกูลของโมเดล) เพื่อแก้มัน

บริษัทนั้นชื่อ **TypeSafe AI** และโมเดลตัวนั้นชื่อ **Jev** — บทความนี้จะพาไปรู้จักมันตั้งแต่ศูนย์

## 1. Jev คืออะไรกันแน่

เริ่มจากคำที่คนอ่านพาดหัวแล้วมักเข้าใจผิด

**Jev ไม่ใช่ chatbot (โปรแกรมแชทที่เราพิมพ์คุยกับ AI) ไม่ใช่ LLM และไม่ใช่โมเดลที่ฉลาดน้อยกว่า LLM** — มันคือสิ่งที่ TypeSafe เรียกว่า **System One Model** ซึ่งเป็น "class" ของโมเดล (คำว่า class ในภาษาช่างโค้ดหมายถึง "ตระกูล" หรือ "แบบ" ของของสิ่งหนึ่ง ไม่ใช่ชื่อรุ่นเดียว) ที่ออกแบบมาให้ **ซอฟต์แวร์เรียกใช้** คือให้โปรแกรมส่งคำถามเข้าไปแล้วรับคำตอบกลับมาเอง โดยไม่มีคนนั่งพิมพ์คุยด้วย

ลองนึกภาพง่าย ๆ:

| | LLM ทั่วไป | System One Model (Jev) |
|---|---|---|
| ถูกออกแบบมาให้ใครใช้ | คน | โค้ด |
| Input | prompt / ข้อความ | `state` (string, JSON object, หรือ array ของข้อความ) + ชุดคำถามแบบ typed |
| Output | ข้อความที่ generate ทีละ token | ค่าที่มี type กำกับ + probability distribution + confidence |
| เวลาตอบ | 3–329 วินาที สำหรับโมเดล frontier ตัวท็อป (ตามข้อมูล TypeSafe) | 70–500 มิลลิวินาที |
| คิดเงินยังไง | จ่าย input + output token (output แพงกว่า input หลายเท่า) | จ่ายเฉพาะ input — output ฟรี |

*คำอธิบายศัพท์ในตาราง: **prompt** = ข้อความคำสั่งที่เราพิมพ์ให้โมเดล · **token** = ชิ้นเล็ก ๆ ที่โมเดลใช้ประกอบเป็นข้อความ (โมเดลอ่านและเขียนทีละชิ้น ไม่ใช่ทีละคำ) · **output token** = จำนวนชิ้นที่โมเดลเขียนออกมา ยิ่งเขียนยาวยิ่งจ่ายแพง · **state** = ข้อมูลตั้งต้นที่เราส่งให้ Jev ใช้ประกอบการตัดสิน · **string / JSON object / array** = ข้อความล้วน ๆ / ข้อมูลแบบมีชื่อกำกับเป็นคู่ / รายการเรียงลำดับ · **typed** = ค่าที่มี "ชนิด" กำกับชัดเจนจนโปรแกรมตรวจได้ว่าถูกต้อง · **probability distribution** = ชุดตัวเลขความน่าจะเป็นของทุกช้อยส์ รวมกันได้ 1 · **confidence** = ตัวเลขเดียวที่ย่อความมั่นใจของโมเดล · **มิลลิวินาที** = หนึ่งในพันของวินาที (500 มิลลิวินาที = ครึ่งวินาที) · **frontier** = โมเดลรุ่นท็อปสุดของแต่ละค่าย*

คำอธิบายสั้นที่สุดที่ TypeSafe ใช้เขียนไว้ในบล็อกเปิดตัวคือ: **"frontier-intelligence function call"** (การเรียกใช้ความฉลาดระดับโมเดลท็อป เหมือนเราเรียกใช้ฟังก์ชันหนึ่งในโค้ด แล้วได้ค่ากลับมาตรงช่อง) — ส่ง state ที่ยังไม่เป็นระเบียบเข้าไป ได้คำตัดสินแบบ typed พร้อมความน่าจะเป็นออกมา

พูดแบบบ้าน ๆ: **LLM คือเพื่อนที่เก่งมาก แต่ตอบกลับมาเป็นข้อความยาว ๆ ที่เราต้องอ่านและตีความเองอีกที · Jev คือเพื่อนที่ตอบสั้น ๆ เป็นตัวเลขกับ label (ป้ายชื่อ เช่น `billing`) ให้เราเอาไปใช้ต่อได้ทันที**

ชื่อ **System One** มาจากแนวคิดในหนังสือ *Thinking, Fast and Slow* (Daniel Kahneman) ที่แบ่งการคิดของคนเป็น System 1 (เร็ว ใช้สัญชาตญาณ) กับ System 2 (ช้า ครุ่นคิด) — ที่นี่เขาเดิมพันกับ System 1 คือ "การตัดสินใจเร็ว ๆ ที่คนรู้เรื่องจะตอบได้ในไม่กี่วินาที"

และชื่อ **Jev** มาจากชื่อนักเศรษฐศาสตร์อังกฤษยุค 1800 เจ้าของแนวคิด **Jevons paradox** (พอของถูกลง คนกลับใช้มากขึ้น) — TypeSafe ให้เหตุผลว่าทุกครั้งที่ต้นทุนของ "สติปัญญา" ถูกลง 10 เท่า จำนวน use case (กรณีใช้งานจริง) ที่เป็นไปได้จะเพิ่มขึ้นเป็นเท่าตัว

## 2. ทำไมของเดิม (LLM + JSON mode) ถึงเจ็บ

ก่อนจะเชื่อว่า Jev ดีกว่า ลองมาดูก่อนว่าวิธีเดิมที่เราใช้กันอยู่มันเจ็บตรงไหน (JSON mode = โหมดที่สั่งให้โมเดลตอบเป็น JSON)

ถ้าเราใช้ LLM ทำงานนี้อยู่ เราคงคุ้นกับ flow (ลำดับขั้นตอน) ประมาณนี้: เขียน prompt สั่งให้ตอบเป็น JSON → แนบ schema (โครงร่างที่กำหนดว่าคำตอบต้องมีฟิลด์อะไรบ้าง ชนิดไหน) → รับ string (ข้อความดิบ ๆ) กลับมา → `JSON.parse()` (คำสั่งแปลงข้อความให้เป็นข้อมูลที่โปรแกรมใช้ได้) → validate (ตรวจว่าคำตอบตรงโครงร่างที่ขอไว้ไหม) → ไม่ผ่านก็ retry

มันทำงานได้ แต่มีรอยรั่วที่แก้ไม่หมด:

1. **parse ผ่านไม่ได้แปลว่าถูก** — schema ผ่านแต่เนื้อหามั่ว (hallucination) ได้เต็มที่ เพราะสิ่งที่โมเดลถูกฝึกมาคือ "เขียนข้อความที่คนชอบ" ไม่ใช่ "ตอบให้ตรงกับความจริง"
2. **ไม่มีตัวเลขความมั่นใจที่เชื่อได้** — เราขอให้มันแนบ `"confidence": 0.9` ได้ แต่ TypeSafe ชี้ว่าโมเดลที่ผ่าน RLHF (วิธีฝึกโมเดลด้วยการให้คนให้คะแนนว่าคำตอบไหนน่าชอบ — เป็นวิธีมาตรฐานที่ใช้กันทั่วไป) มักจะ *overconfident* คือบอกว่ามั่นใจ 0.9 ทั้งที่ตอบถูกจริงแค่บางครั้ง ถ้าเราไม่รู้ว่าคราวนี้มันกำลังอยู่ใน "บางครั้ง" ที่ตอบผิด การ automate (ปล่อยให้ระบบทำงานเองโดยไม่มีคนคอยตรวจ) ก็ทำไม่ได้
3. **mode dropping** ("ทิ้งโหมดคำตอบ" — เหลือคำตอบสไตล์เดียว) — การฝึกด้วย RLHF ทำให้โมเดลถูกบีบให้ชอบสไตล์หนึ่ง ๆ จนความหลากหลายของคำตอบหายไป ซึ่งเป็นรากของความไม่สม่ำเสมอข้ามรอบ
4. **ช้าและแพงในจังหวะที่โค้ดต้องการ** — การ generate ทีละ token (autoregressive) มีค่าใช้จ่ายเชิงเวลาที่คงที่ ไม่ว่าเราจะต้องการแค่ label เดียวหรือไม่ต้องการเลย

จุดที่เจ็บที่สุดของสายนี้คือ **type error** (โปรแกรมเจอค่าที่ไม่ตรงกับช้อยส์หรือชนิดที่เราเขียนไว้ แล้วหยุดทำงานทันที) — เราประกาศช้อยส์ไว้แค่ `billing | technical | sales` แต่โมเดลดันคืนคำว่า `"invoice"` ออกมา โปรแกรมที่รอคำตอบแบบเป๊ะ ๆ ก็พังทันที และนั่นคือสาเหตุที่ TypeSafe เดินออกไปสร้างของใหม่ทั้ง architecture (โครงสร้างระบบ) sampler (ตัวเลือกคำตอบ — ตัวที่หยิบคำตอบจากการกระจายตัวความน่าจะเป็น) และอัลกอริทึมฝึกใหม่

ชื่ออัลกอริทึมนั้นคือ **RLCD — Reinforcement Learning for Calibrated Decisions** (เรียนแบบเสริมกำลังเพื่อการตัดสินใจที่คาลิเบรตแล้ว) ทำงานแทนที่ RLHF/RLVR (RLVR = สายฝึกที่ให้รางวัลกับคำตอบที่ "ตรวจได้ว่าถูกจริง" เช่นโจทย์คณิต) โดยเป้าหมายการฝึกเปลี่ยนจาก "ให้คนชอบคำตอบ" เป็น **"ให้ตัวเลขความมั่นใจตรงกับความจริง"**

คาลิเบรตแล้วหมายความว่าอะไร? ในเชิงปฏิบัติ: ในบรรดาคำตอบทั้งหมดที่โมเดลให้ความมั่นใจ 0.8 ประมาณ **80%** ควรจะถูกจริง (วัดเป็นกลุ่ม ไม่ใช่รับประกันทีละคำตอบ)

และในฝั่งระบบของ TypeSafe **schema matching ถูกรับประกัน 100%** คือคำตอบที่ได้จะตรงกับช้อยส์ที่เรากำหนดไว้เสมอ เพราะคำตอบมีช้อยส์ปิดตายไว้ล่วงหน้าอยู่แล้ว — โมเดล *แต่งคำตอบ* ออกนอกช้อยส์ไม่ได้เลย

## 3. เจาะ primitives 3 ตัว (คำถามพื้นฐานที่มีให้ใช้): Choice / Score / Noul

ทั้งหมดที่ว่ามา สรุปสั้น ๆ ได้ว่าเราถาม Jev ได้แค่ 3 แบบเท่านั้น — จึงไม่มีอะไรซับซ้อน

| primitive | ถามว่าอะไร | ได้อะไรกลับมา |
|---|---|---|
| **Choice** | เลือก 1 จาก list ที่เรากำหนด | `choice` + `probabilities` ของทุกตัวเลือก + `confidence` |
| **Score** | ให้คะแนนตาม rubric (เกณฑ์ที่มีลำดับขั้น) ที่เรากำหนด | `score` + `legend` + `probabilities` ของทุกระดับ + `confidence` |
| **Noul** | ประโยคนี้ "จริง" ไหม | `noul` = ตัวเลข 0–1 (อ่านว่า "ความน่าจะเป็นที่คำตอบคือ จริง") |

*คำอธิบาย: **typed** = ค่าที่มีชนิดข้อมูลกำกับชัดเจนในโค้ด (แบบที่ compiler ตรวจให้ได้) · **rubric** = เกณฑ์ให้คะแนนที่แบ่งเป็นระดับเรียงลำดับ · **probability distribution** = ชุดตัวเลขความน่าจะเป็นของทุกช้อยส์ที่รวมกันได้ 1 · **legend** = คำอธิบายว่าคะแนนตัวเลขแต่ละช่วงหมายถึงอะไร · **compiler** = โปรแกรมที่ตรวจโค้ดให้ก่อนรัน*

จุดสำคัญที่หลายคนมองข้าม: **key (ชื่อที่เราตั้งให้คำถามแต่ละข้อ) ของคำถาม คือ key ของคำตอบที่ได้กลับมา** — ตั้งชื่อว่า `"department"` คำตอบก็กลับมาในชื่อ `"department"` เหมือนกัน และทุกคำถามเห็น `state` ก้อนเดียวกันพร้อมกันทั้งหมด — เพิ่มคำถามแล้วแทบไม่เพิ่มเวลาเลย

(TypeSafe เขียนไว้ตรง ๆ ว่า "adding questions barely changes the response time" และไม่เกิด context rot (อาการที่ใส่ข้อมูลยิ่งเยอะ คำตอบยิ่งเพี้ยน เพราะรายละเอียดที่ไม่เกี่ยวข้องกลายเป็นตัวกวน) ระหว่างคำถาม เพราะแต่ละคำถามถูกประเมินแยกกันจริง ๆ)

![หน้าตา request/response ของ Jev: ถามแบบ typed คืนค่าแบบ typed](/assets/diagrams/jev-02-request-response.svg)

### ตอบพร้อมกัน ไม่ใช่ตอบทีละ token

ความต่างเชิงสถาปัตยกรรมที่ TypeSafe เน้นหนักที่สุดคือ: LLM ตอบแบบ **sequential** (token นี้ต่อจาก token ก่อนหน้า) แต่ Jev ตอบแบบ **parallel** (คำนวณทุกคำตอบพร้อมกันในลักษณะ single query คือยิงคำถามชุดเดียวจบ) — นี่คือเหตุผลหลักที่ความเร็วไม่ผูกกับ "ความยาวคำตอบ" เพราะมันไม่มีคำตอบให้ยาว

พอเห็นแล้วว่ามันเร็วและถูกเพราะตอบพร้อมกัน คำถามต่อไปที่สำคัญกว่าคือ "แล้วเราจะกล้าเชื่อมันแค่ไหน" — คำตอบอยู่ในหัวข้อถัดไป

## 4. confidence: ด่านที่สองที่ทำให้เรากล้า automate

ตรงนี้คือส่วนที่ผมคิดว่าสำคัญที่สุดสำหรับคนที่เอาไปใช้จริง

Jev ให้ค่าสองชั้นแยกกัน คือ **Answer** (คำตอบคืออะไร) กับ **confidence** (มั่นใจแค่ไหน 0–1 ซึ่งคำนวณจากการกระจายตัวของ `probabilities` — ถ้ากระจายแบนราบ = ไม่มั่นใจ)

ในเอกสาร TypeSafe จึงแนะนำ pattern ที่เรียกว่า **confidence-gated routing** — ใช้ confidence เป็นประตูที่สอง:

- **0.85 ขึ้นไป** → ทำเลยอัตโนมัติ (งานความเสี่ยงต่ำ)
- **0.60–0.85** → ทำต่อได้ แต่ขอให้คนยืนยัน หรือติดธงไว้ให้ตรวจ
- **ต่ำกว่า 0.60** → **อย่าลงมือ** ส่งต่อให้คนหรือ LLM ตัวที่คิดลึกกว่า

ตัวอย่างจริงจากเอกสาร: งาน "เช็คยอดเงิน" ใช้ threshold (ค่าขั้นที่ตั้งไว้ล่วงหน้า ว่าตั้งแต่เท่าไรจึงถือว่าผ่าน) 0.60 ก็พอ เพราะถ้าพลาดก็แค่ลูกค้าได้ยินยอดผิด แต่ "อนุมัติโอนเงิน" ต้องเกิน 0.85 ไม่งั้นระบบต้องถามยืนยันก่อน

![confidence-gated routing: แบ่ง confidence เป็น 3 ช่วง แล้วให้โค้ดตัดสินใจต่างกัน](/assets/diagrams/jev-03-confidence-routing.svg)

**มองแบบนี้:** confidence คือกลไกที่ทำให้ AI "พูดได้ว่า อันนี้ผมไม่ชัวร์" — และในทางวิศวกรรม การมีสัญญาณว่า *เมื่อไหร่ไม่ควรเชื่อ* มีค่าพอ ๆ กับความแม่นยำเลย

ข้อควรระวัง 2 ข้อที่เอกสารระบุชัด:
- **Noul ไม่มี `confidence`** — มีแค่ตัวเลข `noul` ตัวเดียว ต้องตั้ง threshold เองในโค้ด
- **อย่าเอา threshold ของ Noul ไปใช้กับ Choice** และอย่าคาดหวังว่าถามคำถามเดียวกันแบบ Noul กับแบบ Choice แล้วตัวเลขจะตรงกัน

ตัวอย่างของข้อ 2 ที่เอกสารยกมาเอง: `P(refund)` = 0.72 กับ `P(ไม่ refund)` = 0.47 (`P(...)` อ่านว่า "ความน่าจะเป็นที่...") สองตัวรวมกันได้ 1.19 ซึ่งดูขัดสายตาคน เพราะปกติความน่าจะเป็นของสองทางตรงข้ามควรบวกกันได้ 1 — แต่ TypeSafe อธิบายว่านี่คือพฤติกรรมที่ตั้งใจให้เป็น แต่ละคำถามถูกประเมินแยกกันจริง ๆ ไม่ได้บังคับให้ตัวเลขสัมพันธ์กัน

เห็นภาพรวมของ confidence แล้ว ถัดไปคือคำถามที่หลายคนสงสัย: แล้วในโลกจริงเขาเอา Jev ไปทำอะไรกัน

## 5. ใช้ทำอะไรได้จริง

เอกสารของ TypeSafe แจก use-case map (แผนที่ว่าโมเดลนี้เอาไปใช้กับงานแบบไหนได้บ้าง) มาเป็นหมวด ๆ ซึ่งลงลึกกว้างมาก ถ้าจะสรุปให้เหลือภาพเดียว ผมแบ่งเป็น 5 กลุ่มนี้

**1. งานจำแนก/จัดเส้นทาง (classification & routing)** — ticket นี้ไปแผนกไหน, ข้อความนี้ขอ refund ไหม, ลูกค้าคนนี้หงุดหงิดแค่ไหน, เคสนี้ควรส่งให้คนหรือปล่อยอัตโนมัติ

**2. Guardrails ให้ LLM** — คัดข้อความก่อนเข้าและก่อนออกจาก LLM app: prompt injection, jailbreak, ข้อมูลส่วนตัวหลุด, คำตอบที่ขัด policy (นโยบายของบริษัท) — จ่ายถูกกว่าการเรียก LLM ตัวใหญ่ไปตรวจงานตัวเอง

**3. ค้นหาและจัดอันดับ (search & ranking)** — ให้คะแนนความเกี่ยวข้องของ query กับ candidate แล้ว rerank ในโค้ด เอกสารมีเคสจริงที่ยก top-1 accuracy ของชุดข้อมูลกฎหมาย CLERC จาก 5% เป็น 18% และ top-10 จาก 38% เป็น 62%

**4. Map-reduce บนข้อมูลก้อนใหญ่** — อ่านเอกสารนับล้านชิ้นแล้วสกัดเป็น feature (สัญญาณเชิงความหมาย) ไปป้อนโมเดล ML ปกติของเรา — เคสนี้ TypeSafe อ้างว่าถูกกว่าเดิมมากถึงระดับที่ทำได้จริงในทางเศรษฐศาสตร์

**5. Real-time** — ด้วยความเร็วระดับ 100 ms มีทีมเอาไปทำบอทเล่นเกม (Doom, Wikiracing) และฝังใน UI ที่ผู้ใช้รู้สึกได้ทันที

*คำอธิบายศัพท์ในส่วนนี้: **guardrail** = ราวกั้นความปลอดภัยของระบบ (ดักไว้ก่อนที่อะไรไม่ดีจะหลุดออกไป) · **prompt injection / jailbreak** = ข้อความที่คนเขียนมาเพื่อหลอกให้ AI ทำในสิ่งที่ควรห้าม · **query** = คำค้นของผู้ใช้ · **candidate** = รายการที่ระบบดึงมาให้คัดเลือก · **rerank** = จัดอันดับรายการที่ดึงมาใหม่ ให้ตัวที่เกี่ยวข้องที่สุดขึ้นบน · **top-1 / top-10 accuracy** = วัดว่าระบบจัดคำตอบที่ถูกไว้ในอันดับ 1 หรือใน 10 อันดับแรก คิดเป็นกี่เปอร์เซ็นต์ · **map-reduce** = วิธีกระจายงานใหญ่ออกเป็นกองเล็ก ๆ เยอะ ๆ แล้วค่อยรวบผลกลับมา · **feature** = ตัวเลขสัญญาณที่ป้อนเข้าโมเดล ML (โมเดลที่เรียนรู้จากข้อมูลตัวเลข ไม่ใช่ LLM) · **RAG** = ระบบที่ให้ LLM ค้นเอกสารก่อนแล้วค่อยตอบจากเอกสารนั้น*

ถ้าอยากเห็นของจริงก่อนตัดสินใจ เอกสารเขามีคุกบุ๊ก (cookbook — ชุดตัวอย่างโค้ดให้ลอกไปใช้) เยอะมาก เช่น ตรวจ citation (หลักฐานอ้างอิง) ว่ารองรับ claim (ข้อความที่อ้างว่าเป็นจริง) จริงไหม, แยก passage (ข้อความตอน) ที่มี prompt injection แอบอยู่ใน RAG, และเคสที่ TypeSafe จับคู่สินค้าสองแคตตาล็อก (entity alignment — จับคู่ข้อมูลชิ้นเดียวกันที่เขียนต่างกันคนละที่ 450 คู่) ด้วยคำถามเดียว

สรุปสั้น ๆ ก่อนไปต่อ: Jev ไม่ได้เก่งเพราะทำได้ทุกเรื่อง แต่เพราะ "งานที่ต้องตัดสินใจซ้ำ ๆ" มีอยู่เต็มไปหมดในระบบจริง — ส่วนถัดไปคือวิธีเริ่มใช้จริง ซึ่งสั้นกว่าที่คิด

## 6. เริ่มใช้จริงใน 5 นาที

ขั้นตอนมีแค่นี้ (ตาม quick start ของเอกสาร):

1. ขอ **API key** (รหัสประจำตัวสำหรับเรียกใช้บริการของเรา — เหมือนกุญแจที่ต้องแนบไปกับทุกคำขอ) จาก console ของ TypeSafe
2. ตั้ง **environment variable** (ค่าที่เก็บไว้ในเครื่องให้โปรแกรมอ่านไปใช้ โดยไม่ต้องฝังลงในโค้ดตรง ๆ) ชื่อ `TYPESAFE_API_KEY`
3. ยิง **request** (คำขอที่ส่งไปถามเซิร์ฟเวอร์) ไปที่ **endpoint** (ที่อยู่ปลายทางที่รับคำขอนี้) เดียว: `POST https://api.typesafe.ai/v1/systemone`

### แบบ curl (ไม่ต้องติดตั้งอะไร — curl = เครื่องมือใน command line สำหรับยิงคำขอไปทดสอบเร็ว ๆ)

```bash
curl -X POST https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "state": "Hi, I have been trying to connect my Stripe account for 3 days and it keeps failing. I am losing sales. Please help ASAP.",
    "model": "jev-latest",
    "questions": {
      "urgency": { "type": "noul", "instructions": "Does this message express urgency?" }
    }
  }'
```

> อ่านบล็อกนี้ทีละท่อน: `Authorization: Bearer ***` คือช่องแนบ API key ของเรา (ตัวอย่างใส่ `***` แทนไว้ อย่าใช้ค่านี้จริง) · `state` คือข้อมูลตั้งต้น — ในที่นี้คือข้อความร้องเรียนของลูกค้า · `model` คือชื่อรุ่นที่เราขอใช้ · `questions` คือชุดคำถามของเรา ซึ่งมีข้อเดียวชื่อ `urgency` แบบ `noul` พร้อม `instructions` = คำอธิบายว่ากำลังถามอะไร

### แบบ Python SDK (อ่านง่ายกว่าเวลาใช้จริง)

```bash
pip install typesafe-sdk
```

```python
# import class ที่ใช้ตั้งคำถามทั้ง 3 แบบ + ตัว client ที่ใช้เชื่อมต่อ
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

# state = ข้อมูลตั้งต้นที่จะให้ Jev ใช้ตัดสิน (เป็น dict แบบนี้ หรือส่งข้อความล้วน ๆ ก็ได้)
state = {
    "ticket": {
        "subject": "Duplicate charge",
        "message": "I was charged twice for order A-104. Please refund the duplicate.",
    },
    "order": {"id": "A-104", "charges": [49, 49]},
    "refund_policy": "Duplicate charges are eligible for a refund.",
}

with TypeSafeClient() as client:            # อ่าน TYPESAFE_API_KEY จาก env
    response = client.system_one(
        state=state,
        questions={
            "department": Choice(
                instructions="Which team should handle this ticket",
                criteria={
                    "billing": "Payment or subscription issues",
                    "technical": "Bugs or integration problems",
                    "sales": "Pricing or account questions",
                },
            ),
            "frustration": Score(
                instructions="How frustrated the customer appears",
                criteria=["Calm, just stating facts", "Frustrated but civil", "Very angry, strong language"],
            ),
            "wants_refund": Noul(instructions="Does this message request a refund?"),
        },
    )

print(response.choices["department"].choice)          # 'billing'
print(response.choices["department"].probabilities)   # {'billing': 0.84, 'technical': 0.159, 'sales': 0.001}
print(response.choices["department"].confidence)      # 0.596
print(response.scores["frustration"].score)           # 1.035
print(response.nouls["wants_refund"].noul)            # 0.95
```

*คำอธิบายโค้ดข้างบน: `Choice(...)` = คำถามแบบเลือก 1 จากช้อยส์ที่เรากำหนด · `Score(...)` = คำถามแบบให้คะแนนเป็นระดับ · `Noul(...)` = คำถามแบบใช่/ไม่ใช่ ที่ตอบกลับมาเป็นตัวเลข 0–1 · **`instructions`** = บอกโมเดลว่ากำลังถามอะไร (เขียนเป็นภาษาอังกฤษได้ผลดีที่สุด เพราะอังกฤษเป็นภาษาแรกของโมเดล) · **`criteria`** = ช้อยส์ที่เราปิดตายไว้ล่วงหน้า โมเดลเลือกได้แค่ในนี้ แต่งคำตอบเองไม่ได้ · บรรทัด `print(...)` ที่มี `#` ต่อท้ายคือตัวอย่างค่าที่จะได้กลับมา*

> 🧪 หมายเหตุความน่าเชื่อถือ: ผมติดตั้ง `typesafe-sdk` 0.7.0 ใน venv (สภาพแวดล้อม Python แยกส่วนไว้สำหรับทดลอง ไม่ปนกับของจริง) แล้ว**ทดสอบจริง**ว่าชื่อ class (`Choice`, `Score`, `Noul`, `TypeSafeClient`) และชื่อ field ของคำตอบ (`choices[...].choice`, `.probabilities`, `.confidence`, `scores[...].score`, `.legend`, `nouls[...].noul`) ตรงกับ SDK จริง และทดสอบการ parse response ได้ครบ — แต่ยัง**ไม่ได้ยิง API จริง** เพราะไม่มี API key ตัวเลขใน response ข้างบนจึงเป็นค่าตัวอย่างจากเอกสาร ไม่ใช่ผลรันของผม

### แล้วเอาไปใช้ต่อยังไง

พอได้ค่ากลับมาแล้ว ส่วนที่เหลือคือโค้ดธรรมดา ๆ — ซึ่งนี่แหละคือประเด็น:

```python
def escalate_to_human(ticket_id): return f"human:{ticket_id}"     # สมมติว่ามีอยู่แล้วในระบบเรา
def auto_route(ticket_id, dept):  return f"auto:{dept}:{ticket_id}"
def queue_for_review(ticket_id):  return f"review:{ticket_id}"


def route_ticket(response, ticket_id):
    answer = response.choices["department"]

    if answer.confidence < 0.6:
        return escalate_to_human(ticket_id)                 # โมเดลไม่ชัวร์ อย่าฝืน
    if answer.choice == "billing" and answer.probabilities["billing"] > 0.9:
        return auto_route(ticket_id, "billing")             # มั่นใจสูง ปล่อยอัตโนมัติ
    return queue_for_review(ticket_id)                      # กลาง ๆ ให้คนดูก่อน
```

*คำอธิบาย: **escalate** = ส่งต่องานที่ระบบตัดสินใจเองไม่ได้ ให้คนหรือระบบที่คิดลึกกว่าจัดการ · **branch** = แยกทางในโค้ด (if/else) ว่าเจอกรณีนี้แล้วให้ไปทำอะไรต่อ · **threshold** = ค่าขั้นที่ใช้ตัดสินว่า "ผ่านหรือไม่ผ่าน" · **probabilities** ต่างจาก `confidence` ตรงที่มันบอกความน่าจะเป็นของ *ทุกช้อยส์* ไม่ได้ย่อเหลือตัวเลขเดียว*

หลักการออกแบบที่เอกสารย้ำตลอดคือ **"โค้ดคุมเกม"** — Jev ตอบแค่คำถามที่แคบและชัด (atomic question — ถามทีละเรื่อง ไม่ยัดหลายเรื่องรวมกัน) ส่วนการชั่งน้ำหนักหลายปัจจัยให้ทำในโค้ดของเราเอง

ตัวอย่างที่เอกสารยกมา: อย่าถามว่า "สตาร์ทอัพนี้ควรลงทุนไหม" ให้ถามแยกเป็น ขนาดตลาด / ความเป็นไปได้ทางเทคนิค / ความต่างจากคู่แข่ง แล้วเอาคะแนนมาคูณน้ำหนักเอง — พอ priorities (ลำดับความสำคัญ) เปลี่ยน ก็แก้ตัวเลขในโค้ด ไม่ต้องรื้อ prompt

ก่อนจะเอาไปใช้จริง มีอีกส่วนที่ผมอยากให้อ่านให้จบ เพราะมันคือ "แผนที่จุดอ่อน" ที่ผู้ผลิตเขียนไว้เอง

## 7. มันยังไม่เก่งทุกเรื่อง — ข้อจำกัดที่ควรรู้ก่อนใช้

ส่วนนี้สำคัญมาก เพราะเอกสารเขาเขียนเองด้วยความซื่อสัตย์ (หน้า "Jev 1.13 jaggedness" — jaggedness แปลว่า "ขรุขระไม่สม่ำเสมอ" คือเก่งบางเรื่อง อ่อนบางเรื่อง — ปรับปรุงล่าสุด 17 กันยายน 2026 พร้อมยอมรับตรง ๆ ว่า Jev "ยังไม่เพอร์เฟกต์")

- **ไม่ deterministic** (ไม่แน่นอนตายตัว) — ยิงซ้ำคำถามเดิมกับ state เดิม อาจได้ตัวเลขต่างกันเล็กน้อย มัน *สม่ำเสมอ* ในเชิงสถิติ (input คล้ายกัน → ผลคล้ายกัน) แต่ไม่ได้การันตีผลเท่าเดิมเป๊ะ ๆ แบบฟังก์ชันบริสุทธิ์ (pure function — ใส่ค่าเดิมเข้าไป ได้ผลเดิมออกมาทุกครั้ง)
- **การนับเลขยังไม่น่าเชื่อถือ (unreliable)** — อย่าให้มันนับจำนวนครั้งของคำในข้อความ ให้ regex (สูตรค้นหาข้อความ) หรือโค้ดนับเอง (เอกสารถึงขั้นบอกว่า "ก่อนจะถามเรื่องการนับ ลองถามตัวเองก่อนว่าทำไมต้องใช้โมเดลตรงนี้")
- **คณิตศาสตร์ยังไม่เก่ง** — เอาเลขไปคำนวณในโค้ดเอง อย่าใช้ `score` เพื่อ interpolation (เดาค่าที่อยู่ระหว่างจุดที่รู้) แทนการคำนวณจริง
- **วันที่/เวลา เปรียบเทียบไม่เก่ง** — มันอ่านวันที่เป็น "ข้อความ" ไม่ใช่ "ปริมาณที่เรียงลำดับได้" ให้แยกส่วนประกอบ (เดือน/วัน/ปี) ออกมาเป็น Choice แล้วประกอบกับเปรียบเทียบในโค้ด
- **อ่านตรงตัวมาก (literal reading)** — มันตอบตามที่เราเขียน ไม่ใช่ตามที่เรา *คิดว่า* เขียน ถ้าเจอคำตอบผิดแล้วเราต้องอธิบายว่า "จริง ๆ ฉันหมายถึง..." คำอธิบายนั้นแหละคือครึ่งหนึ่งของ instruction ที่หายไป
- **indirection หลายชั้นทำคะแนนตก** (ถามอ้อมหลายทอด) — คำถามแบบ "คุณสมบัติของคุณสมบัติ" หรือมี double negative (คำปฏิเสธซ้อนคำปฏิเสธ) คำตอบจะเชื่อถือได้น้อยลง
- **state ยิ่งใหญ่ยิ่งแม่นน้อยลง (context rot — ข้อมูลเยอะเกินจนกลายเป็นตัวกวน)** — รายละเอียดที่ไม่เกี่ยวกับคำถามทำหน้าที่เป็นตัวกวน ให้กรองในโค้ดก่อนส่ง และมีตัวช่วยแบบใช้ Noul กรอง relevance (ความเกี่ยวข้อง) ได้
- **ข้อความที่จงใจปั่นโมเดล (adversarial content) มีผลจริง** — state คือ data ไม่ใช่ศัตรูโดยดีฟอลต์ ข้อความที่เขียนมาเพื่อบิดคำตอบสามารถขยับคำตอบได้ ถ้าเราเอา input ของผู้ใช้มาเป็น state ต้องทดสอบเคสขอบ (edge case — กรณีสุดโต่งที่เกิดน้อยแต่พังแรง) ให้หนัก
- **รับแค่ข้อความ** — ไม่รองรับ image / audio / video (ณ วันที่เขียน) ต้องแปลงเป็น text หรือ field โครงสร้างก่อนส่ง
- **อังกฤษคือภาษาแรกของโมเดล** — ภาษาอื่น (รวมถึงสาย CJK — จีน/ญี่ปุ่น/เกาหลี) ใช้ได้แต่แม่นน้อยกว่า TypeSafe แนะนำให้ทดสอบกับเนื้อหาจริงของเราเองก่อน
- **ไม่ generate ข้อความ** — ถ้าอยากได้ข้อความ ต้องใช้โมเดลที่ generate ได้ (เอกสารบอกตรง ๆ ว่า "ถ้าจำเป็นต้อง generate text จริง ๆ ... มีโมเดลอื่นสำหรับเรื่องนั้น")

และที่ควรรู้เรื่องข้อมูล: TypeSafe ระบุว่า **ไม่ฝึกโมเดลด้วย request/response ของลูกค้า** และ Jev ไม่ได้ถูก fine-tune (ฝึกเพิ่มเป็นพิเศษให้เชี่ยวชาญเรื่องใดเรื่องหนึ่ง) แยกต่อบัญชี — เราปรับให้เข้ากับ domain (วงงานของเราเอง) ด้วยการจัด `state`, `instructions` และ `criteria` ของเราเองทั้งหมด

## 8. เทียบกับคู่แข่ง: แล้วทำไมไม่ใช้ LLM + JSON mode ต่อไป

คำถามที่ยุติธรรมคือ "ฉันมี LLM อยู่แล้ว ต่อ structured output (บังคับให้โมเดลตอบตามโครงสร้างที่กำหนด เช่น JSON) ก็ได้นี่"

ก็ได้ — และในหลายงานมันคือคำตอบที่ถูก ต้องบอกแบบนี้ก่อน แต่ความต่างเชิงพื้นฐานคือ:

| มิติ | LLM + JSON mode / structured output | Jev (System One) |
|---|---|---|
| ธรรมชาติของ output | ยังเป็นข้อความ generate มาแค่ "บังคับรูปแบบ" | ค่าที่มี type ตั้งแต่ต้นทาง |
| type error | เกิดขึ้นได้ (ต้อง validate + retry) | รับประกันว่าไม่มี (ช้อยส์ปิด) |
| ความน่าจะเป็น | ปกติไม่ให้ หรือให้แบบขอร้องแล้วไม่น่าเชื่อ | ให้ทุกคำตอบ พร้อมคาลิเบรต |
| ต้นทุน output | แพงกว่า input หลายเท่า | ฟรี |
| ความเร็ว | วินาที | มิลลิวินาที |
| ความยืดหยุ่น | สูงมาก ทำได้ทุกอย่าง | ต่ำโดยตั้งใจ — ทำได้แค่ตัดสินใจ |
| งานที่เหมาะ | เขียน สรุป คิดหลายชั้น คุยกับคน | ตัดสินใจแคบ ๆ ที่โค้ดต้องเรียกถี่ ๆ |

ในมุมหนึ่ง Jev จริงจังกับมันมาก: TypeSafe เขียนไว้ในบล็อกเปิดตัวว่า โมเดลคู่แข่ง (ในงาน system one) ต้องถูกบีบด้วย wrapper (ตัวห่อที่แปลงคำตอบให้เข้าฟอร์แมตเดียวกัน) ที่ทำหน้าที่จัดรูปแบบให้ได้คำตอบแบบเดียวกัน ซึ่ง "ช้ากว่าและแพงกว่า" การที่โมเดลให้คำตัดสินได้เองตั้งแต่แรก

ตัวเลขบนหน้าแรกเว็บของเขา — **193.6× เร็วกว่า และ 444.6× ถูกกว่า** — มาจากการวัดแบบ "workflow eval" (ทดสอบบนงานเสมือนจริงทั้งสายงาน ไม่ใช่คำถามเดี่ยว ๆ) ที่เขาเทียบผลของ Jev กับค่าเฉลี่ยของโมเดลที่ฉลาดที่สุดและแพงที่สุดในตลาด บน workflow เดียวกัน

และตัวเขาเองก็เขียนกำกับไว้ตรง ๆ ว่าตัวเลขนี้ **"อยู่ปลายบนของกำไรที่เจอในงานจริง"** และงานทดสอบถูกสร้างโดยทีม capabilities ของเขาเอง จึงอาจมี bias (ความเอนเอียงเข้าข้างตัวเอง)

ผมชอบที่เขายอมเขียนแบบนั้น เพราะมันทำให้เรารู้ว่าควรอ่านตัวเลขนี้ยังไง — **เป็นการอ้างของผู้ผลิต ไม่ใช่ผลทดสอบอิสระ** อย่าซื้อด้วยตัวเลขหน้า home page (หน้าแรกของเว็บ) ให้ลองกับงานของตัวเองจริง ๆ

ราคาที่ประกาศตอนนี้คือ **$42 ต่อพันล้าน input token (เท่ากับ $0.042 ต่อล้าน token)** และ output ฟรี พร้อมหมายเหตุว่า rate limit (เพดานจำนวนคำขอที่ยิงได้ต่อช่วงเวลา) ยังปรับแบบ dynamic เพราะ demand สูง

จุดที่ TypeSafe ต่างจากทั้ง OpenAI และ Anthropic เชิงทิศทางก็คือ: เขาไม่ได้พยายามสร้างโมเดลที่ทำได้ทุกอย่าง แต่เดิมพันว่า **การ automate ในอนาคตจะเป็นการคุยกันระหว่างเครื่อง 99% และคุยกับคน 1%** — ถ้าเชื่อสมมติฐานนี้ การออกแบบ interface (ช่องทางที่สองฝ่ายคุยกัน — ตรงนี้คือช่องทางที่โค้ดเรียกใช้) ให้เครื่องใช้ได้ง่ายกว่าการออกแบบให้คนอ่านรู้เรื่อง คือการเดิมพันที่ถูก

## 9. สรุป: เหมาะกับใคร

**เหมาะ** ถ้าคุณกำลังสร้างระบบที่ต้อง "ตัดสินใจ" ซ้ำ ๆ เป็นล้านครั้ง (route ticket, จัดหมวด, ให้คะแนน, ตรวจ guardrail, rerank ผลค้นหา — ศัพท์ชุดนี้อธิบายไว้แล้วในหัวข้อ 5) และต้องการของที่เร็ว ถูก และ **บอกได้ว่าตัวเองไม่มั่นใจตอนไหน** เพื่อให้โค้ดเลือกได้ว่าจะทำเองหรือส่งต่อ

**ยังไม่เหมาะ** ถ้างานของคุณต้อง generate ข้อความ ต้องคิดหลายชั้น หรือต้องการ input ที่ไม่ใช่ข้อความ — หรือถ้างานนั้นโค้ดคำนวณได้ตรง ๆ อยู่แล้ว (คำเตือนของ TypeSafe เอง: อย่าให้โมเดลทำงานที่โค้ดทำได้เป๊ะ ๆ)

ความหมายของ Jev ต่อวงการ AI ตรงนี้ผมคิดว่าชัดเจน: มันเป็นเครื่องเตือนว่า **"chat" ไม่ใช่ปลายทางเดียวของการใช้โมเดล** และสำหรับงานจำนวนมาก สิ่งที่ซอฟต์แวร์ต้องการจริง ๆ ไม่ใช่คำตอบที่อ่านแล้วรู้สึกดี แต่เป็นคำตอบที่ *โค้ดเอาไปใช้ต่อได้* โดยไม่ต้องแอบภาวนาให้ JSON parse ผ่าน
