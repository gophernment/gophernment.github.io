# โปรเซสกับเธรด + ตัวจัดคิว — ทำไมคอมพิวเตอร์ "ทำงานหลายอย่างพร้อมกัน" ได้ (process / thread / context switch / scheduling) (ตอนที่ 18) — CS Fundamentals: จาก 0 สู่พื้นฐานที่แท้จริง

ตอนที่แล้ว (ตอนที่ 17) เราตามเส้นทางของโปรแกรมหนึ่งจากไฟล์ `.c` ไปจนเป็นไฟล์ executable ที่รันได้ แต่พอโปรแกรมนั้น**ถูกกดรันจริง ๆ** เรื่องเพิ่งเริ่มต้น — ระบบปฏิบัติการ (OS, Operating System = โปรแกรมใหญ่ที่คุมเครื่องทั้งหมดให้แอปอื่นทำงานได้) ต้องตัดสินใจว่า**ให้ใครใช้ CPU ตอนไหน** ใช้**นานแค่ไหน** และจะ**สลับงาน**ระหว่างโปรแกรมหลายตัวยังไง โดยที่คุณ (คนใช้งาน) เห็นแต่ภาพเดียวบนจอ แล้วรู้สึกว่า "คอมทำหลายอย่างพร้อมกัน"

ความจริงคือ CPU ของ Raspberry Pi 5 มีแค่ **4 แกน** (core = หน่วยประมวลผลย่อยที่ทำงานได้อิสระจากกัน) แต่ตอนนี้ในเครื่องเรามีงาน (task = หน่วยงานที่เคอร์เนลต้องจัดคิว) วิ่งอยู่เป็น**พันตัว** คำถามที่บทนี้จะตอบด้วยการรันจริงทั้งหมด:

1. **โปรเซส** (process = โปรแกรมหนึ่งตัวที่กำลังทำงาน 1 ชุด) กับ **เธรด** (thread = สายงานย่อยภายในโปรเซสเดียว) ต่างกันยังไง ทำไมเธรดถึง "แชร์หน่วยความจำ" ได้แต่โปรเซสแชร์ไม่ได้
2. **context switch** (การสลับงาน = หยุดงานหนึ่ง ไปทำงานอีกงานหนึ่ง แล้วกลับมา) ราคาจริงเท่าไรบนเครื่องเรา
3. **ตัวจัดคิว** (scheduler = ส่วนของเคอร์เนลที่ตัดสินใจว่าใครได้ CPU ต่อไป) แบ่ง CPU ให้งานหลายตัวยังไง และ `nice` (ค่าความสำคัญของงาน) มีผลจริงแค่ไหน

ทุกตัวเลขในบทนี้มาจากการรันจริงบนเครื่องเรา (Raspberry Pi 5, Linux 6.18.39 aarch64, GCC 14.2.0, glibc 2.41, Go 1.24.4) — ไม่มีตัวเลขไหนยกมาจากตำราโดยไม่รัน

> **คำศัพท์พื้นฐานที่จะใช้ตลอดบทนี้** (อธิบายครั้งเดียวตรงนี้ แล้วใช้ต่อเลย):
> - **โปรเซส** (process) = โปรแกรมที่ถูกโหลดขึ้นมาทำงานแล้ว 1 ชุด · แต่ละโปรเซสมี**พื้นที่หน่วยความจำของตัวเอง** (address space = ช่วงที่อยู่ที่โปรเซสใช้ได้) กับหมายเลขประจำตัวที่เรียกว่า **PID** (Process ID)
> - **เธรด** (thread) = "สายงานย่อย" ภายในโปรเซสเดียว · ทุกเธรดในโปรเซสเดียวกัน**ใช้หน่วยความจำร่วมกัน** แต่มี **TID** (Thread ID) ของตัวเอง
> - **เคอร์เนล** (kernel) = แกนกลางของ OS ที่คุม hardware โดยตรง · โปรแกรมของเราจะขอใช้ hardware (อ่านไฟล์, ขอหน่วยความจำ, รอเวลา) ผ่านทาง**เคอร์เนล**เสมอ
> - **syscall** (system call) = "การเรียกใช้บริการของเคอร์เนล" — โปรแกรมขอให้เคอร์เนลทำอะไรให้ (เช่น `read`/`write`/`fork`) แล้วรอผล
> - **user space / kernel space** = สองโหมดการทำงานของ CPU · โปรแกรมเราอยู่ใน user space (ทำอะไรอันตรายไม่ได้) ส่วนเคอร์เนลอยู่ใน kernel space (สิทธิ์เต็ม) · การเปลี่ยนจาก user ไป kernel ต้องผ่าน syscall หรือ interrupt
> - **context switch** = การสลับงาน · เคอร์เนลบันทึกสถานะของงานปัจจุบัน (ค่ารีจิสเตอร์, ตำแหน่งที่กำลังทำ) แล้วโหลดสถานะของงานถัดไปกลับเข้าไป
> - **ตัวจัดคิว** (scheduler) = โค้ดในเคอร์เนลที่เลือกว่างานไหนได้ CPU ต่อไป · **time slice** (หรือ quantum) = ช่วงเวลาที่งานหนึ่งได้ใช้ CPU ก่อนถูกตัด
> - **preemptive** = "ตัดกลางคันได้" — เคอร์เนลสามารถยึด CPU คืนจากงานที่กำลังวิ่งอยู่ได้ทุกเมื่อ (งานไม่ต้อง "ยอมปล่อย" เอง)
> - **data race** = หลายเธรดอ่าน-เขียนหน่วยความจำชุดเดียวกันพร้อมกันโดยไม่มีกติกา → ผลลัพธ์ขึ้นกับจังหวะ (ผิดเป็นพัก ๆ หาตัวจับยาก)

## 1. แนวคิด: CPU มี 4 แกน แต่มีงานเป็นพัน — ใครเป็นคนจัดคิว (ภาพที่ 1)

ก่อนลงมือเขียนโค้ด ขอตั้งภาพใหญ่ให้ตรงกันก่อน สองคำที่คนมักสับสนที่สุดคือ **โปรเซส** กับ **เธรด** เพราะทั้งคู่ "เป็นงานที่ CPU ต้องรัน" เหมือนกัน แต่**การเป็นเจ้าของหน่วยความจำ**ต่างกันคนละเรื่อง

![เทียบโปรเซสและเธรด: โปรเซสมี address space ของตัวเอง เธรดใช้ร่วมกันในโปรเซสเดียว](/assets/diagrams/ep18-01-process-vs-thread.svg)

ภาพที่ 1 สรุปความต่างไว้ครบ: **โปรเซสคือ "บ้านของตัวเอง"** — มีหน่วยความจำ, ไฟล์ที่เปิด, ตัวแปร global เป็นของตัวเองทั้งหมด พอเรียก `fork()` (syscall ที่ให้โปรเซส "คัดลอกตัวเอง" เป็นสองตัว) ลูกจะได้**สำเนาทั้งบ้าน**ไปเลย แยกขาดจากแม่ทันที · ส่วน**เธรดคือ "ห้องเพิ่มในบ้านเดิม"** — ทุกเธรดแชร์ code/data/heap/ไฟล์เดียวกัน แต่ละตัวมีแค่ stack กับรีจิสเตอร์ของตัวเอง

ทำไมเรื่องนี้สำคัญขนาดต้องแยกให้ชัด? เพราะ**การแชร์หน่วยความจำ**เป็นดาบสองคม:

- **ข้อดีของเธรด**: สร้างถูกกว่าโปรเซสมาก (ไม่ต้องคัดลอกทั้งบ้าน) · สื่อสารกันเร็ว (เขียนตัวแปรร่วมตัวเดียวจบ) · เหมาะกับงานที่ต้องทำงานคู่ขนานแล้วรวมผลกันเร็ว ๆ
- **ข้อเสียของเธรด**: แชร์กันจริง แปลว่า**ชนกันได้** — สองเธรดเขียนตัวแปรตัวเดียวกันพร้อมกัน ผลจะพังแบบหาสาเหตุยาก (เราเจอจริงในหัวข้อ 4)

ลองดูของจริงเลย เริ่มจาก `fork()` ก่อน เพราะเป็น syscall ที่เก่าแก่ที่สุดตัวหนึ่ง (มีมาตั้งแต่ Unix ยุค 1970)

## 2. ลงมือทำ 1: `fork()` — โปรเซสคือ "สำเนา" (คนละบ้าน)

โค้ดตัวแรก `fork_demo.c` พิสูจน์ว่าโปรเซสกับโปรเซสแยกหน่วยความจำกันจริง ๆ เรามีตัวแปร global ตัวหนึ่ง (ตัวแปรระดับโปรแกรมที่ทุกฟังก์ชันเห็นร่วมกัน) ชื่อ `g_counter` ตั้งค่าเริ่มต้นเป็น 100 แล้วเรียก `fork()`:

```c
/* fork_demo.c — "โปรเซส" คือสำเนา: fork() แล้วได้ address space ของตัวเอง
 *
 * build: gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -o fork_demo fork_demo.c
 * run  : ./fork_demo
 */
#define _POSIX_C_SOURCE 200809L

#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

static long g_counter = 100; /* global — ดูเหมือน "ของกลาง" แต่ไม่ใช่ของกลาง */

static void report(const char *who)
{
    int local = (int)(g_counter * 2); /* ตัวแปรบน stack ของฟังก์ชันนี้ */

    printf("%-4s pid=%-7d ppid=%-7d  g_counter=%3ld  &g_counter=%p  &local=%p\n",
           who, (int)getpid(), (int)getppid(), g_counter,
           (void *)&g_counter, (void *)&local);
    fflush(stdout); /* สำคัญ: ถ้าไม่ flush ข้อความที่ค้างใน buffer จะถูกคัดลอกไปโผล่สองรอบ */
}

int main(void)
{
    printf("== 1) ก่อน fork: มีโปรเซสเดียว ==\n");
    report("แม่");

    pid_t pid = fork(); /* << คำสั่งสำคัญ: แยกตัวเองเป็นสองโปรเซส */
    if (pid < 0) {
        fprintf(stderr, "fork ล้มเหลว: %s\n", strerror(errno));
        return EXIT_FAILURE;
    }

    if (pid == 0) {
        /* ---------- ทางนี้มีแค่ลูก ---------- */
        g_counter += 1; /* แก้ "สำเนา" ของตัวเอง */
        printf("== 2) หลัง fork: ลูกแก้ค่าของตัวเอง ==\n");
        report("ลูก");
        return EXIT_SUCCESS;
    }

    /* ---------- ทางนี้มีแค่แม่ ---------- */
    int status = 0;
    if (waitpid(pid, &status, 0) < 0) { /* รอลูกจบ แล้วเก็บรหัสออก */
        fprintf(stderr, "waitpid ล้มเหลว: %s\n", strerror(errno));
        return EXIT_FAILURE;
    }

    printf("== 3) แม่รอลูกจบแล้ว (exit code %d) มาดูของตัวเอง ==\n",
           WIFEXITED(status) ? WEXITSTATUS(status) : -1);
    report("แม่");
    printf("สรุป: ค่าในลูกเปลี่ยน แต่ค่าในแม่เท่าเดิม -> คนละ address space\n");
    printf("      แต่ &g_counter พิมพ์เท่ากันทั้งคู่ เพราะที่อยู่ 'virtual' เหมือนกันคนละชุดข้อมูล\n");
    return EXIT_SUCCESS;
}
```

ขออธิบายจุดที่มือใหม่ต้องรู้ก่อนรัน:

- `fork()` คือ syscall ที่แปลกที่สุดตัวหนึ่ง: **มัน "คืนค่าสองครั้ง"** — ครั้งแรกคืนค่าให้**แม่** (ค่าที่ได้คือ PID ของลูก) และคืนค่าให้**ลูก**อีกครั้ง (ค่าเป็น 0) ดังนั้นหลัง `fork()` บรรทัดเดียวกันจะมีสองโปรเซสเดินต่อพร้อมกัน โดยตรวจว่า `pid == 0` เพื่อแยกว่า "ตอนนี้ฉันคือลูก" หรือ "ฉันคือแม่"
- `getpid()` = ขอ PID ของตัวเอง · `getppid()` = ขอ PID ของแม่ (parent) · สองค่านี้ทำให้เรารู้ว่าตอนนี้เป็นตัวไหน
- `&g_counter` = เครื่องหมาย `&` หน้า ชื่อตัวแปร แปลว่า "ขอบ้านเลขที่ (ที่อยู่) ของตัวแปรนี้" · `%p` = วิธีพิมพ์ค่าที่อยู่เป็นเลขฐานสิบหก · ตรงนี้สำคัญ เพราะมันจะเฉลยเรื่องหน่วยความจำ
- `waitpid(...)` = แม่รอให้ลูกทำงานเสร็จก่อน (ถ้าไม่รอ ลูกอาจเป็น "โปรเซสผี" ที่ไม่มีใครเก็บศพ — เรียกว่า zombie process) · `WIFEXITED`/`WEXITSTATUS` = ตรวจว่าลูกจบแบบปกติไหม แล้วอ่านรหัสออก (exit code)
- `fflush(stdout)` ก่อน `fork()` = **กับดักคลาสสิก** · ค่าที่รออยู่ใน buffer (บัฟเฟอร์ = ที่พักข้อมูลชั่วคราวก่อนส่งออก) จะถูกคัดลอกไปพร้อมกับ `fork()` ด้วย ถ้าไม่ flush ข้อความจะพิมพ์ซ้ำสองรอบ

รันจริง (ผลบนเครื่องเรา):

```
== 1) ก่อน fork: มีโปรเซสเดียว ==
แม่ pid=2443974 ppid=2443849  g_counter=100  &g_counter=0x5556530f0080  &local=0x7ffff59c008c
== 2) หลัง fork: ลูกแก้ค่าของตัวเอง ==
ลูก pid=2443976 ppid=2443974  g_counter=101  &g_counter=0x5556530f0080  &local=0x7ffff59c008c
== 3) แม่รอลูกจบแล้ว (exit code 0) มาดูของตัวเอง ==
แม่ pid=2443974 ppid=2443849  g_counter=100  &g_counter=0x5556530f0080  &local=0x7ffff59c008c
สรุป: ค่าในลูกเปลี่ยน แต่ค่าในแม่เท่าเดิม -> คนละ address space
      แต่ &g_counter พิมพ์เท่ากันทั้งคู่ เพราะที่อยู่ 'virtual' เหมือนกันคนละชุดข้อมูล
```

ดูให้ดี มีเรื่องน่าทึ่งสองอย่าง:

1. **ลูกลบแล้ว แม่ไม่รู้** — ลูกแก้ `g_counter` เป็น 101 แต่แม่ยังเห็น 100 แปลว่าทั้งคู่**คนละชุดข้อมูล** (แยกบ้านกันจริง ไม่ใช่ของกลาง)
2. **`&g_counter` เท่ากันทั้งคู่ (0x5556530f0080)** — ทั้งที่ข้อมูลคนละชุด แต่ "บ้านเลขที่" ตรงกันเป๊ะ นี่คือหัวใจของเรื่อง **virtual memory** (หน่วยความจำเสมือน = ที่อยู่ที่โปรเซสเห็น ไม่ใช่ตำแหน่งจริงบน RAM) ที่เราจะลงลึกเต็ม ๆ ในตอนที่ 20 — ตอนนี้ขอแค่จำไว้ก่อนว่า**ที่อยู่ที่โปรแกรมเห็นเป็นของปลอม** เคอร์เนลแปล "ที่อยู่ปลอม" ของแต่ละโปรเซสไปยังตำแหน่งจริงคนละที่ ซึ่งทำได้ทั้งแม่และลูกที่ที่อยู่ปลอมเท่ากัน

สังเกต `&local` (ตัวแปรบน stack) เท่ากันทั้งคู่ด้วย (0x7ffff59c008c) — ยิ่งยืนยันว่า "ที่อยู่ปลอมเหมือนกัน แต่ข้อมูลแยกกัน"

## 3. ลงมือทำ 2: `pthread_create` — เธรดคือ "ห้องในบ้านเดียวกัน"

คราวนี้ลองสิ่งที่ตรงข้าม: สร้าง**เธรด** 4 ตัวให้บวกตัวนับตัวเดียวกัน 1,000,000 ครั้ง (`thread_demo.c`) แล้วดูว่า "แชร์กันจริง" ต่างจาก `fork()` ยังไง

```c
/* thread_demo.c — "เธรด" คือหลายสายงานในบ้านหลังเดียวกัน (address space เดียว)
 *
 * build: gcc -std=c17 -Wall -Wextra -Wpedantic -O2 -o thread_demo thread_demo.c -pthread
 * run  : ./thread_demo
 */
#define _GNU_SOURCE /* เพื่อให้ได้ gettid() ของ Linux */

#include <errno.h>
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

#define NTHREADS   4
#define PER_THREAD 250000L /* ต่อเธรด -> รวม 1,000,000 */

static long g_counter = 0; /* ข้อมูลที่ "แชร์กันจริง" ระหว่างเธรด */
static pthread_mutex_t g_lock = PTHREAD_MUTEX_INITIALIZER;    /* ประตู: เข้าได้ทีละคน */
static pthread_mutex_t g_io_lock = PTHREAD_MUTEX_INITIALIZER; /* กันข้อความพิมพ์ชนกัน */
static pthread_barrier_t g_start;                             /* จุดนัดพร้อมของทุกเธรด */

struct worker_arg {
    int idx;
    long private_done; /* ตัวนับส่วนตัว: ไม่ได้แชร์ จึงไม่ต้องล็อก */
};

/* pthread ทุกตัว "คืนรหัส error" แทนการตั้ง errno — เช็คทุกครั้งแล้วหยุดอย่างชัดเจน */
static void check_rc(int rc, const char *what)
{
    if (rc != 0) {
        fprintf(stderr, "%s ล้มเหลว: %s\n", what, strerror(rc));
        exit(EXIT_FAILURE);
    }
}

static int current_tid(void)
{
#if defined(__linux__)
    return (int)gettid(); /* บน Linux: TID ของ "เธรดนี้" (เธรดหลัก TID = PID) */
#else
    return (int)getpid();
#endif
}

static void *worker(void *p)
{
    struct worker_arg *a = p;

    pthread_mutex_lock(&g_io_lock);
    printf("เธรด %d เริ่ม: tid=%d  &g_counter=%p (ที่อยู่เดียวกับที่พ่อพิมพ์)\n",
           a->idx, current_tid(), (void *)&g_counter);
    fflush(stdout);
    pthread_mutex_unlock(&g_io_lock);

    /* ทุกเธรดหยุดรอที่นี่ จนกว่าทุกตัวจะพร้อม -> เริ่มพร้อมกันจริง */
    check_barrier(pthread_barrier_wait(&g_start), "barrier_wait");

    for (long i = 0; i < PER_THREAD; i++) {
        check_rc(pthread_mutex_lock(&g_lock), "mutex_lock");
        g_counter++; /* อ่าน-บวก-เขียน ที่ถูกกันด้วยประตู */
        check_rc(pthread_mutex_unlock(&g_lock), "mutex_unlock");
    }

    a->private_done = PER_THREAD;
    return NULL;
}
```

(ย่อเฉพาะส่วนสำคัญ — ไฟล์เต็มอยู่ใน `course/code/ep18/thread_demo.c` พร้อม `main` ที่สร้างเธรด 4 ตัว, นัดทุกตัวให้เริ่มพร้อมกันด้วย barrier, แล้วรอ `pthread_join` จนครบ)

ศัพท์ใหม่ที่ต้องรู้:

- `pthread_create` = สร้างเธรดใหม่ 1 ตัว (pthread ย่อมาจาก POSIX threads = มาตรฐานเธรดของระบบ Unix) · เธรดใหม่จะเริ่มรันฟังก์ชันที่เราส่งให้ทันที
- **mutex** (Mutual Exclusion = "กันไม่ให้เข้าพร้อมกัน") = กุญแจ/ประตู · `pthread_mutex_lock` = ล็อกประตู (ถ้ามีคนอื่นล็อกอยู่ ต้องรอ) · `pthread_mutex_unlock` = ปลดล็อก · เธรดที่ถือประตูอยู่เท่านั้นถึงจะเข้าไปบวก `g_counter` ได้
- **barrier** (จุดนัด) = จุดที่ทุกเธรดต้องมาถึงให้ครบก่อนถึงจะผ่านไปพร้อมกัน · เราใช้เพื่อให้ทุกเธรด "ออกสตาร์ทพร้อมกันจริง" (ไม่งั้นตัวแรกอาจวิ่งจบก่อนตัวสุดท้ายเพิ่งเริ่ม)
- `gettid()` = ขอ TID ของเธรดนี้ · บน Linux เธรดหลัก (ตัวที่รัน `main`) มี **TID = PID** เสมอ ส่วนเธรดลูกได้ TID ใหม่
- ฟังก์ชัน pthread คืน **รหัส error** (ไม่ใช่ตั้งค่าตัวแปรกลาง `errno`) — จึงต้องเช็ครหัสทุกครั้งด้วย `check_rc` (เป็นนิสัย production-safe ที่เราฝึกกันมาตลอด)

### 3.1 เคอร์เนลมองเธรดว่ายังไง — `/proc/self/task`

อยากรู้ว่าเคอร์เนล "เห็น" อะไรจริง ๆ บ้าง ลองมองผ่านไฟล์พิเศษ `/proc` (procfs = ระบบไฟล์เสมือนที่ Linux ใช้เปิดเผยข้อมูลภายในเคอร์เนล เช่น สถานะของทุกโปรเซส) · โปรแกรม `task_view.c` สร้างเธรด 3 ตัวชื่อ worker-a/b/c แล้วเดินดูโฟลเดอร์ `/proc/self/task` ของตัวเอง:

```
โปรเซสนี้: PID=2444387  (เธรดหลัก TID=2444387)  -> PID เขียนไว้ที่ out/task_view.pid แล้ว
ข้างใน /proc/self/task มี:
  task tid=2444387  comm=task_view
  task tid=2444389  comm=worker-a
  task tid=2444390  comm=worker-b
  task tid=2444391  comm=worker-c
  รวม 4 task
```

และจากคำสั่งระบบ `ps -T` (ps = คำสั่งแสดงรายการโปรเซส · ธง `-T` = แสดงทุกเธรด):

```
$ ps -T -p 2444387 -o pid,tid,ni,psr,stat,comm
    PID     TID  NI PSR STAT COMMAND
2444387 2444387   0   2 Sl   task_view
2444387 2444389   0   2 Sl   worker-a
2444387 2444390   0   0 Sl   worker-b
2444387 2444391   0   0 Sl   worker-c
```

ประเด็นสำคัญ: **ทุกเธรดมี PID เดียวกัน (2444387)** แต่ TID ต่างกัน · ในมุมมองของเคอร์เนล คำว่า "โปรเซส" กับ "เธรด" แทบไม่ต่างกันเลย — เคอร์เนลมองทุกอย่างเป็น **task** (หน่วยที่ถูกจัดคิว) ตัวเดียว ๆ แล้วเอา task ที่ TID ตรงกันมา**จับกลุ่ม**เป็นโปรเซสเดียวกันผ่านค่า **Tgid** (Thread Group ID = หมายเลขกลุ่ม ซึ่งเท่ากับ PID ของเธรดหลัก) · ถ้าดูใน `/proc/2444387/status` จะเห็น `Tgid: 2444387` กับ `Pid: 2444387` คู่กัน (สำหรับเธรดลูก Tgid จะยังเป็น 2444387 แต่ Pid จะเป็น TID ของตัวมันเอง)

นี่คือเหตุผลที่ `fork()` (คัดลอกโปรเซส) กับ `pthread_create` (เพิ่มเธรด) มีต้นทุนต่างกันมาก: **fork ต้องคัดลอกตารางหน่วยความจำทั้งโปรเซส ส่วน pthread แค่จดทะเบียน task ใหม่ในกลุ่มเดิม**

## 4. กับดักที่มือใหม่โดนแน่: data race — "แชร์กันได้" ต้องแลกมาด้วยความเสี่ยง

หัวข้อที่แล้ว mutex ทำให้ผลรวมตรงเป๊ะ แต่**ถ้าไม่ใส่ mutex ล่ะ**? คำตอบคือ **data race** — หายนะที่โผล่เป็นพัก ๆ หาสาเหตุแทบไม่เจอ ลองรัน `race_demo.c` สองโหมด:

```c
/* race_demo.c — "ตั้งใจให้ผิด" เพื่อสอน: ตัวนับที่ไม่มีตัวกัน = ตัวเลขหาย
 *
 * build: gcc -std=c17 -Wall -Wextra -Wpedantic -O2 -o race_demo race_demo.c -pthread
 * run  : ./race_demo unsafe   ← ตั้งใจให้ผลผิด (ใช้สอนเท่านั้น ห้ามเอาไปใช้จริง)
 *        ./race_demo safe     ← เวอร์ชันถูกต้องด้วย _Atomic (C11)
 */
#define _POSIX_C_SOURCE 200809L

#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define NTHREADS   4
#define PER_THREAD 1000000L

static volatile long g_naive = 0; /* ผิด: volatile ไม่กันการชนกัน */
static _Atomic long g_atomic = 0; /* ถูก: atomic ให้ฮาร์ดแวร์จัดการให้ */

static void *naive_worker(void *p)
{
    (void)p;
    for (long i = 0; i < PER_THREAD; i++) {
        g_naive++; /* อ่าน -> บวก -> เขียน (สามจังหวะที่คนอื่นแทรกได้) */
    }
    return NULL;
}

static void *atomic_worker(void *p)
{
    (void)p;
    for (long i = 0; i < PER_THREAD; i++) {
        /* relaxed = ไม่ต้องเรียงลำดับกับการเข้าถึงหน่วยความจำอื่น แค่ "บวกครั้งเดียวแบบห้ามหาย" */
        atomic_fetch_add_explicit(&g_atomic, 1, memory_order_relaxed);
    }
    return NULL;
}
```

(ย่อ — ไฟล์เต็มมี `run_threads` กับ `main` ที่เลือกรันโหมด unsafe/safe)

ผลรันจริง (คาดหวัง 4,000,000):

```
$ ./race_demo unsafe
== ตั้งใจให้ผิด: ตัวนับ volatile ที่ไม่มีตัวกัน (4 เธรด x 1000000) ==
แบบไม่มีตัวกัน -> คาดหวัง 4000000 ได้ 1412432
   หายไป 2587568 ครั้ง (64.69%)
   สาเหตุ: หลายเธรดอ่านค่าเดียวกันพร้อมกัน แล้วเขียนทับกัน (lost update)
   volatile ไม่ช่วย เพราะมันไม่ได้กันจังหวะ (ไม่ใช่ mutex/atomic)

$ ./race_demo safe
== เวอร์ชันถูกต้อง: ใช้ _Atomic (4 เธรด x 1000000) ==
แบบใช้ _Atomic  -> คาดหวัง 4000000 ได้ 4000000
   ตรงเป๊ะ ไม่หายแม้แต่ครั้งเดียว
```

ตัวเลข**หายไป 64.69%**! มาดูว่าทำไม: `g_counter++` ดูเหมือนคำสั่งเดียว แต่จริง ๆ ประกอบด้วย **สามจังหวะ** — (1) อ่านค่าปัจจุบัน (2) บวก 1 (3) เขียนกลับ · สมมติทั้งสองเธรดอ่านค่า 100 พร้อมกัน แล้วต่างบวกเป็น 101 แล้วเขียนกลับ 101 กลับคืน **ทั้งคู่เขียนค่าเดิม** — หนึ่งในสองครั้งนั้น "หายไป" (เรียกว่า **lost update** = การอัปเดตที่ถูกทับจนหาย)

ข้อควรรู้สองข้อที่มือใหม่ต้องจำแม่น:

1. **`volatile` ไม่ช่วยกัน data race** — `volatile` แค่บอกคอมไพเลอร์ว่า "ห้ามแคชค่านี้ไว้ในรีจิสเตอร์ ให้อ่านจากหน่วยความจำจริงทุกครั้ง" แต่มัน**ไม่ได้กันจังหวะ**ระหว่าง CPU/เธรดเลย · ความเชื่อผิด ๆ ว่า "เติม volatile แล้วปลอดภัย" เป็นบั๊กยอดฮิต
2. **`_Atomic`** (มีใน C11 ขึ้นไป) = บอกให้ฮาร์ดแวร์จัดการ "บวกครั้งเดียวแบบห้ามแทรกกลางคัน" (atomic = หน่วยย่อยที่แยกไม่ได้ · คำสั่งนี้ CPU ทำจบในจังหวะเดียว ไม่มีใครแทรก) · `memory_order_relaxed` = "ไม่ต้องจัดลำดับกับการเข้าถึงหน่วยความจำอื่น ขอแค่บวกไม่หาย" ซึ่งพอดีกับกรณีนี้

(ตัวเลือกกัน race ที่พบบ่อย: mutex สำหรับโค้ดหลายบรรทัดที่ต้องถือสิทธิ์ทั้งก้อน · `_Atomic` สำหรับค่าตัวเดียวที่แค่บวก/สลับ · ส่วน `volatile` ไม่ใช่เครื่องมือกัน race เลย — ใช้กับ register ที่ hardware เปลี่ยนค่าเองเท่านั้น)

## 5. ลงมือทำ 3: วัดราคา context switch จริง (ภาพที่ 2)

พอมีหลายงานแย่ง CPU กัน เคอร์เนลต้อง**สลับงาน** (context switch) เป็นระยะ ๆ คราวนี้มาวัดว่าราคาจริงเท่าไร — และ "การสลับระหว่างโปรเซส" แพงกว่า "การสลับระหว่างเธรด" หรือเปล่า

![ขั้นตอนของ context switch จาก user mode เข้า kernel แล้วกลับออกมา พร้อมราคาที่วัดได้จริง](/assets/diagrams/ep18-02-context-switch.svg)

ภาพที่ 2 แสดง 6 จังหวะของ context switch หนึ่งครั้ง: โปรแกรมเราวิ่งใน user mode → ทำ syscall (เช่น `read`) เพื่อขอเข้าเคอร์เนล → เคอร์เนลบันทึก context (ค่ารีจิสเตอร์ + ตำแหน่งที่กำลังทำ) ของงานเรา → ตัวจัดคิวเลือกงานถัดไปจากคิวที่พร้อมรัน → ถ้าเป็นโปรเซสอื่น ต้อง**สลับ page table** (ตารางแปลที่อยู่ปลอม→จริงของแต่ละโปรเซส · นี่คือของแพงที่เธรดไม่ต้องจ่าย) → กลับ user mode ให้งานใหม่ทำงานต่อ

โค้ด `ctxswitch_demo.c` วัดด้วยวิธี "ปิงปอง": สองฝั่ง (โปรเซสแม่-ลูก หรือ สองเธรด) ผลัดกันเขียน 1 ไบต์ให้อีกฝั่ง แล้วรออ่านคำตอบ — หนึ่งรอบไป-กลับ = สลับงาน 2 ครั้ง:

```
== วัดราคา context switch: process, 20000 รอบ ==
โหมด process: 20000 รอบ ใช้เวลา 0.088 วินาที
  ต่อ 1 รอบ (ไป-กลับ = สลับงาน 2 ครั้ง) = 4402 ns
  ต่อ 1 ครั้งที่สลับงาน               = 2201 ns (2.20 µs)
  โปรเซสแม่: voluntary_ctxt_switches=18345  nonvoluntary_ctxt_switches=1652

== วัดราคา context switch: thread, 20000 รอบ ==
โหมด thread : 20000 รอบ ใช้เวลา 0.085 วินาที
  ต่อ 1 รอบ (ไป-กลับ = สลับงาน 2 ครั้ง) = 4226 ns
  ต่อ 1 ครั้งที่สลับงาน               = 2113 ns (2.11 µs)
  เธรดหลัก: voluntary_ctxt_switches=17593  nonvoluntary_ctxt_switches=2406

== syscall เปล่า ๆ (getppid) 1000000 ครั้ง ==
syscall เปล่า ๆ (getppid) 1000000 ครั้ง ใช้เวลา 0.178 วินาที = 178 ns ต่อครั้ง
```

(หน่วย ns = นาโนวินาที = หนึ่งในพันล้านของวินาที · µs = ไมโครวินาที = หนึ่งในล้านของวินาที)

ตัวเลขบอกอะไรเราบ้าง:

1. **การสลับงานหนึ่งครั้ง ≈ 2.1–2.2 µs** บนเครื่องเรา — ฟังดูน้อย แต่จำไว้: ถ้าตัวจัดคิวสลับงานทุก 2.1 ms (ค่า time slice จริง ดูหัวข้อ 6) จะเสีย CPU ราว **0.1% ไปกับการสลับงานล้วน ๆ** และยิ่งงานแย่งกันมาก ยิ่งสลับถี่ ยิ่งเสียมาก
2. **โปรเซส (2201 ns) กับเธรด (2113 ns) ต่างกันแค่ ~4%** — ตรงนี้ต้องพูดตรง ๆ: ไมโครเบนช์มาร์กนี้**วัดราคา "การสลับ page table" แยกออกมาไม่ได้** เพราะราคาส่วนใหญ่ (178 ns × 4 syscall ต่อรอบ) ถูกกลบด้วยราคา syscall และการปลุกงาน · ต้นทุนจริงของ "การสลับ address space" ไม่ได้อยู่ที่จังหวะสลับ แต่อยู่ที่**หลังจากสลับแล้ว** — cache (หน่วยความจำเร็วใน CPU) และ TLB (ตารางแปลที่อยู่ที่ CPU เก็บไว้กันเอง) จะถูกทำให้ "เย็น" ต้องโหลดใหม่ ซึ่งจะไปโผล่เป็นความช้าตอนงานทำงานต่อ (เราจะเห็นของพวกนี้ชัดขึ้นในตอน virtual memory)
3. **voluntary vs nonvoluntary** — `voluntary_ctxt_switches` = จำนวนครั้งที่งาน**ยอมปล่อย CPU เอง** (เช่นไปนอนรอ, รออ่านไฟล์) · `nonvoluntary_ctxt_switches` = จำนวนครั้งที่**ถูกเคอร์เนลยึด CPU คืน** (time slice หมด / มีงานสำคัญกว่า) · สังเกตว่าปิงปองเป็น voluntary เกือบหมด (~18,000) เพราะแต่ละฝั่ง "รออ่าน" ตลอด

ประเด็นที่ฝังในตัวเลข: **งานของเราไม่เคยวิ่งต่อเนื่อง** — มันถูกสลับเข้า-ออกนับครั้งไม่ถ้วนตลอดอายุขัย ซึ่งนำไปสู่คำถามต่อไป: ใครเป็นคนตัดสินว่าเมื่อไรต้องสลับ?

## 6. ลงมือทำ 4: ตัวจัดคิวแบ่ง CPU ให้ยังไง (ภาพที่ 3)

ตัวจัดคิว (scheduler) คือโค้ดในเคอร์เนลที่ตอบคำถาม "ต่อไปใครได้ CPU" ลองดูว่าตัวเราถูกจัดคิวยังไงก่อน (`sched_demo info`):

```
== ตัวจัดคิว: โปรเซสนี้ถูกจัดคิวยังไง ==
PID = 2444040   TID ของเธรดหลัก = 2444040  (เท่ากันเสมอ: เธรดหลักคือโปรเซส)
นโยบาย (policy) = SCHED_OTHER (ชื่อจริงในเคอร์เนล: SCHED_NORMAL — ตัวจัดคิวแบบ fair)  รหัส 0
ลำดับความสำคัญในนโยบายนี้ = 0  (ช่วงที่รองรับ 0..0)
nice = 0  (ตั้งแต่ -20 = สำคัญสุด ถึง +19 = ยอมคนอื่นสุด)
CPU ที่อนุญาตให้ใช้ = 0 1 2 3
กำลังรันอยู่บน cpu 2 จากทั้งหมด 4 ตัว
```

ข้อเท็จจริงที่ควรรู้ (ยืนยันจากเคอร์เนลของเครื่องเรา ไม่ได้ยกมาจากตำรา):

- **นโยบาย (policy)**: โปรเซสปกติใช้ `SCHED_OTHER` (เคอร์เนลเรียก `SCHED_NORMAL`) ซึ่งเป็นตัวจัดคิวแบบ **"fair"** (ยุติธรรม — พยายามแบ่ง CPU ให้ทุกงานเท่า ๆ กัน) · ยังมีนโยบาย real-time (`SCHED_FIFO`/`SCHED_RR`) สำหรับงานที่ต้องตอบสนองแม่นยำระดับไมโครวินาที แต่คนธรรมดาไม่ต้องใช้ (และต้องใช้สิทธิ์ root)
- **nice** = ค่าความสำคัญของงาน · จาก -20 (สำคัญสุด) ถึง +19 (ยอมคนอื่นสุด) · ค่าเริ่มต้นคือ 0 · ยิ่ง nice **ต่ำ** = สำคัญ**มาก** (ชื่อ "nice" มาจาก "ความใจดี" — ยิ่งใจดี ยิ่งยอมให้คนอื่นไปก่อน)
- **อัลกอริทึมจริงบนเครื่องเรา**: ตั้งแต่ Linux 6.6 เป็นต้นมา ตัวจัดคิวหลักเปลี่ยนจาก **CFS** (Completely Fair Scheduler ตัวเก่าที่ใช้มากว่าทศวรรษ) เป็น **EEVDF** (Earliest Eligible Virtual Deadline First) — เราเห็นได้จาก `/sys/kernel/debug/sched/features` ที่มีชุดกลไก `PLACE_LAG`, `PLACE_DEADLINE_INITIAL`, `RUN_TO_PARITY` ซึ่งเป็นของ EEVDF · สาระสำคัญที่มือใหม่ต้องรู้เหมือนกันหมด: ตัวจัดคิวให้งานที่มีสิทธิ์น้อยที่สุด (ใช้ CPU ไปน้อยที่สุด) วิ่งก่อน เพื่อให้ระยะยาวทุกงานได้ส่วนแบ่งเท่ากัน
- **time slice จริง** = 2.1 ms (`/sys/kernel/debug/sched/base_slice_ns` = 2100000 ns) · และ tick (สัญญาณนาฬิกาที่เคอร์เนลใช้เช็ค "ควรสลับงานไหม") มาทุก 4 ms (`CONFIG_HZ=250`)

### 6.1 ทดลอง: 8 งานแย่ง 4 CPU — ยุติธรรมแค่ไหน

ภาพที่ 3 แสดงผลจริงจากการปล่อยงานที่ "คิดเลขล้วน ๆ" (CPU-bound = งานที่กินแต่ CPU ไม่รอ I/O) 8 ตัววิ่งพร้อมกัน 1.5 วินาทีบนเครื่อง 4 แกน แล้วนับว่าแต่ละงานได้ทำงานไปกี่หน่วย (งานเดียววิ่งคนเดียว = ฐาน 100%):

![ผลการแบ่ง CPU ของตัวจัดคิว: 8 งานบน 4 CPU และผลของค่า nice พร้อมค่าที่วัดได้จริง](/assets/diagrams/ep18-03-scheduler-fairness-nice.svg)

ผลสำคัญ:

```
== ทดลองที่ 2: งานแบบเดียวกัน 8 ตัว วิ่งพร้อมกัน 1500 ms (เครื่องมี 4 CPU) ==
งานที่ 0: 123670000 หน่วยงาน =  49.9% ของงานเดียว (cpu 2)
งานที่ 1: 139982000 หน่วยงาน =  56.5% ของงานเดียว (cpu 1)
งานที่ 2:  86674000 หน่วยงาน =  35.0% ของงานเดียว (cpu 1)
...
รวมทุกงาน       = 887364000 หน่วย = 358.2% ของงานเดียว
งานที่ได้มากสุด ÷ งานที่ได้น้อยสุด = 1.619  (1.000 = แบ่งเท่ากันเป๊ะ)
context switch ทั้งระบบระหว่างทดลองที่ 2 = 10571 ครั้ง
```

อ่านผลได้สองชั้น:

1. **รวมได้ 358.2% ไม่ใช่ 400%** — อุดมคติคือ 8 งานบน 4 CPU ควรได้รวม 400% ของงานเดียว (4 CPU ทำงานเต็ม 4 × 100%) แต่ได้แค่ 358% · ที่หายไปคือ **overhead** (ต้นทุนแฝง) ของการสลับงาน 10,571 ครั้ง + การแย่ง cache ระหว่างงาน
2. **อัตราส่วน 1.619 ไม่ใช่ 1.000** — แปลว่ายังแบ่งไม่เท่ากันเป๊ะ บางงานได้ 56.5% บางงานได้แค่ 35% · สาเหตุหลัก (เห็นในภาพที่ 3): งานถูกวางไว้คนละ CPU ตั้งแต่ตอน `fork()` และ **การย้ายงานข้าม CPU มีต้นทุน** (`migration_cost_ns` = 500,000 ns) ตัวจัดคิวเลยลังเลที่จะย้ายงานออกจาก CPU ที่วุ่นวาย

บทเรียนสำคัญสำหรับวิศวกร: **"fair" ไม่ได้แปลว่า "เท่ากันทุกวินาที"** — มันแปลว่า "เท่ากันในระยะยาว" ช่วงสั้น ๆ ความเหลื่อมล้ำแบบนี้เป็นเรื่องปกติของระบบจริง

### 6.2 nice มีผลจริงแค่ไหน

คราวนี้ลองให้สองงานมีค่า nice ต่างกัน แล้ว**บังคับให้แย่งกันบน CPU ตัวเดียว** (ถ้าไม่บังคับ ตัวจัดคิวจะวางคนละ CPU แล้วทั้งคู่ได้ CPU เต็มตัว — nice จะดูเหมือน "ไม่มีผล"):

```
== ทดลอง: งาน 2 ตัว nice ต่างกัน 10 หน่วย วิ่ง 1500 ms (ปักหมุด cpu 0) ==
งาน nice +0 : 228098000 หน่วยงาน
งาน nice +10 :  24500000 หน่วยงาน
CPU ที่งาน nice +0 ได้ =  90.3%  (ทฤษฎี 90.3%)
อัตราส่วนที่วัดได้ (nice +0 ÷ nice +10) = 9.31 เท่า · ทฤษฎี 9.31 เท่า

== ทดลอง: งาน 2 ตัว nice ต่างกัน 5 หน่วย (ปักหมุด cpu 0) ==
งาน nice +0 : 184798000 หน่วยงาน
งาน nice +5 :  60790000 หน่วยงาน
CPU ที่งาน nice +0 ได้ =  75.2%  (ทฤษฎี 75.3%)
อัตราส่วนที่วัดได้ (nice +0 ÷ nice +5) = 3.04 เท่า · ทฤษฎี 3.05 เท่า
```

สวยงาม: **ผลวัดตรงกับทฤษฎีแทบทุกทศนิยม** — nice ต่างกัน 1 หน่วย = ได้ CPU ต่างกัน **1.25 เท่า** (เอกสาร `man 7 sched` ของ Linux ระบุไว้) · ต่าง 5 หน่วย = 1.25⁵ ≈ 3.05 เท่า · ต่าง 10 หน่วย = 1.25¹⁰ ≈ 9.31 เท่า

(นอกจากนี้ `sched_demo nice-self` ยังพิสูจน์ข้อเท็จจริงอีกข้อ: บน Linux ค่า nice **เป็นของแต่ละเธรด** ไม่ใช่ของทั้งโปรเซส — เธรดใหม่สืบทอดค่า ณ ตอนสร้าง แต่เปลี่ยนของใครของมันได้)

### 6.3 preemptive: เคอร์เนลตัดกลางคันได้เสมอ

คำถามสุดท้าย: ถ้ามีงาน CPU-bound 8 ตัววิ่งเต็ม 4 CPU แล้วมีโปรเซสนึง "ขอนอน 1 ms" เคอร์เนลจะปลุกมันได้ทันไหม? นี่คือหัวใจของคำว่า **preemptive** (ตัดกลางคันได้):

```
== ทดลอง: มี 8 งานใช้ CPU ล้วนแย่งกันบน 4 CPU ==
ไม่มีการแย่ง CPU : ตื่น 1000 ครั้ง เฉลี่ยช้า 53.8 µs  แย่สุด 335.1 µs
มีงาน 8 ตัวแย่ง : ตื่น 1000 ครั้ง เฉลี่ยช้า 160.5 µs  แย่สุด 12136.1 µs
```

ผลชัดเจน: ถึงจะมีงานเต็มทุก CPU เคอร์เนลก็ยัง**ปลุกงานที่ขอนอนได้** (เฉลี่ยช้า 160 µs แย่สุด 12 ms) — เพราะเคอร์เนลมีสิทธิ์**ยึด CPU คืนจากงานที่กำลังวิ่ง**ได้ทุกเมื่อ (ไม่ต้องรอให้งานนั้น "ยอมปล่อย" เอง) · นี่คือเหตุผลที่ OS ยุคใหม่ตอบสนองได้ลื่นแม้ CPU ทำงานหนัก — และเป็นสิ่งที่ `CONFIG_PREEMPT=y` ในเคอร์เนลเครื่องเรารับประกันไว้

## 7. เธรดของ OS กับ goroutine ของ Go — ของแพง vs ของถูก

หัวข้อที่แล้วเรียน Go มาตั้งแต่ตอนที่ 3 คราวนี้กลับมาใช้มันตอบคำถามที่สำคัญมาก: **เธรด OS หนึ่งตัวแพงแค่ไหน** และ Go กับ C สร้างงานพร้อมกันเยอะ ๆ ได้ต่างกันยังไง

`spawn_many.c` พยายามสร้างเธรดจริง (OS thread) ให้ได้ 10,000 ตัว แล้วดูว่าหน่วยความจำพองแค่ไหน:

```
$ ./spawn_many 1000 0 1500      # 1000 เธรด stack เริ่มต้น
สร้างสำเร็จครบ 1000 เธรด
  VmSize:  8258720 kB   ← พื้นที่เสมือนที่จองไว้ (8.2 GB!)
  VmRSS:     17808 kB   ← หน่วยความจำจริงที่ใช้ (17.8 MB)
  Threads: 1001

$ ./spawn_many 10000 0 1500     # ลอง 10000 เธรด
สร้างได้จริง 9601 เธรด แล้วตัวที่ 9602 ล้มเหลว: Resource temporarily unavailable
  VmRSS:    157936 kB
  Threads: 9602
```

สองประเด็น:

1. **1000 เธรดจองพื้นที่เสมือน 8.2 GB** (VmSize) — เพราะแต่ละเธรดจอง stack เริ่มต้นไว้ 8 MB (`ulimit -s` = 8192 KB) · แต่ใช้จริงแค่ 17.8 MB (VmRSS = Resident Set Size = หน่วยความจำจริงที่แตะถึง) · ที่อยู่เสมือนจองถูก หน่วยความจำจริงจ่ายตามที่ใช้จริง (หลักการ virtual memory อีกแล้ว)
2. **สร้างได้ไม่ถึง 10,000 — ตันที่ 9,601 ตัว** แล้วได้ error `Resource temporarily unavailable` (EAGAIN = ทรัพยากรหมดชั่วคราว) · เหตุผลไม่ใช่เพราะภาษา C แต่อย่างใด แต่เป็น **เพดาน cgroup** (cgroup = กลไกจำกัดทรัพยากรของ Linux · ระบบรันงานของเราตั้ง `pids.max` = 9626) · บทเรียน: ขีดจำกัดของระบบมักมาจากนโยบายที่ตั้งไว้ ไม่ใช่ข้อจำกัดของภาษา

เทียบกับ Go (`go_threads/main.go`) ที่สร้าง **goroutine** (goroutine = งานขนาดเบาที่ Go runtime จัดคิวเองบนเธรด OS ไม่กี่ตัว ไม่ใช่เธรด OS หนึ่งต่อหนึ่ง):

```
$ ./go_threads 1000 1500
goroutine ที่ยังมีชีวิต = 1001
heap ที่ Go จองอยู่ (HeapAlloc) = 0.7 MB
  VmRSS:    5808 kB
  Threads: 6          ← เธรด OS จริงมีแค่ 6 ตัว!

$ ./go_threads 10000 1500
goroutine ที่ยังมีชีวิต = 10001
heap ที่ Go จองอยู่ = 5.9 MB
  VmRSS:   29376 kB
  Threads: 7

$ ./go_threads 100000 1500
goroutine ที่ยังมีชีวิต = 100001
heap ที่ Go จองอยู่ = 56.8 MB
  VmRSS:  264880 kB
  Threads: 7          ← ยังแค่ 7 ตัว ทั้งที่มี goroutine แสนตัว!
```

นี่คือเหตุผลที่ Go ขึ้นชื่อเรื่อง concurrency (การทำงานหลายอย่างพร้อมกัน): **goroutine แสนตัวใช้เธรด OS แค่ 7 ตัว** — Go runtime มีตัวจัดคิวของตัวเองที่เอา goroutine ไปวางบนเธรด OS ไม่กี่ตัว · goroutine ตัวหนึ่งเริ่มต้นด้วย stack แค่ ~2 KB และโตได้ตามต้องการ (เทียบกับเธรด OS ที่จอง 8 MB ต่อตัว) · จึงสร้างได้เป็นแสนโดยไม่ระเบิดหน่วยความจำ · (ตอนที่ 31 เราจะกลับมาลงลึก GC/runtime ของ Go เอง)

แต่อย่าลืมว่า goroutine ก็ยังเป็น "สายงานที่แชร์หน่วยความจำ" — **data race ในหัวข้อ 4 เกิดกับ Go ได้เหมือนกัน** (Go มีเครื่องมือ `go run -race` ไว้ตรวจจับ) · goroutine ทำให้งาน "ถูก" ไม่ได้ทำให้งาน "ปลอดภัย" โดยอัตโนมัติ

## 8. สรุปสิ่งที่ได้เรียนรู้

1. **โปรเซส = คนละบ้าน** (แยก address space, แยกหน่วยความจำ) · **เธรด = ห้องในบ้านเดียวกัน** (แชร์หน่วยความจำ, แชร์ code/heap/ไฟล์) — `fork()` คัดลอกทั้งบ้าน, `pthread_create` แค่เพิ่มห้อง
2. **เคอร์เนลมองทุกอย่างเป็น task** — โปรเซสคือ "กลุ่ม task" ที่มี Tgid เดียวกัน · เธรดหลักมี TID = PID
3. **การแชร์หน่วยความจำ = ดาบสองคม** — ต้องมี mutex/atomic กัน data race ไม่งั้นตัวเลขหาย 64.69% เหมือนที่เราเห็น · `volatile` **ไม่ช่วย**
4. **context switch ราคา ~2.1–2.2 µs/ครั้ง** บนเครื่องเรา — ดูน้อย แต่สะสมเป็น overhead ใหญ่เมื่องานแย่งกันเยอะ
5. **ตัวจัดคิว (EEVDF บน Linux 6.6+) แบ่ง CPU "ยุติธรรมในระยะยาว"** · `nice` ต่าง 1 = ต่าง 1.25 เท่า (ยืนยันด้วยผลวัดจริง) · เคอร์เนล preemptive ตัดกลางคันได้เสมอ จึงตอบสนองลื่น
6. **เธรด OS แพง (8 MB stack/ตัว, ตันที่ 9,601 ตัวด้วยเพดาน cgroup) · goroutine ถูก (แสนตัวบนเธรด 7 ตัว)**

### ระดับ Mini-Project (ประกอบความรู้)

**เขียน "เครื่องนับคำ" แบบคู่ขนาน** — อ่านไฟล์ข้อความ 1 ไฟล์ แบ่งเนื้อหาออกเป็น 4 ส่วนเท่า ๆ กัน (ตามจำนวนบรรทัด) แล้วสร้าง 4 เธรด แต่ละเธรดนับจำนวนคำในส่วนของตัวเอง แล้วรวมผลด้วย mutex

- ข้อกำหนด: ต้องใช้ `pthread_create` + `pthread_join` + mutex · ผลรวมต้องเท่ากับการนับด้วยโปรแกรมแบบเธรดเดียวเป๊ะทุกครั้ง
- ทดสอบ: สร้างไฟล์ทดสอบ 100,000 บรรทัด (ใช้คำสั่ง `yes "hello world this is a test" | head -100000 > big.txt`) แล้วนับทั้งสองวิธี
- โบนัส: ลอง**ไม่ใช้ mutex** (ให้แต่ละเธรดเขียนผลใส่ช่องของตัวเองในอาร์เรย์ แล้วค่อยรวมตอนท้าย) — อธิบายว่าทำไมแบบนี้ไม่ต้องล็อกเลย (หลักการ "แบ่งงานให้ไม่ต้องแชร์" = ดีที่สุด)

## 10. คำเตือนตามกาลเวลา + แหล่งอ้างอิง

**As of กันยายน 2026** — ข้อเท็จจริงทั้งหมดในบทนี้ยืนยันจากการรันจริงบน Raspberry Pi 5 (Linux 6.18.39+rpt-rpi-2712 aarch64, GCC 14.2.0, glibc 2.41, Go 1.24.4) ตัวจัดคิวหลักคือ **EEVDF** (แทน CFS ตั้งแต่ Linux 6.6) · ค่าคงที่ที่อ้างถึง (base_slice_ns = 2.1 ms, CONFIG_HZ = 250, pids.max = 9626, nice ต่าง 1 = 1.25 เท่า) เป็นค่าของ**เคอร์เนลรุ่นนี้บนเครื่องนี้** — เคอร์เนลรุ่นถัดไปหรือ distro อื่นอาจปรับค่าเหล่านี้ได้ จึงควรตรวจจากแหล่งปัจจุบันเสมอ (เช่น `man 7 sched`, เอกสาร kernel.org, หรือลองรันเองตามโค้ดใน `course/code/ep18/`)

แนวคิดเรื่อง process/thread/scheduling อาจถูกท้าทายได้ในอนาคต (เช่น รูปแบบของ CPU แบบ heterogeneous, ตัวจัดคิวรุ่นใหม่ หรือ model ของงานที่เปลี่ยนไป) — จุดที่ไม่เปลี่ยนคือ**หลักการ**: แยกงานยังไงให้ถูก, จัดคิวให้ยุติธรรมยังไง, และจ่ายราคาการสลับงานอย่างรู้ตัว

**แหล่งอ้างอิงหลัก**: เอกสาร Linux `man 7 sched` (nice weight และ policy) · `man 2 fork` / `man 2 clone` · `man 7 pthreads` · เอกสาร kernel.org เรื่อง scheduler/EEVDF (merged Linux 6.6) · เอกสาร Go runtime (GOMAXPROCS และ goroutine scheduling)
