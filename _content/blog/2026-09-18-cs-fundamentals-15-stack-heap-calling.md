# stack vs heap + calling convention: เกิดอะไรขึ้นตอนเรียกฟังก์ชัน (ตอนที่ 15) — CS Fundamentals: จาก 0 สู่พื้นฐานที่แท้จริง

สองคำถามที่เราทิ้งไว้ค้างตอนที่แล้ว (ตอนที่ 14 เรื่อง pointer + array) มีดังนี้

1. ตัวแปรแต่ละตัว "อยู่ตรงไหน" ของหน่วยความจำกันแน่ — ทำไม `&local` (ตัวแปรท้องถิ่น) ถึงอยู่คนละช่วงกับ `&main` (ตัวโค้ด) และทำไมตัวแปร `t` กับ `s` จากตอนที่แล้ว (`t` คือ array ท้องถิ่น `char t[]`, `s` คือตัวชี้ `const char *s`) ถึงอยู่คนละช่วงกัน
2. เวลาส่ง argument (ข้อมูลที่ส่งเข้าไปในฟังก์ชัน) ไปให้ฟังก์ชัน มัน "เดินทาง" ยังไง — ทำไมบางอย่างถูกคัดลอกค่าให้ บางอย่างถูกส่งเป็น address

ตอนนี้เราจะเปิดฝาหน่วยความจำดูของจริง แล้วจะเจอศัพท์สามคำที่อยู่ในปากวิศวกรทุกคน: **stack**, **heap** และ **calling convention** (ธรรมเนียมการเรียกฟังก์ชัน)

## 1. แผนที่หน่วยความจำของโปรแกรม (ภาพที่ 1)

ก่อนหน้านี้เราเห็น address สองแบบวิ่งไปมา: `0x7fff...` กับ `0x5555...` (ตัวเลขฐานสิบหกที่ระบุตำแหน่งในหน่วยความจำ — เราเรียนเลขฐานสิบหกไปแล้วในตอน 8) วันนี้เราจะปะติดภาพเต็ม ๆ ว่าโปรแกรมหนึ่งตัว หน่วยความจำ (memory = ที่เก็บข้อมูลที่โปรแกรมเข้าถึงได้) ถูกแบ่งเป็น 4 ส่วนหลัก ๆ (stack, heap, data, text) บวกกับช่องว่างตรงกลางคั่นระหว่างสองส่วนบนกับสองส่วนล่าง

![พื้นที่หน่วยความจำของโปรแกรม 4 ส่วน: stack บนสุด ลงมาถึง text ล่างสุด](/assets/diagrams/ep15-01-memory-layout.svg)

ไล่จาก **address สูง** (ตัวเลขมาก) ลงมาที่ **address ต่ำ** (ตัวเลขน้อย) ตามผลรันจริงของเครื่องเรา:

1. **stack** — อยู่บนสุด address สูง (`0x7fff...`) เก็บตัวแปรท้องถิ่น (ตัวแปรที่ประกาศไว้ข้างในฟังก์ชัน) และข้อมูลชั่วคราวของการเรียกฟังก์ชัน โต **ลง** (↓) ไปทาง address ต่ำ

   *(ช่องว่างตรงกลาง — ไม่ใช่ส่วนของโปรแกรม)* ระหว่าง stack กับ heap ห่างกันประมาณ **42.7 เทระไบต์** (≈ 47 ล้านล้านไบต์) ตัวเลขนี้เป็น "โลกเสมือน" ของโปรแกรม ไม่ใช่ RAM จริง (RAM = หน่วยความจำจริงของเครื่อง) — เกิดจากกลไก virtual memory (การที่โปรแกรมเห็นหน่วยความจำเป็นพื้นที่ใหญ่สมมติ) ที่เราจะลงลึกในตอน 20

2. **heap** — อยู่ต่ำลงมา (`0x5555...`) เนื้อที่ที่เราขอเพิ่มตอนโปรแกรมรันได้ด้วย `malloc` และคืนด้วย `free` โต **ขึ้น** (↑) ไปทาง address สูง
3. **data** — ตัวแปร global (ตัวแปรที่ประกาศไว้ข้างนอกสุดของทุกฟังก์ชัน) เช่นตัวแปร `base` ในโปรแกรมข้างล่าง
4. **text** — ตัวโค้ดโปรแกรมที่รันอยู่จริง (ฟังก์ชัน `main`, `foo`, `bar` เป็นคำสั่งที่วางอยู่ที่นี่ อ่านได้อย่างเดียว แก้ไม่ได้)

**ทำไมต้องจำ layout นี้** — เพราะ "ตัวแปรอยู่ตรงไหน" ตัดสิน "ตัวแปรมีอายุแค่ไหน" และ "ใครเป็นคนดูแลมัน" ซึ่งเป็นหัวใจของตอนนี้ทั้งหมด

> **หมายเหตุ** ลำดับบน-ล่างนี้เป็นภาพรวมของ **Linux บนเครื่อง 64 บิต** ทั่วไป ไม่ใช่กฎตายตัวของทุกระบบปฏิบัติการหรือทุกสถาปัตยกรรม (เช่น บางระบบที่ฝังตัวเล็ก ๆ ไม่มี virtual memory เลย) — แต่หลักการ "stack โตลง, heap โตขึ้น, คนละที่กัน" เป็นจริงแทบทุกที่

## 2. stack: ที่พักชั่วคราวของตัวแปรท้องถิ่น

**stack** (กองซ้อน) คือพื้นที่ที่โปรแกรมใช้เก็บ "ตัวแปรท้องถิ่น" ของฟังก์ชันที่กำลังทำงานอยู่ มันทำงานแบบ **LIFO** (Last-In-First-Out = อันที่เข้ามาทีหลังออกก่อน เหมือนกองจาน: วางจานทับกัน อันบนสุดถูกหยิบก่อนเสมอ)

เขียนโปรแกรมตัวแรก `stack_frame.c` เพื่อดูว่าแต่ละฟังก์ชัน "ได้พื้นที่ของตัวเอง" จริงไหม (โปรแกรมเต็มอยู่ใน `course/code/ep15/stack_frame.c`):

> โปรแกรมนี้ใช้ตัวช่วยสองอย่างที่ไม่ได้แสดงตรงนี้: ฟังก์ชัน `report(ชื่อ, ป้าย, address)` = ฟังก์ชันที่พิมพ์ป้ายกำกับ + address พร้อมระยะห่างจาก `main_local` และตัวแปร `base` = ตัวแปร global (ประกาศบนสุดของไฟล์) ที่ใช้จด address ของ `main_local` ไว้เป็นจุดอ้างอิง 0 — ทั้งคู่มีครบในไฟล์เต็ม

```c
/* ... ส่วนบนตัดออก: #include <stdio.h>, <stdint.h>, static uintptr_t base, ฟังก์ชัน report() ... */

static void bar(int b)
{
    int bar_local = b * 2;
    printf("[bar] ถูกเรียกแล้ว — ตัวแปรของเราอยู่คนละช่วงกับของ foo\n");
    report("bar", "&b (ตัวรับค่า argument)", (void *)&b);
    report("bar", "&bar_local (ตัวแปรท้องถิ่น)", (void *)&bar_local);
}

static void foo(int a)
{
    int foo_local = a + 1;
    report("foo", "&a (ตัวรับค่า argument)", (void *)&a);
    report("foo", "&foo_local (ตัวแปรท้องถิ่น)", (void *)&foo_local);
    bar(a + 10);
}

int main(void)
{
    int main_local = 7;
    base = (uintptr_t)&main_local;   /* จด address ไว้เป็นจุดอ้างอิง 0 */
    report("main", "&main_local (ตัวแปรท้องถิ่น)", (void *)&main_local);
    report("main", "&base (ตัวแปร global/static)", (void *)&base);
    report("main", "&main (ตัวโค้ดของ main)", (void *)(uintptr_t)&main);
    foo(main_local);
    return 0;
}
```

> ศัพท์ที่เพิ่งโผล่ครั้งแรก: `static` = "ให้ฟังก์ชันนี้ใช้ได้เฉพาะในไฟล์นี้" (ไฟล์อื่นเรียกไม่ได้) · `printf` = คำสั่งพิมพ์ข้อความลงจอ · `(void *)` = การแปลงชนิดให้เป็น "pointer แบบไม่ระบุชนิด" (ต้องทำก่อนพิมพ์ address ด้วย `%p`) · `int b` ในวงเล็บ = ตัวรับค่า argument (ตัวแปรที่รับค่าที่ส่งเข้ามา)

> `&ตัวแปร` คือ "เอาที่อยู่ (address) ของตัวแปรนั้นมา" — เราเรียน `&` ไปแล้วในตอน 13–14 ส่วน `uintptr_t` คือชนิดตัวเลขที่เก็บ address ได้เต็ม เอาไว้ลบระยะห่างระหว่าง address ตรง ๆ

คอมไพล์ (compile = แปลโค้ดที่เราเขียนเป็นโปรแกรมที่เครื่องรันได้ ทำโดยโปรแกรมชื่อ compiler — ในที่นี้คือ GCC) และรัน (`gcc -std=c17 -Wall -Wextra -Wpedantic -o stack_frame stack_frame.c && ./stack_frame`) ได้ผลแบบนี้ (address จะต่างกันทุกครั้งที่รัน เพราะกลไก ASLR ที่เราพูดถึงในตอน 13 แต่**ระยะห่าง**เท่าเดิมเสมอ):

```
[main] เริ่มทำงาน
  main  &main_local (ตัวแปรท้องถิ่น) = 0x7ffff1a7854c   (ห่างจาก main_local +0 ไบต์)

ของที่ไม่ได้อยู่บน stack เอามาเทียบให้เห็นว่าคนละช่วง:
  main  &base (ตัวแปร global/static) = 0x5555e95b0050   (ห่างจาก main_local -46909772039420 ไบต์)
  main  &main (ตัวโค้ดของ main) = 0x5555e959097c   (ห่างจาก main_local -46909772168144 ไบต์)

[foo] ถูกเรียกแล้ว — ได้พื้นที่ของตัวเอง
  foo   &a (ตัวรับค่า argument) = 0x7ffff1a7851c   (ห่างจาก main_local -48 ไบต์)
  foo   &foo_local (ตัวแปรท้องถิ่น) = 0x7ffff1a7852c   (ห่างจาก main_local -32 ไบต์)
[bar] ถูกเรียกแล้ว — ตัวแปรของเราอยู่คนละช่วงกับของ foo
  bar   &b (ตัวรับค่า argument) = 0x7ffff1a784ec   (ห่างจาก main_local -96 ไบต์)
  bar   &bar_local (ตัวแปรท้องถิ่น) = 0x7ffff1a784fc   (ห่างจาก main_local -80 ไบต์)
  bar_local = 34
[foo] หลัง bar คืนค่าแล้ว ยังอ่าน foo_local ได้ = 8

[main] foo คืนค่าแล้ว — กลับมาอ่าน main_local = 7
```

อ่านผลลัพธ์ให้เป็น 4 ข้อ:

1. **ตัวแปรท้องถิ่นของแต่ละฟังก์ชันอยู่คนละช่วงกัน** — `main_local` อยู่ที่ +0, ตัวแปรของ `foo` อยู่ที่ -32/-48, ตัวแปรของ `bar` อยู่ที่ -80/-96 คือ "ซ้อนลงไปเรื่อย ๆ" ไม่ปนกัน
2. **stack โตลง** — ตัวแปรของฟังก์ชันที่ถูกเรียกทีหลังมี address **ต่ำกว่า** (ตัวเลขน้อยกว่า) เสมอ ตรงกับลูกศร "โตลง ↓" ในภาพที่ 1
3. **ตัวแปร global กับตัวโค้ดอยู่คนละโลก** — `&base` (global) และ `&main` (โค้ด) อยู่ที่ `0x5555...` ห่างจากตัวแปรท้องถิ่น `0x7fff...` หลายสิบล้านล้านไบต์ — นี่คือรอยต่อระหว่าง stack กับ data/text ในภาพที่ 1
4. **ฟังก์ชันคืนค่าแล้ว ตัวแปรของฟังก์ชันที่เรียกต่อยังอยู่ครบ** — พอ `bar` จบ `foo` ยังอ่าน `foo_local = 8` ได้ พอ `foo` จบ `main` ยังอ่าน `main_local = 7` ได้ (LIFO: หลังสุดออกก่อน อันล่าง ๆ ยังอยู่)

แต่ละกองของพื้นที่ที่ฟังก์ชันหนึ่งได้ เราเรียกว่า **stack frame** (กรอบพื้นที่ของฟังก์ชันบน stack) — ภาพที่ 2 จะวาดให้เห็นชัด

### 2.1 ฟังก์ชันเรียกตัวเอง: เฟรมซ้อนกันเป็นชั้น

ถ้าฟังก์ชันเรียกตัวเอง (เราเรียกการทำแบบนี้ว่า **recursion** = การเรียกตัวเองซ้ำ) แต่ละชั้นก็ได้เฟรมของตัวเองซ้อนลงไปเรื่อย ๆ เขียน `recursion_frames.c` วัดขนาดเฟรม (โปรแกรมเต็มอยู่ใน `course/code/ep15/recursion_frames.c`):

```
เริ่มเรียกจาก main (ชั้นที่ 0) — main ไม่ได้อยู่ในสาย recursion
ชั้นที่ 0: sp = 0x7fffe2b33f70 ( -80 ไบต์)  &local = 0x7fffe2b33fbc ( -40 ไบต์)
ชั้นที่ 1: sp = 0x7fffe2b33f20 ( -80 ไบต์)  &local = 0x7fffe2b33f6c ( -80 ไบต์)
ชั้นที่ 2: sp = 0x7fffe2b33ed0 ( -80 ไบต์)  &local = 0x7fffe2b33f1c ( -80 ไบต์)
...  (ชั้น 3–6 ในทำนองเดียวกัน ตัดออก)
   กลับจากชั้น 6: marker = 601 (ค่าของชั้นนี้ยังอยู่ครบ)
   กลับจากชั้น 0: marker = 1 (ค่าของชั้นนี้ยังอยู่ครบ)
```

เห็นอะไร: **`sp` ของทุกชั้นลดลงเท่ากัน 80 ไบต์เป๊ะ** (ตัวเลขในวงเล็บคือระยะห่างจากชั้นก่อนหน้า) — นั่นคือขนาดเฟรมของฟังก์ชันนี้ และตัวแปรของแต่ละชั้นอยู่ครบแม้ตอน "ไต่กลับขึ้นมา" เพราะเฟรมล่าง ๆ ยังไม่ถูกทับ จนกว่าฟังก์ชันชั้นนั้นจะคืนค่าจริง ๆ (ส่วน `&local` ของชั้นที่ 0 แสดง `-40 ไบต์` เพราะเทียบกับตัวแปร `top` ใน main ซึ่งเป็นจุดอ้างอิงแรก ไม่ใช่เฟรม recursion — คอลัมน์ท้าย `local อยู่สูงกว่า sp 76 ไบต์` ตัดออกเพื่อให้อ่านง่าย)

`sp` (stack pointer = ตัวชี้ตำแหน่งปลายกอง stack) เป็น register (ที่เก็บค่าเล็ก ๆ เร็ว ๆ ใน CPU — เรารู้จัก register จากตอน 11) ที่ชี้ไปยัง "ยอด" ของ stack เสมอ ทุกครั้งที่เรียกฟังก์ชัน `sp` จะถูกดันลง (ตัวเลขลดลง) เพื่อจองเฟรมใหม่

## 3. calling convention: กติกาการเรียกฟังก์ชัน (ภาพที่ 3)

**calling convention** (ธรรมเนียมการเรียกฟังก์ชัน) คือ "ข้อตกลง" ระหว่างโค้ดที่เรียก (caller) กับฟังก์ชันที่ถูกเรียก (callee) ว่าข้อมูลต้องเดินทางยังไง — argument ไปทางไหน ค่าคืนกลับมาทางไหน ใครเป็นคนเก็บ return address (ที่อยู่ของคำสั่งที่ต้องกลับไปหลังจบฟังก์ชัน)

![6 ขั้นตอนของการเรียกฟังก์ชันบน aarch64 ผูกกับ register x0-x7, x30, sp](/assets/diagrams/ep15-03-calling-convention.svg)

หลัก 6 ขั้นตอน (บนเครื่องเรา ซึ่งเป็น CPU แบบ **aarch64** — สถาปัตยกรรมของ ARM 64 บิตที่ Raspberry Pi ใช้):

1. ผู้เรียกใส่ argument ลง **register** `x0`–`x7` (8 ตัวแรก) — ถ้าเกิน 8 ตัว ที่เหลือวางบน stack
2. คำสั่ง `bl func` (branch-with-link) เก็บ **return address** ลง register `x30` แล้วกระโดดไปยังโค้ดของฟังก์ชัน
3. `sub sp, sp, #N` จอง stack frame เผื่อที่ให้ตัวแปรท้องถิ่น (โดย `#N` = จำนวนไบต์ที่จอง เช่นใน `tiny_call.c` จอง 32 ไบต์)
4. ทำงานตามโค้ดในตัวฟังก์ชัน
5. ใส่ค่าคืนลง `x0`
6. `add sp` คืนเฟรม แล้ว `ret` กระโดดกลับตามที่อยู่ใน `x30`

### 3.1 ดู assembly จริง: เรียกฟังก์ชันหนึ่งครั้ง

เขียนโปรแกรมจิ๋วที่สุด `tiny_call.c` แล้วดู assembly (ภาษาแอสเซมบลี = ภาษาระดับต่ำที่ใกล้ภาษาเครื่องที่สุด อ่านยากแต่ตรงกับสิ่งที่ CPU ทำจริง เราเคยเห็นในตอน 12 — ใช้คำสั่ง `gcc -S` ให้ compiler แปลงโค้ดเป็น assembly ให้ดูได้):

```c
int add(int a, int b)
{
    int sum = a + b;
    return sum;
}
int main(void)
{
    int r = add(3, 4);
    return r;
}
```

คอมไพล์ดู assembly ด้วย `gcc -std=c17 -S -O0 -o tiny_call.s tiny_call.c` แล้วเปิดดูส่วนของ `main` (ตัดบรรทัดย่อย ๆ ที่ไม่เกี่ยวกับการเรียกฟังก์ชันออก เหลือ 7 บรรทัดสำคัญ):

```asm
main:
	stp	x29, x30, [sp, -32]!   // จองเฟรม 32 ไบต์ + เก็บ x30 (return address) ไว้
	mov	w1, 4                   // argument ตัวที่ 2 -> register w1
	mov	w0, 3                   // argument ตัวที่ 1 -> register w0
	bl	add                      // branch-with-link: กระโดดไป add + จดทางกลับไว้
	str	w0, [sp, 28]            // ค่าคืน (ใน x0) ไปเก็บที่ตัวแปร r
	ldp	x29, x30, [sp], 32      // คืนเฟรม + คืนค่า x30
	ret                          // กระโดดกลับตาม x30
```

> `w0`/`w1` คือ register เดียวกับ `x0`/`x1` แต่ใช้แค่ครึ่งล่าง 32 บิต (สำหรับ `int`) — ส่วน `//` ใน assembly คือเครื่องหมายคอมเมนต์ (ข้อความอธิบายที่เครื่องข้าม)

จับจุดสำคัญจาก 7 บรรทัดนี้ให้ได้:

- **argument เดินทางผ่าน register** — `mov w1, 4` แล้ว `mov w0, 3` คือการยัดค่า 4 กับ 3 ใส่ register ก่อนเรียก `bl add` (ตรงกับขั้นที่ 1 ในภาพที่ 3)
- **return address ถูกเก็บไว้จริง** — บรรทัด `stp x29, x30, [sp, -32]!` เก็บ `x30` ไว้ในเฟรม และ `bl` เป็นคนเติมค่า return address ลง `x30` ให้ (ตรงกับขั้นที่ 2)
- **ค่าคืนกลับมาทาง `x0`** — หลัง `bl` ค่าก็อยู่ใน `x0` แล้วเอาไปเก็บ (ตรงกับขั้นที่ 5)

### 3.2 พิสูจน์ว่า return address มีอยู่จริง

เขียน `ret_addr.c` ใช้ `__builtin_return_address(0)` (คำสั่งพิเศษของ GCC ที่อ่าน return address ของฟังก์ชันปัจจุบันออกมา) แล้วตรวจว่ามันตกอยู่ใน "ช่วงโค้ดของ `foo`" จริง (โปรแกรมเต็มอยู่ใน `course/code/ep15/ret_addr.c`):

```
[main] &main = 0x555567270874   &foo = 0x5555672707e8   &bar = 0x555567270814
[bar]  return address ที่อ่านได้ = 0x555567270808
[bar]  &bar (โค้ดของ bar เอง)    = 0x555567270814

[main] ช่วงโค้ดของ foo = 0x5555672707e8 ถึง 0x555567270814
[main] return address  = 0x555567270808
[main] อยู่ในช่วงหรือไม่: ใช่ — อยู่ในโค้ดของ foo จริง
```

return address ที่ `bar` อ่านได้คือ `0x...808` ซึ่งอยู่**ในโค้ดของ `foo`** (`0x...7e8` ถึง `0x...814`) — นี่คือหลักฐานว่า "ที่อยู่ของคำสั่งที่ต้องกลับไป" ถูกเก็บไว้จริง ๆ ตอนเรียกฟังก์ชัน และ `ret` จะใช้มันกระโดดกลับ

### 3.3 ถ้า argument เกิน 8 ตัวล่ะ?

เขียน `many_args.c` ส่ง argument 10 ตัว แล้วดู assembly (โปรแกรมเต็มอยู่ใน `course/code/ep15/many_args.c`) — ตัดมาเฉพาะส่วนของ `main`:

```asm
	mov	x0, 10
	str	x0, [sp, 8]      // ตัวที่ 10 วางบน stack
	mov	x0, 9
	str	x0, [sp]         // ตัวที่ 9 วางบน stack
	mov	x7, 8            // ตัวที่ 8 -> x7
	mov	x6, 7
	mov	x5, 6
	mov	x4, 5
	mov	x3, 4
	mov	x2, 3
	mov	x1, 2
	mov	x0, 1            // ตัวที่ 1 -> x0
	bl	sum10
```

เห็นเลย: 8 ตัวแรก (`1`–`8`) ใส่ register `x0`–`x7` ส่วนตัวที่ 9 และ 10 (`9`, `10`) **ถูกวางบน stack** (`str x0, [sp]` = เก็บค่า 9 ลงบน stack) — ตรงกับขั้นที่ 1 ในภาพที่ 3 ทุกประการ

> **แล้วบน x86-64 (เครื่องพีซี/แล็ปท็อปทั่วไป) ล่ะ?** หลักการเหมือนกันเป๊ะ แต่ชื่อ register ต่างกัน: argument ใช้ `rdi, rsi, rdx, rcx, r8, r9` ค่าคืนใช้ `rax` และ return address ถูกวางบน stack (ไม่ใช่ register) — สิ่งที่ต้องจำคือ "มีกติกากลางที่ทุกคนยึดร่วมกัน" ไม่ใช่ชื่อเฉพาะของเครื่องใดเครื่องหนึ่ง

คราวนี้เราเห็นครบแล้วว่า "ตัวแปรท้องถิ่นถูกวางบน stack เฟรมต่อเฟรม" และ "argument เดินทางผ่าน register" เหลือคำถามเดียว: แล้วของที่อยากให้ **อยู่ข้ามการคืนค่าของฟังก์ชัน** (อย่างข้อมูลที่ต้องเก็บไว้ใช้ต่อหลังฟังก์ชันจบ) ล่ะ ต้องไปไว้ไหน — คำตอบคือ heap ในหัวข้อถัดไป

## 4. heap: เนื้อที่ที่เราขอเองได้ (และต้องคืนเอง)

**heap** (กอง) คือพื้นที่ที่โปรแกรมขอเพิ่มตอนรันได้ ด้วยฟังก์ชัน `malloc` (memory allocate = จองหน่วยความจำ) และคืนด้วย `free` ต่างจาก stack ตรงที่ heap **ไม่ถูกจัดการให้อัตโนมัติ** — จองแล้วต้องคืนเอง ไม่งั้นหน่วยความจำ "รั่ว" (memory leak = จองแล้วไม่คืน สะสมจนเปลือง)

เขียน `heap_vs_stack.c` เทียบ stack กับ heap ตรง ๆ (โปรแกรมเต็มอยู่ใน `course/code/ep15/heap_vs_stack.c`):

```c
int main(void)
{
    int local = 1;
    int arr[3] = {10, 20, 30};
    printf("&local  = %p\n", (void *)&local);
    printf("&arr[0] = %p  (ห่างจาก &local %+ld ไบต์)\n", (void *)&arr[0], ...);

    int *h1 = malloc(3 * sizeof *h1);   /* จองจาก heap 3 ช่อง int */
    int *h2 = malloc(3 * sizeof *h2);
    printf("h1 = %p  (ก้อนแรก)\n", (void *)h1);
    printf("h2 = %p  (ห่างจาก h1 %+ld ไบต์ ---> heap เรียงขึ้นด้านบน)\n", ...);
    ...
}
```

ผลรัน (ส่วนสำคัญ):

```
=== 1) ของที่อยู่บน stack ===
&local  = 0x7ffff2eaec5c
&arr[0] = 0x7ffff2eaec50  (ห่างจาก &local -12 ไบต์)

=== 2) ของที่จองเองจาก heap ด้วย malloc ===
h1 = 0x55560ea5a2b0  (ก้อนแรก)
h2 = 0x55560ea5a2d0  (ห่างจาก h1 +32 ไบต์ ---> heap เรียงขึ้นด้านบน)
ที่ขอจริงก้อนละ 3 x 4 = 12 ไบต์ แต่ห่างกัน 32 ไบต์

&local (stack) อยู่ห่างจาก h1 = 46909167585708 ไบต์ ประมาณ 42 เทระไบต์

=== 3) คืนหน่วยความจำ (free) แล้วจองใหม่ ===
หลัง free(h2) แล้ว malloc ขนาดเดิม: h3 = 0x55560ea5a2d0
ได้ที่เดิมหรือไม่: ได้ที่เดิมเป๊ะ

=== 4) อายุ: ของบน heap อยู่ต่อหลังฟังก์ชันคืนค่าได้ ===
  ใน make_on_heap: ตัว pointer a เองอยู่ที่ 0x7ffff2eaec20 (นี่คือที่อยู่ 'บน stack')
  ใน make_on_heap: ข้อมูลที่ a ชี้ไปอยู่ที่ 0x55560ea5a2d0 (นี่คือที่อยู่ 'บน heap')
หลัง make_on_heap คืนค่าแล้ว อ่านได้: 100 101 102
```

อ่านผลลัพธ์ให้เป็น 4 ข้อ:

1. **stack กับ heap คนละฝั่ง** — `&local` (stack) อยู่ `0x7fff...` ส่วน `h1`/`h2` (heap) อยู่ `0x5555...` ห่างกัน ~42 เทระไบต์ (ตรงกับช่องว่างในภาพที่ 1)
2. **heap โตขึ้น** — `h2` อยู่**สูงกว่า** `h1` 32 ไบต์ (ตรงข้ามกับ stack ที่โตลง)
3. **`free` แล้วจองใหม่ขนาดเดิม ได้ที่เดิม** — ระบบจำได้ว่าช่องนั้นว่างแล้ว เอาคืนให้ใช้ต่อ (นี่คือการจัดการของ heap)
4. **ของบน heap อยู่ข้ามการคืนค่าของฟังก์ชันได้** — `make_on_heap` จบไปแล้ว แต่ข้อมูล 100 101 102 ยังอ่านได้ เพราะอยู่บน heap ไม่ได้ตายไปพร้อมเฟรม

### 4.1 กับดัก: pointer ที่ชี้ไปหาของที่ตายแล้ว (dangling pointer)

ทีนี้ลองเทียบดูว่า ถ้าเราทำแบบเดียวกันแต่ใช้ตัวแปรท้องถิ่น (อยู่บน stack) จะเกิดอะไร เขียน `dangling.c` (โปรแกรมเต็มอยู่ใน `course/code/ep15/dangling.c`):

```c
static int *g;             /* ตัวชี้ที่ "จำ" address ของตัวแปรท้องถิ่นไว้ */
static void f(int tag)
{
    int x = tag;           /* x อยู่ในเฟรมของ f — ตายเมื่อ f คืนค่า */
    g = &x;
    printf("  ใน f(%d): &x = %p\n", tag, (void *)&x);
}
```

รันได้ผล:

```
  ใน f(42): &x = 0x7fffe3982a0c
หลังเรียก f(42) : g = 0x7fffe3982a0c  *g = 42  (ยังอ่านได้)
  ใน f(777): &x = 0x7fffe3982a0c
หลังเรียก f(777): g = 0x7fffe3982a0c  *g = 777

อ่านให้ดี: address เดิมเป๊ะ แต่ค่าเปลี่ยนจาก 42 เป็น 777
เพราะเฟรมของ f ถูกจัดวางที่เดิมทุกครั้งที่ถูกเรียก และ x ถูกสร้างใหม่ที่นั่น
=> เราไม่มีสิทธิ์ใช้ pointer นี้ 'ระหว่าง' สองการเรียก — มันชี้ไปที่ของที่ตายแล้ว
```

ที่เห็นคือ **address เดิมเป๊ะ แต่ค่าเปลี่ยน** — เพราะพอ `f` คืนค่า เฟรมของมัน "ตาย" แล้ว แต่ address เดิมถูกนำกลับมาใช้ใหม่ในการเรียกครั้งถัดไป pointer `g` จึงชี้ไปหาของที่ไม่มีเจ้าของแล้ว เราเรียก pointer แบบนี้ว่า **dangling pointer** (pointer ลอย ๆ ชี้ไปหาหน่วยความจำที่คืนไปแล้ว) — เป็นบั๊กอันตรายสุดคลาสสิกใน C

เขียน `dangling_return.c` ให้ผิดแบบตรงไปตรงมา: คืน address ของตัวแปรท้องถิ่นออกจากฟังก์ชัน:

```
dangling_return.c:12:12: warning: function returns address of local variable [-Wreturn-local-addr]
   12 |     return &x;            /* ผิด: x จะตายทันทีที่ฟังก์ชันนี้คืนค่า */
p = (nil)
Segmentation fault
```

คอมไพเลอร์เตือนก่อนเลย (`-Wreturn-local-addr` = "เตือนเมื่อคืน address ของตัวแปรท้องถิ่น") และพอรันจริง โปรแกรม**ตาย** (Segmentation fault = พยายามเข้าถึงหน่วยความจำที่ไม่มีสิทธิ์) — ตรงข้ามกับ heap ที่คืน pointer ออกมาได้อย่างถูกต้อง

**นี่คือแก่นของ stack vs heap**: ของบน stack ตายพร้อมเฟรมฟังก์ชัน (ได้คืนอัตโนมัติ เร็ว แต่ใช้ข้ามการคืนค่าไม่ได้) ส่วนของบน heap อยู่จนกว่าเราจะ `free` (ยืดหยุ่น แต่ต้องจำคืนเอง)

ทีนี้ถ้า stack ถูกจัดการให้อัตโนมัติดีขนาดนี้ ทำไมไม่วางทุกอย่างบน stack ไปเลย? คำตอบคือ stack มีขนาดจำกัด — และนั่นพาเราไปสู่ stack overflow ในหัวข้อถัดไป

## 5. stack มีเพดาน: stack overflow

stack เป็นกองขนาดจำกัด (เคอร์เนล — แกนกลางของระบบปฏิบัติการที่จัดการทรัพยากร — กำหนดขอบเขตไว้) เขียน `big_stack.c` ลองขอ array ใหญ่เกิน (โปรแกรมเต็มอยู่ใน `course/code/ep15/big_stack.c`):

```
ขอบเขต stack ที่ kernel ให้โปรแกรมนี้ = 8.0 เมกะไบต์ (ถามจาก getrlimit)
ลองขอ array 1,000,000 ช่อง = 4,000,000 ไบต์ บน stack:
  ผ่าน: array 3.8 เมกะไบต์ บน stack (a[0] = 1, a[] ตัวสุดท้าย = 2)
ลองขอ array 3,000,000 ช่อง = 12,000,000 ไบต์ บน stack (ขนาดเดียวกับ big_heap.c):
Segmentation fault
```

array 4 เมกะไบต์ยังผ่าน แต่ 12 เมกะไบต์เกินขอบเขต 8 เมกะไบต์ → โปรแกรมตายทันที (นี่คือ **stack overflow** = ใช้ stack เกินขอบเขตที่กำหนด)

> **หมายเหตุเรื่องหน่วย**: โปรแกรมนี้คำนวณ "เมกะไบต์" ด้วยสูตร `sizeof / 1024 / 1024` (คือ 1 เมกะไบต์ = 1,048,576 ไบต์ ระบบฐานสอง) — 4,000,000 ไบต์จึงแสดงเป็น 3.8 เมกะไบต์ และ 12,000,000 ไบต์ = 11.4 เมกะไบต์ ไม่ต้องกังวลกับเศษ ขอแค่จำว่า "4 ล้านไบต์ผ่าน · 12 ล้านไบต์ตาย" ก็พอ · ส่วน `getrlimit` = คำสั่งขอค่าขีดจำกัดจากเคอร์เนล (kernel = แกนกลางของระบบปฏิบัติการที่จัดการทรัพยากร)

เทียบกับ `big_heap.c` ซึ่งขอ array ขนาดเท่ากันเป๊ะ (12 เมกะไบต์) แต่ขอจาก heap:

```
กำลังจะขอ array 3000000 ช่อง = 11.4 เมกะไบต์ จาก heap ด้วย malloc
สำเร็จ: big[0] = 1, big[2999999] = 2
(จำนวนไบต์เท่ากันเป๊ะกับ big_stack.c — ต่างกันแค่ 'ขอจากที่ไหน')
```

**ขนาดเท่ากันเป๊ะ ต่างกันแค่ "ขอจากที่ไหน"** — stack พัง heap สบาย ๆ เพราะ heap โตได้ตามที่ขอ (จำกัดด้วย RAM ของเครื่อง) ขณะที่ stack ถูกจำกัดให้แค่ไม่กี่เมกะไบต์ต่อโปรแกรม

### 5.1 recursion ไม่รู้จบ = stack overflow ภาคปฏิบัติ

เขียน `stack_overflow.c` เรียกตัวเองไม่รู้จบ (โปรแกรมเต็มอยู่ใน `course/code/ep15/stack_overflow.c`):

```
เริ่ม: SP ครั้งแรก = 0x7fffdfd2dfd0
ลึก 0 ชั้น · ใช้ stack ไปแล้ว 304 ไบต์ · เฉลี่ย 304.0 ไบต์ต่อชั้น
ลึก 5000 ชั้น · ใช้ stack ไปแล้ว 1520304 ไบต์ · เฉลี่ย 304.0 ไบต์ต่อชั้น
ลึก 10000 ชั้น · ใช้ stack ไปแล้ว 3040304 ไบต์ · เฉลี่ย 304.0 ไบต์ต่อชั้น
...
ลึก 25000 ชั้น · ใช้ stack ไปแล้ว 7600304 ไบต์ · เฉลี่ย 304.0 ไบต์ต่อชั้น
Segmentation fault
```

แต่ละชั้นกิน 304 ไบต์ พอไต่ไปถึงชั้น ~27,600 ใช้ stack ครบ 8 เมกะไบต์ → ตาย นี่คือเหตุผลว่า **recursion ที่ไม่มีเงื่อนไขหยุด (base case) จะพังเสมอ** — มันขอเฟรมซ้อนไปเรื่อย ๆ จนชนเพดาน stack

> **ทำไม "ลึก 0 ชั้น" ก็ยังใช้ 304 ไบต์** — ตัวเลขนี้วัดระยะห่างจาก SP (stack pointer) เริ่มต้น ถึง SP หลังจองเฟรมแรกแล้ว นั่นคือ "ชั้นที่ 0" ก็คือเฟรมแรกที่จองไปแล้ว (กินไป 304 ไบต์) ไม่ใช่ยังไม่ได้จอง · และตอนคอมไพล์ GCC จะเตือน `warning: infinite recursion detected [-Winfinite-recursion]` — คอมไพเลอร์มองออกเองว่าเราเขียน recursion ไม่รู้จบ เป็นเรื่องปกติของโปรแกรมนี้

### 5.2 heap โตได้เยอะแค่ไหน?

เขียน `heap_size.c` จอง heap ทีละ 8 เมกะไบต์ 8 ครั้ง แล้วให้เคอร์เนลบอกว่าใช้ RAM จริงไปเท่าไร (โปรแกรมเต็มอยู่ใน `course/code/ep15/heap_size.c`):

```
ก่อนจอง      : VmRSS = 1216 kB (หน่วยความจำที่ใช้จริงตอนนี้)
จองแล้ว  1 ก้อน x 8 เมกะไบต์ =   8 เมกะไบต์ : VmRSS = 9616 kB
...
จองแล้ว  8 ก้อน x 8 เมกะไบต์ =  64 เมกะไบต์ : VmRSS = 67072 kB
รวมที่ขอจาก heap = 64 เมกะไบต์ (มากกว่า stack ทั้งก้อนหลายเท่า)
<- โปรแกรมยังไม่ตาย เพราะไม่ได้ใช้ stack เลย
```

จอง heap ได้ 64 เมกะไบต์ (มากกว่า stack ทั้งก้อน 8 เมกะไบต์ถึง 8 เท่า) โปรแกรมยังสบาย ๆ — ยืนยันว่า heap เป็น "เนื้อที่ใหญ่" สำหรับของที่ต้องการพื้นที่มากและอยู่นาน

## 6. เทียบกับ Go: ทำไม Go ยังมีเรื่องนี้ แต่เล่าไม่เหมือนกัน

เราถามมาตลอดว่า "Go ซ่อนอะไรไว้ให้เรา" เรื่อง stack/heap นี่แหละคือคำตอบใหญ่ที่สุด

**เรื่องที่ 1: Go ยอมให้คืน pointer ของตัวแปรท้องถิ่นได้** — เขียน `go_escape.go` (โปรแกรมเต็มอยู่ใน `course/code/ep15/go_escape.go`):

```go
func newPoint(x, y int) *Point {
	p := Point{X: x, Y: y}   // ตัวแปรท้องถิ่นธรรมดา ๆ
	return &p                // แต่เราส่ง address ของมันออกไป
}
```

คอมไพล์ดูคำตัดสินของ compiler ด้วย `go build -gcflags=-m`:

```
./go_escape.go:13:2: moved to heap: p
./go_escape.go:18:15: moved to heap: p
```

ใน C โค้ดแบบนี้คือบั๊ก (segfault ตาม `dangling_return.c`) แต่ Go compiler **เห็นเองว่า** "ตัวแปรนี้ต้องมีชีวิตต่อหลังฟังก์ชันจบ" แล้ว**ย้ายมันขึ้น heap ให้อัตโนมัติ** (เราเรียกกลไกนี้ว่า **escape analysis** = การวิเคราะห์ว่าตัวแปรไหนต้อง "หนี" ออกจากฟังก์ชัน) — นี่คือเหตุผลว่า Go เขียนง่ายกว่าและปลอดภัยกว่าเรื่องหน่วยความจำมาก

**เรื่องที่ 2: Go ปล่อยให้ stack โตได้ ไม่ตายเงียบ ๆ** — เขียน `go_deep_recursion.go` (โปรแกรมเต็มอยู่ใน `course/code/ep15/go_deep_recursion.go`) แล้วรัน:

```
runtime: goroutine stack exceeds 1000000000-byte limit
runtime: sp=0x4020160430 stack=[0x4020160000, 0x4040160000]
fatal error: stack overflow
```

Go ไม่ปล่อยให้โปรแกรมตายเงียบ ๆ แบบ C (segfault ไม่มีข้อความ) — **runtime** (ส่วนของภาษาที่ทำงานเบื้องหลังตอนโปรแกรมรัน) ของ Go ตรวจจับได้เองและรายงานออกมาชัด ๆ ว่า `stack overflow` พร้อมขีดจำกัด (1,000,000,000 ไบต์) และคำว่า **goroutine** (เธรดเบา ๆ ที่ Go ใช้รันโค้ดแต่ละส่วน)

**สรุปความต่าง**: ใน C เรื่อง stack/heap คือ "เราต้องรู้และจัดการเอง" (จอง heap เอง คืนเอง ระวัง dangling pointer เอง) ส่วน Go **compiler กับ runtime จัดการให้เกือบทั้งหมด** — แต่การรู้ว่าใต้ฮู้ดเกิดอะไร คือสิ่งที่แยกคนที่ "ใช้ภาษาเป็น" ออกจากคนที่ "เข้าใจเครื่องจักร" และนี่คือเหตุผลที่เรามาเรียน C ในระยะ 3 นี้

## 8. โจทย์ฝึก (2 ระดับ)

### ระดับ 2 — mini-project: "แผนที่หน่วยความจำ" (`ep15_map.c`)

เขียนโปรแกรม C ที่พิมพ์ "แผนที่" หน่วยความจำของตัวมันเองออกมาเป็นข้อความ แล้วให้เรายืนยันลำดับในภาพที่ 1 ได้ด้วยตา:

1. ประกาศตัวแปรครบทุกประเภท: ตัวแปร global `int g_global;`, ตัวแปร static `static int g_static;`, ตัวแปรท้องถิ่น `int local;`, และจอง `int *hp = malloc(4 * sizeof *hp);` (ตัวแปร static = ตัวแปรที่เก็บค่าไว้ข้ามการเรียกฟังก์ชัน อยู่ใน data เช่นเดียวกับ global)
2. พิมพ์ address ของทั้งหมด: `&g_global`, `&g_static`, `&local`, `hp`, และ `&main` (โค้ด)
3. เรียงลำดับ address จากมากไปน้อย แล้วพิสูจน์ว่าได้ลำดับ: **stack → heap → data → text** (ตัวแปร global/static กับโค้ดอาจสลับกันได้นิดหน่อย ขึ้นกับคอมไพเลอร์ — ใจความคือ stack สูงสุด heap ต่ำลงมา แล้ว data/text อยู่ต่ำสุด)
4. คืน heap ด้วย `free(hp);` และคอมไพล์ด้วย `gcc -std=c17 -Wall -Wextra -Wpedantic` **ต้องไม่มี warning**

ผลลัพธ์ดิบ (ยังไม่เรียงตาม address — โจทย์ให้เรียงเอง แล้วจะได้ลำดับ stack → heap → data → text):

```
g_global (data)   = 0x5555...
g_static (data)   = 0x5555...
&main    (text)   = 0x5555...
hp       (heap)   = 0x5555...
&local   (stack)  = 0x7fff...
```

**ท้าทายเพิ่ม**: เปลี่ยน `hp` ให้จองในฟังก์ชันย่อยที่คืน pointer ออกมา แล้วพิสูจน์ว่าหลังฟังก์ชันจบ ข้อมูลบน heap ยังอ่านได้ แต่ถ้าเปลี่ยนเป็น `int arr[4]` (ตัวแปรท้องถิ่น) แล้วคืน `&arr[0]` จะได้ warning อะไร และโปรแกรมจะพังไหม — เขียนทั้งสองแบบมาเทียบกัน

## สรุป

ตอนนี้เราเปิดฝาหน่วยความจำดูของจริงครบสองคำถามที่ค้างจากตอน 14 แล้ว เก็บหัวข้อที่ต้องจำให้ครบ:

- **หน่วยความจำของโปรแกรมแบ่ง 4 ส่วน** — จาก address สูงลงต่ำ: **stack** (ตัวแปรท้องถิ่น, โตลง ↓, `0x7fff...`) → **heap** (จองเองด้วย malloc/free, โตขึ้น ↑) → **data** (ตัวแปร global/static) → **text** (โค้ด) — สองช่วงหลังอยู่ `0x5555...` และมีช่องว่างมหึมา (~42 เทระไบต์) คั่นระหว่าง stack กับ heap
- **stack ทำงานแบบ LIFO** — แต่ละฟังก์ชันได้ **stack frame** ของตัวเอง (เก็บ return address + argument + ตัวแปรท้องถิ่น) ซ้อนลงไปเรื่อย ๆ พอฟังก์ชันคืนค่า เฟรมนั้นก็ตายพร้อมตัวแปรท้องถิ่นทั้งหมด
- **calling convention** = ข้อตกลงการเรียกฟังก์ชัน — บน aarch64: argument 8 ตัวแรกผ่าน register `x0`–`x7` (เกินแล้ววางบน stack), return address เก็บใน `x30`, ค่าคืนกลับมาทาง `x0` — เราเห็นทั้งหมดนี้จาก assembly จริงของ `tiny_call.c` และ `many_args.c`
- **heap ต่างจาก stack** — ของบน heap อยู่ข้ามการคืนค่าของฟังก์ชันได้ (เพราะไม่ตายพร้อมเฟรม) แต่ต้อง **คืนเองด้วย `free`** ไม่งั้น memory leak ส่วนการคืน pointer ของตัวแปรท้องถิ่น (ของบน stack) คือ **dangling pointer** → segfault
- **stack มีเพดาน → stack overflow** — ขอบเขตบนเครื่องเราคือ 8 เมกะไบต์ (array 4 MB ผ่าน / 12 MB ตาย) recursion ไม่รู้จบตายที่ชั้น ~27,600 ขณะที่ heap จอง 64 เมกะไบต์สบาย ๆ
- **Go จัดการให้เกือบหมด** — escape analysis ย้ายตัวแปรขึ้น heap ให้เอง (คืน pointer ของตัวแปรท้องถิ่นได้ ไม่เป็นบั๊ก) และ runtime ตรวจ stack overflow แล้วรายงานชัด ๆ ไม่ตายเงียบ ๆ แบบ C

สองคำถามที่เราทิ้งไว้ค้างและจะเฉลยในตอนถัดไป:

(1) ถ้า heap ต้องคืนเอง แล้ว "ลืมคืน" หรือ "คืนแล้วใช้ต่อ" มันอันตรายแค่ไหนกันแน่ — **memory leak** (จองแล้วไม่คืน) กับ **use-after-free** (ใช้หน่วยความจำที่คืนไปแล้ว)

(2) ทำไม security (ความปลอดภัย) ถึงผูกกับเรื่องหน่วยความจำ — เราจะเห็น **buffer overflow** (เขียนข้อมูลล้นขอบเขตที่จองไว้) ตัวร้ายที่ทำให้แฮกเกอร์ยึดเครื่องได้ และนี่คือเหตุผลจริง ๆ ว่าทำไมทุกคนถึงต้องรู้ว่า memory ทำงานยังไง

## ภาคผนวกท้ายบท (ข้ามได้)

- **address จะไม่เหมือนเดิมถ้ารันเอง** — กลไก **ASLR** (การสุ่มตำแหน่งหน่วยความจำ ที่เราพูดถึงในตอน 13) ทำให้ address เปลี่ยนทุกครั้งที่รัน ตัวเลข `0x7fff...` และ `0x5555...` ในบทความนี้จึงเป็นของ "การรันครั้งนั้น" เท่านั้น — สิ่งที่ต้องจำคือ **ช่วง** (stack สูง, heap/data/text ต่ำ) และ **ระยะห่าง** (เช่น เฟรม 80 ไบต์, h1-h2 ห่าง 32 ไบต์) เพราะสิ่งเหล่านี้ไม่ขึ้นกับการสุ่ม
- **ลำดับภายใน stack frame ขึ้นกับคอมไพเลอร์และ ABI** — ในบทความนี้ (aarch64, gcc -O0) ตัวแปรท้องถิ่นอยู่ address สูงกว่า argument ที่ถูก spill ลงมา แต่คอมไพเลอร์ตัวอื่นหรือโหมด optimization อื่นอาจจัดวางต่างกัน — อย่ายึดลำดับภายในเฟรมเป็นกฎตายตัว สิ่งที่ตายตัวคือ "เฟรมใหม่อยู่ address ต่ำลง" และ "แต่ละเฟรมมี return address + argument + ตัวแปรท้องถิ่น"
- **`-O0` (ไม่ optimize) คือกุญแจที่ทำให้เห็นโครงสร้างชัด** — ตอนดู assembly เราสั่ง `-O0` เพื่อปิดการปรับแต่งของคอมไพเลอร์ ไม่งั้นมันอาจตัดตัวแปร/จัดเรียงโค้ดใหม่จนเห็นไม่ชัด (เช่นฟังก์ชันเล็ก ๆ อย่าง `add` อาจถูก inline — เอาโค้ดไปวางแทนที่จุดเรียกเลย) ถ้าเอา `-O0` ออก ภาพที่เห็นจะต่างออกไปแต่ผลลัพธ์เหมือนเดิม
- **`uintptr_t` กับ `%p`** — `uintptr_t` อยู่ใน `<stdint.h>` ใช้เก็บ address เป็นตัวเลขเพื่อลบระยะห่าง ส่วน `%p` คือรูปแบบการพิมพ์ pointer มาตรฐาน (ต้อง cast เป็น `(void *)` ก่อนเสมอ)
- **เวอร์ชันที่ใช้ในบทความนี้** — GCC 14.2.0 (Debian 14.2.0-19) บน Linux aarch64, Go 1.24.4 linux/arm64 ณ วันที่เขียน 18 กันยายน 2026 · สเปคภาษา C ปัจจุบันคือ C23 (ISO/IEC 9899:2024) และ GCC 15 ขึ้นไปเปลี่ยน default เป็น `-std=gnu23` — แต่เราใช้ `-std=c17` เพื่อให้พฤติกรรมตรงกับที่สอนและรันได้เหมือนเดิมทุกเครื่อง ถ้าเครื่องคุณเป็น GCC รุ่นใหม่กว่า ข้อความ warning/error อาจต่างเล็กน้อยแต่ความหมายเหมือนกัน
