# สรุปหลักสูตร — ตอนนี้เรารู้แล้วว่าต้องทำอะไร (ตอนที่ 33)

เรามาถึงตอนสุดท้ายแล้ว

32 ตอนที่ผ่านมาเริ่มจากคำถามง่าย ๆ ว่า "hello world" ที่พิมพ์แล้วมีข้อความโผล่ขึ้นมาบนจอนั้น **มันเกิดขึ้นได้ยังไง** — และตอนนี้ เราตอบคำถามนั้นได้ครบทุกชั้น ตั้งแต่บิต ไปจนถึง **runtime** (ชุดโค้ดที่แถมมากับภาษา คอยจัดคิวงานและเก็บกวาดหน่วยความจำให้ตอนโปรแกรมรัน) ที่คอยทำงานเบื้องหลังให้เราเงียบ ๆ

ตอนที่ 33 นี้จะไม่สอนของใหม่แม้แต่ชิ้นเดียว หน้าที่ของมันมีสามข้อ: **วางแผนที่ทั้งหลักสูตรให้เห็นตรงหน้า** ให้ชัดว่าเราเดินผ่านอะไรมา · **สรุปว่าตอนนี้เราทำอะไรได้แล้วจริง ๆ** (ไม่ใช่ "จำได้" แต่ "ทำได้") · และ **ชี้ทางไปต่อ** ให้เป็นรูปธรรมพอที่วันพรุ่งนี้เราจะเปิดเครื่องแล้วรู้ว่าต้องพิมพ์อะไร (ส่วนหัวข้อ 4–5 เป็นการเอาแผนที่ไปลงมือใช้จริงและปิดหลักสูตร)

ก่อนไปต่อ ขออธิบายศัพท์สองคำที่จะใช้บ่อยในตอนนี้:

> **wrap-up** (แรป-อัพ) = ตอนสรุปปิดท้าย — ไม่เพิ่มเนื้อหาใหม่ แต่รวบของเดิมให้เป็นภาพเดียวแล้วชี้ทางต่อ
>
> **roadmap** (โรดแมป) = แผนที่การเดินทาง — บอกว่าเราอยู่ตรงไหน ผ่านอะไรมาแล้ว และข้างหน้ามีอะไร

![แผนที่ 8 ระยะ (ระยะ 0 + 7 ระยะของเนื้อหา) สู่ 33 ตอน](/assets/diagrams/ep33-01-seven-stages-map.svg)

ภาพข้างบนคือแผนที่ทั้งหมดของหลักสูตร แถวบนคือ **ระยะ 0** (ปฐมนิเทศ) ซึ่งเป็นการเตรียมตัวก่อนออกเดินทาง การ์ดเจ็ดใบคือ **7 ระยะของเนื้อหา** (ระยะ 1–7) ส่วนกล่องมุมขวาล่างคือคำตอบสั้นที่สุดของคำถามว่า "ทั้งหมดนี้เกี่ยวกันยังไง" เราจะไปดูกันในหัวข้อ 1.4

ตัวเลขทุกตัวในภาพ (เวอร์ชันเครื่องมือ, วันที่รัน, จำนวนไฟล์ผลรันที่ยังเปิดเทียบได้, จำนวนโปรเจกต์ capstone — โปรเจกต์ปิดหลักสูตร) ดึงจากไฟล์ผลรันจริงใน `course/code/ep33/out/` ไม่ได้พิมพ์จากความจำ

## 1. แผนที่ใหญ่ — เราเดินผ่าน ระยะ 0 + 7 ระยะมาอย่างไร

### 1.1 ระยะ 0 · ปฐมนิเทศ (ตอน 01–02) — ก่อนออกเดินทาง

สองตอนแรกไม่ได้สอนเขียนโปรแกรม แต่ตอบคำถามที่สำคัญกว่า:

- **ตอน 01** — "พื้นฐานที่แท้จริง" ต่างจาก "เขียนเว็บได้" ตรงไหน และคนที่สร้างเครื่องมือที่เราใช้ทุกวัน (ภาษา, ระบบปฏิบัติการ, คอมไพเลอร์) เขารู้อะไรที่เราไม่รู้
- **ตอน 02** — ติดตั้ง Go, ตั้ง editor กับ terminal (หน้าจอพิมพ์คำสั่ง) และที่สำคัญที่สุดคือ **วิธีเรียนของหลักสูตรนี้** ซึ่งมีสี่จังหวะ: สร้าง → พัง → อ่าน → สร้างใหม่

ถ้าตอนนี้เราจำอะไรจากระยะ 0 ได้อย่างเดียว ขอให้เป็นสี่จังหวะนั้น เพราะมันคือวิธีทำงานจริงของโปรแกรมเมอร์ทุกคน ไม่ใช่แค่เทคนิคการเรียน

### 1.2 เจ็ดระยะของเนื้อหา

| ระยะ | ตอน | คำถามที่ระยะนี้ตอบ | ของที่หยิบติดมือไป |
|---|---|---|---|
| **1 · Go** | 03–07 | "เขียนโปรแกรมเป็นยังไง" | hello world, ตัวแปร, if/for, ฟังก์ชัน, slice/map/struct, ไฟล์/CLI (โปรแกรมสั่งงานแบบพิมพ์คำสั่ง)/error |
| **2 · Computer Organization** | 08–12 | "เครื่องคิดยังไง" | เลขฐานสอง, logic gate (ประตูตรรกะ) → ALU, flip-flop (วงจรจำ 1 บิต) → RAM (หน่วยความจำหลัก), วงจร fetch-decode-execute, assembly (ภาษาเครื่องแบบอ่านออก) |
| **3 · C + หน่วยความจำ** | 13–17 | "หน่วยความจำคืออะไร" | pointer/array, stack vs heap, calling convention (กติกาการส่งค่าเข้าออกฟังก์ชัน), malloc/free (ขอ/คืนหน่วยความจำจาก heap), buffer overflow (เขียนข้อมูลเกินขอบบัฟเฟอร์), compile→link |
| **4 · ระบบปฏิบัติการ** | 18–21 | "โปรแกรมรันบนอะไร" | process/thread, syscall (การเรียกขอให้ kernel ทำงานให้), virtual memory (หน่วยความจำเสมือน), file system + shell จิ๋ว |
| **5 · ทฤษฎีการคำนวณ** | 22–25 | "คอมพิวเตอร์ทำอะไรได้/ไม่ได้" | finite automata (เครื่องสถานะจำกัด) → regex (นิพจน์ทั่วไปสำหรับจับรูปแบบข้อความ), pushdown automata → parsing, Turing machine (เครื่องทัวริง แบบจำลองคอมพิวเตอร์ในอุดมคติ), halting problem, P/NP |
| **6 · Compiler/Interpreter** | 26–30 | "เครื่องมือสร้างภาษาเกิดขึ้นยังไง" | lexer, parser/AST, interpreter, type/scope/symbol table (ตารางเก็บชื่อตัวแปร), codegen → assembly (ภาษาเครื่องแบบอ่านออก) |
| **7 · Capstone** | 31–33 | "รวมทั้งหมดเป็นของชิ้นเดียวได้ไหม" | runtime/GC (garbage collector ตัวเก็บกวาดหน่วยความจำ) ของ Go, 4 โปรเจกต์ที่รันได้จริง, ตอนสรุปนี้ |

อ่านตารางนี้จากบนลงล่างจะเห็น **ลำดับที่ตั้งใจ**: เราเริ่มจาก "ใช้ภาษาเป็น" → "เข้าใจเครื่องที่รันภาษา" → "เข้าใจหน่วยความจำที่เครื่องใช้" → "เข้าใจระบบที่ดูแลเครื่อง" → "เข้าใจขอบเขตทางทฤษฎี" → "สร้างเครื่องมือของตัวเอง" → "ประกอบทุกอย่างเป็นชิ้นเดียว"

### 1.3 แต่ละระยะให้ "ของ" คนละแบบ — และของพวกนั้นจำเป็นต่อกัน

มีจุดหนึ่งที่คนเรียนสายนี้มักเข้าใจผิดตอนอยู่กลางทาง คือคิดว่าแต่ละหัวข้อเป็นกล่องแยกกัน (เรียนจบตอนหนึ่ง = เก็บกล่องนั้นเข้ากรุ) ความจริงคือ **ทุกกล่องถูกยกไปใช้ในกล่องถัด ๆ ไป** และนี่คือตัวอย่างที่ชัดที่สุด:

- **ระยะ 1 (Go)** สอนให้เราเขียนโปรแกรม แต่ยังไม่รู้ว่า `x := 42` ไปอยู่ที่ไหนในเครื่อง
- **ระยะ 2 (เครื่อง)** ตอบว่าคำสั่งหนึ่งถูก "รัน" ได้ยังไง — มี ALU (หน่วยคำนวณ), register (ช่องพักข้อมูลใน CPU) และ RAM
- **ระยะ 3 (หน่วยความจำ)** เอา RAM มาแจกให้โค้ดของเราเป็นที่อยู่ (address) แล้วเราจึงเข้าใจว่า pointer คือ "ตัวเลขที่เก็บที่อยู่" — และ `malloc/free` คือการขอ/คืนที่อยู่จาก heap (พื้นที่จองใช้ยืดหยุ่น) เทียบกับ stack (พื้นที่ที่โตขึ้นตามการเรียกฟังก์ชัน)
- **ระยะ 4 (OS)** ทำให้รู้ว่าโปรแกรมของเรา **ไม่ได้แตะฮาร์ดแวร์เอง** — ทุกครั้งที่อ่านไฟล์หรือพิมพ์ข้อความ มันต้องเรียก syscall แล้ว kernel (แกนกลางของระบบ) เป็นคนทำแทน · อีกทั้งที่อยู่ที่เราเห็น (virtual memory) ก็เป็น "ที่อยู่ปลอม" ที่ MMU (ชิปแปลงที่อยู่) แปลงให้จริงอีกชั้น
- **ระยะ 5 (ทฤษฎีการคำนวณ)** บอกขอบเขตว่าอะไร "ทำได้/ไม่มีทางทำได้" — ทำให้เรารู้ว่าเครื่องที่สร้างจากระยะ 2–4 มีเพดานตรงไหน (halting problem, P/NP)
- **ระยะ 6 (Compiler)** ทำให้เราเข้าใจว่าโค้ดที่เราเขียนกลายเป็นคำสั่งระดับเครื่องได้ยังไง — และเราได้เขียนตัวแปลงนี้ด้วยมือตัวเอง
- **ระยะ 7 (Capstone + runtime)** ประกอบทั้งหมดกลับมาเป็นของใช้จริง

### 1.4 เส้นเดียวจากล่างสุดถึงบนสุด — "พิมพ์ `go run` แล้วเกิดอะไรขึ้น"

ก่อนจะไปต่อ ลองจับทุกระยะมาร้อยเป็นเส้นเดียวด้วยคำสั่งเดียวที่เราพิมพ์กันมาตั้งแต่ตอนที่ 3:

```bash
go run ./hello
```

คำสั่งนี้ทำสามอย่างรวดเดียว: **compile** (แปลงซอร์สโค้ดเป็นโค้ดเครื่อง) → **link** (เชื่อมโค้ดของเรากับ runtime และไลบรารีให้เป็นไฟล์โปรแกรมเดียว) → **exec** (สั่งให้ kernel โหลดไฟล์นั้นขึ้นมาทำงาน)

เพราะเราสงสัยว่า "ข้างในมันทำอะไร" เราจึงรันคำสั่ง `go build -x -o bin/hello ./hello` — flag `-x` (flag = ตัวเลือกที่พิมพ์ต่อท้ายคำสั่ง) สั่งให้ Go **พิมพ์คำสั่งจริงที่มันเรียกออกมา** ลงไฟล์ `out/01_build_trace.txt` เนื้อในไฟล์เริ่มด้วย `WORK=…` แล้วตามด้วยบรรทัดสำคัญสองบรรทัดนี้ (ย่อบรรทัดยาว ๆ ด้วย `…` เพื่อให้อ่านได้):

```text
…/pkg/tool/linux_arm64/compile -o $WORK/b001/_pkg_.a -trimpath "…" -p main \
    -lang=go1.24 … -goversion go1.24.4 -c=4 -pack ./hello/main.go ./hello/stamp.go

GOROOT='/usr/lib/go-1.24' …/pkg/tool/linux_arm64/link -o $WORK/b001/exe/a.out \
    -importcfg $WORK/b001/importcfg.link -buildmode=exe … -extld=gcc $WORK/b001/_pkg_.a
```

สองบรรทัดนี้คือ **ระยะ 6 ทั้งระยะ ย่อเหลือสองบรรทัด**:

- `compile` = ขั้นที่ทำให้โค้ด `.go` กลายเป็นไฟล์ออบเจกต์ `_pkg_.a` (ของที่แปลงแล้วแต่ยังรันเดี่ยว ๆ ไม่ได้) — และสังเกตว่ามันเห็นไฟล์ **ทั้งแพ็กเกจพร้อมกัน** (`main.go` กับ `stamp.go`) ไม่ใช่ทีละไฟล์
- `link` = ขั้นที่เอาไฟล์ออบเจกต์ไป "เชื่อม" กับของที่เราส่งผ่าน `-importcfg` (เช่น `fmt`, `runtime`, `os`, `syscall`) แล้วประกอบเป็นไฟล์โปรแกรมเดียว

สังเกต `-extld=gcc` ในบรรทัด link — นั่นคือหลักฐานว่าระยะ 3 (C) ไม่ได้หายไปไหน: Go ยังต้องพึ่ง gcc (บนเครื่องนี้คือ **gcc 14.2.0**) เป็นตัวเชื่อมชั้นสุดท้ายให้

พอไฟล์โปรแกรมถูกสร้างแล้ว `go run` ก็สั่งให้ kernel โหลดขึ้นมาทำงาน · โปรแกรมเขียนข้อความลง stdout (ช่องทางออกมาตรฐาน) ด้วย syscall ที่เรียนรู้ในระยะ 4 — แล้วข้อความก็โผล่บนจอ นี่คือผลรันจริงจาก `out/02_hello_run.txt`:

```text
$ ./bin/hello
hello from ตอนที่ 33 — โปรแกรมนี้เดินครบทุกชั้นที่เราเรียนมา
runtime ที่ฝังอยู่ในไบแนรี: go1.24.4
GOMAXPROCS = 4 · NumCPU = 4
ไบแนรีนี้ถูกคอมไพล์เมื่อ: built at 2026-10-08 23:14:10

$ file bin/hello
bin/hello: ELF 64-bit LSB executable, ARM aarch64, version 1 (SYSV),
           statically linked, BuildID[sha1]=36c29280…, with debug_info, not stripped
```

สามบรรทัดกลางของผลรันนี้คือ **ระยะ 7 ที่โผล่ขึ้นมาเองโดยที่เราไม่ได้เขียนอะไรเลย**:

- `runtime ที่ฝังอยู่ในไบแนรี: go1.24.4` — ค่านี้มาจาก `runtime.Version()` ไฟล์ `hello/main.go` ของเราไม่มีบรรทัดไหนบอกว่า "go1.24.4" เลย มันเป็นค่าที่ **ติดมากับ runtime และถูกคอมไพล์ฝังลงในไบแนรี** (ไบแนรี = ไฟล์โปรแกรมที่รันได้) ตั้งแต่ตอน build (ทบทวนตอนที่ 31)
- `GOMAXPROCS = 4 · NumCPU = 4` — สองค่านี้ไม่เหมือนกัน · `NumCPU = 4` = จำนวนแกนจริงของเครื่อง · `GOMAXPROCS = 4` = จำนวนงานที่ runtime ยอมให้รันพร้อมกัน (ค่าเริ่มต้นเท่ากับจำนวนแกน)
- `ไบแนรีนี้ถูกคอมไพล์เมื่อ: …` — ค่านี้มาจากไฟล์ `stamp.go` ที่สคริปต์เขียนทับใหม่ทุกครั้ง เพื่อให้ขั้น `compile` ทำงานจริงและเราเห็นมันใน trace · Go ใช้ **แฮช** (ค่าลายนิ้วมือจากเนื้อหาไฟล์) เป็นตัวตัดสินว่า "ต้องคอมไพล์ใหม่ไหม" ถ้าเนื้อหาเป๊ะเหมือนเดิม มันจะข้ามไปใช้ของเดิมทันที ซึ่งถูกต้องและเร็ว แต่เราจะไม่เห็นบรรทัด `compile` เลย
- ส่วน `ELF` ในผลลัพธ์ของ `file` = **Executable and Linkable Format** = รูปแบบไฟล์โปรแกรมที่ Linux ใช้ (ระยะ 4) คำว่า `statically linked` แปลว่ามันพกของที่ต้องใช้ไปด้วยครบ ไม่ต้องพึ่งไฟล์อื่นตอนรัน นี่คือเหตุผลที่ Go ย้ายไบนารีไปวางเครื่องอื่นแล้วมักรันได้เลย

และนี่คือประเด็นที่อยากให้จำที่สุดของหัวข้อนี้: **ทั้งสี่ระยะที่ดูแยกกัน (เครื่อง + หน่วยความจำ + OS + compiler) ถูกใช้พร้อมกันในคำสั่ง `go run` เดียว** ซึ่งเราเคยพิมพ์โดยไม่คิดอะไรมาตั้งแต่ตอนที่ 3

## 2. "ตอนนี้ทำได้แล้ว" — ห้าอย่างที่พิสูจน์ได้ ไม่ใช่แค่ "จำได้"

ประโยค "ฉันเรียนจบหลักสูตร" ไม่มีความหมายถ้าเราไม่รู้ว่าทำอะไรได้ ต่างจากประโยค "ฉันทำสิ่งนี้ได้" ซึ่งตรวจสอบได้ ขอนับของห้าอย่างที่ตอนนี้เราทำได้จริง และทุกข้อตรวจสอบได้ด้วยตัวเราเอง:

**1) อ่านโค้ดแล้วเห็น "ข้างใต้" ไม่ใช่เห็นกล่องวิเศษ**

ตอนที่ 3 การพิมพ์ `fmt.Println("hello")` คือกล่องวิเศษที่เชื่อว่ามันทำงานได้ ตอนนี้เรารู้ว่าทั้งบรรทัดนั้นเดินผ่านอะไร: ตัวอักษรกลายเป็น slice (หน้าต่างที่มองเข้าไปในอาร์เรย์ของไบต์) → เขียนลง fd (ตัวเลขที่ kernel ใช้แทนไฟล์ที่เปิดอยู่ — stdout ของโปรแกรมคือ fd หมายเลข 1) → syscall `write` → kernel ส่งไบต์ไปให้ terminal → terminal วาดตัวอักษร

**2) เขียน compiler จิ๋วได้ — และ "ขยาย" มันได้**

ในตอน 26–30 เราสร้างทั้งสายเอง: **lexer** (ตัดข้อความโปรแกรมเป็นคำ), **parser** (ประกอบคำเป็นต้นไม้ที่เรียกว่า AST), **interpreter** (เดินต้นไม้แล้วคำนวณ), **type/scope** (ตรวจว่าตัวแปรนี้มีอยู่จริงและมีชนิดอะไร) และ **codegen** (แปลงต้นไม้เป็นชุดคำสั่งแบน ๆ)

และในตอน 32 เราเห็นกับตาแล้วว่าเวลาจะเพิ่ม `while` หนึ่งคำ เราต้องแก้ **สามชั้นพร้อมกัน** ไม่ใช่ชั้นเดียว

**3) เขียน shell ได้**

ในตอน 21 เราสร้าง shell จิ๋ว และในตอน 32 เราเห็นกับตาว่าทำไม `cd` ต้องเป็น **builtin** (คำสั่งที่ shell ทำเองในโปรแกรมของมัน ไม่ได้เรียกโปรแกรมข้างนอก): เพราะโฟลเดอร์ปัจจุบันเป็นสมบัติของ process (โปรแกรมที่กำลังรันอยู่) ถ้าให้โปรแกรมลูกเปลี่ยนโฟลเดอร์ การเปลี่ยนนั้นจะหายไปตอนโปรแกรมลูกจบ

**4) เขียนและเข้าใจ kernel ขั้นพื้นฐาน**

ในตอน 32 kernel ของเราบูตบนเครื่องจำลอง QEMU แบบ **bare metal** (ไม่มีระบบปฏิบัติการรองรับอยู่ข้างใต้เลย) แล้วพิมพ์ข้อความผ่านชิป UART (ชิปส่ง-รับข้อความทีละตัวอักษร) โค้ดที่ทำให้ข้อความโผล่บนจอไม่ใช่ `printf` แต่คือการเขียนค่าลง **ที่อยู่ของฮาร์ดแวร์** ตรง ๆ ที่ `0x09000000` และกว่ามันจะทำงานได้ ต้องมี assembly สองสามบรรทัดตั้ง stack (พื้นที่วางตัวแปร) ให้เรียบร้อยก่อน

**5) รู้ "ขอบเขต" ของสิ่งที่คอมพิวเตอร์ทำได้**

นี่คือของที่หลายคนมองข้าม แต่เป็นของที่มีค่าที่สุดในระยะยาว: ในระยะ 5 เราเรียนว่าโจทย์บางอย่าง **ไม่มีทางแก้ด้วยโปรแกรม** (halting problem — ไม่มีโปรแกรมใดตอบได้ว่าอีกโปรแกรมหนึ่งจะหยุดหรือวิ่งวนตลอดไป) และบางอย่าง **แก้ได้แต่ไม่ใช่ในเวลาที่รับได้** (ปัญหา P/NP) — เวลามีคนมาบอกว่า "ให้ AI/โปรแกรมแก้ปัญหานี้ให้หน่อย" เราจะเป็นคนที่ถามกลับได้ว่า "มันอยู่กลุ่มไหน" ก่อนจะเสียเวลาทั้งเดือนไปกับอะไรที่ไม่มีทางออก

> ทั้งห้าข้อนี้ไม่ต้องให้ใครมาสอบ — เราตรวจเองได้ด้วยการเปิดโค้ดเก่าของตัวเองใน `course/code/` แล้วอธิบายออกมาดัง ๆ ว่าบรรทัดต่อบรรทัดมันทำอะไร ถ้าอธิบายได้ = ทำได้จริง ถ้าติด = รู้แล้วว่าต้องกลับไปอ่านตอนไหน (นี่คือเหตุผลที่ทุกตอนมีโฟลเดอร์ `out/` เก็บผลรันไว้)

## 3. ทางไปต่อ — เลือกเส้นทาง ไม่ใช่เลือกเครื่องมือ

![ทางไปต่อ 4 เส้นทางสายงาน ทรัพยากรที่อ้างอิงได้จริง และ capstone M1–M4](/assets/diagrams/ep33-02-next-steps.svg)

ตอนนี้เรามีพื้นฐานที่ **เชื่อมกันเป็นภาพเดียว** ซึ่งเป็นของที่หาได้ยาก ถ้าถามตัวเองว่าต่อจากนี้ไปทางไหน คำตอบที่ดีที่สุดไม่ใช่ "เครื่องมืออะไรกำลังฮิต" แต่คือคำถามนี้:

> **"ฉันอยากแก้ปัญหาชนิดไหน"** — ปัญหาเรื่องข้อมูลและการประสานงาน? ปัญหาเรื่องเครื่องทำงานยังไง? ปัญหาเรื่องอุปกรณ์จริง? หรือปัญหาเรื่องภาษาและการแปลงความหมาย?

สี่คำถามนั้นชี้ไปสี่เส้นทาง และ **ทุกเส้นทางใช้พื้นฐานชุดเดียวกัน** ที่เราเพิ่งเรียนมา ต่างกันแค่ปลายทาง

### 3.1 สี่เส้นทาง — แต่ละเส้นให้อ่านอะไร ฝึกอะไร

**เส้นที่ 1 · Backend / Platform** (ฝั่งบริการและโครงสร้าง)

- **อ่านต่อ:** OSTEP ในส่วน virtualization กับ persistence · CS:APP บทที่ว่าด้วย I/O และการประสานงาน
- **ฝึก:** เขียน HTTP server (โปรแกรมรอรับคำขอจากเบราว์เซอร์) เองโดยไม่พึ่ง framework · ดูว่า request (คำขอหนึ่งครั้ง) เดินผ่าน fd, socket (ช่องทางเชื่อมต่อระหว่างเครื่อง), syscall ยังไง · ต่อกับฐานข้อมูล · ทำ cache (ที่พักข้อมูลไว้ใช้ซ้ำให้เร็วขึ้น) · ทำคิวงาน · ห่อทุกอย่างเป็น container (กล่องแพ็กโปรแกรมพร้อมของที่ต้องใช้) แล้ว deploy (เอาขึ้นเครื่องจริงให้คนอื่นใช้)
- **ภาษา:** Go ต่อยอดได้ทันที เพราะพื้นฐาน concurrency (การทำงานพร้อมกัน) ของ Go สร้างบนเรื่องที่เราเรียนในระยะ 4

**เส้นที่ 2 · Systems / OS** (ฝั่งระบบปฏิบัติการ)

- **อ่านต่อ:** OSTEP ทั้งเล่ม (อ่านฟรี) · OSDev wiki เมื่อลงมือจริง
- **ฝึก:** กลับไปทำ kernel ในตอน 32 ให้ถึง M4 (รับ input → จัดการ exception (เหตุการณ์ผิดปกติที่ CPU ต้องเบรกมาดู) → timer interrupt → scheduler)
- **ภาษา:** C + assembly

**เส้นที่ 3 · Embedded / IoT** (ฝั่งอุปกรณ์)

- **อ่านต่อ:** คู่มือชิปของบอร์ดที่ใช้ (ARM หรือ RISC-V) · CS:APP ในส่วนหน่วยความจำและการติดต่อ I/O
- **ฝึก:** อ่านค่า sensor · ตั้ง timer · ใช้ UART · เขียน interrupt handler (ฟังก์ชันที่จะถูกเรียกอัตโนมัติเมื่อฮาร์ดแวร์แจ้งเหตุ) · จนถึงเขียนแบบ bare metal
- **ภาษา:** C + asm สถาปัตยกรรมนั้น ๆ — และความเข้าใจ `volatile` (คำสั่งบอกคอมไพเลอร์ว่าค่านี้อาจเปลี่ยนเอง) กับที่อยู่ของ register จากตอน 32 จะกลายเป็นของที่ต้องใช้ทุกวัน

**เส้นที่ 4 · Compiler / Language** (ฝั่งภาษาและเครื่องมือ)

- **อ่านต่อ:** Crafting Interpreters (อ่านฟรี) · Writing an Interpreter in Go → Writing a Compiler in Go · และถ้าอยากเข้าใจทฤษฎีให้ลึก ค่อยเข้าเล่มใหญ่สายคอมไพเลอร์
- **ฝึก:** เพิ่ม type system ให้ภาษาของตัวเอง · เขียน garbage collector ของตัวเอง (จับคู่กับตอน 31) · ลอง optimize (ทำให้โค้ดที่สร้างออกมาเร็วขึ้น) · ถ้าอยากท้าทายก็ลอง bytecode VM (เครื่องจำลองที่รันคำสั่งนามธรรม) หรือ JIT (ตัวแปลงโค้ดเป็นโค้ดเครื่องตอนกำลังรัน)
- **ภาษา:** Go หรือ C ก็ได้

หนังสือทุกเล่มในลิสต์นี้มีอย่างน้อยหนึ่งที่ให้อ่านฟรี — เพราะการเรียนรู้พื้นฐานไม่ควรถูกกั้นด้วยราคา ขอให้เริ่มจากเล่มที่ตรงกับเส้นทางที่เราเลือก **เล่มเดียว** อย่าเปิดพร้อมกันสามเล่ม

### 3.3 สิ่งที่ควรทำก่อนอย่างอื่น: กลับไปทำให้ capstone จบ M1 → M4

ก่อนจะเริ่มเส้นทางไหน ขอเสนอให้ปิดงานที่ค้างอยู่ก่อน เพราะมันคือของที่ **ใกล้มือที่สุดและให้ผลตอบแทนเร็วที่สุด**

ตอนที่ 32 เราได้ **M0** (M = milestone = ชั้นความสามารถของโปรเจกต์ ไต่ทีละชั้น) ของทั้งสี่โปรเจกต์มาแล้ว (ของที่รันได้จริง) ซึ่งหมายความว่าเรามี **จุดสตาร์ทที่ทำงานได้** ไม่ต้องเริ่มจากหน้าว่าง สิ่งที่ต้องทำคือไต่ M1 → M2 → M3 → M4 ของโปรเจกต์ที่เลือก **ทีละชั้น**:

```text
เลือก 1 โปรเจกต์  →  M1  →  M2  →  M3  →  M4  →  commit ทุกครั้งที่ผ่านด่าน
```

และกติกาสี่ข้อที่ทำให้ไปถึง M4 ได้จริง (ไม่ใช่เริ่มแล้วทิ้งกลางทาง):

1. **ทำทีละชั้น แล้วรันให้ผ่านก่อนไปชั้นถัดไป** — M1 ยังไม่ผ่าน อย่าเพิ่งเริ่ม M2
2. **commit ทุกครั้งที่ผ่านด่าน** (commit = บันทึกความเปลี่ยนแปลงลงระบบเก็บประวัติโค้ด) — จุดประสงค์แรกของมันไม่ใช่ประวัติสวย แต่คือ "ย้อนกลับไปจุดที่ยังทำงานได้" เมื่อไหร่ก็ได้
3. **เขียนเทสต์สำหรับสิ่งที่เพิ่งทำได้** — ถ้า M1 คือ pipe เราควรมีเทสต์ที่รัน `echo a | wc -l` แล้วได้ `1`
4. **ถ้าติดเกิน 2 ชั่วโมง ให้กลับไปอ่านตอนที่เกี่ยวข้อง** — อย่าอยู่กับหน้าจอเฉย ๆ (ดูหัวข้อ 4.3)

### 4.2 โจทย์ประจำตอน

**ระดับ Drill (ฝึกมือสั้น ๆ 10–15 นาทีต่อข้อ)**

1. **ทำให้ trace เป็นของตัวเอง** — รัน `bash run_all.sh` แล้วเปิด `out/01_build_trace.txt` หาบรรทัด `compile` กับ `link` ให้เจอ แล้วตอบให้ได้ว่า flag `-pack` กับ `-importcfg` ทำหน้าที่อะไร
2. **พิสูจน์ว่าแฮชเนื้อหาเป็นตัวตัดสิน** — เปิด `run_all.sh` แล้วคอมเมนต์บรรทัดที่เขียน `stamp.go` ออก · รัน `go build -x -o bin/hello ./hello` สองครั้งติดกัน แล้วดูว่าครั้งที่สองมีบรรทัด `compile` ไหม (ทำไม) — เสร็จแล้วคืนค่ากลับ
3. **ทบทวน "หนึ่งคำสั่ง หนึ่งชั้น"** — เลือกคำสั่งในชีวิตประจำวันหนึ่งคำสั่ง (เช่น `cat file.txt`, `ls`, `curl`) แล้วเขียนลงกระดาษว่ามันเดินผ่านระยะไหนของหลักสูตรบ้าง (อย่างน้อยต้องมีระยะ 4 และระยะ 7)
4. **อธิบาย `go run` ให้คนอื่นฟังได้** — พูดออกเสียง 60 วินาที: "จากไฟล์ `.go` ถึงข้อความบนจอ มีกี่ขั้น ขั้นไหนเกิดตอน compile ขั้นไหนเกิดตอนรัน" ถ้าติดตรงไหน = จุดที่ต้องกลับไปอ่าน
5. **หาวันที่กับเวอร์ชันด้วยตัวเอง** — เปิด <https://go.dev/doc/devel/release> แล้วบอกว่าเวอร์ชัน stable ล่าสุดตอนนี้คืออะไร และเครื่องเรารันเวอร์ชันอะไร (เทียบกับค่าจริงใน `out/00_env.txt`)

**Mini-project (= เลือกทำ แล้วเก็บหลักฐานไว้)**

เลือก **หนึ่ง** อย่างจากสามข้อนี้ ทำให้จบในคืนเดียว:

- **(ก) ยืนยันเครื่องเราเอง** — รัน `bash run_all.sh` บนเครื่องเรา แล้วเก็บ `out/00_env.txt` กับ `out/01_build_trace.txt` ของเราไว้ (ของเราจะไม่เหมือนของบทความ — คนละ OS คนละเวอร์ชัน) แล้วเขียนสั้น ๆ 5 บรรทัดว่า "ต่างจากของในบทความตรงไหน เพราะอะไร"
- **(ข) ทำ M1 ของ capstone ที่เลือก** — เปิด `course/code/ep32/README.md` แล้วทำความสามารถชั้นแรก (เช่น รองรับ quote `"a b"` ใน shell หรือรับ input จาก UART ใน kernel) ให้รันผ่าน แล้ว commit
- **(ค) เขียน "แผนที่ของตัวเอง"** — วาดแผนผัง (ใช้เครื่องมืออะไรก็ได้) ที่โยง 7 ระยะเข้ากับคำถามที่เรายังตอบไม่ได้ แล้วเลือก **หนึ่งคำถาม** มาเป็นเป้าหมายของเดือนหน้า พร้อมระบุว่าต้องอ่านอะไรจากข้อ 3.2

**โจทย์ปิดท้าย (ไม่มีใครตรวจ แต่มีค่าที่สุด):** เปิดโค้ดเก่าของตัวเองหนึ่งไฟล์ (ไม่ใช่ของในบทความ — ของที่เราเขียนเอง) แล้วอ่านให้จบทั้งไฟล์โดยไม่ต้องเปิดเอกสาร ถ้าอ่านจบและอธิบายได้ แปลว่าเราผ่านหลักสูตรนี้จริง

### 4.3 เมื่อติด — ลำดับที่ได้ผลเร็วที่สุด

หกข้อนี้ใช้ได้กับทุกโปรเจกต์ในหลักสูตร เรียงตาม "ได้ผลเร็วสุดก่อน":

1. **อ่านข้อความ error ให้จบทั้งก้อน** — มันบอกไฟล์ บรรทัด และบ่อยครั้งบอกทางแก้
2. **ดู "บรรทัดแรกที่เริ่มพัง" เท่านั้น** — error 10 บรรทัดมักเป็นผลลูกโซ่จากบรรทัดแรก
3. **แบ่งปัญหาให้เล็กลงครึ่งหนึ่ง** — คอมเมนต์ครึ่งล่างออก รัน ถ้ายังพัง ปัญหาอยู่ครึ่งบน
4. **กลับไปอ่านตอนที่เกี่ยวข้อง** — error พูดถึงไฟล์/process/การรอลูกจบ → ตอน 18–19–21 · พูดถึง pointer/ที่อยู่/`sp` (stack pointer ตัวชี้ตำแหน่งบนสุดของ stack) → ตอน 14–15 · พูดถึงไวยากรณ์/ต้นไม้ → ตอน 26–27 · พูดถึง GC/การจองหน่วยความจำ → ตอน 31
5. **เขียนเทสต์ที่ "ทำให้พัง" ก่อน** — เจอ bug ให้เขียนเทสต์ที่ fail ก่อน แล้วค่อยแก้ พอผ่าน = bug นั้นกลับมาไม่ได้อีก
6. **พักจริง ๆ 10 นาที** — สมองที่ติดมักหาคำตอบได้ตอนที่เราไม่ได้จ้องหน้าจอ

## 5. ปิดท้าย: พื้นฐานที่แท้จริง = เข็มทิศ ไม่ใช่จุดหมาย

มีคำถามหนึ่งที่ควรตอบให้ชัดก่อนจากกัน: **"พื้นฐานที่แท้จริง" ที่ตอนที่ 1 อ้างถึง มันคืออะไรกันแน่**

ถ้าให้ตอบสั้นที่สุด: **มันไม่ใช่รายการหัวข้อที่ต้องท่องจบ แต่คือความสามารถในการ "หาให้เจอว่าปัญหาหนึ่งอยู่ชั้นไหน"**

ลองเทียบสถานการณ์จริงสองแบบ:

- แบบหนึ่ง: โปรแกรมอ่านไฟล์แล้วได้ค่าผิด ผู้เขียนเปิดหาคนใน Stack Overflow หาโค้ดที่ "คล้ายกัน" แล้วลองสลับไปเรื่อย ๆ จนบังเอิญผ่าน
- แบบสอง: ผู้เขียนถามตัวเองว่า "ค่าผิดเกิดตอนอ่าน หรือตอนแปลง?" → เดาว่าอยู่ชั้น read → ตรวจว่า `read` คืนกี่ไบต์ (`err`, `n` เป็นเท่าไร) → เจอว่าโปรแกรมเชื่อว่าไฟล์มีข้อมูลครบทั้งก้อน (ทบทวนตอน 7 และ 21)

แบบที่สองคือสิ่งที่หลักสูตรนี้สร้างให้ วิธีการ "เดาชั้นให้ถูก" ไม่ได้มาจากการท่อง แต่มาจากการที่เราเคย **เห็นทุกชั้นด้วยตาตัวเอง** — เคยทำให้ buffer เกินขอบ (ตอน 16) เคยเห็น syscall ใน strace (เครื่องมือดักดูว่าโปรแกรมเรียก syscall อะไร — ตอน 19) เคยเห็นที่อยู่ปลอมของ virtual memory (ตอน 20) เคยเขียน lexer ที่พังเพราะ regex ผิด (ตอน 26)

และนี่คือเหตุผลที่หัวข้อนี้ชื่อว่า "เข็มทิศ ไม่ใช่จุดหมาย" — **พื้นฐานไม่ใช่ของที่เรียนจบแล้ววางทิ้ง** แต่เป็นเครื่องมือที่ทำให้เราออกเดินต่อได้ตลอดไปโดยไม่หลง

สามสิ่งที่อยากฝากไว้ในฐานะคนที่เดินเส้นนี้มาก่อน:

1. **ความเร็วไม่ได้มาจากการข้าม แต่มาจากการไม่ต้องย้อนกลับบ่อย** — คนที่รู้ทุกชั้นจะแก้ bug ได้เร็วขึ้นเรื่อย ๆ เพราะเขาแคบขอบเขตได้ถูก
2. **การ "ทำไม่ได้" เป็นข้อมูล ไม่ใช่ความล้มเหลว** — ทั้ง halting problem, buffer overflow, และ error ที่อ่านไม่ออก ล้วนสอนขอบเขตของเครื่องให้เรา และขอบเขตที่รู้ชัดคือของมีค่า
3. **สิ่งที่เราเขียนเอง จะอยู่กับเราแบบที่หนังสือไม่เคยทำได้** — kernel ที่บูตได้ใน 200 บรรทัดจะอยู่ในหัวเรานานกว่าบทที่อ่านผ่าน ๆ ยี่สิบหน้าเสมอ

ตอนที่ 1 เราถามว่า "ทำไมต้องรู้พื้นฐานที่แท้จริง" ตอนที่ 33 นี้คำตอบชัดแล้ว — เพราะมันคือสิ่งที่ทำให้เราอยู่ในโลกนี้ได้แบบ **ไม่ต้องเชื่อใคร และไม่ต้องกลัวอะไรที่ยังไม่เจอ**

ขอบคุณที่เดินมาถึงตรงนี้ด้วยกันทั้ง 33 ตอน เก็บโค้ดทุกไฟล์ไว้ อย่าลบโฟลเดอร์ `out/` แล้วออกเดินต่อได้เลย
