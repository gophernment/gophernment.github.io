# SQL Injection (1998): วันที่โลกเรียนรู้ว่า "อย่าเชื่อ input เลยแม้แต่ตัวเดียว" (ตอนที่ 04)

> 📅 เขียนเมื่อ: 12 ตุลาคม 2026 (เวลาไทย, UTC+7) | โค้ดในบทนี้ทดสอบจริงบน Raspberry Pi 5 (Linux 6.18.39, aarch64) ด้วย **Go toolchain 1.26.0** (เครื่องติดตั้ง Go 1.24.4 ไว้ แต่ `go.mod` ของตอนนี้กำหนด `go 1.26.0` Go จึงสลับ toolchain ให้อัตโนมัติ) · **modernc.org/sqlite v1.60.1** (driver แบบ pure Go) · **github.com/mattn/go-sqlite3 v1.14.52** (driver แบบ cgo, คอมไพล์ด้วย gcc 14.2.0) · **SQLite 3.53.4** — เวอร์ชันล่าสุด ณ วันเขียน: **Go 1.27.2** (ออก 8 ตุลาคม 2026) · **SQLite 3.54.0** (ออก 9 ตุลาคม 2026) · **modernc.org/sqlite v1.60.1** และ **go-sqlite3 v1.14.52** (เวอร์ชันล่าสุดของทั้งคู่ ตรงกับที่ใช้)

> 🛡️ **จริยธรรม:** ตอนนี้สอนกลไกของ **SQL injection** (การยัดไวยากรณ์ SQL ผ่าน input เพื่อเปลี่ยนคำสั่งที่ฐานข้อมูลจะรัน) ตรง ๆ — เดโมและโจทย์ทุกข้อในบทนี้ **ทำใน environment ที่คุณควบคุมเองเท่านั้น** (เครื่องตัวเอง, VM, container หรือ lab ที่ตั้งใจให้ทดลอง) **ห้ามใช้เทคนิคเหล่านี้กับระบบของคนอื่นโดยไม่ได้รับอนุญาต** ซึ่งผิดกฎหมายในแทบทุกประเทศ · เดโมของเรา **รันในหน่วยความจำ (`:memory:`) ไม่มีไฟล์ฐานข้อมูลจริง ไม่เชื่อมต่อเครือข่าย และไม่มี argument ให้ยิงใส่เป้าใด ๆ** — เราเรียกฟังก์ชันของตัวเองด้วย payload ที่เขียนไว้ล่วงหน้าในโค้ด เพื่อดูว่าฐานข้อมูล "ตีความ" อะไร

ใน[ตอนที่ 03](/blog/post.html?slug=2026-10-11-software-security-03-smashing-the-stack) เราอยู่ใน**หน่วยความจำ**: ข้อมูล (`buf`) กับคำสั่งที่จะทำต่อไป (`return address`) อยู่ติดกัน และ CPU ไม่รู้จักความต่างระหว่างสองอย่าง

วันนี้เราจะย้ายจาก "หน่วยความจำ" ไปสู่ "ฐานข้อมูล" — และบทเรียนจากตอนที่แล้วจะโผล่มาในร่างใหม่ที่หน้าตาเหมือนกันจนน่าตกใจ

ก่อนไปต่อ ขอนิยามศัพท์ที่จะใช้ทั้งบทให้ตรงกันก่อน: **SQL** (Structured Query Language) = ภาษามาตรฐานสำหรับสั่งงานฐานข้อมูล · **ฐานข้อมูล** = ที่เก็บข้อมูลในรูป**ตาราง** · หนึ่งตารางมีหลาย**แถว** (แถว = 1 รายการ เช่นผู้ใช้ 1 คน) และหลาย**คอลัมน์** (คอลัมน์ = 1 ฟิลด์ เช่น ชื่อผู้ใช้ หรือรหัสผ่าน)

> **ประโยคเดียวที่เป็นหัวใจของทั้งบทนี้:** ฐานข้อมูลไม่ได้เห็น `' OR '1'='1` เป็น "ชื่อผู้ใช้" — มันเห็นเป็น **ไวยากรณ์** ของคำสั่ง

ถ้าคุณเข้าใจประโยคนี้ และเข้าใจว่าทำไมการส่งค่าแยกออกจากคำสั่ง (parameterized query) ถึงแก้ได้ — คุณเข้าใจ SQL injection ทั้งคลาสแล้ว ที่เหลือคือรายละเอียด

> **หมายเหตุสำหรับผู้เรียน:** บทนี้ต่อจาก[ตอนที่ 16 ของซีรีส์ CS Fundamentals](/blog/post.html?slug=2026-09-19-cs-fundamentals-16-memory-safety-overflow) ที่คุณเจอแนวคิด "ข้อมูลกลายเป็นโค้ด" ครั้งแรก และต่อจากตอนที่ 03 ที่คุณเห็นมันในระดับ CPU · ตอนนี้เราจะเห็นแนวคิดเดียวกันในระดับ **interpreter** (โปรแกรมที่อ่านข้อความแล้วตีความเป็นคำสั่ง — ในที่นี้คือตัว engine ของ **SQLite** ซึ่งเป็นฐานข้อมูลตัวเล็กที่ฝังอยู่ในโปรแกรม ไม่ต้องมีเซิร์ฟเวอร์แยก และตัวที่เราใช้ในบทนี้รันอยู่ในหน่วยความจำ) ซึ่งเป็นรากของทั้งตระกูลช่องโหว่ที่เรียกว่า **injection** · ถ้าจำศัพท์เรื่อง parser หรือ interpreter ไม่ได้แล้ว บทนี้จะทวนให้ใหม่ทุกจุดที่ใช้

วันนี้เราจะทำสี่อย่าง: เข้าใจว่า **ทำไม query ที่ต่อสตริงถึงพัง** (และทำไม parameterized query ถึงไม่พัง) · ไปดูว่า **25 ธันวาคม 1998** เกิดอะไรขึ้น และทำไมวันนั้นถึงเป็นวันกำเนิดแนวคิด "never trust input" · **ลงมือเขียนโปรแกรมตัวอย่างเล็ก ๆ (CLI = โปรแกรมที่สั่งงานด้วยบรรทัดคำสั่ง) ใน Go** ที่ต่อ SQLite จริง แล้วเทียบเวอร์ชันที่พังกับเวอร์ชันที่ปลอดภัยด้วยผลรัน · แล้วปิดท้ายด้วย **กับดักที่การ escape ไม่ช่วย** (คำว่า escape จะนิยามให้ในหัวข้อ 1.4) ซึ่งเป็นจุดที่คนเข้าใจผิดมากที่สุด

## 1. แนวคิด: query คือ "ข้อความ" — และ parser ไม่รู้จักคำว่า "ข้อมูล"

ก่อนจะไปถึงเรื่องโจมตี ขอวางภาพให้ตรงกันก่อน เพราะกลไกทั้งหมดอยู่ที่ตรงนี้

### 1.1 SQL query คือข้อความที่ถูก "ตีความใหม่" ทุกครั้ง

คุณเขียนคำสั่งแบบนี้:

```sql
SELECT id, username FROM users WHERE username = 'alice'
```

คำถามคือ: **คอมพิวเตอร์รู้อะไรได้บ้างจากข้อความนี้?** คำตอบคือมันไม่รู้ล่วงหน้าสักอย่าง สิ่งเดียวที่มันรู้คือมันมี "ข้อความ" หนึ่งก้อน แล้วมันต้อง**ตีความ**ข้อความนั้นทีละคำ:

- เจอ `SELECT` → นี่คือคำสั่งดึงข้อมูล
- เจอ `FROM users` → เอามาจากตารางชื่อ `users`
- เจอ `WHERE username = 'alice'` → กรองเฉพาะแถวที่คอลัมน์ `username` เท่ากับข้อความในเครื่องหมายคำพูด

กระบวนการนี้เรียกว่า **parsing** (การแยกข้อความออกเป็นชิ้นตามไวยากรณ์ของภาษา) และโปรแกรมที่ทำคือ **parser** · สังเกตคำสำคัญ: **`'alice'` กับ `SELECT` ถูกอ่านด้วยตาเดียวกัน** ต่างกันแค่ "ตำแหน่งของมันในไวยากรณ์บอกว่ามันเป็นอะไรในความหมาย"

> ขอเทียบกับตอนที่ 03 ให้เห็นภาพ: ตอนนั้น CPU อ่าน**ไบต์**ที่อยู่ในหน่วยความจำและตีความเป็น**คำสั่ง** โดยไม่รู้ว่ามันเขียนขึ้นมาในฐานะ "ข้อมูล" · ตอนนี้ parser อ่าน**ข้อความ**และตีความเป็น**ไวยากรณ์** โดยไม่รู้ว่ามันเขียนขึ้นมาในฐานะ "ค่าที่ผู้ใช้กรอก"

สองเรื่องนี้คือเรื่องเดียวกันในคนละระดับ: **ที่ไหนก็ตามที่ interpreter อ่าน "ข้อมูลของเรา" เป็น "คำสั่งของมัน" ที่นั่นคือช่องโหว่ injection**

### 1.2 ที่มาของปัญหา: การต่อสตริงเพื่อประกอบ query

ทีนี้ นี่คือโค้ดที่คุณจะเจอบ่อยที่สุดในโลกจริง (และเป็น "บรรทัดที่ผิด" ของบทนี้):

```sql
-- สิ่งที่โปรแกรมเมอร์อยากทำ:
SELECT id FROM users WHERE username = '<ชื่อที่ผู้ใช้กรอก>'
```

ถ้าเราใช้ภาษาที่มี database library (ในบทนี้คือ Go) และเผลอประกอบข้อความด้วยการ**ต่อสตริง** — ในไฟล์จริงของเรามันคือสองบรรทัดนี้:

```go
return "SELECT id, username, role FROM users WHERE username = '" + username +
	"' AND password_hash = '" + password + "'"
```

เมื่อ `username` เป็น `alice` ทุกอย่างก็ปกติ — แต่สังเกตว่าสิ่งที่เรา**มอบให้ฐานข้อมูล**คือ "ข้อความก้อนเดียว" ที่มี `alice` ฝังอยู่ในไวยากรณ์เรียบร้อย

แล้วถ้าผู้ใช้กรอก `admin'--` ล่ะ (สมมติรหัสผ่านที่กรอกคือ `x`)? ข้อความที่ส่งเข้าไปจะเป็น:

```sql
SELECT id FROM users WHERE username = 'admin'--' AND password_hash = 'x'
```

และ parser ก็อ่านตามที่มันเห็น:

1. `'admin'` = ค่าของ `username` (ตรงตามที่เรา**คิด**ว่าเป็น)
2. `--` = **คอมเมนต์** (ทุกอย่างหลังจากนี้ถูกมองข้ามไปทั้งสิ้น) ← นี่คือส่วนที่ผู้ใช้แอบใส่
3. เงื่อนไข `AND password_hash = 'x'` ที่เราอุตส่าห์เขียนไว้ → **หายไปทั้งท่อน**

ผลคือโค้ดของเราเชื่อว่ามันกำลังตรวจรหัสผ่าน แต่ความจริงมันตรวจแค่ชื่อผู้ใช้

> **ศัพท์ที่ต้องรู้:** `--` คือ **comment** ในภาษา SQL (เหมือน `//` ใน Go หรือ `#` ใน bash) และ **`'` คือ delimiter** (เครื่องหมายกำหนดขอบเขตของข้อความ) · สองอย่างนี้เป็น "ไวยากรณ์" ไม่ใช่ "ข้อมูล" — และนั่นคือทั้งหมดของเรื่องนี้

### 1.3 หน้าตาของ input ที่กลายเป็นไวยากรณ์ มีกี่แบบ

ในทางปฏิบัติ เราแบ่งเป็น 4 หน้าตาหลัก ๆ ซึ่งบทนี้จะสาธิตจริงทุกแบบ:

| แบบ | ตัวอย่าง input | ใช้ไวยากรณ์อะไร | ผลลัพธ์ |
|---|---|---|---|
| **Tautology** (เงื่อนไขจริงเสมอ) | `' OR '1'='1` | `OR` | ทุกแถวผ่านด่าน เพราะเงื่อนไขเป็นจริง |
| **Comment** (กลืนส่วนที่เหลือ) | `admin'--` | `'` + `--` | เงื่อนไขที่อยู่ท้ายถูกตัดทิ้งทั้งท่อน |
| **UNION** (ต่อผลลัพธ์) | `' UNION SELECT ...--` | `UNION` | ดึงคอลัมน์อื่น/ตารางอื่นออกมาปนกับของเดิม |
| **Stacked query** (ซ้อนคำสั่ง) | `1; DROP TABLE canary` | `;` | รันคำสั่งที่สองต่อจากคำสั่งแรก |

ทั้งสี่แบบนี้**ไม่ใช่ทริกใหม่** — มันคือ "การเขียน SQL ให้ถูกต้อง" ที่บังคับให้เป็นไปในทางที่ผู้โจมตีต้องการ นี่คือเหตุผลที่มันยากจะกันด้วยการ "แบนคำ" (deny list): ไวยากรณ์ SQL มีมากกว่าที่เราจะไล่แบนได้ครบ และทุกครั้งที่เราบล็อกรูปแบบหนึ่ง คนก็หาวิธีเขียนใหม่

### 1.4 แล้วทำไม parameterized query ถึงกันได้ — ส่ง "ค่า" แยกจาก "คำสั่ง"

ทางแก้ไม่ใช่การเขียน query ให้ฉลาดขึ้น แต่เป็นการ**เปลี่ยนช่องทางที่ส่งข้อมูล**:

```go
const q = "SELECT id, username, role FROM users WHERE username = ? AND password_hash = ?"
rows, err := db.QueryContext(ctx, q, username, password)
```

หัวใจอยู่ที่ `?` — **placeholder** (เครื่องหมายบอกตำแหน่งว่าง) · สังเกตว่าตอนนี้มีอยู่ **สองอย่างที่เดินทางแยกกัน**:

1. **คำสั่ง** (`SELECT ... WHERE username = ? AND password_hash = ?`) — สมบูรณ์ในตัวมันเองตั้งแต่ต้น มี `?` เป็นช่องว่างที่ parser รู้ว่า "ตรงนี้จะเป็นค่า"
2. **ค่า** (ชื่อผู้ใช้และรหัสผ่าน) — ถูกส่งไปในรายการที่สอง ไม่ได้ถูกฝังลงในข้อความ

ฐานข้อมูลจึง compile คำสั่งนั้นทิ้งไว้ก่อน (จึงเรียกว่า **prepared statement** — คำสั่งที่เตรียมไว้แล้ว) แล้ว**ค่อย**ผูกค่าลงช่องว่างทีหลัง · โดยหลักการแล้ว ค่าที่ผูกทีหลัง **ไม่มีโอกาสกลายเป็นไวยากรณ์ได้เลย** เพราะ parser ผ่านจุดนั้นไปแล้ว

![comparison of string concatenation vs parameterized queries](/assets/diagrams/ep04-01-concat-vs-param.svg)

> **เกร็ดที่อธิบายให้ครบ:** ใน SQLite จริง ๆ แล้ว placeholder อาจเป็น `?` หรือ `?1` หรือ `:name` ก็ได้ ขึ้นกับไวยากรณ์ของแต่ละ engine (PostgreSQL ใช้ `$1`, SQL Server ใช้ `@p1`) — Go's `database/sql` จะแปลง `?` ให้เองตาม driver · เรื่องนี้สำคัญเวลาใช้ **ORM** (ตัวช่วยแปลงโค้ดในภาษาโปรแกรมเป็น SQL — อธิบายในหัวข้อ 3.10) หรือสลับฐานข้อมูล: **ตัว `?` ไม่ใช่ส่วนสำคัญ ส่วนสำคัญคือ "มีสองช่องทาง"**

มีคำถามที่ต้องตอบให้ชัดตรงนี้: *แล้วการทำ **escape** (เติมอักขระนำหน้า เช่น `\'` หรือ `''` เพื่อบอก parser ว่าเครื่องหมายนี้เป็นข้อความธรรมดา ไม่ใช่ไวยากรณ์) กับเครื่องหมาย `'` ด้วยตัวเองล่ะ กันได้ไหม?* — คำตอบคือ **ไม่พอ** และเราจะพิสูจน์ด้วยโค้ดจริงในหัวข้อ 3.8 (บริบทตัวเลขไม่มีสตริงให้ escape, ชื่อคอลัมน์ไม่ใช่บริบทของค่า, และข้อมูลที่ "ตรวจแล้ว" กลายเป็นไวยากรณ์ได้อีกทีตอนอ่านออกมาใช้) · เอกสารของ **OWASP** (Open Worldwide Application Security Project — องค์กรไม่แสวงกำไรที่รวบรวมแนวปฏิบัติ security ของเว็บ) จัดการ escape เป็น "Defense Option 4: **STRONGLY DISCOURAGED**" และบอกตรง ๆ ว่ามันเปราะกว่าทางเลือกอื่น

ก่อนลงมือเขียนโค้ด เรามาดูกันก่อนว่าคลาสช่องโหว่นี้ถือกำเนิดอย่างไรในคืนคริสต์มาสปี 1998 — และทำไมมันถึงยังกัดเราอยู่ในปี 2026 นี้

## 2. ทำไมสำคัญ: 25 ธันวาคม 1998 — บทความที่ไม่ได้ใช้คำว่า "SQL injection" เลย

### 2.1 วันนั้นเกิดอะไรขึ้น

**Phrack** คือ e-zine (นิตยสารอิเล็กทรอนิกส์) ของชุมชน security ที่ตีพิมพ์ต่อเนื่องมาตั้งแต่ปี 1985 — เราเจอมันแล้วใน[ตอนที่ 03](/blog/post.html?slug=2026-10-11-software-security-03-smashing-the-stack) ฉบับที่ 49

วันคริสต์มาสปี 1998 ฉบับที่ **54** ออก ในนั้นมีบทความชื่อ *NT Web Technology Vulnerabilities* เขียนโดย **rain.forest.puppy** (นามแฝงของ **Jeff Forristal**) บทความนี้พูดเรื่องช่องโหว่หลายอย่างของเว็บที่รันบน **IIS** (เว็บเซิร์ฟเวอร์ของ Microsoft) ซึ่งรวมถึงการที่แอป **ASP** (เทคโนโลยีทำหน้าเว็บของ Microsoft รุ่นก่อน ASP.NET) เอาค่าจากผู้ใช้ไปต่อเข้าไปในคำสั่ง SQL โดยตรง

มีรายละเอียดที่คนมักเล่าผิดกันสองข้อ และน่ารักทั้งสองข้อ:

1. **บทความนั้นไม่ได้ใช้คำว่า "SQL injection" เลย** — มันพูดถึงเทคนิคเป็น "หมายเหตุข้างเคียง" ของช่องโหว่ที่ผู้เขียนคิดว่าร้ายแรงกว่า (ผู้เขียนไม่ได้ตระหนักว่าตัวเองเพิ่งค้นพบคลาสช่องโหว่ที่อายุยืนที่สุดในประวัติศาสตร์)
2. การยัดคำสั่ง SQL ผ่าน input ของเว็บจึงเป็นเทคนิคที่**มีคนใช้อยู่ก่อนแล้ว** — บทความนี้คือคนที่เขียนมันออกมาให้โลกเห็น

### 2.2 ชื่อคลาสนี้ถูกตั้งขึ้นทีหลัง — แล้วมันกลายเป็นหมายเลข

หลังจากนั้นไม่กี่ปี เทคนิคก็ถูกจัดหมวดเป็นระบบสามแบบ — **error-based** (ใช้ข้อความ error ของฐานข้อมูลเดาโครงสร้าง), **UNION-based** (ดึงข้อมูลออกมาผ่าน `UNION`), **blind** (ไม่เห็นผลลัพธ์ตรง ๆ ต้องเดาจากพฤติกรรมของระบบ) — และ**มีงานเขียนเชิงลึกตามมาอีกหลายชิ้น (ราว 1999–2002)** ที่ทำให้มันแพร่หลายในฐานะ "คู่มือ" · **จุดตั้งต้น**คือบทความ *NT Web Technology Vulnerabilities* โดย **rain.forest.puppy** ใน **Phrack ฉบับที่ 54** (บทความเดียวกับหัวข้อ 2.1) · ส่วนชื่อเรียกอย่างเป็นทางการของช่องโหว่คลาสนี้ในระบบมาตรฐานคือ:

> **CWE-89: Improper Neutralization of Special Elements used in an SQL Command** — หรือที่รู้จักในชื่อสั้น ๆ ว่า **SQL Injection**

เราจะเจอระบบหมายเลขแบบนี้เรื่อย ๆ ในซีรีส์นี้: **CWE** (Common Weakness Enumeration — ทะเบียน*คลาส*ของจุดอ่อนซอฟต์แวร์), **CVE** (Common Vulnerabilities and Exposures — รหัสของช่องโหว่*เฉพาะตัว*แต่ละครั้ง) และ **CISA** (Cybersecurity and Infrastructure Security Agency — หน่วยงานความปลอดภัยไซเบอร์ของสหรัฐฯ) · (ตอนที่ 03 เจอ **CWE-121** ไปแล้ว) · สถานะล่าสุดของ CWE-89:

- **CWE Top 25 ประจำปี 2025** จัดให้ CWE-89 อยู่อันดับ **2** (ขยับ**ขึ้น**จากอันดับ 3 ในปีก่อน — คนละตารางกัน: อันดับ 3 นั้นมาจาก **CWE Top 25 ประจำปี 2024**) — ยังมี CVE ที่ถูกใช้จริงอยู่ในรายการ **KEV** (Known Exploited Vulnerabilities — รายการช่องโหว่ที่ถูกใช้โจมตีจริง) 4 รายการ
- ใน **OWASP Top 10:2021** หมวด injection อยู่ที่ **A03** โดยในหมวดนี้มี CWE ที่เกี่ยวข้องถึง **33 ตัว** และข้อมูลของ OWASP บอกว่า **94.04% ของแอปที่ถูกทดสอบถูก*ตรวจหา* injection** — นี่คือค่า **Max Coverage** (สัดส่วนของแอปที่เครื่องมือสแกนเข้าไปตรวจ) **ไม่ใช่สัดส่วนที่*พบ*ช่องโหว่จริง** · ส่วนค่าที่แปลว่า "พบจริง" คืออัตราการเกิดสูงสุด (max incidence) **19.09%** · ค่าเฉลี่ย **3.37%** · รวม **274,228 ครั้ง**
- ในอดีต injection เคยอยู่อันดับ **1** ของ OWASP Top 10 ต่อเนื่องหลายฉบับ (2010, 2013, 2017) ก่อนจะถอยมาอยู่อันดับ 3 ใน **OWASP Top 10 ฉบับ 2021** (คนละตารางกับ CWE Top 25 ข้างบน)

> **อ่านตัวเลขนี้ให้ถูก:** ที่มันถอยอันดับลง**ไม่ใช่เพราะมันหายไป** แต่เพราะ broken access control (การควบคุมสิทธิ์เข้าถึงผิดพลาด — หมวด A01) มีอัตราการเกิดสูงกว่า และเพราะเครื่องมือสมัยใหม่สร้างคำสั่งแบบมี placeholder ให้เป็นค่าปริยายแล้ว — ปัญหาคือ **ทุกครั้งที่มีคน "ต่อสตริงแค่ครั้งเดียว" มันกลับมาทันที**

### 2.3 ภัยจริง: จากการกรอกฟอร์มสู่การล้มทั้งบริษัท

ทั้งคู่เป็น SQL injection ตรง ๆ ไม่ใช่เรื่องแฝง จึงควรจำไว้เป็นกรณีศึกษา

#### TalkTalk (ตุลาคม 2015) — ช่องโหว่ที่สืบทอดมากับการซื้อกิจการ

- **ช่องทางที่ถูกเจาะ:** หน้าเว็บที่ TalkTalk ได้มาจากการซื้อกิจการของ ISP อีกรายในปี 2009 · หน้าเว็บนั้นยังเชื่อมกับฐานข้อมูลชื่อ "Tiscali Master" และ **ผู้ใช้ไม่ได้ถูกตรวจ (user input was not validated)**
- **เครื่องมือของผู้โจมตี:** **sqlmap** — เครื่องมือสแกนหา SQL injection แบบอัตโนมัติ (ยิง payload ลองเองจนกว่าจะเจอ)
- **ผลลัพธ์:** ข้อมูลส่วนตัวของลูกค้าราว **157,000 ราย** หลุด รวมข้อมูลบัญชีธนาคารของกว่า **15,000 ราย**
- **ก่อนหน้านั้น:** มี**การโจมตีสำเร็จมาแล้ว 2 ครั้ง** (17 กรกฎาคม และ 2–3 กันยายน 2015) ด้วยช่องโหว่เดิม
- **บทลงโทษ:** หน่วยงานกำกับดูแลข้อมูลส่วนบุคคลของสหราชอาณาจักร (ICO) ปรับ **£400,000** เมื่อตุลาคม 2016 พร้อมระบุว่า "SQL injection เป็นเรื่องที่เข้าใจกันดี ป้องกันได้ และ TalkTalk ควรรู้ว่ามันเป็นความเสี่ยง"

#### MOVEit Transfer (พฤษภาคม 2023) — ช่องโหว่คลาสเดิม เมื่อ 8 ปีต่อมา

- **ช่องทางที่ถูกเจาะ:** SQL injection (**CVE-2023-34362**) ในซอฟต์แวร์รับส่งไฟล์ **MOVEit Transfer** และเป็น **zero-day** (ช่องโหว่ที่ยังไม่มีใครรู้จักและยังไม่มีแพตช์)
- **ผู้โจมตี:** กลุ่มเรียกค่าไถ่ **Cl0p / TA505**
- **ไทม์ไลน์:** การโจมตีเริ่ม **27 พฤษภาคม 2023** แล้วติดตั้ง **web shell** (โค้ดที่ผู้โจมตีวางไว้บนเครื่องเหยื่อเพื่อกลับเข้ามาสั่งงานได้เรื่อย ๆ) ชื่อ **LEMURLOOT** ซึ่งปลอมชื่อไฟล์เป็น `human2.aspx` ให้คล้ายของจริง · CISA ใส่ช่องโหว่นี้ลงทะเบียน **KEV** (รายการที่นิยามไว้ในหัวข้อ 2.2) เมื่อ **2 มิถุนายน 2023**
- **ผลลัพธ์:** ยอดนับสะสมสาธารณะ (Emsisoft, ข้อมูล ณ 28 มิถุนายน 2024) อยู่ที่ **2,773 องค์กร** และ **95,788,491 คน** — ตัวเลขคนเป็นยอด "รายงานว่ากระทบ" ยังไม่หักตัวซ้ำข้ามองค์กร
- **บทเรียน:** **ช่องโหว่คลาสเดียวกันกับ TalkTalk เมื่อ 8 ปีก่อนเป๊ะ ๆ** — ซอฟต์แวร์คนละตัว คนละยุค แต่จุดที่พังคือจุดเดิม

แล้วทำไมมันถึงยังเกิดอยู่ อีกยี่สิบปีหลังมีทางแก้? มีสามคำตอบที่ใช้ได้จริงในงานประจำวัน:

1. **ทางแก้อยู่ในมือโปรแกรมเมอร์ ไม่ได้อยู่ในเครื่องมือ** — compiler ไม่เตือนว่า "บรรทัดนี้ต่อสตริงเข้าไปใน query" และภาษาไม่ได้บังคับให้คุณใช้ `?` · ทุกภาษาที่ต่อสตริงได้ ก็เขียนโค้ดพังแบบนี้ได้
2. **โค้ดเก่าและโค้ดที่สืบทอดมา** — TalkTalk พังที่หน้าเว็บจากระบบที่ซื้อต่อมาในปี 2009 · โค้ดที่ไม่มีใครดูคือที่ที่พัง
3. **"แค่ครั้งนี้ครั้งเดียว"** — ระบบสมัยใหม่เกือบทั้งหมดปลอดภัย จนกว่าจะมีคนเปิดทางออกฉุกเฉิน (**raw query** = เขียน SQL เองเต็ม ๆ ไม่ผ่านตัวช่วย) แล้วต่อสตริง "เพราะแก้เร็ว"

![timeline of SQL injection from 1998 to 2025 with defenses](/assets/diagrams/ep04-03-timeline-fix.svg)

ทั้งหมดข้างบนคือ "ความเข้าใจ" — แต่ความเข้าใจจะเชื่อได้จริงก็ต่อเมื่อเราลงมือ**รันเอง** หัวข้อถัดไปเราจะเขียนโปรแกรมตัวอย่างเล็ก ๆ ที่ต่อ SQLite จริง แล้วเทียบเวอร์ชันที่พังกับเวอร์ชันที่ปลอดภัยด้วยผลรันบนเครื่องคุณ

## 3. ลงมือทำ: เขียนโปรแกรมตัวอย่างเล็ก ๆ (CLI) ที่ต่อ SQLite จริง แล้วดูความต่าง

หัวข้อนี้คือส่วนที่สำคัญที่สุดของบท — เราจะ**รันจริง** ไม่ใช่แค่อธิบาย

> **หมายเหตุความปลอดภัย:** เดโมทั้งหมดรันในหน่วยความจำ (`:memory:`) ไม่เขียนไฟล์ฐานข้อมูล ไม่เชื่อมต่อเครือข่าย และไม่มี endpoint (จุดเชื่อมต่อที่โปรแกรมอื่นเรียกเข้ามาได้) ให้ยิงจากข้างนอก — เราเรียกฟังก์ชันของตัวเองด้วย payload ที่ฝังไว้ในโค้ด เพื่อเปรียบเทียบ **"ฐานข้อมูลตีความอะไร"** เท่านั้น

### 3.1 ตั้งที่ทำงาน

```bash
mkdir -p ~/security-lab/ep04 && cd ~/security-lab/ep04
go mod init ep04sqli
```

จากนั้นเขียนไฟล์ `sqli_demo.go` (โค้ดอยู่ในหัวข้อถัด ๆ ไป) แล้วให้ Go ดึง dependency ให้เอง:

```bash
go mod tidy
```

เราจะใช้ **modernc.org/sqlite** เป็น **driver** (ตัวกลางที่ Go ใช้คุยกับฐานข้อมูล — โค้ดเราเรียก `database/sql` แล้ว driver แปลเป็นคำสั่งของฐานข้อมูลจริงอีกที) — ตัวนี้เป็น **pure Go** คือไม่ต้องใช้ **cgo** (กลไกให้โค้ด Go เรียกโค้ด C) ทำให้เดโมรันได้ทุกเครื่องแบบเดียวกัน · ไฟล์ `go.mod` ของเราหลัง `go mod tidy` หน้าตาแบบนี้:

```go
module ep04sqli

go 1.26.0

require modernc.org/sqlite v1.60.1
```

**ผลรันขึ้นกับ OS แค่ไหน?** น้อยมาก — เดโมหลักเป็น pure Go และ driver พา SQLite engine (3.53.4) มาในตัว เวอร์ชัน engine จึงเท่ากันทุกแพลตฟอร์ม · ที่ต่างกันมีแค่ "เครื่องมือที่ต้องมี" โดยเฉพาะตอนรันการทดลองเทียบ driver แบบ cgo ในหัวข้อ 3.8 ③:

| OS | สิ่งที่ต้องมีก่อน | เดโมหลัก (`go run .`) | เทียบ driver แบบ cgo (`mattn_probe`) | `run_all.sh` |
|---|---|---|---|---|
| **Linux** | Go toolchain (จะถูกสลับอัตโนมัติถ้า `go.mod` ขอสูงกว่า) | รันได้ · ผลเท่ากัน | ต้องมี `CGO_ENABLED=1` + C compiler ใน `PATH` (เครื่องผู้เขียนใช้ Debian gcc 14.2.0) | `bash run_all.sh` |
| **macOS** | Go toolchain + C compiler (clang ที่มากับ Xcode Command Line Tools) | รันได้ · ผลเท่ากัน | ต้องมี `CGO_ENABLED=1` + C compiler ใน `PATH` | `bash run_all.sh` (bash ที่ macOS เป็น 3.2 — สคริปต์นี้ใช้ได้) |
| **Windows** | Go toolchain (ไม่ต้องมีอะไรเพิ่มสำหรับเดโมหลัก) | รันได้ · ผลเท่ากัน | ต้องมี `CGO_ENABLED=1` + gcc (เช่น MinGW-w64) มิฉะนั้นข้ามการทดลองนี้ได้ | ต้องรันผ่าน **Git Bash** หรือ **WSL** |

> เอกสารของ **go-sqlite3** ระบุตรง ๆ ว่าแพ็กเกจนี้เป็น **cgo** จึงต้องตั้ง `CGO_ENABLED=1` และมี `gcc` อยู่ใน `PATH` — และเราบันทึกไว้ใน `run_all.sh` ตรง ๆ ว่า `CGO_ENABLED=1 go run .` · ถ้าเครื่องคุณไม่มี C compiler การทดลองนี้จะคอมไพล์ไม่ผ่าน ซึ่งไม่กระทบเดโมหลัก (pure Go) เลย

> ผลรันที่ยกมาในบทนี้เป็นของ **Linux aarch64** — ตัวเลขทั้งหมดเป็นค่าคงที่ของเดโม (ไม่ใช่ค่าที่ขึ้นกับสถาปัตยกรรม) จึงเทียบได้ข้ามแพลตฟอร์ม · ถ้าคุณรันแล้วได้ **SQLite engine คนละเลข** ให้เช็คเวอร์ชันของ driver ก่อน (engine มาจาก driver ไม่ได้มาจาก OS)

### 3.2 ตาราง `users` — และสังเกตบรรทัดที่ "ถูก" ตั้งแต่ตรงนี้

ก่อนจะดูโค้ดที่พัง เรามาดูโค้ดที่**ไม่พัง**ก่อน เพื่อให้เห็นว่าความต่างมันเล็กแค่ไหน:

```go
func seed(ctx context.Context, db *sql.DB) error {
	stmts := []string{
		`CREATE TABLE users (
			id            INTEGER PRIMARY KEY,
			username      TEXT NOT NULL UNIQUE,
			password_hash TEXT NOT NULL,
			role          TEXT NOT NULL,
			api_key       TEXT NOT NULL
		)`,
		`CREATE TABLE canary (n INTEGER)`, // ตารางเหยื่อสำหรับทดลอง stacked query เท่านั้น
		`INSERT INTO canary (n) VALUES (1)`,
	}
	for _, s := range stmts {
		if _, err := db.ExecContext(ctx, s); err != nil {
			return err
		}
	}
	// ข้อมูล seed: password_hash เป็นสตริงสมมติ (ของจริงต้องเป็น hash ที่ช้าและมี salt ต่อผู้ใช้)
	users := []struct {
		id       int
		username string
		hash     string
		role     string
		apiKey   string
	}{
		{1, "alice", "hash-alice", "user", "key_alice_aaaa"},
		{2, "bob", "hash-bob", "user", "key_bob_bbbb"},
		{3, "admin", "hash-admin", "admin", "key_admin_TOP_SECRET"},
	}
	for _, u := range users {
		if _, err := db.ExecContext(ctx,
			"INSERT INTO users (id, username, password_hash, role, api_key) VALUES (?, ?, ?, ?, ?)",
			u.id, u.username, u.hash, u.role, u.apiKey); err != nil {
			return err
		}
	}
	return nil
}
```

> **ศัพท์ที่โผล่มาในโค้ดนี้:** ใน `CREATE TABLE` ข้างบน — **`PRIMARY KEY`** = กุญแจระบุแถวไม่ซ้ำ · **`NOT NULL`** = ห้ามว่าง · **`UNIQUE`** = ห้ามซ้ำ (เช่น username ซ้ำกันไม่ได้) · `password_hash` ไม่ได้เก็บรหัสผ่านจริง แต่เก็บ **hash** (ค่าที่คำนวณออกมาจากรหัสผ่าน — เก็บรหัสจริงลงฐานข้อมูลไม่ได้) คู่กับ **salt** (ค่าสุ่มเฉพาะผู้ใช้แต่ละคน เพื่อให้รหัสผ่านเดียวกันได้ hash ไม่เหมือนกัน) · ส่วนคำว่า **"hash ที่ช้า"** ในคอมเมนต์ไม่ได้หมายถึงโค้ดที่เขียนไม่ดี แต่หมายถึง**ตั้งใจเลือกอัลกอริทึมที่ใช้เวลานาน** เพื่อให้การเดารหัสแบบลองทีละตัว (brute force) แพงจนทำไม่ไหว · ส่วน **seed** ที่เห็นในคอมเมนต์ของโค้ดข้างบน = ข้อมูลตัวอย่างเริ่มต้นที่ใส่ให้ตาราง (ในเดโมนี้คือผู้ใช้ 3 คน: alice, bob, admin)

สามอย่างที่อยากให้สังเกต:

- `INSERT ... VALUES (?, ?, ?, ?, ?)` — แม้แต่การเขียนข้อมูลเข้า เราก็ใช้ `?` ทั้งหมด ไม่มีที่ไหนต่อสตริง
- ตาราง `canary` เป็น**ตารางเหยื่อ**ที่เราตั้งใจไว้ให้ทดลอง stacked query เท่านั้น (ชื่อเล่นว่า canary มาจาก "นกขมิ้นในเหมืองถ่านหิน" — เหมือนที่ตอนที่ 03 ใช้เรียกค่าเฝ้าดู) · เราจะไม่แตะตาราง `users` ในการทดลองที่อันตราย
- คอลัมน์ `api_key` เก็บ **API key** (สตริงลับที่โปรแกรมอื่นใช้ยืนยันตัวว่ามีสิทธิ์เรียกบริการของเรา แทนการส่งรหัสผ่านมาทุกครั้ง) — ของจริงต้องไม่หลุดออกมาแบบที่การโจมตี A5 ทำได้

### 3.3 ฝั่งที่พัง: ต่อสตริงเข้าไปใน query

นี่คือสองฟังก์ชันที่ผิด — และผมอยากให้คุณอ่านมันช้า ๆ เพราะมัน**ดูปกติมาก**:

```go
// craftLoginQueryVulnerable สร้างข้อความ query ด้วยการต่อสตริง — นี่คือ "บรรทัดที่ผิด"
func craftLoginQueryVulnerable(username, password string) string {
	return "SELECT id, username, role FROM users WHERE username = '" + username +
		"' AND password_hash = '" + password + "'"
}
```

```go
func vulnerableLoginUsers(ctx context.Context, db *sql.DB, username, password string) ([]string, error) {
	q := craftLoginQueryVulnerable(username, password)
	rows, err := db.QueryContext(ctx, q)
	if err != nil {
		return nil, err
	}
	defer rows.Close() // คืน connection เสมอ ไม่ว่าออกทางไหน
	var out []string
	for rows.Next() {
		var id int
		var uname, role string
		if err := rows.Scan(&id, &uname, &role); err != nil {
			return nil, err
		}
		out = append(out, fmt.Sprintf("#%d %s/%s", id, uname, role))
	}
	if err := rows.Err(); err != nil { // ต้องเช็ค ไม่งั้น error กลางทางหายเงียบ
		return nil, err
	}
	return out, nil
}
```

สังเกตว่าโค้ดนี้**ไม่ได้ทำอะไรผิดในเชิงวิศวกรรมเลย**: มันมี `context` (ไว้ยกเลิกงานที่ค้าง), มี `defer rows.Close()` (คืน connection ทุกเส้นทาง — connection = การเชื่อมต่อกับฐานข้อมูล), มีการเช็ค `rows.Err()` (ไม่ปล่อยให้ error ระหว่างทางหายเงียบ) — มันเป็นโค้ดที่ผ่าน code review ได้สบาย

**แต่มันพังทั้งดุ้น** เพราะบรรทัดเดียว: `craftLoginQueryVulnerable` ที่เอา `username` ไปต่อกับข้อความ SQL

> **บทเรียนเรื่องตำแหน่งของบั๊ก:** ช่องโหว่ security ไม่ได้อยู่ในโค้ดที่ "ผิดหลักวิศวกรรม" — มันอยู่ในโค้ดที่ถูกต้องทุกอย่าง **ยกเว้นความเชื่อเรื่องหนึ่ง** · ตรงนี้ความเชื่อที่ผิดคือ "input คือข้อมูล"

(ที่ต้องมี `context` กับ `defer` ในเดโมนี้ด้วย ไม่ใช่เพราะเกี่ยวกับ SQL injection (SQLi) — แต่เพราะเราเขียนตัวอย่างให้เป็นโค้ดที่**ยกไปใช้จริงได้** ไม่ใช่ตัวอย่างที่สอนนิสัยแย่ ๆ ติดตัวไป)

### 3.4 ฝั่งที่ถูก: ส่งค่าแยกจากคำสั่ง

เทียบกับเวอร์ชันที่แก้แล้ว — ต่างกันแค่เครื่องหมาย `?` กับตำแหน่งของ argument:

```go
// safeLoginUsers ส่งค่าแยกจากคำสั่ง: ? คือช่องที่ driver/ฐานข้อมูลรู้ว่า "ตรงนี้คือค่า"
func safeLoginUsers(ctx context.Context, db *sql.DB, username, password string) ([]string, error) {
	const q = "SELECT id, username, role FROM users WHERE username = ? AND password_hash = ?"
	rows, err := db.QueryContext(ctx, q, username, password)
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	var out []string
	for rows.Next() {
		var id int
		var uname, role string
		if err := rows.Scan(&id, &uname, &role); err != nil {
			return out, err
		}
		out = append(out, fmt.Sprintf("#%d %s/%s", id, uname, role))
	}
	return out, rows.Err()
}
```

**ความต่างทั้งหมดอยู่ที่สองบรรทัด:**
- `craftLoginQueryVulnerable(...)` → ประกอบข้อความเอง (query เปลี่ยนตาม input)
- `const q = ... ? ...` + ส่งค่าเป็น argument แยก → query **คงที่เสมอ** ไม่ว่า input จะเป็นอะไร

จำประโยคนี้ไว้: **"query ที่ปลอดภัยคือ query ที่ข้อความไม่เปลี่ยนตาม input"** ถ้าคุณทำให้ query ของคุณคงที่ได้ทุกที่ คุณก็ปิด SQL injection ได้เกือบทั้งหมด

รันเดโม (`go run .` ในโฟลเดอร์นั้น หรือ `bash run_all.sh` เพื่อรันทุกอย่างพร้อมกัน):

อ่านทั้ง 5 บรรทัดให้ครบ เพราะแต่ละบรรทัดสอนคนละอย่าง:

- **A1 — รหัสผ่านถูกต้อง:** ผ่านทั้งคู่ · สำคัญมาก เพราะมันพิสูจน์ว่าเวอร์ชันที่แก้แล้ว**ยังทำงานได้ตามปกติ** ไม่ได้ "ปฏิเสธทุกอย่างจนปลอดภัย" (นี่คือกับดักทางความคิดที่พบบ่อย: ทางแก้ security ที่ทำให้โปรแกรมใช้ไม่ได้ ไม่ใช่ทางแก้)
- **A2 — รหัสผ่านผิด:** ปฏิเสธทั้งคู่ · และเป็นหลักฐานว่า `?` **ไม่ได้** ทำให้ทุกอย่างผ่าน — มันยังตรวจ "ค่าจริง" ตามปกติ
- **A3 — `admin'--`:** concat **ผ่าน 1 แถว** (ล็อกอินสำเร็จ!) ส่วน `?` ปฏิเสธ · นี่คือ **authentication bypass** (การข้ามการตรวจสิทธิ์เข้าสู่ระบบ) ที่เกิดจากเครื่องหมาย `'` ตัวเดียว
- **A4 — `' OR '1'='1`:** concat คืน **3 แถว** — คือผู้ใช้ทุกคนในตาราง ทั้งที่รหัสผ่านที่กรอกไม่ตรงกับใครเลยแม้แถวเดียว · `?` ปฏิเสธ
- **A5 — `' UNION SELECT 99, (SELECT api_key FROM users WHERE role='admin'), 'leak'--`:** concat คืนแถวที่**ไม่ใช่ผู้ใช้เลย**: `#99 key_admin_TOP_SECRET/leak` — คอลัมน์ที่สองของคำสั่งคือ `username` แต่ค่าที่ได้คือ **API key ของ admin** · นี่คือการ**ขโมยข้อมูล**ที่ไม่ได้อยู่ในการออกแบบของระบบเลย

### 3.6 query ที่ถูกส่งเข้าฐานข้อมูลจริง ๆ — หน้าตามันเป็นแบบนี้

จุดที่คนเข้าใจยากที่สุดคือ "แล้วมันพังได้ยังไง" — คำตอบชัดขึ้นทันทีเมื่อเห็น**ข้อความจริง**ที่ไหลเข้าฐานข้อมูล (คำว่า **result set** ที่จะเจอในผลรันด้านล่าง = ชุดผลลัพธ์ ตารางผลลัพธ์ที่ query คืนมา):

```
┌─ 2) ข้อความ query ที่ vulnerable ส่งเข้าฐานข้อมูล (เต็ม ๆ ดิบ ๆ) ──────┐
--- A3 (username=admin'--) ---
SELECT id, username, role FROM users WHERE username = 'admin'--' AND password_hash = 'x'
--- A4 (username=' OR '1'='1) ---
SELECT id, username, role FROM users WHERE username = '' OR '1'='1' AND password_hash = '' OR '1'='1'
--- A5 (username=' UNION SELECT 99, (SELECT api_key FROM…) ---
SELECT id, username, role FROM users WHERE username = '' UNION SELECT 99, (SELECT api_key FROM users WHERE role='admin'), 'leak'--' AND password_hash = 'x'

input ไม่ได้ "อยู่ใน" query ในฐานะข้อมูล — มันกลายเป็นส่วนหนึ่งของไวยากรณ์:
   A3: เครื่องหมาย ' ปิดสตริงก่อนกำหนด แล้ว -- กลืนเงื่อนไขรหัสผ่านที่เหลือทั้งท่อน
   A4: เงื่อนไข OR ถูกประเมินเป็นจริง จนทุกแถวผ่านด่าน
   A5: UNION ต่อ result set ของผู้โจมตีเข้ากับของเดิม (ต้องมีจำนวนคอลัมน์เท่ากัน)
```

- **A3:** สังเกตว่า `'x'` ที่เราตั้งใจให้เป็น "รหัสผ่าน" ยังอยู่ครบในข้อความ — แต่มัน**อยู่หลัง `--`** ที่หมายความว่า "ไม่ต้องอ่านบรรทัดนี้ต่อ" มันจึงไม่ถูกประเมินเลย
- **A4:** `WHERE username = '' OR '1'='1' AND password_hash = '' OR '1'='1'` · ลำดับความสำคัญ (precedence) ของ SQL คือ `AND` ก่อน `OR` จึงอ่านเป็น `(username = '') OR ('1'='1' AND password_hash = '') OR ('1'='1')` — และพจน์ท้ายเป็นจริงเสมอ → **ทุกแถวผ่าน**
- **A5:** `UNION` เอา result set ของผู้โจมตี "ต่อท้าย" ของเรา · ข้อจำกัดเดียวคือ**จำนวนคอลัมน์ต้องเท่ากัน** — นี่คือเหตุผลที่นักโจมตีเริ่มต้นด้วยการเดาจำนวนคอลัมน์ (`ORDER BY 1`, `ORDER BY 2`, ... — `ORDER BY` = สั่งเรียงลำดับแถว) เพื่อให้ UNION ผ่าน

### 3.7 บทพิสูจน์ที่ผมคิดว่าสำคัญที่สุดของบทนี้

ถึงตรงนี้หลายคนอาจยังคิดว่า "ก็แค่แบนอักขระ `'` กับ `--` ก็จบ" · ต่อไปนี้คือการทดลองที่จะปิดประตูความคิดนั้น:

เราจะ**สมัครผู้ใช้จริง**โดยตั้งชื่อผู้ใช้ว่า `admin'--` (ด้วย parameterized `INSERT` เป็นเรื่องถูกต้องตามปกติ — การรับข้อมูลเข้าปลอดภัย) แล้วลองล็อกอินในชื่อของเขา ด้วยรหัสผ่านที่ถูกต้องของเขาเอง:

```
┌─ 3) บทพิสูจน์: input สตริงเดียวกัน ต่างกันที่ "ช่องทาง" ───────────────┐
สมัครผู้ใช้ชื่อ "admin'--" ด้วย parameterized INSERT (ข้อมูลถูกเก็บทั้งดุ้น)
ล็อกอินด้วย username="admin'--" + รหัสผ่านที่ถูกต้องของเขา:
  vulnerable (concat): 1 แถว (ผ่าน)  -> #3 admin/admin
  safe (?)           : 1 แถว (ผ่าน)  -> #20 admin'--/user
  สตริงเดียวกันเป๊ะ แต่:
    · concat ทำให้มันเป็นไวยากรณ์ -> ผู้ใช้คนนี้ล็อกอินเป็นตัวเองไม่ได้เลย
      แต่ 'ข้าม' เข้าไปในชื่อ admin แทน (เงื่อนไขรหัสผ่านถูกกลืนหายทั้งท่อน)
    · ? ทำให้มันเป็นค่า -> ได้แถวของตัวเองจริง ๆ แถวเดียว
```

อ่านผลรันนี้ช้า ๆ เพราะมันคือหัวใจของทั้งบท:

- **สตริงเดียวกันเป๊ะ** (`admin'--`) — ต่างกันแค่ "ช่องทาง" ที่มันเดินมา
- **concat** ทำให้มันกลายเป็นไวยากรณ์ → ผู้ใช้คนนี้**ล็อกอินเป็นตัวเองไม่ได้เลยแม้แต่ครั้งเดียว** เพราะ query ที่ถูกสร้างคือ `WHERE username = 'admin'` (ส่วนที่เหลือถูกคอมเมนต์) → มันจะ match แถวของ **admin ตัวจริง** (#3) เสมอ ไม่ว่าใครจะกรอกรหัสผ่านอะไรมา · ลองคิดตามในมุมของธุรกิจ: มีบัญชีหนึ่งที่ล็อกอินไม่ได้ตลอดกาล และบัญชีนั้นดันเป็น **ประตูหลังเข้า admin**
- **`?`** ทำให้มันเป็นค่า → ได้ **#20 admin'--/user** = แถวของตัวเองจริง ๆ แถวเดียว (เดโมจงใจให้ id = 20 เพื่อแยกออกจาก 1–3 ให้เห็นชัดว่าเป็นแถวใหม่ · และรหัสผ่านถูกตรวจ)

นี่คือคำตอบของคำถาม "แล้วแบน `'` หรือ escape มันได้ไหม?" — **escaped string ยังเป็น string** ที่มีเครื่องหมาย `'` ข้างใน และเมื่อมันถูก**ต่อ**เข้าไปใน query ที่ไหนสักแห่งในระบบ มันก็พังที่นั่น · การแบน `'` ในชื่อผู้ใช้ยังทำได้ แต่การแบน `'` ใน**ข้อความอิสระ** (textarea, API, comment) ทำไม่ได้ — และถ้าเราแบน `'` ทุกที่ ผู้ใช้ที่ชื่อมีเครื่องหมายนี้ตามธรรมชาติ (เช่น O'Brien) จะกรอกชื่อตัวเองไม่ได้เลย

### 3.8 กับดัก: ที่ ๆ การ escape ไม่ช่วยเลย

นี่คือส่วนที่ผมอยากให้คุณอ่านให้จบ เพราะมันคือเหตุผลที่ OWASP ถึงจัด "การ escape" เป็นตัวเลือกที่ **STRONGLY DISCOURAGED** (ไม่แนะนำอย่างแรง) · คำที่จะเจอในผลรันด้านล่าง: **allow-list** (รายการที่อนุญาต) = รายการค่าที่เราอนุญาตไว้ล่วงหน้า ทุกอย่างที่ไม่อยู่ในรายการถูกปฏิเสธ · คำย่อในผลรันด้านล่าง: **DB** = ฐานข้อมูล):

```
┌─ 4) injection ที่ไม่ต้องใช้เครื่องหมาย ' เลย (บริบทตัวเลข) ─────────────┐
  WHERE id = "2"                              -> 1 แถว (ผ่าน)
  WHERE id = "0 OR 1=1"                       -> 4 แถว (ผ่าน)
  WHERE id = "0 UNION SELECT api_key FROM users" -> 4 แถว (ผ่าน)
      ค่าที่หลุดออกมา: key_admin_TOP_SECRET, key_alice_aaaa, key_bob_bbbb, key_newuser
  บทเรียน: การ "escape เครื่องหมาย ' " ไม่พอกัน — บริบทตัวเลขไม่มีสตริงให้ปิด
           และบริบทชื่อคอลัมน์ก็ไม่ใช่บริบทของค่า
           ที่กันได้จริงคือ ? สำหรับ "ค่า" และ allow-list สำหรับ "โครงสร้าง"

┌─ 5) โครงสร้าง query (ORDER BY): ? ใช้แทนไม่ได้ และต้อง allow-list ──────┐
  ORDER BY id (concat)                    -> alice, bob, admin, admin'--
  ORDER BY ? (param = "id")                -> admin, admin'--, alice, bob
     ^ ไม่เรียงอย่างด้านบน: ? ถูกมองเป็น "ค่าคงที่" ไม่ใช่ชื่อคอลัมน์
       (ค่าที่เรียงออกมาเป็นลำดับของ index จริง ไม่ใช่ลำดับที่เราสั่ง)
  safeOrderBy("id")  (allow-list)          -> alice, bob, admin, admin'--
  safeOrderBy("username; DROP TABLE users --") -> (ว่าง) -> error: ชื่อคอลัมน์ไม่อยู่ใน allow-list
     ^ allow-list ปฏิเสธตั้งแต่ยังไม่สร้าง query — ไม่ต้องพึ่ง parser ของ DB เลย
  ทดลอง stacked query "SELECT 1; DROP TABLE canary": ตาราง canary ถูก DROP จริง -> driver ยอมรับหลายคำสั่งในครั้งเดียว (อันตรายมาก)
```

สามกับดักที่โผล่มาในผลรันนี้:

**① บริบทตัวเลข — `WHERE id = ` + input**

ไม่มีเครื่องหมาย `'` ให้ escape เลย เพราะไม่มีสตริงอยู่ในบริบทนั้น · `0 OR 1=1` คืนทุกแถว (4 แถว) และที่ร้ายกว่าคือ `0 UNION SELECT api_key FROM users` — ดึง **API key ของทุกคนออกมาทางคอลัมน์เดียวที่ query นี้มองเห็น** · ในผลรันด้านบน ค่า `key_newuser` ที่หลุดมาด้วยคือ api_key ของผู้ใช้ `admin'--` (id 20) ที่เราสมัครไว้ในหัวข้อ 3.7 · สังเกตว่าจำนวนคอลัมน์ต้องตรง (1 คอลัมน์) มันจึงผ่าน

ทางแก้สำหรับบริบทนี้คือ **แปลงชนิดข้อมูลและตรวจค่า** เช่นรับเป็น `int` ไม่ใช่ `string` — แยกให้ชัดเป็นสองกรณี:

- **`strconv.Atoi` แปลงไม่ผ่าน** (เช่นค่า `"0 OR 1=1"` ไม่ใช่ตัวเลข) → **ปฏิเสธคำขอนั้นไปเลย** = ปลอดภัย (นี่คือกรณีที่เกิดกับ payload นี้จริง ๆ)
- **`strconv.Atoi` แปลงผ่าน** → ต้องใช้**ค่าที่แปลงเป็น int แล้ว**ส่งต่อเข้า query (เช่น `fmt.Sprintf("%d", parsedValue)`) — **ไม่ใช่สตริงเดิม**ที่ผู้ใช้กรอก

**② ชื่อคอลัมน์ (โครงสร้าง) — `ORDER BY ` + input**

นี่คือจุดที่**หลายคนเข้าใจผิดที่สุด**: ตอนนี้ `?` **ใช้แทนไม่ได้** เพราะ `ORDER BY ?` จะถูกมองว่า "เรียงตามค่าคงที่" ไม่ใช่ "เรียงตามคอลัมน์ชื่อนี้" — ผลรันพิสูจน์ให้เห็นแล้วว่าลำดับที่ออกมา**ไม่ได้ขึ้นกับสิ่งที่เราสั่งเลย** — เพราะ `ORDER BY` ค่าคงที่ทำให้ทุกแถว tie กัน SQLite จึงคืนแถวตามลำดับที่ query planner เลือก scan ซึ่งกรณีนี้คือ auto-index บน `username` (เกิดจาก `UNIQUE`) จึงออกมาเรียงตามชื่อ: admin, admin'--, alice, bob

คำตอบที่ถูกคือ **allow-list** (รายการที่อนุญาต — ตรงข้ามกับ deny list ที่ไล่แบนของที่ไม่ต้องการ) · ดูโค้ดจริง:

```go
// safeOrderBy ใช้ allow-list กับค่าที่เป็น "โครงสร้าง" (ชื่อคอลัมน์ ฯลฯ)
func safeOrderBy(ctx context.Context, db *sql.DB, col string) ([]string, error) {
	if !sortableColumns[col] { // ปฏิเสธตั้งแต่ยังไม่สร้าง query
		return nil, fmt.Errorf("ชื่อคอลัมน์ไม่อยู่ใน allow-list")
	}
	rows, err := db.QueryContext(ctx, "SELECT username FROM users ORDER BY "+col)
	if err != nil {
		return nil, safeError("query", err)
	}
	defer rows.Close()
	var out []string
	for rows.Next() {
		var s string
		if err := rows.Scan(&s); err != nil {
			return out, safeError("scan", err)
		}
		out = append(out, s)
	}
	return out, safeError("rows", rows.Err())
}
```

โดยที่ `sortableColumns` คือ `map[string]bool{"id": true, "username": true, "role": true}` · สังเกตว่าตรงนี้เรายัง**ต่อสตริงอยู่** — แต่ต่อได้ปลอดภัย เพราะค่าที่ต่อผ่านการตรวจกับรายการที่อนุญาตแล้ว · หลักการคือ:

> **"ค่า" ใช้ `?` · "โครงสร้าง" (ชื่อตาราง/คอลัมน์/ทิศการเรียง) ใช้ allow-list · ไม่มีที่ที่สาม**

และสังเกตว่า allow-list ปฏิเสธ **ตั้งแต่ยังไม่สร้าง query** — เราไม่ต้องพึ่ง parser ของฐานข้อมูลให้มาปฏิเสธให้ · เป็นการป้องกันเชิง "ไม่ให้เกิด" ไม่ใช่ "เกิดแล้วค่อยจับ"

**③ Stacked query — `SELECT 1; DROP TABLE canary`**

ผลรันบอกว่าทั้ง **modernc.org/sqlite** และ **github.com/mattn/go-sqlite3** **รันคำสั่งที่สองจริง** (ตาราง `canary` ถูก DROP ไป) · นี่คือบทเรียนสำคัญ: **อย่าพึ่งว่า driver จะกันให้** — บาง driver/บาง config ปฏิเสธหลายคำสั่งในครั้งเดียว บางตัวยอม และพฤติกรรมนี้เปลี่ยนได้ตามเวอร์ชัน · การกันที่ถูกคือกันที่**การต่อสตริง** ไม่ใช่กันที่คำสั่ง `;` (เพราะ `;` ก็เป็นอักขระที่ชอบด้วยกฎหมายในข้อมูลทั่ว ๆ ไป)

> **สรุปหัวข้อ 3.8:** ทั้งสามกับดักนี้พิสูจน์ว่า **"escape ให้ครบ" ไม่ใช่กลยุทธ์ที่ยั่งยืน** เพราะมันขึ้นกับบริบท ขึ้นกับ engine ของฐานข้อมูล (DB) ขึ้นกับ driver — และขึ้นกับว่าโปรแกรมเมอร์คนถัดไปจำได้ครบหรือเปล่า · ส่วน `?` ใช้ได้เหมือนกันทุกบริบทที่ไวยากรณ์คาดว่าเป็น**ค่า** ซึ่งคือเกือบทั้งหมดของที่ที่ข้อมูลจากผู้ใช้ไปถึง

### 3.9 second-order injection: ตรวจตอนรับเข้า ยังไม่พอ

กับดักสุดท้าย และเป็นตัวที่คนพลาดมากที่สุดในงานจริง — **second-order injection** (การโจมตี "รอบสอง": ข้อมูลที่ผ่านการตรวจอย่างดีตอนรับเข้า กลายเป็นอันตรายตอนถูกนำมาใช้):

```
┌─ 6) second-order injection: ตรวจตอน "รับเข้า" ยังไม่พอ ───────────────┐
  ค่าที่เก็บในฐานข้อมูล (insert ด้วย ? — ปลอดภัยตอนรับเข้า): "alice' OR '1'='1"
  query รอบสอง (concat ค่าที่ "เคยตรวจแล้ว"):
    SELECT count(*) FROM users WHERE username = 'alice' OR '1'='1'
  -> count(*) = 5 แถว (ถ้าข้อมูลถูกมองเป็นค่าต้องได้ 1)
  -> ข้อมูลที่ถูกต้องตอน "รับเข้า" กลายเป็นไวยากรณ์ตอน "อ่านออกมาใช้"
     ความปลอดภัยจึงขึ้นกับทุกจุดที่ "ต่อ" ข้อมูล ไม่ใช่จุดที่รับข้อมูล
```

เราสมัครผู้ใช้ชื่อ `alice' OR '1'='1` ด้วย `?` (ปลอดภัยสมบูรณ์ตอนรับเข้า — ข้อมูลถูกเก็บทั้งดุ้น) แล้วมีโค้ดอีกที่หนึ่ง**อ่านชื่อนั้นออกมา**และเอาไปต่อกับข้อความ SQL · ผลคือ `count(*)` คืน 5 แถว (คือทุกแถวในตาราง) แทนที่จะเป็น 1

จุดสำคัญ: **ไม่มีที่ไหนในระบบนี้ที่ "validate ไม่ดี"** — ที่ผิดคือมี**จุดหนึ่ง**ที่ต่อข้อมูลเข้าไปใน query · และถ้าคุณมี 500 ไฟล์ในโปรเจกต์ ที่ที่ผิดเพียงจุดเดียวนั้นก็เพียงพอ

**ปฏิบัติ:** ในโค้ดที่คุณดูแล ให้ค้นหา**ทุกที่**ที่มี `+` อยู่ข้าง ๆ คำว่า `SELECT`/`INSERT`/`UPDATE`/`DELETE` (หรือ template string ที่มี SQL) แล้วเปลี่ยนให้เป็น `?` ทั้งหมด — นี่คือ refactor ที่ให้ผลตอบแทนสูงที่สุดในสายงานนี้

### 3.10 ORM: ช่วยจริง แต่ไม่ใช่ยาครอบจักรวาล

**ORM** (Object-Relational Mapping — library ที่แปลง "วัตถุในภาษาโปรแกรม" เป็น "แถวในฐานข้อมูล" ให้เรา เช่น GORM ใน Go, SQLAlchemy ใน Python, ActiveRecord ใน Ruby) ช่วยลด SQLi ได้เพราะ:

- **เส้นทางปกติของมันสร้างคำสั่งแบบมี placeholder ให้เอง** — คุณเขียน `db.Where("username = ?", name).First(&u)` แล้วมันประกอบเป็น query ที่มี `?` ให้ ไม่เปิดโอกาสให้คุณเผลอต่อสตริง
- **มันไม่ให้คุณเขียน SQL เองในเส้นทางปกติ** — เราเรียก "โครงสร้างที่ป้องกันได้เพราะบังคับทางเดิน" แบบนี้ว่า **secure by default** (ปลอดภัยตั้งแต่ค่าปริยาย)

แต่มัน**ไม่ใช่ยาครอบจักรวาล** เพราะ:

1. **raw query ที่ ORM เปิดให้คือประตูหลัง** — ทุก ORM มีทางออกฉุกเฉิน (`db.Raw(...)`, `.Extra(...)`, `RawSQL`) และนั่นคือจุดที่การต่อสตริงกลับมาทันที · ผลรันในหัวข้อ 3.8 (ชื่อคอลัมน์ใส่ `?` ไม่ได้) ตรงกับปัญหานี้เป๊ะ: คนมักโทษว่า "ORM ไม่มีที่ให้ใส่ชื่อคอลัมน์" จึง "ต่อเอง" แล้วพัง
2. **โครงสร้าง (ชื่อตาราง/คอลัมน์/ทิศเรียง/`LIMIT` แบบไดนามิก — `LIMIT` = จำกัดจำนวนแถวที่คืน)** ยังต้อง allow-list ด้วยมือเสมอ — ไม่ว่าใช้ ORM หรือไม่
3. **มันป้องกันที่ "ทางเดิน" ไม่ได้ป้องกันที่ "คน"** — ถ้าทีมคุณมีคนหนึ่งที่ "ขอแก้เร็ว ๆ" แล้วเปิด raw query จากค่าใน request, ORM ที่เหลือทั้งโปรเจกต์ก็ไม่ช่วยอะไร

> **วิธีคิดที่ผมแนะนำ:** ORM คือ**เข็มขัดนิรภัย** ไม่ใช่**เบรก** · เข็มขัดช่วยให้คุณรอดเมื่อเกิดเหตุ และมันช่วยจริง ๆ — แต่ไม่มีใครออกแบบรถโดยวางแผนจะไม่ใช้เบรกเพราะมีเข็มขัด

### ระดับ Drill (5–10 นาที)

1. **อธิบายด้วยคำของคุณเอง** ว่าทำไม `SELECT ... WHERE username = '` + input + `'` ถึงพัง แต่ `SELECT ... WHERE username = ?` ถึงไม่พัง — คำตอบต้องพูดถึง **parser** และคำว่า **"compile คำสั่งก่อน แล้วค่อยผูกค่า"** ไม่ใช่แค่พูดว่า "เพราะ `?` ปลอดภัย"
2. จากผลรัน A3: อธิบายว่าทำไม `admin'--` ถึงล็อกอินผ่าน ทั้งที่รหัสผ่าน `x` ไม่ตรงกับใครเลย (ตอบให้ครบทั้งบทบาทของ `'` และ `--`)
3. จากผลรัน A5: ค่าที่หลุดออกมาคือ `key_admin_TOP_SECRET` ในคอลัมน์ `username` — อธิบายว่าทำไมมันต้องมี **จำนวนคอลัมน์เท่ากัน** จึงจะ UNION ผ่าน
4. จากผลรันหัวข้อ 3.7 อธิบายให้ได้ว่า **ทำไมผู้ใช้ที่ชื่อ `admin'--` ถึงล็อกอินเป็นตัวเองไม่ได้เลย** ในเวอร์ชัน concat (ใบ้: มันไป match แถวไหนแทน)
5. จากผลรันหัวข้อ 3.8: ยก **สองบริบท** ที่การ escape เครื่องหมาย `'` ไม่ช่วยเลย พร้อมอธิบายว่าทำไม

### ระดับ Mini-project (30–60 นาที)

1. **ทำให้ query ที่ไม่คงที่ ให้กลายเป็นคงที่ทั้งไฟล์** — เอา `vulnerableLoginUsers`, `vulnerableUserByID` และ `vulnerableOrderBy` ในไฟล์ `sqli_demo.go` มาเขียนใหม่ แล้วพิสูจน์ด้วยเทสต์ว่า **payload ทั้ง 5 ตัวใน A1–A5 ให้ผลเหมือนกันทั้งเวอร์ชัน vulnerable-vs-safe** (คือ safe ต้องได้ 1/0/0/0/0) · เป้าหมายไม่ใช่ "ทำให้ payload ไม่ผ่าน" แต่คือ **"ทำให้ query คงที่"** — ทั้งสองอย่างต่างกันตรงที่อันแรกอาจพังกับ payload ที่ 6
2. **เขียน allow-list สำหรับการเรียงลำดับแบบมีทิศทาง** — ต่อยอด `safeOrderBy` ให้รับ `"id desc"` ได้ด้วย โดย**ห้ามแยกด้วยช่องว่างแล้วต่อกลับ** (นั่นเป็นกับดัก) ให้ใช้ `map` ที่แมปสตริงที่อนุญาตเต็ม ๆ ไปยัง SQL fragment ที่กำหนดไว้ตายตัว เช่น `"id desc" -> "id DESC"` · แล้วเขียนเทสต์ที่ยืนยันว่า `"id; DROP TABLE users"` และ `"id DESC, (SELECT 1)"` ถูกปฏิเสธ
3. **หา SQLi ในโค้ดของคุณเอง (หรือของทีม) แล้วรายงาน** — ใช้ `grep -rn` หาที่มีการต่อสตริงในบริบท SQL (คำว่า `SELECT|INSERT|UPDATE|DELETE` ใกล้ ๆ เครื่องหมาย `+` หรือ `fmt.Sprintf`) · เขียนรายงานสั้น ๆ: ไฟล์, บรรทัด, จุดที่ข้อมูลเข้ามา (source), จุดที่ข้อมูลไปถึง query (sink), และวิธีแก้ · **อย่าเพิ่งแก้** — การหาให้ครบก่อนแก้คือทักษะที่สำคัญกว่าการแก้เร็ว
4. **ทดลอง second-order injection แบบครบวง** — เขียนโปรแกรม Go เล็ก ๆ ที่ (ก) รับชื่อผู้ใช้ด้วย parameterized `INSERT` (ข) มีฟังก์ชันรายงานที่อ่านชื่อนั้นออกมาแล้วต่อสตริงเพื่อดึงสถิติ (ค) พิสูจน์ว่าคุณสามารถทำให้รายงาน `count(*)` คืนทุกแถว · แล้วแก้ด้วย `?` พร้อมเทสต์กันการถอยหลัง · นี่คือ **regression test** (เทสต์กันบั๊กเดิมกลับมา) ที่ควรมีติดโปรเจกต์จริง

## 5. สรุปตอนที่ 04

- **แก่นของเรื่อง:** SQL query คือ**ข้อความ**ที่ parser ตีความใหม่ทุกครั้ง และ parser ไม่รู้จักความต่างระหว่าง "ข้อมูลที่ผู้ใช้กรอก" กับ "ไวยากรณ์ที่ผู้เขียนตั้งใจ" — เมื่อไหร่ก็ตามที่เราต่อ input เข้าไปใน query เรากำลังให้ผู้ใช้เขียนไวยากรณ์ของเราได้
- **4 หน้าตาของ input ที่กลายเป็นไวยากรณ์:** tautology (`' OR '1'='1`) · comment (`admin'--`) · UNION (`' UNION SELECT ...--`) · stacked query (`1; DROP TABLE ...`) — ทั้งสี่แบบสาธิตจริงในเดโมของบทนี้
- **25 ธันวาคม 1998** — Phrack ฉบับที่ 54 บทความ *NT Web Technology Vulnerabilities* โดย **rain.forest.puppy** (= **Jeff Forristal**) พูดถึงเทคนิคนี้ **โดยไม่ได้ใช้คำว่า "SQL injection" เลย** · ชื่อคลาสอย่างเป็นทางการวันนี้คือ **CWE-89: Improper Neutralization of Special Elements used in an SQL Command**
- **สถานะปัจจุบัน:** **OWASP Top 10:2021** → injection ที่ **A03** (33 CWE; **94.04%** คือค่า *Max Coverage* = สัดส่วนแอปที่ถูกตรวจ*หา* injection ไม่ใช่สัดส่วนที่พบ · อัตราที่*พบ*จริงสูงสุดคือ **19.09%**) · **CWE Top 25 ประจำปี 2025** → CWE-89 อันดับ **2** (ขยับขึ้นจากอันดับ 3)
- **ภัยจริง:** **TalkTalk (2015)** — ใช้ `sqlmap` ยิงเข้าหน้าเว็บที่สืบทอดมาจากการซื้อกิจการ ข้อมูลลูกค้า ~157,000 รายหลุด มีการโจมตีสำเร็จก่อนหน้าแล้ว 2 ครั้ง ICO ปรับ £400,000 · **MOVEit Transfer (2023)** — SQL injection zero-day **CVE-2023-34362** ถูกใช้ติดตั้ง web shell **LEMURLOOT** (`human2.aspx`) · ยอดนับสาธารณะ ณ 28 มิ.ย. 2024 = **2,773 องค์กร / 95,788,491 คน**
- **ทางแก้ที่ถูก:** ส่ง**ค่า**แยกจาก**คำสั่ง**ด้วย `?` (prepared statement / parameterized query) · สำหรับ **โครงสร้าง** (ชื่อคอลัมน์/ทิศเรียง) ใช้ **allow-list** เพราะ `?` ใช้แทนไม่ได้ — เดโมพิสูจน์แล้วว่า `ORDER BY ?` ไม่เรียงตามที่สั่ง · **การ escape เป็นทางเลือกที่ไม่แนะนำ** (OWASP: STRONGLY DISCOURAGED) เพราะไม่ครอบคลุมบริบทตัวเลข ชื่อคอลัมน์ และ second-order
- **ORM** ช่วยเรื่องนี้จริงในเส้นทางปกติ (สร้าง placeholder ให้เอง) แต่ **raw query ที่มันเปิดให้คือประตูหลัง** และโครงสร้างยังต้อง allow-list เอง — ORM คือเข็มขัดนิรภัย ไม่ใช่เบรก
- **บนเครื่องของคุณ** เดโมนี้พิสูจน์กับของจริงว่า concat คืนแถวใน **4 จาก 5 กรณี** (รวม `1 + 0 + 1 + 3 + 1 = 6 แถว` — เคส A2 รหัสผ่านผิดจึงไม่คืนแถวเลย) ในขณะที่ `?` คืนแค่แถวที่รหัสผ่านถูกจริง (1 แถว) · และผู้ใช้ที่ชื่อ `admin'--` ล็อกอินเป็นตัวเองไม่ได้เลยในเวอร์ชัน concat แต่ได้แถวของตัวเองพอดีในเวอร์ชัน `?`
- **คำถามที่ควรถามตัวเองก่อนปิดบทนี้:** *"ในโค้ดที่ฉันเขียนล่าสุด มีที่ไหนที่ฉันให้ข้อมูลจากข้างนอกกำหนด **โครงสร้าง** ของคำสั่ง (ไม่ใช่แค่ค่า) — และฉันตรวจมันด้วย allow-list แล้วหรือยัง"* · คำถามนี้คือคำถามเดียวกับที่บทความฉบับคริสต์มาสปี 1998 เขียนออกมาเป็นครั้งแรก

ตอนหน้า (ตอนที่ 05) เราจะพาคำถามเดิม — *"ข้อมูลของฉันกลายเป็นคำสั่งของ interpreter ตอนไหน"* — ไปถาม **interpreter อีกตัวหนึ่ง** ที่ทุกคนมีอยู่ในเครื่องแล้ว: **browser** · นั่นคือ **XSS + CSRF** (1999–) เรื่องที่ input ของเราไม่ได้กลายเป็นไวยากรณ์ของฐานข้อมูล แต่กลายเป็น **สคริปต์ที่รันในเบราว์เซอร์ของคนอื่น** และเราเคยเห็นแล้วในอดีตว่ามันแพร่เร็วแค่ไหนเมื่อไม่มีอะไรกัน · ทางแก้ที่ตามมาก็ยังเป็นตระกูลเดิม: บังคับขอบเขตให้ชัด (same-origin policy), จำกัดว่าอะไรจะรันได้ (CSP) และทำให้ข้อมูลที่สำคัญอ่านไม่ได้จากสคริปต์ (HttpOnly cookie) — แยกข้อมูลออกจากคำสั่ง ในบ้านหลังใหม่

ระหว่างรอ ลองกลับไปดูโค้ดที่คุณเขียนล่าสุดอีกครั้ง แล้วถามว่า *"ตรงไหนที่ฉันเชื่อข้อมูลจากข้างนอกมากเกินไป — และถ้ามันเป็นอันตราย มันจะเริ่มจากบรรทัดไหน"*

- **ความปลอดภัยของเดโม:** เดโมทั้งหมดรันใน **หน่วยความจำ (`:memory:`)** ไม่มีไฟล์ฐานข้อมูล ไม่มีการเชื่อมต่อเครือข่าย ไม่มี endpoint ที่ยิงจากภายนอกได้ และไม่มี argument ให้ยิงใส่เป้าใด ๆ — payload ทั้งหมดเป็นค่าคงที่ที่เขียนไว้ในโค้ด (เพื่อให้ผลรันซ้ำได้) · การทดลอง **stacked query** ใช้ตารางเหยื่อชื่อ `canary` ที่สร้างขึ้นเพื่อการนี้โดยเฉพาะ **ไม่แตะตาราง `users`** · ส่วน ORM เราไม่ได้ติดตั้ง ORM จริงในบทนี้ — หัวข้อ 3.10 เป็นการอธิบายหลักการ โดยอ้างข้อความจาก OWASP ไม่ใช่ผลรัน

- **มาตรฐานและตัวเลขที่อ้าง:** **CWE-89 "Improper Neutralization of Special Elements used in an SQL Command ('SQL Injection')"** อยู่อันดับ **2** ของ **CWE Top 25 Most Dangerous Software Weaknesses ประจำปี 2025** (อันดับปีก่อนคือ 3) และมี CVE ใน KEV 4 รายการ — <https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html> · **OWASP Top 10:2021 A03 Injection** มี CWE ที่แมปทั้งหมด 33 ตัว และ OWASP รายงาน **Max Coverage 94.04%** = สัดส่วนของแอปที่ถูก**ตรวจหา** injection (ไม่ได้แปลว่า 94% *พบ* ช่องโหว่) ขณะที่ **max incidence 19.09%** คืออัตราที่*พบ*จริง (ค่าเฉลี่ย 3.37%, รวม 274,228 ครั้ง) — <https://owasp.org/Top10/2021/A03_2021-Injection> · ในอดีต injection อยู่อันดับ 1 ของ Top 10 ในฉบับ 2010, 2013 และ 2017 (ยืนยันจากหน้าราชการของ OWASP: <https://owasp.org/www-project-top-ten/2017/A1_2017-Injection>) · ส่วนการจัด "escaping" เป็น *Defense Option 4: STRONGLY DISCOURAGED* และแนวปฏิบัติ allow-list สำหรับค่าที่เป็นโครงสร้าง มาจาก **OWASP SQL Injection Prevention Cheat Sheet** — <https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html> · ส่วนประวัติของ **OWASP Top 10 ฉบับแรก (2003)** ที่จัด "Injection Flaws" ไว้ที่ **A6** ตรวจจากสไลด์ OWASP Belgium Chapter (2005) ที่แสดงรายการ Top 10 ชุดเดียวกัน — <https://owasp.org/www-chapter-belgium/assets/2005/2005-09-28/OWASP_Belgium_Chapter_Meeting_-_Leuven_-_28_Sep_2005_-_3_OWASP_Top_10_-_Panel.pdf>
- **ภัยจริงสองกรณี** ตรวจกับแหล่งปัจจุบันเมื่อ **2026-10-12**: **TalkTalk** — การโจมตีเกิด 15–21 ตุลาคม 2015, ICO ปรับ **£400,000** (ประกาศ 5 ตุลาคม 2016) ระบุว่าผู้โจมตีใช้ **sqlmap** และ "user input was not validated", กระทบลูกค้าราว **157,000 ราย** (ข้อมูลบัญชีธนาคารกว่า 15,000 ราย), มีการโจมตีสำเร็จก่อนหน้า 2 ครั้ง (17 กรกฎาคม และ 2–3 กันยายน 2015) ผ่านช่องโหว่เดิม โดยหน้าเว็บที่พังสืบทอดมาจากการซื้อกิจการ Tiscali UK ในปี 2009 — <https://ico.org.uk/about-the-ico/news-and-events/news-and-blogs/2016/10/talktalk-gets-record-400-000-fine-for-failing-to-prevent-october-2015-attack/> · **MOVEit Transfer** — CISA/FBI joint advisory **AA23-158A** ระบุการโจมตีเริ่ม **27 พฤษภาคม 2023** ด้วย SQL injection zero-day **CVE-2023-34362**, ติดตั้ง web shell ชื่อ **LEMURLOOT** ที่ปลอมชื่อไฟล์เป็น `human2.aspx`, และ CISA เพิ่มเข้าทะเบียน **KEV** เมื่อ **2 มิถุนายน 2023** — <https://www.cisa.gov/news-events/cybersecurity-advisories/aa23-158a> · ยอดนับสะสมสาธารณะ **2,773 องค์กร / 95,788,491 คน** มาจาก **Emsisoft** ข้อมูล ณ **28 มิถุนายน 2024** ซึ่งระบุชัดว่าเป็นยอด "รายงานว่ากระทบ" **ยังไม่หักคนซ้ำ** ข้ามองค์กร — <https://www.emsisoft.com/en/blog/44123/unpacking-the-moveit-breach-statistics-and-analysis>
- **การทดลองของเราเองเรื่อง driver:** ผลรันในบทนี้ยืนยันว่า **ทั้ง modernc.org/sqlite v1.60.1 และ github.com/mattn/go-sqlite3 v1.14.52 รันคำสั่งที่สองในครั้งเดียวจริง** (`SELECT 1; DROP TABLE canary` ทำให้ตาราง `canary` หายไป) · เราจงใจสรุปให้แคบตามที่วัดได้ — **ไม่ได้** อ้างว่า driver อื่นหรือเวอร์ชันอื่นทำแบบเดียวกัน · บทเรียนที่ถูกคือ **อย่าพึ่ง driver ให้กัน stacked query** ให้กันที่การไม่ต่อสตริง
- ภาพ SVG ทั้งสามภาพในตอนนี้สร้างจากสคริปต์ `security/code/ep04/gen_svgs.py` ที่ดึงตัวเลขจาก `out/` โดยตรง (มี `assert` ตรวจค่าที่ parse ได้ว่าตรงกับที่คาด) และผ่านประตูตรวจ `check_svg_readability.py` (วัดความกว้างข้อความจริงเทียบขอบ viewBox ตรวจข้อความซ้อนกัน) รวมทั้งตรวจด้วยตาจากการ render จริงด้วย `rsvg-convert`
- **จริยธรรม (ย้ำอีกครั้ง — สำคัญที่สุด):** บทนี้สอนกลไกของ SQL injection ตรง ๆ แต่ **ทุกเดโมรันในหน่วยความจำของโปรแกรมตัวเอง ไม่แตะระบบ ไฟล์ หรือเครือข่ายใด ๆ** · การนำเทคนิคในบทนี้ (tautology, comment, UNION, stacked query, second-order) ไปใช้กับระบบที่คุณไม่ได้เป็นเจ้าของหรือไม่ได้รับอนุญาตเป็นความผิดทางกฎหมายในแทบทุกประเทศ · **ทำใน environment ที่คุณควบคุมเองเท่านั้น** (เครื่องตัวเอง, VM, container หรือ lab ที่ตั้งใจให้ทดลอง) · ไฟล์เดโมหลักของบทนี้ (**sqli_demo.go** และ **mattn_probe/probe.go**) มี label **"ห้ามใช้จริงกับระบบของคนอื่น"** กำกับไว้ที่หัวไฟล์แล้ว
