# finite automata → regular language — regex มาจากไหน (ตอนที่ 22) — CS Fundamentals: จาก 0 สู่พื้นฐานที่แท้จริง

ตอนที่ 21 เราสร้าง shell จิ๋วที่ **แยกคำ (tokenize)** คำสั่งผู้ใช้ด้วยการตัดที่ช่องว่าง — วิธีนั้นใช้ได้เพราะภาษาของ shell ง่ายสุด ๆ แต่ลองคิดดูว่าโปรแกรมจะรู้ได้ยังไงว่า `x2 := 42` มีชิ้นส่วนอะไรบ้าง (ชื่อตัวแปร? เครื่องหมาย? ตัวเลข?) หรือจะรู้ยังไงว่า `"192.168.1.7:8080"` เป็นที่อยู่ที่ถูกต้อง นี่คือปัญหาชุดเดียวกันหมด: **"สตริงนี้ตรงกับรูปแบบที่กำหนดไหม"**

และเครื่องมือที่เราทุกคนใช้ตอบคำถามนี้คือ **regex** (regular expression = นิพจน์ปรกติ — รูปแบบข้อความย่อ ๆ อย่าง `^[a-z]+[0-9]*$`) แต่บทนี้จะไม่สอน "ใช้ regex ยังไง" — บทนี้จะตอบว่า **regex มันคืออะไรกันแน่ และมันทำงานยังไง**

คำถามของบทนี้มีข้อเดียว:

> **เวลาเราเขียน regex หนึ่งบรรทัด โปรแกรมข้างในทำอะไรกับมัน? และทำไม"บาง regex"ถึงทำให้โปรแกรมค้างได้?**

คำตอบคือ: regex เป็นแค่ **สัญกรณ์ย่อ** ของสิ่งที่เรียกว่า **เครื่องสถานะจำกัด (finite automaton)** — เครื่องที่ไม่มีอะไรเลยนอกจาก "สถานะ" กับ "ลูกศร" (ไม่มีหน่วยความจำ ไม่มีการนับ ไม่มีตัวแปร) และ "ค้างได้" เพราะเครื่องยนต์ที่รันมันอาจถูกสร้างแบบผิดหลักทฤษฎี

ทุกตัวเลขในบทนี้มาจากการรันจริงบนเครื่องเรา (Raspberry Pi 5 Model B · Linux 6.18.39+rpt-rpi-2712 aarch64 · **Go 1.24.4** · RAM 7.9 GiB) — โค้ดทั้งหมดอยู่ที่ `course/code/ep22/` ผลรันดิบอยู่ที่ `course/code/ep22/out/` และรันซ้ำได้ทั้งหมดด้วย `bash run_all.sh`

> **คำศัพท์พื้นฐานของบทนี้** (อธิบายครั้งเดียวตรงนี้แล้วใช้ต่อทั้งบท — บทความนี้ไม่มี footnote เพราะ dev.to ไม่รองรับ):
> - **automaton (พหูพจน์ automata, ภาษาไทย "เครื่องสถานะ")** = แบบจำลองการคำนวณที่จำกัดความจำที่สุด · จำได้แค่ "ตอนนี้อยู่สถานะไหน" และไม่มีอะไรอื่น
> - **state (สถานะ)** = "ความจำ" ทั้งหมดของเครื่อง มีจำนวนจำกัดและนับได้ · เครื่องไม่มีตัวแปร ไม่มีตัวนับ ไม่มีสแตก (ดูคำอธิบาย "stack" ในกล่องนี้)
> - **alphabet (อักษร)** = เซตของสัญลักษณ์ที่เครื่องยอมรับ เช่น `{a, b}` หรือ `{0, 1}`
> - **input / สตริง** = ลำดับของสัญลักษณ์ที่ป้อนให้เครื่อง เช่น `aab`
> - **transition (การเปลี่ยนสถานะ)** = กฎว่า "อยู่สถานะนี้ เจอสัญลักษณ์นี้ → ไปสถานะไหน"
> - **DFA** (Deterministic Finite Automaton, เครื่องสถานะจำกัดแบบกำหนดได้) = จากทุก (สถานะ, สัญลักษณ์) มีทางไป **หนึ่งทางเท่านั้น** และต้องมีทางเสมอ · ไม่มีการเดา ไม่มีการถอย
> - **NFA** (Nondeterministic Finite Automaton, แบบไม่กำหนด) = ไปได้ **หลายทางพร้อมกัน** หรือไม่ไปเลยก็ได้ · มี "การเดา" อยู่ในตัว โดยไม่มีค่าใช้จ่าย (เพราะทุกทางเดินพร้อมกัน)
> - **ε (epsilon, เอปไซลอน)** = สัญลักษณ์พิเศษของ NFA ที่แปลว่า "ย้ายสถานะโดยไม่กินตัวอักษร" (ε-transition = ขอบที่ย้ายฟรี)
> - **ε-closure (วงปิด ε)** = เซตสถานะทั้งหมดที่ไปถึงได้ด้วยขอบ ε อย่างเดียว
> - **accept state / สถานะรับ** = สถานะที่แปลว่า "สตริงนี้เข้าภาษาของเราแล้ว" · **dead state / กับดักตาย** = สถานะที่เข้าแล้วไม่มีทางรับอีกเลย
> - **regular language (ภาษาปกติ)** = เซตของสตริงที่มี DFA รู้จัก (มีคนสร้างเครื่องที่รับสตริงเหล่านั้นพอดีได้)
> - **regular expression (regex)** = สัญกรณ์เขียน "ภาษาปกติ" ให้สั้น · คำว่า regular ตรงนี้เป็นศัพท์ทางทฤษฎี (แปลว่า "มีแบบแผน") ไม่ได้แปลว่า "ธรรมดา ๆ"
> - **Kleene star (`*`)** = "ซ้ำกี่ครั้งก็ได้ (รวมศูนย์ครั้ง)" · **concatenation (ต่อกัน)** = เขียนติดกันหมายถึงต่อ · **union (`|`)** = อย่างใดอย่างหนึ่ง
> - **subset construction (การสร้างดีเอฟเอจากเซตย่อย)** = ขั้นตอนแปลง NFA → DFA โดย "หนึ่งสถานะของ DFA = หนึ่งเซตของสถานะ NFA"
> - **product construction (ผลคูณ)** = ประกอบ DFA สองเครื่องให้ทำงานพร้อมกัน (ใช้ทำ "และ")
> - **backtracking (การถอย)** = วิธีจับคู่แบบ "เดาไปก่อน ถ้าผิดถอยกลับมาเลือกทางอื่น" · เป็นที่มาของเวลาแบบเอกซ์โพเนนเชียล
> - **catastrophic backtracking / ReDoS** = อาการที่ regex + input บางแบบทำให้เวลาโตแบบ 2 ยกกำลัง n จนโปรแกรมค้าง (ReDoS = ช่องโหว่ที่โจมตีได้ด้วยอาการนี้)
> - **RE2** = ไลบรารี regex ของ Google ที่ "เดินทุกทางพร้อมกัน" แทนที่จะถอย · **engine (เอนจิน)** = เครื่องยนต์ที่ทำหน้าที่จับคู่จริง ๆ ข้างใน
> - **lexer / tokenizer** = ส่วนของคอมไพเลอร์ที่ตัดข้อความยาว ๆ เป็นชิ้นคำที่มีความหมาย (จะเรียนในตอนที่ 26)
> - **stack (สแตก)** = ที่เก็บข้อมูลแบบ "เข้าทีหลัง ออกก่อน" — พักของไว้ชั้นบนสุด แล้วหยิบชั้นบนสุดออกก่อน · เป็นความจำอีกแบบที่ automaton ไม่มี (ตอนที่ 23 จะได้เจอ)
> - **ไลบรารี (library) / แพ็กเกจ (package)** = ชุดโค้ดที่คนอื่นเขียนไว้แล้วให้เราเรียกใช้ต่อ · **standard library** = ชุดที่ติดมากับภาษาเลย (ของ Go ติดมาให้ ไม่ต้องโหลดเพิ่ม)
> - **dependency (สิ่งที่ต้องพึ่ง)** = โค้ดของคนอื่นที่โปรแกรมเราต้องโหลดมาใช้ · "ไม่มี dependency" = ใช้แต่ของที่ติดมากับภาษา
> - **คอมไพเลอร์ (compiler)** = โปรแกรมที่แปลโค้ดที่เราเขียนให้เป็นคำสั่งที่เครื่องรันได้ (เราเคยเขียนกันในตอนที่ 17)
> - **ไบต์ (byte)** = หน่วยข้อมูลขนาด 8 บิต · ตัวอักษรอังกฤษ 1 ตัว = 1 ไบต์
> - **บิตแมป (bitmap)** = อาร์เรย์ที่เก็บคำตอบ "ใช่/ไม่" ของหลาย ๆ อย่างเป็นบิต (1 เรื่อง = 1 บิต) — ประหยัดที่และเช็กเร็ว
> - **matcher / engine (เอนจิน)** = ส่วนที่เอา pattern ไปเทียบกับข้อความจริงแล้วตอบว่า "ตรงไหม" · คนละขั้นกับ "คอมไพล์" (คอมไพล์ = แปล pattern เป็นเครื่อง · matcher = เดินเครื่องนั้นบนข้อความ)
> - **quantifier** = ตัวบอกจำนวนซ้ำใน regex: `*` = 0 ครั้งขึ้นไป · `+` = 1 ครั้งขึ้นไป · `?` = มีหรือไม่มีก็ได้
> - **ขอบ (edge) / self-loop** = เส้นเชื่อมระหว่างสถานะในภาพ automaton · self-loop = ขอบที่วนจากสถานะกลับเข้าตัวเอง (เช่น q2 ที่รับทุกอย่างแล้วอยู่กับที่)
> - **backreference / lookaround** = ฟีเจอร์ regex ที่ต้อง "จำข้อความที่จับไว้" หรือ "มองไปข้างหน้า/ย้อนหลังโดยไม่กินตัวอักษร" (เขียนว่า `\1`, `(?=…)`, `(?<=…)`) · สองอย่างนี้อยู่นอกโลกของเครื่องสถานะจำกัด — ข้อความ error จริงอยู่ที่หัวข้อ 6.3
> - **`\d`, `\w`, `[a-z]`** = คลาสของตัวอักษร (character class = ตัวอักษรกลุ่มหนึ่งที่ยอมรับได้)

## 1. แนวคิด: regex คือ "เครื่องสถานะ" ในชุดสวย ๆ

### 1.1 DFA — เครื่องที่จำได้แค่ "ตอนนี้อยู่ไหน"

![DFA ของภาษา a*b: สถานะ q0, q1 (รับ), q2 (กับดักตาย) พร้อมเส้นทางจริง](/assets/diagrams/ep22-01-dfa-ab-star.svg)

ภาพที่ 1 คือ DFA ที่เล็กที่สุด (minimal) เท่าที่เป็นไปได้สำหรับภาษา `a*b` (สตริงที่ขึ้นต้นด้วย a กี่ตัวก็ได้ แล้วปิดท้ายด้วย b หนึ่งตัวพอดี) — ลองอ่านภาพก่อนอ่านคำอธิบาย: มีวงกลม 3 วง (สถานะ) มีลูกศร (กฎการเปลี่ยนสถานะ) และมีลูกศรจากข้างนอกชี้เข้ามาที่ q0 (จุดเริ่ม)

DFA นิยามด้วยของ 5 อย่างเท่านั้น (จำชื่อภาษาอังกฤษไว้ก็ดี เพราะบทต่อ ๆ ไปจะใช้):

| ส่วน | ชื่อ | ความหมายในเครื่องของเรา |
|---|---|---|
| `Q` | เซตสถานะ | `{q0, q1, q2}` |
| `Σ` | alphabet (อักษร) | `{a, b}` + "อย่างอื่น" |
| `δ` | ฟังก์ชันเปลี่ยนสถานะ | ตาราง `delta[สถานะ][สัญลักษณ์]` |
| `q0` | สถานะเริ่ม | `q0` |
| `F` | เซตสถานะรับ | `{q1}` |

**คำว่า deterministic (กำหนดได้) หมายถึง 2 อย่างนี้เท่านั้น**: (1) จากสถานะหนึ่ง เจอสัญลักษณ์หนึ่ง มีทางไป**ทางเดียว** และ (2) มีทางไปเสมอ (ไม่มี "ไม่มีคำตอบ" ค้างอยู่) เพราะข้อ (1) แปลว่าเครื่องไม่ต้องเลือก — และเพราะไม่ต้องเลือก มันจึง**ไม่ต้องถอย** ซึ่งเป็นคีย์ของทุกอย่างในบทนี้

เขียนเป็นโค้ด Go ง่ายจนน่าแปลกใจ (ไฟล์เต็ม `01_dfa_astar/main.go`):

```go
// delta[สถานะ][สัญลักษณ์] = สถานะถัดไป  — ทั้ง DFA อยู่ใน 3 บรรทัดนี้
var delta = [numStates][numSyms]int{
	//  a   b   other
	{q0, q1, q2}, // จาก q0: เจอ a วนอยู่ที่เดิม · เจอ b ไปสถานะรับ · อย่างอื่นตาย
	{q2, q2, q2}, // จาก q1: เจออะไรอีกก็ตาย (ต้องเป็น b ตัวสุดท้ายของสายเท่านั้น)
	{q2, q2, q2}, // จาก q2: ตายถาวร ไม่มีทางกลับ
}

func accepts(in string) (bool, int, int) {
	state := q0
	steps := 0
	for _, r := range in {
		// classify(r) = แปลงตัวอักษรเป็นเลขช่องของตาราง: a→0 · b→1 · ตัวอื่น→2
		// และแถวของ delta ก็คือเลขสถานะ: q0=0 · q1=1 · q2=2
		state = delta[state][classify(r)] // ก้าวละ 1 ตัวอักษร = เครื่องไม่เคยมองย้อนหลัง
		steps++
	}
	return acceptStates[state], state, steps
}
```

  จาก    a        b        อื่นๆ
  q0     q0       q1       q2
 *q1     q2       q2       q2
  q2     q2       q2       q2
  (* = สถานะรับ · สถานะเริ่ม = q0)

  … (ตัดตารางตัดสินใจ 11 เส้นของโปรแกรมออก — ดู out/01_dfa_astar.out.txt)

  … (อีก 6 เส้น: "" · "b" · "ab" · "a" · "ba" · "aab" — ผลเต็มอยู่ใน out/)
```

  … (อีก 2 บรรทัด: ยาว 11 ตัว และ 101 ตัว — ก้าวเท่ากับจำนวนตัวอักษรทุกบรรทัด)
```

**จุดที่ต้องจำให้ขึ้นใจ**: "8,191 เส้น ไม่ตรงกัน 0 เส้น" ไม่ใช่การเทียบเล่น ๆ — เราทดสอบ**ครบทุกสตริง**ที่ยาว 0 ถึง 12 บน alphabet `{a,b}` (2¹ + 2² + … + 2¹² = 8,190 บวกสตริงว่างอีก 1) ถ้าสองเครื่องต่างกันแม้เส้นเดียว การทดสอบแบบนี้จับได้ทันที (และมันจับได้จริง ๆ ในหัวข้อ 4.1 กับ 4.2 — เราเขียนโค้ดผิดแล้วตัวทดสอบนี้แหละที่บอก)

โปรแกรมเดียวกับที่ประมวลผลสตริงยาว 100,001 ตัวได้ใน **100,001 ก้าว** — นี่คือความหมายของ "เวลาเป็นเชิงเส้นตามขนาด input" ที่เราจะเทียบให้เห็นกับตาในหัวข้อ 6.2

### 1.2 ทำไมต้องมี "กับดักตาย" (dead state)

มือใหม่มักคิดว่า DFA ไม่ต้องมีกับดักตาย แต่มันเป็นส่วนที่ทำให้ DFA **ครบถ้วน (total)** ซึ่งเป็นเงื่อนไขของการเป็น deterministic — ทุกช่องในตารางต้องมีคำตอบ

- จาก `q0` เจอ `b` แล้วจบสาย → `q1` รับ
- แต่ถ้าเจอ `b` แล้วยังมีตัวอักษรตามมาอีก (`abab`) จะไปไหน? คำตอบคือ `q2` (กับดักตาย) — สถานะที่แปลว่า "เรื่องนี้จบแล้ว ไม่ต้องสนใจอีก"
- และ `q2` ไปไหนต่อ? `q2` ตลอดไป (self-loop ทุกสัญลักษณ์)

การมีกับดักตายตัวเดียวที่ "รวมทุกอย่างที่ผิดไว้ที่เดียวกัน" คือเหตุผลที่เครื่องนี้มีแค่ 3 สถานะ ไม่ใช่ 5 และการมีมันทำให้เราตอบคำถาม "รับไหม" ได้ด้วยการ**อ่านค่าเดียว**: สถานะสุดท้ายอยู่ใน `F` ไหม — ไม่ต้องดูประวัติเลย

### 1.3 NFA — เครื่องที่ "เดาได้" และไม่ต้องเสียอะไรเลย

NFA ต่างจาก DFA แค่ข้อเดียว: จาก (สถานะ, สัญลักษณ์) ไปได้**หลายทางพร้อมกัน** (หรือไม่ไปเลย) และมีขอบ ε ที่ย้ายสถานะได้โดยไม่กินตัวอักษร

![NFA ของ a*b แบบ Thompson แปลงเป็น DFA ด้วย subset construction](/assets/diagrams/ep22-02-nfa-to-dfa.svg)

ภาพที่ 2 ซ้ายมือคือ NFA ของ `a*b` ที่สร้างตาม **วิธีของ Thompson** (กติกามาตรฐานที่ใช้แปลง regex เป็นเครื่อง — จะพูดถึงที่มาในหัวข้อ 1.5): ท่อน `a*` กลายเป็น "จุดแยก" ที่มีทางออก 2 ทาง (เข้าเนื้อในเพื่ออ่าน `a` อีกตัว หรือออกจากท่อนไปอ่าน `b`)

```go
// 0 --ε--> 1 ; 1 --ε--> 2 (เข้าเนื้อใน) ; 2 --a--> 1 (วนซ้ำ)
// 1 --ε--> 3 (ออกจาก star) ; 3 --b--> 4 ; 4 = สถานะรับ
eps: [][]int{
	{1},    // 0: ε -> 1
	{2, 3}, // 1: จุดแยกของ star: ไปเข้าเนื้อใน (2) หรือออกจาก star (3)
	nil, nil, nil,
},
```

เวลารัน NFA เราไม่รัน "สถานะเดียว" แต่รัน "**เซตของสถานะ**" — และนี่คือสิ่งที่ทำให้ NFA ทรงพลัง: **มันเดินทุกทางพร้อมกัน ไม่ต้องเลือก และไม่ต้องถอย**

```
== 2) จำลอง NFA: อยู่ได้หลายสถานะพร้อมกัน ==
  "b"      ก้าว=1 รับ=true · เซตใหญ่สุด=4 ตัว
      {0,1,2,3} (เริ่ม) -b-> {4}
  "ab"     ก้าว=2 รับ=true · เซตใหญ่สุด=4 ตัว
      {0,1,2,3} (เริ่ม) -a-> {1,2,3} -b-> {4}
  … (อีก 3 เส้น: "aab" · "a" · "abab" — ดู out/03_nfa_subset.out.txt)
  "ba"     ก้าว=2 รับ=false · เซตใหญ่สุด=4 ตัว
      {0,1,2,3} (เริ่ม) -b-> {4} -a-> {}
```

อ่านบรรทัด `{0,1,2,3}` ให้ดี: ก่อนอ่านตัวอักษรตัวแรก NFA ของเรา "เป็นได้พร้อมกัน 4 สถานะ" — เพราะจากสถานะ 0 ย้ายฟรีไป 1, แล้วจาก 1 ย้ายฟรีไปได้ทั้ง 2 และ 3 (นี่คือ ε-closure) ส่วนบรรทัดสุดท้าย `{}` = เซตว่าง = ตายแล้ว (เหมือนกับดักตายของ DFA แต่ไม่มีตัวตนเป็นสถานะ)

**แล้วทำไมต้องรู้เรื่อง NFA ด้วย ในเมื่อ DFA ก็พอ?** เพราะ NFA **เขียนง่ายกว่าเยอะ** — เวลาคอมไพเลอร์หรือไลบรารีเจอ regex ที่ผู้ใช้พิมพ์ มันไม่ได้ "ออกแบบ DFA" ตรง ๆ มันสร้าง NFA ก่อน (ง่ายกว่า สั้นกว่า ตรงไปตรงมากว่า) แล้วค่อยแปลงเป็น DFA ทีหลัง และขั้นตอนแปลงคือ **subset construction** (ขวาของภาพที่ 2):

> **หัวใจของ subset construction**: หนึ่งสถานะของ DFA = หนึ่ง**เซต**ของสถานะ NFA

```
== 3) subset construction: NFA -> DFA (หนึ่งสถานะ DFA = หนึ่งเซตย่อย) ==
  NFA มี 5 สถานะ -> เซตย่อยที่ไปถึงได้จริง 3 เซต (รวม ∅ ที่เราไม่เก็บเป็นสถานะ)

  สถานะ DFA      เจอ 'a'      เจอ 'b'      รับ?
  S0={0,1,2,3}  {1,2,3}      {4}          false
  S1={1,2,3}    {1,2,3}      {4}          false
 *S2={4}        ∅ (กับดักตาย) ∅ (กับดักตาย) true
  ∅ (กับดักตาย)  ∅            ∅            false
```

เทียบกับภาพที่ 1: `S0`/`S1` คือ `q0` ของเรานั่นเอง (มันรู้จักภาษาเดียวกัน) — โค้ดตรวจแล้วเช่นกัน:

```
== 4) เทียบกับ regexp ของ Go: ทดสอบครบทุกเส้นบน {a,b} ยาว 0..12 ==
  NFA  กับ regexp: ไม่ตรงกัน 0 จาก 8191 เส้น
  DFA กับ regexp: ไม่ตรงกัน 0 จาก 8191 เส้น
```

### 1.4 "ภาษาปกติ" (regular language) คืออะไรกันแน่

ตอนนี้เรามีของ 3 อย่างที่ดูเหมือนคนละเรื่อง:

1. **ภาษาปกติ** — เซตของสตริงที่ DFA รู้จัก (เช่น `a*b`)
2. **NFA** — เครื่องที่เดาได้
3. **regex** — สัญกรณ์ `a*b` ที่เราพิมพ์

**ทฤษฎีบทของ Kleene** (Stephen Kleene, ค.ศ. 1951) บอกว่าสามอย่างนี้คือสิ่งเดียวกัน:

> **regex ≡ NFA ≡ DFA ≡ ภาษาที่เครื่องสถานะจำกัดรู้จัก**

แปลว่า:
- ทุก regex มี DFA ที่รับสตริงชุดเดียวกันได้ (สร้างจาก NFA ด้วย subset construction)
- ทุก DFA เขียนเป็น regex ได้ (มีขั้นตอนมาตรฐานในตำรา — ยาวกว่าและคนไม่ค่อยทำมือ)
- และเพราะ DFA มีสถานะจำกัด **ภาษาปกติจึงเป็นภาษาที่ "จำกัดความจำที่สุด"** — มันจำอะไรได้แค่ "ตอนนี้สถานะไหน" เท่านั้น

ผลพลอยได้ที่ใช้จริงบ่อย (และเป็นเหตุผลที่ภาพรวมของหัวข้อ 4.1 น่าสนใจ): ภาษาปกติ **ปิด (closed)** ใต้การดำเนินการหลายอย่าง เช่น ตัด (intersection), รวม (union), กลับด้าน (complement), ต่อกัน (concatenation) — แปลว่าถ้าสองภาษาเป็น regular, ภาษาใหม่ที่ประกอบขึ้นจากมันก็เป็น regular เสมอ (เราสร้างเครื่องที่พิสูจน์ได้ทันที ไม่ต้องเดา)

และของที่ทำไม่ได้ — **pumping lemma** (บทตั้งการปั๊ม = เครื่องมือพิสูจน์ว่า "ภาษาไหนไม่ regular") บอกว่า `L = {aⁿbⁿ}` (a ยาว n ตามด้วย b ยาว **เท่ากัน** n ตัว) **ไม่ใช่ภาษาปกติ** เพราะการตรวจ "เท่ากันหรือเปล่า" ต้องนับ ซึ่ง DFA ไม่มีที่เก็บตัวนับ — นี่คือสะพานไปตอนที่ 23 (pushdown automaton มีสแตก จึงนับได้)

### 1.5 regex มาจากไหน — ประวัติที่ไม่ใช่ของคนทำโปรแกรม

เรื่องนี้ไม่ใช่แค่เกร็ด แต่เป็นเหตุผลว่าทำไม regex หน้าตาเป็นแบบนี้ในทุกวันนี้:

- **ค.ศ. 1951** — Stephen Kleene ตีพิมพ์บันทึกของ RAND ชื่อ *Representation of Events in Nerve Nets and Finite Automata* เขาสนใจแบบจำลองเซลล์ประสาทของ McCulloch & Pitts (ค.ศ. 1943) แล้ว "แยก" แนวคิด finite automaton กับสัญกรณ์สำหรับบรรยายสตริงที่เครื่องยอมรับออกมา เขาเรียกมันว่า **regular events** และใช้ตัวดำเนินการสามตัว: **union** (วันนี้คือ `|`), **concatenation** (เขียนติดกัน), และ **star** `*` (ซ้ำกี่ครั้งก็ได้) — ตัว `*` ใน regex ที่คุณพิมพ์ทุกวันนี้คือ "Kleene star" ตรง ๆ · และเขาพิสูจน์ด้วยว่า สามตัวนี้พอสำหรับบรรยายทุกภาษาที่ finite automaton รู้จัก (นั่นคือทฤษฎีบทของ Kleene) — **คืองานทฤษฎีล้วน ไม่มีใครเขียนมันเป็นโปรแกรมจริง (implement) บนคอมพิวเตอร์ 17 ปี**
- **ค.ศ. 1968** — Ken Thompson (คนเดียวกับที่ต่อมาสร้าง Unix) หยิบงานของ Kleene มาใช้กับปัญหาการ "ค้นหารูปแบบในข้อความ" เขาตีพิมพ์ *Regular Expression Search Algorithm* ใน CACM (มิถุนายน 1968) — เป็น **implementation ที่ตีพิมพ์และใช้จริงเป็นตัวแรก** (แนวคิดการแปลง regex เป็นเครื่องมีมาก่อนแล้ว: McNaughton & Yamada ตีพิมพ์วิธี construction ตั้งแต่ ค.ศ. 1960) และสิ่งที่เขาทำคือ **แปลง regex เป็นโค้ดเครื่องของ IBM 7094 ทันทีที่ผู้ใช้พิมพ์ (just-in-time compilation)** เทคนิคการแปลง regex → NFA นี้ทุกวันนี้เรียก **Thompson's construction** (เราจะใช้ชื่อนี้ในบทนี้)
- **หลังจากนั้น** — แนวคิดและไวยากรณ์ regex ไปต่อใน editor **QED** → ต่อมาอยู่ใน **ed** ของ Unix → แล้วในปี 1973 Thompson ดึงคำสั่ง `g/re/p` (global / regular expression / print) ออกมาเป็นโปรแกรมเดี่ยว ชื่อก็คือ **grep** นั่นเอง · แต่ต้องระวังจุดนี้ให้ดี: **ed และ grep ใช้ recursive backtracking ไม่ใช่อัลกอริทึม NFA ปี 1968 ของ Thompson** (Cox เขียนไว้ตรง ๆ ว่าเอนจินของ QED/grep เป็นแบบถอย) — เส้นทาง "ไวยากรณ์ regex" กับเส้นทาง "เอนจิน NFA" จึงแยกจากกันที่จุดนี้ และมาเจอกันอีกครั้งตอน RE2 · ปลายทศวรรษ 1970 regex จึงอยู่ใน `ed`, `sed`, `grep`, `egrep`, `awk`, `lex` ครบทั้งชุด
- **ค.ศ. 2007** — Russ Cox เขียนบทความ *Regular Expression Matching Can Be Simple And Fast* ชี้ว่าเอนจินสมัยใหม่หลายตัว (Perl, Python, PHP, Ruby ในยุคนั้น) เลือกวิธี "ถอย" แทนวิธีของ Thompson และทำให้เกิดกรณีที่ input สั้นแค่ 29 ตัวอักษรแต่ใช้เวลาเป็นวินาที (~60 วินาทีในกรณีที่เขาวัด) ขณะที่วิธี Thompson NFA ใช้ราว 20 ไมโครวินาที — **บทความนี้คือจุดเริ่มของ RE2 และเป็นเหตุผลที่ Go เลือกเดินตามแนวทางนี้**
- **วันนี้** — RE2 (ไลบรารีของ Google) เขียนเป้าหมายไว้ชัดว่า **ความปลอดภัยคือเป้าหมายหลัก** และ "ถ้าทำได้เฉพาะด้วยการถอย เอนจินนี้จะไม่รองรับ" เช่น **backreference** (`\1` = "ข้อความตรงกับที่กลุ่มวงเล็บก่อนหน้าจับไว้") และ **lookaround** (`(?=…)` มองไปข้างหน้า · `(?<=…)` มองย้อนหลัง โดยไม่กินตัวอักษร) — สองอย่างนี้ต้อง "จำข้อความ" ซึ่งเครื่องสถานะจำกัดทำไม่ได้ (เราจะทดสอบด้วยข้อความ error จริงในหัวข้อ 6.3)

**สรุปหนึ่งบรรทัด**: regex ไม่ได้ถูกออกแบบมาเพื่อ "เขียน pattern สวย ๆ" มันถูกออกแบบมาเพื่อบรรยาย**ภาษาที่เครื่องสถานะจำกัดรู้จัก** — และทุกข้อจำกัดของมัน (ไม่มีตัวนับ ไม่มีสแตก ไม่มี backreference) สืบมาจากข้อจำกัดของ "เครื่องที่จำได้แค่สถานะเดียว" ทั้งสิ้น

## 2. ทำไมสำคัญ: automata อยู่ในโปรแกรมจริงตรงไหน

บทนี้ดูเป็นทฤษฎีล้วน แต่ห่างจากงานจริงน้อยกว่าที่คิด:

**1) lexer / tokenizer ของคอมไพเลอร์ (ตอนที่ 26 ของคอร์สนี้)** — ตอนที่เราจะเขียนคอมไพเลอร์จริง ๆ ขั้นแรกคือตัดข้อความ `if x2 >= 42 {` เป็นชิ้น: `if` (คำสงวน) · `x2` (ชื่อ) · `>=` (ตัวดำเนินการ) · `42` (ตัวเลข) · `{` (เครื่องหมาย) — แต่ละชนิดคือ DFA ที่รู้จักภาษาของตัวเอง (ชื่อ = `[a-z][a-z0-9]*`, ตัวเลข = `[0-9]+`, ตัวดำเนินการ = หนึ่งในเซตจำกัด) และ lexer ที่เร็วที่สุดในโลกก็แค่ "DFA หลายเครื่องเดินพร้อมกันบนไบต์หนึ่งตัว" — ไม่มี regex วิ่งอยู่จริง ณ จุดนั้น เพราะถูกคอมไพล์เป็นตารางไปแล้วตอนสร้างโปรแกรม (เครื่องมืออย่าง `lex` ปี 1975 และ `flex` ปี 1987 ทำแบบนี้มานับสิบปีแล้ว)

**2) ตรวจรูปแบบ input** — เบอร์โทร, รหัสไปรษณีย์, ที่อยู่ IP, เลขบัตร: ทั้งหมดคือนิยามของ "ภาษาปกติ" และตรวจได้ด้วย DFA ที่ไม่กี่สถานะ · เราเขียน `01_dfa_astar/main.go` แบบไม่มี dependency อะไรเลยได้ — ในระบบที่รับ input ปริมาณมหาศาล (หรือที่ input มาจากผู้โจมตี) การใช้ DFA ที่เขียนเองแทน regex กลาง ๆ คือการตัดความเสี่ยงทิ้งทั้งหมด

**3) แพ็กเกจ `regexp` ของ Go — และ RE2** — นี่คือส่วนที่คนเข้าใจผิดกันเยอะที่สุด จุดที่ต้องพูดให้ตรง:

- `regexp` ของ Go ให้ข้อรับประกันในเอกสารตรง ๆ ว่า **ใช้เวลาเป็นเชิงเส้นตามขนาด input** (linear in the size of the input) และไวยากรณ์ที่รับคือไวยากรณ์ของ RE2 ยกเว้น `\C`
- **แต่ Go ไม่ได้ใช้โค้ดของ RE2** — RE2 เป็นไลบรารี C++ · เอกสาร RE2 ระบุชัดว่า แพ็กเกจ `regexp` ของ Go **ไม่แชร์โค้ดกับ RE2** แต่ "ยึดหลักการเดียวกัน รับไวยากรณ์เดียวกัน และให้ข้อรับประกันประสิทธิภาพเดียวกัน"
- ความหมายของ "เชิงเส้น" ตรงนี้คือ: **ไม่มี regex ที่ทำให้มันระเบิด** — งานที่ยากขึ้นจะเพิ่ม "ค่าคงที่ (constant factor)" ไม่ใช่เพิ่ม "เลขชี้กำลัง"
- และราคาที่จ่ายคือ **ตัดฟีเจอร์ที่ต้องถอยออกไปเลย**: backreference (`\1`), lookahead (`(?=…)`), lookbehind (`(?<=…)`) ทำไม่ได้ — ไม่ใช่ "ยังไม่ทำ" แต่ "จะทำได้ต้องเปลี่ยนหลักการทั้งเอนจิน"

**4) ที่ที่คุณเจอ regex โดยไม่รู้ตัว** — `grep`/`sed`/`awk` (เอนจินคนละแบบกับ Go), การค้นใน editor, การกำหนดเส้นทาง (route) URL ของเว็บเฟรมเวิร์ก, การแยก log, ตัวตรวจ config — และใน Go เองมีที่ใช้ `regexp` ใน standard library หลายที่

**5) ขีดจำกัดที่นักศึกษาต้องรู้ตั้งแต่ตอนนี้** — ถ้างานของคุณคือ "ตรวจว่าวงเล็บเปิด-ปิดเท่ากันไหม" หรือ "ตรวจว่า a ยาว n ตามด้วย b ยาว n เท่ากันไหม" **regex ทำไม่ได้** (ไม่ใช่เพราะ regex ของคุณไม่เก่ง แต่เพราะมันไม่มีกลไกนับ) — สิ่งที่ทำได้จะมาในตอนที่ 23 และสิ่งที่คอมพิวเตอร์ทั้งเครื่องก็ทำไม่ได้จะมาในตอนที่ 24

## 3. ลงมือทำ (1): `01_dfa_astar` — DFA กับ regexp ของ Go เป็นภาษาเดียวกันจริงไหม

เราเห็นผลของโปรแกรมนี้แล้วในหัวข้อ 1.1 ที่เหลือคือ **วิธีทดสอบที่เราจะใช้ทั้งบท**: เขียนโค้ดที่ **แจกแจงสตริงทั้งหมด** ในช่วงความยาวที่ต้องการ (ไม่สุ่ม ไม่เดา) แล้วเทียบผลทีละเส้น

อ่านทีละท่อนก่อน — `out` = สตริงทั้งหมดที่เราจะทดสอบ · `level` = เฉพาะ "ชั้นล่าสุด" ที่เพิ่งสร้าง (เอาไว้ต่อตัวอักษรเพิ่มในรอบถัดไป) · เริ่มจากสตริงว่าง แล้วต่อท้ายทีละตัวอักษร:

```go
// enumerate สร้างสตริงทั้งหมดบน alphabet ที่ให้ ความยาว 0..maxLen เรียงสั้นก่อน
func enumerate(alphabet []rune, maxLen int) []string {
	out := []string{""}
	level := []string{""}
	for n := 1; n <= maxLen; n++ {
		next := make([]string, 0, len(level)*len(alphabet))
		for _, prefix := range level {
			for _, r := range alphabet {
				next = append(next, prefix+string(r))
			}
		}
		out = append(out, next...)
		level = next
	}
	return out
}
```

```go
const maxLen = 12
all := enumerate([]rune{'a', 'b'}, maxLen)
mismatch := 0
for _, s := range all {
	mine, _, _ := accepts(s)              // DFA ที่เราเขียนมือ
	theirs := re.MatchString(s)           // regexp.MustCompile(`^a*b$`) ของ Go
	if mine != theirs {
		mismatch++                       // ถ้าไม่ตรงแม้เส้นเดียว บทความนี้มีบั๊ก
	}
}
```

ในลูปถัดไป `accepts(s)` คือ DFA ที่เราเขียนมือ ส่วน `re.MatchString(s)` คือ regexp ของ Go — ถ้าผลไม่ตรงกันแม้เส้นเดียว `mismatch` จะถูกบวก และตัวเลขนั้นคือ "หลักฐาน" ที่บทนี้ใช้ทั้งบท

**ทำไมต้อง `^` กับ `$`**: ตัว `^` = "ต้นสตริง" และ `$` = "ท้ายสตริง" (anchor = จุดยึด) · ถ้าไม่ใส่ `re.MatchString("xxaab")` ก็จะตอบ `true` เพราะมันเจอ `aab` **อยู่ข้างใน** — ซึ่งเทียบกับ DFA ของเราไม่ได้ (DFA ของเราตอบคำถามว่า "สตริงทั้งเส้นเข้าภาษาไหม") นี่คือความเข้าใจผิดอันดับหนึ่งของคนเริ่มใช้ regex และมันจะโผล่ในแบบฝึกหัดท้ายบท

**ผลลัพธ์**: 8,191 เส้น ไม่ตรงกัน 0 เส้น และก้าว = จำนวนตัวอักษรเสมอ (100,001 ตัว = 100,001 ก้าว)

## 4. ลงมือทำ (2): `02_product_dfa` — "และ" ที่ regex ไม่มี

โจทย์ที่ทำให้เห็นความต่างระหว่าง "คิดแบบ regex" กับ "คิดแบบ automata": **สตริงบน `{0,1}` ที่มีจำนวน `1` เป็นเลขคู่ และลงท้ายด้วย `10`**

- DFA เครื่อง P: "จำนวน 1 เป็นเลขคู่" — 2 สถานะ (คู่/คี่)
- DFA เครื่อง Q: "ลงท้ายด้วย 10" — 3 สถานะ (ยังไม่เห็น 1 / ล่าสุดเป็น 1 / สองตัวล่าสุดเป็น 10)
- **เครื่องที่ต้องการ** = ทั้งสองพร้อมกัน — และเราสร้างมันได้แบบ **กลไก ไม่ต้องคิด**:

> ให้หนึ่งสถานะของเครื่องใหม่ = หนึ่ง**คู่** (สถานะของ P, สถานะของ Q) → ได้ 2 × 3 = 6 สถานะ
> รับก็ต่อเมื่อ **ทั้งคู่รับพร้อมกัน**

```go
// product สร้าง DFA ที่จำ "สถานะของทั้งสองเครื่องพร้อมกัน": หนึ่งสถานะ = หนึ่งคู่ (sP, sQ)
func product(a, b *dfa) *dfa {
	d := &dfa{...}
	for sa := 0; sa < a.n; sa++ {
		for sb := 0; sb < b.n; sb++ {
			// id = "แถว × ที่นั่ง": เอาเลขแถวของ a (sa) คูณจำนวนคอลัมน์ของ b (b.n) แล้วบวกเลขของ b (sb)
			// (เหมือนเลขที่นั่งโรงหนัง: แถวที่ sa นั่งที่ sb = sa*จำนวนที่นั่งต่อแถว + sb) — ไม่มีคู่ไหนชนกัน
			id := sa*b.n + sb
			d.accept[id] = a.accept[sa] && b.accept[sb] // รับก็ต่อเมื่อ "ทั้งคู่" รับ
			for k := 0; k < 2; k++ {
				na, nb := a.delta[sa][k], b.delta[sb][k]
				d.delta[id][k] = na*b.n + nb // สถานะถัดไปก็ยัดคู่ด้วยสูตรเดียวกัน: na × b.n + nb
			}
			d.full[id] = fmt.Sprintf("%s × %s", a.full[sa], b.full[sb])
		}
	}
	return d
}
```

อ่านโค้ดนี้ให้เห็นภาพเดียว: หนึ่งรอบของลูปคู่ = หนึ่งคู่ (sa, sb) → ยัดลงช่อง `id` เดียว · `accept` ของคู่นั้น = "รับทั้งคู่ไหม" · `delta` ของคู่นั้น = "เดินพร้อมกันทั้งสองเครื่อง" · และ `full` เก็บชื่อยาวไว้ให้พิมพ์ดู

ผลรันจริง (ย่อชื่อสถานะให้อ่านในจอแคบได้ · ผลเต็มชื่อยาวอยู่ใน `out/02_product_dfa.out.txt`) — สังเกตว่าทุกแถวมี "×" เพราะมันคือคู่สถานะ:

```

 #    สถานะ (ชื่อย่อ)                เจอ '0' ->             เจอ '1' ->             รับ?
  0   p0 คู่ × q0 ยังไม่เห็น1 [เริ่ม] p0 คู่ × q0 ยังไม่เห็น1 p1 คี่ × q1 ล่าสุด1    false
  1   p0 คู่ × q1 ล่าสุด1            p0 คู่ × q2 ล่าสุด10   p1 คี่ × q1 ล่าสุด1    false

  (* = รับ · [เริ่ม] = สถานะเริ่ม · ผลเต็ม (ชื่อยาวกว่านี้) อยู่ใน out/02_product_dfa.out.txt)
```

### 4.1 กับดักจริง #1 ที่เจอในบทนี้: regex ที่เรา "คิดว่าใช่"

regex **ไม่มีตัวดำเนินการ "และ"** (ไม่มี `∩`) ถ้าอยากได้ภาษาที่เป็น intersection ของสองภาษา จะทำได้ 2 วิธี: (1) สร้าง DFA คูณกัน (ทำแล้ว) หรือ (2) **คิด regex ของ intersection เองด้วยหัว** — และเราเลือกวิธี (2) ครั้งแรกแบบมั่นใจ:

```
  P ∩ Q (รอบแรก — กับดัก)        regexp = ^(0*10*1)*0*10$
      ไม่ตรงกัน 2047 จาก 8191 เส้น · ภาษานี้รับ 1023 เส้น · สถานะของ DFA = 6
      ตัวอย่างแรกที่ไม่ตรง: "10" (DFA=false regexp=true)
```

`"10"` — จำนวน `1` = 1 ตัว = **คี่** แต่รอบแรกเราลืมไปว่าท่อนท้าย `0*10` มี `1` อยู่**ตัวเดียว** จึงรับ `"10"` ทิ้ง ๆ ทั้งที่ DFA ไม่รับ · วิธีแก้คือเติม `0*1` เข้าท่อนท้าย (`0*10` → `0*10*10`) ให้ท่อนท้ายมี `1` **สองตัว = คู่** เสมอ (และยังปิดท้ายด้วย `10` เหมือนเดิม) แล้วได้:

```
  P ∩ Q (รอบสอง — ที่ถูก)        regexp = ^(0*10*1)*0*10*10$
      ไม่ตรงกัน 0 จาก 8191 เส้น · ภาษานี้รับ 1023 เส้น · สถานะของ DFA = 6
```

**บทเรียน**: การ "คิด regex ของ intersection ด้วยหัว" คือความผิดพลาด — รอบแรกผิดไป **2,047 จาก 8,191 เส้น (ราว 1 ใน 4)** ส่วนการสร้างเครื่องคูณกันเป็น **กลไก** — ทำตามกติกาแล้วได้ผลถูกเสมอ นี่คือเหตุผลที่คนทำงานจริงเลือก "สร้างเครื่อง (หรือเขียน DFA ในโค้ด)" เมื่อ logic ซับซ้อน และเลือก regex เมื่อมันสั้นจริง ๆ

### 4.2 อีกกับดัก: ตาราง δ ที่เขียนผิดโดยไม่รู้ตัว

การทดสอบ "ครบทุกเส้น" จับบั๊กจริงใน **ไฟล์แรก** ของบทนี้ด้วย ตอนแรกเราลงตาราง P ว่า

```go
{0, 1}, // p0 (คู่) : 0 ไม่เปลี่ยน · 1 สลับเป็นคี่
{0, 1}, // p1 (คี่) : <- ผิด! แถวนี้เขียนตามแถวบนโดยไม่คิด
```

แถวที่สองผิด เพราะจากสถานะ "คี่" เจอ `1` ต้อง**กลับไปคู่** ที่ถูกคือ `{1, 0}` ซึ่งหมายถึง "เจอ `0` คี่อยู่ที่เดิม · เจอ `1` กลับไปคู่" — ผลคือโปรแกรมตอบ `true` กับ `"10"` (ทั้งที่ควร `false`) และตัวทดสอบครบทุกเส้นก็ฟ้องทันที

```go
{1, 0}, // p1 (คี่) : 0 ไม่เปลี่ยนอะไร · 1 กลับเป็นคู่   <-- จุดที่พลาดง่ายที่สุด
```

กับดักนี้สำคัญกว่ารูปร่างของมัน เพราะมือใหม่มักเชื่อ "ตารางที่ตัวเองเพิ่งเขียน" — **เครื่องมีไว้เขียน ตัวทดสอบมีไว้เถียงมัน**

## 5. ลงมือทำ (3): `03_nfa_subset` — ดูของจริงว่า Go คอมไพล์ regex เป็นอะไร

หัวข้อ 1.3 เราดู NFA แบบทฤษฎี ตอนนี้มาดู **ของจริงจากแพ็กเกจ `regexp/syntax` ของ Go เอง** — โปรแกรมของเราพิมพ์โปรแกรมคำสั่งที่ Go สร้างขึ้นจริง ๆ ให้ดู:

```
== 5) ดูของจริงจาก Go: regex ถูกคอมไพล์เป็น 'โปรแกรม NFA' หน้าตาแบบไหน ==
  ต้นไม้ที่ได้จากการแยก (parse tree): a*b
  โปรแกรมคำสั่งที่ Go สร้าง (syntax.Prog.String()):
     0:   0	fail
     1:   1	rune1 "a" -> 2
     2:   2*	alt -> 1, 3
     3:   3	rune1 "b" -> 4
     4:   4	match
```

ลองเทียบกับ NFA ที่เราวาดเองในภาพที่ 2 ทีละบรรทัด:

| โปรแกรมของ Go | เทียบกับ NFA ของเรา |
|---|---|
| `2* alt -> 1, 3` | **จุดแยกของ star** — `*` ที่ท้ายเลข 2 แปลว่า "นี่คือตำแหน่งเริ่ม" (ตรงกับสถานะ 1 ในภาพที่ 2 ของเรา) |
| `1 rune1 "a" -> 2` | อ่านตัวอักษร `a` หนึ่งตัวแล้วไปต่อ (เนื้อในของ `a*`) |
| `3 rune1 "b" -> 4` | อ่าน `b` แล้วไปสถานะรับ |
| `4 match` | เจอคำตอบแล้ว (เทียบได้กับสถานะรับ) |
| `0 fail` | ทางที่ไม่มีคำตอบ (Go ใส่คำสั่งนี้ไว้เป็นคำสั่งที่ 0 เสมอ) |

**นี่คือคำตอบของคำถามตั้งต้นของบท**: เวลาคุณเขียน `regexp.MustCompile("a*b")` โปรแกรมไม่ได้เก็บ "ข้อความ `a*b`" ไว้ค้นหาทีละตัวอักษร — มัน **คอมไพล์เป็นโปรแกรมของเครื่องสถานะ** (instruction = คำสั่งเครื่อง) แล้วเดินเครื่องนั้นบน input · ความต่างจาก "เครื่องในตำรา" คือ Go มีคำสั่งเพิ่ม (จับกลุ่ม, เงื่อนไขขอบเขตข้อความ, ฯลฯ) เพื่อรองรับไวยากรณ์ที่ซับซ้อนกว่า `a*b` แต่แก่นยังเป็น NFA

คำสั่งที่อยู่ในหัวข้อนี้ (ยืนยันจาก source ที่ติดตั้งบนเครื่องนี้ — `/usr/lib/go-1.24/src/regexp/syntax/prog.go`): `InstAlt` (แยกเป็นสองทาง = เทียบเท่าขอบ ε ของเรา) · `InstRune` / `InstRune1` (กินตัวอักษร) · `InstMatch` (จบแบบสำเร็จ) · `InstFail` (จบแบบล้มเหลว) · `InstCapture` (จับกลุ่ม) · `InstEmptyWidth` (เงื่อนไขขอบเขต เช่น `^` `$`)

และจาก source เดียวกัน เรายังยืนยันได้ว่าทำไมโปรแกรมที่พิมพ์ออกมามี `fail` อยู่บรรทัดแรก: ใน `syntax/compile.go` ฟังก์ชัน `init()` ใส่ `InstFail` เป็นคำสั่งแรก ก่อนคอมไพล์เนื้อ regex (`c.inst(InstFail)`) และตอนจบ `Compile()` ติดป้าย `Start` ให้คำสั่งที่เริ่มจริง — จึงมีเครื่องหมาย `*` ที่บรรทัด `2*` นั่นเอง

### 6.1 เขียน matcher แบบ "ถอย" เอง แล้วนับก้าว

เราเขียน matcher เล็ก ๆ ที่ทำงานแบบเดียวกับเอนจิน backtracking ทั่วไป: ลองทางหนึ่งก่อน ถ้าไม่สำเร็จก็ย้อนกลับมาลองทางอื่น โดยไม่จำอะไรเลยว่าเคยลองอะไรไปแล้ว

อ่านโค้ดนี้ทีละส่วน (ทั้งบทจะพูดถึงมันอีกหลายรอบ):

- `type cont func(pos int) bool` = **CPS (continuation-passing style)**: แทนที่จะ "จับคู่ท่อนนี้แล้วคืนค่า จริง/เท็จ" เรา**ส่งงานที่เหลือทั้งหมดเป็นฟังก์ชัน `k` ติดไปด้วย** — พอท่อนนี้สำเร็จก็เรียก `k(pos)` เพื่อเริ่มจับคู่ส่วนที่เหลือต่อจากตำแหน่งนั้น · การร้อยท่อนของ pattern เข้าด้วยกันแบบนี้เองที่ทำให้ "ถอย" ทำได้ (ถ้าท่อนปลายทางตอบ `false` เราก็ย้อนมาลองทางอื่น)
- `case 'c'` = ท่อนตัวอักษรหนึ่งตัว: ถ้าตรงก็ส่งงานต่อ `k(pos+1)` ถ้าไม่ตรงก็ `false` (ไม่กินอะไรเลย)
- `case 's'` = ต่อกัน (sequence): เรียก `m.matchSeq(...)` — ตัวนั้น**อยู่ในไฟล์เต็ม `04_engines/main.go`** (ในบทนี้ตัดออกเพราะยาว) หน้าที่ของมันคือไล่ท่อนย่อยใน `n.subs` ทีละท่อน แล้วส่งงานต่อให้ท่อนสุดท้าย
- `case 'a'` = เลือกอย่างใดอย่างหนึ่ง: `for` ไล่ทีละทางจนเจอทางที่สำเร็จ ทางไหนไม่สำเร็จก็ตกไปทางถัดไป (นี่คือ "การถอย" ชั้นแรก)
- `case '*'` = จุดที่ราคาแพงที่สุด: **ลอง "ซ้ำอีกรอบ" ก่อน แล้วค่อยถอยไปลอง "หยุดตรงนี้"** (`return k(pos)` ท้ายสุด) · ลำดับการเลือกนี้เองที่ทำให้จำนวนทางที่เป็นไปได้คูณทบกันแบบทวีคูณ

```go
// cont = "ส่วนที่เหลือของการจับคู่" ที่ถูกเรียกเมื่อท่อนนี้สำเร็จ
type cont func(pos int) bool

func (m *naiveMatcher) match(n *node, pos int, k cont) bool {
	m.steps++                        // นับทุกครั้งที่ "ลอง" = ตัวเลขที่ทำให้เห็นความต่างชัดกว่าการจับเวลา
	switch n.kind {
	case 'c':                        // ตัวอักษรหนึ่งตัว
		if pos < len(m.in) && m.in[pos] == n.ch {
			return k(pos + 1)
		}
		return false
	case 's':                        // ต่อกัน: จับคู่ทีละท่อน ส่งไม้ต่อให้ท่อนถัดไป
		return m.matchSeq(n.subs, 0, pos, k)
	case 'a':                        // เลือกอย่างใดอย่างหนึ่ง: ลองทีละทาง
		for _, sub := range n.subs {
			if m.match(sub, pos, k) { return true }
		}
		return false
	case '*':                        // ซ้ำ: ลอง "ซ้ำอีกหนึ่งรอบ" ก่อน แล้วค่อยถอยไปลอง "หยุดตรงนี้"
		if m.match(n.subs[0], pos, func(q int) bool {
			if q == pos { return false }   // กันลูปไม่รู้จบ เมื่อท่อนข้างในไม่กินตัวอักษรเลย
			return m.match(n, q, k)
		}) {
			return true
		}
		return k(pos)
	}
	return false // กันพลาด: ถ้าเจอ kind ที่ไม่รู้จัก ให้ตอบว่า "ไม่ตรง"
}
```

ก่อนจะคุยเรื่องความเร็ว เราต้องรู้ว่า **มันถูกก่อน** — เทียบกับ regexp ของ Go ทุกเส้น:

```
== 1) ตรวจว่า matcher แบบ backtracking ของเรา 'ถูก' ก่อนจะพูดเรื่องความเร็ว ==
  ทดสอบสตริงบน {a,b} ยาว 0..8 ครบทุกเส้น = 511 เส้น · ไม่ตรงกับ regexp ของ Go 0 เส้น
```

แล้วป้อน pattern สองตัวที่**รู้จักภาษาเดียวกันเป๊ะ** — ตัวหนึ่งเขียนแบบซ้อนวงเล็บ ตัวหนึ่งเขียนตรง ๆ:

- `(a+)+b` — a หนึ่งตัวขึ้นไป ซ้ำอีกกี่รอบก็ได้ แล้วปิดด้วย b
- `a+b` — a หนึ่งตัวขึ้นไป แล้วปิดด้วย b

ทั้งสองไม่รับ input `aaaa…` (ไม่มี b) เหมือนกัน — แต่ราคาต่างกันแบบคนละโลก:

```
== 2) ระเบิดแบบเอกซ์โพเนนเชียล: input ที่ไม่มีทางสำเร็จ ==
  pattern (a+)+b กับ input = a×n ที่ไม่มี b ปิดท้ายเลย (ไม่มีทางสำเร็จแน่นอน)
  n      input                      steps (nested) steps (flat)   DFA ก้าว
  4      a×4                        93             14             4
  8      a×8                        1533           26             8
  12     a×12                       24573          38             12
  16     a×16                       393213         50             16
  18     a×18                       1572861        56             18
  20     a×20                       6291453        62             20
  22     a×22                       25165821       68             22
```

อ่านตัวเลขให้ครบ:

- `(a+)+b`: n เพิ่มทีละ 4 ตัว → ก้าวคูณประมาณ **16 เท่า** (n=4 → 93 ก้าว · n=22 → **25,165,821 ก้าว** — คูณราว 270,000 เท่า) — โตแบบ 2ⁿ
- `a+b`: ตัวเดียวกันเป๊ะ แต่โตแบบ **3n + 2** (n=22 → 68 ก้าว)
- **DFA ของเรา**: n ก้าวพอดี

และกับดักที่โหดที่สุดคือ input ที่ "เกือบถูก" — มี `b` ครบตามที่ pattern ต้องการ แต่มีตัวอักษรเกินมาท้ายสุด:

```
== 3) กับดักที่โหดที่สุด: เกือบสำเร็จแล้วพังท้ายสุด ==
  n      input                      steps (nested)   steps (flat)
  8      a×8 + bc                   1533             26
  …
  16     a×16 + bc                  393213           50
  …
  20     a×20 + bc                  6291453          62
```

ตัวเลขเท่ากับหัวข้อ 2 **เป๊ะทุกบรรทัด** (8 → 1,533 · 16 → 393,213 · 20 → 6,291,453 — และ 12, 18 ก็ตรงกันด้วย) เพราะการมี `b` ไม่ได้ช่วยตัดทางเลือกทิ้งเลย: เอนจินยังต้องไล่ลองทุกวิธีแบ่ง `a` ให้ท่อน `(a+)+` เหมือนเดิม แล้วเพิ่งไปพังที่ `c` ตัวเกินตอนท้าย · นี่คือจุดที่คนมักเข้าใจผิด — คิดว่า "เกือบถูก" จะเร็วกว่า "ผิดตั้งแต่ต้น" แต่จริง ๆ ช้ากว่าและเท่ากัน

### 6.2 แล้วของ Go ล่ะ

```
== 4) regexp ของ Go: pattern เดียวกันเป๊ะ บน input ขนาดใหญ่ ==
  n          Go (a+)+b              Go a+b                 DFA ของเรา
  10000      false · 654µs          false · 206µs          false · 29µs
  100000     false · 9.078ms        false · 1.993ms        false · 293µs
  1000000    false · 90.648ms       false · 19.742ms       false · 2.932ms
```

อ่านให้ครบห้าชั้น:

1. **ไม่มีการระเบิด — แต่ต้องอ่านให้ถูกชั้น**: ที่ n=10,000 regexp ของ Go ยังใช้ **bitState backtracker** (ตัวถอยแบบจำสถานะด้วยบิตแมป — อธิบายเต็มในหัวข้อ 6.4; input 10,000 ตัว ยังต่ำกว่าเพดาน `maxBitStateLen` ของ pattern นี้ — `^(a+)+b$` มี 10 คำสั่ง → เพดาน 26,214 ตัวอักษร ส่วน 32,768 ในหัวข้อ 6.4 เป็นของ `(a+)+b` แบบไม่มี anchor) พอ n=100,000 เกินเพดาน จึงสลับไปเดินแบบ **NFA machine** → ตั้งแต่ n ≥ 100,000 เป็นต้นไป ทุกครั้งที่ input โต 10 เท่า เวลาก็โต ~10.0 เท่าพอดี (9.078ms → 90.648ms) ส่วนช่วงรอยต่อ 10,000 → 100,000 เวลาโต 13.9 เท่า (654µs → 9.078ms) เพราะเป็นเวลาของคนละเอนจิน · ถ้าเป็นเอนจินแบบถอยที่ไม่มีอะไรกันเลย ตัวเลขของ `(a+)+b` ที่ n=1,000,000 จะไม่ใช่ 91 มิลลิวินาที แต่เป็นตัวเลขที่ **มากกว่าอายุของเอกภพหลายเท่าตัว**
2. **ค่าคงที่ (constant factor) คือราคาที่จ่าย** — เอกสาร RE2 พูดเรื่องนี้ตรง ๆ ว่า RE2 ไม่ได้ตั้งเป้าเป็นเอนจินที่เร็วที่สุดในทุกสถานการณ์
3. **ทำไม `(a+)+b` ช้ากว่า `a+b`** — 90.648 ms เทียบ 19.742 ms: pattern ที่ซับซ้อนกว่าต้อง "เดินทุกทางพร้อมกัน" เผื่อทางที่ไม่มีทางเกิดขึ้น จึงแบกค่าคงที่มากกว่า
4. **DFA ที่เราเขียนเองใช้ 2.93 ms** — เร็วที่สุด เพราะมันถูกออกแบบมาเพื่อ pattern เดียวนี้เท่านั้น · regex ทั่วไปทำแบบนั้นไม่ได้ (ต้องรองรับ pattern อะไรก็ได้ที่ผู้ใช้พิมพ์มา)
5. **ไม่มี input ที่ทำให้ค้าง** — กฎนี้ใช้ได้เสมอ ซึ่งเป็นเหตุผลที่ Go ปลอดภัยกว่าในการรับ pattern/input จากภายนอก

### 6.3 ราคาที่จ่ายไป: ฟีเจอร์ที่ไม่มี

```
== 5) ข้อจำกัดที่แท้จริงของเอนจินแบบนี้: สิ่งที่ทำไม่ได้เลย ==
  (a)\1      backreference (อ้างถึงกลุ่มที่จับไว้ก่อนหน้า) -> error parsing regexp: invalid escape sequence: `\1`
  (?=ab)a    lookahead (มองล่วงหน้า)              -> error parsing regexp: invalid or unsupported Perl syntax: `(?=`
  (?<=x)y    lookbehind (มองย้อนหลัง)             -> error parsing regexp: invalid named capture: `(?<=x)y`
```

สามบรรทัดนี้คือข้อความ error จริงจาก Go 1.24.4 บนเครื่องนี้ · สังเกตบรรทัดสุดท้ายให้ดี: Go ตีความ `(?<` เป็นไวยากรณ์ของ "กลุ่มแบบมีชื่อ" (`(?<name>…)`) ก่อน จึงฟ้องว่า `invalid named capture` — ข้อความไม่สวยนักก็จริง แต่มันบอกความจริงสำคัญ: **ไม่ใช่แค่ "ยังไม่รองรับ" แต่ไวยากรณ์นี้ไม่มีความหมายในโลกของ automata ที่เดินทุกทางพร้อมกัน**

เหตุผลทางทฤษฎีตรงกับข้อเท็จจริงนี้เป๊ะ: backreference (`\1` = "ข้อความตรงกับที่กลุ่ม 1 จับไว้") ต้อง**จำข้อความที่จับได้** — ซึ่งเกินความสามารถของเครื่องที่รู้แค่ "สถานะ" · และ lookaround ต้อง "มองโดยไม่กินตัวอักษร" ซึ่งถ้าปล่อยให้มองย้อนหลังได้ไม่จำกัด ก็เท่ากับกลับไปต้องถอยอีก · เอกสาร RE2 ระบุหลักการไว้ว่า *"as a matter of principle, RE2 does not support constructs for which only backtracking solutions are known to exist"* (โดยหลักการแล้ว RE2 ไม่รองรับโครงสร้างที่รู้กันว่าทำได้เฉพาะด้วยวิธีถอย)

### 6.4 เบื้องหลัง: Go เลือกเอนจินยังไง

ส่วนนี้ดึงจาก source ของ Go ที่ติดตั้งบนเครื่องนี้ (`$(go env GOROOT)/src/regexp/`) — โปรแกรมที่เราเขียนอ่านไฟล์จริงมาพิมพ์ให้ดู:

![จาก regex ถึงโปรแกรมคำสั่ง และเอนจินที่ Go เลือกใช้](/assets/diagrams/ep22-04-regex-to-prog.svg)

```
== 6) ข้อเท็จจริงจาก source ของ Go 1.24.4 ที่ติดตั้งบนเครื่องนี้ ==
  GOROOT = /usr/lib/go-1.24
  -- src/regexp/backtrack.go
     maxBacktrackProg   = 500        // len(prog.Inst) <= max
     maxBacktrackVector = 256 * 1024 // bit vector size <= max (bits)
     return maxBacktrackVector / len(prog.Inst)
     return len(prog.Inst) <= maxBacktrackProg
     b.visited = make([]uint32, visitedSize, maxBacktrackVector/visitedBits)
  -- src/regexp/exec.go
     func (re *Regexp) doExecute(r io.RuneReader, b []byte, s string, pos int, ncap int, dstCap []int) []int {
     if r == nil && len(b)+len(s) < re.maxBitStateLen {
  …
  จำนวนคำสั่งจริงของแต่ละ pattern (ตัวเลขนี้กำหนดเพดาน maxBitStateLen):
  pattern (a+)+b   len(prog.Inst) =  8  -> maxBitStateLen = 32768 ตัวอักษร
  pattern a+b      len(prog.Inst) =  5  -> maxBitStateLen = 52428 ตัวอักษร
  (input ที่ยาวเกิน maxBitStateLen จะไม่เข้าเส้นทาง backtracker — อ่านคำอธิบายได้ในหัวข้อ 6.2 ของบทความ)
```

แปลว่าอะไร (อ่านจาก `exec.go` + `backtrack.go` + `onepass.go` ตรง ๆ):

`b.visited` คือ **บิตแมป**: หนึ่งบิตต่อหนึ่งคู่ "(คำสั่งที่ pc, ตำแหน่งใน input)" — ก่อนจะลองคู่ไหน ตัวถอยจะเช็กบิตของคู่นั้นก่อน ถ้าเป็น 1 แปลว่า "เคยลองแล้ว" ก็ข้ามทันที (ขนาดสูงสุด `maxBacktrackVector` = 256×1024 บิต = 32 KiB) · และเพราะ `maxBitStateLen` คำนวณจาก `maxBacktrackVector ÷ len(prog.Inst)` เพดาน input จึงขึ้นกับ "pattern นี้มีกี่คำสั่ง" ของจริง

1. **onepass** — ถ้าโปรแกรมคำสั่งมีคุณสมบัติ "ไม่มีจุดที่กำกวม" (ที่ `InstAlt` ทุกจุด ตัดสินได้ทันทีว่าจะไปทางไหน) Go จะเดินครั้งเดียวไม่ถอยเลย
2. **backtracking (bitState)** — ใช้เมื่อเข้าเงื่อนไขครบทั้ง 4 ข้อ: (1) โปรแกรมมี **ไม่เกิน 500 คำสั่ง** (`len(prog.Inst) <= maxBacktrackProg`) (2) จำนวนบิตที่ต้องใช้ไม่เกิน `maxBacktrackVector` (256×1024 บิต) (3) **ความยาว input น้อยกว่า `maxBitStateLen`** ซึ่งคำนวณจาก `maxBacktrackVector ÷ len(prog.Inst)` และ (4) **ผู้เรียกไม่ได้ส่ง `io.RuneReader` มา** — ใน source เขียนตรง ๆ ว่า `if r == nil && len(b)+len(s) < re.maxBitStateLen` (เงื่อนไข `r == nil` นี้เองที่ทำให้ `regexp.MatchString` ที่รับสตริงเข้าเส้นทางนี้ได้ แต่การอ่านแบบสตรีมผ่าน RuneReader ไม่ได้) · **แต่ตัวถอยของ Go ไม่เหมือนตัวที่เราเขียนในหัวข้อ 6.1** เพราะมันมี `visited` (บิตแมปที่จำว่า "(คำสั่ง, ตำแหน่ง)" คู่ไหนลองไปแล้ว) → **ไม่ลองซ้ำ** จึงไม่ระเบิด
3. **NFA machine** — ที่เหลือทั้งหมด (โปรแกรมยาว หรือ input ยาว) ใช้การเดินทุกทางพร้อมกัน ซึ่งเป็นวิธีที่รับประกันเชิงเส้นเต็มตัว

**นี่คือคำตอบสุดท้ายของบทนี้**: ข้อรับประกัน "เวลาเชิงเส้น" ของ Go ไม่ได้มาจาก "ใช้แต่ DFA" (เพราะการสร้าง DFA ให้ regex ทั่วไปอาจได้สถานะเป็นแสน ๆ) แต่มาจาก **การออกแบบที่ไม่มีทางให้ลองซ้ำ** — ไม่ว่าจะเป็น onepass, bitState ที่จำ visited, หรือการเดินทุกทางพร้อมกัน ทั้งสามแบบต่างก็ "ไม่ถอยซ้ำ" ทั้งสิ้น

## 7. กับดักจริงที่เจอในบทนี้ (และวิธีกัน)

1. **ตาราง δ แถวที่ 2 ที่เขียนตามแถวที่ 1** — จากสถานะ "คี่" ต้องสลับกลับเป็น "คู่" เมื่อเจอ `1` ไม่ใช่คงที่ · จับได้ด้วยการทดสอบครบทุกเส้น (หัวข้อ 4.2)
2. **"คิด regex ของ intersection เองด้วยหัว"** — พลาด 2,047 จาก 8,191 เส้น (ราว 1 ใน 4) ในความพยายามแรก · ทางแก้ที่ถูกคือสร้างเครื่องคูณกัน (product construction) แล้วให้เครื่องบอกคำตอบ (หัวข้อ 4.1)
3. **ลืม `^` `$`** — `MatchString` ค้นหาแบบ "เจอที่ไหนก็ได้" ถ้าไม่ยึดหัวท้ายจะเทียบกับ DFA ที่ตรวจทั้งสตริงไม่ได้เลย
4. **`(a+)+` กับ `a+` ไม่เหมือนกันในทาง regex** — `(a+)+` บังคับว่าต้องมี `a` อย่างน้อยหนึ่งตัวเหมือนกัน แต่การซ้อน quantifier ทำให้เอนจินแบบถอย "เห็น" ทางเลือกเป็น 2ⁿ ทาง · matcher ของเราถูกจับได้ด้วยการเทียบทุกเส้น (หัวข้อ 6.1) — ถ้าไม่ทดสอบ เราจะเขียนบทความอธิบายผิดทันที
5. **นับผิดเรื่อง "จำนวนก้าวของ NFA"** — NFA หนึ่งก้าวหมายถึง "ก้าวของ**เซต**สถานะ" ไม่ใช่ก้าวของเส้นทางเดียว · ถ้าเข้าใจผิดจะคิดว่า NFA ช้ากว่า DFA ซึ่งไม่จริงในเชิงจำนวนก้าว (มันจ่ายเป็นขนาดเซต)
6. **ลืม ε-closure** — หลังอ่านตัวอักษรทุกครั้ง (และก่อนอ่านตัวแรก) ต้องปิด ε เสมอ ไม่งั้นจะ "มองไม่เห็น" สถานะที่ย้ายฟรีไปถึง และตอบผิดแบบเงียบ ๆ
7. **สมมติว่า RE2 = Go regexp** — Go ไม่ได้ใช้โค้ดของ RE2 (คนละภาษา คนละโปรเจกต์) แต่ยึดหลักการเดียวกัน รับไวยากรณ์เดียวกัน · ถ้าอ้างผิดจะพลาดรายละเอียดสำคัญ (Go ไม่รองรับ `\C` ซึ่ง RE2 รองรับ)
8. **สมมติว่า "regex ของทุกภาษาเหมือนกัน"** — PCRE/Perl/Python รองรับ backreference (ด้วยราคาของ catastrophic backtracking) · Go/Rust/RE2 ไม่รองรับ · โค้ดที่ย้ายข้ามภาษาแล้ว "ไม่เหมือนเดิม" มักมาจากจุดนี้
9. **ใช้ regex กับ input ที่ผู้ใช้ควบคุมโดยไม่จำกัด** — ถ้าไปรันบนเอนจินแบบถอย (ภาษา/ไลบรารีอื่น) นี่คือช่องโหว่ ReDoS ตัวจริง · ทางกันคือ ใช้เอนจินแบบเดินทุกทางพร้อมกัน, จำกัดความยาว input, หรือเขียน DFA เองเมื่อ pattern รู้ล่วงหน้า
10. **เชื่อว่า "ถ้า regex ผ่านแสดงว่าถูก"** — regex ที่คิดเองจะดูน่าเชื่อถือเสมอ · กฎที่ใช้ได้ตลอดคือ เขียนตัวทดสอบที่แจกแจงครบ (หรือ property-based test — การทดสอบที่ให้โปรแกรมสร้าง/สุ่ม input จำนวนมากมาทดสอบสมบัติ แทนการเขียนตัวอย่างทีละตัว) แล้วให้มันเถียงกับ regex ของคุณ

|---|---|---|---|

## 9. สรุปสั้น 10 ข้อ

1. **regex ไม่ใช่ "ข้อความสำหรับค้นหา" แต่คือสัญกรณ์ย่อของเครื่องสถานะจำกัด** — `regexp.MustCompile("a*b")` ให้โปรแกรมคำสั่ง 5 บรรทัด (`alt`, `rune1`, `match`, …) ไม่ใช่ข้อความ
2. **DFA = กำหนดได้ (deterministic) + ไม่ถอย** — เพราะทุก (สถานะ, สัญลักษณ์) มีทางเดียว จึงรับประกันได้ว่าเวลา = จำนวนตัวอักษร
3. **NFA = เดาได้ + ยังไม่ถอย** — เพราะใช้ "เซตสถานะ" เดินทุกทางพร้อมกัน · NFA เขียนง่ายกว่า DFA เสมอ จึงใช้เป็นตัวกลางก่อนแปลง
4. **subset construction: DFA state = เซตของ NFA state** — NFA 5 สถานะของเรากลายเป็น 3 เซตที่ไปถึงได้จริง (+ ∅)
5. **ทฤษฎีบทของ Kleene: regex ≡ NFA ≡ DFA ≡ ภาษาปกติ** — สามอย่างนี้ไม่ใช่ "คล้ายกัน" แต่เป็นสิ่งเดียวกัน
6. **regex เกิดปี 1951 (Kleene)** จากการศึกษาแบบจำลองเซลล์ประสาท · ถูก implement เป็นโปรแกรมจริงปี 1968 (Thompson) · แนวคิด/ไวยากรณ์สืบต่อผ่าน ed → `grep` ปี 1973 จากคำสั่ง `g/re/p` (แต่ ed/grep ใช้ recursive backtracking ไม่ใช่อัลกอริทึม NFA ของ Thompson)
7. **"และ" (intersection) ทำได้ผ่าน product construction** — ไม่มีใน regex แต่มีในโลกของ automata และตรวจได้จริง 8,191/8,191 เส้น
8. **catastrophic backtracking คือเรื่องจริงที่วัดได้** — pattern `(a+)+b` บน input 22 ตัวอักษร ใช้ 25,165,821 ก้าว ขณะที่ `a+b` ใช้ 68 ก้าว และ DFA ใช้ 22 ก้าว
9. **ราคาของความปลอดภัยคือการตัดฟีเจอร์** — Go ไม่รองรับ backreference/lookaround (ยืนยันด้วยข้อความ error จริง) เพราะสิ่งเหล่านั้นต้องการการถอย
10. **ขีดจำกัดไม่ใช่เรื่องของ "regex ที่เขียนไม่ดี" แต่เป็นข้อจำกัดของแบบจำลอง** — `aⁿbⁿ` และวงเล็บเปิด-ปิดเท่ากันทำไม่ได้เลย ซึ่งนำไปสู่ตอนที่ 23

## 10. โจทย์ฝึกมือ (2 ระดับ)

### ระดับ Drill (ซ้อมทวนความเข้าใจ)

1. **เพิ่มสถานะให้ DFA ของตัวเอง** — แก้ `01_dfa_astar/main.go` ให้รู้จักภาษา `a*b*` (a กี่ตัวก็ได้ แล้วต่อด้วย b กี่ตัวก็ได้) เขียนตาราง `delta` ใหม่ (ต้องมีกับดักตายแยกออกจากสถานะรับ) แล้วเปลี่ยน regexp ที่ใช้ตรวจเป็น `^a*b*$` ให้ตัวทดสอบรายงาน "ไม่ตรงกัน 0 เส้น" · จากนั้นนับก้าวกับ input ที่ยาวขึ้นเรื่อย ๆ — ก้าวโตเท่าจำนวนตัวอักษรไหม?
2. **ทดลองกับ `^` `$` ที่หายไป** — รัน `re.MatchString("xxaab")` กับ pattern `a*b` (ไม่มี `^$`) แล้วเทียบกับ `^a*b$` · อธิบายว่าทำไมตัวแรกตอบ `true` · แล้วแก้โปรแกรมให้ตรวจว่า **เจอที่ตำแหน่งไหน** (ใช้ `FindStringIndex`) เพื่อดูด้วยตาว่ามันเจอกี่ตำแหน่ง
3. **พิสูจน์ว่า NFA "ไม่ช้ากว่า" DFA ในเชิงก้าว** — แก้ `03_nfa_subset/main.go` ให้เพิ่มสตริงยาว ๆ (เช่น `"a"×1000 + "b"`) แล้วพิมพ์ "จำนวนก้าว" กับ "ขนาดเซตใหญ่สุด" ของ NFA เทียบกับ DFA · อธิบายว่าทำไมตัวเลขถึงเป็นแบบนั้น (ใบ้: NFA ใช้ 1,001 ก้าวเท่ากัน แต่แต่ละก้าวต้องรวม (union) หลายสถานะเข้าด้วยกัน)
4. **หาขอบของ catastrophic backtracking** — ใช้ `04_engines/main.go` เพิ่ม n ไปเรื่อย ๆ (24, 26, 28 …) แล้วบันทึกจำนวนก้าวและเวลาที่ใช้จริง · หาว่าที่ n เท่าไรเครื่องนี้เริ่มใช้เวลาเกิน 1 วินาที และทำนาย n ที่จะใช้เกิน 1 ชั่วโมง (จากอัตราส่วนที่วัดได้ — ไม่ต้องรันจริง!) · แล้วรัน pattern เดียวกันด้วย regexp ของ Go ที่ n เท่ากันเพื่อเทียบ

### ระดับ Mini-Project (ประกอบความรู้)

**เขียน `mini_lexer` — ตัวตัดคำจิ๋วที่ใช้ DFA จริง (ไม่ใช้ regex)**

- รับข้อความหนึ่งบรรทัดจาก argument (หรือ stdin) แล้วตัดเป็นชิ้น (token) 4 ชนิด: **ชื่อ** (`[a-z][a-z0-9]*`), **ตัวเลข** (`[0-9]+`), **ตัวดำเนินการ** (หนึ่งใน `+ - * / = ( ) <>`), **ตัวอักษรอื่นที่ไม่รู้จัก** (ต้องรายงานเป็น error พร้อม**ตำแหน่ง** ไม่ใช่ทิ้งไปเงียบ ๆ) · ข้ามช่องว่างและ tab
- **ข้อบังคับ**: เขียนแต่ละชนิดเป็น **ตาราง DFA** (`delta` + สถานะรับ/ตาย) ห้ามใช้แพ็กเกจ `regexp` และห้ามใช้ `strings.Fields` — และวาด **แผนภาพสถานะ (state diagram) ของแต่ละ token** เป็น SVG เอง (ใช้ `gen_svgs.py` เป็นแนวทาง: generator ด้วย Python ไม่ใช่แก้ไฟล์ SVG ตรง ๆ)
- **เกณฑ์ผ่าน**: (1) `x2 := 42` ให้ `[ชื่อ "x2"] [ตัวดำเนินการ ":="] [ตัวเลข "42"]` — **หมายเหตุ: ให้เพิ่ม `:` เข้าเซตตัวดำเนินการ** (2) `007abc` ต้องไม่ตัดเป็นชื่อ (เพราะขึ้นต้นด้วยตัวเลข → ตัวเลข `007` แล้วตามด้วยชื่อ `abc` แยกกัน) (3) `@` ต้องได้ error พร้อมตำแหน่ง (คอลัมน์ที่เท่าไร) (4) รันซ้ำด้วย input เดิมให้ผลเท่าเดิมเสมอ
- **โบนัส**: เพิ่ม token **จำนวนเต็มที่มีเครื่องหมาย** (`-42`) โดยใช้ DFA ที่ "จำได้ว่าครั้งก่อนเพิ่งเจอเครื่องหมายลบ" — สังเกตว่าคุณจะเจอปัญหาการเลือกแบบเดา (จะตีความ `-` เป็นตัวดำเนินการลบหรือเครื่องหมายจำนวนลบ?) ซึ่งในโลกจริงคือเหตุผลที่ lexer ต้องมีกติกา "เลือกให้ยาวที่สุด" (maximal munch) เขียนอธิบายกติกาของคุณไว้ใน README

**bonus ท้าทาย (ไม่บังคับ): `mini_regex` — matcher ของตัวเองพร้อมตารางวัดความเร็ว**

- เขียนฟังก์ชันแปลง regex ขนาดเล็ก (รองรับ `.`, `*`, `+`, `?`, `|`, `()`) เป็น **NFA** ตามวิธีของ Thompson แล้วเดินด้วยเซตสถานะ (เขียนเองทั้งหมด)
- **เกณฑ์ผ่าน**: matcher ของคุณกับ `regexp` ของ Go ตอบตรงกันบนสตริง `{a,b,c}` ที่ยาว 0..7 (ทั้งหมด 3,280 เส้น — ใช้การแจกแจงครบแบบเดียวกับที่เราทำ) ทุกกรณี รวม pattern ที่ซ้อน quantifier
- **โจทย์วัด**: วัดเวลา pattern `(a+)+b` บน input `a`×5,000 ของ matcher คุณ เทียบกับ `naiveMatcher` ในหัวข้อ 6.1 (ถ้าของคุณเร็วต่างกันเป็นพันเท่า แปลว่าคุณสร้าง NFA ถูกแล้ว)

## 11. คำเตือนตามกาลเวลา + แหล่งอ้างอิง

**As of กันยายน 2026** — ทุกตัวเลขในบทนี้มาจากการรันจริงบน Raspberry Pi 5 Model B (Linux 6.18.39+rpt-rpi-2712 aarch64 · **Go 1.24.4 linux/arm64** · RAM 7.9 GiB) เมื่อ `2026-09-26T05:38:08+07:00` — โค้ด+ผลรันดิบอยู่ที่ `course/code/ep22/` (รันซ้ำทั้งหมดด้วย `bash run_all.sh`)

- **"เวลาเชิงเส้น" เป็นการรับประกันเชิงเส้นกำกับ (asymptotic)** — ไม่ได้บอกว่ามันเร็วที่สุดใน ทุกกรณี · วัดจริง: `(a+)+b` บน 1,000,000 ตัวอักษรของ Go ใช้ 90.648 ms ขณะที่ DFA เฉพาะทางของเราใช้ 2.93 ms (ช้ากว่า ~31 เท่า) · เลือกเครื่องมือให้ตรงกับงาน ไม่ใช่เลือกเพราะ "ปลอดภัยกว่า"
- **ตัวเลขเวลาเปลี่ยนทุกครั้งที่รัน** — ตัวเลขก้าว (steps) ต่างจากนี้: **มันเท่าเดิมทุกรอบ** เพราะเป็นการนับเชิงตรรกะ ไม่ใช่การจับเวลา · นี่คือเหตุผลที่ในบทนี้ใช้ "ก้าว" เป็นหลักฐานสำคัญและใช้ "เวลา" เป็นเพียงภาพประกอบ
- **Go อาจเปลี่ยนเกณฑ์การเลือกเอนจินในอนาคต** — `maxBacktrackProg`, `maxBacktrackVector` และเงื่อนไขของ `onepass` เป็นรายละเอียดภายใน (ไม่ใช่ API ที่รับประกัน) · บทนี้ตรวจจาก Go 1.24.4 ที่ติดตั้งบนเครื่องนี้ · ข้อรับประกันจริงที่ควรยึดคือประโยคในเอกสารของแพ็กเกจ `regexp` (linear time in the size of the input) ไม่ใช่ตัวเลข 500
- **ไวยากรณ์ regex ต่างกันระหว่างภาษา** — บทนี้ยึดไวยากรณ์ของ RE2 (ที่ Go รับ) · ถ้าย้ายไป PCRE/Perl/Python จะได้ทั้ง backreference/lookaround (ใช้ได้) และ catastrophic backtracking (ตามมาด้วย) · ทดสอบทุกครั้งที่ย้ายภาษา โดยเฉพาะ pattern ที่มี nested quantifier
- **การวัดของ Russ Cox (2007)** — ตัวเลข "input 29 ตัวอักษรใช้เวลา ~60 วินาที" ในหัวข้อ 1.5 เป็นการวัดของเขาในปี 2007 บนเอนจินในยุคนั้น (Perl เป็นตัวอย่างหลัก) · เอนจินสมัยใหม่บางส่วนเปลี่ยนไปแล้ว · ใช้เป็น "หลักฐานเชิงประจักษ์ว่าปัญหานี้มีจริง" ไม่ใช่ตัวเลขปัจจุบัน
- **ประวัติศาสตร์ในหัวข้อ 1.5** — ข้อสรุปหลัก (Kleene 1951, Thompson 1968, grep 1973) ยืนยันจากแหล่งอ้างอิงด้านล่าง · รายละเอียดปี/ชื่อบทความควรตรวจซ้ำกับต้นฉบับเมื่อใช้ในงานวิชาการ

**แหล่งอ้างอิงหลักที่ใช้ในบทนี้:**

- เอกสารแพ็กเกจ `regexp` ของ Go (pkg.go.dev/regexp) — "guaranteed to run in time linear in the size of the input", ไวยากรณ์ = RE2 ยกเว้น `\C`, leftmost-first matching, `CompilePOSIX`/`Longest`
- README ของ **google/re2** (github.com/google/re2) — "Safety is RE2's primary goal", linear time, "RE2 is pessimistic where a backtracking engine is optimistic … This pessimism is what makes RE2 secure", ไม่รองรับ backreference/look-around, และประโยคที่ว่า **Go `regexp` และ Rust `regex` ไม่แชร์โค้ดกับ RE2 แต่ยึดหลักการ/ไวยากรณ์/ข้อรับประกันเดียวกัน**
- **Russ Cox**, *Regular Expression Matching Can Be Simple And Fast* (swtch.com/~rsc/regexp/regexp1.html, มกราคม 2007) — ประวัติ QED/Thompson, ตัวเลขการวัดที่อ้างในหัวข้อ 1.5, และเหตุผลที่ "เดินทุกทางพร้อมกัน" เร็วกว่า "เดาแล้วถอย"
- **source ของ Go 1.24.4 ที่ติดตั้งบนเครื่องนี้**: `$(go env GOROOT)/src/regexp/regexp.go` (เอกสารในไฟล์ + `compile()`), `exec.go` (`doExecute` เลือกเอนจิน), `backtrack.go` (`maxBacktrackProg = 500`, `maxBacktrackVector = 256*1024`, `visited`), `onepass.go` (`compileOnePass`: ต้องไม่มีจุดกำกวมที่ `InstAlt`), `syntax/compile.go` (ใส่ `InstFail` ก่อน และตั้ง `Start`), `syntax/prog.go` (รายชื่อ opcode: `InstAlt`, `InstRune1`, `InstMatch`, `InstFail`, …)
- เอกสารประวัติศาสตร์ regex: Kleene, *Representation of Events in Nerve Nets and Finite Automata* (RAND, 1951) · Thompson, *Regular Expression Search Algorithm* (CACM, มิถุนายน 1968) · บทความประวัติศาสตร์ regex ของ Wikipedia (สำหรับเส้นทาง QED → ed → grep)
- ไฟล์ในเครื่อง: `getconf PAGESIZE` (ย้อนตอนที่ 20), `go version`, `go env GOROOT`, และผลรันทั้งหมดใน `course/code/ep22/out/`

แนวคิดเรื่องเครื่องสถานะจำกัดอาจถูกท้าทายในอนาคต — โลกใหม่ ๆ กำลังใช้สิ่งที่อยู่เหนือชั้นนี้มากขึ้น (parser (ตัวแยกโครงสร้างโค้ด — จะเรียนตอนที่ 26–30) ที่ใช้เทคนิค packrat/GLR, การตรวจรูปแบบที่ใช้ engine แบบ "หลาย pattern พร้อมกัน" อย่าง Aho–Corasick หรือ Hyperscan (ไลบรารีตรวจรูปแบบความเร็วสูง), การตรวจด้วย ML, การย้ายงานตรวจไปที่ type system (ระบบตรวจชนิดของค่า — จะเรียนตอนที่ 29)) แต่จุดที่ไม่เปลี่ยนคือ**หลักการ**: ถ้าปัญหาของคุณ "จำได้แค่สถานะที่เป็นสัดส่วนกับ pattern ไม่ใช่กับ input" แปลว่าคุณกำลังแก้ปัญหาภาษาปกติ และคุณมีสิทธิ์ได้อัลกอริทึมที่ **ไม่มีทางระเบิด** — ความรู้นี้คือสิ่งที่แยกคนที่ "เขียน regex เป็น" ออกจากคนที่ "รู้ว่า regex ทำอะไรได้และทำอะไรไม่ได้"
