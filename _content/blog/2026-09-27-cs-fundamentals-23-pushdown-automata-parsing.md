# pushdown automata → context-free grammar — ทำไม parser ทำงานได้ (ตอนที่ 23)

ยินดีต้อนรับกลับมา ตอนนี้เราอยู่ในระยะที่ 5 ของคอร์ส ซึ่งเป็นระยะ "ทฤษฎีการคำนวณ" (theory of computation) — ระยะที่เราถอยออกมาจากการเขียนโปรแกรม แล้วมาถามคำถามที่ลึกกว่า: *คอมพิวเตอร์ "ทำอะไรได้" กับ "ทำอะไรไม่ได้" กันแน่*

ตอนที่ 22 เรารู้จัก **finite automaton** (เครื่องสถานะจำกัด) ไปแล้ว — มันคือภาพจำลองของ "โปรแกรมที่ไม่มีหน่วยความจำเลย" มีแค่สถานะจำนวนจำกัด กับลูกศรบอกว่าเมื่อเห็นตัวอักษรตัวหนึ่งจะกระโดดไปสถานะไหน แล้วเราได้บทสรุปหนึ่งว่า เครื่องชนิดนี้มัน**นับไม่ได้** มันจำ "เปิดวงเล็บค้างไว้กี่ตัว" ไม่ได้

คืนนี้เราจะ "ต่อยอด" เครื่องชนิดนั้นให้เก่งขึ้นอีกขั้น ด้วยการแปะหน่วยความจำหนึ่งก้อนเข้าไป แล้วผลลัพธ์ที่ได้จะตอบคำถามใหญ่คำถามหนึ่งของวงการเขียนโปรแกรมได้ว่า

> **ทำไม "parser" (โปรแกรมที่อ่านโค้ดของเรา) ถึงทำงานได้?**

(parser = ตัวแจงโครงสร้าง คือโปรแกรมที่อ่านข้อความที่มีโครงสร้าง เช่น โค้ดภาษาโปรแกรม แล้วเปลี่ยนให้กลายเป็นโครงสร้างข้อมูลที่คอมพิวเตอร์เอาไปใช้ต่อได้ — เดี๋ยวตอนท้ายเราจะเขียน parser จิ๋ว ๆ ด้วยตัวเองเลย)

คำตอบสั้น ๆ ก่อนเฉลยเต็ม ๆ ตอนจบ: เพราะภาษาของโปรแกรม (syntax หรือรูปแบบที่เขียนได้) เป็นสิ่งที่เรียกว่า **context-free language** และมีเครื่องจักรทางทฤษฎีชนิดหนึ่งชื่อ **pushdown automaton** ที่รับรู้ (recognize) ภาษาประเภทนี้ได้พอดี — แล้ว parser ที่เราใช้กันจริง ๆ ทุกวันก็คือ pushdown automaton ในร่างของโค้ดนั่นเอง

คืนนี้เราจะเขียนโค้ด Go ทั้งหมด 5 โปรแกรม (รันจริงบน Raspberry Pi 5) ตั้งแต่ PDA ที่จำวงเล็บสมดุล ไปจนถึง parser จิ๋วที่อ่านนิพจน์คณิตศาสตร์แล้วสร้าง AST (ต้นไม้โครงสร้างโค้ด — อธิบายละเอียดในหัวข้อ 7) เหมือนตัว parser ของ Go จริง ๆ

## 0. ทวนความจำ 30 วินาที: เครื่องสถานะจำกัดไม่มีที่ให้ "นับ"

**finite automaton** (เรียกย่อ ๆ ว่า FA; ถ้าเป็นแบบที่ตัดสินใจได้เสมอจะเรียก **DFA** — deterministic finite automaton) คือภาพจำลองของเครื่องคำนวณที่ประกอบด้วย:

- **สถานะ (state)** จำนวนจำกัด — เช่น `q0`, `q1`, `q2`
- **ตัวอักษร (alphabet)** — เซตของสัญลักษณ์ที่เครื่องอ่านได้ เช่น `{ '(', ')' }`
- **ตารางเปลี่ยนสถานะ (transition table)** — กฎว่า "ถ้าตอนนี้อยู่สถานะ X แล้วอ่านตัวอักษร Y ให้กระโดดไปสถานะ Z"
- **สถานะเริ่มต้น** กับ **สถานะรับ (accepting state)** — ถ้าอ่าน input จบแล้วจอดที่สถานะรับ แปลว่า "ยอมรับ" สตริง (ลำดับตัวอักษร) นี้

หัวใจของเครื่องชนิดนี้คือ **สถานะมีจำนวนจำกัด** — ซึ่งแปลว่า "ความจำ" ทั้งหมดที่มันมีก็คือ "ตอนนี้ฉันอยู่สถานะไหน" เท่านั้นเอง มันไม่มีที่ให้จดตัวเลขไปเรื่อย ๆ

ลองนึกภาพโจทย์ง่าย ๆ โจทย์หนึ่ง:

> รับสตริงที่ประกอบด้วยวงเล็บ `(` และ `)` แล้วตอบว่า "วงเล็บสมดุลไหม" (เปิดหนึ่งอันต้องมีปิดหนึ่งอัน ตรงกันเป็นคู่ ๆ)

- `()` → สมดุล ✓
- `(())` → สมดุล ✓
- `())` → **ไม่สมดุล** ✗ (มีวงเล็บปิดเกินมา)
- `(()` → **ไม่สมดุล** ✗ (วงเล็บเปิดค้างไว้ ไม่มีตัวปิด)

ทำไมเครื่องสถานะจำกัดทำโจทย์นี้ไม่ได้? เพราะตอนที่มันอ่าน `(` ไปเรื่อย ๆ มันต้อง**จำจำนวน**วงเล็บเปิดที่ค้างไว้ — แล้วจำนวนนั้นไม่มีเพดาน เราอยากเขียน `(((((…` กี่ตัวก็ได้ สถานะจำนวนจำกัดยังไงก็จำไม่หมด พอเจอ `)` มันตอบไม่ได้ว่ามี `(` ค้างอยู่เท่าไรให้จับคู่

ตอนที่ 22 เราพิสูจน์เรื่องนี้มาแล้วในภาษารุ่นพี่ของมัน (regular language — ภาษาที่ FA รับได้) คืนนี้เราไม่ต้องเชื่อบนกระดาษอย่างเดียว เราจะ**รันโปรแกรมให้เห็นกับตา**ว่าทำไมมันทำไม่ได้ แล้วค่อยแก้ด้วยเครื่องใหม่

## 1. Pushdown automaton — เอา "stack" มาช่วยจำ

วิธีแก้มันตรงไปตรงมา: เครื่องเดิมขาดแค่ **ที่พัก** — ที่สำหรับจดว่า "วงเล็บเปิดค้างไว้กี่ตัว" — ตอนที่เจอ `(` มันอยาก "จด" ไว้ว่าเปิดค้างอีก 1 แล้วให้เอาจำนวนนี้มา "ใช้" ตอนเจอ `)`

โครงสร้างข้อมูลที่เหมาะกับงานแบบ "เข้ามาก่อน ออกทีหลัง" (เหมือนกองจานที่วางซ้อนกัน: จานที่วางทีหลังสุด จะถูกหยิบก่อนเสมอ) มีชื่อว่า **stack** (อ่านว่า สแต็ก แปลตรง ๆ ว่า "กอง") — การทำงานสองอย่างของมันคือ:

- **push** — วางของลงบนยอดกอง (เพิ่มข้อมูลเข้าไป)
- **pop** — หยิบของจากยอดกองออก (เอาข้อมูลตัวบนสุดออก)

เครื่องสถานะจำกัดที่ถูกแปะ stack เข้าไปหนึ่งกอง เราเรียกมันว่า **pushdown automaton** (PDA — "เครื่องที่ผลักลงกองได้") ชื่อมาจากการกระทำ push ที่มันทำได้นี่แหละ

สิ่งที่เปลี่ยนไปจาก FA มีแค่ 3 อย่าง:

1. มันมี **stack** หนึ่งกอง (เริ่มต้นว่าง หรือมีสัญลักษณ์พิเศษคั่นก้นกอง)
2. กฎเปลี่ยนสถานะ (transition) ตอนนี้ดู **3 อย่างพร้อมกัน**: สถานะปัจจุบัน + ตัวอักษรที่อ่าน + **สัญลักษณ์บนยอด stack** แล้วค่อยตัดสินใจว่ากระโดดไปสถานะไหน และจะ push/pop อะไร
3. สถานะยังคง**มีจำกัด**เท่าเดิม — ความจำ "ไม่จำกัด" ไปอยู่ใน stack แทน

ประเด็นที่หลายคนเข้าใจผิด: PDA **ไม่ได้มีสถานะเยอะขึ้น** มันมีแค่ 2–3 สถานะเหมือนเดิม แต่ stack ของมัน**โตได้เท่าความยาวของ input** ซึ่งนี่คือที่มาของ "ความจำไม่จำกัด" ที่ FA ไม่มี

![Pushdown automaton (PDA) = เครื่องสถานะจำกัด + stack หนึ่งกอง](/assets/diagrams/ep23-01-pda-machine.svg)

ดูภาพประกอบ: ตรงกลางคือ **finite control** (สมองเครื่อง ที่มีสถานะจำกัด) ซ้ายคือเทป input ที่มันอ่านทีละตัว (อ่านซ้ายไปขวา เห็นทีละตัว มองไม่เห็นอนาคต) ขวาคือ stack ก้อนใหม่ — ตัวเลขทุกตัวในภาพมาจากผลรันจริงของโปรแกรมที่เรากำลังจะเขียน

## 2. โปรแกรม 01 — PDA ที่จำ "วงเล็บสมดุล"

มาเขียนเครื่องจริงกัน โค้ดชิ้นนี้อยู่ที่ `01_pda_balanced` แนวคิดง่ายมาก:

- เจอ `(` → **push** สัญลักษณ์ `(` ลง stack (จดว่าเปิดค้าง +1)
- เจอ `)` → **pop** ออกจาก stack (จับคู่กับ `(` ที่ค้างอยู่)
- อ่าน input หมด + stack ว่างพอดี → **ยอมรับ**
- เจอ `)` แต่ stack ไม่มี `(` ให้ pop (มีแต่ก้นกอง `Z0`) → **ปฏิเสธ** (วงเล็บปิดเกิน)

หัวใจของเครื่องคือ "ตารางเปลี่ยนสถานะ" (transition table) ทั้งเครื่องมีแค่ **4 ข้อ** (ในโค้ด `Z0` คือ "สัญลักษณ์ก้นกอง" ที่วางไว้ก้นสุดของ stack — อธิบายเต็ม ๆ ใต้โค้ด):

```go
// delta = ตาราง transition ทั้งหมดของเครื่องนี้ มี 4 ข้อ
// (bottom = สัญลักษณ์ก้นกอง "Z0" · read: 0 = ค่า rune ว่าง ใช้แทน ε "ไม่กิน input")
var delta = []transition{
    {state: "q0", read: '(', top: bottom, next: "q0", act: actPush, push: "("},
    {state: "q0", read: '(', top: "(",    next: "q0", act: actPush, push: "("},
    {state: "q0", read: ')', top: "(",    next: "q0", act: actPop},
    {state: "q0", read: 0,   top: bottom, next: "qAccept", act: actAccept},
}
```

อ่านทีละบรรทัด (นี่คือวิธีอ่านตาราง transition ของ PDA ทั่วไป — ชินแล้วจะอ่านเครื่องใด ๆ ในหนังสือทฤษฎีได้หมด):

- บรรทัด 1–2: อยู่สถานะ `q0` อ่าน `(` → push `(` ลง stack (ไม่ว่ายอด stack จะเป็นก้นกอง `Z0` หรือ `(` ก็ push ได้ทั้งนั้น)
- บรรทัด 3: อยู่ `q0` อ่าน `)` และยอด stack เป็น `(` → pop ทิ้ง (จับคู่ได้)
- บรรทัด 4: อยู่ `q0` **ไม่อ่าน input อีก** (สัญลักษณ์ `ε` = "ไม่กินอะไรเลย") และ stack เหลือแต่ก้นกอง `Z0` → กระโดดไป `qAccept` = ยอมรับ

`Z0` (อ่านว่า "ซี-ศูนย์") คือสัญลักษณ์พิเศษที่เราวางไว้**ก้นสุดของ stack** ตั้งแต่แรก เพื่อให้เครื่องรู้ว่า "ตอนนี้ stack ว่างจริง ๆ แล้ว" (ไม่งั้นมันจะแยกไม่ออกว่า "stack ว่าง" กับ "ยังมี `(` ค้างอยู่" ต่างกันยังไง)

ตอนนี้ลองรันโปรแกรม ดูเครื่องเดินทีละก้าวกับ input `(())` (วงเล็บสมดุล 2 คู่):

```
--- เดินทีละก้าว: "(())" ---
  ก้าวที่ สัญลักษณ์  top      → สถานะ  ทำอะไร   stack (ล่าง→บน)
  0     (          Z0       q0       push     Z0 (
  1     (          (        q0       push     Z0 ( (
  2     )          (        q0       pop      Z0 (
  3     )          (        q0       pop      Z0
  4     ε(จบ input) Z0       qAccept  accept   Z0
  สรุป: ยอมรับ · ความลึก stack สูงสุด = 2
```

สังเกตคอลัมน์ "stack (ล่าง→บน)" — มันคือ**จำนวนวงเล็บเปิดที่ค้างอยู่**แบบเรียลไทม์: เจอ `(` สองตัว stack ก็มีสองชั้น พอเจอ `)` ก็ pop ทีละชั้น จนสุดท้ายเหลือแต่ `Z0` = ว่าง = สมดุล เป๊ะ

แล้วถ้าเป็น `())` (วงเล็บปิดเกิน) ล่ะ:

```
--- เดินทีละก้าว: "())" ---
  ก้าวที่ สัญลักษณ์  top      → สถานะ  ทำอะไร     stack (ล่าง→บน)
  0     (          Z0       q0       push       Z0 (
  1     )          (        q0       pop        Z0
  สรุป: ปฏิเสธ · ความลึก stack สูงสุด = 1
```

เจอ `)` ตัวที่สอง แต่ยอด stack เป็น `Z0` (ไม่มี `(` ให้ pop) → **ไม่มีกฎให้ทำต่อ** → ปฏิเสธทันที งดงาม

โปรแกรมยังทดสอบอีก 12 เส้น (ตั้งแต่สตริงว่าง `""` ไปจนถึงวงเล็บซ้อน 11 ชั้น) เทียบกับคำตอบที่เราคำนวณด้วยมือไว้ — ผลตรงกันหมด `MISMATCH 0 จาก 12 เส้น` และยังยืนยันอีกสองข้อที่นักทฤษฎีสนใจ:

- **determinism** (ความแน่นอน): รัน input เดิมซ้ำแล้วได้ผลเหมือนเดิมทุกก้าว (เครื่องนี้เป็นแบบ *กำหนด* — ตัดสินใจได้เสมอ ไม่ต้องเดา)
- **ความลึก stack = จำนวนวงเล็บเปิดค้างสูงสุด**: ตรงกันทุกเส้นที่ยอมรับ

> **ศัพท์ย่อที่ต้องรู้:** ในหนังสือทฤษฎี PDA มักมีสองแบบคือ **deterministic PDA (DPDA)** ที่ทุกสถานการณ์มีทางเลือกเดียว กับ **nondeterministic PDA (NPDA)** ที่เลือกได้หลายทาง ตรงนี้ละเอียดเกินตอนนี้ — ขอแค่จำว่า "เครื่องที่เราเขียนคือแบบกำหนด" ก็พอ และสิ่งที่ PDA ทำได้มีพลังเท่ากันกับ **context-free grammar** ที่เรากำลังจะเรียนต่อ

## 3. Context-free grammar — เขียน "ภาษา" เป็นกฎสั้น ๆ

การเขียน PDA ด้วยตาราง transition นั้นตรงไปตรงมา แต่พอภาษาซับซ้อนขึ้น (เช่น ภาษาโปรแกรมทั้งภาษา) การเขียนทีละ transition จะปวดหัวมาก นักคณิตศาสตร์เลยคิดเครื่องมือบรรยายภาษาที่อ่านง่ายกว่า: **grammar** (ไวยากรณ์)

**context-free grammar** (เรียกย่อ CFG — ไวยากรณ์นอกบริบท) คือชุดของ **กฎผลิต (production rule)** แต่ละกฎมีหน้าตาแบบนี้:

```
หัว → ตัว
```

อ่านว่า "สัญลักษณ์ทางซ้าย ขยายเป็นสัญลักษณ์ทางขวาได้" ภาษาวงเล็บสมดุลทั้งภาษา บรรยายด้วยกฎแค่ 2 ข้อ:

```
S → ( S ) S      // วงเล็บเปิด แล้ว S แล้ววงเล็บปิด แล้ว S อีกตัว
S → ε            // หรือ "ไม่มีอะไรเลย" (ε = สตริงว่าง)
```

ลองอ่านกฎนี้เป็นภาษาไทย: "S ตัวหนึ่ง จะเป็น `( S ) S` ก็ได้ หรือเป็น `ε` (ว่าง) ก็ได้" — เพราะ `S` ปรากฏทั้งทางซ้ายและขวาของกฎ มันเลย**เรียกตัวเองซ้ำ** (recursive) ได้ไม่รู้จบ ซึ่งนี่แหละคือที่มาของ "วงเล็บซ้อนกี่ชั้นก็ได้"

### 3.1 สองศัพท์ที่ขาดไม่ได้: terminal กับ nonterminal

- **nonterminal** (สัญลักษณ์ไม่สิ้นสุด) = สัญลักษณ์ที่ยัง "ขยายต่อได้" — ในกฎข้างบนคือ `S` (มันคือหัวของกฎ ยังถูกแทนที่ต่อได้) เราเขียนด้วยตัวพิมพ์ใหญ่เป็นธรรมเนียม
- **terminal** (สัญลักษณ์สิ้นสุด) = สัญลักษณ์ที่ "ถึงจุดจบแล้ว ขยายต่อไม่ได้" — คือตัวอักษรจริงในภาษา เช่น `(`, `)`, `a`, `b`, ตัวเลข

จุดหมายของ grammar คือ: เริ่มจาก nonterminal ตัวเริ่มต้น (start symbol มักชื่อ `S`) แล้วค่อย ๆ เอากฎมาแทน nonterminal ทีละตัว จนเหลือแต่ terminal ล้วน — สตริงของ terminal ที่ได้ออกมาก็คือ "สตริงที่อยู่ในภาษานี้"

กระบวนการแทนที่ทีละตัวนี้เรียกว่า **derivation** (การพิสูจน์การสร้างสตริง) ลองสร้าง `(())` ดู:

```
S
→ ( S ) S        (ใช้กฎ S → (S)S)
→ ( ( S ) S ) S  (ใช้กฎ S → (S)S กับ S ตัวในสุด)
→ ( ( ε ) S ) S  (ใช้กฎ S → ε)
→ ( ( ) S ) S    (ε หายไป = ไม่มีอะไร)
→ ( ( ) ε ) S    (S ตัวใน → ε)
→ ( ( ) )        (S ตัวนอกสุด → ε)
```

จบได้สตริง `(())` — อยู่ในภาษาวงเล็บสมดุลจริง ✓

### 3.2 parse tree — เอากระบวนการสร้างมาวาดเป็นต้นไม้

ถ้าเราเอาขั้นตอน derivation มาวาดเป็นรูปต้นไม้ (รากคือ `S` ตัวแรก กิ่งคือการขยายแต่ละครั้ง ใบคือ terminal) เราจะได้ **parse tree** (ต้นไม้แจงโครงสร้าง) — นี่คือโครงสร้างที่สำคัญมาก เพราะ**ตอนที่ 27 เราจะเห็นมันในร่างของ AST ของโค้ดจริง**

![Parse tree ของ a³b³ จากไวยากรณ์ S → aSb | ε](/assets/diagrams/ep23-03-parse-tree-anbn.svg)

ในภาพเป็น parse tree ของภาษา `aⁿbⁿ` (อ่านว่า "เอ-ยกกำลัง-เอ็น บี-ยกกำลัง-เอ็น" = ตัว `a` ซ้ำ n ตัว แล้ว `b` ซ้ำ n ตัว เช่น `aaabbb`) ที่มีไวยากรณ์:

```
S → a S b      // a แล้ว S แล้ว b
S → ε
```

ภาษา `aⁿbⁿ` คือภาษาคู่แฝดของวงเล็บสมดุล (แค่เปลี่ยน `(` เป็น `a`, `)` เป็น `b`) และเป็นตัวอย่างมาตรฐานที่หนังสือทฤษฎีใช้บอกว่า "นี่คือสิ่งที่ FA ทำไม่ได้ แต่ PDA ทำได้" — ต้นไม้นี้พิมพ์จากโปรแกรม 02 จริง จำนวนโหนด 10 โหนด

> **อ่าน parse tree ยังไง:** ดูจากยอดลงล่าง ทุกครั้งที่เห็น `S` ชั้นใหม่ แปลว่า "ยังมี `a` กับ `b` คู่หนึ่งที่รอจับกันอยู่" การใช้กฎ `S → aSb` แต่ละครั้ง = เพิ่ม `a` หนึ่งตัวกับ `b` หนึ่งตัว (3 ครั้ง = 3 คู่) — นี่คือเหตุผลที่ต้องมี stack: ตอนอ่าน `a` แต่ละตัว เรายังไม่รู้ว่าต้องเจอ `b` กี่ตัว จึงต้อง "พัก" จำนวน `a` ที่อ่านมาไว้ก่อน แล้ว stack ก็พักได้ไม่จำกัด

## 4. โปรแกรม 02 — aⁿbⁿ + พิสูจน์ให้เห็นว่า FA ทำไม่ได้จริง ๆ

ก่อนไปต่อ มาเก็บโปรแกรม 02 ให้ครบก่อน — โปรแกรมเดียวกันนี้แหละที่พิมพ์ parse tree ที่เราเพิ่งเห็นในภาพด้านบน และยังพิสูจน์ให้เห็นกับตาว่า FA ทำ `aⁿbⁿ` ไม่ได้จริง ๆ โปรแกรมที่สอง (`02_pda_anbn`) มีสองครึ่ง:

**ครึ่งแรก** เขียน PDA ของ `aⁿbⁿ` ตรง ๆ: เจอ `a` → push สัญลักษณ์ `A`; เจอ `b` ครั้งแรก → สลับไปสถานะ `q1` แล้ว pop `A` ทุกตัวที่เจอ `b`; ถ้า stack ว่างพอดีตอน input หมด → ยอมรับ ตาราง transition มี 6 ข้อ:

```
  สถานะ  อ่าน     top      → สถานะ    การกระทำ
  q0     a        Z0       q0         push A
  q0     a        A        q0         push A
  q0     b        A        q1         pop
  q1     b        A        q1         pop
  q0     ε        Z0       qAccept    accept
  q1     ε        Z0       qAccept    accept
```

ลองดูเครื่องเดินกับ `aaabbb` (ก้าวที่ 4–6 คือช่วง pop):

```
  ก้าว  1: a  → push A   stack = Z0 A
  ก้าว  2: a  → push A   stack = Z0 A A
  ก้าว  3: a  → push A   stack = Z0 A A A
  ก้าว  4: b  → pop      stack = Z0 A A
  ก้าว  5: b  → pop      stack = Z0 A
  ก้าว  6: b  → pop      stack = Z0
  ก้าว  7: ε (input หมด) → accept
  ผล: ยอมรับ · ความลึก stack สูงสุด = 3 (= จำนวน a ในสตริง)
```

ทดสอบ 10 เส้น รวม `a×20 b×20` (ซ้ำ 20 ตัว) — ผลตรงกับคำตอบที่เตรียมไว้ทั้ง 10 เส้น (ยอมรับ 5 · ปฏิเสธ 5) `MISMATCH 0`

**ครึ่งหลัง** คือส่วนที่เจ๋งที่สุดของคืนนี้: แทนที่จะเชื่อตำราว่า "FA ทำไม่ได้" เรา**ลองสร้าง FA ที่พยายามนับจริง ๆ** ด้วยจำนวนสถานะ k สถานะ แล้วให้โปรแกรมรันหาจุดที่มันพังให้เห็น

ลองสองกลยุทธ์ที่ FA มีสิทธิ์ใช้ (เพราะมันมีได้แค่สถานะจำกัด):

- **กลยุทธ์ "นับเศษ" (mod k)**: สถานะ = เศษของการหาร `(#a − #b) ด้วย k` (โดย `#a` = จำนวน `a` ที่อ่านมาแล้ว, `#b` = จำนวน `b`, `k` = จำนวนสถานะ, และ `mod k` = เศษจากการหารด้วย k) — ยอมรับเมื่อเศษเป็น 0 มันรับ `aⁿbⁿ` ได้ถูกหมด แต่**รับผิด**ด้วย: เพราะนับได้แค่เศษ มันแยกไม่ออกว่า `abbb` (a 1 ตัว b 3 ตัว) กับ `aaabbb` ต่างกัน ผลรันจริง:

```
  k    input   ผลจริง    ที่ควรเป็น  ตรงไหม
  2    a¹b³    ยอมรับ    ปฏิเสธ      ผิด (false accept)
  4    a¹b⁵    ยอมรับ    ปฏิเสธ      ผิด
  8    a¹b⁹    ยอมรับ    ปฏิเสธ      ผิด
  16   a¹b¹⁷   ยอมรับ    ปฏิเสธ      ผิด
  → false accept (ยอมรับผิด) = 4 เคส
```

- **กลยุทธ์ "ตัวนับอิ่มตัว" (saturating)**: นับ `a` ไปได้ถึง `k−1` แล้ว "อิ่ม" (จำเพิ่มไม่ได้) — คราวนี้พอ `n` ใหญ่เกิน k มัน**ปฏิเสธ**สตริงที่ควรยอมรับแทน:

```
  k    input      ผลจริง     ที่ควรเป็น  ถูกไหม
  2    aabb       ปฏิเสธ     ยอมรับ     false   ← false reject
  4    aaaabbbb   ปฏิเสธ     ยอมรับ     false
  8    a⁸b⁸       ปฏิเสธ     ยอมรับ     false
  16   a¹⁶b¹⁶     ปฏิเสธ     ยอมรับ     false
  → false reject = 4 เคส (ผิดพลาดที่ n = k ทุกกรณี)
```

**ข้อสรุปที่โปรแกรมพิสูจน์ให้เห็น:** เพิ่ม k ให้ใหญ่เท่าไร ก็แค่**เลื่อนจุดพังออกไปข้างหน้า** (k=2 พังที่ n=2, k=16 พังที่ n=16) ไม่มีทางหมดไป — เพราะ FA ต้องแยก `a¹, a², a³, …` ซึ่งมีไม่จำกัด ออกจากกันด้วยสถานะจำกัด เป็นไปไม่ได้ในเชิงโครงสร้าง แต่ PDA ไม่มีเพดานนี้ เพราะ stack ยาวเท่า input ได้

นี่คือตัวอย่างของแนวคิดที่เรียกว่า **pumping lemma** (บทตั้งเรื่องการสูบซ้ำ — ทฤษฎีที่บอกว่าภาษา regular ทุกภาษาต้องมีคุณสมบัติซ้ำตัวหนึ่ง ซึ่ง `aⁿbⁿ` ละเมิด) แต่คืนนี้เราพิสูจน์ด้วยการรันโปรแกรมให้เห็นตรง ๆ แทน ซึ่งตรงกับทฤษฎีพอดี

![แผนภาพ transition ของ PDA สองเครื่อง + ลำดับชั้นของภาษา](/assets/diagrams/ep23-02-pda-transitions.svg)

## 5. ทฤษฎีบทที่ทำให้ parser ทำงานได้: CFG = PDA

ตอนนี้เรามีของสองชิ้นที่ดูไม่เกี่ยวข้องกัน: **PDA** (เครื่องจักร + stack) กับ **CFG** (กฎเขียนภาษา) คำถามคือทั้งสองบรรยายภาษา**ชุดเดียวกัน**ไหม?

คำตอบคือใช่ และนี่คือหนึ่งในทฤษฎีบทที่สำคัญที่สุดของวิชาทฤษฎีการคำนวณ:

> **ภาษาที่ CFG บรรยายได้ = ภาษาที่ PDA ยอมรับได้** พอดี (เซตเดียวกัน เราเรียกว่า **context-free language**)

ทิศหนึ่ง (CFG → PDA) สร้างง่าย: ตัว parser ที่ใช้ call stack (พื้นที่ที่ระบบจดว่าตอนนี้กำลังเรียกฟังก์ชันอะไรอยู่ แล้วค่อยย้อนกลับ — อธิบายเต็ม ๆ ในหัวข้อ 6) ที่เรากำลังจะเขียนก็คือตัวพิสูจน์ ส่วนทิศกลับ (PDA → CFG) ก็จริงเช่นกันแต่สร้างลำบากกว่า เอาไว้เรียนลึกในวิชาทฤษฎีเฉพาะทาง

ถ้าเอาไปวางใน**ลำดับชั้นของ Chomsky** (แผนผังแบ่งชั้นภาษา ตั้งชื่อตาม Noam Chomsky นักภาษาศาสตร์ที่เสนอไว้ช่วงกลางศตวรรษที่ 20) จะได้ภาพแบบนี้ (ส่วนล่างของ diagram ที่แสดงไว้ในหัวข้อ 4 — สัญลักษณ์ `⊊` แปลว่า "เป็นเซตย่อยแท้" คือข้างซ้ายเล็กกว่าข้างขวาจริง ๆ):

```
ภาษาปกติ (regular) ⊊ ภาษา context-free ⊊ ภาษาที่ Turing machine รับ
```

- **regular language** (ภาษาปกติ — ที่ FA/regex รับได้) เป็น subset แท้ของ context-free — เพราะ FA ก็คือ PDA ที่ไม่เคยแตะ stack เลย (อ่านแล้ว push/pop ไม่เป็น)
- **context-free language** เป็น subset แท้ของภาษาที่เครื่อง Turing machine (ตอนที่ 24) รับ — ยังมีภาษาที่ทั้ง PDA และ CFG ทำไม่ได้อีกชั้นหนึ่ง

แล้วทั้งหมดนี้เกี่ยวกับ parser ยังไง? ขั้นแรก **ไวยากรณ์ของภาษาโปรแกรม (syntax) เขียนเป็น CFG ได้** — เช่น ไวยากรณ์ของนิพจน์ `Expr → Term ( "+" Term )*` (เครื่องหมาย `*` แปลว่า "ซ้ำ 0 ครั้งขึ้นไป") ที่เราจะเขียนต่อจากนี้

เมื่อไวยากรณ์เป็น CFG ก็แปลว่า "มี PDA รับภาษานี้ได้" และ "PDA" ตัวนั้นแหละที่เรียกว่า **parser** — โปรแกรมที่เราเรียกใช้ทุกครั้งที่กด compile (compile = แปลงโค้ดที่เราเขียนให้เป็นโปรแกรมที่เครื่องรันได้) ก็คือ PDA ในร่างซอฟต์แวร์

## 6. Recursive descent — call stack ก็คือ stack ของ PDA

ทีนี้มาถึงจุดที่ทฤษฎีมาบรรจบกับของจริง ตอนเราเขียนโปรแกรมจริง เราไม่ค่อยเขียน PDA ด้วย "ตาราง transition + ก้อน slice (แถวข้อมูลติดกันของ Go)" ตรง ๆ หรอก เราเขียน **recursive descent parser** (parser แบบไล่ลงมาเรื่อย ๆ ด้วยการเรียกฟังก์ชันซ้ำ) แทน เพราะมันตรงกับไวยากรณ์ตัวต่อตัว: nonterminal หนึ่งตัว = ฟังก์ชันหนึ่งฟังก์ชัน

แล้วคำถามที่เจ๋งจริง ๆ คือ: **stack ที่ recursive descent ใช้ (call stack ของภาษา) คือ stack ของ PDA จริงไหม?** โปรแกรม 03 (`03_recursive_descent`) เขียนมาเพื่อพิสูจน์เรื่องนี้โดยเฉพาะ โดยเขียน "ตัวรู้จำ" ไวยากรณ์ `S → ( S ) S | ε` ถึง **สามแบบ** แล้วเทียบกัน:

1. **parserA** — recursive descent: เรียกฟังก์ชัน `parseS()` ซ้ำ ใช้ call stack ของ Go
2. **parserB** — explicit-stack: ใช้ `[]sym` เป็น stack ของ PDA ตรง ๆ (predictive parser — parser ที่ตัดสินใจล่วงหน้าได้จากสัญลักษณ์ถัดไป)
3. **parserC** — recursive descent แต่เขียนไวยากรณ์ใหม่เป็น `S → ( S )*` (ใช้ loop แทนการเรียกซ้ำตัวสุดท้าย)

โค้ดหัวใจของ parserA (recursive descent):

```go
func (p *parserA) parseS() (*node, error) {
    p.depth++                        // ตัวนับความลึก: เข้าไปลึกขึ้น 1 ชั้น
    if p.depth > maxParseDepth {     // ประตูกั้น: กันเรียกซ้ำลึกเกินจนล้น (อธิบายในหัวข้อ 8)
        p.depth--
        return nil, errTooDeep
    }
    defer func() { p.depth-- }()     // defer = "ทำงานนี้ตอนออกจากฟังก์ชัน" → ออก = ลึกน้อยลง 1

    me := &node{label: "S"}          // สร้างโหนด "S" (โหนด = จุดหนึ่งใน parse tree)

    // LL(1) = อ่านล่วงหน้า 1 ตัว แล้วเลือกกฎ (ไม่ต้องเดา ไม่ต้องถอย)
    if p.pos < len(p.src) && p.src[p.pos] == '(' {
        p.rules = append(p.rules, "S → (S)S")
        // ... (ย่อ: กิน '(' แล้วเรียก parseS() ซ้ำ และเช็คว่ามี ')' ตามมา)
        inner, err := p.parseS()     // ← การเรียกซ้ำ = push ลง call stack
        if err != nil { return nil, err }
        me.kids = append(me.kids, inner)
        // ... (ย่อ: เช็ค ')' แล้วเรียก parseS() สำหรับ S ตัวท้าย)
        tail, err := p.parseS()      // ← S ตัวท้าย (เรียกซ้ำอีกชั้น)
        if err != nil { return nil, err }
        me.kids = append(me.kids, tail)
        return me, nil
    }
    p.rules = append(p.rules, "S → ε")
    return me, nil
}
```

จุดสำคัญอยู่ตรงบรรทัด `p.parseS()` ที่เรียกตัวเอง — **การเรียกฟังก์ชันซ้ำหนึ่งชั้น = push หนึ่งครั้งลง call stack** แล้ว `return` = pop กลับ นี่คือเหตุผลที่หนังสือหลายเล่มบอกว่า "recursive descent parser ใช้ call stack เป็น stack ของ PDA โดยธรรมชาติ" (ศัพท์สองตัวที่เพิ่งเห็น: `defer` = คำสั่ง "ทำงานนี้ตอนออกจากฟังก์ชัน", `p.depth` = ตัวนับความลึกปัจจุบัน — ส่วน "stack overflow" ที่คอมเมนต์พูดถึงคือการเรียกซ้ำลึกเกินจนพื้นที่จำของโปรแกรมล้นจนโปรแกรมตาย อธิบายเต็ม ๆ ในหัวข้อ 8)

ผลรันจริงยืนยันว่า A กับ B (เครื่องที่เขียนต่างกันสุดขั้วสองแบบ) ให้ผลตรงกันทุกเส้น และ**ใช้กฎลำดับเดียวกัน** (คอลัมน์ "frame" = เฟรมหน่วยความจำของฟังก์ชันที่กำลังทำงาน เรียกซ้ำหนึ่งชั้น = หนึ่ง frame):

```
  input     A ยอมรับ   B ยอมรับ   กฎตรงกัน   A frame ลึกสุด  B stack สูงสุด
  ""        true       true       true        1              1
  ()        true       true       true        2              2
  (())      true       true       true        3              3
  ((()))    true       true       true        4              4
  ...
  A กับ B ให้ผลตรงกัน + ใช้กฎลำดับเดียวกันทุกเส้น: true
```

แถมยังตรวจแบบ**แจกแจงครบ** (exhaustive): สร้างสตริงทุกเส้นที่ประกอบด้วย `(`/`)` ความยาว 0 ถึง 10 ได้ **2,047 เส้น** แล้วเอา parser ทั้ง 3 ตัว (parserA, parserB, parserC) มาเทียบกับ "oracle" (ตัวตรวจที่เขียนแบบไม่ใช้ไวยากรณ์เลย แค่นับวงเล็บเปิดค้าง) — ไม่ตรงกัน **0 จุด**

นี่คือวิธีที่วิศวกรพิสูจน์ความถูกต้องของ parser จริง ๆ — ไม่ใช่แค่ "ลอง ๆ แล้วมันได้" แต่ทดสอบทุกอินพุตที่ยาวถึง 10 ตัวอักษรจนครบ

### 6.1 กับดักที่ต้องรู้: รูปไวยากรณ์กำหนดความลึกของ stack

โปรแกรม 03 ยังเผยกับดักที่สำคัญมากสำหรับคนจะเขียน parser จริง: **ความลึกของ call stack ไม่ได้ขึ้นกับ "ความซ้อนของ input" อย่างเดียว แต่มันขึ้นกับ "รูปของไวยากรณ์" ด้วย**

ดูผลรันนี้ — เราใส่ input `()()` ซ้ำกัน (ความซ้อนจริงแค่ 1 ตลอด) แล้ววัดความลึก frame ของ parserA (ไวยากรณ์ `S → (S)S`) เทียบ parserC (ไวยากรณ์ `S → (S)*`):

```
  input       A: S → (S)S | ε   C: S → (S)*   ความซ้อนจริง
  "()"×1      2                 2             1
  "()"×10     11                2             1
  "()"×100    101               2             1
  "()"×1000   1001              2             1
  "()"×4000   4001              2             1
```

อ่านออกว่า: สตริงยาวขึ้นเรื่อย ๆ แต่ความซ้อนจริงยังเป็น 1 — parserA กลับ**ลึกลงเรื่อย ๆ ตามจำนวนกลุ่ม** (เพราะ `S → (S)S` มี "S ตัวท้าย" ที่เรียกซ้ำทบทุกกลุ่ม) ส่วน parserC อยู่ที่ 2 ตลอด (เพราะใช้ loop กินกลุ่มซ้ำ ๆ แทนการเรียกซ้ำ)

**นี่คือเหตุผลที่ compiler (โปรแกรมที่แปลงโค้ดทั้งไฟล์ให้เป็นโปรแกรมรันได้) จริงเขียน "รายการ" (list) ด้วย loop ไม่ใช่การเรียกซ้ำ** — ไม่งั้นโค้ด `f(); f(); f(); ...` ซ้ำหมื่นบรรทัด (ภาษา C เขียนคำสั่งเรียงกันแบบนี้ซ้ำ ๆ ได้) จะทำเอา parser ของ Go ตายด้วย stack overflow ไปแล้ว ซึ่งนำไปสู่หัวข้อสุดท้ายพอดี

## 7. โปรแกรม 04 — parser จิ๋วที่อ่านนิพจน์คณิตศาสตร์ แล้วสร้าง AST

พอรู้แล้วว่า parser = PDA แล้ว มาทำของที่จับต้องได้: **parser จิ๋วที่อ่านนิพจน์คณิตศาสตร์** (เช่น `1 + 2 + (3 + 40)`) แล้วเปลี่ยนเป็น **AST (Abstract Syntax Tree = ต้นไม้โครงสร้างนามธรรม)** — ซึ่งก็คือ parse tree เวอร์ชันที่ตัดรายละเอียดไม่จำเป็นทิ้ง เหลือแต่โครงสร้างที่สำคัญ

ไวยากรณ์ (เขียนเป็น CFG) มี 2 กฎ:

```
Expr → Term ( "+" Term )*     // บวกกันกี่ตัวก็ได้
Term → number | "(" Expr ")"  // เลขตัวเดียว หรือวงเล็บห่อ
```

หมายเหตุเครื่องหมาย `*` ในกฎ แปลว่า "ซ้ำ 0 ครั้งขึ้นไป" (ศัพท์ที่เรียกในทฤษฎีว่า **Kleene star** มาจากตอนที่ 22) และ `|` แปลว่า "หรือ"

โปรแกรมนี้มีสองส่วนประกอบที่ parser จริงทุกตัวต้องมี:

1. **lexer** (ตัวตัดคำ — บางทีเรียก tokenizer): แปลงข้อความดิบ `"12 + (3 + 40)"` ให้เป็นก้อนเล็ก ๆ ที่เรียกว่า **token** (หน่วยคำ) เช่น ตัวเลข `12`, เครื่องหมาย `+`, วงเล็บ `(`
2. **parser** (ตัวแจงโครงสร้าง): อ่าน token แล้วสร้างต้นไม้ตามไวยากรณ์

เพราะไวยากรณ์มี nonterminal 2 ตัว (`Expr` กับ `Term`) เราก็เขียนฟังก์ชัน 2 ตัวตามชื่อตรง ๆ:

```go
// parseExpr = กฎ Expr → Term ( "+" Term )*
func (p *parser) parseExpr() (*node, error) {
    first, err := p.parseTerm()
    if err != nil { return nil, err }
    me := &node{op: "+", kids: []*node{first}}
    for p.peek().kind == kindPlus {   // ← loop กิน "+" ไปเรื่อย ๆ
        p.expectPlus()
        t, err := p.parseTerm()
        if err != nil { return nil, err }
        me.kids = append(me.kids, t)
    }
    return me, nil
}

// parseTerm = กฎ Term → number | "(" Expr ")"
func (p *parser) parseTerm() (*node, error) {
    // peek() = ดู token ถัดไปโดยไม่กิน (ต่างจาก next() ที่กินแล้วเลื่อนตำแหน่ง)
    switch p.peek().kind {
    case kindNum:
        t := p.next()
        v := 0
        for i := 0; i < len(t.text); i++ {   // แปลง "123" → เลข 123
            v = v*10 + int(t.text[i]-'0')
        }
        return &node{value: v}, nil
    case kindLParen:
        p.next()
        inner, err := p.parseExpr()   // ← วงเล็บ → ย้อนกลับไป parseExpr (เรียกซ้ำข้ามกัน)
        if err != nil { return nil, err }
        if err := p.expectRParen(); err != nil { return nil, err }  // เช็คว่ามี ')' ปิด
        return inner, nil
    default:
        return nil, fmt.Errorf("นิพจน์ผิดที่ตำแหน่ง %d", p.peek().pos)  // กรณีผิดพลาด
    }
}
```

สังเกตสองจุดที่สวยงาม: (1) `parseExpr` เรียก `parseTerm` แล้ว `parseTerm` ก็เรียกกลับไปที่ `parseExpr` ตอนเจอวงเล็บ — วงจรเรียกซ้ำข้ามกันนี้แหละคือการ "ลงลึก" เข้าไปในโครงสร้างที่ซ้อนกัน และ (2) การบวกหลายตัวใช้ **loop** (ไม่ใช่การเรียกซ้ำ) ตามบทเรียนจากโปรแกรม 03 เป๊ะ

ผลรัน ทดสอบ 10 นิพจน์ คำนวณค่าได้ตรงหมด:

```
  นิพจน์                    ได้    ควรเป็น  frame ลึกสุด  ตรง
  7                         7     7       2           true
  1+2                       3     3       2           true
  1+2+3                     6     6       2           true
  1 + 2 + (3 + (4 + 5))     15    15      6           true
  ((((1))))                 1     1       10          true
  ...                         (ย่อ: อีก 5 นิพจน์ — รวม 10 · เต็มใน out/04)
  ผิด 0 จาก 10 นิพจน์
```

และข้อผิดพลาดที่ผู้ใช้เห็นก็อ่านรู้เรื่อง + บอกตำแหน่ง (ไม่ใช่ panic — สัญญาณตายของโปรแกรม — หรือเลขแปลก ๆ):

```
  "1++2"     → ตำแหน่ง 2: เจอ '+' ทั้งที่ยังไม่มีตัวเลขมาก่อน
  "(1+2"     → ตำแหน่ง 4: เปิดวงเล็บไว้แล้วไม่ปิด (คาดว่าจะเจอ ')')
  "@"        → ตำแหน่ง 0: เจอสัญลักษณ์ "@" ซึ่งไม่รู้จัก
  ...        (ย่อ: อีก 3 กรณี เช่น "1 2", "1+", ")" — เต็มใน out/04)
```

### 7.1 ต้นไม้บอก "ลำดับการคำนวณ" — และกติกานี้อยู่ที่ไวยากรณ์ ไม่ใช่ตัว parser

จุดที่คนเริ่มต้นงงบ่อยที่สุดคือ: **เครื่องหมาย `*` สำคัญกว่า `+`** นี่มันเป็นกติกาที่ตัว parser รู้ได้ยังไง? คำตอบคือ parser **ไม่รู้เลย** — กติกานี้ฝังอยู่ใน**รูปของไวยากรณ์**ต่างหาก

ดูหลักฐานจากโปรแกรม 04 ที่เอา `go/parser` (ตัว parser ของ Go toolchain — ชุดเครื่องมือของภาษา Go — ตัวจริง) มาเทียบกับ parser ของเรา:

```
  go/parser.ParseExpr("1 + 2*3") → *ast.BinaryExpr
    BinaryExpr op = +
      BasicLit INT = 1
      BinaryExpr op = *
        BasicLit INT = 2
        BasicLit INT = 3
```

อ่านต้นไม้ (ศัพท์ของ go/ast: `BinaryExpr` = โหนดการคำนวณสองข้าง, `op` = เครื่องหมาย, `BasicLit` = ค่าคงที่ตรง ๆ เช่น เลข 1): โหนดรากคือ `+` และมี `*` อยู่**ลึกกว่า** (เป็นลูกของ `+`) → แปลว่า `2*3` ถูกคำนวณก่อน แล้วค่อยเอา `1 + ผลลัพธ์` — กติกา "คูณก่อนบวก" ปรากฏออกมาเป็น**รูปทรงของต้นไม้** ไม่ใช่คำสั่ง `if` ที่ไหนใน parser เลย และวงเล็บ `(1 + 2)*3` ก็แค่ "บังคับกลุ่ม" ให้ได้ต้นไม้อีกรูป:

```
  go/parser.ParseExpr("(1 + 2)*3") → *ast.BinaryExpr
    BinaryExpr op = *
      ParenExpr  (วงเล็บ — บังคับให้กลุ่มในถูกคำนวณก่อน)
        BinaryExpr op = +
          BasicLit INT = 1
          BasicLit INT = 2
      BasicLit INT = 3
```

ทั้งสองนิพจน์ให้ค่าต่างกัน (7 กับ 9) **ทั้งที่ตัวเลขกับเครื่องหมายชุดเดียวกันเป๊ะ** — ต่างกันที่โครงสร้างต้นไม้ล้วน ๆ นี่คือแก่นของ "ทำไม parser ต้องสร้างต้นไม้" ไม่ใช่แค่เช็คว่า "เขียนถูกไหม" (รายละเอียด AST ของไฟล์ทั้งไฟล์ เราไปลงลึกในตอนที่ 27 — parser → AST)

## 8. โปรแกรม 05 — เพดานของ "stack ที่ไม่จำกัด"

ทฤษฎีบอกว่า stack ของ PDA "ไม่จำกัด" แต่ของจริงทุกอย่างมีเพดาน และเพดานนี้มีกับดักที่ทำให้ parser เขียนพลาดแล้ว**ตายอย่างเงียบ ๆ** ได้ — โปรแกรมสุดท้าย (`05_nesting_limit`) สาธิตเรื่องนี้

**กับดักที่ 1: stack overflow เป็น fatal error ไม่ใช่ panic**

ใน Go (และภาษา low-level — ภาษาระดับต่ำที่จัดการหน่วยความจำเอง เช่น C — หลายตัว) การเรียกฟังก์ชันซ้ำจนล้น call stack ไม่ได้ทำให้เกิด `panic` (สัญญาณผิดพลาดที่โปรแกรมตั้งใจปล่อย แล้ว `recover()` = ฟังก์ชันที่ดักจับ panic ได้) แต่เป็น **fatal error** (ความผิดพลาดร้ายแรง) ของ runtime (ระบบเบื้องหลังที่รันโปรแกรม Go) — โปรแกรมตายทันที จับอะไรไม่ได้เลย

ผลรันจริง (เราลดเพดาน stack ตัวเองเหลือ 64 MiB — MiB = หน่วยความจำประมาณ 1 ล้านไบต์ — เพื่อให้การทดลองจบเร็ว; "exit code" คือรหัสที่โปรแกรมคืนให้ระบบตอนจบ 0 = สำเร็จ 2 = ตาย):

```
  // (ย่อจากผลรันจริง 2 ครั้ง — ฉบับเต็มอยู่ใน out/05_nesting_limit)
  4,000,000 ชั้น → เรียกซ้ำครบโดยไม่ตาย (exit code 0)
  5,000,000 ชั้น →
    runtime: goroutine stack exceeds 67108864-byte limit
    fatal error: stack overflow
    exit code = 2   ← recover() จับไม่ได้ ตามที่โค้ดเขียนเตือนไว้
```

**กับดักที่ 2: parser ของ Go เองก็ต้องมี "ประตูกั้นความลึก"**

เพราะ parser จริงก็คือ recursive descent ตัวมันเองก็เสี่ยงล้น stack เหมือนกัน — ตัว parser ของ Go จึง**นับความลึกการเรียกซ้ำเอง** แล้วตั้งเพดานไว้ ผลรัน:

```
  ซ้อน      10 ชั้น → อ่านผ่าน
  ซ้อน     100 ชั้น → อ่านผ่าน
  ซ้อน    1000 ชั้น → อ่านผ่าน
  ซ้อน  100000 ชั้น → error: 1:100001: exceeded max nesting depth
  ซ้อน  200000 ชั้น → error: 1:100001: exceeded max nesting depth
  เหตุผล: go/parser นับความลึกเอง (ตัวแปร nestLev) เพดาน maxNestLev = 100000
```

พอเกินเพดาน มันจะคืน **error อย่างสุภาพ** (บอกตำแหน่ง + ข้อความชัดเจน) แทนที่จะปล่อยให้โปรแกรมตาย — และ parser ของเราทุกตัวก็ทำแบบเดียวกัน (`maxParseDepth = 5000` ในโปรแกรม 03, `maxASTDepth = 2000` ในโปรแกรม 04) ผลรันโหมด `ours` (ของเรา — โปรแกรม 05 ที่มีประตูกั้นความลึกเอง):

```
  เรียกซ้ำ  6000 ชั้น (เพดาน 6000) → <nil>  (nil = ไม่มี error ผ่านปกติ)
  เรียกซ้ำ  6001 ชั้น (เพดาน 6000) → ซ้อนลึกเกินเพดานที่ตั้งไว้ (maxDepth)
  สังเกต: เกินเพดานแล้วได้ error ปกติ — โปรแกรมยังอยู่ ยังพิมพ์บรรทัดต่อไปได้
```

> **บทเรียนเชิงวิศวกรรม (ใช้กับงานจริง):** parser ที่ดีต้องมี "ประตูกั้นความลึก" ของตัวเอง แล้วคืน error ที่อ่านรู้เรื่อง — **ห้าม**ปล่อยให้ runtime (ระบบเบื้องหลังของภาษา) เป็นคนตัดสิน เพราะ runtime ตัดสินด้วยการ "ฆ่าโปรแกรม" หลักการนี้ใช้กับโค้ด recursive ทุกอย่าง ไม่ใช่แค่ parser

## 9. สรุป — "ทำไม parser ทำงานได้" ตอบได้แล้ว

วนกลับมาที่คำถามตั้งต้นคืนนี้ เราตอบได้ครบแล้ว:

1. **ไวยากรณ์ของภาษาโปรแกรม (syntax) เป็น context-free grammar** — เขียนเป็นกฎไม่กี่ข้อได้ (เราเห็นกฎ 2 ข้อบรรยายวงเล็บสมดุล, 2 ข้อบรรยายนิพจน์)
2. **ทฤษฎีบทรับประกันว่า** ภาษา context-free ทุกภาษา มี **pushdown automaton** รับรู้ได้ (CFG = PDA)
3. **PDA ก็คือเครื่องสถานะจำกัด + stack** — ส่วนที่ FA ขาดคือ "ที่พัก" สำหรับจำจำนวน/ความลึกที่ไม่รู้ล่วงหน้า
4. **recursive descent parser ที่เราเขียนจริง = PDA** — โดยใช้ call stack ของภาษาเป็น stack ของ PDA ตามธรรมชาติ (พิสูจน์ด้วยโปรแกรม 03: parser สองแบบให้ผลตรงกัน)
5. **ในทางปฏิบัติ** stack ที่ "ไม่จำกัด" ก็มีเพดาน จึงต้องมีประตูกั้นความลึก (โปรแกรม 05) และรูปของไวยากรณ์มีผลต่อความลึกจริง (กับดักในโปรแกรม 03)

ลำดับชั้นของภาษาที่เราสะสมมาได้ตอนนี้: **regular ⊊ context-free ⊊ Turing-recognizable** (ภาษาที่เครื่อง Turing machine รับได้) — แล้วคืนถัดไป (ตอนที่ 24) เราจะขึ้นชั้นสุดท้าย ไปรู้จัก **Turing machine** กับ **halting problem** คำถามว่า "มีอะไรที่คอมพิวเตอร์ทำไม่ได้" — แล้วจะเห็นว่าที่เรียนมาทั้งหมดเป็นบันไดเดียวกัน

## โจทย์ประจำตอน

### ระดับ Drill (ฝึกมือ)

1. เอา PDA ในโปรแกรม 01 มาลองรันกับ input `")(("` และ `"())(()"` แล้ววาดตารางเดินทีละก้าวเหมือนในบทความ (สัญลักษณ์ / top / stack ล่าง→บน) — ตรงไหนที่เครื่องหยุด แล้วหยุดเพราะอะไร?
2. เขียน derivation ของ `(())` ด้วยไวยากรณ์ `S → (S)S | ε` ให้ครบทุกขั้น แล้วลองทำ derivation ของ `(()())` เพิ่มอีกหนึ่งตัว
3. วาด parse tree ของ `aaabbb` ด้วยไวยากรณ์ `S → aSb | ε` — นับจำนวนครั้งที่ใช้กฎ `S → aSb` แล้วเทียบว่าตรงกับจำนวน `a` (3) ไหม (ชั้นของต้นไม้ = 2 × จำนวน `a`)

### Mini-project (ต่อยอดจากโปรแกรม 04)

โปรแกรม 04 รองรับแค่ `+` กับวงเล็บ จงเพิ่มเครื่องหมาย `-`, `*`, `/` เข้าไป **โดยยังให้ "คูณหารก่อนบวกลบ"** ถูกต้อง เริ่มจากแก้ไวยากรณ์ให้เป็น 3 ชั้น (ชั้นบวก → ชั้นคูณ → ชั้นตัวเลข):

```
Expr  → Term  ( ("+"|"-") Term )*
Term  → Factor ( ("*"|"/") Factor )*
Factor → number | "(" Expr ")"
```

แล้วแก้โค้ด `parseExpr/parseTerm` ให้มี `parseFactor` เพิ่มอีกหนึ่งฟังก์ชัน (นี่คือ pattern มาตรฐานที่ parser จริงทุกตัวใช้ เรียกว่า **operator precedence** = กติกาความสำคัญของเครื่องหมาย "คูณหารก่อนบวกลบ") — เป้าหมายคือ `1+2*3` ต้องได้ 7 (ไม่ใช่ 9) และ `(1+2)*3` ได้ 9 ลองให้โปรแกรมพิมพ์ AST ออกมาดูว่าต้นไม้ของสองนิพจน์นี้ต่างกันยังไง
