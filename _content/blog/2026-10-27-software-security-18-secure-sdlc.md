ตอนที่แล้วเราจบด้วยการบ้านที่ให้ทำตารางสิบแถวของโปรเจกต์ตัวเอง — ตรวจแอปหนึ่งตัวด้วย OWASP Top 10 แล้วจดหลักฐานไว้ทุกแถว

ถ้าคุณทำเสร็จ คุณจะเจอคำถามถัดไปด้วยตัวเอง: **ตารางนั้นตรวจตอนไหน** · เราตรวจมันหลังโค้ดเสร็จแล้ว — ซึ่งแปลว่าเราเพิ่งจ่ายเงินซื้อความรู้ที่ควรได้มาก่อนหน้านี้ไปแล้ว · ตอนที่ 17 ตอบว่า "ต้องตรวจอะไร" · ตอนนี้ตอบคำถามที่ใหญ่กว่า: **ตรวจเมื่อไหร่ และใครจ่าย**

และมันมีตัวเลขที่ผมจะพาคุณไปดู — ผมบอกก่อนว่ากำลังวัดอะไร:

- **เดโม 1** — แบบจำลองที่มีข้อบกพร่อง (defect) 60 รายการชุดเดียวกัน ผ่านสองกระบวนการที่ต่างกันแค่ว่าด่านตรวจ (gate) อยู่ขั้นไหน: กระบวนการ A มี gate เดียวตอนก่อนปล่อย · กระบวนการ B มี gate ที่ design, code และ test · ผลคือ **3280 หน่วย vs 1176 หน่วย (A/B = 2.79 เท่า)** · ตกถึง production (สภาพแวดล้อมจริงที่มีผู้ใช้ — ต่างจาก dev/test) **28 vs 9** · และข้อบกพร่องที่จับได้ตอน design คือ **0 vs 24** · ทดสอบซ้ำด้วย 10 seed ที่ต่างกันได้ 2.22–3.76 เท่า ทุกครั้ง
- **เดโม 2** — security gate ที่ผมเขียนเองด้วย `go/ast` (อ่านโครงสร้างโค้ด ไม่ใช่ค้นหาข้อความอย่าง `grep`) · จับโค้ดตัวอย่างที่มีช่องโหว่ได้ **5 finding** (ผลตรวจหนึ่งรายการ — หนึ่งจุดที่กฎข้อหนึ่งจับได้: critical 2 · high 2 · medium 1) แล้ว **exit 1** · และผ่านโค้ดที่แก้แล้วด้วย **0 finding** exit 0
- **เดโม 3 (เล็ก)** — pipeline (สายงานอัตโนมัติที่รันเป็นขั้น ๆ) 3 ขั้นที่หยุดจริงเมื่อ gate ไม่ผ่าน: `stage 3/3 deploy → skipped` ไม่ใช่แค่พิมพ์คำเตือน

## 1. แนวคิด: SDLC คืออะไร และ "shift left" ย้ายอะไรไปทางซ้าย

### 1.1 SDLC — วงจรชีวิตการพัฒนาซอฟต์แวร์

**SDLC (Software Development Life Cycle)** คือคำเรียกรวม ๆ ของ *กิจกรรมทั้งหมดที่ทำให้ซอฟต์แวร์หนึ่งตัวเกิดขึ้นมาและอยู่ต่อ* · มันไม่ใช่ระเบียบวิธีเดียว — waterfall, iterative, agile, DevOps เป็นวิธี *จัดเรียง* กิจกรรมเหล่านี้คนละแบบ · แต่ทุกแบบมีกิจกรรมพื้นฐานชุดเดียวกัน:

| ขั้น | คำถามที่ขั้นนี้ตอบ | ผลลัพธ์ที่ได้ (artifact) |
|---|---|---|
| **plan / requirements** | สร้างอะไร ให้ใคร เพื่ออะไร | ข้อกำหนด, เกณฑ์ยอมรับ |
| **design** | จะสร้างมันอย่างไร | สถาปัตยกรรม, data flow, สัญญาระหว่างส่วน |
| **code** | ลงมือเขียน | ซอร์สโค้ด |
| **test** | มันทำงานตามที่ออกแบบไหม | ผลทดสอบ |
| **deploy** | ปล่อยขึ้นที่ใช้งานจริง | binary/container ที่รันอยู่ |
| **monitor / maintain** | มันยังทำงานดีอยู่ไหม และพังตรงไหน | log, alert, แพตช์ |

ถ้าคุณจบ CS Fundamentals มา คำศัพท์ในตารางนี้คุณรู้หมดแล้ว · สิ่งที่คุณยังไม่รู้คือ **คำถามที่ security ถามในแต่ละขั้น** — และนั่นคือทั้งหมดของบทนี้

### 1.2 ศัพท์ที่บทนี้จะใช้ซ้ำ

ผมจะใช้คำอังกฤษตรง ๆ ทั้งบท (ไม่แปล) เพราะเวลาไปคุยกับทีมจริงคุณจะได้ยินคำเหล่านี้ — และหลายคำจะโผล่ตั้งแต่ย่อหน้าถัดไป:

- **gate** = ด่านตรวจใน pipeline ที่ *ตัดสินได้* ว่าจะให้ผ่านหรือไม่ (ไม่ใช่แค่เตือน) · gate ที่เตือนอย่างเดียวคือ dashboard ไม่ใช่ gate
- **pipeline** = สายงานอัตโนมัติที่รันทุกครั้งที่ push โค้ด: build → test → scan → deploy
- **CI/CD** = Continuous Integration (รวมโค้ดบ่อย ๆ แล้วรันทดสอบอัตโนมัติ) / Continuous Delivery (ปล่อยได้ตลอดเวลาที่ผ่านด่าน)
- **SAST / DAST / SCA** = ตรวจโค้ดนิ่ง / ตรวจแอปที่รันอยู่ / ตรวจ dependency (ตอนที่ 25 ลงลึก)
- **SBOM** = Software Bill of Materials — รายการส่วนประกอบทั้งหมดพร้อมเลขรุ่น (ตอนที่ 8 และ 29)
- **finding** = ผลตรวจหนึ่งรายการจากเครื่องมือ คือหนึ่งจุดที่กฎข้อหนึ่งจับได้ · ไม่ใช่คำตัดสินว่าช่องโหว่นั้นถูกโจมตีได้จริง — มันเป็น *ข้อกล่าวหา* ที่คนยังต้องอ่านแล้วตัดสิน
- **production** = สภาพแวดล้อมจริงที่มีผู้ใช้ใช้งาน (ต่างจาก dev/test) · ผมจะเรียกสั้น ๆ ว่า prod
- **threat model** = เอกสารที่ไล่ว่าในระบบนี้มีอะไรมีค่า ใครอยากได้ และมันจะเข้ามาทางไหน (ตอนที่ 11)
- **shift left** = ย้ายกิจกรรมไปทางซ้ายของแกนเวลา คือทำเร็วขึ้น ก่อนของจะแพง

### 1.3 วิธีดั้งเดิม: ตรวจตอนท้าย

ในองค์กรส่วนใหญ่ที่ผมเห็น (และในหลายทีมที่ยังทำงานแบบนี้อยู่) security ถูกจัดเป็น **เหตุการณ์ (event)** ไม่ใช่ **กระบวนการ (process)** · รูปแบบที่พบบ่อยที่สุดคือ: ทีมพัฒนาเขียนโค้ดจนเสร็จ → ก่อนปล่อยจริงสองสัปดาห์มีทีม security หรือที่ปรึกษาภายนอกเข้ามาทำ **pen-test** (penetration test = การทดสอบเจาะระบบโดยได้รับอนุญาต เพื่อหาว่าระบบถูกเจาะได้จริงหรือไม่) → ส่งรายงาน → ทีมพัฒนาแก้ → ปล่อย

ทำไมวิธีนี้ถึงดูสมเหตุสมผล? เพราะมันมีข้อดีจริงสามข้อ:

1. **ประหยัดคน** — ไม่ต้องมีคน security นั่งอยู่ในทีมทุกวัน จ้างเป็นรอบถูกกว่า
2. **มีคนเก่งตรวจ** — ผู้เชี่ยวชาญที่เจาะระบบทั้งวันย่อมเก่งกว่าคนที่เจาะปีละครั้ง
3. **มีเอกสารให้ลูกค้า/ผู้ตรวจสอบ** — "เราผ่าน pen-test แล้ว" เป็นประโยคที่ซื้อความเชื่อถือได้

และมันพังด้วยเหตุผลสามข้อที่น้ำหนักไม่เท่ากัน:

**หนึ่ง — ช่องโหว่ทุกตัวมี "จุดที่แก้ได้ถูกที่สุด" และจุดนั้นมักอยู่ทางซ้าย** · ถ้าคุณออกแบบระบบโดยไม่มี authorization model (แบบว่า "ใครล็อกอินแล้วก็เข้าถึงได้หมด") การ pen-test จะเจอมันในฐานะ *finding หลายสิบรายการ* — เพราะทุก endpoint ที่ขาดการตรวจสิทธิ์คือหนึ่ง finding

แต่การจะแก้ "จริง" คุณต้องแก้ *การออกแบบ* ซึ่งหมายถึงเขียนใหม่เกือบทั้งชั้น API · ทีมที่เจอตอนท้ายจะไม่ทำแบบนั้น เขาจะ patch ทีละ endpoint แล้วปล่อย — และรอยรั่วก็กลับมาใน endpoint ที่เขียนใหม่เดือนหน้า

**สอง — ต้นทุนการแก้ไม่ได้เป็นเส้นตรง** (หัวข้อ 2.2 มีตัวเลขและการตรวจสอบที่มาที่ไป)

**สาม — pen-test เป็นการสุ่มตัวอย่าง ไม่ใช่การครอบคลุม** · ผู้ทดสอบมีเวลาจำกัด เขาจะไล่ดูเส้นทางที่ "น่าจะพัง" มากที่สุด · ช่องโหว่ที่อยู่ในโค้ดที่ไม่มีใครแตะมาสองปีจะไม่ถูกตรวจเลย — แต่ผู้โจมตีไม่ได้มีเวลาจำกัดแบบนั้น

### 1.4 shift left — ย้ายด่านตรวจไปทางซ้าย

คำว่า **shift left** มาจากภาพง่าย ๆ: ถ้าแกนเวลาไหลจากซ้าย (ความคิด) ไปขวา (ของที่รันอยู่) การย้ายกิจกรรมไปทางซ้ายคือการทำมัน **เร็วขึ้น** ก่อนของจะแพง

ประวัติของคำนี้ควรรู้เพราะมันถูกใช้ผิดบ่อย: คำนี้ไม่ใช่คำของวงการ security · **Larry Smith เขียนบทความชื่อ "Shift-Left Testing" ใน Dr. Dobb's Journal ฉบับกันยายน 2001** และเขาใช้มันหมายถึงการเอา *testing* เข้าไปอยู่ใกล้ *development* มากขึ้น — ไม่ได้พูดถึง security เลย · วงการ security ยืมคำนี้มาใช้ราวทศวรรษ 2010s แล้วความหมายก็ขยายจาก "ทดสอบเร็วขึ้น" เป็น "คิดเรื่องความปลอดภัยเร็วขึ้น"

ความต่างนี้สำคัญเพราะมันบอกอะไรบางอย่าง: **shift left ไม่ใช่เครื่องมือ มันคือการเปลี่ยนว่าใครรับผิดชอบอะไร** · ถ้าคุณซื้อเครื่องมือ SAST มาใส่ pipeline แต่ทีมยังคิดว่า "security เป็นงานของทีม security" คุณไม่ได้ shift left อะไรเลย คุณแค่ย้ายที่ที่คนเดิมทำงาน

![ต้นทุนการแก้ข้อบกพร่องเพิ่มขึ้นตามขั้นที่เจอ](/assets/diagrams/ep18-01-cost-curve.svg)

ตัวเลขในภาพนี้ผมจะกลับไปตรวจที่มาของมันในหัวข้อ 2.2 — และคำตอบคือมันเชื่อถือได้น้อยกว่าที่คนอ้างกันมาก · ผมใส่ภาพไว้ตรงนี้ก่อนเพราะมันคือ *เหตุผล* ที่คนคิดค้น shift left ขึ้นมา ไม่ใช่งานพิสูจน์

### 1.5 Secure SDLC — ใส่ activity ลงไปทุกขั้น

**Secure SDLC** คือ SDLC ที่แต่ละขั้นมีกิจกรรม security ของตัวเอง พร้อม *หลักฐาน* ว่าทำจริง · นี่คือตารางที่ผมใช้สอนทีมใหม่ และมันคือคำตอบของคำถาม "แล้วเราต้องทำอะไรบ้าง":

| ขั้น | กิจกรรม security | เครื่องมือ/วิธีการ | หลักฐานที่ต้องมี |
|---|---|---|---|
| **design** | **threat modeling** (นั่งไล่ว่าใครจะโจมตีอะไรได้บ้าง — ตอนที่ 11), กำหนด security requirement, วาด data flow + trust boundary (ตอนที่ 14) | ประชุม 1–2 ชม. ต่อ feature ใหญ่, STRIDE (ชุดคำถาม 6 หมวดไล่หาความเสี่ยง — ตอนที่ 11) | เอกสาร threat model ที่มีชื่อคน review |
| **code** | **secure coding guideline** (แนวทางที่ทีมตกลงร่วมกันว่าแบบไหนห้ามเขียน เช่น ห้ามต่อสตริงเป็น SQL), **code review** ที่มี security checklist (ตอนที่ 26), ห้าม hardcode secret (เขียนค่าลับลงในโค้ดตรง ๆ) | review checklist, pre-commit hook (สคริปต์ที่รันก่อน commit), secret scanner | หลักฐาน review ใน pull request (คำขอรวมโค้ดก่อน merge) |
| **test** | **SAST** (Static Application Security Testing = วิเคราะห์ซอร์สโค้ดหา pattern อันตราย), **DAST** (Dynamic = ยิงคำขอจริงใส่แอปที่รันอยู่), **dependency scan** (ตรวจว่า library ที่เรียกใช้มีช่องโหว่ที่ประกาศแล้วไหม — ตอนที่ 25) | govulncheck, staticcheck, ZAP, dependency scanner | ผลสแกน + สถานะของทุก finding |
| **deploy** | **hardening** (ปิดของที่ไม่ใช้, ตั้ง timeout, รันด้วยสิทธิ์น้อยสุด — ตอนที่ 12), **secret management**, image scanning | config as code, secret manager, SBOM | diff ของ config + SBOM ที่ผูกกับ release |
| **monitor** | **logging ที่ใช้สอบสวนได้**, alert, **incident response**, post-mortem (ประชุมย้อนดูว่าอะไรพลาด — ตอนที่ 28) | log pipeline, SIEM (ระบบรวม log แล้วค้นหาเหตุการณ์ย้อนหลัง), on-call (เวรรับแจ้งเหตุ) | incident log + สิ่งที่แก้ตามหลัง |

อ่านตารางนี้แล้วมีสามอย่างที่ต้องพูดตรง ๆ:

**หนึ่ง — คอลัมน์ขวาสุดคือคอลัมน์ที่คนลืมที่สุด** · กิจกรรมทุกอย่างในตารางนี้ไร้ค่าถ้าไม่มีหลักฐาน · "เรามี threat model" ที่ไม่มีเอกสารให้เปิดคือประโยคที่ตรวจสอบไม่ได้ เหมือน "เราผ่าน ISO" ที่ไม่มีเลขรุ่น (บทเรียนเดียวกับตอนที่ 17)

**สอง — กิจกรรมเหล่านี้ไม่ได้หนักเท่ากัน** · threat modeling หนึ่งชั่วโมงต่อ feature ใหญ่ให้ผลตอบแทนสูงกว่าการเพิ่ม scanner ตัวที่ห้าใน pipeline มาก · ถ้าคุณมีเวลาแค่สัปดาห์ละสองชั่วโมง เอาไปลงที่ design

**สาม — ไม่มีขั้นไหนทดแทนขั้นอื่นได้** · นี่คือความหมายจริงของ **defense in depth** (ตอนที่ 12): ไม่ใช่การทำเรื่องเดียวกันซ้ำหลายชั้น แต่คือการเอาด่านที่ *มองเห็นคนละอย่าง* มาวางซ้อนกัน · SAST เห็น pattern ในโค้ดแต่ไม่เห็นว่า authentication ถูกออกแบบผิด · pen-test เห็นผลรวมแต่ไม่เห็นว่าโค้ดบรรทัดไหนเป็นต้นเหตุ · threat model เห็นความเสี่ยงที่ยังไม่มีโค้ดให้สแกน

### 1.6 SSDF ของ NIST — และบทเรียนเรื่องอายุของกรอบงาน

ถ้าคุณอยากได้รายการที่ละเอียดกว่าตารางข้างบนโดยไม่ต้องคิดเอง มาตรฐานที่วงการอ้างมากที่สุดคือ **NIST SSDF (Secure Software Development Framework) = SP 800-218** · ผมตรวจสถานะล่าสุดเมื่อ 27 ต.ค. 2026 แล้วได้สิ่งนี้:

- **v1.1 คือฉบับทางการ** ประกาศ **3 กุมภาพันธ์ 2022** (เลข SP 800-218) แทนที่ whitepaper ฉบับเดือน เม.ย. 2020
- โครงสร้างคือ **4 กลุ่ม · 19 practices · 42 tasks**: **PO** (Prepare the Organization) 5 practices / 13 tasks · **PS** (Protect the Software) 3 / 4 · **PW** (Produce Well-Secured Software) 8 / 16 · **RV** (Respond to Vulnerabilities) 3 / 9
- **Rev.1 (จะกลายเป็น v1.2) ยังเป็นร่าง** — initial public draft ลงวันที่ **17 ธันวาคม 2025** · ร่างนี้เพิ่ม PO.6 (continuous process improvement) กับ PS.4 (robust and reliable updates) ซึ่งจะทำให้เป็น 21 practices / 49 tasks — **แต่ยังไม่ใช่ของจริง** อย่าอ้างว่า "SSDF v1.2 บอกว่า…" ในเอกสารของคุณตอนนี้
- และที่สำคัญที่สุด: **OMB M-22-18** ซึ่งบังคับให้ vendor ของรัฐบาลสหรัฐส่ง self-attestation ว่าทำตาม SSDF **ถูกยกเลิกเมื่อ 23 มกราคม 2026** ด้วย **OMB M-26-05** · เหตุผลที่ memo ระบุคือมัน "prioritized compliance over genuine security investments" · หน่วยงานยัง *อาจ* ใช้แบบฟอร์มเดิมและ *อาจ* ขอ SBOM ตามสัญญา แต่ไม่บังคับทั้งรัฐบาลอีกแล้ว

ทำไมผมเล่าเรื่องนี้ในบทที่สอนแนวคิด ไม่ใช่บทการเมือง? เพราะมันเป็นบทเรียนวิชาชีพที่ผมอยากให้คุณติดตัว: **กรอบงานกับนโยบายมีอายุไม่เท่ากัน** · SSDF v1.1 ยังใช้ได้ในปี 2030 · M-22-18 ตายไปแล้วในสามปี · ถ้าคุณสร้างโปรแกรม security ทั้งโปรแกรมโดยผูกกับ "ข้อบังคับ X" คุณจะสร้างสิ่งที่ตายตามข้อบังคับ · ถ้าคุณผูกกับ *หลักการ* (คิด threat ก่อนเขียน, ตรวจทุก commit, ทบทวนหลังพัง) มันจะอยู่ต่อ ไม่ว่าใครจะออก memo อะไร

กรอบงานแบบเดียวกันนี้มีหลายสำเนา และการเห็นว่ามันต่างกันแค่ไหนก็มีประโยชน์: **Microsoft** ทำ **SDL (Security Development Lifecycle)** ตั้งแต่ Trustworthy Computing memo เดือน ม.ค. 2002 และใช้เป็นส่วนหนึ่งของกระบวนการพัฒนาตั้งแต่ปี 2004 · **CISA** เปิดตัว **Secure by Design** (เม.ย. 2023) ที่ผลักความรับผิดชอบไปฝั่ง *ผู้ผลิต* ซอฟต์แวร์ ไม่ใช่ฝั่งลูกค้าที่ต้องไปตั้งค่าเอง · ทั้งสามฉบับ (SSDF, SDL, Secure by Design) พูดเรื่องเดียวกันคนละสำนวน: คิดความเสี่ยงก่อนเขียน, ตรวจทุกครั้งที่ของเปลี่ยน, และมีหลักฐานว่าทำ — ต่างกันที่ใครบังคับใช้ และบังคับกับใคร

## 2. ทำไมมันสำคัญ: เคสที่ "ตรวจหลังเสร็จ" พังจริง

### 2.1 Equifax 2017 — แพตช์มีให้แล้ว หกสิบเจ็ดวันก่อนถูกเจาะ

เคสที่ผมใช้สอนเรื่องนี้ทุกครั้งคือ Equifax (หนึ่งในสามบริษัทจัดอันดับเครดิตของผู้บริโภครายใหญ่ที่สุดของสหรัฐ) เพราะมันไม่ใช่เรื่องของ "ช่องโหว่ใหม่ที่ยังไม่มีใครรู้" — มันเป็นเรื่องของ **ช่องโหว่ที่แพตช์ออกแล้ว และไม่มีใครเอาไปใช้**

ลำดับเหตุการณ์ (ผมตรวจจากหลายแหล่งแล้ว วันที่ต่างกันหนึ่งวันในบางแหล่ง — ผมเขียนช่วงไว้):

| วันที่ | เหตุการณ์ |
|---|---|
| 6–7 มี.ค. 2017 | Apache ประกาศ **CVE-2017-5638** (ช่องโหว่ใน Struts 2 ที่สั่งรันคำสั่งบนเซิร์ฟเวอร์ได้โดยไม่ต้องล็อกอิน) และออกเวอร์ชันที่แก้แล้ว (2.3.32 / 2.5.10.1) · โค้ดทดลองโจมตีเผยแพร่ภายในไม่กี่ชั่วโมง |
| 8 มี.ค. 2017 | US-CERT ออกประกาศเตือน · ทีม security ของ Equifax ได้รับแจ้ง |
| 9 มี.ค. 2017 | ทีม security ส่งอีเมลภายในให้แพตช์ภายใน 48 ชั่วโมง |
| 15 มี.ค. 2017 | ครบกำหนด · มีการสแกนหาเครื่องที่ยังไม่แพตช์ แต่ระบบพอร์ทัลของลูกค้า (ACIS) ไม่ถูกพบ |
| 13 พ.ค. 2017 | ผู้โจมตีเข้าถึงระบบได้ครั้งแรก — **67 วันหลังแพตช์พร้อมใช้** |
| 13 พ.ค. – 30 ก.ค. 2017 | อยู่ในระบบต่อ · ดึงข้อมูลด้วยคำสั่งกว่า 9,000 ครั้งจาก 51 ฐานข้อมูล |
| 29–30 ก.ค. 2017 | ตรวจพบ traffic ผิดปกติ (มีรายงานว่าเกี่ยวกับใบรับรอง SSL ที่หมดอายุของอุปกรณ์ตรวจ traffic) แล้วปิดระบบ |
| 7 ก.ย. 2017 | ประกาศต่อสาธารณะ · **147 ล้านคน** |

ผลลัพธ์ทางกฎหมาย: กรกฎาคม 2019 Equifax ตกลงจ่าย **อย่างน้อย 575 ล้านดอลลาร์ และอาจถึง 700 ล้าน** ในข้อตกลงกับ FTC, CFPB และ 50 รัฐ (ประกาศ FTC 22 ก.ค. 2019)

ถ้าคุณอ่านตารางนี้แบบวิศวกร คุณจะเห็นว่ามันไม่ได้ล้มเหลวที่จุดเดียว — **มันล้มเหลวพร้อมกันในเกือบทุกขั้นของ SDLC**:

- **deploy** — ไม่มี inventory ที่เชื่อถือได้ว่า "เรามีระบบอะไร running อยู่ที่ไหน" · คุณแพตช์ไม่ได้ในสิ่งที่คุณไม่รู้ว่ามี
- **test** — การสแกนไม่ครอบคลุมระบบที่ถูกโจมตี · การมี scanner โดยที่ scope ผิด = ไม่มี scanner
- **monitor** — อุปกรณ์ตรวจ traffic ใช้งานไม่ได้เพราะใบรับรองหมดอายุ · คือชั้นป้องกันชั้นสุดท้ายที่ควรเห็นข้อมูลไหลออก ก็มองไม่เห็นไปด้วย
- **process** — อีเมลแจ้งไปถึง distribution list ที่ไม่รวมทีมดูแลพอร์ทัลนั้น · และไม่มีกลไกยืนยันว่าคนที่ต้องแพตช์ทำแล้ว

นี่คือเหตุผลที่ผมบอกว่า security เป็น **process ไม่ใช่ event** · ถ้าคุณมีแค่ pen-test ก่อนปล่อย ระบบแบบ Equifax จะ *ผ่าน* pen-test นั้น (เพราะตอน pen-test มันยังไม่ถูกเจาะ) แล้วพังในอีกสองเดือนถัดมาเพราะไม่มีอะไรยืนยันว่าของที่ปล่อยไปยังปลอดภัยอยู่

### 2.2 ตัวเลขต้นทุน — และการตรวจที่มาที่ไปของมัน

ทีนี้มาที่ตัวเลขที่ทุกคนอ้าง · ตัวที่ถูกอ้างบ่อยที่สุดคือชุดนี้:

| ขั้นที่เจอ | ตัวคูณต้นทุนการแก้ |
|---|---|
| design | 1 |
| implementation (code) | 6.5 |
| testing | 15 |
| maintenance / หลังปล่อย | 100 |

แหล่งที่ผมตามไปถึงคือตาราง **"Relative Cost of Fixing Defects" ของ IBM System Sciences Institute** ซึ่ง McKinsey อ้างไว้ในบทความ *A new management science for technology delivery* (แกน Y ของเขาคือ 1 · 6.5 · 15 · 100 ตรงกับตารางนี้)

**แต่เดี๋ยวก่อน — และนี่คือส่วนที่ผมอยากให้คุณอ่านช้าที่สุดในบทนี้** · ผมไล่หาตัวเลขชุดนี้ในหลายแหล่งแล้วเจอ **อย่างน้อยสามชุดที่ต่างกัน** และทุกชุดอ้าง "IBM" เหมือนกัน:

| ชุดที่เจอ | คำอ้าง | ปัญหา |
|---|---|---|
| 1 : 6.5 : 15 : 100 | IBM System Sciences Institute (ตาราง Relative Cost of Fixing Defects) | เป็นชุดที่ผมตามถึงต้นทางได้ชัดที่สุด (ผ่าน McKinsey) |
| 1 : 5 : 10 : 15 : 30 : 100 | "1-10-100 rule" / ตารางที่แยกขั้นย่อยและมี UAT (User Acceptance Testing — ขั้นที่ผู้ใช้ทดสอบรับงาน) = 30 | มักถูกติดป้ายว่า "IBM" ทั้งที่โครงต่างกัน (มี 6 ขั้น ไม่ใช่ 4) — **ตัวเลข 30 ที่คนชอบอ้างมาจากตารางนี้** ไม่ใช่จากตาราง IBM ชุดแรก |
| 1 : 10 : 100 | "Rule of 100" | ยิ่งหยาบลงไปอีก บางแหล่งบอก design $100 → production $10,000 |

และมีข้อเท็จจริงที่ต้องบอกตรง ๆ: **งานต้นทางเป็นงานเก่ามาก (ทศวรรษ 1970s)** ผมไม่พบกระดาษต้นฉบับที่เปิดอ่านได้จริงในรอบนี้ เจอแต่การอ้างต่อกันเป็นทอด ๆ · ในวงการวิชาการมีข้อถกเถียงเรื่องนี้มานานว่าตัวเลข 1:100 นั้นมาจากบริบทไหน (บางส่วนมาจากต้นทุนการแก้ *ข้อกำหนด* ไม่ใช่บั๊กโค้ด) และใช้ทดแทนกันได้แค่ไหน

ดังนั้นผมจะใช้มันแบบนี้ — และอยากให้คุณใช้แบบเดียวกัน: **ใช้ตัวเลขนี้เป็นทิศทาง ไม่ใช่ค่าคงที่** · สิ่งที่เถียงไม่ได้คือ *รูปร่าง* ของมัน (เพิ่มขึ้นเร็วมากเมื่อเลื่อนไปทางขวา) · สิ่งที่เถียงได้คือ *เท่าไร*

และนี่คือเหตุผลที่เดโม 1 ของเราออกมาเป็น **2.79 เท่า ไม่ใช่ 100 เท่า** — ซึ่งผมคิดว่าเป็นผลลัพธ์ที่ *มีประโยชน์กว่า* ตัวเลข 100 มาก เพราะมันคือความจริงของระดับ *กระบวนการ* ไม่ใช่ระดับ *ข้อบกพร่อง*:

- 100 เท่า คืออัตราส่วนของ **ข้อบกพร่องตัวเดียวกัน** ที่เจอตอน design กับตอน production
- แต่กระบวนการ "ตรวจท้าย" ไม่ได้เจอทุกอย่างตอน production — มันเจอ *ประมาณครึ่งหนึ่ง* (32 จาก 60) ตอน pen-test ก่อนปล่อย (ที่ต้นทุน 15) แล้วปล่อยที่เหลือ (28 จาก 60) ลง production
- ผลรวมจึงออกมาเป็น 2.79 เท่า ไม่ใช่ 100 · และ 2.79 เท่าก็ยังหมายถึง **ประหยัด 64%** ซึ่งเป็นตัวเลขที่ CFO ฟังแล้วสนใจ

บริบทอีกชั้นที่ควรรู้ (ตรวจเมื่อ 27 ต.ค. 2026): **IBM Cost of a Data Breach Report 2025** (ข้อมูลจาก 600 องค์กรที่โดน breach ระหว่าง มี.ค. 2024 – ก.พ. 2025) รายงานค่าเฉลี่ยเหตุละ **4.44 ล้านดอลลาร์** globally (ลดจาก 4.88 ล้านในปี 2024 เป็นครั้งแรกในรอบห้าปี) และ **10.22 ล้านดอลลาร์** สำหรับสหรัฐ (สูงสุดเป็นประวัติการณ์) · ตัวเลขนี้ไม่เกี่ยวกับต้นทุนการแก้บั๊ก แต่มันคือ *เพดาน* ของสิ่งที่คุณกำลังป้องกัน — และเป็นเหตุผลที่องค์กรยอมจ่ายเพื่อย้ายด่านตรวจไปทางซ้าย

### 2.3 ทำไม shift left ถึงได้ผลจริง (เชิงกลไก ไม่ใช่เชิงตัวเลข)

สี่ข้อนี้คือคำอธิบายว่าทำไมมันได้ผล — ถ้าจำได้ข้อเดียว ให้จำข้อแรก:

1. **ข้อมูลยังสด** · คนที่เขียนโค้ดเมื่อสิบห้านาทีที่แล้วยังจำได้ว่า `name` มาจากไหน · คนที่อ่าน finding ตอน pen-test อีกสามเดือนให้หลังต้อง reconstruct ความคิดทั้งหมดใหม่ (นี่คือเหตุผลที่ code review มีประสิทธิภาพสูงกว่าการทดสอบที่ตามมาทีหลัง ในแง่ต้นทุนต่อ finding)
2. **บางช่องโหว่ไม่มี "จุดแก้" ที่ปลายทาง** · ไม่มี patch ที่ทำให้ระบบที่ไม่มี authorization model กลายเป็นมี · คุณต้องแก้ design ซึ่งแปลว่าแก้ตอน design ถูกแล้ว
3. **บริบทของสถาปัตยกรรมมีจำกัดตามเวลา** · การเปลี่ยนวิธีจัดการ session (ช่วงที่ผู้ใช้ล็อกอินค้างไว้) ตอนที่ยังไม่มีโค้ด = คุยกัน 20 นาที · ตอนที่มี 40 endpoint แล้ว = refactor (เขียนโครงใหม่โดยพฤติกรรมเท่าเดิม) สองสัปดาห์
4. **feedback loop สั้นลง** · gate ที่รันใน 90 วินาทีทุก commit ทำให้คนแก้ทันที · pen-test ที่มาถึงทุกไตรมาสทำให้ finding กองเป็น backlog (กองงานค้าง) ที่ไม่มีใครอยากแตะ (และนี่คือกลไกที่ทำให้ "มี pen-test" กับ "ปลอดภัยขึ้น" ไม่ใช่เรื่องเดียวกัน)

## 3. ลงมือทำ

สี่ข้อข้างบนคือ *เหตุผล* ว่าทำไม gate ควรอยู่ทางซ้าย — ต่อไปนี้คือการวัดว่ามันจริงแค่ไหน ในเงื่อนไขที่ผมควบคุมได้เอง

### 3.1 เดโม 1: ต้นทุนของ "เจอช้า" — แบบจำลองที่ควบคุมได้

ผมออกแบบเดโมนี้ให้ตอบคำถามเดียว และตัดตัวแปรที่กวนใจออกให้หมด: **ถ้าข้อบกพร่องชุดเดียวกัน ผ่านสองกระบวนการที่ต่างกันแค่ว่ามีด่านตรวจ (gate) ที่ขั้นไหน — A มีที่ test เดียว · B มีที่ design, code, test — ผลต่างจะเป็นเท่าไร**

กติกาของแบบจำลอง — อ่านสี่ข้อนี้ก่อนดูโค้ด:

1. ข้อบกพร่อง 60 รายการ · แต่ละตัวมี **จุดกำเนิด (origin)** ว่าเกิดที่ design หรือ code · จับก่อนจุดกำเนิดไม่ได้ (gate ที่ design มองไม่เห็นบั๊กที่เกิดตอนเขียนโค้ด)
2. แต่ละตัวมีค่าคงที่ `obs[p]` = "ถ้ามี gate ที่ขั้น p จะเห็นมันไหม" · ค่านี้ **จับสลากครั้งเดียวต่อข้อบกพร่อง** แล้วใช้ทั้งสองแบบจำลอง — นี่คือหัวใจที่ทำให้การเปรียบเทียบยุติธรรม
3. กระบวนการ A มี gate ที่ test อย่างเดียว · กระบวนการ B มี gate ที่ design, code และ test · **B จึงเป็น superset ของ A** — ผลต่างที่ได้เป็นผลของ *ตำแหน่ง gate* ล้วน ๆ
4. ทุกอย่างมาจาก `rand.NewSource(seed)` ที่ตรึงไว้ → รันซ้ำได้ผลเดิมทุกไบต์

นิยามข้อมูล:

```go
// phase = ช่วงของ SDLC ที่ข้อบกพร่องถูกจับได้
// เรียงจากซ้าย (ต้นทาง) ไปขวา (ปลายทาง) ตามแกนเวลาของ SDLC
type phase int

	design phase = iota
	code
	test
	prod
)

var phaseName = [4]string{"design", "code", "test", "prod"}

// costMul = ตัวคูณต้นทุนการแก้ เทียบกับตอนที่เจอในขั้น design (=1)
//
// ที่มา: ตาราง Relative Cost of Fixing Defects ของ IBM System Sciences Institute
// (design 1 · implementation 6.5 · testing 15 · maintenance 100) ตามที่ McKinsey
// อ้างไว้ใน "A new management science for technology delivery"
//
// ข้อควรระวัง: ตัวเลขชุดนี้เป็นงานเก่าและถูกอ้างต่อกันมาหลายทศวรรษ ตัวเลขจริง
// ในบทความจึงขึ้นกับว่าใครอ้าง — ดูตารางเทียบสามชุดตัวเลขที่เจอจริงในหัวข้อ 2.2
// เราใช้ชุดนี้เป็น *พารามิเตอร์ของแบบจำลอง* ไม่ใช่ความจริงสากล
var costMul = [4]float64{1, 6.5, 15, 100}
```

และตัวตัดสินว่า "ข้อบกพร่องนี้ถูกจับที่ไหน" — เก้าบรรทัดนี้คือทั้งแบบจำลอง:

```go
func (m model) caughtAt(d defect) phase {
	// หา gate ที่อยู่ทางซ้ายที่สุดที่จับได้ · gate ที่อยู่ก่อนจุดกำเนิดจับไม่ได้
	for p := design; p <= prod; p++ {
		if !m.gates[p] || p < d.origin {
			continue
		}
		if d.obs[p] {
			return p
		}
	}
	return prod // ไม่มี gate ไหนจับได้ → ไปโผล่ที่ production
}
```

**สี่ — ผลต่างที่แท้จริงไม่ใช่ตัวเลขเงิน แต่คือจำนวนครั้งที่ต้องออกแบบใหม่** · 24 ข้อบกพร่องที่ B จับได้ตอน design คือ 24 ครั้งที่ทีมได้คุยกันว่า "feature นี้ควรมี authorization ยังไง" ก่อนมีโค้ด · ในแบบ A ข้อบกพร่องเดียวกันกลายเป็น 24 tickets ที่รอ patch

### 3.2 เดโม 2: gate ที่อ่าน AST ไม่ใช่ grep

ทีนี้มาที่ส่วนที่ทำให้ shift left เป็นจริงได้ — **gate ที่รันเองได้ทุก commit และตัดสินได้**

เครื่องมือสแกนที่คนมักเขียนเองวันแรกคือ `grep` (คำสั่งค้นหาข้อความในไฟล์) · และมันพังด้วยเหตุผลที่ตรงไปตรงมา: `grep "db.Query"` เห็นสองบรรทัดนี้เท่ากัน

```text
db.Query("SELECT id, total FROM invoices WHERE id = $1", id)   // ปลอดภัย
db.Query(q)                                                     // อันตราย ถ้า q มาจาก fmt.Sprintf
```

ทั้งคู่มี `db.Query` · ตัวแรกปลอดภัยเพราะค่าถูกส่งแยกจากคำสั่ง SQL (parameterized query — ตอนที่ 4) · ตัวที่สองอันตรายเพราะ `q` คือสตริงที่ต่อเอง

ทางออกคืออ่าน **AST (Abstract Syntax Tree — โครงสร้างต้นไม้ของโค้ดที่ compiler สร้าง)** แล้วถามคำถามเรื่อง *การไหลของข้อมูล* แทนที่จะถามเรื่อง *ข้อความ* · Go มี `go/ast` + `go/parser` อยู่ใน standard library — ไม่ต้องลง dependency อะไรเลย

กฎห้าข้อที่ gate นี้ตรวจ (ทั้งหมดเป็นตัวอย่างการสอน ไม่ใช่ SAST ระดับ production) · ก่อนอ่านตารางมีคำหนึ่งที่ต้องแยกให้ชัด: คอลัมน์ **CWE** คือ *ชนิด* ของจุดอ่อน (CWE-89 = SQL injection, CWE-22 = path traversal) ส่วน **CVE** คือ *ช่องโหว่รายตัว* ในซอฟต์แวร์ตัวหนึ่งที่มีเลขปีกำกับ (แบบที่ตอนที่ 16 พาทำ) · gate ของเราจับ "ชนิด" — มันบอกว่าโค้ดเข้าข่ายจุดอ่อนชนิดไหน ไม่ได้บอกว่ามีคนออก CVE ให้แล้ว

| กฎ | CWE | ระดับ | ตรวจอะไร |
|---|---|---|---|
| G1 | CWE-89 | critical | สตริงที่ต่อเอง (`fmt.Sprintf` หรือ `+`) ไหลถึง `db.Query/Exec` |
| G2 | CWE-798 | critical | ตัวแปรชื่อที่มีคำว่า secret/password/token ถูกกำหนดจาก string literal |
| G3 | CWE-400 | medium | `http.Server` ที่ไม่ตั้ง `ReadHeaderTimeout` **หรือ** `ReadTimeout` (ตั้งอย่างใดอย่างหนึ่งถือว่าผ่าน) |
| G4 | CWE-295 | high | `tls.Config` ที่ `InsecureSkipVerify: true` |
| G5 | CWE-22 | high | ค่าจาก request (`r.URL.Query().Get`, `r.FormValue`, `r.Header.Get`, …) ไหลถึง sink ของระบบไฟล์: `os.Open`, `os.OpenFile`, `os.ReadFile`, `os.Create`, `os.Remove`, `http.ServeFile` |

ตัวที่ผมอยากให้ดูคือโครงของ G1 กับ G5 เพราะทั้งคู่ใช้เครื่องจักรตัวเดียวกัน — **mini taint analysis** (การติดตามว่า "ค่าไม่น่าไว้ใจ" ไหลจากต้นทางไปถึง sink หรือไม่):

`flowFindings` เรียก `traces` สองครั้ง — นอกเหนือจาก `fs`, `fn`, `path` ที่เหมือนกันทั้งสองครั้ง มันเปลี่ยนแค่สี่ตัวที่เหลือ เรียงจากซ้าย: (1) ชื่อกฎ, (2) ฟังก์ชันที่ตอบว่า "expr นี้เป็นต้นทางไหม" (`concatSource` = สตริงที่ประกอบในโค้ด · `requestSource` = ค่าจาก request), (3) ฟังก์ชันที่ตอบว่า "ชื่อนี้เป็น sink ไหม" (`isSQLSink` · `isFileSink`), (4) ฟังก์ชันสร้างข้อความ · เปลี่ยนแค่สองตัวกลาง ก็ได้กฎใหม่หนึ่งข้อ

```go
func flowFindings(fs *token.FileSet, fn *ast.FuncDecl, path string) []finding {
	if fn.Body == nil {
		return nil
	}
	var out []finding
	out = append(out, traces(fs, fn, path, "G1", concatSource, isSQLSink,
		func(sink, src string) string {
			return fmt.Sprintf("%s() รับสตริงที่ต่อเอง (%s) — ใช้ parameter ($1, ?) แทน", sink, src)
		})...)
	out = append(out, traces(fs, fn, path, "G5", requestSource, isFileSink,
		func(sink, src string) string {
			return fmt.Sprintf("%s() รับค่าที่มาจาก request: %s", sink, src)
		})...)
	return out
}
```

และตัวที่ทำให้มันจับของจริงได้คือ **fixpoint** — ทำซ้ำจนค่าไม่เปลี่ยน เพราะการไหลมักยาวกว่าหนึ่ง hop (หนึ่ง hop = หนึ่งทอดของการไหล) · ในลูปนั้น `trace` เป็นคนตัดสิน: มันตอบว่า expr ฝั่งขวาของ `=` นี้ "มาจาก source ไหม และผ่านเส้นทางไหน" (เช่น `fmt.Sprintf(...) → q`) ถ้าตอบว่าใช่ ชื่อตัวแปรฝั่งซ้ายก็ติด taint

```go
func buildTaint(fn *ast.FuncDecl, source func(ast.Expr) (string, bool)) map[string]string {
	tainted := map[string]string{}
	for changed := true; changed; {
		changed = false
		ast.Inspect(fn.Body, func(n ast.Node) bool {
			as, ok := n.(*ast.AssignStmt)
			if !ok || len(as.Lhs) != len(as.Rhs) {
				return true
			}
			for i, lhs := range as.Lhs {
				id, ok := lhs.(*ast.Ident)
				if !ok || id.Name == "_" {
					continue
				}
				if _, seen := tainted[id.Name]; seen {
					continue
				}
				// trace ตอบว่า expr นี้มาจาก source ไหม และผ่านเส้นทางไหน
				if s, hit := trace(as.Rhs[i], tainted, source); hit {
					tainted[id.Name] = s
					changed = true
				}
			}
			return true
		})
	}
	return tainted
}
```

ทำไมต้องวนซ้ำ: ในโค้ดตัวอย่าง การไหลเป็น `name` → `path` → `os.Open(path)` ซึ่งยาวสอง hop · ถ้าทำแค่ hop เดียว gate จะบอกว่า "สะอาด" ทั้งที่ของอันตรายไหลครบ · **หนึ่ง hop ไม่พอเสมอ** — และนี่คือเหตุผลว่าทำไม `grep` ไม่มีทางทำได้เลย

โค้ดที่ gate ต้องจับ — สองฟังก์ชันเต็ม ๆ จาก `samples/vulnerable/billing.go` (ตัดหัวไฟล์กับ import ออก แต่ไม่ได้ตัดกลางฟังก์ชัน คุณจึงอ่านเห็นเส้นทางการไหลจนจบ · **ห้ามใช้จริง**):

```go
// InvoiceByID — G1: ต่อ string เป็น SQL เอง
func InvoiceByID(db *sql.DB, id string) (*sql.Rows, error) {
	q := fmt.Sprintf("SELECT id, total FROM invoices WHERE id = '%s'", id)
	return db.Query(q)
}

// DownloadDoc — G5: ชื่อไฟล์มาจาก query string แล้วไหลถึง os.Open ตรง ๆ
// ส่ง ?name=../../../../etc/passwd มาก็อ่านไฟล์นอกโฟลเดอร์ได้
func DownloadDoc(w http.ResponseWriter, r *http.Request) {
	name := r.URL.Query().Get("name")
	path := filepath.Join("/srv/docs", name)
	f, err := os.Open(path)
	if err != nil {
		http.Error(w, "not found", http.StatusNotFound)
		return
	}
	defer f.Close()
	w.Header().Set("Content-Type", "application/octet-stream")
	_, _ = io.Copy(w, f)
}
```

![gate อ่านการไหลของข้อมูล ไม่ใช่คำที่พิมพ์](/assets/diagrams/ep18-03-taint-path.svg)

**ข้อจำกัดของ gate นี้ที่ผมต้องบอกคุณตรง ๆ** (เพราะเครื่องมือที่ไม่มีใครรู้ข้อจำกัดคือเครื่องมือที่อันตราย):

1. **ไม่ข้ามฟังก์ชัน** · ถ้า `name` ถูกส่งเข้า helper แล้ว helper เป็นคนเปิดไฟล์ gate จะไม่เห็น · SAST จริงทำ inter-procedural analysis (ไล่การไหลข้ามฟังก์ชันไปด้วย — แพงและซับซ้อนกว่ามาก)
2. **sanitizer เป็นการตัดสินของคนเขียน gate** · sanitizer (ฟังก์ชันที่ "ล้าง" ค่าอันตรายให้ปลอดภัย เช่น `filepath.Base`) คือสมมติฐานของคนเขียน gate: ผมถือว่า `filepath.Base` ทำให้ค่า "สะอาด" · ซึ่งจริงสำหรับ path traversal แต่ *ไม่จริง* สำหรับ XSS (Base ไม่ได้ escape HTML) · ทุก sanitizer ในเครื่องมือจริงคือสมมติฐานที่ต้องเขียนไว้และมีคน review
3. **G1 เป็น pattern rule ไม่ใช่ taint rule** · มันจับ "สตริงถูกประกอบในโค้ด" ซึ่งเป็นสาเหตุส่วนใหญ่ แต่ไม่ใช่ทั้งหมด (เช่น query ที่ประกอบมาจากที่อื่นแล้ว)
4. **ไม่มี data flow ข้ามไฟล์ ไม่มี type information** · และไม่รู้ว่า `db` เป็น `*sql.DB` จริงไหม — มันดูจากชื่อ method เท่านั้น

ทั้งสี่ข้อนี้คือเหตุผลที่ในงานจริงเราใช้ `staticcheck` (ตรวจ pattern หลายร้อยแบบ) และ `govulncheck` (ตรวจ dependency ที่มีช่องโหว่) แทนการเขียนเอง — **แต่การเขียนเองหนึ่งครั้งสอนอะไรที่การใช้เครื่องมือสำเร็จรูปไม่สอน** และเราจะไปต่อที่เครื่องมือจริงในตอนที่ 25

### 3.3 เดโม 3: pipeline ที่หยุดจริง ไม่ใช่แค่เตือน

gate ที่ exit 1 มีค่าก็ต่อเมื่อมีอะไรสนใจรหัสออกของมัน · นี่คือการรัน pipeline สามขั้นแบบ fail-fast (หยุดทันทีที่ stage แรกไม่ผ่าน ไม่รัน stage ที่เหลือให้เสียเวลา):

```
pipeline: 3 stage (build → gate → deploy) · หยุดทันทีเมื่อ stage ใดไม่ผ่าน

==============================================
run: commit A (โค้ดที่มีช่องโหว่)
  stage 1/3 build   → ok (go build exit 0)
  stage 2/3 gate    → FAIL (exit 1)
  stage 3/3 deploy  → skipped (ไม่รันเลย)
  ผล: โค้ดไม่ขึ้น production · ผู้เขียนแก้แล้ว push ใหม่

==============================================
run: commit B (โค้ดที่แก้แล้ว)
  stage 1/3 build   → ok (go build exit 0)
  stage 2/3 gate    → PASS (exit 0)
  stage 3/3 deploy  → deployed
  ผล: โค้ดขึ้น production
```

สองบรรทัดที่ผมอยากให้สังเกตคือ `stage 1/3 build → ok (go build exit 0)` ใน **ทั้งสองรอบ** · โค้ดที่มีช่องโหว่ทั้งห้าจุด *คอมไพล์ผ่าน* — และเดโมนี้ไม่มีไฟล์ `*_test.go` เลย (สคริปต์จึงไม่ได้รัน `go test`) · สิ่งที่ผลรันนี้พิสูจน์จึงเป็น "build เขียว" ไม่ใช่ "test เขียว" · นี่คือเหตุผลเชิงประจักษ์ว่าทำไม "build เขียว" ไม่ได้แปลว่าปลอดภัย — และทำไม gate ต้องเป็นด่านแยก ไม่ใช่ความหวังว่าทดสอบจะจับได้

### 3.4 ของจริงที่ควรใช้ และวิธีเอาเข้า team

เครื่องมือที่ผมจะใช้ในโปรเจกต์ Go จริง เรียงตามลำดับที่ควรใส่:

1. **`go vet`** — มากับ Go แล้ว ฟรี รันทุก commit ไม่มีข้ออ้าง
2. **`govulncheck`** — ตรวจว่ามีช่องโหว่ที่ *รู้แล้ว* ใน dependency หรือ standard library ที่โค้ดเราเรียกถึงจริง · เวอร์ชันล่าสุดที่ pkg.go.dev ระบุเมื่อ 27 ต.ค. 2026 คือ **v1.9.0** (เผยแพร่ 11 ต.ค. 2026) ติดตั้งด้วย `go install golang.org/x/vuln/cmd/govulncheck@latest` แล้วรัน `govulncheck ./...` — **ข้อกำหนด:** v1.9.0 ต้องใช้ **Go ≥ 1.26** (เครื่องที่ยังเป็น 1.24 ให้ปล่อย `GOTOOLCHAIN` ให้ Go ดาวน์โหลด toolchain ใหม่ หรืออัปเกรดก่อน) · เครื่องที่เขียนบทนี้ใช้ Go 1.24.4 ผมจึง **ไม่ได้รัน** govulncheck ในรอบนี้ — คำสั่งกับเลขเวอร์ชันข้างบนมาจากการอ่านหน้าเอกสาร ไม่ใช่ผลรัน (ตอนที่ 25 ลงลึก)
3. **`staticcheck`** — กฎตรวจที่กว้างกว่า vet มาก
4. **secret scanner** — กัน G2 ของเราก่อนที่ secret จะเข้า git history (ซึ่งลบยากมาก)
5. **DAST** — ยิงคำขอจริงใส่ staging (สภาพแวดล้อมจำลองที่เหมือน production แต่ยังไม่มีผู้ใช้จริง) เพื่อจับสิ่งที่ไม่ปรากฏในโค้ดเลย เช่น config ผิด

และสามหลักที่ทำให้ gate อยู่รอดในทีมจริง (ผมเคยเห็น gate ถูกปิดภายในสองสัปดาห์ เพราะละเมิดข้อแรก):

1. **เริ่มจาก blocking แค่ critical** · gate ที่ฟ้อง 500 ข้อในวันแรกจะถูกปิด · gate ที่ฟ้อง 3 ข้อที่ทุกคนเห็นด้วยว่าจะปิดงาน จะถูกแก้
2. **ทุก finding ต้องมีเจ้าของและ deadline** · finding ที่ไม่มีเจ้าของคือ finding ที่จะยังอยู่ตอนคุณออกจากงาน
3. **gate ต้องเร็ว** · ถ้าใช้เวลา 20 นาที คนจะข้ามมัน · 90 วินาทีคือเป้าที่ทำให้คน *รอผล*

## 4. โจทย์

### 4.1 Drill (ทำคนเดียว ใช้เวลาราวหนึ่งชั่วโมง)

**ข้อ 1 — หา "gate ที่มองไม่เห็น" ของโปรเจกต์ตัวเอง** · เลือกโปรเจกต์ที่คุณเขียนเอง แล้วตอบสามคำถามนี้เป็นลายลักษณ์อักษร: (ก) มีข้อบกพร่องประเภทไหนที่ *เกิดตอน design* (เช่น ไม่มี authorization model, ไม่มี rate limit ตั้งแต่ต้น) (ข) กระบวนการปัจจุบันของคุณมี gate ที่มองเห็นมันไหม (ค) ถ้าไม่มี ข้อบกพร่องนั้นไปโผล่ที่ขั้นไหน และใครจ่าย

**ข้อ 2 — เพิ่มกฎที่ 6 ให้ gate** · เปิด `cmd/gate/main.go` แล้วเพิ่มกฎหนึ่งข้อที่ *คุณ* คิดว่าสำคัญกับงานตัวเอง (เช่น `exec.Command` ที่รับค่าจาก request = CWE-78, หรือ `math/rand` ที่ใช้ทำ token = CWE-338) · ต้องผ่านเงื่อนไข: มี CWE + severity, จับได้บน `samples/vulnerable` และ **ไม่จับ** บน `samples/fixed` · ถ้าเพิ่มแล้ว fixed กลายเป็น FAIL ให้เขียนใน comment ว่าทำไม (นั่นคือ false positive — gate ฟ้องสิ่งที่จริง ๆ ไม่ผิด — และเป็นสิ่งที่คุณต้องตัดสินใจ ไม่ใช่ปิด gate หนี)

**ข้อ 3 — ทำไม `filepath.Base` ไม่ใช่ sanitizer สากล** · เขียนสองประโยคอธิบายว่าทำไม `filepath.Base` ทำให้ path traversal หมดไป แต่ไม่ทำให้ XSS หมดไป · แล้วยกตัวอย่าง sanitizer หนึ่งตัวที่ *ดูปลอดภัยแต่ไม่ปลอดภัย* (ใบ้: การ escape HTML หนึ่งรอบแต่แทรกใน attribute)

### 4.2 Mini-project: ออกแบบ Secure SDLC ของโปรเจกต์ตัวเอง

เป้าหมาย: เอกสารหนึ่งหน้า (ไม่เกิน 2 หน้า) ที่บอกว่าโปรเจกต์ของคุณจะทำอะไรในแต่ละขั้น และ **หลักฐาน** ที่จะได้จากแต่ละอย่าง

ข้อกำหนดที่ผมจะตรวจ:

1. **ตาราง 5 ขั้น** (design → code → test → deploy → monitor) แต่ละขั้นต้องมี: กิจกรรม, เครื่องมือ, หลักฐาน, และ **ชื่อคนที่รับผิดชอบ** (ตำแหน่งก็ได้)
2. **อย่างน้อยหนึ่งกิจกรรมต่อขั้นต้องเป็น gate จริง** ที่ exit ไม่เป็นศูนย์ได้ — ไม่ใช่ dashboard · ระบุว่ารันตอนไหน (pre-commit / CI / pre-deploy) และใช้เวลากี่วินาที
3. **ระบุ gate ที่คุณ *เลือกจะไม่ทำ* และเหตุผล** · ผมอยากเห็นอย่างน้อยหนึ่งข้อในหัวข้อนี้ เพราะ SDLC ที่ทำทุกอย่างคือ SDLC ที่ไม่มีใครทำ · เหตุผลที่รับได้ เช่น "ยังไม่มี production จึงยังไม่ทำ DAST" — เหตุผลที่ไม่รับคือ "ไม่มีเวลา"
4. **มีตัวชี้วัดหนึ่งตัวที่วัดได้จริง** เช่น "median time จาก finding ถึงปิด" หรือ "จำนวน commit ที่ gate block ต่อสัปดาห์" · ห้ามใช้ "จำนวนช่องโหว่ที่พบ" เป็นตัวชี้วัดเดียว เพราะมันบอกว่าคุณตรวจมากแค่ไหน ไม่ได้บอกว่าปลอดภัยขึ้นไหม
5. **เขียน 3 บรรทัดเรื่อง "ถ้าวันหนึ่งทีมโตเป็น 5 คน อะไรจะพังก่อน"** · คำถามนี้บังคับให้คุณคิดเรื่อง scaling ของ process ไม่ใช่แค่ของโค้ด

เกณฑ์ผ่านของผมคือข้อ 3 กับข้อ 4 · เพราะสองข้อนั้นแยก "เอกสารที่ดูครบ" ออกจาก "กระบวนการที่รันได้จริง"

## 5. สรุป

จบบทนี้ ผมอยากให้คุณถือสามประโยคไป:

**หนึ่ง — security เป็น process ไม่ใช่ event** · Equifax ไม่ได้ล้มเหลวเพราะไม่มีคนเก่ง · มันล้มเหลวเพราะไม่มีกระบวนการที่ทำให้ "แพตช์ที่มีอยู่แล้ว" ไปถึงเครื่องที่ควรได้ · ไม่มี scanner ตัวไหนแพตช์ให้คุณ และไม่มี pen-test ครั้งไหนรับประกันวันพรุ่งนี้

**สอง — gate ต้องตัดสินได้ ไม่ใช่แค่รายงาน** · เดโม 2 ของเราจับได้ 5 finding และ exit 1 · pipeline จึงหยุด · ถ้ามันพิมพ์แค่ "พบ 5 ปัญหา" แล้วปล่อยผ่าน คุณได้ dashboard ไม่ใช่ gate · และการมี dashboard ที่ไม่มีใครดูแยกว่าการไม่มี dashboard เพราะมันสร้างความเชื่อว่ามีคนดูอยู่

**สาม — ตัวเลขที่อ้างต้องผ่านการตรวจ** · 100 เท่าเป็นตัวเลขระดับข้อบกพร่อง · 2.79 เท่าเป็นตัวเลขระดับกระบวนการของเรา · ทั้งคู่จริง แต่นำไปใช้คนละที่ · การพูดตัวเลขให้ตรงคือวิธีที่ทำให้โครงการ security อยู่รอดถึงปีที่สอง

การบ้านของบทนี้คือ Drill ข้อ 1 · เพราะตอนหน้าเราจะขยับจาก *หลักการ* ไป *กรอบงานระดับองค์กร* — NIST CSF กับ ISO 27001 — และคุณจะเห็นว่าที่ที่คุณเพิ่งออกแบบเองใน mini-project มีชื่อเรียกอยู่ในมาตรฐานพวกนั้นแล้ว
