# Fail closed + secure by default: เมื่อตัวตรวจไม่รู้คำตอบ มันต้องปฏิเสธ (ตอนที่ 13)

ตอนที่แล้ว (least privilege + defense in depth) เราจบลงด้วยคำถามข้อหนึ่งที่ผมทิ้งค้างไว้: **"เมื่อตัวตรวจไม่รู้คำตอบ มันควรทำอะไร"**

คำถามนี้ฟังดูเป็นรายละเอียดการเขียนโค้ด แต่จริง ๆ มันคือจุดที่ระบบส่วนใหญ่พังโดยไม่มีใครเขียนบั๊ก · เพราะค่าเริ่มต้นของทุกภาษา คือ **"ไม่มีคำตอบ = ไม่มีข้อห้าม"** — ตัวแปรที่ยังไม่ตั้งค่าเป็นศูนย์, ฟิลด์ที่ไม่ได้กรอกเป็นค่าว่าง, ฟังก์ชันที่คืน error ก็ปล่อยให้ผู้เรียกตัดสินใจเอา · และเมื่อผู้เรียกคือคนที่กำลังรีบ deploy สิ่งที่เกิดขึ้นคือระบบเปิดประตู

บทนี้ตอบคำถามนั้นด้วยหลักคิดที่เหลือจาก paper เดียวกับตอนที่แล้ว · และผมต้องพูดให้ตรงก่อน ไม่งั้นเราจะเข้าใจที่มาผิด:

**paper ของ Saltzer และ Schroeder (1975) มีหลักออกแบบแปดข้อ** ไม่ใช่สี่ข้อ · ตอนที่ 12 เราเอาไปข้อหนึ่ง (least privilege) · บทนี้เอาไปอีกสามข้อ:

1. **fail-safe defaults** — "ตัดสินสิทธิ์จาก *การได้รับอนุญาต* ไม่ใช่จากการไม่มีข้อห้าม"
2. **complete mediation** — "ทุกการเข้าถึง ทุกวัตถุ ต้องถูกตรวจสิทธิ์"
3. **economy of mechanism** — "ออกแบบกลไกให้เล็กและเรียบง่ายที่สุด"

และคำว่า **fail closed** กับ **secure by default** ที่อยู่ในชื่อตอน ไม่ใช่คำใน paper · มันคือคำอุตสาหกรรมที่แยกหลักข้อแรกออกเป็นสองสถานการณ์ที่ต่างกัน:

- **fail closed** = พฤติกรรมเมื่อ *กลไกทำงานไม่ได้* (timeout, error, โปรเซสตาย)
- **secure by default** = พฤติกรรมเมื่อ *ไม่มีใครตั้งค่า* (ฟิลด์ว่าง, ค่า zero value, ผู้ดูแลลืม)

สองอันนี้เป็นหลักเดียวกันมองคนละมุม: **ค่าเริ่มต้นของระบบคือ "ปฏิเสธ" และการผ่อนปรนทุกครั้งต้องเป็นความตั้งใจที่ระบุได้** · บทนี้จึงมีสี่คำในชื่อ แต่เป็นสามหลัก โดยหลักแรกถูกแยกออกเป็นสองสถานการณ์

และเพราะหลักคิดในบทนี้เป็น "หลักคิด" ไม่ใช่ "ไลบรารี" เราจะวัดมันด้วยตัวเลขเหมือนเดิม · คุณจะเห็นว่าตัวตรวจที่ดูคล้ายกันให้ผลต่างกันที่ **5/5 กับ 0/5** · config แปดค่าที่ "ปล่อยว่าง" ให้ผลไม่ปลอดภัย **7 จาก 8** ค่าในแบบเก่า และ **0 จาก 8** ในแบบใหม่ · เส้นทางเข้าถึงข้อมูลเจ็ดเส้นทางที่มีตัวตรวจแค่ **1 จาก 7** เส้นทาง · และชุดกฎเจ็ดข้อที่มี **หนึ่งกฎที่ไม่เคยถูกใช้เลย**

## 1. fail closed: "ล้มแล้วต้องปิด ไม่ใช่ล้มแล้วเปิด"

### 1.1 คำว่า "ล้ม" ไม่ได้มีแบบเดียว

คนส่วนใหญ่คิดว่า fail closed หมายถึง "จัดการ error ให้ดี" · แต่ error เป็นแค่หนึ่งในห้าสภาวะที่ตัวตรวจ "ตอบไม่ได้" · และสี่ข้อที่เหลือคือที่มาของช่องโหว่ส่วนใหญ่ในงานจริง:

| สภาวะ | หน้าตาเป็นอย่างไร | ระบบมักทำอะไร |
|---|---|---|
| timeout | เรียกบริการตัดสินสิทธิ์แล้วไม่ตอบ | ปล่อยผ่านเพราะ "อย่าให้ผู้ใช้ติดขัด" |
| not_found | ไม่มีกฎสำหรับคำขอนี้ | ปล่อยผ่านเพราะ "ไม่ตรงข้อห้าม" |
| unknown value | ค่าใน config ที่ไม่รู้จัก (พิมพ์ผิด) | ตีความเป็นค่าที่ผ่อนปรนที่สุด |
| nil decision | ไม่มีการตัดสินใจเลย | ถือว่า "ไม่มีข้อห้าม" |
| process down | โปรเซสตาย | ปิดทั้งระบบ (นี่คือ fail closed แต่กลายเป็น outage) |

แถวสุดท้ายคือกับดักเชิงความคิด: **การ crash ไม่ใช่ fail closed** · มันคือ availability ที่หายไป · นิยามที่ใช้ได้จริงจึงต้องอยู่ที่ *การตัดสินใจ* ไม่ใช่ที่ *โปรเซส* — เมื่อไม่รู้คำตอบ ให้ปฏิเสธคำขอนั้น แล้วยังคงให้บริการส่วนที่รู้คำตอบได้

คำว่า "failing open" มีรหัสในบัญชีกลางด้วย: **CWE** (Common Weakness Enumeration — บัญชีกลางที่นักวิจัยใช้ตั้งชื่อ 'ความอ่อนแอของโค้ด' ให้อ้างถึงปัญหาเดียวกันได้) · รหัสของมันคือ **CWE-636, Not Failing Securely ("Failing Open")** · และค่าเริ่มต้นที่ไม่ปลอดภัยมีรหัสแยกอีกตัว: **CWE-1188, Initialization of a Resource with an Insecure Default** (การตั้งค่าทรัพยากรเริ่มต้นให้ไม่ปลอดภัย) · สองรหัสนี้คือสองครึ่งของหลัก fail-safe defaults ที่เรากำลังคุยกัน

### 1.2 ตัวตรวจสามแบบ ที่ต่างกันแค่บรรทัดเดียว

เดโมแรกจำลองบริการตัดสินสิทธิ์ (policy service) ที่ล่ม · คำขอมี 10 ตัว — ภัย 5 ตัว (ขอลบใบแจ้งหนี้, ขอคืนเงิน, ขอหมุนกุญแจ, ขอแก้ schema, ขออ่านในนามของ intern) และคำขอปกติ 5 ตัว · จากนั้นเทียบตัวตรวจสามแบบที่ต่างกันแค่สิ่งที่ทำเมื่อเจอ error:

```go
// guardFailOpen — error ใด ๆ = ปล่อยผ่าน
//
// นี่คือพฤติกรรมที่โค้ดส่วนใหญ่ทำโดยไม่ตั้งใจ และเป็นเหตุผลที่ระบบเล็ก
// กลายเป็นระบบที่ "ล่มแล้วเปิด" ซึ่ง attacker เรียนรู้ที่จะใช้
func guardFailOpen(a *authority, r request, m depMode, _ map[string]bool) bool {
	ok, err := a.decide(r.user, r.op, m)
	if err != nil {
		return true
	}
	return ok
}
```

```go
// guardFailClosed — error ใด ๆ = ปฏิเสธ
func guardFailClosed(a *authority, r request, m depMode, _ map[string]bool) bool {
	ok, err := a.decide(r.user, r.op, m)
	if err != nil {
		return false
	}
	return ok
}
```

```go
// guardClosedDegraded — ปฏิเสธเมื่อ error ยกเว้นคำขออ่านที่เคยได้อนุญาตแล้ว
//
// นี่คือ fail closed ที่ยอมลดความสามารถ (degraded) แบบแคบและประกาศได้:
// เฉพาะกริยาอ่าน เฉพาะคู่ (ผู้ใช้, กริยา) ที่เคยได้ "อนุญาต" จากคำตอบจริง
// ไม่ใช่ "ทุกอย่างที่ cache ไว้" และไม่ใช่ "ทุกคำขอ"
//
// ไม่ thread-safe — เดโมรัน goroutine เดียว; production ต้องมี mutex หรือ sync.Map
func guardClosedDegraded(a *authority, r request, m depMode, cache map[string]bool) bool {
	ok, err := a.decide(r.user, r.op, m)
	if err != nil {
		prev, seen := cache[r.user+"|"+r.op]
		return seen && prev && readOnly(r.op)
	}
	cache[r.user+"|"+r.op] = ok
	return ok
}
```

ผลรันจริง:

```
# 1) บริการตัดสินสิทธิ์ล่ม — ตัวตรวจสามแบบตัดสินอย่างไร
# คำขอ 10 ตัว (ภัย 5 · ปกติ 5) · บริการภายนอก timeout ทุกครั้ง

guard            hostile_allowed  legit_allowed  hostile_blocked  legit_blocked
fail_open        5/5              5/5            0/5              0/5          
fail_closed      0/5              0/5            5/5              5/5          
closed_degraded  0/5              5/5            5/5              0/5          
tradeoff=fail_open เปิดช่องให้ภัยทุกตัว · fail_closed ปิดทุกอย่างรวมถึงงานที่ต้องทำ
```

อ่านสามแถวนี้ให้ครบ:

- **`fail_open`** — ภัยผ่าน **5 จาก 5** และงานผ่าน **5 จาก 5** · ตัวเลขสวยทั้งคู่ และนี่คือเหตุผลที่มันถูกเลือกโดยไม่มีการตัดสินใจ: ไม่มีอะไรพังให้เห็น
- **`fail_closed`** — ภัยผ่าน **0 จาก 5** แต่ *งานก็ผ่าน 0 จาก 5* · ปลอดภัยสมบูรณ์และใช้งานไม่ได้เลย
- **`closed_degraded`** — ภัยผ่าน **0 จาก 5**, งานผ่าน **5 จาก 5** · ทางเลือกที่ผมอยากให้คุณสังเกตคือ **มันไม่ใช่ "cache ทุกอย่างแล้วปล่อยผ่าน"** · มันยอมแค่คู่ (ผู้ใช้, กริยา) ที่เคยได้คำตอบว่า *อนุญาต* จากคำตอบจริง และเฉพาะกริยาอ่าน

สามบรรทัดที่สำคัญในฟังก์ชันนี้: `seen && prev && readOnly(r.op)` · `seen` = เคยเห็นคำขอนี้ · `prev` = คำตอบครั้งก่อนคือ *อนุญาต* (ไม่ใช่ "ปฏิเสธ" ที่ cache ไว้) · `readOnly` = ความเสียหายจำกัดอยู่ที่การอ่าน · ถ้าตัดเงื่อนไขใดออกหนึ่งข้อ มันจะกลายเป็น fail open ที่ดูเหมือน fail closed — และนี่คือความต่างระหว่าง "ยอมลดความสามารถ" กับ "ยอมให้ทุกอย่าง" · แต่ cache นี้ใน production ต้องมีอายุจำกัดหรือถูก invalidate เมื่อสิทธิ์เปลี่ยน — ไม่งั้นมันกลายเป็นปัญหาเดียวกับที่เราจะเจอใน §3.3

### 1.3 สภาวะที่ตอบไม่ได้ ห้าแบบ

ตารางนี้คือรายการที่คุณควรเอาไปไล่กับระบบของคุณทีละแถว · สังเกตว่าแถวสุดท้ายให้คำตอบ "down" ทั้งสองคอลัมน์ ไม่ใช่ "deny":

```
# สภาวะที่ตัวตรวจตอบไม่ได้ — ห้าแบบ และสิ่งที่แต่ละแบบทำ
mode           looks_like                     fail_open   fail_closed
timeout        error จากปลายทาง               allow       deny       
not_found      ไม่มีกฎสำหรับคำขอนี้           allow       deny       
unknown_value  ค่าใน config ที่ไม่รู้จัก      allow       deny       
nil_decision   ไม่มีการตัดสินใจ (typed nil)   allow       deny       
process_down   โปรเซสตาย                      down        down       
```

หลักที่ใช้ตัดสินทั้งห้าแถวคือคำถามเดียว: **"ถ้าตัวตรวจนี้ตอบไม่ได้ ใครได้ประโยชน์"** · ถ้าคำตอบคือผู้โจมตี แปลว่าคุณกำลัง fail open · ถ้าคำตอบคือ "ไม่มีใครเลย แต่ระบบหยุด" คุณ fail closed แบบแรงเกินจำเป็น · และถ้าคำตอบคือ "ผู้ใช้ที่ขอข้อมูลของตัวเองเมื่อวาน" คุณกำลังทำสิ่งที่ถูก

### 1.4 กับดักภาษา: typed nil ทำให้ fail closed กลายเป็น fail open

นี่คือกับดักที่ผมเจอบ่อยที่สุดในโค้ด Go และมันน่ากลัวเพราะ **โค้ดดูถูกทุกบรรทัด**:

```go
// lookupTypedNil จำลองฟังก์ชันที่ "ไม่มีข้อผิดพลาด" แต่คืน pointer ที่เป็น nil
// ผ่านตัวแปร interface · err != nil จึงเป็นจริงทั้งที่ไม่มีอะไรผิดพลาด
func lookupTypedNil() (bool, error) {
	var e *denyError
	return false, e
}
```

```go
// guardNaive คือตัวตรวจที่ "ถ้ามี error ก็ปล่อยผ่าน" — fail open รูปแบบที่พบบ่อยที่สุด
func guardNaive(allowed bool, err error) bool {
	if err != nil {
		return true
	}
	return allowed
}
```

ผลรันจริง:

```
# 2) typed nil — กับดักที่ทำให้ "fail closed" กลายเป็น fail open

var e *denyError = nil   // ผู้เขียนตั้งใจให้เป็น nil
err := error(e)          // ห่อ nil pointer เข้า interface
err == nil                          -> false
allowed (ค่าที่อ่านได้จริง)          -> false
guard ที่ fail open เมื่อ err != nil  -> true
```

อ่านสามบรรทัดสุดท้ายให้ช้า ๆ:

- `err == nil` ให้ค่า **false** ทั้งที่ไม่มีอะไรผิดพลาดเลย · เพราะตัวแปรชนิด `error` เป็น interface ซึ่งเก็บคู่ (ชนิด, ค่า) · พอชนิดคือ `*denyError` ค่าข้างในจึงไม่ nil แม้ตัวชี้ข้างในจะเป็น nil — interface ที่ห่อ typed nil จึง **ไม่ใช่ nil**
- `allowed` ให้ค่า **false** — คำตอบจริงคือ "ไม่อนุญาต"
- แต่ guard ที่ fail open เมื่อ `err != nil` ให้ค่า **true** — คือ **อนุญาต**

และมันจะแย่กว่านี้อีกหนึ่งชั้นเมื่อตัวตรวจเป็น method บน pointer (pointer = ค่าที่เก็บ *ที่อยู่* ของข้อมูล ไม่ใช่ตัวข้อมูล · ตัวรับที่ method เรียกผ่านเรียกว่า receiver):

```go
// Allow ตอบว่า "ไม่มีคำตอบ" ควรหมายถึงอะไร
//
// บรรทัดนี้คือช่องโหว่ทั้งดุ้น: โค้ดที่กัน nil ได้แล้ว แต่เลือกให้ nil = อนุญาต
func (d *decision) Allow() bool {
	if d == nil {
		return true
	}
	return d.allow
}
```

ผลรันจริงของส่วนนี้:

```
# 3) nil receiver — โค้ดที่ "กัน nil" แล้วแต่ให้ nil = อนุญาต

d == nil                        -> true
d.Allow()  (nil receiver)       -> true
allowed_when_no_decision        -> true
```

`d == nil` เป็นจริง และ `d.Allow()` ก็คืน **true** · คือโค้ดที่ "กัน nil แล้ว" แต่เลือกให้ nil = อนุญาต · ทั้งสองเคสนี้รวมกันเป็นเหตุผลที่ผมบอกนักศึกษาว่า **"nil คือค่าเริ่มต้นที่อันตรายที่สุดใน Go"** — ไม่ใช่เพราะ nil เอง แต่เพราะทุกคนตีความ nil ว่า "ไม่เป็นไร"

วิธีป้องกันที่ใช้ได้จริงมีสามข้อ:

1. **ประกาศให้ชัดว่า "ไม่มีคำตอบ" หมายถึงอะไร** และให้มันหมายถึงปฏิเสธ · เขียนเป็นค่าคงที่ตัวเดียว เช่น `DenyByDefault` ไม่ใช่ปล่อยให้แต่ละที่ตัดสินเอง
2. **อย่าคืน pointer เป็น error** — คืน `error` ที่เป็น nil จริง (`return nil`) หรือใช้ sentinel error (ค่าคงที่ error ที่ประกาศไว้ตัวเดียว ใช้เทียบว่าเป็นความผิดชนิดเดียวกันด้วย `errors.Is`)
3. **ทดสอบเส้นทางที่ล้ม** — เขียนเทสต์ที่บังคับให้ dependency คืน error, timeout และค่าว่าง แล้ว assert ว่า *ผลลัพธ์คือปฏิเสธ* · ถ้าไม่มีเทสต์นี้ คุณจะมี fail closed ในโค้ดและ fail open ใน production

## 2. secure by default: ค่าเริ่มต้นคือสัญญาที่ผู้ใช้ไม่เคยอ่าน

### 2.1 "ค่าเริ่มต้น" ไม่ใช่รายละเอียด — มันคือผลิตภัณฑ์

เมื่อมีคนติดตั้งซอฟต์แวร์ของคุณ พวกเขาจะรันมันด้วยค่าเริ่มต้น · และเมื่อมีคนลืมเขียนค่าใน config ระบบจะใช้ค่า zero value · ใน Go นั่นหมายถึง `""`, `0`, `false`, `nil` · คำถามเดียวที่ต้องตอบคือ: **ค่าเหล่านี้ปลอดภัยหรือยัง**

หลักจาก paper พูดไว้สั้น ๆ ว่า *"base access decisions on permission rather than exclusion"* — ตัดสินจากการได้รับอนุญาต ไม่ใช่จากการไม่มีข้อห้าม · ในทางปฏิบัติมันแปลว่า: **ทุกอย่างที่ไม่ได้ระบุ = ปิด**

และเรามีหลักฐานจากที่ที่คาดไม่ถึง: ไลบรารีมาตรฐานของ Go เองก็ต้องเลือกค่าเริ่มต้น และเอกสารของมันบอกตรง ๆ ว่าค่าเริ่มต้นคือ "ข้อตกลงที่เปลี่ยนได้":

```
package tls // import "crypto/tls"

type Config struct {
    // MinVersion contains the minimum TLS version that is acceptable.
    // 
    // By default, TLS 1.2 is currently used as the minimum. TLS 1.0 is the minimum
    // supported by this package.
    // 
    // The server-side default can be reverted to TLS 1.0 by including the value
    // "tls10server=1" in the GODEBUG environment variable.
    MinVersion uint16
```

ข้อความนี้ตัดมาเฉพาะฟิลด์ที่เกี่ยวข้อง · บรรทัดที่ควรอ่าน: **ค่าเริ่มต้นคือ TLS 1.2** · แต่ TLS 1.0 ยังเป็นเวอร์ชันต่ำสุดที่แพ็กเกจรองรับ

และค่าเริ่มต้นฝั่ง server "ย้อนกลับไปที่ TLS 1.0 ได้" ผ่านตัวแปรสภาพแวดล้อม `GODEBUG` — GODEBUG `tls10server` ถูกถอดออกถาวรใน Go 1.27 (go.dev/doc/godebug) เอกสารออนไลน์วันนี้จึงไม่มีบรรทัดนี้แล้ว

นี่ไม่ใช่บั๊ก — มันคือการประนีประนอมที่เอกสารไว้ครบ · แต่สำหรับคุณมันหมายความว่า **"ปลอดภัยโดยค่าเริ่มต้น" ของปีนี้ อาจไม่ใช่ของอีกสามปีข้างหน้า** · เพราะฉะนั้นค่าที่สำคัญต่อความปลอดภัยต้อง **ระบุเอง ไม่ใช่พึ่งค่าเริ่มต้น**

### 2.2 แปดค่า ที่ zero value ตัดสินความปลอดภัย

เดโมที่สองมีค่าตั้งค่า 8 ค่า และตีความ config สองแบบ:

```go
// config คือค่าที่ผู้ดูแลเขียนในไฟล์ config
//
// ฟิลด์ที่เป็น pointer ใช้เพื่อแยก "ผู้ดูแลไม่ได้เขียนค่านี้" ออกจาก
// "เขียนว่า false" — ใน Go ค่า zero value แยกสองกรณีนี้ออกไม่ได้
// และการแยกไม่ได้คือต้นตอของค่าเริ่มต้นที่ไม่ปลอดภัย
type config struct {
	authMode          string
	allowedHosts      []string
	tlsMinVersion     string
	cookieSecure      *bool
	debugRoutes       *bool
	rateLimitRPS      int
	dbRequireTLS      *bool
	adminLoopbackOnly *bool
	allowInsecure     bool
}

// settings คือค่าที่ระบบใช้จริงหลังตีความ config แล้ว
type settings struct {
	authRequired  bool
	hostAllowlist []string
	tlsMin        string
	cookieSecure  bool
	debugRoutes   bool
	rateLimitRPS  int
	dbRequireTLS  bool
	adminLoopback bool
}

func boolp(v bool) *bool { return &v }
```

จุดที่ควรสังเกตในโครงสร้างนี้: ฟิลด์ boolean เป็น `*bool` ไม่ใช่ `bool` · เพราะถ้าเป็น `bool` ธรรมดา ระบบจะแยกไม่ออกว่า `false` แปลว่า "ผู้ดูแลสั่งปิด" หรือ "ไม่มีใครเขียนอะไรเลย" · และการแยกไม่ออกนี่เองที่ทำให้ระบบต้องเดา — และมันเดาผิดข้างเสมอ

ตารางที่ระบบต้องตอบให้ครบทั้งแปดค่า (ค่าเดียวกัน สองการตีความ):

```
# 1) ค่า zero value ของ config — แปดค่า และความหมายที่ต่างกัน
field                  zero_value   legacy_means                 secure_means                  
auth_mode              ""           ไม่ตรวจสิทธิ์                บังคับตรวจ (on)               
allowed_hosts          nil          รับทุก Host                  ต้องระบุ ไม่งั้นไม่สตาร์ต     
tls_min_version        ""           TLS 1.0                      TLS 1.2                       
cookie_secure          nil          ไม่ใส่ Secure flag           ใส่ Secure เสมอ               
debug_routes           nil          ปิด (บังเอิญปลอดภัย)         ปิด                           
rate_limit_rps         0            ไม่จำกัด                     60                            
db_require_tls         nil          ต่อ DB แบบ plaintext         บังคับ TLS                    
admin_loopback_only    nil          เปิดจาก IP ไหนก็ได้          loopback เท่านั้น             
```

การนับว่า "ไม่ปลอดภัยกี่ค่า" เขียนตรง ๆ ทั้งแปดค่า ไม่มีค่าใดถูกมองข้าม:

```go
// insecureCount นับว่ามีกี่ค่าที่ "ไม่ปลอดภัย" ภายใต้ settings นี้
// ทั้งแปดค่าถูกตรวจแยกกัน ไม่มีค่าใดถูกมองข้าม
func insecureCount(s settings) int {
	n := 0
	if !s.authRequired {
		n++
	}
	if len(s.hostAllowlist) == 0 {
		n++
	}
	if s.tlsMin == "1.0" {
		n++
	}
	if !s.cookieSecure {
		n++
	}
	if s.debugRoutes {
		n++
	}
	if s.rateLimitRPS == 0 {
		n++
	}
	if !s.dbRequireTLS {
		n++
	}
	if !s.adminLoopback {
		n++
	}
	return n
}
```

ส่วนตัวตีความแบบใหม่ บังคับให้การผ่อนปรนทุกครั้งต้องประกาศ (บล็อกต่อไปนี้ตัดมาเฉพาะส่วนแรกของฟังก์ชัน):

```go
// resolveSecure ตีความ config แบบ "ค่าที่ไม่ได้เขียน = ค่าที่ปลอดภัยที่สุด"
// และปฏิเสธการสตาร์ตถ้าขาดค่าที่เดาไม่ได้ · การผ่อนปรนทุกครั้งต้องเขียนชัดเจน
func resolveSecure(c config) (settings, []string, error) {
	s := settings{
		authRequired:  true,
		tlsMin:        "1.2",
		cookieSecure:  true,
		rateLimitRPS:  60,
		dbRequireTLS:  true,
		adminLoopback: true,
	}
	var warnings []string

	switch c.authMode {
	case "", "on":
		// ค่าเริ่มต้นคือตรวจสิทธิ์ — ไม่ต้องเขียนอะไรเลยก็ปลอดภัย
	case "off":
		if !c.allowInsecure {
			return s, warnings, fmt.Errorf("auth_mode=off ต้องระบุ allow_insecure=true อย่างชัดเจน")
		}
		s.authRequired = false
		warnings = append(warnings, "auth_mode=off ได้รับการอนุญาตโดยชัดเจน (ต้องถูกบันทึกใน audit)")
	default:
		return s, warnings, fmt.Errorf("auth_mode=%q ไม่รู้จัก (อนุญาตเฉพาะ on, off)", c.authMode)
	}

	// allowed_hosts เดาไม่ได้จริง ๆ: ถ้าไม่มีรายการ ระบบไม่รู้ว่าตัวเองชื่ออะไร
	if len(c.allowedHosts) == 0 {
		return s, warnings, fmt.Errorf("ขาด allowed_hosts — ไม่มีค่าที่ปลอดภัยให้เดา")
	}
	s.hostAllowlist = c.allowedHosts
```

สองบรรทัดที่สำคัญในฟังก์ชันนี้: `auth_mode=off` ต้องมาพร้อม `allow_insecure=true` และถ้า `allowed_hosts` ว่าง ระบบ **ไม่ยอมสตาร์ต** · เพราะไม่มีค่าที่ปลอดภัยให้เดา — เซิร์ฟเวอร์ที่ไม่รู้ว่าตัวเองชื่ออะไรไม่ควรเดาว่า "ชื่ออะไรก็ได้"

ผลรันจริง:

```
# 2) เมื่อผู้ดูแลลืมเขียนค่า — config ว่าง เทียบกับเขียนบางส่วน
profile  config    startup   insecure_settings  hostile_ok  legit_ok  settings_to_write 
legacy   empty     serve     7/8                7/8         5/5       8                 
legacy   partial   serve     3/8                3/8         5/5       8                 
secure   empty     refused   0/8                -           -         1                 
secure   partial   serve     0/8                0/8         5/5       1                 
startup_refused_reason=ขาด allowed_hosts — ไม่มีค่าที่ปลอดภัยให้เดา
settings_total=8  legit_requests=5  hostile_requests=8
note=legacy ต้องเขียนครบ 8 ค่าให้ถูกจึงจะปลอดภัย · secure เขียน 1 ค่า ที่เหลือปลอดภัยโดยตัวมันเอง
```

อ่านสี่แถวนี้ให้ครบทั้งสองด้าน:

- **`legacy` + config ว่าง** — ค่าไม่ปลอดภัย **7 จาก 8** (ค่าเดียวที่ปลอดภัยคือ `debug_routes` ที่ zero value เป็น `false` — บังเอิญ) · ภัยผ่าน **7 จาก 8** · งานผ่าน 5 จาก 5 · และถ้าอยากปลอดภัยจริงต้องเขียนเอง **8 ค่า**
- **`legacy` + เขียน 5 ค่า** — เหลือช่อง **3 จาก 8** · นี่คือสภาพปกติของระบบที่ "ตั้งค่าไว้บ้างแล้ว" และเป็นเหตุผลที่การตรวจ config แบบรายการยาวไม่ work: ไม่มีใครเขียนครบ
- **`secure` + config ว่าง** — ค่าไม่ปลอดภัย **0 จาก 8** แต่ระบบ **ปฏิเสธการสตาร์ต** พร้อมเหตุผลว่า `ขาด allowed_hosts — ไม่มีค่าที่ปลอดภัยให้เดา` · ตัวเลข 0/8 ในแถวนี้ยังไม่มีความหมาย เพราะระบบไม่ได้ทำงาน — และนั่นคือประเด็น: **เซอร์วิสที่ไม่สามารถตอบสนองข้อกำหนดความปลอดภัยของตัวเองได้ ต้องไม่สตาร์ต** · ปลอดภัยกว่าเยอะเมื่อเทียบกับเซอร์วิสที่รันอยู่และ insecure
- **`secure` + เขียน 1 ค่า** — ค่าไม่ปลอดภัย **0 จาก 8**, ภัยผ่าน **0 จาก 8**, งานผ่าน 5 จาก 5 · เขียนแค่ `allowed_hosts` ที่เหลือปลอดภัยโดยตัวมันเอง

ตัวเลขคู่ที่ผมอยากให้จำคือ **8 กับ 1** · ในแบบเก่า ผู้ดูแลต้องจำค่าแปดค่าและเขียนให้ถูกทุกค่า · ในแบบใหม่ ต้องเขียนหนึ่งค่า และค่าเริ่มต้นจัดการที่เหลือ · นี่คือความต่างระหว่าง "ความปลอดภัยที่พึ่งความจำของคน" กับ "ความปลอดภัยที่พึ่งโครงสร้าง"

### 2.3 ค่าที่พิมพ์ผิด: ระบบควรเดาหรือปฏิเสธ

ส่วนที่สามของเดโมทดสอบค่าที่ไม่รู้จัก — ซึ่งในงานจริงหมายถึงคำที่พิมพ์ผิด:

```
# 3) ค่าที่พิมพ์ผิดหรือไม่รู้จัก — ระบบควรเดาหรือปฏิเสธ
value    legacy_auth  legacy_silent    secure_auth  secure_error              
"off"    off          yes              error        must_set_allow_insecure   
"of"     off          yes              error        unknown_value             
""       off          yes              on           none                      
silent_disable  legacy=3/3  secure=0/3
```

บรรทัดสุดท้ายคือตัวเลขที่ผมอยากให้จำ: `silent_disable  legacy=3/3  secure=0/3` · ในแบบเก่า ค่าทั้งสาม (`off`, `of` ที่พิมพ์ผิด, และค่าว่าง) ปิดการตรวจสิทธิ์ **เงียบ ๆ ทั้งสามกรณี** · ในแบบใหม่ ไม่มีกรณีใดปิดได้โดยไม่ประกาศ

เหตุผลที่ `of` สำคัญกว่าที่คิด: มันคือความผิดพลาดของคนที่ระบบควรจับได้ · ระบบที่ตอบ `of` ว่า "โอเค ปิดการตรวจสิทธิ์" ไม่ได้กำลังเชื่อใจผู้ดูแล — มันกำลังเดาแทนเขา · และการเดาแทนคนที่พิมพ์ผิดคือการเดาเข้าข้าง "ปิด"

### 2.4 เคสจริง: MongoDB ที่ไม่บังคับ authentication (2017)

วันที่ 7 มกราคม 2017 มีรายงานว่าเครื่อง MongoDB ราวหนึ่งหมื่นห้าร้อยเครื่องถูกสคริปต์เรียกค่าไถ่ลบฐานข้อมูลทิ้ง แล้วเขียนข้อความเรียกค่าไถ่ไว้แทน · ภายในสองวัน ตัวเลขนั้นขึ้นไปถึงราวสองหมื่นแปดพันเครื่อง — ไม่ใช่เพราะสคริปต์เก่งขึ้น แต่เพราะมีเครื่องที่เปิดให้เข้าถึงจากอินเทอร์เน็ตมากกว่าที่ใครคิด: Shodan เห็นเครื่องลักษณะนี้ราวสามหมื่นเครื่องตั้งแต่กลางปี 2015

ต้นตออยู่ในบรรทัดเดียวกับที่บทนี้พูดมาทั้งบท: **ค่าเริ่มต้นคือผลิตภัณฑ์** · แต่ต้องแยกให้ชัดสองเรื่อง เพราะข่าวมักเล่าสองเรื่องนี้ปนกัน · เรื่องแรก **MongoDB ไม่บังคับ authentication โดยค่าเริ่มต้น** — จริงตลอดมาถึงรุ่น 3.x · ใครที่ติดตั้งแล้วยังไม่ได้สร้างผู้ใช้และเปิด `--auth` ฐานข้อมูลก็เปิดให้ทุกคนที่ต่อถึงอ่านและเขียนได้ โดยไม่รู้ตัว · เรื่องที่สอง **การฟังพอร์ต 27017 บนทุก interface** ซึ่งเป็นค่าเริ่มต้นเฉพาะ 2.4.x และเก่ากว่า — ตั้งแต่ 2.6 (2014) แพ็กเกจ .deb/.rpm ตั้ง `bind_ip=127.0.0.1` ให้แล้ว และ 2.4.14 (เมษายน 2015) เป็นรุ่นสุดท้ายของสาย 2.4

เครื่องราวสามหมื่นเครื่องที่ Shodan เห็นในปี 2015 จึงไม่ใช่ผลของค่าเริ่มต้นของรุ่นที่เพิ่งออก แต่เป็น **ของเก่าที่ยังไม่ถูกอัปเกรด** — Shodan รายงานว่าในผลค้นชุดหนึ่งถึง 40% รันรุ่น 1.8.1 ซึ่งเก่ากว่า 2.6 หลายปี — บวกกับคนที่ถอด `bind_ip` ออกเองเพื่อให้เครื่องอื่นในเน็ตเวิร์กเดียวกันต่อได้

และคนที่จ่ายให้ค่าเริ่มต้นที่ผิดของรุ่นเก่า ก็คือคนที่รับช่วงระบบต่อในปี 2017 — ไม่มีใครในนั้นเป็นคนเลือกค่านั้น · บทเรียนคือ: **"ผู้ดูแลต้องไปเปิด authentication เอง" ไม่ใช่ค่าเริ่มต้น — มันคือภาระที่ถูกผลักไปให้คนที่เหนื่อยที่สุด ในวันที่ยุ่งที่สุด** · และค่าเริ่มต้นที่ผิดจะถูกวัดด้วยจำนวนเครื่องที่หายไป ไม่ใช่ด้วยจำนวนคนที่อ่านเอกสาร

## 3. complete mediation: ทุกการเข้าถึง ทุกวัตถุ ทุกครั้ง

### 3.1 ประโยคเดียวที่บรรจุทุกอย่างไว้

หลักข้อนี้ใน paper เขียนสั้นที่สุดในบรรดาแปดข้อ: **"Every access to every object must be checked for authority."** · ทุกการเข้าถึง · ทุกวัตถุ · ตรวจกับสิทธิ์ · แต่ละคำมีความหมายที่คนมักข้าม:

- **ทุกการเข้าถึง** — ไม่ใช่แค่คำขอแรก · ไม่ใช่แค่คำขอที่มาจาก HTTP · ทุกครั้งที่ข้อมูลถูกอ่าน
- **ทุกวัตถุ** — ไม่ใช่แค่ route · ต้องตรวจว่าออบเจกต์ชิ้นนั้นเป็นของใคร
- **สิทธิ์** — สิทธิ์ *ปัจจุบัน* ไม่ใช่สิทธิ์ตอนที่ผู้ใช้ล็อกอินเมื่อเช้า

คำที่สามคือคำที่ทำให้ระบบส่วนใหญ่ตกม้าตาย เพราะมันขัดกับ optimization ที่ทุกคนต้องการ: cache

### 3.2 เจ็ดเส้นทาง กับตัวตรวจที่อยู่ผิดที่

เดโมที่สามไล่เส้นทางที่ไปถึงข้อมูล `invoices` ได้จริงในระบบหนึ่ง ๆ · มีเจ็ดเส้นทาง และทั้งเจ็ดอ่านตารางเดียวกัน:

```go
// guardMemo คือตัวตรวจที่จำคำตอบไว้ · ttl=0 แปลว่าไม่หมดอายุ
func guardMemo(st *store, cache map[string]memo, ttl, now int) bool {
	if m, ok := cache["clerk"]; ok {
		if ttl == 0 || now < m.expiry {
			return m.val
		}
	}
	// "clerk" คือผู้ใช้คนเดียวที่เดโมเฝ้าอยู่ — ในระบบจริงค่านี้มาจากคำขอที่เข้ามา
	v := st.allows("clerk")
	cache["clerk"] = memo{val: v, expiry: now + ttl}
	return v
}
```

ผลรันจริงของตารางเส้นทาง:

```
# 1) เส้นทางเข้าถึง invoices เจ็ดเส้นทาง — ตรวจครบหรือไม่
path           design_A       design_B       design_C      
http_get       yes            yes            yes           
http_export    no             yes            yes           
batch_job      no             yes            yes           
admin_cli      no             yes            yes           
internal_api   no             yes            yes           
cache_hit      no             no             yes           
retry_queue    no             yes            yes           
mediated  1/7  6/7  7/7
design_A=ตรวจที่ HTTP handler · design_B=คัดลอกการตรวจไปทุกเส้นทาง · design_C=ตรวจที่จุดเดียวใต้ cache
```

สามดีไซน์ในตาราง:

- **A: ตรวจที่ HTTP handler** (ฟังก์ชันที่รับคำขอ HTTP เข้ามาทีละคำขอ) — ถูกตรวจ **1 จาก 7** · เส้นทางที่เหลือ (export แบบ bulk, batch job, CLI ของแอดมิน, API ภายใน, cache, retry queue) ไปถึงข้อมูลได้โดยไม่ผ่านตัวตรวจเลย
- **B: คัดลอกการตรวจไปทุกเส้นทาง** — ถูกตรวจ **6 จาก 7** · ดีขึ้นมาก แต่มีหนึ่งเส้นทางที่หลุด: `cache_hit` เพราะคำตอบถูกส่งจาก cache **ก่อน** ถึงบรรทัดที่ตรวจ · และนี่คือธรรมชาติของ design B: การตรวจที่ถูกคัดลอกไว้เจ็ดที่ คือการตรวจที่ถูกทำซ้ำเจ็ดครั้งแล้วจะเพี้ยนจากกัน (มีคนแก้หกที่และลืมหนึ่งที่เสมอ)
- **C: ตรวจที่จุดเดียว ใต้ cache** — ถูกตรวจ **7 จาก 7** · เพราะทุกเส้นทางต้องผ่าน repository layer และ cache อยู่ *ใต้* ตัวตรวจ ไม่ใช่ *เหนือ* มัน

ประโยคที่ผมอยากให้ติดไปใช้: **"ย้าย cache ลงไปใต้ตัวตรวจ ดีกว่าเอาการตรวจไปไว้เหนือ cache"** · ที่หนึ่งคือการออกแบบ อีกที่คือการหวังว่าทุกคนจะจำ

### 3.3 ถอนสิทธิ์แล้ว: คำขอกี่ยังผ่าน

หัวใจของ complete mediation ไม่ใช่ "มีการตรวจ" แต่คือ "การตรวจเห็นสิทธิ์ปัจจุบัน" · เราวัดด้วยสถานการณ์ตรงไปตรงมา: ผู้ใช้ถูกล็อกอินอยู่ มีสิทธิ์อ่าน แล้วผู้ดูแลถอนสิทธิ์ที่เวลา t=0 · จากนั้นมีคำขออีก 12 ตัว (สมมติห่างกันวินาทีละหนึ่งคำขอ) · ถามว่า **มีกี่คำขอที่ยังผ่าน**

```
# 2) ถอนสิทธิ์ที่ t=0 แล้ววัดคำขอถัดไป 12 ตัว (ห่างกัน 1 วินาที)
guard                    allowed_after_revoke   staleness           
memo_no_ttl              12/12                  unbounded           
memo_ttl_60s             12/12                  60s                 
memo_with_invalidation   4/12                   until_missed_call   
per_request              0/12                   0                   
requests=12  seconds_per_request=1
```

ตัวเลขสี่ค่านี้เล่าเรื่องทั้งบท:

- `memo_no_ttl` — ผ่าน **12 จาก 12** · cache ไม่มีวันหมดอายุ = การถอนสิทธิ์ไม่มีผลเลย
- `memo_ttl_60s` — ผ่าน **12 จาก 12** · เพราะทั้ง 12 คำขออยู่ในหน้าต่าง 60 วินาที · TTL (time to live — อายุของค่าที่เก็บใน cache) ทำให้ *หน้าต่างของความเสียหาย* มีขอบเขต แต่ไม่ได้ทำให้มันหายไป
- `memo_with_invalidation` — ผ่าน **4 จาก 12** · ดีขึ้น เพราะมีการเรียก `invalidate` เมื่อสิทธิ์เปลี่ยน — แต่มีจุดเรียกหนึ่งที่ลืม · สี่คำขอที่ผ่านคือคำขอที่วิ่งผ่าน *จุดที่ลืมเรียก* invalidate จึงยังอ่านค่าเก่าจาก cache
- `per_request` — ผ่าน **0 จาก 12** · ตรวจทุกครั้งจากแหล่งความจริง

และนี่คือความจริงที่เจ็บปวดของการออกแบบ: **cache ที่ใส่เข้าไปเพื่อ performance คือกลไกที่เปลี่ยน complete mediation ให้เป็น incomplete mediation โดยอัตโนมัติ** · มันไม่ได้ทำอะไรผิด — มันทำสิ่งที่ถูกของมัน (ตอบเร็ว) ในขณะที่หลักประกันของระบบถูกทำให้อ่อนลงเงียบ ๆ

ทางออกมีสามทาง และต้องเลือกอย่างรู้ตัว:

1. **ตรวจทุกครั้ง แต่ทำให้ถูก** — ถ้าตัวตรวจเร็วพอ (in-memory, indexed) นี่คือค่าเริ่มต้นที่ควรเลือก
2. **cache แบบมีขอบเขตและประกาศได้** — TTL สั้น + บอกลูกค้าว่า "การถอนสิทธิ์มีผลภายใน N วินาที" · นี่คือสัญญา ไม่ใช่ความหวัง
3. **invalidate ให้ครบทุกจุดที่เปลี่ยนสิทธิ์** — และยอมรับว่ามันคือรายการที่ต้องดูแลตลอดไป · ถ้าเลือกทางนี้ ต้องมีเทสต์ที่ลบสิทธิ์แล้วยิงคำขอทันที

### 3.4 ตรวจที่ route หรือตรวจที่ object

คำว่า "every object" ในประโยคของ paper หมายถึงสิ่งที่หลายระบบลืม · การล็อกอินผ่านและการมีสิทธิ์ใน route ไม่ได้แปลว่าผู้ใช้มีสิทธิ์ใน *ข้อมูลชิ้นนั้น*:

```
# 3) ตรวจที่ route หรือตรวจที่ object — คำขอ 4 ตัว (ของตัวเอง 2 · ของ tenant อื่น 2)
request                    route_level  object_level
GET /invoices/42           yes          yes         
GET /invoices/9001         yes          no          
GET /invoices/42/export    yes          yes         
GET /invoices/9001/export  yes          no          
allowed  4/4            2/4         
cross_tenant_reads_blocked=2
```

ในตารางนี้ `tenant` คือลูกค้าหนึ่งรายที่ข้อมูลแยกขาดจากกัน · ตัวตรวจระดับ route ปล่อยผ่าน **4 จาก 4** เพราะทุกคำขอมาจากผู้ใช้ที่ล็อกอินแล้วและยิงไปยัง route ที่มีอยู่จริง · ตัวตรวจระดับ object ปล่อยผ่าน **2 จาก 4** เพราะสองคำขอที่เหลือขอใบแจ้งหนี้ของ `tenant` อื่น

ความต่างนี้คือช่องโหว่ประเภท **IDOR** (insecure direct object reference — การอ้างถึงวัตถุด้วย id ตรง ๆ โดยไม่ตรวจว่าเป็นของใคร) ซึ่งเป็นหนึ่งในช่องโหว่ที่พบมากที่สุดในเว็บแอป · และมันไม่ใช่เรื่องของ "การตรวจสิทธิ์" แบบ role — มันเป็นเรื่องของ *ความสัมพันธ์ระหว่างผู้ใช้กับวัตถุ* · สิทธิ์ `invoices:read` ไม่ได้บอกว่าใบไหน

### 3.5 เคสจริง: `goto fail` (2014)

เคสที่อธิบาย complete mediation ได้คมที่สุดในยุคนี้ไม่ได้เกิดจากโค้ดที่ *ไม่มี* การตรวจ · มันเกิดจากโค้ดที่ **มีการตรวจ แต่วิ่งข้ามมันไป**

ในเดือนกุมภาพันธ์ 2014 นักวิจัยพบว่า Apple Secure Transport (ไลบรารี TLS ที่ iOS และ OS X ใช้) ไม่ได้ตรวจลายเซ็นในข้อความ **TLS Server Key Exchange** — ข้อความที่เซิร์ฟเวอร์ส่งกุญแจสาธารณะชั่วคราวมาพร้อมลายเซ็นยืนยันว่ากุญแจนั้นเป็นของมันจริง · ผลคือผู้โจมตีที่อยู่กลางเส้นทาง (man-in-the-middle) ปลอมเซิร์ฟเวอร์ได้ด้วยกุญแจอะไรก็ได้ หรือข้ามขั้นตอนการเซ็นไปเลย

หมายเลขของช่องโหว่นี้คือ **CVE-2014-1266** · **CVE** (Common Vulnerabilities and Exposures — เลขทะเบียนช่องโหว่กลางที่ทุกฝ่ายอ้างถึงตัวเดียวกัน) คือเลขที่ทำให้คนทั้งโลกพูดถึงช่องโหว่ตัวเดียวกันได้ · มันกระทบ iOS ทุกเวอร์ชันก่อน 7.0.6 (รวม 6.x ก่อน 6.1.6), Apple TV ก่อน 6.0.2 และ OS X 10.9 ก่อน 10.9.2

สาเหตุในโค้ดคือบรรทัด `goto fail;` ที่ถูกเขียนซ้ำสองครั้งติดกัน · บรรทัดแรกอยู่ในเงื่อนไข "ถ้าตรวจไม่ผ่าน" · บรรทัดที่สองอยู่นอกเงื่อนไข จึงถูกเรียกทุกครั้งที่โค้ดไหลมาถึง · ผลคือเมื่อการตรวจก่อนหน้านั้นผ่านแล้ว โค้ดยังกระโดดข้ามสองบรรทัดถัดไป — การเรียก `SSLHashSHA1.final` และ `sslRawVerify` ซึ่งเป็น *การตรวจลายเซ็นจริง* — ไปลงที่ label `fail:` · และเพราะตัวแปร `err` ในจุดนั้นยังเป็น 0 ตัวจัดการจึงคืนค่าเป็น **success** · สังเกตให้ดี: มันไม่ได้ "ข้ามไปทั้งหมด" — มันข้าม *การตรวจ* แล้วรายงานว่าผ่าน

สามบทเรียนจากเคสนี้ที่ตรงกับบทนี้:

1. **การตรวจที่มีอยู่แต่ไม่ถูกเรียกในทุกเส้นทาง ไม่ใช่การตรวจ** · complete mediation พูดถึง "ทุกการเข้าถึง" เพราะโค้ดที่ข้ามได้คือโค้ดที่ไม่มี
2. **มันเป็นความล้มเหลวของ economy of mechanism ด้วย** · บรรทัดที่ซ้ำหนึ่งบรรทัดในฟังก์ชันยาว คือความซับซ้อนที่ตาเปล่าไม่เห็น · และมันอยู่ในโค้ดที่ทุกคนเชื่อว่าถูกตรวจแล้ว
3. **การทดสอบปกติไม่จับมัน** — เพราะเส้นทางที่พังคือเส้นทางที่ "ควรจะพัง" ซึ่งไม่มีใครทดสอบว่ามันพังจริง

## 4. economy of mechanism: กลไกที่อ่านออก คือกลไกที่ตรวจสอบได้

### 4.1 ทำไม "เล็ก" ถึงปลอดภัยกว่า

หลักข้อนี้ใน paper คือ **"keep the design as simple and small as possible"** และเหตุผลไม่ใช่ความสวยงาม — มันคือ **การตรวจสอบ** (assurance) · ถ้ากลไกความปลอดภัยของคุณมีเจ็ดกฎที่พึ่งลำดับกัน คุณจะตอบคำถามว่า "คำขอนี้ผ่านไหม" ได้ก็ต่อเมื่ออ่านครบทั้งเจ็ดกฎ · และถ้าคุณตอบไม่ได้ การตรวจสอบก็ไม่มีอยู่จริง

นี่คือเหตุผลที่ผมบอกนักศึกษาว่า **"ความซับซ้อนไม่ใช่ศัตรูของความปลอดภัย — มันคือความปลอดภัยที่คุณคิดว่ามี"** · ระบบที่ซับซ้อนไม่ได้อ่อนแอกว่าเสมอ แต่มัน *ตรวจสอบไม่ได้* เสมอ

### 4.2 วัดความซับซ้อนด้วยตัวเลข

เดโมที่สี่ตัดสินอินพุตชุดเดียวกัน (1574 ตัว: แจกแจงทุกสายอักขระยาว 1–4 ตัวจากตัวอักษร 6 ตัว จำนวน 1554 ตัว บวกเส้นทางที่เขียนมือ 20 ตัว) ด้วยชุดกฎสองชุด:

```go
// cleverRules คือชุดกฎที่ "ฉลาด": ใช้ pattern หลายแบบและพึ่งลำดับ
// มันทำงานได้ และไม่มีใครอ่านออกทั้งชุดในครั้งเดียว
// ฟิลด์ที่ 4 = catchAll — true เฉพาะกฎ default ที่จับทุกอย่างที่เหลือ
func cleverRules() []rule {
	return []rule{
		{"r1 exact:/admin", exact("/admin"), deny, false},
		{"r2 prefix:/a", prefix("/a"), allow, false},
		{"r3 suffix:.php", suffix(".php"), deny, false},
		{"r4 contains:..", contains(".."), deny, false},
		{"r5 prefix:/api", prefix("/api"), allow, false},
		{"r6 suffix:/", suffix("/"), allow, false},
		{"r7 default", anyRule, deny, true},
	}
}
```

```go
// simpleRules คือชุดกฎที่ "เล็ก": matcher ไม่ทับกันเลย ลำดับจึงไม่มีความหมาย
// แต่ละกฎอ่านแยกกันได้ และการเพิ่มกฎใหม่ไม่เปลี่ยนความหมายของกฎเดิม
func simpleRules() []rule {
	return []rule{
		{"s1 exact:/admin", exact("/admin"), deny, false},
		{"s2 exact:/api/invoices", exact("/api/invoices"), allow, false},
		{"s3 exact:/api/reports", exact("/api/reports"), allow, false},
		{"s4 default", anyRule, deny, true},
	}
}
```

ชุดแรกมี 7 กฎ (`exact`, `prefix`, `suffix`, `contains` ปนกัน + กฎ default) · ชุดที่สองมี 4 กฎ ที่ matcher ไม่ทับกันเลย · แล้วเราวัดสี่ค่า:

- **shadowed** — กฎที่ไม่เคยถูกเลือกเลย เพราะกฎที่อยู่ก่อนหน้าจับอินพุตของมันไปหมดแล้ว (โค้ดตายในนโยบาย)
- **ambiguous_inputs** — อินพุตที่ถูกจับโดยกฎตั้งแต่สองข้อขึ้นไปซึ่งให้คำตอบต่างกัน
- **order_flips** — อินพุตที่คำตอบเปลี่ยนถ้าสลับกฎสองข้อที่อยู่ติดกัน
- **max_rules_per_input** — จำนวนกฎที่ต้องอ่านพร้อมกันเพื่อตอบอินพุตเดียว

ผลรันจริง:

```
# 4) economy of mechanism — สองเอนจินตัดสินอินพุตชุดเดียวกัน
inputs=1574  exhaustive=1554  handpicked=20

engine   rules   explicit  shadowed  ambiguous_inputs   order_flips  max_rules_per_input
clever   7       6         1         22                 7            3               
simple   4       3         0         0                  0            1               

clever_shadowed=r5 prefix:/api
shadowed=กฎที่ไม่เคยถูกเลือกเลย เพราะกฎที่อยู่ก่อนหน้าจับอินพุตของมันไปหมดแล้ว

# อินพุตที่คำตอบขึ้นกับลำดับกฎ (clever: สลับ r2 prefix:/a กับ r3 suffix:.php)
input                as_written   after_swap_r2_r3
/api/x.php           ALLOW        DENY        
/a/x.php             ALLOW        DENY        
/admin               DENY         DENY        

คำถามที่ใช้ตรวจชุดกฎของคุณ: มีอินพุตกี่ตัวที่คำตอบเปลี่ยนเมื่อสลับกฎสองข้อ
```

อ่านตารางนี้ทีละคอลัมน์:

- **`clever` มี 1 กฎที่ตาย** — `r5 prefix:/api` ไม่เคยถูกเลือก เพราะ `r2 prefix:/a` อยู่ก่อนและจับ `/api...` ไปหมดแล้ว · กฎที่ตายไม่ใช่ปัญหาเรื่องประสิทธิภาพ — มันคือ *ความเข้าใจผิด*: คนอ่านนโยบายจะคิดว่า `/api` ถูกจัดการด้วยกฎของมันเอง
- **22 อินพุตถูกจับโดยกฎที่ขัดกัน** · เช่นเส้นทางที่ทั้งกฎ "ห้ามไฟล์ `.php`" และกฎ "อนุญาต path ที่เริ่มด้วย `/a`" จับได้ · คำตอบจึงขึ้นกับว่ากฎไหนอยู่ก่อน
- **7 อินพุตที่คำตอบขึ้นกับลำดับบรรทัดล้วน ๆ** · นี่คือตัวเลขที่ผมอยากให้คุณลองวัดในระบบของคุณมากที่สุด · ถ้ามันมากกว่าศูนย์ คุณมีนโยบายที่ "ความหมาย" อยู่ที่ลำดับการเขียน ไม่ใช่ที่เจตนา
- **`max_rules_per_input=3`** — ต้องอ่านสามกฎพร้อมกันจึงจะตอบอินพุตเดียวได้ · เทียบกับ `simple` ที่ตอบได้ด้วยกฎเดียวเสมอ

และตัวอย่างที่จับต้องได้จากท้ายผลรัน: `/api/x.php` ถูก **อนุญาต** ในลำดับที่เขียนไว้ · แต่ถูก **ปฏิเสธ** ทันทีถ้าสลับกฎ r2 กับ r3 · ไม่มีใครแก้โค้ด ไม่มีใครแก้เจตนา — แค่ย้ายบรรทัด · นี่คือคำจำกัดความของ "นโยบายที่อ่านไม่ออก"

`simple` ให้ `shadowed=0`, `ambiguous_inputs=0`, `order_flips=0` และ `max_rules_per_input=1` · ราคาที่จ่ายคือ **ต้องเขียนรายการที่อนุญาตให้ครบ** (allowlist) แทนที่จะเขียน pattern สั้น ๆ · และนั่นคือการแลกเปลี่ยนที่ถูก: **ความชัดเจนซื้อด้วยความยาว**

### 4.3 เคสจริง: Debian OpenSSL (2008)

ถ้าคุณคิดว่า "กลไกที่เพิ่มเข้ามานิดเดียวไม่น่ากังวล" เคสนี้คือคำตอบ

ในปี 2006 ผู้ดูแลแพ็กเกจ OpenSSL ของ Debian ปรับโค้ดจุดหนึ่งเพื่อระงับคำเตือนของ Valgrind (เครื่องมือตรวจหน่วยความจำ) เรื่องการใช้ข้อมูลที่ยังไม่ถูกกำหนดค่า · แต่นอกเหนือจากจุดที่ตั้งใจแก้ พวกเขา comment บรรทัดที่ผสม entropy (ความไม่แน่นอนจากสิ่งแวดล้อมที่ใช้เป็นเมล็ดสุ่ม) เข้าไปในตัวสร้างเลขสุ่มออกด้วย

ผลคือตัวสร้างเลขสุ่มเหลือเมล็ดจาก process id เท่านั้น · จำนวน process id ที่เป็นไปได้มีราวสามหมื่นกว่าค่า · แปลว่ากุญแจทุกดอกที่สร้างบนระบบที่ได้รับผลกระทบ มาจากชุดค่าที่เดาได้และคำนวณล่วงหน้าได้ทั้งหมด

ไทม์ไลน์: เวอร์ชันแรกที่พังคือ `0.9.8c-1` อัปโหลดเข้า unstable เมื่อ **17 กันยายน 2006** · นักพัฒนา Debian ชื่อ Luciano Bello ค้นพบและเปิดเผยเมื่อ **13 พฤษภาคม 2008** (CVE-2008-0166)

เกือบยี่สิบเดือนที่กุญแจ SSH, กุญแจ OpenVPN, กุญแจ DNSSEC และใบรับรอง X.509 ถูกสร้างจากค่าที่เดาได้และคำนวณล่วงหน้าได้ทั้งหมด

และการแพตช์แก้ไม่ช่วยกุญแจที่สร้างไปแล้ว — ต้องสร้างใหม่ทั้งหมด · นั่นคือราคาของช่องโหว่ที่อยู่ใน *ตัวสร้างความลับ*: โค้ดแก้ได้วันนี้ แต่ความลับที่หลุดไปแล้วไม่ย้อนกลับมา

บทเรียนสำหรับหลัก economy of mechanism: **กลไกที่เพิ่มเข้ามาโดยไม่มีคนอื่นในโปรเจกต์ตรวจ คือกลไกที่อยู่นอกขอบเขตการตรวจสอบ** · ไม่ใช่เพราะคนเขียนไม่เก่ง แต่เพราะการเปลี่ยนแปลงเล็ก ๆ ที่ "แค่ปิด warning" ไม่ถูกมองว่าเป็นการเปลี่ยนพฤติกรรมด้านความปลอดภัย · และทุกครั้งที่คุณเพิ่มกิ่งเงื่อนไขใหม่เข้าไปในโค้ดที่ตัดสินเรื่องความปลอดภัย คุณเพิ่มสิ่งที่ต้องอ่านเพื่อให้มั่นใจ

## 5. สี่หลักเดียวกัน ในรูปที่เจอในงานจริง

| หลัก | คำถามที่ต้องถามก่อน deploy | รูปที่เห็นในงานจริง |
|---|---|---|
| **fail closed** | ถ้าตัวตรวจนี้ตอบไม่ได้ ใครได้ประโยชน์ | firewall ที่ default เป็น drop · circuit breaker ที่เปิดวงจรเมื่อปลายทางล่ม · readiness probe ที่ถอด instance ออกเมื่อไม่แน่ใจ · session cookie ที่ถอดรหัสไม่ได้ต้องไม่ถือว่าถูกต้อง |
| **secure by default** | ถ้าไม่มีใครตั้งค่าอะไรเลย ระบบปลอดภัยไหม | ค่าเริ่มต้นของ TLS · คอลัมน์ `NOT NULL` · container ที่ `--cap-drop=ALL` · bucket ที่ private โดยค่าเริ่มต้น · framework ที่ปิด debug mode ให้ |
| **complete mediation** | มีเส้นทางไหนถึงข้อมูลนี้ได้โดยไม่ผ่านตัวตรวจ | API + batch + CLI + cache + retry queue · การตรวจระดับ object (ไม่ใช่แค่ route) · row-level security ที่ฐานข้อมูล · การตรวจซ้ำที่ชั้น repository |
| **economy of mechanism** | ต้องอ่านกลไกกี่ชิ้นพร้อมกันจึงจะตอบได้ | policy engine ที่พึ่งลำดับกฎ · regex ซ้อนหลายชั้น · กฎที่ตายแล้วแต่ยังอยู่ในไฟล์ · exception list ที่ไม่มีใครกล้าลบ |

ตารางนี้ใช้เป็น checklist ก่อน merge ได้ · สี่คำถาม ไม่ต้องมีเครื่องมือใหม่ ไม่ต้องซื้ออะไร

## 6. บทเรียนเจ็ดข้อ

1. **"ล้ม" มีห้าแบบ ไม่ใช่แบบเดียว** · timeout, ไม่มีกฎ, ค่าที่ไม่รู้จัก, ไม่มีการตัดสินใจ และโปรเซสตาย · ออกแบบแค่กรณี error แล้วอีกสี่แบบจะเปิดประตูให้เอง · ในเดโม ตารางห้าแถวนี้คือรายการที่ต้องตอบให้ครบ
2. **fail closed ที่ใช้งานได้ ต้องแคบและประกาศได้** · `closed_degraded` ผ่านงาน 5 จาก 5 และกันภัย 5 จาก 5 เพราะมันยอมแค่ "อ่าน" และแค่คู่ที่เคยได้อนุญาต · ถ้ามันยอมกว้างกว่านี้หนึ่งเงื่อนไข มันจะกลายเป็น fail open ที่มีชื่อเพราะ
3. **nil คือค่าเริ่มต้นที่อันตรายที่สุด** · typed nil ทำให้ `err == nil` เป็น false และ nil receiver ทำให้ `Allow()` คืน true · ทั้งคู่ทำให้ fail closed ในโค้ดกลายเป็น fail open ใน production · เขียนเทสต์เส้นทางที่ล้มด้วย
4. **ค่าเริ่มต้นคือผลิตภัณฑ์** · config แปดค่าให้ผลไม่ปลอดภัย 7 จาก 8 เมื่อปล่อยว่าง · แบบใหม่ให้ 0 จาก 8 และบังคับเขียนแค่หนึ่งค่า · ความต่างระหว่าง 8 กับ 1 คือความต่างระหว่างการพึ่งความจำกับการพึ่งโครงสร้าง
5. **ระบบที่ตอบข้อกำหนดของตัวเองไม่ได้ ต้องไม่สตาร์ต** · `secure` + config ว่าง ปฏิเสธการสตาร์ตพร้อมบอกว่าขาดอะไร · ปลอดภัยกว่าการรันแล้ว insecure มาก — และมันย้ายปัญหาไปที่เวลาที่แก้ได้
6. **cache คือกลไกที่ทำลาย complete mediation อย่างเงียบ ๆ** · ถอนสิทธิ์แล้วยังผ่าน 12 จาก 12 คำขอ · ทางออกคือวาง cache ใต้ตัวตรวจ หรือประกาศหน้าต่างความล่าช้าเป็นสัญญา
7. **ความซับซ้อนที่วัดได้ คือความเสี่ยงที่วัดได้** · ชุดกฎเจ็ดข้อมีหนึ่งกฎตาย 22 อินพุตที่กฎขัดกัน และ 7 อินพุตที่คำตอบขึ้นกับลำดับบรรทัด · ชุดกฎที่ matcher ไม่ทับกันให้ศูนย์ทั้งสี่ค่า · จ่ายด้วยความยาวของ allowlist แล้วจบ

## 7. สรุปตอนที่ 13

- **สี่คำในหัวข้อ = สามหลักจาก paper ของ Saltzer และ Schroeder (1975)** · fail-safe defaults ถูกแยกในภาษาอุตสาหกรรมเป็น **fail closed** (พฤติกรรมเมื่อกลไกพัง) และ **secure by default** (พฤติกรรมเมื่อไม่มีใครตั้งค่า) · อีกสองหลักคือ **complete mediation** และ **economy of mechanism** · รวมกับ least privilege ของตอนที่ 12 เป็นสี่ข้อจากแปดข้อ
- **fail closed:** เดโมมีคำขอ 10 ตัว (ภัย 5, ปกติ 5) และบริการตัดสินสิทธิ์ timeout ทุกครั้ง · `fail_open` ปล่อยภัย **5/5** และงาน **5/5** · `fail_closed` ปล่อยภัย **0/5** และงาน **0/5** · `closed_degraded` ปล่อยภัย **0/5** และงาน **5/5** · ทางที่สามชนะเพราะมันแคบ: เฉพาะกริยาอ่าน และเฉพาะคู่ที่เคยได้คำตอบว่า *อนุญาต*
- **สภาวะที่ตอบไม่ได้มีห้าแบบ** · timeout, ไม่มีกฎ, ค่าที่ไม่รู้จัก, ไม่มีการตัดสินใจ และโปรเซสตาย · สี่แบบแรกจัดการได้ด้วยการตัดสินใจ · แบบสุดท้ายไม่ได้แก้ด้วย fail closed — มันแก้ด้วย availability
- **typed nil ทำให้ fail closed กลายเป็น fail open:** `err == nil` ให้ **false** ทั้งที่ไม่มีอะไรผิดพลาด · guard ที่ fail open เมื่อ `err != nil` จึงคืน **true** · และ nil receiver ที่ `d == nil` เป็นจริง ก็คืน `Allow()` = **true**
- **secure by default:** config 8 ค่า · ปล่อยว่างแล้วแบบเก่าไม่ปลอดภัย **7/8** (ภัยผ่าน 7/8) · เขียน 5 ค่าเหลือช่อง **3/8** · แบบใหม่ไม่ปลอดภัย **0/8** ทั้งตอนว่างและตอนเขียน 1 ค่า · และตอนว่างมัน **ปฏิเสธการสตาร์ต** เพราะขาด `allowed_hosts`
- **ค่าที่พิมพ์ผิด:** แบบเก่าปิดการตรวจสิทธิ์เงียบ ๆ **3 จาก 3** กรณี (`off`, `of`, ค่าว่าง) · แบบใหม่ **0 จาก 3** เพราะค่า enum ถูกตรวจและ `off` ต้องมี `allow_insecure=true`
- **complete mediation:** เจ็ดเส้นทางถึงข้อมูลเดียวกัน · ตรวจที่ handler = **1/7** · คัดลอกไปทุกที่ = **6/7** (cache หลุด) · จุดเดียวใต้ cache = **7/7** · ถอนสิทธิ์แล้ว 12 คำขอ: memo ไม่มี TTL ผ่าน **12/12**, TTL 60 วินาทีผ่าน **12/12**, มี invalidation แต่ลืมจุดหนึ่งผ่าน **4/12**, ตรวจทุกครั้งผ่าน **0/12**
- **ตรวจที่ object ไม่ใช่ที่ route:** คำขอ 4 ตัว · ระดับ route ผ่าน **4/4** · ระดับ object ผ่าน **2/4** · `invoices:read` ไม่ได้บอกว่าใบไหนเป็นของใคร
- **economy of mechanism:** 1574 อินพุต · ชุดกฎเจ็ดข้อ: กฎตาย **1**, อินพุตที่กฎขัดกัน **22**, อินพุตที่ขึ้นกับลำดับ **7**, ต้องอ่านสูงสุด **3** กฎต่ออินพุต · ชุดกฎสี่ข้อที่ matcher ไม่ทับกัน: **0 ทั้งสี่ค่า** และอ่านกฎเดียวต่ออินพุต
- **คำถามที่ควรพกไปต่อ:** *"ถ้าตัวตรวจตัวนี้ตอบไม่ได้ พรุ่งนี้เช้าใครได้ประโยชน์"* · ถ้าตอบว่า "ผู้โจมตี" คุณยังไม่มี fail closed คุณมี fail open ที่ยังไม่มีใครใช้

## 8. โจทย์

### 8.1 drill (ทำใน `course/code/ep13/` — 30–60 นาที)

1. **เพิ่มคำขอที่ 11** — เพิ่มคำขอที่เป็นภัยแต่เป็นกริยาอ่าน (เช่น `intern` ขอ `reports:read`) แล้วรันใหม่ · ตอบว่า `closed_degraded` เปลี่ยนไหม และเพราะอะไรตัวเลข `hostile_allowed` จึงไม่ขยับ
2. **ใส่ TTL ให้ cache** — แก้ `guardClosedDegraded` ให้ยอมใช้ cache เฉพาะ 5 คำขอหลังคำตอบล่าสุด (สมมติ 1 คำขอ = 1 วินาที) · วัดว่า `legit_allowed` ยังเป็น 5/5 ไหม และภัยเริ่มผ่านเมื่อไร · อธิบายว่าทำไมค่านี้คือ "สัญญา" ไม่ใช่ "ช่องโหว่"
3. **ปิด typed nil ให้จริง** — แก้ `lookupTypedNil` ให้คืน nil จริง (`return false, nil`) แล้วยืนยันว่า `err == nil` เปลี่ยนเป็น true · จากนั้นอธิบายว่าทำไม `errors.Is(err, nil)` ไม่ช่วยในเคสเดิม
4. **เพิ่ม setting ที่ 9** — เพิ่ม `session_idle_minutes` แล้วตัดสินว่า zero value ควรหมายถึงอะไรในสองแบบ · เขียนกฎว่าค่าแบบไหน "เดาได้" (มีค่าที่ปลอดภัยชัดเจน) และค่าแบบไหน "ต้องบังคับให้ระบุ" (เช่น `allowed_hosts`)
5. **เพิ่มเส้นทางที่ 8** — เพิ่ม `webhook_replay` ที่อ่านประวัติใบแจ้งหนี้ · รันใหม่แล้วรายงาน `mediated` ของ A, B และ C · อธิบายว่าทำไม design C ยังได้ 8/8 ขณะที่ design B ต้องแก้โค้ดเพิ่ม
6. **พิสูจน์ว่า `simple` ทนการเพิ่มกฎ** — เพิ่มกฎที่ห้าใน `simpleRules` (เช่น `exact:/api/audit` → deny) แล้วรันใหม่ · ยืนยันว่า `order_flips` ยังเป็น 0 และเขียนเงื่อนไขที่ทำให้เป็นเช่นนั้น (คำใบ้: matcher ต้องไม่ทับกัน)

### 8.2 mini-project: fail-closed audit ของบริการหนึ่งตัว (3–5 ชั่วโมง)

เลือกบริการจริงหนึ่งตัวที่คุณดูแล (หรือ service ในโปรเจกต์เรียน) แล้วทำห้าสิ่งนี้:

1. **ทำรายการ "ตัวตรวจ" ทั้งหมด** — ทุกที่ที่โค้ดตัดสินว่า "ผ่าน/ไม่ผ่าน": middleware auth, การตรวจสิทธิ์ใน handler, การตรวจที่ฐานข้อมูล, feature flag, การตรวจที่ gateway · เขียนเป็นตารางว่าตัวตรวจแต่ละตัวพึ่งอะไร (บริการภายนอก, cache, config, ฐานข้อมูล)
2. **ไล่ห้าสภาวะของแต่ละตัวตรวจ** — timeout, ไม่มีกฎ, ค่าที่ไม่รู้จัก, ไม่มีการตัดสินใจ, โปรเซสตาย · เขียนว่าปัจจุบันเกิดอะไรขึ้น (ผ่าน/ปฏิเสธ/ล่ม) · ห้ามเดา: อ่านโค้ดหรือทดสอบใน environment ของคุณเอง
3. **ทดลองปิด dependency ทีละตัว** — ใน environment ที่คุณควบคุม (ไม่ใช่ production) · แล้วยิงคำขอที่ *ควรถูกปฏิเสธ* หนึ่งตัวและคำขอปกติหนึ่งตัว · บันทึกผลทั้งสอง
4. **วัดเส้นทางเข้าถึงข้อมูลหลักหนึ่งตาราง** — ระบุทุกเส้นทาง (API, batch, CLI, cache, retry) และทำเครื่องหมายว่าอันไหนผ่านตัวตรวจ · นับเป็น `mediated/ทั้งหมด`
5. **วัดการถอนสิทธิ์** — ให้สิทธิ์ผู้ใช้ทดสอบหนึ่งคน, ถอนสิทธิ์ แล้ววัดว่าคำขอกี่ตัวยังผ่านใน 60 วินาทีถัดไป · ตัวเลขนี้คือ "หน้าต่างของความเสียหาย" ของคุณ

**สิ่งที่ต้องส่ง:** รายงานหนึ่งหน้า (ไม่เกิน 800 คำ) ที่มี (ก) ตารางตัวตรวจและพฤติกรรมเมื่อล้มทั้งห้าสภาวะ (ข) ตัวเลข `mediated/ทั้งหมด` ของข้อมูลหลัก (ค) ตัวเลขคำขอที่ยังผ่านหลังถอนสิทธิ์ (ง) ค่า config สองค่าที่คุณจะเปลี่ยนเป็น secure default พร้อมผลข้างเคียงที่คาดว่าจะเกิด (จ) หนึ่งกลไกที่คุณจะ *ลบ* ออกเพราะมันทำให้ระบบตรวจสอบยากขึ้น

**เกณฑ์ผ่าน:** ทุกตัวเลขต้อง reproduce ได้จากคำสั่งหรือสคริปต์ที่แนบมา · และต้องมีประโยคหนึ่งที่ตอบว่า *"ถ้าตัวตรวจหลักของบริการนี้ตอบไม่ได้ พรุ่งนี้เช้าจะเกิดอะไรขึ้น"* — ตอบด้วยรายการ ไม่ใช่คำคุณศัพท์

## 9. สะพานไปสู่ตอนที่ 14

สี่หลักในบทนี้ตอบคำถามว่า "ระบบควรทำอะไรเมื่อไม่รู้" · แต่ยังเหลือคำถามที่ใหญ่กว่าและถูกใช้มากที่สุดในงานจริง: **อะไรคือ "ข้างนอก" ของระบบคุณ**

เพราะการตัดสินใจทั้งหมดในบทนี้ — fail closed, secure by default, complete mediation, economy of mechanism — ถูกบังคับใช้ที่ *ขอบ* ของระบบ · และขอบที่กำหนดผิด คือจุดที่ทุกหลักข้างต้นรั่วพร้อมกัน · ข้อมูลที่ "มาจากข้างใน" จะถูกถือว่าถูกต้องโดยไม่ตรวจ และนั่นคือที่มาของช่องโหว่ที่เราเห็นในตอนที่ 4 (SQL injection) และตอนที่ 5 (XSS) ในปีแรกของซีรีส์นี้

ตอนหน้า (ตอนที่ 14) เราจะคุยเรื่อง **never trust input + trust boundaries** — วิธีกำหนดว่าอะไรอยู่ข้างนอก อะไรอยู่ข้างใน และทำไมการขีดเส้นให้ถูกคือทักษะที่ใช้บ่อยที่สุดในงานนี้

ถ้าอยากเตรียมตัว ลองวาดแผนภาพง่าย ๆ ของบริการคุณหนึ่งหน้า: กล่องแทนองค์ประกอบ, ลูกศรแทนการไหลของข้อมูล แล้วลากเส้นประคั่นระหว่าง "สิ่งที่คุณควบคุม" กับ "สิ่งที่คุณไม่ควบคุม" · ทุกจุดที่ลูกศรตัดเส้นประ คือจุดที่คุณต้องมีตัวตรวจ · ถ้าคุณพบจุดที่ไม่มี — คุณเพิ่งเจองานของตอนหน้า
