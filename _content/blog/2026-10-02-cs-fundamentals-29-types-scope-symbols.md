# type system, scope, symbol table — ตรวจชนิดก่อนรัน (ตอนที่ 29)

ตอนที่ 26–28 เราเดินครบวงจรแรกของภาษาจิ๋วแล้ว: **lexer** ตัดข้อความออกเป็น token (ชิ้นคำ), **parser** ประกอบ token ขึ้นเป็นต้นไม้ที่เรียกว่า AST (abstract syntax tree = ต้นไม้โครงสร้างของโปรแกรม), แล้ว **interpreter** เดินตามต้นไม้คำนวณค่าออกมา แต่มีความรู้สึกหนึ่งที่ค้างคาใจจากตอนที่แล้ว — ทุกครั้งที่เราเจอความผิดอย่าง `1 + true` (เอาเลขมาบวกกับค่าจริง/เท็จ) มันเพิ่ง "โผล่" ให้เห็นก็ต่อเมื่อโปรแกรม**ไหลไปถึงบรรทัดนั้นแล้ว** ระหว่างรัน

```text
ข้อความ  →  lexer (26)  →  parser (27)  →  interpreter (28)  →  ค่า
                                     ↑ ตอน 28 ตรวจ "ชนิด" ตรงนี้ — ตอนรัน
```

ถ้าโปรแกรมยาวพันบรรทัด แล้วบรรทัดที่ 999 เขียน `1 + true` ไว้ เราก็ต้องรันตั้ง 999 บรรทัดกว่าจะรู้ตัว นี่คือจุดที่ภาษาจริงอย่าง Go เก่งกว่า: มัน**รู้ก่อนรัน** ตั้งแต่ยังไม่ทันเริ่มวิ่งโปรแกรม (ตอนที่สั่ง build — build = สั่งคอมไพเลอร์แปลงโค้ดให้เป็นโปรแกรม)

ตอนนี้เราจะปิดช่องว่างนี้ด้วยของสามชิ้นที่คอมไพเลอร์ (ตัวแปลงโค้ดให้เป็นโปรแกรมที่เครื่องรันได้) จริงทุกตัวมี — และทั้งสามชิ้นทำงานร่วมกันเป็นด่านตรวจที่ชื่อว่า **semantic analysis** (การวิเคราะห์ความหมาย):

> **type system** (ระบบชนิด) = กติกาว่า "นิพจน์แต่ละก้อนเป็นชนิดอะไร และเอาอะไรมาผสมกับอะไรได้"
> **scope** (ขอบเขต) = เขตของโปรแกรมที่ "ชื่อหนึ่ง ๆ มองเห็นได้"
> **symbol table** (ตารางสัญลักษณ์) = โครงสร้างข้อมูลที่จด "ชื่อ → ความหมาย" (ชนิด + อยู่ scope ไหน + ประกาศตรงไหน)

ยินดีต้อนรับสู่ตอนสุดท้ายของระยะนี้ — ก่อนที่เราจะเปลี่ยนจาก "เดินต้นไม้" ไปเป็น "สร้างโค้ดจริง" (ตอนที่ 30) — ตอนนี้เป็นตอนแรกที่ภาษาจิ๋วของเรา**จับความผิดได้ก่อนรัน**

> **ที่อยู่ของโค้ดในตอนนี้:** ทุกอย่างอยู่ใน `course/code/ep29/`
> - **01–05** = โฟลเดอร์โปรแกรม แยกตามเลขโปรแกรม
> - **`out/`** = ผลรันจริงของทุกโปรแกรม — `00_env.txt` = สภาพแวดล้อม (เวอร์ชัน Go/เครื่อง/วันที่) · `06_drill_answer.out.txt` = เฉลยโจทย์ท้ายบท · `07_go_real.out.txt` = ตารางสัญลักษณ์ที่ Go สร้างเอง
> - **`internal/check/`** = ตัวตรวจชนิด + ตารางสัญลักษณ์ + scope (ไฟล์เดียว `check.go`) ที่ทุกโปรแกรมเรียกใช้ร่วมกัน · **`internal/eval/` + `internal/lexer/` + `internal/parser/`** = ของเดิมจากตอน 26–28 (แตะ `eval` แค่จุดเดียวเพื่อให้ env มี scope)

ภาพข้างบนคือภาพรวมของทั้งตอน: ไปป์ไลน์เดิมของเรามีสามช่วง (lexer → parser → interpreter) ตอนนี้เราสอด **type checker** (ตัวตรวจชนิด) เข้าไประหว่าง parser กับ interpreter — มันอ่านต้นไม้แล้วตอบ "ชนิด" โดยไม่ต้องคำนวณค่าเลยสักตัว (ช่องสีน้ำเงินคือของใหม่)

## 1. ปัญหา: ตอน 28 รู้ "ชนิด" ตอนรัน — ช้าไปหนึ่งก้าว

ย้อนไปดูสิ่งที่ interpreter ในตอนที่ 28 ทำกับนิพจน์ (ก้อนโค้ดที่คำนวณเป็นค่าได้) `1 + true`:

```text
parser: ผ่าน — ต้นไม้คือ (program (let x (+ 1 true)))
interpreter: error → line 1, column 11: cannot use "+" with int and bool
```

สังเกตสองอย่าง

**อย่างแรก:** parser **ผ่าน** เพราะ parser ดูแค่ "รูปประโยค" — `1 + true` มันเป็น "เลข + ค่าจริง/เท็จ" ซึ่งเข้ารูปไวยากรณ์ `expression = term ((+|-) term)*` (อ่านว่า: นิพจน์ = พจน์หนึ่งตัว แล้วต่อด้วย "+ หรือ - แล้วพจน์" ซ้ำได้เรื่อย ๆ — ไวยากรณ์ที่เราเขียนไว้ในตอนที่ 27) ครบทุกตัวอักษร parser ไม่มีวันรู้ว่า "เลขกับ bool บวกกันไม่ได้" เพราะความรู้เรื่อง**ชนิด** (type) ไม่ได้อยู่ในไวยากรณ์

**อย่างที่สอง:** interpreter **ก็รู้ได้** แต่รู้เพราะมันลองคำนวณจริง ๆ แล้วเจอว่าค่าซ้ายเป็น `int` ค่าขวาเป็น `bool` — มัน "สะดุด" ระหว่างเดิน

ภาษาที่ตรวจชนิด**ระหว่างรัน**แบบนี้เรียกว่า **dynamically typed** (ไดนามิก-ไทป์ = ตรวจตอนรัน) ส่วนภาษาที่ตรวจ**ก่อนรัน**เรียกว่า **statically typed** (สแตติก-ไทป์ = ตรวจก่อนรัน) — Go, C, Rust, Java อยู่ฝั่ง static ส่วน Python, Ruby, JavaScript อยู่ฝั่ง dynamic

ทั้งสองแบบ "ดีต่างกัน" ไม่มีใครเหนือกว่าโดยสิ้นเชิง แต่สำหรับงานที่อยากจับความผิดให้เร็วที่สุด ภาษา static ได้เปรียบตรงที่ **ความผิดเชิงชนิดส่วนใหญ่ถูกจับได้ก่อนโปรแกรมจะวิ่ง**

![ตอน 28 (dynamic) vs ตอน 29 (static): ตรวจชนิดคนละจังหวะ](/assets/diagrams/ep29-04-dynamic-vs-static.svg)

ตอนนี้เราจะเปลี่ยนภาษาจิ๋วจาก "ตรวจตอนรัน" มาเป็น "ตรวจก่อนรัน" โดยเพิ่มด่านตรวจใหม่แทรกอยู่ระหว่าง parser กับ interpreter

## 2. ของชิ้นที่ 1 — type system: นิพจน์ทุกก้อนมี "ชนิด"

> **type** (ชนิด) = หมวดของค่าที่บอกว่า "ค่านี้เป็นอะไร และเอาไปทำอะไรได้บ้าง" เช่น จำนวนเต็ม (int) กับค่าจริง/เท็จ (bool) เป็นคนละชนิดกัน
>
> **type system** (ระบบชนิด) = ชุดกติกาที่กำหนดว่าค่ามีชนิดอะไรบ้าง และตัวดำเนินการแต่ละตัว (เช่น `+` `-` `==`) รับค่าชนิดอะไร ผลลัพธ์เป็นชนิดอะไร

ภาษาจิ๋วของเรามีชนิดแค่สองตัว (จงใจให้เรียบที่สุดเพื่อให้เห็นโครงสร้าง):

| ชนิด | ความหมาย | ตัวอย่างค่าที่เป็นชนิดนี้ |
|---|---|---|
| `int` | จำนวนเต็ม | `3`, `-5`, `42` |
| `bool` | ค่าจริง/เท็จ | `true`, `false` |

ตัวดำเนินการของภาษานี้จึงมี "สัญญา" (contract — ข้อตกลงว่าใส่อะไรเข้า ได้อะไรออก) ชัดเจนตายตัว:

```text
เลขคณิต    + - * /   : (int, int) → int      สองข้างต้องเป็น int ทั้งคู่
เปรียบเทียบ < >       : (int, int) → bool
เท่ากัน/ไม่เท่า == !=  : (ชนิดเดียวกัน, ชนิดเดียวกัน) → bool
เครื่องหมายหน้า - +    : (int) → int
```

สัญกรณ์ `(int, int) → int` อ่านว่า "รับ int สองตัว คืน int หนึ่งตัว" — ตัวซ้ายของลูกศรคือชนิดที่รับเข้า ตัวขวาคือชนิดที่คืนออกมา

ตอนที่ 28 interpreter **ฝัง**กติกาเหล่านี้ไว้ในโค้ดคำนวณ (ทุก case ของ `evalBinary` มีโค้ดเช็คชนิดของสองฝั่ง: เลขคณิตกับ `<` `>` บังคับให้เป็น int ทั้งคู่ ส่วน `==` `!=` บังคับให้ชนิดตรงกัน) — มันจึงรู้ชนิดก็ต่อเมื่อ "ค่าไหลมาถึงมือแล้ว" ตอนนี้เราจะ**ดึงกติกาเหล่านั้นออกมาไว้ต่างหาก** ในตัวตรวจชนิด

หัวใจของตัวตรวจชนิดคือฟังก์ชัน `checkExpr` ซึ่งรูปร่าง**เหมือน** `eval` ของตอนที่ 28 แทบทุกตัวอักษร — ต่างกันแค่สิ่งที่คืน (eval คืน "ค่า" · ตัวนี้คืน "ชนิด"):

โค้ดนี้มีแค่ 3 ท่าที่ต้องอ่าน: ตัวเลข/ค่าจริงเท็จ → ตอบชนิดตรง ๆ · ชื่อ → เปิดตารางสัญลักษณ์หาชนิด · บวก/ลบ → ถามชนิดของลูกสองข้างก่อน (recursive):

```go
// checkExpr — หนึ่ง node ของต้นไม้ = หนึ่ง case นี้ คืน "ชนิด" ไม่ใช่ "ค่า"
func (c *Checker) checkExpr(e parser.Expr, depth int) (Type, *Error) {
	switch n := e.(type) {
	case *parser.NumberLit:
		return c.done(depth, e, Int), nil   // ตัวเลข → int เสมอ

	case *parser.BoolLit:
		return c.done(depth, e, Bool), nil  // true/false → bool เสมอ

	case *parser.Ident:
		// ชื่อไม่บอกชนิดในตัวเอง — ต้องถามตารางสัญลักษณ์ (หัวข้อ 4)
		sym, ok := c.table.Lookup(n.Name)
		if !ok {
			return Int, c.report(n.At, fmt.Sprintf("undefined variable %q", n.Name), "")
		}
		return c.done(depth, e, sym.Type), nil

	case *parser.UnaryExpr:
		rt, err := c.checkExpr(n.Right, depth+1)  // ถามลูกก่อน (recursive)
		if err != nil {
			return Int, err
		}
		if rt != Int {
			return Int, c.report(n.OpTok.Pos, fmt.Sprintf("operator %q is not defined on %s", n.Op, rt), "")
		}
		return c.done(depth, e, Int), nil

	case *parser.BinaryExpr:
		return c.checkBinary(n, depth)
	}
	return Int, c.report(posOf(e), fmt.Sprintf("cannot type-check node of type %T", e), "")
}
```

> **recursive** (รีเคอร์ซีฟ) = การที่ฟังก์ชันเรียกตัวเอง สังเกตว่า `checkExpr` เรียก `checkExpr` กับลูกของมันเอง (เช่น `c.checkExpr(n.Right, ...)`) — ท่านี้คือท่าเดียวกับ `eval` และ `writeTree` ที่เราใช้มาสองตอนแล้ว ต้นไม้ "บังคับ" ให้ทุกอย่างเป็นแบบนี้

การคิดชนิดแบบนี้เรียกว่า **type inference** (การอนุมานชนิด) — เรา**ไม่ต้องเขียนบอก**ว่า `3 + 4 * 5` เป็นชนิดอะไร ตัวตรวจชนิด "เดินจากใบขึ้นราก" (bottom-up) แล้วสรุปเองได้ว่า: `3` เป็น int, `4 * 5` เป็น int, ดังนั้น `3 + 4 * 5` เป็น int

ลองดูผลรันจริงของโปรแกรม 01 (มันตรวจชนิดของนิพจน์ 8 ตัวโดย**ไม่รัน**แม้แต่ตัวเดียว):

```text
   1) 3              → ชนิด int
   2) true           → ชนิด bool
   3) 3 + 4 * 5      → ชนิด int
   4) 7 / 2          → ชนิด int
   5) -(2 + 3)       → ชนิด int
   6) 3 > 2          → ชนิด bool
   7) 1 == 1         → ชนิด bool
   8) 1 != 2         → ชนิด bool
```

สังเกต `7 / 2` ได้ `int` (เพราะภาษาเราตัดเศษทิ้ง — การหารจำนวนเต็ม) และ `3 > 2` ได้ `bool` (เพราะการเปรียบเทียบให้ค่าจริง/เท็จ) ทั้งหมดนี้คือกติกาที่เราประกาศไว้ในตารางด้านบน ครบถ้วนตรงกัน

ตัวตรวจชนิดรู้จัก "ชนิด" แล้ว แต่มันยังตอบคำถามสำคัญอีกข้อไม่ได้: เวลาเจอชื่อ `x` มันจะรู้ได้ยังไงว่า `x` ตัวนี้คือตัวไหน (ถ้าโปรแกรมมี `x` อยู่สองตัว คนละตำแหน่ง)? คำตอบอยู่ที่ "ขอบเขต" (scope) ซึ่งเป็นของชิ้นที่สอง

## 3. ของชิ้นที่ 2 — scope: ชื่อตัวแปรมี "เขตที่มองเห็น"

ตอนที่ 28 `env` (ที่เก็บค่าตัวแปร) เป็น map (แผนที่ = โครงสร้างเก็บคู่ "ชื่อ→ค่า") แบนชั้นเดียว — ประกาศชื่อซ้ำ = ทับค่าเดิมทันที และทุกชื่อมองเห็นกันหมดทั้งโปรแกรม แต่ของจริงโปรแกรมเมอร์ใช้ทุกวันมีกฎที่ละเอียดกว่านั้น:

> **scope** (ขอบเขต) = บริเวณของโปรแกรมที่ชื่อหนึ่ง "มองเห็นได้" (เข้าถึงได้) บล็อก `{ }` แต่ละอันเปิดขอบเขตใหม่ ตัวแปรที่ประกาศข้างในอยู่ได้แค่ในบล็อกนั้น

ผลตามมาของ scope มีสองอย่าง ที่เราจะเห็นในโปรแกรม 02:

**ผลที่ 1 — shadowing (การบัง):** ชื่อที่ประกาศในบล็อก "บัง" ชื่อเดียวกันในชั้นนอกชั่วคราว แต่**ไม่ทำลาย**ค่าของชั้นนอก

```text
 1 | let x = 10;
 2 | if true {
 3 |   let x = 99;
 4 |   print x;
 5 | }
 6 | print x;
```

รันแล้วได้ผลลัพธ์ `99` แล้วตามด้วย `10` — ลองดูว่า env เปลี่ยนไปยังไงระหว่างเดิน (ตอนนี้ env กลายเป็น "ห่วงโซ่ของ scope" แล้ว):

```text
    let x      = 10     → env { x = 10 }
  env chain: [0]{x=10}                          ← scope 0 (ขอบเขตโปรแกรม)
    block { … } → เปิด scope 1 · ทำ 2 คำสั่ง
        let x      = 99     → env { x = 99 }
        print 99          → เขียน "99" ออกจอ
  env chain: [0]{x=10}                          ← ออกจากบล็อกแล้ว scope 1 หายไป
    print 10          → เขียน "10" ออกจอ
```

(ย่อ: ตัด trace ย่อยของ eval ออก ดูฉบับเต็มใน `out/02_scope.out.txt`)

> **scope chain** (ห่วงโซ่ขอบเขต) = การซ้อน scope หลายชั้นซ้อนกัน เหมือน `[0]` ครอบ `[1]` ครอบ `[2]` ... เวลาหาชื่อตัวแปร เราจะเดินจากชั้นในสุดออกไปนอกสุด แล้วเจอชั้นไหนก่อนก็ใช้ชั้นนั้น

**ผลที่ 2 — ตัวแปรในบล็อกมองไม่เห็นจากข้างนอก:** ลองประกาศ `inner` ไว้ในบล็อก แล้วใช้มันข้างนอก:

```text
  checker: error → line 6, column 7: undefined variable "inner"
  (hint: declare it first, e.g. 'let inner = 1;')
```

โปรแกรมนี้**ผ่าน parser** (รูปประโยคถูกต้องทุกตัว) แต่ตัวตรวจชนิดจับได้ว่า `inner` เกิดและตายอยู่ในบล็อก — พอออกมานอกบล็อกแล้วโลกภายนอกไม่รู้จักชื่อนี้ นี่คือจุดที่ภาษาจิ๋วของเราเริ่ม "เหมือนภาษาจริง" แล้ว

![scope: บล็อก { } = เขตที่มองเห็น ซ้อนกันได้](/assets/diagrams/ep29-02-scope.svg)

ในโค้ดจริง เรื่องนี้ฝังอยู่ในโครงสร้างข้อมูลเดียว: `Env` ของตอน 28 เปลี่ยนจาก `map[string]Value` (แผนที่ชื่อ→ค่า ชั้นเดียว) เป็น `[]map[string]Value` (รายการของแผนที่ ซ้อนกันหลายชั้น) ส่วน `Table` ของตัวตรวจชนิดก็ใช้โครงเดียวกันเป๊ะ แค่เก็บ "ชนิด" แทน "ค่า" — ความเรียบนี้คือเหตุผลที่ `Env` (ตัวเก็บค่า) กับ `Table` (ตัวเก็บชนิด) "ตรงกัน" ได้เสมอ

## 4. ของชิ้นที่ 3 — symbol table: สะพานเชื่อม "ชื่อ" กับ "ความหมาย"

ถึงตรงนี้เรามีตัวตรวจชนิดที่รู้จักชนิด และมี scope ที่แบ่งเขตการมองเห็น แต่ยังขาดของชิ้นสุดท้ายที่ผูกสองอย่างแรกเข้าด้วยกัน: **ตัวตรวจชนิดจะจำได้ยังไงว่า `x` ตัวนี้เป็น int?**

> **symbol table** (ตารางสัญลักษณ์) = โครงสร้างข้อมูลที่จดชื่อทุกตัวที่โปรแกรมประกาศไว้ พร้อมข้อมูลของชื่อนั้น — ในคอมไพเลอร์จริงมันเก็บ "ชื่อ → ชนิด + อยู่ scope ไหน + ประกาศตรงไหน"

เวลาตัวตรวจชนิดเจอชื่อ `x` ในนิพจน์ มันไม่ได้ "เดา" ชนิด — มันเปิดตารางสัญลักษณ์แล้วถามว่า "x คืออะไร" ตารางตอบกลับมาเป็นก้อนข้อมูลสามอย่าง (ใน Go เราเก็บก้อนนี้ด้วย struct — กล่องที่รวมข้อมูลหลายช่องไว้ด้วยกัน):

```go
type Symbol struct {
	Name       string        // ข้อความของชื่อ เช่น "x"
	Type       Type          // ชนิดที่ชื่อนี้ถืออยู่ (int/bool)
	ScopeDepth int           // อยู่ใน scope ระดับไหน (0 = ขอบเขตโปรแกรม)
	Pos        lexer.Position // ประกาศไว้ตรงไหน (line:column)
}
```

โปรแกรม 03 รันตัวตรวจชนิดบนโปรแกรมตัวหนึ่ง แล้ว **dump** (เททิ้งออกมาให้ดู) ตารางสัญลักษณ์ทั้งก้อน:

```text
  name     type   scope  declared
  flag     bool   0      line 2, column 1
  x        int    0      line 1, column 1
  z        int    0      line 8, column 1
  x        int    1      line 5, column 3
  y        int    1      line 4, column 3
```

อ่านตารางนี้แล้วเห็นอะไรหลายอย่าง:

- `flag` เป็น `bool` ประกาศที่บรรทัด 2 · `x` `z` เป็น `int` อยู่ scope 0 (ขอบเขตโปรแกรม)
- มีชื่อ `x` **สองตัว** — ตัวแรก scope 0 (บรรทัด 1) ตัวที่สอง scope 1 (บรรทัด 5) นี่คือ shadowing ที่ตัวตรวจยอมให้ เพราะอยู่คนละ scope
- `y` กับ `x` ตัวที่สองอยู่ใน scope 1 (บล็อก if) — เกิดและตายในบล็อก

![ตารางสัญลักษณ์: ชื่อ → ชนิด + scope + ตำแหน่ง](/assets/diagrams/ep29-03-symbol-table.svg)

นี่คือ "สะพาน" ที่ทำให้ชื่อในโค้ดมีความหมาย — และเป็นของชิ้นที่**ขาดไม่ได้**สำหรับตอนที่ 30 เพราะตอนที่เราเปลี่ยนจาก "เดินต้นไม้" ไปเป็น "สร้างโค้ดเครื่อง" เราต้องรู้ชนิดของทุกตัวแปร เพื่อเลือกคำสั่งเครื่องให้ถูก (ยกตัวอย่างในภาษา Go จริง: บวกเลขจำนวนเต็มใช้คำสั่งหนึ่ง บวกเลขทศนิยมใช้อีกคำสั่งหนึ่ง — ภาษาจิ๋วของเรามีแค่ int จึงมีแค่ชุดเดียว)

## 5. ด่านใหม่ (ด่าน 3): type errors — จับความผิดได้ก่อนรัน

ตอนนี้ครบสามชิ้นแล้ว เรามาดูว่ามันทำงานร่วมกันเป็น "ด่านตรวจ" ได้จริงยังไง โปรแกรม 04 เอาโปรแกรมผิด ๆ 6 ตัวมาผ่านตัวตรวจชนิด — จำไว้ว่า**ทุกตัวผ่าน parser สบาย** เพราะรูปประโยคถูกต้องหมด ความผิดเพิ่งโผล่ตอนตรวจชนิด:

```text
 1) บวก int กับ bool
    let x = 1 + true;
    checker: error → line 1, column 11: cannot use operator "+" with int and bool

 2) ใช้ตัวแปรที่ยังไม่ประกาศ
    print z;
    checker: error → line 1, column 7: undefined variable "z"

 3) ประกาศชื่อซ้ำใน scope เดียวกัน
    let a = 1; let a = 2;
    checker: error → line 1, column 12: "a" redeclared in this scope
    interpreter (ถ้าไม่ตรวจก่อน): รันผ่านเงียบ ๆ (พลาด!)

 4) เงื่อนไข if ไม่เป็น bool
    if 1 { print 2; }
    checker: error → line 1, column 4: condition must be bool, got int

 5) เปรียบเทียบ int กับ bool
    let b = 1 == true;
    checker: error → line 1, column 11: cannot compare int with bool

 6) เครื่องหมายลบหน้าค่า bool
    let c = -(true);
    checker: error → line 1, column 9: operator "-" is not defined on bool
```

สองจุดที่อยากให้สังเกตเป็นพิเศษ:

**จุดที่ 1 — ตำแหน่ง error ชี้เป๊ะ:** ทุก error มาพร้อม `line, column` (บรรทัด:คอลัมน์) เหมือน error ของ lexer/parser/interpreter เป๊ะ — เพราะทั้งสี่ด่านใช้โครงสร้าง `Position` ตัวเดียวกัน นี่คือเหตุผลที่คอมไพเลอร์จริงรายงานตำแหน่งได้แม่นยำขนาดนั้น

**จุดที่ 2 — checker จับได้มากกว่า interpreter:** ดูเคส 3 (`let a = 1; let a = 2;`) — ถ้าไม่มีตัวตรวจชนิด interpreter จะ "รันผ่านเงียบ ๆ" (ประกาศซ้ำ = เขียนทับ) แต่ตัวตรวจชนิดจับได้ว่า "ประกาศซ้ำใน scope เดียวกัน" เพราะการประกาศซ้ำเป็น**ความผิดเชิงความหมาย** ไม่ใช่ความผิดของค่า — ไม่มีทางที่ interpreter จะรู้ได้เลยว่ามัน "ตั้งใจเขียนทับ" หรือ "ลืมไปว่าประกาศแล้ว"

นี่คือบทเรียนใหญ่ของตอนนี้: **มี error หลายชนิดที่ "รันก็ไม่เจอ" มีแต่การตรวจชนิดเท่านั้นที่จับได้**

## 6. ของจริง: go/types ทำแบบนี้เป๊ะ (และ Go ก็มีตารางสัญลักษณ์ของตัวเอง)

ตัวตรวจชนิดที่เราเขียนไม่ใช่ "ของเล่นที่แต่งขึ้น" — Go มีตัวตรวจชนิดจริงอยู่ใน standard library (ไลบรารีมาตรฐานที่มาพร้อมภาษา) ชื่อ `go/types` ซึ่งคอมไพเลอร์ตัวจริงใช้ โปรแกรม 05 เทียบผลของเรากับของ Go สำหรับนิพจน์ชุดเดียวกัน:

```text
  3            ของเรา=int   go/types=int     ✓
  true         ของเรา=bool  go/types=bool    ✓
  3 + 4 * 5    ของเรา=int   go/types=int     ✓
  7 / 2        ของเรา=int   go/types=int     ✓
  3 > 2        ของเรา=bool  go/types=bool    ✓
  1 == 1       ของเรา=bool  go/types=bool    ✓
  1 != 2       ของเรา=bool  go/types=bool    ✓
  → ชนิดตรงกัน 7/7 นิพจน์
```

ส่วนนิพจน์ที่ผิด ทั้งสองฝ่ายก็จับได้เหมือนกัน (สำนวนต่างกัน เพราะคนละเครื่องมือ):

```text
  1 + true     ของเรา: cannot use operator "+" with int and bool
               go/types: invalid operation: 1 + true (mismatched types untyped int and untyped bool)
```

และที่สำคัญที่สุด — โปรแกรม 07 พิสูจน์ว่า **Go ก็สร้างตารางสัญลักษณ์ของตัวเอง** ตอนแปลงโค้ดเป็นโปรแกรม (เราเรียกเครื่องมือ `go/types` ของ Go มาตรวจ แล้วขอรายการชื่อที่ Go ประกาศไว้ผ่าน `info.Defs`):

```text
ตารางสัญลักษณ์ที่ Go สร้าง (เรียงตามลำดับที่สคริปต์คัดออกมา):
  name     kind     type         declared
  main     func     func()       10:6
  n        var      int          11:2
  counter  var      int          3:5
  x        var      int          5:10
  y        var      int          5:17
  add      func     func(x int, y int) int  5:6
  z        var      int          6:2
```

เห็นโครงสร้างเหมือนของเราเป๊ะ — **ชื่อ + ชนิด + ตำแหน่งที่ประกาศ** ต่างกันแค่ Go มีชนิดมากกว่า (func, var) และเก็บ scope เป็นก้อน ส่วนของเราเก็บเป็นห่วงโซ่ นี่คือข้อพิสูจน์ว่า "ตารางสัญลักษณ์" เป็นแนวคิดสากลของวงการคอมไพเลอร์ ไม่ใช่สิ่งประดิษฐ์ของภาษาจิ๋วในบทเรียนนี้

> **untyped** (อันไทป์ = ยังไม่ผูกชนิด) ที่โผล่ในข้อความของ go/types หมายถึง "ค่าคงที่" (ค่าที่เขียนตรง ๆ ในโค้ด เช่น `3` หรือ `true`) ซึ่งยังไม่ถูกผูกกับตัวแปร จึงยังไม่ "ลงหลักปักฐาน" เป็นชนิดเต็ม — ภาษาจิ๋วของเราตัดความซับซ้อนนี้ทิ้งไป (เลข 3 เป็น int ตรง ๆ) จึงเทียบกับของ Go ได้หลังจากตัดคำว่า untyped ออก

## 7. ปิดวงจร: ไปป์ไลน์ใหม่ของภาษาจิ๋ว

ตอนนี้ภาษาจิ๋วของเรามีครบสี่ด่าน ไล่จากต้นทางไปปลายทาง:

```text
ด่าน 1 lexer    : ข้อความ → token        (จับ: พิมพ์ผิด ตัดคำไม่ได้)
ด่าน 2 parser   : token → ต้นไม้          (จับ: วงเล็บไม่ครบ เครื่องหมายตกหล่น)
ด่าน 3 checker  : ต้นไม้ → ชนิด (ใหม่!)   (จับ: บวก int กับ bool, ใช้ตัวแปรไม่ประกาศ)
ด่าน 4 interpreter : ต้นไม้ → ค่า         (จับ: หารด้วยศูนย์, ค่าที่ไหลผิด)
```

(หมายเหตุ: ตอนที่ 28 เราเรียก interpreter ว่า "ด่านที่สาม" เพราะตอนนั้นมีแค่ lexer → parser → interpreter — พอตอนนี้สอด checker เข้ามาเป็นด่านสาม interpreter จึงเลื่อนเป็น "ด่านที่สี่")

ของจริงคอมไพเลอร์ก็เรียงแบบนี้ (เรียกว่า "เฟส" — phase) แต่ละด่านมีหน้าที่เดียว จับความผิดคนละชนิด และรายงานตำแหน่งกลับมาให้มนุษย์แก้ — นี่คือเหตุผลที่ข้อความ error ของ Go/C ละเอียดและแม่นยำขนาดนั้น

ตอนที่ 30 เราจะเดินต่อจากจุดนี้: เมื่อเรารู้ชนิดของทุกนิพจน์และมีตารางสัญลักษณ์ครบแล้ว ขั้นถัดไปตามธรรมชาติคือ **codegen** (การสร้างโค้ด) — เปลี่ยนต้นไม้ให้กลายเป็นภาษาแอสเซมบลี (assembly) ที่เครื่องอ่านได้จริง ตอนนั้นความรู้เรื่องชนิดจากตอนนี้จะเป็นสิ่งที่เราต้องใช้ทันที

4. ประกาศ `let x = 10;` แล้วในบล็อกประกาศ `let x = true;` — ชนิดของ `x` ชั้นนอกกับชั้นในคืออะไร และทำไมไม่ชนกัน?
5. `let a = 1; let a = 2;` — ตัวตรวจชนิดจับได้ แต่ interpreter รันผ่านเงียบ ๆ ทำไมถึงเป็นแบบนั้น?

### Mini-project (ต่อยอดจาก `internal/check` และ `internal/parser`)

ก่อนเริ่ม รู้จักโครงไฟล์ที่ต้องแตะ: **`internal/check/check.go`** = ตัวตรวจชนิด + ตารางสัญลักษณ์ทั้งหมด · **`internal/eval/eval.go`** = ตัวเดินต้นไม้ (ตอนนี้ env มี scope แล้ว) · **`internal/parser/ast.go` + `parser.go`** = ชนิด node + ตัว parse · **`internal/lexer/lexer.go`** = ตัวตัดคำ · รันทุกอย่างพร้อมกันด้วย `bash run_all.sh` (สคริปต์ที่สั่งรันทุกโปรแกรมในโฟลเดอร์เดียว)

ให้ทำสามอย่างเรียงจากง่ายไปยาก (ข้อ 1–2 ต้องแตะครบทั้งสามชั้น — lexer → parser → checker):

1. **เพิ่มชนิดที่สาม: `string` (ข้อความ)** — ต้องเติมครบสามชั้นเช่นกัน:
   - lexer: เพิ่ม token `STRING` สำหรับข้อความในเครื่องหมาย `"..."`
   - parser: เพิ่ม node `StringLit` (อย่าลืมเติมลงใน `childrenOf` ของ ast.go)
   - checker: เพิ่มชนิด `String` เข้าไปใน `Type` แล้วเติมกฎให้ `StringLit → String` และ `+` ต่อ string ได้ (ต่อข้อความ)
   - ทดสอบว่า `let s = "hi" + "!"; print s;` ผ่านการตรวจแล้วรันได้
2. **เพิ่ม type annotation (การเขียนชนิดกำกับ)** — ให้เขียน `let x: int = 3;` ได้ (ตอนนี้ภาษา infer ชนิดเอง ข้อนี้ให้เขียนกำกับได้):
   - lexer: เพิ่ม token `COLON` สำหรับ `:`
   - parser: ใน `parseLet` ให้อ่าน `: TYPE` ที่เป็น optional (มีก็ได้ไม่มีก็ได้)
   - checker: ถ้ามี annotation ให้**เทียบ**ว่าชนิดที่เขียนกับชนิดที่ infer ได้ตรงกันไหม — ไม่ตรงกัน = error (นี่คือจุดที่ภาษาที่มี type annotation จริงจับผิดได้ เช่น เขียนว่า `int` แต่ค่าเป็น `true`)
   - ทดสอบว่า `let x: int = 3;` ผ่าน และ `let x: bool = 3;` โดนจับ
3. **รายงาน error ครบทุกจุดในรอบเดียว** — ตอนนี้ `Checker.Check` เก็บ error ไว้ใน `c.errs` แล้ว แต่คืนแค่ตัวแรก ลองเขียนฟังก์ชันที่พิมพ์ error ทั้งหมดออกมา (เหมือนคอมไพเลอร์จริงบางตัวที่รายงานหลายจุดพร้อมกัน) แล้วทดสอบกับโปรแกรมที่ผิดหลายจุด เช่น `let x = 1 + true; print y;`

- บทความนี้เขียนและรันโค้ดจริงเมื่อ **2026-10-02** (เวลาประเทศไทย) บน **Raspberry Pi 5 Model B Rev 1.0**, Linux 6.18.39+rpt-rpi-2712 (aarch64), ภาษา **Go 1.24.4 (linux/arm64)**, RAM 7.9 GiB · เครื่องมือที่ใช้สร้างและตรวจภาพ: Python 3.13.5 (สร้าง SVG) และ `rsvg-convert` 2.60.0 (render ตรวจตาด้วยภาพ)
- ตัวเลขและข้อความทุกตัวที่ยกมาในบทความ (ชนิดของทุกนิพจน์, ตารางสัญลักษณ์ทั้งก้อน, บรรทัด:คอลัมน์ในข้อความ error ทั้งหมด, และผลเทียบกับ `go/types` ของ Go) เป็นค่าที่**คัดจากผลรันจริง**ใน `course/code/ep29/out/` ไม่ได้พิมพ์จากความจำ
- ภาพ SVG ทุกภาพ (4 ภาพ) สร้างจากสคริปต์ `gen_svgs.py` — ตารางสัญลักษณ์ (ภาพ 3) และสภาพแวดล้อมอ่านค่าจากผลรันโดยตรง และสคริปต์จะหยุดทำงานทันทีถ้าจำนวนแถวไม่ตรงกับที่คาด
- บล็อก "ผลรันจริง" บางส่วนถูกย่อเพื่อความกระชับ (ตัด trace บางบรรทัด) — ค่าตัวเลขและข้อความ error ทุกตัวไม่ถูกเปลี่ยนแปลง ดูฉบับเต็มได้ใน `out/`
- ค่าที่อาจแปรผันตามเครื่องมีเท่านั้น: เวอร์ชันของ Go/rsvg/Python, ชื่อและรุ่นของ CPU, ปริมาณ RAM และวันที่รัน — ตรรกะและชนิดของนิพจน์ในตัวอย่างโค้ดไม่แปรผันตามเครื่อง
- ข้อเท็จจริงเชิงแนวคิดในบทนี้ (type system แบบ static/dynamic, scope, symbol table, ไปป์ไลน์ lexer→parser→type checker→codegen) เป็นความรู้ตั้งหลักมาตรฐานในสาขาการเขียนคอมไพเลอร์ ณ เวลาที่เขียน
- เทคโนโลยีและซอฟต์แวร์พัฒนาต่อเนื่องเสมอ — เนื้อหาในที่นี้สะท้อนสถานะ ณ เวลาที่เขียน หากเวอร์ชันภาษา Go เครื่องมือ หรือรูปแบบ API ของ standard library เปลี่ยนไปในอนาคต ควรตรวจสอบกับเอกสารปัจจุบันอีกครั้ง
