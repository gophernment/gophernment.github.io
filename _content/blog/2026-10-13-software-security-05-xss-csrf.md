# XSS + CSRF (1999–): วันที่ข้อมูลของเรากลายเป็นสคริปต์ในเบราว์เซอร์ของคนอื่น (ตอนที่ 05)

> 📅 เขียนเมื่อ: 13 ตุลาคม 2026 (เวลาไทย, UTC+7) | โค้ดในบทนี้ทดสอบจริงบน Raspberry Pi 5 (Linux 6.18.39, aarch64) ด้วย **Go toolchain 1.27.1** (เครื่องติดตั้ง Go 1.24.4 ไว้ แต่ `go.mod` ของตอนนี้กำหนด `go 1.27.1` Go จึงสลับ toolchain ให้อัตโนมัติ) — ตอนนี้ใช้ **standard library ล้วน** (`net/http`, `html/template`, `net/http/httptest`, `net/url`) ไม่มี dependency ภายนอกเลย · **Python 3.13.5** · **rsvg-convert 2.60.0** · **curl 8.14.1** · ส่วนการพิสูจน์ว่า "สคริปต์รันจริงในเบราว์เซอร์" ทำด้วยเบราว์เซอร์จริง **HeadlessChrome 151.0.0.0** ผ่าน lab server ที่ฟังเฉพาะ loopback
> ⚠️ เครื่องมือและภาษาเปลี่ยนเวอร์ชันเรื่อย ๆ — ก่อนใช้จริงให้ตรวจเอกสารทางการล่าสุดเสมอ · เวอร์ชันล่าสุดของ Go ณ วันเขียน (ตรวจเมื่อ 2026-10-13): **Go 1.27** ออก **19 สิงหาคม 2026** และ **Go 1.27.1** ออก **1 กันยายน 2026** (<https://go.dev/doc/devel/release>)
> 🛡️ **จริยธรรม:** ตอนนี้สอนกลไกของ **XSS** (การทำให้ข้อมูลของเรา "กลายเป็นสคริปต์" ที่รันในเบราว์เซอร์ของคนอื่น) และ **CSRF** (การหลอกให้เบราว์เซอร์ของเหยื่อส่งคำขอที่เหยื่อไม่ได้ตั้งใจส่ง) ตรง ๆ — เดโมและโจทย์ทุกข้อในบทนี้ **ทำใน environment ที่คุณควบคุมเองเท่านั้น** (เครื่องตัวเอง, VM, container หรือ lab ที่ตั้งใจให้ทดลอง) **ห้ามใช้เทคนิคเหล่านี้กับระบบของคนอื่นโดยไม่ได้รับอนุญาต** ซึ่งผิดกฎหมายในแทบทุกประเทศ
>
> เดโมของเรา **รันบน `127.0.0.1` (loopback) เท่านั้น ไม่ผูกกับ `0.0.0.0` ไม่มีข้อมูลจริง ไม่เชื่อมต่อเครือข่ายภายนอก และไม่มีเป้าให้ยิง** — เราสร้างเซิร์ฟเวอร์ของตัวเองขึ้นมาเพื่อดูว่า "เบราว์เซอร์ตีความอะไร" และไฟล์ที่สอนฝั่งที่พังเขียนกำกับไว้ชัดว่า **"ห้ามใช้จริงกับระบบของคนอื่น"**

ใน[ตอนที่ 04](/blog/post.html?slug=2026-10-12-software-security-04-sql-injection) เราเห็นว่า **ฐานข้อมูล** อ่าน "ข้อความก้อนเดียว" แล้วตีความค่าของผู้ใช้เป็น **ไวยากรณ์** ของคำสั่ง SQL · ใน[ตอนที่ 03](/blog/post.html?slug=2026-10-11-software-security-03-smashing-the-stack) เราเห็น **CPU** อ่านไบต์ในหน่วยความจำแล้วตีความเป็น **คำสั่งเครื่อง**

วันนี้เราจะเจอ **interpreter** (โปรแกรมที่อ่านข้อความ/ข้อมูลแล้วตีความเป็นความหมาย — คำนี้เรานิยามไว้ตั้งแต่ตอนที่ 04) อีกตัวหนึ่งที่ทุกคนมีอยู่ในเครื่องแล้ว และทำงานกับเราทุกวัน: **เบราว์เซอร์**

และบทเรียนจะซ้ำเดิมแบบน่าขนลุก: **ที่ไหนก็ตามที่ interpreter อ่าน "ข้อมูลของเรา" เป็น "คำสั่งของมัน" ที่นั่นคือช่องโหว่**

ก่อนไปต่อ ขอนิยามศัพท์ที่จะใช้ทั้งบทให้ตรงกันก่อน เพราะตอนนี้มีศัพท์ใหม่หลายตัว:

- **XSS** (Cross-Site Scripting) = ช่องโหว่ที่ทำให้ข้อมูลจากผู้ใช้กลายเป็น **HTML หรือสคริปต์ที่เบราว์เซอร์รัน** ในหน้าเว็บของเรา · ชื่อเต็มของมันคือ "cross-site scripting" เพราะ**สิ่งที่ถูกฉีด** เดินทาง "ข้ามเว็บ" มาจากที่อื่น (คำนี้จะเล่าให้ครบในหัวข้อ 2.1) · ในระบบหมายเลขมาตรฐานของช่องโหว่ มันคือ **CWE-79** (**CWE** = Common Weakness Enumeration ทะเบียน*คลาส*ของจุดอ่อนซอฟต์แวร์ — นิยามไว้แล้วในตอนที่ 04)
- **CSRF** (Cross-Site Request Forgery — "cross-site request forgery") = การหลอกให้ **เบราว์เซอร์ของเหยื่อ** ส่งคำขอที่เหยื่อไม่ได้ตั้งใจส่ง ไปยังเว็บที่เหยื่อล็อกอินค้างไว้ · มันคือ **CWE-352**
- **cookie** (คุกกี้) = ข้อมูลก้อนเล็ก ๆ ที่เซิร์ฟเวอร์สั่งให้เบราว์เซอร์เก็บไว้ แล้วเบราว์เซอร์จะแนบกลับไปกับทุกคำขอถัดไปที่ไปยังเว็บนั้น — ใช้จำว่า "ใครล็อกอินอยู่" · **session** (เซสชัน) = "ช่วงเวลาที่ผู้ใช้ล็อกอินอยู่" ที่ฝั่งเซิร์ฟเวอร์จำไว้ · ทั้งคู่ผูกกันด้วยคุกกี้ที่เป็นตัวระบุเซสชัน (มักชื่อ `sid`)
- **sanitize** (ทำความสะอาดข้อมูล) = พยายาม "ลบ/กรอง" ส่วนอันตรายออกจากข้อมูลก่อนเอาไปใช้ (เช่น ตัดแท็ก `<script>` ทิ้ง) · **output encoding / escaping** (การเข้ารหัสตอนส่งออก) = ไม่แตะข้อมูล แต่**แปลงค่าตอนประกอบเอกสาร** ให้ interpreter มองมันเป็น "ข้อความ" ไม่ใช่ "ไวยากรณ์" — สองวิธีนี้ให้ผลต่างกันมาก และบทนี้จะพิสูจน์ให้เห็นด้วยโค้ดจริง
- **same-origin policy** (นโยบาย "แหล่งกำเนิดเดียวกัน") = กฎของเบราว์เซอร์ที่ว่า เอกสารจาก origin หนึ่งจะอ่าน/แก้ข้อมูลของอีก origin ไม่ได้ · คำว่า **origin** ไม่ใช่แค่ชื่อเว็บ แต่คือ **scheme + host + port** รวมกัน (เช่น `https://example.com:443` กับ `http://example.com:443` เป็นคนละ origin · `example.com:3000` กับ `example.com:3001` ก็คนละ origin)
- **CSP** (Content Security Policy) = header (**header** = ส่วนหัวของคำตอบ HTTP ที่เซิร์ฟเวอร์ส่งมาก่อนเนื้อหา) ที่เว็บบอกเบราว์เซอร์ว่า "หน้านี้โหลด/รันอะไรได้บ้าง" — เป็นเกราะชั้นที่สองที่ทำงานแม้เราพลาดการเข้ารหัส
- **HttpOnly cookie** = คุกกี้ที่ใส่ attribute `HttpOnly` กำกับไว้ (**attribute** = ค่าที่เขียนกำกับไว้กับแท็ก หรือคุกกี้ เช่น `Path`, `HttpOnly`, `SameSite`) → สคริปต์ในหน้าเว็บอ่านค่าของมันผ่าน `document.cookie` ไม่ได้ (แต่มันยังถูกส่งไปกับคำขอปกติ)
- **SameSite cookie** = attribute ที่บอกเบราว์เซอร์ว่า "คุกกี้ตัวนี้ให้แนบไปกับคำขอ *ข้าม site* หรือไม่"

> **ประโยคเดียวที่เป็นหัวใจของทั้งบทนี้:** ข้อมูลของเราปลอดภัยหรือไม่ ขึ้นอยู่กับว่า **ตอนที่มันถูกประกอบเข้าไปในเอกสาร** เราทำให้มันเป็น "ข้อความ" แล้วหรือยัง

ถ้าคุณเข้าใจประโยคนี้ และเข้าใจว่าทำไม **การกรองตอนรับเข้า** ถึงไม่เคยพอ แต่ **การเข้ารหัสตามบริบทตอนส่งออก** ถึงพอ — คุณเข้าใจ XSS ทั้งคลาส

วันนี้เราจะทำห้าอย่าง:

1. เข้าใจว่า **ทำไม "ข้อมูล" ถึงกลายเป็น "สคริปต์" ได้** — และทำไมบริบทมีผลกับการเข้ารหัส
2. ไปดู **ปี 1999–2000 ที่คำว่า XSS ถูกตั้งขึ้น** และ **4 ตุลาคม 2005 ที่หนอนตัวหนึ่งทำให้เว็บทั้งเว็บต้องปิดตัว**
3. **ลงมือเขียนเซิร์ฟเวอร์ Go จริง** ที่มีทั้งเวอร์ชันที่พังและเวอร์ชันที่ถูก แล้วเทียบผลรัน (รวมถึงเปิดในเบราว์เซอร์จริงเพื่อดูว่าสคริปต์รันหรือไม่)
4. ต่อด้วย **เดโม CSRF** ที่จำลองเบราว์เซอร์สี่แบบ (ไม่มีเกราะ / SameSite / token / มี XSS) แล้วดูว่าแต่ละเกราะกันได้แค่ไหน
5. ปิดท้ายด้วย **กับดักที่คนพลาดมากที่สุด** สามข้อ

## 1. แนวคิด: เบราว์เซอร์คือ interpreter ที่อ่านหน้าของเราเป็น "คำสั่ง"

### 1.1 ข้อมูลหนึ่งก้อน สองการตีความ

ลองนึกภาพว่ามีสตริงสั้น ๆ แบบนี้ (**HTML** = ภาษาที่ใช้บรรยายโครงสร้างหน้าเว็บ ด้วย **แท็ก** อย่าง `<div>` และ `<script>` — เบราว์เซอร์อ่าน HTML แล้วสร้างหน้าเว็บขึ้นมาจากมัน):

```html
<script>alert(1)</script>
```

ถ้าเราเก็บสตริงนี้ลงฐานข้อมูลแล้วอ่านออกมาเป็นข้อมูล มันก็คือข้อความธรรมดา ๆ หนึ่งก้อน — ไม่มีอะไรอันตรายเลย

แต่ถ้าเราประกอบมันลงไปในหน้าเว็บแบบนี้:

```html
<div class="result">results for: <script>alert(1)</script></div>
```

แล้วส่งเอกสารนั้นให้เบราว์เซอร์ — เบราว์เซอร์จะทำในสิ่งที่มันถูกออกแบบให้ทำ: **สร้างแท็ก `<script>` ขึ้นมาหนึ่งตัว แล้วรันโค้ดข้างใน**

นี่คือความต่างเดียวกับตอนที่ 04 เป๊ะ ๆ:

| | ตอน 04 (SQL injection) | ตอน 05 (XSS) |
|---|---|---|
| interpreter ตัวที่อ่าน | parser ของฐานข้อมูล | เบราว์เซอร์ (HTML parser + JS engine) |
| "ข้อมูลของเรา" ถูกตีความเป็น | ไวยากรณ์ของ SQL | แท็ก/สคริปต์ของ HTML |
| ผลลัพธ์ | คำสั่งที่เราไม่ได้เขียนถูกรัน | โค้ดที่เราไม่ได้เขียนถูกรัน **ในเครื่องของคนอื่น** |
| จุดที่ต้องแก้ | ตอน**ประกอบคำสั่ง** (parameterized query) | ตอน**ประกอบเอกสาร** (output encoding) |

ความต่างที่ทำให้ XSS น่ากลัวกว่า SQL injection ในแง่หนึ่งคือ: **โค้ดที่ถูกรัน ทำงานในบริบทของเหยื่อ** — มันรันด้วยสิทธิ์ของ "คนที่กำลังเปิดเว็บนั้นอยู่" ซึ่งหมายความว่ามันอ่านข้อมูลในหน้านั้นได้ ส่งคำขอในนามของเขาได้ และ (ถ้าไม่มีเกราะ) ขโมยคุกกี้ของเขาได้

> **หมายเหตุสำหรับผู้เรียน:** บทนี้ต่อจากตอนที่ 04 โดยตรง — ถ้าคุณเข้าใจว่า "parser ไม่รู้จักคำว่าข้อมูล" คุณเข้าใจกลไกของ XSS ครึ่งหนึ่งแล้ว อีกครึ่งหนึ่งคือ **บริบท (context)** ซึ่งเป็นของใหม่ในบทนี้

### 1.2 ที่มาของปัญหา: เราประกอบสตริงเข้าไปในเอกสาร

นี่คือโค้ดที่คุณจะเจอบ่อยที่สุดในโลกจริง — และมันดูปกติมาก (นี่คือ "บรรทัดที่ผิด" ของบทนี้):

```go
// vulnSearchHandler ❌ ต่อ input เข้าไปใน HTML ตรง ๆ — "ห้ามใช้จริงกับระบบของคนอื่น"
func vulnSearchHandler(w http.ResponseWriter, r *http.Request) {
	q := r.URL.Query().Get("q")
	w.Header().Set("Content-Type", "text/html; charset=utf-8")
	io.WriteString(w, pageHead)
	io.WriteString(w, `<div class="result">results for: `+q+`</div>`)
	io.WriteString(w, pageFoot)
}
```

สังเกตว่าโค้ดนี้ **ไม่ได้ทำอะไรผิดในเชิงวิศวกรรมเลย**: มันตั้ง `Content-Type` ถูกต้อง (**Content-Type** = header ที่บอกว่าเนื้อหาที่ส่งไปเป็นชนิดไหน — ที่นี่คือ `text/html; charset=utf-8`), เขียน header ก่อน body และไม่ได้ซ่อนอะไรไว้เลย ... มันต่างจากเวอร์ชันที่ปลอดภัยตรงที่ **มันเอา `q` ไปต่อกับข้อความ HTML ด้วยตัวเอง**

ผลลัพธ์จริงคือแบบนี้ (นี่คือคำขอ HTTP จริงบน loopback — ไม่ได้ยกมาจากความจำ):

```
# คำขอจริงผ่าน HTTP บน loopback (ไม่ใช่การเรียกฟังก์ชันตรง ๆ) — ผลรันเดียวกับหัวข้อ 3.2 (out/01_xss.txt)
--- GET /vuln?q=%3Cscript%3Ealert(1)%3C%2Fscript%3E ---
<!DOCTYPE html><html lang="th"><head><meta charset="utf-8"><title>ep05 lab</title></head><body><div class="result">results for: <script>alert(1)</script></div></body></html>
--- GET /safe?q=%3Cscript%3Ealert(1)%3C%2Fscript%3E ---
<!DOCTYPE html><html lang="th"><head><meta charset="utf-8"><title>ep05 lab</title></head><body><div class="result">results for: &lt;script&gt;alert(1)&lt;/script&gt;</div></body></html>
```

อ่านสองบรรทัดนี้ให้ครบ เพราะทั้งบทขึ้นอยู่กับมัน:

- **`/vuln`** — เบราว์เซอร์ได้รับ `<script>alert(1)</script>` ที่ยังเป็น **แท็กจริง** → มันจะสร้างและรันสคริปต์นั้น
- **`/safe`** — เบราว์เซอร์ได้รับ `&lt;script&gt;alert(1)&lt;/script&gt;` ซึ่งเป็น **ข้อความ** → มันจะแสดงผลให้ผู้ใช้เห็นเป็นตัวอักษร ไม่รันอะไรทั้งสิ้น

`&lt;` กับ `&gt;` คือ **HTML entity** (การเขียนอักขระพิเศษในรูปข้อความ — `&lt;` คือ "น้อยกว่า" ที่ *ไม่ใช่* ตัวเปิดแท็ก) · งานที่ `/safe` ทำเรียกว่า **output encoding** หรือ **escaping** — แปลงค่าให้เป็นข้อความปลอดภัยตอนที่ประกอบเอกสาร

### 1.3 ต้องเข้ารหัส "ตามบริบท" — เพราะจุดที่ค่าจะไปอยู่ กำหนดว่าอะไรต้องทำให้ปลอดภัย

นี่คือจุดที่คนเข้าใจผิดมากที่สุด: **ไม่มีการเข้ารหัสแบบ "สูตรสำเร็จ" ที่เดียวจบ** ค่าเดียวกัน เมื่อถูกใส่ในตำแหน่งต่างกันของเอกสาร ต้องถูกเข้ารหัสต่างกัน

เราทดลองกับค่าเดียวกันหมด (`O'Reilly <script>alert(1)</script>`) ใน 6 บริบท แล้วให้ **`html/template`** (แพ็กเกจมาตรฐานของ Go ที่รู้จักบริบทของเอกสาร — มันจะแทรกขั้นตอนเข้ารหัสให้เองตอน parse template) แสดงผลออกมา:

```
--- 2) ค่าเดียวกันใน 6 บริบท: html/template เข้ารหัสไม่เหมือนกัน ---
     input: O'Reilly <script>alert(1)</script>
     HTML text      | O&#39;Reilly &lt;script&gt;alert(1)&lt;/script&gt;
     attr (quoted)  | <a title="O&#39;Reilly &lt;script&gt;alert(1)&lt;/script&gt;">x</a>
     attr (unquote) | <a title=O&#39;Reilly&#32;&lt;script&gt;alert(1)&lt;/script&gt;>x</a>
     URI (href)     | <a href="/search?q=O%27Reilly%20%3cscript%3ealert%281%29%3c%2fscript%3e">x</a>
     JS string      | <script>var s = "O\u0027Reilly \u003cscript\u003ealert(1)\u003c\/script\u003e";</script>
     CSS value      | <style>p { color: ZgotmplZ }</style>
```

อ่านทีละบรรทัด สังเกตว่าอักขระเดียวกันถูกเปลี่ยนหน้าตาไม่เหมือนกันเลย:

| บริบท | สิ่งที่ต้องกัน | escape ที่ได้ |
|---|---|---|
| HTML text | ไม่ให้ `<` กลายเป็นตัวเปิดแท็ก | `&lt;script&gt;` |
| attribute (มี quote) | ไม่ให้ปิด attribute แล้วหนีออกมา | `&#39;` (quote ถูกเข้ารหัส) |
| attribute (ไม่มี quote) | ไม่ให้ "ช่องว่าง" จบ attribute | `&#32;` (ช่องว่างถูกเข้ารหัส) |
| URI (ใน `href`) | ไม่ให้ปิดพารามิเตอร์/เติมค่าใหม่ | `%3c`, `%3e` (percent-encode) |
| สตริงใน JavaScript | ไม่ให้ปิด quote แล้วเขียนโค้ดต่อ | `\u003c` (escape ในสตริง JS) |
| ค่าใน CSS | ไม่ให้ค่าที่ไม่ใช่ CSS ผ่านเข้าไป | `ZgotmplZ` (**ถูกปฏิเสธทั้งค่า**) |

`ZgotmplZ` ไม่ใช่ค่าที่ตั้งเล่น ๆ — มันเป็น **sentinel value** (ค่าสัญญาณพิเศษที่โปรแกรมใช้บอกว่า "เกิดกรณีที่ต้องระวัง" — ไม่ใช่ข้อความสำหรับมนุษย์อ่าน) ที่ Go ใช้บอกว่า **unsafe content เข้าไปในบริบทที่ไม่ปลอดภัย** แทนที่จะเดาว่าควรทำอะไร มันเลือก "ไม่ยอมใส่" ซึ่งเป็นพฤติกรรมที่เราต้องการ: **ปลอดภัยตั้งแต่ค่าปริยาย (secure by default)**

> **ศัพท์ที่ต้องรู้:** เวลาคนพูดว่า "escape" ในบริบทเว็บ หมายถึง "แปลงค่าที่มีความหมายพิเศษในบริบทนั้น ให้กลายเป็นข้อความธรรมดา" · งานนี้ทำที่ **ตอนส่งออก** ไม่ใช่ตอนรับเข้า เพราะตอนรับเข้ายังไม่รู้ว่าค่าจะไปอยู่ในบริบทไหน

### 1.4 XSS มีสามหน้าตา — และมันต่างกันที่ "ข้อมูลเดินทางยังไง"

ในทางปฏิบัติ เราแบ่ง XSS เป็นสามแบบ (คำว่า reflected/stored เราจะใช้ซ้ำอีกหลายรอบ):

1. **Reflected XSS** (สะท้อนกลับ) — ค่าที่ผู้ใช้ส่งมา **ถูกสะท้อนกลับไปในคำตอบทันที** โดยไม่ถูกเก็บไว้ · ตัวอย่างจริง: `/search?q=<script>...` แล้วหน้าเว็บเอาคำค้นไปแสดง ("ผลการค้นหาสำหรับ: ...") · ผู้โจมตีต้อง **ล่อให้เหยื่อคลิกลิงก์** ที่มี payload ฝังอยู่ในนั้น · เพราะการโจมตี "ผ่านลิงก์" แบบนี้จึงเป็นที่มาของชื่อ XSS (ดูหัวข้อ 2.1)
2. **Stored XSS** (เก็บไว้) — ค่าที่ผู้ใช้ส่งมา **ถูกเก็บไว้ที่เซิร์ฟเวอร์** (คอมเมนต์, ชื่อโปรไฟล์, ที่อยู่จัดส่ง, ชื่อไฟล์) แล้วค่อยถูกส่งออกไปให้ "ทุกคนที่เปิดหน้านั้น" ในภายหลัง · อันนี้ร้ายแรงที่สุดเพราะ **ไม่ต้องล่อใครเลย** — เหยื่อแค่เปิดหน้าที่มีข้อมูลนั้นก็ติดแล้ว และมันแพร่ได้เองแบบหนอน (นี่คือกรณีของ Samy worm ในหัวข้อ 2.2)
3. **DOM-based XSS** — ไม่เกี่ยวกับเซิร์ฟเวอร์เลย: โค้ด JavaScript ฝั่งเบราว์เซอร์เองเอาค่าจาก URL/ที่อื่นไปใส่ในหน้าเว็บด้วยคำสั่งอย่าง `innerHTML` โดยไม่เข้ารหัส · คำว่า **DOM** (Document Object Model) = โครงสร้างต้นไม้ของเอกสารที่สคริปต์ใช้แก้หน้าเว็บ · เราไม่ได้ลงลึกเรื่องนี้ในบทนี้ แต่ต้องรู้ว่ามันมีอยู่ เพราะแก้ที่เซิร์ฟเวอร์อย่างเดียวไม่ช่วยอะไรกับมัน

### 1.5 แล้ว "กรองตอนรับเข้า" (sanitize) ล่ะ? ทำไมถึงไม่พอ

คำถามที่ตามมาทันทีคือ: *"ถ้ากรอง input ตอนรับเข้าให้สะอาด ก็จบไม่ใช่หรือ"* — บทนี้จะพิสูจน์สามข้อว่าทำไมคำตอบคือ **ไม่**:

1. **ข้อมูล "ที่สะอาดแล้ว" ยังต้องถูกเข้ารหัสอยู่ดี** เพราะบริบทกำหนดหน้าตาของการเข้ารหัส (หัวข้อ 1.3) · ค่าที่ปลอดภัยใน HTML text ไม่ได้แปลว่าปลอดภัยใน `href` หรือในสตริง JS
2. **Deny-list (blacklist) ไม่มีวันครบ** — การ "แบนคำ" (ลบ `<script>` ออก, แบนคำว่า `javascript`) ต้องไล่แบนทุกอย่างที่เบราว์เซอร์ยอมรับ ซึ่งมีมากกว่าที่เราคิด · (เทียบกับแนวทาง **allow-list** — "อนุญาตเฉพาะสิ่งที่รู้ว่าดี" — ที่เราเจอใน[ตอนที่ 04](/blog/post.html?slug=2026-10-12-software-security-04-sql-injection)) · คนที่แบนครบทุกอย่างได้จริงมีอยู่อย่างเดียวคือ **ตัว parser เอง** และนั่นคือสิ่งที่ output encoding ใช้
3. **ข้อมูลเดียวกันถูกใช้หลายที่** — ข้อมูลที่เราเก็บไว้ (ชื่อผู้ใช้ ข้อความคอมเมนต์) จะถูกนำไปใช้ทั้งในหน้าเว็บ, ในอีเมล, ใน log, ใน API — ที่ที่เราลืมเข้ารหัสคือที่ที่พัง

หัวข้อ 3.4 จะโชว์ให้เห็นผลรันจริงทั้งสามข้อนี้ · ส่วนคำถามว่า *"แล้วเราควรตรวจ input หรือไม่"* — คำตอบคือ **ควร** (เพราะมันช่วยเรื่องความถูกต้องของข้อมูล, ช่วยตรวจชนิดข้อมูล, และเป็นเกราะชั้นแรก) แต่ **มันไม่ใช่เกราะกัน XSS** · เกราะกัน XSS อยู่ที่ "ตอนส่งออก" เสมอ

ก่อนลงมือเขียนโค้ด มาดูกันก่อนว่าปัญหานี้ถูก **ค้นพบและตั้งชื่อ** อย่างไร — เพราะชื่อของมันบอกเราว่า "การข้ามเว็บ" สำคัญตรงไหน

## 2. ทำไมสำคัญ: จากชื่อที่เพิ่งถูกตั้ง (1999) ถึงหนอนที่ปิดเว็บทั้งเว็บ (2005)

### 2.1 ปลายปี 1999 — เดือนที่ช่องโหว่ยังไม่มีชื่อ

เรื่องนี้เริ่มจากทีม security ของ **Microsoft** ปลายปี 1999 — ตอนนั้นมีรายงานการโจมตีที่หน้าเว็บของหลายเว็บ "มีแท็กที่ผู้ใช้ไม่ได้เขียน" ติดเข้าไปในหน้าเว็บ (ทั้งแบบที่ติดไปกับ*คำตอบทันที* และแบบที่*ถูกเก็บไว้*ในหน้าโปรไฟล์)

สิ่งที่ไม่มีในตอนนั้นคือ **ชื่อของปัญหา** — จึงเกิดการคุยกันเรื่องชื่อ · บันทึกของทีม (David Ross เขียนไว้ในบล็อกของ *dross* ที่ Microsoft เก็บถาวรไว้) เล่าว่าวันที่ **16 มกราคม 2000** มีการเสนอชื่อหลายแบบ: *Unauthorized Site Scripting*, *Unofficial Site Scripting*, *URL Parameter Script Insertion*, *Cross Site Scripting*, *Synthesized Scripting*, *Fraudulent Scripting* · และ **วันถัดมา (17 ม.ค. 2000) ทีมก็ตกลงกันว่าชื่อคือ "Cross Site Scripting"**

**2 กุมภาพันธ์ 2000** มี advisory (**advisory** = ประกาศเตือนช่องโหว่/คำแนะนำด้านความปลอดภัย ที่หน่วยงานออกให้สาธารณะ) ออกร่วมกันระหว่าง **CERT/CC** (ทีมรับมือเหตุการณ์ของมหาวิทยาลัย Carnegie Mellon) และหน่วยงานความปลอดภัยอื่น ๆ ของสหรัฐฯ: **CA-2000-02 — *Malicious HTML Tags Embedded in Client Web Requests*** · เอกสารนี้คือจุดที่โลกได้อ่านคำอธิบายเรื่องนี้อย่างเป็นทางการเป็นครั้งแรก และเป็นที่มาของคำจำกัดความที่เรายังใช้จนวันนี้:

> "At the heart of this vulnerability is the violation of trust that results from the 'injected' script or HTML running within the security context established for the example.com site."

สองประเด็นที่อยากให้จำจากย่อหน้านั้น:

1. **"violation of trust"** — ปัญหาไม่ใช่ "มีสคริปต์ในหน้าเว็บ" แต่คือ **สคริปต์ที่ผู้โจมตีเขียน กำลังรันด้วยความน่าเชื่อถือที่ผู้ใช้มอบให้เว็บเหยื่อ** · ผู้ใช้เชื่อ `example.com` (เพราะเห็นชื่อใน address bar) แต่โค้ดที่รันอยู่ไม่ใช่ของ `example.com`
2. **ทำไมชื่อจึงมีคำว่า "cross-site"** — เอกสารนั้นอธิบายตรง ๆ ว่า "เพราะมีแหล่งหนึ่ง *ฉีด* โค้ดเข้าไปในหน้าที่ส่งโดยอีกแหล่งหนึ่ง" · กล่าวคือ **ผู้โจมตีข้ามจาก "เว็บของเขา" มาอยู่ใน "เว็บของเหยื่อ"**

### 2.2 4 ตุลาคม 2005 — Samy worm: หนอนที่แพร่ในเวลาไม่ถึงหนึ่งวัน

ปี 2005 **MySpace** คือโซเชียลเน็ตเวิร์กที่ใหญ่ที่สุดในโลก · และสาวกคนหนึ่งของมันชื่อ **Samy Kamkar** (ตอนนั้นอายุ 19) เล่าว่าเขาแค่อยากรู้ว่า *"ใช้ JavaScript ทำให้โปรไฟล์ของฉันเพิ่มเพื่อนอัตโนมัติได้ไหม"* — เขาไม่คิดว่ามันจะแพร่ "ไปเป็นล้าน"

โค้ดที่เขาเขียนกลายเป็น **XSS worm** (หนอน = โปรแกรมที่แพร่ตัวเองได้โดยไม่ต้องมีคนพาไป) ที่รู้จักในชื่อ **Samy** หรือ **JS.Spacehero** · กลไกของมันสั้น ๆ มีสี่ขั้น:

1. **ซ่อนตัวเองในโปรไฟล์ของเหยื่อ** — MySpace กรองคำว่า `javascript`, แบนแท็ก `<script>` และตัด attribute บางตัวออก แต่ Kamkar ประกอบสตริงที่ถูกแบนขึ้นมาใหม่ตอนรัน (ในซอร์สของหนอนมีการเรียก `eval('J.onr'+'eadystatechange=BI')` — คือแบ่งคำว่า `onreadystatechange` เป็นสองท่อนเพื่อให้ตัวกรองที่มองหาคำเต็มมองไม่เห็น)
2. **เมื่อมีคนเปิดโปรไฟล์ที่ติดแล้ว** สคริปต์ก็ทำงานในเบราว์เซอร์ของคนนั้น — **ใน security context ของ MySpace** ไม่ใช่ของ Kamkar
3. **มันก็อปตัวเองลงโปรไฟล์ของเหยื่อ** แล้วส่ง **friend request** ไปหา Kamkar ด้วย AJAX (**AJAX** = ให้สคริปต์ยิงคำขอ HTTP เบื้องหลังโดยไม่ต้องโหลดหน้าใหม่ · ชื่อเต็มคือ Asynchronous JavaScript and XML)
4. **เพื่อให้คำขอนั้นผ่าน** มันอ่าน **token ยืนยันตัวตน** ที่ MySpace ฝังไว้ในหน้านั้น แล้วแนบไปกับคำขอของตัวเอง (ในซอร์สจริงเห็นเป็น `Mytoken=` + ค่าที่อ่านมาจากหน้าเว็บ) — นี่คือประเด็นที่สำคัญมาก และเราจะกลับมาหามันในหัวข้อ 3.8: **XSS ที่อยู่ใน origin เดียวกัน อ่านได้ทุกอย่างที่หน้าเว็บนั้นอ่านได้ รวมทั้ง CSRF token**

ผลลัพธ์: **มากกว่า 1,000,000 โปรไฟล์ติดภายในเวลาไม่ถึง 20 ชั่วโมง** บนแพลตฟอร์มโซเชียลที่ใหญ่ที่สุดในโลกตอนนั้น · MySpace ต้อง **ปิดเว็บทั้งเว็บชั่วคราว** เพื่อล้างโค้ดออกจากทุกโปรไฟล์ · ข้อความที่หนอนทิ้งไว้บนโปรไฟล์เหยื่อทุกหน้าคือ *"but most of all, samy is my hero"*

ส่วน Kamkar: **2006** มีการบุกค้นโดยหน่วย United States Secret Service · **31 มกราคม 2007** เขายอมรับข้อกล่าวหา (plea agreement) · ผลคือ **3 ปี probation** (ภาคทัณฑ์), **90 วัน community service**, **ค่าชดเชยให้ MySpace** (สื่อรายงานว่าไม่เปิดเผยจำนวน — บางแหล่งเล่าว่า 15,000–20,000 ดอลลาร์) และ **โทษจำคุก 20 ปีแบบรอลงอาญา** รวมทั้งข้อห้ามใช้อินเทอร์เน็ตซึ่ง**ภายหลังถูกยกเลิกโดยผู้พิพากษา** (Kamkar เล่าเองในรายการ *Greatest Moments in Hacking History* ของ Motherboard)

> **บทเรียนที่อยากให้ติดตัวจากเรื่องนี้:** หนอนตัวนี้ไม่ได้ใช้ช่องโหว่ใหม่เลย ไม่ได้เจาะเซิร์ฟเวอร์ ไม่ได้ขโมยรหัสผ่าน · มันใช้ "ช่อง XSS แบบ stored" หนึ่งช่อง + เทคนิคมาตรฐานของเว็บ (AJAX, การอ่าน token จากหน้า) · **หนึ่งช่องที่ไม่ได้เข้ารหัส output เพียงพอที่จะทำให้เว็บทั้งเว็บต้องปิดตัว** — และเมื่อคะแนน Top 25 ของปี 2025 ออกมา XSS ก็ยังอยู่อันดับ 1

### 2.3 CSRF: ช่องโหว่ที่ "ไม่มีร่องรอย" — และถูกตั้งชื่อในปี 2001

**CSRF** (ย่อมาจาก **Cross-Site Request Forgery** — ที่มาของชื่อเต็มอยู่ในหัวข้อนี้) เป็นอีกมุมหนึ่งของปัญหา trust เดียวกัน แต่กลับทิศทาง:

- **XSS** ใช้ประโยชน์จาก **ความเชื่อที่ผู้ใช้มีต่อเว็บ** (ผู้ใช้เชื่อว่าสคริปต์ที่รันเป็นของเว็บนั้น)
- **CSRF** ใช้ประโยชน์จาก **ความเชื่อที่เว็บมีต่อเบราว์เซอร์ของผู้ใช้** (เว็บเชื่อว่าคำขอที่แนบคุกกี้ที่ถูกต้องมา = คำขอที่ผู้ใช้ตั้งใจส่ง)

ชื่อ **"Cross-Site Request Forgery"** ถูกตั้งโดย **Peter Watkins** ในโพสต์ไปยัง **Bugtraq** (mailing list ด้าน security ที่ได้รับความนิยมในยุคนั้น) เมื่อ **มิถุนายน 2001** — แต่ตัวแนวคิดเก่ากว่านั้น: มันเป็นตัวอย่างหนึ่งของ **confused deputy** (ผู้ช่วยที่ถูกหลอก) ซึ่ง **Norm Hardy** อธิบายไว้ตั้งแต่ปี **1988** · เบราว์เซอร์คือ "ผู้ช่วย" ที่มีสิทธิ์เข้าถึงข้อมูลของเหยื่อ และถูกหลอกให้ทำธุระให้ผู้โจมตี โดยเจ้าของสิทธิ์ไม่รู้ตัว

กลไกที่ทำให้มันเป็นไปได้นั้นเรียบง่ายจนน่าตกใจ:

1. คุณล็อกอินเข้าเว็บธนาคาร → เบราว์เซอร์เก็บ **คุกกี้ session** ไว้
2. คุณเปิดหน้าเว็บของผู้โจมตี (ลิงก์ในอีเมล, โฆษณา, หน้าเว็บที่ถูกฝัง)
3. หน้านั้นมีฟอร์มที่ **ส่ง POST ไปที่เว็บธนาคารโดยอัตโนมัติ** (หรือใช้ `<img src>` ที่มี URL เป็น action)
4. เบราว์เซอร์แนบ **คุกกี้ของธนาคาร** ไปกับคำขอนั้น **เพราะคำขอ "ไปที่ธนาคาร"** — ไม่ใช่เพราะผู้ใช้ตั้งใจ
5. ธนาคารเห็นคุกกี้ที่ถูกต้อง → เชื่อว่าเป็นคำขอของผู้ใช้ → ทำงานให้

และเหตุผลที่มัน "ไม่มีร่องรอย": คำขอทุกอย่างมาจาก **IP ของเหยื่อเอง**, ด้วย **คุกกี้ของเหยื่อเอง**, เป็นการทำงานปกติของระบบ — log ฝั่งเซิร์ฟเวอร์จะเห็นเป็น "ผู้ใช้ล็อกอินโอนเงินตามปกติ"

ภัยจริงที่ถูกเปิดเผยหลังชื่อนี้ได้รับการพูดถึงมากขึ้น:

- **Netflix (2006)** — นักวิจัย David Ferguson เปิดเผยว่าเว็บ Netflix เปิดให้คำขอข้ามเว็บสั่งงานได้ (เปลี่ยนที่อยู่, เปลี่ยนอีเมล/รหัสผ่าน, เพิ่มหนังเข้าคิว) โดยเหยื่อไม่รู้ตัว
- **Gmail (2007)** — มีรายงานช่องโหว่ CSRF ที่ทำให้ตั้ง forward อีเมลไปหาผู้โจมตีได้
- **Princeton (2008)** — William Zeller และ Edward Felten เผยช่องโหว่ CSRF สี่ที่ รวมทั้ง **ING Direct** ที่โอนเงินออกจากบัญชีได้จริง (รายงานว่าอาจเป็นครั้งแรกที่ CSRF แตะการโอนเงิน) และ **YouTube** ที่ทำได้แทบทุก action ของผู้ใช้

### 2.4 เกราะที่เกิดจากรอยแผลพวกนี้

ทุกวันนี้เรามีเกราะสี่ชั้นที่ใช้กันเป็นปกติ และ **ทุกชั้นเกิดจากช่วงปีที่เล่ามาแล้วข้างบน**:

1. **Cookie + session ที่ออกแบบให้เบราว์เซอร์แนบเอง** — นี่คือ "ต้นเหตุ" ของ CSRF แต่ในทางกลับกัน same-origin policy ที่มีมาก่อนหน้า (หลักการนี้มีมาตั้งแต่ยุค Netscape Navigator และถูกเขียนเป็นมาตรฐานชัดเจนในภายหลังที่ **RFC 6454** (**RFC** = Request for Comments — เอกสารมาตรฐานอินเทอร์เน็ตที่ออกโดย IETF · ฉบับนี้ลงเดือนธันวาคม 2011)) ทำให้สคริปต์จากเว็บอื่น **อ่านคำตอบ** ของคำขอที่มันยิงไปที่เว็บเราไม่ได้ — มันสั่งงานได้ (แบบ CSRF) แต่ไม่รู้ผลลัพธ์
2. **HttpOnly cookie (2002)** — **Internet Explorer 6 SP1** (ช่วง "Windows Security Push" เดือน ก.พ.–มี.ค. 2002) เพิ่ม attribute นี้ครั้งแรก เพื่อ "ลดความเสียหาย" ของการขโมยคุกกี้ด้วย XSS · ต่อมาถูกทำให้เป็นมาตรฐานใน **RFC 6265 §4.1.2.6** (เมษายน 2011) ซึ่งอธิบายว่า attribute นี้ "จำกัดขอบเขตของคุกกี้ให้อยู่กับคำขอ HTTP — สั่งให้ user agent ไม่ให้คุกกี้นั้นเมื่อมีใครขอเข้าถึงผ่าน API ที่ไม่ใช่ HTTP (เช่น API ของเบราว์เซอร์ที่เปิดคุกกี้ให้สคริปต์)" · จุดสำคัญที่ต้องเข้าใจให้ถูก: **HttpOnly ไม่ได้กัน XSS และไม่ได้กัน CSRF** — มันแค่ทำให้สคริปต์ที่หลุดเข้ามาแล้วอ่านคุกกี้ออกไปไม่ได้
3. **CSP (2011 → 2013)** — **Content Security Policy** เกิดจากข้อเสนอของทีมความปลอดภัย Mozilla (แนวคิด "ให้เอกสารกำหนดข้อจำกัดเนื้อหาของตัวเอง" ถูกคุยกันตั้งแต่ปี 2007, มีรุ่นทดลองใน Firefox 4 เมื่อ มี.ค. 2011) → **W3C First Public Working Draft 29 พฤศจิกายน 2011** → **Chrome 25 เริ่มรองรับ header ที่ไม่มี prefix เมื่อ กุมภาพันธ์ 2013** · ปัจจุบันข้อกำหนดที่ใช้คือ **CSP Level 3** ซึ่งยังเป็น W3C Working Draft (ฉบับที่อัปเดตล่าสุด: <https://www.w3.org/TR/CSP3/>) ส่วน **CSP Level 2** เป็น W3C Recommendation เมื่อ **15 ธันวาคม 2016** · ปรัชญาของมันคือ **"จำกัดว่าอะไรจะรันได้"** แทนที่จะเชื่อว่าทุกอย่างที่รันได้ปลอดภัย
4. **SameSite cookie (2016 → 2020)** — ในที่สุดเบราว์เซอร์ก็แก้ที่ต้นเหตุของ CSRF ตรง ๆ · **Chrome 51 (2016)** เพิ่มค่า `Lax`/`Strict` ให้ผู้พัฒนาตั้งเอง · แล้ว **Chrome 80 (stable 4 กุมภาพันธ์ 2020; เริ่มบังคับ `Lax` เป็นค่าปริยายในสัปดาห์ 17 กุมภาพันธ์ 2020)** เป็นจุดเปลี่ยน: คุกกี้ที่ **ไม่ระบุ** SameSite เลย จะถูก **ถือว่าเป็น `Lax`** — ความหมายคือ **"ไม่แนบไปกับคำขอข้าม site"** (ยกเว้นการนำทางระดับบนสุดด้วยวิธีปลอดภัยอย่างการคลิกลิงก์/GET) · ยังมีข้อยกเว้นชั่วคราวชื่อ **"Lax+POST"**: คุกกี้ที่เพิ่งถูกตั้งไม่เกิน **2 นาที** จะถูกแนบไปกับ cross-site POST ด้วย (ทำไว้ให้ระบบ **SSO** เดิมพังน้อยลง — **SSO** = Single Sign-On, ล็อกอินครั้งเดียวใช้ได้หลายเว็บ) ซึ่งในทางปฏิบัติคือ **อีกเหตุผลที่ควรระบุ SameSite เองให้ชัด ไม่ควรพึ่งค่าปริยาย**

### 2.5 วันนี้: XSS อยู่อันดับ 1 และ CSRF อยู่อันดับ 3

ตัวเลขที่ควรรู้ ณ วันเขียนนี้:

- **CWE Top 25 Most Dangerous Software Weaknesses ฉบับปี 2025** (จัดทำโดย CISA ร่วมกับ MITRE เผยแพร่ **11 ธันวาคม 2025** จากช่องโหว่กว่า **39,000 รายการ** ที่ถูกเปิดเผยระหว่าง มิ.ย. 2024 – มิ.ย. 2025):
  - **อันดับ 1: CWE-79 (XSS)** — คะแนน 60.38 และมี CVE ใน **KEV** (**Known Exploited Vulnerabilities** = รายการช่องโหว่ที่ถูกใช้โจมตีจริง) **7 รายการ** · XSS **รักษาตำแหน่งที่ 1 ติดต่อกัน** (อันดับไม่เปลี่ยนจากปีก่อน)
  - **อันดับ 2: CWE-89 (SQL injection)** — คะแนน 28.72 (ขยับขึ้นจาก 3 — ตรงกับที่เราเล่าไว้ในตอนที่ 04)
  - **อันดับ 3: CWE-352 (CSRF)** — คะแนน 13.64 (ขยับขึ้นจาก 4)
- **OWASP Top 10:2021** — **ฉบับที่เราใช้เล่าใน[ตอนที่ 04](/blog/post.html?slug=2026-10-12-software-security-04-sql-injection)** (OWASP = องค์กรไม่แสวงกำไรที่รวบรวมแนวปฏิบัติ security ของเว็บ) · **ฉบับ 2025 ออกแล้ว:** XSS ย้ายไป **A05:2025 Injection** ส่วน CSRF ยังอยู่ **A01:2025 Broken Access Control** (ตัวเลขข้างล่างเป็นของฉบับ 2021):
  - XSS (CWE-79) อยู่ในหมวด **A03:2021 Injection** — หมวดเดียวกับ SQL injection
  - CSRF (CWE-352) อยู่ในหมวด **A01:2021 Broken Access Control** (การควบคุมสิทธิ์เข้าถึงที่พัง) ซึ่งเป็นหมวดที่ **มี CWE แมปอยู่ 34 ตัว**, มีอัตราการเกิดเฉลี่ย **3.81%** (สูงสุด 55.97%), จำนวนครั้งรวม **318,487 ครั้ง** และ CVE รวม **19,013 รายการ**
- **กรณีจริงที่แพงที่สุดของยุคนี้** — **British Airways (2018)**: ผู้โจมตีแก้ **ไฟล์ JavaScript ของบุคคลที่สามที่โหลดในหน้าเว็บ** (**Modernizr 2.6.2** — พบการแก้ครั้งแรกที่ไฟล์ซึ่งหน้า baggage claim โหลด) ประมาณ **22 บรรทัด** แล้วให้มันคัดลอกข้อมูลบัตรเครดิตของผู้ใช้ (รวม **CVV** = รหัส 3–4 หลักที่อยู่ด้านหลังบัตร) ส่งไปยังโดเมนที่ผู้โจมตีตั้งชื่อให้คล้ายของจริง (`baways.com`) ก่อนที่ข้อมูลจะถูกส่งต่อไปยังระบบชำระเงินจริง · ข้อมูลบัตรของลูกค้าราว **380,000 ราย** หลุด และ **ICO** (Information Commissioner's Office — หน่วยงานกำกับดูแลข้อมูลส่วนบุคคลของสหราชอาณาจักร) ปรับเป็นเงิน **20 ล้านปอนด์** (ต.ค. 2020 หลังลดจากที่ประกาศไว้ตอนแรกราว 183 ล้านปอนด์)
  - **ข้อควรระวังในการเล่าเคสนี้ให้ถูก:** เคสนี้ **ไม่ใช่** reflected/stored XSS ที่เกิดจาก "ไม่ได้เข้ารหัส output ของ input ผู้ใช้" แต่เป็นการฉีดสคริปต์เข้าไปใน **โค้ดที่โหลดในหน้าเพจ** (สคริปต์ของบุคคลที่สาม) — มันคือ "การฉีดสคริปต์ฝั่งไคลเอนต์" ในครอบครัวเดียวกัน · เกราะที่ตอบสนองต่อมันคือสิ่งที่บทนี้พูดถึงทั้งบท: **CSP** (จำกัดว่าหน้านี้รันสคริปต์จากที่ไหนได้), **Subresource Integrity** (ตรวจลายนิ้วมือของไฟล์สคริปต์ที่โหลดจากข้างนอก) และ **การตรวจสอบความสมบูรณ์ของสคริปต์บนหน้าจ่ายเงิน**

![timeline of XSS and CSRF from 1999 to today, with the defenses each era produced](/assets/diagrams/ep05-02-xss-csrf-timeline.svg)

ทั้งหมดข้างบนคือ "ความเข้าใจ" — และความเข้าใจจะเชื่อได้จริงก็ต่อเมื่อเราลงมือ **รันเอง** หัวข้อถัดไปเราจะเขียนเซิร์ฟเวอร์ Go จริงขึ้นมาสองตัว (หนึ่งสำหรับ XSS หนึ่งสำหรับ CSRF) รันบนเครื่องเรา แล้วดูผลจริง ๆ

## 3. ลงมือทำ: เขียนเซิร์ฟเวอร์ Go จริง แล้วพิสูจน์ด้วยผลรัน

### 3.1 ตั้งที่ทำงาน

```bash
mkdir -p ~/security-lab/ep05 && cd ~/security-lab/ep05
go mod init ep05xss
```

ตอนนี้ **ไม่ต้องดึง dependency ใด ๆ** — ทุกอย่างอยู่ใน standard library · ไฟล์ `go.mod` ของเราหน้าตาแบบนี้:

```
# go.mod ของตอนนี้ — ไฟล์จริงที่ใช้รันเดโม (ไม่มี dependency ภายนอก)
module ep05xss

go 1.27.1
```

**หมายเหตุเรื่องการรัน:** `go.mod` ระบุ `go 1.27.1` แต่เครื่องผู้เขียนติดตั้ง Go 1.24.4 ไว้ — Go command จะเห็นว่า `go.mod` ขอเวอร์ชันสูงกว่า แล้ว **สลับ toolchain ให้อัตโนมัติ** (พฤติกรรม `GOTOOLCHAIN=auto`) ซึ่งในเครื่องนี้มี toolchain 1.27.1 อยู่ในแคชแล้วจึงไม่ต้องดาวน์โหลดอะไร

**ผลรันขึ้นกับ OS แค่ไหน?** น้อยมาก — เดโมเป็น pure Go ทั้งหมด (ไม่มี cgo, ไม่มี SQLite) และฟีเจอร์ที่เราใช้ (`html/template`, `httptest`) เหมือนกันทุกแพลตฟอร์ม:

| OS | สิ่งที่ต้องมีก่อน | เดโม (`go run .`) | `run_all.sh` |
|---|---|---|---|
| **Linux** | Go toolchain | รันได้ · ผลเท่ากัน | `bash run_all.sh` |
| **macOS** | Go toolchain | รันได้ · ผลเท่ากัน | `bash run_all.sh` (bash 3.2 ที่ macOS ก็ใช้ได้) |
| **Windows** | Go toolchain | รันได้ · ผลเท่ากัน | ต้องรันผ่าน **Git Bash** หรือ **WSL** |

> ผลรันในบทนี้เป็นของ **Linux aarch64** แต่ทุกตัวเลขเป็นค่าคงที่ของเดโม (นับจาก response body จริง ไม่มีค่าสุ่มพิมพ์ออกมา) จึงเทียบข้ามแพลตฟอร์มได้ · เราเช็คแล้วด้วย `diff -r` ว่า **รันซ้ำแล้วผลเท่าเดิมทุกบรรทัด ยกเว้นบรรทัด `date:` ใน `out/00_env.txt`**

### 3.2 ฝั่งที่พัง กับฝั่งที่ถูก — ต่างกันที่ "ใครประกอบเอกสาร"

นี่คือสอง handler ที่เราจะเทียบกัน (อยู่ในไฟล์ `xss_demo.go`):

```go
// vulnSearchHandler ❌ ต่อ input เข้าไปใน HTML ตรง ๆ — "ห้ามใช้จริงกับระบบของคนอื่น"
func vulnSearchHandler(w http.ResponseWriter, r *http.Request) {
	q := r.URL.Query().Get("q")
	w.Header().Set("Content-Type", "text/html; charset=utf-8")
	io.WriteString(w, pageHead)
	io.WriteString(w, `<div class="result">results for: `+q+`</div>`)
	io.WriteString(w, pageFoot)
}

// safeSearchTmpl ✅ html/template เข้ารหัสค่าตามบริบทให้เองตอน render
var safeSearchTmpl = template.Must(template.New("search").Parse(
	pageHead + `<div class="result">results for: {{.Q}}</div>` + pageFoot))

func safeSearchHandler(w http.ResponseWriter, r *http.Request) {
	q := r.URL.Query().Get("q")
	w.Header().Set("Content-Type", "text/html; charset=utf-8")
	err := safeSearchTmpl.Execute(w, struct{ Q string }{Q: q})
	if err != nil {
		// ส่งข้อความกลาง ๆ ออกไป ไม่ส่งรายละเอียดภายในให้ผู้ใช้เห็น
		http.Error(w, "internal error", http.StatusInternalServerError)
	}
}
```

สังเกตความต่าง:

- **`vulnSearchHandler`** ประกอบ HTML เองด้วย `+` → **ผู้ใช้กำหนดโครงสร้างเอกสารได้**
- **`safeSearchHandler`** ส่งค่าเข้า `html/template` → **ผู้เขียนเทมเพลตกำหนดโครงสร้าง** และค่าของผู้ใช้ถูกเข้ารหัสตามบริบทให้เอง
- `safeSearchTmpl` ถูก parse **ครั้งเดียวตอนโปรแกรมเริ่ม** (ไม่ parse ใหม่ทุกคำขอ) — เป็นรูปแบบที่ใช้จริงและเร็วกว่า
- เมื่อเกิด error เราไม่ส่งรายละเอียดภายในออกไป (ส่ง `internal error` กลาง ๆ) — เพราะข้อความ error เองก็เป็นข้อมูลที่อาจรั่วข้อมูลภายในได้

ผลรันจริงของสองเส้นทางนี้ (นับแท็กดิบจาก response body จริง):

```
--- 1) reflected XSS: /vuln?q=... เทียบ /safe?q=... ---
[1a] /vuln → ส่วนผลลัพธ์ที่เซิร์ฟเวอร์ส่งไป (ตัดมาจาก response body จริง):
     <div class="result">results for: <script>alert(1)</script></div>
     นับแท็ก <script ที่ยัง "เป็นแท็กจริง" : 1
[1b] /safe → ส่วนผลลัพธ์ที่เซิร์ฟเวอร์ส่งไป:
     <div class="result">results for: &lt;script&gt;alert(1)&lt;/script&gt;</div>
     นับแท็ก <script ที่ยัง "เป็นแท็กจริง" : 0
```

อ่านให้ครบ: **`1` กับ `0`** — สองตัวเลขนี้คือความต่างระหว่าง "เว็บที่มีช่องโหว่" กับ "เว็บที่ไม่มี" และมันต่างกันที่ **ใครเป็นคนประกอบเอกสาร**

> **กับดักทางความคิดที่พบบ่อย:** หลายคนคิดว่า "ก็แค่เขียน HTML เองไม่ให้มีรู" — แต่โค้ดที่พังในบทนี้ **ไม่มีรูที่ไหนเลย** มันผิดแค่ *ความเชื่อเรื่องเดียว*: "input คือข้อความ"

### 3.3 Stored XSS: ข้อมูลที่ "นอนรอ" อยู่ในระบบ

Stored XSS ต่างจาก reflected ตรงที่ข้อมูลถูก **เก็บก่อน** แล้วค่อยถูกส่งออกให้คนอื่นทีหลัง · ที่เก็บของเราง่ายมาก:

```go
type commentStore struct {
	mu   sync.Mutex
	list []string
}

func (s *commentStore) add(c string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.list = append(s.list, c)
}

func (s *commentStore) all() []string {
	s.mu.Lock()
	defer s.mu.Unlock()
	out := make([]string, len(s.list))
	copy(out, s.list)
	return out
}
```

(สังเกต `sync.Mutex` — handler ของ `net/http` รัน **พร้อมกันได้หลายคำขอ** ดังนั้นข้อมูลที่ใช้ร่วมกันต้องมี lock ไม่งั้นจะเกิด **data race**)

ส่วนการ "ส่งออก" มีสองเวอร์ชัน:

```go
// renderCommentsVuln ❌ ต่อข้อความที่เก็บไว้เข้าไปใน HTML ตรง ๆ — "ห้ามใช้จริง"
func renderCommentsVuln(cs []string) string {
	var b strings.Builder
	b.WriteString(pageHead + `<ul class="comments">`)
	for _, c := range cs {
		b.WriteString(`<li>` + c + `</li>`)
	}
	b.WriteString(`</ul>` + pageFoot)
	return b.String()
}

// renderCommentsSafe ✅ เข้ารหัสทุกค่าตอนส่งออก — เก็บข้อมูล "ดิบ" ไว้ได้ ไม่เป็นไร
func renderCommentsSafe(w io.Writer, cs []string) error {
	const tpl = pageHead + `<ul class="comments">{{range .}}<li>{{.}}</li>{{end}}</ul>` + pageFoot
	t, err := template.New("comments").Parse(tpl)
	if err != nil {
		return err
	}
	return t.Execute(w, cs)
}
```

`renderCommentsVuln` ต่อ `<li>` + ข้อความ + `</li>` เอง — และนั่นคือทั้งหมดของ stored XSS · ส่วน `renderCommentsSafe` ให้ `html/template` ทำ `{{.}}` ซึ่งจะถูกเข้ารหัสอัตโนมัติ

> **จุดสำคัญที่อยากให้สังเกต:** ในเวอร์ชัน safe เรา **เก็บข้อมูลไว้ "ดิบ" เหมือนกันเป๊ะ** — ไม่ได้กรองอะไรตอน `add` · เพราะความปลอดภัยของเราอยู่ที่ *ตอน render* ไม่ใช่ *ตอนรับเข้า* · นี่คือความต่างเชิงสถาปัตยกรรมที่สำคัญที่สุดของบทนี้ และมันมีผลจริงในงานประจำวัน: **ถ้าคุณเก็บข้อมูลดิบไว้ คุณยังแก้ได้ทีหลัง · แต่ถ้าคุณกรองข้อมูลทิ้งตอนรับเข้า ข้อมูลจริงจะหายไปตลอดกาล** (ลองคิดถึงลูกค้าที่ชื่อมีเครื่องหมาย `'` หรือคอมเมนต์ที่พูดถึงโค้ด HTML)

ผลรันจริง (เก็บ payload สองตัว แล้ว render ทั้งสองแบบ):

```
--- 3) กับดัก: ทางแก้ที่ยังพัง ---
[3a] stored XSS (ผู้ใช้คอมเมนต์ไว้ แล้วคนอื่นเปิดอ่าน)
     vulnerable: แท็กดิบในหน้า = <script 1 ตัว, <img 1 ตัว
     safe      : แท็กดิบในหน้า = <script 0 ตัว, <img 0 ตัว
```

บรรทัด **safe** ทั้งสองบรรทัดเป็น `0` — ไม่มีแท็ก `<script>` หรือ `<img>` หลุดออกมาเป็น "แท็กจริง" เลยแม้แต่ตัวเดียว ทั้งที่ข้อมูลในที่เก็บเหมือนกันเป๊ะ

### 3.4 กับดักสามข้อ: "ทางแก้" ที่ยังพัง

นี่คือส่วนที่ผมอยากให้อ่านช้า ๆ เพราะมันคือคำตอบของคำถาม "แล้ว sanitize ล่ะ"

```go
// stripScriptTag ❌ "sanitize" แบบ deny-list (blacklist): ตัดคำที่คิดว่าไม่ดีออก
// ใช้ไม่ได้ เพราะ deny-list ไม่มีวันครบ (ดูผลรันในหัวข้อ 3.4) — "ห้ามใช้จริง"
func stripScriptTag(in string) string {
	return strings.ReplaceAll(in, "<script>", "")
}
```

ผลรันจริงของกับดักทั้งสาม (บวกอีกหนึ่งที่ `html/template` กันให้เอง):

```
[3b] template.HTML(...) — "ข้ามการเข้ารหัส"; อย่าเอา input ผู้ใช้มาใส่ในนี้
     ผลลัพธ์: <div><img src=x onerror=alert(1)></div>
     แท็ก <img ดิบที่ยังรันได้ = 1
[3c] "sanitize" แบบ deny-list (blacklist): ลบ <script> ออก ยังพัง
     input        : <img src=x onerror=alert(1)>
     หลัง filter  : แท็ก <script เจอ 0 ตัว
     แต่แท็ก <img พร้อม onerror= ยังอยู่ใน output : 1 ตัว  ← เบราว์เซอร์ยังรัน
[3d] ลิงก์ที่ผู้ใช้กรอก: input javascript:alert(1) -> <a href="#ZgotmplZ">x</a>
     (html/template มีตัวกรอง scheme ให้เอง — ดูผลรันด้านบน)
```

อ่านทีละข้อ:

**① `template.HTML(...)` คือการบอก Go ว่า "เชื่อฉัน ค่านี้ปลอดภัย"** — `template.HTML` เป็น **type พิเศษ** ที่ห่อสตริงไว้เพื่อบอก `html/template` ว่า *"อย่าเข้ารหัสค่านี้"* · เราจำเป็นต้องมีมันจริงในบางกรณี (เช่น HTML ที่เราสร้างเองและรู้ว่าปลอดภัย 100%) แต่ **ทันทีที่เราเอา input ของผู้ใช้มาใส่ type นี้ การเข้ารหัสหายไปทั้งดุ้น** — ในผลรันเห็นชัดว่ามีแท็ก `<img>` ดิบออกไป `1` ตัว
· **กฎที่ควรใช้:** `template.HTML` ใช้ได้เฉพาะกับสตริงที่ **เราเขียนเองแบบคงที่** หรือผลลัพธ์จาก **HTML sanitizer ที่เชื่อถือได้** เท่านั้น — ห้ามรับค่า dynamic จากผู้ใช้เด็ดขาด

**② Deny-list (blacklist) ยังพัง** — เรา "sanitize" ด้วยการลบคำว่า `<script>` ออก (นี่คือวิธีที่คนเขียนกันจริง ๆ เยอะมาก) · ผลคือแท็ก `<script>` เหลือ `0` ตัวจริง — **แต่ payload ของเราไม่ได้ใช้ `<script>` เลย** มันใช้ `<img src=x onerror=...>` · และ `onerror` คือ **event handler attribute** (attribute ที่เบราว์เซอร์เรียกใช้เมื่อเกิดเหตุการณ์ — ในที่นี้คือ "โหลดรูปไม่สำเร็จ") ซึ่งเป็นโค้ดที่รันได้เหมือนกันทุกประการ · นี่คือเหตุผลเชิงประจักษ์ว่า **deny-list (blacklist) ไม่มีวันครบ**: เราแบนสิ่งที่เรานึกออก แต่ผู้โจมตีเลือกจากทั้งรายการของเบราว์เซอร์

**③ บริบท URL และ CSS มีตัวกรองของตัวเอง** — `javascript:alert(1)` ใน `href` ถูก `html/template` ตัดเป็น `#ZgotmplZ` (เพราะนั่นคือ URL ที่ไม่ใช่ scheme ที่ปลอดภัย) และค่าที่ไม่ใช่ CSS ที่ถูกต้องใน `<style>` ก็ถูกปฏิเสธ · จุดนี้สอนว่า **ตัวกรองที่รู้บริบททำได้มากกว่าแค่ "escape อักขระ"** — มันรู้ว่าค่าหน้าตาแบบไหน *ไม่มีความหมายที่ถูกต้อง* ในบริบทนั้น แล้วเลือกปฏิเสธ

> **สรุปหัวข้อ 3.4:** ทั้งสามกับดักพิสูจน์ว่า **"กรองให้ครบ" ไม่ใช่กลยุทธ์ที่ยั่งยืน** เพราะมันขึ้นกับว่าเรานึกถึง payload แบบไหน และ **การข้ามการเข้ารหัสเพียงจุดเดียวก็พอที่จะเปิดช่องทั้งหมด** · ทางที่ยั่งยืนคือเปลี่ยนวิธีคิด: ไม่ได้พยายาม "หา payload ให้เจอ" แต่ทำให้ข้อมูล **ไม่มีทางกลายเป็นไวยากรณ์ได้เลย** ซึ่ง `html/template` ทำผ่าน contextual autoescaping · เอกสารของ Go ระบุหลักการนี้ไว้สามข้อที่ควรท่อง (จาก `pkg.go.dev/html/template`): **Structure Preservation** (แท็กที่ผู้เขียนเขียน ต้องเป็นแท็กเสมอ ไม่ว่าข้อมูลจะเป็นอะไร) · **Code Effect** (มีแต่โค้ดที่ผู้เขียนเขียนเท่านั้นที่จะรัน) · **Least Surprise** (คนอ่านโค้ดต้องเดาได้ว่า `{{.}}` จะถูกทำอะไร)

### 3.5 Header ที่ควรมี: CSP และคุกกี้ที่ตั้ง attribute ครบ

การเข้ารหัสที่ถูกคือเกราะชั้นแรก · เกราะชั้นสองคือ header ที่เราตั้งให้ทุก response:

```go
func safeHeaders() []string {
	h := http.Header{}
	// CSP = บอกเบราว์เซอร์ว่า "หน้านี้โหลดอะไรได้บ้าง" — ชั้นป้องกันที่สองถ้าการเข้ารหัสพลาด
	h.Set("Content-Security-Policy",
		"default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'")
	// กันโหมดแปลก ๆ ของ IE/MIME sniffing
	h.Set("X-Content-Type-Options", "nosniff")
	// คุกกี้ session: HttpOnly = script อ่านไม่ได้ · SameSite=Lax = ไม่ติดไปกับ cross-site POST
	h.Set("Set-Cookie", "sid=<random32hex>; Path=/; HttpOnly; SameSite=Lax")
	var res []string
	for k, v := range h {
		res = append(res, k+": "+v[0])
	}
	sort.Strings(res) // เรียงให้ผลรันคงที่ — map ของ Go ไม่รับประกันลำดับการวนซ้ำ
	return res
}
```

ผลลัพธ์ที่ส่งออกไปจริง:

```
--- 4) header ที่ต้องมี (ปลอดภัยตั้งแต่ค่าปริยาย) ---
     Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'
     Set-Cookie: sid=<random32hex>; Path=/; HttpOnly; SameSite=Lax
     X-Content-Type-Options: nosniff
```

> **ชี้แจงให้ตรงกับความจริงของเดโม:** ชุด header ข้างบนคือ **เป้าหมายที่ควรตั้ง** — ฟังก์ชัน `safeHeaders()` ถูกเรียกในเดโมแค่ที่เดียวคือเพื่อ **พิมพ์ค่าออกมาให้ดู** ยังไม่มี handler ตัวไหนเรียกใช้จริง และ `/vuln`/`/safe` (หัวข้อ 3.2 และ 3.6) ส่งแค่ `Content-Type` เท่านั้น · `/vuln` **จงใจไม่ส่ง CSP** เพื่อให้เห็นว่า payload รันได้ — นั่นคือภาพของ "เกราะชั้นแรกหาย" · ถ้าเราเอา payload เดียวกันไปที่หน้าที่ **มี** CSP ชุดนี้ สคริปต์ inline นั้นจะไม่รันเลย (เบราว์เซอร์ตัดที่ `script-src 'self'` เพราะไม่มี `'unsafe-inline'` และไม่มี nonce) — นั่นคือภาพของ **เกราะชั้นที่สอง** ที่ทำงานจริง (เทคนิค nonce ใน Mini-project ข้อ 2 จะทำให้สคริปต์ที่เราตั้งใจให้รันยังทำงานได้)

อธิบายทีละตัว:

- **`Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'`** — บอกเบราว์เซอร์ว่า: ค่าเริ่มต้นให้โหลดทรัพยากรจาก **origin เดียวกัน** (`'self'`) เท่านั้น · สคริปต์ก็ให้รันจาก `'self'` เท่านั้น (แปลว่า `<script>` ที่ถูกฉีดเข้ามา *ในเอกสาร* จะถูกรันไม่ได้ ถ้าเป็นสคริปต์ inline) · ห้าม `object`/`embed` เลย · และห้ามแท็ก `<base>` ชี้ออกจากเว็บเรา (เพราะ `<base>` เปลี่ยนการตีความ URL ทั้งหน้า — เป็นกับดักที่คนมองข้าม)
  - **ข้อควรรู้ที่ทำให้ CSP ไม่ใช่ยาครอบจักรวาล:** CSP ที่ดี **ไม่ใช้** `'unsafe-inline'` (คำสั่งที่อนุญาตสคริปต์ในเอกสาร — ถ้าใส่คำนี้ CSP ก็แทบไม่เหลืออะไร) และในงานจริงต้องระวัง **nonce/hash** — **nonce** = ค่าสุ่มที่ต้องใส่ทั้งใน header CSP และในแท็ก `<script nonce="...">` ให้ตรงกัน และ **สุ่มใหม่ทุกคำขอ** · CSP เป็น **เกราะชั้นที่สอง** ไม่ใช่แทนการเข้ารหัส: ถ้าคุณเข้ารหัสถูก CSP ก็ไม่ได้ทำงานอะไรเพิ่ม · มันมีไว้เพื่อ "วันที่เราพลาด"
- **`X-Content-Type-Options: nosniff`** — ห้ามเบราว์เซอร์ "เดา" ชนิดไฟล์เอง (พฤติกรรม **MIME sniffing**) เพราะการเดาผิดเคยทำให้ไฟล์ข้อความถูกตีความเป็น HTML/สคริปต์ได้
- **`Set-Cookie: sid=...; Path=/; HttpOnly; SameSite=Lax`** — `HttpOnly` (สคริปต์อ่านไม่ได้) + `SameSite=Lax` (ไม่ติดไปกับคำขอข้าม site)
  - ในโค้ดจริงของเรามี `Secure: false` พร้อมคอมเมนต์ว่า **"ของจริงต้องเป็น true บน HTTPS"** — เราใส่ `false` เพราะเดโมรันบน `http://127.0.0.1` (คุกกี้ที่ติด `Secure` จะไม่ถูกส่งผ่าน HTTP เลย) · รูปแบบที่ปลอดภัยและใช้ได้ทั้งสองกรณีคือตั้งตามสภาพจริง: `Secure: r.TLS != nil` (หรือตั้ง `true` ตายตัวเมื่อทุกอย่างอยู่บน HTTPS)

### 3.6 รันจริงผ่าน HTTP และตัวนับที่ยืนยันทุกอย่าง

โค้ดเดโมของเราเปิด **เซิร์ฟเวอร์จริงบน `127.0.0.1`** และเรียกผ่าน HTTP จริง (ไม่ได้เรียก function ตรง ๆ) — เพื่อให้สิ่งที่เราตรวจคือ **สิ่งที่เซิร์ฟเวอร์ส่งออกไปจริงบนสาย**:

```go
	mux := http.NewServeMux()
	mux.HandleFunc("/vuln", vulnSearchHandler)
	mux.HandleFunc("/safe", safeSearchHandler)
	srv := httptest.NewServer(mux)
	defer srv.Close()

	fmt.Fprintln(out, "\n--- 1) reflected XSS: /vuln?q=... เทียบ /safe?q=... ---")
	vulnBody := fetch(srv.URL + "/vuln?q=" + urlEncode(payloadReflected))
	safeBody := fetch(srv.URL + "/safe?q=" + urlEncode(payloadReflected))
```

(`httptest.NewServer` สร้างเซิร์ฟเวอร์จริงที่ผูกกับ loopback แล้วคืน URL ให้ — วิธีนี้ทำให้เดโมเป็น HTTP ทั้งวงจร แต่ยังรันได้ในเครื่องเดียวโดยไม่เปิดพอร์ตออกภายนอก)

และสุดท้าย ตัวนับทั้งหมดที่โปรแกรมนับจาก response body จริง (ไม่ได้พิมพ์มือ):

```

reflected_script_tag_vuln=1
reflected_script_tag_safe=0
stored_raw_script_vuln=1
stored_raw_script_safe=0
stored_raw_img_vuln=1
```

### 3.7 พิสูจน์ในเบราว์เซอร์จริง: สคริปต์รันหรือไม่รัน

ตัวนับข้างบนบอกว่า "มีแท็กดิบกี่ตัว" ซึ่งเป็นหลักฐานที่ดี — แต่มันยังไม่ใช่หลักฐานว่า **เบราว์เซอร์รันมันจริง** · เราจึงเปิด lab server (`go run . -serve 127.0.0.1:18086`) แล้วใช้ **เบราว์เซอร์จริง (HeadlessChrome 151)** เปิดหน้าเว็บ โดย payload ของเราคือ `<img src=x onerror="window.__ep05='executed'">` — ถ้าสคริปต์รันจริง ตัวแปร global `window.__ep05` จะมีค่า · **ทำไมคนละพอร์ต:** หลักฐานชุดนี้เก็บด้วยมือแยกจาก `run_all.sh` — รอบนั้นมี lab server ที่ค้างจากรอบก่อนอยู่ที่พอร์ตของสคริปต์ (`18085`) จึงเปิดเซิร์ฟเวอร์บนพอร์ตว่างอีกตัว (`18086`) เพื่อไม่ให้ชนกัน

นี่คือผลที่อ่านได้จากหน้าเว็บจริง:

```
# หลักฐานจากเบราว์เซอร์จริง — เก็บด้วยมือ ไม่ได้สร้างโดย run_all.sh (ต้องมีเบราว์เซอร์)
# เบราว์เซอร์: Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) HeadlessChrome/151.0.0.0 Safari/537.36
# เซิร์ฟเวอร์ : code/ep05 (go run . -serve 127.0.0.1:18086) — ฟังเฉพาะ loopback
# payload     : <img src=x onerror="window.__ep05='executed'">
# query string: q=%3Cimg%20src%3Dx%20onerror%3D%22window.__ep05%3D%27executed%27%22%3E
=== ผลที่อ่านได้จากหน้าเว็บจริง (ค่าของ window.__ep05) ===
GET /vuln?q=<payload>        -> window.__ep05 = executed    | มีแท็ก <img ดิบใน DOM = true
GET /safe?q=<payload>        -> window.__ep05 = undefined   | มีแท็ก <img ดิบใน DOM = false
   ข้อความที่ผู้ใช้เห็นบนหน้าฝั่ง safe = results for: <img src=x onerror="window.__ep05='executed'">
GET /comments (stored)       -> window.__ep05 = executed
GET /comments-safe (stored)  -> window.__ep05 = undefined
   ข้อความที่ผู้ใช้เห็นบนหน้าฝั่ง safe = <img src=x onerror="window.__ep05='executed'">
```

อ่านให้ครบ เพราะนี่คือหลักฐานที่ชัดที่สุดของทั้งบท:

- **`/vuln` → `executed`** — เบราว์เซอร์ **รันสคริปต์ของเรา** ในหน้าที่ถูกเสิร์ฟจากเซิร์ฟเวอร์ของเรา
- **`/safe` → `undefined`** — payload เดียวกันเป๊ะ แต่ไม่รันอะไรเลย · สิ่งที่ผู้ใช้เห็นคือ **ตัวอักษร** ของ payload
- **`/comments` (stored) → `executed`** — โปรไฟล์/คอมเมนต์ที่ "นอนรอ" อยู่ในระบบก็รันได้เหมือนกัน
- **`/comments-safe` → `undefined`** — ไม่รัน และผู้ใช้เห็นเป็นข้อความ

สังเกตว่าค่าของ `window.__ep05` ที่ได้คือ `executed` (สตริง) ไม่ใช่ `true` — เพราะ payload ตั้งค่าเป็นสตริง และ `String(undefined)` ให้คำว่า `undefined` ไม่ใช่ "ว่าง" · รายละเอียดเล็ก ๆ แบบนี้คือเหตุผลที่เราเก็บค่า **ค่าจริงที่อ่านได้** ไว้ใน `out/` ไม่ใช่สรุปด้วยคำพูด

> **ทำไมการพิสูจน์ด้วยเบราว์เซอร์จริงสำคัญ:** เพราะ "การเข้ารหัสถูก" กับการ "ไม่ถูกรัน" เป็นคนละข้อความ · การอ่าน response body บอกเราว่าเอกสารหน้าตาเป็นอย่างไร ส่วนเบราว์เซอร์บอกเราว่า **เอกสารนั้นทำอะไร** — และมีหลายกรณี (เช่น DOM-based XSS) ที่ response body สะอาดหมดจด แต่สคริปต์ยังรันอยู่ดี

### 3.8 เดโม CSRF: คุกกี้ถูกแนบไปกับคำขอที่ผู้ใช้ไม่ได้ตั้งใจ

ตอนนี้เรามาสร้าง "ธนาคาร" ที่มี action อันตราย (`POST /transfer`) แล้วรันสี่แบบที่ต่างกันแค่เกราะที่เปิดใช้ · เริ่มจากคุกกี้ session ซึ่งเป็นศูนย์กลางของเรื่อง:

```go
func (b *bank) sessionCookie(sid string) *http.Cookie {
	return &http.Cookie{
		Name:     "sid",
		Value:    sid,
		Path:     "/",
		HttpOnly: b.httpOnly,
		Secure:   false, // เดโมรันบน http://127.0.0.1 — ของจริงต้อง true บน HTTPS
		SameSite: b.sameSite,
		MaxAge:   3600,
	}
}
```

และส่วนที่ "จำลองเบราว์เซอร์" — จุดนี้ต้องอธิบายให้ชัดก่อน เพราะเป็นส่วนที่เราตัดสินใจออกแบบอย่างตรงไปตรงมา:

> **ความซื่อสัตย์ทางเทคนิค:** `http.Client` ของ Go เป็น HTTP client ธรรมดา — มัน**ไม่รู้จัก SameSite** และ**ไม่รู้ว่าคำขอนี้เริ่มจากหน้าเว็บของ site ไหน** (สองอย่างที่เบราว์เซอร์จริงรู้) · เราจึงเขียน **ตัวจำลองนโยบายคุกกี้ของเบราว์เซอร์** ขึ้นมาเอง โดยจำลองแค่สองเรื่อง: (1) "site" ของเราคือ hostname (ในเดโมมีสอง host คือ `127.0.0.1` กับ `localhost` ซึ่งเบราว์เซอร์ก็นับเป็นคนละ site) และ (2) กฎ SameSite ส่วนการคุย HTTP ทั้งหมดเป็นของจริง (เซิร์ฟเวอร์จริง, คำขอจริง, คุกกี้จริง) · **ข้อจำกัดที่ตั้งใจ:** ตัวจำลองดูแค่ธง `topNav` ไม่ได้ดู HTTP method ของคำขอ จึงไม่จำลองข้อยกเว้น **"Lax+POST"** ของเบราว์เซอร์จริง (cross-site top-level POST ภายใน 2 นาทีหลังตั้งคุกกี้จะยังได้คุกกี้) — เดโมจึงไม่ยิงคำขอแบบนั้นเลย

```go
func (b *browserModel) Cookies(u *url.URL) []*http.Cookie {
	toSite := u.Hostname()
	var out []*http.Cookie
	for _, c := range b.store.Cookies(u) {
		switch c.SameSite {
		case http.SameSiteStrictMode:
			if toSite == b.docSite {
				out = append(out, c)
			}
		case http.SameSiteLaxMode:
			if toSite == b.docSite || b.topNav {
				out = append(out, c)
			}
		default: // ไม่ระบุ SameSite (หรือ None) → ส่งทุกครั้ง
			out = append(out, c)
		}
	}
	return out
}
```

> **หมายเหตุเรื่องค่าปริยายของ SameSite:** กรณี A และ C ใช้คุกกี้ที่ **ไม่ระบุ SameSite** — นั่นคือการจำลองค่าปริยายในยุค **ก่อน Chrome 80** (หรือกรณีที่ตั้ง `SameSite=None` โดยตรง) · คุกกี้ที่ไม่ระบุเลยในเบราว์เซอร์ยุคใหม่จะ **ถูกถือเป็น `Lax`** (หัวข้อ 2.4 ข้อ 4) จึงให้ผลเท่ากรณี B ไม่ใช่กรณี A

**กรณี A: ไม่มีเกราะเลย** (คุกกี้ไม่ระบุ SameSite):

```
-- [A] ไม่กันเลย (cookie ไม่ระบุ SameSite) --
   victim login                                    : 200
   ผู้ใช้จริงโอนเองผ่านหน้าเว็บของธนาคาร          : 200  |  ยอดเงิน=900 โอนสำเร็จ=1 ครั้ง
   คำขอที่ผู้โจมตีส่ง (คนละ site, คุกกี้เดิม)     : 200 (ok transfer amount=100)
   ยอดเงินของผู้เสียหายหลังคำขอของผู้โจมตี         : ยอดเงิน=800 โอนสำเร็จ=2 ครั้ง
```

- บรรทัด **"ผู้ใช้จริงโอนเองผ่านหน้าเว็บของธนาคาร"** ได้ `200` — พิสูจน์ว่าเวอร์ชันนี้ *ใช้งานได้ปกติ* (นี่สำคัญ เพราะเกราะที่ทำให้โปรแกรมใช้ไม่ได้ ไม่ใช่เกราะ)
- บรรทัด **"คำขอที่ผู้โจมตีส่ง (คนละ site, คุกกี้เดิม)"** ได้ `200` **เช่นกัน** — และบรรทัดสุดท้ายบอกว่ายอดเงินหายไป 100 · ผู้ใช้ไม่เห็นอะไรผิดปกติเลย

**กรณี B: เหมือนกันทุกอย่าง แต่คุกกี้เป็น `SameSite=Lax`**

```
-- [B] SameSite=Lax (cookie ไม่ระบุ token) --
   victim login                                    : 200
   ผู้ใช้จริงโอนเองผ่านหน้าเว็บของธนาคาร          : 200  |  ยอดเงิน=900 โอนสำเร็จ=1 ครั้ง
   คำขอที่ผู้โจมตีส่ง (คนละ site, คุกกี้เดิม)     : 401 (no session)
   ยอดเงินของผู้เสียหายหลังคำขอของผู้โจมตี         : ยอดเงิน=900 โอนสำเร็จ=1 ครั้ง
   คลิกลิงก์จากเว็บโจมตีเข้ามา (GET, top-level)   : 200 (ยอดเงิน=900 โอนสำเร็จ=1 ครั้ง)
```

- บรรทัด **"ผู้ใช้จริงโอนเองผ่านหน้าเว็บของธนาคาร"** ได้ `200` (ยังใช้ได้ปกติ)
- **บรรทัด "คำขอที่ผู้โจมตีส่ง (คนละ site, คุกกี้เดิม)" ได้ `401`** — เพราะเบราว์เซอร์ **ไม่แนบ** คุกกี้ไปกับ cross-site POST → เซิร์ฟเวอร์มองไม่เห็น session เลย → ยอดเงินไม่หาย
- บรรทัดสุดท้ายสำคัญมาก: **คลิกลิงก์จากเว็บโจมตีเข้ามาที่ธนาคารยังได้ `200`** — คือ `Lax` ไม่ได้ทำลายการใช้งานปกติ (การนำทางระดับบนสุดด้วย GET ยังแนบคุกกี้ให้) · ถ้าใช้ `Strict` แทน บรรทัดนี้จะพัง (ผู้ใช้ที่มาจากลิงก์ภายนอกจะดูเหมือน "หลุดล็อกอิน" จนกว่าจะคลิกอีกครั้ง) — นี่คือ trade-off ที่ต้องเลือกต่อเว็บ

**กรณี C: ใช้ CSRF token** (คุกกี้ยังไม่ระบุ SameSite)

```
-- [C] CSRF token (cookie ไม่ระบุ SameSite) --
   victim login                                    : 200
   ผู้ใช้จริงโอนเองผ่านหน้าเว็บของธนาคาร          : 200  |  ยอดเงิน=900 โอนสำเร็จ=1 ครั้ง
   คำขอที่ผู้โจมตีส่ง (คนละ site, คุกกี้เดิม)     : 403 (bad csrf token)
   ยอดเงินของผู้เสียหายหลังคำขอของผู้โจมตี         : ยอดเงิน=900 โอนสำเร็จ=1 ครั้ง
```

คำขอของผู้โจมตีได้ `403` (ปฏิเสธเพราะ token ไม่ตรง) · token ฝั่งเซิร์ฟเวอร์ทำงานแบบนี้:

```go
func (b *bank) handleForm(w http.ResponseWriter, r *http.Request) {
	sid, ok := b.sid(r)
	if !ok {
		http.Error(w, "no session", http.StatusUnauthorized)
		return
	}
	b.mu.Lock()
	tok := b.tokens[sid]
	b.mu.Unlock()
	w.Header().Set("Content-Type", "text/html; charset=utf-8")
	// หน้าจริงฝัง token ไว้ในฟอร์ม — และมันอยู่ใน DOM ให้สคริปต์ของหน้านั้นอ่านได้เสมอ
	io.WriteString(w, `<form method="POST" action="/transfer">`+
		`<input type="hidden" name="csrf" value="`+tok+`">`+
		`<input name="to" value="friend"><input name="amount" value="100">`+
		`<button>โอน</button></form>`)
}
```

```go
func (b *bank) handleTransfer(w http.ResponseWriter, r *http.Request) {
	sid, ok := b.sid(r)
	if !ok {
		// ไม่มีคุกกี้ที่ใช้ได้ = คำขอไม่ได้มาจากเบราว์เซอร์ที่ล็อกอินอยู่
		http.Error(w, "no session", http.StatusUnauthorized)
		return
	}
	if b.useToken {
		sent := r.PostFormValue("csrf")
		b.mu.Lock()
		want := b.tokens[sid]
		b.mu.Unlock()
		if subtle.ConstantTimeCompare([]byte(sent), []byte(want)) != 1 {
			http.Error(w, "bad csrf token", http.StatusForbidden)
			return
		}
	}
	b.mu.Lock()
	b.balance -= 100
	b.transfers++
	b.mu.Unlock()
	io.WriteString(w, "ok transfer amount=100")
}
```

จุดที่อยากให้สังเกตในโค้ด:

- **token ถูกสุ่มด้วย `crypto/rand`** (ไม่ใช่ `math/rand` ที่ทำนายได้) และยาว 32 ไบต์ — คำว่า **synchronizer token pattern** แปลว่า "เซิร์ฟเวอร์ออก token ให้ฟอร์มของตัวเอง แล้วตรวจว่าคำขอที่เข้ามามี token ที่ตรงกับ session นั้นไหม" · ถ้าคำขอมาจากเว็บอื่น มัน **อ่าน token ไม่ได้** (same-origin policy) จึงเดาไม่ถูก
- **การเทียบใช้ `subtle.ConstantTimeCompare`** — เพื่อไม่ให้ระยะเวลาที่ใช้เทียบรั่วไหลข้อมูล (เรียกว่า **timing leak**: ถ้าใช้ `==` และหยุดเทียบที่ตัวแรกที่ไม่ตรง เวลาที่ใช้จะบอกผู้โจมตีว่า "เดาถูกกี่ตัวอักษรแล้ว")
- **โค้ดตอบกลับพร้อม HTTP status ที่ชัดเจน** (`401` ไม่มี session, `403` token ผิด) แต่ **ไม่บอกว่าทำไมละเอียดกว่านั้น**

**กรณี D: มี XSS อยู่ในหน้าเว็บของธนาคารเอง — แล้วเกราะ token ที่ว่าไปไหน**

```
-- [D] CSRF token + มี XSS ในหน้าเว็บของธนาคารเอง --
   victim login                                    : 200
   ผู้ใช้จริงโอนเองผ่านหน้าเว็บของธนาคาร          : 200  |  ยอดเงิน=900 โอนสำเร็จ=1 ครั้ง
   คำขอที่ผู้โจมตีส่ง (คนละ site, คุกกี้เดิม)     : 401 (no session)
   ยอดเงินของผู้เสียหายหลังคำขอของผู้โจมตี         : ยอดเงิน=900 โอนสำเร็จ=1 ครั้ง
   สคริปต์ที่ถูกฉีดอ่าน token จากหน้าเว็บของธนาคาร: 200, token ยาว 64 ตัวอักษร
   แล้วยิง POST พร้อม token ที่อ่านมาได้นั้น        : 200 (ok transfer amount=100)
   ยอดเงินของผู้เสียหายหลังสคริปต์ทำงาน            : ยอดเงิน=800 โอนสำเร็จ=2 ครั้ง
```

อ่านบรรทัดที่ 5–7 ให้ดี: **สคริปต์ที่ถูกฉีดอ่าน token ได้ (`200`, ยาว 64 ตัวอักษร) แล้วยิงคำขอพร้อม token นั้นสำเร็จ (`200`) และยอดเงินหายไป 100**

นี่คือบทเรียนที่สำคัญที่สุดของหัวข้อนี้: **CSRF token ไม่ได้กัน XSS** — เพราะเมื่อสคริปต์ของเรา (หรือของผู้โจมตี) รันอยู่ในหน้าเว็บของธนาคารแล้ว มัน **อยู่ข้างในขอบเขตที่เชื่อถือได้** มันอ่าน DOM ได้ อ่าน token ได้ และยิงคำขอด้วยคุกกี้ของผู้ใช้ได้ — ทุกอย่างที่หน้าเว็บนั้นทำได้ มันทำได้หมด · **นี่คือสิ่งที่ Samy worm ทำกับ MySpace เมื่อปี 2005 เป๊ะ ๆ** (หัวข้อ 2.2 — การอ่าน `Mytoken` จากหน้าเว็บ) และเป็นเหตุผลว่าทำไม **"CSRF token" กับ "output encoding" ต้องมีทั้งคู่** · ถ้ามีแต่ token คุณกัน CSRF ได้แต่กัน XSS ไม่ได้ · ถ้ามีแต่ encoding คุณก็ยังต้องมี token (หรือ SameSite) เพื่อกัน CSRF

**กรณี E: HttpOnly — ลดความเสียหาย ไม่ได้กันการโจมตี**

```
-- [E] HttpOnly: สคริปต์อ่านคุกกี้ session ได้หรือไม่ --
   cookie ไม่มี HttpOnly  → document.cookie = sid=<32 ตัวอักษร hex>
   cookie มี HttpOnly     → document.cookie = (ว่าง — สคริปต์อ่านไม่ได้)
```

โค้ดที่ทำให้เป็นแบบนี้คือการเช็ค `HttpOnly` ตอนสคริปต์ขออ่านคุกกี้:

```go
// documentCookie คือสิ่งที่สคริปต์ในหน้าเว็บเห็นผ่าน document.cookie
// HttpOnly คือคุกกี้ที่จะ "หายไป" จากมุมมองนี้ (แต่ยังถูกส่งไปกับ request ปกติ)
func (b *browserModel) documentCookie(host string) string {
	u := &url.URL{Scheme: "https", Host: host, Path: "/"}
	var parts []string
	for _, c := range b.store.Cookies(u) {
		if c.HttpOnly {
			continue
		}
		parts = append(parts, c.Name+"="+c.Value)
	}
	return strings.Join(parts, "; ")
}
```

อ่านผลให้ครบ: คุกกี้ที่ไม่มี `HttpOnly` — สคริปต์อ่านค่าได้ **32 ตัวอักษร** (ตัวระบุเซสชัน) · คุกกี้ที่มี `HttpOnly` — อ่านได้ **0** (คือว่าง) · แต่คุกกี้ตัวเดียวกันนั้น **ยังถูกส่งไปกับคำขอทุกครั้งตามปกติ** (ไม่งั้นก็ล็อกอินไม่ได้เลย)
· **สรุปที่ถูกต้อง:** HttpOnly ไม่ได้ *กัน* XSS และไม่กัน CSRF — มัน **ตัดความสามารถที่ XSS จะ "ขโมย" ตัวระบุเซสชันออกไปใช้ต่อจากเครื่องอื่น** ทิ้งไป · มันทำให้ช่องโหว่ร้ายแรงลดระดับลง แต่ไม่ทำให้หายไป (เพราะ XSS ยังยิงคำขอในนามของผู้ใช้ได้อยู่ดี — เหมือนกรณี D)

และนี่คือโค้ดที่ทำให้เรา "จำลองเบราว์เซอร์" ได้อย่างควบคุมได้หมด (ส่วนที่เหลือของ HTTP เป็นของจริง):

```go
// do ยิง request โดยระบุ "เอกสารต้นทาง" ว่าอยู่ site ไหน และเป็น top-level navigation ไหม
func (b *browser) do(method, target, docSite string, topNav bool, form url.Values) (int, string) {
	if _, err := url.Parse(target); err != nil {
		return 0, "bad url"
	}
	b.model.docSite = docSite
	b.model.topNav = topNav
	var body io.Reader
	if form != nil {
		body = strings.NewReader(form.Encode())
	}
	req, err := http.NewRequest(method, target, body)
	if err != nil {
		return 0, "bad request"
	}
	if form != nil {
		req.Header.Set("Content-Type", "application/x-www-form-urlencoded")
	}
	resp, err := b.http.Do(req)
	if err != nil {
		return 0, "err: " + err.Error()
	}
	defer resp.Body.Close()
	raw, _ := io.ReadAll(io.LimitReader(resp.Body, 8192))
	return resp.StatusCode, strings.TrimSpace(string(raw))
}
```

`docSite` คือ "site ของเอกสารต้นทาง" และ `topNav` คือ "คำขอนี้เป็นการนำทางระดับบนสุดหรือไม่" — สองตัวนี้คือข้อมูลที่เบราว์เซอร์รู้แต่ HTTP client ไม่รู้ และเป็นกุญแจทั้งหมดของ SameSite

### ระดับ Drill (5–10 นาที)

1. **อธิบายด้วยคำของคุณเอง** ว่าทำไม `<div>results for: ` + input + `</div>` ถึงพัง แต่ `<div>results for: {{.Q}}</div>` (ผ่าน `html/template`) ถึงไม่พัง — คำตอบต้องพูดถึงคำว่า **บริบท (context)** และ **ตอนที่ข้อมูลถูกประกอบเข้าไปในเอกสาร** ไม่ใช่แค่ "เพราะ template ปลอดภัย"
2. จากผลรันหัวข้อ 3.2: ทำไม `/safe` ต้องเก็บ payload ไว้ **เป็นตัวอักษร** (`&lt;script&gt;`) ไม่ใช่ "ลบทิ้ง" — และการเลือกแบบนี้ให้ประโยชน์อะไรกับผู้ใช้
3. จากผลรันหัวข้อ 3.4 ข้อ ②: อธิบายว่าทำไมการลบคำว่า `<script>` ออกไม่ช่วยอะไร พร้อมยก payload อีก **สอง** แบบที่ยังรันได้ (ใบ้: `onerror=`, `onload=`, `javascript:`)
4. จากผลรันหัวข้อ 3.4 ข้อ ③: `ZgotmplZ` หมายถึงอะไร และทำไม "ปฏิเสธค่าที่ไม่รู้จัก" ถึงปลอดภัยกว่า "พยายามทำความสะอาดมัน"
5. จากกรณี D ของเดโม CSRF: อธิบายให้ได้ว่า **ทำไม CSRF token กันกรณี D ไม่ได้** ทั้งที่กันกรณี C ได้ (คำตอบต้องพูดถึงคำว่า "ขอบเขตที่เชื่อถือได้/origin" และ "DOM")
6. เปรียบเทียบ `SameSite=Lax` กับ `SameSite=Strict`: ถ้าเว็บคุณมีการล็อกอินผ่านลิงก์จากเว็บอื่นด้วย แบบไหนเหมาะกว่า และได้/เสียอะไร

### ระดับ Mini-project (30–60 นาที)

1. **ทำให้ "safe" ครบทั้งไฟล์** — ใน `xss_demo.go` มีสองจุดที่ปลอดภัยอยู่แล้ว (`safeSearchHandler` และ `renderCommentsSafe`) · จงหาจุดที่เหลืออีก **3 จุด** (reflected, stored และ `stripScriptTag`) แล้วทำให้ทั้งหมดใช้ `html/template` หรือ `template.HTMLEscapeString` · **ส่วนการ render CSRF token ลงฟอร์ม** อยู่นอกไฟล์นี้ — ที่ `csrf_demo/main.go` ฟังก์ชัน `handleForm` (ในเดโม token เป็น hex ที่เราสร้างเอง จึงยังไม่มีปัญหา แต่ถ้าค่าไหนมาจากผู้ใช้ก็ต้องเข้ารหัส) · แล้วเขียนเทสต์ที่พิสูจน์ว่า payload ทั้งสามตัว (`<script>`, `<img onerror>`, `javascript:` ใน href) ให้ **จำนวนแท็กดิบเป็น 0** ทุก endpoint
2. **เขียน CSP ที่ปลอดภัยจริง แล้วพิสูจน์** — เริ่มจาก header ที่เราใช้ แล้วทำให้สคริปต์ inline ของหน้าเว็บยังทำงานได้ด้วยเทคนิค **nonce** (ดูนิยามในหัวข้อ 3.5) · เขียนเทสต์ที่ยืนยันว่า (ก) สคริปต์ที่มี nonce ถูกต้องรันได้ (ข) สคริปต์ที่ถูกฉีดเข้ามา (ไม่มี nonce) ไม่รัน
3. **เพิ่ม HttpOnly และ SameSite ให้ครบทุกคุกกี้ในโปรเจกต์ของคุณ** — ใช้ `grep -rn "http.Cookie{" .` (หรือค้นหา `SetCookie` ในภาษาโปรเจกต์ของคุณ) แล้วทำตาราง: ไฟล์, บรรทัด, คุกกี้นั้นเป็น `HttpOnly` ไหม, `SameSite` อะไร, เหตุผลที่เลือก · แล้วรายงาน **คุกกี้ที่เป็น `SameSite=None` โดยไม่มี `Secure`** (เพราะเบราว์เซอร์สมัยใหม่จะ **ปฏิเสธ** คุกกี้แบบนั้นทิ้ง)
4. **ทดลอง Lax+POST** — เขียนเดโมที่ตั้งคุกกี้ `SameSite=Lax` แล้วยิง cross-site POST **ภายใน 2 นาที** หลังตั้งคุกกี้ เทียบกับ **หลัง 2 นาที** · อธิบายว่าทำไมเบราว์เซอร์มีข้อยกเว้นนี้ และทำไมคุณ **ไม่ควรพึ่งมัน**

## 5. สรุปตอนที่ 05

- **แก่นของเรื่อง:** เบราว์เซอร์เป็น interpreter อีกตัวที่อ่าน "ข้อความก้อนเดียว" และแยกไม่ออกระหว่าง HTML ที่เราเขียน กับ HTML ที่ข้อมูลของเราพาเข้ามา · ที่ไหนก็ตามที่เราประกอบเอกสารด้วยการต่อสตริง ที่นั่นมีช่องโหว่
- **XSS สามหน้าตา:** reflected (สะท้อนกลับทันที — ต้องล่อเหยื่อ) · stored (เก็บไว้แล้วกระจายเอง — ร้ายสุด) · DOM-based (เกิดในเบราว์เซอร์เอง)
- **ทางแก้ที่ถูกคือ "เข้ารหัสตามบริบทตอนส่งออก"** ไม่ใช่ "กรองตอนรับเข้า" · พิสูจน์แล้วด้วยผลรัน: payload เดียวกันให้ **แท็กดิบ 1 ตัว** ฝั่ง vulnerable และ **0 ตัว** ฝั่ง safe · และบริบทต่างกันต้องเข้ารหัสต่างกัน (6 บริบท: HTML text, attribute ×2, URI, JS string, CSS)
- **กับดักสามข้อ:** `template.HTML(...)` ข้ามการเข้ารหัส (แท็กดิบรันได้ 1 ตัว) · deny-list (blacklist) ลบ `<script>` ได้ 0 ตัว แต่ `<img onerror>` ยังรันได้ 1 ตัว · ส่วนบริบท URL/CSS ถูก `html/template` ปฏิเสธให้เอง (`#ZgotmplZ`, `ZgotmplZ`)
- **ประวัติ:** **16–17 ม.ค. 2000** ทีม security ของ Microsoft ตกลงชื่อ "Cross Site Scripting" → **2 ก.พ. 2000** CERT advisory **CA-2000-02** ("violation of trust") · **4 ต.ค. 2005** **Samy worm** ทำให้ MySpace ต้องปิดแพลตฟอร์ม: มากกว่า **1,000,000 โปรไฟล์ในไม่ถึง 20 ชั่วโมง** · ชื่อ **CSRF** ตั้งโดย **Peter Watkins** ใน Bugtraq **มิ.ย. 2001** (รากคิดคือ confused deputy ของ Norm Hardy, 1988) · ภัยจริงยุคถัดมา: Netflix (2006), Gmail (2007), ING Direct + YouTube (2008), British Airways (~22 บรรทัด JS, 380,000 บัตร, ปรับ 20 ล้านปอนด์)
- **เกราะสี่ชั้นและที่มา:** same-origin policy (ยุค Netscape → มาตรฐาน RFC 6454) · **HttpOnly** (IE 6 SP1, 2002 → RFC 6265 §4.1.2.6) · **CSP** (Mozilla 2011 → W3C FPWD 29 พ.ย. 2011 → Chrome 25 ก.พ. 2013 → ปัจจุบัน CSP Level 3 เป็น Working Draft) · **SameSite** (Chrome 51, 2016 → Chrome 80 stable 4 ก.พ. 2020 และเริ่มบังคับ `Lax` เป็นค่าปริยาย ในสัปดาห์ 17 ก.พ. 2020)
- **เดโม CSRF ทั้งสี่กรณี:** ไม่มีเกราะ → คำขอข้าม site สำเร็จ (`200`, ยอดเงินหาย) · `SameSite=Lax` → `401` (ไม่มีคุกกี้) แต่การคลิกลิงก์เข้าเว็บยังได้ `200` · CSRF token → `403` · **token + XSS ในขอบเขตเดียวกัน → `200` อีกรอบ** เพราะสคริปต์อ่าน token จาก DOM ได้ (กรณีเดียวกับที่ Samy worm ทำ)
- **HttpOnly คือการลดความเสียหาย ไม่ใช่การป้องกัน:** คุกกี้ที่มี HttpOnly → สคริปต์อ่านได้ **0** ตัวอักษร (ไม่มี HttpOnly → อ่านได้ 32) แต่คุกกี้ยังถูกส่งไปกับคำขอตามปกติ · และ XSS ยังยิงคำขอในนามของผู้ใช้อีกเช่นเคย
- **วันนี้:** **CWE Top 25 ประจำปี 2025** → **XSS (CWE-79) อันดับ 1** (คะแนน 60.38, CVE ใน KEV 7 รายการ) · SQL injection อันดับ 2 · **CSRF (CWE-352) อันดับ 3** · ใน **OWASP Top 10:2021** (ฉบับที่ตอน 04 อ้างอิง; ฉบับ 2025 มีแล้ว — XSS ย้ายไป **A05:2025 Injection** ส่วน CSRF ยังอยู่ **A01:2025**) XSS อยู่ใน A03 Injection ส่วน CSRF อยู่ใน A01 Broken Access Control (34 CWE, อัตราการเกิดเฉลี่ย 3.81%, 318,487 ครั้ง)
- **คำถามที่ควรถามตัวเองก่อนปิดบทนี้:** *"ในโค้ดที่ฉันเขียนล่าสุด มีที่ไหนที่ข้อมูลจากผู้ใช้ถูกต่อเข้าไปในเอกสาร HTML สตริง JavaScript URL หรือ CSS — และที่นั้นใช้การเข้ารหัสตามบริบท หรือใช้การ 'กรองคำ'?"* · ถ้าคำตอบคืออย่างหลัง คุณเพิ่งพบรายการงานที่ควรทำก่อนสิ่งอื่น

ตอนหน้า (ตอนที่ 06) เราจะย้ายจาก "trust" ไปสู่ "ความลับ" · เราจะเริ่มจาก **cryptography** ที่เก่าแก่ที่สุด — Caesar cipher สมัยโรมัน → Vigenère → **Enigma** ในสงครามโลกครั้งที่สอง → DES → **RSA** → จนถึง TLS ที่คุณใช้ทุกวันนี้ · และเราจะตอบคำถามที่คนเขียนโปรแกรมทุกคนควรตอบให้ได้: *ทำไม confidential, integrity และ authenticity ถึงต้องมาจากคณิตศาสตร์ ไม่ใช่จากความหวัง* (คำว่า confidential, integrity, authenticity และ TLS เราจะ **นิยามให้ชัดในตอนหน้า**)

ระหว่างรอ ลองกลับไปดูโค้ดที่คุณเขียนล่าสุดอีกครั้ง แล้วถามว่า *"มีที่ไหนที่ฉันเอาข้อมูลจากข้างนอกไปต่อเข้าไปในหน้าเว็บ — และเบราว์เซอร์จะมองมันเป็นข้อความ หรือเป็นคำสั่ง"*
