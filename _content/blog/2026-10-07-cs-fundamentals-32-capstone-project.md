# Capstone project — รวมทุกอย่างที่เรียนมาเป็นของชิ้นเดียว (ตอนที่ 32)

เราผ่านมา **31 ตอน** แล้ว ตลอดทางเราสะสมของสองชนิดปนกันไป ชนิดแรกคือ **ความเข้าใจ** — ทำไมหน่วยความจำถึงทำงานแบบนั้น ทำไม shell ต้องมี builtin (คำสั่งที่ shell ทำเองในตัว ไม่ได้เรียกโปรแกรมข้างนอก) ชนิดที่สองคือ **โค้ดที่รันได้จริง** — compiler จิ๋วของเราเอง, shell จิ๋ว, โปรแกรม assembly, kernel ที่พิมพ์ข้อความบนจอ

ตอนนี้คือตอนที่เราจะ **หยุดเรียนของใหม่** แล้วหันมาประกอบทุกอย่างเข้าด้วยกันเป็น **ของชิ้นเดียวที่ทำงานได้จริงของเราเอง** — สิ่งนั้นเรียกว่า **capstone project** (อ่านว่า "แคปสโตน โปรเจกต์")

> **capstone project** = โครงงานปิดท้ายที่รวมความรู้ทั้งหมดของหลักสูตรไว้ในงานชิ้นเดียว คำว่า capstone แปลตรงตัวว่า "หินยอด" — หินก้อนบนสุดที่ปิดยอดกำแพงหรือพีระมิด เป็นก้อนที่ยึดทุกก้อนใต้มันให้อยู่ด้วยกัน ในมหาวิทยาลัยวิศวกรรมหรือวิทยาศาสตร์สาขาที่ต้องทำงานจริง (วิศวกรรมโยธา, วิทยาการคอมพิวเตอร์, สถาปัตยกรรม) นักศึกษาปีสุดท้ายจะต้องทำโครงงานแบบนี้ก่อนจบ เพื่อพิสูจน์ว่า "ทำเป็น" ไม่ใช่แค่ "สอบผ่าน"

ก่อนไปต่อ ขออธิบายอีกคำที่เจอในทุกโปรเจกต์ของตอนนี้:

> **starter** (สตาร์ท-เทอร์) = โค้ดตั้งต้นที่ทำงานได้จริงแล้วส่วนหนึ่ง เอาไว้ให้เราเริ่มจาก "ของที่เดินได้" แทนที่จะเริ่มจากหน้าว่าง
>
> **milestone** (ไมล์สโตน) = "หลักไมล์" = เป้าหมายย่อยที่ต้องผ่านไปทีละด่าน เราใช้ชื่อ **M0, M1, M2, M3, M4** โดย **M0 = สิ่งที่สคริปต์ในตอนนี้ทำให้แล้ว** (ของที่รันได้จริงเดี๋ยวนี้) และ M1 ขึ้นไปคือด่านที่เราต้องทำเองต่อ

> **ที่อยู่ของโค้ดในตอนนี้:** ทุกอย่างอยู่ใน `course/code/ep32/`
> - **`shell/` `compiler/` `tetris/` `kernel/`** = 4 โปรเจกต์ แยกโฟลเดอร์ตามชื่อ
> - **`internal/`** = lexer/parser/eval ที่ยกมาจาก `course/code/ep29/` (ผ่านการตรวจในตอน 26–30 แล้ว) โดยแก้แค่ชื่อ import — ไม่ได้เขียนใหม่จากศูนย์
> - **`out/`** = ผลรันจริงของทุกโปรเจกต์ (ไฟล์ `00_env.txt` ถึง `08_drill_answer.txt` — ไฟล์ไหนทำอะไร ดูตาราง "ไฟล์ใน `out/`" ท้ายบท)
> - **`run_all.sh`** = คอมไพล์+รันทุกอย่างแล้วเก็บผลลง `out/` (รันซ้ำได้เสมอ) · **`gen_svgs.py`** = สคริปต์วาดภาพทั้งสองในตอนนี้ โดยดึงตัวเลขจาก `out/` ตรง ๆ
> - **`README.md`** = วิธีรันแต่ละโปรเจกต์แบบสั้น ๆ
>
> โค้ดฉบับสมบูรณ์ทั้งหมดอยู่ในโฟลเดอร์ `course/code/ep32/` ของรีโปคอร์ส และบทความนี้ **ตัดโค้ดสำคัญมาใส่ครบทุกบรรทัด** ให้พิมพ์ตามได้โดยไม่ต้องเดา

ภาพข้างบนคือแผนที่ของทั้งตอน: การ์ดสี่ใบคือสี่โปรเจกต์ที่เราเลือกได้ · ด้านล่างคือ "พื้นฐานร่วม" ที่ทั้งสี่โปรเจกต์ดึงไปใช้เหมือนกัน (หน่วยความจำ, process/thread, syscall, virtual memory, ไฟล์, ทฤษฎีออโตมาตา, compiler/interpreter, runtime) · แถบสีเขียวล่างสุดคือตัวเลขที่ **คัดจากผลรันจริง** ใน `out/` ของตอนนี้ ไม่ได้พิมพ์จากความจำ

## 1. capstone คืออะไร — และทำไมมันสำคัญกว่าที่เราคิด

ถ้าให้สรุปสั้นที่สุดว่าตอนนี้ต่างจาก 31 ตอนที่ผ่านมาตรงไหน:

> ตอนที่ 1–31 เราสร้าง "ชิ้นส่วน" ทีละชิ้น แต่ละชิ้นอยู่ในกล่องของตัวเอง (มี `.go` แยก มี `out/` แยก มีโจทย์แยก) — ตอนที่ 32 เราจะ **ประกอบชิ้นส่วนหลายกล่องเข้าด้วยกันเป็นโปรแกรมเดียว** ที่ไม่มีใครบอกว่าต้องเขียนอะไรต่อ

ความต่างนี้ฟังดูเล็ก แต่ผลของมันใหญ่ในสามเรื่อง

### 1.1 มันพิสูจน์ว่าเรา "เข้าใจ" ไม่ใช่ "ทำตาม"

ตลอด 31 ตอน มีหลายครั้งที่เราเดินตามขั้นตอน: พิมพ์คำสั่งนี้ แล้วจะเห็นผลลัพธ์แบบนี้ การทำตามเป็นวิธีเริ่มที่ดีมาก — แต่มีจุดอ่อนหนึ่งข้อที่โหด:

> **โค้ดที่ทำตามได้ จะรันได้เฉพาะตอนที่เราทำตามเป๊ะ ๆ** — พอเจอโจทย์ที่ไม่เหมือนตัวอย่าง เราจะไม่รู้ว่าเริ่มจากตรงไหน

ลองนึกภาพสองคนที่เรียนเรื่องเดียวกัน:

- คนแรกทำตามทุกอย่างในตอน 26–30 จบ (lexer, parser, interpreter, codegen) สอบผ่านทุกตอน
- คนที่สองทำเหมือนกัน แต่ **เพิ่ม `while` loop เข้าไปในภาษาของตัวเองได้เอง**

ทั้งสองคนตอบข้อสอบเรื่อง "AST คืออะไร" ได้เท่ากัน แต่มีแค่คนที่สองที่รู้จริงว่า **สามชั้นของ compiler ต้องแก้พร้อมกันเสมอ** (lexer ต้องรู้จักคำสงวนใหม่ → parser ต้องมีกฎไวยากรณ์ใหม่ → interpreter ต้องมี node ใหม่) เพราะเขาได้แก้ทั้งสามชั้นด้วยมือตัวเอง

capstone คือเครื่องมือที่บังคับให้เรากลายเป็นคนที่สอง มันไม่มีเฉลย ไม่มี `out/` ให้เทียบ ไม่มี "ตอนที่ 33" ให้เปิดดู — มีแค่เรากับปัญหาที่เราตั้งขึ้นเอง

### 1.2 มันกลายเป็น portfolio ชิ้นแรกที่จับต้องได้

ถ้าจะสมัครงานสาย software engineer สิ่งที่คนคัดเลือกอยากเห็นไม่ใช่ "จบหลักสูตรออนไลน์ N คอร์ส" (เขาเห็นได้จาก resume ทุกใบ) แต่คือ **ลิงก์ที่กดเข้าไปดูได้ว่าของทำงานยังไง** — และคำถามที่ดีที่สุดที่ผู้สัมภาษณ์จะถามคือ "ตัวนี้คุณเขียนเองตรงไหน แล้วทำไมเลือกทำแบบนั้น"

> portfolio (พอร์ต-โฟลิโอ) = แฟ้มผลงาน — ตัวอย่างผลงานจริงที่แสดงว่าคนคนนี้ทำงานเป็น

capstone หนึ่งชิ้นที่เราอธิบายได้ทุกบรรทัด มีค่ามากกว่าคอร์สอบรมสิบใบที่เราจำได้แค่ชื่อเครื่องมือ

### 1.3 มันทำให้เห็นว่าแต่ละเรื่อง "เชื่อมกัน" ตรงไหน

นี่คือเหตุผลที่สำคัญที่สุด และเป็นเหตุผลที่เราตั้งใจเลือก 4 โปรเจกต์ให้มี "เนื้อ" ต่างกัน ห่างกันคนละทิศ:

| เรื่องที่เรียน (ตอน) | ไปโผล่ที่ไหนเวลาเขียนของจริง |
|---|---|
| memory, pointer, ตัวแปร (14–16) | kernel ต้องรู้ว่า stack คืออะไรก่อนจะ `bl kmain` ได้ · tetris เก็บกระดานเป็นอาร์เรย์ 2 มิติในสแตก ไม่จอง heap (พื้นที่หน่วยความจำสำหรับจองใช้ยืดหยุ่นตอนโปรแกรมรัน) เลย |
| stack กับ calling convention (15) | `boot.S` ตั้ง `sp` ให้ C มีที่วางตัวแปร · compiler ของเราต้องเดาว่าตัวลูกต้องถูกคำนวณก่อนตัวพ่อ |
| process, thread, การจัดคิว (18) | shell ต้องรอโปรแกรมลูกจบ (wait) · kernel จะเริ่มมี scheduler ตอน M4 |
| syscall: user ↔ kernel (19) | shell ทุกคำสั่งคือ `exec` ผ่าน syscall จริง · tetris ต้องเรียก `ioctl` เพื่อเปลี่ยนโหมดคีย์บอร์ด |
| virtual memory, paging (20) | ตัวเลข `0x40080000` ของ kernel คือที่อยู่ที่เราเลือกให้ linker · "แยกสิทธิ์อ่าน/เขียน (ต่อหน้า)" ยังไม่มีใน M0 |
| ไฟล์ + shell (21) | `cd` ต้องเป็น builtin เพราะโฟลเดอร์ปัจจุบันเป็นสมบัติของ process shell · `-demo` ของ tetris คือการเขียนผลลง stdout ซึ่งเป็น "ไฟล์" ชนิดหนึ่ง |
| ออโตมาตา + ทฤษฎี (22–25) | lexer คือ finite automata ตัวเป็น ๆ · ไหนจะเรื่อง P / NP / NP-hard ที่สอนเราว่าโจทย์ไหน "อย่าไปไล่หาคำตอบแบบตรง ๆ" |
| lexer → parser → eval → codegen (26–30) | ทั้งชุดถูกยกมาอยู่ใน `internal/` ของโปรเจกต์ mini-compiler โดยตรง |
| runtime + GC ของ Go (31) | tetris สร้าง `time.Ticker` แล้วปล่อยให้ runtime จัดการหมด — ไม่มี `free` ให้เรียก · `-demo` พิสูจน์ว่าโค้ดของเราทำงานได้แม้ไม่มีหน้าจอ |

อ่านตารางนี้ช้า ๆ สักรอบ — แต่ละแถวคือ "ทฤษฎี" ที่เคยดูเหมือนนามธรรม แล้วมันกลายเป็น "ข้อจำกัดจริง" ทันทีที่เราลงมือเขียนของเอง

### 1.4 ข้อดีอีกอย่างที่มองไม่เห็นในบทความ: โหมดไม่มีหน้าจอ

โปรเจกต์ทุกตัวในตอนนี้ถูกออกแบบให้ **รันได้โดยไม่มีหน้าจอ (TTY) และไม่มีคนนั่งเฝ้า** แม้ว่าตัวเกมและ kernel จะดูเหมือนต้องมีจอก็ตาม เพราะ:

- **พิสูจน์ผลได้** — ถ้าโปรแกรมของเราไม่ยอมคายอะไรออกมาเป็นข้อความ/ไฟล์ เราก็ไม่มีทางยืนยันว่า "มันทำงาน" ได้จริง นอกจากนั่งดูเอง
- **เป็นนิสัยของงานจริง** — โค้ดที่รันได้เฉพาะตอนมีคนนั่งเฝ้าหน้าจอ คือโค้ดที่รันบนเซิร์ฟเวอร์ไม่ได้ และวันหนึ่งเราจะต้องรันมันบนเซิร์ฟเวอร์

นี่คือเหตุผลที่ tetris ในตอนนี้มี flag (ตัวเลือกที่พิมพ์ต่อท้ายคำสั่ง เช่น `-demo`) และ shell/compiler อ่านคำสั่งจาก pipe ได้ — ไม่ใช่ของเล่นเพิ่ม แต่เป็น **ข้อกำหนดเดียวกับที่ทีมจริงใช้ตัดสินว่าโค้ด "พร้อม" หรือยัง**

> **TTY** ย่อจาก teletypewriter (เทลีไทป์ไรเตอร์) = คำเรียกดั้งเดิมของ "หน้าจอ terminal ที่คนนั่งพิมพ์อยู่"; ในสายตาโปรแกรม Unix หน้าจอคือ **ไฟล์ชนิดพิเศษ** ชนิดหนึ่ง ถ้าไม่ได้ต่อกับหน้าจอ อ่านจาก stdin ก็จะได้ EOF (End-Of-File = สัญญาณ "จบข้อมูล" ที่อ่านเจอเมื่อถึงท้ายไฟล์/ท่อปิด) ทันทีเมื่อท่อปิด — นี่คือเหตุผลที่ `./bin/shell < commands.txt` ทำงานได้และจบเอง

## 2. สี่โปรเจกต์ให้เลือก — แต่ละอันดึงความรู้คนละชุด

เราเลือกสี่โปรเจกต์นี้เพราะมัน **ห่างกันคนละทิศ** บนแผนที่ความรู้ที่เราเรียนมา:

- **Shell** อยู่ฝั่ง "ระบบ" (process, syscall, ไฟล์)
- **Mini-compiler** อยู่ฝั่ง "ภาษา" (ไวยากรณ์, ต้นไม้, ความหมาย)
- **Tetris** อยู่ฝั่ง "สถานะกับเวลา" — state machine (เครื่องสถานะ = โปรแกรมที่จำ "สถานะปัจจุบัน" แล้วเปลี่ยนตาม input), input, การวาดจอ
- **Mini-kernel** อยู่ฝั่ง "ฮาร์ดแวร์" (หน่วยความจำ, ที่อยู่, การบูต)

อ่านการ์ดทั้งสี่ก่อน แล้วค่อยไปดูหัวข้อ 3 ว่าเลือกยังไง — **อย่าเพิ่งตัดสินใจ**

---

### โปรเจกต์ 1 — Shell (ภาษา Go) ★★☆ · ประมาณ 8–12 ชั่วโมง

> **สร้างอะไร:** shell ของตัวเองที่ใช้ได้จริง — พิมพ์คำสั่งแล้วโปรแกรมทำงาน, `cd` ได้, รันคำสั่งอื่นบนเครื่องได้ แล้วค่อยขยายไปจนรองรับ `|` (pipe) และ `>` (redirect)
>
> **ใช้ความรู้ตอนไหน:**
> - **ตอน 19 (syscall)** — ทุกคำสั่งที่เราพิมพ์ กลายเป็นการเรียก `exec` ที่ข้ามจากโปรแกรมเราไปหา kernel จริง ๆ
> - **ตอน 21 (ไฟล์ + shell)** — ตอนที่เรียนว่า shell ทำงานยังไง, ทำไม `cd` ต้องเป็น builtin, fd (file descriptor = เลขที่ kernel ใช้แทนไฟล์ที่เปิดอยู่) สืบทอดไปให้โปรแกรมลูกได้
> - **ตอน 18 (process)** — shell ต้องรอโปรแกรมลูกจบ แล้วรู้ว่ามันจบด้วยสถานะอะไร
>
> **ระดับยาก:** ★★☆ — โค้ดสั้น (M0 ~160 บรรทัด ถ้าไม่นับคอมเมนต์) แต่แนวคิด "process ที่แยกจากกัน" ต้องเข้าใจจริง ๆ ไม่งั้นจะงงว่าทำไม `cd` ธรรมดาใช้ไม่ได้
>
> **พิสูจน์อะไร:** พิสูจน์ว่าเราเข้าใจว่า "โปรแกรมที่รันบนเครื่อง" กับ "โปรแกรมที่รันอยู่" ต่างกันตรงไหน — และเป็นโปรเจกต์ที่เพื่อนเปิดเครื่องเราแล้วใช้ทันทีได้เลย (ของเล่นที่ใช้จริง)

**ทำไมโปรเจกต์นี้เหมาะเป็นตัวแรก:** เพราะมันคือ *เครื่องมือที่เราอยู่กับมันทุกวัน* ถ้าเราสงสัยว่าทำไม `cd` (ที่อยู่ในโปรแกรม shell เดียวกัน) เปลี่ยนโฟลเดอร์ได้ แต่ `ls` (โปรแกรมภายนอก) ทำแบบนั้นไม่ได้ — คำตอบทั้งหมดอยู่ในโค้ดที่เราจะเขียนเอง (ไม่ถึง 250 บรรทัด)

---

### โปรเจกต์ 2 — Mini-compiler (ภาษา Go) ★★★ · ประมาณ 15–25 ชั่วโมง

> **สร้างอะไร:** ต่อยอดภาษาจิ๋วของตัวเองจากตอน 26–30 — เพิ่ม feature ใหม่ที่เราอยากได้ (เช่น `while`, ฟังก์ชัน, `for`) แล้วไปให้ไกลถึง **ตรวจชนิด (type check)** และ **สร้างโค้ด (codegen)**
>
> **ใช้ความรู้ตอนไหน:**
> - **ตอน 26 (lexer)** — ตัดข้อความโปรแกรมออกเป็นคำ
> - **ตอน 27 (parser + AST)** — ประกอบคำเป็นต้นไม้ตามกฎไวยากรณ์
> - **ตอน 28–29 (interpreter + scope/type)** — เดินต้นไม้แล้วคำนวณค่า, ตารางสัญลักษณ์
> - **ตอน 30 (codegen → assembly)** — แปลงต้นไม้เป็นชุดคำสั่งแบน ๆ
>
> **ระดับยาก:** ★★★ — ไม่ต้องคิดกลไกใหม่เลย (ทุกอย่างมีอยู่แล้ว) แต่ต้องแก้ **สามชั้นพร้อมกัน** ทุกครั้งที่เพิ่ม feature หนึ่งอย่าง นี่คือจุดที่คนส่วนใหญ่ตาย: เพิ่ม `while` ใน lexer เสร็จ แต่ลืมแก้ parser แล้วงงว่าทำไมถึงเจอข้อผิดพลาดทางไวยากรณ์ (parse error)
>
> **พิสูจน์อะไร:** พิสูจน์ว่าเราไม่ได้ "ทำตาม" แต่ **อ่านโค้ดของคนอื่น (ของตัวเองในอดีต) แล้วขยายต่อได้** — ทักษะนี้คือ 80% ของงาน software engineer จริง ๆ

**ทำไมโปรเจกต์นี้เหมาะกับคนที่ชอบตรรกะ:** มันเป็นโปรเจกต์เดียวที่เราคุม **ทุกบรรทัดของเส้นทางทั้งหมด** ข้อความ → คำ → ต้นไม้ → ค่า และเมื่อเราทำได้ เราจะไม่มีวันกลัว error ของ compiler อีกตลอดชีวิต

**เริ่มยังไงไม่ให้จม:** อย่าเพิ่งเพิ่ม feature ใหม่ — เปิด REPL (Read-Eval-Print Loop = ลูป อ่าน→คำนวณ→พิมพ์ผล→วนใหม่) ที่มีให้ (`go run ./compiler`) แล้วลองเดินดูว่ามันทำอะไรได้ อะไรไม่ได้ จากนั้นค่อยเพิ่มของที่เราอยากได้มากที่สุด **หนึ่งอย่าง** แล้วรัน test ทุกครั้ง

---

### โปรเจกต์ 3 — Tetris บน terminal (ภาษา Go) ★★☆ · ประมาณ 10–15 ชั่วโมง

> **สร้างอะไร:** เกม Tetris ที่เล่นจริงได้บนหน้าจอ terminal — กระดาน 10×20, ชิ้นส่วนตกลงมาด้วยแรงโน้มถ่วง, ปุ่ม `a`/`d` เลื่อน, หมุนได้, ลบแถวได้, มีคะแนน
>
> **ใช้ความรู้ตอนไหน:**
> - **ตอน 18–19 (process + syscall)** — เกมต้อง "ยืม" หน้าจอและคีย์บอร์ดชั่วคราว แล้วคืนให้เสมอไม่ว่าจะจบยังไง (นี่คือ `ioctl` ตัวเป็น ๆ)
> - **ตอน 21 (ไฟล์)** — stdout ของเราคือ "ไฟล์" ชนิดหนึ่ง เราเขียนไบต์ที่ควบคุมการเคลื่อนเคอร์เซอร์ลงไปได้
> - **ตอน 26 (lexer)** — การอ่านคีย์ทีละตัวคือการอ่าน "สตรีมไบต์" — หลักการเดียวกับที่ lexer เราใช้ตัดคำ
> - **ตอน 28 (interpreter)** — เกมคือ state machine: สถานะเปลี่ยนตาม input ทีละติ๊ก หัวใจเดียวกับ `eval()`
>
> **ระดับยาก:** ★★☆ — เขียนสนุกที่สุดในสี่ แต่มี "กับดักระบบ" ที่โปรเจกต์อื่นไม่มี: ถ้าเราเผลอจบโปรแกรมโดยไม่คืนค่าเทอร์มินัล หน้าจอผู้ใช้จะพัง (พิมพ์ไม่เห็นตัวอักษร) จนต้องพิมพ์ `reset`
>
> **พิสูจน์อะไร:** พิสูจน์ว่าเราเข้าใจว่า **input, จอ, กับเวลา เป็นเรื่องเดียวกันหมด** — และพิสูจน์ว่าเราแยก "ตรรกะ" ออกจาก "การวาด" ได้หรือไม่ ซึ่งเป็นทักษะที่ใช้ทุกวันในงานจริง

**ทำไมโปรเจกต์นี้เหมาะเป็น "รางวัล" ให้ตัวเอง:** มันเป็นของที่เรา **เล่นได้** ข้อดีทางจิตใจไม่ใช่เรื่องเล่น ๆ — โปรเจกต์แรกที่ได้นั่งเล่นเอง คือเชื้อเพลิงที่ทำให้โปรเจกต์ต่อไปเกิดขึ้น

---

### โปรเจกต์ 4 — Mini-kernel (C + aarch64 asm, QEMU) ★★★★ · ประมาณ 30–50 ชั่วโมง

> **สร้างอะไร:** kernel ของตัวเองที่ **boot บนโลหะเปล่า ๆ** (bare metal = ไม่มีระบบปฏิบัติการรองรับเลย) ในเครื่องจำลอง QEMU — เริ่มจากพิมพ์ข้อความผ่านชิป UART (ชิปส่ง-รับข้อความทีละตัวอักษร) แล้วขยายไปจนรับ input ได้, จัดการ exception (เหตุการณ์ผิดปกติที่ CPU ต้องเบรกมาดูทันที) ได้, และมี scheduler จ่ายงาน
>
> **ใช้ความรู้ตอนไหน:**
> - **ตอน 12 (assembly แรก)** — `boot.S` คือ "โค้ดบรรทัดแรกที่ CPU รัน" ต้องตั้ง stack ก่อนจะเรียกภาษา C ได้
> - **ตอน 13–14 (C + pointer)** — kernel เขียนด้วย C แต่ **ไม่มี libc (คลังฟังก์ชันมาตรฐานของภาษา C ที่ปกติมีให้ใช้ฟรี) ให้ใช้เลย** — `memcpy`/`memset` ต้องเขียนเอง
> - **ตอน 19 (syscall user ↔ kernel)** — ที่นี่เราไปยืนอยู่อีกฝั่ง: เรา *เป็น* kernel ที่คนอื่นเรียก
> - **ตอน 20 (virtual memory + paging)** — ที่อยู่ `0x40080000` ที่เรากำหนดใน linker script (แผนที่บอกว่าโค้ดแต่ละส่วนจะถูกวางที่ที่อยู่ไหนในหน่วยความจำ) คือความจริงที่ MMU (ชิปที่แปลงที่อยู่เสมือนเป็นที่อยู่จริง) จะต้องมาจัดการทีหลัง
>
> **ระดับยาก:** ★★★★ — ยากที่สุด และ **คุ้มที่สุด** ถ้าเป้าหมายของเราคือ "อยากเข้าใจลึกสุดว่าระบบทำงานยังไง" ทุก error ที่นี่เป็น error ชนิดที่ debug ไม่ได้ด้วย `printf` (เพราะ `printf` ยังไม่มี — เราต้องสร้างมันเองก่อน)
>
> **พิสูจน์อะไร:** พิสูจน์ว่าเราเข้าใจว่า **"ระบบปฏิบัติการ" ไม่ใช่ของวิเศษ** — มันเป็นโค้ดของคนอื่นที่ทำเรื่องที่เรากำลังทำอยู่นี่แหละ แค่ทำมานานกว่ามาก

**คำเตือนตามจริง:** โปรเจกต์นี้จะทำให้เราสงสัยคำถามที่หาคำตอบยาก ("ทำไม `sp` ต้องหารด้วย 16 ลงตัว", "ทำไมต้องปิด CPU แกนอื่นก่อน") และเราจะเข้าไปอ่านเอกสารของ ARM แทนที่จะได้เขียนโค้ด 1–2 ชั่วโมง ถ้าเราโอเคกับแบบนั้น — เลือกอันนี้ได้เลย ไม่มีโปรเจกต์ไหนให้ความเข้าใจลึกเท่านี้

## 3. วิธีเลือก — ตารางเดียว + คำถามสี่ข้อ

อย่าเลือกจาก "อันไหนเท่ที่สุด" ให้เลือกจาก **"อันไหนเราอยากเปิดดูผลลัพธ์ของมันทุกวัน"** เพราะโปรเจกต์ที่เราอยากเห็นผลคือโปรเจกต์ที่เราจะทำจนจบ

### ตารางเปรียบเทียบ

| โปรเจกต์ | ภาษา | ความรู้ที่ใช้ | ยาก | เวลา | เหมาะกับใคร | ได้อะไรกลับไป |
|---|---|---|---|---|---|---|
| **1 · Shell** | Go | ตอน 18, 19, 21 | ★★☆ | 8–12 ชม. | อยากได้ **เครื่องมือใช้จริง** และชอบเรื่องระบบ | shell ที่เพื่อนใช้ได้ |
| **2 · Mini-compiler** | Go | ตอน 26–30 | ★★★ | 15–25 ชม. | ชอบ **ตรรกะกับภาษา** ไม่กลัว tree | ภาษาของตัวเอง |
| **3 · Tetris** | Go | ตอน 18, 19, 21, 26, 28 | ★★☆ | 10–15 ชม. | อยากได้ **ของเล่น** และชอบเห็นผลทันตา | เกมที่เล่นได้ |
| **4 · Mini-kernel** | C + asm | ตอน 12, 13–14, 19, 20 | ★★★★ | 30–50 ชม. | อยากเข้าใจ **ลึกสุด** ไม่กลัวอ่านเอกสาร | kernel ที่ boot ได้ |

### คำถามประเมินตัวเองสี่ข้อ

ตอบในใจตามตรง (ไม่มีคำตอบไหน "ถูก") แล้วดูว่าชี้ไปที่โปรเจกต์ไหน:

1. **เวลาว่างติดกันนานสุดที่คุณมี คือ 2 ชั่วโมง หรือ 6 ชั่วโมง?**
   ถ้าตอบ 2 ชั่วโมง → Tetris หรือ Shell (เป็นงานที่แบ่งเป็นชิ้นสั้น ๆ ได้ ไม่ต้องจำ state เยอะข้ามวัน)
   ถ้าตอบ 6 ชั่วโมง → Mini-compiler หรือ Mini-kernel (งานที่ต้อง "อยู่ในโซน" ต่อเนื่องจึงจะไปได้ไกล)

2. **คุณอยากได้ "ของเล่นที่ใช้ได้จริง" หรือ "ความเข้าใจเชิงลึกที่จับต้องเป็นของเล่นไม่ได้"?**
   อยากได้ของเล่น → Tetris หรือ Shell (จบแล้วได้อะไรที่เปิดใช้ได้ทันที)
   อยากได้ความเข้าใจ → Mini-kernel (จบแล้วได้ความเข้าใจที่หาจากที่อื่นไม่ได้ — แต่ไม่มีใครเห็นจากข้างนอก)

3. **เวลาเจอ error ที่อ่านไม่ออก คุณอ่านต่อ หรือหันไปทำอย่างอื่น?**
   อ่านต่อได้ → Mini-kernel หรือ Mini-compiler (error ที่นี่จะอ่านไม่ออกบ่อยมาก และนั่นคือส่วนที่สนุก)
   หันไปทำอย่างอื่น → Tetris หรือ Shell (ป้อนกลับเร็ว เห็นผลทันที ทำให้กลับมาได้ง่าย)

4. **เป้าหมายสูงสุดของคุณ คือ "เขียนโปรแกรมเป็น" หรือ "เข้าใจว่าเครื่องคิดยังไง"?**
   เขียนเป็น → เริ่มจาก Shell แล้วต่อด้วย Mini-compiler (เส้นทางนี้ปูไปสู่การทำงานเร็วที่สุด)
   เข้าใจเครื่อง → Mini-kernel (เส้นทางนี้ปูไปสู่ระบบ/ฝังตัว/hardware)

**คำแนะนำตรง ๆ:** ถ้าไม่แน่ใจ ให้เริ่มที่ **Shell** มันเป็น M0 ที่สั้นที่สุด (ของจริง ~160 บรรทัด ถ้าไม่นับคอมเมนต์) และเป็นฐานให้เข้าใจโปรเจกต์อื่นทั้งหมด — ทุกคนที่ทำ Shell จบ จะเข้าใจโปรเจกต์ที่เหลือเร็วขึ้นชัดเจน และที่สำคัญ: **โจทย์ Mini-project ท้ายตอนนี้ทำ Shell ได้ครบทุกข้อ**

### 4.1 โปรเจกต์ Shell — REPL + builtin + คำสั่งภายนอก

โครงของ M0 มีสี่ส่วน (ดู `shell/main.go`):

1. **วงวน REPL** — อ่านบรรทัด → ทำ → พิมพ์ผล → กลับไปอ่านใหม่
2. **builtin สี่ตัว** — `cd`, `pwd`, `help`, `exit` (คำสั่งที่ shell ทำเองในโปรแกรมเรา)
3. **รันคำสั่งภายนอก** — หาโปรแกรมด้วย `exec.LookPath` แล้วรันผ่าน `os/exec`
4. **คืน exit code** — ส่งต่อสถานะของคำสั่งสุดท้ายให้คนที่เรียก shell เรา

หัวใจที่อยากให้สังเกตคือ **"ทำไม `cd` ต้องเป็น builtin"** — นี่เป็นคำถามที่คนเขียน shell มือใหม่ทุกคนเคยแพ้

ก่อนดู `cd` ขอดู builtin ที่สั้นกว่าอย่าง `exit` ก่อน เพื่อเห็นโครง `switch` ของ `handle` ให้เข้าใจง่าย ๆ:

```go
// shell/main.go (ตัดมาเฉพาะส่วนที่สำคัญ)
switch args[0] {
case "exit", "quit":
    // ออกจาก shell — คืน code ที่ส่งมาได้ (exit N)
    st.lastExit = 0
    if len(args) > 1 {
        if n, ok := atoi(args[1]); ok {
            st.lastExit = n
        }
    }
    return true, nil
}
```

และนี่คือส่วน `cd` ที่เป็นหัวใจของเรื่องทั้งหมด:

```go
case "cd":
    // builtin ที่สำคัญที่สุด: ถ้า cd เป็นโปรแกรมภายนอก การเปลี่ยนโฟลเดอร์
    // จะเกิดใน "โปรแกรมลูก" แล้วหายไปตอนโปรแกรมลูกจบ — shell ตัวพ่อไม่ขยับ
    target := os.Getenv("HOME")
    if len(args) > 1 {
        target = args[1]
    }
    if e := os.Chdir(target); e != nil {
        return true, fmt.Errorf("cd: %s: no such directory", target)
    }
    return true, nil
```

ส่วนการรันคำสั่งภายนอก — ลำดับตรงกับที่เรียนในตอน 21 พอดี (shell หาโปรแกรมได้โดยไล่ค้นหาจาก **PATH** = รายการโฟลเดอร์ที่เก็บโปรแกรมไว้):

```go
func (st *state) runExternal(args []string) error {
    path, err := exec.LookPath(args[0])   // 1) หาว่าโปรแกรมชื่อนี้อยู่ไฟล์ไหน (เดินตาม PATH)
    if err != nil {
        st.lastExit = 127                 // 127 = exit code มาตรฐานเมื่อ "หาคำสั่งไม่เจอ"
        return fmt.Errorf("%s: command not found", args[0])
    }

    cmd := exec.Command(path, args[1:]...) // 2) สร้างคำสั่ง ยังไม่รัน
    cmd.Stdin = os.Stdin                   // 3) ต่อท่อสามท่อของโปรแกรมลูก
    cmd.Stdout = st.out                    //    เข้ากับหน้าจอเดียวกับเรา
    cmd.Stderr = st.errOut

    if err := cmd.Run(); err != nil {      // 4) รัน + รอจนจบ + อ่าน exit code
        var ee *exec.ExitError
        switch {
        case errors.As(err, &ee):
            st.lastExit = ee.ExitCode()
            return fmt.Errorf("%s: exited with status %d", args[0], ee.ExitCode())
        default:
            return fmt.Errorf("%s: cannot run: %v", args[0], err)
        }
    }
    st.lastExit = 0
    return nil
}
```

เราสั่ง shell นี้ด้วยการ **ป้อนคำสั่งผ่านท่อ** (เพื่อให้เก็บผลรันได้โดยไม่มีหน้าจอ) — นี่คือผลรันจริงจาก `out/02_shell_session.txt`:

สามอย่างที่ควรสังเกตในผลรันนี้:

1. **`cd /tmp` แล้ว `pwd` พิมพ์ `/tmp`** — นี่คือหลักฐานว่า `cd` ทำงานในโปรเซสของ shell เอง ถ้ามันเป็นโปรแกรมภายนอก `pwd` จะยังพิมพ์โฟลเดอร์เดิม
2. **`command not found`** ไม่ได้ทำให้ shell ตาย — มันพิมพ์ error แล้วกลับไปรอคำสั่งถัดไป (shell ที่ error แล้วจบ คือ shell ที่ใช้ไม่ได้)
3. **exit code = 3** — ค่ามาจากคำสั่งสุดท้าย `exit 3` และ shell **ส่งต่อ** ให้คนที่เรียกมัน นี่คือกลไกที่ทำให้เชนคำสั่งอย่าง `prog && next` ทำงานได้ในโลกจริง

### 4.2 โปรเจกต์ Mini-compiler — REPL ที่ต่อยอดจากของเดิม

จุดสำคัญที่สุดของโปรเจกต์นี้คือ **เราไม่เขียนใหม่จากศูนย์** — M0 ยกของที่ตรวจมาแล้วจากตอน 26–30 มาใส่ `internal/` ทั้งชุด:

```text
compiler/main.go        ← ของใหม่: เปลือก REPL
internal/lexer/lexer.go ← ของเดิมจากตอน 26 (แก้แค่ชื่อ import)
internal/parser/ast.go  ← ของเดิมจากตอน 27
internal/parser/parser.go
internal/eval/eval.go   ← ของเดิมจากตอน 28–29
```

ทำไมต้องทำแบบนี้ — เพราะ **การยกโค้ดที่ผ่านการตรวจมาใช้ คือทักษะของวิศวกร ไม่ใช่การโกง** สิ่งที่เราเพิ่มใน M0 มีสองอย่างเท่านั้น:

1. **วงวน REPL** ที่แยกแยะได้ว่าบรรทัดที่พิมพ์มาเป็น *นิพจน์* (`3 + 4`), *การกำหนดค่าใหม่* (`x = x + 5`), หรือ *คำสั่ง* (`let x = 3`, `if ... { }`)
2. **การรวบหลายบรรทัด** เมื่อบล็อก `{ }` ยังไม่ปิด — พิมพ์ `if x > 0 {` แล้ว Enter ได้ โดยไม่ต้องพิมพ์ทั้งหมดในบรรทัดเดียว

การแยกแยะว่าบรรทัดไหนเป็น "คำสั่ง" มีกับดักเล็ก ๆ ที่ทำให้โค้ดมือใหม่พังบ่อย และ M0 มีเทสต์ดักไว้:

```go
// compiler/main.go — looksLikeStmt
func looksLikeStmt(s string) bool {
    for _, kw := range []string{"let", "if", "print"} {
        if s == kw || strings.HasPrefix(s, kw+" ") || strings.HasPrefix(s, kw+"\t") {
            return true
        }
    }
    return strings.HasSuffix(s, ";") || strings.HasSuffix(s, "}")
}
```

> **กับดัก:** ถ้าเราเช็คด้วย `strings.HasPrefix(s, "let")` ตรง ๆ ตัวแปรชื่อ `letter` จะถูกมองว่าเป็นคำสั่ง `let` ทันที — bug ชนิดนี้เงียบมาก (ไม่มี error แค่ทำงานผิด) และมีเทสต์ `TestLooksLikeStmt` ใน `compiler/main_test.go` คอยดักไว้ให้

การเพิ่ม **การกำหนดค่าใหม่** (`x = 5` ให้กับตัวแปรที่มีอยู่แล้ว) เราทำที่ชั้น REPL ไม่ได้แตะ `internal/` เลย — เพราะ `eval.Env.Define` เขียนทับค่าเดิมได้อยู่แล้ว:

```go
// parseAssign — จับรูปแบบ "ชื่อ = นิพจน์" (โดยไม่สับสนกับ == และ !=)
func parseAssign(s string) (name, rhs string, ok bool) {
    for i, r := range s {
        if r != '=' {
            continue
        }
        if i+1 < len(s) && s[i+1] == '=' {      // ข้าม ==
            continue
        }
        if i > 0 && (s[i-1] == '=' || s[i-1] == '!' || s[i-1] == '<' || s[i-1] == '>') {
            continue                            // ข้าม != <= >=
        }
        lhs := strings.TrimSpace(s[:i])
        rhs = strings.TrimSpace(s[i+1:])
        if rhs == "" || !isIdent(lhs) {
            return "", "", false
        }
        return lhs, rhs, true
    }
    return "", "", false
}
```

**ทำไมเลือกทำแบบนี้:** เพราะถ้าเราไปแก้ `internal/lexer` กับ `internal/parser` เพื่อรองรับ `=` เป็นเครื่องหมายกำหนดค่า เราจะ **เสี่ยงทำของเดิมพัง** (ของเดิมใช้ `=` ใน `let` อยู่แล้ว) การแยกงานที่ "ยังไม่แน่ใจ" ไปไว้ชั้นบนสุด แล้วค่อยย้ายลงไปทีหลังเมื่อเข้าใจครบ — คือวิธีทำงานที่ปลอดภัยกว่ามาก

นี่คือผลรันจริงจาก `out/03_compiler_repl.txt` (บรรทัดที่ขึ้นต้นด้วย `>` คือบรรทัดที่เราป้อนเข้าไป):

สี่อย่างที่ควรสังเกต:

1. **`3 + 4 * 5` ให้ต้นไม้ที่ `*` อยู่ลึกกว่า `+`** — นี่คือหลักฐานว่า precedence (ลำดับความสำคัญของเครื่องหมาย) ไม่ได้ถูก "ใส่เป็นตัวเลขลำดับ" แต่เกิดจาก **ความลึกของชั้นไวยากรณ์** ที่เราเขียนไว้ในตอน 27

4. **ข้อความ error เป็นภาษาอังกฤษ แต่มีตำแหน่งบรรทัด:คอลัมน์** — ธรรมเนียมของเครื่องมือสร้างโปรแกรมทั่วโลกคือข้อความ error เป็นอังกฤษ (เพื่อให้ค้นหาต่อได้) ส่วนคำอธิบายเป็นไทยอยู่ในบทความและในคอมเมนต์โค้ด

### 4.3 โปรเจกต์ Tetris — เกมที่พิสูจน์ว่าตรรกะแยกจากหน้าจอได้จริง

นี่คือโปรเจกต์ที่ "กับดักเครื่องมือ" เยอะที่สุด และ M0 ของเราออกแบบมาสู้กับกับดักนั้นโดยตรง

**กับดักที่ 1: ต้องเปลี่ยนโหมดคีย์บอร์ดของเทอร์มินัล**
ปกติ terminal จะรอให้เรากด Enter ก่อนส่งข้อความมาให้โปรแกรม (เรียกว่าโหมด canonical) และจะ echo ตัวอักษรกลับมาให้เห็นด้วย เกมต้องปิดทั้งสองอย่าง — นี่คือ **raw mode** และต้องใช้ syscall `ioctl` (ทบทวนตอน 19):

```go
// tetris/main.go — makeRaw (สรุป)
//   ECHO        = ปิดการสะท้อนตัวอักษรกลับไปที่จอ
//   ICANON      = ปิดการรอ Enter (อ่านได้ทีละไบต์ทันทีที่กด)
//   ISIG/IEXTEN = ปิดการแปลง Ctrl-C เป็นสัญญาณ + อักขระพิเศษของโหมดบรรทัด
raw.Lflag &^= syscall.ECHO | syscall.ICANON | syscall.ISIG | syscall.IEXTEN
//   IXON/ICRNL/BRKINT/INPCK/ISTRIP = ปิดการประมวลผล input พิเศษ (Ctrl-S/Ctrl-Q, แปลง CR เป็น NL ฯลฯ)
raw.Iflag &^= syscall.IXON | syscall.ICRNL | syscall.BRKINT | syscall.INPCK | syscall.ISTRIP
raw.Cc[syscall.VMIN] = 1  // VMIN=1: รออย่างน้อย 1 ไบต์ก่อนคืนค่าอ่าน
raw.Cc[syscall.VTIME] = 0 // VTIME=0: ไม่ตั้งเวลาหมดเขต (รอจนได้ไบต์จริง)
```

**กับดักที่ 2: ถ้าจบโปรแกรมโดยไม่คืนค่าเดิม หน้าจอผู้ใช้จะพัง** — ต้อง `defer restore(...)` (defer = สั่งให้ทำสิ่งนี้ตอนฟังก์ชันจบ ไม่ว่าจะจบทางไหน) ทันทีหลังเปลี่ยน เพราะไม่ว่าจะออกทางไหน (กด `q`, ถูกฆ่า, panic) ค่าเดิมต้องกลับมาเสมอ

**กับดักที่ 3 (แพงที่สุด): โปรแกรมที่ต้องมี "หน้าจอจริง" จะพิสูจน์ตัวเองไม่ได้ในอัตโนมัติ** — cron/CI (ระบบรันงานอัตโนมัติที่ไม่มีคนนั่งเฝ้า), เซิร์ฟเวอร์ ไม่มีหน้าจอ ถ้าเรารัน `tetris` ที่นั่นมันจะค้างหรือ error ทันที

M0 แก้กับดักที่สามด้วยการ **แยกตรรกะเกมออกจากการวาดโดยสิ้นเชิง** — ฟังก์ชัน `collides`, `clearLines`, `gravitate` ไม่รู้จักคีย์บอร์ดและไม่รู้จัก ANSI escape (รหัสลับที่พิมพ์ลงจอเพื่อสั่งให้เคอร์เซอร์ขยับ/ล้างจอ) เลย:

```go
// ตรรกะล้วน — ทดสอบได้ ไม่ต้องมีจอ
func collides(b board, p piece, x, y int) bool {
    for _, c := range p.cells {
        nx, ny := x+c.x, y+c.y
        if nx < 0 || nx >= boardW || ny >= boardH {
            return true
        }
        if ny >= 0 && b[ny][nx] != empty {
            return true
        }
    }
    return false
}
```

`tick 0` คือชิ้นแรกที่ตกลงมาหนึ่งช่องแล้ว · `tick 19` คือจังหวะที่ชิ้นแรก **ล็อกลงพื้น** (ช่องบนกระดานกลายเป็น `#`) แล้วชิ้นใหม่เกิดที่ด้านบน (ช่อง `@`) · และท้ายที่สุดการวาง 4 ชิ้นให้แถวล่างสุดเต็ม 10 ช่อง ทำให้ `clearLines()` ลบไป 1 แถว ได้ 100 คะแนน

เราปิดท้ายไฟล์ผลรันด้วยการทดสอบตรง ๆ เพื่อให้ **กรณีขอบ** ที่คนเขียนเกมมักพลาด กลายเป็นข้อความที่อ่านได้:

```text
  collides(x= 3, y= 0) = false  ← ในที่ว่าง
  collides(x= 6, y= 0) = false  ← ชิดขอบขวาพอดี
  collides(x= 7, y= 0) = true   ← หลุดขอบขวา
  collides(x=-1, y= 0) = true   ← หลุดขอบซ้าย
  collides(x= 3, y=19) = false  ← แตะพื้นพอดี
  collides(x= 3, y=20) = true   ← เลยพื้น
```

สองบรรทัดกลางสำคัญที่สุด: **"ชิดขอบพอดี" ต้องไม่ชน แต่ "เลยขอบไปหนึ่งช่อง" ต้องชน** — ความต่างของสองกรณีนี้คือ bug ที่คนเขียนเกมทุกคนเคยเจอ (ตัวอักษรโผล่ผิดคอลัมน์ หรือเกมจบทันทีที่ชิ้นแตะพื้น) และเพราะเรามีเทสต์ (`tetris_test.go`) เราจึงมั่นใจได้ก่อนเปิดหน้าจอ

### 4.4 โปรเจกต์ Mini-kernel — โปรแกรมแรกที่ไม่มีใครช่วย

นี่คือโปรเจกต์ที่ "ทุกอย่างที่เคยมีให้ฟรี ต้องสร้างเอง" — ไม่มี libc, ไม่มี `main()`, ไม่มีระบบไฟล์, ไม่มี terminal ให้ใช้แบบที่เราเคยใช้

**ชิ้นที่ 1: `linker.ld` (แผนที่การวางโค้ดในหน่วยความจำ)**

```ld
ENTRY(_start)
SECTIONS
{
    . = 0x40080000;              /* ที่อยู่ที่ QEMU (machine virt) โหลด kernel ไปวาง */
    .text.boot : { *(.text.boot) }   /* ต้องเป็นส่วนแรกสุด — CPU กระโดดมาที่นี่พอดี */
    .text   : { *(.text*) }        /* โค้ดโปรแกรมทั้งหมด (ฟังก์ชันที่ compiler แปลจาก C) */
    .rodata : { *(.rodata*) }      /* ค่าคงที่อ่านอย่างเดียว (เช่นข้อความ banner) */
    .data   : { *(.data*) }        /* ตัวแปร global ที่มีค่าเริ่มต้นไม่ใช่ศูนย์ */
    .bss : {
        __bss_start = .;
        *(.bss*) *(COMMON)
        __bss_end = .;
    }
    . = ALIGN(16);                 /* จัดที่อยู่ถัดไปให้ลงตัว 16 ไบต์ (aarch64 บังคับ sp หาร 16 ลงตัว) */
    . = . + 0x4000;                /* จองที่ 16 KiB ให้ stack */
    __stack_top = .;               /* ยอด stack — sp โตลงจากตรงนี้ */
}
```

`0x40080000` ไม่ใช่เลขสุ่ม แต่เป็น **สัญญาของ QEMU รุ่นนี้** ถ้าเราเปลี่ยนเป็นที่อยู่อื่น CPU จะกระโดดไปเจอความว่างเปล่า แล้วเครื่องจะค้างแบบที่ไม่มี error ให้อ่านเลย

**ชิ้นที่ 2: `boot.S` — โค้ดชิ้นแรกที่ CPU รัน (assembly)**

```asm
_start:
    mrs     x0, mpidr_el1        /* อ่านหมายเลข CPU (แกนไหนตื่นอยู่) */
    and     x0, x0, #0xFF        /* มาสก์เอาเฉพาะ 8 บิตล่าง = เลขแกน CPU */
    cbz     x0, master
hang:
    wfe                          /* แกนอื่นนอนรอ — ไม่ไปแย่ง UART กับแกน 0 */
    b       hang
master:
    ldr     x1, =__stack_top     /* ต้องตั้ง stack ก่อน ไม่งั้นเรียก C ไม่ได้ */
    mov     sp, x1
    ldr     x2, =__bss_start     /* ล้าง .bss (ตัวแปร global ต้องเริ่มที่ 0) */
    ldr     x3, =__bss_end
clear_bss:
    cmp     x2, x3
    b.ge    bss_done
    str     xzr, [x2], #8        /* เขียน 0 ทีละ 8 ไบต์ แล้วเลื่อนนิ้วไป 8 */
    b       clear_bss
bss_done:
    bl      kmain                /* กระโดดเข้าโค้ดภาษา C แล้วไม่กลับมา */
```

สามบรรทัดแรกของ `master` คือคำตอบของคำถามที่คนเขียน kernel มือใหม่ทุกคนเจอ: **"ทำไมต้อง assembly ก่อน ทำ C เลยไม่ได้หรือ"** — เพราะภาษา C ต้องมี stack กับตัวแปร global และสองอย่างนั้นต้องมี "ที่ให้วาง" ก่อน ซึ่งคือสิ่งที่ `linker.ld` กับ `boot.S` เพิ่งทำเสร็จ

**ชิ้นที่ 3: `kernel.c` — ของที่ libc เคยทำให้**

```c
/* กับดัก: เมื่อไหร่ที่ compiler "เลือก" เปลี่ยน loop ที่คัดลอกหรือล้างข้อมูล
 * (เช่นคัดลอก struct ใหญ่ หรือ zero array) ให้กลายเป็นการเรียก memcpy()/memset()
 * บน bare metal มันไม่มี libc ให้เรียก — ตอนนั้นจะกลายเป็น "link ไม่ผ่าน"
 * ไม่ใช่ทุกโปรแกรมที่โดน · kernel M0 ก้อนนี้ยังไม่มี struct ใหญ่จึงยังไม่โดน
 * แต่เขียนดักไว้ก่อน เพราะ M1 ขึ้นไป (รับ input + จัดการ exception) จะเจอแน่นอน */
void *memset(void *dst, int c, size_t n) { /* เนื้อใน: วนเขียน c ลง dst ทีละไบต์ n ครั้ง */ }
void *memcpy(void *dst, const void *src, size_t n) { /* เนื้อใน: วนก๊อป src ไป dst ทีละไบต์ n ครั้ง */ }
```

และการ "พิมพ์ข้อความ" คือการเขียนไบต์ลงใน **ที่อยู่ของฮาร์ดแวร์** ตรง ๆ:

```c
#define UART0_BASE 0x09000000UL
#define UART_DR (*(volatile uint32_t *)(UART0_BASE + 0x00)) /* Data Register */
#define UART_FR (*(volatile uint32_t *)(UART0_BASE + 0x18)) /* Flag Register */
#define FR_TXFF (1u << 5) /* Transmit FIFO Full — ถ้า 1 แปลว่า "ส่งไม่ได้ ต้องรอ" */

static void uart_putc(char c)
{
    while (UART_FR & FR_TXFF) {
        /* busy-wait จนกว่าฮาร์ดแวร์จะบอกว่าพร้อม
           ถ้าเขียนตอน FIFO เต็ม ตัวอักษรจะหายเงียบ ๆ */
    }
    UART_DR = (uint32_t)c;
}
```

> **คำศัพท์:** **UART** (ยู-อาร์ต) ย่อจาก Universal Asynchronous Receiver/Transmitter = ชิปที่ทำหน้าที่รับ-ส่งข้อความทีละตัวอักษร · **PL011** คือรุ่นของ UART ที่ ARM ทำ (บนบอร์ด QEMU รุ่น virt มันอยู่ที่ที่อยู่ `0x09000000`) · **register** (รีจิสเตอร์) = ช่องเล็ก ๆ ในหน่วยความจำที่ผูกกับฮาร์ดแวร์โดยตรง — เขียนค่าลงไปแล้วฮาร์ดแวร์ทำตามทันที

คอมไพล์ด้วย cross compiler (เพราะ "เครื่องที่เขียนโค้ด" กับ "เครื่องเป้าหมาย" ต้องเป็น aarch64 เหมือนกัน ทั้งคู่คือ ARM64):

```bash
cd course/code/ep32/kernel
./build.sh     # aarch64-linux-gnu-gcc -ffreestanding -nostdlib → kernel.elf
./run.sh       # qemu-system-aarch64 -M virt -cpu cortex-a53 -nographic ... -kernel kernel.elf
```

`-ffreestanding` แปลว่า "ไม่มีระบบปฏิบัติการอยู่ข้างหลัง" → compiler จะไม่สมมติว่ามี libc ให้ และ `-nostdlib` คือห้าม link มาตรฐาน C เข้ามาเลย นี่คือผลลัพธ์จาก `out/05_kernel_build.txt`:

```text
== 1) แสดงว่า toolchain คืออะไร ==
aarch64-linux-gnu-gcc (Debian 14.2.0-19) 14.2.0

== 2) คอมไพล์ assembly (boot.S → boot.o) ==
== 3) คอมไพล์ C (kernel.c → kernel.o) ==
== 4) เชื่อมตามแผนที่ใน linker.ld (boot.o + kernel.o → kernel.elf) ==

== 5) ตรวจไฟล์ที่ได้ (ไฟล์ ELF สำหรับ aarch64) ==
kernel.elf: ELF 64-bit LSB executable, ARM aarch64, version 1 (SYSV), statically linked, ...
--- ส่วนหัวของ ELF: entry point ต้องเป็น 0x40080000 ---
  Class:                             ELF64
  Machine:                           AArch64
  Entry point address:               0x40080000
--- ขนาด section ---
   text	   data	    bss	    dec	    hex	filename
   2417	      0	      8	   2425	    979	kernel.elf
```

> **ELF** (ย่อจาก Executable and Linkable Format) = ไฟล์ ELF (รูปแบบไฟล์โปรแกรมที่ระบบปฏิบัติการโหลดไปรัน — บน Linux ทุกโปรแกรมที่รันได้อยู่ในรูปแบบนี้) · `entry point` ในส่วนหัวคือที่อยู่ของคำสั่งแรกที่ CPU ไปเริ่มรัน — ของเราคือ `0x40080000` ตรงตามที่เขียนไว้ใน `linker.ld`

และเมื่อเรา **บูตมันจริงบน QEMU** (โหมด headless — ไม่มีหน้าจอ) ได้ข้อความจาก kernel ของเราเอง (จาก `out/06_kernel_boot.txt`):

```text
========================================
  Hello from my kernel!
========================================
ข้อความนี้พิมพ์โดย kernel ของเราบน bare metal
ไม่มี Linux ไม่มี libc มีแต่เรา กับ PL011 UART ที่ address 0x09000000 (= 0x9000000)

[ข้อมูลจากฮาร์ดแวร์]
  banner (static const) อยู่ที่ address : 0x400808a8
  ข้อความใน banner                     : mini-kernel ep32
  CurrentEL                            : EL1
  MPIDR (แกนที่กำลังรัน)               : 0x80000000
  counter ใน .bss เริ่มต้นเป็น          : 0  (พิสูจน์ว่า boot.S ล้าง .bss สำเร็จ)

[เราสั่งฮาร์ดแวร์ได้จริง — พิมพ์ตัวอักษร 16 ตัว]
  a b c d e f g h i j k l m n o p

== จบการทำงานของ kmain — เข้าลูป wfe (นอนรอเหตุการณ์) ==
   (บนเครื่องจริง ขั้นถัดไปคือเปิด interrupt เพื่อรับ input)
```

สี่ตัวเลขในผลรันนี้คือ **หลักฐานที่ตรวจสอบได้** ทั้งหมด:

- **`0x400808a8`** คือที่อยู่จริงของข้อความ `banner` ในหน่วยความจำ — ยืนยันว่า `linker.ld` วางส่วน `.rodata` ตามแผนจริง
- **`CurrentEL: EL1`** บอกว่าโค้ดของเรารันอยู่ที่ "ชั้นสิทธิ์" ระดับ kernel ไม่ใช่ user — (ทบทวนตอน 19: ที่นี่คือฝั่งที่คนอื่นต้องขอผ่าน syscall)
- **`MPIDR = 0x80000000`** ยืนยันว่า `boot.S` ปล่อยให้ **แกน 0** ทำงานจริงตามที่เขียนไว้ (รหัสแกนอยู่ในบิตต่ำ)
- **`counter ใน .bss = 0`** ยืนยันว่าลูป `clear_bss` ใน `boot.S` ทำงานจริง — และ `.bss` มีขนาด **8 ไบต์** ตามที่เห็นใน `size` ด้านบน เพราะเราประกาศตัวแปร `counter` เป็น `volatile` (ถ้าไม่ใส่ `volatile` compiler จะ "เห็นว่าไม่มีใครเขียนค่าเลย" แล้วพับตัวแปรทิ้ง — `.bss` จะเหลือ 0 ไบต์และการพิสูจน์ของเราก็จะไม่จริง)

**หมายเหตุตามจริงเรื่อง QEMU บนเครื่องนี้:** บน Debian 13 ชุดนี้ คำสั่ง QEMU **ต้องมี `-nic none`** ไม่งั้นมันจะตายด้วยข้อความ `failed to find romfile "efi-virtio.rom"` (แพ็กเกจไม่มีไฟล์ option ROM ของการ์ดเครือข่ายมาให้) ทั้งที่โปรเจกต์นี้ไม่ใช้เครือข่ายเลย — `run.sh` ใส่ไว้ให้แล้วพร้อมคอมเมนต์อธิบาย และนี่คือตัวอย่างจริงของ "กับดักเครื่องมือ" ที่เจอได้ทุกสัปดาห์ในงานจริง: โค้ดเราถูก แต่ **environment** ไม่พร้อม และเราต้องอ่าน error ให้เป็น

### 4.5 Roadmap: ต่อจาก M0 ไป M4 ยังไง

![ตัวอย่าง milestone roadmap จาก M0 ถึง M4](/assets/diagrams/ep32-02-milestone-roadmap.svg)

ภาพข้างบนคือ roadmap ของโปรเจกต์ Shell ในฐานะ **ตัวอย่าง** — โปรเจกต์อื่นใช้หลักคิดเดียวกัน (เพิ่มความสามารถหนึ่งชั้นต่อหนึ่ง M และจบด้วยของที่ใช้จริงได้) ตารางข้างล่างคือ roadmap ย่อของทั้งสี่:

| | **Shell** | **Mini-compiler** | **Tetris** | **Mini-kernel** |
|---|---|---|---|---|
| **M0** (มีแล้ว) | REPL + builtin + คำสั่งภายนอก + exit code | REPL รัน expr/`let`/`if`/`print` | กระดาน 10×20 + gravity + `a`/`d` + `q` + หมุน (wall kick = กติกาที่ให้ชิ้นหมุนชิดกำแพงได้โดยดันออกเล็กน้อย) + ลบแถว + คะแนน + `-demo` | ตั้ง stack → `kmain` → UART พิมพ์ข้อความ |
| **M1** | ตัดคำด้วย quote (`"a b"`) + pipe `cmd \| cmd` (แยก fd + ปิดท่อทุกอัน) | `while` loop (แก้ 3 ชั้นพร้อมกัน) | ครบทั้ง 7 ชิ้น (tetromino) + สุ่มด้วย seed | รับ input จาก UART (echo กลับ) |
| **M2** | redirect `> >> < 2>` + background `&` + `wait` | ฟังก์ชัน + ค่าที่คืนได้ | hold + next queue + ระดับความเร็วเพิ่มขึ้น | exception handler + พิมพ์ข้อมูล exception (เหตุการณ์ผิดปกติที่ CPU ต้องเบรกมาดู) |
| **M3** | shell state: ตัวแปร env + `export` + `$?` | type check (ตารางสัญลักษณ์จากตอน 29) | เมนู + บันทึกไฮสกอร์ + pause | timer interrupt + ตัวนับเวลา |
| **M4** | history + tab completion + อ่าน `~/.shellrc` + alias | codegen → ชุดคำสั่งแบน (ต่อจากตอน 30) | (ต่อยอด) เอฟเฟกต์/เสียง/สถิติ | scheduler จ่ายงานหลาย task สลับกัน |

สังเกตว่า **M0 ของทั้งสี่เริ่มจาก "พิสูจน์ว่ารากฐาน (foundation) ใช้ได้"** ไม่ได้เริ่มจาก "feature แรก" — เพราะเป้าหมายของ M0 ไม่ใช่การมี feature แต่น้อย แต่คือการมี **เส้นทางที่รันได้จริง** ซึ่งเราต่อยอดได้ วิธีคิดนี้ต่างจากวิธีที่มือใหม่มักทำ (เขียนทุกอย่างแล้วค่อยรัน) และเป็นเหตุผลที่ M0 ของทั้งสี่มีผลรันอยู่ใน `out/` ตั้งแต่ตอนนี้

## 5. วิธีทำต่อจนจบโปรเจกต์ — dev loop, git, และ "เมื่อติด"

### 5.1 dev loop: สร้าง → พัง → อ่าน → สร้างใหม่

ลูปการทำงานของโปรแกรมเมอร์ทุกคน (ไม่ว่าจะเก่งแค่ไหน) มีสี่จังหวะซ้ำ ๆ และ **จังหวะที่สำคัญที่สุดคือจังหวะที่สาม**:

```text
1. สร้าง (write)   — เขียนโค้ดส่วนเล็ก ๆ ที่เรามั่นใจว่าถูก
2. รัน (run)       — รันทันที อย่ารอให้ครบทั้งโปรเจกต์
3. อ่าน (read)     — อ่านข้อความ error ที่เครื่องบอก จริง ๆ อ่านให้จบ
4. แก้ (fix)       — แก้ "หนึ่งอย่าง" แล้วกลับไปข้อ 1
```

คนที่ติดอยู่นานมักติดที่จังหวะ 3 ไม่ใช่จังหวะ 1 — เขาเขียนโค้ดเพิ่มทั้งที่ยังไม่อ่านว่าเครื่องบ่นอะไร และ**จังหวะ 1 ที่ใหญ่เกินไป** คือสาเหตุอันดับหนึ่งที่ทำให้ลูปนี้พัง เพราะเมื่อแก้อะไรสักอย่างแล้วพัง เราจะไม่รู้ว่า 12 บรรทัดที่เพิ่งเพิ่ม บรรทัดไหนเป็นตัวการ

**ขนาดที่แนะนำ:** เขียนโค้ดใหม่ไม่เกิน 20–30 บรรทัดต่อรอบ แล้วรัน ถ้ามันพัง ให้ย้อนกลับมาที่จุดที่รันผ่านล่าสุดทันที (ใน git ใช้ `git stash` หรือ `git checkout -- <ไฟล์>`)

### 5.2 เก็บงานด้วย git — ทำทันทีในวันที่หนึ่ง ไม่ใช่ตอนจบ

กติกาเดียวที่ต้องทำ: **commit ทุกครั้งที่ผ่าน M หรือแก้ bug สำเร็จ** ไม่ต้องรอให้สวย

> **ศัพท์ git ที่ใช้ในตอนนี้:** `git` = ระบบเก็บประวัติโค้ด · **branch (กิ่ง)** = สายงานแยก ไม่ทับ `main` · **clone** = ก๊อปทั้งโปรเจกต์ลงเครื่อง · **push** = ส่งโค้ดขึ้นที่เก็บกลาง

```bash
cd course/code/ep32

git checkout -b cs-fundamentals/ep32-capstone     # ทำงานบนกิ่งของตัวเอง ไม่ทับ main
git add shell/
git commit -m "ep32 shell: M0 — REPL + builtin + exec ผ่านครบ"

# ทำงานต่อ... พอ M1 เสร็จ
git add shell/
git commit -m "ep32 shell: M1 — ตัดคำด้วย quote ได้"
```

**ทำไม commit บ่อยสำคัญกว่า commit สวย:** เพราะจุดประสงค์แรกของ git ไม่ใช่ "ประวัติที่คนอื่นอ่านสวย" แต่คือ **"ย้อนกลับไปจุดที่ยังทำงานได้"** ถ้าเรา commit บ่อย เราจะย้อนกลับได้เสมอด้วยการเสียเวลาน้อยที่สุด ส่วนข้อความ commit สวย ๆ เป็นโบนัส ไม่ใช่เป้าหมาย

**กับดักเล็ก ๆ ที่ควรรู้:** อย่า commit ไฟล์ที่สร้างจากคำสั่งได้ (ไฟล์ `.o`, `kernel.elf`, โฟลเดอร์ `bin/`) — แต่ **ควร commit โฟลเดอร์ `out/`** เพราะมันคือหลักฐานผลรันที่บทความอ้างถึง และคนอ่านที่ clone ไปจะตรวจเทียบได้โดยไม่ต้องรันเอง (ในตอนนี้ `run_all.sh` สร้าง `out/` ใหม่ได้เสมอ ถ้าใครอยากตรวจก็รันสคริปต์นั้น)

### 5.3 เมื่อติด ให้ทำอะไร (ตามลำดับ)

นี่คือเช็กลิสต์ที่ใช้ได้กับทุกโปรเจกต์ในตอนนี้ เรียงตาม "ได้ผลเร็วสุดก่อน":

1. **อ่าน error ให้จบทั้งก้อน** — ข้อความ error ของ Go และ gcc มีข้อมูลครบกว่าที่เราคิด มันบอกไฟล์ บรรทัด และบางครั้งบอกวิธีแก้ ลองอ่านออกเสียงในใจช้า ๆ หนึ่งรอบก่อนจะเลื่อนผ่าน
2. **หา "บรรทัดแรกที่เริ่มพัง"** — ถ้า error โผล่ 10 บรรทัด ให้ดูบรรทัดแรกเท่านั้น บรรทัดที่เหลือมักเป็นผลลูกโซ่จากบรรทัดแรก
3. **แบ่งปัญหาให้เล็กลงครึ่งหนึ่ง** — คอมเมนต์โค้ดครึ่งล่างออก รัน ถ้ายังพัง ปัญหาอยู่ครึ่งบน ถ้าหาย ปัญหาอยู่ครึ่งล่าง ทำซ้ำ (เทคนิคเดียวกับที่เราใช้หาค่าในตอน 30)
4. **กลับไปอ่านตอนที่เกี่ยวข้อง** — ถ้า error พูดถึง fd, process, หรือการรอลูกจบ → กลับไปตอน 18–19–21 · ถ้าพูดถึง pointer, `sp`, ที่อยู่ → ตอน 14–15 · ถ้าพูดถึงไวยากรณ์/ต้นไม้ → ตอน 26–27 · และดู `gen_svgs.py` / `out/` ของตอนนั้นได้เลย (ทุกโปรเจกต์ของแต่ละตอนอยู่ใต้ `course/code/ep<เลขตอน>/`) เพราะมันสาธิตเรื่องนั้นไว้ครบ
5. **เขียนเทสต์ที่ "ทำให้พัง"** — เมื่อเจอ bug ให้เขียนเทสต์ที่ fail ก่อน แล้วค่อยแก้ พอแก้เสร็จเทสต์ผ่าน = bug นั้นกลับมาไม่ได้อีก (ดูตัวอย่างจริงใน `tetris_test.go` กับ `shell/main_test.go`)
6. **พักจริง ๆ 10 นาที** — สมองที่ติดจะหาคำตอบได้เองเมื่อไม่ได้จ้องหน้าจอ นี่ไม่ใช่คำพูดเล่น แต่เป็นเพราะการแก้ปัญหาต้องใช้ความจำระยะยาวที่ถูกเปิดขึ้นเมื่อเรา "ปล่อยวาง" ไม่ใช่ตอนเพ่ง

## โจทย์ประจำตอน

### ระดับ Drill (ฝึกมือ — ตัวเล็ก ทำได้ใน 10 นาทีต่อข้อ)

1. **รันทุกอย่างพร้อมกัน** — `cd course/code/ep32 && bash run_all.sh` แล้วเปิด `out/00_env.txt` กับ `out/01_quality.txt` ดูว่ามีข้อมูลอะไรบ้าง และ **`out/` มีกี่ไฟล์** (นับให้ตรง)
2. **อธิบาย exit code ให้ได้** — รัน `printf 'exit 7\n' | ./bin/shell; echo $?` แล้วดูว่าพิมพ์อะไร ทำไมต้องเป็น 7 (และลองอธิบายว่าทำไม `go run ./shell` ให้ผลไม่เหมือน `./bin/shell`)
3. **แก้ "กับดัก `letter`" ให้เห็นกับตา** — เปิด `compiler/main_test.go` แล้วดู `TestLooksLikeStmt` · จากนั้นลองแก้ `looksLikeStmt` ให้เช็คด้วย `strings.HasPrefix(s, "let")` เฉย ๆ (ไม่มีเงื่อนไข `+ " "`) แล้วรัน `go test ./compiler` ดูว่าเทสต์ตัวไหน fail (แก้กลับด้วย)
4. **เพิ่มกรณีทดสอบให้ tetris** — เปิด `tetris/tetris_test.go` แล้วเพิ่มเคส `collides(x=6, y=19)` และ `collides(x=6, y=20)` ใน `TestCollides` ว่าควรได้ `false` และ `true` ตามลำดับ แล้วรัน `go test ./tetris` ให้ผ่าน
5. **เปลี่ยนข้อความใน kernel** — แก้ข้อความ `Hello from my kernel!` ใน `kernel/kernel.c` เป็นข้อความของตัวเอง แล้วรัน `cd kernel && ./build.sh && ./run.sh --headless 5` ดูว่าข้อความที่พิมพ์ออกมาเปลี่ยนจริงไหม (และ `.bss` ยังเป็น 8 ไบต์ไหม — ทำไม)

> **เฉลยของ drill ทั้งหมดอยู่ใน `out/08_drill_answer.txt`** — ซึ่งคือผลรันจริงของ `go test -v ./shell ./compiler ./tetris` (17 เทสต์ PASS) เพราะเราเขียนโจทย์ให้ตรวจได้ด้วยการรัน ไม่ใช่ด้วยการเชื่อ

### Mini-project (= ทำ M0 ให้ผ่าน แล้วดันขึ้น git)

เลือก **หนึ่ง** โปรเจกต์ แล้วทำสามอย่างนี้ให้ครบ:

1. **ทำให้ M0 ผ่านบนเครื่องตัวเอง** — รันคำสั่งตาม `README.md` ของโฟลเดอร์นั้น แล้วเก็บผลรันของตัวเองไว้ (ใช้ `run_all.sh` หรือรันเดี่ยวก็ได้) โดยเฉพาะ **ไฟล์ `out/00_env.txt` ของตัวเอง** ให้มีวันที่กับเวอร์ชันเครื่องมือของเราเอง (จะได้เห็นว่าเวอร์ชันต่างกันได้แค่ไหน)
2. **อ่านโค้ด M0 ให้เข้าใจทุกบรรทัด** — ถ้ามีบรรทัดไหนที่ยังไม่เข้าใจ ให้กลับไปอ่านตอนที่เกี่ยวข้อง (ตารางในหัวข้อ 5.3 ช่วยบอกว่าตอนไหน) แล้ว **เขียนคอมเมนต์อธิบายบรรทัดนั้นด้วยคำของตัวเอง** ลงไปในโค้ด (คอมเมนต์ภาษาไทยได้เลย) — นี่คือการพิสูจน์ว่าเข้าใจจริง
3. **ดันขึ้น git** — สร้างกิ่งของตัวเอง, commit อย่างน้อย 2 ครั้ง (ครั้งแรก: M0 ที่รันผ่าน + `out/` · ครั้งที่สอง: คอมเมนต์อธิบายที่เราเพิ่ม) แล้ว push

**โบนัส (ถ้าอยากไปต่อทันที):** เลือก **M1 ของโปรเจกต์ที่เลือก** จากตารางในหัวข้อ 4.5 ทำครึ่งทางก่อน (ไม่ต้องจบ) แล้ว commit ไว้ในสภาพที่ "ยังรัน M0 ได้อยู่" — เพราะการทิ้งงานไว้ในสภาพที่ย้อนกลับได้ คือทักษะที่ทำให้เรากล้าลองของใหม่

- ข้อเท็จจริงเชิงแนวคิดในบทนี้ (capstone project, REPL, builtin ของ shell, `exec`/`fork`/`wait`, stdin/stdout/stderr และ fd, raw terminal mode, bare-metal boot, linker script, PL011 UART, `memcpy`/`memset` บน bare metal, AT&T-free AArch64 assembly) เป็นความรู้ตั้งหลักมาตรฐาน · ภาพ SVG ทั้งสองภาพในตอนนี้สร้างจากสคริปต์ `gen_svgs.py` ที่ดึงตัวเลขจาก `out/` โดยตรง และผ่านประตูตรวจ `check_svg_readability.py` (วัดความกว้างข้อความจริงกับขอบ viewBox) รวมทั้งตรวจด้วยตาจากการ render จริง
- เทคโนโลยีและซอฟต์แวร์พัฒนาต่อเนื่องเสมอ — เนื้อหาในที่นี้สะท้อนสถานะ ณ เวลาที่เขียน หากเวอร์ชัน Go, gcc, QEMU หรือรายละเอียดภายในของฮาร์ดแวร์/ระบบเปลี่ยนไปในอนาคต ควรตรวจสอบกับเอกสารปัจจุบันอีกครั้ง เช่น [The Go Programming Language Specification](https://go.dev/ref/spec), [os/exec — Go standard library](https://pkg.go.dev/os/exec), [QEMU: Arm System emulator (virt)](https://www.qemu.org/docs/master/system/target-arm.html) และ [ARM Architecture Reference Manual (AArch64)](https://developer.arm.com/documentation/ddi0487/latest/)
