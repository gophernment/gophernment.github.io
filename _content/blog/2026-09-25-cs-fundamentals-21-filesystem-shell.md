# file system + สร้าง shell จิ๋ว — ไฟล์ไม่ได้เก็บชื่อของตัวเอง (ตอนที่ 21) — CS Fundamentals: จาก 0 สู่พื้นฐานที่แท้จริง

ตอนที่ 19 เราจบด้วยคำที่โผล่มาแล้วแต่ยังไม่ได้แกะ: **fd** (file descriptor = หมายเลขตั๋วที่เคอร์เนลแจกให้โปรเซสใช้แทนไฟล์ที่เปิดอยู่) ตอนนั้นเราเห็นว่า `open()` คืนเลข 3 ส่วนตอนที่ 20 เราเห็นว่าหน่วยความจำถูกตัดเป็นหน้า (page) ขนาด 16384 ไบต์ บนเครื่องที่เราใช้

บทนี้จะตอบสองคำถามที่ค้างอยู่ และมันเชื่อมกันเป็นเรื่องเดียว:

> **1) บนดิสก์ ไฟล์ถูกเก็บยังไงกันแน่ — name, ข้อมูล, metadata อยู่ตรงไหน?**
> **2) ทำไมเราพิมพ์แค่ `ls` ก็ได้ — ทั้งที่โปรแกรมจริงอยู่ที่ `/usr/bin/ls`? แล้ว shell ที่รับคำสั่งเรามันทำอะไรบ้าง?**

คำตอบข้อ 2 จะพาเราสร้าง **shell จิ๋ว** ขึ้นมาจริง ๆ 213 บรรทัด (นับจากไฟล์ `06_shell.c` จริง) — และในกระบวนการนั้นเราจะพิสูจน์ด้วยตาตัวเองว่า file system ทำงานแบบที่เราอธิบาย และ `fork`/`execvp`/`waitpid` (ที่เรียนในตอนที่ 18) ทำงานจริงยังไง

ทุกตัวเลขในบทนี้มาจากการรันจริงบนเครื่องเรา (Raspberry Pi 5 · Linux 6.18.39+rpt-rpi-2712 aarch64 · GCC 14.2.0 · glibc 2.41 · strace 6.13 · man-pages 6.9.1) — โค้ดทั้งหมดอยู่ที่ `course/code/ep21/` และผลรันดิบอยู่ที่ `course/code/ep21/out/` (รันซ้ำได้เองด้วย `bash run_all.sh`)

> **คำศัพท์พื้นฐานของบทนี้** (อธิบายครั้งเดียวตรงนี้แล้วใช้ต่อทั้งบท — บทความนี้ไม่มี footnote เพราะ dev.to ไม่รองรับ):
> - **file system (ระบบไฟล์)** = ชุดกติกา+โครงสร้างที่ระบบปฏิบัติการใช้จัดเก็บไฟล์บนอุปกรณ์เก็บข้อมูล · เครื่องเราที่ `/home` ใช้ **ext4** บนพาร์ติชัน `/dev/nvme0n1p2` (**พาร์ติชัน** = ส่วนแบ่งของดิสก์ 1 ลูกที่แยกออกมาใช้เป็นหน่วย · **`/dev/nvme0n1p2`** = ชื่ออุปกรณ์ที่ระบบใช้เรียกพาร์ติชันนั้น ไม่ใช่ชื่อไฟล์)
> - **block (บล็อก)** = หน่วยการจองพื้นที่บนดิสก์ · ext4 บนเครื่องนี้ = **4096 ไบต์/บล็อก**
> - **inode (ไอโหนด)** = "บัตรประชาชนของไฟล์" เก็บ metadata ทุกอย่าง (ขนาด · สิทธิ์ · เจ้าของ · เวลา · nlink · ตำแหน่งบล็อก) **แต่ไม่เก็บชื่อไฟล์**
> - **metadata** = ข้อมูล "เกี่ยวกับ" ข้อมูล ไม่ใช่เนื้อไฟล์
> - **directory (ไดเรกทอรี/โฟลเดอร์)** = ไฟล์ชนิดพิเศษที่เก็บตาราง **ชื่อ → เลข inode**
> - **path (เส้นทาง)** = สตริงที่บอกว่าจะเดินเข้าไปถึงไฟล์ไหน เช่น `/home/pallat/x.md` · เดินจากราก `/` ทีละท่อน
> - **root (`/`)** = โฟลเดอร์บนสุดของระบบ · เปิดด้วย `ls /` ได้เหมือนโฟลเดอร์อื่น
> - **cwd** (current working directory) = โฟลเดอร์ที่โปรเซสกำลัง "ยืนอยู่" · path ที่ไม่ขึ้นต้นด้วย `/` จะถูกตีความเป็น "เทียบกับ cwd"
> - **hard link (ชื่อที่สอง)** = ชื่ออีกชื่อที่ชี้ inode เดียวกัน · **nlink** = จำนวนชื่อที่ชี้ inode นี้
> - **fd** (file descriptor) = เลขช่องในตารางของ **โปรเซส** ที่ชี้ไปยังไฟล์/ช่องที่เปิดอยู่ · 0=stdin 1=stdout 2=stderr
> - **open file description ("ตัวเปิดไฟล์")** = ก้อนสถานะของการเปิดหนึ่งครั้ง เก็บ **offset** (ตำแหน่งอ่าน/เขียนล่าสุด) · fd หลายตัวชี้ตัวเดียวกันได้ (เกิดจาก `dup`)
> - **offset** = ตำแหน่งถัดไปที่จะอ่าน/เขียน · **ไม่เก็บใน inode** แต่เก็บในตัวเปิดไฟล์
> - **syscall ที่ใช้บ่อย**: `open()`/`openat()` เปิดไฟล์ · `read()` · `write()` · `close()` · `lseek()` เลื่อน offset · `stat()`/`lstat()` อ่าน inode · `unlink()` ลบชื่อ · `link()` สร้างชื่อที่สอง · `rename()` เปลี่ยนชื่อ · `mkdir()`/`rmdir()` · `chdir()` เปลี่ยน cwd · `readdir()` อ่านตารางชื่อของไดเรกทอรี
> - **PATH** (ตัวพิมพ์ใหญ่ทั้งหมด) = ตัวแปร environment ที่เก็บ **รายการโฟลเดอร์** คั่นด้วย `:` ไว้ให้ค้นหาคำสั่ง · ตัวอย่างบนเครื่องนี้: `/usr/local/bin:/usr/bin:/bin`
> - **libc** = ไลบรารีมาตรฐานของภาษา C (`glibc` บนเครื่องนี้) ที่ห่อ syscall ไว้ให้ใช้ง่าย · **glibc** = implementation ของ libc ที่ Linux ส่วนใหญ่ใช้
> - **fork()** = syscall สร้างโปรเซสลูก (สำเนาโปรเซสพ่อ) · **execvp()** = แทนที่โปรแกรมปัจจุบันด้วยโปรแกรมใหม่ + ค้น PATH ให้ · **waitpid()** = รอลูกจบแล้วอ่านสถานะ
> - **built-in** = คำสั่งที่ shell ทำเองในโปรเซสของตัวเอง (ไม่ได้ fork ไปรันโปรแกรมอื่น)
> - **buffer** = พื้นที่พักข้อมูลในหน่วยความจำก่อนเขียนออกจริง · `fflush()` = สั่งให้เขียน buffer ออกเดี๋ยวนี้
> - **tmpfs** = ระบบไฟล์ที่อยู่บนแรม (เครื่องนี้ `/tmp` เป็น tmpfs) · **ext4** = ระบบไฟล์บนดิสก์

> **แผนที่ไฟล์ของบทนี้** (ทั้งหมดใน `course/code/ep21/`): `01_inode_stat.c` = inode คืออะไร/ชื่อไม่ใช่ไฟล์ · `02_dir_map.c` = ไดเรกทอรีคือตารางชื่อ→inode · `03_fd_table.c` = ตาราง fd, `dup`, `dup2` (นี่คือกลไกของ `>`) · `04_path_walk.c` = เดิน path ทีละท่อน + ค้น PATH · `05_exec_probe.c` = `execve` กับ `execvp` ต่างกันตรงไหน · `06_shell.c` = shell จิ๋ว · `run_shell_session.py` = ตัวขับ shell ผ่าน pty (คู่ปลายทางปลอมที่ทำให้โปรแกรมคิดว่ากำลังคุยกับ terminal จริง) เพื่อเก็บ transcript · `gen_svgs.py` = วาดภาพทั้ง 4 · `run_all.sh` = คอมไพล์+รันทุกอย่างแล้วเก็บผลลง `out/` — **ทุกบล็อกโค้ดที่เห็นด้านล่างคือตัดมาเฉพาะแกน ไฟล์เต็มอยู่ที่ `course/code/ep21/`**

## 1. แนวคิด: ไฟล์หนึ่งไฟล์ = 3 ส่วนที่แยกกันอยู่ (ภาพที่ 1)

![ไฟล์ = ชื่อในไดเรกทอรี + inode (metadata) + บล็อกข้อมูลบนดิสก์ พร้อมหลักฐานจาก 01_inode_stat.c](/assets/diagrams/ep21-01-file-inode-dir.svg)

ภาพที่ 1 คือคำตอบสั้นสุดของครึ่งแรกของบทนี้: **ชื่อไฟล์ไม่ได้อยู่ในไฟล์** ชื่ออยู่ในไดเรกทอรี ส่วนข้อมูลจริงอยู่ในบล็อกบนดิสก์ และมี inode เป็นตัวกลางที่ทั้งสองฝ่ายชี้มาหา

ก่อนไปโค้ด ขอตั้งภาพให้ตรงกัน 4 ข้อ:

**ข้อ 1 — inode คือ "บัตรประชาชน" ไม่ใช่ "ตัวไฟล์"** เปิดไฟล์ขึ้นมาด้วย `stat()` จะได้ข้อมูลทุกอย่างที่ไม่ใช่เนื้อหา: ชนิด (ไฟล์/โฟลเดอร์/**symlink** = ชื่อที่ชี้ไปไฟล์หรือโฟลเดอร์อื่น), สิทธิ์, เจ้าของ, ขนาด, จำนวนชื่อที่ชี้มาที่มัน (nlink), เวลาทั้งสาม (**atime** = อ่านล่าสุด · **mtime** = เนื้อหาเปลี่ยนล่าสุด · **ctime** = metadata เปลี่ยนล่าสุด) และรายการบล็อกที่เก็บข้อมูลจริง — ทั้งหมดนี้คือ metadata **ชื่อไฟล์ไม่อยู่ในรายการนี้**

**ข้อ 2 — ไดเรกทอรีเป็นไฟล์ชนิดพิเศษที่เก็บ "ตารางชื่อ → inode"** เปิดอ่านด้วย `open()` ได้ (ได้ fd จริง) แต่ `read()` เป็นไบต์ไม่ได้ — เคอร์เนลตอบ `EISDIR` (errno 21) เพราะข้างในไม่ใช่ลำไบต์ แต่เป็นหน่วย "รายการ" ที่ต้องอ่านผ่าน `readdir()` (จริง ๆ แล้วข้างล่างคือ syscall `getdents`) · ขนาดของไดเรกทอรีจึงเป็นขนาด **ตาราง** ไม่ใช่ผลรวมไฟล์ข้างใน (**ext4 = 4096 ไบต์ทุกโฟลเดอร์** เพราะขนาดตารางถูกปัดเป็นบล็อก · **tmpfs ไม่คงที่** — เครื่องนี้ `/tmp` = 500 ไบต์ เพราะเก็บเป็นโครงสร้างในแรม)

**ข้อ 3 — path คือการเดินทีละก้าว และทุกก้าวต้องมีสิทธิ์ `x`** เปิด `/home/pallat/devto-drafts/course/ep-20-...md` จริง ๆ แล้วเคอร์เนลทำแบบนี้:

- เปิด `/` → ค้นชื่อ `home` ในตาราง → ได้ inode → เปิดโฟลเดอร์นั้น → ค้น `pallat` → … ไปเรื่อย ๆ จนถึงไฟล์สุดท้าย (ทุกท่อนต้องเป็นชื่อที่มีอยู่จริงในตารางของโฟลเดอร์ก่อนหน้า)
- ท่อนกลางหายไป → ได้ **`ENOENT`** (errno 2 = ไม่มีชื่อนี้) ทันที แม้ไฟล์ปลายทางจะอยู่ครบ
- ท่อนกลางมีอยู่ แต่ไม่มีสิทธิ์เข้า (ขาดเครื่องหมาย `x`) → ได้ **`EACCES`** (errno 13 = ไม่มีสิทธิ์ผ่าน) ทั้งที่ชื่อโฟลเดอร์โผล่อยู่ใน `ls` เฉย ๆ

นี่คือเหตุผลว่าทำไม `chmod` โฟลเดอร์กลางให้หาย `x` แล้วทุกอย่างข้างในเข้าถึงไม่ได้พร้อมกัน (กับดักคลาสสิกเวลาซ่อมสิทธิ์โฟลเดอร์บ้าน)

**ข้อ 4 — fd ยังเป็นแค่ "เลขช่อง" เหมือนตอนที่ 19** สิ่งที่บทนี้เพิ่มเข้ามาคือคำตอบว่าเลขช่องนั้นชี้ไปที่อะไร: ชี้ไปที่ *ตัวเปิดไฟล์* (มี offset ของตัวเอง) ซึ่งชี้ต่อไปที่ inode อีกที — สามชั้นนี้แยกจากกัน และการแยกนี้เองที่ทำให้ `dup` (ก๊อปช่อง) ต่างจาก `open` ซ้ำ (เปิดใหม่)

**และทำไมต้องแยกกันขนาดนี้?** เพราะประโยชน์ที่ได้มาคุ้มมาก:

- **มีหลายชื่อได้** — ไฟล์เดียวมีชื่อสองชื่อ (`link()` / ตอนที่พิมพ์ `ln` ใน terminal) โดยไม่ต้องคัดลอกข้อมูล
- **เปลี่ยนชื่อถูกมาก** — `rename()` แค่แก้ตารางในไดเรกทอรี inode ไม่ขยับ ข้อมูลไม่ย้าย
- **ลบชื่อสุดท้ายค่อยคืนของ** — `unlink()` แค่ตัดชื่อออก เมื่อ nlink = 0 (และไม่มีใครเปิด fd ค้างอยู่) เคอร์เนลจึงคืน inode + บล็อกกลับเป็นพื้นที่ว่าง
- **สิทธิ์ผูกกับตัวไฟล์ ไม่ใช่กับชื่อ** — เปลี่ยนชื่อไม่ทำให้สิทธิ์เปลี่ยน
- **แยก "ชื่อ" ออกจาก "ตำแหน่ง" ได้** — ชื่อยาวได้ถึง `NAME_MAX` = 255 ไบต์ต่อท่อน (ตรวจได้ด้วย `getconf NAME_MAX /home`) โดยไม่ต้องไปขยายโครงสร้าง inode

## 2. ลงมือทำ (1): `01_inode_stat.c` — จับ inode มาดูด้วยตา

โปรแกรมนี้ทำ 5 การทดลองในโฟลเดอร์ชั่วคราวที่มันสร้างเอง (และลบทิ้งตอนจบ) โดยแต่ละข้อจงใจโชว์ "สิ่งที่มือใหม่มักเข้าใจผิด":

```c
/* 01_inode_stat.c (ตัดมาเฉพาะแกน) — build: gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -g -o 01_inode_stat 01_inode_stat.c */
static int show(const char *what, const char *path)
{
	struct stat sb;

	if (lstat(path, &sb) != 0) {           /* lstat = ไม่ตาม symlink */
		fprintf(stderr, "  lstat(\"%s\") ล้มเหลว: %s\n", path, strerror(errno));
		return -1;
	}
	printf("  %-14s inode=%-9llu ขนาด=%-7lld ไบต์  พื้นที่บนดิสก์=%lld ไบต์  nlink=%lu  สิทธิ์=%04o  %s\n",
	       what,
	       (unsigned long long)sb.st_ino,
	       (long long)sb.st_size,
	       (long long)sb.st_blocks * 512,   /* st_blocks นับเป็นหน่วย 512 ไบต์ */
	       (unsigned long)sb.st_nlink,
	       (unsigned)(sb.st_mode & 07777),
	       kind_of(sb.st_mode));
	return 0;
}
```

การทดลองที่ 1 เปิดไฟล์ว่าง เขียนข้อความ 28 ไบต์ แล้ว `stat()` ทั้งก่อนและหลัง · ที่ 2 ใช้ `link()` สร้างชื่อที่สอง · ที่ 3 ใช้ `rename()` เปลี่ยนชื่อ · ที่ 4 สร้างไฟล์ 1 ไบต์เพื่อดู `st_size` กับ `st_blocks` · ที่ 5 `unlink()` ชื่อสุดท้าย

อ่านผลรันให้ครบ 5 บทเรียน:

1. **ขนาดเปลี่ยนได้ แต่ identity ไม่เปลี่ยน** — บรรทัดที่ 1 กับ 2 เป็น inode 801 ทั้งคู่ ทั้งที่ขนาด 0 → 28 ไบต์ · การเขียนข้อมูลไม่ทำให้ "ไฟล์" กลายเป็นคนละไฟล์
2. **สองชื่อ inode เดียวกัน** — `link()` ไม่ได้ก๊อปข้อมูลเลย มันแค่เพิ่มบรรทัดในตารางของไดเรกทอรีว่า "`alias.txt` → 801" · สังเกตว่า nlink กลายเป็น 2 พร้อมกัน**ทั้งสองชื่อ** (เพราะเป็นตัวเลขตัวเดียวกันในบัตรประชาชนใบเดียว)
3. **`rename()` ไม่ย้ายข้อมูล** — inode ยัง 801 และ nlink ยัง 2 · **ข้ามระบบไฟล์ `rename()` ล้มเหลวด้วย `EXDEV` (errno 18) ไม่ก๊อปให้** — ที่ `mv` ข้ามไดรฟ์ช้าคือ **coreutils** เห็น EXDEV แล้วก๊อป+ลบเอง
4. **ขนาด ≠ พื้นที่ที่ใช้จริง** — ไฟล์ 1 ไบต์ใช้พื้นที่ **16384 ไบต์** บน tmpfs (`/tmp` ของเครื่องนี้อยู่บนแรม) เพราะ tmpfs จ่ายหน่วยเป็น **หน้า = 16384 ไบต์** เท่ากับ page ในตอนที่ 20 พอดี ส่วน ext4 บนดิสก์จ่ายเป็นบล็อก 4096 ไบต์ · ข้อเท็จจริงที่วัดคู่กันมาดูให้เห็นชัด:

```
## ไฟล์ 1 ไบต์: tmpfs vs ext4 (ขนาดเท่ากัน แต่พื้นที่ที่จองไม่เท่ากัน)
  tmpfs ($TMPDIR): size=1 ไบต์ blocks=32 (=16384 ไบต์) io_blksize=16384
  ext4  ($HOME):  size=1 ไบต์ blocks=8 (=4096 ไบต์) io_blksize=4096
```

5. **ลบชื่อสุดท้าย = หมดชื่อ ไม่ใช่ "หายไปทันที"** — `unlink()` ตัดชื่อออก ถ้า nlink เหลือ 0 และไม่มี fd เปิดค้าง ข้อมูลจึงถูกคืน แต่ถ้ามีโปรเซสเปิด fd อยู่ ไฟล์จะยังมีชีวิต (นี่คือเหตุผลที่ลบไฟล์ที่โปรแกรมกำลังเขียนอยู่ได้ และเหตุผลที่ `/proc` ทำงานได้)

> **ข้อควรระวังเวลาอ่านตัวเลขในบทนี้**: ตัวเลขหลายตัว **เปลี่ยนทุกครั้งที่รัน** — เลข inode ของไฟล์ในโฟลเดอร์สาธิต (`01_inode_stat`: 801, 802 · `03_fd_table`: 804) · pid ที่โผล่ใน `/proc/<pid>/fd` (30767) · ชื่อโฟลเดอร์สาธิต (`/tmp/ep21_inode.XXXXXX`, `/tmp/ep21_fd.XXXXXX`) ที่ถูกสุ่มใหม่ทุกรอบ · pid/pointer ใน strace (หัวข้อ 5.3 และ 5.4) ก็เหมือนกัน ส่วนเลข inode ของไฟล์ในโปรเจกต์ (`01_inode_stat.c` = 4468251, `06_shell.c` = 4468259) คงที่เพราะไฟล์ถูกสร้างครั้งเดียว — สิ่งที่ต้องจำไม่ใช่ตัวเลข แต่เป็น *ความสัมพันธ์*: สองชื่อ → เลขเดียวกัน

## 3. ลงมือทำ (2): `02_dir_map.c` — พิสูจน์ว่าไดเรกทอรีคือตารางชื่อ→inode

โปรแกรมที่สองกวาดอ่านไดเรกทอรีด้วย `readdir()` แล้ว**ตรวจสอบกับ** `lstat()` ของทุกชื่อ: ถ้าไดเรกทอรีเป็นตารางจริง ตัวเลข `d_ino` ที่อ่านจากตารางต้องตรงกับ `st_ino` ที่ได้จาก `lstat` ของชื่อนั้น

```c
/* 02_dir_map.c (ตัดมาเฉพาะแกน) */
	while ((de = readdir(d)) != NULL) {
		total++;
		if (shown >= max_show) continue;
		shown++;
		if (snprintf(path, sizeof path, "%s/%s", dir, de->d_name) >= (int)sizeof path)
			continue;
		struct stat es;
		if (lstat(path, &es) != 0) continue;
		worst_checked++;
		/* หัวใจ: d_ino ที่อ่านจากไดเรกทอรี ต้องตรงกับ inode ที่ lstat บอก */
		const char *mark = (es.st_ino == de->d_ino) ? "ตรง" : "ไม่ตรง!";
		if (es.st_ino != de->d_ino) mismatch++;
		printf("  %-28s d_ino=%-9llu lstat.st_ino=%-9llu %s  %s\n", ...);
	}
```

สามเรื่องที่ได้จากผลรันนี้:

- **ตรวจ 6 รายการ ไม่ตรงกัน 0 รายการ** — ตารางชื่อ→inode เป็นเรื่องจริง ไม่ใช่การเปรียบเทียบเล่น ๆ · `d_ino` กับ `st_ino` คือเลขเดียวกัน
- **`"."` กับ `".."` ดูเหมือนเป็นสิ่งพิเศษ แต่ที่จริงก็แค่ชื่อสองชื่อในตาราง** — `.` คือ "โฟลเดอร์นี้เอง" (inode 4468249 — ตรงกับ inode ของโฟลเดอร์เองด้านบน) และ `..` คือ "โฟลเดอร์แม่" นี่คือเหตุผลที่โฟลเดอร์มี nlink = 2 + จำนวนโฟลเดอร์ลูก **(เฉพาะระบบไฟล์อย่าง ext4/tmpfs — btrfs ตั้ง nlink ของไดเรกทอรีเป็น 1 เสมอ สูตรนี้จึงใช้ไม่ได้)**: ลูกแต่ละตัวมี `..` ที่ชี้กลับมาหาพ่อ = เพิ่มชื่อให้พ่อ

> **หมายเหตุ**: ลำดับรายการจาก `readdir()` **ไม่รับประกัน** — ในโฟลเดอร์ใหญ่ ระบบไฟล์จัดของเป็นตาราง hash ลำดับที่ได้จึงไม่เรียงตามตัวอักษรและไม่คงที่ อย่าเขียนโค้ดที่พึ่งลำดับ (บทเรียนนี้จะโผล่อีกครั้งใน ep เรื่อง sorting)

## 4. ลงมือทำ (3): `03_fd_table.c` — ช่อง fd, offset, และความลับของ `>` ("เขียนผลลัพธ์ลงไฟล์แทนจอ") (ภาพที่ 2)

![ตาราง fd ของโปรเซส → ตัวเปิดไฟล์ (offset) → inode ดิสก์ พร้อมกลไกของ ">" ("เขียนผลลัพธ์ลงไฟล์แทนจอ") ที่ใช้ dup2](/assets/diagrams/ep21-02-fd-table.svg)

ภาพที่ 2 คือหัวใจของหัวข้อนี้: มีสามชั้นไม่ใช่สอง — **ตาราง fd (ต่อโปรเซส) → ตัวเปิดไฟล์ (มี offset) → inode (metadata, ไม่มี offset)** · ทุกอย่างที่คนงงเรื่อง `read`/`write`/`dup` อธิบายได้จากโครงนี้

โปรแกรมนี้ทำ 5 ข้อ โดยเริ่มจากถามเคอร์เนลตรง ๆ ว่าตอนนี้ตาราง fd ของโปรเซสเราหน้าตาเป็นยังไง (อ่านจาก `/proc/self/fd` ซึ่งเป็นโฟลเดอร์ที่แต่ละ fd ปรากฏเป็น symlink ชี้เป้าจริง):

```

===== 1) ตาราง fd ของโปรเซสนี้ตอนเริ่มรัน =====
  เคอร์เนลบอกว่า fd แต่ละเลขชี้ไปที่อะไร (อ่านจาก /proc/self/fd):
  fd 0   -> /dev/null
  fd 1   -> /home/pallat/devto-drafts/course/code/ep21/out/03_fd_table.out.txt

  fd 3   -> /proc/30767/fd
  (ทั้งหมด 4 ช่อง — ตัว readdir เองก็เปิด fd อยู่ จึงเห็นตัวเองโผล่มาเป็นเลขสูงสุด)
```

**อ่านให้ดี**: บรรทัด `fd 1 -> .../out/03_fd_table.out.txt` ไม่ได้แปลว่าโปรแกรมนี้ "เขียนลงไฟล์" อะไรเป็นพิเศษ — มันแค่ถูกสั่งให้ stdout ของโปรเซสนี้เป็นไฟล์ (ด้วย `>` ของ shell = "เขียนผลลัพธ์ลงไฟล์แทนจอ") และ **fd 1 คือช่องเลข 1 ในตาราง ไม่ใช่ "จอ"** · ตรงนี้เองคือความเข้าใจผิดที่หายไปทันทีเมื่อเราดู `/proc/self/fd` · และบรรทัด `fd 3 -> /proc/30767/fd` ก็เป็นหลักฐานว่า *`readdir` เองก็ต้องเปิด fd* — มันจึงเห็นตัวเองในรายการ

จากนั้นโปรแกรมทดลอง `open` ซ้ำ, `dup`, `dup2` และ `close`:

```
===== 2) เปิดไฟล์เดียวกันสองครั้ง =====
  fd1 = 3  inode = 804  offset = 0
  fd2 = 4  inode = 804  offset = 0
  -> fd ต่างกัน แต่ inode เดียวกัน = "เลข 3 กับ 4" ไม่ใช่ไฟล์ แต่เป็นช่องในตารางของโปรเซส

  เขียน "ABCDEFGH" ผ่าน fd1 -> offset(fd1) = 8

===== 4) dup2() เปลี่ยนปลายทางของ fd 1 = "ข้อความ > ไฟล์" ทำงานยังไง =====
  อ่านไฟล์กลับมาได้: [บรรทัดนี้ถูก printf ธรรมดา แต่ไม่ได้ออกจอ — มันไปอยู่ท้ายไฟล์ /tmp/ep21_fd.NqE8k4/redirect.txt]
  -> shell ไม่ได้ "บอกให้ printf เขียนที่อื่น" แต่สลับช่อง fd 1 ในตารางชั่วคราว

===== 5) ปิด fd แล้วเปิดใหม่ = ใช้เลขเดิม =====
  ปิด fd 4 แล้วเปิดไฟล์ใหม่ -> ได้ fd = 4 (เลขว่างต่ำสุดถูกใช้ก่อน)
```

สามบทเรียน:

1. **`open` สองครั้ง = ตัวเปิดไฟล์สองตัว (offset แยกกัน)** ทั้งที่ inode เดียวกัน — สองโปรแกรม/สอง fd อ่านไฟล์เดียวกันโดยไม่รบกวนตำแหน่งของกัน ถ้าอยากได้คนละ offset ก็ `open` ใหม่
2. **`dup` = ก๊อปช่อง ไม่ใช่ก๊อปไฟล์** — อ่านผ่าน fd 5 แล้ว offset ของ fd 3 ขยับตาม (เขียนเสร็จ = 8 → `lseek` กลับต้นไฟล์ = 0 → อ่าน 4 ไบต์ = 4 เพราะเป็น offset ก้อนเดียวกัน) นี่คือ "ตัวเปิดไฟล์เดียวกัน" ตามภาพที่ 2 · ใน shell จริง กลไกนี้สำคัญมาก: เมื่อ child ถูก fork ตัว child ได้สำเนาตาราง fd มา และ offset ของ pipe/ไฟล์ที่แชร์กันจะเดินต่อเนื่องกัน
3. **`dup2(fd, 1)` คือหัวใจของ `>`** — และมี "กับดักจริง" ที่เจอในโค้ดตัวเองระหว่างเขียนบทนี้: **ต้อง `fflush(stdout)` ก่อนสลับ fd 1** เพราะข้อความก่อนหน้าทั้งหมดที่ยังค้างใน buffer ของ stdout จะถูกเขียนลงไฟล์ใหม่ด้วยตอนที่ buffer ถูกฟลัช (รอบแรกที่รัน ข้อความหัวโปรแกรมทั้งหมดไหลลง `redirect.txt` ไปเลย) · นี่คือภาพจำที่ใช้ตอบคำถาม "ทำไม output หาย/ไปโผล่ผิดที่" ได้ตลอดชีวิต

```c
/* 03_fd_table.c (ตัดมาเฉพาะแกนของข้อ 4) */
	saved = dup(STDOUT_FILENO);                  /* 1) เก็บช่องเดิมไว้คืน */
	fout_fd = open(fout, O_WRONLY | O_CREAT | O_TRUNC, 0644);
	fflush(stdout);                              /* 2) กับดัก: ล้าง buffer ก่อนสลับ! */
	dup2(fout_fd, STDOUT_FILENO);                /* 3) ช่อง 1 -> ไฟล์ */
	close(fout_fd);                              /* 4) ปิดตัวสำรองได้ เพราะ fd 1 ชี้อยู่ */
	printf("[บรรทัดนี้ถูก printf ธรรมดา แต่ไม่ได้ออกจอ]\n");
	fflush(stdout);
	dup2(saved, STDOUT_FILENO);                  /* 5) คืนช่อง 1 ให้ชี้จอ */
	close(saved);
```

รู้แล้วว่า `>` ทำงานยังไง — ต่อไปมาดูว่าตอนเราพิมพ์ `ls` เฉย ๆ shell หาโปรแกรมเจอได้ยังไง

### 5.1 เดิน `path` ทีละท่อน — และเลข inode ที่ได้ในแต่ละก้าว

```c
/* 04_path_walk.c (ตัดมาเฉพาะแกน) — เดินทีละ "/" แล้ว lstat ทุกท่อนกลาง */
	char comp[PATH_MAX];        /* comp = บัฟเฟอร์พักชื่อท่อนที่กำลังประกอบ */
	size_t cn = 0;              /* cn = ความยาวปัจจุบันของท่อนนั้น (component length) */
	for (size_t i = 0; path[i] != '\0'; i++) {
		if (path[i] == '/' && cn > 1 && comp[cn - 1] == '/') continue;  /* ยุบ // ซ้อน */
		comp[cn++] = path[i];
		if (path[i] == '/') {          /* ถึงขอบเขตท่อน -> ตัด comp แล้ว lstat ท่อนนั้น */
			comp[cn - 1] = '\0';
			struct stat sb;
			if (lstat(comp, &sb) == 0)
				printf("  ท่อนที่ %d: %-46s inode=%-10llu %s\n", step++, comp,
				       (unsigned long long)sb.st_ino, kind_of(sb.st_mode));
			comp[cn - 1] = '/';
		}
	}
```

### 5.3 `execve` vs `execv` vs `execvp` — และ strace ที่หักล้างความเชื่อของผม

คำถามธรรมชาติคือ: `exec` มันรู้จัก PATH ได้ยังไง? ลองด้วย `05_exec_probe.c` ที่ fork ลูกสามตัวแล้วลองคนละแบบ:

```
== 1) execve("ls") — ส่งชื่อล้วน ไม่มี /
  [ลูก execve("ls")] exec ล้มเหลว: errno=2 (No such file or directory)
  ลูก execve("ls")           -> จบปกติ (exit code = 127)
  -> 127 + ENOENT ทั้งที่คำสั่ง ls มีอยู่จริงบนเครื่อง · เพราะ execve ไม่รู้จัก PATH เลย

== 2) execv("/bin/ls") — ส่ง path เต็ม
/etc/hostname
  ลูก execv("/bin/ls")       -> จบปกติ (exit code = 0)
  -> สำเร็จ (ข้อความด้านบนคือ ls พิมพ์ชื่อไฟล์ออกมา) · แต่ผู้ใช้ไม่ได้พิมพ์ /bin/ls ใช่ไหม

== 3) execvp("ls") — ให้ libc ค้น PATH ให้
/etc/hostname
  ลูก execvp("ls")           -> จบปกติ (exit code = 0)
  -> สำเร็จ · execvp แยก PATH ด้วย ":" แล้วลองทุกโฟลเดอร์จนเจอไฟล์ที่รันได้
  (นับจริง: 12 โฟลเดอร์)

== 4) ถ้าคำสั่งไม่มีจริง
  [ลูก execvp(ไม่มีจริง)] exec ล้มเหลว: errno=2 (No such file or directory)
  ลูก execvp(ไม่มีจริง) -> จบปกติ (exit code = 127)
```

ขอทวนชื่อให้ครบทั้งสามก่อน: **`execve`** = ยื่น path เต็ม + ต้องส่ง environment เอง · **`execv`** = เหมือน `execve` แต่รับ argv เป็นลิสต์ (v = vector) และไม่ต้องส่ง environment (libc ใช้ตัวปัจจุบันให้) · **`execvp`** = เหมือน `execv` แต่ค้น PATH ให้ (p = PATH)

บรรทัดที่สำคัญคือข้อ 1: **`execve` ไม่ค้น PATH เลย** — มันรับ path ตรง ๆ ถ้าส่ง `"ls"` มันจะมองหาว่า *มีไฟล์ชื่อ `ls` ใน cwd* (ไม่มี) แล้วคืน ENOENT ทันที · ส่วน `execvp` (p = PATH) เป็นฟังก์ชันของ libc ที่แยก PATH แล้วลองทีละโฟลเดอร์ให้ เราจึงต้องใช้ `execvp` ใน shell ที่เรากำลังจะเขียน

จุดนี้ผมทดสอบจริงเพราะเกือบเขียนลงบทความผิด ๆ ว่า "PATH ว่าง = ใช้ `.:/bin:/usr/bin`":

```
## strace: PATH= (entry ว่าง = cwd) แล้วสั่ง ls

```

- **ไม่มีตัวแปร PATH เลย** → libc ใช้ค่า `confstr(_CS_PATH)` ซึ่งบนเครื่องนี้คือ `/bin:/usr/bin` (ดูได้จาก `getconf PATH`) จึงยังหา `ls` เจอ — และ strace โชว์ว่า execve ไปที่ `/bin/ls` ตรง ๆ (ไม่ผ่าน `/usr/bin/ls` เพราะ `/bin` มาก่อนในรายการสำรอง ไม่เหมือน PATH จริงของเรา)
- **ตั้ง PATH เป็นค่าว่าง `""`** → ต่างกันคนละเรื่อง! ไม่ได้แปลว่า "ไม่มีรายการให้ค้น" แต่หมายถึง **มี entry เดียว และ entry นั้นว่างเปล่า** ซึ่ง glibc ตีความเป็นโฟลเดอร์ปัจจุบัน (cwd) ไม่ใช่ `/bin:/usr/bin` → จึงหา `ls` ไม่เจอ → ENOENT → exit 127
- **หลักฐานจาก strace**: `execve("ls", ["ls", "/etc/hostname"], ...) = -1 ENOENT` — glibc เอา entry ว่างไปต่อกับชื่อคำสั่งเฉย ๆ ผลคือกลายเป็น path สัมพัทธ์กับ cwd (ที่นี่ไม่มีไฟล์ `ls` ใน cwd) ไม่ใช่การค้นใน `/bin:/usr/bin` เลย · ตรงกับที่ `04_path_walk.c` รายงานไว้: `entry ว่าง -> ตีความเป็นโฟลเดอร์ปัจจุบัน (cwd)`

บทเรียน: "ไม่มีค่า" กับ "มีค่าแต่ว่าง" ไม่เหมือนกัน ของแบบนี้ต้องทดสอบ ไม่ใช่คิดเอา

**shell คือโปรแกรมที่วนลูป 6 ก้าว:**

1. พิมพ์ prompt (`ep21> ` = ข้อความเชิญให้พิมพ์) แล้ว `fflush` ให้ออกจอทันที
2. อ่านคำสั่งทั้งบรรทัดด้วย `getline()` (libc จัดการ realloc = ขยายก้อนหน่วยความจำเดิม ให้เอง — ไม่ต้องเดาความยาวล่วงหน้า)
3. แยกคำ (tokenize) เป็น `argv[]` แบบที่ `exec` ต้องการ — พร้อมตรวจจำนวนคำกัน overflow
4. ถ้าเป็น **built-in** (`cd`, `exit`, `help`) → ทำในโปรเซสของ shell เองแล้ววนกลับ (ไม่ fork)
5. ถ้าเป็นคำสั่งภายนอก → `fork()` สร้างลูก · ในลูก: `execvp()` แทนที่ตัวเองด้วยโปรแกรมจริง · ในพ่อ: `waitpid()` นอนรอลูกจบ
6. อ่านสถานะของลูก → วนกลับข้อ 1

โค้ดแกน ๆ ของลูป (ไฟล์เต็มอยู่ที่ `course/code/ep21/06_shell.c`):

```c
/* 06_shell.c (ตัดมาเฉพาะแกน) — build: gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -g -o 06_shell 06_shell.c */
#define MAX_ARGS 64
#define PROMPT   "ep21> "

	for (;;) {
		fputs(PROMPT, stdout);
		if (fflush(stdout) != 0) { ... }              /* 1. prompt ออกทันที */

		ssize_t len = getline(&line, &cap, stdin);    /* 2. อ่านทั้งบรรทัด (จบด้วย Ctrl-D) */
		if (len < 0) { if (feof(stdin)) break; ... }

		char *start = line;
		while (*start == ' ' || *start == '\t') start++;
		if (*start == '\0' || *start == '#') continue;  /* บรรทัดว่าง/คอมเมนต์ */

		char *argv[MAX_ARGS + 1];
		int argc = tokenize(start, argv, MAX_ARGS + 1); /* 3. แยกคำ + กัน overflow */
		if (argc < 0) { fprintf(stderr, "คำสั่งยาวเกิน %d คำ — ไม่รัน\n", MAX_ARGS); continue; }

		int should_exit = 0, exit_code = 0;
		if (run_builtin(argc, argv, &should_exit, &exit_code) == 0) {  /* 4. built-in */
			if (should_exit) return exit_code;
			continue;
		}

		fflush(NULL);                                 /* 5. ก่อน fork ต้องล้าง buffer ทุก stream (ช่องทางไฟล์ที่ libc เปิดให้) */
		pid_t pid = fork();
		if (pid < 0) { fprintf(stderr, "fork ล้มเหลว: %s\n", strerror(errno)); continue; }

		if (pid == 0) {
			if (signal(SIGINT, SIG_DFL) == SIG_ERR) _exit(126);
			execvp(argv[0], argv);                    /* กลายเป็นโปรแกรมจริง (ค้น PATH ให้) */
			fprintf(stderr, "%s: %s\n", argv[0], strerror(errno));
			_exit(127);                               /* มาถึงนี่ = exec ล้มเหลว */
		}

		int status = 0;
		while (waitpid(pid, &status, 0) < 0) {        /* 6. นอนรอลูก */
			if (errno == EINTR) continue;
			status = -1; break;
		}
		if (status >= 0 && WIFEXITED(status)) {
			if (WEXITSTATUS(status) == 127)
				printf("[ไม่เจอคำสั่ง \"%s\" — shell ทั่วไปคืน 127]\n", argv[0]);
		}
	}
```

### 6.1 built-in ทั้งสาม และเหตุผลว่าทำไม `cd` ต้องเป็น built-in

```c
static int run_builtin(int argc, char **argv, int *should_exit, int *exit_code)
{
	if (strcmp(argv[0], "cd") == 0) {                      /* ไม่ใส่ arg = กลับบ้าน (HOME) */
		const char *target = (argc > 1) ? argv[1] : getenv("HOME");
		if (chdir(target) != 0)
			fprintf(stderr, "cd: %s: %s\n", target, strerror(errno));
		return 0;
	}
	if (strcmp(argv[0], "help") == 0) { print_help(); return 0; }
	if (strcmp(argv[0], "exit") == 0) { /* ตรวจว่าเป็นเลข 0-255 จริง แล้วตั้ง should_exit */ }
	return -1;   /* ไม่ใช่ built-in */
}
```

**ทำไม `cd` ต้องเป็น built-in**: cwd เป็นสมบัติของ **โปรเซส** · ถ้าเราเขียนคำสั่ง `cd` เป็นโปรแกรมแยกแล้ว fork ไปรัน `chdir("/tmp")` ในโปรเซสลูก ผลคือ *ลูก* เปลี่ยนโฟลเดอร์ แล้วลูกก็จบไป พ่อยังยืนที่เดิม — ลองได้เลยด้วยคำสั่งนี้ใน terminal:

```
bash -c 'cd /tmp'   # จบแล้วโฟลเดอร์ปัจจุบันของคุณไม่เปลี่ยน
```

ด้วยเหตุผลเดียวกัน `exit` ก็ต้องทำใน shell เอง และ `help` ก็ไม่มีความหมายถ้าไปรันเป็นโปรแกรมแยก · ตรงกันข้าม คำสั่ง `pwd` **ไม่ได้** ต้องเป็น built-in (โปรแกรม `/usr/bin/pwd` ก็รายงานได้) — แต่ shell ส่วนใหญ่ทำเป็น built-in เพราะเร็วและเพื่อความสม่ำเสมอ (นี่คือโจทย์ให้ลองในแบบฝึกหัด)

### 6.2 สัญญาณ + กับดักที่ต้องจัดการ

- **`signal(SIGINT, SIG_IGN)`** ในโปรเซส shell — shell ตัวจริงไม่ตายเมื่อกด Ctrl-C มันกันสัญญาณไว้ แล้วปล่อยให้สัญญาณไปที่โปรเซสลูก (foreground) · **แต่**ค่าที่ตั้งเป็น `SIG_IGN` จะติดข้าม `fork` **และข้าม `exec` ไปด้วย** (ตาม POSIX) ดังนั้นในฝั่งลูกต้อง `signal(SIGINT, SIG_DFL)` คืนค่าให้เป็นปกติก่อน `execvp` — ถ้าลืม พฤติกรรมนี้จะทำให้โปรแกรมที่รับ Ctrl-C ไม่ทำงาน และเป็นบั๊กที่หายากมากถ้าไม่รู้มาก่อน
- **`fflush(NULL)` ก่อน `fork`** — ไม่งั้นข้อความที่ค้างใน buffer ของ stdout จะถูกคัดลอกไปกับโปรเซสลูก แล้วพิมพ์ซ้ำสองครั้ง (หนึ่งครั้งจากพ่อ หนึ่งครั้งจากลูก) นี่คือคู่แฝดของกับดัก `dup2` ในหัวข้อ 4
- **`waitpid` ต้องวนเมื่อ `EINTR`** — สัญญาณใด ๆ ก็ทำให้ waitpid ถูกขัดจังหวะได้ ถ้าไม่วนจะอ่านสถานะผิดพลาด
- **ในลูกใช้ `_exit(127)` ไม่ใช่ `exit(127)`** — `_exit` ไม่ล้าง buffer/ไม่รัน `atexit` ของโปรเซสที่กำลังจะกลายเป็นโปรแกรมอื่น
- **โหมดโค้ดตกแต่งด้วย `EP21_SHELL_VERBOSE=1`** เพื่อโชว์ pid ของลูกและ exit code ทุกคำสั่ง (เป็นวิธี debug shell ที่ดีมาก)

### 6.3 transcript จริงจากการใช้งาน

ขับผ่าน pty (คู่ปลายทางปลอมที่ทำให้โปรแกรมคิดว่ากำลังคุยกับ terminal จริง) เพื่อให้ `isatty` (คำถามว่า "fd นี้เป็น terminal ไหม") เป็นจริง และ prompt/echo ทำงานเหมือนใช้งานจริง:

```
ep21> help
shell จิ๋วนี้เข้าใจ 3 อย่าง:
  cd [โฟลเดอร์]   เปลี่ยนโฟลเดอร์ทำงาน (ไม่ใส่ = กลับบ้าน)
  help            พิมพ์ข้อความนี้
  exit [สถานะ]    ออกจาก shell (ไม่ใส่สถานะ = 0)
นอกจากนี้พิมพ์อะไรก็ได้: จะหาโปรแกรมชื่อนั้นใน PATH แล้วรันให้ (เช่น ls, cat, date, uname)
หมายเหตุ: ยังไม่รองรับ | , > , < , ; , & , * , " , ' — เป็นโจทย์ในแบบฝึกหัดท้ายบท
ep21> ls /etc/hostname
/etc/hostname
ep21> pwd
/home/pallat/devto-drafts/course/code/ep21
ep21> cd /tmp
ep21> pwd
/tmp
ep21> cd
ep21> pwd
/home/pallat
ep21> roflcopter-ep21
roflcopter-ep21: No such file or directory
roflcopter-ep21: ไม่เจอโปรแกรมนี้ใน PATH
[ไม่เจอคำสั่ง "roflcopter-ep21" — shell ทั่วไปคืน 127]
ep21> uname -r
6.18.39+rpt-rpi-2712
ep21> sleep 30
^C["sleep" ถูกฆ่าด้วยสัญญาณ 2]
ep21> pwd
/home/pallat
ep21> exit 7
```

อ่านให้ครบทุกจุด:

- `pwd` ไม่ได้เป็น built-in ของ shell จิ๋วนี้ แต่ทำงานได้เพราะใน PATH มี `/usr/bin/pwd` และเรา `execvp` มัน
- `cd /tmp` แล้ว `pwd` = `/tmp` → **built-in ได้ผลจริงในโปรเซสของ shell เอง** · `cd` เฉย ๆ กลับไป `/home/pallat` ผ่านตัวแปร `HOME`
- `roflcopter-ep21` → error สองบรรทัด (ของลูกและของพ่อ) แล้วได้ 127
- `sleep 30` แล้วกด **Ctrl-C**: `^C` ปรากฏ, ลูกตายด้วยสัญญาณ 2, **shell ไม่ตาย** และพร้อมรับคำสั่งต่อ — นี่คือผลตรง ๆ ของการกัน SIGINT ใน shell + คืนค่า `SIG_DFL` ในลูก
- `exit 7` ออกด้วยสถานะ 7 จริง ๆ — ตรวจได้ด้วยการรันผ่าน pipe:

```
printf 'exit 7\n' | ./06_shell -> rc=7
roflcopter-ep21 แล้ว exit -> rc=0
```

(คำสั่งสุดท้ายได้ rc=0 เพราะ `roflcopter-ep21` ไม่ได้ทำให้ shell ตาย — สถานะ 127 เป็นของ "ลูก" ไม่ใช่ของ "shell" · shell ที่ดีควรเก็บค่าไว้ในตัวแปร `$?` เพื่อให้คำสั่งถัดไปอ่านได้ ซึ่งเป็นโจทย์ในแบบฝึกหัดเช่นกัน)

### 6.4 shell ของเรามีอะไร และยังไม่มีอะไร

**มีแล้ว**: prompt · อ่านบรรทัด · tokenize (พร้อมกัน overflow) · built-in 3 ตัว · fork/execvp/waitpid · ค้น PATH · ส่งต่อ exit code · กัน SIGINT · จัดการ error ทุกทางออก (`getline`, `fork`, `waitpid`, `chdir`, `strtol`) · ไม่มี fd leak (ปิดทุก descriptor ที่เปิด)

**ยังไม่มี** (จงใจ — เก็บไว้เป็นแบบฝึกหัด): pipe `|` · redirect `>` `<` `>>` · ตัวคั่น `;` `&&` · background `&` · เครื่องหมายคำพูด `"` `'` · wildcard `*` · history/ตัวแก้บรรทัด · job control · ตัวแปร `$?` `$HOME` ในคำสั่ง · เซมิโคลอนในคอมเมนต์

ทุกอย่างที่ยังไม่มีเหล่านี้ **ประกอบจากของที่เรียนแล้วทั้งนั้น**: pipe = `pipe()` + `dup2` + fork สองตัว, redirect = `dup2` (หัวข้อ 4), background = fork แล้วไม่ `waitpid`, wildcard = `readdir()` (หัวข้อ 3) — ทำได้จริงทั้งหมด

## 7. ตารางสรุป: syscall ที่แตะระบบไฟล์และโปรเซสในบทนี้

| งาน | syscall | คืนอะไร | หมายเหตุจากบทนี้ |
|---|---|---|---|
| เปิดไฟล์ | `open()` / `openat()` | fd (เลขช่อง) | สำเร็จแล้ว fd ยังใช้ได้แม้ไฟล์ถูกลบ |
| อ่าน/เขียน | `read()` / `write()` | จำนวนไบต์ที่ทำได้จริง | อ่านไดเรกทอรีไม่ได้ → `EISDIR` (21) |
| เลื่อนตำแหน่ง | `lseek()` | offset ใหม่ | offset อยู่ในตัวเปิดไฟล์ ไม่ใช่ inode |
| ปิด | `close()` | 0/-1 | คืนช่องในตาราง ไม่ได้ลบไฟล์ |
| ก๊อปช่อง | `dup()` / `dup2()` | fd ใหม่ / fd เป้าหมาย | `dup2` = กลไกของ `>` และ `|` |
| อ่าน metadata | `stat()` / `lstat()` / `fstat()` | struct stat | `lstat` ไม่ตาม symlink · `fstat` ใช้ fd ที่เปิดแล้ว |
| ลบ/สร้างชื่อ | `unlink()` / `link()` / `rename()` | 0/-1 | `unlink` ตัดชื่อ · ชื่อสุดท้าย → คืน inode |
| อ่านตารางไดเรกทอรี | `readdir()` (libc) → `getdents` | รายการ (`d_name`, `d_ino`) | ลำดับไม่รับประกัน |
| เปลี่ยน cwd | `chdir()` | 0/-1 | มีผลกับโปรเซสเอง จึงต้องเป็น built-in |
| สร้างโปรเซส | `fork()` → จริง ๆ คือ `clone()` | pid ลูก | ตาราง fd สืบทอดทั้งชุด |
| เปลี่ยนโปรแกรม | `execve()` / `execvp()` | (ไม่คืน ถ้าสำเร็จ) | `vp` = ค้น PATH ให้; `execve` ไม่ค้น |
| รอลูก | `waitpid()` | pid ลูก + status | อ่านด้วย `WIFEXITED`/`WEXITSTATUS` |

และตารางค่าคงที่ของเครื่องนี้ที่อ้างในบท:

| ค่า | เครื่องนี้ | หาได้จาก |
|---|---|---|
| ระบบไฟล์ของ `/home` | ext4 บน `/dev/nvme0n1p2` | `findmnt -n -o SOURCE,FSTYPE --target /home` |
| บล็อกของ ext4 | 4096 ไบต์ | `stat -f -c '%s' /home` |
| `NAME_MAX` / `PATH_MAX` | 255 / 4096 | `getconf NAME_MAX` · `getconf PATH_MAX` |
| จำนวน inode ทั้งหมดบน ext4 | 31,105,920 (ใช้ไป ~6%) | `df -i /home` |
| `/tmp` | tmpfs · bsize 16384 ไบต์ · 1,048,576 inode | `findmnt -T /tmp` · `stat -f /tmp` |
| page size | 16384 ไบต์ (เท่ากับ bsize ของ tmpfs) | `getconf PAGESIZE` (ย้อนตอนที่ 20) |
| `_CS_PATH` ของ libc | `/bin:/usr/bin` | `getconf PATH` |
| PATH ของ shell ที่รัน | 12 รายการ (ซ้ำ 2) | `echo $PATH` แล้วนับ |
| `ls` ตัวที่ถูกเรียก | `/usr/bin/ls` inode 2925 | `04_path_walk` หรือ `which -a ls` |

## 8. กับดักจริงที่เจอในบทนี้ (และวิธีกัน)

1. **buffer + `dup2`** — สลับ fd 1 โดยไม่ `fflush(stdout)` ก่อน ข้อความที่ค้างใน buffer ทั้งหมดจะไหลลงไฟล์ปลายทาง (เจอจริงในรอบแรกของ `03_fd_table.c`) → เรียก `fflush(NULL)` ทุกครั้งก่อนสลับ fd หรือ fork
2. **`fork` แล้วข้อความพิมพ์ซ้ำ** — เหตุเดียวกัน แต่เกิดกับ stdout ที่ค้างอยู่ตอน fork
3. **`PATH` ว่าง ≠ ไม่มี `PATH`** — ไม่มีตัวแปร → libc ใช้ `/bin:/usr/bin` (เจอ `ls`); ตั้งเป็น `""` = entry เดียวที่ว่าง = cwd (ไม่ใช่ `/bin:/usr/bin`) → ENOENT ทันที (ทดสอบจริงในหัวข้อ 5.4)
4. **`execve("ls")` ไม่ทำงาน** — ต้อง `execvp` ถ้าอยากให้ค้น PATH · และชื่อที่มี `/` จะข้ามการค้น PATH ทั้งหมด (man 3 execvp)
5. **`SIG_IGN` ติดข้าม `exec`** — ลูกต้องคืน `SIG_DFL` เอง ไม่งั้นโปรแกรมที่รันต่อจะกด Ctrl-C ไม่ได้
6. **`waitpid` คืน `-1` เพราะ `EINTR`** — ต้องวนรอบ ไม่งั้นอ่านสถานะพลาด
7. **อ่านไดเรกทอรีด้วย `read()`** — ไม่ได้ ต้อง `readdir()` (errno 21 EISDIR)
8. **ไว้ใจลำดับของ `readdir()`** — ไม่ได้ ระบบไฟล์ไม่รับประกันลำดับ (และไม่มี `.`/`..` นำหน้าเสมอไป)
9. **เลข inode ไม่ใช่ identity ถาวร** — ไฟล์ใหม่ได้เลขใหม่ เลขเก่าถูกใช้ซ้ำได้เมื่อไฟล์ถูกลบ อย่าเก็บ inode ไปอ้างอิงข้ามเวลา/ข้ามเครื่อง (`st_dev` + `st_ino` ต้องดูคู่กัน)
10. **`exit()` ในโปรเซสลูกหลัง `exec` ล้มเหลว** — ใช้ `_exit()` เพื่อไม่ให้ buffer/atexit ของโปรแกรมเดิมทำงานซ้ำ
11. **คำสั่งเกิน 64 คำ** — shell เราปฏิเสธพร้อมข้อความชัดเจน ไม่ overflow (และ `argv[argc] = NULL` ต้องมีเสมอ ไม่งั้น `execvp` อ่านเกินขอบเขต)
12. **state ที่เหลือในโปรเซสพ่อ** — `errno` และตัวแปรสถานะต่าง ๆ ต้อง initialize ใหม่ทุกครั้งก่อนใช้ เช็คค่าที่คืนก่อนอ่าน `errno` เสมอ (ย้อนตอนที่ 19)

## 9. สรุปสั้น 10 ข้อ

1. **ไฟล์ = บล็อกข้อมูล + inode(metadata) + ชื่อในไดเรกทอรี** — ชื่อไม่ได้อยู่ในไฟล์ และ inode ไม่มีชื่อ
2. **ไดเรกทอรีคือตารางชื่อ→inode** — ตรวจแล้ว 6/6 รายการตรงกัน · `read()` บนไดเรกทอรีได้ EISDIR (21)
3. **path = เดินจาก `/` ทีละท่อน** — วัดจริง 6 ก้าวจาก `/` (inode 2) ถึงไฟล์ปลายทาง (inode 4189672) · ทุกก้าวคือการค้นในไดเรกทอรี
4. **`st_size` ≠ พื้นที่ที่จองจริง** — ไฟล์ 1 ไบต์ = 4096 ไบต์ (ext4, บล็อก) หรือ 16384 ไบต์ (tmpfs, หน้า = page ในตอนที่ 20)
5. **hard link/rename ไม่แตะข้อมูล** — inode เดิมตลอด · nlink คือตัวนับชื่อ
6. **fd = ช่องในตารางของโปรเซส** — 0/1/2 ถูกจองแต่เกิด · เลขว่างต่ำสุดถูกใช้ก่อน · ดูของจริงได้ที่ `/proc/self/fd`
7. **`open` ซ้ำ = offset แยก · `dup` = offset ร่วม** — เพราะ offset อยู่ที่ตัวเปิดไฟล์ ไม่ใช่ inode
8. **`dup2` คือกลไกของ `>`** — เปลี่ยนช่อง fd 1 · และต้อง `fflush` ก่อน ไม่งั้นข้อความก่อนหน้าไหลลงไฟล์
9. **`execvp` ค้น PATH ให้ และการค้นคือการยิง `execve` ทีละโฟลเดอร์** (strace พิสูจน์) · `fork` บน Linux = `clone()`, รอลูก = `wait4()`
10. **shell = วงจร prompt → อ่าน → แยกคำ → built-in หรือ fork/execvp/waitpid** — 3 built-in ที่ต้องมีคือ `cd`/`exit`/`help` และ `cd` ต้องอยู่ในโปรเซส shell เองเพราะ cwd เป็นสมบัติของโปรเซส

## 10. โจทย์ฝึกมือ (2 ระดับ)

### ระดับ Drill (ซ้อมทวนความเข้าใจ)

1. **ไล่ inode ของเครื่องตัวเอง** — รัน `stat -c '%i %s %h %n' ไฟล์` กับ 3 ไฟล์ในเครื่อง แล้วรัน `02_dir_map.c` บนโฟลเดอร์ที่ไฟล์เหล่านั้นอยู่: ตัวเลข `d_ino` ตรงกับ `stat` ไหม? · จากนั้น `ln` ไฟล์หนึ่ง (hard link) แล้วรัน `stat` ทั้งสองชื่อ — nlink เปลี่ยนเป็นเท่าไร และ inode เปลี่ยนไหม? ลบชื่อหนึ่งแล้วอีกชื่อยังเปิดได้ไหม (ลอง `cat`)
2. **เดาแล้วทดสอบ PATH** — ก่อนรัน ให้เขียนคำตอบลงกระดาษว่า `env -u PATH ./06_shell` แล้วสั่ง `ls /etc/hostname` จะได้อะไร และ `env PATH= ./06_shell` จะได้อะไร (คำตอบอยู่ในหัวข้อ 5.4) · แล้วทดสอบ `PATH= ls` เทียบกับ `env PATH= ls` ใน terminal เอง — เหมือนกันไหม ทำไม
3. **แก้ `03_fd_table.c` ให้พิสูจน์ `>>`** — เพิ่มการทดลองเปิดไฟล์ด้วย `O_APPEND` แล้วเขียน 2 ครั้ง: ไฟล์ต้องได้เนื้อหาต่อกัน (ไม่ทับ) · อธิบายว่า `O_APPEND` ช่วยเรื่องนี้ยังไง และทำไม `dup2` อย่างเดียวไม่พอที่จะทำ `>>` ให้ถูกต้อง

### ระดับ Mini-Project (ประกอบความรู้)

**เขียน `mini_ls.c` — "ls จิ๋ว" ที่แสดงชื่อ + inode + ชนิด + ขนาดแบบเรียงเอง**

- รับ path ของโฟลเดอร์จาก argument (ไม่ใส่ = `.`) · ใช้ `opendir`/`readdir` อ่าน แล้วสำหรับแต่ละรายการ: `lstat()` + `d_ino` แล้ว **ตรวจว่า `d_ino` ตรงกับ `st_ino`** (ถ้าไม่ตรง ให้รายงานเป็น warning ไม่ใช่เงียบ ๆ)
- พิมพ์ 4 คอลัมน์: `inode` · ชนิด (ไฟล์/โฟลเดอร์/symlink — ถ้าเป็น symlink ให้ `readlink` แล้วพิมพ์เป้าด้วย) · `ขนาด` (ไดเรกทอรีให้พิมพ์ `-`) · `ชื่อ`
- **เรียงตามชื่อเอง** (ด้วย `qsort` — ห้ามพึ่งลำดับของ `readdir`) · ข้าม `.` และ `..` เว้นแต่ผู้ใช้ใส่ `-a`
- ข้อกำหนดความปลอดภัย: เปิด/ปิด `DIR` ทุกทางออก · ตรวจค่าที่คืนของ `opendir`, `lstat`, `readlink` ทุกครั้ง แล้วรายงานข้อความไทยที่อ่านรู้เรื่อง (ไม่ใช่แค่ "error") · path ที่ยาวเกิน `PATH_MAX` ต้องไม่ overflow · โฟลเดอร์ที่ไม่มีสิทธิ์อ่าน → ต้องบอก errno ให้ถูก ไม่ crash
- **เกณฑ์ผ่าน:** `./mini_ls` บนโฟลเดอร์เดียวกันให้ inode ตรงกับ `ls -i` เป๊ะ (เทียบด้วย `diff` หลัง `sort`) และรันซ้ำ 2 ครั้งได้ผลเหมือนเดิมเสมอ (พิสูจน์ว่าเราไม่พึ่งลำดับของ readdir)
- โบนัส: เพิ่ม `-l` ที่พิมพ์สิทธิ์เป็นตัวอักษรแบบ `ls -l` (`-rw-r--r--`) จาก `st_mode` เอง — เขียนฟังก์ชันแปลง mode เป็นสตริง 10 ตัวอักษร

**bonus ท้าทาย (ไม่บังคับ): `mini_shell.c`** — ต่อยอด `06_shell.c` เพิ่ม **redirect** `>` และ `>>` (ใช้ `dup2` — หัวข้อ 4) กับ **pipe `|`** 1 ตัว (ใช้ `pipe()` + `dup2` + fork 2 ตัว) · พร้อมเก็บ `$?` เป็นตัวแปรใน shell แล้วให้พิมพ์คำสั่ง `echo $?` ได้
- **เกณฑ์ผ่าน:** `echo hello > /tmp/x.txt` แล้ว `cat < /tmp/x.txt` ได้ `hello` · `ls /usr/bin | wc -l` ให้ตัวเลขเท่ากับที่รันใน bash · และ `roflcopter; echo $?` พิมพ์ `127`
- ระวัง: ต้องปิด fd ที่ไม่ใช้ในทุกโปรเซส (ไม่งั้น pipe จะไม่จบ — `wc` จะรอ EOF ไม่รู้จบ) นี่คือบทเรียน pipe ที่คนพลาดมากที่สุด

## 11. คำเตือนตามกาลเวลา + แหล่งอ้างอิง

**As of กันยายน 2026** — ข้อเท็จจริงในบทนี้ยืนยันจากการรันจริงบน Raspberry Pi 5 (Linux 6.18.39+rpt-rpi-2712 aarch64 · GCC 14.2.0 · glibc 2.41 · strace 6.13 · man-pages 6.9.1) · ค่าที่อ้างเป็นของ **เครื่องนี้**: ext4 บล็อก 4096 ไบต์ บน `/dev/nvme0n1p2` · `NAME_MAX` 255 · `PATH_MAX` 4096 · `_CS_PATH` = `/bin:/usr/bin` · `/tmp` เป็น tmpfs (bsize 16384) — **ไม่ใช่ค่าสากล**

- **ขนาดบล็อกและชนิดระบบไฟล์ต่างกันตามเครื่อง** — ext4 มัก 4096 ไบต์ แต่ tmpfs จ่ายเป็นหน้า (ที่นี่ 16384) และระบบไฟล์อื่น (xfs/btrfs/zfs) จองไม่เหมือนกันเลย ไฟล์ 1 ไบต์จึงกินพื้นที่ไม่เท่ากันบนคนละระบบ **เช็คด้วย `stat -f <path>` เสมอ**
- **จำนวน inode ของ ext4 ถูกกำหนดตอนสร้างระบบไฟล์** — `mkfs.ext4` ที่ตั้งจำนวน inode ไว้น้อยจะเกิดปัญหา "ดิสก์ว่างแต่สร้างไฟล์ไม่ได้" (`df -i` เต็ม) แม้ `df -h` ยังเหลือ — เรื่องนี้จะเจอในงานจริงบนเซิร์ฟเวอร์ที่เก็บไฟล์เล็กจำนวนมาก
- **รายละเอียด `execvp` เป็นของ libc ไม่ใช่เคอร์เนล** — พฤติกรรมการค้น PATH, การข้ามเมื่อชื่อมี `/`, การลองต่อเมื่อเจอ `EACCES` อยู่ใน man 3 execvp · อย่างที่ strace ในบทนี้โชว์ การค้นเกิดขึ้นเป็นชุด `execve` ที่ล้มเหลว ถ้าเปลี่ยน libc (musl/Alpine) รายละเอียดการลองอาจต่างออกไป และ **glibc เคยเปลี่ยนค่า default เรื่องการใส่ cwd ใน PATH ระหว่างเวอร์ชัน** (man 3 execvp ระบุไว้ในส่วน VERSIONS) — อย่าอาศัยพฤติกรรมนี้โดยไม่ทดสอบ
- **ค่า `readdir` และ `st_ino` ขึ้นกับระบบไฟล์และ kernel** — เลข inode ของโฟลเดอร์สาธิตในบทนี้เปลี่ยนทุกครั้งที่รัน เพราะระบบเลือกเลขว่าง (และ ext4 อาจส่ง inode 32 บิตแบบเก่าให้แอปที่ยังไม่รองรับ 64 บิตรวมถึงผ่าน `readdir` บนบาง config)
- **ตัวเลข ns/ms ไม่มีในบทนี้โดยเจตนา** — ราคาของ syscall ขึ้นกับงานที่วิ่งอยู่ ให้วัดเองบนเครื่องจริง (บทที่ 19 มีวิธีอยู่)

**แหล่งอ้างอิงหลักที่ใช้ในบทนี้**:

- `man 2 open`, `man 2 read` (EISDIR), `man 2 write`, `man 2 lseek`, `man 2 close`, `man 2 dup`, `man 2 stat`, `man 2 unlink`, `man 2 link`, `man 2 rename`, `man 2 chdir` (man-pages 6.9.1)
- `man 7 path_resolution` — ขั้นตอนเดิน path ทีละส่วน และสิทธิ์ที่ต้องมีในแต่ละท่อน
- `man 3 execvp` — PATH search, การใช้ `confstr(_CS_PATH)` เมื่อไม่มี PATH, การข้ามเมื่อชื่อมี `/`, การลองต่อเมื่อ `EACCES`
- `man 2 fork`, `man 2 clone`, `man 2 waitpid`, `man 2 signal`, `man 2 pipe`, `man 2 dup2`

- ไฟล์ในเครื่อง: `/proc/self/fd`, `getconf NAME_MAX`, `getconf PATH_MAX`, `getconf PATH`, `stat -f`, `df -i`

โค้ดทั้งหมดในบทนี้พร้อมผลรันดิบ: `course/code/ep21/` (ดู `out/` สำหรับผลรันที่แปะในบทนี้ · `gen_svgs.py` สำหรับภาพทั้ง 4 · `run_all.sh` สำหรับรันซ้ำทั้งหมด) — คอมไพล์ผ่านสะอาดด้วย `gcc -std=c17 -Wall -Wextra -Wpedantic` ทั้ง 6 โปรแกรม

แนวคิดเรื่อง file system และ shell อาจถูกท้าทายในอนาคต (ระบบไฟล์แบบ log-structured, ระบบไฟล์ที่ไม่มี inode แบบเดิม, object storage, container image ที่รับ "path" ได้หลากหลาย, shell ยุคใหม่ที่ออกแบบโมเดลข้อมูลเป็น structured ไม่ใช่ข้อความ) แต่จุดที่ไม่เปลี่ยนคือ **หลักการ**: แยก "ชื่อ" ออกจาก "ตัวข้อมูล" ให้มี metadata กลางที่ทุกฝ่ายอ้างถึง และให้โปรแกรมหนึ่งประกอบคำสั่งของผู้ใช้ให้กลายเป็นการเรียก syscall ที่มีแบบแผน — shell คือตัวอย่างแรกที่นักศึกษาวิทยาการคอมพิวเตอร์ควรอ่านโค้ดให้จบทั้งไฟล์
