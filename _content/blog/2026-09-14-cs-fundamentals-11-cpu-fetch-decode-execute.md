ตอนที่ 09 เราสร้าง **ALU** (Arithmetic Logic Unit = วงจรที่บวก-ลบ-เทียบ-AND/OR ได้ ตามตอน 09) จนเครื่องบวกเลขทำงานได้จริง ตอนที่ 10 เราสร้าง **RAM** และ **register** (ที่พักข้อมูลชั่วคราวในซีพียู) จนเครื่อง "จำ" ค่าได้

แต่เครื่องสองตัวนั้นยังเป็นแค่ "ชิ้นส่วน" ที่นอนเฉย ๆ ไม่ได้ทำอะไรด้วยตัวเอง

คำถามของตอนนี้คือ: **อะไรทำให้ชิ้นส่วนทั้งสอง "วิ่ง" เองได้?** ทำไมเวลาเราดับเบิลคลิกโปรแกรม มันถึงทำงานไปทีละบรรทัดตั้งแต่บรรทัดแรกจนจบ โดยไม่มีใครมายืนกดสวิตช์ทีละตัว?

คำตอบคือ **CPU** (Central Processing Unit = หน่วยประมวลผลกลาง = สมองของเครื่อง) และหัวใจของมันคือวงจรที่วนลูปสามขั้นซ้ำไม่รู้จบ: **fetch → decode → execute** — อ่านคำสั่ง → ถอดความหมาย → ลงมือทำ แล้ววนกลับไปอ่านคำสั่งถัดไป

ตอนนี้ไม่มีโค้ด Go ให้พิมพ์ เพราะเราอยู่ชั้นล่างกว่าระดับโค้ด (ชั้นวงจร) เหมือนตอน 09–10 แต่มีวงจรให้ต่อจริงใน CircuitVerse — และท้ายตอน เราจะต่อ **CPU จิ๋ว 4 บิต** ที่รันโปรแกรมบวกเลข `3 + 4` ได้จริง ด้วยมือล้วน ๆ

## 0. ปัญหา: เครื่องที่ "บวกเลขได้" ยังไม่ใช่ "คอมพิวเตอร์"

ย้อนกลับไปดูสิ่งที่เรามี ณ ตอนนี้:

- **ALU** (ตอน 09) — วงจรคำนวณ เอาบิตเข้า แปลงเป็นบิตออกทันที จำอะไรไม่ได้
- **RAM + register** (ตอน 10) — วงจรจำ เก็บบิตไว้ได้ แต่ตัวมันเอง "คิด" ไม่เป็น

ถ้าเราต้องการบวกเลข `3 + 4` ด้วยมือ เราต้องทำแบบนี้ทุกครั้ง:

1. เดินไปตั้งค่า input ของ ALU เป็น `0011` (3) กับ `0100` (4)
2. อ่านผลลัพธ์ `0111` (7) ที่ output
3. (ถ้าจะบวกอีกตัว) ลบแล้วตั้งค่าใหม่ วนไป

นี่คือ "เครื่องคิดเลขที่ต้องมีคนคอยกด" — ไม่ใช่คอมพิวเตอร์

> **คำศัพท์: โปรแกรม (program)** = ชุดคำสั่งที่เขียนไว้ล่วงหน้า ให้เครื่องทำตามทีละคำสั่งโดยอัตโนมัติ แทนที่จะต้องมีคนคอยสั่งทีละก้าว — ตอนนี้เรารู้จัก "ตัวแปร" กับ "ฟังก์ชัน" ใน Go (ตอน 03–05) มาแล้ว แต่ยังไม่เห็นว่า "การทำงานอัตโนมัติ" เกิดจากกลไกอะไรในระดับเครื่อง

คอมพิวเตอร์คือเครื่องที่**อ่านคำสั่งเอง ตีความเอง ลงมือทำเอง แล้วเลื่อนไปอ่านคำสั่งถัดไปเอง** — ไม่มีใครต้องคอยกดปุ่ม

แล้ว "คำสั่ง" เก็บไว้ที่ไหน? คำตอบเรามีแล้ว: **RAM** (ตอน 10) แล้ว "เลื่อนไปคำสั่งถัดไป" มาจากไหน? คำตอบคือ register ตัวหนึ่งชื่อ **Program Counter** ซึ่งเป็นพระเอกของตอนนี้

ดูภาพที่ 1 ภาพรวมของทั้งเครื่องก่อน แล้วเราจะค่อย ๆ แกะทีละชิ้น

![ภาพรวมซีพียูและลูป fetch-decode-execute](/assets/diagrams/ep11-01-cpu-machine-cycle.svg)

ภาพที่ 1 ฝั่ง A คือแผนผังของ CPU ทั้งหมด กับ RAM ที่มันคุยด้วยตลอดเวลา — ส่วนฝั่ง B คือลูปสามขั้นที่มันวนซ้ำไม่รู้จบ

จดรายชื่อ "ตัวละคร" ไว้ก่อน เดี๋ยวเราจะรู้จักทีละตัว:

- **PC — Program Counter** (โปรแกรมเคาน์เตอร์) = register ที่ชี้ว่า "คำสั่งถัดไปอยู่ที่ address ไหน" — ตัวเอกของตอนนี้
- **IR — Instruction Register** = register ที่พัก "คำสั่งที่เพิ่งอ่านมา"
- **MAR / MDR** = register ที่พัก address / ข้อมูล ระหว่างที่ CPU คุยกับ RAM
- **Control Unit** = วงจรถอดความหมายของคำสั่ง (ดูตอนนี้)
- **ALU** = วงจรคำนวณ (ตอน 09)
- **ACC — Accumulator** = register ที่พัก "ผลคำนวณสะสม"

เริ่มจากขั้นแรกของลูป

## 1. FETCH — อ่านคำสั่ง (ตามที่ PC ชี้)

> **คำศัพท์: fetch (เฟตช์)** = การไป "หยิบ" คำสั่งจาก RAM เข้ามาใน CPU — มาจากคำว่า "ไปเอามา" นั่นเอง

ขั้น fetch มีกฎเหล็กแค่ข้อเดียว: **อ่านคำสั่งจาก RAM ที่ address ตามที่ PC บอก แล้วเอามาใส่ IR**

ดูภาพที่ 2

![วงจรขั้น fetch: PC → MAR → RAM → MDR → IR และรูปแบบคำสั่ง 4 บิต](/assets/diagrams/ep11-02-fetch-instruction-format.svg)

ไล่ตามลูกศรในภาพที่ 2 ฝั่ง A จากซ้ายไปขวา:

1. **PC** เก็บค่า address ไว้ (ในตัวอย่าง `01` = คำสั่งถัดไปอยู่ช่องที่ 1)
2. ค่านั้นถูก "ก๊อป" ไปที่ **MAR** (Memory Address Register = ที่พัก address ก่อนยื่นให้ RAM)
3. RAM คืน "ข้อมูลที่ช่องนั้น" ออกมา ซึ่งก็คือ **คำสั่ง 4 บิต** ของเรา
4. คำสั่งเดินเข้าผ่าน **MDR** (Memory Data Register = ที่พักข้อมูล) แล้วเข้าไปพักที่ **IR**

พร้อมกันนั้น (ลูกศรล่าง) วงจรบวก 1 จะเอา `PC + 1` เก็บกลับเข้า PC — เพื่อให้ PC ชี้คำสั่งถัดไปเรียบร้อยก่อนรอบหน้า

> **ทำไมต้องมี MAR/MDR แทรกตรงกลาง?** ใน CPU จริง ๆ RAM ไม่ได้ต่อสายตรงกับ register ตัวอื่นได้ทุกตัว เพราะ CPU คุยกับ RAM ได้ผ่าน "สายกลาง" เส้นเดียว (เรียกว่า **bus** = ช่องทางส่งข้อมูลร่วม) — ต้องมีที่พักคั่นว่าตอนนี้ "กำลังยื่น address ไหน" (MAR) และ "ข้อมูลที่ได้มาคืออะไร" (MDR) ก่อนส่งต่อไปที่จุดหมายจริง ๆ ใน CPU จิ๋วที่เราจะต่อท้ายตอน เราตัด MAR/MDR ออกเพื่อให้ต่อจบในหน้าจอเดียว แต่กลไกข้างในเหมือนกัน

หัวใจของ fetch ที่ต้องจดไว้: **RAM ไม่รู้หรอกว่าคำสั่งอยู่ไหน — มันแค่คืนค่าที่ address ที่เราป้อนให้** ตัวที่ "จำได้" ว่าโปรแกรมเดินมาถึงบรรทัดไหนแล้ว คือ PC นี่แหละ

## 2. คำสั่งหน้าตาเป็นยังไง: opcode + operand

ก่อนไปขั้น decode เราต้องรู้ก่อนว่า "คำสั่ง 4 บิต" ที่เพิ่ง fetch เข้ามานั้น หน้าตาเป็นยังไง

ดูภาพที่ 2 ฝั่ง B — คำสั่ง 4 บิตแบ่งเป็นสองส่วน:

- **opcode** (2 บิตแรก ทางซ้าย) = รหัสบอกว่า "ให้ทำ**อะไร**" — ในเครื่องเรามี 4 แบบ: `LOAD`, `ADD`, `STORE`, `OUT`
- **operand** (2 บิตหลัง ทางขวา) = ข้อมูลที่คำสั่งทำด้วย — ในเครื่องเราคือ address ของช่องข้อมูล (2 บิต เลือกได้ 4 ช่อง)

> **คำศัพท์: opcode** (อ่านว่า "ออป-โค้ด" มาจาก operation code = รหัสการทำงาน) = ส่วนของคำสั่งที่บอก "ทำอะไร" · **operand** (อ่านว่า "โอเปอร์แรนด์") = ส่วนที่บอก "ทำกับข้อมูลตัวไหน"

ตัวอย่างในภาพ: `0010` แปลว่า opcode `00` (= LOAD) + operand `10` (= address 2) → ใจความคือ "โหลดค่าจาก RAM ช่อง 10 มาใส่ ACC"

> **คำศัพท์: ISA** (Instruction Set Architecture = สถาปัตยกรรมชุดคำสั่ง) = "พจนานุกรม" ที่ระบุว่าเครื่องนี้มีคำสั่งอะไรบ้าง แต่ละคำสั่งมี opcode เป็นเลขอะไร และทำงานยังไง — CPU แต่ละตระกูลมี ISA ของตัวเอง เช่น x86 (ชิป Intel/AMD), ARM (ชิปมือถือ / Raspberry Pi ของเรา) และ ISA ของ CPU จิ๋วเรามีแค่ 4 คำสั่ง (ดูภาพที่ 5 ฝั่ง B)

เอาล่ะ ตอนนี้ IR เก็บคำสั่งไว้แล้ว ไปขั้นถัดไป

## 3. DECODE — ถอดความหมาย (Control Unit)

> **คำศัพท์: decode (ดีโค้ด)** = การ "ถอดรหัส" — เอาเลข opcode ไปแปลว่าต้องทำอะไร แล้วเปิดสัญญาณให้ถูกจุด

ขั้น decode ทำงานโดย **Control Unit** (หน่วยควบคุม) — วงจรที่รับ opcode 2 บิตเข้าไป แล้ว "เปิดสวิตช์" สัญญาณควบคุมให้ถูกเส้น

ดูภาพที่ 3

![ขั้น decode: Control Unit อ่าน opcode แล้วเปิดสัญญาณควบคุม](/assets/diagrams/ep11-03-decode-control-unit.svg)

ในภาพที่ 3 ฝั่ง A คำสั่ง `0010` ใน IR ถูกแยกเป็นสองส่วนด้วย **Splitter** (ชิ้นส่วนที่แยกกลุ่มบิตออกเป็นเส้น ๆ):

- **opcode `00`** เดินไปที่ Control Unit → มันอ่านแล้วเปิดสัญญาณ `LOAD_EN = 1` (ส่วนสัญญาณอื่นเป็น 0 หมด)
- **operand `10`** เดินตรงไปที่ address ของ RAM ข้อมูลเลย — **ไม่ผ่าน** Control Unit เพราะ "จะทำกับข้อมูลตัวไหน" ถูกระบุมาแล้วในคำสั่งเอง

> **ความลับของ CPU ทั้งหมด อยู่ในบรรทัดเดียว:** CPU ไม่รู้จักคำว่า "ADD" — มันเห็นแค่เลข `01` แล้วเปิดสวิตช์ตัวที่ชื่อ `ADD_EN` เท่านั้น ความฉลาดทั้งหมดของมันคือ "เลข opcode → สัญญาณที่ถูกเปิด" เป็นตารางตายตัว ดูภาพที่ 3 ฝั่ง B

ตาราง decode ของ CPU จิ๋วเรา (จำ 4 บรรทัดนี้ได้ ก็อ่าน CPU ทั้งเครื่องออก):

| opcode | ชื่อคำสั่ง | สัญญาณที่ถูกเปิด | ผลที่เกิดขึ้น |
|---|---|---|---|
| `00` | LOAD addr | LOAD_EN = 1 | ACC ← ค่าจาก RAM[addr] |
| `01` | ADD addr | ADD_EN = 1 | ACC ← ACC + RAM[addr] |
| `10` | STORE addr | WRITE = 1 (ที่ RAM) | RAM[addr] ← ACC |
| `11` | OUT | OUT_EN = 1 | ACC → LED (แสดงผล) |

> **ศัพท์ที่ผูกกัน:** `_EN` ท้ายชื่อสัญญาณ มาจาก **enable** (อ่านว่า "เอนาเบิล" = เปิดใช้งาน / อนุญาต) — สัญญาณที่ชื่อ `LOAD_EN` แปลว่า "อนุญาตให้โหลดค่า" เมื่อเป็น 1 อนุญาต เมื่อเป็น 0 ห้าม เราเจอแนวคิด enable ครั้งแรกในตอน 10 (ขา E ของ D latch)

แล้ว opcode แต่ละตัว "เปิดสัญญาณยังไง"? ก็วงจร logic ธรรมดา (ตอน 09) — เช่น ถ้า opcode เป็น `00` (บิตแรก 0 บิตสอง 0) ก็ให้ `LOAD_EN = 1` ถ้าเป็น `01` ให้ `ADD_EN = 1` ไปเรื่อย ๆ Control Unit จึงเป็น **combinational logic ล้วน ๆ** (วงจรที่ผลลัพธ์ขึ้นกับอินพุตตอนนั้นเท่านั้น ตามตอน 09) — ไม่มีนาฬิกา ไม่จำอะไรเลย มันแค่ "แปล" opcode เป็นสัญญาณตลอดเวลา

## 4. EXECUTE — ลงมือทำ (ALU + ACC)

> **คำศัพท์: execute (เอ็กซ์คิวต์)** = ลงมือทำตามคำสั่ง — เปิดทางให้ ALU / register / RAM ทำงานจริงตามสัญญาณที่ decode เปิดไว้

ขั้นสุดท้ายของลูปคือให้วงจร "ทำงานจริง" ดูภาพที่ 4

![ขั้น execute: ALU บวกค่าใน ACC กับค่าจาก RAM แล้วเก็บผลที่ ACC](/assets/diagrams/ep11-04-execute-alu-accumulator.svg)

ภาพที่ 4 ฝั่ง A แสดงคำสั่ง `ADD 11` (opcode `01` + operand `11`):

1. Control Unit เปิด `ADD_EN = 1` (จากการ decode ในตอนก่อน)
2. ค่าเดิมใน **ACC** (`0011` = 3) กับค่าจาก **RAM[11]** (`0100` = 4) ไหลเข้าสองขาของ **ALU**
3. ALU บวกได้ `0111` (7)
4. ผลลัพธ์ไหลกลับเข้าพักที่ **ACC ใหม่** = `0111`

> **คำศัพท์: accumulator (แอคคิวมูเลเตอร์, ACC)** = register ที่พัก "ผลสะสม" — เพราะ ALU ของเราบวกได้ทีละสองค่า (ตอน 09) การบวกหลายตัวจึงต้อง "บวกต่อจากผลเดิม" ไปเรื่อย ๆ โดยเก็บผลไว้ที่ ACC แล้วรอบถัดไปก็เอาผลนี้กลับไปบวกต่อ

สามคำสั่งที่เหลือก็คือการเปิด-ปิดทางเดินต่าง ๆ (ภาพที่ 4 ฝั่ง B):

- **LOAD addr** — ก๊อปค่าจาก RAM[addr] เข้ามาพักที่ ACC (ทางที่ "โหลดค่าใหม่")
- **ADD addr** — เอา ACC + RAM[addr] ผ่าน ALU เก็บกลับ ACC (ทางที่ "บวกต่อ")
- **STORE addr** — เขียนค่า ACC กลับลง RAM[addr] (ทางเดียวที่ค่าจะ "กลับไปนอน" ใน RAM — ถ้าไม่ STORE ค่าจะอยู่แค่ใน ACC แล้วหายไปเมื่อโหลดค่าอื่นทับ)
- **OUT** — เปิดไฟ LED แสดงค่า ACC (ทาง "แสดงผล")

> **ทำไมต้องมี ACC ทำไม ALU ไม่เก็บผลเอง?** เพราะ ALU เป็น combinational logic (ตอน 09) — มันจำไม่ได้! พอ input หาย ผลลัพธ์ก็หายทันที ต้องมี register (วงจรจำจากตอน 10) มารับผลไว้ แล้ว ACC คือ register ตัวนั้นนี่แหละ

พอ execute เสร็จ ลูปก็**วนกลับไป fetch** (ภาพที่ 1 ฝั่ง B ลูกศรวนกลับ) — แล้วทุกอย่างเริ่มใหม่กับคำสั่งถัดไป

## 5. ทำไมเรื่องนี้สำคัญ: Program Counter คือหัวใจของ "โปรแกรมทำงาน"

ถึงตรงนี้ เราน่าจะเห็นภาพรวมของเครื่องทั้งเครื่องแล้ว มาดูว่า "แนวคิด" ที่แท้จริงในตอนนี้คืออะไร

**แนวคิดข้อที่ 1 — โปรแกรม "ไหล" ได้เพราะ PC**

คอมพิวเตอร์ไม่ได้ "ฉลาด" ที่รู้ว่าควรทำบรรทัดถัดไป — มันแค่ทำตามกฎโง่ ๆ ข้อเดียว:

> อ่านคำสั่งที่ address ตาม PC → PC + 1 → อ่านคำสั่งถัดไป → PC + 1 → ...

PC คือกลไกที่ทำให้โปรแกรม "ไหล" จากคำสั่งแรกไปคำสั่งสุดท้าย แล้วบรรทัด `if` กับ loop ใน Go (ตอน 04) ล่ะ? ในระดับเครื่อง คำสั่ง `if` กับ loop ล้วนถูกแปลเป็นคำสั่ง **jump / branch** (กระโดด = แก้ค่า PC ให้ข้ามไป address อื่นแทนการ +1) — ซึ่งเราจะเห็นของจริงในตอน 12 เรื่อง assembly

**แนวคิดข้อที่ 2 — เครื่องรัน "เร็ว" ได้เพราะลูปนี้ถี่มหาศาล**

CPU จริง ๆ วนลูป fetch-decode-execute นี้ซ้ำ ๆ ด้วยความเร็วสูงมาก — อย่างชิป ARM Cortex-A76 ใน Raspberry Pi 5 ของเรามีความเร็ว clock (นาฬิกาที่เต้นเป็นจังหวะ คุมจังหวะทำงาน ตามตอน 10) สูงสุด **2.4 GHz** (2,400 ล้านรอบต่อวินาที) — แต่ละรอบคือลูป fetch-decode-execute อย่างน้อยหนึ่งรอบ นั่นคือเหตุผลที่โปรแกรมที่ "วนลูปล้านครั้ง" ทำงานเสร็จในพริบตา

> **คำศัพท์: GHz (กิกะเฮิรตซ์)** = พันล้านรอบต่อวินาที ใช้บอกความเร็ว clock ของ CPU — 2.4 GHz แปลว่า clock เต้น 2,400,000,000 ครั้งต่อวินาที

**แนวคิดข้อที่ 3 — ทุกภาษาที่เราเขียน ในที่สุดก็กลายเป็น "เลข opcode"**

ตอน 03–07 เราเขียน Go — แต่ CPU วิ่งภาษา Go ไม่ได้ มันรู้จักแค่ "เลข 4 บิต" แบบที่เห็นในตาราง decode เท่านั้น กระบวนการที่แปลง `func` / `if` / `for` ของเรา ให้กลายเป็นลำดับของ opcode ที่ CPU เข้าใจ เรียกว่า **compile** (คอมไพล์ = แปลงโค้ดเป็นภาษาเครื่อง) ซึ่งเป็นหัวข้อของตอน 17 — และถ้าอยากเห็น "หน้า" ของภาษาเครื่องจริง ๆ เราจะเขียนมันเองในตอน 12 เรื่อง assembly

## 6. ลงมือทำ: ต่อ CPU จิ๋ว 4 บิตที่บวกเลข 3+4 ได้จริง

> **ก่อนเริ่ม:** เปิด https://circuitverse.org แล้วสร้าง project ใหม่ · สวิตช์/ปุ่มอยู่ในกลุ่ม **Input** · ไฟ LED อยู่ในกลุ่ม **Output** · D flip-flop, RAM อยู่ในกลุ่ม **Sequential Elements** · Adder อยู่ในกลุ่ม **Misc** · Splitter อยู่ในกลุ่ม **Misc**

เราจะต่อ **CPU จิ๋ว 4 บิต** ที่มี ISA แค่ 4 คำสั่ง (ภาพที่ 5) แล้วรันโปรแกรมบวกเลข `3 + 4` จริง ๆ (ภาพที่ 6)

ดูภาพที่ 5 ก่อน — นี่คือแผนผังทั้งวงจรที่เราจะต่อ

![แผนผังวงจร CPU จิ๋ว 4 บิต และชุดคำสั่ง ISA](/assets/diagrams/ep11-05-mini-cpu-circuit.svg)

องค์ประกอบทั้งหมด (จากภาพที่ 5):

| ชิ้นส่วน | จำนวน | ทำหน้าที่ |
|---|---|---|
| RAM โปรแกรม | 1 | 4 ช่อง × 4 บิต เก็บคำสั่ง |
| RAM ข้อมูล | 1 | 4 ช่อง × 4 บิต เก็บตัวเลข |
| PC (2 บิต) | 1 | ชี้คำสั่งถัดไป (สร้างจาก D flip-flop 2 ตัว) |
| IR (4 บิต) | 1 | พักคำสั่งที่เพิ่ง fetch (D flip-flop 4 ตัว) |
| Control Unit | 1 | อ่าน opcode เปิดสัญญาณ (ต่อจาก logic gate) |
| ALU (Adder) | 1 | บวก ACC + ค่าจาก RAM (Adder ในกลุ่ม Misc) |
| ACC (4 บิต) | 1 | พักผลคำนวณ (D flip-flop 4 ตัว) |
| LED × 4 | 1 | แสดงผลตอนคำสั่ง OUT |
| ปุ่ม Clock | 1 | กดหนึ่งครั้ง = เดินหนึ่งก้าว |

> **หมายเหตุเรื่องความง่าย (สำคัญ):** ใน CPU จริง การต่อ PC เข้ากับ RAM ต้องผ่าน MAR/MDR และมี bus กลาง แต่ใน CPU จิ๋วนี้เราตัดสิ่งเหล่านั้นออก — ต่อ PC เข้ากับ address ของ RAM โปรแกรมตรง ๆ และใช้ operand จาก IR เป็น address ของ RAM ข้อมูลตรง ๆ เพื่อให้ต่อจบได้ในหน้าจอเดียว กลไกแกนกลาง (fetch-decode-execute) เหมือนเดิมทุกประการ

### ข้อ A — สร้าง fetch: PC → RAM โปรแกรม → IR

1. ลาก **RAM** 2 ตัวมาวาง ตั้ง Properties (แผงขวา) ทั้งคู่: **Address Width = 2** (ช่อง BitWidth อยู่ด้านบนของแผง Properties), **BitWidth = 4** — ตัวบนคือ "RAM โปรแกรม" ตัวล่างคือ "RAM ข้อมูล"
2. สร้าง **PC 2 บิต**: ลาก D flip-flop 2 ตัว (กลุ่ม Sequential Elements) มาต่อเป็น register 2 บิต — วิธีเดียวกับตอน 10 ข้อ C ที่ต่อ register 4 บิต
3. ต่อค่า PC เข้า address ของ RAM โปรแกรม (พิน ADDRESS 2 บิต)
4. สร้าง **IR 4 บิต**: ลาก D flip-flop 4 ตัว ต่อ DATA OUT ของ RAM โปรแกรม (4 บิต) เข้าขา D ของ flip-flop ทั้ง 4 ตัว
5. สร้างวงจร **PC + 1**: ลาก **Adder** (กลุ่ม Misc) ตั้ง BitWidth = 2 ต่อ PC (2 บิต) เข้าขา A และตั้งขา B เป็นค่าคงที่ `01` (ใช้สวิตช์/ค่าคงที่) แล้วต่อผลลัพธ์กลับเข้าขา D ของ PC (เส้นป้อนกลับ ตามตอน 10)
6. ต่อ **ปุ่ม Clock** (กลุ่ม Input) หนึ่งปุ่ม เข้า Clock ของ flip-flop ทุกตัว (ทั้ง PC และ IR)
7. **ทดสอบ**: กดปุ่ม Clock ทีละครั้ง → สังเกต PC เดิน `00 → 01 → 10 → 11 → 00` วนไป (2 บิต นับเกิน 3 ก็วนกลับ 0) และ IR รับคำสั่งจาก RAM โปรแกรมตาม address ที่ PC ชี้

> **จุดที่มักงง:** ครั้งแรกที่กด Clock ค่าใน IR จะดู "ไม่ตรง" กับที่คิด — เพราะในจังหวะ clock เดียว PC เพิ่มเป็น `01` พร้อมกับ IR รับคำสั่งจาก address `00` (ค่าที่ PC เป็น**ก่อน**เพิ่ม) ข้อมูลใน register ทุกตัวขยับ "พร้อมกัน" ในจังหวะ clock เดียวกัน (ตามตอน 10)

### ข้อ B — เขียนโปรแกรมลง RAM โปรแกรม

เราจะเขียนโปรแกรมบวก `3 + 4` ลง RAM โปรแกรม (ใช้วิธีเดียวกับตอน 10 ข้อ D):

| address | คำสั่ง 4 บิต | opcode | operand | ใจความ |
|---|---|---|---|---|
| `00` | `0010` | 00 LOAD | 10 (address 2) | LOAD 10 → ACC = ค่าช่อง 10 (= 3) |
| `01` | `0111` | 01 ADD | 11 (address 3) | ADD 11 → ACC = ACC + ค่าช่อง 11 (= 4) |
| `10` | `1011` | 10 STORE | 11 (address 3) | STORE 11 → เขียน ACC ลงช่อง 11 |
| `11` | `1100` | 11 OUT | 00 (ไม่ใช้) | OUT → แสดง ACC ที่ LED |

และตั้งข้อมูลลง RAM ข้อมูล: ช่อง `10` = `0011` (3) · ช่อง `11` = `0100` (4) · ช่อง `00` และ `01` = `0000`

### ข้อ C — เพิ่ม decode: Splitter + Control Unit

1. ลาก **Splitter** (กลุ่ม Misc) มาวาง ต่อค่า IR (4 บิต) เข้า Splitter แล้วตั้งให้แยกเป็น 2 กลุ่ม: บิตบน 2 บิต (opcode) และบิตล่าง 2 บิต (operand)
2. ต่อ operand (2 บิต) ตรงไปที่ address ของ RAM ข้อมูล (พิน ADDRESS)
3. สร้าง **Control Unit** จาก logic gate (ตอน 09): รับ opcode 2 บิตเข้า แล้วเปิดสัญญาณตามตาราง decode ในภาพที่ 3 ฝั่ง B — `00 → LOAD_EN`, `01 → ADD_EN`, `10 → WRITE`, `11 → OUT_EN` (ใบ้: ใช้ AND gate + NOT gate แปลงเลข opcode เป็นสัญญาณทีละเส้น)

### ข้อ D — เพิ่ม execute: ALU + ACC + LED

1. สร้าง **ACC 4 บิต** จาก D flip-flop 4 ตัว (เหมือน IR)
2. ลาก **Adder** (กลุ่ม Misc) ตั้ง BitWidth = 4 ต่อ ACC เข้าขา A และ DATA OUT ของ RAM ข้อมูลเข้าขา B
3. ต่อผลลัพธ์ Adder เข้ากับขา D ของ ACC ผ่าน gate ที่คุมด้วย `ADD_EN` (และแยกเส้นสำหรับ `LOAD_EN` ที่โหลดค่า RAM ข้อมูลตรง ๆ เข้า ACC — ตามภาพที่ 5)
4. ลาก **LED 4 ดวง** (กลุ่ม Output) ต่อกับ ACC ผ่านทางที่คุมด้วย `OUT_EN`
5. ต่อสัญญาณ `WRITE` จาก Control Unit เข้าพิน WRITE ของ RAM ข้อมูล (สำหรับคำสั่ง STORE)

### ข้อ E — เดินเครื่องจริง

ดูภาพที่ 6 แล้วกดปุ่ม Clock ตามตาราง

![โปรแกรมบวกเลขใน RAM และตารางเดินเครื่องทีละก้าว](/assets/diagrams/ep11-06-program-and-trace.svg)

ภาพที่ 6 ฝั่ง B คือ "ร่องรอย" (trace = บันทึกค่าในแต่ละก้าว) ของการเดินเครื่อง — กดปุ่ม Clock หนึ่งครั้ง = register ทุกตัวขยับหนึ่งจังหวะ:

| กดครั้งที่ | PC | IR | ACC | RAM[11] | สิ่งที่เห็น |
|---|---|---|---|---|---|
| 1 | `01` | `0010` LOAD 10 | `0000` (0) | `0100` (4) | fetch ได้คำสั่งแรก (LOAD 10) |
| 2 | `10` | `0111` ADD 11 | `0011` (3) | `0100` (4) | LOAD ทำงาน: ACC = 3 |
| 3 | `11` | `1011` STORE 11 | `0111` (7) | `0100` (4) | ADD ทำงาน: ACC = 3+4 = 7 |
| 4 | `00` | `1100` OUT | `0111` (7) | `0111` (7) | STORE เขียน 7 ลง RAM[11] |
| 5 | `01` | `0010` LOAD 10 | `0111` (7) | `0111` (7) | OUT เปิด LED = 7 แล้ว fetch LOAD 10 (รอบใหม่) |

> **อ่านตารางนี้แล้วจะเห็น "การไหล" ของโปรแกรมชัด ๆ:** PC เดินหน้าทีละ 1 ทุกครั้งที่กด · IR เปลี่ยนตาม · ACC สะสมผล · LED โผล่ผลลัพธ์ตอนคำสั่ง OUT สังเกตจุดสำคัญ: **คำสั่งที่เห็นใน IR จะออกฤทธิ์เต็มที่ในการกดครั้งถัดไป** เพราะจังหวะ clock เดียว ทั้ง fetch (รับคำสั่งใหม่เข้า IR) และ execute (ของคำสั่งก่อนหน้า) เกิดขึ้นพร้อมกัน

ถ้าต่อครบและกดจนถึงครั้งที่ 5 แล้ว LED โชว์ `0111` (7) — **ยินดีด้วย คุณเพิ่งสร้าง CPU ที่บวกเลขได้จริง ด้วยมือล้วน ๆ**

## 7. โจทย์ฝึก (2 ระดับ)

### ระดับ 1 — drill (ฝึกความแม่นยำ)

1. อธิบายด้วยภาษาตัวเอง 1 ประโยค: fetch ทำอะไร ใช้ register อะไรบ้าง และ PC เปลี่ยนไปยังไงหลัง fetch เสร็จ
2. คำสั่ง `0111` แปลว่าอะไร? จงแยก opcode กับ operand ออกมา แล้วบอกใจความ (ใบ้: ดูภาพที่ 2 ฝั่ง B)
3. ถ้า RAM โปรแกรมมีคำสั่งที่ address `00` และ PC เริ่มที่ `00` — หลังกด Clock ครั้งแรก PC จะเป็นค่าไหน และ IR จะได้คำสั่งจาก address ไหน?
4. ถ้าอยากให้โปรแกรม "ข้าม" คำสั่งที่ address 1 ไปทำ address 3 เลย ต้องแก้ค่าอะไรของ PC?
5. CPU ของเรามีคำสั่ง 4 แบบ (LOAD/ADD/STORE/OUT) — ถ้าเป็น CPU จริงอย่าง x86 จะมีคำสั่งอีกมากมาย เช่น ลบ คูณ เปรียบเทียบ กระโดด ลองนึกดูว่าทำไม ISA ยิ่งมีคำสั่งเยอะ วงจร decode (Control Unit) ยิ่งซับซ้อนขึ้น

### ระดับ 2 — mini-project: เพิ่มคำสั่ง HALT ให้โปรแกรมหยุดได้

ใน CPU จิ๋วของเรา โปรแกรมจะวนซ้ำไม่รู้จบ (PC นับ `00→01→10→11→00→...` เพราะ 2 บิตวนกลับเอง) — สังเกตจากตาราง trace ว่า LED จะกลายเป็น `1010` (10) แล้ว `1101` (13) เพิ่มขึ้นเรื่อย ๆ เพราะโปรแกรมบวก 3 เพิ่มทุกรอบ

โจทย์: ออกแบบให้โปรแกรมหยุดได้จริง โดยทำข้อต่อไปนี้

1. **เพิ่มคำสั่งใหม่:** เราใช้ opcode 2 บิตหมดแล้ว (4 ค่า) — จงขยาย ISA: ถ้าเพิ่ม opcode เป็น 3 บิต จะมีคำสั่งได้กี่แบบ? (ใบ้: 3 บิตแทนค่าได้กี่ค่า)
2. **นิยาม HALT:** คำสั่ง HALT (หยุด = หยุดไม่ให้ PC เพิ่มอีก และตรึง LED ไว้) — จงกำหนด opcode ใหม่ให้ HALT แล้วเขียนความหมายลงในตาราง decode ของตัวเอง
3. **ต่อวงจร:** เพิ่มสัญญาณ `HALT` ใน Control Unit ให้มันไป "ตรึง" PC (เช่น ปิดทางที่ PC จะรับค่าใหม่ หรือปิด clock ของ PC) แล้วต่อให้ใช้งานได้จริง
4. **ทดสอบ:** เขียนโปรแกรม `LOAD 10 → ADD 11 → OUT → HALT` ลง RAM แล้วเดินเครื่องจน LED แสดง 7 แล้ว**ค้าง** (ไม่วนต่อ) — บันทึกตาราง trace ไว้

(ท้าทาย) ลองเขียนโปรแกรมที่คำนวณ `3 + 4 + 2` — ต้องใช้ RAM ข้อมูลเพิ่มอีกช่อง และต้องเห็นว่า ACC "สะสม" ผลอย่างไรในแต่ละก้าว

## สรุป

วันนี้เราเดินจาก "ชิ้นส่วนสองชิ้นที่นอนเฉย ๆ" ไปจนถึง "เครื่องที่รันโปรแกรมได้เอง" ครบเส้นทาง:

- **CPU** = กล่องที่วนลูป **fetch → decode → execute** ซ้ำไม่รู้จบ (machine cycle)
- **fetch** = อ่านคำสั่งจาก RAM ตาม address ที่ PC บอก → ใส่ IR → แล้ว PC + 1
- **decode** = Control Unit อ่าน opcode แล้วเปิดสัญญาณควบคุม (`_EN`) ให้ถูกเส้น
- **execute** = ALU / register / RAM ทำงานจริงตามสัญญาณ — ผลสะสมพักที่ ACC
- **คำสั่ง** = opcode (ทำอะไร) + operand (กับข้อมูลไหน) · ISA = พจนานุกรมคำสั่งของเครื่อง
- **PC (Program Counter)** = หัวใจของ "โปรแกรมไหล" — เครื่องฉลาดเพราะวนลูปโง่ ๆ ข้อเดียวนี้ซ้ำเร็ว ๆ

และจุดที่สำคัญที่สุดในเชิง "พื้นฐานที่แท้จริง": **สิ่งที่เราเขียนเป็นโค้ด Go ในตอน 03–07 ไม่ว่า `var`, `if`, `for`, `func` — ในที่สุดทั้งหมดถูกแปลง (compile) ให้กลายเป็นลำดับของ "เลข opcode" ที่ CPU จิ๋วตัวนี้วิ่ง fetch-decode-execute ทีละตัว** จากตอนนี้ไป เวลาโปรแกรม "ทำงาน" คุณจะเห็นภาพเบื้องหลัง: PC ชี้ไปเรื่อย ๆ, IR รับคำสั่ง, Control Unit เปิดสวิตช์, ALU คำนวณ, ACC เก็บผล — วนแบบนี้เป็นพันล้านครั้งต่อวินาที

ตอนต่อไปเราจะก้าวขึ้นมาอีกชั้น: **assembly** (ภาษาเครื่องที่คนอ่านออก) — เรียนว่าคำสั่ง `LOAD`/`ADD`/`STORE` เหล่านี้ เวลาเขียนด้วยภาษา LC-3 มันหน้าตาเป็นยังไง วน loop และเรียกฟังก์ชันในระดับนี้ได้ยังไง — ซึ่งก็คือ "คำสั่งที่ CPU ตัวที่เราเพิ่งสร้าง fetch-decode-execute" โดยตรงนั่นเอง
