# GC/runtime ของ Go — ทุกอย่างที่เรียนมาบรรจบกัน (ตอนที่ 31)

เราผ่านมา 30 ตอนแล้ว และตลอดทางเราเรียนเรื่องที่ดูเหมือนเป็น "ของคนอื่น" ไปเรื่อย ๆ — **memory** กับ **pointer** (ตอน 14–16) · **stack กับ heap** (ตอน 15) · **process, thread และการจัดคิว** (ตอน 18) · **syscall** ที่ข้ามเขตจากโปรแกรมไปหา kernel (ตอน 19) · **virtual memory** ที่ทำให้ทุกโปรแกรมเห็นหน่วยความจำเป็นของตัวเอง (ตอน 20) — แล้วก็เคยลงมือสร้าง **compiler กับ interpreter ของตัวเอง** ตั้งแต่ lexer ไปจนถึง codegen (ตอน 26–30)

ทุกเรื่องที่ว่ามาเคยเป็น "ทฤษฎีที่เราอ่านแล้วทำตาม" แต่มีที่ที่หนึ่งที่ทุกอย่างมาบรรจบกันจริง ๆ และเราสัมผัสมันทุกครั้งที่เขียนโปรแกรม Go โดยไม่รู้ตัว — ที่นั่นชื่อว่า **runtime**

ถ้าให้พูดสั้นที่สุด:

> การเขียน Go = เราเขียนแค่ "ตรรกะของงาน" ที่เหลือ (จองหน่วยความจำ, เก็บกวาดหน่วยความจำ, จัดคิวงานให้รันพร้อมกัน, คุยกับ kernel — แกนกลางของระบบปฏิบัติการที่คุมฮาร์ดแวร์และทรัพยากร) มี **runtime** คอยทำให้เบื้องหลังทั้งหมด

## 1. runtime คืออะไร — 'เพื่อน' ที่นั่งอยู่ใต้โปรแกรม Go

เริ่มจากคำศัพท์ก่อน เพราะคำว่า runtime มีหลายความหมาย และความหมายที่ใช้ในตอนนี้เฉพาะเจาะจง

> **runtime** (อ่านว่า รัน-ไทม์) ในความหมายของภาษาคอมพิวเตอร์ = **ชุดโค้ดที่ทำงาน "ระหว่างที่โปรแกรมกำลังรัน"** เพื่อดูแลสิ่งที่โปรแกรมเองไม่ต้องทำ เช่น จอง/คืนหน่วยความจำ, จัดคิวงานให้รันพร้อมกัน, หรือแปลงคำสั่งบางอย่างให้ kernel เข้าใจ — ตรงข้ามกับ **compile time** (คอมไพล์-ไทม์) = ช่วงเวลาที่ compiler แปลงซอร์สโค้ดของเราเป็นโค้ดเครื่อง ยังไม่มีอะไร "รัน" จริง
>
> **AOT (ahead-of-time)** = วิธีที่ compiler แปลโค้ดล่วงหน้าให้เสร็จก่อนรัน โปรแกรม Go ใช้วิธีนี้ — **runtime ของ Go ถูกคอมไพล์รวมเข้าไปในไบนารีทุกไฟล์** (ไฟล์ไบนารี = ไฟล์โปรแกรมที่เครื่องรันได้จริง) พอย้ายไฟล์โปรแกรมไปเครื่องอื่น ตัวรันไทม์ก็ไปด้วย ไม่ต้องติดตั้งอะไรเพิ่ม
>
> **VM (virtual machine)** = เครื่องเสมือน "อีกชั้น" ที่ค่อย ๆ แปลคำสั่งทีละบรรทัดตอนรัน (แบบที่ Java หรือ Python ทำ) Go **ไม่มี** ชั้นนี้ — มี runtime ที่ถูกคอมไพล์เข้าไปเป็นโค้ดเครื่องตรง ๆ เท่านั้น

### ทำไมเรื่องนี้สำคัญ — เทียบกับ C ตอนที่ 16

ย้อนกลับไปตอนที่ 16 เราลองเขียน C ที่จองหน่วยความจำด้วย `malloc` กับคืนด้วย `free` (ทบทวนตอน 14: `int *p` = ตัวแปร `p` ที่เก็บ "ที่อยู่" ของข้อมูลชนิด int ไม่ใช่ตัวข้อมูลเอง):

```c
/* C — เราเป็นคนสั่งทุกอย่าง */
int *p = malloc(sizeof(int));   /* ขอหน่วยความจำจาก heap เอง */
*p = 42;
free(p);                         /* และต้องคืนเอง ไม่งั้นรั่ว (leak) */
```

บรรทัด `free(p)` คือความรับผิดชอบทั้งหมดของเรา และตอนที่ 16 เราเห็นว่าเมื่อเราลืม (หรือคืนซ้ำ) เกิดอะไรขึ้น — หน่วยความจำรั่ว หรือโปรแกรมพังแบบหา bug ได้ยากเป็นชั่วโมง

Go เปลี่ยนความรับผิดชอบนี้: เราเขียน `x := 42` หรือ `make([]int, 3)` แล้ว **จบ** ไม่มี `free` ให้เรียก ไม่มีอะไรให้ลืม (ทบทวนตอน 15: `make([]int, 3)` = สร้าง slice ของ int ความยาว 3 — slice คือ "หน้าต่าง" ที่มองเข้าไปในอาร์เรย์) สิ่งที่มาแบกงานนี้แทนคือ runtime — และนี่คือของที่ตอนนี้เราจะแยกดูให้ชัด:

1. **memory allocator** — ตัวที่จัดหาหน่วยความจำเวลาเราใช้ `new` หรือ `make` (สิ่งที่ `malloc` ทำใน C)
2. **garbage collector (GC)** — ตัวที่ไล่หาว่าของชิ้นไหน "ไม่มีใครใช้แล้ว" แล้วคืนหน่วยความจำ (สิ่งที่ `free` ทำใน C — แต่ทำเองอัตโนมัติ)
3. **goroutine scheduler** — ตัวที่จับงานหลายพันชิ้น (goroutine = งานเบา ๆ ที่ runtime จัดคิวให้ — อธิบายเต็มในหัวข้อ 4) ไปกระจายลงเธรดของระบบ (OS thread) ที่มีอยู่จริงไม่กี่ตัว (เรื่องนี้เราเคยเห็น "thread จริง" มาแล้วในตอน 18)

ก่อนลงมือ มีอีกจุดที่ Go ต่างจากภาษา **managed runtime** ทั่วไป (managed runtime = ภาษาที่มีตัวจัดการหน่วยความจำให้เอง เช่น Java, C#, Python) และมันจะโผล่ชัดในหัวข้อถัดไป:

- **ให้ค่ามาก่อนที่อยู่ (value-oriented)**: ตัวแปรปกติเก็บ "ตัวข้อมูล" ไว้ในตัวเอง ไม่ใช่เก็บ "ที่อยู่ของข้อมูลที่อยู่บน heap" แบบที่ภาษา managed ส่วนใหญ่ทำ
- **เปิดให้ใช้ pointer เต็มที่**: รวมถึง pointer ที่ชี้เข้าไป "กลาง" object (บางภาษาซ่อนรายละเอียดนี้ไว้)
- **บอกได้ว่าเมื่อไรค่าจะถูกย้ายไป heap**: เราจะเห็นด้วยตาตัวเองผ่าน escape analysis ในหัวข้อ 2

### ลงมือทำ: โปรแกรมแรก — ส่องสิ่งที่ runtime ทำ

ก่อนจะลงลึกทีละชิ้น เรามาเขียนโปรแกรมสั้น ๆ ที่ดึงตัวเลขจริงจาก runtime ออกมาดู (ไฟล์ `05_converge/main.go`):

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/metrics"
	"unsafe"
)

// //go:noinline = ห้าม compiler ยุบฟังก์ชันนี้เข้าไปในที่เรียก (อธิบายเต็มที่หัวข้อ 2)
//go:noinline
func stackValue() int { return 7 }

//go:noinline
func heapValue() *int {
	x := 7
	return &x // คืน pointer ของตัวแปร local → x หนีไป heap
}

func main() {
	fmt.Printf("ขนาด pointer บน aarch64 = %d ไบต์\n", unsafe.Sizeof((*int)(nil)))
	fmt.Printf("ค่าที่อยู่บน stack       = %d\n", stackValue())
	fmt.Printf("ค่าที่อยู่บน heap        = %d\n", *heapValue())

	done := make(chan int)
	go func() { done <- stackValue() + *heapValue() }()
	fmt.Printf("ผลรวมจาก goroutine       = %d\n", <-done)

	runtime.GC()
	samples := []metrics.Sample{
		{Name: "/sched/gomaxprocs:threads"},
		{Name: "/sched/goroutines:goroutines"},
		{Name: "/memory/classes/heap/objects:bytes"},
		{Name: "/gc/cycles/total:gc-cycles"},
	}
	metrics.Read(samples)
	fmt.Println("\nสถานะ runtime ที่อ่านได้ (runtime/metrics):")
	fmt.Printf("  GOMAXPROCS (P)          = %d\n", samples[0].Value.Uint64())
	fmt.Printf("  goroutine ตอนนี้        = %d\n", samples[1].Value.Uint64())
	fmt.Printf("  heap objects (ไบต์)     = %d\n", samples[2].Value.Uint64())
	fmt.Printf("  GC cycles ทั้งหมด       = %d\n", samples[3].Value.Uint64())
	fmt.Printf("  NumCPU ที่ kernel เห็น  = %d\n", runtime.NumCPU())
}
```

อ่านโครงโปรแกรมนี้เป็นกลุ่ม:

- `package main` = ประกาศว่าไฟล์นี้เป็นโปรแกรมที่รันได้ (ไม่ใช่ไลบรารี) · `import (...)` = ยืมของจากแพ็กเกจมาตรฐาน 4 ตัวที่ไฟล์นี้ใช้
- `//go:noinline` = ห้าม compiler ยุบฟังก์ชันนี้เข้าไปในที่เรียก (รายละเอียดในหัวข้อ 2)
- `done := make(chan int)` = สร้าง "ท่อ" (channel) ไว้ส่งค่า int ระหว่าง goroutine — ดูกล่องด้านล่าง
- `go func(){ ... }()` = สั่งให้ฟังก์ชันนี้รันเป็นงานเบา ๆ แยกออกไป (goroutine) แล้วรับผลกลับด้วย `<-done`
- `runtime/metrics` = อ่าน "มิเตอร์" ของ runtime ตรง ๆ แทนการเดา

> **channel (แชนแนล) คืออะไร?** = "ท่อ" สื่อสารระหว่าง goroutine — ส่งค่าด้วย `ch <- v` และรับด้วย `v := <-ch` (ฝั่งรับจะ**รอ**จนกว่าจะมีค่าส่งมา) สร้างด้วย `make(chan int)` (ท่อที่ส่งค่า int) ตัวแปร `done` ในโค้ดข้างบนคือ channel ที่ใช้รับผลจาก goroutine

โปรแกรมนี้ใช้ของจากหลายตอนพร้อมกัน: `unsafe.Sizeof` วัดขนาด pointer (ตอน 14) — `unsafe` = แพ็กเกจสำหรับงานระดับล่างที่แตะหน่วยความจำตรง ๆ และ `nil` = ค่าว่างของ pointer · `*heapValue()` แตะค่าที่ runtime ย้ายไป heap · คำสั่ง `go` เปิด goroutine (ตอน 18) · และ `runtime/metrics` เป็นช่องทาง "อ่านมิเตอร์" ของ runtime ตรง ๆ

ผลรันจริงบนเครื่องนี้ (`out/05_converge.out.txt`):

```text
ขนาด pointer บน aarch64 = 8 ไบต์
ค่าที่อยู่บน stack       = 7
ค่าที่อยู่บน heap        = 7
ผลรวมจาก goroutine       = 14

สถานะ runtime ที่อ่านได้ (runtime/metrics):
  GOMAXPROCS (P)          = 4
  goroutine ตอนนี้        = 1
  heap objects (ไบต์)     = 90320
  GC cycles ทั้งหมด       = 1
  NumCPU ที่ kernel เห็น  = 4
```

อ่านได้ว่า:

- เครื่องนี้มี CPU 4 คอร์ และ kernel เห็น 4 คอร์
- runtime ตั้ง **GOMAXPROCS** (จำนวน "processor" ตรรกะที่จะดูในหัวข้อ 4) ไว้เท่ากับ 4
- ตอนนี้มี goroutine อยู่ 1 ตัว (คือตัว main)
- การเรียก `runtime.GC()` เมื่อกี้ทำให้ตัวนับ GC cycles ขึ้นเป็น 1 รอบ
- และ heap มี object รวมกัน 90,320 ไบต์

> ค่าตัวเลขทั้งหมดนี้ **เป็นค่าจากเครื่องนี้ ณ วินาทีที่รัน** — บางตัว (เช่น heap objects) ต่างกันได้ทุกครั้งแม้รันโปรแกรมเดิมซ้ำ สิ่งที่ไม่แปรผันคือ "หน้าตาของมิเตอร์" ที่ runtime เปิดให้อ่าน

## 2. stack กับ heap ใน Go — และคนที่ตัดสินใจให้เราชื่อ escape analysis

ย้อนไปตอนที่ 15 เราแยกสองคำนี้ออกจากกันแล้ว:

- **stack** (สแตก) = พื้นที่หน่วยความจำแบบ "ซ้อนจาน" ใช้เก็บตัวแปรชั่วคราวของฟังก์ชัน เป็นระเบียบ เข้าออกตามลำดับ จอง/คืนราคาถูกมาก — และที่สำคัญ **ถูกคืนให้อัตโนมัติทันทีที่ฟังก์ชัน return** ไม่มีอะไรต้องเก็บกวาด
- **heap** (ฮีป) = พื้นที่หน่วยความจำแบบ "คลังของ" จองได้ตอนไหนก็ได้ อยู่ได้นานเท่าที่ต้องการ แต่ต้องมีคนคอยบอกว่า "ชิ้นนี้ไม่ใช้แล้วนะ" ก่อนคืน

คำถามคือ: เวลาเราเขียน Go ตัวแปรหนึ่งตัว **อยู่ที่ไหน?** คำตอบสั้น ๆ คือ: **"compiler ตัดสินใจให้เองตอนคอมไพล์"** และการตัดสินใจนี้มีชื่อว่า **escape analysis** ("การวิเคราะห์การหลบหนี" — วิเคราะห์ว่าค่าหนึ่ง "หนี" ออกจากฟังก์ชันที่มันเกิดหรือเปล่า)

> **escape analysis** = การวิเคราะห์เชิงสถิติของ compiler ว่า ที่อยู่ (address) ของตัวแปรหนึ่ง จะถูกนำไปใช้ต่อ "หลัง" ฟังก์ชันที่ประกาศตัวแปรนั้น return ไปแล้วหรือไม่ ถ้าไม่ → ตัวแปรอยู่ stack ได้ปลอดภัย ถ้าใช่ → ตัวแปรนั้นต้องย้ายไปอยู่บน heap

ทำไมต้องสนใจ? เพราะสองที่นี้ราคาต่างกันมาก: ของที่อยู่ stack ถูกเก็บกวาด "ฟรี" ตอน return — ไม่มีงานให้ GC เลย ส่วนของที่อยู่ heap กลายเป็นภาระของ GC ตั้งแต่ถูกสร้างจนถูกเก็บ ค่าโดยสารที่เราเห็นในหัวข้อ 3 จะชัดเจนว่าต่างกันแค่ไหน

### กฎของ escape analysis

ตอนที่ 15 เราเห็นแล้วว่า stack เป็นระเบียบแบบ "ซ้อนจาน" — พอฟังก์ชัน return จานใบบนสุดถูกยกออก (ในภาษาของเรา: **frame** ถูกทำลาย) กฎจึงตรงไปตรงมา:

> **ถ้าที่อยู่ของตัวแปรหนึ่ง "มีชีวิตอยู่ต่อ" หลัง frame ของมันถูกทำลาย → ตัวแปรนั้นต้องอยู่บน heap**

กรณีที่ทำให้ "หนี" ได้บ่อย ๆ มี 3 แบบ: **(1)** คืน pointer ของตัวแปร local ออกไป (`return &x`) · **(2)** ยัดค่าลงใน interface (`any` = กล่องใส่ค่าได้ทุกชนิดของ Go) ซึ่งต้อง "ห่อ" ค่าไว้ที่อื่น · **(3)** เก็บค่าลงตัวแปรระดับ package (global = ตัวแปรระดับแพ็กเกจ ที่อยู่นานกว่าฟังก์ชัน)

### ลงมือทำ: สั่ง compiler ให้พูด (go build -gcflags='-m')

เครื่องมือที่ทำให้เรามองเห็นการตัดสินใจนี้คือ flag ของคอมไพเลอร์ `-gcflags='-m'` (อ่านว่า "ลบจีแฟลกส์ ลบเอ็ม") — `-m` = ให้ compiler พิมพ์ *optimization decisions* (คำอธิบายจริงจาก `go tool compile -h` ซึ่งระบุว่า `-m  print optimization decisions`) ซึ่งรวมผลของ escape analysis บอกว่าแต่ละค่าไปอยู่ที่ไหน

เรามีโปรแกรม `01_escape/main.go` ที่มีฟังก์ชันห้าตัว — สองตัวที่ตั้งใจให้อยู่ stack และสามตัวที่ตั้งใจให้หนีไป heap:

```go
// อยู่บน stack — คืน "ค่า" ออกไป ไม่มีใครถือที่อยู่ของ x ไว้
//
//go:noinline
func stayInt() int {
	x := 42
	return x
}

// หนีไป heap — คืน pointer ของตัวแปร local
//
//go:noinline
func escapeInt() *int {
	x := 42
	return &x
}

// อยู่บน stack — อาร์เรย์ขนาดคงที่ ใช้ในฟังก์ชันเดียว ไม่มีใครรับช่วงต่อ
//
//go:noinline
func staySlice() int {
	s := [3]int{1, 2, 3}
	return s[0] + s[1] + s[2]
}

// หนีไป heap — คืน slice ออกไป (backing array = อาร์เรย์ตัวจริงที่ slice ชี้เข้าไป ต้องอยู่ต่อ)
//
//go:noinline
func escapeSlice(n int) []int {
	s := make([]int, n)
	for i := range s {
		s[i] = i
	}
	return s
}

// หนีไป heap — ยัดค่าลง interface{}
//
//go:noinline
func escapeIface(n int) any {
	x := n * 2
	return x
}
```

(ใช้ `//go:noinline` กำกับเพื่อ "ห้าม compiler ยุบฟังก์ชันเข้าไปที่จุดเรียก" — ถ้าไม่กำกับ บางฟังก์ชันจะถูก inline และ escape analysis จะดูไม่ออกว่าใครเป็นต้นเหตุจริง ๆ)

สั่งให้ compiler พูดด้วยคำสั่ง:

```bash
go build -gcflags='-m' -o /dev/null ./01_escape
```

ข้อความจริงที่ได้บนเครื่องนี้ (`out/01_escape_gcflags_m.txt` — ตัดบรรทัด noise เรื่อง `fmt.Println`/inlining ที่ไม่เกี่ยวกับตัวแปรของเราออก):

```text
01_escape/main.go:19:2: moved to heap: x
01_escape/main.go:35:11: make([]int, n) escapes to heap
01_escape/main.go:47:9: x escapes to heap
```

อ่านทีละบรรทัด (เลข `19:2` = ไฟล์บรรทัดที่ 19 คอลัมน์ที่ 2):

- `moved to heap: x` — ตัวแปร `x` ใน `escapeInt` (บรรทัด 19) **ถูกย้ายไป heap** เพราะเราคืน `&x` ออกไป
- `make([]int, n) escapes to heap` — backing array (อาร์เรย์ตัวจริงที่ slice ชี้เข้าไป) ที่ `make` สร้างใน `escapeSlice` (บรรทัด 35) หนีไป heap เพราะ slice ถูกคืนออกไปข้างนอก
- `x escapes to heap` — ตัวแปร `x` ใน `escapeIface` (บรรทัด 47) หนีไป heap เพราะถูกยัดลง `any` แล้วคืนออกไป

และสังเกตสิ่งที่ **ไม่มี** ในข้อความ: ไม่มีบรรทัดไหนพูดถึง `stayInt` หรือ `staySlice` เลย — เพราะสองตัวนั้น compiler ตัดสินว่าอยู่ stack ได้ปลอดภัย ไม่ต้องย้ายไปไหน

![escape analysis: compiler ตัดสินเองว่าตัวแปรอยู่ stack หรือ heap](/assets/diagrams/ep31-02-escape-stack-heap.svg)

ผลรันของโปรแกรมนี้ (`out/01_escape.out.txt`) คือ `ผลรวมจากทุกฟังก์ชัน = 135` — ยืนยันว่าโปรแกรมทำงานถูกต้องเหมือนเดิม การย้ายของไป heap ไม่ได้เปลี่ยน "ความหมาย" ของโปรแกรมเลย มันเปลี่ยนแค่ "ที่อยู่" และ "ค่าโดยสารที่ต้องจ่ายให้ GC"

> **ทำไมต้องรู้เรื่องนี้?** เพราะการเขียน Go ให้ดีบ่อยครั้งไม่ใช่การเขียนให้ถูก แต่คือการเขียนให้ "ของไม่หนีไป heap โดยไม่จำเป็น" — ยกตัวอย่างจริง: ถ้าฟังก์ชันของคุณสร้าง slice สั้น ๆ แล้วคืนมันออกไปทั้งก้อนในลูปที่เรียกหลายล้านครั้ง คุณกำลังป้อนขยะให้ GC มหาศาล (หัวข้อ 3 จะวัดให้ดูเป็นตัวเลข)

สรุปสั้น ๆ ก่อนขึ้นหัวข้อ 3: escape analysis บอกเราว่า "ของชิ้นไหนถูกย้ายไป heap" — และของที่อยู่บน heap นั่นแหละคือของที่ **ต้องรอให้มีคนเก็บกวาด** นี่คือเหตุผลตรง ๆ ว่าทำไมเรื่องถัดไป (GC) จึงสำคัญกับเรา

## 3. garbage collector (GC) — ตัวเก็บกวาดที่ทำงานไปพร้อมกับโปรแกรม

### ปัญหา: เมื่อ heap ไม่มีเจ้าของ

สมมติเราจอง object บน heap ไปเรื่อย ๆ (สร้าง slice, struct, map) แล้ว "ปล่อย" มันไปโดยไม่เก็บ reference ไว้ (reference = ตัวอ้างถึง — ตัวแปรที่ชี้ไปยัง object นั้น) — หน่วยความจำก้อนนั้นยังถูกจองอยู่ แต่ไม่มีใครอ้างถึงแล้ว มันคือ **ขยะ (garbage)** ใน C เราต้องเป็นคนเรียก `free` เอง (ตอน 16) ซึ่งพลาดง่ายมาก

Go แก้ปัญหานี้ด้วย **garbage collector** — โปรแกรมย่อยที่คอยหาว่า object ชิ้นไหน "เอื้อมไม่ถึงแล้ว" (unreachable = ไม่มีเส้น pointer ใด ๆ จากตัวแปรที่ยังมีชีวิตพาไปถึง) แล้วคืนหน่วยความจำนั้นกลับมาใช้ใหม่

> **ห้ามสับสน:** GC เก็บกวาดเฉพาะของบน **heap** เท่านั้น ของบน stack ถูกคืนอัตโนมัติตอนฟังก์ชัน return อยู่แล้ว (นี่คือเหตุผลที่หัวข้อ 2 สำคัญ — ของที่อยู่ stack ช่วยให้ GC ทำงานน้อยลง)

### วิธีทำงาน: mark-and-sweep แบบ tri-color

GC ของ Go ใช้วิธีที่เรียกว่า **mark-and-sweep** ("ทำเครื่องหมายแล้วกวาด") และทำเครื่องหมายแบบ **tri-color** ("สามสี") ภาพจำง่าย ๆ คือแท็กสีสามสีบน object ทุกชิ้น:

- **ขาว (white)** = ยังไม่ถูกตรวจ — ยังไม่รู้ว่าตายหรืออยู่
- **เทา (gray)** = อยู่ในคิว กำลังจะไล่ตรวจลูกของมัน
- **ดำ (black)** = ตรวจครบแล้ว และที่ยัง "ขาว" อยู่เมื่อจบรอบ = ขยะ

![GC ของ Go: mark-and-sweep แบบ tri-color ที่ทำงานไปพร้อมกับโปรแกรม](/assets/diagrams/ep31-03-tricolor-gc.svg)

หนึ่งรอบ GC มีสี่ขั้น (ภาพข้างบนอธิบายไว้):

1. **STW สั้น ๆ ก้อนแรก — sweep termination**: หยุดทุกอย่างชั่วคราวเพื่อ "ปิด sweep ของรอบก่อน" ให้เรียบร้อย แล้ว "เตรียมราก" (root — ตัวแปร global และ stack ของทุก goroutine) เพื่อเริ่มรอบใหม่
2. **เทา → ดำ — concurrent mark**: เริ่มจากตั้ง object ที่มีเส้น pointer ตรงจาก "ราก" ให้เป็นสีเทา แล้วไล่ตามเส้น pointer ของ object สีเทา จัดลูกที่ยังขาวให้กลายเป็นเทา (ขั้นนี้ทำงาน **คู่ขนาน** ไปกับโปรแกรมของเรา)
3. **STW สั้น ๆ อีกครั้ง — mark termination**: ปิดงานทำเครื่องหมายให้แน่นอน
4. **sweep**: object ที่ยังเหลือสีขาว = ไม่มีใครอ้างถึง → คืนหน่วยความจำกลับมาใช้ใหม่

> **STW (stop-the-world)** = ช่วงเวลาที่ GC สั่ง "หยุดทุกอย่าง" ให้โปรแกรมของเราหยุดชั่วคราวเพื่อจัดฉาก คำว่า "ชั่วคราว" ใน Go สั้นมาก ๆ — ระดับ **หลักไมโครวินาที** (ไมโครวินาที = 1 ในล้านของวินาที) ส่วนงานเก็บกวาดจริง ๆ เกือบทั้งหมดทำ "ไปพร้อมกับโปรแกรม" นี่คือจุดที่ Go ลงทุนมหาศาล และเป็นสิ่งที่ทำให้ Go ต่างจาก GC รุ่นเก่า ๆ ที่หยุดโปรแกรมนาน ๆ

`GOMAXPROCS` ที่เราเห็นในหัวข้อ 1 เป็นตัวเลข **processor (P)** ของ Go — และ gctrace จะโชว์ค่านี้ท้ายบรรทัดว่า `4 P` นั่นคือจำนวน P ที่ runtime ใช้ในรอบนั้น (คำว่า processor (P) จะอธิบายเต็ม ๆ ในหัวข้อ 4 — ตอนนี้อ่านว่า "ที่ทำงานตรรกะ" ไปก่อน)

### ลงมือทำ: ดู GC ทำงานจริงด้วย GODEBUG=gctrace=1

Go เปิดช่องให้เรา "ดม" GC ได้ด้วยตัวแปรแวดล้อม **GODEBUG** และค่า `gctrace=1` — ทุกครั้งที่ GC ทำงานหนึ่งรอบ มันจะพิมพ์บรรทัดสรุปออกมา

> **ตัวแปรแวดล้อม (environment variable)** = ค่าตั้งต้นที่เราส่งให้โปรแกรมจาก "นอก" โปรแกรม ตอนสั่งรัน (`GODEBUG=gctrace=1 ./โปรแกรม`) โดยไม่ต้องแก้โค้ดเลย

โปรแกรม `02_gc_trace/main.go` ทดลองสามอย่าง: **(1)** สั่ง `runtime.GC()` ให้เก็บกวาดเดี๋ยวนี้เลย · **(2)** จัดสรร 2 MiB (MiB = เมกะไบต์แบบไบนารี, 1 MiB ≈ 1 ล้านไบต์) จำนวน 30 ก้อนเก็บ reference ไว้ (ของยังไม่ตาย) — ในโค้ด `keep := make([][]byte, 0, 30)` คือ slice ของ `[]byte` ที่เริ่มยาว 0 แต่ **จองความจุ 30** ไว้ล่วงหน้า · **(3)** ปิด GC ชั่วคราวด้วย `debug.SetGCPercent(-1)` (ค่า `-1` = ปิด GC) แล้วจัดสรรก้อนใหญ่ 64 MiB — แล้วเปิดกลับ

```go
// [1] สั่งเก็บกวาดเดี๋ยวนี้เลย (block รอจนเสร็จ)
runtime.GC()

// [2] จัดสรร 2 MiB จำนวน 30 ก้อน · เก็บ reference ไว้ (ของยังไม่ตาย)
keep := make([][]byte, 0, 30)
for i := 0; i < 30; i++ {
	keep = append(keep, alloc(2))
}

// [3] ปิด GC ชั่วคราว แล้วจัดสรรก้อนใหญ่
old := debug.SetGCPercent(-1)
fmt.Printf("ค่า GCPercent เดิม = %d\n", old)
big := alloc(64)

// เปิดกลับ + สั่งเก็บกวาด
debug.SetGCPercent(old)
runtime.GC()
```

> **`alloc(mib)` ทำงานอะไร?** = สร้าง `[]byte` ขนาด `mib` MiB แล้ว "แตะ" ทุกหน้าหน่วยความจำทีละ 4096 ไบต์ (`for i := 0; i < len(b); i += 4096 { b[i] = byte(i) }`) เพื่อบังคับให้หน่วยความจำจริงถูกใช้ ไม่ใช่แค่ "จอง" ไว้เฉย ๆ — จึงเห็นตัวเลข heap ขยับจริง

รันด้วยคำสั่ง (คอมไพล์เป็น binary ก่อน เพื่อให้ GODEBUG มีผลเฉพาะโปรแกรมของเรา ไม่ไปปนกับตัว `go` ที่กำลังคอมไพล์):

```bash

GODEBUG=gctrace=1 ./bin/02_gc_trace
```

ส่วนท้ายบรรทัดบอกขนาด heap: `60->60->0 MB` — อ่านสามค่าตามลำดับ:

- ค่าแรก = heap ตอน GC เริ่ม
- ค่ากลาง = heap ตอน GC จบ
- ค่าสุดท้าย = heap ที่ยังมีชีวิตอยู่จริง (ไลฟ์)

สังเกตบรรทัด `gc 6`: ก่อน GC heap อยู่ที่ 60 MiB พอเก็บกวาดเสร็จเหลือ **0 MB** เพราะเราปล่อย `keep = nil` ไปหมดแล้ว GC จึงเก็บได้ทั้งหมด (คำว่า `(forced)` ท้ายบรรทัดคือสัญญาณว่ารอบนั้นเกิดจากคำสั่ง `runtime.GC()` ของเรา ไม่ใช่จาก GC ตัดสินใจเอง)

และตัวเลขที่ควรจำที่สุดสำหรับมือใหม่คือ **`pause รวม 0.171 ms`** — นี่คือเวลาที่โปรแกรม "หยุดจริง ๆ" รวม **ทั้งโปรแกรม** (7 รอบ GC) ไม่ใช่ต่อครั้ง สองส่วนในสิบของมิลลิวินาที นี่คือเหตุผลที่คนพูดกันว่า GC ของ Go เหมาะกับงานที่ต้องการหยุดน้อย ๆ

### ตัวเลขที่ 2: จ่ายแพงแค่ไหนเมื่อเราสร้างขยะเยอะ

คิดต่อจากหัวข้อ 2 ว่า "ของที่หนีไป heap มีราคา" — โปรแกรม `04_alloc_compare` วัดให้เห็นชัด ๆ ด้วยการเทียบสองวิธีทำงาน **เดียวกันเป๊ะ** (ได้ checksum เท่ากัน — checksum = ค่าตรวจสอบผลลัพธ์ ถ้าคำนวณตรงกันจะได้ค่าเดียวกัน) ต่างกันแค่ "จัดสรรหน่วยความจำยังไง": วิธีหนึ่งจองใหม่ทุกรอบ (เกิดขยะ) อีกวิธีใช้บัฟเฟอร์เดิมซ้ำ (ไม่เกิดขยะ)

```go
// วิธี 1: จองใหม่ทุกครั้ง → ขยะเต็มไปหมด
func allocFresh(sz int) uint64 {
	var sink uint64
	for i := 0; i < iters; i++ {
		b := make([]byte, sz) // ← หัวใจ: make ใหม่ทุก iteration
		b[0] = byte(i)
		b[sz-1] = byte(i >> 8)
		sink += uint64(b[0]) + uint64(b[sz-1])
	}
	return sink
}

// วิธี 2: ใช้บัฟเฟอร์เดิมซ้ำ → แทบไม่เกิดขยะ
func reuseBuf(buf []byte) uint64 {
	var sink uint64
	n := len(buf)
	for i := 0; i < iters; i++ {
		buf[0] = byte(i) // ← เขียนทับบัฟเฟอร์เดิม
		buf[n-1] = byte(i >> 8)
		sink += uint64(buf[0]) + uint64(buf[n-1])
	}
	return sink
}
```

> อธิบายตัวแปรในโค้ด: `iters` = จำนวนรอบ (กำหนดไว้ 200,000) · `uint64` = เลขจำนวนเต็ม 64 บิตแบบไม่คิดเครื่องหมาย (ใช้เป็นที่พักค่าผลรวม) · `sink` = ตัวแปรรับผลสะสม — หัวใจคือต้อง "ใช้" ค่าที่คำนวณได้ทุกครั้ง ไม่งั้น compiler อาจมองว่าโค้ดไร้ผลแล้วตัดทิ้ง

รัน 200,000 รอบ ก้อนละ 512 ไบต์ สลับ alloc/reuse อย่างละสองครั้ง ผลจริง (`out/04_alloc_compare.out.txt`) — ในผลรัน `µs` = ไมโครวินาที และ `MiB` = เมกะไบต์แบบไบนารี (1 MiB ≈ 1 ล้านไบต์):

```text
ทดสอบ 200000 รอบ · ก้อนละ 512 ไบต์ · สลับวิธีจัดสรร (alloc = จองใหม่, reuse = ใช้ซ้ำ)

alloc  | เวลา 39.341ms     | GC เพิ่ม 31 รอบ | จัดสรรสะสม   97.7 MiB | heap ล่าสุด   2.8 MiB | checksum=50582176
reuse  | เวลา 347µs        | GC เพิ่ม  0 รอบ | จัดสรรสะสม    0.0 MiB | heap ล่าสุด   0.1 MiB | checksum=50582176
alloc  | เวลา 51.544ms     | GC เพิ่ม 11 รอบ | จัดสรรสะสม   97.7 MiB | heap ล่าสุด   1.7 MiB | checksum=50582176
reuse  | เวลา 350µs        | GC เพิ่ม  0 รอบ | จัดสรรสะสม    0.0 MiB | heap ล่าสุด   0.1 MiB | checksum=50582176

รวมทั้งโปรแกรม: GC ทำงาน 47 รอบ · จัดสรรสะสม 195.4 MiB · pause รวม 1.786 ms
```

เทียบกันจะ ๆ: **alloc** จัดสรรสะสม 97.7 MiB และทำให้ GC ทำงานเพิ่ม 31 รอบ ใช้เวลา ~39 ms · **reuse** จัดสรรสะสม 0.0 MiB GC ทำงานเพิ่ม **0 รอบ** ใช้เวลา ~347 ไมโครวินาที — เร็วกว่ากันราว **ร้อยเท่า** ทั้งที่คำนวณผลออกมา checksum เดียวกันเป๊ะ

นี่คือ "ค่าโดยสาร" ของการสร้างขยะ: ไม่ใช่แค่หน่วยความจำ แต่คือ **เวลา CPU ที่ GC ต้องเอาไปใช้เก็บกวาด** — ซึ่งกินเวลาเดียวกับที่โปรแกรมของเราอยากใช้ทำงานจริง

> **จ่ายให้เป็น:** งานที่ต้องทำซ้ำ ๆ ในลูปหนัก ๆ (ประมวลผลไฟล์, parse ข้อมูล = แปลงข้อความดิบให้เป็นข้อมูลที่โปรแกรมใช้ต่อได้, เขียน server ที่รับ request ต่อเนื่อง = โปรแกรมฝั่งให้บริการที่รับ "คำขอ" จากผู้ใช้ทีละคำขอ) ถ้า reuse บัฟเฟอร์ได้ก็ควรทำ — และ `sync.Pool` ของ Go ถูกออกแบบมาเพื่อ "ยืม-คืนบัฟเฟอร์ข้ามงาน" พอดี (ดู mini-project ท้ายบท)

### ตัวปรับที่ควรรู้: GOGC และ runtime.GC()

- **`GOGC`** = ตัวแปรแวดล้อมที่ตั้ง "เป้า" ว่าเมื่อ heap โตขึ้นกี่เปอร์เซ็นต์จากรอบก่อน GC จะทำงานรอบใหม่ ค่าเริ่มต้นคือ `GOGC=100` แปลว่า "เมื่อจัดสรรของใหม่เพิ่มเป็น **สองเท่า** ของของที่ยังมีชีวิตอยู่ → เก็บกวาด" ตั้งเป็น `off` คือปิด GC ทั้งหมด (อันตราย ใช้ตอน debug เท่านั้น)
- **`debug.SetGCPercent(p)`** = ปรับค่าเดียวกันนี้ตอนรัน — ในผลรันของเรา `SetGCPercent(-1)` คืนค่าเดิม `100` ออกมาให้เห็น (ค่าเริ่มต้นคือ 100 จริง) แล้วเราคืนค่ากลับทันที
- **`runtime.GC()`** = สั่ง "เก็บกวาดเดี๋ยวนี้เลย" (block รอจนเสร็จ) — ใช้ในที่ที่เรารู้จังหวะที่เหมาะ เช่นหลังปลดของชุดใหญ่ หรือตอนเริ่ม benchmark (benchmark = การวัดเวลา/ทรัพยากรของโปรแกรมอย่างเป็นระบบ) — โปรแกรม `04` เรียกมันก่อนวัดทุกครั้งเพื่อให้ทั้งสองวิธีเริ่มจากสภาพเดียวกัน

## 4. goroutine scheduler — goroutine หลายพันบนเธรดไม่กี่ตัว (โมเดล M:N)

ย้อนไปตอนที่ 18 อีกครั้ง: **thread (เธรด)** ของระบบปฏิบัติการมี **ของจริงใน kernel** แต่เป็นของ "หนัก" — สร้างมีค่าใช้จ่าย สลับกันมีค่าใช้จ่าย และมีหน่วยความจำของตัวเองจำนวนหนึ่ง ถ้าเราลองสร้าง thread จริงหลายพันตัวพร้อมกัน ระบบจะเริ่มหายใจไม่ออก

Go แก้ปัญหานี้ด้วยแนวคิด **goroutine** (กอ-รูทีน) — งานที่ "เบา" กว่ามากและจัดการโดย runtime เอง ไม่ใช่ kernel สิ่งที่ทำให้เบาและยังรันพร้อมกันได้คือโมเดลที่เรียกว่า **M:N scheduling**

> **M:N scheduling** = การจับงานจำนวน **N** ชิ้น (goroutine เยอะมาก) ไปรันบนเธรดของระบบจำนวน **M** ตัว (น้อย) โดยมีตัวกลางคอยจัดคิว ต่างจากโมเดล 1:1 ที่งาน 1 ชิ้น = thread 1 ตัว (แล้วก็สร้างได้ไม่เยอะ)

ตัวกลางนั้นมีชื่อว่า **P** และเป็นตัวที่เรามองไม่เห็นเลยในโค้ด — สรุปตัวย่อสามตัวที่ต้องรู้ (ภาพข้างล่างจะเห็นทั้งสาม):

- **G (goroutine)** = งานของเรา หนึ่ง `go func()` = หนึ่ง G ถูกจัดให้เบามาก
- **M (machine → OS thread)** = เธรดของระบบ "ของจริง" ที่ kernel เห็น
- **P (processor)** = "ที่ทำงานตรรกะ" จำนวนเท่ากับ **GOMAXPROCS** พอดี (เอกสารภายในของ runtime ระบุไว้ตรง ๆ ว่า *"There are exactly GOMAXPROCS Ps"* — แปลว่า "มี P อยู่เท่ากับ GOMAXPROCS พอดี")

![goroutine M:N scheduler — หลายพัน G บนไม่กี่ M โดยมี P เป็นตัวกลาง](/assets/diagrams/ep31-04-goroutine-mn.svg)

### ลงมือทำ: วัดด้วยตาตัวเอง

โปรแกรม `03_goroutines` สร้าง goroutine 5,000 ตัวให้ค้าง (blocked) พร้อมกัน — ทุกตัวรันงานเล็ก ๆ ให้แตะ stack ตัวเอง แล้วค้างรอสัญญาณเดียวกัน จากนั้นวัดจำนวนและหน่วยความจำจริง แล้วลองบังคับ `GOMAXPROCS = 1`

```go
const n = 5000

gate := make(chan struct{})
var wg sync.WaitGroup
var started atomic.Int64

for i := 0; i < n; i++ {
	wg.Add(1)
	go func(idx int) {
		defer wg.Done()
		_ = localWork(idx)  // แตะ stack ของตัวเอง แล้วจึงค้าง
		started.Add(1)
		<-gate              // ทุกตัวค้างรอสัญญาณเดียวกัน → ยังมีชีวิตอยู่
	}(i)
}
for started.Load() < int64(n) { // รอให้ทุกตัวได้รันจริงก่อนวัด
	runtime.Gosched()
}
```

> อธิบายของที่ใช้ในบล็อกนี้ (อ่านทีละบรรทัด):
> - `sync.WaitGroup` = ตัวนับ "รอกี่งาน": `wg.Add(1)` เพิ่มงานก่อน spawn (สปอว์น = สร้าง/ปล่อย goroutine) · `defer wg.Done()` ลดเมื่อ goroutine จบ · `wg.Wait()` รอให้ครบ
> - `defer` = สั่งให้เรียกฟังก์ชันนี้ "ตอนฟังก์ชันจบ" (ไม่ว่าจบทางไหน) จึงเหมาะกับการคืนงานให้ WaitGroup
> - `atomic.Int64` = ตัวนับที่ปลอดภัยเมื่อหลาย goroutine เพิ่มค่าพร้อมกัน (`started.Add(1)` / `started.Load()`) — กัน race condition
> - `<-gate` = ค้างรอรับค่าจาก channel `gate` (ในโค้ดสร้างด้วย `make(chan struct{})` — channel ที่ไม่ส่งค่าใด ๆ เพราะ `struct{}` เป็นชนิดเปล่าขนาด 0 ใช้เป็นสัญญาณล้วน ๆ) ทำให้ goroutine ไม่จบ จึงยังมีชีวิตอยู่ให้วัด
> - `runtime.Gosched()` = "ปล่อยคิว" ให้ goroutine อื่นได้รัน ใช้ในลูป busy-wait (ลูปที่วนเช็คซ้ำ ๆ โดยไม่ปล่อยให้งานอื่นได้รัน)
> - `localWork(idx)` = ฟังก์ชันที่แตะ stack ของ goroutine ตัวเอง (เขียนอาร์เรย์ 1 KiB) เพื่อให้วัดหน่วยความจำได้จริง

ผลรันจริง (`out/03_goroutines.out.txt`):

```text
จุดเริ่ม · GOMAXPROCS = 4 · NumCPU = 4 · NumGoroutine = 1
spawn goroutine 5000 ตัว → NumGoroutine = 5001 (main + 5000)
หน่วยความจำ heap ที่เพิ่มขึ้น ≈ 0.62 KiB ต่อ goroutine หนึ่งตัว (ค่าจากเครื่องนี้)
ทำงานจบทุกตัว → NumGoroutine = 1

ตั้ง GOMAXPROCS = 1 (เดิม 4) — เธรดที่รันโค้ด Go พร้อมกันเหลือ 1 ตัว
NumGoroutine ตอนนี้ = 5001 (ยังสร้างครบ แม้มี P เดียว)
คืนค่า GOMAXPROCS = 4 · NumGoroutine สุดท้าย = 1
```

อ่านตัวเลขจากผลรัน:

- สร้าง goroutine 5,000 ตัว → `NumGoroutine` ขยับเป็น **5,001** (นับ main ด้วย)
- หน่วยความจำที่เพิ่มขึ้นวัดได้ราว **0.62 KiB ต่อ goroutine หนึ่งตัว** (KiB = กิโลไบต์แบบไบนารี · ค่าจากเครื่องนี้ ณ วินาทีนั้น เป็นการวัดแบบ "เหมารวมจากส่วนที่เพิ่มขึ้นจริง" ไม่ใช่ค่าทางทฤษฎี)
- และที่สำคัญที่สุด: เราบังคับ `GOMAXPROCS = 1` แล้ว goroutine ทั้ง 5,000 ตัวก็ **ยังสร้างและรันได้ครบ** — นี่คือหลักฐานว่า "งาน" (G) กับ "เธรด" (M) ไม่ใช่สิ่งเดียวกัน

> **0.62 KiB ต่อตัวคืออะไร?** คือหน่วยความจำที่เพิ่มขึ้นโดยเฉลี่ยจากการมี goroutine ค้างอยู่เพิ่มหนึ่งตัวบนเครื่องนี้ ตีความแบบใช้งานจริงได้ว่า "goroutine ถูกกว่าการสร้าง thread ของระบบมาก" — คุณจึงสร้างมันเป็นพัน ๆ ตัวได้โดยไม่ต้องกลัวว่าระบบจะพังก่อน

> **บางครั้งเราตั้ง `GOMAXPROCS` เองได้** — ตัวควบคุมคือ `runtime.GOMAXPROCS(n)` ถ้าไม่ตั้ง Go จะเลือกให้เท่ากับจำนวน CPU ที่ kernel เห็น (`runtime.NumCPU()`) ในเครื่องนี้คือ 4 (หมายเหตุ Go 1.25 ขึ้นไป: ค่าเริ่มต้นเปลี่ยนเป็น *container-aware* — มองจำนวน CPU ที่ container ถูกจำกัดไว้ด้วย ไม่ใช่แค่ `NumCPU` ของทั้งเครื่อง บทความนี้รันบน Go 1.24.4 จึงได้ค่าเท่ากับ `NumCPU`) งานที่ต้องใช้ CPU หนัก ๆ ควรได้ P เท่าจำนวนคอร์จริง แต่ goroutine ที่รอ I/O (อ่านไฟล์/เน็ต) จะไม่กิน P ตอนรอ — นี่คือเหตุผลที่ "งานคนละแบบ" อยู่รวมกันได้

## 5. บรรจบกัน — runtime ประกอบจากทุกอย่างที่เราเรียนมา

ถึงตรงนี้ลองมองย้อนกลับไปที่ 30 ตอน จะเห็นว่า runtime ของ Go ไม่ใช่ "ของวิเศษ" แต่คือการเอาความรู้ที่เราเรียนมาแต่ละชิ้นมาประกอบเข้าด้วยกัน:

| สิ่งที่เรียน (ตอน) | ไปปรากฏที่ไหนใน runtime |
|---|---|
| memory, pointer, ตัวแปร (14) | allocator จัดก้อนหน่วยความจำให้ `new`/`make` · pointer 8 ไบต์บน aarch64 |
| stack vs heap + calling convention (15) | escape analysis ตัดสินว่าไปอยู่ที่ไหน · stack ของ goroutine |
| malloc/free และกับดักหน่วยความจำ (16) | GC มารับหน้าที่ `free` ให้อัตโนมัติ — แต่ขยะเยอะก็จ่ายแพง (วัดได้ในหัวข้อ 3) |
| process, thread, scheduling (18) | goroutine = งานเบา · M = OS thread จริง · P = ตัวจัดคิว (โมเดล M:N) |
| syscall user/kernel (19) | runtime เรียก kernel แทนเราเวลาขอหน่วยความจำจริง/สร้าง thread จริง |
| virtual memory, paging (20) | heap/stack ที่ runtime จัดให้ "นั่งอยู่บน" หน่วยความจำเสมือนที่ kernel ดูแล |
| compiler/interpreter ที่เราสร้าง (26–30) | compiler ของ Go ก็เดินต้นไม้ตัดสินใจคล้ายที่เราทำ — escape analysis คือ "การวิเคราะห์" อีกชั้นหนึ่ง |

ตามที่สัญญาไว้ในตอนที่ 30 ("ตอนที่ 31 เราจะเดินต่อจากตรงนี้สู่เรื่องสุดท้ายของระยะนี้") — ตอนนี้เราเดินครบแล้ว ก่อนปิดระยะนี้ด้วย capstone project (capstone project = โครงงานปิดท้ายที่รวมทุกอย่างไว้ — ตอนที่ 32) ลองย้ำภาพเดียวให้ติดหัว:

> **runtime = ตัวจัดการ memory (ตอน 14–16) + ตัวจัดคิวงาน (ตอน 18) + virtual memory (ตอน 20) + syscall (ตอน 19) ที่รวมกันเป็นเครื่องเดียว และถูกคอมไพล์เข้าไปในไบนารีทุกตัว**

และทั้งหมดนี้ทำงาน "โดยที่เราไม่ต้องเขียนสั่ง" — เราเขียนแค่ `x := 42`, `make(...)`, `go func(){...}` แล้วปล่อยให้เครื่องจักรที่ผ่านการกลั่นจากภาษา C มาทั้งชีวิตหลังนี้ทำงานของมัน

## สรุป

- โปรแกรม Go ทุกตัวมี **runtime** แนบมาด้วย (คอมไพล์เข้าไบนารี AOT) ทำหน้าที่สามอย่าง: จัดสรรหน่วยความจำ, เก็บกวาดหน่วยความจำ, จัดคิวงาน
- **escape analysis** ให้ compiler ตัดสินว่า object อยู่ stack (ฟรี) หรือหนีไป heap (มีค่าใช้จ่าย) — เห็นได้ด้วย `go build -gcflags='-m'` ข้อความ `escapes to heap` / `moved to heap`
- **GC** เป็น mark-and-sweep แบบ tri-color ที่ทำงาน "ไปพร้อมกับโปรแกรม" — STW สั้นระดับไมโครวินาที · ดูได้ด้วย `GODEBUG=gctrace=1` · วัดค่าโดยสารของขยะด้วยการเทียบ alloc vs reuse
- **goroutine scheduler** ใช้โมเดล M:N — G หลายพันบน M ไม่กี่ตัวโดยมี P (เท่า GOMAXPROCS) เป็นตัวกลาง
- สรุปสุดท้าย: runtime = ทุกอย่างที่เรียนมาใน 30 ตอน ประกอบเป็นเครื่องเดียว

### ระดับ Drill (ฝึกมือ)

1. รัน `go build -gcflags='-m' -o /dev/null ./01_escape` แล้วดูว่ามีบรรทัดที่พูดถึง `escapes`/`moved to heap` กี่บรรทัด และแต่ละบรรทัดตรงกับฟังก์ชันไหน (เฉลย: `out/01_escape_gcflags_m.txt`)
2. เรียก `runtime.GC()` หนึ่งครั้ง แล้ว `NumGC` เพิ่มขึ้นกี่รอบ?
3. สร้าง goroutine 100 ตัวให้ค้างพร้อมกัน แล้ว `runtime.NumGoroutine()` ได้เท่าไร (นับ main ด้วยไหม)?
4. `runtime.GOMAXPROCS(0)` กับ `runtime.NumCPU()` บนเครื่องนี้ได้เท่าไร? สองค่านี้ควรเท่ากันไหม?
5. ค่า `GCPercent` เริ่มต้น (ที่มาจาก `GOGC`) ของ Go คือเท่าไร?

### Mini-project (ต่อยอดจากโปรแกรมในตอนนี้)

ทำสองอย่างเรียงจากง่ายไปยาก:

1. **เพิ่มวิธี "pool" ให้ `04_alloc_compare`** — ตอนนี้เราวัดสองวิธี (alloc vs reuse) ให้เพิ่มวิธีที่สามที่ใช้ `sync.Pool` ยืม-คืนบัฟเฟอร์ (อ่าน doc ของ `sync.Pool` ประกอบ — จุดสำคัญคือต้อง `Put` บัฟเฟอร์คืนทุกครั้ง แล้วรัน `bash run_all.sh` เทียบ GC rounds ของสามวิธีว่าต่างกันอย่างไร)
