# Turing machine + halting problem — อะไรที่คอมพิวเตอร์ทำไม่ได้ (ตอนที่ 24)

ยินดีต้อนรับกลับมา ตอนนี้เรายืนอยู่ที่ **ตอนสุดท้ายของระยะที่ 5** (ทฤษฎีการคำนวณ) — ระยะที่เราถอยออกมาจากการเขียนโปรแกรม แล้วถามคำถามที่ลึกที่สุดข้อหนึ่งของศาสตร์นี้ว่า

> **คอมพิวเตอร์ "ทำอะไรได้" กับ "ทำอะไรไม่ได้" กันแน่?**

สองตอนที่แล้วเราเดินบันไดขึ้นมาแล้วสองขั้น:

- **ตอนที่ 22** — **finite automaton** (FA): เครื่องที่มีแค่ "สถานะจำนวนจำกัด" ไม่มีที่จำอะไรเพิ่มเลย มันจึง**นับไม่ได้** (จำ "วงเล็บเปิดค้างกี่ตัว" ไม่ได้)
- **ตอนที่ 23** — **pushdown automaton** (PDA): เอา FA ไปแปะ **stack** (กอง) เข้าหนึ่งกอง มันก็เริ่ม "นับ" ได้ รับภาษาอย่าง `aⁿbⁿ` หรือ "วงเล็บสมดุล" ได้แล้ว

คืนนี้เราจะขึ้นบันไดขั้นสุดท้าย รู้จักเครื่องที่ถูกยกให้เป็น "นิยามที่แม่นยำของคำว่า คอมพิวเตอร์" — ชื่อ **Turing machine** แล้วใช้มันตอบคำถามสุดท้ายของระยะนี้:

(ชื่อมาจาก **Alan Turing** นักคณิตศาสตร์ชาวอังกฤษ ผู้คิดค้นแนวคิดนี้ขึ้นในปี 1936 — *ก่อน*ที่คอมพิวเตอร์อิเล็กทรอนิกส์เครื่องแรกจะถูกสร้างขึ้นเสียอีก)

> **มีปัญหาที่ "ไม่มีทาง" เขียนโปรแกรมแก้ได้ไหม?** คำตอบคือ *มี* — และปัญหาที่โด่งดังที่สุดชื่อ **halting problem** (ปัญหาการหยุด: "โปรแกรมนี้จะวนไม่รู้จบหรือเปล่า") เราจะพิสูจน์ให้เห็นว่ามันแก้ไม่ได้จริง ๆ

คืนนี้เราจะเขียนโค้ด Go ทั้งหมด 5 โปรแกรม (รันจริงบน Raspberry Pi 5) ตั้งแต่ซิมูเลเตอร์ (โปรแกรมจำลองการทำงานของเครื่อง) ของ Turing machine ที่ตัดสินภาษา `aⁿbⁿcⁿ` (ภาษาที่ PDA ทำไม่ได้) ไปจนถึงการพิสูจน์ว่า "ตัวตรวจว่าหยุดไหม" ที่สมบูรณ์แบบ**ไม่มีอยู่จริง** ทุกตัวเลขในบทความนี้มาจากการรันจริง เก็บไว้ที่ `course/code/ep24/out/` และรันซ้ำได้หมดด้วย `bash run_all.sh` (ลำดับหัวข้อไม่ตรงเลขโปรแกรมเป๊ะ เพราะเรียงตามเนื้อเรื่อง ไม่ใช่เลขไฟล์ — อย่าเพิ่งงง)

## 0. ทวนความจำ 30 วินาที: บันไดสองขั้นที่ผ่านมา

ก่อนขึ้นขั้นสุดท้าย ขอทวนภาพรวมสั้น ๆ (ถ้าเพิ่งมา ตอนที่ 22–23 ปูพื้นฐานเต็ม ๆ ไว้แล้ว):

- **FA (finite automaton)** = สถานะจำกัด + ลูกศรเปลี่ยนสถานะ **ไม่มีหน่วยความจำเพิ่ม** รับได้แต่ "regular language" (ภาษาปกติ — ภาษาที่ตรวจได้ด้วยสถานะจำกัดล้วน ๆ) เช่น `a*b` (ตัว `a` กี่ตัวก็ได้ แล้วตามด้วย `b` ตัวเดียว)
- **PDA (pushdown automaton)** = FA + **stack** หนึ่งกอง (โครงสร้าง "เข้าก่อนออกทีหลัง" เหมือนกองจาน) รับได้ "context-free language" (ไวยากรณ์นอกบริบท) เช่น วงเล็บสมดุล, `aⁿbⁿ`

ข้อจำกัดของ PDA คือ stack ของมัน **มีแค่ "ด้านบน" กองเดียว** — ใส่ได้จากด้านบน หยิบได้จากด้านบนเท่านั้น มัน "อ่านตรงกลาง" ของสิ่งที่จำไว้ไม่ได้ และที่สำคัญคือมันอ่าน input (ข้อมูลที่ป้อนเข้าเครื่อง) **ทางเดียว** (ซ้ายไปขวา) **ย้อนกลับไม่ได้** **เขียนทับไม่ได้**

สองข้อจำกัดนี้แหละคือสิ่งที่ทำให้มันแพ้ภาษา `aⁿbⁿcⁿ` (ตัว `a` `b` `c` อย่างละ n ตัว) — เพราะต้องเทียบจำนวน **สาม** กลุ่มพร้อมกัน แต่ stack เดียวเทียบได้แค่ **ทีละคู่** (หลักฐานเชิงตัวเลขอยู่ที่โปรแกรม 05 ของตอนนี้เอง: PDA เทียบได้ทีละคู่ ผิดกลยุทธ์ละ 9/64 ขณะที่ TM ผิด 0/64)

คำถามคืนนี้: แล้วถ้าเราให้เครื่องมี "หน่วยความจำที่เข้าถึงตรงไหนก็ได้ แก้ไขตรงไหนก็ได้ เดินย้อนกลับได้" — มันจะเก่งขึ้นอีกแค่ไหน?

## 1. Turing machine — เอาทุกข้อจำกัดของ PDA ออกให้หมด

ลองจินตนาการเครื่องที่เรียบง่ายที่สุดที่ "แก้ทุกข้อจำกัด" ของ PDA:

1. **หน่วยความจำ = เทป (tape) อนันต์** — แถบยาวไม่สิ้นสุดทั้งสองข้าง แบ่งเป็นช่อง (cell) ช่องละหนึ่งสัญลักษณ์
2. **หัวอ่าน/เขียน (head)** — ชี้อยู่ช่องเดียวในแต่ละขณะ แต่**เขียนทับ**ช่องนั้นได้ แล้ว**เลื่อนซ้ายหรือขวา**ได้อิสระ (ไม่ถูกบังคับให้อ่านซ้ายไปขวาทางเดียวอีกแล้ว)
3. **สมอง = สถานะจำนวนจำกัด** (finite control) — เหมือนเดิม กับ **ตารางเปลี่ยนสถานะ** (transition table) ที่บอกว่า "ถ้าอยู่สถานะ X แล้วอ่านสัญลักษณ์ Y → เขียนทับด้วย Z, เลื่อนหัวไปทาง L/R, ไปสถานะ W"

เท่านี้แหละ — ไม่มีจอ ไม่มีคีย์บอร์ด ไม่มีระบบไฟล์ แค่ "เทป + หัวอ่าน + สถานะ" แต่นักทฤษฎีพิสูจน์แล้วว่าเครื่องแค่นี้ **คำนวณได้ทุกอย่างที่คอมพิวเตอร์จริงคำนวณได้** (แนวคิดนี้เรียกว่า **Church–Turing thesis** — เป็น "สมมติฐาน" ที่วงการยอมรับกันทั่ว ไม่ใช่ทฤษฎีบทที่พิสูจน์ได้ แต่ยังไม่มีใครหาตัวอย่างค้านได้เลยตั้งแต่ปี 1936)

![Turing machine = สถานะจำกัด + เทปไม่จำกัด + หัวอ่านที่เขียนทับและเดินสองทาง](/assets/diagrams/ep24-01-tm-machine.svg)

ดูภาพประกอบ (ภาพที่ 1) ให้เห็นองค์ประกอบครบทั้งสามส่วน: **เทป** (แถบช่องไม่สิ้นสุด, `_` = ช่องว่าง), **finite control** (กล่องสถานะ 9 ช่อง = 7 สถานะทำงาน + qaccept + qreject พร้อมจำนวนกฎของแต่ละสถานะ), และ **ตารางเปลี่ยนสถานะ** ตัวอย่าง 8 จาก 32 กฎ — ตัวเลขทุกตัวในภาพดึงมาจากผลรันจริงของโปรแกรม 01 ที่เรากำลังจะเขียน

**ตารางเปลี่ยนสถานะอ่านยังไง** — แต่ละบรรทัดมี 5 ส่วน อ่านว่า:

> อยู่สถานะ `[1]` อ่าน `[2]` → เขียนทับด้วย `[3]` เลื่อนหัวไป `[4]` แล้วไปสถานะ `[5]`

เช่น `q0 a X R q1` แปลว่า "อยู่สถานะ q0 อ่าน `a` → เขียน `X` ทับ → เลื่อนหัว**ขวา** (R) → ไปสถานะ q1"

(ทิศทางการเลื่อนมี 3 แบบ: `L` = ซ้าย, `R` = ขวา, `N` = ไม่เลื่อน — ตัวหลังใช้ตอนเครื่องจบงานแล้ว ไม่ต้องไปไหนต่อ)

## 2. โปรแกรม 01 — เขียน Turing machine ที่ตัดสิน aⁿbⁿcⁿ

มาพิสูจน์กันด้วยโค้ดว่า Turing machine เก่งกว่า PDA จริง ภาษาเป้าหมายของเราคือ

> `L = { aⁿbⁿcⁿ | n ≥ 1 }` = `"abc"`, `"aabbcc"`, `"aaabbbccc"`, …

โจทย์คือตอบว่า "สตริง (แถวตัวอักษร) นี้อยู่ในภาษาไหม" (มี `a` `b` `c` อย่างละเท่ากัน และเรียงตามลำดับนี้)

**กลยุทธ์ของเครื่อง** (เรียบง่ายมาก ใช้ของที่ PDA ไม่มี คือ "เขียนทับ" + "เดินย้อนกลับ"):

1. เดินขวาจากซ้ายสุด หา `a` ตัวแรกที่ยังไม่ถูกแตะ → เขียน `X` ทับ (= "นับแล้ว 1 ตัว")
2. เดินขวาต่อ หา `b` ตัวแรกที่ยังไม่ถูกแตะ → เขียน `Y` ทับ
3. เดินขวาต่อ หา `c` ตัวแรกที่ยังไม่ถูกแตะ → เขียน `Z` ทับ
4. เดิน**กลับซ้าย**จนสุด แล้วเริ่มรอบใหม่
5. ถ้า `a` หมดแล้ว (เจอ `Y` แทน) → เดินขวาตรวจว่ายังมี `b` หรือ `c` ที่ยังไม่ถูกทำเครื่องหมายเหลือไหม — มี = จำนวนไม่เท่า → ปฏิเสธ · ไม่มี = ครบ → ยอมรับ

เราใช้ `X` `Y` `Z` เป็น "สัญลักษณ์ทำเครื่องหมายแล้ว" ของ `a` `b` `c` ตามลำดับ — เทคนิคนี้ทำได้เพราะหัวอ่าน**เขียนทับได้** (PDA ทำไม่ได้ เพราะมันได้แต่ push/pop)

โค้ดส่วนตารางเปลี่ยนสถานะ (ไฟล์เต็มมี 32 กฎ อยู่ใน `01_tm_anbncn/main.go`):

```go
// กลยุทธ์: ทำเครื่องหมาย a→X, b→Y, c→Z ทีละรอบ แล้วกวาดกลับ
// (tm.NewRule(สถานะ, อ่าน, เขียน, เลื่อน, สถานะถัดไป) = หนึ่งบรรทัดของตารางเปลี่ยนสถานะ)
var anbncnRules = []tm.Rule{
    tm.NewRule("q0", 'a', 'X', tm.R, "q1"), // เจอ a ตัวแรก → ทำเป็น X
    tm.NewRule("q1", 'a', 'a', tm.R, "q1"), // เดินขวาผ่าน a ที่เหลือ
    tm.NewRule("q1", 'Y', 'Y', tm.R, "q1"), // และผ่าน b ที่ทำแล้ว (Y)
    tm.NewRule("q1", 'b', 'Y', tm.R, "q2"), // เจอ b ตัวแรก → ทำเป็น Y
    tm.NewRule("q2", 'b', 'b', tm.R, "q2"), // เดินขวาผ่าน b ที่เหลือ
    tm.NewRule("q2", 'Z', 'Z', tm.R, "q2"), // และผ่าน c ที่ทำแล้ว (Z)
    tm.NewRule("q2", 'c', 'Z', tm.R, "q3"), // เจอ c ตัวแรก → ทำเป็น Z
    tm.NewRule("q3", 'c', 'c', tm.R, "q3"), // เดินขวาผ่าน c ที่เหลือ
    tm.NewRule("q3", '_', '_', tm.L, "q4"), // สุดสตริง → ถอยซ้าย
    tm.NewRule("q4", 'X', 'X', tm.R, "q5"), // กลับถึง X → หันขวา (เริ่มรอบใหม่)
    // … กฎที่เหลือ (ตรวจความถูกต้อง + ทางออกของ input ที่ผิดรูป) อยู่ในไฟล์จริง
}
```

หัวใจของซิมูเลเตอร์ (ไฟล์ `tm/tm.go`) สั้นมาก — มันคือ **loop** (การวนซ้ำคำสั่งเดิมจนกว่าเงื่อนไขจะพาออก) ไม่กี่บรรทัดที่ "อ่าน→เขียน→เลื่อน→เปลี่ยนสถานะ" วนไป (`break` = ออกจาก loop ทันที):

```go
for {
    if state == m.Accept { break }   // จบที่สถานะรับ = ยอมรับ
    if state == m.Reject { break }   // จบที่สถานะปฏิเสธ = ปฏิเสธ
    sym := tape[head]                // อ่านช่องที่หัวชี้อยู่ตอนนี้
    rule, ok := m.RuleAt(state, sym) // หากฎตาม (สถานะ, สัญลักษณ์)
    if !ok { break }                 // ไม่มีกฎให้ทำต่อ = เครื่อง "หยุด" ทันที
    tape[head] = rule.Write          // 1) เขียนทับช่องปัจจุบัน
    // 2) เลื่อนหัว (L ซ้าย / R ขวา) แล้ว 3) เปลี่ยนสถานะ
    head += moveDelta(rule.Move)
    state = rule.Next
}
```

ลองรันเครื่องกับ input `"abc"` แล้วดูมันเดินทีละก้าว (คัดเฉพาะบรรทัดสำคัญจากผลรันจริง):

```
--- เดินทีละก้าว: "abc" ---
ก้าว  สถานะ  อ่าน  เขียน  เลื่อน  → สถานะ   เทป (หัวอ่านใน [ ])
0     q0     a     X      R       q1        _ _ _ _ [X] b c _ _ _ _
1     q1     b     Y      R       q2        _ _ _ X [Y] c _ _ _ _
2     q2     c     Z      R       q3        _ _ X Y [Z] _ _ _ _
3     q3     _     _      L       q4        _ X Y Z [_] _ _ _ _   ← สุดสตริงแล้ว ถอยกลับ
4–5   q4     …     …      L       q4        (กวาดกลับซ้ายผ่าน Z Y)
6     q4     X     X      R       q5        _ _ _ _ [X] Y Z _ _ _ _   ← กลับถึง X หันขวา
7–8   q5→q6  Y/Z   Y/Z    R       …         (เดินขวาตรวจ Y Z ที่เหลือ)
9     q6     _     _      N       qaccept    _ X Y Z [_] _ _ _ _   ← ตรวจครบ → ยอมรับ
สรุป: ยอมรับ · จำนวนก้าว 10 · เทปสุดท้าย: _ X Y Z [_] _
```

สังเกตสิ่งที่ PDA ทำไม่ได้เลย: หัวอ่าน **ถอยกลับซ้าย** (ก้าว 3→4) และ **เขียน `a` ทับเป็น `X`** — สองความสามารถนี้คือกุญแจที่ทำให้ Turing machine ขึ้นบันไดขั้นสุดท้ายได้

เครื่องตัวนี้เราทดสอบกับ 13 สตริง (ตั้งแต่ `"abc"` ไปจนถึงของผิดรูปอย่าง `"abcabc"`, `"aaabbbcc"`) **ตอบถูกหมด 13/13** และเราเช็กด้วยว่า `aabbcc` ใช้ 29 ก้าว `aaabbbccc` ใช้ 58 ก้าว — จำนวนก้าวโตตามสูตร **5n² + 4n + 1** ตรงกับผลรันจริง **8/8 ค่า** (แปลว่า: input ยาวขึ้น n เท่า เครื่องต้องทำงานหนักขึ้นราว ๆ n² เท่า — เพราะต้อง "กวาดกลับไปกลับมา" หลายรอบ)

## 3. โปรแกรม 02 — palindrome: เห็น "เดินสองทาง + เขียนทับ" ชัด ๆ

เพื่อให้เห็นสองความสามารถนั้นชัดขึ้น มาดูเครื่องอีกตัวที่ทำโจทย์คลาสสิกอีกข้อ:

> **palindrome** = สตริงที่อ่านจากหน้าไปหลังได้ความหมายเดียวกับอ่านจากหลังมาหน้า (เช่น `"aba"`, `"abba"`, `"abbba"` เหนือตัวอักษร `{a, b}`)

**กลยุทธ์** (ตรงไปตรงมา สอนให้เห็นกลไกชัด ๆ):

1. ลบตัว**ซ้ายสุด**ทิ้ง (เขียน `_` ทับ) แล้ว**จำ**ไว้ว่ามันคือ `a` หรือ `b`
2. เดิน**ขวา**จนสุดสตริง แล้วถอยกลับมาหนึ่งช่อง (ตัวขวาสุด)
3. เทียบตัวขวาสุดกับตัวที่จำไว้ — ตรงกัน → ลบทิ้งแล้วเดิน**กลับซ้าย**ไปเริ่มรอบใหม่ · ไม่ตรง → ปฏิเสธ
4. ถ้าถึงช่องว่างตั้งแต่ต้น (ไม่มีตัวเหลือ) = palindrome

โค้ดส่วนตารางเปลี่ยนสถานะ (ใน `02_tm_palindrome/main.go`):

```go
var palRules = []tm.Rule{
    tm.NewRule("q0", 'a', '_', tm.R, "qA"),      // ลบตัวซ้ายสุด + จำว่า 'a'
    tm.NewRule("q0", 'b', '_', tm.R, "qB"),      // ลบตัวซ้ายสุด + จำว่า 'b'
    tm.NewRule("q0", '_', '_', tm.N, "qaccept"), // ไม่มีตัวเหลือ = palindrome
    tm.NewRule("qA", 'a', 'a', tm.R, "qA"),      // เดินขวาผ่านตัวที่ยังเหลือ
    tm.NewRule("qA", 'b', 'b', tm.R, "qA"),
    tm.NewRule("qA", '_', '_', tm.L, "qAcmp"),   // สุดสตริง → ถอย 1 ช่อง
    tm.NewRule("qAcmp", 'a', '_', tm.L, "qback"), // ตัวขวาสุด = 'a' ตรงกัน → ลบ + ถอยกลับ
    tm.NewRule("qAcmp", 'b', 'b', tm.N, "qreject"), // ไม่ตรง → ปฏิเสธ
    // … (กฎของฝั่ง b และการถอยกลับอยู่ในไฟล์จริง)
}
```

จุดที่เราอยากเน้น: เครื่องนี้**เขียนทับได้** (ลบตัวอักษรด้วย `_`) และ**เดินย้อนกลับ**ได้ (ไปขวา แล้วถอยซ้าย แล้วไปขวาอีก) — หลักฐานจากผลรันจริงกับ `"abba"`: ใช้ 15 ก้าว, เลื่อนขวา 8 ครั้ง, เลื่อนซ้าย 6 ครั้ง, **กลับทิศ 4 ครั้ง** (PDA เลื่อนซ้ายได้ 0 ครั้งเสมอ เพราะมันอ่านทางเดียว)

แล้วเรา "พิสูจน์ว่ามันถูก" ยังไง? วิธีคือ**แจกแจงครบ** — สร้างสตริงเหนือ `{a, b}` **ทุกสตริง**ยาว 1 ถึง 12 ตัว (รวม `2¹ + 2² + … + 2¹² = 8,190` สตริง) แล้วเทียบคำตอบของเครื่องกับ **oracle** (โปรแกรมที่กลับสตริงแล้วเทียบตรง ๆ ไม่ได้ใช้ Turing machine เลย) ผลคือ:

```
สตริงที่ทดสอบทั้งหมด 8190 เส้น (ยาว 1-12 เหนือ {a,b})
ไม่ตรงกับ oracle 0 เส้น · ชนเพดานก้าว (ค้าง) 0 เส้น
สูตร (n+1)(n+2)/2 ถูกในเส้นที่ยอมรับ 252 เส้น · ผิด 0 เส้น
```

(บรรทัด "252 เส้น" = จำนวนสตริง palindrome ที่ยาว 1–12 ตัวทั้งหมด; สูตร `(n+1)(n+2)/2` ทำนายจำนวนก้าวของเครื่องตรงกับผลรันจริงทั้ง 252 เส้น ผิด 0 เส้น)

"ไม่ตรง 0, ค้าง 0" = เครื่องถูกต้อง **และ** ไม่มีทางวนไม่รู้จบ (เครื่องนี้เป็น **decider** = "ตัวตัดสิน" ที่ทุก input จบในจำนวนก้าวจำกัดเสมอ) — คำว่า decider จะกลับมามีความหมายสำคัญตอนหัวข้อ 8

## 4. โปรแกรม 05 (ตอนที่ 1) — เครื่องจักรสากล: "โปรแกรม" กลายเป็น "ข้อมูล"

มีแนวคิดหนึ่งที่ Turing machine ทำให้เป็นไปได้ และเป็นรากฐานของคอมพิวเตอร์ทุกเครื่องที่เราใช้อยู่:

> **เครื่องจักรสากล (universal machine)** = Turing machine ตัวเดียวที่รันเครื่องอื่นได้ทุกเครื่อง

ฟังดูเหมือนเวทมนตร์ แต่ทำได้ง่ายมาก: เราแยก "ตัวรัน" (ซิมูเลเตอร์) ออกจาก "นิยามเครื่อง" (ตารางเปลี่ยนสถานะ) แล้วส่งนิยามเครื่องเข้าไปเป็น **ข้อมูล** — เหมือนที่ interpreter (โปรแกรมที่รันโปรแกรมอื่นทีละบรรทัด) รับไฟล์โค้ดเข้าไปรัน

ไฟล์นิยามเครื่องของเราเป็นข้อความล้วน ๆ (`machines/*.tm`):

```
# นิยามเครื่อง Turing machine — ข้อมูล ไม่ใช่โค้ด
name anbncn
blank _
start q0
accept qaccept
reject qreject
rule q0 a X R q1
rule q1 a a R q1
...
```

ซิมูเลเตอร์ตัวเดียวอ่านไฟล์นี้แล้วรันได้ — เรามีไฟล์นิยาม 3 ไฟล์ (`anbncn.tm`, `palindrome.tm`, `walkright.tm`) ที่รันด้วยซิมูเลเตอร์ตัวเดียวกัน:

```
--- รันด้วยซิมูเลเตอร์ตัวเดียวกัน ---
เครื่อง      input    ผลจริง   ควรเป็น   ตรงไหม
anbncn      aabbcc   accept   true      true
anbncn      aabc     reject   false     true
palindrome  abba     accept   true      true
palindrome  abab     reject   false     true
anbncn      abc      accept   true      true
ตรงกับที่ควรเป็น 5 จาก 5 เคส
```

**บทเรียน:** ทุก interpreter, VM (เครื่องเสมือน เช่น JVM ของ Java), JIT compiler (ตัวแปลโค้ดแบบ "แปลแล้วรันทันที") ที่เราใช้กัน — ทั้งหมดคือ "เครื่องจักรสากล" ในร่างต่าง ๆ กัน นี่คือเหตุผลที่ Turing machine ถูกยกเป็นนิยามของ "คอมพิวเตอร์" เพราะมันจับ "โปรแกรมเป็นข้อมูลได้" ตรงกับเครื่องจริงทุกเครื่อง

## 5. แล้ว "โปรแกรมนี้จะหยุดไหม" ล่ะ — คำถามที่ตอบไม่ได้

ทีนี้มาถึงหัวใจของตอนนี้ เราเห็นแล้วว่าเครื่องจักรสากลรันเครื่องอะไรก็ได้ ลองคิดโจทย์ต่อไปนี้:

> รับโปรแกรม P กับ input x มา แล้วตอบว่า **"P จะหยุดเมื่อรันกับ x ไหม"** (หรือจะวนไปเรื่อย ๆ ไม่มีวันจบ)

ปัญหานี้ชื่อ **halting problem** ฟังดูเป็นโจทย์ที่ "น่าจะเขียนโปรแกรมตอบได้" — คอมไพเลอร์ (compiler) ก็เตือนเราเรื่อง infinite loop (การวนไม่รู้จบ) อยู่ไม่ใช่เหรอ?

ลองดูว่า "ตัวตรวจ" ในชีวิตจริงทำได้แค่ไหน (โปรแกรม 04 สร้างตัวตรวจ 2 ชั้นเหมือน compiler กับ IDE — โปรแกรมเขียนโค้ดครบชุด — ที่เราใช้จริง):

```go
func detect(m *tm.Machine, input string, budget int) verdict {
    // ชั้นที่ 1 (โครงสร้าง): "ไม่หยุดแน่นอน" ต้องไม่มีกฎไปรับ/ไปปฏิเสธเลย
    //                       และไม่มีสถานะไหน "ตัน" (ทุกสถานะมีกฎครบทุกสัญลักษณ์)
    reachesAccept, reachesReject := false, false
    for _, r := range m.Rules {
        if r.Next == m.Accept { reachesAccept = true }
        if r.Next == m.Reject { reachesReject = true }
    }
    if !reachesAccept && !reachesReject && !canStuck(m) {
        return neverHalt // โครงสร้างยืนยันได้: วนตลอด ไม่มีทางหยุด
    }
    res := m.Run(input, budget, 0)   // ชั้นที่ 2: รันจริงแบบจำกัดก้าว
    switch res.Status {
    case tm.Accepted:  return willHalt
    case tm.StepLimit: return dontKnow // ยังไม่หยุดภายในเพดาน → ตอบ "ไม่รู้"
    }
    return willHalt                    // ตัน หรือปฏิเสธ ก็คือ "หยุด" ทั้งคู่
}
```

ตัวตรวจนี้ตอบได้**แน่นอน**แค่สองอย่าง — "หยุด" (เมื่อรันถึงสถานะรับภายในเพดาน) และ "ไม่หยุด" (เมื่อโครงสร้างยืนยันว่าไม่มีทางหยุด) — ส่วนที่เหลือตอบ **"ยังไม่รู้"** และนี่คือรอยร้าว:

![ตัวตรวจ "หยุดไหม": ทุกเพดานมีโปรแกรมที่หลบได้ · และตัวตรวจสมบูรณ์ไม่มีอยู่จริง](/assets/diagrams/ep24-04-halting-limits.svg)

ภาพที่ 4 แสดงกับดัก: เครื่อง counter (เดินขวาผ่าน `0` ไปเรื่อย ๆ เจอ `1` แล้วหยุด) กับ input `"0"×B + "1"` (`B` = จำนวนตัว `0` ซึ่งเราตั้งให้เท่ากับเพดานก้าวของตัวตรวจ) จะหยุดที่ก้าว **B+1 พอดี** — ตัวตรวจที่ตั้งเพดาน B ก้าวจึงตอบ "ยังไม่รู้" เสมอ ส่วนตัวตรวจที่ตั้ง B+1 ก้าวตอบได้ทันที:

```
เพดาน B   หยุดที่ก้าว   ตัวตรวจ(B)   ตัวตรวจ(B+1)   ตัวตรวจ(B) ตัดสินได้ไหม
10        11          ยังไม่รู้     หยุด (ยืนยันได้)  ไม่ได้
100       101         ยังไม่รู้     หยุด (ยืนยันได้)  ไม่ได้
1000      1001        ยังไม่รู้     หยุด (ยืนยันได้)  ไม่ได้
10000     10001       ยังไม่รู้     หยุด (ยืนยันได้)  ไม่ได้
100000    100001      ยังไม่รู้     หยุด (ยืนยันได้)  ไม่ได้
```

**อ่านให้ดี:** ตัวตรวจไม่ได้ "ตอบผิด" — มันตอบ "ยังไม่รู้" ตรงที่เพดานไม่พอ แล้วเพิ่งตอบได้เมื่อเพดานใหญ่ขึ้น ปัญหาคือ **ต่อให้เพิ่มเพดานเท่าไร ก็มีโปรแกรมที่ "หยุดช้ากว่านั้น" อยู่เสมอ** ไม่มีเพดานใดใช้ได้กับทุกโปรแกรม

มีกรณีจริงที่ "ยังไม่มีใครรู้คำตอบ" ด้วยซ้ำ — **Collatz** (โปรแกรม: ถ้า x คี่ → x = 3x+1, ถ้าคู่ → x = x/2, หยุดเมื่อ x = 1): สแกน n = 1 ถึง 1,000,000 พบว่าจำนวนก้าวมากสุดคือ 524 ก้าว (ที่ n = 837,799) และ n = 27 ใช้ 111 ก้าว — แต่ **ยังไม่มีใครพิสูจน์ได้ว่าทุก n หยุดเสมอ** มันเป็นโจทย์คณิตศาสตร์ที่เปิดค้างมานานเกือบศตวรรษ

## 6. พิสูจน์: ตัวตรวจสมบูรณ์ไม่มีอยู่จริง

แต่ "ยังไม่รู้ตอนนี้" กับ "ไม่มีทางรู้เลย" มันคนละเรื่องกัน ทัวริงพิสูจน์ข้อหลังไว้ — ต่อไปคือการพิสูจน์ที่สวยที่สุดบทหนึ่งของวิทยาการคอมพิวเตอร์ ใช้แนวคิดง่าย ๆ แค่ **การอ้างถึงตัวเอง**:

ก่อนอื่นต้องปูพื้นหนึ่งอย่าง: จากหัวข้อ 4 เรารู้ว่าโปรแกรมส่ง**โค้ดของโปรแกรม**เข้าเป็น input ได้ (เครื่องจักรสากล) — หมายความว่าโปรแกรมหนึ่งสามารถส่ง "โค้ดของตัวมันเอง" ไปเป็น input ของอีกโปรแกรมได้ด้วย

สมมติว่า **มี** โปรแกรม `H` ที่ตอบถูกทุก (โปรแกรม, input) — ไม่จำกัดเวลา ไม่มีเพดานก้าว ตอบ "หยุด" หรือ "ไม่หยุด" ได้แม่นเสมอ

แล้วสร้างโปรแกรม `D` ที่ทำแบบนี้: `D` ถาม `H` ว่า "ตัว D เอง รันกับ input 0 แล้วหยุดไหม" แล้ว**ทำตรงกันข้าม**กับคำตอบ

ดูสองกรณี (ไม่มีกรณีที่สาม):

- **กรณี 1:** `H` ตอบว่า "D หยุด" → `D` ต้องทำตรงกันข้าม = **วนไม่รู้จบ** → แต่ `H` เพิ่งบอกว่า D หยุด ✗ **ขัดแย้ง**
- **กรณี 2:** `H` ตอบว่า "D ไม่หยุด" → `D` ต้องทำตรงกันข้าม = **หยุดทันที** → แต่ `H` เพิ่งบอกว่า D ไม่หยุด ✗ **ขัดแย้ง**

ทั้งสองกรณีขัดแย้งกันเอง แปลว่า **สมมติฐาน "มี H" เป็นเท็จ** — ตัวตรวจการหยุดที่สมบูรณ์แบบ**ไม่มีอยู่จริง** นี่คือ halting problem: "โปรแกรมนี้หยุดไหม" เป็นปัญหาที่ **ตัดสินไม่ได้ (undecidable)**

**แล้วทำไม compiler/IDE ยังทำงานอยู่ทุกวัน?** เพราะมันไม่พยายาม "ตอบให้ครบทุกกรณี" — มันทำได้แค่ (1) ยืนยัน "หยุด" เมื่อรันสั้นพอ, (2) ยืนยัน "ไม่หยุด" เฉพาะรูปแบบที่รู้จัก, (3) ที่เหลือตอบ "ยังไม่รู้" แล้วปล่อยผ่าน เรามีหลักฐานจริง: โปรแกรมที่วนไม่รู้จบ (`for {}` เปล่า ๆ) ผ่าน `go vet` (ตัวตรวจโค้ดของ Go) และ `go build` (คำสั่งคอมไพล์) อย่างสะอาด **ไม่มีคำเตือน** — แล้วพอรันจริง `timeout` ต้องสั่งฆ่าที่ 3 วินาที (exit code 124):

```
-- go vet ./probe/loop_forever --
go vet: ผ่าน ไม่มีคำเตือน (exit 0)
-- go build ... --
go build: สำเร็จ ไม่มีคำเตือน (exit 0)
-- รันจริง (บังคับจบด้วย timeout 3 วินาที) --
โปรแกรมนี้จะวนไม่รู้จบ (ไม่มีการเปลี่ยนสถานะเลย)
exit code = 124  (124 = timeout สั่งฆ่า เพราะโปรแกรมไม่ยอมจบเอง)
```

**ไม่มีเครื่องมือไหนตรวจจับ infinite loop ได้ครบทุกแบบ — พิสูจน์แล้วว่าทำไม่ได้**

## 7. โปรแกรม 03 — ทำไมต้อง "มีปัญหาที่แก้ไม่ได้": การทแยงกลับด้าน

การพิสูจน์ข้างบน "อ้างถึงตัวเอง" ฟังดูเป็นเทคนิคเฉพาะกิจ แต่จริง ๆ มันมีรากที่ลึกกว่า — เรียกว่า **diagonalization** (การทแยง) คิดค้นโดยนักคณิตศาสตร์ Georg Cantor ตั้งแต่ปี 1891 ทัวริงแค่เอามาปรับใช้ โปรแกรม 03 ทำให้เราเห็นรากนั้นกับตา

เริ่มจาก**กลุ่มโปรแกรม**เล็ก ๆ ที่ควบคุมได้ครบ (เรียกว่า "โปรแกรมตัวนับ") ซึ่งแต่ละตัวง่ายมาก:

- มี**ตัวแปร** (ช่องเก็บค่า) ตัวเดียวชื่อ `x` และ**คำสั่ง**เดียว: `x = (x + a) mod m` (`mod` = หารเอาเศษ เช่น `7 mod 3 = 1`) · หยุดเมื่อ `x = 0`
- `a` กับ `m` คือค่าคงที่ที่ต่างกันในแต่ละโปรแกรม — `a ∈ {1,2,3,4}` (`∈` = "เป็นหนึ่งใน") และ `m ∈ {6,8}` → รวมกันได้ 8 โปรแกรม

แล้วสร้าง **ตารางการหยุด**: ช่อง `T[i][j]` = "โปรแกรม i หยุดไหมเมื่อเริ่มด้วย x = j" — ทุกช่องมาจากการรันจริง:

![ตารางการหยุด (halting table) + เส้นทแยงกลับด้าน](/assets/diagrams/ep24-03-halting-table.svg)

ภาพที่ 3: ตาราง 8×8 (เขียว = หยุด, แดง = ไม่หยุด) แล้วเราทำสิ่งนี้กับมัน:

1. ลาก**เส้นทแยง** `T[0][0], T[1][1], …` (ช่องกรอบน้ำเงิน)
2. สร้างแถว `D` โดย**กลับค่า**ทุกช่องบนเส้นทแยง (`1`↔`0`) — ได้ `D = 01110101`
3. ถามว่า: มีแถวไหนในตาราง **เหมือนแถว D ทั้งแถว**ไหม?

คำตอบคือ **ไม่มี** — เพราะแถว i ต้องต่างจาก D ที่ช่อง `x=i` ของตัวเองเสมอ (D[i] คือ "ตรงข้าม" ของ T[i][i]) ผลรันจริงยืนยัน: `แถวที่เท่ากับ D ทั้งแถว: 0 แถว จาก 8 แถว` ต่อให้เพิ่มโปรแกรมอีกกี่ล้านตัว ก็ยังมีแถวที่ "หลุด" ออกไปเสมอ

แล้วทำไมเรื่องนี้แปลว่า "มีปัญหาที่แก้ไม่ได้"? เพราะการนับ:

- **โปรแกรม** = สตริงไบนารี (ลำดับของ 0/1) ความยาวจำกัด → **นับได้** (ไล่เลขขึ้นทะเบียนได้เรื่อย ๆ แม้จะไม่มีวันหมด)
- **ฟังก์ชัน** (งานที่ "รับ input แล้วตอบ 0/1") ทั้งหมด มีมากถึง `2^(2^N)` แบบ (`N` = ความยาวของ input เป็นบิต) → **นับไม่ได้** (มากเกินกว่าจะไล่เลขขึ้นทะเบียนทัน)

เมื่อ "งาน" มีมากกว่า "โปรแกรม" อย่างไม่มีวันทัน → **ต้องมีงานบางอย่างที่ไม่มีโปรแกรมไหนทำได้แน่นอน** — halting problem ก็เป็นหนึ่งในนั้น (รายละเอียดการนับตัวเลขอยู่ในผลรันของโปรแกรม 03)

## 8. โปรแกรม 05 (ตอนที่ 2) — ลำดับชั้นของปัญหา: อะไรตัดสินได้ อะไรตัดสินไม่ได้

เอาทุกอย่างมารวมกัน เราแยกปัญหาเป็นสามชั้นตาม "ความยากของการตอบ":

| ปัญหา | ชั้น | เหตุผล |
|---|---|---|
| วงเล็บสมดุล, `aⁿbⁿ` | **ตัดสินได้ (decidable)** | PDA ตรวจได้ (ตอนที่ 23) |
| `aⁿbⁿcⁿ` | **ตัดสินได้** | TM ตรวจได้ (โปรแกรม 01) ไม่มี PDA ทำได้ |
| halting problem (`P หยุดกับ x ไหม`) | **รับรู้ได้ แต่ตัดสินไม่ได้** | พิสูจน์ด้วยการอ้างถึงตัวเอง (หัวข้อ 6) |
| ส่วนเติมเต็มของ halting problem (complement = คำถามกลับด้าน "P **ไม่**หยุดกับ x ใช่ไหม") | **ไม่ใช่ "รับรู้ได้" ด้วย** | ถ้าตรวจ "ไม่หยุด" ได้ด้วยการรันจำกัดก้าว ก็จะได้ตัวตัดสิน (ขัดแย้ง) |

คำศัพท์สองคำที่ต้องจับให้ชัด:

- **decidable (ตัดสินได้)** = มีโปรแกรมที่ตอบถูก**ทุก input** ในเวลาจำกัดเสมอ (ไม่ว่า "ใช่" หรือ "ไม่" ก็ตอบได้)
- **recognizable (รับรู้ได้)** = ยืนยันฝั่ง "ใช่" ได้ (รันแล้วถ้ามันยอมรับเราก็รู้) แต่ฝั่ง "ไม่" **ไม่รับประกัน** — ถ้าโปรแกรมไม่หยุด เราไม่มีวันรู้ว่ามัน "จะไม่หยุดตลอดไป" หรือ "แค่ยังไม่หยุด"

และข้อสรุปสำคัญสำหรับคนเขียนโปรแกรม:

> **ไม่มีคอมไพเลอร์หรือ IDE ตัวไหนตรวจจับ infinite loop ได้ทุกแบบ** — เพราะนั่นคือ halting problem นั่นเอง สิ่งที่เครื่องมือทำได้คือ "จับบางรูปแบบ + ตอบยังไม่รู้ที่เหลือ" แล้วปล่อยให้คนตัดสิน

![ลำดับชั้นเครื่องคำนวณ: เพิ่มความจำทีละชั้น แล้วได้ภาษาที่ "ทำได้" เพิ่มขึ้น](/assets/diagrams/ep24-02-hierarchy.svg)

ภาพที่ 2 สรุปลำดับชั้นที่เราสะสมมาทั้งหมด: **FA ⊊ PDA ⊊ Turing machine** (`⊊` = "เซตย่อยแท้" แปลว่าชั้นล่างเป็นส่วนหนึ่งของชั้นบน แต่เล็กกว่าอย่างแท้จริง) — ความจำเพิ่มขึ้นทีละชั้น เครื่องก็ทำได้มากขึ้น ตัวเลขในภาพคือหลักฐานจริง: PDA ที่มี stack กองเดียวเทียบจำนวนได้ทีละคู่ จึงผิด 9 จาก 64 กรณี ขณะที่ TM ผิด 0 จาก 64

## 9. สรุป — ตอบคำถามของระยะนี้ได้แล้ว

ตลอดระยะที่ 5 (ตอน 22–24) เราถามว่า "คอมพิวเตอร์ทำอะไรได้/ไม่ได้" ตอนนี้ตอบได้ครบ:

1. **FA** (สถานะจำกัด) → รับได้แค่ regular language, นับไม่ได้
2. **PDA** (FA + stack) → รับได้ context-free language, นับได้หนึ่งกอง
3. **Turing machine** (FA + เทปอนันต์ + เขียนทับ + เดินสองทาง) → เทียบเท่า "คอมพิวเตอร์ทั่วไป" (Church–Turing thesis)
4. **แต่** ต่อให้ทรงพลังเท่านี้ ก็ยังมีปัญหาที่มันทำไม่ได้ — **halting problem** (และอีกมากมายที่ "มากกว่า" จำนวนโปรแกรมทั้งหมด ตามการนับของ Cantor)

ไอเดียสองชิ้นที่คุ้มค่าที่สุดในคืนนี้:

- **โปรแกรมเป็นข้อมูลได้** (เครื่องจักรสากล) — นี่คือเหตุผลที่เรามี interpreter, VM, JIT และ "คอมพิวเตอร์ที่ตั้งโปรแกรมได้" ต่างจาก "เครื่องคิดเลขที่ทำได้เฉพาะงานเดียว"
- **ขอบเขตมีจริง** — มีคำถามที่ไม่มีอัลกอริทึมตอบได้ และเราพิสูจน์ได้ด้วยการ "อ้างถึงตัวเอง" ง่าย ๆ

แล้วคืนถัดไป (ตอนที่ 25) จะถามคำถามถัดไปทันที: ปัญหาที่**ตัดสินได้**ก็ยัง "ยาก" ต่างกันมหาศาล (บางอย่างตอบได้แต่ใช้เวลานานแบบใช้ไม่ได้จริง) — นั่นคือเรื่อง **P/NP** ซึ่งเป็นคนละแกนกัน: ตอนที่ 24 คือขอบเขตของ **"ทำได้"** ส่วนตอนที่ 25 คือขอบเขตของ **"ทำได้เร็วพอ"**
