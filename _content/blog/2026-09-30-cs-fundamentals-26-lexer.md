# Lexer — ตัดข้อความโปรแกรมออกเป็น "คำ" (ตอนที่ 26)

ยินดีต้อนรับเข้าสู่**ระยะที่ 6 (Compiler/Interpreter — ตัวแปลภาษา)** — ระยะสุดท้ายก่อน **capstone** (โปรเจกต์ปิดท้ายคอร์ส) และเป็นระยะที่เราเปลี่ยนจาก "ผู้ใช้เครื่องมือ" มาเป็น "**ผู้สร้างเครื่องมือ**" อย่างแท้จริง

> **สองศัพท์ที่พบบ่อยในระยะนี้:** **compiler** (อ่านว่า "คอมไพเลอร์") = โปรแกรมที่แปลโค้ดทั้งไฟล์ให้เสร็จก่อนแล้วค่อยรัน **interpreter** (อ่านว่า "อินเทอร์พรีเตอร์") = แปลแล้วรันไปทีละบรรทัด — ทั้งคู่เป็น "ตัวแปลภาษา" เหมือนกัน ต่างกันแค่จังหวะทำงาน

ตลอด 25 ตอนที่ผ่านมา เราสั่งให้คอมพิวเตอร์ทำงานผ่าน**ภาษาที่คนอื่นสร้างไว้ให้** (Go และ C — ภาษาโปรแกรม; assembly — ภาษาระดับใกล้เครื่องที่สุดที่คนยังพออ่านออก) — เราเขียนโค้ด แล้วมีโปรแกรมบางอย่างแปลมันให้เครื่องเข้าใจ ตอนนี้เราจะถอยกลับไปถามว่า **เจ้าโปรแกรมแปลนั้นมันทำงานยังไงกันแน่?** แล้วตอบด้วยการลงมือสร้างมันขึ้นมาเอง ตั้งแต่ก้าวแรกสุด

ก้าวแรกสุดที่ว่ามีชื่อว่า **lexer** (อ่านว่า "เล็กเซอร์")

> **ที่อยู่ของโค้ดในตอนนี้:** โปรแกรมทุกตัวอยู่ที่ `course/code/ep26/` แยกโฟลเดอร์ตามเลขโปรแกรม (01–05) พร้อมผลรันจริงในโฟลเดอร์ `out/` (ไฟล์ `07_drill_answer.out.txt` ในนั้นคือ**เฉลยโจทย์** ไม่ใช่โฟลเดอร์โปรแกรม) — เปิดดูตามไปด้วยได้ตลอด

## 1. ปัญหา: คอมพิวเตอร์ "เห็น" โปรแกรมของเราเป็นแค่ตัวหนังสือเรียงกัน

ลองเปิดโปรแกรมที่เราเขียนขึ้นมาเองสักไฟล์ — ตอนเราเขียนโค้ด เรามองเห็นมันเป็น "โครงสร้าง" ที่มีความหมาย: บรรทัดนี้ประกาศ**ตัวแปร** (ตัวแปร = กล่องมีชื่อไว้เก็บค่า), บรรทัดนี้เป็น**เงื่อนไข** (เงื่อนไข = การตัดสินใจว่าจะทำอะไรตามสถานการณ์ เช่น "ถ้า…ก็…"), ตรงนี้คือการบวกเลข แต่**คอมพิวเตอร์ไม่ได้เห็นแบบนั้น**

สำหรับคอมพิวเตอร์ ไฟล์โปรแกรมทั้งไฟล์ก็เป็นแค่ **string** (อ่านว่า "สตริง" = ข้อความ/สายตัวอักษร) ก้อนยาว ๆ ก้อนเดียว — ตัวอักษรเรียงติดกันไปเรื่อย ๆ เหมือนเส้นเทปยาว ๆ ที่ไม่มีรอยต่อ:

```
let x = 3 + 4 * 5;
```

สำหรับเครื่อง นี่ไม่ใช่ "ประกาศตัวแปร x แล้วเอาค่ามาใส่" — มันคือตัวอักษร `l` `e` `t` เว้นวรรค `x` เว้นวรรค `=` ... ไล่ไปจนถึง `;` ไม่มีคำว่า "ตัวแปร" หรือ "บวก" โผล่ขึ้นมาเลย

แล้วเครื่องจะ "เข้าใจ" โปรแกรมของเราได้ยังไง? คำตอบคือ: **มันต้องตัดข้อความก้อนนั้นออกเป็นชิ้น ๆ ที่มีความหมายก่อน** แล้วค่อยเอาแต่ละชิ้นไปตีความ — เหมือนเวลาเราอ่านประโยคภาษาไทย เราต้องแยกคำออกจากกันก่อนถึงจะเข้าใจความหมาย ("ฉันกินข้าว" ต้องรู้ว่า `ฉัน` `กิน` `ข้าว` เป็นคนละคำ ไม่ใช่ `ฉันกินข้าว` คำเดียว)

ชิ้นที่เล็กที่สุดที่มีความหมายนี่แหละ เรียกว่า **token** (อ่านว่า "โทเคน" = คำ/หน่วยเล็กสุด) และโปรแกรมที่ทำหน้าที่ตัด token เรียกว่า **lexer**

**lexer มีชื่อเรียกอีกสองชื่อที่เจอบ่อย** — ในตำราและโค้ดจริงเราจะเจอคำว่า **tokenizer** และ **scanner** ทั้งสามคำนี้หมายถึงสิ่งเดียวกัน อย่าเพิ่งงงถ้าเจอคำต่างกัน

![จากซอร์สโค้ดถึง token stream](/assets/diagrams/ep26-01-pipeline.svg)

ภาพข้างบนสรุปงานทั้งหมดของตอนนี้: ซอร์สโค้ด (source code = ข้อความโปรแกรมที่มนุษย์เขียน) เข้าทางซ้าย lexer ตรงกลางตัดมันออกเป็น token แล้วคายออกมาเป็น **token stream** (ลำดับของ token) ทางขวา — และลำดับนี้เองคือสิ่งที่ขั้นถัดไป (parser ในตอนที่ 27) จะรับไปใช้ต่อ

ช่องล่างสุดของแผนผังคือเส้นทางที่เหลือของระยะนี้ (จะค่อย ๆ ทำในตอนที่ 27–30): **parser → AST** (AST = แผนภูมิต้นไม้ที่แสดงโครงสร้างของโปรแกรม) → **interpreter** (ตัวรันโปรแกรมทีละขั้น) → **type/scope** (ระบบชนิดข้อมูล + ขอบเขตของตัวแปร) → **codegen** (สร้างโค้ดภาษาเครื่อง) — ตอนนี้เรายังไม่ต้องรู้รายละเอียด แค่เห็นภาพรวมว่า lexer คือ**ด่านแรก**ของท่อทั้งหมด

**โจทย์ที่ lexer ตอบได้แค่คำเดียว:** "ข้อความก้อนนี้ ตัดแล้วได้คำอะไรบ้าง เรียงลำดับยังไง?" — แค่นั้น ไม่มากไม่น้อย

## 2. token หนึ่งตัว หน้าตาเป็นยังไง?

ถ้า lexer จะตัด "คำ" ออกมา คำหนึ่งคำต้อง "บอก" อะไรบ้างถึงจะใช้งานต่อได้? มองที่ `3 + 4` — พอตัดแล้วได้คำสามคำ เราอยากรู้ของแต่ละคำว่า:

1. **มันเป็นอะไร** (ชนิด / type) — `3` เป็นตัวเลข, `+` เป็นเครื่องหมายบวก (คนละอย่างกันเลย ถึงแม้จะตัดมาเป็นคำเดี่ยวเหมือนกัน)
2. **ข้อความจริงของมันคืออะไร** (literal) — ตัวเลข `3` กับตัวเลข `4` เป็นชนิดเดียวกัน แต่ข้อความจริงต่างกัน (`"3"` กับ `"4"`)
3. **มันอยู่ตรงไหนของไฟล์** (ตำแหน่ง / position) — บรรทัดไหน คอลัมน์ไหน — เผื่อต้องบอกมนุษย์ว่า "โค้ดคุณผิดตรงนี้"

![ส่วนประกอบของ token หนึ่งตัว](/assets/diagrams/ep26-02-token-anatomy.svg)

สามอย่างนี้ประกอบกันเป็น token หนึ่งตัว ในโค้ด Go จริงของเราหน้าตาแบบนี้ (จากไฟล์ `internal/lexer/lexer.go`):

```go
// Token — หนึ่งคำที่ lexer ตัดออกมาได้
type Token struct {
	Type    Type     // คำนี้เป็นประเภทไหน (NUMBER? PLUS? IDENT = ชื่อที่เราตั้งเอง?)
	Literal string   // ข้อความจริงที่ตัดได้จากไฟล์ (ของ EOF = สัญญาณจบไฟล์ เป็น "")
	Pos     Position // อยู่ตรงไหน — ใช้รายงาน error ให้คนอ่านออก
}
```

> **ศัพท์ที่ต้องรู้จักก่อนไปต่อ** (ถ้ายังไม่เคยเจอ):
> - `type` (อ่านว่า "ไทป์") = คำ Go ที่ใช้**ตั้งชื่อชนิดใหม่** — เมื่อใช้ร่วมกับ `struct` จะได้โครงสร้างที่มีฟิลด์
> - `struct` (อ่านว่า "สตรัค") = คำ Go ที่ใช้ประกาศโครงสร้างข้อมูล — บอกว่า "ของชิ้นนี้ประกอบด้วยฟิลด์ (field = ช่องข้อมูล) กี่ช่อง อะไรบ้าง"
> - `string` = ชนิดข้อมูลที่เป็นข้อความ · `int` = จำนวนเต็ม · `Position` = โครงสร้างอีกตัวที่เราเพิ่งประกาศ — Go อนุญาตให้โครงสร้างหนึ่งใส่โครงสร้างอีกตัวไว้ข้างใน เหมือนกล่องซ้อนกล่อง

ตอนนี้เรายังไม่รู้ว่า `Type` (ชนิดของ token) มีค่าอะไรบ้าง — นั่นคือหัวใจของตอนนี้ และเราจะค่อย ๆ เติมมันเข้าไปทีละขั้น

## 3. ก้าวแรกที่เล็กที่สุด: lexer ตัวจิ๋วที่รู้จักแค่ตัวเลขกับเครื่องหมาย

หลักการของ lexer ทุกตัวบนโลกนี้เหมือนกันหมด ไม่ว่าจะเป็นของ Go, gcc, หรือตัวจิ๋วที่เรากำลังจะเขียน: **เดินดูตัวอักษรทีละตัว แล้วตัดสินใจว่าตรงนี้ควร "อ่าน" อะไรต่อ**

เราเริ่มจากเวอร์ชันที่เล็กที่สุดเท่าที่จะเล็กได้ (โปรแกรม `01_lexer_basic`) — รู้จักแค่ 4 อย่าง: ตัวเลข, เครื่องหมาย `+`, เครื่องหมาย `*`, และช่องว่าง

ก่อนดูโค้ด รู้จักของที่ใช้ในโค้ดชุดแรกนี้ก่อน (ถ้ายังไม่เคยเจอ):

- `func` = คำขึ้นต้นประกาศ**ฟังก์ชัน** (ฟังก์ชัน = บล็อกโค้ดที่มีชื่อ เรียกใช้ซ้ำได้)
- `:=` = สร้างตัวแปรพร้อมใส่ค่าทันที · `var` = ประกาศตัวแปร
- `[]token` = กลุ่มข้อมูลชนิด `token` เรียงเป็นแถว (ใน Go เรียกโครงสร้างแบบนี้ว่า **slice**)
- `append(...)` = ต่อของชิ้นใหม่เข้าไปท้ายแถว
- `src[start:i]` = ตัดข้อความออกมาเฉพาะช่วงหนึ่ง (เรียกการ "ตัดช่วง" แบบนี้ว่า slice ข้อความ)
- `token{kind: "...", text: ..., at: ...}` = สร้างโครงสร้าง token ขึ้นมา พร้อมระบุค่าแต่ละฟิลด์
- **ไบต์ (byte)** = หน่วยวัดความยาวข้อความ: ตัวอักษรภาษาอังกฤษ 1 ตัว = 1 ไบต์ (อักษรไทย 1 ตัว = 3 ไบต์ — เรื่องนี้เราจะกลับมาพูดท้ายบท)

```go
// lexBasic — เดินอ่านตัวอักษรทีละตัว แล้วตัดออกมาเป็น token
func lexBasic(src string) ([]token, []string) {
	var toks []token
	var notes []string

	i := 0 // i = "นิ้วชี้" ของเรา (ตำแหน่งไบต์ในข้อความ)
	for i < len(src) {
		c := src[i]
		switch {
		case c == ' ':
			notes = append(notes, fmt.Sprintf("pos %2d: เจอช่องว่าง → ข้าม ไม่นับเป็นคำ", i))
			i++
		case c >= '0' && c <= '9':
			start := i
			for i < len(src) && src[i] >= '0' && src[i] <= '9' {
				i++ // อ่านตัวเลข "ติดกัน" ให้ครบก่อน (23 ต้องได้ 23 ไม่ใช่ 2 กับ 3)
			}
			text := src[start:i]
			toks = append(toks, token{kind: "NUMBER", text: text, at: start})
		case c == '+':
			toks = append(toks, token{kind: "PLUS", text: "+", at: i})
			i++
		case c == '*':
			toks = append(toks, token{kind: "STAR", text: "*", at: i})
			i++
		default:
			i++ // อักขระไม่รู้จัก — ข้ามไป (เวอร์ชันนี้ยังไม่รายงาน error)
		}
	}
	return toks, notes
}
```

มาอ่านโค้ดนี้ด้วยกันทีละส่วน เพราะ**ทุกตัวจะกลับมาอีกในเวอร์ชันเต็ม**:

- **`for i < len(src)`** — วงวน (loop) ที่เดินนิ้วชี้ `i` ไปเรื่อย ๆ จนสุดข้อความ `src` (ชื่อย่อของ source)
- **`switch`** — โครงสร้าง "เช็คเงื่อนไขแล้วเลือกทำหนึ่งทาง": ถ้าตัวอักษรปัจจุบันเป็นช่องว่างก็ข้าม, เป็นเลขก็อ่านตัวเลข, เป็น `+` ก็ตัดเป็น `PLUS`, ฯลฯ
- **อ่านตัวเลขติดกัน** — ตรง `for i < len(src) && src[i] >= '0' && src[i] <= '9'` คือหัวใจที่มือใหม่มักพลาด: เจอ `1` ต้องอ่านต่อไปว่า `2` ตามมาไหม `3` ตามมาไหม — เพื่อให้ `345` กลายเป็นตัวเลข**หนึ่งตัว** ไม่ใช่ `3` `4` `5` สามตัวแยกกัน

> โปรแกรม 01 ตั้งใจใช้โครงสร้างย่อ (ฟิลด์ชื่อ `kind`/`text`/`at`) เพื่อให้อ่านง่าย ส่วน lexer จริงในหัวข้อ 2 ใช้ `Token{Type, Literal, Pos}` — ความหมายเดียวกันทุกประการ แค่ชื่อฟิลด์ต่างกัน

ลองรันดูผลจริง (ผลนี้อยู่ใน `out/01_lexer_basic.out.txt`):

```
== นิพจน์เลขคณิต: "1 + 2 * 3" ==
คำที่ตัดได้ (5 คำ):
   1) NUMBER  "1"  (เริ่มที่ pos 0)
   2) PLUS    "+"  (เริ่มที่ pos 2)
   3) NUMBER  "2"  (เริ่มที่ pos 4)
   4) STAR    "*"  (เริ่มที่ pos 6)
   5) NUMBER  "3"  (เริ่มที่ pos 8)

== ตัวเลขติดกันต้องไม่ถูกแยก: "12 + 345" ==
คำที่ตัดได้ (3 คำ):
   1) NUMBER  "12" (เริ่มที่ pos 0)
   2) PLUS    "+"  (เริ่มที่ pos 3)
   3) NUMBER  "345" (เริ่มที่ pos 5)
```

สังเกตสองสิ่ง:

1. **ช่องว่างไม่เป็น token** — มันถูก "ข้าม" ไปเงียบ ๆ เพราะช่องว่างมีไว้ให้**มนุษย์**อ่านโปรแกรมเท่านั้น ตัวแปลภาษาไม่สนใจมันเลย (แต่ต้องรู้จักมัน เพื่อจะได้ข้ามมันถูก)
2. **`12` และ `345` ถูกตัดเป็นตัวเลขตัวเดียว** — เพราะวงวนอ่านตัวเลขติดกันจนหมด

แล้วมีจุดสำคัญสุดในโปรแกรมนี้ — ลองดูผลของบรรทัดนี้:

```
== ไวยากรณ์ผิด แต่ lexer ยังตัดผ่าน: "1 + * 3" ==
คำที่ตัดได้ (4 คำ):
   1) NUMBER  "1"  (เริ่มที่ pos 0)
   2) PLUS    "+"  (เริ่มที่ pos 2)
   3) STAR    "*"  (เริ่มที่ pos 4)
   4) NUMBER  "3"  (เริ่มที่ pos 6)
```

`1 + * 3` เขียน**ผิดไวยากรณ์** (ไวยากรณ์/grammar = กฎการเรียงคำให้เป็นประโยคที่ถูกต้อง) แน่นอน — มีเครื่องหมาย `+` ตามด้วย `*` โดยไม่มีตัวเลขคั่นกลาง แต่ lexer ยังตัดผ่านสบาย ๆ — **เพราะ lexer ดูแค่ "คำ" ไม่ได้ดู "ไวยากรณ์"** มันไม่รู้ว่าการเรียง `PLUS` ตามด้วย `STAR` มันผิด มันแค่รายงานว่าเจอคำอะไรบ้างเรียงลำดับยังไง

หน้าที่ "จับว่าเรียงคำไม่ถูกไวยากรณ์" เป็นของ **parser** (ตัวถัดไป ตอนที่ 27) — นี่คือเส้นแบ่งงานที่ต้องจำไว้ให้แม่น

## 4. ทำไมต้อง "แอบดูตัวถัดไป" (peek / lookahead)

ตอนนี้ลองคิดเคสที่ดูเหมือนง่ายแต่ซ่อนกับดักไว้: เราเห็นตัวอักษร `=` ตัวเดียว — จะรู้ได้ไงว่ามันคือ

- **`=`** เครื่องหมาย "ให้ค่า" (assign) เช่น `x = 1` (เอาค่า 1 ไปใส่ใน x) หรือ
- **`==`** เครื่องหมาย "เท่ากันหรือเปล่า" (เปรียบเทียบ) เช่น `x == 1` (ถามว่า x เท่ากับ 1 ไหม)?

สองอย่างนี้ความหมาย**ตรงข้ามกันเลย** — ตัวแรกสั่งให้ทำงาน ตัวหลังถามคำถาม แล้วตัวอักษรที่ต่างกันก็แค่ "มี `=` สองตัวหรือตัวเดียว"

ปัญหาคือ: ตอนที่เรามอง `=` ตัวแรกอยู่ เรายังไม่รู้ว่า "คำ" นี้จบแล้วหรือยัง — มันอาจมี `=` อีกตัวตามมาก็ได้

ทางแก้คือความสามารถที่เรียกว่า **peek** (อ่านว่า "พีค" = แอบดู) หรือชื่อทางการคือ **lookahead** (อ่านว่า "ลุคอะเฮด" = มองไปข้างหน้า): **แอบดูตัวอักษรถัดไป โดยยังไม่ขยับนิ้ว** ถ้าเป็น `=` อีกตัว → รวมกันเป็น `==` ถ้าไม่ใช่ → ก็คือ `=` ตัวเดียว จบคำ

ในโค้ดจริง (จาก `internal/lexer/lexer.go` — โปรแกรม 02 ใช้ lexer ตัวนี้ตรวจซ้ำอีกชั้นในชั้น B) เขียนแบบนี้:

```go
// อยู่ในฟังก์ชัน Next() ของ lexer (l = ตัว lexer เอง · start = ตำแหน่งเริ่มต้นของคำนี้)
case '=':
	l.advance()
	if l.ch() == '=' { // "=" ตัวเดียว หรือ "==" สองตัว?
		l.advance()
		return Token{Type: EQ, Literal: "==", Pos: start}, nil
	}
	return Token{Type: ASSIGN, Literal: "=", Pos: start}, nil
```

`l.ch()` คือ "มองตัวอักษรที่นิ้วชี้อยู่ตอนนี้โดยไม่ขยับ" ส่วน `l.advance()` คือ "ขยับนิ้วไปหนึ่งตัว" — เราเลยทำได้แบบนี้: กิน `=` ตัวแรกไป แล้ว**มอง**ว่าตัวถัดไปเป็น `=` ไหม ถ้าใช่ก็กินมันด้วย (ได้ `==`) ถ้าไม่ใช่ก็หยุด (ได้ `=`) คำว่า `nil` (อ่านว่า "นิล") ที่คืนพร้อม token = "ไม่มีค่าอะไร" — ใช้บอกว่า "ไม่เกิด error"

หลักการเดียวกันนี้ใช้กับ `!` → `!=`, และ `/` → `//` (เครื่องหมายหาร vs เครื่องหมาย**คอมเมนต์** — คอมเมนต์ = ข้อความหมายเหตุในโค้ดที่เครื่องข้ามไป ไม่นับเป็นคำสั่ง) ผลจริงจากโปรแกรม 02:

```
-- ชั้น A: ตัดสินใจแบบมือ --
  "="          → ASSIGN   "="   เห็น '=' → แอบดู ไม่เจอ '=' → เป็น "=" ตัวเดียว
  "=="         → EQ       "=="  เห็น '='→ แอบดู เจอ '=' → รวมกันเป็น "=="
  "!"          → ERROR    "!"   เห็น '!' → แอบดู ไม่เจอ '=' → ภาษานี้ไม่มี "!" เดี่ยว
  "!="         → NEQ      "!="  เห็น '!' → แอบดู เจอ '=' → รวมกันเป็น "!="
  "// หมายเหตุ" → COMMENT  "//" เห็น '/' → แอบดู เจอ '/' → ที่เหลือทั้งบรรทัดเป็นคอมเมนต์
  ...   (ตารางนี้ย่อเหลือ 5 แถวจาก 8 แถวจริง — ดูครบได้ใน out/02_lexer_peek.out.txt)

-- ชั้น B: ให้ lexer จริงตัดข้อความเดียวกัน แล้วเทียบว่าตรงกันไหม --
  เทียบแล้วตรงกัน 8/8 กรณี
```

ทำไมเรื่องนี้ถึงสำคัญขนาดนั้น — ดูสองประโยคที่ต่างกันแค่ตัวอักษรเดียว:

```
"x = 1"  → IDENT(x) · ASSIGN(=) · NUMBER(1) · EOF()
"x == 1" → IDENT(x) · EQ(==) · NUMBER(1) · EOF()
```

บรรทัดแรก = "เอาค่า 1 ไปใส่ในตัวแปร x" บรรทัดที่สอง = "ถามว่าตัวแปร x เท่ากับ 1 ไหม" — **คนละความหมายโดยสิ้นเชิง** ถ้า lexer ไม่รู้จัก peek มันจะตัด `==` เป็น `ASSIGN ASSIGN` สองตัวรัว ๆ แล้วภาษาเราจะเขียนเงื่อนไขเปรียบเทียบไม่ได้เลย

## 5. "สเปก" ของ token — ภาษาจิ๋วของเรารู้จักคำอะไรบ้าง?

ตอนนี้เราพร้อมจะมองภาพรวมแล้ว ภาษาจิ๋วที่คอร์สนี้จะสร้าง (ตอนที่ 26–30) หน้าตาแบบนี้:

```
let x = 3 + 4 * 5;
let y = (x - 2) * 2;
if y > 10 { print y; }
```

ทุก "คำ" ที่ภาษานี้รู้จัก รวมเป็นตารางที่เรียกว่า **สเปก (spec)** — รายการชนิดของ token ทั้งหมด แบ่งเป็น 5 กลุ่ม:

![ตารางสเปกของ token](/assets/diagrams/ep26-04-token-spec.svg)

| กลุ่ม | ชนิด token | ความหมาย (สำหรับมือใหม่) |
|---|---|---|
| **NUMBER** | `NUMBER` | ตัวเลข เช่น `3`, `42` |
| **IDENT** | `IDENT` | ชื่อตัวแปรที่เราตั้งเอง เช่น `x`, `total_1` (identifier = ตัวระบุ/ชื่อ) |
| **KEYWORD** | `LET IF ELSE TRUE FALSE PRINT` | **คำสงวน** — คำที่ตัวภาษาจองไว้ ห้ามเอาไปตั้งชื่อตัวแปร |
| **OPERATOR** | `PLUS` `MINUS` `STAR` `SLASH` `ASSIGN` `EQ` `NEQ` `LT` `GT` `LPAREN` `RPAREN` `LBRACE` `RBRACE` `SEMI` | เครื่องหมาย `+` `-` `*` `/` `=` `==` `!=` `<` `>` `(` `)` `{` `}` `;` ตามลำดับ (บางตัวต้อง peek) |
| **EOF** | `EOF` | สัญญาณ "จบไฟล์" — ไม่ใช่ตัวอักษรจริง แต่ parser ต้องรู้ว่า "หมดแล้ว" |

> **ศัพท์สามตัวที่มือใหม่ควรจำ:** **keyword** (อ่านว่า "คีเวิร์ด" = คำสงวน) คือคำที่ภาษาเก็บไว้ใช้เอง เช่น `let` `if` — คุณตั้งชื่อตัวแปรว่า `let` ไม่ได้; **identifier** (อ่านว่า "ไอเดนทิฟายเออร์") คือชื่อที่**เราตั้งเอง** เช่น ชื่อตัวแปร `x`, `total_1`; **operator** (อ่านว่า "โอเปอเรเตอร์") คือเครื่องหมาย เช่น `+` `-` `*` `=` — สัญลักษณ์ที่สั่งให้ทำอะไรบางอย่างกับค่าข้าง ๆ

จุดสำคัญที่แยก IDENT ออกจาก KEYWORD: ดูจากตัวสะกดล้วน ๆ — ถ้าชื่อที่อ่านมาได้สะกดตรงกับคำในตารางคำสงวน (เช่น `let`) ก็เป็น KEYWORD ถ้าไม่ตรง (เช่น `letx` หรือ `x`) ก็เป็น IDENT นี่คือเหตุผลที่ lexer ต้อง**อ่านชื่อให้จบก่อน** แล้วค่อยเอาไปเทียบตาราง

ในโค้ดจริง ตารางคำสงวนเขียนเป็น **map** (อ่านว่า "แมป" = ตารางจับคู่: ใส่กุญแจเข้าไป แล้วได้ค่าออกมา) แบบนี้:

```go
// Keywords — คำสงวนของภาษาจิ๋ว พร้อมชนิด token ของแต่ละคำ
var Keywords = map[string]Type{
	"let":   LET,
	"if":    IF,
	"else":  ELSE,
	"true":  TRUE,
	"false": FALSE,
	"print": PRINT,
}
```

แต่สเปกที่เขียนเป็น "เอกสาร/คอมเมนต์" มักเจอปัญหา: **แก้โค้ดแล้วลืมแก้เอกสาร** แล้วสองอย่างก็ค่อย ๆ หลุดออกจากกันเงียบ ๆ โปรแกรม `03_lexer_spec` เลยแก้ปัญหานี้ด้วยการเก็บสเปกเป็น**ข้อมูลในโค้ด** แล้วยิงข้อความตัวอย่างจริงเข้าสู่ lexer เพื่อพิสูจน์ว่าสเปกกับโค้ดตรงกัน:

```
-- A) สเปกแต่ละกลุ่ม พร้อมผลตรวจกับ lexer จริง --
  [1] กลุ่ม NUMBER     ตัวอย่าง: "42"        → สเปกบอก: NUMBER EOF · ตัดได้: NUMBER EOF · ตรง
  [2] กลุ่ม IDENT      ตัวอย่าง: "total_1"   → สเปกบอก: IDENT EOF  · ตัดได้: IDENT EOF  · ตรง
  [3] กลุ่ม KEYWORD    ตัวอย่าง: "let if ..." → สเปกบอก: LET IF ELSE TRUE FALSE PRINT EOF · ตรง
  [4] กลุ่ม OPERATOR   ตัวอย่าง: "+ - * / ..." → ตัดได้ตรงครบทุกเครื่องหมาย · ตรง
  [5] กลุ่ม EOF        ตัวอย่าง: ""          → ตัดได้: EOF · ตรง
  → ตรวจได้ 5/5 กลุ่มตรงกับสเปก
```

โปรแกรมเดียวกันยังนับได้ด้วยว่า**ชนิด token ไหนยังไม่เคยถูกใช้ในตัวอย่างเลย** — มี 7 ชนิด (`ELSE`, `EQ`, `FALSE`, `LT`, `NEQ`, `SLASH`, `TRUE`):

- นับได้ว่าชนิดไหน "โผล่" ไปแล้วในตัวอย่างทั้ง 3 โปรแกรม (เช่น `NUMBER` เจอ 14 ครั้ง, `IDENT` เจอ 9 ครั้ง)
- 7 ชนิดข้างต้นยังเป็น 0 เพราะ**เรายังไม่ได้เขียนตัวอย่างที่ใช้มัน** (ตอนนี้ยังไม่มีโปรแกรมใช้ `else`, `==`, `<` เป็นต้น)
- นี่คือการเตือนตัวเองว่า "สเปกของฉันมีของที่ยังไม่เคยเทสต์จริง" — มันจะโผล่ในตอนถัดไป (parser) ที่ต้องใช้ครบ

## 6. ลงมือดู token stream ของโปรแกรมจริงทั้ง 3 ตัว

ตอนนี้ลองรัน lexer เต็มตัวกับโปรแกรมตัวอย่าง 3 ตัว (โปรแกรม `04_lexer_programs`) — นี่คือ**ผลลัพธ์จริง**ที่ parser ตอนที่ 27 จะรับไปใช้ต่อ

ในตารางผลลัพธ์ต่อจากนี้ คอลัมน์แรก `#` = ลำดับที่ · คอลัมน์ที่สองเช่น `1:3` = **บรรทัด:คอลัมน์** (บรรทัดที่ 1 คอลัมน์ที่ 3) · คอลัมน์ที่สาม = ชนิดของ token · คอลัมน์ที่สี่ = ข้อความจริง

**ตัวอย่าง 1 — นิพจน์เลขคณิตล้วน:**

```
  1 | 1 + 2 * 3
token ทั้งหมด 6 ตัว:
  1   1:1    NUMBER    "1"
  2   1:3    PLUS      "+"
  3   1:5    NUMBER    "2"
  4   1:7    STAR      "*"
  5   1:9    NUMBER    "3"
  6   1:10   EOF       ""
สตรีมแบบอ่านเร็ว: NUMBER(1) PLUS(+) NUMBER(2) STAR(*) NUMBER(3) EOF()
```

> **เลข 5 คำ vs 6 ตัว ไม่ได้ขัดกัน:** โปรแกรม 01 (หัวข้อ 3) ยังไม่คืน EOF จึงนับได้ 5 คำ ส่วน lexer เต็มตัวคืน `EOF` ต่อท้ายเสมอ — จึงนับรวมได้ 6 ตัว

**ตัวอย่าง 2 — ตัวแปร + คอมเมนต์ที่มีอักษรไทย:**

```
  1 | // หาค่าของ x กับ y (คอมเมนต์นี้มีอักษรไทย)
  2 | let x = 3 + 4 * 5;
  3 | let y = (x - 2) * 2;
  4 | print y;

token ทั้งหมด 24 ตัว:
  1   2:1    LET       "let"
  2   2:5    IDENT     "x"
  3   2:7    ASSIGN    "="
  4   2:9    NUMBER    "3"
  ...
 21   4:1    PRINT     "print"
 22   4:7    IDENT     "y"
 23   4:8    SEMI      ";"
 24   4:9    EOF       ""
สตรีมแบบอ่านเร็ว: LET(let) IDENT(x) ASSIGN(=) NUMBER(3) PLUS(+) NUMBER(4) STAR(*) NUMBER(5) SEMI(;) LET(let) IDENT(y) ASSIGN(=) LPAREN(() IDENT(x) MINUS(-) NUMBER(2) RPAREN()) STAR(*) NUMBER(2) SEMI(;) PRINT(print) IDENT(y) SEMI(;) EOF()
```

สังเกตว่า**บรรทัดที่ 1 (คอมเมนต์) ไม่มี token เลย** — เพราะคอมเมนต์คือข้อความที่เขียนไว้ให้มนุษย์อ่าน ตัวแปลภาษาข้ามมันไปทั้งหมด (นี่คือเหตุผลที่ต้องรู้จัก `//` ในหัวข้อ 4)

และสังเกต**ตำแหน่ง `บรรทัด:คอลัมน์`** — token แรกของบรรทัดที่ 2 อยู่ที่ `2:1` (บรรทัด 2 คอลัมน์ 1) เพราะ lexer ติดตามว่าตอนนี้เราอ่านถึงบรรทัดไหน คอลัมน์ไหนอยู่ตลอด

**ตัวอย่าง 3 — เงื่อนไข + บล็อก (3 บรรทัด):**

```
  3 | if y > 10 { print y; }

token ทั้งหมด 30 ตัว — ตารางข้างล่างแสดงเฉพาะ 10 ตัวท้าย (ตัวที่ 21–30) เพราะ 20 ตัวแรก
(บรรทัด 1–2) เหมือนกับตัวอย่าง 2 ทุกประการ:

 21  3:1    IF        "if"
 22  3:4    IDENT     "y"
 23  3:6    GT        ">"
 24  3:8    NUMBER    "10"
 25  3:11   LBRACE    "{"
 26  3:13   PRINT     "print"
 27  3:19   IDENT     "y"
 28  3:20   SEMI      ";"
 29  3:22   RBRACE    "}"
 30  3:23   EOF       ""
```

รวมทั้งสามตัวอย่างได้ **60 token** (ผลด้านบนมาจากโปรแกรม 04)

นอกจากนี้ โปรแกรม 03 ยังยืนยันอีกชั้นว่าตำแหน่ง `บรรทัด:คอลัมน์` ของทั้ง 60 token **คำนวณซ้ำเองแล้วตรง 0 จุด** — คือไม่ได้เชื่อผลของ lexer เอง แต่คำนวณจากซอร์สโค้ดตรง ๆ แล้วเทียบกัน

จุดที่ต้องเน้นให้เห็นชัด: ดู "สตรีมแบบอ่านเร็ว" ของตัวอย่าง 2 จะเห็นว่า token เรียงกันเป็นลำดับแบน ๆ แบบนี้:

- **ไม่มีต้นไม้ ไม่มีโครงสร้าง** — แค่ `LET IDENT ASSIGN NUMBER PLUS ...` เรียงยาวเป็นเส้นเดียว
- นี่แหละคือสิ่งที่ lexer มอบให้ parser **และแค่นั้น**
- ปัญหาอย่าง "คูณก่อนบวกไหม", "วงเล็บจับกลุ่มยังไง", "บล็อก `{ }` ครอบอะไร" — lexer ตอบไม่ได้เลย มันไม่รู้จักไวยากรณ์

## 7. เมื่อเจออักขระที่รู้จักไม่ได้ — error ต้องบอก "ตรงไหน" และ lexer ต้อง "เดินต่อได้"

ก่อนลงรายละเอียด error ขอวาง**ภาพรวมหนึ่งรอบของ lexer** ไว้ตรงนี้ก่อน — ฟังก์ชันที่คืนคำทีละคำชื่อ `Next()` (อ่านว่า "เน็กซ์"): เรียกครั้งหนึ่งก็คืน token หนึ่งตัว เดินหน้าหนึ่งก้าว เรียกซ้ำไปเรื่อย ๆ จนกว่าจะคืน `EOF`

![วงจรการทำงานของ lexer ทีละหนึ่งคำ](/assets/diagrams/ep26-03-lexer-loop.svg)

ทุกครั้งที่เรียก `Next()` มันทำเหมือนเดิม: ข้ามช่องว่าง/คอมเมนต์ → ดูตัวอักษรที่ชี้อยู่ → เลือกอ่านตามชนิด (ตัวเลข/ชื่อ/เครื่องหมาย) → คืน token หนึ่งตัว → วนกลับเริ่มใหม่ ภาพนี้รวมเส้นทาง error ไว้ด้วย ซึ่งคือเรื่องของหัวข้อนี้พอดี

ภาษาจริง ๆ ไม่ได้มีแต่โค้ดที่เขียนถูกเสมอไป — ผู้ใช้พิมพ์ผิดบ้าง พิมพ์อักษรที่ภาษาไม่มีบ้าง lexer จึงต้องรู้จัก "ความผิด" และรายงานมันอย่างมีประโยชน์ (โปรแกรม `05_lexer_errors`)

ข้อกำหนดสองข้อที่ error ของ lexer ต้องทำได้:

**ข้อ 1 — ต้องบอกตำแหน่งที่ผิด** ผลจริงจาก lexer ของเรา:

```
[1] อินพุต : "@"
    error  : line 1, column 1: unexpected character '@'   ← (= เจอตัวอักษรที่ภาษาไม่รู้จัก)
[3] อินพุต : "99999999999999999999"
    error  : line 1, column 1: number too large to fit in an int: 99999999999999999999
[5] อินพุต : "let x = 1;\nlet y = @;"   ← (\n = ขึ้นบรรทัดใหม่)
    error  : line 2, column 9: unexpected character '@'
```

เคส [5] สำคัญมาก: ผิดอยู่ที่**บรรทัดที่ 2** — lexer ต้องนับบรรทัด/คอลัมน์ถูกตลอดทาง (ข้ามบรรทัดที่ 1 ที่เขียนถูกไปแล้ว) ถึงจะชี้ตำแหน่งผิดถูก

**ข้อ 2 — ต้อง "เดินต่อได้" (recovery)** ดูผลนี้:

```
-- B) อ่านรอบเดียวเก็บ error ได้หลายจุด --
  อินพุต:
    1 | let x = 1 @ 2;
    2 | let y = 3 # 4;
    3 | !
  เก็บ error ได้ 3 จุด ในการอ่านรอบเดียว:
    1) line 1, column 11: unexpected character '@'
    2) line 2, column 11: unexpected character '#'
    3) line 3, column 1: expected '=' after '!'
```

lexer อ่านไฟล์**รอบเดียว** แต่เจอและรายงานความผิดได้ถึง 3 จุดในคราวเดียว — เพราะมันมี "สัญญา" หนึ่งข้อ: **ถ้าคืน error แปลว่าตัวอักษรที่ทำให้ผิดถูก "กิน" ไปแล้ว และตำแหน่งเดินหน้าแล้ว** เรียกซ้ำได้เลยเพื่อหาจุดผิดถัดไป นี่คือสิ่งที่ตัวแปลภาษาจริง (Go, gcc, clang — gcc และ clang คือตัวแปลภาษา C ที่ใช้กันทั่วไป) ทำ เพื่อให้เรากด **compile** (compile = สั่งให้ตัวแปลภาษาแปลงโค้ดเป็นโปรแกรม) แล้วเห็น error หลายจุดในครั้งเดียว แทนที่จะเจอทีละจุดแก้ทีละจุด

แล้วทำไมสัญญานี้ถึงสำคัญ? เพราะถ้า lexer **ลืม**ขยับนิ้วตอน error — โปรแกรมที่วนหาความผิดจะ**วนไม่จบ** (loop ไม่มีวันหยุด) โปรแกรม 05 สาธิตกับดักนี้ให้เห็นจริง:

```
-- C) กับดัก: lexer ที่ลืมขยับนิ้ว เมื่อ error --
  อินพุต: "@@"  · ลองอ่านซ้ำโดยมีเพดาน 5 รอบ (กันโปรแกรมค้าง):
    รอบ 1: pos 0: unexpected character "@"   ← ตำแหน่งยังเป็น pos 0 เหมือนเดิม
    รอบ 2: pos 0: unexpected character "@"   ← ตำแหน่งยังเป็น pos 0 เหมือนเดิม
    ... (ซ้ำอีก 3 รอบที่ pos 0)
```

error เดิมซ้ำห้ารอบ ตำแหน่งไม่ขยับเลย — โปรแกรมจริงจะค้างเป็นอนันต์ ทางแก้คือ**เติมแค่บรรทัดเดียว**ก่อนคืน error: ขยับนิ้วไปหนึ่งตัว (`i++`) ตรงนี้คือกับดักที่โปรแกรมเมอร์เจอได้จริงบ่อยมาก และเราอยากให้เห็นกับตาก่อนจะไปเขียนเอง

## 8. เส้นแบ่งงาน: สิ่งที่ lexer "ไม่" ผิด แต่ parser จะผิด

ปิดท้ายเนื้อหาด้วยการวาดเส้นแบ่งให้ชัด เพื่อไม่ให้สับสนว่า lexer รับผิดชอบแค่ไหน (โปรแกรม 05 ส่วน D):

```
-- D) เคสที่ lexer ไม่ผิด แต่ parser จะผิด --
  "x <= 5" → lexer: IDENT(x) LT(<) ASSIGN(=) NUMBER(5) EOF()
  "1 + * 3" → lexer: NUMBER(1) PLUS(+) STAR(*) NUMBER(3) EOF()
```

เคสแรก `x <= 5` — ภาษาจิ๋วของเรายัง**ไม่มี**เครื่องหมาย `<=` ในสเปก lexer จึงตัดได้ `LT` (คือ `<`) กับ `ASSIGN` (คือ `=`) แยกกันสองตัว แล้ว lexer ก็**ไม่ถือว่าผิด** เพราะมันดูแค่คำ ส่วนการที่ `<=` ควรเป็นเครื่องหมายเดียว ไม่ใช่สองเครื่องหมายเรียงกัน เป็นเรื่องของ parser

เคสที่สอง `1 + * 3` — เรียงคำไม่เป็นประโยค (มี `+` ตามด้วย `*` ติดกัน) แต่ lexer ดูแค่คำ ไม่ดูไวยากรณ์ จึงไม่ผิด

**ทั้งสองเคส parser (ตอนที่ 27) จะเป็นคนบอกว่า "ไวยากรณ์ผิด"** พร้อมชี้ตำแหน่ง token ที่ทำให้ผิด — เพราะ parser คือชั้นถัดไปที่ "ดูการเรียงลำดับของคำ" ไม่ใช่ "ดูว่าคำแต่ละคำคืออะไร"

จำภาพนี้ไว้ให้แม่น: **lexer รู้จักคำ (token) แต่ไม่รู้จักประโยค (ไวยากรณ์/grammar)** — ประโยคเป็นเรื่องของ parser

### ระดับ Drill (ฝึกมือ)

1. ตัดข้อความ `let total = 10 - 3;` ด้วยมือ — จะได้ token ทั้งหมดกี่ตัว (รวม EOF)? แต่ละตัวชนิดอะไร อยู่บรรทัด:คอลัมน์ไหนบ้าง? (เฉลยตรวจได้จาก `out/07_drill_answer.out.txt`)
2. อธิบายด้วยคำพูดตัวเองว่า ทำไม lexer ถึงตัด `1 + * 3` ผ่านทั้งที่มันผิดไวยากรณ์ — หน้าที่จับผิดตรงนี้เป็นของใคร?
3. ต่างกันตรงไหน ระหว่าง `x = = 1` กับ `x == 1` — ทั้งสองแบบตัดได้ token คนละกี่ตัว และชนิดต่างกันตรงไหน? (ใบ้: ย้อนดูหัวข้อ 4 เรื่อง peek)
4. `12 + 345` ตัดได้กี่ token? ทำไมถึงเป็นตัวเลข 2 ตัว ไม่ใช่ 5 ตัว?

### Mini-project (ต่อยอดจากโปรแกรม 02 และ internal/lexer)

ก่อนเริ่ม รู้จักโครงไฟล์ที่ต้องแตะ: **`internal/lexer/lexer.go`** = ตัวตัดคำ (มีฟังก์ชัน `Next()` ที่คืนคำทีละตัว) · **`internal/lexer/spec.go`** = ตารางสเปก · รันทุกโปรแกรมพร้อมกันด้วย `./run_all.sh`

ภาษาจิ๋วของเราตอนนี้ยังไม่มีเครื่องหมาย `<=` (น้อยกว่าหรือเท่ากับ) และ `>=` (มากกว่าหรือเท่ากับ) — จากหัวข้อ 8 เราเห็นแล้วว่า `x <= 5` ถูกตัดเป็น `LT` กับ `ASSIGN` แยกกัน ซึ่งไม่ถูกต้อง

ให้**เพิ่ม** token ชนิดใหม่ 2 ตัว (`LTE` สำหรับ `<=` และ `GTE` สำหรับ `>=`) เข้าไปใน `internal/lexer/lexer.go` โดยใช้หลักการ peek แบบเดียวกับ `==` (เห็น `<` → แอบดูว่าถัดไปเป็น `=` ไหม) แล้ว:

1. เพิ่มเคสใน `switch` ของ `Next()` สำหรับ `<` และ `>` (ตอนนี้ `case '<':` กับ `case '>':` ตัดเป็น LT/GT ทันทีโดยไม่ peek — ต้องแก้ให้ peek ก่อน)
2. เพิ่ม `LTE` `GTE` ลงในสเปกกลุ่ม OPERATOR ใน `spec.go` (อัปเดตฟิลด์ `Pattern` = กฎการอ่าน และ `Example` = ข้อความตัวอย่างที่ทำให้เกิดชนิดนั้น) — และ**เพิ่ม `lex.LTE` `lex.GTE` ในลิสต์ `all` ของ `03_lexer_spec/main.go` ด้วย** ไม่งั้นตารางนับชนิดในส่วน B จะยังนับแค่ 23 ชนิดและไม่โผล่ชนิดใหม่
3. **อย่าลืมแก้โปรแกรม 02 ด้วย** — ฟังก์ชัน `decision()` ใน `02_lexer_peek/main.go` มีตารางตัดสินใจแบบมือของตัวเอง (`case '<': return "LT", ...` ไม่มี peek) ต้องเพิ่ม peek ที่ `<` และ `>` ให้ตรงกับ lexer จริง มิฉะนั้นชั้น B ของโปรแกรม 02 จะรายงาน "ไม่ตรง" แทนที่จะเป็น 8/8
4. **อัปเดตข้อความสรุปในโปรแกรม 05 ส่วน D ด้วย** — หลังเพิ่ม `<=` แล้ว ข้อความ "ภาษาจิ๋วยังไม่มี '<=' ในสเปก" จะกลายเป็นข้อความเก่า ต้องแก้ให้ตรง (เช่นชี้ว่า `<=` ตอนนี้เป็น LTE ตัวเดียวแล้ว)
5. รัน `./run_all.sh` แล้วเช็คว่าโปรแกรม 03 ยังตรวจสเปกผ่าน 5/5 (ตอนนี้ส่วน B ควรนับได้ 25 ชนิด และ "ยังไม่ถูกใช้" เพิ่มเป็น 9 ชนิด), ตรวจว่า `x <= 5` กลายเป็น `IDENT(x) LTE(<=) NUMBER(5)` แทนที่จะเป็น LT+ASSIGN แยกกัน
