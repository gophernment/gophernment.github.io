สี่ตอนที่ผ่านมาเราปูเรื่อง type กันมาครบแล้ว ตั้งแต่พื้นฐานยัน generics และ narrowing ต่อจากนี้คือครึ่งหลังของซีรีส์ — **การเขียน test** ซึ่งเป็นเหตุผลที่เราอุตส่าห์เรียน type กันมาทั้งหมด

แต่ก่อนจะข้ามไปติดตั้งเครื่องมือ ผมอยากให้เราหยุดคุยกันเรื่อง "ทำไม" และ "เขียนยังไงให้คุ้ม" ก่อน เพราะคนส่วนใหญ่เขียน test กันแบบส่ง ๆ โดยไม่เข้าใจหลักการ แล้วสุดท้ายก็เลิกเขียนเพราะรู้สึกว่าเสียเวลา

## ทำไมต้องเขียน test

เหตุผลหลักมีสามข้อ และมันไม่เกี่ยวกับ "เป็นคนดี" เลย — มันเป็นเรื่องการทำงานจริงล้วน ๆ

**ข้อแรก — ความมั่นใจตอนแก้โค้ด** ตอนแก้บั๊กหรือ refactor โค้ด (ปรับโครงสร้างภายในให้ดีขึ้นโดยไม่เปลี่ยนพฤติกรรม) ถ้าไม่มี test คุณจะไม่รู้ว่าที่แก้ไปพังส่วนอื่นไหม ต้องมานั่งไล่คลิกเองทุกหน้า แต่ถ้ามี test ที่ครอบคลุม พอแก้เสร็จแค่รัน `bun test` แล้วรอดูว่ามีตัวไหนแดงบ้าง

**ข้อสอง — test คือเอกสารที่มีชีวิต** โค้ดบอกว่า "มันทำอะไร" แต่ test บอกว่า "มันควรทำอะไร" — อ่าน test จะเห็นเจตนาของคนเขียนชัดกว่าอ่านโค้ดเป็นพันบรรทัด เพราะ test แสดงตัวอย่างการใช้งานจริง

**ข้อสาม — กันบั๊กกลับมา** บั๊กที่เคยแก้แล้ว ถ้าไม่มี test คอยดัก มันจะกลับมาอีกในอนาคต (โค้ดเก่าถูกแก้โดยคนใหม่ที่ไม่รู้ที่มา) test คือกำแพงกันไม่ให้บั๊กเดิมย้อนคืน

## Test Pyramid: เขียนอะไร เยอะแค่ไหน

แนวคิดที่ใช้กันแพร่หลายที่สุดคือ **test pyramid** — รูปพีระมิดที่แบ่ง test ตาม "ต้นทุน vs ความเร็ว"

```
        ▲
       / \
      / e2e \        ← น้อยสุด ช้าสุด แพงสุด (จำลองผู้ใช้จริง)
     /-------\
    / integ.  \      ← ปานกลาง (เชื่อมหลายส่วนเข้าด้วยกัน)
   /-----------\
  /    unit      \   ← เยอะสุด เร็วสุด ถูกสุด (ฟังก์ชันเดี่ยว)
 /-----------------\
```

**ชั้นล่างสุด — Unit test** คือการทดสอบฟังก์ชันหรือ component เดี่ยว ๆ แบบแยกส่วน ไม่มี dependency ภายนอก เร็วมาก (รันพันตัวในหลักวินาที) และเขียนง่าย จึงควรมีมากที่สุด

**ชั้นกลาง — Integration test** ทดสอบว่าหลายส่วนทำงานร่วมกันได้ เช่น component + ฐานข้อมูล + API จริง เชื่อมเข้าด้วยกัน

**ชั้นบนสุด — E2E (End-to-End) test** จำลองผู้ใช้จริงกดปุ่มผ่าน browser จริง ตรวจว่าทั้งระบบทำงานตั้งแต่ต้นจนจบ ช้าที่สุดและแพงที่สุด จึงควรมีน้อยสุด แต่ดักบั๊กระดับ "ภาพรวมพัง" ที่ unit test มองไม่เห็น

หลักการง่าย ๆ คือ **ยิ่งขึ้นสูง ยิ่งแพง ยิ่งเขียนน้อย** — ส่วนใหญ่ทีมจะเขียน unit test เยอะสุด แล้วไล่ขึ้นไปตามความสำคัญ

## Test ที่ดีหน้าตาเป็นยังไง

ก่อนเขียนจริง ขอย้ำคุณสมบัติของ test ที่ดีสักสี่ข้อ

1. **รันเร็ว** — ถ้า test ตัวเดียวใช้เวลาเป็นนาที คุณจะไม่รันมันบ่อย และ test ที่ไม่ค่อยรันก็ไร้ค่า
2. **เป็นอิสระ** — test แต่ละตัวต้องรันแยกกันได้ ไม่ขึ้นกับลำดับหรือ state จากการรันก่อนหน้า
3. **ตรวจพฤติกรรม ไม่ใช่ implementation** — เขียน test ว่าระบบ "ทำอะไร" (ผลลัพธ์) ไม่ใช่ "ทำยังไง" (ภายใน) ไม่งั้นแค่ refactor ภายใน test ก็พังทั้งที่พฤติกรรมยังถูก
4. **อ่านแล้วรู้ว่ามันเช็คอะไร** — ชื่อ test ควรเป็นประโยคบอกเจตนา เช่น `should return error when email is invalid`

## เครื่องมือที่เราจะใช้

ในสามตอนสุดท้าย เราจะใช้เครื่องมือสองตัวนี้ (ทั้งคู่ใช้ TypeScript ได้เต็มที่)

**Playwright** — สำหรับ e2e test จำลองเบราว์เซอร์จริง คลิก พิมพ์ รอดูผล เหมือนมีหุ่นยนต์มานั่งเทสต์เว็บให้ ใช้ test ว่า "ทั้งระบบทำงานร่วมกันได้จริง"

**Vitest** — สำหรับ unit test รันเร็ว ใช้กับโค้ดและ component ระดับย่อย (มี React Testing Library ช่วยทดสอบ component)

ตอนหน้าเราจะเริ่มลงมือจริง — ติดตั้ง Playwright และเขียน e2e test ตัวแรก ซึ่งจะได้ใช้ type กับ discriminated union ที่เรียนมาในตอนที่แล้วด้วย
